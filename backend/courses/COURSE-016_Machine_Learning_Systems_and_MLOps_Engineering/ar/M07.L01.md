## 1. النشر يعني جعل Model قابلًا للتشغيل والوصول (Deployment means making the model runnable and accessible)

أثناء التطوير، يعمل ML model عادةً داخل بيئة Development. ينقل Deployment الـ Model خارج هذه البيئة حتى يتمكن نظام آخر أو مستخدم نهائي من استخدامه فعليًا.

قد ينتقل Model أولًا إلى **Staging** للاختبار، ثم إلى **Production** للاستخدام الحقيقي.

يؤكد الفصل أن Production ليس حالة واحدة ثابتة، بل طيف. ففي أحد طرفيه، قد يعني Production توليد Outputs مفيدة لفريق أعمال داخلي. وفي الطرف الآخر، قد يعني خدمة ملايين المستخدمين بزمن استجابة بالمللي ثانية ودرجة Uptime مرتفعة جدًا.

بالنسبة إلى Demo بسيط، قد يبدو Deployment هكذا:

```text
طلب العميل (Client request)
      ↓
واجهة التنبؤ (Prediction API)
      ↓
Model محمّل (Loaded model)
      ↓
استجابة التنبؤ (Prediction response)
```

لكن هذا المخطط يخفي الأجزاء الصعبة في Production:

- التوسع لخدمة عدد كبير من المستخدمين،
- الحفاظ على Latency مقبول،
- إبقاء الخدمة متاحة،
- اكتشاف الأعطال،
- تنبيه الأشخاص المناسبين،
- Debugging للأعطال،
- نشر تحديثات Model بأمان.

يثبت Web endpoint صغير فقط أن Model يمكن استدعاؤه. لكنه لا يثبت أن النظام يستطيع العمل بموثوقية على نطاق Production.

## 2. تصدير Model يفصل Training عن Serving (Model export separates training from serving)

قد لا يشغّل فريق Deployment الـ Model داخل Framework أو البيئة نفسها المستخدمة أثناء التطوير. وقد يحتاج Model إلى **Export** بصيغة تستطيع Application أخرى تحميلها.

يصف المصدر جزأين أساسيين يجب تمثيلهما:

1. **تعريف Model (model definition)** — بنية Model،
2. **قيم Parameters (parameter values)** — القيم التي تعلّمها Model داخل هذه البنية.

وعادةً ما يتم Export لهذين الجزأين معًا.

يعرض الفصل أمثلة مثل TensorFlow SavedModel وONNX export من PyTorch.

يقود ذلك إلى مبدأ هندسي مهم:

> يجب أن تؤثر الطريقة التي سيُقدَّم بها Model في كيفية تطويره.

قد يكون Model غير مناسب حتى لو كان Offline metric ممتازًا، إذا لم يستطع تلبية قيود Hardware المستهدف أو Latency أو Export.

## 3. أربع خرافات عن النشر (Four deployment myths)

### الخرافة 1: أنت تنشر Model واحدًا أو اثنين فقط (Myth 1: You only deploy one or two models)

قد تعتمد Applications حقيقية على عدد كبير من Models.

قد يستخدم نظام Ride-sharing Models منفصلة من أجل:

- الطلب على الرحلات (ride demand)،
- توافر السائقين (driver availability)،
- وقت الوصول المتوقع (estimated arrival time)،
- التسعير الديناميكي (dynamic pricing)،
- اكتشاف الاحتيال (fraud detection)،
- التنبؤ بالتسرب (churn prediction).

يمكن لاختلاف البلدان أو المنتجات أو اللغات أو مجموعات المستخدمين أن يضاعف العدد أكثر. وقد تفشل Infrastructure المصممة لـ Model واحد فقط في دعم Portfolio حقيقي داخل Production.

### الخرافة 2: يظل الأداء كما هو إذا لم نفعل شيئًا (Myth 2: Performance stays the same if we do nothing)

تتغير Production data. وقد يواجه Model تم تدريبه على Distribution الأمس Distribution مختلفة لاحقًا.

يصف الفصل ذلك باستخدام **Data distribution shift**، ويشير إلى أن Models غالبًا ما تحقق أفضل أداء بعد Training مباشرة، ثم يتراجع الأداء مع تغير العالم.

### الخرافة 3: نادرًا ما تحتاج Models إلى تحديثات (Myth 3: Models rarely need updates)

السؤال الأكثر فائدة ليس فقط "كم مرة ينبغي تحديث Model؟" بل "ما مدى سرعة المؤسسة في تحديثه بأمان عند الحاجة؟"

تصبح سرعة Iteration مهمة عندما تتغير Data أو السلوك بسرعة.

### الخرافة 4: معظم ML engineers لا يحتاجون إلى الاهتمام بالحجم (Myth 4: Most ML engineers do not need to care about scale)

لا يعني Scale شركات بحجم الإنترنت فقط. فقد تؤدي مئات Queries في الثانية، أو ملايين المستخدمين، أو كثرة Models المنشورة، أو أهداف Latency الصارمة، كلها إلى متطلبات Scalability.

## 4. ثلاثة أنماط للتنبؤ يجب تذكرها (Three prediction modes to remember)

يعترف الفصل بأن مصطلحات الصناعة قد تكون غير متسقة. وأفضل Mental model هو تذكر ثلاثة أوضاع تشغيل:

1. **Batch prediction باستخدام Batch features**
2. **Online prediction باستخدام Batch features**
3. **Online prediction باستخدام كل من Batch features وStreaming features**

يُسمى الوضع الثالث أحيانًا **Streaming prediction**.

هذا التمييز مهم لأن توقيت Prediction وحداثة Features خياران تصميميان مختلفان.

## 5. مقارنة Batch prediction وOnline prediction

### التنبؤ عبر Online prediction

يولد Online prediction نتيجة بمجرد وصول Request.

مثال:

```text
يرسل المستخدم نصًا (User submits text)
      ↓
طلب تنبؤ (Prediction request)
      ↓
تشغيل Model الآن (Model runs now)
      ↓
إرجاع التنبؤ فورًا (Prediction returned immediately)
```

يُسمى Online prediction أيضًا **On-demand prediction**. وعند تنفيذه عبر Request-response APIs مباشرة، يوصف غالبًا بأنه Synchronous prediction.

### التنبؤ عبر Batch prediction

يولد Batch prediction تنبؤات دوريًا أو عند Trigger. ويتم تخزين النتائج ثم استرجاعها لاحقًا عندما يحتاج إليها المستخدمون أو Applications.

مثال:

```text
كل 4 ساعات (Every 4 hours):
ولّد توصيات لعدد كبير من المستخدمين (Generate recommendations for many users)
      ↓
خزّن التوصيات (Store recommendations)
      ↓
يزور المستخدم لاحقًا (User visits later)
      ↓
استرجع النتيجة المخزنة (Fetch stored result)
```

يوصف Batch prediction غالبًا بأنه Asynchronous لأن توليد Prediction غير متزامن مع User request.

### المفاضلة الرئيسية (Main trade-off)

| البعد | التنبؤ الدفعي (Batch prediction) | التنبؤ عند الطلب (Online prediction) |
|---|---|---|
| متى تُولَّد Predictions | دوريًا / عند Trigger | عند وصول Requests |
| هدف التحسين الرئيسي | Throughput مرتفع | Latency منخفض |
| الحالة المناسبة | لا يلزم أن تعكس النتائج أحدث Event فورًا | النتيجة مطلوبة فورًا |
| الاستجابة للسلوك الحديث | أقل | أعلى |
| الحاجة إلى توقّع Requests مسبقًا | نعم عادةً | لا |

## 6. ميزات Batch وOnline وStreaming (Batch features, online features, and streaming features)

نمط Prediction ونوع Feature ليسا الشيء نفسه.

تأتي **Batch features** من Historical data تتم معالجتها دوريًا.

مثال:

- متوسط وقت تحضير مطعم خلال الشهر الماضي (mean preparation time).

يتم حساب **Streaming features** من Events الواردة في Near real time.

أمثلة:

- عدد الطلبات خلال آخر 10 دقائق (number of orders)،
- عدد عمال التوصيل المتاحين حاليًا (number of delivery workers currently available).

**Online features** هي أي Features تُستخدم في Online prediction. ويمكن أن تشمل كلًا من Batch features وStreaming features.

على سبيل المثال، يمكن أن يكون Item embedding المحسوب مسبقًا Batch feature مخزنًا للاستخدام لاحقًا. وإذا تم استرجاعه أثناء Online prediction request، فهو Online feature لكنه **ليس** Streaming feature.

وهذا يعطينا ثلاث حالات مفيدة:

```text
التنبؤ الدفعي (Batch prediction):
ميزات Batch (batch features) → استدلال دوري (periodic inference) → تنبؤات مخزنة (stored predictions)

التنبؤ Online باستخدام Batch features (Online prediction with batch features):
ميزات Batch مخزنة/محسوبة مسبقًا → استدلال وقت الطلب (request-time inference)

التنبؤ Streaming (Streaming prediction):
ميزات Batch + ميزات Streaming حديثة → استدلال وقت الطلب (request-time inference)
```

## 7. الاختيار بين Batch prediction وOnline prediction

يكون Batch prediction مفيدًا عندما تحتاج إلى عدد كبير من Predictions ولا تحتاجها فورًا.

ويمكنه أيضًا إخفاء بطء Inference: فبدلًا من جعل المستخدم ينتظر Model معقدًا، احسب Predictions مسبقًا واجعل Serving عبارة عن Lookup سريع.

لكن Batch prediction له قيود مهمة.

### قد يهدر Compute

إذا كانت نسبة صغيرة فقط من المستخدمين تزور المنتج كل يوم، فإن حساب Predictions يومية للجميع يهدر العمل على المستخدمين غير النشطين.

### قد تصبح النتائج قديمة (Stale)

قد لا تعكس Recommendation تم توليدها قبل ساعات ما يفعله المستخدم الآن.

### يتطلب Requests يمكن توقعها

يمكن حساب Movie recommendations مسبقًا لمستخدمين معروفين. لكن Requests ترجمة عشوائية لا يمكن توقعها بالكامل مسبقًا.

### بعض Applications تتطلب قرارات فورية

يسرد الفصل أمثلة مثل:

- التداول عالي التردد (high-frequency trading)،
- المركبات ذاتية القيادة (autonomous vehicles)،
- المساعدات الصوتية (voice assistants)،
- فتح القفل بالقياسات الحيوية (biometric unlocking)،
- اكتشاف السقوط (fall detection)،
- اكتشاف الاحتيال (fraud detection).

يكون Fraud prediction بعد ثلاث ساعات من Transaction أقل فائدة من Prediction يستطيع منع Transaction قبل اكتمالها.

### الأنظمة الهجينة (Hybrid systems)

يمكن أن يتعايش Batch prediction وOnline prediction. فقد تحسب النتائج مسبقًا لـ Requests الشائعة أو القابلة للتوقع، وتشغّل Model عبر Online للـ Requests طويلة الذيل أو غير المتوقعة.

## 8. ما الذي يتطلبه Online prediction؟

يتطلب الانتقال نحو Online prediction قدرتين رئيسيتين.

### 1. Data pipeline شبه لحظي (Near-real-time data pipeline)

يجب على النظام Ingest للبيانات الواردة، وحساب Streaming features المطلوبة، وJoin بينها وبين Features أخرى، وإتاحتها بسرعة.

### 2. Model سريع بما يكفي (Sufficiently fast model)

يجب على Model إنتاج Prediction داخل Latency budget الذي يتوقعه المستخدم أو النظام اللاحق. وبالنسبة إلى كثير من Consumer applications، يعني ذلك أجزاء من الثانية.

Model سريع مع Feature pipeline بطيء لا يصنع Prediction service سريعًا. وبالمثل، لا يستطيع Streaming pipeline سريع تعويض Model يتجاوز Inference time الخاص به Latency budget للمنتج.

## 9. عدم اتساق Training-serving pipeline (Training-serving pipeline inconsistency)

يظهر Bug مهم في Production عندما يحسب Training وInference الـ Feature نفسها عبر Code paths مختلفة.

فكّر في Feature لتقدير ETA للمسار:

> متوسط سرعة السيارات على المسار خلال آخر خمس دقائق.

أثناء Training، قد تتم معالجة Historical data داخل DataFrame على Batch كبير. وأثناء Production inference، قد يتم تحديث Feature نفسها باستمرار باستخدام Sliding window على Event stream.

من حيث المفهوم، Feature هي نفسها. لكن من حيث التشغيل، يتم تنفيذها مرتين.

يؤدي ذلك إلى Failure mode:

```text
يتغير Training pipeline (Training pipeline changes)
         ↓
لا يتم تحديث Serving pipeline بالطريقة نفسها (Serving pipeline is not updated identically)
         ↓
يحسب Training وProduction قيم Features مختلفة (Training and production compute different feature values)
         ↓
يرى Model تعريف Input مختلفًا في Production (Model sees a different input definition in production)
```

يمكن أن تجعل ملكية الفرق المنفصلة المشكلة أسوأ لأن التغييرات يجب تنسيقها عبر حدود المؤسسة.

يصف الفصل جهود الصناعة لتوحيد Batch processing وStream processing، ويشير إلى أن Feature stores يمكن أن تساعد في الحفاظ على الاتساق بين Features المستخدمة في Training وتلك المستخدمة في Prediction.

## 10. ضغط Model من أجل Inference أسرع وأصغر (Model compression for faster, smaller inference)

إذا كان Model بطيئًا جدًا في Serving، يعرض الفصل ثلاثة اتجاهات عامة:

1. جعل تنفيذ Inference أسرع،
2. جعل Model أصغر،
3. استخدام Hardware أسرع.

يركز **Model compression** على تقليل حجم Model. وغالبًا ما تقلل Models الأصغر أيضًا Inference latency ومتطلبات Memory.

يسلط الفصل الضوء على أربع عائلات رئيسية من Compression:

- التفكيك منخفض الرتبة (Low-rank factorization)،
- تقطير المعرفة (Knowledge distillation)،
- التقليم (Pruning)،
- Quantization.

## 11. أربع تقنيات لضغط Model (Four model-compression techniques)

### التفكيك منخفض الرتبة (Low-rank factorization)

الفكرة الأساسية هي استبدال Tensors عالية الأبعاد أو Operations المكلفة ببنى منخفضة الأبعاد تقرّب الحساب نفسه.

يستخدم الفصل Compact convolutional filters كمثال. ويمكن لـ MobileNet-style depthwise and pointwise convolutions خفض عدد Parameters بشكل كبير مقارنةً بـ Full convolution.

المفاضلة هي التخصص: غالبًا ما تتطلب هذه الأساليب معرفة بالـ Architecture وقد تنطبق فقط على عائلات Models معينة.

### تقطير المعرفة (Knowledge distillation)

يتم تدريب Model أصغر يسمى **Student** ليحاكي Model أكبر يسمى **Teacher** أو Ensemble.

```text
Model المعلّم الكبير (Large teacher model)
       ↓ يعلّم (teaches)
Model الطالب الصغير (Small student model)
       ↓ نشر (deploy)
خدمة التنبؤ (Prediction service)
```

يعرض المصدر DistilBERT كمثال على Model أصغر صُمم للاحتفاظ بكثير من قدرات BERT الأكبر مع التشغيل بسرعة أعلى.

يتميز Distillation بالمرونة لأن Teacher وStudent لا يلزم أن يستخدما Architecture نفسها. لكنه يعتمد على وجود Teacher مفيد.

### التقليم (Pruning)

يزيل Pruning أو يعطّل مكونات Model التي تسهم بدرجة قليلة.

بالنسبة إلى Neural networks، قد يعني ذلك:

- إزالة Nodes أو Structures كاملة،
- أو تعيين Weights منخفضة القيمة إلى صفر لإنشاء Sparsity.

يمكن أن تحتاج Sparse models إلى Storage أقل، وقد تعمل بكفاءة أعلى عندما يستطيع Hardware وRuntime الاستفادة من Sparsity.

### Quantization

يستخدم Quantization عددًا أقل من Bits لتمثيل Parameters وأحيانًا Activations.

مثال توضيحي للـ Memory:

```text
100 million parameters × 32 bits ≈ 400 MB — تمثيل Parameters بدقة 32-bit
100 million parameters × 16 bits ≈ 200 MB — تمثيل Parameters بدقة 16-bit
100 million parameters ×  8 bits ≈ 100 MB — تمثيل Parameters بدقة 8-bit
```

يمكن للدقة الأقل أن تقلل Memory usage وتزيد سرعة Computation.

المفاضلة هي Numerical error: فالتمثيلات الأصغر تملك Precision أقل وRepresentable range أصغر. وقد يؤدي Rounding أو Scaling السيئ إلى خفض جودة Model.

يمكن أن يحدث Quantization أثناء Training أو بعد Training من أجل Inference.

## 12. مقارنة Cloud inference وEdge inference

يجب أن يعمل Model المنشور في مكان ما.

يُشغّل **Cloud inference** معظم Computation على Remote servers.  
ويُشغّل **Edge inference** جزءًا كبيرًا مباشرة على أجهزة المستخدم أو Embedded devices.

يمكن أن تشمل Edge devices:

- المتصفحات (browsers)،
- الهواتف (phones)،
- أجهزة الكمبيوتر المحمولة (laptops)،
- الساعات الذكية (smartwatches)،
- السيارات (cars)،
- الكاميرات (cameras)،
- الروبوتات (robots)،
- الأجهزة المضمنة (embedded devices)،
- وحدات FPGA وASIC.

### لماذا Cloud خيار جذاب؟

- أسهل للبدء (easier to get started)،
- Managed infrastructure متاحة على نطاق واسع،
- يمكن أن يكون Server hardware قويًا ويتم صيانته مركزيًا.

### لماذا Edge خيار جذاب؟

#### خفض تكلفة Cloud

يمكن لتنفيذ Computation أكثر على الجهاز أن يقلل الطلب على Server compute.

#### التشغيل دون اتصال (Offline operation)

يمكن لـ Edge applications العمل مع اتصال Internet غير موثوق أو غير موجود.

#### خفض Network latency

لا يحتاج Model إلى Network round trip لكل Prediction.

#### مزايا Privacy

يمكن أن تبقى Sensitive data على الجهاز بدلًا من إرسالها إلى Centralized servers.

### قيود Edge

تمتلك Edge devices موارد محدودة من:

- القدرة الحاسوبية (compute)،
- memory،
- البطارية أو الطاقة (battery or power)،
- Operators وRuntimes المدعومة.

قد يكون Model المناسب لـ Server GPU غير قابل للاستخدام على Phone أو Sensor.

## 13. التمثيلات الوسيطة تربط Frameworks بالـ Hardware (Intermediate representations bridge frameworks and hardware)

تعرض Hardware backends المختلفة Compute primitives وMemory layouts وCaches وفرص Optimization مختلفة.

إن دعم كل ML framework مباشرة على كل Hardware backend يخلق مشكلة هندسية Many-to-many مكلفة.

يمكن لـ Compiler تقديم **Intermediate representation (IR)**:

```text
Model داخل Framework عالي المستوى (High-level framework model)
          ↓
تمثيل وسيط عالي المستوى (High-level IR)
          ↓
تمثيلات وسيطة منخفضة المستوى (Lower-level IR(s))
          ↓
كود أصلي للـ Hardware (Hardware-native code)
```

يستهدف مطورو Frameworks الـ IR بدلًا من كل قطعة Hardware. ويدعم Hardware vendors الـ IR ومسار Compiler بدلًا من كل Framework.

غالبًا ما تسمى هذه العملية **Lowering** لأن Operations عالية المستوى تتحول تدريجيًا إلى Operations منخفضة المستوى ومخصصة للـ Hardware.

على المستوى العالي، يُمثل ML model غالبًا على هيئة **Computation graph** يصف Operators وترتيب تنفيذها.

[[IMAGE_NEEDED: Framework to hardware through intermediate representations | Several ML frameworks feeding a shared high-level IR, then lower-level IR, then branching to CPU, GPU, and accelerator machine code | Learner should notice how IRs reduce the need for every framework to directly support every hardware backend]]

## 14. تحسين Model بعد Compilation (Model optimization after compilation)

يمكن أن يكون Code قابلًا للتنفيذ على Hardware من دون أن يكون فعالًا على ذلك Hardware.

يحاول Optimization الاستفادة من Memory locality وCaches وVector operations وParallel execution وبنية Computation graph الكاملة.

يفصل الفصل بين **Local optimization** و**Global optimization**.

### التحسين المحلي (Local optimization)

تحسين Operator واحد أو مجموعة صغيرة من Operators.

#### المعالجة المتجهية (Vectorization)

معالجة عدة Elements متجاورة معًا بدلًا من Element واحد في كل Loop iteration.

#### التنفيذ المتوازي (Parallelization)

تقسيم العمل المستقل إلى Chunks يمكن تنفيذها في الوقت نفسه.

#### تقسيم الحلقات (Loop tiling)

إعادة ترتيب Memory access بحيث تستفيد Computation بصورة أفضل من Memory hierarchy وCache في Hardware المستهدف.

ولأن Hardware layouts تختلف، فقد لا يكون Access pattern الجيد لـ CPU جيدًا لـ GPU.

#### دمج العمليات (Operator fusion)

دمج عدة Operators حتى لا تحتاج Intermediate results إلى الكتابة إلى Memory ثم إعادة قراءتها مرارًا.

مثال توضيحي:

```text
بدون دمج (Without fusion):
قراءة Array → العملية A (op A) → كتابة (write)
قراءة Array → العملية B (op B) → كتابة (write)

مع الدمج (With fusion):
قراءة Array → op A + op B → كتابة مرة واحدة (write once)
```

### التحسين الشامل (Global optimization)

بدلًا من تحسين Operators معزولة، افحص Computation graph من البداية إلى النهاية وأعد تنظيم مناطق أكبر من Computation.

[[IMAGE_NEEDED: Operator fusion reduces memory traffic | A before/after diagram where two operators each read and write an intermediate tensor versus one fused operator that keeps the intermediate result local | Learner should notice that reducing memory movement can speed inference even if the mathematical operations are unchanged]]

## 15. استخدام ML لتحسين تنفيذ ML (Using ML to optimize ML execution)

قد يحتوي Computation graph على عدد كبير من Execution plans الصالحة.

ينشئ Engineers تقليديًا Hardware-specific heuristics لاختيار استراتيجيات تنفيذ سريعة. وقد تعمل هذه Heuristics جيدًا، لكن الفصل يبرز قيدين:

- قد تكون غير مثالية (nonoptimal)،
- وقد لا تتكيف جيدًا مع Models أو Hardware الجديدة.

غالبًا ما يكون اختبار كل Execution plan مستحيلًا لأن Search space ينمو Combinatorially.

وهذا يخلق فرصة لـ ML-assisted optimization.

### فكرة الضبط التلقائي (Autotuning idea)

يمكن للنظام البحث في Candidate implementations وقياس Execution time الحقيقي وتعلّم **Cost model** يتنبأ بالـ Candidates الواعدة مستقبلًا.

يصف الفصل autoTVM مفاهيميًا بهذه الخطوات:

1. تقسيم Graph إلى Subgraphs،
2. تقدير صعوبة أو حجم Search لكل Subgraph،
3. توزيع Search effort،
4. اختبار Candidate execution plans،
5. التعلم من Runtime المقاس،
6. دمج أفضل Implementations للـ Subgraphs.

يمكن أن يستغرق هذا Optimization ساعات أو أيامًا، لكنه في الأساس One-time cost لـ Model وHardware target محددين. وبعد ذلك يمكن Cache للنتيجة المحسنة وإعادة استخدامها عبر Deployments كثيرة على عائلة Hardware نفسها.

## 16. ML داخل المتصفحات وWebAssembly

يوفر Browser execution نوعًا آخر من Portability: فإذا استطاع Model العمل داخل Browser، فيمكنه العمل عبر أجهزة كثيرة دون استهداف Native hardware interface لكل جهاز مباشرة.

يمكن لـ JavaScript تشغيل ML logic، لكن الفصل يصفها بأنها محدودة في Computational workloads الثقيلة مقارنة بـ Native execution.

يوفر **WebAssembly (WASM)** هدف Browser execution أعلى أداءً.

مفاهيميًا:

```text
Model داخل ML framework (Model in ML framework)
        ↓ تجميع (compile)
ملف WebAssembly قابل للتنفيذ (WebAssembly executable)
        ↓
Browser على أنواع كثيرة من الأجهزة (Browser on many device types)
```

الميزة هي Portability عبر الأجهزة التي تدعم Browsers.

المفاضلة التي يعرضها الفصل هي Performance: يمكن أن يكون WASM أسرع بكثير من JavaScript في بعض Workloads، لكنه قد يظل أبطأ من Native code.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: Deployment يعني تغليف `predict()` داخل API

قد ينشئ ذلك Demo، لكن Production يتطلب أيضًا Scale وLatency وAvailability وMonitoring وAlerting وDebugging وUpdates آمنة.

### المفهوم الخاطئ 2: Online prediction يعني أن كل Features هي Streaming

قد يستخدم Online request ميزات Batch محسوبة مسبقًا. أما Streaming features فتأتي تحديدًا من Live event streams.

### المفهوم الخاطئ 3: Batch prediction أرخص دائمًا

يمكن أن يهدر Batch الحوسبة عبر توليد Predictions لمستخدمين أو Requests لا تحدث أبدًا.

### المفهوم الخاطئ 4: يمكن لـ Training وServing تنفيذ Feature logic بصورة مستقلة

يُعد تكرار Logic مصدرًا رئيسيًا لعدم اتساق Training-serving.

### المفهوم الخاطئ 5: Compression يقلل Storage فقط

يمكن لـ Compression أيضًا تقليل Memory usage وInference latency، رغم ضرورة فحص جودة Model ودعم Hardware.

### المفهوم الخاطئ 6: Edge inference أفضل تلقائيًا من Cloud inference

يقلل Edge الاعتماد على Network ويمكنه تحسين Privacy وLatency، لكن Compute وMemory وBattery ودعم Runtime على الجهاز تصبح قيودًا.

### المفهوم الخاطئ 7: إذا كان Compiled code يعمل فهو محسّن بالفعل

قد يظل Executable code يهدر Memory bandwidth أو Caches أو Parallelism أو قدرات Hardware-specific.

## المصطلحات الأساسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| Deployment | جعل Model قابلًا للتشغيل والوصول خارج Development environment الخاصة به. |
| بيئة ما قبل Production (Staging) | بيئة Pre-production تُستخدم لاختبار Deployments. |
| بيئة التشغيل الفعلية (Production) | البيئة التي يخدم فيها Model مستخدمين حقيقيين أو Operational systems. |
| تصدير Model (Model export) | تحويل بنية Model وParameters المتعلمة إلى صيغة تستطيع Application أخرى تحميلها. |
| Inference | توليد Predictions من Model مدرَّب. |
| التنبؤ الدفعي (Batch prediction) | توليد Predictions دوريًا أو عند Trigger ثم تخزينها لاستخدامها لاحقًا. |
| التنبؤ عند الطلب (Online prediction) | توليد Prediction عند وصول Request. |
| التنبؤ المتدفق (Streaming prediction) | Online prediction يدمج Streaming features. |
| ميزة Batch (Batch feature) | Feature محسوبة من Historical data، وعادةً بصورة دورية. |
| ميزة Streaming (Streaming feature) | Feature محسوبة من Incoming event streams. |
| ميزة Online (Online feature) | أي Feature مستخدمة في Online prediction، بما في ذلك Batch features وStreaming features. |
| انحراف Training-serving (Training-serving skew) | عدم تطابق Data أو Feature computation بين Training وInference. |
| ضغط Model (Model compression) | تقليل حجم Model، وغالبًا لخفض Memory usage وInference latency. |
| التفكيك منخفض الرتبة (Low-rank factorization) | استبدال بنى عالية الأبعاد ومكلفة بتقريبات منخفضة الأبعاد. |
| تقطير المعرفة (Knowledge distillation) | تدريب Student model صغير ليحاكي Teacher أكبر. |
| التقليم (Pruning) | إزالة أو تصفير مكونات Model التي تُعد أقل أهمية. |
| Quantization | تمثيل قيم Model باستخدام عدد أقل من Bits. |
| الاستدلال على Edge (Edge inference) | تشغيل Computation الخاصة بـ Model أساسًا على أجهزة Consumer أو Embedded محلية. |
| الاستدلال على Cloud (Cloud inference) | تشغيل Computation الخاصة بـ Model أساسًا على Remote servers. |
| التمثيل الوسيط (Intermediate representation — IR) | تمثيل على مستوى Compiler يربط Model code عالي المستوى بـ Hardware code منخفض المستوى. |
| الخفض (Lowering) | تحويل Operations عالية المستوى تدريجيًا إلى Operations منخفضة المستوى وموجهة للـ Hardware. |
| مخطط الحساب (Computation graph) | Graph يصف Operations الخاصة بـ Model وتبعيات Execution. |
| المعالجة المتجهية (Vectorization) | معالجة عدة Data elements معًا باستخدام Vector operations. |
| التنفيذ المتوازي (Parallelization) | تقسيم العمل المستقل حتى يمكن تشغيله في الوقت نفسه. |
| تقسيم الحلقات (Loop tiling) | إعادة ترتيب Computation للاستفادة بصورة أفضل من Cache وMemory layout. |
| دمج العمليات (Operator fusion) | دمج Operations لتقليل الوصول المتكرر غير الضروري إلى Intermediate memory. |
| نموذج التكلفة (Cost model) | Model يُستخدم لتقدير Execution cost لاستراتيجيات Optimization المرشحة. |
| WebAssembly | Portable executable format مصممة للعمل بكفاءة داخل Browser environments. |

## التحقق الذاتي (Self-check)

قبل المتابعة، تأكد من أنك تستطيع الإجابة عن:

1. لماذا لا يُعد إتاحة Prediction endpoint وحدها مساوية للجاهزية لـ Production؟
2. ما الجزآن العامان من Model المدرَّب اللذان يتم تمثيلهما عادةً عند Export؟
3. لماذا قد يحتاج Application واحد إلى مئات Models؟
4. لماذا يتراجع أداء Model غالبًا بعد Deployment؟
5. ما أنماط Prediction الثلاثة التي يركز عليها هذا الدرس؟
6. كيف يختلف Batch prediction عن Online prediction؟
7. ما الفرق بين Streaming feature وOnline feature؟
8. لماذا يمكن لـ Batch prediction إهدار Compute؟
9. لماذا يستحيل تقديم بعض Tasks بالكامل عبر Predictions محسوبة مسبقًا؟
10. ما القدرتان اللازمتان لـ Online prediction فعال؟
11. كيف يمكن لفصل Batch feature pipeline عن Streaming feature pipeline أن يسبب Bugs؟
12. ما طرق Model compression الأربع التي نوقشت؟
13. كيف يختلف Knowledge distillation عن Pruning؟
14. لماذا يمكن لـ Quantization تقليل كل من Memory وLatency؟
15. ما Numerical risk الذي يقدمه Quantization؟
16. ما الفوائد الرئيسية لـ Edge inference؟
17. ما القيود الجديدة التي تظهر على Edge devices؟
18. لماذا تُعد Intermediate representations مفيدة لمطوري Frameworks وHardware؟
19. ما الفرق بين Local optimization وGlobal optimization للـ Model؟
20. كيف يقلل Operator fusion من Memory traffic؟
21. لماذا قد يستخدم ML-powered compiler نموذج Cost model؟
22. ما ميزة Portability التي يوفرها WebAssembly، وما مفاضلة Performance التي تظل موجودة؟

## احتفظ بهذه الفكرة (Retain this idea)

**Deployment هو بداية مرحلة هندسية جديدة، وليس نهاية مشروع ML. يجب أن يتوافق Model المفيد في Production مع Prediction mode وFeature pipeline وLatency budget وHardware target وUpdate process وOperational constraints الخاصة به، لا أن يكتفي بإنتاج Offline predictions جيدة.**
