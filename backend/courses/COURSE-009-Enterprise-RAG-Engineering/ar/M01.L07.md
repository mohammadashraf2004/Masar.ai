## 1. من Software Agents إلى LLM Agents

فكرة **agent** أقدم من generative AI. فقد درست أبحاث distributed AI المبكرة مكونات برمجية مستقلة تستطيع العمل ذاتيًا والتواصل مع مكونات أخرى. ويُعد Actor Model مقدمة تاريخية مهمة لأنه ركّز على actors مستقلة بذاتها، وasynchronous message passing، والسلوك المتزامن.

بحلول ثمانينيات وتسعينيات القرن الماضي، وصف الباحثون agents بأنها كيانات برمجية autonomous وreactive وproactive وقادرة على التفاعل اجتماعيًا. وكان القيد أن معظم ذكائها يأتي من قواعد مكتوبة يدويًا وsymbolic logic. وقد تعمل جيدًا داخل بيئات منظمة بعناية، لكنها تصبح هشة خارج تلك الافتراضات.

لم تخترع LLMs الحديثة هدف البرمجيات المستقلة. لكنها وفرت محرك reasoning مرنًا باللغة الطبيعية جعل الأفكار agentic القديمة أسهل بكثير في التطبيق على المهام المفتوحة.

## 2. نموذج BDI: المعتقدات والرغبات والنوايا (Beliefs, Desires, and Intentions)

نظّم نموذج **Belief-Desire-Intention (BDI)** الـ agent حول ثلاثة مفاهيم. تصف Beliefs ما يفهمه agent حاليًا عن العالم. وتمثل Desires الأهداف التي يريد تحقيقها. أما Intentions فهي الخطط التي التزم بمتابعتها.

لا يزال هذا الفصل مفيدًا كنموذج ذهني. فهو يميّز بين state وgoal وplanned action. لكن أنظمة BDI التقليدية كانت عادةً مبرمجة وليست learned، لذلك اعتمدت بشدة على قدرة المصممين على توقع المواقف الممكنة.

## 3. من Reactive Assistants إلى Goal-Driven LLM Agents

أدى نمو الإنترنت وAPIs إلى زيادة الأنظمة التي تستطيع البرمجيات التفاعل معها، بينما جعلت assistants مثل Siri وAlexa اللغة الطبيعية هي الواجهة. ومع ذلك، كانت هذه assistants غالبًا reactive: يُربط الطلب بدالة ثابتة نسبيًا مثل التحقق من الطقس أو ضبط منبه.

غيّرت LLMs هذا النمط لأنها تستطيع تفسير high-level goal، وتحديد المعلومات الناقصة، واختيار tool، وفحص نتيجته، ثم المتابعة. وجعلت frameworks مثل ReAct هذا النمط التكراري من reasoning-and-action عمليًا.

## 4. ما هو AI Agent؟ (What Is an AI Agent?)

AI agent هو **نظام برمجي autonomous أو semi-autonomous يكون محرك reasoning المركزي فيه هو LLM**. التغيير المهم مقارنةً بـ chatbot عادي هو أن Model يستطيع تحديد ما الذي ينبغي فعله بعد ذلك بدل الاكتفاء بتوليد نص نهائي.

نموذج مفيد هو:

> **LLM + orchestration + tools + الحالة التكرارية = agentic system.**

يفسر Model الأهداف ويختار الإجراءات. وتنفذ orchestration هذه الإجراءات وتدير state. وتربط tools الـ agent بالمعلومات والأنظمة الخارجية. وتستمر loop حتى تكتمل المهمة.

## 5. مقارنة Classic RAG وAgentic RAG

يتبع Classic RAG عادةً مسارًا ثابتًا نسبيًا: استرجاع evidence ثم توليد إجابة. أما Agentic RAG فيجعل retrieval قرارًا واحدًا داخل loop أوسع وديناميكية.

قد يقرر agent أن retrieval واحدًا غير كافٍ، فيعيد صياغة السؤال، ويبحث في مصدر آخر، ويستدعي calculator، ويسأل database، ثم ينفذ retrieval مرة أخرى، وبعدها يركّب النتيجة. وبذلك تصبح RAG قدرة يمكن للـ agent استدعاؤها بدل أن تكون workflow كاملة.

**Classic RAG:** الاستعلام -> الاسترجاع -> التوليد.  
**Agentic RAG:** الهدف -> التفكير -> اختيار أداة -> المراقبة -> التفكير مرة أخرى -> ربما استدعاء أدوات أخرى -> التركيب.

هذه المرونة قوية، لكنها تضيف أيضًا نقاط فشل جديدة: اختيار tool، وtool arguments، وترتيب الإجراءات، وstopping، والتفسير.

## 6. المكدس Agentic (The Agentic Stack)

ينظم الفصل أنظمة agents الحديثة في ثلاث طبقات:

1. **Reasoning LLM** — يفهم intent، ويفكك goals، ويختار actions، ويركّب النتائج.
2. **Agent orchestration** — تدير state وtool calls وretries وcontrol flow والـ loop نفسها.
3. **Tools** — تكشف معلومات أو إجراءات خارجية.

هذا الفصل معماري. يمكنك استبدال Model دون إعادة كتابة كل tool، أو تغيير orchestration framework مع الحفاظ على business systems الموجودة أسفلها.

## 7. نموذج Reasoning LLM

Reasoning Model هو النواة المعرفية للـ agent. يمكنه تفسير user intent، وتقسيم objective واسع إلى subtasks، وتحديد tool التي يمكنها سد فجوة معرفية، وتوليد tool arguments، وتفسير observations، وإنتاج response النهائية.

يحسن Model القوي planning، لكن Model capability عامل واحد فقط. قد يستخدم Model قادر tool سيئة، أو يسيء قراءة tool output، أو يسيء فهم goal. لذلك فإن جودة agent خاصية end-to-end تخص النظام كله.

## 8. تنسيق Agent (Agent Orchestration)

تحوّل orchestration layer الإجراءات التي يطلبها LLM إلى تنفيذ حقيقي. فهي تسجل tools، وترسل schemas إلى Model، وتتحقق من requests، وتشغّل functions، وتلتقط outputs، وتعيد observations لدورة reasoning التالية.

تتعامل production orchestration أيضًا مع timeouts وretries وstate وloop limits وstreaming وconcurrency وtracing وerror handling وapproval checkpoints. ولهذا فإن agent أكثر من مجرد prompt يحيط بـ LLM.

## 9. واجهة Agent مع العالم (Tools)

تحدد Tools ما الذي يستطيع agent معرفته وفعله فعليًا. تشمل tools المعتادة search وRAG وretrieval وText2SQL وcalculators وmessaging systems وcalendars وCRM APIs وinternal services.

يؤثر **اسم tool ووصفها وschema وpermissions وoutput format** جميعها في reliability. إذا تداخلت عدة tools بشدة، فقد يختلط الأمر على Model. وإذا كانت tool تستطيع تنفيذ write operation خطيرة، تصبح أخطاء Model أوسع تأثيرًا.

تعامل مع tool design مثل API design لمتصل ذكي لكنه احتمالي.

## 10. منظومة Agents (The Agent Ecosystem)

تتوافق الطبقات الثلاث مع منظومة providers. يوفّر Model providers الـ reasoning LLM. وتنفذ orchestration frameworks مثل LangChain وLlamaIndex وAutoGen وsmolagents وCrewAI وPydantic AI الـ agent loop. ويمكن للمنصات التجارية إدارة قدر أكبر من runtime. وأي نظام يمتلك API يمكن أن يصبح tool provider.

تحافظ Architecture الجيدة على اقتران ضعيف بين هذه الأدوار حتى تتطور كل طبقة بصورة مستقلة.

## 11. أنظمة Single-Agent

يستخدم نظام Single-Agent agent واحدة لحل مشكلة مركزة. وعادةً يملك latency أقل، وtoken usage أقل، وstate transitions أقل، وdebugging أبسط من تصميم Multi-Agent.

تعد Single-Agent architectures خيارًا افتراضيًا قويًا عندما تكون المهمة محددة جيدًا، وtool surface قابلة للإدارة، وsecurity domain واحدة كافية، وفريق واحد يمتلك workflow. وينبغي إضافة complexity فقط عندما تعالج قيدًا ملموسًا.

## 12. أنظمة Multi-Agent

يوزع نظام Multi-Agent العمل بين agents متخصصة. قد تبحث agent، وتحلل أخرى الأرقام، وتكتب ثالثة التقرير النهائي.

قد يحسن التخصص التركيز لأن كل agent ترى goal أضيق وcontext أصغر وtool set أصغر. كما يمكن تشغيل subtasks المستقلة بالتوازي. لكن كل agent إضافية تضيف model calls وتواصلًا وstate ونقاط فشل محتملة.

## 13. طوبولوجيا Supervisor وCollaborative

في **supervisor architecture**، تفكك agent قائدة global task، وتفوض subtasks، وتجمع النتائج، وتنسق الإكمال. ويظل التحكم مركزيًا.

أما في **collaborative architecture**، فيمكن للـ agents التواصل peer-to-peer واختيار agent أخرى للتواصل معها. وهذا يمكّن سلوكًا مرنًا وemergent لكنه يجعل التنفيذ أقل قابلية للتنبؤ.

عادةً تكون Supervisor designs أسهل في governance وdebugging. أما peer-to-peer designs فقد تكون مفيدة للتعاون المفتوح لكنها تتطلب tracing وstopping rules أقوى.

## 14. ضريبة تعقيد Multi-Agent (The Multi-Agent Complexity Tax)

تدفع Multi-Agent systems تكلفة التخصص على شكل latency إضافية، وtoken cost، ومشكلات concurrency، وخطر recursive delegation، وobservability أصعب.

قد تكون الإجابة النهائية خاطئة حتى عندما تصرفت معظم workers بصورة صحيحة. وبدون traces تفصيلية، قد يصعب العثور على أول agent أو message فاشلة. لذلك فإن Multi-Agent design مفاضلة وليست تحسينًا تلقائيًا.

## 15. متى تكون Agents متعددة مبررة؟ (When Multiple Agents Are Justified)

يقدم الفصل ثلاثة أسباب قوية خصوصًا للانتقال إلى أكثر من agent:

- **Security domains مميزة:** تحتاج workers منفصلة إلى permissions أو datasets حساسة مختلفة.
- **Tool surfaces هائلة:** تمتلك agent واحدة عددًا كبيرًا جدًا من tools بحيث يصبح tool selection غير موثوق.
- **Organizational boundaries:** تحتاج فرق هندسية مختلفة إلى ownership وversioning مستقلين.

قد يحسن Multi-Agent design التركيز أيضًا عبر تقليل context لكل worker، ويمكنه تقليل cost بتوجيه subtasks البسيطة إلى Models أرخص. ومع ذلك، يجب أن يكون السؤال الأول هو ما إذا كانت agent واحدة مصممة بعناية تستطيع حل المشكلة.

## 16. نمط Orchestrator-Worker

يمثل نمط Orchestrator-Worker حلًا وسطًا عمليًا. تفهم orchestrator مركزية global goal، وتفككه، وترسل مهام ضيقة إلى specialist workers، وتجمع النتائج، وتركب الإجابة النهائية.

لا تتواصل Workers مباشرةً مع بعضها. وهذا يحافظ على التخصص دون إدخال peer-to-peer behavior ناشئ بالكامل. كما ينشئ نقطة واضحة لفرض permissions وtimeouts وauditability.

## 17. حالة استخدام: خدمة العملاء (Customer Service)

تعتمد support bots التقليدية غالبًا على decision trees كبيرة. أما LLM agents فيمكنها دمج natural-language reasoning مع retrieval وbusiness tools، مما يسمح لها بالإجابة عن نطاق أوسع من الأسئلة والتكيف مع context.

قد تسترجع support agent policy، وتفحص order، وتتحقق من account state، ثم تعد response مخصصة. ولأن output موجهة للعميل، تصبح hallucination mitigation وpermission boundaries وhuman escalation أمورًا حاسمة.

## 18. حالة استخدام: الخدمات المالية (Financial Services)

غالبًا ما تتضمن Financial workflows مثل investment research وdue diligence وregulatory analysis وcustomer support جمع evidence من مصادر متعددة وإنتاج نتيجة structured. وتناسب agents هذا النمط جيدًا.

لكن كلما زاد أثر الإجراء، وجب أن تصبح autonomy أكثر تقييدًا. إعداد investment memo مختلف تمامًا عن نقل الأموال بصورة autonomous. تحتاج الإجراءات عالية التأثير إلى authorization صريح وauditability وغالبًا human approval.

## 19. حالة استخدام: الرعاية الصحية (Healthcare)

تشمل تطبيقات Healthcare clinical documentation وadministrative automation وclinical-trial matching وpersonalized treatment support وvirtual assistants.

النمط التصميمي المتكرر هو augmentation بدل unsupervised autonomy. يمكن للـ agent إعداد notes أو تلخيص evidence أو تجهيز plan، بينما يبقى clinician مسؤولًا عن review وapproval في high-stakes workflows.

## 20. حالة استخدام: Coding Agents

يمكن لـ Coding agents فحص repositories، وتوليد الملفات وتعديلها، وتشغيل tests، وتنفيذ shell commands، والتكرار بناءً على failures. وهي تتجاوز autocomplete بكثير.

يصبح Software engineer بصورة متزايدة director وreviewer: يحدد goal، ويفحص patch، ويتحقق من tests، ويراجع security، ويقرر قبول changes من عدمه.

نموذج ذهني مفيد هو مساهم junior سريع: عالي الإنتاجية لكنه لا يزال يحتاج إلى review.

## 21. Human-in-the-Loop للإجراءات عالية التأثير

المهام طويلة الأفق محفوفة بالمخاطر لأن أخطاء reasoning أوtool الصغيرة يمكن أن تتراكم عبر خطوات كثيرة. وفي workflows المنظمة أو غير القابلة للعكس، قد يكون fully autonomous execution غير مناسب.

يسمح تصميم human-in-the-loop للـ agent بتنفيذ research وpreparation وdrafting، لكنه يتوقف قبل إجراءات مثل إرسال message حساسة، أو تغيير production data، أو الموافقة على transaction، أو اتخاذ قرار consequential.

وهذا يحافظ على automation مع تقليل blast radius لأخطاء agent.

## 22. الحلقة Agentic (The Agentic Loop)

في قلب agent توجد دورة متكررة:

1. **Observation** — استقبال user request أو نتيجة action سابقة.
2. **Reasoning and planning** — تقييم التقدم واختيار الخطوة التالية.
3. **Action** — تنفيذ tool أوoperation المختارة.

تصبح النتيجة observation التالية. وتستمر loop حتى يقرر agent أن goal تحقق أو تم الوصول إلى stopping condition.

## 23. بناء Current State من Observation

يمكن أن تكون Observation هي user input، أو retrieved text، أو database result، أو calculator output، أو API response، أو error message.

لا يمكن أن يكون القرار التالي أكثر موثوقية من observation نفسها. فإذا أعادت tool معلومات stale أوغير صحيحة، فقد يستدل Model بصورة منطقية على evidence سيئة ومع ذلك يفشل. لذلك ينبغي التحقق من tool output عندما يكون ذلك عمليًا بدل التعامل معها بوصفها حقيقة غير قابلة للنقاش.

## 24. التخطيط وReasoning (Reasoning and Planning)

في كل دورة، ينظر agent إلى goal وprevious steps وworking memory وأحدث observation. ويقرر ما إذا كانت المهمة مكتملة، وما الذي لا يزال مجهولًا، وأي tool يمكنها تقليل uncertainty، وما arguments التي ينبغي إرسالها.

لذلك لا يكون Planning بالضرورة plan لمرة واحدة تُنشأ في البداية. يستطيع agent القوي إعادة planning بعد كل observation.

## 25. تنفيذ الخطة (Action)

تحوّل orchestration layer الـ requested action إلى operation حقيقية. وتتحقق robust action layer من tool identity وarguments، وتفحص authorization، وتفرض timeouts، وتلتقط errors، وتسجل النتيجة.

ثم تصبح action result هي observation التالية، ما يعني أن action الخاطئة قد تمتد إلى reasoning اللاحق. لذلك تعد execution controls جزءًا من reasoning reliability.

## 26. البيانات غير المنظمة: Retrieval Tool أم RAG Tool؟

يمكن للـ agent الوصول إلى المستندات عبر **retrieval-as-a-tool** أو **RAG-as-a-tool**.

تعيد Retrieval tool raw chunks وتترك interpretation وsynthesis للـ agent. وهذا يمنح agent transparency وflexibility أكبر.

أما RAG tool فتؤدي retrieval مع grounded generation وتعيد إجابة جاهزة، وغالبًا مع citations. وهذا يركز grounding logic ويمكن أن يجعل السلوك أكثر اتساقًا.

لا يوجد خيار أكثر agentic بطبيعته. السؤال هو: أين تريد أن توجد مسؤولية reasoning؟

## 27. تصحيح الحلقة التكرارية (Debugging)

تتسلسل أخطاء Agent. ينشئ bad tool call observation سيئة، ثم تؤثر هذه observation في خطوة reasoning التالية. وقد تخفي الإجابة النهائية السبب الأصلي.

تشمل debugging data المفيدة tool التي تم اختيارها، وarguments المرسلة، والنتيجة المعادة، والمدة، وretries، وstate transitions. والهدف هو تحديد **أول انتقال غير صحيح**، لا مجرد فحص آخر response.

## 28. استدعاء Tools (Tool Calling)

يسمح Tool calling، ويُسمى أيضًا function calling، للـ Model بطلب تنفيذ function يحددها developer باستخدام structured arguments.

يعرض التطبيق اسم tool ووصفها وinput schema. ويقرر Model ما إذا كان سيستخدمها وينتج structured arguments. ثم تتحقق ordinary software من call وتنفذه.

هذا الفصل مهم: يختار Model، لكن application code تظل مسؤولة عن التنفيذ الحقيقي وsecurity.

## 29. نمط ReAct: Reason وAct وObserve

يمزج ReAct بين decision making وtool use. ومسار تنفيذ مبسط هو:

```text
الهدف: الإجابة عن سؤال مكوّن من جزأين
القرار: جمع evidence للجزء A
الإجراء: استدعاء RAG tool
الملاحظة: evidence A
القرار: جمع evidence للجزء B
الإجراء: استدعاء RAG tool
الملاحظة: evidence B
النهائي: تركيب النتيجتين
```

الأثر الأهم في debugging هو التسلسل الظاهر خارجيًا للقرارات وtool calls وobservations وoutcomes، وليس hidden internal reasoning.

## 30. مخططات Tools وأوصافها (Tool Schemas and Descriptions)

يرى Model عادةً تعريفًا structured لكل tool متاحة. ولذلك تؤثر جودة tool interface مباشرةً في سلوك agent.

تستخدم Tool definitions الجيدة اسمًا محددًا، ومسؤولية ضيقة، وtyped arguments، وأوصافًا واضحة، وoutputs يمكن توقعها. ويمكن للأوصاف المتداخلة أن تسبب tool confusion، بينما تزيد broad write-enabled tools الضرر الممكن من قرار سيئ واحد.

صمم Tools بعناية كما تصمم Public APIs.

## 31. ضوابط Production لاستخدام Tools (Production Controls for Tool Use)

ينبغي التعامل مع Tool calls بوصفها probabilistic inputs لا requests مضمونة الصحة. تشمل production controls التحقق من schema، وفحوصات permission خارج LLM، وtimeouts، وsafe retries، وidempotency حيثما أمكن، وloop detection، وفصل read/write، وlogging تفصيلي.

قد يساعد Tool-calling Model أقوى، لكن reliability في tool use تبقى في النهاية خاصية للنظام كله.

## 32. بروتوكول Model Context Protocol

مع نمو agent ecosystems، أصبحت direct one-off integrations مجزأة. يوحّد **Model Context Protocol** كيفية اكتشاف AI applications للقدرات والوصول إلى tools أوdata دون اقتران شديد بتفاصيل implementation.

الفائدة المعمارية الأساسية هي decoupling. يمكن للـ agent التواصل مع MCP server معياري بينما يترجم server الطلب إلى database أوfile system أوAPI أوinternal service خاص بالمورّد.

تصبح MCP ذات قيمة خاصة عندما تحتاج agents كثيرة إلى الوصول إلى مكتبة مشتركة من enterprise capabilities.

## 33. مكوّنات MCP الأساسية: Tools وResources وPrompts

تكشف MCP ثلاثة أنواع مهمة من capabilities.

**Tools** هي executable functions. يمكنها تنفيذ actions أواسترجاع المعلومات ديناميكيًا.

**Resources** تمثل contextual data أوstate، وغالبًا يُشار إليها باستخدام URIs. وهي مفيدة عندما تكون المعلومات كبيرة جدًا أوpersistent بحيث لا تناسب tool response واحدة بصورة طبيعية.

**Prompts** هي reusable instruction templates ترمز intent وconstraints وinteraction patterns الموصى بها. وهي توجه agent لكنها لا تنفذ action بنفسها.

التمييز مفيد: tools **تنفذ**، وresources **توفر context**، وprompts **توجّه interaction**.

## 34. بنية MCP: Host وClient وServer

تتبع MCP بنية client-server.

- **Host:** التطبيق أوenvironment التي يعمل فيها agent.
- **Client:** مكوّن داخل host يتحدث MCP ويرسل structured requests.
- **Server:** adapter يكشف tools أوresources أوprompts ويترجم MCP requests إلى operations على نظام أساسي.

قد يغلّف Server قاعدة بيانات داخلية أوfile system أوText2SQL service. وبذلك يستخدم agent protocol ثابتًا حتى لو كان underlying system proprietary.

[[IMAGE_NEEDED: MCP host-client-server architecture | Show an agent host containing MCP clients connected to several MCP servers, each wrapping a tool or data source. | The client speaks MCP; each server adapts MCP requests to an underlying capability.]]

## 35. وسائل نقل MCP وأمنها (MCP Transports and Security)

يصف المصدر local standard-input/output transport وremote HTTP-style transport. والدرس المهم في production هو أن protocol لا يلغي مسؤوليات security المعتادة.

لا تزال Remote MCP services تحتاج إلى transport security وauthentication وauthorization وsecret management وaccess logging وrate limits. كما تحتاج Local integrations إلى operating-system permissions وprocess isolation.

ينبغي ألا تُضمّن Credentials عشوائيًا داخل protocol messages. فلا تكون standardized integration layer آمنة إلا إذا أُدير deployment المحيط بها بصورة صحيحة.

## 36. القيمة المؤسسية لـ MCP (Enterprise Value of MCP)

يمكن لـ MCP توفير governed trust boundary بين agent والأنظمة المؤسسية الحساسة. كما يمكنها توحيد reusable integrations، وإتاحة legacy systems عبر standard adapters، والسماح للـ tools بالتوسع بصورة مستقلة عن agents.

ويشدد الفصل أيضًا على مفاضلة: في تطبيق local صغير مع tool set ضيقة وثابتة، قد يكون direct integration أبسط. وتزداد قيمة MCP كلما انتقلت المؤسسة من تجارب منفصلة إلى agent ecosystem مشتركة.

## 37. التواصل بين Agents باستخدام A2A (Agent-to-Agent Communication)

توحّد MCP أساسًا الاتصال الرأسي من agent إلى tools وdata. أما **Agent-to-Agent (A2A)** communication فتعالج المشكلة الأفقية الخاصة بتعاون agent مع agent أخرى.

يسمح A2A للـ agents بالإعلان عن capabilities، واكتشاف بعضها، وتفويض العمل، وتبادل المعلومات، وتتبع progress. ويصف المصدر **Agent Card** بوصفها profile لمهارات agent والمهام التي تدعمها.

النموذج الذهني بسيط:

- MCP: يربط agent بـ tools والبيانات.
- A2A: يربط agent بـ agent أخرى.

تجعل هذه standards معًا agent ecosystems الكبيرة أكثر modular وinteroperable.

المبدأ التصميمي الأوسع هو إعطاء agents **structured observations**. كلما قل interface noise غير ذي الصلة الذي تعيده tool، أصبح reasoning على النتيجة أسهل على Model.

## 43. لماذا يهم Streaming لأحداث Agent؟ (Why Agent Event Streaming Matters)

يجعل Streaming execution events تقدم agent ظاهرًا أثناء تشغيل المهمة. يستطيع developer ملاحظة tool التي تم استدعاؤها، وarguments المستخدمة، وما إذا كان call نجح، وكيف تغير القرار التالي.

يحسن ذلك debugging وقد يحسن UX أيضًا. كما يخلق نقاطًا لإدخال policy checks، مثل التوقف قبل high-impact action.

## 44. منصات Agents المُدارة مقابل Orchestration Libraries

مع orchestration library، يكتب application team الـ agent ويظل مسؤولًا عن hosting وscaling وoperational reliability. أما managed agent platform فتجرد قدرًا أكبر من runtime وتسمح للـ developer بالتركيز على tool definitions وmodel configuration وbusiness instructions.

هذه هي مفاضلة build-versus-platform نفسها التي ظهرت سابقًا في RAG: control وflexibility من جانب، وoperational simplicity من الجانب الآخر.

## 45. واجهة Vectara Agents API

ينشئ مثال managed-platform في الفصل أولًا corpus وRAG-search tool، ثم يحدد model الخاصة بالـ agent ووصفها وinstructions عبر API.

## 47. لماذا يمكن أن يحسن التخصص أنظمة Agents؟ (Why Specialization Can Improve Agent Systems)

يشدد المصدر على عدة أسباب تجعل التخصص مفيدًا.

**Tool bottleneck:** كل tool definition تستهلك context، وقد تسبب كثرة tools ارتباكًا في selection.

**Cognitive precision:** يمكن لـ contexts أصغر ومهام أضيق أن تساعد كل worker على البقاء مركزة.

**Cost efficiency:** يمكن توجيه subtasks السهلة إلى Models أرخص، مع حجز Models المكلفة لـ difficult reasoning أوsynthesis.

يمكن لـ Multi-Agent systems أيضًا parallelize المهام المستقلة وجعل specialist capabilities قابلة لإعادة الاستخدام.

## 48. ذاكرة Agentic (Agentic Memory)

Memory هي قدرة agent على الاحتفاظ بالمعلومات وإعادة استخدامها عبر steps أوinteractions أوsessions. وهي ما يجعل agent persistent بدل أن تكون stateless one-shot responder.

قد تحسن Memory personalization وcontinuity وefficiency، لكنها تنشئ أيضًا مسؤوليات privacy وrelevance وlifecycle. ولا يكون تخزين history أكثر دائمًا أفضل.

## 49. الذاكرة قصيرة المدى أو Working Memory

توجد Short-term memory للجلسة الحالية من reasoning. فهي تساعد agent على تذكر previous tool results، وحل pronouns، والحفاظ على multistep plan.

Implementation شائع هو sliding window من recent conversation history. وبدون هذا working context تصبح multistep agent فعليًا stateless ولا تستطيع ربط التعليمات اللاحقة بالخطوات السابقة بصورة موثوقة.

## 50. الذاكرة طويلة المدى (Long-Term Memory)

تستمر Long-term memory عبر sessions. ويمكنها تخزين recurring preferences أوproject history أوحقائق أخرى تقلل الاحتكاك في interactions المستقبلية.

يوصي الفصل باستخدام long-term memory عندما تخلق معرفة user أوproject قيمة تراكمية حقيقية. وقد لا تحتاج one-off transactional agent إلى persistent memory أصلًا، ويمكن لتجنبها تبسيط privacy وcompliance.

## 51. دمج الجلسات (Session Consolidation)

تنمو Raw session history بمرور الوقت. إحدى الاستراتيجيات هي **session consolidation**: تلخيص الحقائق المهمة دوريًا واستبدال histories الطويلة بتمثيل مضغوط.

على سبيل المثال، قد تُدمج عدة محادثات سفر في حقيقة قابلة لإعادة الاستخدام مثل “يفضل مقاعد النافذة.” وهذا يقلل token usage وnoise، لكن يجب أن يكون summary صحيحًا لأن consolidation السيئة قد تصبح مصدرًا دائمًا للأخطاء المستقبلية.

## 52. الاسترجاع الدلالي للذاكرة طويلة المدى (Semantic Retrieval for Long-Term Memory)

تُخزن Long-term memory غالبًا في database أوvector store. وعند بدء مهمة جديدة، يسترجع agent semantic memories تاريخية ذات صلة بالـ current query ويضعها في working context.

يشبه ذلك RAG: يسترجع النظام history المفيدة فقط بدل تحميل كل interaction سابق. ولذلك تعتمد جودة memory على ما يتم تخزينه، وكيفية indexing، وكيف يتم تحديد relevance.

{{exercise:M01.L07.EX10}}

## 53. حوكمة Memory والخصوصية (Memory Governance and Privacy)

تحوّل Persistent memory الـ agent إلى data steward. تحتاج Enterprise systems إلى القدرة على حذف memories المرتبطة بمستخدم، وعمل redact للمعلومات الحساسة قبل التخزين، واحترام privacy requirements المعمول بها.

السؤال التصميمي ليس فقط “هل تستطيع agent تذكر هذا؟” بل “هل ينبغي أن تتذكره، وكم من الوقت، وتحت authorization من؟”

## 54. تسميم Memory (Memory Poisoning)

قد تخزّن agent معلومات غير صحيحة أوmalicious عن طريق الخطأ ثم تسترجعها لاحقًا كما لو كانت trusted history. وهذا هو **memory poisoning**.

يقترح المصدر validation gate قبل long-term persistence. ويمكن لـ lightweight secondary check أن يقرر ما إذا كانت memory المقترحة factual وآمنة وذات قيمة كافية للاحتفاظ بها.

لذلك ينبغي أن تكون Long-term memory حالة curated، لا dump غير مفلتر للنص الكامل.

## 55. دورة حياة بيانات Memory وتلاشيها (Memory Data Lifecycle and Decay)

للمعلومات shelf life. فقد تصبح preference أوproject fact كانت مفيدة منذ أشهر غير ذات صلة أوغير صحيحة لاحقًا.

تساعد decay أوarchival policy على إبقاء memory حديثة والحد من retention غير الضرورية. ويعتمد قرار persistence الصحيح على ما إذا كانت المعلومات قابلة لإعادة الاستخدام ودائمة أم انتقالية فقط.

{{exercise:M01.L07.EX11}}

## 56. لماذا تختلف حالات فشل Agents؟ (Why Agent Failures Are Different)

ترتبط Traditional software failures غالبًا بـ deterministic bugs. أما agent failures فقد تنشأ من behavior عبر LLM وtool calls وmemory وقرارات متكررة.

قد يملك النظام CPU usage منخفضًا، واستجابات سريعة، وصفر HTTP errors ومع ذلك يفشل في user goal. لذلك يجب أن يقيّم Production monitoring ليس فقط infrastructure health بل behavioral correctness أيضًا.

## 57. هلوسة Tool أوEvidence سيئة من Tool

قد تعيد Tool معلومات غير دقيقة، وقد يقبلها agent دون verification. قد تعيد RAG tool إجابة خاطئة أوقد تولد Text2SQL tool query خاطئًا.

يمكن للـ agent بعد ذلك نشر evidence السيئة بأمانة. ويختلف هذا failure عن response hallucination لأن الخطأ يبدأ في observation التي توفرها tool.

## 58. هلوسة الاستجابة (Response Hallucination)

في Response hallucination، توفر tools معلومات صحيحة لكن agent يشوهها أو يضيف محتوى غير مدعوم عند إنتاج final answer.

يشبه ذلك generation failure في RAG العادي. والتمييز مهم لأن remediation تختلف: مشكلات tool quality تتطلب إصلاح tool، بينما response hallucination تتطلب تحسين generation أوgrounding أوprompting أوpost-generation checks.

## 59. سوء تفسير Goal (Goal Misinterpretation)

قد يسيء agent فهم ما يريده user ويحل مشكلة قريبة لكنها مختلفة. على سبيل المثال، قد ينشئ destination plan خاطئة مع أن جميع tools تعمل بصورة صحيحة.

ولهذا لا يكفي تقييم tool success فقط. يجب أن تبقى workflow كاملة aligned مع user goal الأصلي.

## 60. فشل توليد الخطة (Plan Generation Failure)

قد يختار agent خطوات تبدو منطقية محليًا ولكن بترتيب خاطئ، أو يحذف خطوة مطلوبة. Scheduling meeting قبل فحص availability مثال بسيط.

تبدو Planning failures غالبًا معقولة محليًا. ولا يصبح الخطأ واضحًا إلا عند فحص workflow كاملة مقابل task prerequisites وconstraints.

{{exercise:M01.L07.EX12}}

## 61. استخدام Tool بصورة غير صحيحة (Incorrect Tool Use)

قد يختار agent tool خاطئة أو يستدعي tool الصحيحة باستخدام arguments سيئة. ويصبح الخطر كبيرًا عندما تستطيع tools تغيير state.

تمثل Permissions دفاعًا حاسمًا. فإذا كانت email tool read-only، لا يستطيع reasoning mistake حذف الرسائل. ويقلل تقييد write capabilities وتطبيق least privilege من blast radius لأخطاء Model.

## 62. فشل Verification وTermination

يجب أن يعرف agent متى تحقق goal بالفعل. فقد يتوقف مبكرًا ويعيد partial result، أو يستمر في استدعاء tools بعد انتهاء العمل المفيد.

تساعد Loop limits وexplicit completion criteria وprogress checks وmaximum cost أوstep budgets على منع runaway execution.

## 63. Prompt Injection في الأنظمة Agentic

يصبح Prompt injection أكثر خطورة عندما تستطيع agents تنفيذ actions. فقد تحاول malicious instruction تجاوز الدور المقصود، أوإعادة توجيه tool use، أوالتسبب في كشف معلومات حساسة.

يتطلب الدفاع layered controls: تنظيف وتصنيف inputs حيثما كان ذلك مناسبًا، والتعامل مع external content بوصفه untrusted data، وفرض permissions خارج Model، والتحقق من tool requests، وإبقاء high-risk actions خلف approval gates.

## 64. قابلية الرصد Agentic (Agentic Observability)

يجيب Traditional monitoring عن أسئلة مثل “هل server سليم؟” أما Agentic observability فتسأل “هل أنجز agent المهمة بصورة صحيحة وآمنة؟”

وهي تجمع logs وmetrics وtraces المعتادة مع **evaluation** و**governance**. تقيس Evaluation الجودة. وتتحقق Governance من أن agent بقيت داخل rules وpermissions.

الهدف هو تحويل workflow مبهمة إلى نظام يمكن فحص execution فيه وقياسه وتحسينه.

## 65. تتبع Agent (Tracing an Agent)

يسجل Trace التنفيذ end-to-end لطلب واحد في hierarchy من spans. ويمكن لـ span أن تمثل LLM call أوRAG query أوText2SQL invocation أووحدة عمل أخرى.

يمكن لـ trace مفيدة الإجابة عن:

- أي Tool تم استدعاؤها؟
- ما Arguments التي مُررت؟
- ماذا أعادت؟
- كم استغرقت Step؟
- كم Retry حدث؟
- أين انحرفت Workflow عن المسار المتوقع؟

على سبيل المثال، قد تكشف الاستدعاءات المتكررة لنفس flight-search tool عن arguments سيئة حتى إذا نجحت final answer في النهاية.

## 66. مقاييس Agentic Observability

تشمل Agent-specific metrics المفيدة:

- **Token usage** — cost وكفاءة prompt/reasoning.
- **Inference latency** — time to first token وend-to-end completion time.
- **LLM/API call count** — تعقيد workflow واحتمال loops.
- **Tool-call success/failure rate** — reliability لتفاعلات agent-tool.
- **Response quality** — hallucination وrelevance وhelpfulness أوdomain metrics.
- **Human handoff rate** — عدد المرات التي لا يستطيع agent فيها إكمال task autonomously.

يحتاج Agent evaluation أيضًا إلى أبعاد تتجاوز RAG العادي، مثل tool-use efficiency وmultiturn coherence وما إذا كانت autonomous decisions تظل aligned مع user intent.

## 67. مقارنة Traditional Observability وAgentic Observability

تفترض Traditional observability أن operational stability proxy مفيد لـ functional correctness. وهذا الافتراض غير كافٍ للـ agents.

قد تكون agent سليمة تمامًا على infrastructure level ومع ذلك تختار tool خاطئة، أوتسيء فهم goal، أوتهلوس response، أوتفشل في termination.

لذلك تحتاج Production dashboards إلى system-health metrics وbehavioral metrics معًا.

## 68. استخدام OpenTelemetry لأنظمة Agents

يشدد المصدر على **OpenTelemetry (OTel)** بوصفه standard vendor-neutral للـ traces وmetrics وlogs. ويمكن لـ AI-specific semantic conventions أن تمنح frameworks المختلفة vocabulary مشتركة لـ LLM calls وtool calls وvector-database operations.

الفائدة الاستراتيجية هي interoperability. ويمكن أن تبقى instrumentation مستقلة نسبيًا عن backend المستخدمة لعرض telemetry أوتحليلها.

## 69. منصات Observability للـ Agents

يذكر الفصل tools مثل Langfuse وArize Phoenix وLangSmith، إضافةً إلى agent platforms التي تتضمن observability مباشرةً.

المنتج المحدد أقل أهمية من capabilities: traces تفصيلية، وlatency وcost monitoring، وتتبع prompt وconfiguration، وevaluation datasets، وdebugging لـ routers وplanners وretrieval وtool calls.

اختر tooling تسمح لك بتتبع execution واحدة بعمق وتجميع behavior عبر executions كثيرة أيضًا.

## 70. قائمة فحص Agent في Production

قبل منح agent autonomy ذات معنى، تحقق من وجود:

- tools ضيقة وموصوفة جيدًا؛
- least-privilege permissions؛
- schema validation؛
- retry وtimeout policy؛
- loop وcost limits؛
- إدارة short-term state؛
- deliberate long-term memory policy؛
- human approval للإجراءات irreversible؛
- tracing وbehavior metrics؛
- regression evaluation؛
- prompt-injection defenses؛
- مسار تصعيد بشري (human escalation path).

تهدف Agent production engineering أساسًا إلى جعل dynamic behavior **محدودة وقابلة للرصد والاسترداد**.

## 71. مفاهيم خاطئة شائعة (Common Misconceptions)

**“Agent مجرد LLM مع Prompt طويل.”**  
تحتاج Agent إلى execution loop وstate وexternal capabilities.

**“المزيد من Agents يعني دائمًا ذكاءً أكبر.”**  
قد تزيد Agents المتعددة latency وcost وتعقيد failure.

**“MCP تؤمّن Tools تلقائيًا.”**  
توحّد MCP communication؛ لكن authentication وauthorization وsecret management لا تزال تتطلب implementation مقصودة.

**“Memory تعني حفظ Transcript كامل.”**  
Memory المفيدة تُنتقى وتُلخص وتُسترجع وتُحكم وتُنهى صلاحيتها.

**“إذا نجحت كل Tool calls فقد نجحت Agent.”**  
قد تسيء Agent فهم goal أوتركب النتيجة بصورة خاطئة.

**“Latency منخفضة وصفر Server errors يثبتان أن Agent سليمة.”**  
تحتاج Agentic systems إلى behavioral evaluation بالإضافة إلى infrastructure monitoring.

| مضيف MCP (MCP host) | Application environment التي يعمل فيها agent |
| عميل MCP (MCP client) | Protocol component داخل host |

| بروتوكول A2A | Protocol concept للتواصل agent-to-agent |
| الذاكرة العاملة (Working memory) | State المستخدمة داخل task/session الحالية |
| الذاكرة طويلة المدى (Long-term memory) | معلومات تستمر عبر sessions |
| تسميم الذاكرة (Memory poisoning) | حفظ معلومات harmful أوfalse تؤثر لاحقًا في agent |

## 73. احتفظ بهذا النموذج الذهني (Retain This Mental Model)

Agent الموثوقة ليست “chatbot أذكى.” فكّر فيها بوصفها **controlled software runtime يكون planner فيها احتماليًا**.

يقرر LLM ما الذي قد يكون مفيدًا بعد ذلك. وتفرض orchestration layer ما هو مسموح فعليًا. وتوفر Tools evidence وactions. وتحمل Memory state المفيدة. وتشرح Observability ما حدث. وتقيّد Governance ما يمكن أن يحدث.

عندما تفشل agent، افحص السلسلة بهذا الترتيب: **goal -> plan -> tool choice -> tool result -> memory/state -> synthesis -> stopping condition**.

## الخلاصة النهائية (Final takeaway)

يمثل الانتقال من RAG إلى agents انتقالًا من information pipeline ثابتة في الغالب إلى **نظام ديناميكي لاتخاذ القرارات وتنفيذ الإجراءات**. تظل RAG مهمة، لكنها تصبح tool واحدة بين tools كثيرة. وينتقل التحدي الهندسي من مجرد استرجاع context الصحيحة إلى التحكم في planner احتمالي يستطيع اختيار tools وإنشاء plans والحفاظ على memory وتنفيذ actions.

عقلية production الأكثر أمانًا هي جعل autonomy **محدودة وقابلة للرصد وقابلة للعكس حيثما أمكن**. ابدأ ببساطة، ولا تمنح agents إلا tools وpermissions التي تحتاج إليها، ولا تحفظ إلا memory التي تخلق قيمة دائمة، وتتبع execution path، وقيّم behavior باستمرار، وضع human approval أمام الإجراءات ذات العواقب المهمة.
