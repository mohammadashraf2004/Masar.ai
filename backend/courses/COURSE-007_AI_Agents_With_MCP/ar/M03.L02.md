## 1. من تقديم Primitives إلى بناء Server متكاملة

ركز الدرس السابق على Primitives الثلاثة الأساسية في Server:

```text
Tools     → إجراءات
Prompts   → تعليمات تفاعل قابلة لإعادة الاستخدام
Resources → Data سياقية
```

هذه Primitives هي الأساس، لكن Server جادة تحتاج أيضًا إلى دعم Usability وObservability وLarge result sets وLong-running work وClient compatibility وInteraction flows أكثر ثراءً.

يقسم الفصل هذه الإضافات إلى فئتين عامتين.

### Server utilities

تحسن Utilities كيفية تواصل Server وتشغيلها. يغطي المصدر:

- Completions،
- Server/Primitive icons،
- كائن `Context` في Python SDK،
- Logging،
- Progress reporting،
- Manual change notifications،
- Pagination.

### القدرات التي يوفرها الـ Client (Client-provided capabilities)

يعكس النصف الثاني الاتجاه المعتاد: بدلًا من أن تقدم Server قدرات لـ Clients فقط، قد تحتاج Server شيئًا من Client application.

يغطي المصدر:

- **Elicitation** → طلب Input من User،
- **Sampling** → طلب استخدام LLM الخاصة بالـ Client،
- **Roots** → طلب معلومات عن نطاق Filesystem،
- **Cancellation** → السماح لـ Client/User بإيقاف عمل طويل.

## 2. Completions: إكمال تلقائي لمعاملات Prompts وResource templates

Completions مستوحاة من IDE code completion. تسمح لـ Server بإعادة Suggestions أثناء قيام User بملء Arguments لـ Prompt أو Resource template.

يستقبل Completion handler ثلاث Inputs مهمة:

| Input | المعنى |
|---|---|
| `ref` | أي Prompt أو Resource template يتم تنفيذ Completion لها |
| `argument` | اسم Argument وقيمتها الجزئية الحالية |
| `context` | معلومات اختيارية عن Values سبق إدخالها لـ Arguments أخرى |

يعيد Handler نتيجة Completion تحتوي:

- `values` — Suggested strings بحد أقصى 100 قيمة،
- `total` — العدد الاختياري للـ Suggestions المتاحة،
- `has_more` — هل توجد Suggestions أكثر مما تمت إعادته.

### نموذج ذهني بسيط

```text
User يكتب جزءًا من Argument
        ↓
Client يرسل Completion request
        ↓
Server تفحص Prompt/Template + Partial value + Previous args
        ↓
Server تعيد Suggestions
        ↓
Client تعرضها لـ User
```

### لماذا تهم Previous arguments؟

افترض أن Prompt تطلب كلًا من `country` و`city`. بعد أن يختار User الدولة، تستطيع Server استخدام هذه Value السابقة لتضييق اقتراحات City. يجعل ذلك Completion واعية بالسياق بدل مطابقة Static list فقط.

### تصميم Defensive للـ Completion

يوصي المصدر بالتفكير في:

- Rate limiting، لأن Client قد ترسل Completion requests بتكرار مرتفع جدًا،
- Relevance ranking،
- Input validation،
- تجنب Sensitive suggestions مثل Credentials أو API keys،
- احترام حد 100 قيمة.

## 3. Icons وكائن Context

يقدم الفصل Icons بصورة مختصرة باعتبارها Metadata يمكن لـ Client application اختيار عرضها. يمكن لـ Server توفير Icons لنفسها، وإرفاق Icons بـ Tools وPrompts وResources.

أما المفهوم الأهم فهو **كائن Context** في Python SDK.

⟦CODE_0⟧

يتعرف SDK على Type ويحقن Current request context تلقائيًا.

### ماذا يتيح لك Context؟

على مستوى عالٍ، يمنح `Context` وصولًا إلى:

- Server identity/Configuration،
- Current client/session information،
- Request metadata،
- Request ID،
- Request method وParameters،
- Lifespan context،
- Client capabilities،
- Logging helpers،
- Progress reporting،
- إشعارات الـ Primitives والموارد (Primitive/Resource notifications).

Hierarchy مفيدة هي:

```text
Context
├── معلومات Server (`mcp_server`)
├── Session (`session`)
├── Client capabilities
└── Request context (`request_context`)
    ├── Request ID
    ├── Request metadata
    ├── Raw method/Params
    ├── Lifespan context
    └── Transport-level request عندما تكون متاحة
```

[[IMAGE_NEEDED: MCP Python Context hierarchy | A tree diagram showing Context at the top and its mcp_server, session, client_capabilities, and request_context branches with their major properties | Learner should notice that one injected object exposes both static server state and per-request state]]

### معلومات Server

يمكن لـ `ctx.mcp_server` إتاحة معلومات مثل اسم Server وInstructions وWebsite URL وIcons وDebug mode وConfigured log level.

### معلومات Session وClient

توفر `ctx.session` رؤية Low-level للتواصل مع Connected client. يشير المصدر إلى أن Client identity metadata قد تكون Optional، لذلك ينبغي ألا يفترض Code وجودها دائمًا.

إذا كنت تحتاج فقط إلى معرفة Capabilities التي يدعمها Client، فإن `ctx.client_capabilities` هي المصدر الأكثر مباشرة.

### Request context وLifespan state

يتيح Request context للـ Handler الوصول إلى Data خاصة بعملية واحدة. ويمكنه كذلك كشف State تم Yield لها بواسطة Lifespan function — مثل Database handles أو Shared caches أو Resources أخرى يتم إنشاؤها عند Startup وتنظيفها عند Shutdown.

## 4. Logging: Protocol logging مقابل Application logging العادي

يعرض الفصل Protocol-level logging عبر Methods في `Context` مثل:

```text
ctx.debug(...)
ctx.info(...)
ctx.warning(...)
ctx.error(...)
```

تاريخيًا، كانت هذه Messages تُرسل إلى **Client** في صورة MCP logging notifications.

### ملاحظة مهمة عن Deprecation

يذكر المصدر أن Protocol-level logging أصبحت Deprecated ضمن توجه Specification بتاريخ 2026-07-28. وبالنسبة إلى Servers الجديدة، يوصي باستخدام Python logging العادي بدل إرسال Logs عبر MCP.

يهم هذا التمييز:

| أسلوب Logging | الوجهة | التوصية الحديثة في المصدر |
|---|---|---|
| MCP protocol logging | Client application | Legacy compatibility فقط |
| Python logging | وجهة Logging العادية في Server مثل stderr/File/Collector | مفضلة للـ Servers الجديدة |

### لماذا تظل Logs مهمة؟

سواء استخدمت Legacy MCP logging أو Server logging عادية، تساعد Logs المفيدة في تشخيص:

- أي Operation تم تنفيذها،
- أي Request فشلت،
- Timing وLatency،
- Capability changes،
- Cancellations،
- حالة server غير متوقعة (Unexpected server state).

## 6. Manual notifications عندما تتغير قدرات Server

قد تتغير Tools أو Prompts أو Resources في Server أثناء Runtime. وإذا كانت Clients تخزن هذه Lists في Cache، فهي تحتاج Signal تخبرها بإعادة Refresh.

Methods الحديثة التي يصفها المصدر هي:

```text
notify_tools_changed()   — إشعار بتغير قائمة الأدوات
notify_prompts_changed()   — إشعار بتغير قائمة الـ Prompts
notify_resources_changed()   — إشعار بتغير قائمة الموارد
notify_resource_updated(uri)   — إشعار بتحديث مورد محدد
```

تعني الثلاثة الأولى أن **List نفسها تغيرت**. أما الأخيرة فتعني أن **Resource معروفة واحدة تغيرت**.

### نموذج subscriptions/listen

في Modern protocol model الذي يصفه الفصل، تقوم Clients بالاشتراك في Change notifications عبر Request باسم `subscriptions/listen`. وتنشر Server أحداث التغيير، ثم يرسل SDK هذه Events إلى Listening streams المطابقة.

إذا لم يكن هناك Client يستمع، فإن نشر Notification لا يسبب Error — ببساطة لا يوجد Recipient.

### يجب على Server code إعلان التغيير

يدير SDK Mechanics الخاصة بالتسليم، لكنه لا يعرف تلقائيًا أن Business logic الخاصة بك غيرت Tool list أو Resource. تقع مسؤولية استدعاء Notification helper المناسبة بعد Mutation على Server code.

### Legacy compatibility

يصف المصدر أيضًا Methods أقدم على مستوى Session من نوع `send_*` notifications لإصدارات Protocol السابقة. وقد تحتاج Server تريد دعم Clients قديمة وحديثة إلى كلا المسارين.

## 7. Pagination لقوائم Discovery الكبيرة

تسمح Pagination للـ Server بإعادة List كبيرة في Pages يمكن التعامل معها بدل Response ضخمة واحدة.

يذكر المصدر أن Pagination تنطبق على List operations:

- `resources/list`،
- `resources/templates/list`،
- `prompts/list`،
- `tools/list`.

ولا يصف Pagination لـ Normal tool calls أو Resource reads.

### نموذج Cursor

```text
Client تطلب First page
        ↓
Server تعيد Items + next_cursor
        ↓
Client تكرر Request مع Cursor
        ↓
Server تعيد Next page + ربما Cursor أخرى
        ↓
عدم وجود next_cursor = انتهى
```

ينبغي أن تكون Cursor Opaque بالنسبة إلى Client. داخليًا، قد تستخدم Server شيئًا بسيطًا مثل List index، لكن على Client فقط تخزين Token وإعادتها.

### متى تكون Pagination مناسبة؟

يشدد المصدر على أن معظم Servers لا تحتاج إليها. فإذا كانت Server تعرض مئات أوآلاف Tools مثلًا، فقد تكون Pagination تعالج عرضًا لمشكلة أعمق في Interface design.

### لماذا تظهر Low-level API هنا؟

تولد High-level API تلقائيًا Primitive-list handlers. ولعرض Custom pagination logic، ينتقل المصدر إلى Low-level server API حتى يستطيع التحكم مباشرة في List response.

## 9. Resolvers: Dependency injection قبل تنفيذ Tool

Resolvers من أهم أفكار Implementation في هذا الفصل.

تقوم Resolver بحساب أوالحصول على Value **قبل تنفيذ Tool body**، ثم يقوم SDK بحقن هذه Value داخل Parameter.

مفاهيميًا:

```text
تصل Tool call
      ↓
SDK يفحص Resolved parameters
      ↓
Resolver تطلب External value
      ↓
SDK يتحقق من Response
      ↓
يتم حقن Resolved value
      ↓
يُنفذ Tool body
```

لا يلزم أن تظهر Resolved parameter داخل Model-visible tool input schema، وهذا مفيد عندما لا ينبغي لـ Model اختراع هذه Value بنفسها.

### Resolver dependencies

يشرح المصدر أن Resolvers يمكن أن تعتمد على:

- Ordinary tool arguments بالاسم،
- كائن Context،
- Values من Resolvers أخرى.

يحلل SDK Dependency graph هذه وقت Registration، ويرفض Cycles، ويتأكد من عدم تنفيذ Resolver نفسها أكثر من مرة بلا داعٍ داخل Tool call واحدة.

## 10. Elicitations: طلب Structured user input

تسمح Elicitation لـ Server workflow بطلب معلومات مباشرة من User عبر Client application.

تشمل الأمثلة:

- طلب Clarification،
- جمع Shipping address،
- اختيار Option،
- تأكيد Decision،
- ملء Form صغيرة.

توفر Server Schema ورسالة تشرح ما تحتاج إليه. وتعرض Client واجهة مناسبة وتحصل على Consent.

### ثلاث نتائج ممكنة

يمكن لـ User:

- **Accept** — توفير المعلومات المطلوبة،
- **Decline** — رفض Request صراحة،
- **Cancel** — ترك Interaction دون رفض صريح.

ينبغي لـ Tool التعامل عمدًا مع الحالات الثلاث.

### Form schemas محدودة عمدًا

يذكر المصدر أن Elicitation form schemas تستخدم Subset مقيدة من Primitive JSON types مثل Strings وNumbers وBooleans وEnums. يحول SDK حقول Pydantic المدعومة إلى Client-facing schema ويتحقق من Structure الخاصة بالـ Response.

لكن هذا Structural validation لا يكفي وحده. قد تحتاج Tool أيضًا إلى Semantic validation:

- هل Email معقول فعلًا؟
- هل Address تقع داخل Delivery region مدعومة؟
- هل Numeric value منطقية في Business domain؟

### تصميم حساس للـ Consent

يحذر الفصل بصورة محددة من طلب Sensitive information بصورة عادية عبر Form elicitations.

### URL mode

ينبغي لبعض Interactions أن تحدث **خارج Model/Client data path**، مثل:

- OAuth consent،
- Payment pages،
- Password entry.

تسمح URL elicitation للـ Server بطلب أن يكمل User الإجراء في Browser دون إرسال تلك Secrets عبر Model context.

## 11. Sampling: وصول Legacy إلى LLM الخاصة بالـ Client

تسمح Sampling للـ Server بطلب Model completion من LLM الموجودة في Client application.

يمكن لذلك دعم Workflows مثل:

- طلب شرح Computed result من Model،
- استخدام Model للتصنيف داخل Tool workflow،
- تخطيط مجموعة Server-side steps،
- تحويل Intermediate data.

### تحذير Deprecation

يذكر المصدر صراحة أن Sampling أصبحت Deprecated في Specification revision بتاريخ 2026-07-28، ويوصي بأن تقوم Servers الجديدة بالIntegration مباشرة مع LLM provider بدل استعارة Model الخاصة بالـ Client.

لذلك ينبغي دراسة Sampling أساسًا لفهم Existing/Legacy systems وResolver patterns.

### توقع Human-in-the-loop

من المتوقع أن تطلب Client موافقة User قبل السماح لـ External server باستهلاك Model resources أوحقن Server-generated prompt داخل Model session الخاصة بالمستخدم.

لذلك يجب أن تكون Server مستعدة للرفض.

### Sampling result

قد تحتوي Returned result على Text أو Image أو Audio content، وتحدد أي Model تم استخدامها ولماذا توقفت Generation.

ينبغي لـ Server التحقق من Returned content type بدل افتراض أنها Text.

### Model preferences مجرد Hints وليست Commands

يصف المصدر Model preferences مثل:

- Cost priority،
- Speed priority،
- Intelligence priority،
- تلميحات عائلة النموذج (Model-family hints).

لا تكون Client ملزمة باتباعها حرفيًا. لذلك ينبغي ألا تجعل Server صحة العملية تعتمد على الحصول على Model بعينها.

### Prompt injection ما تزال مهمة

إذا تم إدخال Tool arguments داخل Sampling prompt، فتحقق منها كما تتحقق من Dynamic SQL parameters أو أي Untrusted input آخر. قد يقلل Validation الصارم جدًا من Utility، لذلك الهدف هو تحقيق توازن منطقي بين Security وFlexibility.

## 12. Roots: تنسيق Filesystem وليس Security للـ Filesystem

تسمح Roots للـ Client بإبلاغ Server عن Filesystem locations التي يُفترض أن تعمل Server داخلها.

قد تعرض Client Project directory عبر Directory picker، مما يسمح لـ Local server بمعرفة Workspace التي يقصد User استخدامها.

### تحذير Deprecation

يذكر المصدر أن Roots أصبحت Deprecated في Revision بتاريخ 2026-07-28. وينبغي لـ Servers الجديدة التفكير بدلًا من ذلك في Paths ضمن Tool arguments أو Resource URIs أو Server configuration.

### أهم قاعدة في Roots

**Roots ليست Security boundary.**

ما تزال Local server process تعمل بالصلاحيات التي يوفرها Operating system لتلك Process. ويمكن لـ Server ضارة أوبها Bug تجاهل Root معلنة ما لم تمنع Enforcement mechanism أخرى الوصول.

تأتي الحدود الفعلية من أشياء مثل:

- ما إذا كان User يثبت/يشغل Server أصلًا،
- Process sandboxing،
- OS permissions،
- Container/VM isolation،
- ضوابط الوصول على مستوى التطبيق (Application-level access controls).

### التحقق الصحيح من Paths

بالنسبة إلى Compatibility مع Legacy roots، يعرض المصدر Path check أكثر أمانًا:

1. Resolve للـ Requested path لتطبيع `..` segments وSymlinks.
2. Decode للـ File URI إلى Operating-system path.
3. Resolve للـ Root path أيضًا.
4. استخدم Path-aware containment check مثل `is_relative_to()`.

لا تعتمد على Naive string-prefix checks، لأن Paths ذات Prefixes المتشابهة يمكن أن تتجاوزها.

### قيد Locality

يذكر المصدر أن Server تتعامل عمومًا مع Files على Machine التي تعمل عليها Server نفسها؛ ولا يوفر SDK بطريقة سحرية Remote access إلى Filesystem الخاصة بالـ Client.

## 13. Request cancellation وGraceful cleanup

تحتاج Long-running operations إلى وسيلة تسمح لـ User بإيقافها.

يشرح الفصل أن Cancellation behavior تختلف حسب Transport وProtocol version، لكن Python SDK يقوم بتوحيد معظم التعامل.

### stdio

ترسل Client Cancellation notification تحدد Request التي يجب إيقافها.

### Modern Streamable HTTP

يمكن إغلاق Per-request stream، ويفسر SDK هذا Disconnection بوصفه Cancellation للـ Running handler المرتبط.

### الدرس العام على جانب Server

بغض النظر عن Transport، تظهر Cancellation في النهاية للـ Running handler على هيئة Cancellation للـ Task الخاصة بها. ولذلك يجب أن تكون Cleanup داخل Operation نفسها.

### لماذا نعيد Raise؟

Cancellation هي Control flow وليست Business error عادية قابلة للاسترداد. بعد Cleanup، تحافظ إعادة Raise على Cancellation signal حتى يستطيع Framework إنهاء Request بصورة صحيحة.

### معالج الإشعارات الاختياري (Optional notification handler)

يمكن لـ Separate cancellation-notification handler توفير Metadata مثل Request ID وClient-supplied reason عندما تكون Notification متاحة. وهي مفيدة للـ Observability، لكن يشدد المصدر على أن SDK ينفذ Cancellation الفعلية بالفعل.

### ما الذي ينبغي أن تفعله Graceful cancellation؟

- توقف العمل بسرعة،
- تحرر Locks/Files/Network resources،
- تنفذ Rollback للـ Partial state عند الملاءمة،
- تتجنب Commit لعملية غير مكتملة،
- تسجل Context مفيدة،
- لا تبتلع Cancellation دون قصد.

## 14. تجميع الفصل: تصميم MCP server ناضجة

تظهر القيمة الحقيقية لهذه Features عندما تعمل معًا.

فكر في Tool طويلة لتنفيذ Deployment analysis:

```text
1. Client تستدعي deployment_analysis(...)
2. Resolver قد تطلب اختيار Environment من User عبر Elicitation
3. Tool تبدأ العمل
4. Context ترسل Progress دوريًا
5. Tool تقرأ Database/Cache state تديرها Lifespan
6. قد تتغير Resource data
7. Server ترسل Resource update notification
8. يمكن لـ Client إلغاء Operation
9. تعمل Tool cleanup
10. تعاد Final result إذا لم يتم Cancellation
```

يوضح ذلك تحولًا مهمًا: تطوير MCP server متقدمة لا يعني إضافة Protocol tricks معزولة. بل يعني إنشاء Interaction تظل مفهومة وآمنة وسريعة الاستجابة وقابلة للتعافي عبر Request lifecycle كاملة.

### قواعد تصميم عملية من الفصل

- استخدم Completions فقط عندما تحسن Input UX فعليًا.
- تعامل مع `Context` بوصفها Bridge الأساسية إلى Request/Session/Server state.
- فضّل Normal server logging في الأنظمة الجديدة بدل Protocol logging التي أصبحت Deprecated.
- أرسل Progress للعمليات الطويلة فعلًا.
- أخبر Clients عندما تتغير Dynamic primitive/resource state.
- استخدم Pagination فقط عندما تكون List كبيرة حقًا.
- لا تفترض أبدًا وجود Optional client capabilities.
- استخدم Resolvers لإبقاء Values المشتقة من User/Client خارج Model-controlled schema.
- تعامل مع Decline/Cancel paths بوصفها Outcomes من الدرجة الأولى.
- تعامل مع Sampling/Roots التي أصبحت Deprecated بوصفها Compatibility concepts لا Default architecture للـ Servers الجديدة.
- اجعل Long-running work دائمًا آمنة عند Cancellation.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: «Completions هي Model completions.»

**لماذا هذا خطأ:** المقصود بـ Completions في هذا الفصل هو Autocomplete suggestions لمعاملات Prompt أو Resource template.

### المفهوم الخاطئ 2: «كائن Context جزء من MCP specification.»

**لماذا هذا خطأ:** يقدم المصدر `Context` بوصفه Convenience abstraction من Python SDK.

### المفهوم الخاطئ 3: «Protocol-level logging هي طريقة Logging الحديثة المفضلة.»

**لماذا هذا خطأ:** يذكر المصدر أن In-protocol logging أصبحت Deprecated، ويوصي بـ Python logging العادية للـ Servers الجديدة.

### المفهوم الخاطئ 4: «SDK يعلن تلقائيًا كل Runtime change للـ Clients.»

**لماذا هذا خطأ:** يجب على Server code استدعاء Change-notification helper المناسبة صراحة.

### المفهوم الخاطئ 5: «يمكن عمل Pagination لكل شيء.»

**لماذا هذا خطأ:** يقصر الفصل Pagination على List operations مثل `tools/list` و`resources/list`.

### المفهوم الخاطئ 6: «إذا كانت Client لا تدعم Resolver capability، يمكن دائمًا تشغيل Tool بصورة طبيعية.»

**لماذا هذا خطأ:** Required resolver capability قد تجعل SDK يرفض Operation قبل تنفيذ Tool body.

### المفهوم الخاطئ 7: «ينبغي أن تملأ Model قيم Elicitation.»

**لماذا هذا خطأ:** تحصل Resolver على Value من User/Client وتحقنها خارج Model-visible tool argument schema.

### المفهوم الخاطئ 8: «Roots تؤمّن Host filesystem.»

**لماذا هذا خطأ:** تعبّر Roots عن Intended scope لكنها لا تفرض OS-level access.

### المفهوم الخاطئ 9: «يمكن لـ Server فرض Model المفضلة نفسها بدقة أثناء Sampling.»

**لماذا هذا خطأ:** Model preferences هي Hints، وقد تختار Client شيئًا مختلفًا.

### المفهوم الخاطئ 10: «Cancellation مجرد Error أخرى يمكن Catch لها وتجاهلها.»

**لماذا هذا خطأ:** Cancellation هي Control flow. ينبغي للـ Handler تنفيذ Cleanup ثم عادةً إعادة Raise للـ Cancellation signal.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Completion | Autocomplete suggestion تقدمها Server لمعامل Prompt أو Resource template |
| `CompletionContext` | معلومات Optional عن Arguments السابقة متاحة لـ Completion handler |
| Icon | Metadata لـ Server أو Primitive يمكن لـ Client عرضها في UI |
| `Context` | كائن Python SDK يمنح Handlers وصولًا إلى Server وSession وRequest وCapability وLogging وProgress وNotification information |
| `ServerSession` | Lower-level session interface تستخدمها Server للتواصل مع Connected client |
| Request context | Per-request state تتضمن Request ID وMetadata وMethod/Params وLifespan state وSession |
| Protocol logging | Legacy MCP logging notifications تُرسل من Server إلى Client |
| Progress notification | Update من Server توضح مدى تقدم Long-running operation |
| إشعار تغير قائمة الـ Primitives (Primitive list notification) | Signal بأن Tools أو Prompts أو Resources المتاحة من Server تغيرت |
| إشعار تحديث المورد (Resource update notification) | Signal بأن Content وراء Resource URI واحدة تغيرت |
| Pagination | تقسيم Large list operation إلى عدة Cursor-based pages |
| Cursor | Opaque token تحدد موضع استكمال الصفحة التالية |
| Client capability | Optional feature تعلن Connected client أنها تستطيع توفيرها |
| Resolver | Mechanism في SDK تحصل على Value أوتحسبها وتحقنها قبل تنفيذ Tool body |
| Elicitation | Request للحصول على Structured user input أو Browser-based continuation عبر Client |
| Accepted elicitation | User وافق وقدم المعلومات المطلوبة |
| Declined elicitation | User رفض Request صراحة |
| Cancelled elicitation | User ترك Interaction دون Approval/Decline صريح |
| Sampling | Capability أصبحت Deprecated وتسمح لـ Server بطلب استخدام LLM الخاصة بالـ Client |
| Model preferences | Sampling hints عن Model family ومقايضات مثل Cost/Speed/Intelligence |
| Roots | Capability أصبحت Deprecated تصف Filesystem locations التي يقصد Client أن تستخدمها Server |
| Cancellation | Mechanism لإيقاف In-flight request وتشغيل Server cleanup |
