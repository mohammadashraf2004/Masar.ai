## 2. تعتمد احتياجات Infrastructure على Scale و Specialization

يحذر الفصل من نسخ Infrastructure الخاصة بشركة أخرى بصورة عمياء.

تحتاج Organizations المختلفة إلى مستويات مختلفة من الاستثمار.

### Small أو Ad hoc use cases

قد لا يحتاج Team ينفذ Analytics أحيانًا أو Application صغيرة واحدة إلى أكثر من Python و Notebooks و Data-processing libraries و Framework متوافقة مع Deployment target.

### أنظمة عالية التخصص

قد تبرر Applications مثل Autonomous systems أو Search شديدة Scale بناء Custom infrastructure بسبب Requirements غير معتادة للـ Latency أو Accuracy أو Scale أو Hardware.

### منتصف الطيف

تستخدم معظم Companies الـ ML في عدة Business problems شائعة على Scale معقولة، مثل:

- Fraud detection،
- Price optimization،
- Churn prediction،
- Recommendation.

يمكن لهذه Organizations غالبًا الاستفادة من General-purpose ML infrastructure أكثر Standardization بدل بناء كل شيء من الصفر.

مبدأ التصميم هو:

> **اختر Infrastructure وفق Workload و Organization و Scale الفعلية لديك — لا من أجل Prestige.**

## 3. طبقات Infrastructure الأربع

ينظم الفصل ML infrastructure في أربع Layers.

| Layer | المسؤولية الأساسية |
|---|---|
| Storage و Compute | تخزين Data وتوفير Resources تنفذ ML workloads. |
| Resource management | Scheduling و Coordination وتخصيص Resources للـ Jobs والـ Services. |
| ML platform | توفير Shared ML-specific capabilities مثل Deployment و Model stores و Feature stores. |
| Development environment | منح Practitioners مكانًا لكتابة Code واختبارها وعمل Version لها وتجربة أفكارهم. |

تشكل Storage و Compute الأساس لأن كل ML workflow تحتاج في النهاية إلى Data و Computation.

Development environment هي Layer التي يتفاعل معها Practitioners بصورة مباشرة أكثر.

أما ML platform فهي Shared layer أعلى مستوى تظهر عادةً بعد امتلاك Organization عدة ML use cases ورغبتها في إعادة استخدام Capabilities مشتركة.

## 4. Storage و Compute هما الأساس المادي

Storage layer هي المكان الذي تُجمع فيه Data وتُخزن.

قد تكون:

- Local disk،
- Object storage،
- Data warehouse،
- On-premises data center،
- Cloud storage،
- أوعدة Systems معًا.

يركز الفصل بصورة أكبر على Compute لأن مفاهيم Data systems غُطيت سابقًا.

تحتوي **Compute layer** على Resources و Mechanisms المستخدمة لتنفيذ Jobs.

قد تكون Compute unit صغيرة أوكبيرة:

- CPU thread،
- CPU أو GPU core،
- Multi-core machine،
- Virtual machine،
- Short-lived serverless-style unit،
- Spark أو Ray job،
- Kubernetes pod.

تعرض Platforms المختلفة Abstractions مختلفة، لكن السؤال الأساسي واحد: **ما Resource التي ستنفذ هذه Workload؟**

## 5. Memory و Operation speed و Utilization و Bandwidth

يجب على Job تحميل Data إلى Memory قبل أن تعمل Computation عليها.

وهذا يجعل خاصيتين في Compute مهمتين بصورة خاصة:

1. مقدار Data الذي يمكن أن يتسع داخل Memory،
2. مدى سرعة تنفيذ العمل المفيد.

### Memory capacity

تسمح Memory الأكبر ببقاء Datasets أكبر أو Tensors أكبر أو Models أكبر داخل Memory.

### I/O bandwidth

حجم Memory وحده غير كافٍ. يحتاج System أيضًا إلى نقل Data إلى Memory ومنها بسرعة كافية لإبقاء Compute units مشغولة.

### FLOPS

كثيرًا ما يوصف Hardware باستخدام Floating-point operations per second.

لكن Theoretical FLOPS لا تخبرك بسرعة Workload الفعلية لديك.

### Utilization

إذا كان Machine يمكنها نظريًا تنفيذ مليون Floating-point operation لكل وحدة زمن، لكن Job تحقق 300,000 فقط، فإن Utilization تقريبًا:

```text
الاستخدام (Utilization) = Throughput المحقَّق / Throughput النظري
            = 0.3
            = 30%
```

قد تنتج Low utilization من Memory bottlenecks أو Poor parallelism أو Unsuitable workloads أوعدم توافق آخر بين Hardware و Software.

النصيحة العملية في المصدر هي Benchmark للـ Hardware باستخدام Workloads تشبه Tasks التي تهتم بها فعلًا بدل الاعتماد فقط على Theoretical FLOPS.

## 6. Public cloud مقابل Private data centers

تجعل Public cloud services الحصول على Storage و Compute سهلًا دون بناء Data center أولًا.

ويكون ذلك جذابًا بصورة خاصة للـ **Bursty ML workloads**.

قد يحتاج Team إلى Burst كبيرة من Compute أثناء Experimentation، ثم يحتاج إلى قدر أقل بكثير بعد ذلك. تسمح Cloud elasticity للـ Team بزيادة Resources وتقليلها بدل شراء Peak capacity بصورة دائمة.

### مزايا Cloud التي يؤكدها الفصل

- Startup سريع،
- Elastic capacity،
- Operational burden أقل،
- الدفع مقابل Resources عند الحاجة بدل امتلاك Peak capacity كاملة.

### Cloud مرنة وليست بلا حدود

تفرض Providers Resource quotas، وقد لا تتوفر دائمًا Capacity المطلوبة بشدة. كما يمكن للـ Discounted أو Interruptible capacity أن تعقد Workload design.

### قد تغير Cloud cost القرار عند Scale كبيرة

يشرح المصدر أن Organizations الكبيرة تنقل أحيانًا Workloads مختارة مرة أخرى إلى Infrastructure الخاصة بها لتقليل Long-term cost. يسمى ذلك **Cloud repatriation**.

يكون الابتعاد عن Cloud صعبًا لأن Private infrastructure تتطلب Up-front hardware investment و Engineering effort.

لذلك تنتشر Hybrid approach: إبقاء بعض Workloads في Cloud مع تشغيل Workloads مختارة تدريجيًا داخل Private infrastructure.

[[IMAGE_NEEDED: Public cloud versus private infrastructure trade-off | A comparison showing cloud elasticity and low startup burden versus private infrastructure's higher up-front investment and potential long-term cost control | Learner should notice that the economically attractive option can change with scale]]

## 7. يمكن لـ Multicloud تقليل Lock-in لكنها تزيد Complexity

توزع **Multicloud strategy** الـ Workloads عبر عدة Cloud providers.

تشمل Motivations محتملة:

- الوصول إلى نقاط القوة المختلفة للـ Providers،
- Pricing flexibility،
- تقليل الاعتماد على Vendor واحد،
- Organizational history أو Acquisitions.

الفصل واضح في أن Multicloud صعبة Operationally.

يزيد نقل Data بين Providers وجعل Systems متوافقة مع Environments متعددة و Orchestrating للـ Workloads عبر Clouds من Complexity.

وقد تحدث Multicloud بصورة غير مقصودة لأن Independent teams تختار Providers مختلفة أولأن Companies تم الاستحواذ عليها تجلب Existing infrastructure الخاصة بها.

المبدأ ليس أن Multicloud جيدة أوسيئة. بل إن تجنب Vendor lock-in يأتي معه Engineering cost حقيقية.

## 9. Notebooks قوية لأنها Stateful — وهذا أيضًا مصدر خطرها

تكون Notebooks مفيدة لـ Exploratory ML work لأنها تستطيع احتواء:

- Code،
- Plots،
- Images،
- Tables،
- Narrative analysis.

وهي أيضًا **Stateful**.

إذا كان تحميل Dataset كبيرة يستغرق وقتًا طويلًا وفشلت Cell 4، يمكن أن تظل State الخاصة بالـ Cells السابقة داخل Memory. وقد تحتاج فقط إلى إعادة تشغيل Step الفاشلة.

لكن Statefulness تسمح بتنفيذ Cells خارج Order.

```text
التنفيذ المتوقع:
1 → 2 → 3 → 4

History ممكنة للـ Notebook:
1 → 4 → 2 → 3 → 4
```

يمكن لهذا جعل Notebook تبدو وكأنها تعمل داخل Current session بينما تفشل عند Clean restart.

لذلك ينبغي الجمع بين Productivity الخاصة بالـ Notebook و Reproducibility discipline.

## 10. وحّد Environment قبل Debugging لـ "Ghosts"

يستخدم الفصل عدة أمثلة لـ Bugs ناتجة عن Environment differences.

قد يستخدم Engineer Package version مختلفة. وقد يستخدم آخر Python version مختلفة. وقد يمتلك Laptop جديد Processor architecture مختلفة.

لذلك قد تتصرف Code بصورة مختلفة رغم أن الجميع يعتقد أنهم يشغلون "Project نفسها".

يشمل Standardization المفيد:

- Exact package versions،
- Language/Runtime version،
- System dependencies،
- Environment setup instructions،
- وعندما يكون مناسبًا، Machine environment نفسها.

### بيئات التطوير السحابية

إحدى طرق Standardization الأقوى هي السماح للـ Engineers بالاتصال بالنوع نفسه من Cloud machine مع الاستمرار في استخدام Preferred local IDE عبر SSH.

تشمل Benefits التي يناقشها الفصل:

- Machine-specific setup problems أقل،
- IT support أسهل،
- Remote work أسهل،
- Centralized access control،
- تشابه أكبر بين Cloud development و Cloud production،
- الوصول إلى Data لا يمكن تنزيلها محليًا.

تشمل Trade-offs: Cost و Security policy و Setup work والحاجة إلى Good cloud hygiene.

## 11. Containers تجعل Environments قابلة لإعادة الإنتاج عبر Machines

يمكن لـ Production services أن تعمل عبر Machines كثيرة. وتحتاج Machines الجديدة بالضبط إلى Software environment التي تتطلبها Workload.

تعالج Container technology هذه Problem.

### Dockerfile

Sequence من Instructions تصف كيفية بناء Environment.

### Docker image

الـ Packaged environment التي يتم إنشاؤها من Dockerfile.

### Docker container

Running instance من تلك Image.

نموذج ذهني:

```text
Dockerfile = Recipe
Docker image = Mold/Template قابلة لإعادة الاستخدام
Container = Running instance منشأة من Image
```

يمكن بناء Images فوق Existing images — مثل Framework و GPU-aware base environment مع Project-specific dependencies.

تخزن **Container registry** الـ Images وتوزعها لإعادة الاستخدام.

## 12. قد تحتاج Pipeline steps المختلفة إلى Containers مختلفة

يمكن لـ ML application واحدة أن تحتوي Steps ذات Resource requirements مختلفة جدًا.

مثال:

- Featurization: تحتاج Memory كبيرة ولا تحتاج GPU كثيرًا،
- Training: تعتمد بقوة على GPU وتمتلك Memory profile مختلفة.

تشغيل كلتيهما على GPU instance مكلفة نفسها قد يهدر Resources.

تسمح Containers المنفصلة لكل Step بالعمل داخل Environment و Hardware الملائمين لها.

تساعد Containers أيضًا عندما تتعارض Dependencies — مثل احتياج Stage ين إلى Versions غير متوافقة من Library نفسها.

مع زيادة عدد Services تصبح Manual container management صعبة.

### Container orchestration

يمكن لـ Docker Compose تنسيق Containers على Host واحدة.

أما Distributed environment فتحتاج Orchestration أوسع. يقدم الفصل Kubernetes بوصفها المثال الأكبر لـ Networking و Scaling و Resource sharing والحفاظ على Service availability عبر Hosts.

## 13. انتقلت Resource management من تعظيم الندرة إلى Cost effectiveness

في Fixed private data centers تكون Compute حدًا صلبًا. إعطاء Resources أكثر لـ Job قد يعني أخذها من Job أخرى.

تغير Cloud elasticity هذه Optimization problem.

بدل أن نسأل فقط:

> كيف نحقق أقصى Utilization للـ Fixed hardware؟

تسأل Teams بصورة متزايدة:

> هل إنفاق Compute أكثر مبرر بما يوفره من Engineering time أو Business value؟

يؤكد المصدر أن Human engineering time قد تكون أغلى من Compute. وقد تكون أتمتة Workloads عقلانية اقتصاديًا حتى لو استخدمت Automation Hardware أكثر قليلًا.

## 14. Cron و Schedulers و Orchestrators تحل مشكلات مختلفة

تتميز ML workflows بشيئين:

1. أنها تتكرر،
2. وأن Steps الخاصة بها تعتمد بعضها على بعض.

### Cron

تشغّل Cron Command في Time محددة مسبقًا.

وهي جيدة من أجل:

```text
شغّل هذا Script كل ليلة الساعة 2 a.m.
```

لا تعبر Cron بصورة طبيعية عن Dependencies معقدة مثل:

```text
شغّل B فقط إذا نجحت A.
شغّل C إذا فشلت A.
```

### Scheduler

تفهم Scheduler الـ Jobs و Dependencies و Priorities و Retries و Queues و Resource requirements.

وهي تسأل:

> **متى ينبغي تشغيل كل Job، وما Resources التي تحتاجها Job؟**

### Orchestrator

تعمل Orchestrator على Infrastructure level أدنى — Machines و Clusters و Replicas و Services و Resource provisioning.

وهي تسأل:

> **من أين تأتي Resources المطلوبة، وكيف ينبغي الحفاظ على Infrastructure؟**

الحد الفاصل ليس نظيفًا تمامًا. بعض Tools تحتوي Scheduling و Orchestration features معًا.

## 15. تُمثَّل ML workflows طبيعيًا كـ DAGs

فكر في Workflow التالية:

1. اسحب Data الخاصة بالأسبوع الماضي،
2. استخرج Features،
3. درّب Model A،
4. درّب Model B،
5. قارن A و B،
6. انشر Winner.

توجد Dependencies:

```text
اسحب Data
    ↓
استخرج Features
   ↙       ↘
درّب A    درّب B
   ↘       ↙
قارن Models
      ↓
Conditional deployment
```

تعبر **Directed acyclic graph (DAG)** عن Execution order.

- **Directed**: توضح Edges أي Task تعتمد على أي Task،
- **Acyclic**: لا يمكن للـ Graph احتواء Endless dependency loop.

يمكن للـ Schedulers استخدام DAG لتحديد متى تصبح Tasks جاهزة، وكيف تعيد Retry للـ Failures، وما Resources التي ينبغي تخصيصها.

[[IMAGE_NEEDED: ML workflow DAG | Data ingestion flowing into feature extraction, branching to two model-training tasks, joining at comparison, then conditionally deploying the winner | Learner should notice parallel tasks, dependencies, and conditional execution]]

## 16. تعمل Data-science workflow-management tools فوق Individual jobs

تسمح Workflow-management tools للـ Teams بتعريف Multi-step workflows، غالبًا في صورة DAGs.

كل Step هي **Task**.

يمكن تعريف Workflow باستخدام:

- Python أو Programming language أخرى،
- Configuration مثل YAML.

ثم تعمل Workflow system مع Schedulers و Orchestrators لتنفيذ كل Task على Resources مناسبة.

يناقش الفصل Airflow و Prefect و Argo و Kubeflow و Metaflow ليس لإعلان Winner واحدة للجميع، بل لتوضيح Design choices مهمة في Workflow tools.

## 17. Airflow: Configuration as Code مع Limitations تاريخية

تعرّف Airflow الـ Workflows باستخدام Python وتوفر Ecosystem كبيرة من Operators للـ Databases و Clouds و Containers وأنظمة أخرى.

يسلط الفصل الضوء على ثلاث Limitations في Generation الخاصة بـ Airflow التي يناقشها المصدر:

### تحزيم الـ workflow بشكل متكتل (Monolithic)

قد يكون عزل Steps مختلفة تمتلك Dependencies متعارضة أمرًا غير مريح، رغم أن Container operators يمكن أن تساعد.

### محدودية تحويل الـ workflow إلى معاملات

يكون تشغيل Logical workflow نفسها باستخدام Experiment parameters مختلفة أقل طبيعية.

### Static DAG structure

يكون إنشاء Workflow steps جديدة تمامًا بصورة Dynamic أثناء Runtime صعبًا في Model الموصوفة.

حفزت هذه Limitations أنظمة Workflow لاحقة على التركيز أكثر على Dynamic و Parameterized behavior.

## 18. Prefect و Argo تؤكدان تحسينات مختلفة

### Prefect

يقدم الفصل Prefect باعتبارها تحسن Parameterized و Dynamic workflows مع الحفاظ على Approach موجهة لـ Python من نوع "Configuration as code".

يمكن استخدام Containerized isolation، لكن Containers ليست Central abstraction بالطريقة نفسها الموجودة في Argo.

### Argo

تجعل Argo كل Workflow step عبارة عن Container.

تُمثَّل Workflows الخاصة بها Declaratively في YAML ومصممة حول Kubernetes.

يسلط المصدر الضوء على Inconvenience أثناء Development: تشغيل Argo workflow محليًا يتطلب عادةً Environment شبيهة بـ Kubernetes أيضًا.

## 19. تحاول Kubeflow و Metaflow ربط Development بـ Production

إحدى مشكلات ML workflow الرئيسية هي أن Development يحدث غالبًا محليًا بينما يحدث Full-scale execution داخل Cloud أو Production infrastructure.

تحاول Kubeflow و Metaflow تقليل Boilerplate المطلوبة للانتقال بين هاتين Environment ين.

### Kubeflow

يصف الفصل Kubeflow Pipelines بأنها تعمل فوق Infrastructure قائمة على Kubernetes/Argo. وهي تقدم ML-oriented workflow abstractions لكنها قد تظل تحتاج قدرًا كبيرًا من Docker/YAML configuration.

### Metaflow

يسلط المصدر الضوء على Experience تعتمد على Python/Decorators حيث يمكن لكل Step إعلان Library و Resource requirements الخاصة بها.

يمكن لـ Step صغيرة العمل محليًا بينما تُفوَّض GPU-heavy step إلى Cloud batch infrastructure.

الفكرة المهمة ليست Recommendation لمنتج معين. بل Abstraction مرغوبة:

> **استخدم Logical workflow نفسها عبر Local experimentation و Production-scale execution، مع السماح بتغير Infrastructure details تحت كل Task.**

## 20. تظهر ML platform عندما تحتاج Teams كثيرة Capabilities نفسها

تبني Early ML teams عادةً Tools من أجل Application واحدة — مثلًا، يحتاج Recommender system إلى Deployment و Features و Model management و Monitoring.

مع بناء Teams إضافية لـ ML applications، تكتشف Organization أن كثيرًا من هذه Capabilities مشتركة.

يمكن عندئذٍ لـ **ML platform** مخصصة أن توفر Reusable infrastructure عبر Teams.

يركز المصدر على ثلاثة Components شائعة في ML platform:

1. Model deployment،
2. Model store،
3. Feature store.

Monitoring مهمة أيضًا لكن الفصل السابق غطاها بصورة منفصلة.

عند تقييم Platform tools، يقترح الفصل النظر على الأقل إلى:

- Compatibility مع Cloud أو Private infrastructure لديك،
- Trade-offs بين Open-source/Self-hosted و Managed services.

## 21. ينبغي لـ Model deployment services دعم Serving modes التي تحتاجها فعلًا

تساعد Deployment service على نقل Model و Dependencies الخاصة بها إلى Production وجعل Predictions قابلة للوصول.

يظل Serving distinction السابق مهمًا:

- Online prediction تنتج Predictions استجابةً لـ Requests،
- Batch prediction تنتج أوتخزن Predictions كـ Batch jobs.

يحذر الفصل من الخلط بين **Batching للـ Online requests** و**True batch prediction**.

وقد تستخدم Organization Infrastructure منفصلة لهذين Serving pattern ين.

كما ينبغي لـ Deployment platform أن تجعل Production tests المطلوبة عملية، مثل Controlled deployment techniques التي نوقشت في الفصل السابق.

## 22. Model store ليست مجرد Folder من Serialized models

تخيل أن Production model بدأت تفشل مع Subset من Inputs.

يحتاج Debugging team إلى أكثر من File مثل `.pkl` أو`.pt` أو Model file أخرى.

يحتاجون إلى الإجابة عن أسئلة مثل:

- من يملك هذه Model؟
- ما Exact model version الموجودة في Live؟
- أي Feature definition استخدمتها؟
- أي Featurization code أنتجت Inputs؟
- ما Data التي دربتها؟
- ما Environment/Dependencies المطلوبة؟
- ما Code و Hyperparameters التي أنشأتها؟
- ما Evaluation results التي حققتها؟

إذا كانت هذه Pieces موزعة عبر Systems منفصلة بلا Reliable references، فقد يصبح Reproducing لـ Production failure صعبًا للغاية.

هذا هو الغرض الحقيقي من Model store: **جعل Production model قابلة للاكتشاف وإعادة الإنتاج والصيانة.**

## 23. ما الذي ينبغي ربطه بـ Production model؟

يسرد الفصل ثماني Categories عامة من Artifacts.

### 1. Model definition

Structure الخاصة بالـ Model و Loss definition و Architecture و Layer sizes و Configuration المرتبطة بها.

### 2. Model parameters

القيم Learned للـ Parameters المطلوبة لإعادة بناء Trained model.

### 3. Featurize و Predict functions

الـ Code التي تحول Request إلى Model features وتحول تلك Features إلى Prediction.

### 4. Dependencies

Runtime requirements مثل Python و Package versions، وغالبًا يتم التقاطها داخل Container.

### 5. Data

Pointers أو Identifiers أو Versions تصف أي Data أنتجت Model.

### 6. شيفرة توليد الـ Model

Training code وتفاصيل مثل:

- Framework،
- Split construction،
- Experiment count،
- Hyperparameter search space،
- Final hyperparameters.

### 7. Experiment artifacts

Loss curves و Metrics و Reports و Outputs أخرى من Model development.

### 8. Tags

Metadata للاكتشاف والملكية، مثل Responsible team و Business task.

## 24. تعالج Feature stores ثلاث مشكلات أساسية

يُستخدم مصطلح **Feature store** بصورة مختلفة بين Tools، لكن الفصل يحدد ثلاث Problems أساسية.

### 1. Feature management

تعيد Models مختلفة استخدام Features نفسها كثيرًا.

يمكن لـ Feature store أن تعمل كـ Catalog حيث تستطيع Teams:

- اكتشاف Features موجودة،
- إعادة استخدامها،
- توثيق Ownership،
- التحكم في Access إلى Sensitive features.

### 2. Feature computation

ما تزال Feature definition بحاجة إلى التنفيذ.

إذا كانت Feature مكلفة في Calculation وتحتاجها Models كثيرة، احسبها مرة واحدة وأعد استخدام أوتخزين Result بدل تكرار Expensive work بصورة مستقلة.

في هذا الدور، تبدأ Feature store في التشابه مع Specialized data system.

### 3. Feature consistency

تستخدم Training و Inference غالبًا Execution environments مختلفة.

قد تُكتب Feature مرة في Development language لـ Historical batch data ثم يُعاد كتابتها في Language أخرى لـ Real-time serving.

تزيد Duplicated logic من احتمال Divergence بين Feature definition ين.

تهدف Modern feature stores إلى توحيد Feature definition المستخدمة في Batch training و Online/Streaming inference، ما يقلل Training-serving inconsistency.

[[IMAGE_NEEDED: Feature-store three-problem model | A central feature store with three branches labeled catalog/management, computation/storage, and training-serving consistency, connected to multiple models | Learner should notice that 'feature store' can refer to several related but distinct capabilities]]

## 25. تختلف Capabilities الخاصة بالـ Feature stores بين Tools

يشدد الفصل على أن Feature stores كانت Category ما تزال تتطور في الفترة الزمنية الخاصة بالمصدر.

قد توفر Systems مختلفة Subsets مختلفة من Capabilities:

- Feature definitions فقط،
- Definitions مع Computation،
- Batch features،
- Online features،
- Streaming features،
- Validation مقابل Feature schemas،
- Access management و Discovery.

لذلك شراء شيء يسمى "Feature store" لا يضمن أنه يحل Problems الثلاث كلها. قيّم Actual capabilities مقابل احتياجات System.

## 26. Build versus Buy قرار Strategic في Infrastructure

تستخدم معظم Companies خليطًا من Managed services و In-house infrastructure.

في Extreme، يمكن لـ Vendor إدارة ML application كلها تقريبًا.

وفي Extreme الآخر، قد تجبر Regulatory أو Technical requirements Organization على تشغيل كل شيء تقريبًا بنفسها.

يسلط الفصل الضوء على ثلاثة Decision factors رئيسية.

### العامل 1: مرحلة الشركة

تستفيد Early companies غالبًا من Vendors لأن Speed أهم من Infrastructure customization.

ومع نمو Usage، يمكن أن تصبح Vendor cost كبيرة بما يكفي لتبرير Internal investment.

### العامل 2: الميزة الاستراتيجية

إذا كانت Capability مركزية لما تريد Company أن تتفوق فيه بشدة، فقد يكون Building لهذه Layer أوالسيطرة العميقة عليها مبررًا.

أما إذا لم تكن Strategically differentiating، فيمكن للشراء توفير Engineering effort.

### العامل 3: نضج الأدوات المتاحة

أحيانًا تريد Team الشراء لكن لا يوجد External product يلبي Requirements. لذلك قد يبني Early adopters Custom infrastructure ببساطة لأن Market غير ناضجة.

## 27. Building ليست أرخص تلقائيًا

تمتلك Custom infrastructure تكاليف تتجاوز Hardware أو Cloud bills.

أنت تدفع أيضًا مقابل:

- Engineers لبنائها،
- Engineers لصيانتها،
- Operational support،
- Migrations،
- Integrations مع بقية Stack،
- Adoption أبطأ للتقنيات الجديدة عندما لا تلائمها Custom interfaces.

يصف الفصل Problem الأخيرة باعتبارها نوعًا من **Integration cost**: يمكن لـ Infrastructure عالية Customization أن تجعل Future tools صعبة Adoption.

للشراء Costs أيضًا:

- Recurring vendor fees،
- Vendor lock-in،
- Data/Privacy considerations،
- Integration constraints،
- تحكم أقل في Roadmap و Behavior.

لا توجد إجابة صحيحة Universal. قرار Build-versus-buy يعتمد بقوة على Context.

## 28. تجميع Infrastructure stack كاملة

يمكن الآن فهم Production ML stack عملية بوصفها Layers متصلة:

```text
Data scientists / ML engineers
            ↓
Development environment
  IDEs, Notebooks, Versioning, CI/CD
            ↓
ML platform
  Deployment, Model store, Feature store
            ↓
Workflow وResource management
  DAGs, Schedulers, Orchestrators, Containers
            ↓
Storage وCompute
  Data systems, CPU/GPU, Cloud/Private infrastructure
```

الرسالة الأوسع في الفصل هي أن **نقل ML إلى Production مشكلة Infrastructure بقدر ما هي Modeling problem**.

أفضل Infrastructure ليست Stack تحتوي أكبر عدد من Tools. بل Stack التي تسمح للـ Practitioners بتطوير ML applications الفعلية الخاصة بالـ Organization وإعادة إنتاجها ونشرها وتشغيلها وتحديثها بـ Cost و Complexity مقبولتين.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: كل ML team تحتاج ML platform كاملة

ينبغي أن يعكس Infrastructure investment عدد Use cases ودرجة Specialization و Scale والاحتياجات Organizational.

### المفهوم الخاطئ 2: FLOPS النظرية الأعلى تضمن ML workloads أسرع

تعتمد Actual speed على Utilization و Data movement و Memory وخصائص Workload.

### المفهوم الخاطئ 3: Cloud compute لا نهائية

Clouds مرنة لكنها تظل تمتلك Quotas و Capacity constraints و Operational trade-offs.

### المفهوم الخاطئ 4: Multicloud تحميك تلقائيًا من كل Vendor problem

تقلل بعض Dependency لكنها تضيف Complexity كبيرة في Data movement و Orchestration.

### المفهوم الخاطئ 5: Notebook تعمل مرة واحدة تعني أنها Reproducible

يمكن لـ Hidden state و Out-of-order execution جعل Notebook صعبة إعادة الإنتاج من Clean environment.

### المفهوم الخاطئ 6: Containers و Virtual environments تحلان Problem نفسها تمامًا

يستخدم الفصل Containers لإعادة إنشاء Executable environment أوسع عبر Machines يتم تخصيصها Dynamically.

### المفهوم الخاطئ 7: Cron هي Workflow orchestrator

تتعامل Cron مع Fixed-time execution، لكنها لا تتعامل مع Dependencies و Retries و Conditions و Resource logic الغنية في ML workflows.

### المفهوم الخاطئ 8: Kubernetes و Workflow scheduler شيء واحد

تتداخل مسؤولياتهما، لكن Scheduler تعمل أساسًا على Jobs/Workflows بينما Orchestrator تدير Lower-level resources و Services.

### المفهوم الخاطئ 9: Model store مجرد Object storage

يمكن لـ Object storage الاحتفاظ بـ Model binary، لكن Reliable model operations تحتاج Lineage و Ownership و Code و Dependencies و Data references و Experiment artifacts.

### المفهوم الخاطئ 10: كل Feature store تمتلك Capabilities نفسها

الـ Category واسعة؛ وتختلف Tools في Management و Computation و Streaming support و Validation و Consistency features.

### المفهوم الخاطئ 11: Building للـ Infrastructure أرخص دائمًا من Buying

Building يضيف أيضًا Costs خاصة بالـ Engineering و Maintenance و Integration و Future innovation.
