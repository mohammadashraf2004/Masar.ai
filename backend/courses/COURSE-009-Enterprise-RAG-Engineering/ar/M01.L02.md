## 1. مكدس RAG الأساسي: Pipeline وليس Model واحدًا

قدّم الفصل 1 فكرة Grounding لـ LLM باستخدام معرفة خارجية. ويحوّل الفصل 2 هذه الفكرة إلى Pipeline هندسية. نظام RAG الأساسي ليس Model واحدًا ولا Database واحدة. بل هو سلسلة من المكونات التي تحوّل المعلومات الخام إلى تمثيلات قابلة للبحث، وتسترجع أدلة مفيدة لطلب معين، ثم تطلب من Generative Model إنتاج استجابة اعتمادًا على تلك الأدلة.

من المفيد ذهنيًا تقسيم النظام إلى تدفقين:

```text
تدفق الإدخال (INGESTION FLOW)
البيانات الخام (raw data)
→ تحليل المستند (parse)
→ تقسيم النص (chunk)
→ إنشاء Embedding وفهرسة (embed / index)
→ تخزين تمثيلات قابلة للبحث (store searchable representations)

تدفق الاستعلام (QUERY FLOW)
طلب المستخدم (user request)
→ إعادة الصياغة من أجل Retrieval (rewrite for retrieval)
→ استرجاع Candidates (retrieve candidates)
→ إعادة الترتيب والاختيار (rerank / select)
→ تجميع Prompt (assemble prompt)
→ LLM توليدي (generative LLM)
→ الاستجابة (response)
```

يجهّز تدفق Ingestion المعرفة قبل أن يطرح المستخدم سؤالًا. أما تدفق Query فيستخدم تلك المعرفة المجهزة في وقت Inference. ويهم هذا الفصل بينهما لأن التدفقين يخضعان لقيود Performance مختلفة: يمكن لـ Ingestion غالبًا أن يعمل بصورة Asynchronous وأن يعيد محاولة معالجة المستندات التي فشلت، بينما يختبر المستخدم عمليات Query-time مباشرة، ولذلك يجب أن تكون سريعة بما يكفي للاستخدام التفاعلي.

أهم درس في هذا الفصل هو أن الجودة **من البداية إلى النهاية (end-to-end)**. لا يستطيع LLM قوي إصلاح مستند جرى Parsing له بصورة خاطئة بشكل موثوق. ولا تستطيع Vector Database قوية استعادة معلومات فُقدت أثناء Chunking. ولا يمكن لـ Prompt جيد تعويض Retrieval زوّد النظام بأدلة خاطئة. كل مرحلة تنشئ افتراضات ترثها المرحلة التالية.

## 2. مقارنة تدفق Ingestion بتدفق Query

يعمل تدفق Ingestion عند إدخال معلومات لأول مرة أو عند تغير معلومات موجودة. وتتمثل مهمته في تحويل Source Data إلى صيغة يمكن لـ Retrieval استخدامها بكفاءة لاحقًا. أما تدفق Query فيعمل كلما طلب المستخدم من النظام تنفيذ شيء اعتمادًا على تلك المعرفة.

يوضح هذا الفرق لماذا يجمع تطبيق RAG نفسه بين **Data Engineering بأسلوب Offline** و **Online Inference**.

| التدفق | المشغّل المعتاد | العمل الرئيسي | الاهتمام الأساسي |
|---|---|---|---|
| تدفق Ingestion (Ingestion) | بيانات جديدة أو محدّثة | Parsing و Chunking و Embedding و Indexing | الصحة والاكتمال |
| تدفق Query (Query) | طلب المستخدم | Rewriting و Retrieval و Reranking و Prompting و Generation | Relevance و Latency و Grounded Output |

التدفقان مترابطان. افترض أن دليلًا لموظفي HR جرى Ingestion له بصورة خاطئة، فدُمج عنوان قسم مع الفقرة الخطأ. عند وقت Query، قد يسترجع Semantic Search الـ Chunk المشوّه بدقة كاملة وفق ما هو مخزن. ثم يتلقى Generator دليلًا سيئًا. يبدو الفشل النهائي كأنه مشكلة في LLM، لكن السبب الجذري الحقيقي وقع مبكرًا أثناء Ingestion.

لهذا ينبغي عند Debug لنظام RAG تتبّع الطلب عكسيًا عبر المكدس، بدلًا من البدء بالإجابة النهائية المولّدة والانتهاء عندها.

## 3. مصادر Ingestion المنظمة وغير المنظمة

يمكن أن تأتي بيانات RAG من Databases و APIs وملفات محلية أو سحابية ومصادر جرى Web Scraping لها. وتعتمد كمية Preprocessing بدرجة كبيرة على مقدار البنية التي يوفرها المصدر أصلًا.

تحتوي Database أو API عادةً على Schema واضح. فعند Ingestion لرسائل Chat مثلًا، قد يحتوي كل Record بالفعل على `text` و `role` و `timestamp` و `conversation_id`. يمكنك Flatten للكائنات المتداخلة، والتخلص من الحقول غير المهمة لـ Retrieval، والحفاظ على الحقول المفيدة كـ Metadata. وقد يحتاج Text الرسالة فقط إلى Embedding، بينما يبقى Role والوقت وهوية المحادثة متاحة لـ Filtering و Context.

الملفات أصعب. تمزج صيغ PDF و DOCX و PPTX و HTML وما شابهها المعرفة مع Presentation. قد يحتوي ملف Word على Fonts وألوان وصور وجداول وعناوين وقواعد Layout. وقد لا يحتوي PDF ممسوح ضوئيًا على أي Text قابل للقراءة آليًا. يجب على نظام Ingestion أن يقرر أي الأجزاء تمثل معرفة، وأيها Metadata، وأيها مجرد Presentation.

لذلك لا يكون سؤال التصميم العملي ببساطة: «هل أستطيع استخراج Text؟» بل يكون:

> **هل أستطيع الحفاظ على المعلومات التي ستكون مهمة لاحقًا، مع التخلص من المعلومات التي لن تساعد Retrieval أو Generation؟**

يقود هذا السؤال مباشرة إلى Document Parsing.

## 4. Document Parsing: استخراج معرفة قابلة للاستخدام

**Document Parsing** هو عملية فصل المعلومات التي ينبغي أن تدخل Knowledge Base الخاصة بـ RAG عن Formatting و Coordinates و Markup أو أي بنية أخرى لا ينبغي أن تصبح Search Content.

لا يمثل Parsing مجرد خطوة تنظيف شكلية. فهو يحدد المعرفة الموجودة في المراحل اللاحقة.

قد يحتاج Parser إلى استعادة:

- Text الفقرات،
- العناوين وهرمية الأقسام،
- قيم الجداول،
- مراجع الصور أو Captions،
- هوية المتحدث،
- Timestamps،
- معرفات المستندات،
- موضع الصفحة أو المصدر،
- Metadata أخرى لازمة لـ Filtering أو Citations.

وقد يحتاج أيضًا إلى إزالة:

- تعليمات Fonts و Styling،
- Rendering Coordinates،
- Headers و Footers المكررة،
- Markup الذي لا يؤدي دورًا دلاليًا،
- Layout Artifacts التي تفسد ترتيب القراءة.

إذا فشل Parsing، فستعمل المكونات اللاحقة على بيانات تالفة. وهذا يجعل دقة Ingestion عنصرًا أساسيًا من عناصر جودة RAG، لا مجرد تفصيل متعلق بتحويل الملفات.

## 5. لماذا يصعب Parsing لملفات PDF؟

تُعد PDF صعبة بصورة خاصة لأنها صُممت أساسًا للحفاظ على المظهر البصري، لا على البنية المنطقية للمستند. يمكن لصفحة PDF تخزين أحرف منفردة بإحداثيات ثنائية الأبعاد بدلًا من هرمية واضحة للفقرات والعناوين والجداول.

يعني ذلك أن Parser قد يحتاج إلى استنتاج ترتيب القراءة من Geometry. فكّر في صفحة ذات عمودين:

```text
العمود A (Column A)           العمود B (Column B)
A1                          B1
A2                          B2
A3                          B3
```

قد يعيد Extractor بسيط النتيجة التالية:

```text
A1 B1 A2 B2 A3 B3
```

رغم أن ترتيب القراءة المقصود كان `A1 A2 A3` ثم `B1 B2 B3`.

تخلق ملفات PDF الممسوحة ضوئيًا صعوبة إضافية: فقد يكون Text المرئي في الحقيقة Pixels. عندها نحتاج إلى Optical Character Recognition (OCR). وتعتمد جودة OCR على عوامل مثل Resolution والوضوح ونمط Font و Page Layout.

[[IMAGE_NEEDED: PDF visual layout versus logical text | A two-column PDF page represented as positioned text boxes, next to a correct and an incorrect extracted reading order | Learner should notice that PDF coordinates do not automatically encode paragraph or column order]]

المغزى الهندسي بسيط: **افحص مخرجات Parser قبل أن تثق في Metrics الخاصة بـ Retrieval**. إذا كان ترتيب Text تالفًا بالفعل، فإن Retrieval Evaluation تقيس Corpus مكسورًا.

## 6. لا تتخلص من البنية المفيدة: Metadata

لا يعني Parsing إزالة كل Tag أو Attribute. فبعض عناصر البنية تحمل معلومات ينبغي أن تبقى بعد Ingestion.

يوضح الفصل ذلك باستخدام Chat Log. قد يبيّن عنصر HTML ما إذا كانت رسالة ما صادرة من User أم من AI. وإذا احتفظنا فقط بـ Text المرئي، نفقد هوية المتحدث. وهذه المعلومات المفقودة تمنع لاحقًا Queries مثل «وفقًا لما قاله AI، ...» من أن تُقيّد بصورة صحيحة.

التمثيل الأفضل يفصل Searchable Text عن Metadata:

```text
النص (text):     "The capital of France is Paris."
البيانات الوصفية (metadata): {"who": "AI"}
```

يمكن إنشاء Embedding للنص من أجل Semantic Search، بينما يمكن Filtering للـ Metadata باستخدام منطق Database عادي.

هذا الفرق أساسي:

```text
Semantic Search → "ما المحتوى الذي يحمل معنى مشابهًا؟"
Metadata Filter → "ما Records المسموح بها أو المؤهلة بنيويًا؟"
```

يتصرف Metadata Filtering بصورة أقرب إلى عبارة SQL من نوع `WHERE` منه إلى Semantic Similarity. ويمكنه ترميز المتحدث ونوع المستند و Tenant و Department والتاريخ والشركة و Security Label أو أي حقل منظم آخر.

إن الحفاظ على Metadata أثناء Ingestion يمنح تدفق Query طريقة ثانية لتضييق الأدلة إلى جانب Vector Similarity.

## 7. Parsing باستخدام Vision-Language Models

يمكن لـ Vision-Language Models (VLMs) معالجة المعلومات البصرية مع Text، لذلك يمكن استخدامها لتفسير Slides و Forms و Infographics والمستندات المعقدة بصريًا التي تعاني معها Parsers التقليدية.

الجاذبية واضحة: بدلًا من كتابة قواعد خاصة بكل Format، يمكنك تقديم مستند وطلب استخراج محتوى معين من Model. لكن الفصل يؤكد ضرورة الحذر.

قد يكون VLM Parser:

- أبطأ من Deterministic Parser،
- أعلى Cost على نطاق Enterprise،
- غير مثالي في استخراج Text بدقة حرفية،
- عرضة لـ Hallucination أو تغيير المحتوى،
- غير قادر على إعادة إنتاج كل صورة أو عنصر بصري بأمانة كاملة.

العقلية الموصى بها هي **استخدام أرخص Parser ناجح أولًا**:

```text
Parser مدرك للـ Format
→ OCR عند الحاجة
→ VLM للحالات الصعبة / عالية القيمة أو كـ Fallback
```

لا يعني ذلك أن Classical Parsing أفضل دائمًا. بل هي استراتيجية هندسية: استخدم أدوات متوقعة السلوك وفعالة حيث تنجح، واحتفظ بـ Generative Visual Parsing للحالات التي تبرر فيها قدراته الإضافية Cost والمخاطر.

## 9. فصل محتوى الجداول عن Free Text

عندما تحتوي صفحة على Prose وجداول معًا، فإن التعامل مع كل Token مستخرج باعتباره Stream نصيًا واحدًا يمكن أن ينتج Chunks مربكة. لذلك يعرض الفصل استراتيجية من جزأين:

1. اكتشاف الجداول واستخراجها،
2. إزالة Text الموجود في مناطق الجداول من Stream الخاص بـ Page Text العادي.

يكشف PyMuPDF الجداول المكتشفة عبر `page.find_tables()`. ويمكن استخراج كل Table كبنية ثنائية الأبعاد. كما يمكن استخدام Bounding Box للجدول لتحديد المنطقة التي لا ينبغي تكرار Text الخاص بها في مخرجات Free Text.

تصوريًا:

```text
الصفحة (page)
├── Text الفقرة
├── منطقة Table
│   ├── خلايا Header
│   └── خلايا Data
└── مزيد من Text الفقرات
```

بدلًا من Flatten لكل شيء، حافظ على هذه Modalities بصورة منفصلة. يمنحك ذلك خيار Serialize للجدول بتمثيل منظم، مع تنفيذ Chunking للـ Prose بتمثيل موجه للفقرات.

المبدأ الأعمق هو أن Ingestion لا ينبغي أن يدمّر بنية قد تكون مفيدة لاحقًا. الجداول ليست مجرد Text توجد مسافات بين قيمه؛ فالصفوف والأعمدة ترمز إلى علاقات.

## 12. استخدام LLM في Parsing لملفات PDF الصعبة

يعرض الفصل مسارًا آخر: رفع PDF إلى API تدعم LLM وتوجيه Model لاستخراج أجزاء محددة، مثل Free Text مع استبعاد الجداول والصور، أو إعادة الجداول بصيغة Markdown.

الميزة هي المرونة. إذ يمكن لتعليمة مكتوبة باللغة الطبيعية أن تحل محل جزء من منطق Parsing المكتوب يدويًا. لكن الخطر هو أن Generative Extraction لا يضمن أمانة تامة للنص الأصلي.

عند التفكير في Parsing المعتمد على LLM، اطرح أربعة أسئلة:

1. **Accuracy:** هل يستطيع Model إعادة إنتاج المحتوى المطلوب بصورة موثوقة؟
2. **Cost:** كم عدد المستندات/الصفحات التي ستُعالج؟
3. **Latency:** هل يحدث Parsing بصورة متقطعة أم على نطاق ضخم؟
4. **Auditability:** هل يمكنك اكتشاف متى يغيّر Parser المحتوى أو يخترعه بصمت؟

لهذا تُعد استراتيجية Fallback في الفصل مهمة. إن VLM أو LLM Parser قوي، لكنه لا ينبغي أن يُعامل باعتباره بديلًا سحريًا عن Validation.

## 13. Chunking: لماذا لا يمكن أن يبقى Document سلسلة نصية عملاقة واحدة؟

بعد Parsing، قد يظل النظام يحتوي Segments أكبر أو أوسع بكثير من أن تكون فعالة في Retrieval. تقوم **Chunking** بتقسيم Text الكبير إلى أجزاء أصغر يمكن إنشاء Embeddings لها والبحث فيها وتمريرها انتقائيًا إلى Generator.

توجد Chunking لثلاثة أسباب مختلفة:

1. **Capacity:** نوافذ Context الخاصة بـ LLM و Embedding Model محدودة.
2. **Efficiency:** معالجة Context أطول من اللازم تزيد Latency و Cost.
3. **Quality:** تمثل Chunks الأصغر والمتماسكة Topic واحدًا بصورة أوضح غالبًا، وتقلل المواد غير المهمة المقدمة إلى Retriever و Generator.

افترض أن لديك كثيرًا من Earnings-call Transcripts لكن المستخدم يسأل فقط عن نمو عدد الموظفين. إرسال Transcripts كاملة يهدر Context على Revenue و Product Launches وموضوعات أخرى. تسمح Chunking لـ Retrieval باختيار المقاطع التي تتناول الموضوع المطلوب فقط.

الهدف ليس إنشاء أصغر أجزاء ممكنة. بل إنشاء **Retrieval Units صغيرة بما يكفي لتكون مركزة، وكبيرة بما يكفي للحفاظ على Context اللازم لفهمها**.

## 14. نوافذ Context في LLM كبيرة، لكنها ما تزال محدودة

يعرض المصدر أمثلة لنوافذ Context كبيرة جدًا كانت متاحة وقت الكتابة. قد تبدو هذه الأرقام هائلة، لكن Enterprise Corpora يمكن أن تتجاوزها سريعًا.

الخطأ الأساسي هو التفكير بهذه الطريقة:

> «يدعم Model لدي Context Window ضخمة، لذلك لا أحتاج إلى Retrieval أو Chunking.»

Context Window حد لطلب واحد، وليست Storage System قابلة للتوسع. وحتى إذا كان من الممكن تقنيًا إدخال مستندات كثيرة، فإن إرسال كل شيء يفرض تكاليف أخرى:

- Input Tokens أكثر،
- Time to First Token أطول،
- مزيد من الأدلة غير المهمة التي تتنافس على Attention،
- Cost مالية أو Hardware Cost أعلى،
- جودة Retrieval عملية أقل داخل Context شديدة الطول.

لذلك تبقى Chunking مفيدة حتى عندما تدعم Models مدخلات طويلة. لا تمثل RAG مجرد حل مؤقت لنوافذ Context الصغيرة؛ بل هي أيضًا استراتيجية **لاختيار الأدلة الصحيحة**.

## 15. طول Context و Latency و Cost

يستخدم الفصل مثال Benchmark ليوضح كيف ترتفع Latency بحدة مع زيادة Sequence Length. ترتبط القياسات المحددة بـ Hardware و Model المستخدمين في Benchmark، لكن الدرس الهندسي أوسع: تمرير Tokens أكثر ليس مجانيًا.

في Transformer Inference، تحتاج Context الأطول إلى Compute و Memory أكثر. ويستخدم المصدر قياسات Time-to-first-token (TTFT) لتوضيح التأثير: تعيد Prompts القصيرة النتائج بسرعة، بينما تستغرق Sequences الأطول بكثير وقتًا أكبر بصورة ملحوظة على GPUs عالية الأداء.

بالنسبة إلى مهندس RAG، يعني ذلك أن Chunking لا تؤثر في جودة Retrieval فقط، بل أيضًا في اقتصاديات Runtime.

فكّر في Context باعتبارها Budget:

```text
السياق المتاح (available context)
= التعليمات (instructions)
+ استعلام المستخدم (user query)
+ حالة المحادثة (conversation state)
+ المقاطع المسترجعة (retrieved chunks)
+ مساحة للإجابة المولّدة (room for generated answer)
```

إذا أهدرت Retrieval هذه Budget على Chunks مكررة أو غير مهمة، يدفع النظام الثمن مرتين: يجب على LLM معالجة Input أكبر، وتبقى مساحة أقل للأدلة المفيدة.

تساعد Chunking الجيدة على جعل كل Token مسترجع يستحق مكانه.

## 16. لدى Embedding Models حدود Context خاصة بها

يظهر قيد Capacity ثانٍ قبل Generation: تقبل Embedding Models أيضًا كمية محدودة فقط من Text في كل Call.

إذا تجاوز Chunk نافذة Context الخاصة بـ Embedding Model، فقد يقوم Serving Framework بعمل Truncation له. ويُعد Silent Truncation خطيرًا بصورة خاصة لأن Pipeline تستمر في العمل من الناحية التركيبية بينما تفقد معلومات من الناحية الدلالية.

تخيل Chunk بحجم 12,000 Token يُرسل إلى Embedder يقبل 8,000 Token فقط. سيصبح Vector ممثلًا للجزء المحتفظ به فقط. وقد يفشل Query الذي توجد إجابته في الجزء المحذوف في استرجاع ذلك Chunk نهائيًا، رغم أن Raw Document يبدو أنه يحتوي الإجابة.

لذلك:

```text
سياسة Chunk Size
يجب أن تكون متوافقة مع
حد Input في Embedding Model
```

وهذا أحد أسباب عدم إمكانية ضبط Model Selection و Chunking بصورة مستقلة.

## 17. كيف يغيّر Chunk Size جودة Retrieval؟

قد يناقش Chunk كبير Topics كثيرة. ويجب على Embedding الخاص به ضغطها كلها في Vector واحد، لذلك لا يجري تمثيل أي Topic منفرد بالوضوح نفسه. أما Chunk أصغر ومتماسك فيمكنه تركيز تمثيله على فكرة واحدة.

ينشئ ذلك مفاضلة:

```text
كبير أكثر من اللازم
→ Topics مختلطة
→ Representation مخفف
→ Context غير مهم أكثر

صغير أكثر من اللازم
→ Context مفقود
→ Evidence مجزأ
→ قد تُفقد العلاقات
```

لا يُعرّف أفضل Chunk بعدد مطلق من Tokens. بل يُعرّف بمدى خدمته لمهمتي Retrieval و Generation على Dataset الفعلية.

يشير المصدر أيضًا إلى أن Context الطويل قد يجعل Generation أصعب: فقد تكون Models أقل فاعلية في العثور على الأدلة المطلوبة عندما تكون مدفونة وسط كميات كبيرة من Text. ويربط ذلك Chunking بمشكلة **lost in the middle** التي ستناقش لاحقًا في Evaluation.

## 18. Fixed-size Chunking و Overlap

تقطع Fixed-size Chunking المستند كل عدد ثابت من Characters أو Words أو Tokens. ومن نقاط قوتها البساطة، وأحجام يمكن التنبؤ بها، و Batching فعال، وسهولة التنفيذ.

أما ضعفها فبسيط بالقدر نفسه: **Text لا يحترم الحدود الاعتباطية**.

قد تقسم Boundary:

- Word،
- Sentence،
- Paragraph،
- Code Block،
- حجة منطقية.

يُضاف Overlap عادةً بحيث تتكرر نهاية Chunk في بداية Chunk التالي:

```text
المقطع 1 (chunk 1): [--------------------]
المقطع 2 (chunk 2):              [--------------------]
                     ^ تداخل مكرر (repeated overlap)
```

يحافظ Overlap على Context المحلي عبر Boundaries لكنه ينشئ Text مكررًا. ويعني Overlap أكبر Vectors أكثر و Storage أكثر وربما Retrieval Results أكثر تكرارًا.

لذلك تكون Fixed-size Chunking جذابة عندما تهم السرعة وإمكانية التنبؤ، لكن ينبغي تقييم Parameters الخاصة بها بدلًا من قبولها لمجرد الاعتياد.

## 19. Chunking المدركة للـ Sentences و Paragraphs

تحترم Content-aware Chunking الحدود اللغوية. فبدلًا من القطع بعد عدد اعتباطي من Characters، تقسم عند Sentences أو Paragraphs، ويمكنها دمج الوحدات المتجاورة للوصول إلى حجم عملي.

ينتج هذا عادةً وحدات دلالية أنظف، لكن Sentence Splitting لها حالات طرفية:

- الاختصارات،
- العناوين التي تحتوي نقاطًا،
- علامات ترقيم غير معتادة،
- Question Marks أو علامات ترقيم داخل النصوص المقتبسة.

توفر Libraries مثل spaCy و Stanza و NLTK أدوات Sentence Segmentation مصممة للتعامل مع هذه الحالات بصورة أفضل من `text.split(".")` البسيطة.

قد تبدو Pipeline المدركة للـ Sentences كما يلي:

```text
المستند (document)
→ اكتشاف الجمل (detect sentences)
→ تجميع الجمل حتى الحجم المستهدف (accumulate sentences until target size)
→ الاحتفاظ بـ Overlap اختياريًا (optionally retain overlap)
→ إخراج Chunk (emit chunk)
```

التحسين الأساسي هو أن Boundaries أصبحت تعكس بنية اللغة بدلًا من Length فقط.

## 20. التقسيم التكراري (Recursive Chunking)

تستخدم Recursive Chunking هرمية من Separators. تبدأ بمحاولة Boundary خشنة مثل Paragraphs. وإذا ظل Segment كبيرًا أكثر من اللازم، تنتقل إلى Boundaries أصغر مثل Sentences ثم Clauses أو Characters.

تصوريًا:

```text
Boundary عند Paragraph
    ↓ إذا ظل الحجم كبيرًا أكثر من اللازم
Boundary عند Sentence
    ↓ إذا ظل الحجم كبيرًا أكثر من اللازم
Delimiter أصغر
```

يجعل ذلك Recursive Chunking مرنة: فهي تحاول الحفاظ على الوحدات الطبيعية الكبيرة مع فرض Maximum Size في الوقت نفسه.

يُعد `RecursiveCharacterTextSplitter` في LangChain تنفيذًا ممثلًا لهذه الفكرة.

مع ذلك تعتمد الطريقة على جودة Delimiters. فالـ Recursive Splitter لا يعرف البنية إلا من خلال Separators التي تقدمها له؛ ولا يفهم Topic Boundaries بطبيعته.

## 21. Chunking المدركة لبنية Document

إذا كشف Document عن هرمية صريحة، مثل عناوين Markdown أو أقسام HTML أو فصول المستند، فيمكن لتلك Boundaries أن تصبح جزءًا من استراتيجية Chunking.

بالنسبة إلى Markdown:

```text
# الفصل (Chapter)
## القسم (Section)
### القسم الفرعي (Subsection)
```

يمكن التعامل معها كهرمية بدلًا من Plain Text.

يحافظ ذلك على علاقات قد تمحوها Fixed-size Splitting. ويمكن لـ Chunk مأخوذ من Subsection أن يحتفظ بـ Metadata تحدد Parent Section أو Chapter. وتفيد هذه البنية الإضافية في Filtering و Citations و Context Expansion.

القيد هو أن هذه الاستراتيجية تعتمد على بنية موثوقة. فالمستندات سيئة التنسيق أو غير المنظمة توفر Boundaries قابلة للاستخدام بدرجة أقل.

## 22. التقسيم الدلالي (Semantic Chunking)

تحاول Semantic Chunking إنشاء Boundaries اعتمادًا على المعنى بدلًا من Syntax فقط. إحدى الطرق تُنشئ Embeddings للـ Sentences وتجمع Sentences المتقاربة ما دام Semantic Similarity بينها مرتفعًا، لتنشئ Chunks تتوافق بدرجة أكبر مع تغير Topics.

جاذبيتها واضحة: إذا كانت Retrieval نفسها دلالية، فلماذا لا نبني Retrieval Units متماسكة دلاليًا؟

لكن Semantic Chunking تفرض تكاليف:

- يلزم تنفيذ Embedding أثناء بناء Chunks،
- يصبح Chunk Size أقل قابلية للتنبؤ،
- يصبح Implementation و Tuning أكثر تعقيدًا،
- قد يصبح Debug للـ Boundaries أصعب.

يسلط المصدر الضوء على نتيجة بحثية مهمة: في بعض Benchmarks، لم تتفوق Semantic Chunking بوضوح على Fixed-size Chunking. ولا ينبغي اعتبار هذه النتيجة قاعدة عامة لأن Benchmarks الأقدم تحتوي غالبًا مقاطع قصيرة نسبيًا.

الخلاصة العملية هي **التقييم على Corpus و Queries الخاصة بك** بدلًا من افتراض أن أكثر Chunker تعقيدًا يجب أن يكون الأفضل.

## 23. كيفية تقييم استراتيجية Chunking

يمكن تقييم Chunking في مرحلتين.

### Evaluation على جانب Retrieval

اسأل ما إذا كانت الأدلة الصحيحة قد استُرجعت. تشمل Metrics المذكورة في الفصل:

- Precision،
- Recall،
- F1،
- nDCG،
- مقياس MRR.

تركز هذه Metrics على جودة Ranking و Retrieval.

### Evaluation على جانب Generation

اسأل ما إذا كان Generator يستطيع إنتاج إجابة صحيحة ومفيدة من Context المسترجع. يذكر الفصل Evaluation بأسلوب Question Answering / Machine Reading Comprehension و BERTScore والأحكام المعتمدة على LLM.

تتأثر Generation Metrics بأكثر من Chunking. يهم ترتيب Retrieved Chunks لأن Models قد تمنح Attention أكبر للأدلة القريبة من بداية Prompt ونهايته في Prompt طويل، وهي ظاهرة **lost in the middle**.

لذلك لا تستطيع Generation Score وحدها إثبات تفوق استراتيجية Chunking على أخرى. اعزل أداء Retrieval حيثما أمكن، ثم قيّم النظام الكامل.

## 25. Embeddings: تمثيل المعنى بدلًا من طريقة الكتابة

يعتمد Keyword Matching على Surface Form. وهذا يخلق حالات فشل واضحة:

```text
"United States" ≠ "U.S." ≠ "America" — صيغ مختلفة قد تشير إلى مفهوم متقارب
"two" ≠ "2" — تمثيلان مختلفان قد يحملان المعنى نفسه
```

رغم أن هذه المصطلحات قد تشير إلى مفاهيم مترابطة بدرجة كبيرة.

تحوّل Embeddings النص إلى Numerical Vectors مصممة بحيث تنعكس العلاقات الدلالية في العلاقات الهندسية. ويمكن لنصين مختلفين في Spelling أن يقع كل منهما قريبًا من الآخر إذا كان معناهما متشابهًا.

يساعد ذلك على حل مشكلتين متعاكستين:

- **اختلاف في Surface Form مع تشابه دلالي:** يمكن أن تكون “Uncle Sam” و “US Government” مرتبطتين.
- **تشابه في Surface Form مع اختلاف دلالي:** تبدو “cat” و “hat” متشابهتين في الكتابة لكن معناهما مختلف.

الفكرة لا تقتصر على Synonym Matching. يمكن لـ Embedding جيد التقاط علاقات دلالية أوسع. يعطي الفصل مثالًا على أن Query عن قضايا في US قد يسترجع مستندًا عن California ويرفض مستندًا عن Alberta، حتى لو لم يذكر أي من المستندين كلمة “US” حرفيًا.

ولهذا تُسمى Semantic Retrieval باسم **Dense Retrieval**: إذ تُستخدم Dense Numerical Representations لمقارنة المعنى.

## 26. ما Embedding بالضبط؟

يحوّل Embedding Model نص Input إلى Vector من أعداد Floating-point:

```text
النص (text)
→ نموذج Embedding (embedding model)
→ [0.021, -0.114, 0.337, ...] — Embedding Vector رقمي
```

يمثل كل موضع Dimension في Embedding Space. ولا يكون لكل Dimension عادةً Label بسيط يمكن للبشر قراءته. الخاصية المفيدة هي Geometry الخاصة بالـ Vector كاملًا.

إذا أشار Vectorان في اتجاهين متشابهين، تكون نصوصهما مترابطة دلاليًا عادةً. وهذا يسمح لنظام RAG بمقارنة Query Vector مع Stored Chunk Vectors باستخدام عمليات رقمية فعالة.

مسار شائع في RAG هو:

```text
مقطع Document (document chunk) ──Embedding──> المتجه المخزن (stored vector)
استعلام المستخدم (user query) ──Embedding──> متجه الاستعلام (query vector)
                           ↓
                    بحث التشابه (similarity search)
```

الـ Vector هو Search Representation. فهو ليس Text نفسه، وليس ما يقرأه Generative LLM في النهاية. بعد Retrieval يعود النظام إلى Text الأصلي للـ Chunk من أجل Generation.

## 27. من One-hot Vectors إلى Contextual Embeddings

يضع الفصل بإيجاز Embeddings الحديثة في سياقها التاريخي.

تعطي تمثيلات مبكرة مثل One-hot Encoding لكل عنصر في Vocabulary موضعًا خاصًا به داخل Vector ضخم جدًا. هذا النوع من Representation يرمز إلى الهوية، لكنه لا يرمز إلى قرب دلالي مفيد.

غيّر Word2Vec الصورة عبر تعلم Vectors من Prediction للكلمات المحيطة. وقد أنتج علاقات هندسية شهيرة بين معاني الكلمات، لكن Word Embeddings الخاصة به **Static**: تحصل Word على Vector نفسه بغض النظر عن Context.

قدّم BERT Contextualized Representations، حيث يعتمد Representation الخاص بـ Token على Text المحيط به.

بالنسبة إلى RAG، يكون التطور المهم كالتالي:

```text
Representation قائم على الهوية
→ Representation دلالي متعلم
→ Representation دلالي حساس للـ Context
```

تبني Embedding Models الحديثة الخاصة بـ Sentences/Documents على هذه الفكرة لتمثيل Queries و Chunks كاملة بطرق مناسبة لـ Retrieval.

## 28. اختيار Embedding Model

ينشئ اختيار Embedding Model عدة مفاضلات.

### حجم Model وجودة Retrieval

قد تلتقط Models الأكبر الدلالات بدقة أعلى، لكنها قد تحتاج Memory أكبر و Inference Time أطول. ويمكن لـ Benchmarks مثل MTEB المساعدة في مقارنة Models المرشحة، لكن يبقى Evaluation الخاص بالتطبيق ضروريًا.

### أبعاد Embedding

يمكن لعدد أكبر من Dimensions الحفاظ على معلومات أكثر، لكنه يزيد:

- Vector Storage،
- Memory Bandwidth،
- Index Size،
- تكلفة Search (Search Cost).

### طول Input Context

يجب أن يقبل Model حجم Chunk المختار. وإلا فقد يحدث Truncation للبيانات.

### قيود Deployment

قد يهتم تصميم Production بـ Throughput و Hardware و API Cost واللغات المدعومة وتوافق Database.

لذلك لا يكون Embedding Model الصحيح تلقائيًا هو صاحب أعلى Benchmark Score. بل هو الذي يحقق جودة Retrieval مناسبة ضمن قيود نظامك.

## 29. تقليل الأبعاد باستخدام Matryoshka Representation Learning

تُدرّب بعض Embedding Models باستخدام **Matryoshka Representation Learning (MRL)** بحيث تتركز المعلومات الدلالية المفيدة أكثر في Dimensions الأولى. ويسمح ذلك بعمل Truncation للـ Vector الكامل مع الاحتفاظ بجزء كبير من قدرة Retrieval.

الدافع تشغيلي:

```text
Dimensions أقل
→ Vectors أصغر
→ Storage أقل
→ Memory Traffic أقل
→ Search أسرع
```

لكن Reduction المفرط قد يقلل جودة Retrieval.

يشير الفصل إلى أنه رغم سماح MRL بعمل Truncation، تُستخدم عادةً Subdimensions على هيئة Powers of Two لأن Training يحسن غالبًا Granularities معينة.

القرار الهندسي هو مشكلة Evaluation أخرى: قلل Dimensions حتى تصل إلى نقطة Efficiency مفيدة **من دون تجاوز Quality Threshold الذي يحتاجه تطبيقك**.

## 30. قيود عملية في Embeddings: Truncation و Precision و Transport

يمكن لثلاث مشكلات عملية أن تؤثر بصمت في نظام RAG.

### 1. الاقتطاع الصامت للمدخلات (Silent Input Truncation)

إذا تجاوز Chunk نافذة Context الخاصة بـ Embedding Model، فقد تقوم بعض Serving Frameworks بعمل Truncation له. اجعل حدود Chunk Size صريحة دائمًا واختبر Boundary Cases.

### 2. دقة Vector (Vector Precision)

يُعد تخزين أعداد Floating-point بدقة 32-bit دقيقًا لكنه مكلف. ويمكن لـ Precision أقل، مثل 16-bit Floats أو 8-bit Integers، تقليل Storage و Compute على حساب احتمال فقد بعض الجودة.

### 3. تمثيل النقل (Transport Representation)

قد تقوم Embedding APIs بعمل Serialization للمصفوفات في JSON. ويُعد JSON مريحًا لكنه غير فعال للـ Numerical Payloads ويمكن أن يخلق Overhead ناتجًا عن String Serialization. ويشير الفصل إلى أن بعض Platforms تدعم Binary Data مشفرة بـ Base64، وهو ما يحافظ على Floating-point Values بكفاءة أكبر لكنه يتطلب Client-side Decoding.

لا تغير هذه التفاصيل نظرية Embedding، لكنها تؤثر عند Production Scale في Bandwidth و Storage و Latency و Cost.

## 32. Vector Similarity: Dot Product و Cosine Similarity

يحتاج Retriever إلى قاعدة رقمية لتحديد Stored Vectors الأقرب إلى Query.

عملية شائعة هي **Dot Product**:

```text
a · b = Σ aᵢbᵢ
```

إذا جرى Normalize للـ Vectors لتصبح Magnitude الخاصة بها مساوية لـ 1، يصبح Dot Product مكافئًا لـ Cosine Similarity. وتركز Cosine Similarity على الزاوية بين Vectors بدلًا من Absolute Magnitude.

بالنسبة إلى Normalized Embeddings:

```text
الاتجاه نفسه     → Similarity مرتفعة
اتجاه مختلف → Similarity أقل
```

يمنح ذلك Semantic Search Primitive رياضية سريعة.

انتبه إلى Operators الخاصة بـ Database: تعرض بعض الأنظمة **Distance** بدلًا من Similarity. وتعني Cosine Distance الأصغر Vectors أقرب. وإذا أردت Score بأسلوب Similarity، فقد تحتاج إلى تحويل القيمة. يستخدم مثال pgvector لاحقًا هذا الفرق بصورة صريحة.

## 33. Exact Search مقابل Approximate Nearest Neighbors

أبسط طريقة لاسترجاع أقرب Vector هي Brute Force:

```text
لكل Stored Vector:
    احسب similarity(query, vector)
أعد أفضل k
```

هذا Exact وله تقريبًا Cost مقارنة `O(n)` عند وجود `n` من Stored Vectors.

بالنسبة إلى Datasets الصغيرة، يمكن أن يكون Exact Search منطقيًا تمامًا. بل قد تحتفظ بكل Vectors في Memory.

عند ملايين أو مليارات Chunks، تصبح مقارنة Query بكل Vector مكلفة أكثر من اللازم. وتستبدل Algorithms الخاصة بـ **Approximate Nearest Neighbor (ANN)** قدرًا صغيرًا من Exactness بسرعة Search أعلى بكثير.

هذه مفاضلة أساسية في Production:

```text
أقرب جار دقيق (exact nearest neighbor)
→ أعلى دقة مطابقة (maximum exactness)
→ عمل أكبر (more work)

أقرب جار تقريبي (approximate nearest neighbor)
→ عمل أقل بكثير (much less work)
→ قد يفوّت أحيانًا أقرب نقطة رياضيًا (may occasionally miss the mathematical nearest point)
```

لا يكون هدف Retrieval عادةً الكمال الرياضي بأي Cost، بل استرجاع الأدلة بدقة كافية ضمن قيود Latency والموارد.

## 34. البحث المتجهي من العام إلى الدقيق باستخدام HNSW

تُعد Hierarchical Navigable Small World (HNSW) واحدة من أشهر Algorithms الخاصة بـ ANN. فهي تنظم Vectors في Graph متعدد الطبقات.

تحتوي الطبقات العليا نقاطًا أقل وتوفر Navigation عامة. أما الطبقات السفلى فتحتوي نقاطًا أكثر وتوفر Local Search أدق.

يجعل تشبيه المدن في الفصل الفكرة بديهية. للعثور على موقع قريب من Los Altos، لا تقارن بكل مدينة في United States. بل تختار أولًا Region واسعة باستخدام عدد قليل من Landmarks الرئيسية، ثم تضيق إلى مدن الغرب، ثم Bay Area، ثم مدن South Bay.

```text
معالم عامة (coarse landmarks)
      ↓
مرشحون إقليميون (regional candidates)
      ↓
مرشحون محليون (local candidates)
      ↓
أقرب نطاق محلي (nearest neighborhood)
```

يمكن لـ Greedy Navigation في HNSW أحيانًا الدخول إلى Region خاطئة قليلًا، ولهذا تُعد Approximate. وفي المقابل، تفحص جزءًا صغيرًا فقط من البيانات وتكون فعالة جدًا عمليًا.

FAISS هي Library مفتوحة المصدر مستخدمة على نطاق واسع وتنفذ HNSW وطرق ANN أخرى.

## 35. ما الذي تضيفه Vector Database فوق ANN؟

لا تمثل Vector Database مجرد Function لـ ANN. فهي تدير High-dimensional Vectors كبيانات تطبيق Persistent.

- حذف Records،
- Persistent Storage،
- ANN Indexes،
- Metadata Fields،
- Filtering،
- Replication أو Scaling،

## 36. Metadata Filtering قبل Vector Search أو حوله

تجيب Vector Similarity عن سؤال دلالي، لكن Queries كثيرة تحتوي أيضًا قيودًا بنيوية Exact.

## 37. اختيار `k` وأبعاد Embedding

يمكن لمعاملين يبدوان بسيطين التأثير بقوة في سلوك النظام.

### عدد نتائج Retrieval: `k`

إذا كانت `k` صغيرة أكثر من اللازم، فقد يقع Chunk الذي يحتوي الإجابة مباشرة خارج المجموعة المعادة.

إذا كانت `k` كبيرة أكثر من اللازم:

- تدخل Chunks غير مهمة إلى Prompt،
- تستهلك الأدلة المكررة Tokens،
- ترتفع Latency و Generation Cost،
- قد يقترب Prompt من Context Limit،
- قد تضعف وضوح الأدلة المفيدة.

### أبعاد Embedding

يمكن لتقليل Dimensions خفض Index Size وتسريع Retrieval. أما تقليلها بصورة مفرطة فيمكن أن يتخلص من معلومات دلالية.

لا يوجد لأي من المعاملين قيمة صحيحة عالميًا. اضبطهما باستخدام Evaluation Set ممثلة، وراقب كلًا من Retrieval Metrics وجودة الإجابات اللاحقة.

مبدأ مفيد هو:

> **زد Retrieval Breadth فقط عندما تحسن Candidates الإضافية احتمال الوصول إلى أدلة مفيدة بما يكفي لتبرير Noise و Cost الإضافيين.**

## 41. Semantic Search و Keyword Search و Hybrid Search و Reranking

يركز المكدس الأساسي أساسًا على Semantic Retrieval، لكن الفصل يضعها في سياق طرق أخرى.

### البحث الدلالي / الكثيف (Semantic / Dense Search)

ينشئ Embeddings للـ Query والمستندات ويطابقها في Vector Space. ويكون قويًا عندما يُعبَّر عن المعنى بكلمات مختلفة.

### البحث بالكلمات المفتاحية / المتناثر (Keyword / Sparse Search)

يطابق Lexical Signals باستخدام طرق مثل TF-IDF أو BM25. ويكون قويًا مع الأسماء Exact و Rare Tokens و Identifiers والقيود الأخرى المعتمدة على Surface Form.

### Hybrid Search

يجمع Semantic Signals و Keyword Signals. ويطور الفصل 3 هذه الفكرة بصورة أوسع.

### Reranking

قد يعيد First-stage Retriever عددًا كبيرًا من Candidates المكررة أو غير المرتبة بصورة مثالية. ويمكن لـ Reranker إعادة ترتيبها أو اختيارها قبل Generation.

تُعد Maximum Marginal Relevance (MMR) إحدى الطرق التي توازن بين Relevance و Diversity. وتذهب Transformer Rerankers أبعد من ذلك عبر تقييم Query و Candidate معًا باستخدام Cross-attention بدلًا من إنشاء Embedding لكل منهما بصورة مستقلة.

يقترح ذلك نمط Retrieval شائعًا:

```text
استرجاع سريع وواسع (fast broad retrieval)
→ مجموعة مرشحين (candidate set)
→ إعادة ترتيب أعلى تكلفة (more expensive reranking)
→ سياق صغير وعالي الجودة (small high-quality context)
```

## 42. يقرأ Generative LLM النص، لا Embedding Vectors

بعد Retrieval، يمتلك النظام شيئين:

1. طلب المستخدم الأصلي،
2. Text الأصلي للـ Retrieved Chunks.

يُجمع هذان العنصران في Prompt للـ Generative LLM.

من الأخطاء الشائعة الاعتقاد بأن LLM يتلقى Embedding Vectors. عادةً لا يحدث ذلك. تستخدم طبقة Retrieval الـ Embeddings لتحديد **أي Text** ينبغي اختياره. أما Generator فيتلقى ذلك Text.

```text
الاستعلام (query)
→ Embedding للاستعلام (query embedding)
→ بحث متجهي (vector search)
→ سجلات Vector مختارة (selected vector records)
→ استعادة Text الأصلي للـ Chunk (recover original chunk text)
→ قالب Prompt (prompt)
→ نموذج LLM (LLM)
→ الإجابة (answer)
```

ثم ينفذ Generator مهام مثل Question Answering أو Summarization على الأدلة المسترجعة.

هذا الفصل مفيد في Debug: إذا اختارت Retrieval الـ Chunks الخطأ، فقد لا يؤدي تغيير Generative Model إلى حل المشكلة.

## 43. اختيار Generative LLM: Quality و Latency و Cost و Privacy

يصف الفصل عدة اعتبارات عند اختيار Generator.

### Quality مقابل Speed

غالبًا تمتلك Models الأكبر Capacity أعلى للمهام الصعبة، لكن Question Answering البسيط في RAG قد لا يستفيد بما يكفي لتبرير Cost و Latency الإضافيتين. قيّم على Workload الخاصة بك بدلًا من افتراض أن الأكبر ضروري دائمًا.

### تحسين Inference

تشمل التقنيات المذكورة في الفصل:

- Quantization لخفض Numerical Precision،
- FlashAttention لجعل Attention Computation أكثر كفاءة،
- Serving Frameworks مثل vLLM و Ollama.

### Deployment و Privacy

تتطلب بعض المؤسسات تشغيلًا On-premises أو Air-gapped. وفي تلك البيئات، قد يكون إرسال Private Context إلى Public Model Endpoints محظورًا. لذلك يُعد اختيار Model أيضًا قرارًا في Data Governance.

Generator الصحيح هو Model الذي يحقق **هدف الجودة الخاص بالتطبيق ضمن قيوده التشغيلية**.

## 44. Prompt Engineering في RAG

Prompt Engineering في RAG هو عملية ترتيب Instructions وطلب المستخدم الأصلي والأدلة المسترجعة بحيث يعرف Model كيف يستخدم Context.

نمط Minimal هو:

```text
أنت مساعد مفيد لمعالجة المعلومات.

<query>
{original_query}
</query>

<context>
{retrieved_chunks}
</context>

أجب عن الاستعلام باستخدام السياق المقدَّم.
```

يقدم الفصل عدة نقاط مفيدة.

أولًا، يمكن لـ Generation Prompt استخدام **Original Query** حتى لو استُخدم Rewritten Query في Retrieval. إذ يحافظ Original Query على Task التي قصدها المستخدم.

ثانيًا، قد يهم Placement. يشير المصدر إلى أن Models كثيرة قد تستجيب بصورة أفضل عندما يظهر Query قبل Context.

ثالثًا، يمكن لـ Prompt Instructions تقييد الإجابات غير المدعومة بصورة صريحة:

```text
إذا تعذّر استنتاج الإجابة بشكل معقول من السياق،
فقل إنك لا تعرف.
```

رابعًا، يمكن أن تكون Prompts خاصة بكل Task. فلا يلزم أن يطابق Question-answering Prompt شكل Summarization Prompt.

وأخيرًا، تستطيع Tags بأسلوب XML جعل أقسام Prompt متميزة بصريًا وبنيويًا.

القاعدة العامة ليست «استخدم Prompt عالميًا واحدًا». بل **صمّم Prompts وقيّمها وطبّق Versioning لها باعتبارها جزءًا من نظام RAG**.

## 45. تقييم LLMs و Prompt Templates

لاختيار Generator و Prompt، ابدأ بـ Evaluation Queries تشبه طلبات المستخدم الحقيقية. إذا كانت Real Traffic متاحة، خذ Sample منها. وإلا فأنشئ Test Cases ممثلة اعتمادًا على البيانات والاستخدام المتوقع.

يسلط الفصل الضوء على بُعدين أساسيين للإجابة:

- **Relevance:** هل تجيب الإجابة فعلًا عن Query؟
- **Faithfulness:** هل تدعم Retrieved Documents الإجابة؟

تُناقش ثلاثة أساليب Evaluation.

### التقييم باستخدام LLM-as-a-judge

يُطلب من Model إعطاء Score أو Critique للمخرجات. هذا مريح ومرن، لكنه قد يكون مكلفًا وبطيئًا وغير متسق، كما أن Model نفسه قد يرتكب Reasoning خاطئًا.

### نماذج Evaluation مخصصة لـ NLG

يمكن لـ Models أصغر مدرّبة على أبعاد Evaluation محددة أن تكون أرخص وأسرع وأكثر استقرارًا لمهام مستهدفة مثل Faithfulness Detection.

### التقييم البشري (Human Evaluation)

يمكن للبشر تقديم أكثر الأحكام دقة وعمقًا، لكن ذلك مكلف ويستغرق وقتًا. يعامل الفصل Human Evaluation باعتبارها مرجعًا عالي الجودة، وتُستخدم غالبًا في Final Checks أصغر.

Workflow العملية هي:

```text
استعلامات التقييم (evaluation queries)
→ تشغيل إعدادات RAG المرشحة (run candidate RAG configurations)
→ جمع الإجابات (collect answers)
→ تقييم Relevance و Faithfulness ومعايير أخرى (score relevance / faithfulness / other criteria)
→ مقارنة الإعدادات (compare configurations)
→ اختيار أفضل مفاضلة (select the best trade-off)
```

## 47. Debug لنظام RAG باعتباره نظامًا متفاعلًا

خلاصة الفصل أهم من أي مثال Library منفرد: **مكونات RAG لا تعمل بصورة مستقلة**.

يمكن أن ينتقل الفشل عبر المراحل:

```text
OCR سيئ
→ Text تالف
→ Chunks ضعيفة
→ Embeddings مضللة
→ Retrieval خاطئ
→ Answer غير مدعومة
```

أو:

```text
Documents جيدة
→ Chunks كبيرة أكثر من اللازم
→ Embeddings مخففة
→ Chunk الإجابة يقع أسفل k
→ Generator لا يرى الإجابة أبدًا
```

أو:

```text
Retrieval جيد
→ Chunks مكررة أكثر من اللازم
→ Prompt طويل ومليء بالـ Noise
→ Generation أضعف
```

لذلك تفحص Workflow منضبطة للـ Debug الـ Intermediate Artifacts:

1. ماذا أنتج Parsing بالضبط؟
2. ما Chunks التي أُنشئت؟
3. ما Metadata التي جرى الحفاظ عليها؟
4. ما Vector Model وما Dimensions المستخدمة؟
5. ما Candidates التي أعادها Retrieval؟
6. وبأي ترتيب؟
7. ما Context التي أُرسلت أخيرًا إلى LLM؟
8. بماذا وجّه Prompt الـ Model؟
9. هل كانت الإجابة Relevant و Faithful؟

هذا هو الأساس لهندسة RAG في Production.

## 48. تجميع المكدس الأساسي لـ RAG

يمكنك الآن قراءة مكدس RAG الأساسي كتدفق واحد مستمر لتحويل المعلومات:

```text
بيانات المصدر (SOURCE DATA)
   ↓
تحليل المستند (PARSING)
استعادة محتوى مفيد مع Metadata (recover useful content + metadata)
   ↓
تقسيم النص (CHUNKING)
إنشاء وحدات دلالية بحجم Retrieval (create retrieval-sized semantic units)
   ↓
إنشاء Embedding والفهرسة (EMBEDDING / INDEXING)
إنشاء تمثيلات قابلة للبحث (create searchable representations)
   ↓
قاعدة البيانات المتجهية (VECTOR DATABASE)
حفظ Vectors و Text و Metadata (persist vectors, text, and metadata)
   ↓
استعلام المستخدم (USER QUERY)
   ↓
إعادة صياغة الاستعلام (QUERY REWRITING)
فصل حاجة Retrieval عن تعليمة المهمة (separate retrieval need from task instruction)
   ↓
الاسترجاع (RETRIEVAL)
بحث كثيف وطرق Hybrid لاحقًا (dense search and later hybrid methods)
   ↓
إعادة الترتيب والاختيار (RERANKING / SELECTION)
تقليل التكرار وتحسين الترتيب (reduce redundancy and improve ordering)
   ↓
تجميع Prompt (PROMPT ASSEMBLY)
الاستعلام الأصلي مع الأدلة النصية المختارة (original query + selected text evidence)
   ↓
التوليد (GENERATION)
ينتج LLM استجابة Grounded (LLM produces grounded response)
   ↓
التقييم (EVALUATION)
Relevance + Faithfulness + معايير التطبيق (application criteria)
```

كل سهم يمثل Interface. ويمكن لكل Interface إدخال Loss أو Latency أو افتراضات غير صحيحة. تأتي RAG بجودة Production من فهم هذه Interfaces وقياسها، لا من تحسين مكوّن واحد بمعزل عن البقية.

## تصورات خاطئة مهمة

### التصور الخاطئ

> «إذا استخدمت LLM قويًا، تصبح جودة Ingestion أقل أهمية.»

### لماذا هذا خطأ؟

لا يرى Generator إلا ما حافظت عليه Upstream Pipeline وما استرجعته. لا يمكن لـ Model أقوى إعادة بناء Parsing تالف أو Chunks مفقودة بصورة موثوقة.

### التصور الخاطئ

> «يحتوي PDF بالفعل على فقرات مرتبة وفق ترتيب القراءة المنطقي.»

### لماذا هذا خطأ؟

PDF هو أساسًا Format للـ Visual Layout. ويمكن تخزين Text كأحرف موضوعة بإحداثيات، لذلك يجب غالبًا استنتاج ترتيب القراءة.

### التصور الخاطئ

> «يعني Parsing حذف كل Formatting و Metadata.»

### لماذا هذا خطأ؟

قد تكون بعض عناصر البنية، مثل المتحدث والتاريخ وقسم المستند و Security Label أو Attributes أخرى، ضرورية لـ Filtering والتفسير لاحقًا.

### التصور الخاطئ

> «استخدام VLM يجعل Document Parsing أكثر دقة تلقائيًا.»

### لماذا هذا خطأ؟

VLMs مرنة لكنها Generative. يمكن أن تقوم بـ Hallucination، وتكون أعلى Cost وأبطأ، وقد تظل تفشل في إعادة إنتاج محتوى المستند بدقة تامة.

### التصور الخاطئ

> «نوافذ Context الضخمة في LLM تلغي الحاجة إلى Chunking.»

### لماذا هذا خطأ؟

تحسن Chunking أيضًا اختيار Evidence، وتضبط Latency و Cost، ويجب أن تحترم Context Limit الخاص بـ Embedding Model نفسه.

### التصور الخاطئ

> «Chunks الأصغر أفضل دائمًا.»

### لماذا هذا خطأ؟

يمكن لـ Chunks شديدة الصغر أن تفقد Context المحيط والعلاقات. تمثل Chunking توازنًا بين التركيز و Context الكافي.

### التصور الخاطئ

> «Semantic Chunking هي أفضل استراتيجية تلقائيًا.»

### لماذا هذا خطأ؟

يستشهد الفصل بأدلة Benchmark حققت فيها Semantic Chunking و Fixed-size Chunking أداءً متقاربًا. ويجب التحقق من الاختيار الصحيح على Corpus المستهدفة.

### التصور الخاطئ

> «Embeddings مجرد حيلة لمطابقة Synonyms.»

### لماذا هذا خطأ؟

يمكن لـ Embeddings تمثيل علاقات دلالية أوسع، مثل ربط Query عن US بمستند يتناول California.

### التصور الخاطئ

> «المزيد من Embedding Dimensions أفضل دائمًا.»

### لماذا هذا خطأ؟

يمكن للأبعاد الأعلى زيادة Storage و Compute. ويكون أفضل Dimension نتيجة مفاضلة بين Quality و Efficiency.

### التصور الخاطئ

> «يعيد ANN Search أقرب Vector بصورة Exact.»

### لماذا هذا خطأ؟

تستبدل Approximate Nearest-neighbor Methods عمدًا جزءًا من Exactness بالسرعة، وقد تفوّت أحيانًا أقرب نقطة رياضيًا.

### التصور الخاطئ

> «Vector Database مجرد Function للعثور على Nearest Neighbors.»

### لماذا هذا خطأ؟

تتعامل Vector Database أيضًا مع Persistence و Updates و Deletes و Metadata و Filtering و Indexing و Operational Integration.

### التصور الخاطئ

> «يتلقى Generator قيم Embedding Vectors.»

### لماذا هذا خطأ؟

تختار Embeddings الـ Records. أما Generator فيتلقى عادةً Text الأصلي للـ Chunks بالإضافة إلى طلب المستخدم.

### التصور الخاطئ

> «إذا أعادت Retrieval Chunks مهمة، فإضافة Chunks أكثر لا يمكن إلا أن تساعد.»

### لماذا هذا خطأ؟

يمكن لقيمة `k` كبيرة إدخال Redundancy و Evidence غير مهمة و Cost أعلى و Prompt أكثر Noise.

### التصور الخاطئ

> «ينبغي لـ Query Rewriting استبدال طلب المستخدم الأصلي في كل مكان.»

### لماذا هذا خطأ؟

تُحسن Rewritten Query من أجل Retrieval. لكن Original Query تظل مطلوبة أثناء Generation للحفاظ على Task التي طلبها المستخدم.

### التصور الخاطئ

> «يمكن الحكم على جودة RAG من Final Answer فقط.»

### لماذا هذا خطأ؟

قد ينشأ Final Error من Parsing أو Chunking أو Embeddings أو Filtering أو Ranking أو Prompt Assembly أو Generation. لذلك يجب فحص Intermediate Artifacts.

## احتفظ بهذه الفكرة

**لا يكون نظام RAG أقوى من مسار Evidence الذي يصل إلى Generator الخاص به.** يجب تنفيذ Parsing للـ Raw Documents دون تدمير البنية المفيدة، وتقسيمها إلى Retrieval Units تحافظ على Context كافٍ، وتمثيلها باستخدام Embeddings تلائم Model و Database المختارين، والبحث فيها بتوازن مناسب بين Exact Constraints و Semantic Similarity، وتقليصها إلى مجموعة صغيرة من Evidence عالية الجودة قبل Generation. عندما تفشل إجابة، افحص ذلك المسار مرحلةً بعد مرحلة: فالـ LLM النهائي ليس إلا آخر مكوّن في سلسلة من القرارات الهندسية.
