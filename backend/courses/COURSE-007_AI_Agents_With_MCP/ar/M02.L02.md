## 1. الانتقال إلى ما بعد MCP client أساسي (Moving beyond a basic MCP client)

في الدرس السابق، كان client يستهلك غالبًا القدرات من server: tools و resources و prompts. يضيف هذا الفصل الاتجاه العكسي: **يمكن لـ client أيضًا توفير قدرات يستطيع server الاستفادة منها**.

يركز المصدر على ثلاث قدرات من جانب client:

| القدرة (Capability) | ما يتلقاه server من client |
|---|---|
| قدرة Sampling | وصول إلى LLM الخاص بتطبيق host عبر client |
| نطاقات Roots | معلومات حول مواقع filesystem المراد إتاحتها |
| قدرة Elicitation | طريقة لطلب معلومات أو موافقة من المستخدم عبر UI الخاص بـ host |

يعتمد نمط التنفيذ العام على callbacks:

```text
1. نفّذ callback داخل client.
2. طابق توقيع callback الذي يتوقعه نوع SDK/protocol.
3. مرّر callback إلى constructor الخاص بـ Client.
4. يعلن SDK عن هذه القدرة ويستدعي callback عند الحاجة.
```

يمثل هذا تحولًا معماريًا مهمًا. لم يعد MCP client مجرد قناة من host إلى server. بل يصبح حدًا نشطًا للثقة والتفاعل بين server والمستخدم و LLM وجهاز host.

> **ملاحظة إصدار من الفصل المقدم:** يصف المصدر roots و sampling و logging بأنها في اتجاه deprecation ضمن specification/SDK الحديث. وما زالت تُدرَّس كي تستطيع clients دعم servers الأقدم. تعامل معها كموضوعات توافق مرتبطة بإصدار محدد، لا كميزات ينبغي إضافتها تلقائيًا إلى كل نظام جديد.

## 2. فهم MRTR

يشرح الفصل تغييرًا مهمًا في نموذج تفاعل MCP الحديث. كان سلوك protocol الأقدم قد يسمح لـ server ببدء requests مباشرة إلى client. أما في النموذج الأحدث الموضح في المصدر، فتُعالَج احتياجات server إلى client كجزء من request **بدأ أصلًا من client**.

هذا هو نمط **MRTR**.

### MRTR خطوة بخطوة (MRTR step by step)

```text
Client → Server: request أصلي
Server → Client: InputRequiredResult(inputRequests=...) — طلب input إضافي
Client: تشغيل callback / جمع input المطلوب
Client → Server: إعادة محاولة الإجراء الأصلي باستخدام request ID جديد + inputResponses
Server → Client: النتيجة النهائية
```

القاعدة الأساسية هي أن طلب server لـ input إضافي يحدث **داخل تدفق إجراء بدأ من client**.

بالنسبة للمطور، فالخبر الجيد هو أن Python SDK يتولى معظم آلية round-trip هذه خلف الكواليس. ومسؤوليتك الأساسية هي تنفيذ callback بصورة صحيحة وآمنة.

[[IMAGE_NEEDED: MCP Multi Round-Trip Request flow | A sequence diagram with Client sending request, Server returning InputRequiredResult, Client callback collecting information, Client retrying with inputResponses and a new request ID, then Server returning the final result | Learner should notice that the server's extra request is part of a client-originated workflow]]

## 3. Sampling: السماح لـ server بطلب استخدام LLM الخاص بـ host

تسمح Sampling لـ server متصل بأن يطلب من client استخدام LLM الخاص بتطبيق host. ويمكن أن يتيح ذلك workflows متداخلة ومتقدمة. على سبيل المثال، قد يحتاج tool على جانب server إلى أن يصنف model شيئًا ما، أو يولد نصًا، أو يختار بين خيارات، أو يساعد في إكمال جزء من عملية أكبر.

### لماذا Sampling قوية؟ (Why sampling is powerful)

من دون Sampling، يستطيع server تنفيذ code حتمي خاص به، لكنه لا يحصل تلقائيًا على وصول إلى model الخاص بـ host. توفر Sampling جسرًا مضبوطًا إلى ذلك model.

قد يحمل request الخاص بـ Sampling معلومات مثل:

- messages الخاصة بالمحادثة،
- تفضيلات model،
- system prompt اختياري،
- سلوك context المطلوب،
- قيمة temperature،
- الحد الأقصى من tokens،
- تسلسلات التوقف (stop sequences).

يترجم callback الخاص بـ client هذا request إلى التنسيق الذي يتوقعه LLM provider الخاص بـ host، ثم يستدعي model، ويحوّل النتيجة مرة أخرى إلى محتوى MCP، ويعيدها إلى server.

### أهم قاعدة في Sampling: الحفاظ على تحكم المستخدم (The most important sampling rule: preserve user control)

يشدد المصدر بقوة على موافقة **Human-in-the-Loop**. لا ينبغي لـ server أن ينفق ميزانية model الخاصة بالمستخدم بصمت أو يحقن model prompts عشوائية عبر client.

التدفق الأكثر أمانًا هو:

```text
Server يطلب Sampling
      ↓
Client يعرض هوية server + prompt/الغرض المطلوب
      ↓
المستخدم يوافق أو يرفض
      ↓
إذا تمت الموافقة، يستدعي client الـ LLM
      ↓
قد يعرض client الـ output للموافقة
      ↓
تعود النتيجة المعتمدة إلى server
```

يوصي الفصل أيضًا باحترام إشارات تفضيلات model عند ملاءمة ذلك، وتنفيذ rate limiting.

## 4. Roots: تنسيق نطاق filesystem (Roots: coordinating filesystem scope)

توضح Roots مواقع filesystem المراد إتاحتها لـ server. فمثلًا، قد يتيح coding assistant فقط مجلد المشروع الذي اختاره المستخدم.

تحتوي root على file URI واحد على الأقل، وقد تتضمن اسمًا مقروءًا للبشر و metadata.

### Roots للتنسيق وليست للإنفاذ (Roots are coordination, not enforcement)

هذه واحدة من أهم التحذيرات في الفصل:

**Roots ليست security sandbox.**

يمكن لـ server اختيار عدم احترامها. لذلك، ما يزال تطبيق host يحتاج إلى access controls فعلية حول الملفات والمجلدات.

يسرد المصدر عدة توقعات للتنفيذ:

- إتاحة المواقع التي تتوافق permissions الخاصة بها مع الاستخدام المقصود فقط،
- التحقق من root URIs لمنع path traversal،
- تنفيذ access controls فعلية،
- مراقبة accessibility،
- الحصول على موافقة المستخدم قبل مشاركة roots،
- توفير UI مفهوم لفحص roots وتغييرها.

### نمط Callback (Callback pattern)

يمكن لـ client الاحتفاظ بقائمة من filesystem URIs المهيأة، والتحقق منها، وتحويلها إلى كائنات `Root`، وإعادتها من roots callback. وإذا لم تبقَ roots صالحة بعد التحقق، فيمكن لـ callback إعادة معلومات error منظَّمة.

يوضح مثال الفصل أيضًا مبدأ تصميم أوسع: **يمتلك host إعدادات المستخدم؛ ويعرض client هذه الإعدادات إلى MCP بصيغة protocol**.

[[IMAGE_NEEDED: Roots as coordination vs real access control | A diagram showing a user-selected project directory passed as an MCP root to a server, while a separate host-side permission boundary enforces actual filesystem access | Learner should notice that the root is a hint/scope declaration, while security enforcement must exist elsewhere]]

## 5. Elicitations: إدخال الإنسان في الحلقة (Elicitations: bringing the human into the loop)

تسمح Elicitations لـ server بأن يطلب من المستخدم معلومات إضافية عبر client و UI الخاص بتطبيق host. وهذا مفيد عندما يحتاج workflow إلى توضيح أو موافقة أو معلومات منظَّمة أو قرار لا ينبغي لـ model تخمينه.

يصف الفصل ثلاث نتائج ممكنة للمستخدم:

| النتيجة (Outcome) | المعنى |
|---|---|
| قبول (accept) | يوافق المستخدم ويقدم المعلومات المطلوبة |
| رفض (decline) | يرفض المستخدم الطلب صراحةً |
| إلغاء (cancel) | ينتهي التفاعل دون موافقة أو رفض صريح |

يمكن لـ servers توفير schema منظَّمة تصف الحقول المطلوبة. ويستطيع client عرض form، وجمع input، والتحقق منه، وإعادة البيانات المقبولة.

### UX آمن لـ Elicitation (Safe elicitation UX)

يوصي المصدر بأن يقوم client بما يلي:

- عرض server الذي يطلب المعلومات،
- شرح المعلومات المطلوبة وسبب طلبها،
- السماح بخيارات accept/decline/cancel،
- التحقق من البيانات المعادة مقابل schema،
- تطبيق rate limiting على الطلبات المتكررة.

يناقش الفصل أيضًا Elicitation بأسلوب URL. يعرض client الآمن destination URL كاملًا ويطلب موافقة صريحة من المستخدم قبل فتحه.

### Callback عام و UI محدد (Generic callback, specific UI)

لا ينبغي أن يحتاج callback إلى معرفة hard-coded بكل server. فهو يستقبل request schema ويعرض أو يجمع المعلومات المطلوبة ديناميكيًا. ويحافظ ذلك على أحد الأهداف المركزية لـ MCP: فصل تطبيقات host عن تطبيقات server الفردية.

[[IMAGE_NEEDED: Elicitation user-consent flow | A sequence diagram showing Server requesting information, Client displaying server identity and schema, User choosing accept/decline/cancel, and accepted structured data returning through the client | Learner should notice that the client protects the user from silent server data collection]]

## 6. تفويض MCP servers البعيدة باستخدام OAuth 2.1 (Authorizing remote MCP servers with OAuth 2.1)

غالبًا ما تعرض MCP servers البعيدة tools أو بيانات محمية. يستخدم الفصل OAuth 2.1 كنموذج authorization لهذه الاتصالات.

تتوافق أدوار OAuth الأساسية طبيعيًا مع MCP:

| مفهوم OAuth | المقابل في MCP |
|---|---|
| عميل OAuth (OAuth client) | MCP client / تطبيق host |
| خادم الموارد (Resource server) | MCP server محمي |
| خادم التفويض (Authorization server) | نظام مستقل للهوية/authorization |

### تدفق authorization المفاهيمي (Conceptual authorization flow)

```text
المستخدم يطلب من host الوصول إلى MCP server محمي
        ↓
MCP client يتلقى authorization challenge
        ↓
Authorization server يتحقق من هوية المستخدم
        ↓
Client يتلقى/يخزن token
        ↓
Client يستخدم token عند الوصول إلى MCP server
        ↓
MCP server يتحقق من token ويسمح/يرفض الوصول
```

[[IMAGE_NEEDED: OAuth flow for a remote MCP server | A diagram showing User/Host, MCP Client as OAuth client, Authorization Server, and MCP Server as resource server; show token issuance and authenticated MCP request | Learner should notice that the authorization server is separate from MCP even though the MCP client uses its token]]

### تسجيل Client (Client registration)

يقدم الفصل فكرتين للتسجيل:

- **CIMD** — المسار المفضل الموضح في المصدر لهوية client مستضافة.
- **DCR** — fallback/بديل مدعوم عبر client metadata.

يوفر التطبيق تفاصيل مثل redirect URIs و scopes وتخزين token ومعالجة redirect و authorization callbacks. ثم يتولى SDK جزءًا كبيرًا من تدفق registration/authorization التفصيلي.

### لماذا ينتمي OAuth إلى طبقة HTTP client؟ (Why OAuth belongs in the HTTP client layer)

يمكن لـ client wrapper قبول كائن `auth` وتمريره إلى asynchronous HTTP client المستخدم بواسطة Streamable HTTP. وهذا يبقي authorization مدمجًا مع سلوك remote transport بدل hard-coding لمنطق token في أنحاء agent.

### مبدأ الأمان (Security principle)

تمثل authorization tokens بيانات اعتماد. وينبغي تخزينها والتعامل معها باستخدام آلية آمنة لتخزين tokens تناسب التطبيق، وألا تُطبع أو تُضمَّن داخل prompts أو تُرسل إلى source control.

## 7. دعم عدة model providers (Supporting multiple model providers)

لا ينبغي أن يُجبر MCP تطبيق host على استخدام model provider واحد. لكن model APIs المختلفة تمثل tools و messages بطرق مختلفة.

من التصميم السيئ أن تجعل MCP client يعيد كائنات tool منسقة مسبقًا لـ provider واحد. فهذا يربط client بذلك provider.

التصميم الأفضل هو إنشاء **internal representation**.

```text
أداة MCP (MCP Tool)
   ↓
تمثيل InternalTool
  ├── translate_to_anthropic() — تحويل إلى Anthropic
  ├── translate_to_openai() — تحويل إلى OpenAI
  └── translate_to_other_provider() — تحويل إلى provider آخر
```

### لماذا هذه المعمارية أفضل؟ (Why this architecture is better)

- تبقى معالجة MCP protocol مستقلة عن اختيار model.
- يمتلك host قرار اختيار model.
- إضافة model provider آخر لا تتطلب إعادة تصميم اتصال server.

## 8. اكتشاف servers باستخدام MCP Registry (Discovering servers with the MCP Registry)

يصف الفصل MCP Registry باعتباره آلية اكتشاف مركزية لـ MCP servers. ومن منظور مطور client، تتمثل الفائدة الأساسية في أن registry metadata يمكن أن توفر المعلومات المطلوبة لتهيئة الاتصال.

بالنسبة إلى remote server، قد توفر registry data عنوان Streamable HTTP URL.

بالنسبة إلى local packaged server، قد توفر registry metadata معلومات تُحوَّل إلى:

- runtime مثل `uvx` أو `npx`،
- معرّف package،
- runtime arguments،
- معلومات transport.

يتيح ذلك UX مثل:

```text
المستخدم يختار server بالاسم
        ↓
Host يستعلم من registry
        ↓
Host يحدد transport المدعوم
        ↓
Host يبني إعدادات اتصال MCP client
        ↓
Client يتصل
```

### الثقة في Registry ليست مراجعة code (Registry trust is not code auditing)

يمكن لـ registry تحسين قابلية الاكتشاف وهوية publisher، لكنها لا تعني تلقائيًا أن code الخاص بكل server آمن. يوصي الفصل بممارسات production مثل version pinning والتعامل الآمن مع authorization.

هذا مهم خصوصًا مع local packages، لأن تثبيت/تشغيل local MCP server يعني تنفيذ code داخل بيئة المستخدم أو التطبيق.

## 9. الاتصال بعدة MCP servers (Connecting to multiple MCP servers)

لا تزال كل low-level client session تمثل علاقة مع server واحد. وللتطبيقات التي تحتاج إلى عدة servers، يقدم المصدر `ClientSessionGroup` كطريقة لإدارة عدة sessions معًا.

يمكن لـ session group أن:

- يتصل بعدة servers،
- يحتفظ بمجموعة من sessions،
- يجمع tools و resources و prompts،
- يربط tools مرة أخرى بالـ session المناسبة،
- يفصل اتصال servers فردية.

يغيّر ذلك client wrapper. فبدل تخزين `_client` واحد و flag واحد باسم `_connected`، يمكنه تخزين session group وتحديد الجاهزية بحسب وجود sessions حاليًا في المجموعة.

### تعارض الأسماء يصبح مشكلة معمارية حقيقية (Name collisions become a real architecture problem)

يحذر الفصل من أن أسماء primitives تُجمَّع داخل dictionaries. لذلك قد يحدث تعارض عندما يعرض serverان الاسم نفسه لـ tool أو primitive.

تشمل الحلول:

- رفض حالات التعارض،
- تطبيق namespacing على primitives بحسب server،
- استخدام component-name hook لإعادة تسميتها بصورة متسقة.

على سبيل المثال:

```text
github:create_issue — tool من GitHub
linear:create_issue — tool من Linear
```

أكثر أمانًا بكثير من وجود toolين غير مؤهلين بالاسم `create_issue`.

## 10. Context engineering لمجموعات tools الكبيرة (Context engineering for large tool sets)

تستهلك تعريفات tools مساحة من model context. وإذا اتصل التطبيق بعدة servers، فإن إرسال كل tool schema في كل LLM call قد يصبح مكلفًا ويجعل اختيار tool أصعب أيضًا.

يستكشف الفصل عدة أنماط لتقليل هذا الحجم.

### النمط A: tool assembler / التحديث في كل turn (Pattern A: tool assembler / refresh every turn)

يعيد التطبيق بناء قائمة tools المتاحة في كل conversation turn. ولا يقلل ذلك tokens بالضرورة، لكنه يقلل التعريفات القديمة.

لا يلزم أن يضغط discovery المتكرر على server إذا كانت SDK cache مهيأة. تسمح TTL لـ client بخدمة tool metadata الحديثة محليًا حتى تنتهي صلاحية cache أو يبطلها list-change event.

فكّر في هذا النمط باعتباره يعطي الأولوية لـ **freshness**، لا لتقليل tokens.

### النمط B: Tool search (Pattern B: tool search)

بدل عرض كل tool، اعرض قدرة صغيرة باسم `search_tools`. يبحث model أولًا عن tool مناسب، ثم لا تُضاف إلى قائمة tools النشطة إلا تعريفات tools المطابقة.

```text
كل tools مخزنة خارج context النشط
        ↓
Model يرى search_tools فقط
        ↓
Model يبحث: 'count'
        ↓
تُضاف تعريفات tools المطابقة
        ↓
Model يختار tool الفعلي
```

يمكن لهذا أن يقلل حجم context بدرجة كبيرة عندما يحتوي التطبيق على عشرات أو مئات tools.

المقابل هو خطوة search إضافية وربما round trip إضافية بين model و tool.

يمكن استخدام المفهوم نفسه للبحث في resources قبل تحميلها إلى context.

### النمط C: Code execution / Code mode (Pattern C: code execution / code mode)

يصف الفصل نمطًا أكثر جذرية: إعطاء model execution interface صغيرة إلى جانب typed tool stubs قابلة للبحث، ثم طلب إنشاء code ينسق عدة عمليات داخل sandbox.

يمكن أن يقلل ذلك:

- عدد tool schemas داخل model context،
- عدد round trips الوسيطة إلى model،
- كمية intermediate result data المنسوخة إلى context window.

لكنه يضيف متطلبًا حاسمًا: **يجب أن تكون execution sandbox معزولة فعليًا**.

يسلط المصدر الضوء على توقعات العزل مثل:

- عدم وجود outbound network access من sandbox،
- عدم وجود authorization credentials داخل sandbox،
- عدم وجود وصول عكسي إلى execution environment الخاصة بتطبيق host،
- استمرار توجيه تنفيذ MCP tools عبر trusted client boundary.

## 11. الأمان: تعامل مع client كحد للثقة (Security: treat the client as a trust boundary)

هذه واحدة من أهم دروس production في الفصل.

يقع MCP client بين servers قد تكون غير موثوقة وبين تطبيق host و model وبيانات المستخدم و filesystem و credentials. لذلك، **client هو trust boundary**.

### تعريفات Tools هي input غير موثوق (Tool definitions are untrusted input)

قد يحتوي اسم tool أو description أو schema أو result أو resource أو prompt على نص يصل إلى context الخاص بـ LLM. ويشير المصدر إلى أن هذا فعليًا prompt injection مقصود: إذ تُدرج البيانات الخارجية داخل prompt الخاص بـ model بحكم التصميم.

التحدي الهندسي هو السماح بـ context مشروع مع الحد من التأثير الخبيث.

### وسائل دفاع مفيدة من جانب client في الفصل (Useful client-side defenses from the chapter)

- طلب موافقة المستخدم قبل تمكين tools جديدة،
- عرض أسماء tools و descriptions و schemas،
- إعادة طلب الموافقة بعد تغييرات capability-list عند الحاجة،
- تطبيق namespacing على tools حسب server لتقليل هجمات name-shadowing،
- استخدام معالجة credentials المعتمدة على environment للـ local servers،
- استخدام OAuth للخدمات البعيدة المحمية،
- تثبيت versions الخاصة بـ local server/package،
- تفضيل registries الموثوقة،
- إبقاء العمليات الحساسة خلف موافقة صريحة من المستخدم.

### مخاطر Local server (Local server risk)

تشغيل local MCP server يعني تنفيذ code داخل البيئة المحلية. ويستحق ذلك الحذر نفسه المطلوب عند تثبيت أي package أو executable آخر.

يعتمد الوضع الأمني الصحيح أيضًا على ما يستطيع host الوصول إليه. يختلف risk profile لحاسبة محلية تجريبية اختلافًا كبيرًا عن تطبيق بنكي أو تطبيق لإدارة المؤسسة.

## 12. إدارة اتصال resilient (Resilient connection management)

يشدد الفصل على سلوك retry-and-refresh بدل حالة connection-resume المعقدة.

### استعادة stdio (stdio recovery)

غالبًا ما يعني انقطاع stdio session أن subprocess قد تعطلت. تتطلب الاستعادة عادةً:

```text
اكتشاف الفشل → إعادة تشغيل subprocess → إعادة الاتصال → تحديث capabilities → إعادة محاولة الإجراء المناسب
```

أي شيء كان محفوظًا فقط في memory الخاصة بعملية server القديمة يضيع، لذلك لا يمكن لـ client افتراض بقاء server state.

### استعادة Streamable HTTP (Streamable HTTP recovery)

يمكن إعادة محاولة remote requests باستخدام backoff. لكن المصدر يثير مسألة مهمة: قد تؤدي إعادة محاولة إجراء إلى تكرار side effects إذا لم يكن tool من نوع idempotent.

لذلك، قد يحتاج host/client إلى deduplication logic لإجراءات مثل إنشاء tickets أو إرسال messages أو تحصيل أموال.

### الاشتراكات (Subscriptions)

بالنسبة إلى clients التي تستمع إلى change events، ينبغي لانقطاع subscription أن يؤدي عادةً إلى:

```text
فقدان Subscription
      ↓
Backoff — انتظار قبل إعادة المحاولة
      ↓
إعادة الاستماع (Re-listen)
      ↓
إعادة جلب state عند الحاجة
```

يشير المصدر أيضًا إلى أن servers الأقدم قد لا تدعم `listen()`، لذلك تحتاج clients إلى fallback path عندما لا يكون listening مدعومًا.

### نمط Background watcher (Background watcher pattern)

يمكن لـ change watcher أن يعمل بجانب conversation loop الرئيسية كمهمة async وأن يُلغى أثناء shutdown. وهذا يبقي معالجة capability changes مستقلة عن حلقة تفاعل المستخدم الرئيسية.

[[IMAGE_NEEDED: MCP recovery and resubscription flow | A diagram showing stdio crash recovery on one side and Streamable HTTP retry/backoff on the other, with a shared branch for refreshing capabilities and restoring subscriptions | Learner should notice that recovery strategy differs by transport but both require refresh and careful retry]]

## 13. تجربة المستخدم: Pagination و Caching والوضوح (User experience: pagination, caching, and visibility)

قد يبدو client الصحيح تقنيًا بطيئًا أو مربكًا رغم ذلك. يختتم الفصل بربط هندسة MCP بـ UX.

### تقسيم النتائج إلى صفحات (Pagination)

ينبغي جلب القوائم الكبيرة على صفحات. يمكن لـ server إعادة `nextCursor`، ويمرر client هذا cursor إلى list method نفسها لطلب الصفحة التالية.

يحدد المصدر دعم pagination لعمليات list مثل:

- الدالة `list_resources()`،
- الدالة `list_resource_templates()`،
- الدالة `list_prompts()`،
- الدالة `list_tools()`.

تساعد Pagination في كل من استخدام memory والاستجابة المحسوسة.

### Caching

يؤدي Caching لبيانات metadata الخاصة بـ tool/resource/prompt باستخدام TTLs مناسبة إلى تجنب network أو process calls المتكررة في workloads كثيرة القراءة. ويتمثل التحدي في الموازنة بين responsiveness و stale data.

تساعد list-change notifications ومسارات refresh الصريحة في حل ذلك.

### اجعل حالات الفشل ظاهرة (Make failures visible)

إذا اختفى tool كان متاحًا سابقًا، فينبغي أن يعكس UI ذلك بسرعة. إخفاء capabilities القديمة يؤدي إلى حالات فشل مربكة ويقلل ثقة المستخدم.

### Production client هو أيضًا جزء من UX product (A production client is partly a UX product)

إن approval dialogs و authorization redirects و elicitation forms و progress indicators و error messages و retries و server pickers ليست مجرد protocol glue. فهي تحدد ما إذا كان النظام يبدو آمنًا ومفهومًا.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: «القدرات التي يوفرها client تعني أن server يستطيع التحكم بحرية في host الخاص بي.»

**لماذا هذا خطأ:** يقرر client أي callbacks سيوفر، وينبغي أن يتوسط في التفاعلات الحساسة عبر validation و policy وموافقة المستخدم.

### المفهوم الخاطئ 2: «Roots تؤمّن filesystem.»

**لماذا هذا خطأ:** توضح roots النطاق المقصود لكنها ليست enforcement boundary. ولا تزال access controls الحقيقية مطلوبة.

### المفهوم الخاطئ 3: «Sampling ليست سوى model call أخرى على جانب server.»

**لماذا هذا خطأ:** تستخدم sampling الـ LLM الخاص بـ host عبر client، ما يخلق اعتبارات التكلفة والثقة والخصوصية والموافقة.

### المفهوم الخاطئ 4: «OAuth ينفذ authentication لكل شيء تلقائيًا.»

**لماذا هذا خطأ:** يتولى OAuth تدفقات authorization، لكن التطبيق ما يزال يحتاج إلى تخزين token آمن، ومعالجة صحيحة لـ redirect/callback، و scopes مناسبة.

### المفهوم الخاطئ 5: «دعم عدة models يعني تكرار MCP client بالكامل.»

**لماذا هذا خطأ:** يسمح internal representation المحايد بالنسبة إلى providers ببقاء طبقة MCP مستقرة بينما تترجم adapters إلى كل model API.

### المفهوم الخاطئ 6: «وجود entry في registry يعني أن server موثوق بالكامل.»

**لماذا هذا خطأ:** لا تساوي discovery/publisher metadata مراجعة code. ما تزال local packages تنفذ code وينبغي version pinning لها وتقييمها بصورة مناسبة.

### المفهوم الخاطئ 7: «الاتصال بعدد أكبر من servers لا يفعل إلا زيادة القدرات.»

**لماذا هذا خطأ:** يزيد ذلك أيضًا تعارضات tools وحجم context و security surface والتعقيد التشغيلي.

### المفهوم الخاطئ 8: «Tool search و Code mode يحلان المشكلة نفسها بالطريقة نفسها.»

**لماذا هذا خطأ:** يضيّق tool search تعريفات tools التي تدخل context؛ بينما يغيّر code execution كيفية تنسيق عدة عمليات ويمكنه إبقاء intermediate results خارج model context.

### المفهوم الخاطئ 9: «إعادة محاولة tool call فاشلة آمنة دائمًا.»

**لماذا هذا خطأ:** يمكن تكرار الإجراءات non-idempotent. يجب أن يفهم retry logic الـ side effects أو يتضمن deduplication safeguards.

## المصطلحات الأساسية (Key terminology)

| المصطلح (Term) | المعنى |
|---|---|
| قدرة Client (Client capability) | وظائف يعرضها MCP client لـ server workflows عبر callbacks |
| MRTR | نمط يطلب فيه server input إضافيًا داخل request flow بدأ من client |
| InputRequiredResult | استجابة من server تشير إلى الحاجة لمزيد من input من client/user قبل أن تكتمل العملية الأصلية |
| قدرة Sampling | قدرة client تسمح لـ server بطلب استخدام LLM الخاص بتطبيق host |
| HITL | موافقة أو input بشري أثناء workflow آلي |
| نطاقات Roots | مواقع filesystem يعرّفها client باعتبارها نطاقًا مقصودًا لـ server؛ وليست access-control boundary كاملة |
| Elicitation | طلب من server للحصول على user input أو موافقة أو structured form data أو متابعة URL عبر client |
| OAuth 2.1 | معيار authorization يستخدمه المصدر للوصول المحمي إلى remote MCP server |
| خادم التفويض (Authorization server) | نظام ينفذ authentication/authorization للمستخدم ويصدر access tokens |
| خادم الموارد (Resource server) | خدمة محمية تستقبل access tokens؛ وتقابل MCP server في نموذج OAuth الخاص بالفصل |
| CIMD | metadata document يُستخدم لنشر client registration metadata |
| DCR | fallback/بديل لتسجيل client ديناميكيًا |
| InternalTool | internal representation محايد بالنسبة إلى provider لـ MCP tool |
| سجل MCP (MCP Registry) | مصدر metadata لاكتشاف servers موضح في الفصل |
| ClientSessionGroup | abstraction في SDK لإدارة عدة MCP server sessions معًا |
| تعارض الأسماء (Name collision) | تعارض يحدث عندما تعرض عدة servers primitives بالاسم نفسه |
| Tool assembler | نمط يحدّث/يعيد تجميع tools في كل turn، ويكون غالبًا مدعومًا بـ cache |
| Tool search | نمط progressive disclosure لا يحمل إلا تعريفات tools ذات الصلة بالمهمة الحالية |
| Code mode | نمط ينسق فيه code الذي يولده model العمليات داخل sandbox معزولة |
| TTL | مدة Time to live قبل انتهاء صلاحية capability metadata المخزنة في cache |
| إجراء Idempotent (Idempotent action) | عملية يمكن تكرارها بأمان دون side effects مكررة غير مقصودة |
| Backoff | الانتظار بين retries، وغالبًا مع زيادة التأخير بعد حالات الفشل المتكررة |
| `nextCursor` | pagination pointer يُستخدم لطلب الصفحة التالية من نتائج list |

## تحقق ذاتي (Self-check)

قبل المتابعة، تأكد من أنك تستطيع الإجابة عن:

1. ما الذي يتغير عندما يوفر MCP client قدرات إلى server؟
2. ما المشكلة التي يحلها MRTR في نموذج request الحديث الموضح في المصدر؟
3. لماذا ينبغي أن تتطلب sampling عادةً موافقة المستخدم؟
4. لماذا لا تعادل roots أمان filesystem؟
5. ما الفرق بين accept و decline و cancel في elicitation؟
6. كيف تتوافق أدوار OAuth client و resource server و authorization server مع MCP؟
7. لماذا يُعد internal representation باسم `InternalTool` والمحايد بالنسبة إلى provider مفيدًا؟
8. ما الذي يمكن أن تبسّطه registry لتطبيق host؟
9. لماذا قد تتعارض أسماء primitives عند تجميع عدة servers؟
10. ما المشكلة التي يحلها namespacing؟
11. ما الفرق بين tool assembler و tool search؟
12. لماذا يمكن لـ code execution تقليل استخدام model context؟
13. ما خصائص العزل التي ينبغي أن تمتلكها sandbox الخاصة بـ code execution؟
14. لماذا ينبغي التعامل مع تعريفات tools نفسها بوصفها input غير موثوق؟
15. لماذا قد يؤدي retry إلى تكرار side effects؟
16. ماذا ينبغي أن يحدث بعد فقدان change subscription؟
17. كيف تحسن pagination و caching تجربة المستخدم؟
18. لماذا ينبغي أن يعكس UI تغييرات capabilities بسرعة؟

## احتفظ بهذه الفكرة (Retain this idea)

**MCP client المخصص للإنتاج هو trust boundary و orchestration layer، وليس مجرد protocol adapter. فهو يقرر ما الذي يمكن لـ servers الوصول إليه، ومتى يجب أن يوافق المستخدم على إجراء، وكيف تُترجم وتُكتشف models و servers، وكمية context التي تصل إلى LLM، وكيف يتعافى النظام عندما تتغير حالة network أو process أو capabilities.**
