## 1. ما Anomaly؟

**Anomaly** هي Observation تختلف عن بقية Data بصورة تستحق الانتباه.

قد تسمع أيضًا مصطلحات:

- Outlier،
- Deviation،
- Exception،
- Novelty،
- Unusual value،
- Noise.

الكلمة المهمة ليست "مختلفة".

العبارة الأهم هي:

> **مختلفة بما يكفي لأننا نحتاج إلى فهم السبب.**

افترض أن أغلب Purchases تقع بين 100 و500 EGP، وهناك Purchase واحدة بقيمة 80,000 EGP.

قد تكون:

```text
معاملة احتيالية (a fraudulent transaction)
طلبًا شرعيًا من شركة (a legitimate enterprise order)
دفعة مكررة (a duplicated payment)
مشكلة في تحويل الوحدات (a unit-conversion problem)
معاملة اختبار (a test transaction)
```

الرقم وحده لا يخبرنا بالسبب.

### مصدران عامان للـ Anomalies

تأتي معظم Anomalies من واحد من مصدرين.

#### 1. حدث حقيقي غير معتاد

أمثلة:

- Fraud،
- Cyberattack،
- Campaign ناجحة بصورة غير معتادة،
- استخدام Product بطريقة غير متوقعة،
- Earthquake كبيرة،
- Customer عالي القيمة بصورة غير معتادة.

قد تكون Data صحيحة تمامًا.

الحدث نفسه هو غير المعتاد.

#### 2. مشكلة في جودة Data أوProcessing

أمثلة:

- Typo،
- Missing validation،
- Duplicated rows،
- Failed pipeline،
- Logging change،
- Unit mismatch،
- Default placeholder مخزن وكأنه Value حقيقية.

قد لا يكون Event نفسه غير معتاد إطلاقًا.

المشكلة في **تمثيل Event**.

[[IMAGE_NEEDED: IMG-M01-L06-01 / Instructor Figure — Two sources of anomalies and what to do next | Start with an unusual observation, branch into Real Event and Data/Processing Error; under Real Event show investigate business/security/scientific meaning and usually preserve the record, under Data Error show validate source, correct/remove if justified, and fix upstream; both branches feed into documented analysis decisions | Learner should notice that anomaly detection does not automatically mean anomaly deletion]]

### Anomalies الإيجابية مهمة أيضًا

Anomaly detection ليست مخصصة للمشكلات فقط.

قد ترغب في اكتشاف:

```text
عملاء ذوي Lifetime value مرتفعة بصورة غير معتادة (customers with unusually high lifetime value)
Campaigns ذات Conversion مرتفعة بصورة غير معتادة (campaigns with unusually high conversion)
Products ذات Return rates منخفضة بصورة غير معتادة (products with unusually low return rates)
Teams ذات Response times سريعة بصورة غير معتادة (teams with unusually fast response times)
```

Anomaly هي ببساطة شيء غير معتاد نسبةً إلى Baseline.

أما كون "غير المعتاد" جيدًا أوسيئًا فيعتمد على Context.

## 2. متى تكون SQL Tool جيدة لاكتشاف Anomalies؟

تكون SQL مفيدة عندما:

- تكون Data موجودة بالفعل في Database،
- يمكن التعبير عن Detection logic في صورة Rules واضحة،
- تحتاج إلى Summarize لملايين Rows،
- تكون Anomaly detection مرحلة داخل SQL analysis أكبر،
- تحتاج إلى Calculations قابلة لإعادة الإنتاج،
- لا تحتاج Latency إلى أن تكون فورية.

تكون SQL قوية بصورة خاصة لأسئلة مثل:

```text
ما Values الموجودة ضمن أعلى 1%؟ (Which values are in the top 1%?)
أي Customers اشتروا أكثر بكثير من المعتاد؟ (Which customers purchased much more than usual?)
أي Days شهدت Traffic مرتفعة بصورة غير معتادة؟ (Which days had unusually high traffic?)
أي Locations لديها Values خارج نطاقها الطبيعي؟ (Which locations have values outside their normal range?)
أي Accounts لم تظهر منذ مدة أطول بكثير من المعتاد؟ (Which accounts have not been seen for much longer than normal?)
```

### لماذا SQL جذابة؟

يمكن فحص SQL anomaly rule بصورة مباشرة.

مثلًا:

⟦CODE_0⟧

هذه Rule صريحة.

يستطيع Analyst آخر رؤية سبب Flagging لأي Row بدقة.

### أين تصبح SQL أضعف؟

قد لا تكون SQL أفضل Tool عندما:

#### نحتاج إلى Advanced statistical modeling

توفر Python وR Systems أوسع للـ Statistics وMachine learning.

#### نحتاج Detection لحظية على مستوى Milliseconds

قد تحتاج Fraud أوIntrusion systems إلى Streaming infrastructure بدل Analytics warehouse تستقبل Data بتأخير.

#### تتغير Pattern بصورة Adaptive

لا تتعلم Rule-based SQL تلقائيًا سلوك Attacker الجديد.

قد تكون Machine learning أفضل عندما يجب أن تتكيف Decision boundary اعتمادًا على Data.

### Pattern شائعة في Production

Architecture مفيدة هي:

```text
Historical data داخل SQL
        ↓
تعلم Typical ranges وSuspicious patterns
        ↓
تعريف Features وThresholds قابلة للتفسير
        ↓
تنفيذ Real-time checks داخل Streaming / Serving infrastructure
```

تظل SQL ذات قيمة حتى عندما لا تكون هي Final detection engine.

## 4. قِس مقدار عدم الاعتياد باستخدام Percentiles

يساعد Sorting على رؤية Extremes.

وتساعد Percentiles على **قياس** موضع Value داخل Distribution.

إذا كانت Value عند 95th percentile، فهذا يعني تقريبًا أن 95% من Observations أقل منها.

تشمل Reference points مفيدة:

```text
25th percentile — المئين 25
50th percentile = median — المئين 50 هو الوسيط
75th percentile — المئين 75
95th percentile — المئين 95
99th percentile — المئين 99
```

### `percent_rank`

يمكن لـ Window function حساب Relative rank لكل Row.

⟦CODE_6⟧

وللمقارنة الخاصة بكل Group:

⟦CODE_7⟧

يكون ذلك غالبًا أكثر معنى من Global percentile.

### احسب Rank قبل Aggregation

إذا كانت Repeated values مهمة للـ Distribution، فاحسب Percentile على مستوى Row أولًا.

تسلسل سيئ:

```text
اجمع Values (aggregate values)
-> percentile
```

عندما يكون Goal هو Row-level ranking.

تسلسل أفضل:

```text
Values على مستوى Row (row-level values)
-> percentile
-> Aggregate أوSummarize عند الحاجة
```

### `ntile`

تقسم `ntile` الـ Ordered rows إلى عدد محدد من Buckets.

⟦CODE_8⟧

```text

NTILE(10)  -> Deciles
NTILE(100) -> Buckets شبيهة بالـ Percentiles
```

تكون `ntile` مفيدة عندما لا تكون Exact percentile مهمة بقدر تقسيم Records إلى Relative bands.

### Thresholds الدقيقة للـ Percentiles

أحيانًا تريد Threshold value نفسها.

⟦CODE_9⟧

```text

```

والفرق مهم.

### `percentile_cont`

تعيد Interpolated value عند Percentile المطلوبة.

قد لا توجد هذه Value أصلًا داخل Raw data.

### `percentile_disc`

تعيد Actual observed value الأقرب إلى Percentile boundary المطلوبة.

قاعدة عملية:

```text
Continuous numeric measures -> غالبًا percentile_cont أنسب
Discrete أوCategorical-like ordered values -> قد تكون percentile_disc أكثر وضوحًا
```

تختلف Exact database syntax.

### ملاحظة Performance

قد تتطلب Exact percentile calculations عمليات Sort كبيرة.

على Tables ضخمة جدًا، يمكن أن تكون Approximate percentile functions أسرع بكثير وقد تكون دقيقة بما يكفي لـ Anomaly thresholds.

## 5. Standard Deviation وZ-Scores

تجيب Percentiles عن:

```text

ما نسبة Observations الأقل من هذه Value؟ (What share of observations are below this value?)

```

أما z-score فتجيب عن:

```text

كم Standard deviation تبعد هذه Value عن Mean؟ (How many standard deviations is this value away from the mean?)

```

### Standard deviation

تصف Standard deviation مقدار Spread للـ Values حول Mean.

Standard deviation صغيرة:

```text

Values متقاربة بإحكام (values are tightly clustered)

```

Standard deviation كبيرة:

```text

Values أكثر انتشارًا (values are more spread out)

```

بالنسبة إلى Distribution تقارب Normal distribution:

```text
حوالي 68% من Values تقع داخل ±1 Standard deviation
حوالي 95% من Values تقع داخل ±2 Standard deviations
```

هذه Intuitions مفيدة، وليست Laws عامة لكل Real-world distribution.

### Population مقابل Sample

توفر Databases كثيرة:

```text
STDDEV_POP
STDDEV_SAMP
STDDEV
```

استخدم `STDDEV_POP` عندما تمثل Dataset الـ Full population موضع الاهتمام.

واستخدم `STDDEV_SAMP` عندما تمثل Rows Sample من Population أكبر.

في Datasets ضخمة جدًا، قد يكون الفرق العددي صغيرًا، لكن المعنى الإحصائي مختلف.

### معادلة Z-score

بالنسبة إلى Value `x`:

```text
z = (x - mean) / standard deviation — المسافة عن المتوسط بوحدات الانحراف المعياري
```

التفسير:

```text
z = 0    -> عند Mean بالضبط
z = +1   -> Standard deviation واحدة فوق Mean
z = -2   -> Standard deviations اثنتان تحت Mean
z = +5   -> بعيدة للغاية فوق Mean
```

## 6. أدوات Visual: Histogram وScatter Plot وBox Plot

يمكن لـ SQL تجهيز Data.

لكن Graph قد تجعل Anomaly واضحة فورًا.

### Histogram أوFrequency Plot

تساعد Histogram في الإجابة عن:

```text
ما شكل Distribution؟ (What is the shape of the distribution?)
هل هي Symmetric أمSkewed؟ (Is it symmetric or skewed?)
هل توجد Peaks متعددة؟ (Are there multiple peaks?)
هل بعض Values متكررة بصورة غير متوقعة؟ (Are some values unexpectedly frequent?)
هل Tails طويلة جدًا؟ (Are the tails very long?)
```

قد تبدو SQL preparation هكذا:

⟦CODE_12⟧

### Scatter Plot

تكون Scatter plot مفيدة عندما يهم Numeric variables اثنان.

أمثلة:

```text
Transaction amount مقابل Account age
Delivery time مقابل Distance
Model error مقابل Input size
Earthquake magnitude مقابل Depth
```

قد لا تكون Point غير معتادة في أي Variable بمفردها، لكنها قد تكون غير معتادة في **Combination** بينهما.

### Box Plot

تلخص Box plot Distribution رقمية.

مكوناتها الأساسية هي:

```text
Q1 = 25th percentile — الربيع الأول
median = 50th percentile — الوسيط
Q3 = 75th percentile — الربيع الثالث
IQR = Q3 - Q1 — المدى الربيعي
```

Rule شائعة للـ Whiskers هي:

```text
lower boundary = Q1 - 1.5 × IQR — الحد الأدنى
upper boundary = Q3 + 1.5 × IQR — الحد الأعلى
```

تُعرض Values خارج هذه Boundaries كـ Outliers.

{{image:box-plot-anatomy}}

### Box Plot ليست "Truth" تلقائية

Point خارج `1.5 × IQR` هي Mathematically unusual وفق هذه Rule.

لكنها ليست تلقائيًا:

```text
خاطئة (wrong)
احتيالية (fraudulent)
غير ذات صلة (irrelevant)
```

افصل دائمًا بين:

```text

غير معتادة إحصائيًا (statistically unusual)

```

وبين:

```text

غير صالحة (invalid)

```

## 7. ثلاثة أشكال مهمة للـ Anomalies

لا تظهر Anomalies دائمًا كرقم ضخم واحد.

Framework مفيدة هي:

1. Anomalous **values**،
2. Anomalous **counts أوfrequencies**،
3. Anomalous **presence أوabsence**.

كل شكل يتطلب سؤالًا مختلفًا.

## 8. Anomalous Values

قد تكون Value anomaly:

```text
مرتفعة للغاية (extremely high)
منخفضة للغاية (extremely low)
بدقة غير معتادة (unusually precise)
بتنسيق غير متوقع (unexpectedly formatted)
غير صالحة لفئتها (invalid for its category)
```

### القيم الرقمية المتطرفة (Extreme Numeric Values)

أمثلة:

```text
Purchase amount = أكبر من الطبيعي بـ 10,000×
Temperature = -999
Duration = 0.000001 seconds
```

### Precision مشبوهة

افترض أن Measurement عادةً ما تحتوي منزلتين عشريتين:

```text
1.08
1.09
1.10
1.11
```

لكنها أحيانًا تحتوي:

```text
1.08000004
```

قد يعكس ذلك:

- Measurement instrument مختلفة،
- Floating-point conversion،
- Processing path مختلفة،
- Increase صحيحة في Precision.

Anomaly ليست بالضرورة في Numeric magnitude.

قد تكون Anomaly في **Representation** نفسها.

### Text Anomalies

يمكنك اكتشاف Differences في Capitalization بمقارنة Cardinality.

⟦CODE_13⟧

إذا كان:

```text
distinct_types = 25
distinct_lower_types = 24
```

فهذا يعني أن Category واحدة على الأقل تختلف فقط في Capitalization.

يمكنك التحقيق باستخدام:

⟦CODE_14⟧

### تحقّق مقابل Known Allowed Values

إذا كانت لديك Trusted list:

```text
earthquake — زلزال
explosion — انفجار
ice quake — زلزال جليدي
landslide — انهيار أرضي
```

فاربط Incoming data مع Reference table.

Unexpected unmatched values تصبح Candidates للتحقيق.

هذا أقوى من تخمين أي Rare spelling هي الخاطئة.

### افحص Attributes المرتبطة

عند العثور على Extreme value، افحص:

- Timestamp،
- Location،
- Source system،
- Device،
- Customer،
- Product،
- Status،
- Ingestion batch.

الهدف هو فهم:

```text

ما الأشياء الأخرى المختلفة في Rows الشاذة؟ (What else is different about the anomalous rows?)

```

وغالبًا بهذه الطريقة تُكتشف Root cause.

## 9. Anomalous Counts وSpikes وتغيرات Frequency

أحيانًا تبدو كل Row منفردة طبيعية.

Anomaly هي أن **عددًا كبيرًا جدًا من Rows يحدث معًا**.

مثال:

```text
Purchase بقيمة 100 EGP طبيعية.
لكن 100 EGP كل Minute لمدة 48 ساعة ليست طبيعية.
```

Value طبيعية.

لكن Frequency غير طبيعية.

### ابدأ بصورة واسعة

بالنسبة إلى Event data:

⟦CODE_15⟧

ثم انتقل إلى Months:

⟦CODE_16⟧

### نفّذ Drill-down بصورة Iterative

غالبًا يبدو Investigation جيد هكذا:

```text

↓
Month
↓
Day
↓
Hour
↓
قسّم حسب Status / Source / Product / Location
```

أنت تسأل:

```text
أين تظهر Anomaly أول مرة؟ (Where does the anomaly first appear?)
أي Subgroup تفسرها؟ (Which subgroup explains it?)
```

### Structural Changes قد تبدو كأنها Behavioral Changes

تخيل أن Monthly event counts قفزت فجأة.

قد تشمل التفسيرات:

```text
نمو حقيقي في Users (real user growth)
إطلاق Product جديدة (new product launch)
Duplicate logging
Instrumentation جديدة
Review status مختلفة
Data source جديدة
```

## 10. الغياب قد يكون Anomaly أيضًا

غالبًا يبحث Analysts عن:

```text
كمية كبيرة جدًا (too much)
Value مرتفعة جدًا (too high)
Frequency كبيرة جدًا (too frequent)
```

لكن Anomalies قد تكون أيضًا:

```text

لم يحدث شيء (nothing happened)

```

أمثلة:

- Server توقفت عن إرسال Heartbeats،
- Customer توقف عن Login،
- Sensor توقف عن Reporting،
- Store توقفت عن تسجيل Sales،
- Subscription لم تنتج Expected renewal event.

### الصعوبة

يصعب رؤية Missing row لأنها غير موجودة أصلًا.

لاكتشاف Absence، تحتاج غالبًا إلى **Expected grid**.

مثال:

```text
كل Customer (every customer)
×
كل Day (every day)
```

ثم نفذ Left join مع Actual activity.

هذه هي Technique نفسها المستخدمة مع Sparse time-series وCohort data.

### الوقت منذ آخر ظهور (Time Since Last Seen)

Technique مفيدة أخرى هي:

```text

كم مر من الوقت منذ Last event؟ (How long has it been since the last event?)

```

يمكنك حساب Gaps باستخدام `lead` أو`lag`.

⟦CODE_17⟧

ثم:

```text
gap = next_event - event_time — الفجوة حتى الحدث التالي
```

وبالنسبة إلى Current gap:

```text
current_time - latest_event
```

### قارن Current Gap بالسلوك التاريخي

افترض أن Customer تعود عادةً كل:

```text
5–8 days — من 5 إلى 8 أيام
```

وهي الآن غائبة لمدة:

```text
45 days — 45 يومًا
```

هذا أكثر إفادة بكثير من مجرد قول:

```text

شوهدت آخر مرة منذ 45 Day (last seen 45 days ago)

```

تشمل Features مفيدة:

```text
متوسط Historical gap
أكبر Historical gap
Median historical gap
Current gap
Current gap / average gap
```

هذه Pattern مفيدة لـ:

- Churn risk،
- Device monitoring،
- Maintenance،
- Sensor health،
- سلوك الشراء المتكرر (Recurring purchase behavior).

### Absence ليست Failure تلقائيًا

بعض Behavior غير منتظمة بطبيعتها.

استخدم Historical pattern وDomain context قبل تحديد Alert threshold.

## 11. حقق قبل تغيير Data

بعد اكتشاف Anomaly، لا تحذفها فورًا.

Workflow قوية هي:

```text
اكتشف (detect)
-> افحص (inspect)
-> قارن Rows مرتبطة
-> حدد Source محتملة
-> قِس Analytical impact
-> اختر Action
```

### افحص Row كاملة

إذا كانت Amount متطرفة:

⟦CODE_18⟧

ابحث عن Clues:

- Source،
- User،
- Timestamp،
- Status،
- Region،
- Batch،
- Version،
- الحقول الأخرى ذات الصلة.

### قارن Neighboring أوRelated Records

اسأل:

```text
هل تصرفت Rows أخرى في Day نفسها بالطريقة نفسها؟ (Did other rows from the same day behave similarly?)
هل أنشأت Data source نفسها Rows غريبة أخرى؟ (Did the same data source create other strange rows?)
هل لدى Customer نفسها Values مشابهة سابقًا؟ (Did the same customer have similar values before?)
هل حدث Logging change في ذلك الوقت؟ (Did a logging change happen at that time?)
```

### اسأل Domain Experts

قد تكون Value تبدو مستحيلة إحصائيًا لكنها متوقعة تشغيليًا.

قد يعرف Domain expert أن:

```text
Policy تغيرت
Sensor استُبدلت
Promotion أُطلقت
Product category جديدة ظهرت
Data-collection rule تغيرت
```

Anomaly detection مزيج من Statistics وDetective work.

## 12. التعامل مع Anomalies: الاحتفاظ أم الحذف أم الاستبدال؟

بعد فهم Root cause قدر الإمكان، اختر Handling strategy مناسبة.

### Option 1 — احتفظ بها

استخدم هذا عندما:

- يكون Event حقيقيًا،
- يكون مهمًا للتحليل،
- يؤدي حذفه إلى إخفاء Behavior مهمة.

مثال:

```text

Customer شرعي عالي القيمة (a legitimate high-value customer)

```

### Option 2 — احذف Row

يكون ذلك مناسبًا عندما:

- تكون Row كلها على الأرجح Corrupted،
- يكون Record Duplicate،
- يكون Source event غير صالح،
- تكون Dataset كبيرة ولا تؤثر Rows السيئة القليلة ماديًا في Coverage.

مثال:

⟦CODE_19⟧

لكن Removal يجب أن يكون مبررًا، لا تلقائيًا.

### قِس Impact قبل الحذف

قارن Metrics:

⟦CODE_20⟧

أحيانًا لا تغير Anomaly النتيجة الإجمالية إلا قليلًا.

وأحيانًا تغير Subgroup بدرجة كبيرة.

كلتا الحقيقتين مهمتان.

### Global Removal مقابل Calculation-specific Exclusion

تحذف `WHERE` Row من كل شيء.

أما `CASE` فتستطيع استبعادها من Calculation واحدة فقط.

مثال:

⟦CODE_21⟧

يحافظ ذلك على Row counts وFields الأخرى مع حماية Calculation.

### Option 3 — استبدلها بـ Known Correct Value

إذا كان Cause معروفًا وكان Correction قابلًا للدفاع:

⟦CODE_22⟧

أوحوّل Known category typo إلى Canonical value.

### Option 4 — ادمج Rare Categories

إذا كانت Rare categories كثيرة ولا تضيف Analytical value:

⟦CODE_23⟧

يبسط ذلك Reporting لكنه يفقد بعض Detail.

وثّق القرار.

## 13. Winsorization: حدّ Extremes بدل حذفها

**Winsorization** تستبدل Values الواقعة خارج Percentile boundaries مختارة بقيم Boundary نفسها.

مثال:

```text
أقل من 5th percentile -> اضبطها على p05
أعلى من 95th percentile -> اضبطها على p95
```

يحافظ ذلك على كل Row مع تقليل تأثير Extremes.

### احسب Thresholds

⟦CODE_24⟧

### ما الذي تغيره Winsorization؟

افترض:

```text
p05 = 20
p95 = 500
```

عندها:

```text
5     -> 20
50    -> 50
300   -> 300
800   -> 500
10000 -> 500
```

Rows تظل موجودة.

لكن التأثير الرقمي المتطرف ينخفض.

### لا توجد Percentile واحدة Universal

تشمل اختيارات محتملة:

```text
1st / 99th
5th / 95th
0.1th / 99.9th
```

تعتمد Threshold على:

- Distribution،
- عدد Extremes،
- Business meaning،
- Downstream model أوMetric.

لا تستخدم Winsorization فقط لأن Outliers غير مريحة.

## 14. Rescaling مع الاحتفاظ بالـ Observations

Strategy أخرى هي الاحتفاظ بكل Value مع تغيير Scale.

### Z-score Scaling

حوّل Values إلى وحدات Standard deviation:

```text
z = (x - mean) / stddev — صيغة الـ z-score
```

يسهّل ذلك مقارنة Variables ذات Units مختلفة.

كما يحافظ على ما إذا كانت Value أعلى أوأقل من Mean.

### Log Transformation

بالنسبة إلى Positive values ذات Range واسع جدًا:

⟦CODE_25⟧

Log transformation:

- تحافظ على Ordering،
- تضغط Large values،
- توسع Small positive values،
- وقد تجعل Skewed patterns أسهل في الفحص.

مثال:

```text
1       -> log10 = 0 — كل زيادة بعشرة أضعاف تضيف واحدًا
10      -> log10 = 1
100     -> log10 = 2
1000    -> log10 = 3
```

Range مقدارها 1000× تصبح Range مقدارها 3 Units.

### قيد مهم

Logarithm غير معرفة للقيم Zero أوNegative في Ordinary real-number analysis.

يجب أن تقرر كيفية التعامل مع:

```text
0 — الصفر
negative values — القيم السالبة
```

قبل تطبيق Transformation.

### Transformations أخرى

بحسب المشكلة (Problem):

```text
square root — الجذر التربيعي
cube root — الجذر التكعيبي
reciprocal — المقلوب
unit conversion — تحويل الوحدات
```

قد تكون مفيدة.

Rescaling ليست نفسها إصلاح Bad data.

هي تغيّر Representation مع الاحتفاظ بالـ Observation.

## 15. Workflow عملية لاكتشاف Anomalies

استخدم Workflow هذه عند التعامل مع Dataset جديدة.

### الخطوة 1 — عرّف ما الذي قد يعني "Anomalous"

ضع في الاعتبار:

```text
Value
Frequency
Absence
Combination من Variables
Group-specific behavior
```

### الخطوة 2 — اعمل Profile للـ Raw Data

تحقق من:

- Nulls،
- Minimum،
- Maximum،
- Distinct values،
- Frequency،
- Basic percentiles،
- Sample rows،
- Subgroup differences.

### الخطوة 3 — Visualize للـ Key Distributions

استخدم:

```text
histogram — المدرج التكراري
scatter plot — مخطط التشتت
box plot — مخطط الصندوق
time series — السلسلة الزمنية
```

وفق Question.

### الخطوة 4 — قِس Extremity

جرّب:

```text
percentiles — المئينات
ntiles — التقسيم إلى مجموعات متساوية العدد
IQR boundaries — حدود المدى الربيعي
z-scores — درجات z
```

لا تعتمد على Method واحدة فقط.

### الخطوة 5 — قارن Local Baselines

اسأل هل Row غير معتادة:

```text
لهذه Segment
لهذا Location
لهذا Customer
لهذا Product
لهذه Period
```

### الخطوة 6 — حقق في Context

تحقق من:

- Source system،
- Status،
- Event time،
- Ingestion version،
- Related rows،
- التغييرات الأخيرة في منطق التسجيل (Logging).

### الخطوة 7 — قِس Impact

قارن Metrics المهمة:

```text
مع Anomaly
من دون Anomaly
مع Corrected value
```

### الخطوة 8 — اختر Handling Strategy

تشمل Actions الممكنة:

```text
احتفظ بها (keep)
ضع Flag عليها (flag)
احذفها (remove)
استبعدها من Calculation
استبدلها (replace)
طبّق Winsorization
أعد Scaling
```

### الخطوة 9 — أصلح Source عندما يكون ذلك ممكنًا

إذا كانت Broken validation rule تنشئ Bad value كل Day، فإن SQL cleanup query تعالج Symptom فقط.

أصلح:

```text
data-entry validation — التحقق عند إدخال البيانات
logging logic — منطق التسجيل
ETL transformation — تحويلات ETL
deduplication — إزالة التكرار
unit conversion — تحويل الوحدات
schema constraint — قيود الـ Schema
```

في Upstream عندما تستطيع.

### الخطوة 10 — وثّق Assumption

سجل:

```text
لماذا اعتُبرت Value غير طبيعية
كيف جرى التعامل معها
ما Thresholds المستخدمة
ما Business context التي دعمت القرار
```

يجعل ذلك Analysis قابلة لإعادة الإنتاج والـ Audit.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> كل Outlier هي Bad data.

خطأ. بعض Outliers هي أهم Real events في Dataset.

### المفهوم الخاطئ 2

> تكون Value Anomalous إذا كانت كبيرة.

Anomaly نسبية. قد تكون Large value طبيعية في Subgroup ومتطرفة في أخرى.

### المفهوم الخاطئ 3

> Z-score أكبر من 3 تكون دائمًا Invalid.

تعني High z-score أن Value متطرفة إحصائيًا نسبةً إلى Distribution المختارة. لا تثبت أن Data خاطئة.

### المفهوم الخاطئ 4

> لا يمكن اكتشاف Missing rows لأنها غير موجودة.

يمكن لـ Expected grids وDate dimensions وGap analysis كشف Absence.

### المفهوم الخاطئ 5

> أكثر Response أمانًا للـ Outliers هي الحذف.

قد يحذف Removal معلومات حقيقية وقيمة. حقق أولًا.

### المفهوم الخاطئ 6

> Winsorization تصحح Bad data.

Winsorization تحد Extremes. لا تكتشف Root cause ولا تصلحها.

### المفهوم الخاطئ 7

> الزيادة المفاجئة في Events تعني أن User behavior تغير.

قد تعكس بدلًا من ذلك تغيرًا في Instrumentation أوStatus أوSource أوProcessing.

| `percent_rank` | Window function تعيد Relative rank لـ Row داخل Ordered set |
| `ntile` | Window function تقسم Ordered rows إلى عدد محدد من Buckets |

| `percentile_disc` | Observed value الأقرب إلى Requested percentile |

| Z-score | Distance من Mean مقاسة بوحدات Standard deviation |
| IQR | Interquartile range: Q3 ناقص Q1 |
| Box Plot | Visualization تعرض Quartiles وMedian وWhiskers وOutliers |
| شذوذ Frequency (Frequency Anomaly) | Count أوRate غير معتادة من Events |

## التحقق الذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة عن الآتي:

1. ما المصدران العامان للـ Anomalies؟
2. لماذا لا ينبغي حذف Real extreme events تلقائيًا؟
3. متى تكون SQL Tool قوية لـ Anomaly detection؟
4. لماذا ينبغي فحص الطرفين المرتفع والمنخفض من Distribution؟
5. كيف تساعد Frequency على التمييز بين One-off outlier وSystematic issue؟
6. لماذا قد تكون Value طبيعية عالميًا لكنها Local anomaly؟
7. ما الفرق بين `percentile_cont` و`percentile_disc`؟
8. ماذا تعني Z-score مقدارها +4؟
9. لماذا قد تكون Z-score thresholds مضللة في Highly skewed distribution؟
10. ما Information التي تلخصها Box plot؟
11. ما Anomalous frequency؟
12. كيف يمكن جعل Absence من Data قابلة للاكتشاف؟
13. لماذا ينبغي مقارنة Results مع Outlier ومن دونها قبل Removal؟
14. ما الفرق بين Row removal وCalculation-specific exclusion؟
15. ماذا تفعل Winsorization؟
16. متى تكون Log rescaling مفيدة؟
17. لماذا يُعد Root-cause investigation أهم من Anomaly score نفسها؟
