## 1. من Query لمرة واحدة إلى Analytical data set قابلة لإعادة الاستخدام

ركزت الدروس السابقة على أسئلة تحليلية محددة:

- Time-series trends؛
- Cohort retention؛
- Text parsing؛
- Anomaly detection؛
- التجارب (Experiments).

في العمل الحقيقي، يُطلب منك غالبًا إنشاء شيء أوسع:

> **ابنِ Data set يمكنها دعم تحليلات مستقبلية كثيرة.**

قد تكون Destination:

- BI dashboard؛
- CSV أوParquet export؛
- Table داخل Warehouse؛
- Python notebook؛
- Machine-learning pipeline؛
- تقرير متكرر (Recurring report).

هذا يغيّر المشكلة.

تحتاج One-off query فقط إلى الإجابة عن سؤال اليوم بصورة صحيحة.

أما Reusable analytical data set فتحتاج أيضًا إلى أن تكون:

```text
صحيحة
قابلة للصيانة
مفهومة
سريعة بصورة معقولة
مستقرة بما يكفي للاستخدام المتكرر
بمستوى تفصيل مناسب
مراعية للخصوصية
```

### لماذا تزداد Complexity

قد تجمع Reusable data set:

```text
سمات العملاء (Customer attributes)
+ ملخصات المعاملات (Transaction summaries)
+ معلومات Cohort
+ مؤشرات الحالة (Status flags)
+ المقاييس المتحركة (Rolling metrics)
+ حقول النص المحللة (Parsed text fields)
+ تعيينات التجارب (Experiment assignments)
+ قواعد تنظيف الشذوذ (Anomaly-cleaning rules)
```

ثم قد يسأل Stakeholders:

```text
هل يمكنك إضافة Country؟
هل يمكنك إضافة First purchase؟
هل يمكنك إضافة 30-day revenue؟
هل يمكن تقسيم هذا حسب Plan؟
هل يمكن استبعاد Test users؟
```

يمكن أن تصبح Query صعبة الفهم قبل وقت طويل من أن تصبح مستحيلة تقنيًا في التنفيذ.

لهذا تصبح **Organization وArchitecture** مهارتين تحليليتين.

## 2. حدد أين يجب أن يعيش Logic

يمكن تنفيذ Transformation غالبًا في أماكن متعددة:

```text
جداول قاعدة البيانات الخام (Raw database tables)
-> استعلام SQL
-> View / Materialized view — عرض عادي أو مادي
-> ETL / Transformation pipeline — مسار التحويل
-> أداة BI
-> بيئة Python / R / ML
```

نادرًا ما توجد إجابة واحدة عامة.

يعتمد الموقع الصحيح على Use case.

[[IMAGE_NEEDED: IMG-M01-L08-01 / Instructor Figure — Where analytical logic should live | Show a left-to-right pipeline Raw Data -> SQL Query -> View/Materialized View -> ETL/Curated Table -> BI/Python/R, with decision callouts for rapid iteration, reuse, performance, freshness, governance, and specialized analytics | Learner should notice that logic placement is a trade-off between flexibility, speed, visibility, maintainability, and downstream needs rather than a rule that everything must live in SQL]]

### أبقِ Logic داخل SQL عندما

تكون SQL خيارًا جذابًا عندما:

- يكون Analysis ما يزال يتغير بسرعة؛
- تحتاج إلى Iteration سريعة؛
- تعمل Query بسرعة كافية؛
- تكون Source data موجودة أصلًا في Database؛
- تكون Result مطلوبة عند الطلب؛
- يمكنك تعديل Logic دون انتظار Deployment process.

أثناء Exploration، تكون هذه Flexibility ذات قيمة كبيرة جدًا.

Workflow نموذجية هي:

```text
نفّذ Profiling للبيانات
-> اكتب Transformation واحدة
-> افحص Output
-> اكتشف Exception
-> أضف Transformation أخرى
-> تحقّق
-> كرر
```

### انقل Logic إلى ETL عندما

تصبح ETL أوScheduled transformation layer جذابة عندما:

- تكون Query مكلفة؛
- يحتاج كثيرون إلى Result نفسها؛
- يكون Logic قد استقر؛
- يكون تكرار Computation إهدارًا؛
- يجب حفظ Historical snapshots؛
- تحتاج Data إلى Governance وReview أقوى.

يمكن تشغيل Complex transformation مرة واحدة في الخلفية وكتابة:

```text
analytics_customer_daily
```

ثم يستعلم Downstream users عن Prepared table بسرعة.

### اللقطات اليومية (Daily snapshots)

تكون Snapshot tables مفيدة خصوصًا عندما يتم Overwrite للـ Attributes داخل Operational systems.

مثال:

```text
customer_status اليوم = "Enterprise"
```

لا يخبرك:

```text
ماذا كانت حالة Customer قبل ستة أشهر؟
```

يمكن لـ Daily snapshot حفظ:

```text
customer_id — معرّف العميل
snapshot_date — تاريخ اللقطة
plan — الخطة
pipeline_status — حالة المسار
lifetime_orders — إجمالي الطلبات التاريخية
lifetime_revenue — إجمالي الإيراد التاريخي
...
```

قد يكون إعادة إنشاء ذلك من Raw history في كل مرة مكلفًا، ولذلك يمكن أن تكون Materialization جديرة بالتنفيذ.

### لماذا تكون Views مفيدة

يمكن لـ Views توفير:

- Definitions قابلة لإعادة الاستخدام؛
- Interfaces أبسط لـ Complex joins؛
- Filtering متسق؛
- Controlled access إلى Columns؛
- Visibility للـ Code.

يمكن لـ View إخفاء PII:

```text
جدول العملاء الخام (Raw customer table):
email — البريد الإلكتروني
phone — الهاتف
address — العنوان
plan — الخطة
country — الدولة

العرض التحليلي (Analytical view):
customer_id — معرّف العميل
plan — الخطة
country — الدولة
```

### قيد مهم

لا تقوم Normal view عادة **بتخزين** Result.

عند الاستعلام عنها، ما تزال Database تنفذ Logic الأساسية.

لذلك:

```text
View != Precomputed table — الـ View ليست جدولًا محسوبًا مسبقًا
```

يمكن لـ View تحسين Maintainability دون تحسين Computation مكلفة بطبيعتها.

### الـ Views المادية (Materialized views)

تخزن Materialized view الـ Output.

يمكن أن يحسن ذلك Performance، لكن عليك الآن تحديد:

- متى يتم Refresh لها؛
- إلى أي حد يمكن السماح لها بأن تصبح Stale؛
- هل Incremental refresh ممكن؛
- ما Resources التي تستهلكها.

وهذا يجعلها أقرب إلى Analytical table تديرها ETL.

## 4. متى تترك العمل لـ BI أوPython أوR

الهدف ليس:

> **افعل كل شيء داخل SQL.**

بل الهدف هو:

> **نفّذ كل جزء في المكان الأنسب له.**

### جداول البيانات (Spreadsheets)

Spreadsheets مرنة ومألوفة لكنها تعاني غالبًا مع:

- ملايين Rows؛
- Manual transformations متكررة؛
- Complex joins؛
- قابلية إعادة الإنتاج (Reproducibility).

نمط جيد هو:

```text
Database تنفذ Filtering/Aggregation الثقيلة
-> Spreadsheet تستقبل Result مدمجة
```

### أدوات BI

تختلف BI tools.

بعضها:

- ينفذ Cache للـ Imported data؛
- ينفذ Computation محليًا؛
- يدعم Calculations غنية.

وبعضها الآخر يرسل Queries مرة أخرى إلى Database كلما تغير Report.

تحتاج إلى فهم Tool التي تستخدمها.

بالنسبة إلى Exploratory dashboards، قد تتعمد الاحتفاظ بقدر أكبر من Dimensional detail مقارنة بما يحتاجه Fixed report.

### Python وR

بالنسبة إلى:

- Statistics؛
- Machine learning؛
- Advanced NLP؛
- Custom visualization؛

قد تكون Python أوR أفضل.

لكن نقل مليارات Rows خام خارج Database غالبًا غير ضروري.

Workflow قوية تكون كثيرًا:

```text
SQL تنفذ Joins وFilters وإنشاء Features أساسية
-> Python/R تستقبل Analytical grain اللازمة للـ Modeling
```

### تجنب الخطوات اليدوية

مبدأ Engineering أساسي:

> **إذا كانت Transformation مهمة، فاكتبها كـ Code.**

تجنب:

```text
Export إلى CSV
Open للـ Spreadsheet
Delete لعمودين
Rename للقيم يدويًا
Save لملف CSV جديد
```

الخطوات اليدوية:

- صعبة Reproduce؛
- سهلة النسيان؛
- صعبة Review؛
- غير متسقة عبر Reruns.

حتى Analysis "لمرة واحدة" تعود غالبًا لاحقًا.

## 6. افهم Logical evaluation order في SQL

تُكتب SQL بداية من:

```text
SELECT
```

لكن هذا ليس الجزء الأول الذي يتم تقييمه منطقيًا.

ترتيب مبسط مفيد هو:

```text
1. FROM + JOIN + ON — تحديد المصادر والربط
2. WHERE — تصفية الصفوف
3. GROUP BY + Aggregates — التجميع والحسابات المجمعة
4. HAVING — تصفية المجموعات
5. Window functions — دوال النوافذ
6. SELECT — إنتاج الأعمدة
7. DISTINCT — إزالة التكرار
8. UNION / UNION ALL — دمج النتائج
9. ORDER BY — ترتيب النتائج
10. LIMIT / OFFSET — تحديد الجزء المعاد
```

تزيل `DISTINCT` الـ Duplicate output rows بعد إنتاج `SELECT` expressions.


### لماذا تساعد Subqueries

تكون مفيدة عندما:

- تعتمد Calculation لاحقة على Aggregation سابقة؛
- تريد تغيير Grain؛
- تريد عزل Logical step واحدة؛
- كانت Expression طويلة ستتكرر لولا ذلك.

### قد تصبح Nested subqueries صعبة

هذا:

```text
استعلام (Query)
  -> استعلام فرعي (Subquery)
      -> استعلام فرعي (Subquery)
          -> استعلام فرعي (Subquery)
```

قد يعمل بصورة صحيحة لكنه يصبح صعب التفكير فيه.

هنا يمكن لـ CTEs أوTemporary tables تحسين Clarity.

### الاستعلامات الفرعية الجانبية (Lateral subqueries)

يمكن لـ Lateral subquery الرجوع إلى Rows أنتجت سابقًا في Clause `FROM`.

ويكون هذا مفيدًا لبعض Per-row dependent calculations.

مفاهيميًا:

```text
لكل Row في A
شغّل Dependent query صغيرة B
```

لكن Lateral syntax أقل ألفة.

استخدمها عندما تحسن الحل فعلًا، لا لمجرد أنها Advanced syntax.

## 16. تحليل Funnel

الـ Funnel هي سلسلة Actions تقود إلى Goal.

أمثلة:

### التجارة الإلكترونية (Ecommerce)

```text

-> أضف إلى السلة (Add to cart)
-> إدخال Shipping
-> أرسل الدفع (Submit payment)
-> شراء (Purchase)
```

### منصة تعلم (Learning platform)

```text
التسجيل (Enroll)
-> بدء الدرس (Start lesson)
-> إنهاء الوحدة (Finish module)
-> إكمال المشروع (Complete project)
-> إنهاء المقرر (Finish course)
-> الحصول على الشهادة (Earn certificate)
```

### تطبيق SaaS

```text
إنشاء حساب (Sign up)
-> إنشاء Workspace
-> إكمال أول Workflow
-> دعوة زميل للفريق
-> الترقية (Upgrade)
```

## 19. مشكلات Basket analysis الشائعة

تبدو Basket analysis بسيطة، لكنها تحتوي Traps مهمة.

### الأداء (Performance)

تحتوي Basket بها `n` Items فريدة على:

```text
n × (n - 1) / 2
```

Pair.

بالنسبة إلى 100 Item:

```text
100 × 99 / 2 = 4,950 Pairs — عدد الأزواج الناتج
```

يمكن أن يتضخم الحجم بسرعة مع Baskets كبيرة عبر ملايين Users.

تشمل Mitigations الممكنة:

- Filter إلى Time window؛
- إزالة Items شديدة الندرة؛
- تحليل Category واحدة؛
- Preaggregate للـ Unique user-item membership؛
- قصر التحليل على Relevant products.

### العناصر المهيمنة (Dominant items)

إذا كان الجميع تقريبًا يشتري:

```text
Milk — عنصر شائع
```

فقد تظهر Milk في معظم Top pairs.

هذا لا يعني تلقائيًا أن:

```text
Milk + X — اقتران عنصر شائع بعنصر آخر
```

علاقة قوية بصورة فريدة.

ضع دائمًا Individual item frequency في الاعتبار.

قد تستخدم Association analysis الأكثر تقدمًا مفاهيم مثل:

- Support؛
- Confidence؛
- الرفع (Lift).

لكن Simple SQL pair counts تظل نقطة بداية استكشافية ذات قيمة.

### التوصيات ذاتية التعزيز (Self-fulfilling recommendations)

لنفترض:

```text
A وB يحدثان معًا كثيرًا
```

فتبدأ Product في Recommendation لـ B بعد A.

الآن سيحدث A وB معًا بصورة أكثر تكرارًا جزئيًا **بسبب Recommendation**.

بعد ذلك تعزز Future observational data القاعدة الأصلية.

هذه Feedback loop.

الحل ليس التخلي عن Basket analysis.

بل التحقق من Recommendation value باستخدام Experimentation.

## 21. Checklist لـ Analytical SQL جاهزة للإنتاج

قبل تسليم Complex analytical data set، تحقق مما يلي.

### مستوى التفصيل (Grain)

هل يمكنك إكمال الجملة التالية؟

```text
تمثل Row واحدة ________ واحدة.
```

إذا لم تستطع، فالـ Dataset ليست جاهزة.

### تعددية الـ Join (Join cardinality)

لكل Join، هل تعرف ما إذا كانت:

```text
واحد إلى واحد (One-to-one)
واحد إلى متعدد (One-to-many)
متعدد إلى واحد (Many-to-one)
متعدد إلى متعدد (Many-to-many)
```

تُعد Unexpected many-to-many joins مصدرًا شائعًا للـ Metrics المتضخمة.

### عوامل التصفية (Filters)

هل Business exclusions موثقة؟

أمثلة:

```text
مستخدمو الاختبار (Test users)
حسابات داخلية (Internal accounts)
معاملات مستردة (Refunded transactions)
صفوف Sensor غير صالحة
```

### دلالة Null (Null semantics)

هل تعني Null:

```text
مفقود (Missing)
غير قابل للتطبيق (Not applicable)
لم تتم ملاحظته بعد (Not yet observed)
صفر (Zero)
```

لا تدمج هذه المعاني عن طريق الخطأ.

### منطق الوقت (Time logic)

هل:

```text
المناطق الزمنية (Time zones)
نوافذ الملاحظة (Observation windows)
تواريخ Cohort
تواريخ اللقطات (Snapshot dates)
```

محددة بصورة متسقة؟

### قابلية إعادة الإنتاج (Reproducibility)

هل يستطيع Analyst آخر إعادة تشغيل العمل دون Manual spreadsheet edits؟

### الأداء (Performance)

هل Query سريعة بما يكفي للاستخدام المقصود؟

إذا لم تكن كذلك، ففكر في:

- Materialization؛
- ETL؛
- Materialized view؛
- Source subsets أصغر؛
- التجميع المسبق (Preaggregation).

### الخصوصية (Privacy)

هل يحتوي Output على الحد الأدنى فقط من Sensitive data المطلوبة؟

### التحقق (Validation)

هل تحققت من:

- Row counts؛
- Duplicate keys؛

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> ينبغي دائمًا إبقاء Complex analytical logic داخل SQL.

لا. قد يكون Logic المستقر والمكلف أنسب داخل ETL أوMaterialized tables، بينما قد تكون Specialized modeling أنسب Downstream.

### المفهوم الخاطئ 2

> تجعل View الـ Query المكلفة سريعة تلقائيًا.

عادة تخزن Standard view الـ Query logic، لا Output.

### المفهوم الخاطئ 3

> CTEs أسرع دائمًا من Subqueries.

يعتمد Performance على Database optimizer. وغالبًا يتم اختيار CTEs من أجل Clarity وReuse.

### المفهوم الخاطئ 4

> `LIMIT 100` تعني أن Database تعالج 100 Row فقط.

ليس بالضرورة. تأتي `LIMIT` منطقيًا في وقت متأخر وقد تقلل فقط ما يتم إرجاعه.

### المفهوم الخاطئ 5

> Modulo sample بنسبة 1% تكون Unbiased تلقائيًا.

فقط إذا كان Sampled identifier موزعًا بصورة كافية بالنسبة إلى Variables موضع الاهتمام.

### المفهوم الخاطئ 6

> Hashed PII آمنة تلقائيًا.

Hashing ليست مكافئة لـ Encryption، وقد تظل Predictable inputs عرضة للخطر.

### المفهوم الخاطئ 7

> ينبغي أن تستخدم Funnel conversion دائمًا Previous step كـ Denominator.

ليس عندما تكون Steps Optional أويمكن الوصول إليها بصورة مستقلة.

### المفهوم الخاطئ 8

> Churn تعني دائمًا 30 يومًا دون Activity.

ينبغي أن تعكس Threshold سلوك Product الفعلي وBusiness context.

### المفهوم الخاطئ 9

> أكثر Basket pair تكرارًا هي تلقائيًا أفضل Recommendation.

يمكن لـ Item شائعة جدًا أن تهيمن على Pair counts دون وجود Association خاصة.

### المفهوم الخاطئ 10

> SQL الأكثر تعقيدًا تعني Analysis أفضل.

يستخدم أفضل Analysis أبسط Method موثوقة تمثل Process بصورة صحيحة وتدعم القرار.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مجموعة بيانات تحليلية (Analytical data set) | Data مشكلة للتحليل المتكرر أوDownstream tools |
| عملية ETL | Process لـ Extract-transform-load تقوم Materialization للـ Transformed data |
| عرض (View) | Saved query تُعرض مثل Table |
| عرض مادي (Materialized view) | كائن شبيه بـ View يخزن Query results |
| جدول لقطات (Snapshot table) | Table تسجل State الخاصة بـ Entity عند نقاط متكررة عبر الزمن |
| ترتيب تقييم الاستعلام (Query evaluation order) | Logical sequence التي تُحل وفقها SQL clauses |
| استعلام فرعي (Subquery) | Query متداخلة داخل Query أخرى |
| استعلام فرعي جانبي (Lateral subquery) | Subquery يمكنها الرجوع إلى عناصر سابقة في `FROM` |
| جدول مؤقت (Temporary table) | Materialized table مقيدة بالـ Session |
| تعبير جدولي مشترك (CTE) | Named intermediate result معرفة باستخدام `WITH` |
| مجموعات التجميع (`GROUPING SETS`) | Syntax لعدة Explicit aggregation groupings |
| المكعب (`CUBE`) | تنتج جميع Combinations للأبعاد المستخدمة في Grouping |
| التجميع الهرمي (`ROLLUP`) | تنتج Hierarchical aggregation levels |
| أخذ العينات (Sampling) | اختيار Subset من Observations |
| الأبعاد (Dimensionality) | عدد وتركيبات Attribute values الممثلة |
| المعلومات المعرّفة للشخص (PII) | معلومات يمكن أن تحدد هوية الشخص (Personally identifiable information) |
| الاستعارة (Pseudonymization) | استبدال Direct identifiers بـ Indirect stable identifiers |
| القمع التحليلي (Funnel) | Sequence من Actions تقود نحو Goal |
| الفئة المؤهلة (Eligible population) | Entities التي لديها فرصة لدخول Funnel |
| تحويل الخطوة (Step conversion) | النسبة التي تنتقل من Funnel stage إلى التالية |
| التسرب (Churn) | Operational definition للمغادرة/عدم النشاط |
| الخمول (Lapsed) | حالة Inactivity وسيطة قبل Churn |
| تحليل الفجوات (Gap analysis) | تحليل Elapsed time بين Events |
| الوقت منذ آخر نشاط (Time since last) | Elapsed time منذ أحدث Activity |
| تحليل السلة (Basket analysis) | تحليل Items أوBehaviors التي تحدث معًا |
| الربط الذاتي (Self-join) | Join لـ Table مع نفسها |
| العنصر المهيمن (Dominant item) | Item شائعة جدًا يمكن أن تطغى على Basket-pair counts |

## التحقق الذاتي

قبل إكمال المقرر، تأكد من قدرتك على الإجابة:

1. متى ينبغي أن يظل Transformation logic داخل SQL؟
2. متى تكون ETL أفضل؟
3. ما الفرق بين View وMaterialized view؟
4. لماذا ينبغي تجنب Manual transformation steps؟
5. ما Logical evaluation order لـ `FROM` و`WHERE` و`GROUP BY` و`HAVING` وWindow functions و`SELECT`؟
6. لماذا تستطيع `HAVING` عمل Filter لـ Aggregate values بينما لا تستطيع `WHERE` ذلك؟
7. متى تكون Subquery اختيارًا جيدًا؟
8. متى تكون Temp table أفضل؟
9. لماذا قد تحسن CTE الـ Maintainability؟
10. ما المشكلة التي تحلها `GROUPING SETS` و`CUBE` و`ROLLUP`؟
11. لماذا ينبغي غالبًا تنفيذ Sampling على مستوى User بدل Event؟
12. كيف تتحقق من أن Sample المعتمدة على ID ليست منحازة؟
13. كيف يمكن لـ Category grouping تقليل Dimensionality؟
14. لماذا ينبغي إزالة PII من Analytical outputs كلما أمكن؟
15. لماذا لا تعني Hashing الشيء نفسه مثل Encryption؟
16. ما الذي يحدد Top of funnel؟
17. متى ينبغي Join لـ Funnel steps بصورة Sequential؟
18. ما الفرق بين Overall وStep conversion؟
19. لماذا ينبغي أن تستند Churn thresholds إلى Historical gaps؟
20. ما الغرض من حالة Lapsed؟
21. كيف تساعد `b.product > a.product` داخل Basket self-join؟
22. لماذا يمكن لـ Common products الهيمنة على نتائج Basket analysis؟
23. كيف يمكن لـ Experiments تحسين Recommendation systems المبنية من Basket analysis؟
24. ماذا يعني تعريف Analytical grain؟
25. لماذا تعد Communication جزءًا من Analytical correctness؟
