# تجربة المستخدم للـ Multi-Agent الحية وتحويل AgentOps إلى Production

> **الدرس:** M01.L09  
> **مواءمة المصدر:** الفصلان 14 و15 من مادة Early Release المقدَّمة.  
> يجمع هذا الدرس بين Product experience و Operational productionization في مسار واحد متصل.

---

## نتائج التعلم

بحلول نهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يمكن لـ Live agent صحيحة تقنيًا أن تبدو معطلة للمستخدم.
- شرح لماذا تحتاج Live multimodal multi-agent systems إلى أكثر من Chat transcript.
- تطبيق القاعدة: Voice تحمل Intent، و Screen تحمل Durable detail.
- تعريف Live states موجهة للمستخدم مثل Listening و Speaking و Tool use و Specialist work و Approval و Reconnecting و Completion و Failure.
- التمييز بين Interrupting speech و Revising scope و Pausing work و Canceling work و Asking a side question.
- تصميم Agent activity labels تشرح Meaningful work دون كشف Protocol machinery.
- شرح لماذا ينبغي أن تمتلك Long-running backend Tasks هوية مرئية في UI.
- تصميم Task cards و Activity timelines و Source panels و Approval prompts و Recovery banners و Artifact views.
- شرح لماذا تقلل Fake progress precision الثقة.
- شرح مبدأ Host-controlled generative UI.
- تصميم Human-in-the-loop approval و Authentication flows بوضوح.
- تصميم Error states حول Recovery actions بدلًا من Generic failure messages.
- شرح لماذا ينبغي أن تكون Provenance و Conflicts و Recency و Partial-output status مرئية.
- تطبيق قواعد Personalization الثلاث: Visible و Scoped و Reversible.
- شرح متطلبات Accessibility للـ Voice و Visual state و Keyboard/Touch و Screen-reader paths.
- تتبع Long-running workflow كاملة من منظور User.
- تحديد UX patterns و Anti-patterns المتكررة.
- شرح الانتقال من DevOps إلى MLOps ثم GenAIOps ثم AgentOps.
- التمييز بين Model creators و Model consumers.
- شرح PromptOps و RAGOps و AgentOps بوصفها Sub-disciplines من GenAIOps وفق framing المصدر.
- شرح لماذا تجعل Autonomous decision-making الـ AgentOps مختلفة تشغيليًا.
- شرح لماذا يجب أن يغطي AgentOps evaluation اختيار Tool و Execution path، وليس Final output فقط.
- شرح الغرض من Tool Registries و Agent Registries.
- شرح لماذا تحتاج Short-term و Long-term memory إلى Governance.
- شرح People/Process/Technology framing المستخدم عبر المصدر.
- وصف انتقال MLOps environments من Sandbox إلى Production و Governance وفق المصدر.
- شرح Three-step model-selection process في المصدر.
- شرح كيف تدعم Prompt catalogs و Prompt-template catalogs الـ Evaluation و Reuse.
- مقارنة Labeled-data metrics و Human evaluation و LLM-as-a-judge approaches.
- شرح لماذا تحتاج Production GenAI applications إلى Guardrails و Context retrieval و Monitoring و Feedback loops.
- شرح إضافات AgentOps platform في المصدر: Augmented evaluation catalog و Agents as a Service و Registries و Dedicated memory.
- شرح كيف يمكن لـ MLOps و GenAI/AgentOps التعايش داخل Unified enterprise platform.

## 1. تجربة المستخدم ليست مجرد تلميع بصري (UX is not visual polish)

يبدأ المصدر بنقطة مهمة:

قد يكون System غير Blocking من الناحية التقنية ومع ذلك يبدو غير موثوق.

قد يعرف Backend تمامًا ما الذي يفعله.

لكن إذا لم يستطع User معرفة ما إذا كانت Assistant:

```text
تستمع (listening)
تفكر (thinking)
تتحدث (speaking)
تستخدم Tool
تفوض Task
تنتظر Approval
تتعافى من مشكلة
```

فستبدو Experience معطلة.

### المبدأ الأساسي (Core principle)

> UX للـ Integrated agents هي العمل على جعل System state مفهومة وواضحة للمستخدم.

هذا ليس أمرًا لاحقًا.

بل هو جزء من System design.

## 2. لماذا تختلف تجربة Live Multi-Agent

Traditional chat لها Rhythm بسيطة:

```text
يرسل User
ترد Assistant
ينمو Transcript
```

أما Live systems فلديها عدة Channels في الوقت نفسه.

على سبيل المثال:

```text
Microphone نشطة
Assistant تتحدث
Video preview تعمل
Specialist تعمل
Tool تعالج
Progress updates تصل
يمكن لـ User المقاطعة
```

هذه Channels ليست متزامنة بصورة مثالية.

قد تتوقف Assistant عن الكلام بينما تستمر Background task.

قد تفشل Tool بينما تنجح بقية Workflow.

قد ينقطع Connection بينما تبقى Task حية.

لا تستطيع Chat transcript بسيطة تمثيل كل هذا بوضوح.

---

## 3. اعرض State ذات معنى، لا Machinery

لا يهتم Users عادةً بما إذا كانت Implementation تستخدم:

```text
A2A
MCP
JSON-RPC
عامل في الخلفية (background worker)
```

بل يهتمون بما يعنيه ذلك.

Labels جيدة:

```text
Research agent تجمع Sources.
Data tool تعالج Spreadsheet.
Calendar access تحتاج Authentication.
Report generator تجمع Document.
```

Labels ضعيفة:

```text
تم استلام A2A statusUpdate.
MCP tool معلقة.
JSON-RPC request قيد التنفيذ.
```

### قاعدة Product

> ترجم Implementation events إلى Activity مفهومة للمستخدم.

## 4. من Live chat إلى Live workspace

كان Live app السابق يحتوي:

- Microphone،
- WebSocket،
- Video preview،
- Audio output،
- استدعاءات Tools (Tool calls).

لكن Durable task handling تحول ذلك إلى Workspace.

قد تحتاج UI الآن إلى:

```text
بطاقات المهام
الجدول الزمني للنشاط
لوحات المصادر
طلبات الموافقة
نتائج جزئية
artifacts نهائية
حالة إعادة الاتصال
إجراءات التعافي
```

لا ينبغي أن تختفي Task داخل Invisible backend process.

## 5. أربعة أسئلة ينبغي أن تجيب عنها Workspace

في معظم اللحظات، ينبغي أن تساعد Interface في الإجابة عن:

```text
ماذا تفعل Assistant الآن؟
هل تنتظر مني شيئًا؟
هل يمكنني المقاطعة أو الإلغاء أو تغيير الاتجاه؟
أين ستظهر Result؟
```

توفر هذه الأسئلة UX review checklist عملية.

إذا لم يستطع User الإجابة عنها، فغالبًا ما تخفي Interface State مهمة.

## 6. تصميم Voice-first و Visual-augmented

Voice قوية في:

- Intent،
- Steering،
- Natural language،
- تصحيحات سريعة (Quick corrections).

Voice أضعف في:

- Long lists،
- Citations،
- Tables،
- Approvals،
- خيارات Recovery كثيفة (Dense recovery choices).

قاعدة Design في المصدر هي:

> اجعل Voice تحمل Intent، واجعل Screen تحمل Durable detail.

مثال:

User:

```text
"قارن بين ثلاثة موردين من حيث السعر،
وزمن التسليم، والضمان."
```

Response جيدة:

```text
"سأقارن بينهم.
وسأعرض الجدول أثناء اكتماله."
```

تبقى Spoken response مختصرة.

ويعيش Table بصريًا.

## 7. Voice للتنبيه؛ و Screen للمراجعة

لنفترض أن System عثرت على Paid dataset.

يمكن لـ Voice أن تقول:

```text
"أحتاج إلى موافقتك قبل الوصول إلى dataset المدفوع."
```

لكن ينبغي أن تعرض Screen:

```text
التكلفة (cost)
Provider
الاستخدام المقصود (intended use)
النتائج المترتبة (consequences)
Approve
Skip
Details
```

في Actions المكلفة أو المدمرة أو الحساسة للخصوصية، تكون Exact review أهم من Conversational convenience.

## 8. صمّم Live system state model صريحة

تجنب Labels غامضة مثل:

```text
قيد العمل
جارٍ التحميل
جارٍ التفكير
```

لأن "Working" قد تعني:

- Model تحضر Response،
- Tool تعمل،
- Specialist تعالج،
- انتظار Approval،
- Backend تعيد الاتصال،
- توليد Artifacts (Artifact generation).

Model أفضل تميز بين هذه States.

States محتملة:

```text
idle    # حالات واجهة الصوت والـ agent
connecting
listening
user_speaking
assistant_thinking
assistant_speaking
tool_running
agent_working
input_required
reconnecting
completed
failed
canceled
```

## 9. Controls متشابهة قد تعني أشياء مختلفة جدًا

هذه ليست متكافئة:

```text
كتم
مقاطعة
إلغاء المهمة
إيقاف الجلسة
```

### كتم الصوت (Mute)

توقف إرسال Audio.

### المقاطعة (Interrupt)

توقف Current assistant speech وتبدأ الاستماع.

### إلغاء Task (Cancel task)

تطلب إنهاء Background work.

### إيقاف Session (Stop session)

تنهي Live interaction.

لا ينبغي أن تدمج UI الحالات الأربع داخل زر Stop غامض واحد.

## 10. المقاطعة جزء من Interface

مثال:

Assistant:

```text
"وجدت اثني عشر موردًا. الأول هو—"
```

User:

```text
"في الواقع، قارن الموردين الأوروبيين فقط."
```

ينبغي لـ System جيدة أن:

1. توقف Speech بسرعة،
2. تؤكد التغيير،
3. تحدث Visible task scope،
4. تشرح ما إذا كان Collection سيبدأ من جديد أم سيجري Filtering للنتائج الحالية.

ويجب أن تتغير Background task بصورة مناسبة.

إيقاف Audio وحده لا يكفي.

## 11. خمس نوايا مختلفة للمقاطعة

يفصل المصدر بين:

### مقاطعة Speech (Interrupt speech)

توقف الكلام وتبدأ الاستماع.

### تعديل Scope (Revise scope)

تغيّر Constraints الخاصة بـ Active task.

### إيقاف Work مؤقتًا (Pause work)

توقف Work مؤقتًا دون التخلص منها.

### إلغاء Work (Cancel work)

تنقل Task نحو Terminal cancellation.

### طرح سؤال جانبي (Ask a side question)

تجيب من دون تعديل Active Task.

هذا مهم لأن قول User "wait" قد لا يعني "احذف كل Work."

## 12. اعرض نشاط Agents تحت Conversational owner واحدة

يوصي المصدر بإبقاء Main assistant هي Conversational owner.

يمكن أن تظهر Specialists و Tools كـ:

- Activity cards،
- Timeline entries،
- تعليقات Sources (Source annotations).

تجنب تحويل كل Agent إلى Personality منفصلة إلا إذا كان Product يريد هذا Style عمدًا.

جيد:

```text
Research agent تجمع Sources.
```

غير جيد:

```text
ثلاث شخصيات agent تتناقش في المحادثة.
```

## 13. الخط الزمني للنشاط (Activity timeline)

يمكن لـ Timeline توفير Visibility هادئة:

```text
10:14 بدأ Supplier comparison
10:15 جمع Sources
10:16 استخرج 23 Row من Spreadsheet
10:17 انتظار Approval لبيانات مدفوعة
```

يمكن لـ Advanced users فتح:

```text

عرض Sources
فحص Activity
```

وتبقى Default interface بسيطة.

## 15. تجنب الدقة الوهمية (Fake precision)

بعض Tasks لا تستطيع أن تقول بصدق:

```text
37% مكتمل
```

قد تكون Phase label أفضل:

```text
جمع Sources
مراجعة Documents
بناء Comparison table
كتابة Draft report
انتظار Approval
```

الدقة الزائفة تقلل الثقة.

استخدم Numeric progress فقط عندما يكون Denominator ذا معنى حقيقي.

## 16. اعرض Partial results عندما تكون مفيدة

قد لا تكون Task مكتملة، لكن Useful artifacts قد تكون موجودة بالفعل.

أمثلة:

- Source list،
- Draft table،
- Outline،
- Chart أولية (Preliminary chart).

اعرضها مع Status labels مثل:

```text
مسودة
لا يزال يُحدَّث
نتيجة جزئية
```

Partial output مفيدة عندما تكون عدم اكتمالها واضحة.

## 17. Generative UI: Agent تقترح و Host يتحكم

قد تكتشف Specialist أنها تحتاج إلى:

- Comparison table،
- Approval card،
- Chart،
- لوحة Sources (Source panel).

المبدأ الثابت في UX حسب المصدر هو:

> يمكن لـ Agents اقتراح Surfaces؛ لكن Host يتحكم في Rendering.

تقرر Host:

- أي Approved component مسموح،
- أي Props صالحة،
- ما Actions الموجودة،
- كيف تعمل Accessibility،
- هل High-risk approval مقبولة.

لا ينبغي لـ Agent إرسال Arbitrary executable UI code.

## 18. UX الخاصة بـ Human-in-the-loop تطرح أربعة أسئلة

يجب أن تخبر Approval interface الجيدة الـ User:

```text
ما الذي يحتاجه System؟
لماذا يحتاجه؟
ماذا يحدث إذا وافقت؟
ماذا يحدث إذا رفضت أو تجاهلت؟
```

ضعيف:

```text
الموافقة على الإجراء؟
```

قوي:

```text
الموافقة مطلوبة

Dataset: ExampleData
التكلفة: £120
الغرض: تقديرات إيرادات الموردين

[الموافقة على الشراء]
[تخطي dataset]
[عرض التفاصيل]
```

## 19. Authentication prompts تحتاج الوضوح نفسه

إذا احتاج System إلى:

- Calendar،
- Repository،
- CRM،
- Document store،

فينبغي أن تشرح Prompt:

```text
أي Service
لماذا Access مطلوبة
أي Task تعتمد عليها
```

لا ينبغي أن يفاجأ User بطلبات Permission.

## 20. Structured input مكانها Screen عندما تهم Precision

يمكن لـ Voice التعامل مع Choice صغيرة.

مثال:

```text
"PDF or PowerPoint?"
```

لكن الاختيار من بين:

```text
20 schema لقاعدة البيانات
```

ينبغي أن يكون Visual.

استخدم Form أو Selection surface عندما:

- تكون Options كثيرة،
- تكون Values دقيقة،
- تكون Mistakes مكلفة.

## 21. عرض Error ينبغي أن يقود إلى Recovery

"Something went wrong" نادرًا ما تكون كافية.

تحتاج Failures المختلفة إلى Recovery مختلفة.

أمثلة:

### Voice input غير واضحة

```text
كرّر
اكتب بدلًا من ذلك
استخدم عناصر التحكم باللمس
```

### فشل Tool

```text
أعد المحاولة
تابع بدونه
```

### انتهاء Authentication

```text
أعد الاتصال
تخطَّ الخطوة
```

### انتهاء مهلة Remote agent

```text
انتظر
أعد المحاولة
إلغاء
```

### اكتمال جزئي (Partial completion)

```text
نزّل مجموعة المصادر المكتملة
أعد محاولة التصدير فقط
```

### انقطاع Network

```text
أعد الاتصال
تابع لاحقًا
```

## 22. Provenance و Sources و Confidence

قد تدمج Integrated systems معلومات من:

- Model knowledge،
- Documents،
- APIs،
- User files،
- Specialist agents،
- مخرجات Tools (Tool outputs).

قد تبدو Final response كإجابة واحدة.

ومع ذلك ينبغي أن تساعد UI الـ Users على فهم مصدر Claims.

حقول مفيدة في Source panel:

```text
المصدر
الطابع الزمني
artifact
تحذير حداثة
تحذير ثقة
تعارض غير محلول
```

## 23. اعرض الخلاف بدلًا من إخفائه

لنفترض أن Providerين يختلفان حول Revenue.

يمكن لـ UI قوية أن تقول:

```text
"تختلف تقديرات الإيرادات بين المصادر."
```

ثم تعرض:

```text
المصدر A: القيمة + الطابع الزمني
المصدر B: القيمة + الطابع الزمني
```

لا تُخفِ Conflict خلف رقم واحد زائف.

## 24. Personalization قد تحسن الثقة أو تضرها

الفرق هو Control.

يعطي المصدر ثلاث قواعد:

```text
مرئية (visible)
محددة النطاق (scoped)
قابلة للعكس (reversible)
```

---

## 25. اجعل Personalization مرئية

إذا كان Project context مستخدمًا، فقل ذلك.

مثال:

```text
استخدام سياق المشروع:
Battery Storage Research

[تغيير]
[تجاهل لهذه المهمة]
```

إذا تم تكييف Response style:

```text
وضع الصوت: ملخصات موجزة
[ضبط]
```

لا ينبغي أن يبدو System وكأنه يستخدم Hidden knowledge بصورة غامضة.

---

## 26. عرّف Scope الخاصة بـ Personalization

"Remember this" عبارة غامضة.

Scope محتملة:

```text
هذه Response
هذه Task
هذا Project
هذا Device
كل Sessions المستقبلية
```

لا ينبغي أن تتوسع Preference بصمت خارج Intent الخاصة بـ User.

هذا مهم خصوصًا لـ Approval memory.

الموافقة على Purchase واحدة لا تعني Permission لكل Purchases المستقبلية.

---

## 27. اجعل Personalization قابلة للعكس

ينبغي أن يستطيع Users فحص وتغيير:

```text
تنسيق التقرير
المصادر المفضلة
أسلوب الصوت
سياق المشروع
إعدادات إمكانية الوصول
memory الموافقات
```

لا ينبغي لـ Concision أن تخفي Detail بصورة دائمة.

إذا كانت Voice مختصرة، فينبغي أن تبقى Detailed content متاحة بصريًا.

---

## 28. Accessibility جزء من State model

Multimodal لا تعني Accessible تلقائيًا.

تحتاج Critical interactions إلى Paths متداخلة عبر:

```text
الصوت
المرئيات
اللمس
لوحة المفاتيح
قارئ الشاشة
```

أمثلة:

- Spoken response -> Captions/Transcript،
- Color state -> Text label،
- Chime -> Visible state،
- Voice interruption -> Explicit button،
- Report كثيفة -> بنية Visual دلالية (Semantic visual structure).

---

## 29. High-risk review يجب أن تبقى آمنة عبر Modalities

لا ينبغي لـ Accessibility تجاوز Review.

إذا طلب User بالصوت تجهيز Purchase:

فينبغي أن تعرض UI أيضًا:

```text
السلعة
السعر
التاجر
التسليم
طريقة الدفع
```

وتطلب Explicit confirmation.

ينبغي أن تحافظ Alternative input/output paths على Safeguards.

## 30. استعراض UX من البداية إلى النهاية (End-to-end UX walkthrough)

يعيد المصدر زيارة Long-running battery-storage report.

### البداية (Start)

ينطق User بالـ Request.

وترد Assistant بإقرار مختصر.

### هوية Task (Task identity)

تظهر Task card.

### تغيير Scope (Scope change)

## 32. UX anti-patterns شائعة

تصبح Implementation details جزءًا من Product UI.

تبدأ Work دون Durable identity مرئية.

### رسائل Error عامة (Generic error messages)

### Personalization مخفية (Hidden personalization)

يحدث Adaptation دون Explanation.

### أسماء Protocols بوصفها مفاهيم Product

يضطر Users إلى تعلم Implementation vocabulary.

### إلغاء واسع أكثر من اللازم (Overbroad cancellation)

تؤدي مقاطعة Speech إلى إلغاء Background work.

## 64. AgentOps improvement loop الكاملة

ينبغي لـ Production agent platform دعم Cycle:

```text
التصميم
  ↓
التطوير
  ↓
التقييم
  ↓
النشر
  ↓
المراقبة
  ↓
جمع feedback
  ↓
تحديث كتالوج evaluation
  ↓
تحسين prompts/الأدوات/agents
  ↓
إعادة deploy
```

إذًا AgentOps ليست Deployment فقط.

بل Lifecycle management.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "إذا كان Backend صحيحًا، فستبدو UX موثوقة."

لا. Hidden state تجعل Systems صحيحة تقنيًا تبدو معطلة.

### المفهوم الخاطئ 2
> "Chat transcript تكفي لـ Live multi-agent work."

لا. تحتاج Long-running و Multimodal workflows إلى Stateful workspace surfaces.

### المفهوم الخاطئ 3
> "ينبغي لـ Voice حمل كل Information داخل Voice-first product."

لا. تحمل Voice الـ Intent جيدًا؛ أما Dense durable detail فمكانها Visual غالبًا.

### المفهوم الخاطئ 4
> "ينبغي لمقاطعة Speech أن تلغي Active Task تلقائيًا."

لا. Speech interruption و Task cancellation Actionان مختلفان.

### المفهوم الخاطئ 5
> "كلما زادت Protocol labels تفصيلًا أصبحت UI أكثر شفافية."

لا. Transparency تعني State ذات معنى، لا Raw implementation jargon.

### المفهوم الخاطئ 6
> "يجب على Task card دائمًا عرض Numeric progress."

لا. Honest phase labels أفضل من Fake precision.

### المفهوم الخاطئ 7
> "ينبغي السماح للـ Agents بتوليد Arbitrary UI code."

لا. المبدأ الثابت في المصدر هو Host-controlled rendering عبر Approved components.

### المفهوم الخاطئ 8
> "Approval prompt لا تحتاج إلا زر Approve."

لا. يحتاج User إلى Context و Consequence و Alternatives و Safe expiry.

### المفهوم الخاطئ 9
> "ينبغي أن تكون Personalization غير مرئية عندما تكون مفيدة."

لا. يؤكد المصدر على Adaptation تكون Visible و Scoped و Reversible.

### المفهوم الخاطئ 10
> "Voice تحل Accessibility تلقائيًا."

لا. تحتاج Critical interactions إلى Alternative modalities.

### المفهوم الخاطئ 11
> "AgentOps تستبدل MLOps و GenAIOps."

لا. يقدم المصدر Evolution بوصفها Additive.

### المفهوم الخاطئ 12
> "يمكن تقييم Agent quality من Final answers فقط."

لا. يهم أيضًا Tool choice و Parameters و Trajectory و Latency و Cost.

### المفهوم الخاطئ 13
> "Tool Registry و Agent Registry مجرد Inventories بسيطة."

لا. تدعمان Governance و Ownership و Versioning و Discovery و Secure reuse.

### المفهوم الخاطئ 14
> "Memory مجرد Model-context feature."

لا. Persistent memory تنشئ Governance و Privacy و Lifecycle concerns.

### المفهوم الخاطئ 15
> "Model ذات Highest accuracy هي تلقائيًا Model الصحيحة."

لا. يوازن المصدر Performance مع Cost و Latency/Business priorities.

### المفهوم الخاطئ 16
> "Public model leaderboards كافية لاختيار Production model."

لا. قيّم Candidate models على Use-case data الخاصة بك.

### المفهوم الخاطئ 17
> "Human evaluation و LLM-as-a-judge متعارضان."

لا. يصف المصدر Progression وجمعًا بينهما وفق Precision و Scale.

### المفهوم الخاطئ 18
> "AgentOps مجرد Monitoring."

لا. تشمل Evaluation و Registries و Memory و Governance و Deployment و Observability و Lifecycle improvement.
