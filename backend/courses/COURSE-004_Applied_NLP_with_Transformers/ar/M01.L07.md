## 1. ما هي Question Answering؟

لا تكتفي Search Systems دائمًا بإرجاع Documents، بل قد تعيد أيضًا Answer Snippet قصيرة مباشرة.

Architecture شائعة هي:

```text
سؤال المستخدم
    ↓
استرجاع Documents ذات صلة
    ↓
استخراج الإجابة أوتوليدها
```

يركز الفصل أولًا على Extractive QA.

في Extractive QA، يجب أن تكون الإجابة Span موجودة أصلًا داخل Document.

مثال:

```text
السؤال: هل الساعة مقاومة للماء؟
السياق: هذه الساعة مقاومة للماء حتى عمق 30m.
الإجابة: مقاومة للماء حتى 30m
```

توجد أشكال أخرى من QA أيضًا، منها:

- Community QA،
- Long-form QA،
- QA على Tables،
- Generative QA،
- Multimodal QA.

```text

```

هذه الـ Dataset صعبة لأن كثيرًا من الأسئلة Subjective. فعبارة مثل "جودة ضعيفة" لا تمتلك تعريفًا عالميًا واحدًا.

يحتوي QA Example عادة على:

| الحقل | المعنى |
|---|---|
| question | سؤال المستخدم |
| context | Review أو Document |
| answer text | Answer Span الصحيحة |
| answer start | Character Offset الذي تبدأ عنده الإجابة |

بعض الأسئلة تكون Unanswerable عمدًا وتحتوي على إجابة فارغة.

Electronics Split في الفصل صغيرة نسبيًا، ولذلك يصبح Transfer Learning مهمًا جدًا.

### Closed-domain مقابل Open-domain QA

Closed-domain QA تبحث داخل Domain ضيقة، مثل Product Category واحدة.

أما Open-domain QA فتبحث في Knowledge Source أوسع بكثير.

نظام Product-review QA في الفصل مثال على Closed-domain QA.

## 3. لماذا SQuAD مهمة؟

ساهمت Stanford Question Answering Dataset (SQuAD) في ترسيخ Format القياسي المستخدم في Extractive QA: Question + Passage + Answer Span

تحتوي SQuAD 1.1 على Answerable Questions تكون إجاباتها موجودة داخل Passage.

أما SQuAD 2.0 فتضيف Questions تبدو مرتبطة بالسياق لكنها لا يمكن الإجابة عنها من Passage.

وهذا مهم لأن نظام QA قويًا يجب أن يستطيع أحيانًا أن يقول:

```text
لا توجد إجابة يدعمها هذا السياق.
```

يبدأ الفصل من MiniLM Model سبق Fine-tuning لها على SQuAD 2.0 بدلًا من تدريب QA Head من الصفر، لأن Training Set الخاصة بـ SubjQA صغيرة.

هذا Pattern مفيد في Transfer Learning:

```text
General Language Pretraining
        ↓
Fine-tuning على QA Dataset كبيرة
        ↓
Adaptation إلى Target Domain أصغر
```

## 4. Extractive QA هي Span Classification

لا يولّد الـ Model نص الإجابة مباشرة.

بدلًا من ذلك، يتنبأ بـ:

- أكثر Start Token احتمالًا،
- وأكثر End Token احتمالًا.

لنفترض أن Tokenized Context هي:

```text
السياق بعد تقسيمه إلى Tokens: [this] [watch] [is] [waterproof] [at] [30m] [depth]
```

قد تقابل الإجابة الصحيحة:

```text
start = waterproof   — الرمز الذي تبدأ عنده الإجابة
end   = 30m          — الرمز الذي تنتهي عنده الإجابة
```

تنتج QA Head Scoreين لكل Input Token:

```text
موضع الـ Token (Token Position)
   ├── درجة البداية (Start Score)
   └── درجة النهاية (End Score)
```

## 9. من Passage واحدة إلى آلاف: Retriever-Reader Architecture

حتى الآن افترضنا أن Context الصحيحة معروفة بالفعل.

لكن المستخدم الحقيقي يرسل عادة سؤالًا فقط.

إذا كان Product يمتلك مئات Reviews، فإرسال كل Review إلى Reader سيكون بطيئًا جدًا.

لذلك تفصل QA الحديثة العمل إلى مرحلتين:

### Retriever

يعثر على Documents/Passages الأكثر صلة بالـ Query.

### Reader

يجري Reading Comprehension أعمق على المجموعة المسترجعة الأصغر، ثم يستخرج Answer Spans.

```text
السؤال (Question)
   ↓
Retriever
   ↓ أفضل k مقطعًا (Top-k Passages)
Reader
   ↓
الإجابات المرشّحة (Answer Candidates)
```

يمكن إدراج Optional Reranking أو Postprocessing Stages بين هذه المكونات أو بعدها.

[[IMAGE_NEEDED: Retriever-reader QA architecture | Question -> document store -> retriever -> top-k documents -> optional reranker -> reader -> answer candidates, with clear separation of retrieval and reading stages | Learner should notice that retrieval reduces the amount of text the expensive reader must process]]

## 11. Sparse Retrieval باستخدام BM25

أول Retriever في الفصل يعتمد على BM25.

BM25 هي Sparse Lexical Retrieval Method. تقوم بتقييم Documents اعتمادًا بدرجة كبيرة على Term Matching وTerm Frequency وInverse Document Frequency وDocument-length Normalization.

من نقاط قوتها:

- سرعة Indexing وRetrieval،
- Lexical Matching قوي،
- دعم ناضج في Search Engines.

أما نقطة ضعفها فهي احتمال فقد Semantic Matches عندما يستخدم Query وDocument كلمات مختلفة.

مثال:

```text
Query:  هل هو جيد للقراءة؟
Review: الشاشة الأكبر تجعل قراءة الكتب أسهل
```

العبارات مختلفة حرفيًا، رغم أن المعنى قريب جدًا.

يسترجع الفصل Top Documents أولًا، ثم يترك QA Reader تستخرج Answer Spans منها.

## 12. الـ Reader تستخرج الإجابات من Retrieved Passages

يستخدم الفصل MiniLM SQuAD 2.0 Reader.

وظيفتها ليست البحث في Corpus كاملة، فقد قام Retriever بالفعل بتقليل Candidate Set.

عند إعطائها Query وعدة Candidate Passages، تتنبأ Reader بـ Answer Spans وتقوم بترتيب Answer Candidates.

قد تبدو End-to-end Result مثل:

```text
السؤال: هل هو جيد للقراءة؟

الإجابة 1: أستخدمه أساسًا لقراءة الكتب
الإجابة 2: الشاشة الأكبر ... تجعل القراءة أسهل
الإجابة 3: ممتاز لقراءة الكتب عندما لا يتوفر ضوء
```

يوضح ذلك لماذا يكمل Retrieval وReading أحدهما الآخر:

- Retriever يضيّق Search Space،
- Reader تنفذ Detailed Answer Extraction.

## 13. تقييم Retriever باستخدام Recall@k

يحدد Retriever أي Documents ستراها Reader.

إذا لم يتم استرجاع Relevant Passage، فلن تستطيع حتى Reader مثالية الإجابة بصورة صحيحة.

لهذا يركز الفصل على Retriever Recall.

يسأل Recall@k:

> في كم Question تظهر Relevant Document واحدة على الأقل ضمن أفضل k Documents مسترجعة؟

يحقق الفصل تقريبًا Recall@3 = 0.95 في أحد إعدادات تقييم BM25.

زيادة `k` غالبًا تحسن Recall، لكنها تخلق تكلفة:

```text
k أعلى
  → احتمال أكبر للعثور على Relevant Passages
  → عدد أكبر من Passages يُرسل إلى Reader
  → Reader Latency أعلى
```

هذه System-level Trade-off، وليست Retrieval Metric فقط.

## 14. الاسترجاع الكثيف للمقاطع (Dense Passage Retrieval — DPR)

يعتمد Sparse Retrieval بدرجة كبيرة على Lexical Overlap.

أما Dense Retrieval فتقوم بتحويل Questions وPassages إلى Learned Dense Vectors.

تستخدم DPR اثنين من Transformer Encoders:

- Question Encoder،
- Passage Encoder.

هدف التدريب هو جعل Relevant Question-Passage Pairs ذات Similarity مرتفعة، بينما تحصل Irrelevant Pairs على Similarity أقل.

```text
السؤال ──► مرمِّز السؤال (Question Encoder) ──► المتجه q

المقطع ──► مرمِّز المقطع (Passage Encoder)  ──► المتجه p

الصلة ≈ similarity(q, p)
```

[[IMAGE_NEEDED: DPR bi-encoder architecture | A question enters one BERT-like encoder and a passage enters another; each produces a dense vector and their similarity determines relevance | Learner should notice that the question and passage are encoded separately, which enables efficient retrieval over many stored passage vectors]]

في تجربة SubjQA في الفصل، لا تتفوق DPR على BM25 في Recall. وهذا درس مهم: Dense Retrieval ليست أفضل تلقائيًا. Domain Fit وطريقة تدريب Retriever لهما أهمية كبيرة.

## 15. تقييم Reader باستخدام EM وF1

اثنتان من أشهر Metrics لتقييم Extractive-QA Reader هما:

### Exact Match (EM)

يجب أن تتطابق Normalized Prediction تمامًا مع Reference Answer.

### F1-score

تقيس Token Overlap بين Prediction وReference باستخدام Harmonic Mean بين Precision وRecall.

مثال:

```text
Reference: 6000 hours        — الإجابة المرجعية
Prediction: about 6000 hours — إجابة النموذج
```

تكون EM مساوية 0 لأن Strings مختلفة بعد Normalization.

لكن قد تبقى F1 مرتفعة لأن أغلب Answer Tokens متداخلة.

إلا أن F1 يمكن أيضًا أن تبالغ في تقييم إجابة سيئة. فإذا تنبأ الـ Model مثلًا:

```text
about 6000 dollars   — إجابة خاطئة المعنى
```

فما زال بعض Tokens متداخلًا رغم أن المعنى خاطئ.

لذلك يوصي الفصل بمتابعة EM وF1 معًا بدلًا من الاعتماد على Metric واحدة.

## 16. Domain Adaptation: SQuAD ليست Customer Reviews

تؤدي Model تم Fine-tuning لها على SQuAD أداءً أضعف بكثير على SubjQA مقارنة بأدائها على Benchmark الأصلية.

لماذا؟

- Wikipedia رسمية وFactual.
- Customer Reviews غير رسمية.
- Questions وAnswers في SubjQA غالبًا Subjective.
- Language Distribution مختلفة.

يقوم الفصل بعمل Adaptation لـ MiniLM Reader عن طريق Fine-tuning إضافي على SubjQA.

مسار Transfer المفيد هو:

```text
Pretrained MiniLM
      ↓
Fine-tuning على SQuAD QA Data كبيرة
      ↓
Fine-tuning مرة أخرى على SubjQA Domain Data الصغيرة
```

يؤدي ذلك إلى تحسن كبير في أداء SubjQA.

ويقارن الفصل هذا الأسلوب أيضًا بإجراء Fine-tuning مباشرة للـ Base MiniLM على SubjQA فقط. الأسلوب المباشر يعطي أداءً أضعف، ما يدعم قيمة Intermediate QA Training Stage الكبيرة عندما تكون Target-domain Data قليلة.

## 17. تقييم QA Pipeline كاملة

تقييم Reader عندما تكون Context الصحيحة مقدمة لها مسبقًا أسهل من Production QA الحقيقية.

في النظام الحقيقي:

```text
Question
   ↓
Retriever قد يعيد Passages غير مثالية
   ↓
Reader يجب أن تجيب من هذه Passages
```

عندما يقيّم الفصل Retriever + Reader معًا، تكون End-to-end EM/F1 أقل من Reader-only Evaluation بأسلوب SQuAD.

وهذا يكشف واحدًا من أهم مبادئ الفصل:

> **جودة المكونات منفردة لا تعني تلقائيًا جودة النظام كاملًا.**

ينبغي تقييم:

- Retriever Recall،
- Reader EM/F1 باستخدام Known-good Contexts،
- End-to-end EM/F1 باستخدام Retrieved Contexts،
- Latency وTop-k Trade-offs.

[[IMAGE_NEEDED: QA component versus end-to-end evaluation | A diagram with separate metric boxes under retriever (Recall@k), reader (EM/F1 with gold contexts), and full system (end-to-end EM/F1 + latency) | Learner should notice that every layer needs its own evaluation as well as a final system-level evaluation]]

## 18. تجاوز Extractive QA باستخدام RAG

لا تستطيع Extractive QA إرجاع سوى Spans موجودة بالفعل في Retrieved Passages.

أحيانًا ينبغي للإجابة دمج Evidence من عدة أماكن داخل جملة جديدة. وهذا ما يحفّز Generative QA.

يقدم الفصل RAG.

تستبدل RAG الـ Extractive Reader بـ Generator.

```text
السؤال (Question)
   ↓
Dense Retriever (DPR)
   ↓ المستندات ذات الصلة (Relevant Documents)
مولّد Seq2seq (Seq2seq Generator)
   ↓
الإجابة المولَّدة (Generated Answer)
```

يمكن أن تكون الـ Generator من نوع Sequence-to-sequence Transformer مثل BART أو T5.

يميّز الفصل بين:

### RAG-Sequence

تستخدم Retrieved-document Evidence على مستوى الـ Sequence لتوليد الإجابة.

### RAG-Token

يمكنها عمليًا الاستفادة من Documents مختلفة أثناء توليد Tokens مختلفة، ما يسمح بدمج Evidence بمرونة أكبر.

[[IMAGE_NEEDED: RAG architecture | Question -> dense retriever -> top-k passages -> sequence-to-sequence generator -> generated answer, with the retrieval stage visually connected to generation | Learner should notice that RAG grounds generation in retrieved external documents rather than generating from the language model alone]]

يوضح مثال الفصل أن RAG قد تنتج إجابات معقولة، خصوصًا للأسئلة الأكثر Factual، لكن Subjective Questions قد تظل مربكة لها.

## 19. Hierarchy عملية لبناء QA Systems

توصي خلاصة الفصل بمنهج Incremental لبناء QA في العالم الحقيقي.

Hierarchy مفيدة هي:

```text
1. ابنِ Search/Retrieval قوية
          ↓
2. أضف Extractive QA
          ↓
3. فكّر في Generative QA فقط عند الحاجة
```

لماذا هذا الترتيب؟

- Search وحدها توفر قيمة فعلية للمستخدم.
- Extractive QA أسهل في الفحص لأن الإجابة تأتي مباشرة من Evidence.
- Generative QA أكثر مرونة، لكنها تضيف Failure Modes أكثر تعقيدًا.

[[IMAGE_NEEDED: QA hierarchy of needs | A three-level pyramid with retrieval/search at the base, extractive QA in the middle, and generative QA/RAG at the top | Learner should notice that strong retrieval is foundational and generative QA should build on a reliable evidence pipeline]]

يشير الفصل أيضًا إلى اتجاهات مستقبلية مثل:

- Multimodal QA عبر Text وTables وImages،
- QA فوق Knowledge Graphs،
- Synthetic Question Generation من أجل Data Augmentation.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: QA Model تبحث في Corpus كاملة بنفسها

> أعطِ Transformer سؤالًا وستجد تلقائيًا Document الصحيحة.

### لماذا هذا خطأ

تتوقع Extractive Reader وجود Question وContext. ولذلك نحتاج عادة إلى Retriever لاختيار Documents ذات الصلة أولًا.

### المفهوم الخاطئ 2: Truncation للـ QA Contexts الطويلة غير مؤذٍ

> إذا كانت Document طويلة جدًا، يكفي الاحتفاظ بالبداية.

### لماذا هذا خطأ

قد توجد الإجابة قرب النهاية. Sliding Windows تحافظ على Coverage عبر Context كاملة.

### المفهوم الخاطئ 3: Dense Retrieval أفضل دائمًا من BM25

> Transformer Embeddings تتفوق تلقائيًا على Lexical Retrieval.

### لماذا هذا خطأ

في تجربة SubjQA في الفصل، لا تحسن DPR الـ Recall مقارنة بـ BM25. تعتمد Retrieval Quality على البيانات وDomain Adaptation.

### المفهوم الخاطئ 4: Reader قوية تضمن QA System قوية

> إذا كانت Reader F1 مرتفعة، فستكون End-to-end Performance مرتفعة أيضًا.

### لماذا هذا خطأ

لا تستطيع Reader العمل إلا على Evidence تم استرجاعها. تنتقل Retrieval Errors إلى المراحل التالية وتقلل جودة النظام كاملًا.

### المفهوم الخاطئ 5: Generative QA أفضل دائمًا من Extractive QA

> إذا كانت Generator قادرة على تركيب الإجابات، فينبغي أن تستبدل Search وExtraction.

### لماذا هذا خطأ

Generative QA أكثر مرونة، لكنها تمتلك Failure Modes أكثر خفاءً. يوصي الفصل ببناء Retrieval قوية وExtractive Capabilities أولًا.

## المصطلحات الرئيسية

| المصطلح | المعنى |
|---|---|
| Question Answering (QA) | نظام يجيب عن Natural-language Questions اعتمادًا على Evidence أو Model Knowledge |
| Extractive QA | تعيد Answer Span مباشرة من Context Document |
| Generative QA | تولّد Answer Sequence جديدة من Retrieved Evidence |
| Span Classification | التنبؤ بموضعي Start وEnd الخاصين بالإجابة |
| Start Logit | Score يعبّر عن احتمال أن تبدأ الإجابة عند Token معينة |
| End Logit | Score يعبّر عن احتمال أن تنتهي الإجابة عند Token معينة |
| Unanswerable Question | سؤال لا يدعم Context إجابة له |
| Sliding Window | Chunks متداخلة لمعالجة Contexts أطول من Model Limit |
| Stride | عدد Tokens المتداخلة بين Windows المتجاورة |
| Retriever | مكوّن يختار Documents/Passages ذات الصلة |
| Reader | مكوّن يستخرج إجابة من Retrieved Text |
| Document Store | Storage Layer قابلة للبحث للمستندات وMetadata |
| BM25 | طريقة لتسجيل الصلة تعتمد على Sparse Lexical Retrieval |
| DPR | Dense Passage Retrieval باستخدام Question Encoder وPassage Encoder منفصلين |
| Recall@k | نسبة Questions التي تظهر Relevant Evidence لها ضمن Top-k Retrieved Documents |
| Exact Match | Metric صارمة تقيس تطابق Normalized Answer String بالكامل |
| F1 | Token-overlap Metric توازن بين Precision وRecall |
| Domain Adaptation | تدريب إضافي للـ Model على Target-domain Data |
| RAG | Retrieval-Augmented Generation؛ توليد Answers بالاعتماد على Retrieved Evidence |
| RAG-Sequence | صيغة RAG تستخدم Document Evidence على مستوى Sequence |
| RAG-Token | صيغة RAG تسمح بتغير Document Evidence عبر Generated Tokens |

## اختبر نفسك

قبل المتابعة، تأكد أنك تستطيع الإجابة عن الأسئلة التالية:

1. ما الذي يجعل Extractive QA مختلفة عن Text Classification العادية؟
2. ماذا تمثل Start Logits وEnd Logits؟
3. لماذا يجب أن تدعم QA Systems الأسئلة غير القابلة للإجابة؟
4. لماذا تكون Sliding Window أفضل من Naive Truncation؟
5. ما دور Retriever؟
6. ما دور Reader؟
7. لماذا قد تؤدي زيادة Top-k إلى تحسين Recall لكنها تزيد Latency؟
8. كيف تختلف DPR عن BM25؟
9. لماذا ينبغي متابعة EM وF1 معًا؟
10. لماذا لا ينتقل Fine-tuning على SQuAD بصورة مثالية إلى SubjQA؟
11. لماذا تبالغ Reader-only Evaluation في تقدير End-to-end System Performance؟
12. كيف تختلف RAG عن Extractive Retriever-Reader Pipeline؟

## احتفظ بهذه الفكرة

**QA System عملية هي Evidence Pipeline: استرجع Passages الصحيحة، وعالج Long Contexts بأمان، ثم استخرج الإجابة أوولّدها، وقيّم كل مرحلة منفصلة. تحدد Retrieval Quality السقف الأعلى، ويحسن Domain Adaptation الـ Reader، بينما توسّع RAG التصميم نفسه القائم على Evidence من Extraction إلى Generation.**
