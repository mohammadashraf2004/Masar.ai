## مخرجات التعلم



بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:



- شرح كيف تؤثر System instructions وVoice configuration في سلوك الـ Live assistant وطريقة تقديمه.

- فصل Persona design عن Task logic وTool behavior.

- شرح قيمة مبدأ "Show, don't tell" عند إضافة Camera أوScreen input إلى Assistant.

- وصف كيفية الحصول على Webcam وScreen-sharing streams داخل Browser.

- شرح لماذا تقوم تطبيقات Multimodal الحية غالبًا بأخذ Periodic frames بدل إرسال Full-rate video.

- تتبع Image ملتقطة من Browser video إلى Canvas ثم Base64 encoding ثم WebSocket transport ثم Backend decoding ثم Model input.

- شرح دورة Function calling كاملة من User intent حتى Final response.

- تصميم Local tool handler وFunction declaration واضحة.

- شرح لماذا تمد External APIs الـ Model ببيانات تتجاوز Static learned knowledge.

- وصف كيف يمكن لـ System instructions توجيه Tool-use policy.

- شرح الفرق بين Developer test UI وMobile-first product interface.

- تحديد الغرض من Responsive controls وContextual UI وCamera switching وTouch-friendly design.

- شرح كيف تقوم Docker containers بحزم Application وDependencies الخاصة بها.

- شرح دور Cloud Build وCloud Run في مسار Deployment الموجود في المصدر.

- تتبع نشر Backend وFrontend وشرح لماذا يجب أن يستخدم Browser عنوان Backend آمنًا من نوع `wss://` في Production.

- التمييز بين Architectural concepts الدائمة وبين Model names وAPI schemas وQuotas وSDK objects وDeployment commands الخاصة بمزود معين والتي يجب إعادة التحقق منها قبل Production.

## 1. من محادثة سلسة إلى مساعد قادر



في الدرس السابق بنينا Architecture لتجربة صوتية Real-time:



```text
الميكروفون
   ↓
مسار الصوت داخل Browser
   ↓
WebSocket
   ↓
Secure proxy
   ↓
Live model session
   ↓
Streaming audio response
   ↓
السماعة
```



هذا يمنحنا نظامًا Conversational.



لكن Conversation وحدها لا تكفي لبناء Assistant قادر.



يحتاج نظام أكثر فائدة إلى:



```text
التحدث بشخصية متسقة
+
إدراك السياق البصري
+
استخدام Tools للوصول إلى Live data أوتنفيذ Actions
+
العمل جيدًا على Mobile device
+
التشغيل خارج localhost
```



لذلك يوسّع هذا الدرس Application في أربعة اتجاهات:



```text
1. الشخصية  -> System instructions + Voice
2. العينان  -> Camera + Screen input
3. اليدان   -> Tools + Function calling
4. التنقل   -> Mobile UI + Cloud deployment
```



هذه الإضافات ليست Features منفصلة.



بل تنقل Application من:



```text
chatbot فوري
```



نحو:



```text
مساعد متعدد الوسائط
```



ويتعمّد المصدر التعامل مع هذا باعتباره Foundation لـ Agent أكثر اكتمالًا، وليس الشكل النهائي لنظام Fully autonomous يمتلك Advanced memory وMulti-step task execution.

## 2. إعطاء المساعد شخصية



قد يكون الـ Live assistant صحيحًا تقنيًا لكنه يظل Generic في تجربة المستخدم.



يفصل المصدر "Character" إلى طبقتين من Configuration:



1. **System instructions**

2. **Voice configuration**



### 2.1 System instructions



System instruction هي إرشادات عالية المستوى تُطبَّق في بداية Interaction.



يمكن أن تؤثر في:



- Tone،

- Style،

- Rules،

- Priorities،

- Boundaries،

- وTask behavior.



فكر فيها باعتبارها Guidance مستمرة أثناء Session.



على سبيل المثال:



```text
أنت مساعد ودود ومفيد.
ابدأ كل إجابة بتحية محددة.
```



يستخدم المصدر Greeting rule واضحة جدًا بقصد الاختبار.



لماذا؟



لأن Behavior الظاهرة تجعل من السهل التأكد مما إذا كانت Configuration تصل فعلًا إلى Model.



وهذه Technique هندسية مفيدة:



> عند اختبار مسار Configuration، اختر Behavior يمكن ملاحظة نجاحها أوفشلها فورًا.



### 2.2 Voice configuration



تؤثر System instructions في **ما الذي يقوله المساعد وكيف يتواصل من ناحية المعنى والأسلوب**.



أما Voice configuration فتؤثر في **كيف يبدو الصوت الناتج Acoustically**.



يختار المصدر Voice profile باسم محدد.



اسم Voice نفسه خاص بالمزود وقد يتغير.



أما الفكرة الدائمة فهي:



```text
إعدادات السلوك/الشخصية
        +
إعدادات صوت الكلام
        =
شخصية أكثر تماسكًا في مواجهة المستخدم
```



### Persona ليست مجرد Decoration



يمكن أن تؤثر Persona في User experience بطرق مهمة.



على سبيل المثال، يمكن إعداد الـ Assistant التقني نفسه ليكون:



- Formal،

- Concise،

- Friendly،

- Teacher-like،

- Supportive،

- Highly technical،

- أوTask-focused.



لكن Persona لا ينبغي أن تتجاوز Product requirements الأساسية مثل:



- Safety،

- Accuracy،

- Tool rules،

- أوUser control.



### افصل Persona عن Business logic



تصميم مفيد هو:



```text
System instructions:
    السلوك وTone والقواعد عالية المستوى

Tools:
    القدرات القابلة للتنفيذ

Application code:
    Validation وPermissions وSide effects

UI:
    العرض وControls
```



يجعل هذا الفصل بين المسؤوليات النظام أسهل في الصيانة.

## 3. "أرِني بدل أن تصف": لماذا يهم الإدخال البصري؟



يجبر Text وVoice المستخدم غالبًا على وصف العالم بالكلمات.



لكن الوصف يكون أحيانًا غير فعّال.



تخيل أنك تحاول شرح:



- Error message معقدة،

- جزء Machine متضرر،

- Handwritten equation،

- Chart،

- Phone screen،

- أوObject غير مألوف.



تغيّر Visual interface التفاعل من:



```text
"دعني أصف لك ما أراه."
```



إلى:



```text
"انظر إلى هذا."
```



يسمي المصدر ذلك **"show, don't tell" paradigm**.



### مثال: فني ميداني



من دون Vision:



```text
"الصمام معدني ودائري وله مسماران..."
```



مع Vision:



```text
[اعرض الكاميرا]
"هل هذا صمام Standard أمHigh-pressure؟"
```



### مثال: طالب



من دون Vision:



```text
"كتبت x squared minus 4x..."
```



مع Vision:



```text
[اعرض المعادلة المكتوبة بخط اليد]
"أين أخطأت؟"
```



### مثال: سائح



من دون Vision:



```text
"أنظر إلى مبنى به أقواس..."
```



مع Vision:



```text
[وجّه الكاميرا]
"ماذا يمكنك أن تخبرني عن هذه Architecture؟"
```



يمكن لـ Visual input أن تقلل عبء Translation والوصف على المستخدم.



لكنها تضيف أيضًا Engineering concerns جديدة:



- Permissions،

- Camera selection،

- Frame capture،

- Bandwidth،

- Latency،

- Cost،

- Privacy،

- وVisual quality.

## 4. إدارة Webcam وScreen-sharing streams



يضيف المصدر Class مخصصة باسم `MediaHandler`.



وهذا مثال جيد على Separation of responsibilities.



بدل وضع Media logic كلها داخل Application file كبيرة، ينشئ التطبيق Component واحدة مسؤولة عن Visual media.



مفاهيميًا:



```text
MediaHandler
├── initialize()
├── startWebcam()
├── startScreenShare()
├── stopAll()
├── switchCamera()
├── startFrameCapture()
└── stopFrameCapture()
```



### `initialize()`



تربط Media handler بعنصر Preview داخل Browser.



### `startWebcam()`



تستخدم Browser media API لطلب Camera access.



مفاهيميًا:



⟦CODE_0⟧



### `startScreenShare()`



تستخدم Screen-capture APIs لتسمح للمستخدم باختيار:



- Screen،

- Window،

- أوBrowser tab.



مفاهيميًا:



⟦CODE_1⟧



### `stopAll()`



ينبغي أن تقوم Cleanup صحيحة بما يلي:



1. إيقاف كل Track داخل Media stream الحالية،

2. إنهاء Camera/Screen capture،

3. إخفاء Preview أوإعادة ضبطها،

4. إيقاف أي Frame-capture timer.



وهذا مهم لأن إخفاء عنصر `<video>` وحده لا يعني بالضرورة إيقاف Physical camera.



### `switchCamera()`



يهم ذلك بصورة خاصة على Mobile devices لأن المستخدم قد يريد التبديل بين:



- Front-facing camera،

- الكاميرا الخلفية.



ويُعد المصدر هذه Capability للـ Mobile UI.



### لماذا نستخدم Class مخصصة؟



لأن Media state لها Complexity مستقلة:



```text
حالة Permission
Active stream
Current camera
Screen share
Preview element
Capture timer
Cleanup
```



تغليف هذا المنطق يجعل Application أسهل في الفهم.

## 5. لماذا تتفوق Periodic frame capture على Full video في كثير من مهام Assistant؟



قد تنتج Camera:



```text
30 FPS
60 FPS
أوأكثر
```



لكن Conversational assistant غالبًا لا تحتاج إلى كل Frame.



افترض أن المستخدم يسأل:



> ما Object الذي أمسكه؟



إذا كان Scene يتغير ببطء، فإن إرسال 30 Image كل ثانية قد يكون هدرًا.



لذلك يتخذ المصدر قرارًا معماريًا:



```text
اعرض Smooth video محليًا للمستخدم
لكن
أرسل Periodic snapshots فقط إلى Model
```



### استراتيجية المصدر



يستخدم الفصل:



```text
1 captured frame per second — Frame واحدة ملتقطة في الثانية
```



وهذا اختيار Implementation خاص بالمصدر.



أما المبدأ الدائم فهو **Frame sampling**.



### لماذا نستخدم Sampling؟



يمكن أن تقلل Frame sampling:



- Network bandwidth،

- Token/Media usage،

- Provider cost،

- Backend work،

- وModel processing load.



كما تمنح Model تدفقًا manageable من Visual context.



### متى تعمل Sampling جيدًا؟



أمثلة:



- التعرف على Object،

- فحص Static chart،

- شرح Screen،

- مشاهدة Homework page،

- فحص Environment تتغير ببطء.



### متى تكون Sampling ضعيفة؟



أمثلة:



- Fast sports movement،

- Gesture timing،

- Frame-by-frame defects،

- Rapid assembly-line events،

- تتبّع دقيق للحركة.



إذن السؤال الصحيح ليس:



> هل ينبغي أن أستخدم دائمًا 1 FPS؟



بل:



> ما Visual sampling rate التي تحتفظ بمعلومات كافية لهذه Task؟



[[IMAGE_NEEDED: Local smooth video vs sampled AI frames | A live camera stream displayed smoothly to the user on the left, while only periodic snapshots (for example at t=0s, 1s, 2s) are sent to the AI on the right | Learner should notice that the user can see full-motion video while the model receives a much lower-rate visual stream]]

## 7. توسيع Proxy من Audio-only إلى Multimodal



في الدرس السابق كانت Proxy تتعامل أساسًا مع Audio.



الآن يجب أن تميز بين عدة Message types.



مفاهيميًا:



⟦CODE_6⟧



تصبح Proxy بوابة Multimodal.



### مسار Audio



```text
PCM من المتصفح
    ↓
Base64
    ↓
فك الترميز في الـ proxy
    ↓
كتلة الصوت (blob)
    ↓
النموذج المباشر
```



### مسار Image



```text
إطار الكاميرا/الشاشة
    ↓
JPEG
    ↓
Base64
    ↓
WebSocket
    ↓
فك الترميز في الـ proxy
    ↓
image/jpeg مدخل
    ↓
النموذج المباشر
```



### لماذا نبقي Proxy بسيطة؟



يتعامل المصدر معها في البداية كـ Transparent relay تقريبًا.



وهذا مفيد لأنه يجعل المسؤوليات واضحة:



```text
Browser:
    التقاط Media

Proxy:
    Authentication + Translation + Relay

Model:
    Reasoning على Media
```



مع نمو النظام قد تحتاج Proxy أيضًا إلى:



- Validation،

- Logging،

- Rate limiting،

- Moderation،

- Tool execution،

- Authorization،

- أوStorage decisions.



لكن ينبغي أن يظل Basic multimodal transport path مفهومًا.



[[IMAGE_NEEDED: Multimodal proxy flow | Browser sends two labeled streams, Audio and JPEG Frames, into one backend proxy; proxy decodes each and forwards both into one live model session | Learner should see that one session can receive multiple input types through the same application architecture]]

## 8. اختبار Visual reasoning



يستخدم المصدر Checkpoint بسيطة:



1. ابدأ Live audio session.

2. فعّل Webcam.

3. اسمح بـ Camera access.

4. اعرض Object.

5. اطرح Visual question.

6. أوقف Camera.



أمثلة Prompts:



```text
"ماذا ترى؟"
"صف Object الموجودة أمامي."
"ما لون الكوب؟"
```



### لماذا هذه Checkpoint مفيدة؟



لأنها تختبر عدة Layers دفعة واحدة:



```text
زر UI
-> إذن المتصفح
-> بث الكاميرا
-> المعاينة
-> مؤقت الالتقاط
-> ترميز JPEG
-> WebSocket
-> فك الترميز في الـ proxy
-> مدخل النموذج
-> استجابة صوتية
```



إذا أجابت Assistant بصورة صحيحة عن Object المرئية، فغالبًا أن Visual pipeline كاملة تعمل.



### استراتيجية Debugging أفضل



إذا فشل الأمر، اعزل Pipeline.



تحقق من:



```text
1. هل Camera preview تعمل؟
2. هل يتم التقاط Frames؟
3. هل يتم إنتاج Base64 data؟
4. هل Browser يرسل Image messages؟
5. هل Proxy تستقبلها؟
6. هل Proxy تفك الترميز بصورة صحيحة؟
7. هل Upstream session تقبل Image input؟
8. هل Model تستجيب للـ Visual context؟
```



مرة أخرى، Debugging الجيدة تتبع Data path.

## 9. إعطاء Assistant "يدين": Tools وFunction calling



تسمح Vision للمساعد بإدراك المزيد من العالم.



لكن الإدراك ما يزال Passive.



للتفاعل مع Systems حية أوتنفيذ Tasks، يحتاج Assistant إلى **Tools**.



يمكن أن تربط Tool الـ Model بـ:



- Weather service،

- Calendar،

- Database،

- Booking system،

- Shopping cart،

- Smart-home device،

- أوCustom application logic.



يستخدم الفصل Weather مثالًا تعليميًا.



### لماذا Weather مثال جيد؟



لا تعد Training knowledge الخاصة بالـ Model مصدرًا موثوقًا لـ:



```text
Current weather right now — الطقس الحالي الآن
```



يجب أن تأتي هذه المعلومات من Live data source.



لذلك توضح Weather الفرق بين:



```text
معرفة النموذج
```



و:



```text
بيانات خارجية فورية
```



### النموذج الذهني لـ Function calling



يسأل المستخدم:



```text
"كيف الطقس في لندن؟"
```



تتعرف Model على:



```text
أحتاج إلى بيانات خارجية حالية.
```



ثم:



```text
1. تحديد الأداة
2. استخراج المدينة
3. طلب استدعاء دالة
4. المضيف ينفّذ الدالة الفعلية
5. تعود نتيجة الأداة
6. النموذج يركّب الاستجابة
```



وهذه هي Core execution loop التي ظهرت سابقًا، ولكنها الآن مدمجة داخل Live multimodal assistant.

## 11. Architecture محلية لتنفيذ Tools



ينشئ المصدر:



```text
backend/tool_handler.py    # مسار ملف معالج الأدوات
```



وغرضه بسيط:



```text
تخزين Tool implementations الحقيقية
```



وهذا يبقي Tool logic منفصلة عن WebSocket proxy.



### Architecture



```text
proxy.py
   |
   | تستقبل Tool request
   v
tool_handler.py
   |
   | تستدعي External service
   v
Weather API
```



وهذه Architecture تعليمية جيدة لأنها:



- بسيطة،

- Local،

- سهلة Debugging،

- سريعة التعديل،

- وخالية من تعقيد Deploy لخدمة منفصلة.



### فصل المسؤوليات



بنية جيدة:



```text
proxy.py
    Transport / Session / Tool routing

tool_handler.py
    Tool implementations الفعلية

system-instructions.txt
    High-level behavior rules

.env
    Secrets / Configuration
```



وهذا أنظف من وضع كل شيء داخل File واحدة.



### شكل Tool مثال

## 12. تعليم Model عن Tool



كتابة Python function وحدها لا تكفي.

- Types،

- Required fields.

⟦CODE_12⟧


| Build substitution | Deployment-time value تُحقن داخل Build configuration |

## التحقق الذاتي



قبل المتابعة، تأكد من قدرتك على الإجابة:



1. ما الفرق بين System instructions وVoice configuration؟

2. لماذا تمثل Greeting rule واضحة اختبارًا مفيدًا للـ Configuration؟

3. ما الذي يحسنه "show, don't tell" interaction model؟

4. لماذا يستخدم المصدر `MediaHandler` class مخصصة؟

5. لماذا ينبغي عند إيقاف Video stream إيقاف Underlying media tracks؟

6. لماذا قد تكفي Frame واحدة في الثانية لبعض Tasks ولا تكفي لأخرى؟

7. ما دور Hidden canvas في Visual pipeline؟

8. تتبع Image frame من Webcam حتى Model.

9. ما التغييرات المطلوبة في Proxy لدعم Audio وImage messages معًا؟

10. لماذا يمثل Live weather request مثالًا جيدًا على Function calling؟

11. ما الفرق بين Python tool implementation الحقيقية وبين Function declaration التي تراها Model؟

12. من الذي ينفذ Weather function فعليًا؟

13. لماذا يمكن لـ System instruction أن تطلب من Model استخدام Tool لكنها لا تستبدل Backend validation؟

14. لماذا تكون Clean internal tool result أفضل من إعادة Raw external API payload؟

15. ما الذي يجعل Mobile-first interface مختلفة عن Developer test UI؟

16. لماذا تكون Contextual UI مفيدة على Small screen؟

17. ما المشكلة التي تحلها Containerization؟

18. ما الدور الذي تلعبه Cloud Build في Deployment flow؟

19. لماذا ينشر Backend قبل Frontend في Workflow الخاصة بالمصدر؟

20. لماذا تحتاج Production frontend إلى `wss://` بدل Localhost `ws://` URL؟

21. أي أجزاء من الدرس تمثل Durable architecture وأيها Provider-specific implementation details؟

22. ما Privacy controls التي ينبغي إحاطتها بميزات Camera وScreen sharing؟
