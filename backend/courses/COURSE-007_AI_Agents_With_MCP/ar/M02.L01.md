## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح الفرق بين LLM provider client و MCP client.
- وصف ما الذي يجعل التطبيق MCP host application.
- شرح علاقة one-client-instance-to-one-server المستخدمة في فصل المصدر.
- تصميم MCP client wrapper قابل لإعادة الاستخدام يضم أساليب connect و disconnect و discovery و use.
- الاختيار بين stdio و Streamable HTTP وفق سيناريو الـ Deployment.
- شرح سبب فائدة `AsyncExitStack` في إدارة lifecycle لاتصال MCP.
- اكتشاف MCP tools واستدعائها مع التعامل مع أنواع محتوى متعددة.
- بناء tool-use loop متكررة تعيد نتائج Tool إلى LLM حتى يتم إنتاج إجابة نهائية.
- سرد MCP resources واختيارها وتحميلها إلى context الخاص بـ Model.
- استخدام resource templates وفهم سبب كون اختيار Resource قرارًا ضمن context engineering.
- اكتشاف MCP prompts وتمرير parameters إليها وتحميلها.
- التعامل بأمان مع أخطاء MCP و timeouts والانقطاعات غير المتوقعة والتنظيف.
- تطبيق مبادئ تصميم على جانب Client مثل capability filtering و model agnosticism و logging و retries والتعامل مع secrets.

## 1. من تطبيق LLM عادي إلى MCP host

قبل إضافة MCP، ابدأ بأبسط تطبيق ممكن: برنامج يستقبل إدخال المستخدم، ويرسله إلى LLM API، ويتلقى response، ثم يطبع هذا response.

تصوريًا:

```text
المستخدم (User) → برنامج المضيف (Host program) → LLM API → برنامج المضيف (Host program) → المستخدم (User)
```

هذا التطبيق مفيد، لكنه لا يستخدم MCP بعد. لكي يصبح **MCP host application**، يجب أن يستضيف أيضًا MCP client واحدًا أو أكثر يتواصل مع MCP servers.

يمكن أن يكون Host صغيرًا جدًا أو بالغ التعقيد. يعرض الفصل أمثلة تبدأ من chatbot script بسيط وتمتد إلى IDE أو coding-agent harness أو chatbot platform أو agent framework. تتمثل المسؤوليات الأساسية لـ Host في التفاعل مع LLM واحتواء Client code الذي يوفّر الوصول إلى MCP servers.

إذا أراد Host أن يتيح لـ Model اختيار Tools، فيجب أن يدعم Model أيضًا tool calling.

### نوعان مختلفان من Clients يجب ألا تخلط بينهما

من السهل على المبتدئ أن يخلط بين **LLM provider client** و **MCP client**.

| العميل (Client) | يتحدث إلى | الغرض |
|---|---|---|
| عميل مزود LLM (LLM provider client) | API الخاص بمزود Model | يرسل messages إلى Language Model ويتلقى responses من Model |
| عميل MCP (MCP client) | خادم MCP (MCP server) | يكتشف MCP capabilities مثل tools و resources و prompts ويستخدمها |

ينسّق Host application بين الجانبين.

```text
                    ┌───────────────┐
المستخدم (User) ─────────────→ │ تطبيق المضيف (Host App)      │
                    │               │
                    │ عميل LLM (LLM Client) ───────→ LLM API
                    │ عميل MCP (MCP Client) ───────→ خادم MCP (MCP Server)
                    └───────────────┘
```

### أبقِ secrets خارج source code

يقوم Host الابتدائي في الفصل بتحميل API key من environment variables، واختياريًا من خلال ملف `.env`. القاعدة الهندسية المهمة ليست Library بعينها، بل ألا تُكتب secrets مباشرة داخل code وألا تُضاف إلى version control.

> إذا كُشف API key للعامة بالخطأ، فألغِه أو ألغِ تفويضه واستبدله بدل افتراض أن حذفه من repository history كافٍ.

## 2. ما مسؤوليات MCP client؟

يمثل MCP client الجسر بين Host application و MCP server. في التصميم المستخدم في فصل المصدر، يتواصل كل Client instance مع Server واحد. وإذا احتاج Host إلى عدة Servers، فإنه ينشئ عدة Client instances.

كحد أدنى، ينبغي أن يكون Client المفيد قادرًا على:

1. **الاتصال (Connect)** بـ Server.
2. **الاكتشاف (Discover)** لما يوفّره Server.
3. **الإتاحة أو التحويل (Expose or translate)** لهذه capabilities إلى صيغة يستطيع Host و LLM استخدامها.
4. **الاستدعاء (Invoke)** للـ capability المختارة.
5. **قطع الاتصال والتنظيف (Disconnect and clean up)** للموارد بأمان.

يحدد الفصل أيضًا خصائص مفيدة تمتد عبر وظائف Client المختلفة:

- المصادقة (Authentication)
- تصفية القدرات (Capability filtering)
- الاستقلال عن Model (Model agnosticism)
- التسجيل (Logging)
- سلوك إعادة المحاولة (Retry behavior)
- تحويل Response (Response transformation)

### لماذا نضع Wrapper حول SDK client؟

يمكن استخدام Python SDK client مباشرة. ومع ذلك، يضع الفصل Wrapper حوله في class باسم `MCPClient` مخصص للتطبيق. يمنح هذا Wrapper التطبيق حدًا واضحًا يمكنه عنده:

- التحقق من connection state قبل الاستدعاءات،
- إضافة logs،
- إضافة retry policies،
- تحويل MCP-native objects إلى صيغة يتوقعها Model API،
- تصفية capabilities،
- معالجة النتائج قبل وصولها إلى بقية التطبيق،
- التحكم يدويًا في الاتصالات طويلة العمر.

## 3. اختيار Transport: stdio أم Streamable HTTP

قبل تنفيذ `connect()`، يجب أن يعرف Client كيف سيتواصل مع Server.

يركز الفصل على نوعين مدمجين من Transport:

| النقل (Transport) | الموقع المعتاد | الفكرة الأساسية |
|---|---|---|
| النقل المحلي (`stdio`) | Server محلي | يشغّل Host عملية فرعية (subprocess) ويتواصل عبر standard input/output |
| النقل البعيد (Streamable HTTP) | Server بعيد | يرسل Client طلبات MCP إلى HTTP endpoint بعيد |

### متى يناسب stdio؟

استخدم stdio عندما يُتوقع أن يعمل Server بجانب Host application. وهذا شائع في أدوات المطور المحلية وسيناريوهات IDE حيث يثبّت المستخدمون Server على أجهزتهم.

يعرف Host عادةً:

- executable command،
- command-line arguments،
- environment variables اختيارية.

### متى يناسب Streamable HTTP؟

استخدم Streamable HTTP عندما لا ينبغي أن يحتاج المستخدمون إلى تثبيت Server وتشغيله محليًا. وهو خيار طبيعي للمنصات المستضافة و SaaS integrations والأدوات المُدارة مركزيًا وخدمات المؤسسات.

يحتاج Host عادةً إلى Server URL، وإلى HTTP headers أو إعدادات authentication بحسب الخدمة.

### فرق مهم

مع stdio، يتم تشغيل subprocess محلي حقيقي وإدارته. أما في تصميم Streamable HTTP عديم الحالة (stateless) الموصوف في الفصل، فلا تعني كلمة 'connect' فتح socket ثنائي الاتجاه دائمًا يظل حيًا إلى الأبد. بدلًا من ذلك، يهيئ Client مسار اتصال HTTP وينفّذ protocol discovery بحيث يمكن إرسال الطلبات اللاحقة بصورة صحيحة.

[[IMAGE_NEEDED: stdio versus Streamable HTTP client connection | A side-by-side architecture: left shows Host + MCP Client launching a local MCP Server subprocess via stdio; right shows Host + MCP Client sending requests to a remote MCP Server URL over Streamable HTTP | Learner should notice that stdio manages a local process while Streamable HTTP targets a remote service]]

### الأمان يظل مهمًا عند طبقة Transport

يحذر المصدر بوضوح من ضرورة تأمين Remote transport. ويذكر authentication للاتصال والتحقق من origin headers للدفاع ضد هجمات شبيهة بـ DNS rebinding. والدرس الأوسع هو أن اتصال MCP لا يلغي متطلبات أمن الشبكات المعتادة.

يمكن فهم تدفق stdio في المصدر عبر أربع خطوات:

### تدفق اتصال Streamable HTTP

بالنسبة إلى Remote servers، يخزن Wrapper عنوان URL بدل executable محلي. وإذا احتاج التطبيق إلى headers مخصصة، فيمكنه بناء asynchronous HTTP client وتمريره إلى Streamable HTTP transport. وإذا لم يحتج إلى إعداد مخصص، يستطيع SDK إنشاء Transport الافتراضي من Server URL.

ينبغي أن يغلق `disconnect()` القوي الـ exit stack ويعيد ضبط connection state. كما يجب تنفيذ Cleanup إذا فشل إعداد الاتصال نفسه؛ وإلا فقد تظل موارد مهيأة جزئيًا قيد التشغيل.

## 5. نمط MCP القابل لإعادة الاستخدام: اكتشف ثم استخدم

إحدى الأفكار التي تبسّط هذا الفصل بصورة كبيرة هي أن tools و resources و prompts تتبع جميعها نمطًا متشابهًا:

```text
الاتصال (Connect)
  ↓
اكتشاف Capability المتاحة (Discover available capability)
  ↓
اختيار Capability (Select capability)
  ↓
استخدام Capability (Use capability)
  ↓
معالجة النتيجة (Process result)
```

تستخدم Discovery عادةً عملية Protocol من نوع `*/list` مغلفة داخل أسلوب SDK من نوع `list_*()`. ثم تستدعي مرحلة Use العملية المناسبة للـ primitive، مثل `call_tool()` أو `read_resource()` أو `get_prompt()`.

يتيح لك تغليف أساليب SDK داخل Application client تطبيق سلوك متسق عبر جميع primitives: فحوص الاتصال و logging و retries ودعم pagination و filtering وتحويل output.

### الإشعارات (Notifications)

يمكن لـ Servers أيضًا إرسال notifications. يستطيع Python client الاستماع إليها، مما يتيح للتطبيق التفاعل عندما تتغير capabilities أو resources بدل افتراض أن نتيجة Discovery الأولى ستظل صالحة إلى الأبد.

## 6. اكتشاف Tools واستدعاؤها

تمثل Tools قدرات قابلة للتنفيذ يمكن لـ Model اختيار استدعائها. يستطيع Client اكتشافها باستخدام استدعاء `list_tools()` في SDK.

يقدم تعريف Tool عادةً معلومات إلى Client مثل:

- الاسم (name)،
- الوصف (description)،
- input schema،
- ملاحظات (annotations).

بالنسبة إلى Model API يقبل structured tools، قد يحول Client wrapper كل MCP tool إلى بنية بسيطة تحتوي فقط على ما يتوقعه ذلك Model API.

⟦CODE_3⟧

الصيغة الدقيقة الخاصة بـ Model أقل أهمية من درس التصميم: **Wrapper هو adaptation boundary**. فهو يستطيع تحويل بيانات MCP-native إلى أي representation يحتاجها LLM المختار.

### التخزين المؤقت لقائمة Tools وإشعارات التغيير

يذكر الفصل أن SDK قد يخزن Tools المكتشفة مؤقتًا وفق TTL يتحكم فيه Server. ويمكن لـ tool-list-changed notification إبطال هذه الرؤية المخزنة مؤقتًا. وهذا سبب إضافي لعدم افتراض أن Discovery حدث لمرة واحدة طوال عمر التطبيق.

### استدعاء Tool

يستطيع Wrapper استدعاء `call_tool()` في SDK باستخدام اسم Tool و arguments. ومن المهم أن نتائج Tool قد تحتوي على أكثر من نص عادي.

يصف المصدر أنواع المحتوى المحتملة التالية:

- `TextContent` — محتوى نصي
- `ImageContent` — محتوى صورة
- `AudioContent` — محتوى صوتي
- `EmbeddedResource` — Resource مضمن

يمكن لاستدعاء واحد إرجاع **قائمة (list)** من content blocks. ويجب على Client أو Host أن يقرر هل يطبّع هذه Blocks إلى representation أبسط أم يحتفظ بأنواع المحتوى الأصلية من أجل Caller.

يعتمد هذا القرار على المستخدم. ينبغي لـ Client عام شبيه بـ SDK أن يحافظ عادةً على المرونة؛ بينما قد يفضّل Client مخصص للتطبيق تطبيع البيانات من أجل downstream Model ثابت.

### Progress و timeouts

تحتاج Tools طويلة التشغيل إلى UX جيد وحدود واضحة للفشل. يعرض الفصل progress callback يمكنه استقبال progress وقيمة total اختيارية و message، مما يسمح لـ Host بعرض progress indicator. كما يذكر read timeout لإنهاء الاستدعاءات التي تظل معلقة وقتًا طويلًا.

## 7. تحويل الوصول إلى Tools إلى agentic tool-use loop

لا يمثل اكتشاف Tool واستدعاؤها Agent كاملًا بعد. يجب أن يعيد Host ربط استخدام Tool بمحادثة LLM.

تبدو tool loop الشائعة كما يلي:

```text
1. إرسال طلب المستخدم + تعريفات Tools المتاحة إلى LLM.
2. فحص Response الخاص بـ Model. (Inspect the model response.)
3. إذا طلب Model Tool واحدة أو أكثر: (If the model asks for one or more tools:)
      a. تنفيذ كل Tool مطلوبة عبر MCP client، (execute each requested tool through the MCP client,)
      b. تغليف كل نتيجة مع tool-use ID المطابق، (package each result with the matching tool-use ID,)
      c. إلحاق نتائج Tool بـ conversation history، (append tool results to conversation history,)
      d. استدعاء LLM مرة أخرى. (call the LLM again.)
4. التكرار حتى يعيد Model response نهائيًا بدل طلب Tool أخرى. (Repeat until the model returns a final response instead of another tool request.)
```

هذه الحلقة المتداخلة مهمة لأن مهمة مستخدم واحدة قد تتطلب عدة tool calls تعتمد بعضها على بعض. فقد يحسب Model قيمة أولًا، ويفحص النتيجة، ثم يستدعي Tool أخرى قبل أن يتمكن من الإجابة.

## 8. التعامل مع الأخطاء و retries والانقطاعات

تفشل الأنظمة المعتمدة على الشبكات و subprocesses. ينبغي لـ MCP client بجودة production أن يتعامل مع ذلك بوصفه هندسة طبيعية، لا فكرة استثنائية لاحقة.

يذكر الفصل أن استدعاءات MCP الفاشلة ترفع `MCPError` الذي يحمل error code و message. ويمكن أن تكون بعض الأخطاء transient، ومنها حالات connection-closed و request-timeout. وهذا يجعل Wrapper مكانًا طبيعيًا لتنفيذ retry policy.

### فشل stdio المحلي

إذا اختفى اتصال stdio محلي على نحو غير متوقع، فربما انهارت subprocess. وقد يتطلب التعافي بدء Session جديدة وربما إعادة محاولة العملية.

### فشل Streamable HTTP البعيد

لأن Streamable HTTP عديم الحالة في نموذج الفصل، يستطيع Client نظريًا الاستمرار بإرسال Request أخرى. ومع ذلك، يشير المصدر إلى فائدة استخدام reconnect path نفسه لكلا النوعين من Transport: إذ يمكنه تحديث معلومات protocol-version المتفاوض عليها وتقليل خطر عدم التطابق بعد ترقية Server.

### استخدام `try/finally` من أجل Cleanup

عندما تمتلك run loop الخاصة بـ Agent اتصال Client، فإن تغليف Loop داخل `try/finally` يضمن قطع اتصال Client حتى عندما يخرج المستخدم أو يفلت Exception.

## 9. استخدام MCP resources بوصفها context لـ Model

تتيح Tools لـ Agent **تنفيذ أشياء**. أما Resources فتعطي Host و Model **بيانات للاستدلال عليها**.

يمكن أن تمثل Resources سجلات database و text files و images و configuration files و documentation وبيانات أخرى يوفرها Server. ويقدم الفصل عدة عمليات خاصة بـ Resource:

| العملية (Operation) | الغرض |
|---|---|
| عملية سرد Resources (`resources/list` / `list_resources()`) | اكتشاف Resources الثابتة |
| عملية سرد قوالب Resources (`resources/templates/list` / `list_resource_templates()`) | اكتشاف URI templates لـ Resources ذات العناوين الديناميكية |
| عملية قراءة Resource (`resources/read` / `read_resource()`) | قراءة البيانات من Resource URI محدد |
| سلوك الاستماع/الاشتراك (listen/subscription behavior) | React: التفاعل مع تغيّر قائمة Resources أو محتوى Resource |

### Resources مقابل resource templates

تمتلك Resource ثابتة URI محددًا. أما resource template فلديها URI pattern يُملأ بقيم. ويذكر المصدر أن كليهما يشتركان في descriptive metadata متشابهة، لكن الأولى تحمل `uri` بينما تحمل الثانية `uri_template`.

### أساليب Resource wrapper

### اختيار Resource هو context engineering

لا ينبغي عادةً أن يضع Host كل Resource متاحة داخل كل Prompt. يعرض المصدر استراتيجية واحدة: استخدام LLM لفحص User query و dictionary يحتوي أسماء Resources وأوصافها، ثم إعادة Resources التي تبدو ذات صلة فقط.

تصوريًا:

```text
metadata الخاصة بـ Resources المتاحة (Available resource metadata)
        +
طلب المستخدم (User request)
        ↓
محدد Resources (Resource selector)
        ↓
أسماء Resources المختارة (Selected resource names)
        ↓
قراءة URIs المختارة (Read selected URIs)
        ↓
إدخال المحتويات إلى Model context (Inject contents into model context)
```

يتحقق الفصل من الأسماء المختارة مقابل dictionary المعروف للـ Resources. ويساعد هذا guard البسيط على تجنب قبول اسم Resource اخترعه LLM.

### استراتيجيات اختيار أخرى صالحة

يذكر المصدر بوضوح أن استخدام LLM selector ليس سوى UX ممكن واحد. وتشمل البدائل:

- أدوات اختيار files/resources للمستخدم،
- system prompt متخصصًا يحتوي resource metadata،
- retrieval تقوده resource templates،
- تحميل مجموعة صغيرة ثابتة من Resources مقدمًا،
- prompt caching للـ context الثابت.

المفاضلة الأساسية تكون بين relevance و latency و Model calls الإضافية و token cost وتحكم المستخدم.

### إدخال Resources المختارة

يمكن إدراج text resources باعتبارها content blocks إضافية إلى جانب Message المستخدم. ويمكن تحويل image blobs إلى representation الذي يحتاجه multimodal Model إذا كان MIME type مدعومًا.

يشير الفصل إلى نقطة مهمة في بنية Message: ينبغي تجميع context الإضافي داخل بنية محتوى User message المنطقية نفسها بدل التظاهر بأن كل جزء من Context يمثل User turn جديدًا.

## 10. اكتشاف MCP prompts واستخدامها

تمثل Prompts الـ MCP primitive الرئيسية الثالثة. وفي فصل المصدر تكون Prompts عمدًا **خاضعة لتحكم المستخدم (user-controlled)**: يمكن للتطبيق عرض Prompts المتاحة على المستخدم وتركه يختار إحداها.

يمكن أن يتضمن تعريف Prompt:

- اسمًا فريدًا،
- وصفًا اختياريًا،
- صفرًا أو أكثر من arguments،
- ما إذا كان كل argument مطلوبًا.

### الـ Prompts الديناميكية (Dynamic prompts)

Prompt مكتوب مباشرة مثل:

```text
Review this Python code for bugs: ...   — Prompt ثابتة بلا معاملات
```

أقل قابلية لإعادة الاستخدام من Prompt يستقبل parameters مثل:

```text
Review the following {language} code for bugs and style issues:   — Prompt بمعاملات
{code}   — شيفرة المستخدم
```

يجمع Host قيم `language` و `code`، ثم يستدعي `get_prompt()` باستخدام هذه arguments. ويعيد Server prompt messages بعد ملئها لتكون جاهزة للإدراج في محادثة LLM بعد أي تحويل مطلوب.

### UX الخاص بـ Prompt على جانب Host

يبني المصدر تدفقًا صغيرًا حيث يقوم Host بما يلي:

1. يعرض أسماء Prompts وأوصافها،
2. يعرض arguments وما إذا كانت مطلوبة،
3. يجمع القيم من المستخدم،
4. يحمّل Prompt المملوءة من MCP server،
5. يحول محتوى Prompt المدعوم إلى LLM conversation messages.

هذا مثال جيد على الحد الفاصل بين MCP و UX الخاص بالتطبيق. يتيح MCP تعريف Prompt؛ بينما يقرر Host كيف يكتشفها المستخدم ويختارها ويملؤها.

### أنواع محتوى Prompt وأدوارها

يمكن أن تحتوي prompt messages على أكثر من text. ويذكر المصدر أنواع محتوى من text و image و audio و embedded-resource. ويمكن للتطبيق أن يختار دعم subset فقط، لكن ينبغي أن يفعل ذلك عن قصد وأن يسجل الأنواع غير المدعومة أو يرفضها.

تحمل prompt message أيضًا role. ويحذر الفصل بدقة من أن بعض Model APIs لا تستطيع بدء محادثة بـ assistant-role message. لذلك يجب على Host التحقق من prompt roles أو تكييفها مع Model API الذي يستخدمه.

## 11. مبادئ تصميم MCP client قوي

أمثلة Code في الفصل صغيرة عن قصد، لكن عدة مبادئ هندسية أوسع تظهر منها.

### 11.1 أبقِ Client مستقلًا عن Model قدر الإمكان

لا يقتصر MCP على Model provider واحد. إذا حوّل Wrapper أدوات MCP و Resources و Prompts أولًا إلى internal objects محايدة لمزود الخدمة، فيمكن لـ Host لاحقًا إضافة adapters لـ LLM APIs مختلفة.

### 11.2 صفِّ Capabilities عن قصد

لا يتعين على Client إتاحة كل capability يوفرها Server إلى Model. يمكن لـ capability filtering تحسين safety و UX وجودة tool choice.

### 11.3 افصل اهتمامات Protocol عن اهتمامات التطبيق

ينبغي لـ MCP client إدارة protocol communication. أما Host أو Agent layer فينبغي أن يمتلك user interaction و conversation logic الخاصة بـ Model و business rules، ما لم يكن لديك سبب واضح لوضعها في Wrapper.

### 11.4 احتفظ بمعلومات Type المفيدة

قد يؤدي الإفراط في normalization للمحتوى مبكرًا إلى إزالة معلومات يحتاجها التطبيق. يمكن لـ Client عام أن يعيد MCP-native resource أو content objects؛ بينما يستطيع Client متخصص تبسيطها بأمان عندما تكون توقعات جميع المستهلكين متطابقة.

### 11.5 صمّم مع توقع الفشل

تُعد connection checks و timeouts و retries و logging و cleanup المضمون متطلبات عادية في هندسة البرمجيات. ولا تلغيها Agentic software.

### 11.6 حدّث Server capabilities القابلة للتغير

يمكن أن تتغير Tools و Resources و Prompts. تساعد TTLs و list-change notifications و refresh commands وإعادة Discovery الصريحة جميعها في منع Host من العمل اعتمادًا على capability metadata قديمة.

### 11.7 راقب تكلفة استراتيجيات اختيار Context

يمكن لاستخدام LLM call إضافي لاختيار Resources أن يحسن relevance، لكنه يضيف cost و latency. ينبغي أن يراعي context engineering كلًا من جودة Model وكفاءة النظام.

## مفاهيم خاطئة مهمة

### الاعتقاد الخاطئ 1: 'LLM provider SDK client هو MCP client.'

**لماذا هذا خطأ:** يتواصل Provider client مع Language Model API. بينما يتواصل MCP client مع MCP server. وينسّق Host application بين الاثنين.

### الاعتقاد الخاطئ 2: 'يمكن لـ MCP client instance واحدة التحدث إلى كل Server.'

**لماذا هذا خطأ:** في تصميم فصل المصدر، ترتبط Client instance واحدة باتصال Server واحد. ولذلك تتطلب عدة Servers عدة Client instances.

### الاعتقاد الخاطئ 3: 'استدعاء `list_tools()` مرة واحدة يكفي إلى الأبد.'

**لماذا هذا خطأ:** يمكن أن تتغير Server capabilities، وتنتهي صلاحية caches، كما يمكن لإشعارات التغيير إبطال القوائم السابقة.

### الاعتقاد الخاطئ 4: 'نتائج Tool دائمًا strings.'

**لماذا هذا خطأ:** قد تعيد tool calls نصًا أو صورًا أو صوتًا أو embedded resources أو عدة content blocks.

### الاعتقاد الخاطئ 5: 'يجب عرض نتيجة Tool على المستخدم فورًا.'

**لماذا هذا خطأ:** في agentic loop، تعود نتائج Tool عادةً إلى LLM أولًا حتى يقرر ما إذا كانت هناك حاجة إلى actions أخرى وينتج response النهائي الموجه للمستخدم.

### الاعتقاد الخاطئ 6: 'ينبغي دائمًا تحميل Context أكثر.'

**لماذا هذا خطأ:** تستهلك Resources غير ذات الصلة tokens وقد تجعل reasoning أسوأ. تحميل Resources هو مفاضلة بين relevance و latency و cost.

### الاعتقاد الخاطئ 7: 'يلغي MCP الحاجة إلى أمان البرمجيات المعتاد.'

**لماذا هذا خطأ:** ما تزال API keys و authentication و transport security و origin validation و timeouts و safe cleanup مهمة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| تطبيق المضيف (Host application) | تطبيق يعتمد على LLM ويحتوي MCP client واحدًا أو أكثر |
| عميل مزود LLM (LLM provider client) | SDK/client يُستخدم للتواصل مع API الخاص بمزود Model |
| عميل MCP (MCP client) | مكوّن يتواصل مع MCP server ويتيح capabilities الخاصة به إلى Host |
| غلاف Client (Client wrapper) | class خاص بالتطبيق يوضع حول SDK client لإضافة guardrails و translation و logging والتحكم في lifecycle |
| `stdio` — Transport محلي | Transport محلي يستخدم standard input/output الخاص بـ Server subprocess |
| Streamable HTTP — Transport بعيد | Transport بعيد stateless للتواصل مع MCP servers المستضافة |
| `AsyncExitStack` — أداة Python | أداة Python لإدارة عدة asynchronous context managers و cleanup بصورة ديناميكية |
| اكتشاف القدرات (Capability discovery) | سرد tools و resources و prompts أو الخصائص الأخرى التي يوفّرها Server |
| الأداة (Tool) | capability قابلة للتنفيذ على Server يمكن لـ Model اختيار استدعائها |
| `input_schema` — بنية arguments | تعريف منظم للـ arguments التي تقبلها Tool |
| حلقة استخدام Tool (Tool-use loop) | دورة متكررة LLM → tool call → result → LLM حتى ينتج Model إجابة نهائية |
| Progress callback — دالة تقدم | async function تُستدعى عندما تبلغ Tool طويلة التشغيل عن progress |
| MCPError — نوع خطأ | نوع Error يصفه المصدر لاستدعاءات MCP الفاشلة، ويتضمن معلومات code و message |
| المورد (Resource) | بيانات يوفرها Server ويمكن عنونتها بواسطة URI |
| قالب Resource (Resource template) | URI pattern يمكن ملؤه ديناميكيًا لتحديد Resources |
| اختيار Resource (Resource selection) | عملية تحديد Resources ذات الصلة الكافية لتحميلها إلى Context |
| Prompt — تعريف Message قابل لإعادة الاستخدام | تعريف Model message قابل لإعادة الاستخدام يوفّره Server |
| Dynamic prompt — Prompt ديناميكية | Prompt تُملأ placeholders الخاصة بها من arguments يقدّمها المستخدم أو التطبيق |
| تصفية القدرات (Capability filtering) | اختيار Server capabilities التي سيتيحها Host فعليًا |
| الاستقلال عن Model (Model agnosticism) | تصميم Client بحيث يمكنه دعم أكثر من LLM provider |
