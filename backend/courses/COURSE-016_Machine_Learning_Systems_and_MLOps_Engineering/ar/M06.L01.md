## 1. اختيار Model قرار على مستوى System

عندما تصل إلى مرحلة Modeling، توجد عادةً Algorithms كثيرة يمكنها حل Task نفسها. التحدي ليس العثور على *Algorithm* ما؛ بل اختيار مجموعة صغيرة من Candidates تناسب Task وقيود Production.

بالنسبة إلى Text classification problem، قد تشمل Candidates Logistic regression و Naive Bayes و Recurrent networks أو Transformer-based models. وبالنسبة إلى Anomaly detection، قد تشمل Candidates Nearest-neighbor methods و Isolation forests و Clustering أو Neural networks.

يؤكد الفصل أن اختيار Model ينبغي أن يأخذ في الاعتبار أكثر من Predictive performance:

| السؤال | لماذا يهم |
|---|---|
| ما مقدار Labeled data التي تحتاجها؟ | بعض Model families تحتاج Data أكثر بكثير. |
| ما تكلفة Training؟ | تؤثر Training cost في سرعة Iteration والميزانية. |
| ما سرعة Inference؟ | قد تحدد Latency ما إذا كانت Model قابلة للاستخدام Online. |
| ما مقدار Hardware الذي تحتاجه؟ | قد تكون Model المعتمدة على GPU مكلفة تشغيليًا. |
| ما مدى قابليتها للتفسير؟ | تحتاج بعض Applications إلى Explanations. |
| ما مدى سهولة Deployment؟ | تعقيد Production مهم. |

قد تكون Logistic regression بسيطة أقل Accuracy من Neural network كبيرة، ومع ذلك تكون أفضل First production model إذا كانت سريعة ورخيصة وقابلة للتفسير وسهلة Deployment.

## 2. ست نصائح عملية لاختيار Models

### النصيحة 1: تجنب فخ State of the art

قد تكون Model هي State of the art لأنها تحقق أفضل Performance على Static benchmark محددة. لكن هذا لا يثبت أنها سريعة بما يكفي أو منخفضة التكلفة بما يكفي أو سهلة الصيانة بما يكفي أو حتى أفضل على Data الخاصة بك.

إذا كان حل أبسط يحقق Real requirements، فاستخدم الحل الأبسط.

### النصيحة 2: ابدأ بأبسط Model مفيدة

تكون Models البسيطة مفيدة لأنها:

1. أسهل في Deployment مبكرًا،
2. أسهل في الفهم و Debugging،
3. توفر Baseline للـ Models الأكثر تعقيدًا.

يوضح الفصل تمييزًا مهمًا: **Simple** ليست دائمًا هي نفسها **Low effort**. قد تكون Pretrained complex model سهلة البدء لأن Tooling و Community support ناضجة. ومع ذلك، يستحق الأمر اختبار Alternatives أبسط حتى تعرف ما إذا كان Complexity مبررًا.

### النصيحة 3: تجنب Human bias في المقارنات

إذا نفذ Engineer مئة Experiment على Architecture واحدة وتجربتين فقط على Architecture أخرى، فالمقارنة ليست عادلة. ينبغي تقييم Model families باستخدام Effort و Data و Metrics و Tuning budgets متقاربة.

### النصيحة 4: قيّم Good performance الآن مقابل لاحقًا

قد تفوز Model اليوم ثم تخسر بعد وصول Data إضافية.

تعرض **Learning curve** أداء Model مقابل كمية Training data. وقد تكشف ما إذا كانت Data إضافية مرجح أن تساعد.

ويعطي الفصل أيضًا Example لـ Recommender model خسرت Offline في البداية، لكنها استطاعت التحديث باستمرار ثم تفوقت في النهاية على Winner الأولى.

[[IMAGE_NEEDED: Learning curves for two model families | A plot of validation performance versus number of training examples for a simple model and a higher-capacity model, where the simple model starts stronger but the higher-capacity model continues improving | Learner should notice that the best model today may not be the best model after more data arrives]]

### النصيحة 5: قيّم Trade-offs المهمة

تشمل Examples:

- False positives مقابل False negatives،
- Compute مقابل Accuracy،
- Latency مقابل Model complexity،
- Interpretability مقابل Predictive performance.

تعتمد Trade-off الصحيحة على Application. ففي Fingerprint unlocking، قد تمنح False positive وصولًا إلى User غير مصرح لها. وفي Disease screening، قد تفوّت False negative مريضًا.

### النصيحة 6: افهم Model assumptions

كل Model تقرّب Reality باستخدام Assumptions. تشمل Examples التي يناقشها الفصل:

- **Prediction assumption:** يمكن Predict للـ `Y` من `X`.
- **IID:** يتم سحب Examples بصورة مستقلة من Distribution نفسها.
- **Smoothness:** تميل Inputs المتشابهة إلى Outputs متشابهة.
- **Tractability:** حسابات Probability المطلوبة قابلة للتنفيذ.
- **Linear boundaries:** تفترض Linear classifiers حدود Decision خطية.
- **Conditional independence:** تفترض Naive Bayes أن Features مستقلة بالنظر إلى Class.
- **Normality:** تفترض بعض Statistical methods أن Data موزعة بصورة Normal.

قد تفشل Model ليس لأنها سيئة Implementation، بل لأن World تنتهك Assumption تعتمد عليها Model.

## 3. Ensembles: ادمج Models بدلًا من الثقة في Model واحدة

تجمع Ensemble تنبؤات عدة **Base learners**.

بالنسبة إلى Classification، قد تستخدم Ensemble بسيطة Majority vote. وبالنسبة إلى Regression، قد تستخدم Average للـ Predictions.

يقدم المصدر Intuition مفيدة. لنفترض أن لدينا ثلاث Classifiers، كل منها Accuracy تساوي 70%، وتخطئ بصورة مستقلة. تكون Ensemble صحيحة عندما تكون Modelان على الأقل صحيحتين:

```text
P(all 3 correct) = 0.7³ = 0.343 — احتمال أن تكون Models الثلاث صحيحة
P(exactly 2 correct) = 3 × 0.7² × 0.3 = 0.441 — احتمال أن تكون Modelان فقط صحيحتين

Ensemble accuracy = 0.343 + 0.441 = 0.784 — Accuracy الخاصة بـ Ensemble
```

إذًا يمكن لثلاث Models مستقلة كل منها Accuracy تساوي 70% أن تحقق Majority-vote accuracy مقدارها 78.4%.

Assumption الخاصة بالاستقلال مهمة. إذا ارتكبت Models الثلاث الأخطاء نفسها تمامًا، فلن تحقق Ensembling أي Gain. وتكون Diversity بين Base learners ذات قيمة.

Trade-off تشغيلية هي أن Ensembles أكثر تعقيدًا في Deployment و Maintenance.

## 4. Bagging و Boosting و Stacking

### Bagging

تعني **Bagging** عبارة Bootstrap aggregating.

1. أنشئ عدة Bootstrap datasets عبر Sampling with replacement.
2. درّب Learner واحدة على كل Bootstrap.
3. ادمج Predictions باستخدام Vote أو Averaging.

يمكن لـ Bagging تقليل Variance وتحسين Stability. وتعد Random forests مثالًا مألوفًا: فهي تجمع Bootstrap sampling مع Randomness في Features المتاحة.

[[IMAGE_NEEDED: Bagging workflow | One original dataset branching into several bootstrap samples, each training a model, with model outputs merged by majority vote or averaging | Learner should notice that learners are trained independently on different resampled datasets]]

### Boosting

تدرّب Boosting الـ Learners بصورة Iterative. وتركز Learners اللاحقة بصورة أكبر على Examples التي تعاملت معها Learners السابقة بصورة ضعيفة.

مفاهيميًا:

```text
Train learner 1 — درّب Learner الأولى
      ↓
Increase weight on its mistakes — زد Weight للأخطاء
      ↓
Train learner 2 — درّب Learner الثانية
      ↓
Focus again on remaining difficult examples — ركّز على Examples الصعبة المتبقية
      ↓
Combine learners into a stronger predictor — ادمج Learners في Predictor أقوى
```

تمثل Gradient boosting machines Family مهمة، مع Implementations مثل XGBoost و LightGBM التي يناقشها الفصل.

### Stacking

تدرّب Stacking عدة Base learners ثم تستخدم **Meta-learner** لدمج Outputs الخاصة بها.

قد تكون Meta-learner عبارة عن Voting/Averaging بسيط أو Learned model أخرى مثل Logistic regression.

[[IMAGE_NEEDED: Bagging versus boosting versus stacking | A three-panel comparison: independent bootstrapped models for bagging, sequential error-focused learners for boosting, and parallel base models feeding a meta-model for stacking | Learner should notice the different way each ensemble creates and combines diversity]]

## 5. تتبع Experiments وإجراء Versioning لها

تطوير Model عملية تجريبية. قد تختلف Runان بـ Hyperparameter واحدة فقط، ومع ذلك تنتجان Outcomes مختلفة جدًا.

يسجل **Experiment tracking** ما حدث أثناء Run.  
ويسجل **Versioning** ما يكفي من تعريف Experiment لمقارنتها أو إعادة إنشائها لاحقًا.

تشمل الأشياء المفيدة التي ينبغي تتبعها:

- Train و Validation loss curves،
- Metrics مثل Accuracy و F1 أو Perplexity،
- Example inputs و Predictions و Ground Truth labels،
- Training speed،
- CPU/GPU utilization و Memory،
- Learning rate بمرور الوقت،
- Gradient norms،
- Weight norms،
- Logs و Intermediate artifacts.

يحسن Tracking الـ Observability داخل Learning process ويساعد على تفسير سبب اختلاف Behavior بين Run وأخرى.

### نفّذ Versioning لأكثر من Code

تعتمد ML systems على **Code و Data**، ولذلك تحتاج Reproducibility إلى الاثنين.

تكون Data versioning أصعب من Code versioning لأن Datasets كبيرة وقد لا تتسع على Local machines ولا تتمثل طبيعيًا كـ Line-by-line text diffs.

وقد تجعل Privacy regulations الاحتفاظ بـ Old data versions إلى أجل غير مسمى مستحيلًا إذا وجب حذف User data لاحقًا.

حتى Tracking القوي لا يضمن Reproducibility مطابقة تمامًا، لأن Hardware و ML frameworks قد تضيف Nondeterminism.

## 6. Debugging للـ ML models

يكون ML debugging صعبًا بصورة غير معتادة لثلاثة أسباب:

1. **قد تكون Failures صامتة.** تعمل Code وتُعاد Predictions، لكنها خاطئة.
2. **Validation بطيئة.** قد تتطلب Fix مشتبه بها إعادة Training لعدة ساعات.
3. **Systems متعددة التخصصات.** قد توجد المشكلة في Data أو Labels أو Features أو Model code أو Hyperparameters أو Infrastructure.

تشمل مصادر Failure المحتملة:

- انتهاك Theoretical assumptions،
- Implementation bugs،
- Hyperparameters ضعيفة،
- مشكلات Data أو Labels،
- Preprocessing statistics قديمة،
- اختيارات Features سيئة.

يوصي الفصل بعادات Debugging وقائية وعلاجية.

### تقنية Debugging رقم 1: ابدأ ببساطة

ابنِ أصغر Version معقولة أولًا. أضف Complexity مكونًا واحدًا في كل مرة. إذا انهار Performance بعد إضافة Component، تصبح Search space الخاصة بالـ Bug صغيرة.

### تقنية Debugging رقم 2: نفّذ Overfit لـ Tiny batch واحدة

خذ مجموعة صغيرة جدًا من Examples ودرّب/قيّم على Examples نفسها. ينبغي أن تتمكن Model من Memorize لها تقريبًا.

إذا لم تستطع Image classifier الوصول إلى Training accuracy شبه كاملة على عشرة Examples، فقد توجد Bug في Implementation أو Training procedure.

### تقنية Debugging رقم 3: ثبّت Random seed

تضيف Random initialization و Dropout و Shuffling اختلافًا بين Runs. يجعل تثبيت Seed المقارنات أكثر تحكمًا، ويجعل Failures أسهل في Reproduce.

## 7. Distributed training وقيود Memory

قد تكون Modern models و Datasets كبيرة جدًا بالنسبة إلى Machine واحدة.

عندما لا تتسع Dataset في Memory، فقد تحتاج Preprocessing و Shuffling و Batching إلى Out-of-core و Parallel techniques.

وأحيانًا تكون Model نفسها أو حتى Sample واحدة كبيرة جدًا. يناقش الفصل **Gradient checkpointing**، التي تستبدل Memory أقل بمزيد من Computation.

### التوازي على Data (Data parallelism)

يخزن كل Worker نسخة من Model، ويتلقى Subset مختلفة من Data، ويحسب Gradients، ويسهم في Parameter updates.

يناقش الفصل أسلوبين للـ Updates:

- **Synchronous SGD:** انتظر كل Workers قبل Update.
- **Asynchronous SGD:** نفّذ Update بمجرد وصول Gradients.

قد تعاني Synchronous training من **Stragglers**: Worker بطيئة واحدة تؤخر الجميع.

وقد تعاني Asynchronous training من **Gradient staleness**: ربما تم حساب Gradient باستخدام Weights تغيرت بالفعل.

كما تغير Distributed batch sizes الكبيرة جدًا Optimization behavior. قد يقلل Batch size الأكبر عدد Update steps، لكنه يصل في النهاية إلى Diminishing returns وقد يتطلب ضبط Learning rate بعناية.

### التوازي على Model (Model parallelism)

تعيش أجزاء مختلفة من Model واحدة على Machines مختلفة.

هذا مفيد عندما لا تتسع Model على Device واحدة. لكن مجرد وضع Layers مختلفة على Machines مختلفة لا يضمن Parallel execution حقيقية إذا كان على Layers اللاحقة انتظار السابقة.

### التوازي على Pipeline (Pipeline parallelism)

تقسم Pipeline parallelism الـ Mini-batch إلى Micro-batches، بحيث تعمل Machines مختلفة على Stages مختلفة في الوقت نفسه.

[[IMAGE_NEEDED: Data, model, and pipeline parallelism | Three diagrams: replicated models processing different data shards, one model split across machines, and micro-batches flowing through model stages like an assembly line | Learner should notice what is split in each strategy: data, model components, or staged computation]]

يمكن أيضًا دمج Data parallelism و Model parallelism، لكن Engineering تصبح أكثر تعقيدًا.

## 8. AutoML: أتمتة أجزاء من تطوير Model

تعني AutoML بصورة عامة أتمتة Search عن Model configurations التي تحل Task.

### Soft AutoML: ضبط Hyperparameters

تشمل Hyperparameters اختيارات مثل:

- Learning rate،
- Batch size،
- عدد Hidden layers،
- Hidden width،
- Dropout probability،
- Optimizer parameters،
- Numeric precision أو Quantization choices.

تشمل Search methods الشائعة:

- Grid search،
- Random search،
- Bayesian optimization.

تؤثر بعض Hyperparameters في Performance بدرجة أكبر بكثير من غيرها، ولذلك تستحق Search أدق.

> **لا تنفذ Tuning للـ Hyperparameters على Test set أبدًا.** استخدم Validation performance للـ Tuning، واحتفظ بـ Test split للتقدير النهائي.

### Hard AutoML: البحث عن Architecture

تعامل Neural architecture search الاختيارات المعمارية بوصفها Variables يجري Search عليها.

يتكون NAS system من ثلاثة أجزاء رئيسية:

1. **Search space** — Building blocks و Combinations الممكنة.
2. **Performance estimation strategy** — تقدير Quality الخاصة بـ Candidate دون Training كاملة لكل Candidate.
3. **Search strategy** — استكشاف Candidate architectures.

قد تشمل Search strategies Random search أو Reinforcement learning أو Evolutionary methods.

### Optimizers متعلمة (Learned optimizers)

يقدم الفصل أيضًا فكرة استبدال Hand-designed update rule بـ Learned model تقرر كيفية Update للـ Weights.

قد تكون هذه Approaches مكلفة جدًا في Development، لكن Results الناجحة قد تصبح قابلة لإعادة الاستخدام عبر Tasks كثيرة.

## 9. أربع مراحل لتطوير Model

يقدم الفصل Progression مفيدة لتبني ML.

### المرحلة 1: قبل Machine Learning

ابدأ بـ Heuristic أو Non-ML solution. هذا يثبت Baseline وقد يكون جيدًا بما يكفي أصلًا.

مثال: Predict للحرف التالي المكتوب باستخدام أكثر English letters شيوعًا.

### المرحلة 2: أبسط ML models

جرّب Models سهلة الفحص و Deployment، مثل Logistic regression أو Nearest-neighbor methods أو Gradient-boosted trees اعتمادًا على Problem.

الهدف هو التحقق من End-to-end ML framework و Problem framing.

### المرحلة 3: حسّن Models البسيطة

حسّن باستخدام:

- Objective functions أفضل،
- Hyperparameter search،
- Feature engineering،
- Data أكثر،
- Ensembles.

### المرحلة 4: Models معقدة

لا تستثمر في Models أكثر تعقيدًا بدرجة كبيرة إلا بعد وصول Approaches الأبسط إلى Useful limit الخاصة بها.

وينبغي أيضًا دراسة سرعة Decay الخاصة بـ Models بعد Deployment حتى تستطيع Infrastructure دعم Retraining cadence المطلوبة.

## 10. Offline evaluation تحتاج Context، لا أرقامًا معزولة

بعد أن تمتلك Candidate models، تحتاج إلى تحديد أيها مناسبة للـ Production.

غالبًا لا تعني Metric value شيئًا بمفردها. قد تبدو F1 score مقدارها 0.90 مثيرة للإعجاب، لكن إذا حققت Random baseline أو Majority baseline بسيطة Score مشابهة، فقد تضيف Model Value قليلة.

لا تستطيع Offline evaluation التنبؤ بصورة مثالية بـ Production behavior لأن Development environments غالبًا تحتوي Labels و Data أنظف مما يوجد في Production.

مع ذلك، تستطيع Offline evaluation الجيدة استبعاد Models ضعيفة أو غير آمنة قبل Deployment.

## 11. خمس Baselines مفيدة

### Baseline عشوائية (Random baseline)

ماذا يحدث إذا كانت Predictions عشوائية؟

قد تتبع Random predictions Uniform distribution أو Observed label distribution.

### Heuristic بسيطة

ما Performance التي تستطيع Hand-written rule تحقيقها دون ML؟

بالنسبة إلى Newsfeed، قد ترتب Heuristic بسيطة أحدث Items أولًا.

### Baseline باسم Zero-rule

تنبأ دائمًا بـ Most common class أو Most common outcome.

إذا كانت التوصية بأكثر App استخدامًا لدى User تحقق أصلًا Accuracy مقدارها 70%، فينبغي لـ Complex model أن تحسن بما يكفي لتبرير Cost الإضافية.

### Baseline بشرية (Human baseline)

إذا كانت ML system تؤتمت أو تساعد Human work، فقارنها بأداء Human ذي صلة.

### الحل الحالي (Existing solution)

قارن مع Business rules الحالية أو Third-party system أو Incumbent model.

لا تحتاج ML model جديدة دائمًا إلى Raw accuracy أعلى كي تكون مفيدة. فقد تظل أفضل إذا كانت أرخص أو أسرع أو أسهل في التشغيل.

وهذا يقود إلى تمييز مهم:

> **Model الجيدة ليست تلقائيًا System مفيدة، وقد تظل Model غير مثالية تقنيًا مفيدة عمليًا.**

## 12. اختبارات Perturbation و Invariance و Directional expectation

Average metrics لا تكفي. ينبغي لـ Production models أيضًا أن تتصرف بصورة منطقية عندما تتغير Inputs.

### اختبارات Perturbation

نفّذ تغييرات صغيرة وواقعية على Evaluation inputs وقِس Performance degradation.

بالنسبة إلى Audio model، أضف Background noise أو حرّك Recording قليلًا. وبالنسبة إلى Images، غيّر Lighting أو أضف Noise صغيرة. وبالنسبة إلى Text، حاكِ Typos أو Input variations أخرى معقولة.

قد تكون Model شديدة الحساسية لتغييرات صغيرة وواقعية صعبة الصيانة في Production.

### اختبارات Invariance

بعض التغييرات **ينبغي ألا تغير** Prediction.

تشمل Examples تغيير Name أو Gender marker أو Sensitive attribute أخرى عندما لا ينبغي أن تؤثر هذه Attribute في Decision.

إذا تغير Output عندما ينبغي أن يبقى ثابتًا، فافحص Bias أو Shortcut learning.

### اختبارات Directional expectation

بعض التغييرات **ينبغي أن تغير** Output بصورة متوقعة.

بالنسبة إلى Housing-price model، إذا بقي كل شيء آخر ثابتًا وزاد Lot size، فلا ينبغي أن تنخفض Predicted value إذا كانت Domain expectations تقول إن العلاقة ينبغي أن تكون Monotonic.

[[IMAGE_NEEDED: Three behavioral model tests | Three panels showing realistic perturbation with expected stability, a sensitive attribute swap with an unchanged expected prediction, and a meaningful feature increase with an expected directional output change | Learner should notice that evaluation can test behavior, not just aggregate accuracy]]

## 13. معايرة Model (Model calibration)

تكون Probabilistic model **Calibrated** عندما تتوافق Predicted probabilities مع Observed frequencies.

إذا تنبأت Model مرارًا بـ Probability مقدارها 70% لـ Event ما، فينبغي أن يحدث هذا Event في نحو 70% من الحالات.

يمكن لـ Model ترتيب Items بصورة صحيحة ومع ذلك تكون Calibration ضعيفة.

مثال:

```text
Ad A predicted click probability: 10% — Probability المتوقعة للنقر على Ad A
Ad B predicted click probability:  8% — Probability المتوقعة للنقر على Ad B
```

قد يكون Ranking `A > B` صحيحًا حتى إذا كانت Real click rates تساوي 5% و4%. لكن إذا استخدمت هذه Numbers لتوقع Total clicks أو Revenue، فتصبح Miscalibration مهمة.

### منحنى Calibration

اجمع Predictions حسب Predicted probability وقارن Predicted probability مع Observed frequency.

تتبع Model ذات Calibration المثالية:

```text
predicted probability = observed frequency — Probability المتوقعة تساوي Frequency المرصودة
```

يذكر الفصل Platt scaling بوصفها Method واحدة للـ Calibration.

[[IMAGE_NEEDED: Calibration curve | A probability calibration plot with a diagonal perfect-calibration line and one model curve above/below it | Learner should notice that calibration measures whether probability values themselves are trustworthy, not merely whether ranking is correct]]

## 14. Confidence أداة لاتخاذ Decision لكل Prediction

تلخص System-level metrics الـ Average behavior. أما Confidence reasoning فتسأل ما إذا كانت **هذه Prediction الفردية** موثوقة بما يكفي للتصرف بناءً عليها.

إذا كانت Model غير متأكدة، فقد تشمل Responses المحتملة:

- عدم إظهار Prediction،
- سؤال User عن Information إضافية،
- إرسال Case إلى Human،
- Fallback إلى Rule-based method أكثر أمانًا.

ينشئ ذلك سؤال Design عمليًا:

> ما Confidence threshold التي ينبغي أن تطلق Automated action؟

يمكن لـ System مفيدة أن تتعمد Abstain على Uncertain examples بدلًا من إجبار نفسها على Prediction في كل مرة.

## 15. التقييم حسب Slices (Slice-based evaluation)

تعني **Slicing** تقييم Performance الخاصة بـ Model على Subsets ذات معنى من Data.

لنفترض أن 90% من Data تنتمي إلى Majority group.

| Model | Accuracy للفئة الأكبر | Accuracy للفئة الأصغر | Accuracy الإجمالية |
|---|---:|---:|---:|
| A | 98% | 80% | 96.2% |
| B | 95% | 95% | 95% |

إذا نظرت فقط إلى Overall accuracy، تبدو Model A أفضل. لكن النظر إلى Slices يكشف أن Model A تعمل بصورة أسوأ بكثير للفئة الأصغر.

وأحيانًا لا تكون Equal performance عبر Slices هي Goal أصلًا. فقد تكون بعض Slices أكثر أهمية للـ Business. وبالنسبة إلى Churn prediction، قد يستحق Paid users تدقيقًا أكبر من Nonpaying users.

### مفارقة Simpson (Simpson's paradox)

قد تنعكس Aggregate trends مقارنة بـ Subgroup trends. ويعطي المصدر Example تعمل فيها Model واحدة بصورة أفضل داخل كل Group، بينما تبدو Model أخرى أفضل بعد دمج Groups.

الدرس ليس أن Simpson's paradox ستحدث دائمًا، بل أن **Aggregation قد تخفي Structure مهمة**.

[[IMAGE_NEEDED: Aggregate metric versus slice metrics | A large overall accuracy bar beside separate majority/minority bars for two models, showing how the model with the best overall score can perform poorly on one subgroup | Learner should notice that aggregate metrics can hide critical weaknesses]]

## 16. كيف تكتشف Critical slices

يصف الفصل ثلاث Approaches.

### Slicing اعتمادًا على Heuristics

استخدم Domain knowledge. بالنسبة إلى Web traffic، قد تشمل Slices مفيدة:

- Mobile مقابل Desktop،
- Browser type،
- Geographic location.

### تحليل الأخطاء (Error analysis)

افحص Failures يدويًا وابحث عن Patterns متكررة.

يعطي المصدر Example كان فيها Poor mobile performance ناتجًا في النهاية عن مشكلة Interface غير مرتبطة بالـ ML: Button كانت مخفية جزئيًا على Small screens.

### الاكتشاف الآلي للـ Slices

يمكن لـ Research systems إنشاء Candidate slices باستخدام Search أو Clustering أو Decision-based methods، ثم Prune و Rank للـ Candidates الأكثر إثارة للاهتمام.

أياً كانت Method المستخدمة، يحتاج Slice evaluation إلى Evaluation data مصنفة بصورة صحيحة وبكمية كافية لكل Slice. وتظل Quality الخاصة بالتحليل محدودة بجودة Slice data نفسها.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: State of the art تعني الأفضل للـ Production

Benchmark leadership لا تخبرك إلا بالقليل عن Latency أو Compute أو Cost أو Maintenance أو Data constraints الخاصة بك.

### المفهوم الخاطئ 2: أكثر Model تعقيدًا هي أفضل نقطة بداية

البدء ببساطة يمنحك Baseline قابلة للـ Deployment ومسار Debugging أسهل بكثير.

### المفهوم الخاطئ 3: Ensemble تحسن Performance دائمًا

قد ترتكب Base learners شديدة الترابط الأخطاء نفسها، فتختفي فائدة Ensemble.

### المفهوم الخاطئ 4: تتبع Hyperparameters يكفي للـ Reproducibility

قد تحتاج أيضًا إلى Code و Data و Environment و Framework و Hardware و Random seed و Artifacts.

### المفهوم الخاطئ 5: انخفاض Loss يثبت أن ML system صحيحة

قد تفشل ML systems بصمت حتى عندما تبدو Training طبيعية.

### المفهوم الخاطئ 6: ينبغي Tuning للـ Hyperparameters على Test set

Validation split هي المستخدمة للـ Tuning. وينبغي الاحتفاظ بـ Test split للتقييم النهائي.

### المفهوم الخاطئ 7: Metric مرتفعة واحدة Offline تثبت Production readiness

تحتاج Models أيضًا إلى Baselines مفيدة و Robustness checks و Calibration عندما تكون Probabilities مهمة و Slice analysis.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| منحنى التعلم (Learning curve) | Performance مرسومة مقابل كمية Training data. |
| Base learner | Model فردية داخل Ensemble. |
| Bagging | تدريب Learners مستقلة على Bootstrap samples ثم Aggregate للـ Predictions. |
| Boosting | تدريب Learners بصورة Sequential مع تركيز أكبر على أخطاء Learners السابقة. |
| Stacking | دمج Outputs الخاصة بـ Base models باستخدام Meta-learner. |
| تتبع Experiments (Experiment tracking) | تسجيل Metrics و States و Artifacts وتقدم Training runs. |
| Versioning | تسجيل تعريفات Experiment و Dependencies من أجل المقارنة أو إعادة الإنشاء. |
| Artifact | File تنتجها Experiment مثل Logs أو Curves أو Checkpoints أو Outputs. |
| Overfit a batch | Debugging test تُطلب فيها من Model Memorize تقريبًا لـ Tiny training subset. |
| التوازي على Data (Data parallelism) | Replicate للـ Model وتقسيم Data بين Workers. |
| التوازي على Model (Model parallelism) | تقسيم Model components بين Workers. |
| التوازي على Pipeline (Pipeline parallelism) | استخدام Micro-batches لتداخل Computation عبر Model stages. |
| Straggler | Worker بطيئة تؤخر Synchronous distributed training. |
| Gradient staleness | Gradient محسوبة باستخدام Model parameters أقدم في Asynchronous training. |
| AutoML | أتمتة Search على Models أو Hyperparameters. |
| NAS | البحث عن البنية العصبية (Neural architecture search). |
| Baseline | Reference solution تُستخدم لتفسير Metric الخاصة بـ Model. |
| اختبار Perturbation | اختبار Stability الخاصة بـ Model تحت تغييرات واقعية صغيرة في Input. |
| اختبار Invariance | اختبار أن تغييرات Input غير المهمة أو Sensitive لا تغير Output. |
| Directional expectation | اختبار أن تغير Input يحرك Prediction في اتجاه متوقع. |
| Calibration | توافق Predicted probabilities مع Observed event frequencies. |
| Confidence threshold | Threshold لكل Prediction لتقرير ما إذا كانت Automated action مبررة. |
| تقييم قائم على الشرائح (Slice-based evaluation) | تقييم Performance على Subsets ذات معنى من Data. |
| مفارقة Simpson (Simpson's paradox) | Aggregate trends تختلف عن Subgroup trends أو تعكسها. |
