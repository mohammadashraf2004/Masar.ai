## 1. قد تصبح Model المنشورة خاطئة من دون أن يتعطل النظام

يبدأ الفصل بنظام Forecasting للمخزون كان يعمل جيدًا عند نشره، لكنه أصبح أقل فائدة بمرور الوقت. بدأ يبالغ في تقدير بعض Products ويقلل تقدير أخرى، ما تسبب في Inventory منتهية الصلاحية ومبيعات مفقودة.

الدرس أساسي:

> **Deployment ليست نهاية دورة حياة ML.**

توجد Model داخل Environment متغيرة. يمكن أن يتغير User behavior و Markets و Products و Application interfaces و Data pipelines و Business processes كلها بعد Training.

لذلك تحتاج Production system إلى Loop مستمرة:

```text
Deployment
  ↓
Monitoring
  ↓
اكتشاف التدهور أوAnomalies
  ↓
التحقيق في Root cause
  ↓
تحديث / إعادة Training / إصلاح النظام
  ↓
Deployment مرة أخرى
```

## 2. ما الذي يُعد Failure في ML system؟

تحدث Failure عندما يخالف النظام واحدًا أوأكثر من Expectations.

في Traditional software تكون Expectations غالبًا Operational:

- Latency،
- Throughput،
- Availability،
- Successful responses،
- Resource usage.

تمتلك ML systems هذه **بالإضافة إلى Predictive expectations**.

تخيل English-to-French translation service.

Operational expectation:

```text
أعد Response خلال 1 ثانية.
```

ML-performance expectation:

```text
أعد Translation دقيقة عند مستوى الجودة المطلوب.
```

إذا انتهت Service بمهلة Timeout، تكون Failure واضحة. أما إذا أعادت Translation سلسة لكنها خاطئة، فقد تبدو Service سليمة رغم أن ML behavior خاطئة.

لهذا يقول الفصل إن أنظمة ML كثيرًا ما **تفشل بصمت**.

## 3. Software failures مقابل ML-specific failures

### إخفاقات أنظمة البرمجيات

يمكن أن تحدث هذه في أي Software system:

- Dependency failure،
- نشر Binary أو Model version خاطئة،
- Permission errors،
- Hardware failures،
- Server downtime،
- Orchestration failures،
- أخطاء الـ pipeline الخاص بالبيانات.

يشير الفصل إلى أن كثيرًا من Failures الحقيقية داخل ML pipelines تأتي من مشكلات Software و Distributed systems عادية، لا من Learning algorithm نفسها.

### ML-specific failures

تشمل أمثلة ذلك:

- Poor أو Changed data collection،
- Label problems،
- Hyperparameters غير مناسبة،
- Training-serving inconsistencies،
- Data distribution shifts،
- Edge cases،
- حلقات Feedback المنحطة (Degenerate).

يهم هذا التمييز لأن أنواع Failure المختلفة تحتاج Debugging skills مختلفة.

## 4. لماذا تختلف Production data عن Training data؟

تتعلم Model أنماطًا من Training distribution الخاصة بها ويُتوقع أن تعمم على Unseen production data.

يفترض ذلك أن Training data و Unseen data متشابهتان بما يكفي.

في الواقع، ينكسر هذا الافتراض غالبًا لسببين.

### السبب 1: Training data لا تمثل الواقع بصورة مثالية أبدًا

Training data محدودة. أما Real-world data فأوسع بكثير وتتغير عبر Users و Devices و Regions و Encodings و Behaviors و Contexts.

لذلك يمكن لـ Sampling و Selection biases إنشاء Mismatch منذ البداية.

قد تحقق Development model أداءً جيدًا على Held-out test data ثم تفشل بعد Deployment لأن Real production population تختلف. يستخدم الفصل مصطلح **Train-serving skew** لهذا النوع من عدم التطابق بين Development و Production.

### السبب 2: العالم الحقيقي غير ثابت

حتى إذا مثلت Training data الـ Deployment جيدًا عند الإطلاق، يمكن أن تتغير Environment لاحقًا.

قد تكون Shifts:

- Sudden،
- Gradual،
- Seasonal أو Cyclic.

تشمل الأمثلة تغير Pricing لدى Competitors، وإطلاق Product في Region جديدة، و Celebrity تسبب Traffic غير متوقع، وتغير Language تدريجيًا، وتغيرات Seasonal في Ride demand.

### ليست كل Drift ظاهرة ناتجة عن العالم الحقيقي

قد تبدو Monitoring dashboard كما لو أن Data تغيرت بينما يكون السبب الحقيقي داخليًا:

- Preprocessing pipeline معطلة،
- Feature أصبحت Missing أو NaN،
- عدم تطابق Logic الخاصة بـ Training و Inference للـ Features،
- Standardization statistics خاطئة،
- Model version خاطئة،
- Bug في Application interface غيّر User behavior.

لذلك فإن اكتشاف Shift ليس سوى الخطوة الأولى. يظل Root-cause analysis مهمًا.

## 5. Edge cases هي Performance failures وليست مجرد Data غير معتادة

يميز الفصل بصورة مفيدة بين **Outliers** و**Edge cases**.

**Outlier:** Example تختلف بدرجة كبيرة عن Data points الأخرى.  
**Edge case:** Example يكون Performance الخاص بالـ Model عليها أسوأ بكثير من المعتاد.

يمكن لـ Outlier أن تكون Edge case، لكن ليس بالضرورة.

مثال:

Pedestrian يمشي على Highway أمر غير معتاد. إذا اكتشفت Autonomous vehicle هذا الشخص واستجابت بصورة صحيحة، فهو Outlier لكنه ليس Edge case بالنسبة إلى Model.

تهم Edge cases أكثر عندما تكون Consequences شديدة. قد يظل نظام متوسط نجاحه 99.99% غير صالح للاستخدام إذا احتوت الـ 0.01% المتبقية على Catastrophic failures.

ينطبق هذا المبدأ على Safety-critical systems مثل Medical أو Vehicle applications، وكذلك على Brand-sensitive systems مثل Chatbots التي قد تنتج أحيانًا Outputs مسيئة جدًا.

## 6. حلقات Feedback المنحطة (Degenerate)

تحدث **Degenerate feedback loop** عندما تغيّر Output الخاصة بالنظام الـ Future data التي ستُستخدم لاحقًا لتدريب النظام نفسه أوتقييمه.

مفاهيميًا:

```text
Prediction من Model
      ↓
تغيّر ما يراه Users
      ↓
تغيّر ما ينقر عليه Users / يشترونه / يتفاعلون معه
      ↓
تصبح هذه Interactions بيانات Training جديدة
      ↓
تعزز Future model نمط Prediction الأصلي
```

### مثال Recommendation

افترض أن Song A و Song B متقاربتان جدًا في Relevance في البداية، لكن A لها Ranking أعلى قليلًا. لأن A تظهر أولًا، يراها Users وينقرون عليها أكثر. تصبح هذه Clicks دليلًا على أن A أفضل، فتمنحها Versions المستقبلية Ranking أعلى أكثر.

مع الوقت، يمكن لاختلاف أولي صغير أن يتحول إلى Popularity gap كبيرة.

تشمل أفكار مرتبطة بذلك:

- Exposure bias،
- Popularity bias،
- Filter bubbles،
- Echo chambers.

### مثال Hiring

إذا فضّلت Resume model Feature معينة وكان Recruiters يقابلون فقط Candidates الذين توصي بهم Model، فقد تحتوي Future training data بنسبة أكبر على Successful candidates الذين يمتلكون هذه Feature. ثم تستطيع Model تعزيز Preference الأصلية.

## 7. اكتشاف Degenerate feedback loops وتصحيحها

### اكتشف تركّز Popularity

بالنسبة إلى Recommenders، قِس مقدار Diversity في Outputs عبر Popular items و Long-tail items.

إذا أصبحت Recommendations متركزة بصورة متزايدة على Items الشائعة بالفعل، فقد يكون النظام يعزز Patterns الخاصة بالـ Exposure التي أنشأها بنفسه.

إحدى Approaches التي يصفها الفصل هي تقسيم Items إلى Buckets وفق Historical popularity ومقارنة Recommendation quality عبر هذه Buckets. إذا كان Performance أفضل بكثير للـ Popular items، فقد توجد Popularity bias.

### طريقة التصحيح 1: Randomization

اعرض للمستخدمين بعض Items المختارة عشوائيًا حتى يستطيع النظام جمع Feedback أقل انحيازًا عن Items التي لا يمنحها Ranking مرتفعًا عادةً.

الـ Trade-off هو User experience: قد تقلل Random exploration المفرطة من Relevance.

### طريقة التصحيح 2: Positional features

تعتمد User feedback على مكان عرض Item. فقد تحصل النتيجة الأولى على Clicks أكثر ببساطة لأنها في الموضع الأول.

تساعد إضافة Position كـ Feature الـ Model على فصل **Item quality** عن **Exposure advantage**.

يصف الفصل أيضًا فكرة أكثر تقدمًا تعتمد على Model ين:

1. Model لاحتمال أن يرى User الـ Item أوينظر فيها بالفعل،
2. Model لاحتمال Click بشرط أن User رأى الـ Item.

يفصل ذلك Exposure المدفوعة بالـ Position عن User preference.

[[IMAGE_NEEDED: Position bias correction | A ranked recommendation list where top position affects probability of being seen, followed by a two-stage model separating 'seen/considered' from 'clicked given seen' | Learner should notice that clicks combine item preference with exposure position]]

## 8. Source distribution و Target distribution

Distribution المستخدمة في Training هي **Source distribution**.  
Distribution التي تتم مواجهتها أثناء Inference هي **Target distribution**.

في Supervised learning، لنفترض:

- أن `X` تمثل Inputs الخاصة بالـ Model،
- وأن `Y` تمثل Outputs أو Labels.

يمكن تحليل Joint distribution إلى:

```text
P(X, Y) = P(Y|X) P(X)
```

أو:

```text
P(X, Y) = P(X|Y) P(Y)
```

تساعد هذه Decompositions في تعريف ثلاثة أنواع من Shift:

| Shift | ما الذي يتغير؟ | ما الذي يبقى ثابتًا في التعريف؟ |
|---|---|---|
| Covariate shift | `P(X)` | `P(Y|X)` |
| Label shift | `P(Y)` | `P(X|Y)` |
| Concept drift | `P(Y|X)` | `P(X)` |

[[IMAGE_NEEDED: Covariate shift, label shift, and concept drift | Three panels showing changes to P(X), P(Y), and P(Y|X), with the unchanged conditional or marginal distribution noted in each case | Learner should notice that 'data drift' is not one single mathematical phenomenon]]

## 9. Covariate shift: تتغير Input distribution

تحدث Covariate shift عندما:

```text
P(X) تتغير
P(Y|X) تبقى كما هي
```

مثال من الفصل:

قد تحتوي Breast-cancer dataset على Women فوق سن 40 بنسبة أكبر من Deployment population. تتغير Age distribution بين Training و Production، لكن بالنسبة إلى Age group محددة، يُفترض أن Probability relationship بين Age و Cancer لم تتغير.

قد تنشأ Covariate shift من:

- Sample-selection bias،
- Oversampling متعمد للـ Rare classes،
- Active learning تغير أي Inputs يتم اختيارها،
- Product تجذب User population جديدة،
- Environmental changes.

إذا كانت Target input distribution معروفة مسبقًا، يمكن إعادة Weight للـ Training examples باستخدام Density ratio. لكن في Production لا تكون Future shifts معروفة عادةً مسبقًا.

---

## 10. Label shift: تتغير Output distribution

تحدث Label shift عندما:

```text
P(Y) تتغير
P(X|Y) تبقى كما هي
```

تُسمى أيضًا Prior shift أو Prior-probability shift أو Target shift.

على سبيل المثال، قد يتغير Overall rate لتشخيص Positive بين Training و Deployment حتى إذا ظلت Feature distribution لدى الأشخاص الذين لديهم ذلك التشخيص متشابهة.

ويشير الفصل أيضًا إلى أن Covariate shift و Label shift قد تحدثان معًا. لا تحتاج Real production shifts إلى الانتماء بدقة إلى Category واحدة فقط.

---

## 11. Concept drift: تتغير العلاقة

تحدث Concept drift عندما:

```text
P(Y|X) تتغير
P(X) تبقى كما هي
```

فكر فيها بهذه الصورة:

> **نوع Input نفسه، لكن Expected output مختلفة.**

يستخدم المصدر أسعار Housing مثالًا. قد تظل Physical features للشقة نفسها، لكن Market disruption يمكن أن تغير Expected price المرتبطة بهذه Features.

قد تكون Concept drift أيضًا Cyclic أو Seasonal. فمثلًا يمكن أن تختلف Ride prices و Travel demand بين Weekdays و Weekends و Holidays.

## 12. تحولات Production مهمة أخرى

ليس كل تغيير ضار في Production يطابق بصورة مثالية Categories الثلاث التقليدية.

### Feature changes

تشمل الأمثلة:

- إضافة Feature جديدة،
- إزالة Feature قديمة،
- تغيير Units،
- تغيير Allowed values،
- Bug في Pipeline يحول Feature إلى NaN.

تغيير Feature الخاصة بالعمر من Years إلى Months يغير Numerical distribution بقوة حتى إذا ظلت Semantic idea متشابهة.

### تغيّرات مخطط الـ Label

يمكن أن تتغير Structure أو Set الخاصة بالـ Labels الممكنة.

مثال Regression:

- النطاق القديم لـ Credit score: 300–850،
- النطاق الجديد: 250–900.

مثال Classification:

```text
Labels القديمة للـ Sentiment:
POSITIVE / NEGATIVE / NEUTRAL

Labels الجديدة:
POSITIVE / SAD / ANGRY / NEUTRAL
```

قد تتطلب Label-schema change إعادة Labeling للبيانات وتغيير Output structure الخاصة بالـ Model.

## 13. اكتشاف Distribution shifts

أكثر Signal مباشرةً لوجود Shift ضارة هي تغير Real performance الخاصة بالـ Model.

إذا وصلت Ground-truth labels بسرعة كافية، راقب Metrics مثل:

- Accuracy،
- F1،
- Recall،
- AUC-ROC،
- Business أو Quality metrics خاصة بالـ Task.

ينبغي أن يؤدي الانخفاض إلى Investigation. وقد تستحق الزيادات غير المتوقعة أو Fluctuations غير المعتادة Investigation أيضًا.

الصعوبة الرئيسية في Production هي أن Labels قد لا تكون متاحة أوقد تصل متأخرة.

عندما لا تتوفر Labels، تراقب Teams غالبًا Quantities لا تحتاج إليها، خصوصًا Input-feature distribution `P(X)` و Prediction distribution.

## 14. Statistical methods لاكتشاف Drift

### Summary statistics

قارن Statistics الخاصة بـ Source و Target مثل:

- Minimum،
- Maximum،
- Mean،
- Median،
- Variance،
- Quantiles،
- Skewness،
- Kurtosis.

يسهل حساب هذه وهي مفيدة كـ First check.

لكن:

> تشابه Summary statistics **لا** يثبت أن Distribution ين متطابقتان.

### اختبارات العينتين (Two-sample)

تسأل Two-sample hypothesis test ما إذا كان من المرجح أن Sample ين من Data قد جاءتا من Underlying distribution نفسها.

يشير Difference ذات Statistical significance إلى أن Difference المرصودة من غير المحتمل تفسيرها فقط بـ Ordinary sampling variation.

لكن Statistical significance ليست مساوية لـ Practical importance. مع Sample sizes ضخمة، قد تصبح Differences صغيرة جدًا قابلة للكشف إحصائيًا رغم عدم أهميتها للـ Model.

### اختبار Kolmogorov-Smirnov

يصف الفصل KS test بأنها Nonparametric two-sample test لا تفترض Underlying distribution معينة.

أهم Limitation هنا هي Dimensionality: فقد صُممت لـ One-dimensional data.

يمكن أن تناسب Predictions أو Scalar labels هذا الإعداد. أما High-dimensional feature vectors فلا.

يذكر المصدر أيضًا Methods مثل Least-Squares Density Difference و Maximum Mean Discrepancy (MMD)، مع الإشارة إلى أن Research techniques لا تُعتمد دائمًا بصورة واسعة في Production.

ولأن كثيرًا من Statistical tests تعمل بصورة أفضل داخل Lower-dimensional spaces، قد تكون Dimensionality reduction مفيدة قبل اختبار High-dimensional data.

## 15. تغير Time windows ما تستطيع رؤيته من Drift

يعتمد اكتشاف Temporal drift بقوة على Comparison window.

إذا اتبعت Data Weekly cycle، فقد تجعل المقارنة باستخدام Window قصيرة فقط Seasonality طبيعية تبدو كأنها Drift.

كلما قصرت Monitoring window:

- أمكن اكتشاف Changes بصورة أسرع،
- لكن زادت حساسية النظام للـ Noise و False alarms.

كلما طالت Monitoring window:

- أصبحت Estimates أكثر Smoothness واستقرارًا،
- لكن أصبح من الأسهل إخفاء Short-lived failure.

### Sliding statistics

تُحسب فقط عبر Recent fixed window، مثل Last hour.

### Cumulative statistics

تجمع كل Data التي تمت ملاحظتها حتى الآن.

يمكن لـ Cumulative metrics إخفاء Sharp recent failures لأن Healthy history الأقدم تهيمن على Aggregate.

## 16. كيف تستجيب الأنظمة لتحولات Data؟

لا يؤدي اكتشاف Drift تلقائيًا إلى إصلاحها.

يصف الفصل ثلاثة Approaches عامة.

### Approach 1: Training على Data واسعة جدًا

استخدم Training distribution كبيرة ومتنوعة على أمل أن تظل Future production examples ضمن Patterns تعلمتها Model.

### Approach 2: Adaptation من دون Target labels

تحاول Research methods تنفيذ Unsupervised أو Weakly supervised domain adaptation. ويشير الفصل إلى أن Adoption لهذه Approaches ما تزال محدودة داخل Industry.

### Approach 3: إعادة Training باستخدام Target-distribution data

هذه هي الاستجابة الشائعة في Industry عندما يمكن الحصول على New labels موثوقة.

تشمل خيارات Retraining:

- Training من الصفر على Old + New data،
- متابعة Training من Previous checkpoint،
- استخدام Recent data فقط،
- استخدام Data منذ بداية Shift،
- استخدام Historical window أطول.

أفضل Strategy هي Empirical وتعتمد على Application.

### صمّم من أجل Stability

تنجرف بعض Features أسرع من غيرها. قد تجبر Feature عالية Accuracy لكنها سريعة التغير على Frequent retraining، بينما قد تقلل Feature أكثر Coarseness لكنها أكثر Stability من Maintenance cost.

يمكن لـ System decomposition أن تساعد أيضًا. إذا تغير Market بسرعة وآخر ببطء، يمكن لـ Models منفصلة السماح بـ Independent update schedules.

وتذكر: إذا كان Apparent degradation ناتجًا عن Software أو Human error، فالحل هو إصلاح هذا الخطأ — لا تطبيق ML adaptation technique.

## 17. Monitoring و Observability و Instrumentation و Telemetry

**Monitoring** هي عملية Measuring و Tracking و Logging للـ Signals التي تساعدك على تحديد ما إذا كان شيء ما خاطئًا.

**Observability** هي خاصية في System تمنحك Visibility كافية للتحقيق في *ما* الذي حدث خطأ و*لماذا*.

**Instrumentation** هي عمل إضافة Signals التي تجعل System قابلة للـ Observability.

تشمل أمثلة Instrumentation:

- Timing للـ Functions،
- Counting لقيم NaN،
- Tracking لكيفية تغير Inputs عبر Processing stages،
- Recording للـ Inputs الطويلة بصورة غير معتادة،
- ربط IDs و Metadata بالـ Requests.

**Telemetry** هي Runtime data يتم جمعها من Components، بما يشمل Remote services أو User devices.

طريقة مفيدة لتذكر العلاقة:

```text
Instrumentation تنشئ Telemetry
Telemetry تغذي Monitoring
Telemetry جيدة + Structure تنشئ Observability
```

---

## 18. راقب Operational health أولًا

ما تزال ML systems أنظمة Software، ولذلك تظل Ordinary production metrics أساسية.

تشمل الأمثلة:

- Request latency،
- Throughput،
- Prediction request count،
- HTTP success rate،
- CPU/GPU utilization،
- Memory utilization،
- Service availability.

### SLOs و SLAs

يمكن لـ Service تعريف معنى "Healthy" باستخدام Service-level objectives أو Agreements.

مثلًا:

```text
latency الوسيط < 200 ms
latency عند المئين 99 < 2 ثانية
```

يترك Uptime target مثل 99.99% بضع دقائق فقط من Downtime المسموح بها شهريًا.

لكن Uptime لا تكفي لـ ML:

> قد تكون Prediction service متاحة بالكامل ومع ذلك تعيد Predictions غير مفيدة.

لذلك يجب استكمال Operational monitoring بـ ML-specific monitoring.

---

## 19. أربع ML artifacts ينبغي مراقبتها

يقسم الفصل ML-specific monitoring إلى أربع Artifacts:

1. Accuracy-related metrics،
2. Predictions،
3. Features،
4. Raw inputs.

تقع هذه على أعماق مختلفة من ML pipeline.

Raw inputs هي الأقرب إلى Reality لكنها قد تكون فوضوية وصعبة Monitoring. أما Predictions فهي شديدة Structure وسهلة الفحص لكنها تقدم Information مباشرة أقل عن موضع بدء Problems upstream.

[[IMAGE_NEEDED: Four monitoring layers in an ML pipeline | A pipeline from raw inputs to transformed features to predictions to accuracy/feedback metrics, with monitoring attached at each layer | Learner should notice the trade-off between upstream root-cause visibility and downstream monitoring simplicity]]

## 20. Monitoring للـ Accuracy-related metrics و User feedback

إذا كانت Production feedback تستطيع تقديم Natural labels، فقم بـ Logging لها.

قد تشمل Signals مفيدة:

- Clicks،
- Purchases،
- Hides،
- Upvotes/Downvotes،
- Favorites،
- Shares،
- Completion rate،
- Explicit corrections.

عندما تستطيع هذه Signals تقريب Ground truth، يمكن استخدامها لحساب Production performance metrics.

حتى عندما لا تكون Feedback Direct label، يمكن للتغيرات أن تكشف Degradation.

مثال:

```text
Click-through rate: مستقرة
Video completion rate: تنخفض
```

قد يظل Recommendation system يجذب Clicks بينما يوصي بـ Content أقل إرضاءً.

يمكن للأنظمة أيضًا جمع Feedback عمدًا — مثل السماح للمستخدمين بعمل Upvote أو Downvote لـ Output.

---

## 21. Monitoring للـ Prediction distributions

تعد Predictions من أسهل Artifacts في Monitoring لأنها غالبًا Low-dimensional.

في Regression، تكون Prediction عادةً Scalar. وفي Classification قد تكون Class أو Small probability vector.

تشمل Checks مفيدة:

- Mean/Median للـ Predicted value،
- Class frequency،
- Score quantiles،
- Runs غير معتادة مثل Outputs متطابقة كثيرة،
- Two-sample tests بين Historical و Recent predictions.

إذا ظلت Parameters الخاصة بالـ Model دون تغيير، يمكن لـ Shift في Prediction distribution أن تعمل Proxy عن Shift في Inputs.

يكون Prediction monitoring ذا قيمة خاصة عندما تصل Real labels ببطء. يمكن اكتشاف Model تتنبأ فقط بـ `False` لمدة عشر دقائق فورًا، قبل وقت طويل من وصول Labels كافية لحساب Accuracy.

---

## 22. Monitoring للـ Features و Schema validity

تكون Features منظمة بما يكفي لدعم Validation rules قوية.

تشمل Checks ممكنة:

- Min/Max/Median ضمن Acceptable range،
- Values تطابق Required regular expression،
- Categories تنتمي إلى Approved set،
- Cross-feature relationships تظل Valid،
- Missing-value و NaN rates،
- Distribution comparisons عبر الزمن.

تُوصف Feature validation أحيانًا بأنها **Table testing** أو**Unit testing for data**.

### أربعة تحديات عملية

#### 1. Monitoring cost

تؤدي مئات Models مضروبة في مئات أوآلاف Features إلى عدد هائل من Statistics التي يجب حسابها وتخزينها.

#### 2. Alert fatigue

تنحرف Features كثيرًا، وكثير من Changes لا تضر Model performance. يؤدي Alert على كل Shift صغيرة إلى False positives حتى يتوقف الناس عن الانتباه.

#### 3. غموض السبب الجذري

قد تتغير Feature لأن Real input تغيرت — أو لأن Preprocessing step تعطلت.

#### 4. Schema evolution

إذا تغيرت Schemas بمرور الوقت من دون Versioning، فقد تخطئ Monitoring وتعتبر Expected schema migration Unexpected distribution shift.

[[IMAGE_NEEDED: Feature monitoring with schema and drift checks | A tabular feature set with range checks, category checks, missing-value checks, and distribution comparisons, followed by alerts filtered by model impact | Learner should notice that feature drift alone does not prove model degradation]]

## 23. Monitoring للـ Raw inputs

يمكن لـ Monitoring للـ Raw inputs أن تساعد في التمييز بين Changes حقيقية في العالم و Errors أدخلتها Preprocessing.

لكن Raw input monitoring صعبة لأن Raw data قد:

- تأتي من Sources كثيرة،
- تستخدم Formats مختلفة،
- تمتلك Shared structure قليلة،
- تكون تحت سيطرة Data-platform team منفصلة،
- تكون غير متاحة مباشرةً لـ ML engineers.

لذلك يتعامل الفصل مع Raw-input monitoring باعتبارها Concern مهمة لكنها منفصلة تنظيميًا في أحيان كثيرة.

## 24. Logs و Distributed tracing

تسجل Logs Runtime events قد تصبح مهمة لاحقًا للتشخيص.

تشمل الأمثلة:

- Container start و Stop events،
- Function calls،
- Execution duration،
- Inputs و Outputs،
- Crashes،
- Stack traces،
- Resource usage،
- Error codes.

قد تحتوي Modern systems على Services كثيرة، ولذلك قد يكون تحديد *أين* حدث Error أصعب من معرفة أن Error حدث أصلًا.

### Distributed tracing

امنح Request أو Process Unique identifier وانشرها عبر System. سجّل Metadata مثل:

- Timestamp،
- Service،
- Function،
- User أو Request identity حيث يكون ذلك مناسبًا،
- استدعاءات Upstream/Downstream.

عندما تحدث Failure، تسمح Identifier للمهندسين بإعادة بناء Path الخاصة بالـ Request عبر Services.

### Batch مقابل Streaming log analysis

يمكن معالجة Logs دوريًا من أجل High throughput، لكن ذلك يؤخر اكتشاف Problems.

من أجل Near-real-time anomaly detection، يمكن أن تتدفق Logs عبر Real-time transports و Stream-processing systems.

## 25. Dashboards و Alerts

### Dashboards

تجعل Dashboards الـ Numerical trends أسهل للفحص وتجعل Monitoring متاحة للمهندسين وغير المهندسين من Stakeholders.

لكن Graph لا تشرح نفسها. تظل Statistical understanding و Domain context مطلوبة.

كما أن كثرة Graphs تنشئ **Dashboard rot**: تصبح Dashboard مزدحمة بـ Low-value metrics لا يستخدمها أحد.

### Alerts

تحتوي Alert مفيدة على ثلاثة أجزاء.

#### 1. Alert policy

الـ Condition التي تشغّل Alert.

أمثلة:

```text
Model accuracy أقل من 90%
```

أو:

```text
HTTP latency > 1 ثانية لمدة 10 دقائق على الأقل
```

#### 2. Notification channel

من الذي ينبغي أن يستقبلها وعبر أي System؟

#### 3. Description و Action

ينبغي أن تشرح Alert ما الذي حدث وأين ومتى، ومن الأفضل أن ترتبط بـ **Runbook** تصف Routine mitigation و Diagnostic steps.

### Alert fatigue

تُدرّب Alerts كثيرة منخفضة القيمة الناس على تجاهل System. ينبغي لـ Alert policies تركيز Attention على Signals التي تتطلب Human action.

## 26. Observability: اجعل System قابلة للتفسير أثناء Runtime

تخبرك Monitoring **أن** شيئًا مريبًا حدث.

تهدف Observability إلى منحك Runtime information كافية للتحقيق في **لماذا** حدث ذلك.

في Well-instrumented system، ينبغي أن يتمكن Engineers من طرح أسئلة مفصلة مثل:

- أي Users تلقوا Predictions خاطئة خلال Last hour؟
- ما Regions أو Device types المتأثرة؟
- أي Requests كانت Outliers خلال Last ten minutes؟
- ما Intermediate feature values التي أنتجتها Request إشكالية معينة؟
- أي Feature ساهمت أكثر في Recent incorrect predictions؟

تتطلب الإجابة عن هذه الأسئلة Logs و Metrics تحتوي Metadata و Tags مفيدة حتى يمكن تقسيمها عبر Time و Users و Services و Features و Model versions.

يربط الفصل Observability بـ Model interpretability:

- **Interpretability** تساعد في شرح ما تفعله Model،
- **Observability** تساعد في شرح ما تفعله ML system كاملة.

Monitoring قوية لكنها Passive. فهي تكتشف Problem وتساعد في تشخيصها؛ لكنها لا تقوم بنفسها Adapt للـ Model.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: إذا كانت API تعمل، فإن ML system سليمة

Operational availability لا تضمن Prediction quality.

### المفهوم الخاطئ 2: كل Feature shift هي Model failure

كثير من Feature changes غير ضارة. تهم Drift عندما تؤثر بصورة ذات معنى في System behavior أوتشير إلى Problem أخرى.

### المفهوم الخاطئ 3: أي Input غير معتادة هي Edge case

Outlier هي Data غير معتادة؛ أما Edge case فهي Input يكون Model performance عليها أسوأ بصورة غير معتادة.

### المفهوم الخاطئ 4: Feedback data هي Ground truth غير منحازة

تؤثر Model outputs في ما يراه Users، وهذا قد يؤثر في Feedback التي تُستخدم لاحقًا كـ Training data.

### المفهوم الخاطئ 5: Summary statistics تستطيع إثبات عدم حدوث Drift

تشابه Mean أو Variance أو Quantiles لا يضمن تطابق Distributions.

### المفهوم الخاطئ 6: Statistical significance تعني Operational importance

قد تصبح Difference صغيرة جدًا ذات Statistical significance عند وجود Data كثيرة بما يكفي بينما تظل غير مهمة لـ Model quality.

### المفهوم الخاطئ 7: Cumulative metrics أكثر أمانًا دائمًا من Sliding metrics

قد تخفي Cumulative history Recent degradation.

### المفهوم الخاطئ 8: Monitoring تصلح Drift

تكتشف Monitoring الـ Signals وتدعم Diagnosis. وقد يتطلب إصلاح System Software repair أو Retraining أو Adaptation أو Data collection أو Intervention أخرى.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Silent failure | ML-quality failure تحدث بينما تستمر Software في إعادة Outputs تبدو طبيعية |
| انحراف Train-serving | Mismatch بين ظروف Development/Training وظروف Production serving |
| Outlier | Data example تختلف بدرجة كبيرة عن Examples الأخرى |
| Edge case | Example يكون Model performance عليها أسوأ بكثير من المعتاد |
| حلقة Feedback منحطة (Degenerate) | Loop تؤثر فيها Model outputs في Future inputs أو Training data ثم تعزز نفسها |
| Exposure bias | Bias تنتج من حصول بعض Items على فرص أكبر للظهور من غيرها |
| Source distribution | Distribution التي تُسحب منها Training data |
| Target distribution | Distribution التي تتم مواجهتها أثناء Inference |
| Covariate shift | تغير في `P(X)` مع بقاء `P(Y|X)` ثابتة بحسب التعريف |
| Label shift | تغير في `P(Y)` مع بقاء `P(X|Y)` ثابتة بحسب التعريف |
| Concept drift | تغير في `P(Y|X)` مع بقاء `P(X)` ثابتة بحسب التعريف |
| تغيّر مخطط الـ Label | تغير في Structure أو Range أو Classes المسموح بها للـ Labels |
| اختبار العينتين (Two-sample) | Statistical test لمعرفة ما إذا كان Sample ان على الأرجح من Distribution نفسها |
| KS test | Nonparametric one-dimensional two-sample test يناقشها الفصل |
| Sliding statistic | Metric تُحسب فقط على Recent fixed-size time window |
| Cumulative statistic | Metric مجمعة عبر كل Observations التي جُمعت حتى الآن |
| Monitoring | قياس Signals وتتبعها و Logging لها لاكتشاف Problems |
| Observability | القدرة على استنتاج Internal system behavior والتحقيق فيه من Runtime outputs |
| Instrumentation | إضافة Measurements و Metadata اللازمة لـ Runtime visibility |
| Telemetry | Runtime measurements مجمعة من Components أو Remote systems |
| SLO | Service-level objective تحدد Target level لصحة Service |
| SLA | Service-level agreement قد تتضمن Explicit guarantees و Consequences |
| Distributed tracing | Tracking لـ Request واحدة عبر Services متعددة باستخدام Shared identifiers و Metadata |
| Alert fatigue | Desensitization تنتج عن Alerts كثيرة منخفضة القيمة أو False-positive |
| Runbook | خطوات Routine موثقة لتشخيص Operational incident أو Mitigation لها |

9. لماذا يمكن لـ Position نفسها أن تصبح Feature مفيدة عند Modeling للـ Clicks؟

12. عرّف Label shift رياضيًا.
