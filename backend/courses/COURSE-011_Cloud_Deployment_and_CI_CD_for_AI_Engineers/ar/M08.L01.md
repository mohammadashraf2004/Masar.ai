## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح لماذا لا ينبغي إجراء العمل التطويري الروتيني بمستخدم AWS الجذر (root user).
- شرح استخدام المصدر للمصادقة الثنائية 2FA ولمستخدم IAM منفصل.
- التمييز بين مستخدم IAM والمجموعة والسياسة المرفقة بها.
- شرح خيارات إعداد EC2 في المصدر: الـ AMI ونوع النسخة (instance type) وزوج المفاتيح (key pair) والتخزين.
- شرح لماذا يجب حماية المفتاح الخاص بصيغة `.pem`.
- تعريف الـ security group على أنه جدار حماية افتراضي.
- شرح أن CIDR `/32` يمثّل عنوان IPv4 واحدًا في مثال التحكم بالوصول في المصدر.
- ربط منافذ التطبيقات في المصدر بكلٍّ من SSH وStreamlit وFlask وJenkins.
- شرح لماذا يقلّل تقييد الوصول بعناوين IP موثوقة أو بـ VPN من سطح التعرّض.
- شرح لماذا يوفّر Elastic IP عنوانًا عامًا ثابتًا لنسخة EC2.
- وصف البنية التحتية النهائية للفصل 1 بدءًا من هوية المستخدم وانتهاءً بالوصول عبر الشبكة.

## 1. ابدأ بأمان الحساب، لا بالـ deployment

يبدأ المصدر بمبدأ مهم في الحوسبة السحابية:

> قبل نشر أي تطبيق، أمِّن الحساب الذي يتحكم في البنية التحتية.

يمنحك حساب AWS الجديد في البداية **المستخدم الجذر (root user)**.

يمتلك المستخدم الجذر صلاحيات غير مقيّدة على مستوى الحساب.

ولهذا لا يصلح للعمل التطويري الروتيني.

سير العمل في المصدر هو:

```text
حساب AWS الجذر (root)
      ↓
تفعيل 2FA
      ↓
إنشاء مستخدم IAM
      ↓
العمل بمستخدم IAM بدلًا من root
```

### لماذا نفصل الـ root عن العمل اليومي؟

إذا استُخدمت هوية الـ root في العمل اليومي، فإن أي خطأ أو اختراق لبيانات الاعتماد يكون أثره هو الأوسع على الإطلاق.

أما هوية IAM منفصلة فتُنشئ حدًّا بين:

```text
ملكية الحساب
```

و:

```text
العمل التقني اليومي
```

### 2FA للـ root

يطلب الفصل صراحةً من المتعلّم تفعيل **المصادقة الثنائية (Two-Factor Authentication، أو 2FA)** لحساب الـ root.

والفكرة مباشرة:

```text
كلمة المرور فقط
    <
كلمة المرور + عامل ثانٍ
```

يجعل العامل الثاني الاستيلاء على الحساب أصعب عند انكشاف كلمة المرور.

## 2. مستخدمو IAM والمجموعات والصلاحيات

**IAM** هو خدمة AWS Identity and Access Management لإدارة الهويات والصلاحيات.

ينشئ الفصل مستخدمًا موجّهًا للتطوير ويضيفه إلى مجموعة.

من الناحية المفاهيمية:

```text
مستخدم IAM (User)
   ↓ عضو في
مجموعة IAM (Group)
   ↓ لها
سياسات (Policies)
   ↓ تسمح بتنفيذ
إجراءات/موارد AWS
```

### مستخدم IAM

يستخدم المصدر مثالًا وصفيًا مثل:

```text
developer-user    # اسم مستخدم تطويري
```

هذه الهوية مخصّصة لأعمال الـ deployment العملية.

### مجموعة IAM

ينشئ المصدر مجموعة مثل:

```text
developer-group    # اسم مجموعة تطويرية
```

وبدلًا من إدارة الصلاحيات لكل شخص على حدة، يمكن إرفاق الصلاحيات بالمجموعة.

### السياسات التي يستخدمها المصدر

يسرد الفصل المرجعي ما يلي:

```text
AmazonEC2FullAccess
AmazonS3FullAccess
ElasticLoadBalancingFullAccess
```

هذه هي الصلاحيات التي يستخدمها المصدر في مسار تمارينه.

وينبغي فهمها على أنها **صلاحيات تدريبية خاصة بالمصدر**.

ويبرّر الفصل نفسه هذا الإعداد بمبدأ أقل الامتيازات (least privilege)، مع أن هذه السياسات المُدارة المسمّاة واسعة داخل كلٍّ من خدماتها.

### الدرس العملي

المبدأ الأمني ليس:

> "يجب أن يحصل كل مطوّر دائمًا على هذه السياسات الثلاث بعينها."

أما الدرس الذي يدعمه المصدر فهو:

> استخدم هوية IAM منفصلة، وامنحها عن قصد الصلاحيات اللازمة لأعمال الـ deployment، بدلًا من استخدام المستخدم الجذر غير المقيّد.

## 3. EC2: أنشئ الخادم الذي سيستضيف التطبيقات

**نسخة EC2 (EC2 instance)** هي خادم افتراضي يعمل داخل AWS.

ينشئ المصدر جهازًا واحدًا سيستضيف لاحقًا عدة خدمات.

وإعداده في المثال هو:

```text
الاسم: my-web-server
AMI: Amazon Linux 2
نوع النسخة (Instance type): t2.xlarge
```

ويصف المصدر `t2.xlarge` بأنه:

```text
4 vCPUs
16 GiB ذاكرة
```

ويختاره ليتمكّن الجهاز من استضافة عدة أدوات وتطبيقات أثناء تمارين الكتاب.

### الـ AMI

تحدّد **صورة الجهاز من Amazon (AMI)** صورة نظام التشغيل الابتدائية.

يختار المصدر Amazon Linux 2.

ويؤثر هذا الاختيار في الأوامر اللاحقة، ولهذا يستخدم الفصل التالي أدوات مثل:

⟦CODE_0⟧

### نوع النسخة (Instance type)

يتحكم نوع النسخة في سعة الحوسبة، مثل:

- المعالج (CPU)،
- الـ memory.

وفي المصدر يكون الجهاز كبيرًا عن قصد ليكفي عدة خدمات لاحقة.

### زوج المفاتيح (Key pair)

ينشئ الفصل زوج مفاتيح لـ EC2 وينزّل ملفًا مثل:

```text
my-web-server-key-pair.pem    # ملف المفتاح الخاص
```

سيُستخدم هذا المفتاح الخاص لاحقًا في SSH.

تعامل معه على أنه حساس.

من الناحية المفاهيمية:

```text
جانب المفتاح العام
   → مرتبط بالوصول إلى EC2

مفتاح .pem الخاص
   → يبقى معك
```

لا تشارك المفتاح الخاص بلا اكتراث.

### التخزين

يوصي المصدر بزيادة حجم القرص الجذري إلى:

```text
50 GiB
```

على الأقل، ويقترح:

```text
100 GiB
```

نقطة بداية عملية لتمارينه الكثيفة الاستخدام لـ Docker.

وتعليله أن بناء صور Docker المتكرر والصور المخزّنة مؤقتًا يستهلكان مساحة القرص.

وهذا درس تشغيلي قيّم:

> يهمّ تخطيط التخزين حتى عندما تبدو قدرة المعالج والـ memory كافية.

## 4. مجموعات الأمان (Security groups): تحكّم فيمن يستطيع الوصول إلى الخادم

يعمل الـ **security group** بوصفه جدار حماية افتراضيًا حول موارد AWS مثل نُسخ EC2.

وهو يتحكم في:

- الحركة الواردة (inbound)،
- الحركة الصادرة (outbound).

صُمّم الـ security group في المصدر لأربع خدمات.

### المنافذ الواردة في المصدر

| الغرض | البروتوكول | المنفذ |
|---|---|---:|
| SSH | TCP | 22 |
| Streamlit | TCP | 8501 |
| Flask | TCP | 8502 |
| Jenkins | TCP | 8504 |

المصدر **لا** يفتح هذه المنافذ للجميع.

بل يقصرها على عنوان موثوق مثل:

```text
35.123.123.58/32
```

### ماذا يعني `/32`؟

في IPv4 يمثّل `/32` عنوانًا واحدًا بعينه.

إذن:

```text
35.123.123.58/32
```

يعني:

> هذه القاعدة تسمح بعنوان IPv4 واحد فقط.

### الوصول عبر VPN

ويناقش المصدر أيضًا الوصول عبر VPN المؤسسي.

فإذا كان الموظفون يظهرون على الإنترنت من عنوان خروج VPN معروف، يمكن للـ security group أن يسمح بهذا المصدر الموثوق.

وهذا يُنشئ مسار وصول عمليًا:

```text
المطوّر
   ↓
شبكة VPN الخاصة بالشركة
   ↓
عنوان IP عام معروف
   ↓
مجموعة الأمان تسمح بالطلب
   ↓
خدمة EC2
```

### السلوك الافتراضي للحركة الصادرة

يترك المصدر القواعد الصادرة على وضعها الافتراضي:

```text
السماح بكل حركة المرور الصادرة
```

وهذا جزء من إعداد التمرين في المصدر.

### لماذا يهمّ هذا؟

قارن بين:

```text
0.0.0.0/0
```

لمنفذ إداري حساس، وبين:

```text
trusted-ip/32    # عنوان موثوق
```

الثاني سطح تعرّضه أصغر بكثير.

[[IMAGE_NEEDED: EC2 security-group access model | A diagram showing a trusted developer IP or corporate VPN on the internet sending TCP traffic to EC2 only on ports 22, 8501, 8502, and 8504, while other sources are blocked | Learner should notice that a security group filters traffic before it reaches the instance]]

## 5. Elastic IP: احتفظ بعنوان عام ثابت

قد يتغيّر عنوان EC2 العام العادي عند إيقاف النسخة ثم تشغيلها.

وهذا يخلق مشكلة عملية.

افترض أن أمر SSH لديك هو:

⟦CODE_1⟧

فإذا تغيّر `PUBLIC_IP` بعد إعادة التشغيل، تصبح إعدادات الاتصال لديك قديمة.

يحل المصدر هذه المشكلة باستخدام **Elastic IP**.

### مفهوم Elastic IP

الـ Elastic IP هو عنوان IPv4 عام تحجزه وتربطه بمورد من موارد AWS مثل نسخة EC2.

وعملية المصدر هي:

```text
حجز Elastic IP
      ↓
اختيار نسخة EC2
      ↓
اختيار عنوان IP الخاص بالنسخة
      ↓
الربط (associate)
```

والآن صار للنسخة عنوان عام ثابت للخطوات اللاحقة.

### عنوان IP العام مقابل الخاص

ويطلب منك المصدر أيضًا تحديد عنوان IP الخاص بالنسخة.

وهذه العناوين تؤدي أدوارًا مختلفة.

```text
عنوان IP العام / Elastic IP
→ يمكن الوصول إليه من الشبكات الخارجية وفق قواعد الأمان

عنوان IP الخاص
→ عنوان داخل شبكة AWS VPC
```

يصبح عنوان IP الخاص مهمًا في درس الـ load balancer اللاحق.

## 6. اجمع قطع الفصل 1 معًا

في نهاية هذا الدرس يكون المصدر قد بنى الأساس التالي:

```text
المستخدم الجذر (Root User)
   └── محمي بـ 2FA

مستخدم IAM للتطوير
   └── صلاحياته عبر مجموعة/سياسات IAM

عنوان IP موثوق / VPN
   ↓
مجموعة الأمان (Security Group)
   ↓
نسخة EC2
   ├── Amazon Linux 2
   ├── زوج المفاتيح (key pair)
   ├── تخزين موسّع
   └── منافذ التطبيقات

Elastic IP
   ↓
عنوان عام ثابت لـ EC2
```

هذه البنية التحتية ليست بعدُ معمارية الإنتاج النهائية.

إنها الأساس الذي تبني عليه الفصول من 2 إلى 4.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1
> "مستخدم AWS الجذر هو حساب المطوّر العادي."

يفصل المصدر صراحةً بين العمل الروتيني والوصول على مستوى الـ root.

### المفهوم الخاطئ 2
> "مستخدم IAM ومستخدم EC2 شيء واحد."

هما مفهومان مختلفان.

يتحكم IAM في هوية AWS API/console. أما `ec2-user` لاحقًا فهو حساب Linux المستخدم عند الاتصال بجهاز Amazon Linux.

### المفهوم الخاطئ 3
> "الـ security group هو شيفرة تطبيق."

الـ security group هو إعداد للوصول الشبكي حول موارد AWS.

### المفهوم الخاطئ 4
> "`/32` يفتح المنفذ للإنترنت كله."

في أمثلة IPv4 في المصدر، يحدّد `/32` عنوانًا واحدًا بعينه.

### المفهوم الخاطئ 5
> "Elastic IP وعنوان IP الخاص قابلان للتبادل."

لكل منهما دور شبكي مختلف.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مستخدم AWS الجذر (root user) | هوية على مستوى الحساب بوصول غير مقيّد إليه |
| 2FA | عامل مصادقة ثانٍ إضافة إلى كلمة المرور |
| IAM | خدمة AWS Identity and Access Management |
| مستخدم IAM | هوية AWS لشخص أو لحِمل عمل |
| مجموعة IAM | مجموعة من مستخدمي IAM تشترك في الصلاحيات |
| السياسة (Policy) | مستند صلاحيات يتحكم في إجراءات AWS المسموح بها |
| EC2 | خدمة الحوسبة الافتراضية في AWS |
| AMI | صورة الجهاز الابتدائية لنسخة EC2 |
| نوع النسخة (Instance type) | حجم أو سعة الحوسبة في EC2 |
| زوج المفاتيح (Key pair) | مادة مفاتيح عامة/خاصة تُستخدم للوصول إلى النسخة |
| ملف `.pem` | صيغة ملف المفتاح الخاص المستخدمة في إعداد SSH لـ EC2 في المصدر |
| مجموعة الأمان (Security group) | جدار حماية افتراضي في AWS |
| CIDR `/32` | نطاق يمثّل عنوان IPv4 واحدًا |
| Elastic IP | عنوان IPv4 عام محجوز يمكن أن يبقى ثابتًا عبر أحداث دورة حياة النسخة |
| عنوان IP الخاص (Private IP) | عنوان يُستخدم داخل شبكة الـ VPC |
