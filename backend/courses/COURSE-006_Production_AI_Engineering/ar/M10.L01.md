## 1. ابدأ ببساطة، ثم أضف Components لأنك تحتاج إليها

أبسط تطبيق AI هو:

```text
استعلام المستخدم (user query) -> Model -> الاستجابة (response)
```

لا Retrieval. لا Guardrails. لا Router. لا Cache. لا Agent Loop.

هذه البساطة مفيدة لأن كل Component إضافية تقدم Failure Modes جديدة و Latency وعملًا تشغيليًا وصعوبة في Debugging.

لذلك يبني الفصل Architecture تدريجيًا:

1. حسّن Context.
2. أضف Guardrails.
3. أضف Routing و Model Gateway.
4. أضف Caches.
5. أضف Agent Patterns و Write Actions.
6. زوّد النظام كاملًا بـ Observability.
7. نسّق Components داخل Pipeline قابلة للصيانة.

هذا الترتيب ليس وصفة عالمية. المبدأ الحاكم هو:

> أضف التعقيد عندما يحل مشكلة حقيقية في تطبيقك.

## 2. الخطوة 1 — حسّن Context

تفشل Foundation Model غالبًا لأنها تفتقر إلى المعلومات الصحيحة في الوقت الصحيح.

يمكن لـ Context Construction توفير هذه المعلومات من خلال:

- Text Retrieval.
- Image Retrieval.
- Tabular أو Database Retrieval.
- Uploaded Files.
- Search APIs.
- Weather أو News أو Event APIs.
- Tools أخرى تجمع المعلومات.

يقارن الفصل Context Construction بـ Feature Engineering: كلاهما يحاول تقديم Inputs إلى Model تجعل Target Task أسهل.

يدعم Model Providers و Frameworks المختلفة حدود Context مختلفة وأنواع Documents و Retrieval Algorithms و Chunking Options و Tool-execution Modes.

لا تختر Provider بناءً على Model Name فقط. قيّم ما إذا كانت قدرات Context Construction الخاصة به تتوافق مع تطبيقك.

[[IMAGE_NEEDED: Context-enhanced architecture | User query flowing into retrieval/tools, retrieved context joining the query, then both entering the model | Learner should notice that external information is constructed per query rather than memorized inside every prompt]]

## 3. الخطوة 2 — ضع Guardrails حيث توجد المخاطر

تقلل Guardrails المخاطر حول Inputs و Outputs و Actions.

ينبغي ربطها بمواطن التعرض الفعلية. فالنظام الذي يرسل Sensitive Data إلى External API يحتاج إلى Guardrails مختلفة عن نظام Self-hosted بالكامل.

يفصل الفصل بين فئتين عامتين:

- **Input Guardrails** — تحمي النظام قبل Main Model Call.
- **Output Guardrails** — تكتشف Model Responses السيئة وتتعامل معها.

لا تستطيع Guardrails القضاء على جميع حالات الفشل. بل تقلل Probability وتأثيرها.

---

## 4. Input Guardrails

يوجد خطران مهمان على جانب Input:

1. خروج Sensitive Information خارج Trust Boundary الخاصة بك.
2. اختراق Malicious أو Unsafe Prompts لسلوك النظام.

يمكن أن تدخل Sensitive Information إلى Prompt لأن:

- المستخدم يلصق Private Data.
- موظف يلصق Internal Secrets.
- System Prompt تحتوي على Confidential Information.
- Tool تسترجع Protected Data وتضيفها إلى Context.

تشمل أهداف Detection الشائعة:

- Identity Numbers.
- Phone Numbers.
- تفاصيل الحساب البنكي (Bank-account Details).
- Human Faces.
- Internal IP Keywords أو Privileged Phrases.

بعد Detection، يستطيع التطبيق Block للـ Request أو Redact أو Mask للقيمة الحساسة.

---

## 5. إخفاء المعلومات الخاصة واستعادتها (Masking and Unmasking Private Information)

من الأنماط المفيدة استبدال Private Values قبل إرسال Data إلى External Model.

مثال:

```text
الأصل (Original):
Call me at 01012345678.

بعد الإخفاء (Masked):
Call me at [PHONE_NUMBER].
```

يخزن التطبيق Private Reverse Map:

```text
[PHONE_NUMBER] -> 01012345678
```

إذا أعادت Model الـ Placeholder، يستطيع التطبيق استعادة Original Value بعد External Model Step.

تُعد Reverse Map نفسها حساسة ويجب أن تبقى داخل Trusted System.

## 6. Output Guardrails

تمتلك Output Guardrails وظيفتين:

1. اكتشاف Output Failures.
2. تحديد ما ينبغي للتطبيق فعله عند اكتشاف Failure.

### إخفاقات الجودة (Quality Failures)

- Response فارغة عندما تكون Response متوقعة.
- JSON غير صالحة أو Structure أخرى Malformed.
- Claims تتضمن Hallucination أو Factual Inconsistency.
- Output غير ذات صلة أو ضعيفة عمومًا.

### إخفاقات الأمان (Security Failures)

- Toxic أو Unsafe Content.
- تسريب Sensitive Information.
- Output تؤدي إلى Unsafe Remote Execution.
- سلوك يعرّض العلامة التجارية للخطر (Brand-risk Behavior).

ينبغي لـ Security Evaluation أيضًا تتبع **False Refusals**. فالنظام الذي يمنع كل شيء قد يكون "آمنًا" لكنه غير قابل للاستخدام.

## 7. Retries و Parallel Candidates و Human Fallback

Foundation Models احتمالية. لا يتكرر Failed Response دائمًا في Call التالية.

بالنسبة إلى بعض حالات الفشل، تكون Retry Logic البسيطة مفيدة:

- مخرجات فارغة -> إعادة المحاولة (Empty Output -> Retry).
- Invalid Structure -> Retry أو Repair.
- Temporary Provider Failure -> Retry أو Fallback.

لكن Retries تزيد Cost و Latency.

أحد البدائل هو توليد عدة Candidates بالتوازي واختيار Response صالحة أو أفضل. يضبط ذلك Latency لكنه يزيد Redundant Computation.

بالنسبة إلى الحالات الصعبة أو عالية المخاطر، قد يكون أقوى Fallback هو Human Operator.

يمكن أن تشمل Human Escalation Triggers:

- High-risk Intents معينة.
- Frustration أو Anger لدى المستخدم.
- عددًا كبيرًا من Conversation Turns غير الناجحة.
- Low Confidence.
- تكرار إخفاقات Guardrail (Repeated Guardrail Failures).

---

## 8. Guardrails لها تكاليف في Latency و UX

يمكن لكل Detector أو Scorer إضافية أن تضيف Model Call أو Classifier Call أو Validation Pass أخرى.

ينشئ ذلك مفاضلة:

```text
مزيد من الفحص (more checking) -> موثوقية أعلى محتملة (potentially higher reliability)
مزيد من الفحص (more checking) -> Latency/Cost أعلى
```

ينشئ Streaming تحديًا آخر. فبمجرد إظهار Tokens للمستخدم، لا تستطيع Output Guardrail لاحقة منع رؤية تلك Tokens السابقة.

يعتمد تصميم Guardrail الصحيح على Risk و Latency Requirements و Model Provider وما إذا كنت تنفذ Self-hosting.

## 9. الخطوة 3 — أضف Router

استخدام General Model مكلفة واحدة لكل Query يكون غير ضروري غالبًا.

تقرر **Router** أي Solution ينبغي أن تتعامل مع Request.

إحدى Routers الشائعة هي **Intent Classifier**.

أمثلة Support Routes:

```text
إعادة تعيين كلمة المرور (password reset) -> FAQ / Retrieval
نزاع Billing (billing dispute) -> Human Operator
مشكلة تقنية (technical issue) -> Technical Assistant
طلب خارج النطاق (out-of-scope request) -> Stock Refusal/Redirect
```

يمكن لـ Routing تحسين:

- Quality من خلال Specialization.
- Cost باستخدام Models أصغر أو أرخص للـ Requests السهلة.
- Safety عبر اعتراض Unsupported Requests.
- UX عبر طلب Clarification للـ Queries الغامضة.

---

## 10. Routing أوسع من Intent Classification

يمكن لـ Routers تحديد ما سيحدث لاحقًا داخل نظام معقد.

أمثلة:

- Search API أم Code Interpreter؟
- استخدام Short-term Memory أم Long-term Memory؟
- استخدام Retrieval أم الإجابة مباشرة؟
- البقاء مع Current Model أم الانتقال إلى Model ذات Context Window أكبر؟

يمكن أن يحدث Routing قبل Retrieval أو بعد Retrieval أو بين Agent Steps.

ولأن Routers قد تُستدعى بصورة متكررة، ينبغي أن تكون عادةً صغيرة وسريعة ورخيصة مقارنة بـ Main Generation Model.

## 11. Model Gateway: واجهة واحدة محكومة لعدة Models

الـ **Model Gateway** هي طبقة وسيطة بين Applications و Model Providers.

أبسط غرض لها هو Abstraction:

```text
التطبيق (application)
   -> Model Gateway
        -> Provider A
        -> Provider B
        -> Self-hosted Model
```

بدلًا من أن ينفذ كل Application كل Provider API بصورة منفصلة، تعتمد Applications على Internal Interface واحدة.

يجعل ذلك تغييرات Providers أسهل في الاستيعاب ويركز Operational Controls في مكان واحد.

## 13. ما الذي ينتمي إلى Model Gateway؟

تُعد Gateway نقطة مركزية طبيعية من أجل:

- Access Control.
- API-key Protection.
- Usage Quotas.
- Cost Monitoring.
- التعامل مع حدود المعدل (Rate-limit Handling).
- Provider Fallback.
- Load Balancing.
- Logging و Analytics.
- Optional Caching.
- Optional Guardrails.

تقلل Gateway من Duplicated Logic عبر Applications.

لكن تجنب تحويلها إلى "Everything Service" غير قابلة للصيانة. حافظ على حدود واضحة لما تريد مؤسستك جعله مركزيًا.

## 14. الخطوة 4 — Exact Caching

تتجنب Caching تكرار Work مكلفة.

تعيد **Exact Caching** استخدام Result فقط عندما تتطابق Cache Key تمامًا.

أمثلة:

- Product Summary Request نفسها.
- Embedding Query نفسها.
- Deterministic Multi-step Computation نفسها.

يمكن أن تشمل Storage Layers الممكنة In-memory Caches أو Redis-like Stores أو Databases أو Tiered Storage.

تحتاج Cache أيضًا إلى **Eviction Policy** مثل:

- LRU — الأقل استخدامًا مؤخرًا (Least Recently Used).
- LFU — الأقل استخدامًا تكرارًا (Least Frequently Used).
- FIFO — الداخل أولًا يخرج أولًا (First In, First Out).

تكون Caching أكثر منطقية للـ Requests المرجح تكرارها وبقاء Results الخاصة بها صالحة.

## 15. أمان Cache: يمكن لـ Personalization تسريب Data

قد تبدو Cache Entry عامة بينما تعتمد Response الخاصة بها فعليًا على Private User Context.

مثال:

```text
يسأل المستخدم A: What is the return policy?
يسترجع النظام Membership Tier الخاصة بـ A.
تحتوي Response على Policy خاصة بـ A.
تُخزن Response في Cache كما لو كانت عامة.

يسأل المستخدم B بالصياغة نفسها.
يعيد النظام Cached Answer الخاصة بـ A.
```

هذا Data Leak.

يجب أن تتضمن Cache Keys كل المعلومات التي تغير Answer بصورة جوهرية، أو ينبغي عدم مشاركة Response بين المستخدمين.

قد تكون Time-sensitive و Highly User-specific Queries Candidates ضعيفة لـ Caching.

## 16. Semantic Caching

تعيد Semantic Caching استخدام Results للـ Requests **المتشابهة**، وليس المتطابقة.

Flow نموذجي:

```text
Query واردة (incoming query)
 -> Query Embedding
 -> Vector Search داخل Cached-query Embeddings
 -> أعلى Similarity Score
 -> إذا كانت Score >= Threshold: أعد Cached Result
 -> وإلا: احسب Result وخزنها في Cache
```

يزيد ذلك Cache Hits الممكنة، لكنه ينشئ Failure Mode جديدة: يمكن أن تكون Queryان متقاربتين دلاليًا بينما تحتاجان إلى إجابتين مختلفتين.

تعتمد Semantic Caching على:

- Embedding Quality.
- جودة البحث بالمتجهات (Vector-search Quality).
- Similarity Metric.
- Threshold Calibration.
- Cache Size و Query Latency.

قيّم ما إذا كانت Savings تبرر التعقيد ومخاطر Correctness.

## 17. الخطوة 5 — أضف Agent Patterns عندما تحتاج Workflow إلى Loops أو Branches

تكون Architecture السابقة Sequential في معظمها. ويمكن لـ Agentic Systems إضافة:

- Loops.
- Conditional Branches.
- Parallel Actions.
- Repeated Retrieval.
- Tool Calls.
- Write Actions.

على سبيل المثال، بعد توليد Answer، قد يقرر النظام أن Evidence غير كافية، فيسترجع Context إضافية ثم يولد مرة أخرى.

يجعل ذلك النظام أكثر قدرة، لكنه أيضًا أصعب في Reasoning و Debugging.

---

## 18. Write Actions تضاعف القدرة والمخاطر

يمكن لـ Agent تجاوز قراءة Data والبدء في تغيير العالم:

- إرسال Email.
- تنفيذ Order.
- تحديث Record.
- بدء Transfer.
- تعديل Files.

تجعل Write Tools النظام أكثر فائدة بكثير، لكن الأخطاء لم تعد مجرد Text سيئة؛ فقد تتحول إلى Side Effects حقيقية.

ولذلك تحتاج High-impact Actions إلى Controls أقوى مثل Permissions و Validation و Confirmation و Logging و Human Approval.

---

## 19. ينبغي تصميم Observability من البداية، لا إضافتها لاحقًا

مع زيادة تعقيد Architecture، يزداد عدد Failure Points الممكنة.

تساعد Monitoring على اكتشاف المخاطر والفرص. وتذهب Observability أبعد: ينبغي Instrumentation للنظام بحيث عندما يحدث خطأ، تستطيع تحديد **أين ولماذا** من دون نشر Debugging Code جديدة أولًا.

توجد ثلاثة Operational Measures مفيدة:

- **MTTD** — متوسط زمن الاكتشاف (Mean Time to Detection).
- **MTTR** — Mean Time to Response أو Resolution.
- **CFR** — معدل فشل التغييرات (Change Failure Rate).

ينبغي أن تعزز Evaluation و Monitoring بعضهما. يجب أن تتحول Production Failures إلى Future Evaluation Cases؛ وينبغي لـ Evaluation Metrics أن تتنبأ بـ Production Behavior قدر الإمكان.

[[IMAGE_NEEDED: Evaluation-monitoring feedback loop | Offline evaluation -> deployment -> monitoring/observability -> production failures -> new evaluation cases -> next release | Learner should notice that evaluation and production monitoring form one learning loop]]

## 20. صمّم Metrics حول Failure Modes

Metrics أدوات، وليست أهدافًا.

ابدأ بحالات الفشل التي تهتم بها، ثم اختر Measurements تكشف هذه الحالات.

أمثلة:

- Hallucination Risk -> Groundedness أو Factual-consistency Metric.
- JSON غير صالح -> معدل إخفاق التنسيق (Format-failure Rate).
- Safety Risk -> Toxicity و PII Leakage و Refusal أو False-refusal Rates.
- Cost Risk -> Tokens/Request و Queries/User و Cache Hit Rate و Provider Spend.
- Latency Risk -> TTFT و TPOT و Total Latency.
- Retrieval Risk -> Context Relevance أو Precision.

ينبغي أيضًا ربط Metrics بـ Business North-star Metrics عندما يكون ذلك ممكنًا.

إذا تحسنت Metric لكنها لا ترتبط بـ Product Success، فقد لا تستحق Optimization Effort كبيرة.

---

## 21. سلوك Conversation نفسه Production Metric

يمكن لـ User Behavior كشف مشكلات Quality حتى دون Explicit Ratings.

تشمل Signals المفيدة:

- إيقاف المستخدمين Generation مبكرًا.
- عدد Turns لكل Conversation.
- Trends في Input-token Length.
- Trends في Output-token Length.
- تغيرات Output-token Distribution.
- Refusal Frequency.
- تكرار تفعيل Guardrail (Guardrail-trigger Frequency).

تهم Length Metrics لـ Quality و Latency و Cost في الوقت نفسه.

قسّم Aggregate Metrics دائمًا وفق أبعاد ذات معنى مثل:

- User Segment.
- Release أو Version.
- Prompt أو Chain Version.
- Task Type.
- Time.

---

## 22. Spot Checks مقابل Exhaustive Monitoring

بعض Metrics منخفضة التكلفة بما يكفي لتشغيلها على كل Request. وبعضها مكلف.

استخدم:

- **Exhaustive Checks** للـ Validations المهمة منخفضة التكلفة.
- **Spot Checks** للـ Expensive Judges أو Human Review.

تسمح Mixed Strategy بـ Monitoring واسعة من دون دفع Full Cost لـ Heavyweight Evaluation على كل Request.

---

## 23. Logs تشرح الأحداث الفردية

تقوم Metrics بالتجميع. وتحافظ Logs على Event Detail.

Debugging Pattern شائع هو:

1. Metric Alert تقول إن شيئًا خاطئًا يحدث.
2. افحص Logs حول Time أو Request ذات الصلة.
3. اعثر على Failing Event أو Configuration.
4. اربطها مرة أخرى بتغير Metric.

تشمل AI-application Logs المفيدة:

- Model أو Provider أو Version.
- Sampling Configuration.
- Prompt Template أو Version.
- User Query.
- الـ Prompt النهائية الموجهة إلى Model (Final Model Prompt).
- Model Output.
- Intermediate Outputs.
- Tool Calls و Tool Results.
- Component Start أو End أو Crash Events.
- Request IDs و Tags التي تربط Events ذات الصلة.

تنمو Logs بسرعة، لذلك يصبح Automated Analysis مهمًا.

## 24. Traces تعيد بناء مسار Request الكامل

تربط Trace الـ Logs ذات الصلة داخل Timeline لـ Request أو Workflow واحدة.

قد تعرض AI Trace مفيدة:

```text
Query الأصلية (raw query)
 -> قرار Router
 -> Retrieval Query
 -> Retrieved Documents
 -> Final Prompt
 -> Model Generation
 -> Tool Call
 -> Guardrail Score
 -> Final Response
```

ينبغي لكل Step أن تتضمن بصورة مثالية Latency و Errors و Cost عندما تكون قابلة للقياس.

إذا فشلت Request، ينبغي أن تساعد Tracing على تحديد ما إذا كان Error جاء من Routing أو Retrieval أو Prompt Construction أو Model Generation أو Tools أو Post-processing.

[[IMAGE_NEEDED: AI request trace | A horizontal timeline showing router, retrieval, model, tool, guardrail, and final response spans with latency/cost annotations | Learner should notice how one trace connects component-level failures to the user-visible result]]

## 25. اكتشاف Drift

يمكن لنظام AI في Production أن يتغير حتى إذا لم تغير Application Code عمدًا.

يسلط الفصل الضوء على ثلاثة أشكال.

### انحراف System Prompt (System-prompt Drift)

يتغير Template أو Typo Fix أو Shared Configuration في Prompt.

### انحراف سلوك المستخدم (User-behavior Drift)

يتعلم المستخدمون كيفية التفاعل مع النظام ويغيرون Prompts أو Lengths أو Wording أو Workflows.

### انحراف Model الأساسية (Underlying-model Drift)

قد يغير Provider الـ Model الفعلية خلف Stable API Name.

نفّذ Versioning لكل ما تتحكم فيه، وراقب Behavior لاكتشاف التغيرات التي لا تتحكم فيها.

---

## 26. تنسيق AI Pipeline

قد يتضمن تطبيق AI كلًا من Models و Retrievers و Databases و Tools و Scorers و Guardrails و Humans.

تحدد **Orchestrator** كيفية عمل هذه Components معًا.

على مستوى عام، تقوم بشيئين:

### تعريف Components (Component Definition)

عرّف النظام بالـ Models و Data Sources و Tools و Evaluators و Components الأخرى الموجودة.

### الربط (Chaining)

حدد كيف تصبح Output من Component Input إلى Component التالية.

يمكن أن تتضمن Pipeline خطوات Sequential و Branches و Loops و Parallel Work و Retries و Human Escalation.

---

## 27. مثال على Orchestrated Pipeline

يمكن أن تكون RAG Support Workflow بسيطة كالتالي:

```text
Query المستخدم الأصلية (raw user query)
 -> Preprocess للـ Query
 -> Retrieve للبيانات ذات الصلة
 -> Construct لـ Model Prompt
 -> Generate لـ Response
 -> Evaluate لـ Response
 -> إذا كانت جيدة (if good): أعدها
 -> إذا كانت سيئة/High-risk: Human Fallback
```

ينبغي لـ Orchestrator أيضًا اكتشاف Data-contract Failures. فإذا أعادت Component Data في Shape لا تستطيع Component التالية استهلاكها، فينبغي أن يكون هذا الفشل مرئيًا وقابلًا للتصرف.

بالنسبة إلى Strict-latency Applications، نفذ Steps المستقلة بالتوازي عندما يكون ذلك ممكنًا.

## 28. متى وكيف تختار Orchestrator

يمكن لـ Orchestration Framework توفير Engineering Work، لكنها تضيف أيضًا Abstraction Layer.

يمكن للبدء دون واحدة أن يساعد الفريق على فهم النظام الفعلي قبل إخفائه خلف Framework.

عند تقييم Orchestrators، افحص:

### Integration و Extensibility

- هل تدعم Models و Databases و Tools الخاصة بك؟
- ما مدى صعوبة إضافة Components غير مدعومة؟

### دعم Pipeline المعقدة (Complex Pipeline Support)

- Branching.
- Parallel Execution.
- Loops.
- Error Handling.
- مسارات الإنسان في الحلقة (Human-in-the-loop Workflows).

### سهولة الاستخدام و Performance و Scalability

- APIs أو Documentation واضحة.
- لا توجد Hidden Expensive Calls.
- أقل قدر من Latency غير الضرورية.
- القدرة على التوسع مع Traffic وحجم Team.

## 29. User Feedback هي Product Data

تساعد User Feedback في ثلاثة أهداف رئيسية:

1. **Evaluation** — فهم أداء Product.
2. **Development** — تحسين Prompts و Systems و Datasets و Future Models.
3. **Personalization** — تكييف التطبيق مع مستخدم فردي.

يمكن أن تصبح Feedback Data خاصة وتنشئ Data Flywheel:

```text
منتج أفضل (better product)
 -> استخدام أكثر (more usage)
 -> Feedback/Data أكثر
 -> Evaluation/Training أفضل
 -> منتج أفضل (better product)
```

لكن Feedback تظل User Data. وتنطبق Privacy و Consent و Transparency.

## 30. Explicit مقابل Implicit Feedback

### Explicit Feedback

يجيب المستخدمون عمدًا عن Feedback Request:

- Thumbs Up أو Down.
- Star Rating.
- Better أو Worse Comparison.
- عبارة مثل: "Did we solve your problem?"

يسهل تفسير ذلك لكنه قد يكون Sparse ومتحيزًا نحو المستخدمين المتحمسين بدرجة كافية للرد.

### Implicit Feedback

استنتج رضا المستخدم أو Preferences من السلوك:

- Regenerate.
- Edit.
- Stop Generation.
- Rephrase.
- Share أو Bookmark أو Delete.
- Accept أو Ignore لـ Suggestion.

Implicit Feedback وفيرة لكنها أكثر Noise.

نادراً ما يثبت Action واحد Interpretation واحدة. Context مهمة.

---

## 31. الإشارة الحوارية: الإنهاء المبكر (Conversational Signal: Early Termination)

إذا أوقف المستخدم Response في منتصفها، أو خرج، أو طلب من Voice Agent التوقف، أو ترك Agent قبل اختيار Option، فقد يكون Interaction يسير بصورة سيئة.

هذه ليست Evidence مثالية. فقد يكون المستخدم قد تعرض لمقاطعة ببساطة. لكنها على نطاق واسع يمكن أن تكون Signal مفيدة، خصوصًا عند دمجها مع Evidence أخرى مثل Rephrasing أو Negative Sentiment.

---

## 32. Conversational Signal: Correction و Rephrasing

Follow-ups مثل:

- "No, ..."
- "I meant ..."
- "Check again."
- عبارة مثل: "Are you sure?"
- عبارة مثل: "Show me the sources."

يمكن أن تشير إلى Misunderstanding أو Insufficient Detail أو Distrust أو Factual Concern.

تكون Rephrasing Attempts مفيدة بصورة خاصة لأنها تظهر كيف يختلف Intent الأصلي للمستخدم عما فهمه النظام على ما يبدو.

بالنسبة إلى Agentic Systems، يمكن للمستخدمين أيضًا تصحيح Action Plan: "Check the company's repository too."

---

## 33. تعديلات المستخدم يمكن أن تصبح Preference Data قوية

إذا عدل المستخدمون Generated Code أو Text أو Structured Output مباشرة، فإن Edit توفر Signal قوية.

مفاهيميًا:

```text
Query
Generated Response -> Response خاسرة (losing response)
نسخة عدّلها المستخدم (user-edited version) -> Response مفضلة/فائزة
```

يمكن لذلك إنشاء Preference Data لـ Future Model Alignment، مع مراعاة Privacy أو Consent و Quality Checks.

---

## 34. Complaints و Sentiment

قد يشتكي المستخدمون صراحةً من أن Answer:

- خاطئة.
- غير ذات صلة.
- غير Grounded في Evidence.
- غير مكتملة.
- غامضة أكثر من اللازم.
- مطولة أكثر من اللازم.
- متكررة.
- فظة.

حتى Emotional Signals الغامضة مثل Frustration أو Disappointment أو Ridicule يمكن أن تساعد في كشف Interactions ضعيفة.

Sentiment خاصة بالتطبيق ولا ينبغي المبالغة في تفسيرها. يمكن للمستخدم أن يبدأ غاضبًا وينتهي راضيًا، ما قد يشير إلى أن النظام حل المشكلة بنجاح.

يمكن أن يكون Model Refusal Rate مفيدًا أيضًا: فقد تشير Responses متكررة مثل "I can't help" إلى Over-restriction أو ضعف Task Coverage.

---

## 35. Regeneration مفيدة لكنها غامضة

قد يكون المستخدم الذي يطلب Answer أخرى غير راضٍ، أو قد يريد Options فقط.

تصبح Signal أكثر معنى عند دمجها مع Context:

- هل نفذ المستخدم Regenerate بصورة متكررة؟
- هل اختار إحدى Responses بعد ذلك؟
- هل اشتكى قبل Regenerating؟
- هل تكلف Regeneration المستخدم Money أو Credits؟

إذا سأل Product أي Regenerated Response أفضل، يمكن أن تصبح Comparison Preference Data.

---

## 36. تنظيم Conversation وطولها

يمكن أن تكون Actions مثل Delete و Rename و Share و Bookmark أيضًا Signals.

يعتمد Interpretation على Context:

- قد يعني Delete Conversation سيئة، أو Content حساسة أو محرجة.
- قد يعني Rename أن Conversation ذات قيمة لكن Automatic Title ضعيفة.
- قد يعني Share أنها مفيدة للغاية، أو خاطئة بصورة مضحكة.

كذلك يكون Conversation Length غامضًا.

- Companionship Chat طويلة -> Engagement إيجابية محتملة.
- Customer-support Chat طويلة -> Problem Solving غير كفء محتمل.

ادمج Length مع **Dialogue Diversity**. فقد تشير Conversation طويلة مع Content متكررة إلى Loop.

---

## 37. تصميم Feedback: اجمعها دون تعطيل Workflow

ينبغي أن تكون Feedback Collection الجيدة:

- سهلة.
- غير مزعجة.
- Optional عندما يكون ذلك ممكنًا.
- مدمجة بصورة وثيقة مع Task الخاصة بالمستخدم.
- واضحة في معنى Signal.

ينبغي أن تكون Feedback متاحة طوال User Journey بدلًا من Final Survey فقط.

---

## 38. متى تجمع Feedback

### في البداية

استخدم Initial Calibration عندما يحتاج التطبيق إليها فعلًا، مثل Language Level أو Voice Profile أو Personal Preferences. وإلا فإن Optional Calibration تقلل Onboarding Friction.

### عندما يحدث خطأ

اسمح للمستخدمين بالإبلاغ عن Hallucinations أو Bad Refusals أو Slow Responses أو Incorrect Outputs. والأفضل أن تسمح لهم بتصحيح Result حتى يتمكنوا من إنهاء Task.

### عندما تكون Model غير واثقة

اطلب Targeted Clarification أو قدم Choices عندما تكون Uncertainty مهمة.

### عندما يكون شيء ما جيدًا بصورة استثنائية

يمكن لـ Positive Feedback تحديد High-value Features، لكن Prompts المستمرة لطلب Praise قد تملأ UX بالفوضى. ويمكن لـ Sampling لطلبات Feedback تقليل المقاطعة.

---

## 39. أفضل Feedback تأتي غالبًا من Product Actions الطبيعية

لا ينبغي أن يحتاج المستخدمون دائمًا إلى ملء Form.

أمثلة على Workflow-integrated Signals:

- اختيار Generated Image واحدة لتنفيذ Upscale لها.
- طلب Variations.
- Regenerate لكل شيء.
- Accept لـ Code Suggestion.
- Ignore للـ Suggestion ومواصلة الكتابة.
- Edit لـ AI-generated Text قبل إرسالها.

يمكن للمنتجات المدمجة ملاحظة ما يحدث بعد Generation. أما Standalone Chatbot فعادةً لا تستطيع معرفة ما إذا كان Generated Content قد استُخدم فعلًا.

[[IMAGE_NEEDED: Workflow-integrated feedback | A generated suggestion with actions accept, edit, regenerate, ignore, and share, each producing different feedback strengths | Learner should notice that useful feedback can be collected as a natural side effect of accomplishing the task]]

---

## 40. Feedback دون Context غالبًا غير كافية

تخبرك Thumbs-down أن المستخدم لم يحب شيئًا، لكنها قد لا تخبرك بالسبب.

قد يتطلب Diagnosis مفيد Surrounding Conversation Turns و Prompt و Retrieved Context و Model Version و Tool Trace.

لكن هذه Context يمكن أن تحتوي على Personal Data. يجب أن تتبع Collection متطلبات User Consent و Privacy.

كن شفافًا حول ما إذا كانت Feedback تستخدم من أجل:

- Personalization.
- Analytics.
- Product Improvement.
- Training لـ Future Models.

لا تعد أبدًا بأن Data لا تستخدم في Training أو لا تغادر Device إلا إذا كان ذلك صحيحًا فعلًا.

---

## 41. لا تطلب Feedback لا يستطيع المستخدمون تقديمها بصورة موثوقة

قد لا يعرف المستخدم أي إجابتين رياضيتين صحيحة. وإجباره على الاختيار مع ذلك ينشئ Noise.

تقوم Feedback Interfaces الجيدة بما يلي:

- تسمح للمستخدمين بقول "I don't know" عندما يكون ذلك مناسبًا.
- تشرح Choices باستخدام Labels أو Tooltips.
- تتجنب Confusing Icon Placement.
- تتجنب إجبار المستخدم على Extra Work غير ضرورية بعد Negative Rating.

تُعد Feedback UI جزءًا من Data Pipeline. وتنتج UI السيئة Labels سيئة.

---

## 42. Public مقابل Private Feedback تغير السلوك

قد يتصرف المستخدمون بصورة مختلفة عندما تكون Feedback مرئية للآخرين.

يمكن لـ Private Feedback تشجيع الصراحة لأن المستخدمين يشعرون بأنهم أقل تعرضًا للحكم.

يمكن لـ Public Feedback تحسين Discoverability و Social Explanation لكنها قد تشوه Behavior أيضًا.

لذلك فإن Signal Visibility ليست مجرد قرار UI؛ بل يمكنها تغيير Distribution و Reliability الخاصة بـ Feedback Data نفسها.

---

## 43. Feedback هي Data متحيزة

لا ينبغي أبدًا التعامل مع Feedback بوصفها Objective Truth تلقائيًا.

يصف الفصل عدة Biases.

### انحياز التساهل (Leniency Bias)

قد يعطي الأشخاص Ratings إيجابية أكثر من اللازم لأن ذلك أسهل اجتماعيًا أو يتطلب Follow-up Effort أقل.

### العشوائية (Randomness)

قد ينقر المستخدمون Response دون قراءة جميع Choices بعناية.

### انحياز الموضع (Position Bias)

قد تحصل Option الأولى على Clicks أكثر لمجرد ظهورها أولًا.

### انحياز Preference أو Length

قد يفضل المستخدمون Response أطول لأن Length أسهل في الملاحظة من Factual Quality.

### انحياز الحداثة (Recency Bias)

قد يفضل المستخدمون Answer التي شاهدوها في وقت أحدث.

قِس Feedback Distributions ونفذ Experiments لفهم هذه التأثيرات داخل Product الخاص بك.

## 44. حلقات الملاحظات المتدهورة (Degenerate Feedback Loops)

تحصل على Feedback فقط على ما يختار النظام عرضه.

ينشئ ذلك Loop خطيرة:

```text
ترتب Model الخيار A أعلى قليلًا من B
 -> يحصل A على Exposure أكبر
 -> يحصل A على Clicks أكثر
 -> يفسر النظام Clicks كدليل على أن A أفضل
 -> يحصل A على Exposure أكبر بدرجة أكبر
```

يمكن أن تتضخم فروق أولية صغيرة. وتشمل التأثيرات المرتبطة Exposure Bias و Popularity Bias و Filter Bubbles.

يمكن للديناميكية نفسها تغيير هوية Application كاملة: إذا كافأت مجموعة صغيرة Content Type واحدة، فقد يولد النظام منها أكثر، فيجذب مزيدًا من المستخدمين الذين يحبونها، مما يعزز Cycle.

[[IMAGE_NEEDED: Degenerate feedback loop | Ranking -> exposure -> user feedback -> model update -> stronger ranking, shown as an amplifying cycle | Learner should notice that model outputs influence the data that later trains the model]]

---

## 45. User Preference ليست دائمًا مساوية للحقيقة أو الفائدة

يمكن لـ Training غير الانتقائي على User Approval أن يعلم Model إنتاج ما تعتقد أن المستخدمين يريدونه بدلًا مما هو Accurate أو Beneficial.

قد تصبح Model **Sycophantic**، فتوافق User View لكسب Positive Feedback.

لذلك ينبغي دمج User Feedback مع Signals أخرى:

- Factual Evaluation.
- Safety Requirements.
- Expert Review.
- Product Goals.
- أخذ عينات متنوعة من المستخدمين (Diverse User Sampling).
- Counterfactual أو Exploration Data عندما يكون ذلك مناسبًا.

Feedback Input قيمة، وليست Objective Function لا يمكن التشكيك فيها.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> ينبغي أن يبدأ تطبيق AI في Production بأكمل Architecture ممكنة.

**لماذا هذا خطأ:** تضيف Components غير الضرورية Latency و Cost و Operational Complexity و Failure Modes.

### المفهوم الخاطئ 2

> يمكن لـ Guardrails القضاء على مخاطر AI.

**لماذا هذا خطأ:** تقلل المخاطر لكنها لا تضمن سلوكًا مثاليًا.

### المفهوم الخاطئ 3

> المزيد من Guardrails أفضل دائمًا.

**لماذا هذا خطأ:** يمكن للفحوص الإضافية زيادة False Refusals و Latency و Cost و User Frustration.

### المفهوم الخاطئ 4

> Router و Gateway هما الشيء نفسه.

**لماذا هذا خطأ:** تقرر Router أين ينبغي أن تذهب Request؛ بينما توفر Gateway واجهة موحدة ومحكومة إلى Model Endpoints و Policies.

### المفهوم الخاطئ 5

> إذا كانت Queryان متشابهتين دلاليًا، فإن Answer الخاصة بهما قابلة للتبادل.

**لماذا هذا خطأ:** يمكن لفروق دلالية صغيرة أو User Context أو Time أن تتطلب Answers مختلفة.

### المفهوم الخاطئ 6

> Monitoring تعني جمع أكبر عدد ممكن من Metrics.

**لماذا هذا خطأ:** ينبغي اختيار Metrics لاكتشاف حالات الفشل والفرص المهمة.

### المفهوم الخاطئ 7

> Metrics و Logs و Traces مكررة.

**لماذا هذا خطأ:** تقوم Metrics بالتجميع، وتحفظ Logs الأحداث، وتعيد Traces بناء End-to-end Execution Paths.

### المفهوم الخاطئ 8

> Thumbs-up هي Ground-truth Training Data نظيفة.

**لماذا هذا خطأ:** يمكن أن تكون Feedback متحيزة أو عشوائية أو غامضة أو ناتجة عن UI Position بدلًا من الجودة.

### المفهوم الخاطئ 9

> Conversations الأطول تعني دائمًا Engagement أفضل.

**لماذا هذا خطأ:** في Productivity Applications، قد تعني Conversations الطويلة أن النظام يفشل في حل Task.

### المفهوم الخاطئ 10

> Optimization لما يوافق عليه المستخدمون فقط سيحسن Truthfulness بالضرورة.

**لماذا هذا خطأ:** يمكن لـ Approval-driven Learning تضخيم Bias أو Sycophancy.

## المصطلحات الأساسية (Key Terminology)

| المصطلح | المعنى |
|---|---|
| بناء Context (Context Construction) | تزويد Model بمعلومات أو Tools خارجية خاصة بكل Query. |
| حاجز Input (Input Guardrail) | Check أو Transformation تُطبق قبل Main Model أو Tool Step. |
| حاجز Output (Output Guardrail) | Check و Response Policy تُطبق على Generated Output. |
| رفض خاطئ (False Refusal) | Legitimate Request يمنعها نظام مفرط في التقييد. |
| مكوّن Router | Component تحدد أي Model أو Solution أو Action تتعامل مع Request. |
| مصنف Intent (Intent Classifier) | Model أو Classifier تتنبأ بـ Task أو Intent الخاصة بالمستخدم لأغراض Routing. |
| بوابة Model (Model Gateway) | واجهة موحدة ومحكومة لعدة Model Providers أو Endpoints. |
| ذاكرة Exact Cache | Cache يعاد استخدامها فقط مع Exact Matching Keys. |
| ذاكرة Semantic Cache | Cache يعاد استخدامها للـ Queries المتشابهة بدرجة كافية استنادًا إلى Embeddings أو Similarity. |
| سياسة LRU | سياسة إخلاء Cache للأقل استخدامًا مؤخرًا (Least Recently Used Cache-eviction Policy). |
| سياسة LFU | سياسة إخلاء Cache للأقل استخدامًا تكرارًا (Least Frequently Used Cache-eviction Policy). |
| قابلية الرصد (Observability) | Instrumentation لنظام بحيث يمكن Diagnosis لحالات الفشل من Runtime Information المجمعة. |
| مقياس MTTD | متوسط زمن الاكتشاف (Mean Time to Detection). |
| مقياس MTTR | Mean Time to Response أو Resolution. |
| مقياس CFR | معدل فشل التغييرات (Change Failure Rate). |
| سجل Log | Append-only Record لـ Event. |
| تتبع Trace | Timeline مترابطة لـ Events ذات صلة عبر Request أو Workflow واحدة. |
| ظاهرة Drift | تغير في Prompts أو Users أو Models أو Data أو System Behavior مع الزمن. |
| منسق Orchestrator | Layer تنسق Components و Data Flow عبر AI Pipeline. |
| أسلوب Chaining | تركيب Components بحيث تغذي Output من إحداها Component أخرى. |
| Feedback صريحة (Explicit Feedback) | Feedback يقدمها المستخدم عمدًا استجابةً لطلب Feedback. |
| Feedback ضمنية (Implicit Feedback) | Feedback تُستنتج من User Behavior أو Actions الطبيعية. |
| حلقة Data Flywheel | استخدام Product ينشئ Data تساعد على تحسين Product، مما يجذب Usage أكبر. |
| إنهاء مبكر (Early Termination) | يوقف المستخدم Response أو Workflow أو يتركها قبل الاكتمال. |
| Data تفضيلات (Preference Data) | Evidence مقارنة تشير إلى تفضيل Response أو Action على أخرى. |
| تنوع Dialogue (Dialogue Diversity) | تنوع Tokens أو Topics أو Actions عبر Conversation. |
| انحياز Leniency | الميل إلى Rating أكثر إيجابية مما تستحقه الحالة. |
| انحياز Position | تأثر Feedback بمكان عرض Option. |
| انحياز Recency | Preference لـ Option تم Encounter لها لاحقًا أو بصورة أحدث. |
| حلقة Feedback منحرفة (Degenerate Feedback Loop) | تؤثر Predictions في Exposure أو Feedback التي تعزز لاحقًا Predictions أخرى. |
| سلوك Sycophancy | توافق Model مع المستخدمين لكسب Approval بدلًا من إعطاء الأولوية للدقة. |

## الفكرة التي ينبغي الاحتفاظ بها (Retain This Idea)

**منتجات AI الناجحة أنظمة، وليست مجرد Model Calls. أضف Architecture فقط عندما تحل مشكلة حقيقية، ونفذ Instrumentation لكل Component مهمة، وتعامل مع User Feedback بوصفها Data كثيرة Noise لكنها قيّمة. تأتي الميزة طويلة المدى من Loop تحسن فيها Production Behavior كلًا من Evaluation و Data و Models و Product Design من دون السماح للتعقيد أو Privacy Risk أو Feedback المتحيزة بالسيطرة على النظام.**
