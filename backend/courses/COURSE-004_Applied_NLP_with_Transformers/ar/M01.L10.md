## 1. متى ينبغي أن تدرّب من الصفر؟

اعتمد معظم هذا المقرر على Transfer Learning لأن Labeled Task Data تكون محدودة عادة. والبدء من Pretrained Transformer أرخص بكثير في المعتاد من إنشاء Model بنفسك.

يستكشف الفصل 10 الحالة المقابلة: لديك Domain Corpus ضخمة جدًا وتريد بناء Language Model متخصصة فيها.

المشروع التطبيقي هو CodeParrot، وهي GPT-like Model يتم تدريبها على توليد Python Code.

يصبح Training from Scratch أكثر منطقية عندما:

- تمتلك كمية هائلة من Domain Data،
- يكون الـ Domain مختلفًا بصورة كبيرة عن Corpora التي تدربت عليها Models المتاحة،
- تمثل Tokenizer الحالية الـ Domain بكفاءة ضعيفة،
- تمتلك Compute كافيًا لـ Pretraining،
- تحتاج إلى تحكم مباشر في Pretraining Corpus والـ Tokenizer.

قاعدة قرار مفيدة:

```text
Small/Medium Domain Corpus
        → Adapt أو Fine-tune Existing Model

Very Large Distinct Corpus + Sufficient Compute
        → فكّر في Custom Tokenizer + Model Pretraining from Scratch
```

## 2. الـ Model ترث خصائص الـ Corpus

تتعلم Pretrained Model الأنماط الموجودة في أي بيانات تضعها داخل Pretraining Corpus.

وهذا يشمل الأنماط المفيدة، لكنه يشمل العيوب أيضًا.

يسلط الفصل الضوء على مشكلات ظهرت في Large Public Corpora، مثل:

- مواد Machine-translated غير مرغوبة،
- Filtering Choices تزيل بعض Language Varieties بصورة غير متوازنة،
- Explicit-content Filtering قد يحذف Vocabulary مشروعة،
- Copyright Problems،
- Genre Imbalance،
- Overrepresentation أو Underrepresentation لبعض الفئات والموضوعات.

وهذا يعني أن Dataset Design جزء من Model Design.

إذا كانت Corpus منحازة أوغير متوازنة، فقد تعيد الـ Model إنتاج هذا الانحياز في Generated Outputs.

يوضح الفصل ذلك بمقارنة GPT وGPT-2 Models متقاربة في الحجم لكنها دُرِّبت على Corpora مختلفة، ثم ملاحظة اختلاف واضح في أسلوب النص المولّد.

الفكرة الأساسية:

> **Pretraining Data تؤثر في ما تعتبره الـ Model لغة طبيعية أوشائعة.**

[[IMAGE_NEEDED: Corpus-to-model behavior pipeline | A large dataset containing useful patterns plus bias/noise/copyright/privacy risks feeding pretraining, followed by a model whose generated outputs reflect both the useful and undesirable corpus patterns | Learner should notice that corpus choices propagate into model behavior]]

## 5. لماذا ندرّب Domain-specific Tokenizer؟

Pretrained Model وTokenizer الخاصة بها عبارة عن زوج مترابط.

إذا استخدمت Existing Model، فيجب عادة استخدام الـ Tokenizer التي تم Pretraining للـ Model معها.

لكن عندما تدرّب Model جديدة، قد تكون Tokenizer من Domain مختلفة مهدرة وغير كفؤة.

توضح أمثلة الفصل المشكلة:

- Tokenizer مدرَّبة على Filtered Web Text قد تقسّم كلمات عادية بطريقة غير متوقعة،
- Tokenizer مدرَّبة على French فقط قد تمثل English بكفاءة ضعيفة،
- Natural-language Tokenizer قد تتعامل بصورة سيئة مع Python Indentation.

تؤثر كفاءة Tokenization لأن Transformer Context تُقاس بوحدة Tokens لا Characters.

إذا احتاجت Tokenizer إلى ضعف عدد Tokens لتمثيل الـ Code نفسه، فأنت فعليًا تفقد نصف المحتوى المفيد الذي يمكن إدخاله داخل Fixed Context Window.

### جودة الـ Tokenizer ليست مجرد Vocabulary Size

يقترح الفصل Metrics مثل:

- Subword Fertility — متوسط عدد Subtokens لكل Original Word،
- Continued-word Proportion — نسبة الكلمات التي تُقسّم إلى عدة أجزاء،
- Coverage/Unknown-token Measures،
- Robustness لـ Noisy أو Misspelled Inputs،
- وفي النهاية Downstream Model Performance.

## 6. Byte-level BPE مناسبة جدًا للكود

تعتمد Python Syntax على Whitespace، وخصوصًا Indentation.

Tokenizer تحذف Whitespace أوتطبّعها بعنف قد تدمر Structure مفيدة.

لذلك يبدأ الفصل من GPT-2-style Byte-level BPE Tokenizer.

### لماذا Byte Level؟

يمكن تمثيل UTF-8 Text باستخدام 256 Byte Value فقط كـ Base Alphabet.

وهذا يضمن تمثيل أي Unicode Input تقريبًا من دون الحاجة إلى Character Vocabulary ضخمة.

### لماذا نستخدم BPE فوق Bytes؟

استخدام Bytes منفردة فقط سيجعل Sequences طويلة جدًا.

تتعلم Byte-Pair Encoding دمج Frequent Combinations وتحويلها إلى Tokens أكبر.

النتيجة حل وسط:

```text
Tiny Byte Vocabulary
      +
Learned Frequent Byte Combinations
      ↓
Compact Vocabulary قادرة على تمثيل أي Text
```

في GPT-2 Tokenizer Display، قد تمثل Special Visible Characters الـ Whitespace أو Newline Bytes. وهذا يسمح للـ Tokenizer بالحفاظ على Code Formatting.

[[IMAGE_NEEDED: Byte-level BPE for Python code | A short indented Python function mapped first into byte-aware symbols for spaces and newlines, then frequent byte combinations merged into larger BPE tokens | Learner should notice that indentation and line breaks remain represented rather than being discarded]]

## 8. اختر Pretraining Objective قبل Architecture

أفضل Architecture تعتمد على ما تريد أن تتعلمه الـ Model.

يقارن الفصل بين ثلاثة Objectives.

### نمذجة اللغة السببية (Causal Language Modeling — CLM)

التنبؤ بالـ Next Token من Previous Tokens.

```text
def area(a, b):
    return  → توقّع Next Token
```

هذا يتوافق طبيعيًا مع Code Autocompletion، لذلك تكون GPT-style Decoder-only Model اختيارًا مناسبًا.

### نمذجة اللغة المقنَّعة (Masked Language Modeling — MLM)

قم بعمل Mask أو Corruption لبعض Tokens ثم أعد بناء الـ Original Tokens.

هذا مناسب لتعلم General Representations من أجل Downstream Tasks لاحقًا، ويتوافق مع BERT-like Encoder Pretraining.

### التدريب من تسلسل إلى تسلسل (Sequence-to-sequence Training)

إنشاء Input/Output Pairs مثل:

```text
الكود (Code) → التوثيق (Documentation)
التوثيق (Documentation) → الكود (Code)
```

وهذا يتوافق طبيعيًا مع Encoder-decoder Architectures مثل T5 أو BART.

[[IMAGE_NEEDED: Three pretraining objectives for code | Three side-by-side mini diagrams: CLM predicts future code with a decoder, MLM reconstructs masked code with an encoder, and seq2seq maps code to comments or comments to code with an encoder-decoder | Learner should notice that task objective determines the appropriate architecture]]

يستهدف CodeParrot Autocompletion، لذلك يختار الفصل Causal Language Modeling.

## 10. أطعم الـ Model Sequences كاملة وبطول ثابت

يكون GPU Training أكثر كفاءة عندما تمتلك Batches Shapes موحدة.

لكن Source Files تختلف بشدة في الطول.

يحل الفصل هذه المشكلة عبر:

1. قراءة عدة Source Files،
2. عمل Tokenization لها،
3. إدخال End-of-sequence Token بين الملفات،
4. Concatenate لكل شيء في Long Token Stream،
5. تقسيم الـ Stream إلى Fixed-size Chunks مثل 1,024 Token.

```text
رموز الملف A (File A Tokens) + EOS + رموز الملف B (File B Tokens) + EOS + رموز الملف C (File C Tokens)
                         ↓
تدفق طويل جدًا من الرموز (Very Long Token Stream)
                         ↓
[1024] [1024] [1024] [1024] ...
```

[[IMAGE_NEEDED: Constant-length CLM preprocessing | Several code files of different lengths are tokenized and concatenated with EOS markers, then sliced into equal 1024-token chunks | Learner should notice that file boundaries are preserved with EOS tokens while training sequences stay fully packed]]

يقلل ذلك كميات Padding الكبيرة، ويحافظ على Training Compute مركزة على Real Tokens.

ويقدّر الفصل Average Characters-per-token Ratio لتحديد مقدار Raw Text الذي يجب Buffer له قبل Tokenization وChunking.

## 13. اجعل Training Jobs الكبيرة تلائم GPU Memory المحدودة

يستخدم الفصل تقنيتين مرتبطتين بالذاكرة.

### Gradient Accumulation

إذا كان Desired Batch أكبر من أن يدخل دفعة واحدة في Memory، قم بمعالجة عدة Microbatches وتأخير Optimizer Update.

```text
دفعة صغيرة 1 (Microbatch 1) ┐
دفعة صغيرة 2 (Microbatch 2) │ تجميع الـ Gradients (Accumulate Gradients)
...                         │
دفعة صغيرة N (Microbatch N) ┘
       ↓
خطوة المُحسِّن (Optimizer Step)
```

### Gradient Checkpointing

عادةً يحتفظ Training بعدد كبير من Intermediate Activations من Forward Pass لاستخدامها أثناء Backpropagation.

أما Gradient Checkpointing فتحتفظ بعدد أقل من Activations وتعيد حساب بعض منها لاحقًا.

الـ Trade-off:

```text
GPU Memory أقل
      ↕
Compute أكثر / Training أبطأ
```

يذكر الفصل تباطؤًا يقارب 20% مقابل توفير الذاكرة في إعداده.

## 14. التوازي الموزع للبيانات (Data Distributed Parallelism — DDP)

تستخدم Accelerate Data Parallelism في Multi-GPU Training Run الخاصة بالفصل.

تحتفظ كل GPU بنسخة كاملة من الـ Model.

العملية هي:

1. يحصل كل Worker/GPU على Batch مختلفة،
2. تنفذ كل Model Copy Forward وBackward Passes،
3. يتم Average للـ Gradients بين Workers،
4. تطبق كل Worker التحديث المتوسط نفسه،
5. يستمر التدريب مع Batches جديدة.

[[IMAGE_NEEDED: Four-GPU data parallel training | A main data stream splits into four batches sent to four GPUs, each GPU contains the same model, local gradients flow into an averaging/reduce operation, and the averaged gradient is sent back to all four model copies | Learner should notice that data is divided while each GPU maintains a synchronized copy of the model]]

تزيد DDP الـ Throughput وEffective Batch Size، لكنها تفترض أن الـ Model نفسها تستطيع الدخول داخل Worker واحدة. إذا كانت الـ Model أكبر من Memory الموجودة على GPU واحدة، فسنحتاج إلى Model-parallel Strategies أكثر تقدمًا.

## 18. قيّم الكود بتنفيذه، لا بمجرد مقارنة النص

Text-overlap Metric مثل BLEU غير مناسبة بدرجة كبيرة لـ Code Generation.

لماذا؟

قد يكون Programان متكافئين وظيفيًا رغم اختلاف:

- Variable Names،
- Helper Functions،
- Formatting،
- Control Structures.

Lexical Metric قد تعاقب هذه الاختلافات غير المؤذية.

لكن Code تملك أداة تقييم أقوى: Unit Tests.

```text
Prompt
  ↓
ولّد عدة Candidate Programs
  ↓
شغّل Hidden Unit Tests
  ↓
احسب عدد Candidates التي تعمل بصورة صحيحة
```

[[IMAGE_NEEDED: Functional evaluation for generated code | A programming prompt branches into several generated code candidates; each candidate runs through the same unit-test suite, producing pass/fail results; the final metric is based on functional success rather than text overlap | Learner should notice that semantic correctness of code is best checked by execution]]

يشير الفصل إلى أن هذا Executable-evaluation Style أفضل بكثير لتقييم Code Models بصورة منهجية من N-gram Overlap.

```text
6. قيّم Tokenizer Efficiency
              ↓
7. اختر Pretraining Objective
              ↓
8. أنشئ Model من Configuration بأوزان جديدة
              ↓
9. ابنِ Fully Packed Constant-length Batches
              ↓
10. اختبر الـ Pipeline على Small Model
              ↓
11. وسّع باستخدام Accelerate / Distributed Training
              ↓
12. تابع Loss وPerplexity وCheckpoints
              ↓
13. افحص Generations
              ↓
14. قيّم الـ Downstream Behavior الحقيقي
```

تدريب Neural Network ليس سوى مرحلة واحدة. Corpus Engineering وTokenization وData Loading وDistributed Systems وMonitoring وEvaluation كلها مهمة بالقدر نفسه.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Training from Scratch مجرد Fine-tuning لعدد أكبر من Epochs

> حمّل Pretrained Checkpoint واستمر في Training فترة طويلة.

### لماذا هذا خطأ

From-scratch Pretraining تبدأ بـ Fresh Model Weights، وقد تستخدم Tokenizer جديدة تم تدريبها أيضًا من الصفر أو للـ Domain. أما Fine-tuning فتبدأ من Pretrained Weights.

### المفهوم الخاطئ 2: المزيد من Pretraining Data أفضل تلقائيًا

> إذا كانت الـ Corpus ضخمة، فلن تعود الجودة مهمة.

### لماذا هذا خطأ

تتعلم الـ Model عيوب الـ Corpus أيضًا. Noise وBias وDuplication وLicensing Problems وSensitive Information كلها تصبح جزءًا من Pretraining Risk.

### المفهوم الخاطئ 3: أي Tokenizer جيدة بما يكفي

> Tokenization تؤثر فقط في Preprocessing ولا تؤثر في Model Efficiency.

### لماذا هذا خطأ

Tokenizer غير الكفؤة تستهلك Context Tokens أكثر وتزيد Transformer Computation. ويمكن لـ Domain-specific Tokenizer تمثيل Source نفسها بعدد Tokens أقل.

### المفهوم الخاطئ 4: Multi-GPU Training تعني تقسيم Model واحدة إلى أجزاء

> كل GPU تخزن جزءًا مختلفًا من Network في DDP العادية.

### لماذا هذا خطأ

في Data Parallelism، تحتفظ كل Worker بنسخة كاملة من الـ Model وتعالج Data مختلفة، ثم تتم مزامنة Gradients بين Workers.

### المفهوم الخاطئ 5: Perplexity منخفضة تثبت أن الكود صحيح

> إذا كانت Language Model تتنبأ بالـ Tokens جيدًا، فلا بد أن كل Program تولده سيعمل.

### لماذا هذا خطأ

Perplexity تقيس Token Prediction. جودة الكود الوظيفية تحتاج إلى Execution-based Tests أو Downstream Evaluation أخرى.

## المصطلحات الرئيسية

| المصطلح | المعنى |
|---|---|
| التدريب من الصفر (Pretraining from Scratch) | تدريب Fresh Model Weights على Corpus ضخمة قبل Downstream Adaptation |
| Pretraining Corpus | Dataset كبيرة تُستخدم لتعلم General/Domain Representations |
| Memory Mapping | الوصول إلى Large On-disk Data من خلال Mapped Memory بدل تحميلها بالكامل إلى RAM |
| Streaming | قراءة Examples تدريجيًا من دون Materializing للـ Dataset كاملة محليًا |
| Tokenizer على مستوى البايت (Byte-level Tokenizer) | Tokenizer تستخدم Byte Values كـ Base Alphabet |
| BPE | Byte-Pair Encoding؛ تبني Tokens أكبر عبر دمج Frequent Token Pairs تدريجيًا |
| Subword Fertility | متوسط عدد Subtokens المستخدمة لترميز Word واحدة |
| نمذجة اللغة السببية (Causal Language Modeling) | التنبؤ بالـ Future/Next Tokens من Previous Context |
| نمذجة اللغة المقنَّعة (Masked Language Modeling) | إعادة بناء Tokens تم Mask أو Corrupt لها عمدًا |
| Sequence-to-sequence | تحويل Input Sequence إلى Output Sequence منفصلة |
| Fresh Initialization | إنشاء Model Weights من Configuration بدل تحميل Checkpoint |
| EOS | End-of-sequence Marker تُستخدم للفصل بين Documents/Examples |
| مجموعة بيانات ثابتة الطول (Constant-length Dataset) | Dataset تنتج Fixed-size Fully Packed Token Sequences |
| Accelerate | مكتبة تبسط Mixed-precision وDistributed Training Setup |
| Gradient Accumulation | جمع Gradients عبر Microbatches قبل Optimizer Update |
| Gradient Checkpointing | استبدال جزء من Activation Memory بإعادة الحساب أثناء Backpropagation |
| DDP | Distributed Data Parallelism باستخدام Synchronized Model Replicas عبر Workers |
| Perplexity | Exponentiated Language-model Cross-entropy Loss؛ الأقل أفضل |
| Functional Evaluation | تقييم Generated Code بتنفيذ Tests بدلًا من الاكتفاء بمقارنة النص |

## اختبر نفسك

قبل المتابعة، تأكد أنك تستطيع الإجابة عن الأسئلة التالية:

1. متى يكون Training from Scratch أكثر منطقية من Fine-tuning عادي؟
2. لماذا يمكن لـ Corpus Bias أن تؤثر في Model Generations؟
3. ما الفرق بين Memory Mapping وStreaming؟
4. لماذا تؤثر Tokenizer Efficiency في Effective Context Length؟
5. لماذا تكون Byte-level BPE مناسبة لـ Python Code؟
6. كيف تختلف Causal LM عن Masked LM وSeq2seq Training؟
7. ماذا يعني `from_config()` مقارنة بـ `from_pretrained()`؟
8. لماذا نربط Documents باستخدام EOS Markers قبل Chunking؟
9. ماذا تفعل `prepare()` في Accelerate بصورة مفاهيمية؟
10. كيف تحل Gradient Accumulation وGradient Checkpointing مشكلتين مختلفتين؟
11. ما الذي تتم مزامنته في DDP؟
12. لماذا تكون Unit-test Evaluation أقوى من BLEU في Code Generation؟

**تدريب Transformer من الصفر مشروع Systems كامل: تحدد الـ Corpus ما الذي يمكن للـ Model أن تتعلمه، وتحدد الـ Tokenizer مدى كفاءة تمثيل هذه الـ Corpus، ويحدد الـ Objective الـ Architecture المناسبة، بينما يحدد Data Loading القابل للتوسع وDistributed Training هل Pretraining ممكنة حسابيًا أصلًا. وفي النهاية يجب الحكم على Model Quality من خلال Downstream Behavior الحقيقي، وليس Pretraining Loss وحدها.**
