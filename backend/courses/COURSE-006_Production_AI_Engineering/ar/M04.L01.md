## نتائج التعلم (Learning Outcomes)

بحلول نهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- تطبيق التطوير القائم على Evaluation عبر تحديد النجاح قبل بناء تطبيق AI.
- تنظيم معايير اختيار Model ضمن قدرات Domain، وجودة Generation، واتباع التعليمات، والتكلفة، و Latency، والحجم، والقيود التشغيلية.
- التمييز بين الاتساق الواقعي المحلي (Local Factual Consistency) والاتساق الواقعي العالمي (Global Factual Consistency).
- شرح عدة أساليب للتحقق من Factuality، بما فيها AI Judges و Self-verification والتحقق المدعوم بـ Search و Textual Entailment.
- تصميم Safety Evaluations مناسبة لمخاطر التطبيق.
- تقييم سلوك Instruction Following باستخدام قيود قابلة للتحقق تلقائيًا ومعايير Subjective.
- الموازنة بين الجودة و Latency والتكلفة باستخدام Hard Requirements و Soft Preferences.
- التمييز بين Hard Model Attributes و Soft Attributes عند اختيار Model.
- مقارنة Model APIs و Self-hosting من حيث Privacy و Data Lineage والأداء والوظائف والتكلفة والتحكم وقيود Deployment.
- تقييم ما إذا كان Public Benchmark ذا صلة وموثوقًا بالنسبة إلى تطبيقك.
- شرح Benchmark Saturation و Correlation و Aggregation و Contamination.
- تصميم Evaluation Pipeline متكاملة تقيم Components و Turns و Tasks و Metrics وسلوك Production.
- بناء Scoring Rubrics مرتبطة بنتائج العمل و Usefulness Thresholds.
- استخدام Data Slices و Bootstrap Analysis و Experiment Tracking لتحسين موثوقية Evaluation.

## 1. التطوير القائم على Evaluation (Evaluation-driven Development)

لا يكون Model مفيدًا إلا إذا نجح في الغرض الذي تهتم به. وهذا يعني أن Evaluation ينبغي أن تُصمم **قبل** اكتمال بناء التطبيق، لا أن تُضاف كفكرة لاحقة.

يسمي الفصل هذا النهج **Evaluation-driven Development**. والفكرة مستوحاة من Test-driven Development في Software Engineering:

```text
هندسة البرمجيات (software engineering):
الاختبارات (tests) -> التنفيذ (implementation)

هندسة AI (AI engineering):
معايير Evaluation (evaluation criteria) -> تطوير التطبيق (application development)
```

قبل إنفاق موارد كبيرة على تطبيق، اسأل:

- ما القيمة التجارية أو قيمة المستخدم التي يجب أن ينشئها هذا التطبيق؟
- كيف سنعرف ما إذا كان ينشئ تلك القيمة؟
- ما حالات الفشل التي قد تجعله غير آمن أو غير قابل للاستخدام؟
- ما مستوى الجودة الذي يبدو مثيرًا للإعجاب فقط، وما المستوى الذي يصبح مفيدًا فعلًا؟

يكون تبرير التطبيقات ذات النتائج الواضحة والقابلة للقياس وتحسينها أسهل. يمكن ربط Recommendation Systems بـ Engagement أو سلوك الشراء. ويمكن ربط Fraud Systems بالخسائر التي تم منعها. وغالبًا يمكن اختبار Code المولدة عبر Execution.

لا يعني ذلك أن الفرق ينبغي أن تبني التطبيقات سهلة القياس فقط. بل يعني أن التطبيقات الصعبة تحتاج إلى استثمار أكثر تعمدًا في Evaluation Infrastructure.

## 2. البدء بمعايير Evaluation خاصة بالتطبيق (Application-specific Evaluation Criteria)

يجمع الفصل المعايير الشائعة في أربع فئات عامة:

1. **قدرة خاصة بـ Domain (Domain-specific Capability)** — هل يستطيع Model تنفيذ نوع العمل الذي يتطلبه Domain الخاص بك؟
2. **قدرة Generation (Generation Capability)** — هل Outputs المولدة مفيدة و Faithful وآمنة ومترابطة أو عالية الجودة بطريقة أخرى؟
3. **قدرة اتباع التعليمات (Instruction-following Capability)** — هل يتبع Model فعلًا التعليمات والقيود التي تعطيها له؟
4. **التكلفة و Latency** — هل تستطيع تحمل تكلفة تشغيل النظام، وهل هو سريع بما يكفي لتجربة المنتج؟

تخيل أداة تلخيص للعقود القانونية. قد تسأل:

- هل يفهم Model المحتوى القانوني؟
- هل Summary متسقة واقعيًا مع العقد؟
- هل تتبع Summary الطول والتنسيق المطلوبين؟
- كم تستغرق من الوقت وكم تكلف؟

لا تستطيع Score إجمالية واحدة الإجابة عن كل هذه الأسئلة.

## 3. القدرة الخاصة بـ Domain (Domain-specific Capability)

يجب أولًا أن يمتلك Model القدرات التي يحتاجها التطبيق. يحتاج Coding Agent إلى Coding Ability. ويحتاج تطبيق Translation إلى اللغات المطلوبة. ويحتاج Scientific Assistant إلى Knowledge و Reasoning Ability ذات الصلة.

تكون هذه القدرات مقيدة بـ Training Data و Architecture وحجم Model و Training Process الخاصة به.

### استخدام Exact Evaluation عندما يكون ذلك ممكنًا (Use Exact Evaluation When Possible)

تُعد Coding Tasks مثالًا قويًا. يمكن تنفيذ Code المولدة والتحقق من Functional Correctness الخاصة بها. لكن Correctness وحدها قد لا تكون كافية.

قد تعيد SQL Query مولدة Rows الصحيحة لكنها تكون بطيئة لدرجة تجعلها غير قابلة للاستخدام. لذلك قد تشمل Evaluation:

- صحة Execution.
- Runtime.
- Memory Usage.
- سهولة القراءة أو Maintanability.

غالبًا يمكن قياس العناصر الثلاثة الأولى بدقة. أما Readability فقد تحتاج إلى Human Judgment أو AI Judgment.

### لماذا تحظى Multiple-choice Benchmarks بالشعبية (Why Multiple-choice Benchmarks Are Popular)

تحول كثير من Domain Benchmarks أسئلة Knowledge أو Reasoning مفتوحة النهاية إلى Multiple-choice Questions لأن الإجابات تصبح أسهل في التحقق والنتائج أسهل في إعادة الإنتاج.

بالنسبة إلى سؤال يحتوي على أربعة Options وإجابة صحيحة واحدة، يمنح Random Guessing خط أساس يبلغ 25%. ويُعد Classification حالة خاصة مرتبطة بذلك حيث يعاد استخدام Answer Categories نفسها عبر الأمثلة.

ومع ذلك، تختبر MCQs بصورة أساسية **Recognition أو Selection**. وهي ليست قياسًا كاملًا لقدرة Open-ended Generation.

كما يمكن للتغييرات الصغيرة في تنسيق Prompt أو طريقة عرض Options أن تغير سلوك Model، لذلك فإن تصميم Benchmark مهم.

## 4. قدرة Generation (Generation Capability)

دُرست Open-ended Generation منذ وقت طويل في Natural Language Generation. وشملت Metrics التقليدية:

- **Fluency:** هل النص طبيعي من الناحية النحوية؟
- **Coherence:** هل يتبع النص بنية منطقية؟
- **Faithfulness:** هل يحافظ المحتوى المولد على معنى المصدر؟
- **Relevance:** هل تركز Output على ما يهم؟

غالبًا ما تكون Foundation Models الحديثة شديدة Fluency بالفعل، لذلك تصبح Failure Modes الأخرى أكثر أهمية. ومن الفئتين الرئيسيتين اللتين يؤكد عليهما الفصل **Factual Consistency** و **Safety**.

## 5. الاتساق الواقعي (Factual Consistency)

يمكن لـ Response سلسة أن تحتوي رغم ذلك على معلومات غير مدعومة أو خاطئة. ولذلك يكون Factual Consistency معيار Evaluation حاسمًا في كثير من التطبيقات.

يفصل الفصل بين حالتين.

### الاتساق الواقعي المحلي (Local Factual Consistency)

قيّم Output مقابل Context صريحة.

أمثلة:

- ينبغي أن تكون Summary مدعومة بـ Source Document الخاصة بها.
- ينبغي أن تتوافق إجابة Customer Support مع سياسة الشركة.
- ينبغي أن تكون إجابة RAG مدعومة بـ Retrieved Passages.

إذا كانت Context تقول شيئًا وكانت Response تقول عكسه، تكون Response غير متسقة محليًا حتى إذا صادف أن Response تتطابق مع حقيقة خارجية ما.

### الاتساق الواقعي العالمي (Global Factual Consistency)

قيّم Output مقابل Open-world Knowledge. وهذا أصعب لأن النظام يجب أولًا أن يحدد أي External Sources موثوقة.

غالبًا لا يكون الجزء الصعب هو المقارنة، بل تحديد ما هي الحقائق فعلًا.

[[IMAGE_NEEDED: Local versus global factual consistency | A split diagram where local factuality compares an answer directly against provided context, while global factuality first retrieves trusted external evidence and then verifies the answer | Learner should notice that global verification adds an evidence-discovery problem]]

### تصميم اختبارات Factuality حول أنماط Hallucination المعروفة (Design Factuality Tests Around Known Hallucination Patterns)

يوصي الفصل بتحليل Outputs لاكتشاف الأماكن التي يكثر فيها Hallucination لدى Model، ثم تمثيل أنماط الفشل هذه بدرجة أكبر في Evaluation.

تشمل أمثلة الفصل أسئلة عن Niche Knowledge وأسئلة تفترض بشكل خاطئ وجود شيء ما.

## 6. أساليب تقييم الاتساق الواقعي (Methods for Evaluating Factual Consistency)

### استخدام AI كـ Judge (AI-as-a-judge)

عند وجود Source Context و Response مولدة، يمكن سؤال AI Judge عما إذا كانت كل Claim مهمة مدعومة.

### التحقق الذاتي (Self-verification)

تولد طريقة مثل SelfCheckGPT عدة Responses وتبحث عن الاختلاف بينها. فإذا تعارضت Outputs المتكررة بشدة، فقد تكون الإجابة الأصلية غير موثوقة.

المفاضلة هنا هي التكلفة: قد يكون توليد Responses إضافية كثيرة لمجرد تقييم إجابة واحدة مكلفًا.

### التحقق المدعوم بالمعرفة (Knowledge-augmented Verification)

يصف الفصل نهجًا مدعومًا بـ Search باستخدام تسلسل مثل:

```text
الاستجابة (response)
  -> تقسيمها إلى عبارات واقعية (split into factual statements)
  -> إعادة كتابة العبارات لتصبح مستقلة بذاتها (rewrite statements to be self-contained)
  -> توليد Search Queries (generate search queries)
  -> استرجاع Evidence (retrieve evidence)
  -> تقييم كل عبارة مقابل Evidence (judge each statement against evidence)
```

يحول ذلك Global Factuality إلى مجموعة من عمليات الفحص المحلية المدعومة بـ Evidence.

### الاستلزام النصي أو Natural Language Inference (Textual Entailment / Natural Language Inference)

عند إعطاء **Premise** وهي Context و **Hypothesis** وهي Claim، صنّف العلاقة على أنها:

- **Entailment:** تتبع Claim من Context.
- **Contradiction:** تتعارض Claim مع Context.
- **Neutral:** لا تدعم Context الـ Claim ولا تناقضها.

يحول ذلك Evaluation الخاصة بـ Factual Consistency إلى Classification Task يمكن لـ Specialized Scorers تنفيذها.

## 7. تقييم Safety (Safety Evaluation)

تمثل Safety مظلة تشمل أنواعًا كثيرة من Outputs الضارة. وبحسب التطبيق، قد تشمل Evaluation فئات مثل:

- لغة غير مناسبة أو Explicit.
- توصيات ضارة.
- Hate Content أو محتوى تمييزي.
- تهديدات أو Graphic Violence.
- Stereotypes.
- انحياز نحو وجهات نظر أيديولوجية أو دينية معينة عندما يتطلب المنتج Neutrality.

تشمل Evaluators المحتملة:

- AI Judges عامة الغرض.
- أنظمة الإشراف التي يقدمها المزوّد (Provider Moderation Systems).
- Small Specialized Classifiers لاكتشاف Toxicity أو Hate Speech.
- Human Reviewers.

يمكن أن تكون Specialized Safety Models أصغر وأسرع وأقل تكلفة بكثير من General-purpose Judges الكبيرة.

المبدأ الأساسي هو عدم تبني Generic Safety Benchmark بصورة عمياء. حدد الأضرار المهمة لمنتجك وقيّم تلك المخاطر.

## 8. قدرة اتباع التعليمات (Instruction-following Capability)

قد يفهم Model الـ Domain لكنه يفشل في التطبيق بسبب تجاهل التعليمات.

افترض أن Model يفهم Tweet Sentiment بصورة صحيحة، لكنه طُلب منه إخراج واحد فقط من:

```text
NEGATIVE
POSITIVE
NEUTRAL
```

إذا أخرج `HAPPY`، فلا تكون المشكلة بالضرورة في فهم Sentiment. فقد تكون المشكلة في Instruction Following.

يشمل Instruction Following أكثر بكثير من JSON Formatting. فقد تطلب:

- Keywords محددة.
- كلمات Forbidden.
- لغة ثابتة.
- حدًا لعدد الكلمات أو الجمل أو Paragraphs.
- عددًا دقيقًا من Bullet Points.
- JSON أو YAML أو Formats أخرى.
- Content Constraints.
- Tone أو Linguistic Style معينًا.

### التعليمات القابلة للتحقق تلقائيًا (Automatically Verifiable Instructions)

يمكن فحص بعض التعليمات باستخدام Deterministic Code. على سبيل المثال:

- هل تحتوي Output على Keyword المطلوبة؟
- هل هي JSON صالحة؟
- هل تحتوي بالضبط على ثلاث Bullet Points؟
- هل يقل طولها عن 100 كلمة؟

### التعليمات Subjective (Subjective Instructions)

تحتاج تعليمات أخرى مثل "اكتب لجمهور صغير السن" أو "استخدم Tone محترمة" إلى Human Judgment أو AI Judgment.

من الأساليب المفيدة تفكيك التعليمة إلى Criteria واضحة بنعم أو لا، ثم حساب عدد Criteria التي تم تحقيقها.

### هل هو فشل Model أم فشل Prompt؟ (Model Failure or Prompt Failure?)

يوجد غموض مهم في Evaluation الخاصة بـ Instruction Following: قد ينتج الأداء الضعيف عن Model أو عن تعليمات سيئة. ويجب أن تتحكم Evaluation Process الخاصة بك في جودة Prompt بعناية.

تتمثل النصيحة العملية للفصل في بناء Instruction Benchmark **خاص بك** باستخدام التعليمات التي يحتاجها منتجك فعلًا.

## 9. Roleplaying بوصفه مشكلة في Instruction Following

يشيع Roleplaying في Games و Companions و Interactive Stories و Prompt-engineering Workflows.

يمكن تقييم Roleplaying Model على بُعدين على الأقل:

1. **Style:** هل تبدو Output مثل الدور المقصود؟
2. **Knowledge:** هل تظل Output ضمن ما يُفترض أن يعرفه الدور؟

يتضمن الشرط الثاني **Negative Knowledge**: ينبغي ألا يكشف Model Knowledge لا يُفترض أن تعرفها الشخصية.

يمكن فحص بعض Role Constraints باستخدام Heuristics، لكن غالبًا تكون AI Judges أو Human Evaluators ضرورية للسلوك الدقيق.

## 10. التكلفة و Latency والحجم جزء من جودة Model

قد يكون Model الذي ينتج إجابات ممتازة غير قابل للاستخدام إذا كان بطيئًا جدًا أو مكلفًا جدًا.

### التحسين متعدد الأهداف (Multi-objective Optimization)

غالبًا يتضمن اختيار Model أهدافًا متعددة متنافسة. ومن الاستراتيجيات المفيدة تحديد **Hard Requirements** أولًا.

على سبيل المثال:

```text
يجب أن يكون TTFT < 200 ms
يجب أن تكون التكلفة (cost) < الميزانية المستهدفة (target budget)
يجب أن تتجاوز الجودة (quality) الحد الأدنى المطلوب (minimum threshold)
```

استبعد Models التي تفشل في Hard Requirements. ثم قارن Models المتبقية وفق Soft Preferences.

### مقاييس Latency الشائعة (Common Latency Metrics)

- Time to First Token أو TTFT.
- الزمن لكل Token ناتجة (Time per Output Token).
- الزمن بين Tokens (Time Between Tokens).
- زمن الاستجابة الكلي للاستعلام (Total Query Latency).

تعتمد Latency على سلوك Model وطول Prompt وطول النص المولد و Sampling Configuration.

### اعتماد التكلفة على Deployment Model (Cost Depends on Deployment Model)

بالنسبة إلى APIs، غالبًا تتناسب التكلفة مع Token Usage. أما في Self-hosted Systems، فتهيمن Infrastructure إلى جانب تكاليف Engineering و Operations على التكلفة.

يمكن أن تتحسن Cost per Token في Self-hosting مع Utilization و Scale، لذلك قد يتغير قرار API مقابل Self-hosting مع نمو Traffic.

## 11. سير عمل عملي لاختيار Model (A Practical Model-selection Workflow)

ليس الهدف العثور على أفضل Model بصورة عالمية. بل العثور على أفضل Model **لتطبيقك**.

يميز الفصل بين **Hard Attributes** و **Soft Attributes**.

### السمات الصلبة (Hard Attributes)

هي Attributes يستحيل أو يصعب عمليًا على فريقك تغييرها، مثل:

- قيود License.
- قيود Privacy.
- توفر Model.
- قيود Deployment Size.
- قيود Provider.

### السمات المرنة (Soft Attributes)

هي Attributes قد تتمكن من تحسينها باستخدام Prompting أو Retrieval أو Finetuning أو Optimization أو System Design، مثل:

- Accuracy.
- Factual Consistency.
- Toxicity.
- وأحيانًا Latency، إذا كنت تتحكم في Model Stack.

يعتمد كون Attribute صلبة أو مرنة على حالتك. إذا كنت تتحكم في Model Serving، فقد تكون Latency قابلة للتحسين. أما إذا كان External Provider يتحكم في Serving، فقد تصبح Latency عمليًا Hard Attribute.

### سير العمل المكون من أربع خطوات (Four-step Workflow)

1. رشّح Models التي تخالف Hard Requirements واستبعدها.
2. استخدم Public Information و Benchmarks لتضييق قائمة الخيارات.
3. شغّل Evaluation Pipeline الخاصة بك على Candidates الأكثر وعدًا.
4. راقب Model المختار في Production واستمر في جمع Evidence.

هذه الخطوات Iterative. فقد تدفعك Evidence جديدة إلى إعادة النظر في قرار سابق.

## 12. Open Source و Open Weight وتراخيص Models

توجد درجة انفتاح Model على Spectrum.

- **Open Weight:** تكون Weights الخاصة بـ Model متاحة، لكن Training Data قد لا تكون عامة.
- **Open Model:** يستخدم الفصل هذا المفهوم لـ Models التي تكون Data الخاصة بها متاحة أيضًا بدرجة أكبر.
- **Commercial أو Proprietary Model:** يكون Access محكومًا أساسًا بواسطة Provider، وغالبًا من خلال API.

تُعد Model Licenses أمرًا حاسمًا. قبل اعتماد Model، تحقق من أسئلة مثل:

- هل Commercial Use مسموح؟
- هل توجد قيود على Usage Scale؟
- هل يمكن استخدام Outputs لتدريب Models أخرى أو تحسينها؟
- هل Redistribution أو Finetuning أو Derivative Models مسموحة؟

لا تفترض أن عبارة "Weights متاحة" تعني استخدامًا غير مقيد.

## 13. المقارنة بين Model APIs و Self-hosting

تستضيف Inference Service نموذجًا، وتستقبل Requests، وتشغل Inference، ثم تعيد Responses. وتمثل Model API الواجهة التي يصل التطبيق من خلالها إلى هذه Service.

يمكن أحيانًا أن يتوفر Model نفسه عبر Providers متعددين، مع اختلاف Pricing و Features و Optimization و Performance.

يقترح الفصل سبعة محاور لاتخاذ قرار بين استخدام API أو استضافة Model بنفسك:

1. Data Privacy.
2. Data Lineage و Copyright.
3. Performance.

## 14. Privacy و Data Lineage والقيود القانونية

### خصوصية البيانات (Data Privacy)

تتطلب External API إرسال البيانات إلى External Service، ما لم تُنشر Service داخل بيئة تسيطر عليها. وبالنسبة إلى بعض المؤسسات، يجعل ذلك وحده APIs معينة غير مقبولة.

تشمل الأسئلة:

- أين تتم معالجة البيانات؟
- هل يتم الاحتفاظ بالبيانات؟
- هل يمكن أن تتغير سياسة Provider؟
- هل يمكن أن تظهر Sensitive Data في Training مستقبلي؟
- هل توجد Data-residency Rules؟

### أصل البيانات و Copyright (Data Lineage and Copyright)

قد تحتاج الفرق أيضًا إلى فهم مصدر Training Data الخاصة بـ Model. وهذا مهم لأغراض Auditing و IP Risk والمتطلبات التنظيمية.

يمكن لـ Open Data تحسين قابلية الفحص، لكن Datasets الضخمة تظل صعبة في Auditing بشكل كامل. ويمكن لـ Commercial Contracts أحيانًا نقل أو توضيح أجزاء من المسؤولية القانونية، لكن هذا قرار تنظيمي وقانوني وليس تقنيًا فقط.

## 15. الوظائف والتحكم والمفاضلات التشغيلية (Functionality, Control, and Operational Tradeoffs)

### الوظائف (Functionality)

قد يحتاج التطبيق إلى أكثر من Raw Text Generation:

- Scalable Serving.
- Function أو Tool Calling.
- Structured Outputs.
- Guardrails.
- Log Probabilities.
- دعم Finetuning.

قد توفر API Providers قدرات كثيرة جاهزة، مما يوفر Engineering Time. لكنك تكون مقيدًا بما يعرضه Provider.

تمنح Open Models وصولًا أكبر إلى Weights و Logprobs و Internals و Finetuning و Quantization وخيارات Serving، لكن فريقك يصبح مسؤولًا عن قدر أكبر من العمل الهندسي.

### تكلفة API مقابل تكلفة Engineering (API Cost versus Engineering Cost)

يمكن أن تصبح APIs مكلفة عند Scale كبير. ويمكن لـ Self-hosting تقليل Marginal Usage Cost لكنه يضيف تكاليف Engineering و Operations و Monitoring و Optimization و Reliability.

أرخص Token Price لا يعني بالضرورة أرخص System.

### التحكم والشفافية (Control and Transparency)

يمكن لـ External Providers فرض Rate Limits أو تغيير Models أو تغيير السلوك أو تغيير الشروط أو إيقاف الدعم. ومع Open أو Self-hosted Models، تحصل على تحكم أكبر ويمكنك تثبيت Versions، لكنك تتحمل أيضًا مسؤولية تشغيلية أكبر.

### النشر على الجهاز (On-device Deployment)

إذا كان يجب أن يعمل Model محليًا دون External Network Access، فلن تكون Remote API كافية. ويفضل On-device Deployment النماذج التي يمكن تشغيلها وتحسينها محليًا.

## 16. كيفية استخدام Public Benchmarks بصورة صحيحة

توجد آلاف Benchmarks. تجعل Evaluation Harnesses تشغيل عدد كبير منها أسهل، لكن وجود Benchmark لا يعني أنه ذو صلة بتطبيقك.

تكون Public Benchmarks أكثر فائدة باعتبارها **أداة Filtering**. فهي تساعد على استبعاد Candidates الضعيفة بوضوح وتحديد Models التي تستحق اختبارًا أعمق.

عند مراجعة Benchmark، اسأل:

- ما Capability التي يقيسها؟
- هل هذه Capability مهمة لمنتجي؟
- هل وصل Benchmark إلى Saturation؟
- هل Benchmark موثوق ومبني جيدًا؟
- هل من المحتمل أن يكون Benchmark ملوثًا؟
- هل يشبه Task Format المهام الفعلية في تطبيقي؟

## 17. Public Leaderboards وتجميع Benchmarks

يجمع Leaderboard عدة Benchmark Scores في Ranking. ويتمثل الجزء الصعب في تحديد **أي** Benchmarks ينبغي تضمينها و **كيفية** دمجها.

### التغطية غير مكتملة دائمًا (Coverage Is Always Incomplete)

يتطلب تشغيل Benchmarks قدرًا من Compute، لذلك لا تتضمن Leaderboards عادةً إلا مجموعة فرعية من Capabilities الممكنة. قد يركز Leaderboard على Reasoning و Knowledge مع إهمال Coding أو Tool Use أو Retrieval أو Summarization أو Safety أو Capability أخرى تحتاج إليها.

### أهمية Benchmark Correlation

إذا كان Benchmarks اثنان يقيسان Capability نفسها تقريبًا وكانا شديدي Correlation، فقد يؤدي تضمينهما معًا إلى إعطاء تلك Capability وزنًا أكبر مما ينبغي.

### Aggregation تغير Ranking

يعطي Simple Average كل Benchmark الوزن نفسه حتى عندما تختلف Benchmarks في الأهمية أو الصعوبة أو Scale أو Units.

قد تجمع Leaderboards أخرى النتائج باستخدام Win Rates أو طرق مختلفة. ويمكن لاختيارات Aggregation المختلفة إنتاج Rankings مختلفة.

### إنشاء Private Leaderboard لتطبيقك

بالنسبة إلى منتج حقيقي، تكون Model-selection Process الخاصة بك فعليًا Private Leaderboard تعكس Criteria و Weights الخاصة باحتياجاتك.

استخدم Public Data لإنشاء Shortlist من Candidates، ثم اختبرها باستخدام Prompts و Datasets و Metrics الخاصة بك.

## 18. تلوث Benchmark (Benchmark Contamination)

يحدث **Data Contamination** عندما تظهر Evaluation Data أيضًا ضمن Training Data. ويُوصف ذلك أيضًا بـ Leakage أو Training on the Test Set.

يمكن عندها أن يحقق Model Score مرتفعة لأنه يتذكر Benchmark Examples، لا لأنه يعمم Capability الأساسية.

### كيف يحدث Contamination؟

- يمكن Scraping لبيانات Public Benchmark من Web إلى Training Data.
- قد تأتي Training Data و Evaluation Data من المصدر نفسه.
- قد يتعمد المطورون Training على Benchmark Data بعد Model Selection.

### كيف يمكن اكتشاف Contamination؟

**تداخل N-gram (N-gram Overlap)**  
ابحث عن تسلسلات طويلة مشتركة بين Benchmark Examples و Training Data.

**مقياس Perplexity**  
قد تشير Perplexity المنخفضة بصورة غير معتادة على Evaluation Text إلى أن Model رأى ذلك النص من قبل أو حفظه.

تكون N-gram Comparison أقوى عندما تكون Training Data متاحة لكنها قد تكون مكلفة. أما Perplexity فهي أقل تكلفة لكنها أقل حسمًا.

ينبغي لـ Benchmark موثوق أن يحتفظ بصورة مثالية بـ Private Holdout Set أو أن يجعل Contamination Analysis ممكنًا بطريقة أخرى.

## 19. الخطوة 1 في Evaluation Pipeline: تقييم كل Component

تحتوي أنظمة AI الحقيقية على مراحل متعددة. فإذا قيّمت Final Answer فقط، فقد تعرف أن النظام فشل لكنك لا تعرف **أين** فشل.

افترض أن نظامًا يستخرج Current Employer من Resume بصيغة PDF:

```text
PDF — ملف PDF
 -> استخراج النص (text extraction)
 -> استخراج جهة العمل (employer extraction)
 -> الإجابة النهائية (final answer)
```

قد تنتج جهة عمل خاطئة بسبب PDF Extraction سيئة أو Entity Extraction سيئة. قيّم كل مرحلة بصورة مستقلة.

### المقارنة بين Turn-based Evaluation و Task-based Evaluation

- **Turn-based Evaluation:** قيّم كل System Response أو Interaction Turn.
- **Task-based Evaluation:** قيّم ما إذا كان المستخدم قد حقق الهدف في النهاية ومدى كفاءة تحقيقه.

غالبًا تكون Task-based Evaluation أقرب إلى ما يهتم به المستخدمون. فـ Debugging Assistant يحل مشكلة خلال Turnين يختلف بصورة ذات معنى عن Assistant يحتاج إلى عشرين Turn.

## 20. الخطوة 2 في Evaluation Pipeline: إنشاء Guideline واضحة

يسمي الفصل Evaluation Guideline واحدة من أهم أجزاء Pipeline. تنتج Guidelines الغامضة Scores غامضة.

حدد كليهما:

- ما الذي **ينبغي** أن يفعله التطبيق.
- وما الذي **ينبغي ألا** يفعله التطبيق.

على سبيل المثال، قد يحتاج Support Bot إلى Policy للأسئلة Out-of-scope.

### تحديد Criteria

الإجابة الصحيحة ليست دائمًا إجابة جيدة. فقد تكون Response صحيحة واقعيًا لكنها وقحة أو غير مفيدة أو غير ذات صلة أو غير آمنة.

قد يستخدم Customer-support System معايير مثل:

- Relevance.
- Factual Consistency.
- Safety.

### إنشاء Scoring Rubrics مع أمثلة

لكل Criterion، اختر Scoring System وحدد معنى كل Score. تساعد الأمثلة Evaluators على تفسير Rubric باتساق.

تشمل Scales الممكنة:

- Binary: 0/1.
- ثلاثية: Contradiction أو Neutral أو Entailment.
- Numerical Discrete: 1–5.

تحقق من Rubric باستخدام البشر. فإذا فسّرها الأشخاص بطرق مختلفة، فإن Rubric تحتاج إلى تحسين.

## 21. ربط Evaluation Metrics بـ Business Metrics

تكون Model Metric مهمة فقط إذا ساعدت في الإجابة عن سؤال متعلق بالمنتج أو العمل.

بدلًا من قول:

```text
Factual consistency = 90% — نسبة Factual Consistency تساوي 90%
```

حاول فهم ما الذي تتيحه هذه النتيجة:

```text
90% من Factual Consistency (90% factual consistency)
 -> تسمح بأتمتة X% من طلبات الدعم (allows automation of X% of support requests)
 -> تقلل Response Time بمقدار Y (reduces response time by Y)
 -> تغير Cost أو Customer Satisfaction بمقدار Z (changes cost/customer satisfaction by Z)
```

يساعد هذا الربط على تحديد ما إذا كان تحسين Metric يستحق الجهد.

### حد الفائدة (Usefulness Threshold)

حدد Minimum Quality التي يصبح عندها النظام مفيدًا. وأسفل هذا Threshold، لا ينبغي Deployment للتطبيق في Use Case تلك.

انتبه عند اختيار Business Metrics. فقد تخلق Metrics مثل Engagement أو Time Spent حوافز لا تتوافق دائمًا مع User Well-being أو Product Quality.

## 22. الخطوة 3 في Evaluation Pipeline: اختيار الأساليب والبيانات

يمكن لـ Criteria المختلفة استخدام Evaluators مختلفة.

على سبيل المثال:

```text
Toxicity -> Specialized Classifier
Relevance -> Semantic Similarity
Factual Consistency -> AI Judge
Structured Format -> Deterministic Validator
نجاح Task (task success) -> End-to-end Functional Metric
```

يمكنك أيضًا الجمع بين Methods للـ Criterion **نفسها**. فقد يقيم Model منخفض التكلفة 100% من Traffic بينما يقيم Expensive Judge أو Human Expert عينة أصغر.

### استخدام Logprobs عند توفرها

بالنسبة إلى Classification، يمكن لـ Log Probabilities إظهار ما إذا كان Model واثقًا أو غير واثق بين Allowed Classes. كما يمكنها دعم Perplexity-based Measurements.

### إبقاء البشر في الحلقة عند الحاجة (Keep Humans in the Loop When Needed)

تُعد Automatic Metrics ذات قيمة، لكن Open-ended Tasks قد تظل بحاجة إلى Expert Review. ويمكن أن تعمل Human Evaluation باعتبارها North Star Signal وتُستخدم على Sampled Production Outputs.

### اختلاف Experimentation عن Production

قد تحتوي Offline Experiments على Curated Reference Answers. وقد لا يحتوي Production عليها. لكن Production يوفر Real User Feedback وأنماط Traffic حقيقية.

## 23. بناء Evaluation Datasets تمثيلية

استخدم Annotated Examples لتقييم كل Component و Criterion. وتكون Real Production Examples ذات قيمة خاصة عندما تكون متاحة.

### تقسيم Evaluation Data إلى Slices

يمكن لـ Aggregate Scores إخفاء حالات فشل خطيرة. قسّم Data إلى Slices وفق Attributes ذات معنى مثل:

- المستخدمون Free مقابل Paid.
- Mobile مقابل Web Traffic.
- Input Length.
- Topic أو Domain.
- الحالات المعروفة بصعوبتها.
- Typos أو Noisy Input.
- الطلبات خارج النطاق (Out-of-scope Requests).

يساعد Slicing على اكتشاف Bias و Debugging للإخفاقات وتحديد مجالات التحسين.

### مفارقة Simpson (Simpson's Paradox)

يمكن لـ Aggregated Results أن تروي قصة مختلفة عن كل Subgroup. فقد يبدو Model معين أفضل إجمالًا بينما يكون Model آخر أفضل داخل كل Slice ذات صلة، بسبب تقييم Models على توزيعات مختلفة لأحجام Slices.

[[IMAGE_NEEDED: Simpson's paradox in model evaluation | A two-group table where Model A performs better than Model B inside each subgroup but Model B has a higher aggregated score due to different group sizes | Learner should notice why aggregate metrics must be inspected alongside slice-level results]]

من المبادئ العملية في الفصل:

> **إذا كنت تهتم بشيء، فأنشئ Test Set له.**

## 24. هل Evaluation Set كبيرة بما يكفي؟

يجب أن تكون Evaluation Set كبيرة بما يكفي لإنتاج استنتاجات مستقرة، وصغيرة بما يكفي لتشغيلها بتكلفة معقولة.

### تحليل Bootstrap

أحد اختبارات Reliability العملية هو Bootstrapping:

1. اسحب Samples من Evaluation Set **مع الإرجاع**.
2. أعد تقييم النظام على Bootstrapped Set هذه.
3. كرر العملية مرات عديدة.
4. افحص مقدار تغير Score.

إذا كانت Scores تتقلب بدرجة كبيرة، فقد تكون Evaluation Set صغيرة جدًا أو تحتوي على Noise كبير.

### اكتشاف التحسينات الصغيرة يحتاج إلى Samples أكثر

تحتاج فروق Score الكبيرة إلى أمثلة أقل لاكتشافها بموثوقية مقارنة بفروق Score الصغيرة. ويقدم الفصل Heuristic تقريبيًا يوضح أن تقليل Effect Size بنحو 3 أضعاف قد يتطلب تقريبًا 10 أضعاف عدد الأمثلة للحصول على Confidence مشابهة.

الدرس العام أهم من حفظ أعداد دقيقة:

**ادعاء تحسن بنسبة 1% يحتاج إلى Evidence إحصائية أقوى بكثير من تحسن بنسبة 30%.**

## 25. تقييم Evaluation Pipeline نفسها

يمكن أن يكون Evaluation System نفسه خاطئًا أو مليئًا بـ Noise أو مكلفًا أو مضللًا.

اسأل:

### هل Signals صالحة؟

- هل تحصل Responses الأفضل فعلًا على Scores أفضل؟
- هل تؤدي Evaluation Metrics المحسنة إلى Product Outcomes أفضل؟

### هل Pipeline موثوقة؟

- هل يؤدي تشغيل Pipeline نفسها مرتين إلى استنتاجات متشابهة؟
- ما مقدار Variance الذي يظهر عبر Evaluation Samples المختلفة؟

بالنسبة إلى AI Judges، حافظ على Configurations مستقرة وقلل Sampling Variation غير الضرورية.

### هل Metrics مكررة؟

إذا كان Metricان مترابطين بصورة شبه مثالية، فقد يكون أحدهما Redundant. وإذا كانا غير مترابطين على نحو غير متوقع، فقد يكشف ذلك إما عن خاصية مثيرة للاهتمام في Model أو Metric معيبة.

### ما تكلفة Evaluation؟

يمكن أن تضيف Evaluation قدرًا كبيرًا من Latency والتكلفة المالية. ويجب تصميم هذه التكلفة ضمن النظام بدلًا من تجاهلها.

## 26. التكرار دون فقدان قابلية المقارنة

ستتطور Evaluation Criteria مع تغير المنتج وسلوك المستخدم. وقد تحتاج إلى تحديث Datasets أو Rubrics أو Judges أو Scoring Methods.

لكن إذا تغيرت Evaluation Process باستمرار دون Versioning، يصبح من المستحيل مقارنة Scores عبر الزمن.

تتبع كل ما يمكن أن يؤثر في Evaluation، بما في ذلك:

- إصدار Evaluation Dataset.
- Data Slices.
- إصدار Rubric.
- Judge Model أو Version.
- Judge Prompt.
- إعدادات Sampling الخاصة بالـ Judge (Judge Sampling Configuration).
- Model تحت الاختبار.
- Application Prompt أو Version.
- Retrieval أو Tool Configuration عندما يكون ذلك ذا صلة.

ينبغي أن تتطور Evaluation، لكن بطريقة محكومة وقابلة للملاحظة.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Model صاحب أعلى ترتيب في Public Leaderboard هو تلقائيًا أفضل Model لتطبيقي.

**لماذا هذا خطأ:** تمثل Public Leaderboards الـ Benchmarks و Aggregation Rules التي اختارتها، لا Task الخاصة بك ولا Traffic ولا Cost Constraints ولا Failure Modes الخاصة بتطبيقك.

### المفهوم الخاطئ 2

> Functional Correctness كافية لكل تطبيقات Coding.

**لماذا هذا خطأ:** قد يكون الحل صحيحًا لكنه بطيء جدًا أو يستهلك Memory أكثر من اللازم أو غير آمن أو مستحيل الصيانة.

### المفهوم الخاطئ 3

> إذا كانت الإجابة صحيحة عالميًا، فهي Faithful محليًا لـ Context.

**لماذا هذا خطأ:** تسأل Local Factual Consistency عما إذا كانت Context المقدمة تدعم الإجابة، لا عما إذا كانت العبارة صحيحة في مكان آخر.

### المفهوم الخاطئ 4

> Model API أرخص دائمًا من Self-hosting.

**لماذا هذا خطأ:** تتغير المفاضلة مع Scale و Utilization و Engineering Cost و Infrastructure والمتطلبات التشغيلية.

### المفهوم الخاطئ 5

> نتائج Public Benchmark موثوقة لأن إجابات Benchmark موضوعية.

**لماذا هذا خطأ:** يمكن لكل من تصميم Benchmark و Saturation و Relevance و Aggregation وحساسية Prompt و Training-data Contamination تشويه معنى Score.

### المفهوم الخاطئ 6

> إذا تحسنت Overall Metric، فإن كل User Group تستفيد.

**لماذا هذا خطأ:** يمكن لـ Aggregate Metrics إخفاء Regressions خاصة بـ Slices وحتى Simpson's Paradox.

## المصطلحات الأساسية (Key Terminology)

| المصطلح | المعنى |
|---|---|
| التطوير القائم على Evaluation (Evaluation-driven Development) | تحديد Evaluation Criteria قبل بناء التطبيق. |
| القدرة الخاصة بـ Domain (Domain-specific Capability) | قدرة مطلوبة لمجال أو Task معينة، مثل Coding أو Legal Reasoning. |
| قدرة Generation (Generation Capability) | خصائص جودة Outputs مفتوحة النهاية مثل Faithfulness أو Relevance. |
| الاتساق الواقعي المحلي (Local Factual Consistency) | ما إذا كانت Output مدعومة بـ Context مقدمة صراحة. |
| الاتساق الواقعي العالمي (Global Factual Consistency) | ما إذا كانت Output مدعومة بـ Open-world Knowledge موثوقة. |
| الاستلزام النصي (Textual Entailment) | Classification لـ Claim باعتبارها Entailed أو Contradicted أو Neutral بالنسبة إلى Premise. |
| اتباع التعليمات (Instruction Following) | القدرة على الالتزام بقيود Format أو Content أو Style أو Language أو Behavior المطلوبة. |
| السمة الصلبة (Hard Attribute) | خاصية في Model يستحيل أو يصعب عمليًا على فريقك تغييرها. |
| السمة المرنة (Soft Attribute) | خاصية في Model قد تتحسن عبر Adaptation أو Optimization. |
| مقياس TTFT | الزمن حتى أول Token (Time to First Token). |
| تحسين Pareto (Pareto Optimization) | Multi-objective Optimization قد يؤدي فيها تحسين Objective إلى تدهور آخر. |
| خدمة Inference (Inference Service) | نظام يستضيف Model وينفذ Requests ويعيد Outputs. |
| نموذج Open Weight | Model تكون Weights الخاصة به متاحة حتى إذا لم تكن Training Data عامة بالكامل. |
| واجهة Model API | Interface للوصول إلى Inference Service أو Model Service أخرى. |
| أصل البيانات (Data Lineage) | معلومات عن مصدر Model Data وكيفية معالجتها. |
| أداة Evaluation Harness | Tooling لتشغيل Models مقابل Benchmarks متعددة. |
| تشبع Benchmark (Benchmark Saturation) | حالة تقترب فيها Models كثيرة من Ceiling الخاصة بـ Benchmark. |
| ارتباط Benchmarks (Benchmark Correlation) | درجة تحرك Scores الخاصة باثنين من Benchmarks معًا عبر Models. |
| تلوث البيانات (Data Contamination) | ظهور Evaluation Examples ضمن Model Training Data. |
| Evaluation على مستوى Turn (Turn-based Evaluation) | تقييم Interaction Turns الفردية. |
| Evaluation على مستوى Task (Task-based Evaluation) | تقييم ما إذا تم تحقيق هدف المستخدم كاملًا. |
| دليل Scoring Rubric | قواعد صريحة تصف معنى كل Evaluation Score. |
| حد الفائدة (Usefulness Threshold) | الحد الأدنى من مستوى Evaluation المطلوب ليكون التطبيق مفيدًا. |
| تقسيم البيانات (Data Slicing) | تقييم الأداء بصورة منفصلة على Subsets ذات معنى من البيانات. |
| مفارقة Simpson (Simpson's Paradox) | انقلاب Aggregate Results للنمط الظاهر داخل Subgroups. |
| أسلوب Bootstrap | إعادة Sampling مع Replacement لتقدير Score Variability أو Reliability. |
| تتبع التجارب (Experiment Tracking) | تسجيل Evaluation Data و Prompts و Rubrics و Models و Configurations حتى تبقى Results قابلة لإعادة الإنتاج. |

## التحقق الذاتي (Self-check)

قبل المتابعة، تأكد من قدرتك على الإجابة:

1. ماذا يعني Evaluation-driven Development؟
2. ما الفئات الأربع العامة لـ Evaluation التي يقدمها الفصل؟
3. لماذا يمكن لـ SQL Query صحيحة وظيفيًا أن تظل غير قابلة للاستخدام؟
4. لماذا تكون MCQs سهلة Evaluation لكنها غير مكتملة لقياس Generative Capability؟
5. ما الفرق بين Local Factual Consistency و Global Factual Consistency؟
6. كيف يعمل Search-augmented Factuality Verification؟
7. ما المقصود بـ Entailment و Contradiction و Neutral؟
8. لماذا ينبغي أن تكون Safety Evaluation خاصة بالتطبيق؟
9. كيف يمكن لـ Deterministic Code تقييم Instruction Following؟
10. لماذا يمكن الخلط بين ضعف Instruction Following وضعف Domain Capability؟
11. ما دور Negative Knowledge في Evaluation الخاصة بـ Roleplaying؟
12. ما TTFT وما Total Query Latency؟
13. ما الفرق بين Hard Model Attribute و Soft Model Attribute؟
14. ما المراحل الأربع العامة لـ Model Selection؟
15. لماذا تهم Model License حتى إذا كانت Weights قابلة للتنزيل؟
16. اذكر المحاور السبعة لاتخاذ قرار API مقابل Self-hosting.
17. لماذا قد يصبح Self-hosting أكثر جاذبية عند Scale كبير؟
18. لماذا قد تظل API مفضلة رغم ارتفاع Token Cost؟
19. لماذا ينبغي التعامل مع Public Benchmarks كـ Filters بدلًا من Final Selectors؟
20. لماذا يكون Benchmark Correlation مهمًا عند بناء Leaderboard؟
21. ما Data Contamination ولماذا يرفع Benchmark Scores بصورة مصطنعة؟
22. كيف يمكن لـ N-gram Overlap و Perplexity المساعدة في اكتشاف Contamination؟
23. لماذا ينبغي تقييم Intermediate Components بصورة مستقلة؟
24. ما الفرق بين Turn-based Evaluation و Task-based Evaluation؟
25. لماذا تُعد Scoring Rubrics أساسية لموثوقية Evaluation؟
26. كيف ينبغي ربط Model Metrics بـ Business Metrics؟
27. لماذا ينبغي تقسيم Evaluation Data إلى Slices؟
28. ما الذي تحذر منه Simpson's Paradox؟
29. كيف يمكن لـ Bootstrapping كشف أن Evaluation Set صغيرة جدًا؟
30. لماذا يجب تقييم Evaluation Pipeline نفسها؟
31. ما المتغيرات التي ينبغي عمل Versioning لها للحصول على AI-judge Evaluation قابلة لإعادة الإنتاج؟
