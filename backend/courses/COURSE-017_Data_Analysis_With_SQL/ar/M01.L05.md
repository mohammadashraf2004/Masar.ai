## 1. ما معنى Text Analysis — وأين تناسب SQL؟

النص موجود في كل مكان داخل الأنظمة التحليلية:

- أسماء المنتجات؛
- أوصاف المواقع؛
- تعليقات الاستبيانات؛
- support tickets؛
- log messages؛
- social posts؛
- نصوص المراجعات؛
- الملاحظات الحرة؛
- الحقول semistructured في التطبيقات.

**تحليل النصوص (Text analysis)** يعني تحويل النص إلى معلومات يمكن فحصها أوتجميعها أوعدّها أومقارنتها أواستخدامها للإجابة عن سؤال.

يوجد نوعان عامان من تحليل النصوص.

### التحليل النوعي للنصوص (Qualitative text analysis)

الهدف هو فهم المعنى وcontext والموضوعات والـ nuance.

أمثلة:

```text
لماذا يشعر المستخدمون بالإحباط من عملية Onboarding؟
ما الموضوعات التي تظهر في مقابلات العملاء؟
كيف تختلف اللغة في هذه التقارير؟
```

غالبًا يكون البشر — أوأنظمة NLP/LLM المتقدمة مع evaluation مناسبة — أنسب لهذا النوع من المهام.

### التحليل الكمي للنصوص (Quantitative text analysis)

الهدف هو إنشاء معلومات structured أوcountable.

أمثلة:

```text
كم عدد Tickets التي تذكر "refund"؟
ما النسبة المئوية للتقارير التي تذكر "battery"؟
ما المدن التي تظهر أكثر؟
كم عدد Rows في كل Parsed category؟
```

هنا يمكن أن تكون SQL فعالة جدًا.

### لماذا SQL مفيدة؟

تكون SQL اختيارًا قويًا عندما:

- يكون النص موجودًا بالفعل داخل database؛
- تكون المهمة rule based؛
- تعرف مسبقًا ما الذي تريد البحث عنه؛
- تحتاج إلى تنظيف أوتوحيد عدد كبير من rows؛
- تحتاج إلى استخراج categories أوfields؛
- تكون final output عبارة عن counts أوrates أوgroups أوmetrics structured أخرى.

مثال:

⟦CODE_0⟧

هذه مشكلة واضحة ومناسبة لـ SQL.

### متى لا تكون SQL الخيار الأفضل؟

تصبح SQL أقل جاذبية عندما تكون المهمة:

#### تفسيرًا مفتوحًا (Open-ended interpretation)

```text
لماذا هؤلاء المستخدمون غير سعداء؟
```

قد تفشل مجموعة ثابتة من SQL rules في التقاط synonyms أوsarcasm أوcontext أوindirect language.

#### استرجاع Full-text بزمن استجابة منخفض

إذا كان التطبيق يجب أن يسترجع فورًا documents تحتوي patterns نصية معقدة، فقد تكون أنظمة search متخصصة مثل Elasticsearch أوSplunk أنسب.

#### NLP متقدم

مهام مثل:

- robust sentiment analysis؛
- part-of-speech tagging؛
- named-entity recognition؛
- semantic similarity؛
- text generation؛
- learned classification؛

تكون عادةً أنسب لـ Python/NLP أوmachine-learning tooling.

### SQL تعتمد على Rules

هذه نقطة مهمة.

إذا كتبت:

⟦CODE_1⟧

فإن database ستطبق هذه rules حرفيًا.

لن تتعلم تلقائيًا أن:

```text
"not excellent" — أي ليس ممتازًا
```

قد تكون negative، أوأن:

```text
"surprisingly decent" — أي جيد على نحو مفاجئ
```

قد تكون positive.

تظل rules قيّمة لأنها:

- transparent؛
- testable؛
- قابلة لإعادة الإنتاج (reproducible).

لكنها تصبح أصعب في الصيانة كلما زاد عدد special cases.

## 9. Regular Expressions: لغة مختصرة لوصف أنماط النص

الـ **regular expression** أو**regex** تصف pattern نصية.

تصبح regex مفيدة عندما تكون pattern أكثر مرونة من wildcard search بسيطة.

مثلًا:

```text
رقم واحد أو أكثر
يتبعه Space
ثم "light" أو "lights"
```

يمكن تمثيل ذلك باستخدام pattern مختصرة.

### يختلف دعم Regex بين Databases

تتضمن PostgreSQL operators بنمط POSIX مثل:

```text
~     مطابقة حساسة لحالة الأحرف (case-sensitive match)
~*    مطابقة غير حساسة لحالة الأحرف (case-insensitive match)
!~    عدم مطابقة حساس لحالة الأحرف (case-sensitive non-match)
!~*   عدم مطابقة غير حساس لحالة الأحرف (case-insensitive non-match)
```

وقد تستخدم databases أخرى functions مثل:

```text
REGEXP_LIKE
RLIKE
REGEXP_SUBSTR
REGEXP_REPLACE
```

تختلف syntax الدقيقة، لكن concepts الخاصة بالـ pattern قابلة للنقل.

## 13. Workflow عملية لمشروعات Text Analysis الحقيقية

تصبح text analysis أسهل كثيرًا عندما تُنفذ بصورة منهجية.

### الخطوة 1 — حدد السؤال

تجنب:

```text
حلّل هذا النص.
```

وفضّل:

```text
كم عدد Support tickets التي تذكر Billing problems؟
```

أو:

```text
استخرج Location وDuration من هذا Semistructured field.
```

### الخطوة 2 — قرر هل SQL هي Tool المناسبة

استخدم SQL عندما:

```text
Pattern معروفة
+ Data موجودة بالفعل في Database
+ Output منظمة/قابلة للعد
```

فكر في tools أخرى عندما:

```text
المهمة تحتاج Semantic interpretation
أو Fast search على Application scale
أو Advanced NLP
```

### الخطوة 3 — اعمل Profile للمصدر

افحص:

- samples؛
- length distribution؛
- nulls؛
- empty strings؛
- common values؛
- outliers؛
- الصفوف غير الصحيحة (malformed rows).

### الخطوة 4 — نفّذ Parsing قبل Transformation

افصل المهام ذهنيًا:

```text
استخرج Target
-> نظّفها
-> تحقّق منها
-> حوّل Type
```

### الخطوة 5 — فضّل Rules بسيطة

استخدم:

```text
IN
```

قبل سلسلة `OR` ضخمة.

استخدم:

```text
LIKE
```

قبل regex عندما تكون كافية.

ولا تستخدم regex إلا عندما تتطلب pattern ذلك فعلًا.

### الخطوة 6 — تحقّق عبر Dataset كاملة

قد تعمل parsing rule على أمثلة قليلة وتفشل في production.

أنشئ quality checks مثل:

⟦CODE_70⟧

### الخطوة 7 — احتفظ بالقيمة Raw

لا تتخلص من original field مبكرًا.

غالبًا من المفيد أن تحتوي transformation table على:

```text
raw_text
parsed_value
clean_value
quality_flag
```

وهذا يجعل debugging ممكنًا.

### الخطوة 8 — انقل Logic المتكررة إلى Pipeline

إذا سيعاد تشغيل التحليل:

```text
مصدر خام (raw source)
-> تحليل وتنظيف قابلان للتكرار (repeatable parsing/cleaning)
-> جدول أو View منظَّم (structured table/view)
-> تحليل لاحق (downstream analysis)
```

أفضل عادة من نسخ nested query كبيرة إلى كل report.

### الخطوة 9 — وثّق افتراضات Rules

مثلًا:

```text
Rule:
أي شيء يبدأ بـ "triang" يُصنف على أنه Shape.

Known limitation:
قد يصنف كلمات غير مرتبطة تبدأ بالحروف نفسها.
```

يجعل ذلك rule-based systems قابلة للصيانة.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1

> SQL مفيدة فقط للبيانات الرقمية.

تحتوي SQL على string functions كثيرة، وهي مفيدة جدًا للمعالجة النصية structured وrule-based.

### المفهوم الخاطئ 2

> إذا نجحت Parsing على خمس Rows تجريبية، فهي مكتملة.

تحتوي real data عادة على exceptions. تحقّق دائمًا من rule على dataset كاملة.

### المفهوم الخاطئ 3

> `LIKE '%good%'` هي Sentiment Analysis.

إنها مجرد string rule. لا تفهم negation أوcontext أوirony أوsynonyms.

### المفهوم الخاطئ 4

> Regex أفضل دائمًا من `LIKE`.

Regex أكثر expressiveness، لكنها أيضًا أصعب في القراءة والصيانة. استخدم أبسط tool صحيحة.

### المفهوم الخاطئ 5

> Cleaning يعني حذف Characters غير المعتادة.

قد ترمز character غير معتادة إلى uncertainty أوinformation مفيدة أخرى.

### المفهوم الخاطئ 6

> Word-frequency table تفهم معنى النص.

تكشف frequency counts التكرار، لا semantics.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| تحليل النصوص (Text analysis) | استخراج information structured أوinsight من النص |
| التحليل النوعي (Qualitative analysis) | تفسير meaning وthemes بالاعتماد على الإنسان أوcontext |
| التحليل الكمي للنصوص (Quantitative text analysis) | تحويل النص إلى information قابلة للعد أوالقياس |
| النص المنظم (Structured text) | نص مخزن بالفعل في fields ذات معانٍ واضحة |
| النص شبه المنظم (Semistructured text) | نص يحتوي structure يمكن التعرف عليها لكنه يحتاج parsing |
| النص غير المنظم (Unstructured text) | نص حر بلا field boundaries موثوقة |
| التحليل البنيوي (Parsing) | استخراج جزء مفيد من text value أكبر |
| الفاصل (Delimiter) | Character أوstring تحدد الحدود بين الأجزاء |
| التوحيد (Standardization) | تحويل values المتكافئة إلى representation متسقة |
| الرمز البديل (Wildcard) | Symbol تمثل character واحدة أوأكثر غير محددة داخل pattern |
| المعامل `LIKE` | معامل SQL لمطابقة الأنماط (pattern matching) |
| المعامل `ILIKE` | Pattern matching غير حساسة لحالة الأحرف في databases التي تدعمها |
| التعبير النمطي (Regex) | لغة لوصف flexible text patterns |
| فئة المحارف (Character class) | Regex expression تصف characters مسموحة، مثل `[0-9]` |
| محدد التكرار (Quantifier) | Regex symbol تحدد التكرار، مثل `+` أو`*` أو`{3}` |
| الدالة `regexp_replace` | Regex-aware text replacement function في databases الداعمة |
| دمج النصوص (Concatenation) | دمج text values داخل string واحدة |
| تجميع النصوص (String aggregation) | دمج text من عدة rows داخل field واحدة |
| تقسيم النص إلى وحدات (Tokenization) | تقسيم text إلى وحدات أصغر مثل words |
| كلمة توقف (Stop word) | كلمة شائعة جدًا تُزال غالبًا من simple frequency analyses |
| نظام قائم على القواعد (Rule-based system) | Logic تتبع rules مكتوبة صراحة بدل تعلم patterns من data |

## اختبر نفسك (Self-check)

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما أنواع text-analysis tasks المناسبة لـ SQL؟
2. متى تكون Python/NLP أوsearch engine خيارًا أفضل؟
3. لماذا ينبغي عمل profile للنص قبل كتابة parsing rules؟
4. متى تكون `left` و`right` أكثر أمانًا من delimiter-based parsing، ومتى تصبح أكثر fragile؟
5. ما الفرق بين parsing وtransformation؟
6. لماذا ينبغي validation للـ values قبل casting؟
7. ماذا يعني `%` و`_` في `LIKE` pattern؟
8. لماذا يمكن لـ `CASE` واحدة أن تفقد information عندما يمكن أن تظهر عدة categories في row نفسها؟
9. متى تكون `IN` أفضل من مجموعة `OR` expressions؟
10. ماذا تعني `[0-9]+` في regex؟
11. لماذا لا تكون regex أفضل تلقائيًا من `LIKE`؟
12. ما غرض `regexp_replace`؟
13. ما الفرق بين `string_agg` وsplit-to-table function؟
14. لماذا تُزال stop words عادة من word-frequency analysis؟
15. لماذا ينبغي غالبًا الاحتفاظ بالـ raw text إلى جانب cleaned outputs؟
