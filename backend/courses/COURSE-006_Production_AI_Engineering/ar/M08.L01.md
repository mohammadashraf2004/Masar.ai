## 1. ما هي هندسة Dataset؟ (What Dataset Engineering Is)

لا يستطيع Model تعلم سلوك لا تعرضه Training Data الخاصة به بوضوح كافٍ.

Dataset Engineering هي عملية إنشاء Dataset تسمح لـ Model بتعلم السلوك الذي تريده **ضمن Budget المتاحة لديك**.

ويشمل ذلك أكثر بكثير من جمع Files. فقد تحتاج إلى:

- تحديد السلوكيات التي ينبغي أن تظهر في Data.
- تحديد السلوكيات التي ينبغي إزالتها.
- الحصول على Examples أو Annotate لها.
- توليد Examples مفقودة بصورة Synthetic.
- التحقق من الجودة.
- موازنة Coverage.
- إزالة Duplicates.
- تنظيف Data غير الآمنة أو غير المتوافقة.
- تحويل كل شيء إلى Format الدقيقة التي يتوقعها Model.

يؤكد الفصل أن Curation و Generation و Processing ليست Pipeline باتجاه واحد. غالبًا تنتقل بينها ذهابًا وإيابًا عندما تكشف Experiments عن نقاط ضعف جديدة.

## 2. منظور Data-centric لـ AI (A Data-centric View of AI)

توجد طريقتان عامتان لتحسين أنظمة AI.

### نهج Model-centric AI

حسّن Model نفسها:

- Architecture جديدة.
- Model أكبر.
- Optimizer أو Training Technique أفضل.
- Post-training Method أفضل.

### نهج Data-centric AI

أبقِ Model أكثر ثباتًا وحسّن Data:

- صحح Labels السيئة.
- أضف Edge Cases مفقودة.
- حسّن Annotation Quality.
- زد Diversity.
- أزل Duplication أو Noise.
- ابنِ Training-data Mix أفضل.

في الواقع العملي، تحسن الأنظمة الناجحة غالبًا Model و Data معًا. والتحول الذهني المفيد هو التعامل مع Data بوصفها System يجري هندستها، لا Input سلبية.

## 3. مراحل Training المختلفة تحتاج إلى Data مختلفة (Different Training Stages Need Different Data)

ينبغي أن تتطابق Dataset Format مع ما يتم Training للـ Model عليه.

### الضبط الدقيق ذاتي الإشراف (Self-supervised Finetuning)

تحتاج إلى Sequences من Text خاص بـ Domain أو Raw Data أخرى ذات صلة.

### Instruction Finetuning

تحتاج إلى Examples مثل:

```text
(instruction, response) — (Instruction، Response)
```

### Preference Finetuning

تحتاج إلى Comparative Examples مثل:

```text
(instruction, winning_response, losing_response) — (Instruction، Response الفائزة، Response الخاسرة)
```

### Training لـ Reward Model

يمكن استخدام Preference Pairs أو Scored Examples مثل:

```text
((instruction, response), score) — ((Instruction، Response)، Score)
```

تظل High-level Curation Principles متشابهة حتى عندما تتغير بنية Example المطلوبة.

---

## 4. ينبغي أن تعرض Training Data السلوك المطلوب (Training Data Should Demonstrate the Desired Behavior)

Dataset ليست معلومات فقط؛ بل هي أيضًا Demonstration لـ **كيفية تصرف Model**.

إذا كنت تريد إجابات مختصرة، فينبغي أن تحتوي Dataset على إجابات مختصرة. وإذا كنت تريد Tool Use، فينبغي أن تحتوي Dataset على Tool-use Trajectories صحيحة. وإذا كنت تريد Step-by-step Explanations، فتحتاج Dataset إلى Examples تعرض ذلك السلوك.

ويعمل ذلك أيضًا في الاتجاه العكسي. فإذا ظهر سلوك غير مرغوب فيه بصورة متكررة في Training Data، فقد يتعلمه Model. لذلك يمكن أن تشمل Dataset Engineering إزالة Examples تعلّم سلوكيات لم تعد تريدها.

---

## 5. Data الخاصة بـ Reasoning و Step-by-step

إذا كنت تريد من Model إنتاج Step-by-step Responses، فينبغي أن تعرض Training Examples استجابات Step-by-step.

يكون إنشاء هذه Data أعلى تكلفة من جمع Final Answers لأن Annotators يجب أن يشرحوا Intermediate Steps بصورة صحيحة وواضحة.

يستخدم الفصل ذلك مثالًا على مبدأ عام:

> كلما كان السلوك الذي تريده أكثر تعقيدًا، أصبحت عملية Annotation أكثر تطلبًا.

وهذا أحد أسباب كون Specialized Reasoning Datasets أقل وفرة من Instruction-response Datasets العادية.

---

## 6. Data الخاصة باستخدام Tools (Tool-use Data)

لتعليم Model استخدام Tools، اجمع Examples تتضمن Actions المطلوبة لإكمال Task.

يمكن لـ Human Experts المساعدة في إنشاء هذه Data، لكن تظهر مشكلة مهمة: **Human-efficient Workflows ليست دائمًا AI-efficient Workflows**.

قد ينفذ الإنسان:

```text
فتح Browser -> لصق Query -> النقر على Result -> قراءة Page
```

بينما قد يكون الأفضل لـ AI Agent:

```text
استدعاء Search API -> معالجة Results المعادة مباشرة
```

لذلك تكون مراقبة Human Work مفيدة، لكن Simulations و Synthetic Tool Trajectories قد تكتشف أحيانًا Actions أفضل وأكثر ملاءمة لـ AI.

وقد تحتاج Tool-use Data أيضًا إلى Message Structures أغنى من Chat العادية، لأن Turn واحدة من Model يمكن أن تحتوي على Messages موجهة إلى Tools أو Recipients مختلفة.

## 7. Data أحادية Turn مقابل متعددة Turn (Single-turn versus Multi-turn Data)

تعلم **Single-turn Data** الاستجابة لـ Instructions معزولة.

أما **Multi-turn Data** فتعلم التفاعل عبر Task:

- طرح Clarifying Questions.
- قبول Corrections.
- استخدام معلومات جديدة قُدمت لاحقًا.
- الحفاظ على Goals و Constraints عبر Turns.

يكون الحصول على Single-turn Data أسهل. وغالبًا تكون Multi-turn Data أكثر واقعية للتطبيقات التي تحل Tasks من خلال Conversation.

## 8. الثلاثي الذهبي: الجودة و Coverage والكمية (The Golden Trio: Quality, Coverage, Quantity)

ينظم الفصل Data Curation حول ثلاثة معايير أساسية:

1. **الجودة (Quality)** — هل Examples جيدة بما يكفي للتعلم منها؟
2. **التغطية (Coverage)** — هل تمثل Examples نطاق المواقف التي يجب أن يتعامل معها Model؟
3. **الكمية (Quantity)** — هل توجد Examples كافية للتعلم المطلوب؟

يمكن استخدام تشبيه الطبخ:

- Quality = Ingredients غير فاسدة.
- Coverage = لديك المزيج الصحيح من Ingredients.
- Quantity = لديك كمية كافية من Ingredients.

يمكن أن تكون Dataset ضخمة ومع ذلك ضعيفة إذا احتوت على Examples سيئة أو Coverage ضيقة.

## 9. جودة Data (Data Quality)

يؤكد الفصل أن كمية صغيرة من Data المنتقاة بعناية يمكن أن تتفوق على Dataset أكبر بكثير لكنها مليئة بـ Noise.

ويقترح ست خصائص مفيدة للجودة.

### ذات صلة (Relevant)

ينبغي أن تكون Examples ذات صلة بـ Task الفعلية. يمكن أن تكون Data القديمة أو غير المرتبطة صحيحة تقنيًا لكنها مع ذلك غير مفيدة للسلوك المستهدف.

### متوافقة مع متطلبات Task (Aligned with Task Requirements)

ينبغي أن تعرض Annotation بالضبط ما يحتاج إليه المنتج. فإذا كانت Task تحتاج إلى إجابات Factual، فينبغي أن تكون Annotations واقعية. وإذا كانت Task تحتاج إجابات مختصرة، فينبغي أن تكون Annotations مختصرة.

### متسقة (Consistent)

ينبغي أن تحصل الحالات المتشابهة على Labels أو Answers متشابهة عبر Examples و Annotators. يجعل Inconsistency الـ Learning Signal غامضة.

### منسقة بصورة صحيحة (Correctly Formatted)

أزل HTML غير ذي الصلة و Whitespace غير المتسقة و Casing Errors و Numeric Formatting غير الصحيح و Format Tokens التي لا ينبغي أن يتعلمها Model.

### فريدة بدرجة كافية (Sufficiently Unique)

يؤدي Duplication المفرط إلى Bias في Learned Distribution وإهدار Compute.

### متوافقة (Compliant)

يجب أن تلبي Training Data السياسات الداخلية والقوانين و Licensing Rules و Privacy Rules والمتطلبات الأخرى ذات الصلة بالمؤسسة.

## 10. Coverage و Diversity في Data

تسأل Coverage عما إذا كانت Dataset تمثل المواقف التي سيخلقها المستخدمون الحقيقيون.

قد تشمل أبعاد Diversity المحتملة:

- Prompts قصيرة مقابل مفصلة.
- Text نظيفة مقابل Text مليئة بـ Typos.
- Programming Languages متعددة.
- Topic Diversity.
- Language و Cultural Diversity.
- Input Length و Response Length.
- Single-turn و Multi-turn Interactions.
- Open-ended و Close-ended Tasks.
- Output Formats مثل Prose و JSON و Code و Tables أو Yes/No.

تعتمد الأبعاد الصحيحة على التطبيق.

قد لا يحتاج French-to-English Translator إلى Languages كثيرة، لكنه قد يحتاج إلى Diversity في Topics و Sentence Lengths و Styles. أما Global Product Assistant فقد يهتم كثيرًا بـ Linguistic و Cultural Diversity.

يحذر الفصل أيضًا من أن Heterogeneous Data ليست أفضل تلقائيًا. فقد تضر إضافة Data غير مرتبطة بالأداء. وينبغي أن تعكس Coverage مزيج Data متعمدًا.

## 11. تصميم Data Mix

نقطة البداية البسيطة هي جعل Dataset تشبه الاستخدام الحقيقي للتطبيق.

إذا كانت 60% من Real Requests عبارة عن Support Questions و 10% منها Account Changes، فإن استخدام Training Mix بنسبة 50/50 بصورة عمياء يغير الأهمية المتعلمة لهذه السلوكيات.

لكن نسخ Production Frequency لا يكون كافيًا دائمًا. تستحق بعض Capabilities تمثيلًا زائدًا متعمدًا لأنها صعبة أو High-risk أو مفيدة لـ General Reasoning.

يصف الفصل فرق تطوير Models وهي تجرب Data Mixes مختلفة على Models أصغر قبل اختيار Mix لـ Training Runs أكبر.

المبدأ الأساسي هو أن **Data Mixture هي Hyperparameter** وينبغي تقييمها Empirically.

## 12. ما مقدار Data الذي تحتاج إليه؟ (How Much Data Do You Need?)

لا توجد إجابة عالمية.

تعتمد متطلبات Data على الأقل على:

- Data Quality.
- Data Diversity.
- Task Complexity.
- قدرة النموذج الأساسي (Base-model Capability).
- Finetuning Method.
- Budget المتاحة لـ Data و Compute.

### طريقة Finetuning

يحتاج Full Finetuning عادةً إلى Data أكثر من PEFT Methods مثل LoRA.

### تعقيد Task

قد يحتاج Binary Sentiment Classification إلى Data أقل بكثير من Financial Question Answering معقدة.

### أداء Base Model

إذا كانت Base Model قريبة بالفعل من السلوك المطلوب، فقد تحتاج إلى Examples أقل.

يقترح الفصل البدء بحجم صغير، وغالبًا عشرات Examples المنتقاة بعناية، لمعرفة ما إذا كان Finetuning يدفع Model في الاتجاه الصحيح قبل الاستثمار في Annotation Effort كبيرة.

## 13. استخدم Scaling Curves قبل شراء المزيد من Data

نفّذ Training على Subsets من Dataset نفسها، على سبيل المثال:

```text
25% من Data -> Score A
50% من Data -> Score B
100% من Data -> Score C
```

ارسم Performance مقابل Dataset Size.

- **Slope شديد الانحدار:** قد تستمر Data الإضافية في توفير Gains قوية.
- **Slope مسطح أو يصل إلى Plateau:** مضاعفة Dataset قد تحقق تحسنًا صغيرًا.

يساعد ذلك على تقدير ما إذا كانت Annotation الإضافية تستحق التكلفة.

كما يسلط الفصل الضوء على Diminishing Returns: يمكن للأمثلة المبكرة توفير Gains كبيرة، بينما غالبًا تقدم الأمثلة اللاحقة Gains أصغر.

قد يكون لـ Task Diversity منحنى مشابه: تضيف Task Types الجديدة Gains كبيرة في البداية، ثم يظهر Plateau.

## 14. استخدم Data الأقل تكلفة أو الأقل كمالًا قبل Premium Data النادرة

يقدم الفصل ثلاث استراتيجيات على مراحل.

### Self-supervised ثم Supervised

استخدم Raw Domain Text الوفيرة أولًا، ثم استخدم Labeled Examples النادرة.

### الأقل صلة ثم الأعلى صلة

تعلم سلوكًا مرتبطًا من Dataset وفيرة، ثم نفّذ Adaptation باستخدام Target-domain Dataset الأصغر.

### Synthetic ثم Real

استخدم Synthetic Examples لبناء سلوك أولي واسع، ثم حسّنه باستخدام Real Data النادرة.

يمكن لهذه الاستراتيجيات تقليل كمية Human-annotated Data المكلفة المطلوبة، لكنها تضيف Training Complexity ويجب تقييمها بعناية.

## 15. استراتيجية الحصول على Data (Data Acquisition Strategy)

تشمل Sources المحتملة:

- Application Data الخاصة بك.
- Public Datasets.
- Purchased أو Proprietary Datasets.
- Manual Annotation.
- Synthetic Generation.

يعامل الفصل **Application Data** بوصفها ذات قيمة خاصة لأنها تعكس بصورة طبيعية Distribution التي تهتم بها فعلًا.

يمكن لـ User-generated Content و Usage Traces و System Events و Feedback تكوين **Data Flywheel** عند استخدامها بمسؤولية لتحسين المنتج.

قبل إنشاء Data من الصفر، ابحث في Sources الموجودة. لكن لا تفترض أبدًا أن Public Dataset صحيحة أو نظيفة أو قابلة للاستخدام قانونيًا أو ذات صلة. افحص Origin و Processing و License و Quality الخاصة بها.

## 16. Annotation Guidelines جزء من Dataset

لا تعني Annotation الجيدة فقط "وظف أشخاصًا واطلب منهم وضع Labels".

يحتاج Annotators إلى تعريف واضح للجودة:

- ما الذي يجعل Response جيدة؟
- هل يمكن لإجابة أن تكون صحيحة لكنها غير مفيدة؟
- ما الذي يفصل Score 3 عن Score 4؟
- كيف ينبغي التعامل مع Uncertainty؟
- ما Sources التي يمكن استخدامها لـ Fact-checking؟
- ماذا ينبغي أن يحدث مع Examples الغامضة؟

يربط الفصل بين Annotation و Evaluation: يمكن غالبًا إعادة استخدام Guidelines الدقيقة نفسها المستخدمة للحكم على Outputs لإنشاء Training Data.

وهذه فائدة كبيرة للاستثمار مبكرًا في Evaluation System قوية.

## 17. Data Augmentation مقابل Data Synthesis

تنشئ **Data Augmentation** Examples جديدة عبر تحويل Real Examples.

مثال:

```text
صورة Cat حقيقية -> Flip/Crop/Rotate -> صورة Cat بعد Augmentation
```

تنشئ **Data Synthesis** Examples اصطناعية تهدف إلى محاكاة خصائص مفيدة من Real Data.

مثال:

```text
Simulation -> مطالبة تأمين Synthetic
```

تتداخل المصطلحات أحيانًا في الاستخدام العملي لأن كليهما يؤتمت إنشاء Data.

## 18. لماذا نستخدم Synthetic Data؟

يمكن لـ Synthetic Data المساعدة في عدة أهداف.

### زيادة الكمية (Increase Quantity)

ولّد Examples عندما تكون Real Events نادرة أو مكلفة في الجمع.

### زيادة Coverage

استهدف المناطق المفقودة في Data Distribution:

- Rare Classes.
- Edge Cases.
- Long Inputs.
- Short Inputs.
- Adversarial Cases.
- Underrepresented Behaviors.

### زيادة الجودة (Increase Quality)

يمكن لـ AI-generated Examples أحيانًا أن تكون أكثر Consistency أو أنسب لـ AI-native Workflows من Examples التي أنشأها البشر.

### حماية Privacy

يمكن استخدام Synthetic Examples عندما تكون Real Records حساسة أو غير متاحة.

### Distill Models

استخدم Outputs من Teacher Model قوية لتدريب Student أقل تكلفة أو أسرع.

## 19. Rule-based Synthesis و Templates

يستخدم أبسط Synthetic-data System قواعد أو Templates صريحة.

قد تحتوي Transaction Template على Fields مثل:

```text
transaction_id   — معرّف المعاملة
date             — التاريخ
amount           — المبلغ
merchant         — التاجر
location         — الموقع
payment_method   — طريقة الدفع
status           — حالة المعاملة
```

يملأ Generator هذه Fields باستخدام Controlled Distributions.

تعمل Templates جيدًا مع Structured Artifacts:

- Invoices.
- Resumes.
- Tax Forms.
- Contracts.
- Configuration Files.
- Mathematical Expressions.

الميزة هي Control و Verifiability. أما القيد فهو أن Templates قد تنتج Distributions متكررة وغير واقعية إذا صُممت بصورة سيئة.

## 20. Transformations و Perturbations

يمكن تحويل Real Examples لإنشاء Examples جديدة مع الحفاظ على Label أو Behavior المقصودة.

بالنسبة إلى Images:

- Crop.
- Rotate.
- Scale.
- Flip.
- تغيير Brightness.
- إضافة Noise.

بالنسبة إلى Text:

- استبدال Words بأخرى متشابهة دلاليًا.
- Rephrase.
- Translate.
- إدخال Typos أو Noise واقعية.

يمكن أيضًا تصميم Transformations لتقليل Bias، مثل تبديل Gendered Terms عندما ينبغي أن تظل Target Label دون تغيير.

تضيف **Perturbation** تغييرات صغيرة بصورة متعمدة. ويمكن لـ Training على Perturbed Examples تحسين Robustness ضد Inputs noisy بصورة طبيعية وضد Attacks.

## 21. Simulation

تكون بعض Data خطيرة أو مكلفة أو نادرة عند جمعها في العالم الحقيقي.

يمكن لـ Simulation إنشاءها بأمان وبتكلفة أقل.

تشمل الأمثلة:

- Edge Cases للقيادة الذاتية.
- مسارات تحكم الروبوتات في الأجسام (Robot Manipulation Trajectories).
- Manufacturing Defects.
- الأحداث المالية النادرة (Financial Rare Events).
- سيناريوهات الطقس الشديد (Extreme Weather Scenarios).
- Tool-use Trajectories لـ AI Agents.

تظل Simulated Environment تقريبًا للعالم. وينشئ ذلك تحدي **Sim-to-real**: قد ينجح System في Simulation ثم يفشل في الواقع.

ومع ذلك، تكون Simulation مفيدة جدًا غالبًا لاستكشاف Action Sequences كثيرة والاحتفاظ فقط بالمسارات الناجحة أو الكفؤة.

## 22. Data Synthesis المدعومة بـ AI

توسع Foundation Models نطاق Data التي يمكن توليدها Programmatically.

يمكنها محاكاة:

- Outputs من APIs.
- Customer Interactions.
- بيئات استخدام الأدوات (Tool-use Environments).
- Games و Self-play.
- التعليمات بلغة طبيعية (Natural-language Instructions).
- Explanations و Documentation.
- Code.
- Images و Media أخرى.

تكون AI Synthesis جذابة بصورة خاصة لـ Post-training Data لأن Instruction Data و Preference Data مكلفتان عند إنشائهما بشريًا.

## 23. Self-play و Simulated Participants

يمكن لـ AI توليد جانبي Interaction.

أمثلة:

- Agents في Chess أو Go تلعب ضد نفسها.
- Negotiation Agents تستخدم Strategies مختلفة.
- Simulated Customer يتحدث إلى Simulated Support Assistant.

يمكن لـ Self-play توليد Interaction Data أكثر بكثير مما يستطيع البشر إنتاجه يدويًا، لكن النجاح يعتمد على Realism و Diversity الخاصة بـ Simulated Participants.

## 24. Paraphrasing و Translation و Back-translation

يمكن لـ Model تحويل Example جيدة إلى Surface Forms كثيرة.

مثال:

```text
How to reset my password?   — السؤال الأصلي
 -> I forgot my password.   — صياغة بديلة
 -> How can I change my password?   — صياغة بديلة
 -> What are the steps to reset a password?   — صياغة بديلة
```

يمكن لـ Translation نقل Datasets من High-resource Languages إلى Low-resource Languages.

### التحقق باستخدام Back-translation

```text
English X
 -> ترجم إلى Lao Y (translate to Lao Y)
 -> ترجم Y مرة أخرى إلى English X' (translate Y back to English X')
 -> قارن X مع X' (compare X with X')
```

يشير الاختلاف الكبير إلى أن Translation قد تكون ضعيفة.

يمكن للفكرة نفسها التحقق من Generated Code Explanations أو Documentation: ولّد Text من Code، ثم أعد توليد Code من Text، وبعد ذلك قارن Code المعاد توليدها أو نفّذها.

## 25. توليد Instruction Data بصورة Synthetic

- كليهما.

1. حدد Topics أو Keywords أو Task Types أو Templates.

## 26. Reverse Instruction

يزيد توليد Responses طويلة وواقعية من الصفر احتمالية Hallucination.

يقلب Reverse Instruction الاتجاه:

```text
Content موجودة عالية الجودة (existing high-quality content)
 -> يولّد AI Instruction/Question
 -> اربط Instruction بالـ Trusted Content بوصفها Response
```

يمكن لذلك تحويل Long-form Text موثوقة، مثل Articles أو Stories أو Documentation، إلى Instruction Data دون مطالبة AI باختراع Response الطويلة نفسها.

يمكن حتى Bootstrapping لـ Model بصورة Iterative:

1. درّب Model ضعيفة انطلاقًا من Seed Set صغيرة.
2. ولّد Instructions لـ Trusted Content.
3. نفّذ Finetune على Pairs الجديدة.
4. كرر العملية وتحقق من التحسن.

## 27. Synthetic Data لسلوك Long Context

نمط مفيد لتوليد Long-context Data هو:

1. خذ Document طويلة.
2. قسمها إلى Chunks قصيرة يستطيع Model الحالي معالجتها بموثوقية.
3. ولّد Question-answer Pairs من كل Chunk.
4. أثناء Training، قدم **Full Long Document** بوصفها Context لهذه Questions.

تتعلم Model العثور على Evidence ذات الصلة واستخدامها داخل Context أكبر بكثير.

## 29. التحقق من Synthetic و Real Training Data

ينبغي تقييم Synthetic Data قبل Training باستخدام كثير من Methods نفسها المستخدمة لتقييم Model Outputs.

### الصحة الوظيفية (Functional Correctness)

استخدمها عندما يمكن تنفيذ Outputs أو فحصها بصورة Objective.

أمثلة:

- Code تجتاز Tests.
- SQL تعيد Rows المتوقعة.
- Structured Output تجتاز Validation.

### AI Verifiers أو Judges

اطلب من Model منح Score للـ Examples أو Classification لها مقابل Quality Criteria صريحة.

### فحوص Factuality

نفّذ Filtering للـ Examples المرجح أن تحتوي على Unsupported Claims أو Hallucinations.

### مرشحات Topic

أزل Examples الموجودة خارج Target Domain.

### اكتشاف Anomalies

حدد Examples غير المعتادة التي قد تمثل Corruption أو جودة منخفضة.

### Heuristics

أزل Examples التي تكون:

- فارغة.
- قصيرة جدًا أو طويلة جدًا بالنسبة إلى Use Case.
- متكررة.
- Instruction نفسها مع Responses متعارضة.
- Outputs تعيد Input ببساطة.

يظل التحقق النهائي Empirical: هل يؤدي Training على Dataset إلى تحسين Target Model على Target Evaluation Set؟

## 30. القيد 1: التحكم في الجودة (Quality Control)

يمكن أن تكون Synthetic Data خاطئة أو سطحية أو متكررة أو متحيزة أو Hallucinated. وإذا لم تستطع التحقق من Generated Examples، فينبغي أن تكون حذرًا عند استخدامها بوصفها Training Truth.

تقلل Synthetic Generation تكلفة **إنشاء Candidates**. لكنها لا تلغي تكلفة تحديد أي Candidates موثوقة.

---

## 31. القيد 2: التقليد السطحي (Superficial Imitation)

يمكن لـ Student تعلم تقليد **Style** الخاصة بـ Teacher قوية دون اكتساب Reasoning Capability الأساسية لدى Teacher.

هذا خطير لأن Student قد تتعلم إنتاج Outputs **تبدو مثل حلول صحيحة** حتى عندما لا تستطيع حل المشكلة فعلًا.

لذلك يحذر الفصل من تفسير Imitation Quality بوصفها دليلًا على Factual Accuracy أو تحسن General Reasoning.

---

## 32. القيد 3: Model Collapse و Feedback Loops

يمكن أن يؤدي Training المتكرر لـ Models على Data مولدة Recursively إلى تشويه Data Distribution.

تميل Model إلى توليد Common أو High-probability Events أكثر من Rare Events. وإذا أصبحت Outputs الخاصة بها Training Data للجيل التالي، فقد تنخفض Rare Patterns بدرجة أكبر. وتكرار العملية قد يؤدي إلى نسيان Tails الخاصة بالـ Real Distribution.

غالبًا ما تسمى هذه الظاهرة **Model Collapse**.

تشير الأبحاث التي يناقشها الفصل إلى أن إبقاء Real Data ضمن Mix يمكن أن يقلل هذا الخطر، رغم عدم وجود Synthetic-to-real Ratio عالمية ثابتة.

يمكن لـ Feedback Loops أيضًا تضخيم Biases الموجودة.

[[IMAGE_NEEDED: Synthetic-data feedback loop | Real distribution -> model -> synthetic dataset biased toward common cases -> next model -> even narrower distribution, with rare cases fading | Learner should notice how repeated synthetic-only training can erase the tails]]

## 33. القيد 4: غموض Data Lineage

عندما تولد Model X الـ Data، فقد يعكس Generated Example بصورة غير مباشرة Training Data غير المعروفة الخاصة بـ Model X.

ينشئ ذلك عدة مخاطر:

- يمكن لمشكلات Copyright أو Licensing أن تنتقل بصورة غير مباشرة.
- قد يلوث Benchmark الـ Training Data الخاصة بك عبر Teacher Model.
- يصبح Auditing لمصدر معلومات معينة أصعب.
- قد يكون تقييم Commercial Viability صعبًا دون Provenance.

لذلك تظل Data Lineage مهمة حتى عندما تكون Examples Synthetic.

## 34. Model Distillation

تدرب **Knowledge Distillation** Model أصغر تسمى **Student** لتقليد Model أكبر أو أقوى تسمى **Teacher**.

يكون الهدف عادةً Deployment Efficiency:

- Model أصغر.
- Inference أسرع.
- تكلفة أقل.
- Task Performance مشابهة عندما يكون ذلك ممكنًا.

يمكن Training للـ Student من الصفر أو Finetune لها من Pre-trained Model.

ليست كل Synthetic-data Training عملية Distillation. تصبح Distillation عندما يكون سلوك Teacher هو Target الذي يُتوقع من Student إعادة إنتاجه صراحة.

ولا يشترط أن تمتلك Teacher عدد Parameters أقل من Student؛ إذ يمكن لـ Synthetic Data أيضًا Bootstrapping لـ Student أكثر قدرة عندما يتم التحقق بعناية من Generated Examples الخاصة بـ Teacher.

تحقق دائمًا من Model Licenses: فبعضها يمنع استخدام Outputs لتدريب Models أخرى أو منافسة.

## 35. مبادئ Data Processing

يمكن لـ Large-scale Data Processing أن تستغرق ساعات أو أيامًا. نفّذ Processing بترتيب يوفر Compute.

أمثلة:

- إذا كانت Deduplication منخفضة التكلفة، فأزل Duplicates قبل Cleaning مكلفة.
- إذا كان Low-quality Filtering منخفض التكلفة، فأزل Bad Data قبل Deduplication مكلفة.

قاعدتان عمليتان من الفصل مهمتان بصورة خاصة:

### نفّذ Trial Run لـ Processing Scripts

شغّلها على Sample صغيرة قبل تطبيقها على Dataset كاملة.

### تجنب Destructive In-place Processing

احتفظ بالـ Original Data لأن:

- Use Case أخرى قد تحتاج إلى Processing مختلفة.
- Buggy Script قد تفسد Transformed Dataset.

## 36. افحص Data قبل Training

قبل بناء Processing Pipelines معقدة، افهم ما لديك.

افحص Metadata مثل:

- Source و Provenance.
- Processing السابقة.
- الاستخدامات السابقة.

ارسم Distributions مثل:

- Token Frequencies.
- Input Lengths.
- Response Lengths.
- Topics.
- Languages.
- Scores.
- Annotators.
- Time Periods.

ابحث عن Outliers و Clusters غير متوقعة.

### اختلاف Annotators (Inter-annotator Disagreement)

إذا قام عدة Annotators بوضع Labels لنفس Example، فقِس Disagreement وافحص Conflicts. قد يكشف Disagreement الكبير عن Guidelines غامضة أو Annotators غير متسقين.

### ما زال Manual Inspection مهمًا

لا تحل Data Dashboards محل قراءة Examples الفعلية. افحص Queries و Labels و Responses و Contradictions و Duplicates و Factual Claims يدويًا. يمكن لبضع دقائق من Direct Inspection كشف مشكلات تخفيها Statistics.

## 37. إزالة Duplicates من Data

تشوه Duplicates الـ Training Distribution وتهدر Compute ويمكن أن تسبب Train أو Test Contamination.

يمكن أن تظهر Duplicates على عدة مستويات:

- التكرارات على مستوى المستند كاملًا (Whole-document Duplicates).
- Paragraphs مكررة داخل Document واحدة.
- Passages مشتركة عبر Documents.
- Near-duplicates مع Edits صغيرة.

يجب أن تحدد معنى "Duplicate" بالنسبة إلى تطبيقك:

- Exact Equality؟
- تداخل بنسبة 80%؟
- Items نفسها بترتيب مختلف؟
- المعنى الدلالي نفسه بصياغة مختلفة؟

### التشابه الثنائي (Pairwise Similarity)

قارن Examples باستخدام Exact Match أو N-gram Overlap أو Fuzzy Matching أو Semantic Similarity. تكون قوية لكنها مكلفة على نطاق كبير.

### Hashing

ضع Examples المرجح تشابهها داخل Buckets ثم قارن داخل Buckets. يذكر الفصل Techniques مثل MinHash و Bloom Filters.

### Dimensionality Reduction أو أفكار Vector Search

قلل Dimensionality الخاصة بـ Representation أو استخدم Approximate-neighbor Methods لتضييق Candidate Duplicate Pairs قبل Comparison المكلفة.

## 38. تنظيف Data وتصفيتها

ينبغي أن تحسن Cleaning من Model Quality و Safety و Compliance.

تشمل Operations الشائعة:

- إزالة HTML أو Markdown Artifacts غير ذات الصلة.
- Normalization لـ Whitespace و Formatting.
- إزالة Fields التي لا ينبغي أن يراها Model.
- إزالة PII أو Sensitive Data عندما تتطلب Policy ذلك.
- إزالة Data غير المرخصة أو التي تحتوي على Copyright Problems عند الحاجة.
- Filtering للـ Toxic أو Unsafe Data بناءً على Application Policy.
- إزالة Low-quality Examples باستخدام Verification Methods.

يمكن لـ Manual Inspection كشف Filtering Heuristics مفيدة. ويشير الفصل أيضًا إلى أن Annotation Quality يمكن أن تتغير أثناء Annotation Sessions الطويلة، مما يوضح لماذا يمكن أن تكون Metadata مثل Annotator و Time مفيدة.

إذا كان لديك Data أكثر مما تسمح به Compute Budget، فيمكن لأساليب مثل Active Learning أو Importance Sampling أو Data Pruning المساعدة في اختيار Examples يُعتقد أنها الأكثر فائدة.

## 39. نسّق Data تمامًا كما يتوقع Model

بعد Cleaning و Deduplication، حوّل Examples إلى Tokenizer و Chat Template التي تتوقعها Base Model.

يمكن لـ Formatting غير الصحيحة إنشاء Model Bugs دقيقة.

بالنسبة إلى SFT، قد تبدو Data مفاهيميًا مثل:

```text
(instruction, response) — (Instruction، Response)
```

يمكن غالبًا تفكيك Prompt مستخدمة أثناء Few-shot Prompting إلى Training Examples منفردة. وبعد Finetuning، قد تصبح Inference Prompt أقصر بكثير لأن Examples لم تعد تحتاج إلى التكرار داخل كل Request.

ينبغي أن تظل Inference Format متسقة مع Format المستخدمة أثناء Finetuning. ويمكن للتغييرات الصغيرة في Separators أو Prefixes أو Spaces أو Special Tokens أن تؤثر في السلوك.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> المزيد من Training Data أفضل دائمًا.

**لماذا هذا خطأ:** يمكن لـ Data noisy أو duplicated أو غير ذات صلة أو سيئة Mix أن تجعل Model أسوأ مع زيادة التكلفة.

### المفهوم الخاطئ 2

> Data Quality تعني فقط أن الإجابة صحيحة واقعيًا.

**لماذا هذا خطأ:** تشمل Quality أيضًا Relevance و Alignment مع Task Requirements و Consistency و Formatting و Uniqueness و Compliance.

### المفهوم الخاطئ 3

> Human-generated Data أعلى جودة دائمًا من Synthetic Data.

**لماذا هذا خطأ:** يمكن للبشر أن يكونوا غير متسقين أو متعبين أو غير مناسبين لـ AI-native Workflows. ويمكن لـ Synthetic Data أن تكون قوية عندما تكون مستهدفة وقابلة للتحقق.

### المفهوم الخاطئ 4

> Synthetic Data تلغي الحاجة إلى البشر.

**لماذا هذا خطأ:** لا يزال البشر مطلوبين لتحديد Desired Behavior و Guidelines و Edge Cases و Policies و Validation Criteria.

### المفهوم الخاطئ 5

> إذا بدت AI-generated Example واقعية، فهي Training Data جيدة.

**لماذا هذا خطأ:** قد تكون Style مقنعة بينما Facts أو Reasoning أو Generalization خاطئة.

### المفهوم الخاطئ 6

> Training باستخدام Self-generated Data فقط طريقة آمنة للتحسن إلى الأبد.

**لماذا هذا خطأ:** يمكن لـ Recursive Synthetic-data Feedback تضييق Distribution والتسبب في Model Collapse أو Bias Amplification.

### المفهوم الخاطئ 7

> Distillation تعني كل Synthetic-data Training.

**لماذا هذا خطأ:** تعامل Distillation تحديدًا سلوك Teacher Model بوصفه Target لـ Student.

### المفهوم الخاطئ 8

> Deduplication تعني فقط إزالة Rows المتطابقة تمامًا.

**لماذا هذا خطأ:** يمكن أن يظهر Duplication على مستوى Document أو Paragraph أو Sentence أو N-gram أو Semantic.

### المفهوم الخاطئ 9

> يمكن تطبيق Data Processing بأمان مباشرة على النسخة الوحيدة من Data.

**لماذا هذا خطأ:** يمكن لـ Processing Bugs إفساد Data، وقد تحتاج تطبيقات مختلفة إلى Transformations مختلفة.

| التوليد الإجرائي (Procedural Generation) | توليد تلقائي للـ Data أو Environments قائم على Rules أو Programs. |
| عملية Perturbation | إدخال Noise أو Modifications محكومة إلى Example. |
| عملية Simulation | توليد Data داخل Environment ممثلة بدلًا من العالم الحقيقي. |
| أسلوب Self-play | Agents أو Models تولد Interactions عبر اللعب ضد نفسها أو Agents أخرى. |
| أسلوب Back-translation | ترجمة أو تحويل Example إلى الأمام ثم إلى الخلف للتحقق من Faithfulness. |
| أسلوب Reverse Instruction | توليد Instruction من شأنها أن تستدعي Response موجودة عالية الجودة. |
| نظام AI Verifier | Model تُستخدم لـ Scoring أو Filtering للـ Generated Training Examples. |
| ظاهرة Model Collapse | تدهور Distribution نتيجة الاعتماد المتكرر على Generated Data. |
| أصل Data (Data Lineage) | سجل يوضح من أين جاءت Data وكيف تم تحويلها. |
| عملية Knowledge Distillation | Training لـ Student Model لتقليد Teacher Model. |
| عملية Deduplication | اكتشاف Examples المكررة أو Near-duplicate وإزالتها. |
| أسلوب MinHash | Hashing Method تُستخدم كثيرًا لتقدير Set Similarity بكفاءة. |
| بنية Bloom Filter | Probabilistic Data Structure مفيدة لفحوص Membership أو Duplicate بكفاءة. |
| اختلاف Annotators (Inter-annotator Disagreement) | درجة اختلاف Annotators على Examples نفسها. |
| أسلوب Active Learning | اختيار Examples مفيدة بصورة خاصة من أجل Labeling أو Training. |
| أسلوب Importance Sampling | Sampling للـ Examples وفق الأهمية المقدرة بالنسبة إلى Objective. |
| قالب Chat (Chat Template) | Formatting Structure الدقيقة التي تتوقعها Conversational Model. |

## الفكرة التي ينبغي الاحتفاظ بها (Retain This Idea)

**Training Dataset هي Behavioral Specification معبّر عنها عبر Examples. لا تسعى Dataset Engineering القوية إلى تعظيم عدد Rows؛ بل تختار بصورة متعمدة ما ينبغي أن يتعلمه Model، وتغطي المواقف المهمة، وتتحقق من كل Shortcut ممكن، وتحافظ على Provenance و Compliance، وتقيس ما إذا كانت كل دفعة جديدة من Data تحسن Model فعلًا.**
