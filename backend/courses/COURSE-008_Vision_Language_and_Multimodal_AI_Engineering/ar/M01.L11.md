## من الرؤية إلى الفعل (From seeing to doing)

يمكن لـ VLM أن يجيب:

```text
"What is on the screen?" — ما الموجود على الشاشة؟
```

يمكن لـ Agentic VLM أن يذهب أبعد من ذلك:

```text
"Click the correct button." — انقر الزر الصحيح.
"Fill the form." — املأ النموذج.
"Search the website." — ابحث في الموقع.
"Use a tool." — استخدم Tool.
```

ويذهب Vision-Language-Action Model أبعد من ذلك أيضًا:

```text
"Pick up the cup." — التقط الكوب.
"Fold the shirt." — اطوِ القميص.
"Pour the coffee." — اسكب القهوة.
```

تبدو هذه الأنظمة مختلفة جدًا ظاهريًا.

أحدها يتعامل مع:

```text
البرمجيات (software)
```

والآخر يتعامل مع:

```text
العالم المادي (the physical world)
```

لكن الفكرة المركزية في الفصل هي أن كليهما يتبع الحلقة نفسها:

```text
OBSERVE
   ↓
DECIDE
   ↓
ACT
   ↓
OBSERVE AGAIN
```

بالنسبة إلى Computer-use agent:

```text
observation = screenshot — الملاحظة هي Screenshot
action      = click / type / scroll / tool call — الفعل هو Click أو Type أو Scroll أو Tool call
```

وبالنسبة إلى Robot:

```text
observation = camera + language + proprioception   — الملاحظة: الكاميرا واللغة والإحساس الذاتي
action      = future joint/gripper set-points   — الفعل: نقاط ضبط مستقبلية للمفاصل والقابض
```

تربط هذه الحلقة المشتركة نصفي الفصل.

## 2. ما الـ Agent؟ (What is an agent?)

يقدم المصدر تعريفًا عمليًا:

```text
LLM — نموذج لغوي كبير
يعمل داخل Loop
مع إمكانية الوصول إلى Tools
```

تُعد **Loop** عنصرًا أساسيًا.

يمكن لـ One-shot model أن يجيب:

```text
"Use tool X." — استخدم Tool X.
```

أما Agent فيمكنه:

```text
يفكر (reason)
→ يستدعي Tool X
→ يفحص النتيجة
→ يراجع الخطة
→ يستدعي Tool Y
→ يفحص النتيجة
→ يتوقف عند اكتمال الهدف
```

إذن تنشأ Agency من:

```text
القرار (decision)
+
الفعل (action)
+
التغذية الراجعة (feedback)
+
التكرار (repetition)
```

## 3. الـ Agency تقع على طيف (Agency is a spectrum)

يعرض الفصل مستويات متزايدة من Autonomy.

### المستوى 1 — اختيار Tool (Tool selection)

يختار Model أي Operation ينبغي تشغيلها.

مثال:

```text
"translate this" — ترجم هذا
→ دالة Translation
```

### المستوى 2 — Tool calling

ينتج Model Structured arguments.

مثال:

⟦CODE_0⟧

لـ Weather function.

### المستوى 3 — Loop متعددة الخطوات (Multistep loop)

ينفذ Model بصورة متكررة:

```text
يفكر (thinks)
ينفذ (acts)
يلاحظ (observes)
يحدّث Memory
يواصل (continues)
```

حتى الاكتمال.

### درس مهم (Important lesson)

زيادة Autonomy ليست أفضل تلقائيًا.

سؤال التصميم الصحيح هو:

> **ما مقدار Open-ended reasoning الذي تتطلبه هذه المهمة فعلًا؟**

## 4. حلقة ReAct (The ReAct loop)

يصف الفصل هذه الدورة.

### الخطوة 1 — استلام المهمة (Receive task)

```text
تعليمات المستخدم (user instruction)
```

### الخطوة 2 — التفكير / التخطيط (Think / plan)

يقرر Model:

- ما المعروف؛
- ما المفقود؛
- أي Tools قد تساعد؛
- ماذا يفعل بعد ذلك.

### الخطوة 3 — التنفيذ (Act)

نفّذ Tool/Action.

### الخطوة 4 — الملاحظة (Observe)

اقرأ:

- Tool output؛
- Screenshot؛
- Error؛
- الحالة الخارجية (External state).

### الخطوة 5 — القرار (Decide)

إذا اكتمل الهدف:

```text
أعد الإجابة النهائية (return final answer)
```

وإلا:

```text
احفظ State مفيدة
→ واصل Loop
```

من الناحية المفاهيمية:

```text
المهمة (TASK)
 ↓
التفكير (THINK)
 ↓
التنفيذ (ACT)
 ↓
الملاحظة (OBSERVE)
 ↓
هل اكتملت؟ (DONE?)
 ├─ نعم → الإجابة النهائية (FINAL)
 └─ لا  → MEMORY → التفكير (THINK)
```

[[IMAGE_NEEDED: ReAct loop |
Show task → think/plan → action/tool → observation → completion decision →
either final answer or memory and another cycle |
Learner should understand feedback as the defining feature of agent behavior]]

## 5. متى تحتاج فعلًا إلى Agent؟ (When do you actually need an agent?)

يحذر المصدر صراحةً من أن ليس كل تطبيق يحتاج إلى Agent.

إذا كان Tool call واحد يحل المشكلة:

```text
استخدم Tool call واحدًا
```

مثال:

```text
اختر أمرًا واحدًا لمعالجة الصورة
→ نفّذه
```

لا توجد حاجة إلى Loop معقدة.

يصبح Agent مفيدًا عندما يتطلب Workflow:

- عدة خطوات مترابطة؛
- External state؛
- Failures/retries؛
- Dynamic planning؛
- معلومات متغيرة.

## 6. افصل Open-ended reasoning عن Deterministic operations

يتضمن مثال GPU-provider في المصدر مهام مثل:

```text
ابحث عن Providers
تنقّل بين Sites
تحقق من الإنفاق الداخلي
قارن النتائج
اكتب Draft email
أنشئ Reminder
```

تحتاج بعض الخطوات إلى Reasoning.

بينما تكون خطوات أخرى Deterministic.

مثال:

```text
قيمة Billing الداخلية
```

إذا كانت API موجودة، فاستدعها مباشرةً.

لا تجبر Visual agent على التعامل بصعوبة مع:

- Login pages؛
- Popups؛
- Two-factor prompts؛

عندما تتوفر API موثوقة.

قاعدة الفصل هي:

> **على نطاق واسع، نفّذ الأجزاء Deterministic بصورة Deterministic، واترك للـ
> Agent الأجزاء Open-ended.**

## 7. لماذا تهم Feedback loops؟

قد تفشل Open-ended workflows بطرق غير متوقعة.

يقدم المصدر أمثلة:

### تدفق Site ديناميكي (Dynamic site flow)

قد يتطلب السعر استخدام Calculator.

قد يفشل Visual path.

### تسجيل الدخول / طلب المصادقة الثنائية (Login / Two-factor prompt)

استخدم بديلًا Deterministic إذا كان متاحًا.

### حقيقة مهلوسة داخل Draft

أضف خطوة Verification.

ولهذا تحتاج Agents القوية إلى:

```text

+
الملاحظة (observation)
+
التحقق (verification)
+
البدائل (fallbacks)
```

وليس مجرد Tool access.

## 8. تقييم Agents (Evaluating agents)

يفصل الفصل بين مستويين من Evaluation.

### Grounding على مستوى الخطوة (Step-level grounding)

السؤال:

```text
هل نفّذ Agent الإجراء الصحيح الآن؟ (Did the agent take the correct action now?)
```

بالنسبة إلى GUI agents:

- هل اختار Button الصحيح؟
- هل Coordinates صحيحة؟
- هل Text field صحيح؟
- هل Action type صحيح؟

يمكن قياس Localization هندسيًا.

أما صحة Agentic action فقد تتطلب Semantic comparison.

### النجاح على مستوى المهمة (Task-level success)

السؤال:

```text
هل اكتملت المهمة كلها بصورة صحيحة؟ (Did the whole job finish correctly?)
```

أمثلة:

- تم إرسال Form؛
- File موجود؛
- اكتمل Booking؛
- تغيرت Database value؛
- يحتوي Email على المحتوى الصحيح.

قد يتطلب Task-level evaluation:

- Final state قابلة للتحقق؛
- التقييم البشري (Human judgment).

## 11. لماذا يستخدم الفصل smolagents؟

يقدم المصدر ثلاثة أسباب رئيسية.

### صغير وسهل القراءة (Small and readable)

تكون Framework مخفية تحت طبقات كثيرة.

### ملاحظات Multimodal (Multimodal observations)

يمكن للصور أن تمر عبر Agent memory.

وهذا مهم لـ Computer-use agents.

### وكيل CodeAgent

بدل الاكتفاء بإخراج JSON tool calls، يمكن للـ Agent كتابة/تنفيذ Python
لتركيب Tools ومعالجة البيانات.

مع ذلك، يوصي المصدر بـ Frameworks أخرى
عندما تتطلب Production requirements:

- Complex branching؛
- Approval gates؛
- Heavy retrieval؛
- حفظ حالة أكثر ثراءً (Richer persistence).

## 14. Lifecycle الخاصة بالـ Agent داخل Memory

يصف المصدر أربع فئات Memory steps.

### كائن TaskStep

تخزن User instruction الأصلية.

وقد تتضمن Images.

### كائن PlanningStep

تخزن High-level plan عندما يكون Planning مفعّلًا.

### كائن ActionStep

تخزن دورة Think-act-observe واحدة.

وقد تحتوي على:

- Model output؛
- Tool calls؛
- Text observations؛
- ملاحظات صورية (Image observations).

### كائن FinalAnswerStep

تخزن النتيجة النهائية.

من الناحية المفاهيمية:

```text
TaskStep — خطوة المهمة
  ↓
PlanningStep — خطوة التخطيط (اختيارية)
  ↓
ActionStep — خطوة فعل
  ↓
ActionStep — خطوة فعل
  ↓
...
  ↓
FinalAnswerStep — خطوة الإجابة النهائية
```

## 17. يمكن أن تكون Agent framework مستقلة عن Model provider (Model-agnostic)

### Models محلية (Local models)

- Transformers runtime؛
- Runtime موجهة إلى Apple Silicon؛
- خادم vLLM.

### Models مستضافة (Hosted models)

- Inference provider/client؛
- OpenAI-compatible server؛
- طبقة تجريد API.

الدرس المعماري الدائم:

```text
حلقة Agent (agent loop)
≠
Model provider محدد
```

افصل:

```text
واجهة Reasoning
عن
Backend خاص بـ Model serving
```

وهذا يجعل Infrastructure قابلة للاستبدال.

## 18. لماذا توجد Computer-use agents؟

غالبًا ما تستخدم UI automation التقليدية:

- Selectors؛
- HTML structure؛
- أتمتة Browser مبرمجة (Scripted browser automation).

يمكن أن تكون هذه الأساليب هشة عندما:

- يتغير Layout؛
- تكون المعلومات الحرجة بصرية؛
- لا يكون التطبيق Web/DOM based؛
- لا تتوفر Selectors.

يمكن لـ VLM بدلًا من ذلك العمل انطلاقًا من:

```text
لقطات الشاشة (screenshots)
```

وهذا يحاكي طريقة استخدام الإنسان لـ GUI.

لكن المصدر يؤكد أن Screenshot-based approaches تكون عمومًا
أكثر هشاشة من Structured API/tool interaction.

## 19. Structured APIs مقابل Screenshot-based computer use

يصف المصدر عدة أساليب في لقطة من أوائل 2026.

### Agents المعتمدة على API/Tools

```text
Structured request — طلب منظّم

```

## 38. ثلاثة أساليب عامة لسلوك Robot

```text
عروض بشرية (human demonstrations)
```

## 52. الـ Action expert


## 54. لماذا نعمل Cache لـ VLM context؟

تتطلب Diffusion/flow matching عدة Refinement steps.

إذا لم تتغير Observation الخاصة بـ VLM داخل هذه الخطوات، فإن إعادة تشغيل
VLM كاملًا إهدار للـ Compute.

بدلًا من ذلك:

```text
شغّل VLM مرة واحدة
→ خزّن Context K/V/features في Cache

لكل Action denoising step:
أعد استخدام VLM context
```

يتغير فقط Action-query representation.

وهذا يجعل Iterative action generation أقل تكلفة.

تعكس هذه الفكرة مباشرةً منطق KV cache في Language-model inference.

### تكييف Advantage (Advantage conditioning)

- أي Inputs غير موثوقة؟

- Control frequency؟

## 65. النموذج الذهني الكامل لـ Agentic VLM/VLA

يمكن ضغط الفصل في Loop مشتركة واحدة:

```text
OBSERVE
   ↓
BUILD STATE
   ↓
DECIDE / GENERATE ACTION
   ↓
VALIDATE
   ↓
EXECUTE
   ↓
OBSERVE AGAIN
```

### النسخة الرقمية (DIGITAL VERSION)

```text
Screenshot / Tool result
→ LLM/VLM
→ Tool call / Click / Type / Code
→ Software environment
→ Observation جديدة
```

```text
Cameras + Instruction + Proprioception
→ Pretrained VLM
→ Cached semantic context
→ Diffusion/flow Action expert
→ Action chunk
→ Low-level controller
→ Observation جديدة
```

والقواعد الهندسية الرئيسية هي:

```text
استخدم Deterministic code للمهام Deterministic
اجعل Actions منظّمة ومتحققًا منها
قيّم الخطوات الفردية والنتائج النهائية معًا

اعمل Cache لـ Semantic context البطيئة عند الحاجة إلى Refinement متكرر
```

المبدأ النهائي للفصل بسيط:

> **سواء كان المخرج JSON tool call أو Mouse click أو Joint angle، ينجح
> Multimodal system القادر على الفعل عبر إغلاق Loop بين
> Perception وAction.**

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: "Agent هو مجرد LLM يستطيع استدعاء Function واحدة."

Tool calling هو مستوى واحد من Agency.

أما Multistep feedback loop فهي التي تتيح Open-ended agent behavior.

### المفهوم الخاطئ 2: "زيادة Autonomy أفضل دائمًا."

لا.

غالبًا ما يكون Simple routing أو Deterministic
call واحدة هو الحل الهندسي الأفضل.

### المفهوم الخاطئ 3: "ينبغي تفويض كل شيء إلى Agent."

لا.

استخدم Deterministic software للخطوات Deterministic.

### المفهوم الخاطئ 4: "إذا نجحت المهمة النهائية مرة واحدة، فهذا يعني أن Agent موثوق."

تحتاج أيضًا إلى Repeated task evaluation وStep-level traces.

### المفهوم الخاطئ 5: "Code-generating agents وStructured tool-calling agents متطابقة."

إنها تعرض Action surfaces مختلفة ومفاضلات مختلفة في Security/validation.

### المفهوم الخاطئ 6: "Screenshot-based computer-use agent أكثر موثوقية من Direct API."

يقدم المصدر Structured APIs/tool calls بوصفها الأفضل عندما تكون متاحة.

### المفهوم الخاطئ 7: "GUI localization وGUI reasoning هما المشكلة نفسها."

تجيب Localization عن **أين**.

أما Agentic control فتقرر أيضًا **ما Action التي ينبغي تنفيذها وبأي ترتيب**.

### المفهوم الخاطئ 8: "كل GUI model تستخدم Coordinates مطبّعة 0–1000."

لا.

Coordinate systems خاصة بكل Model.

### المفهوم الخاطئ 9: "الاحتفاظ بكل Screenshot يحسن Agent memory."

يمكن لعدد كبير من Screenshots القديمة أن يهدر Context ويشتت Model.

### المفهوم الخاطئ 10: "Agent security تتعلق أساسًا بالمخرجات النصية الضارة."

Tool permissions وThird-party code وUntrusted web content
تنشئ مخاطر فعلية على Actions والوصول إلى البيانات.

### المفهوم الخاطئ 11: "VLA تعني إرسال Raw motor voltage من LLM."

يصف المصدر Action set-points تستهلكها Lower-level controllers.

### المفهوم الخاطئ 12: "يمكن لـ Robotics data تحمل Timestamp alignment تقريبي."

قد تؤدي أخطاء Timing الصغيرة إلى تعليم علاقات
Observation-action خاطئة بصورة منهجية.

### المفهوم الخاطئ 13: "Demonstration واحدة تكفي إذا كان VLM قويًا."

تحتاج Policies إلى Episodes ذات Variation
meaningful حتى لا تحفظ Trajectory واحدة.

### المفهوم الخاطئ 14: "VLA هي Architecture جديدة تمامًا وغير مرتبطة بـ VLMs."

يقدم الفصل VLAs الحديثة بوصفها Pretrained VLMs مع State/action machinery إضافية.

### المفهوم الخاطئ 15: "يجب إعادة تشغيل VLM في كل Action denoising step."

يصف المصدر Cache لـ VLM context أثناء Refinement لـ Action queries.

### المفهوم الخاطئ 16: "التنبؤ بـ Action واحدة كل مرة أكثر دقة دائمًا، ولذلك هو أفضل."

قد يجعل ذلك متطلبات Inference غير عملية؛ إذ تستبدل Action chunks
بعض Refresh frequency بكفاءة أعلى في Continuous control.

## المصطلحات الأساسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| الوكيل (Agent) | Model يعمل داخل Feedback loop مع إمكانية الوصول إلى Tools/Actions |
| طيف الوكالة (Agency spectrum) | مستويات متزايدة من Tool routing حتى Multistep autonomous loops |
| نمط ReAct | Think/act/observe loop مع Feedback متكررة |
| اختيار Tool (Tool selection) | اختيار External function التي ينبغي أن تعالج المهمة |
| استدعاء Tool (Tool calling) | إنتاج Structured tool invocation |
| كائن TaskStep | كائن Agent memory يحتوي المهمة الأولية |
| كائن PlanningStep | High-level plan اختيارية |
| كائن ActionStep | دورة Reasoning/action/observation واحدة |
| كائن FinalAnswerStep | النتيجة النهائية التي يعيدها Agent |
| المتغير `observations_images` | Visual observations مثل Screenshots المخزنة في Agent step |
| فئة CodeAgent | Agent يكتب/ينفذ Code بوصفه Action mechanism |
| فئة ToolCallingAgent | Agent ينتج Structured tool calls |
| وكيل استخدام الحاسوب (Computer-use agent) | Agent يشغل GUI environments |
| تحديد موقع GUI (GUI localization) | التنبؤ بموضع Target داخل Interface |
| الإحداثي المطبّع (Normalized coordinate) | موضع ممثل بالنسبة إلى Fixed scale بدل Pixels |
| مساحة الفعل (Action space) | مجموعة Operations الصالحة التي يمكن للـ Agent تنفيذها |
| Grounding على مستوى الخطوة (Step-level grounding) | ما إذا كانت كل Action صحيحة بالنسبة إلى Current state |
| نجاح على مستوى المهمة (Task-level success) | ما إذا اكتمل Workflow كاملًا بصورة صحيحة |
| طبقة التحكم (Control plane) | Deterministic runtime تدير Sessions وPermissions وQueues وDispatch |
| نموذج VLA | Vision-language-action model يحوّل Observations/instructions إلى Actions |
| السياسة (Policy) | دالة تحوّل Observations إلى Actions |
| الحس الداخلي للجسم (Proprioception) | الحالة الداخلية لجسم Robot |
| الحلقة الكاملة (Episode) | Demonstration كاملة لمهمة |
| التحكم عن بُعد (Teleoperation) | تحكم الإنسان المستخدم لجمع Robot demonstrations |
| التعلم بالمحاكاة (Imitation learning) | تعلم Policy من Expert demonstrations |
| حزمة أفعال (Action chunk) | Sequence من Future actions يتم التنبؤ بها دفعة واحدة |
| المطابقة التدفقية (Flow matching) | طريقة Continuous generation تكرارية تستخدم لـ Action vectors |
| محول الانتشار (DiT) | Transformer يُستخدم ضمن Diffusion لتوليد Actions تكراريًا |
| خبير الأفعال (Action expert) | Network متخصصة تولد Future robot actions |
| القيمة المستهدفة للمتحكم (Controller set-point) | Joint/gripper state مستهدفة تُرسل إلى Lower-level control |
| قائمة انتظار الأفعال (Action queue) | Buffer من Future robot actions تنتظر التنفيذ |
| التحكم غير المتزامن (Asynchronous control) | توليد Chunks مستقبلية أثناء تنفيذ Actions الحالية |
| تجسيد الروبوت (Embodiment) | Sensors وJoints وAction structure الخاصة بجسم Robot معين |
| تكييف Advantage (Advantage conditioning) | Conditioning للـ Policy وفق ما إذا كان السلوك أفضل أو أسوأ من المتوقع |

## احتفظ بهذه الفكرة (Retain this idea)

**Agentic VLMs وVLAs صورتان للفكرة الأساسية نفسها: يصبح Perception مفيدًا
عندما يرتبط بـ Closed action loop. لا تكتفي أقوى الأنظمة بتعظيم
Autonomy؛ بل تعرّف Observations بعناية، وتقيد Actions وتتحقق منها،
وتبقي Deterministic infrastructure خارج Model، وتقيس Success
على مستوى الخطوة والمهمة معًا، وتلاحظ مرارًا
نتائج ما تنفذه.**
