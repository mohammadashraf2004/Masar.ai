> **الدرس:** M01.L11  
> **مواءمة المصدر:** Chapter 18 من مادة Early Release المقدَّمة.  
> يركّز هذا الدرس على **الطبقة الاجتماعية في AgentOps**: توحيد Agents، واكتشافها، وحوكمة من يمكنه استخدامها.

## نواتج التعلّم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يخلق نجاح Agents مشكلات تشغيلية جديدة على مستوى المؤسسات.
- تعريف Snowflake Problem وDiscovery Gap وAccess Control Sprawl.
- شرح لماذا يجب أن تبدأ الحوكمة عند إنشاء source code بدلًا من وقت النشر.
- شرح الغرض من Agent Template Catalog.
- مقارنة قوالب Simple Chat وRAG Agent وAction Agent.
- شرح لماذا تحسّن بنية repository الموحّدة قابلية الصيانة والأمان والاختبار والتعاون.
- شرح دور `agent.py` و`context.py` و`prompts.py` و`examples.py` و`tools.py` ومجلدات evaluation وmonitoring وtests وdeployment.
- شرح دور `.well-known/agent.json` وAgent Card.
- شرح بنية sub-agent العودية داخل خدمة واحدة قابلة للاكتشاف خارجيًا.
- شرح لماذا يمكن لـ Agent Card واحدة ظاهرة خارجيًا أن تمثل نظام multi-agent داخليًا.
- تصميم metadata لـ Agent Template Catalog.
- تتبّع workflow المكوّن من أربع خطوات لإنشاء نسخة من template: discovery وselection/input وhydration وpipeline initialization.
- التمييز بين template العام والمشروع الذي تم إنشاؤه منه.
- شرح نموذج الملكية بين Center of Excellence ووحدات الأعمال.
- شرح كيف يصبح Agent منشورًا Agent-as-a-Service.
- التمييز بين Agent Template Catalog وAgent Registry.
- شرح لماذا يكون Registry دليل خدمات حيًا وليس مكتبة source code.
- شرح لماذا لا تكفي A2A Agent Card القياسية وحدها لحوكمة المؤسسات.
- شرح نمط Registry Record wrapper.
- تعريف Agent Identity وInternal Code Name وGovernance Metadata وPublic Facade Definition.
- شرح لماذا يجب ألا يحصل المستخدمون النهائيون على عناوين service الداخلية أو تفاصيل authentication.
- شرح Registry Hygiene: التسجيل التلقائي عند الإنشاء، وpruning/Zombie detection، وmetadata التي يحافظ عليها المالك.
- تتبّع تفاعل آمن من frontend → backend → registry → agent.
- شرح Agent Gateway كمحرك policy يجيب عن السؤال: "هل يمكن لـ Subject A الوصول إلى Agent B؟"
- التمييز بين سياسات user-to-agent وgroup-to-agent وagent-to-agent.
- شرح القيمة الأدائية والأمنية لـ agent-to-agent allow-lists.
- مقارنة نماذج central-admin وagent-owner وgroup-automation وfederated-hybrid للحوكمة.
- شرح Birthright Access مقارنةً بـ Subscription Marketplace Access.
- مقارنة تطبيقات Gateway المعتمدة على configuration-as-code وdatabase/policy-store وcloud-IAM.
- شرح دور Agent Registry Portal للمستهلكين والمالكين والمنصة.
- شرح الفرق بين صيانة infrastructure وصيانة policy.
- شرح Policy Drift والمراجعة الدورية للوصول.
- تتبّع مثال Marketing Router → Sales Analytics باستخدام Agent Identities صريحة.
- شرح فجوة الهوية بين service identity وhuman user identity.
- شرح لماذا تظل user identity propagation وdelegated authorization مطلوبة بعد Gateway authorization.
- تتبّع دورات الحياة الكاملة للإنشاء والحوكمة والاستخدام.
- شرح كيف تتكامل Template Catalog وRegistry وGateway وPortal وbackend في نظام AgentOps واحد.

## 2. مشكلة Snowflake (Snowflake Problem)

Snowflake Agent هو Agent فريد بكل الطرق الخاطئة.

قد يحل Agentان المشكلة نفسها لكنهما يختلفان في:

- logging،
- التعامل مع secrets،
- configuration،
- deployment،
- testing،
- monitoring،
- بنية directory (directory layout).

مثال:

```text
Math Agent A -> إعداد آمن + cloud logging
Math Agent B -> API key مكتوب مباشرة + local text logs
```

كلاهما "يعمل".

لكن واحدًا فقط آمن وقابل للصيانة.

### لماذا هذا مكلف؟

تزيد Snowflakes من:

```text
تكلفة debugging
مخاطر security
جهد المراجعة
تعقيد deployment
وقت onboarding
```

### المبدأ الأساسي

> يجب أن يبدأ التوحيد قبل كتابة أول سطر من business logic المخصص.

---

## 3. فجوة الاكتشاف (Discovery Gap)

قد يقضي فريق أسابيع في إعادة بناء Agent موجود بالفعل في مكان آخر.

مثال:

```text
فريق Student Success:
يبني Natural Language -> SQL Agent

فريق Data Engineering:
يمتلك بالفعل NL -> SQL Agent بمستوى production
```

المشكلة ليست في القدرة التقنية.

بل في discoverability.

وهذا يخلق:

```text
تكلفة مكررة
مراجعة security مكررة
جودة أقل
ملكية مجزأة
```

يحل Registry هذه المشكلة أثناء runtime.

ويحل template catalog مشكلة مرتبطة بها وقت الإنشاء.

---

## 4. تضخم التحكم في الوصول (Access Control Sprawl)

مع زيادة عدد المستخدمين وAgents، تتضخم علاقات الوصول.

وتظهر أسئلة مثل:

```text
أي الطلاب يمكنهم استخدام أي tutors؟
أي أعضاء هيئة التدريس يمكنهم استخدام grading agents؟
أي Agents يمكنها استدعاء أي Agents أخرى؟
أي خدمات داخلية يجب ألا تظهر للمستخدم أبدًا؟
```

لا يمكن لتضمين permissions داخل كل Agent بشكل مباشر أن يتوسع بكفاءة.

يجب أن تصبح access policy نظامًا منفصلًا يخضع للحوكمة.

## 5. الطبقة الاجتماعية في AgentOps

يقدّم المصدر ثلاثة مكوّنات رئيسية:

```text
دليل قوالب Agent (Agent Template Catalog)
سجل Agents (Agent Registry)
بوابة Agents (Agent Gateway)
```

### دليل قوالب Agent (Agent Template Catalog)

يوحّد عملية الإنشاء.

### سجل Agents (Agent Registry)

يتيح اكتشاف Agents المنشورة.

### بوابة Agents (Agent Gateway)

تتحكم في الوصول إلى تلك Agents.

وتشكّل هذه المكونات معًا الطبقة الاجتماعية:

```text
كيف تولد Agents
كيف يتم العثور على Agents
من المسموح له بالتفاعل معها
```

## 6. دليل قوالب Agent (Agent Template Catalog)

يجب أن تبدأ الحوكمة من source code.

بدلًا من أن تقول المنصة لكل developer:

```text
"من فضلك تذكّر كل معايير security وmonitoring وdeployment."
```

فإنها تمنحه blueprint معتمدًا مسبقًا.

Agent Template Catalog هو:

```text
مكتبة من scaffolding جاهز لمستوى production
```

يستخدم المصدر تشبيه "Cookie Cutter".

يبدأ كل Agent جديد بالـ DNA الأساسي نفسه.

## 7. قالب المحادثة البسيطة (Simple Chat Template)

يكون Simple Chat template مناسبًا لـ:

```text
مدرّس الرياضيات (Math Tutor)
مدرّس القواعد (Grammar Tutor)
مساعد محادثي أساسي
```

وقد يتضمن مسبقًا:

- conversation memory،
- guardrails أساسية،
- prompts قياسية،
- tests،
- هيكل deployment (deployment skeleton).

بعد ذلك يركّز developer على سلوك المجال.

---

## 8. قالب RAG Agent

يكون RAG template مناسبًا عندما يجب على Agent الإجابة من knowledge base.

وقد يتضمن:

```text
تكامل vector database
embeddings — تمثيلات متجهية
document pipeline — مسار معالجة المستندات
retrieval — الاسترجاع
نمط grounded-answer
```

مثال:

```text
Agent للمناهج (Curriculum Agent)
```

يزيل template أعمال الإعداد المتكررة.

ويضيف developer بيانات syllabus/data الفعلية.

---

## 9. قالب Action Agent

يقوم Action Agent باستدعاء tools أو خدمات خارجية.

وقد يتضمن:

```text
تطبيق A2A
معالجة الأخطاء
authentication flow — مسار المصادقة
بنية tools
```

أمثلة:

```text
Agent للتقويم (Calendar Agent)
Agent لـ Drive (Drive Agent)
Agent لسير العمل (Workflow Agent)
```

يمنح هذا template الـ action-oriented Agents نقطة بداية آمنة.

## 10. مستودع Agent موحّد

يقترح المصدر بنية "Gold Standard".

تصوريًا:

```text
<agent_name>/ — مجلد Agent الرئيسي
├── .well-known/ — مجلد الاكتشاف القياسي
│   └── agent.json — ملف Agent Card
├── deploy/ — ملفات deployment
├── evaluation/ — ملفات evaluation
├── monitoring/ — ملفات monitoring
├── sub_agents/ — مجلد sub-agents
├── tests/ — ملفات tests
├── utils/ — أدوات مساعدة

├── context.py — إدارة context
├── examples.py — أمثلة few-shot
├── prompts.py — تعريفات prompts
├── tools.py — تعريفات tools

```

الأسماء الدقيقة خاصة بالمصدر.

## 11. ملفات Agent الأساسية

يفصل المصدر عدة مسؤوليات.

### ملف `agent.py`

يحتوي على orchestration الرئيسي ومنطق Agent.

### ملف `context.py`

يحتوي على session state وإدارة context window.

### ملف `prompts.py`

يحتوي على system instructions وتعريفات persona.

### ملف `examples.py`

يحتوي على few-shot behavior examples.

وهذا مفيد لأن prompt engineers يستطيعون تعديل examples/prompts دون لمس core orchestration code.

## 12. طبقة Tools وUtilities

### ملف `tools.py`

يعرّف tools لـ Agents الأبسط.

وقد تستبدله المشاريع الأكثر تعقيدًا بهيكل `tools/` كامل.

### ملف `utils/helper.py`

يحتوي على helpers عامة.

أمثلة:

```text
تنسيق التاريخ
أدوات strings
تحويلات شائعة
```

وهذا يُبقي منطق Agent الخاص بالمجال نظيفًا.

## 13. طبقة Protocol: ملف `.well-known/agent.json`

يعدّ المصدر هذا واحدًا من أهم ملفات interoperability.

تصف Agent Card الخدمة المنشورة.

وقد تتضمن:

```text
الاسم (name)
الوصف (description)
الإصدار (version)
القدرات (capabilities)
نقطة النهاية (endpoint)
المصادقة (authentication)
المهارات (skills)
```

ووضعها تحت:

```text
.well-known/ — موقع الاكتشاف القياسي
```

يدعم standard discovery.

يستطيع Agent Registry قراءة هذه القدرات دون إعادة إدخالها يدويًا.

## 14. يمكن لـ sub-agents اتباع البنية نفسها بشكل عودي

قد يحتوي Agent معقد على:

```text
Agent مشرف (Supervisor)
Agent للهندسة (Geometry Agent)
Agent للجبر (Algebra Agent)
Agent للتقويم (Calendar Agent)
```

يسمح template في المصدر لـ `sub_agents/` بتكرار نسخة أصغر من البنية نفسها.

وهذا يعطي تصميمًا "fractal":

```text
Agent أب
  يحتوي على
Agents أبناء
  تستخدم
اتفاقيات متشابهة
```

يمكن اختبار كل child بصورة مستقلة.

## 15. يمكن لخدمة واحدة قابلة للاكتشاف أن تحتوي عدة Agents داخلية

قد يعمل repository بالكامل كـ runtime/container واحد.

خارجيًا:

```text
Agent Card واحدة
service identity واحدة
endpoint واحد
```

داخليًا:

```text
Agent مشرف (Supervisor)
+ عدة sub-agents
```

وهذا قوي لأن مستهلكي المؤسسة لا يحتاجون إلى فهم orchestration الداخلي.

### مبدأ Encapsulation

> اعرض service boundary مستقرة، وأخفِ تعقيد multi-agent الداخلي.

في مؤسسة صغيرة:

## 19. من Catalog إلى Codebase

يصف المصدر workflow من أربع خطوات.

```text

3. Hydration — إنشاء نسخة المشروع

```

يجب أن يشبه ذلك استخدام internal product catalog.

## 20. الخطوة 1 — الاكتشاف (Discovery)

يبحث developer عن capability.

مثال:

```text
"SQL"
```

ويجد:

```text
قالب Natural Language to SQL (Natural Language to SQL Template)
```

يتم اختيار template وفق business need.

## 21. الخطوة 2 — الاختيار والإدخال (Selection and Input)

يوفّر developer metadata خاصة بالمشروع.

أمثلة:

```text
اسم Agent الجديد
المشروع/البيئة المستهدفة
الفريق المالك
```

---

## 22. الخطوة 3 — Hydration

تقوم automation باستنساخ/نسخ blueprint إلى repository جديد مخصص.

في هذه اللحظة:

```text
template عام
```

يصبح:

```text
project instance محدد
```

يذكر المصدر Infrastructure-as-Code-style automation كآلية محتملة.

التقنية الدقيقة ليست هي الفكرة الدائمة.

---

## 23. الخطوة 4 — تهيئة Pipeline (Pipeline Initialization)

لا ينبغي أن يحتوي repository الجديد على code فقط.

بل يجب أيضًا تهيئة CI/CD pipeline الخاصة به.

يمكن لهذه pipeline لاحقًا التعامل مع:

```text
testing — الاختبار
evaluation — التقييم
container build — بناء container
deployment — النشر
registration — التسجيل
```

وهذا يربط بنية code الموحّدة بعمليات موحّدة.

### الاختبارات (Tests)


## 26. من Repository إلى Agent-as-a-Service

لا يكون repository قابلًا لإعادة الاستخدام أثناء runtime بعد.

بعد deployment، يصبح Agent:

```text
خدمة مستقلة (independent service)
```

مع:

```text
endpoint — نقطة النهاية
identity — الهوية
version — الإصدار
lifecycle — دورة الحياة
```

يسمّي المصدر هذا التحول Agent-as-a-Service.

وهذا هو أساس runtime لإعادة الاستخدام.

---

## 27. Agents كـ Microservices

سواء كان Agent بسيطًا أو multi-agent داخليًا، يمكن أن يظهر كل Agent منشور كخدمة واحدة.

أمثلة:

```text
مدقق القواعد (Grammar Checker)
مدرّس الرياضيات (Math Tutor)
مخطط المناهج (Curriculum Planner)
```

ولكل منها:

- endpoint خاص بها،
- lifecycle خاصة بها،
- identity خاصة بها.

وهذا يجعل deployment والاكتشاف المستقلين ممكنين.

## 28. Deployment يخلق مشكلة Discovery

افترض أن Math Tutor يعمل في مكان ما داخليًا.

كيف تعثر عليه خدمة أخرى؟

كتابة:

```text
https://math-service-v1.internal — عنوان service داخلي
```

مباشرة في كل مكان أمر هش.

يحل Agent Registry هذه المشكلة.

## 29. سجل Agents (Agent Registry)

يقارن المصدر Agent Registry بدليل موظفي الجامعة.

وهو:

```text
قاعدة بيانات مركزية حية لـ Agents المنشورة
```

عندما يبدأ Agent العمل، تسجّل pipeline الخاصة به:

```text
من هو
أين يوجد
ما الذي يستطيع فعله
هل هو نشط
```

ثم يستعلم المستهلكون من Registry بدلًا من hard-coding لعناوين service.

## 30. Template Catalog مقابل Agent Registry

## 31. لماذا لا تكفي Agent Card لحوكمة المؤسسات؟

صُممت Agent Card القياسية من أجل interoperability.

وهي تشبه بطاقة أعمال.

وقد تحتوي على:

```text
الاسم (name)
الوصف (description)
الإصدار (version)
القدرات (capabilities)
URL — عنوان الخدمة
طرق authentication
```

لكن عمليات المؤسسة تحتاج إلى المزيد.

أمثلة:

```text

المالك (owner)
سياسة الحقول public/private
internal code name — الاسم الرمزي الداخلي
```

هذه الأمور لا تنتمي إلى public protocol contract.

## 47. سياسات Agent-to-Agent

مثال:



## 63. Authentication وAuthorization وIdentity Propagation

يستعرض المصدر ثلاث احتياجات إضافية.

### التفويض / Delegation (Authorization / Delegation)

هل منح ذلك user الـ Agent تفويضًا للتصرف نيابةً عنه؟

### تمرير الهوية (Identity Propagation)

هل يمكن للأنظمة downstream معرفة:

```text
تم تنفيذ هذا الإجراء
بواسطة Agent X
نيابةً عن User Y
```

ويصبح هذا بالغ الأهمية من أجل:

- row-level security،
- audit،
- أقل صلاحية (least privilege).

يتعمق الفصل التالي في هذا الموضوع.

## 71. النموذج الذهني الكامل

النظام الكامل هو:

```text
كتالوج قوالب الـ Agent
        ↓
مشروع موحّد
        ↓
CI/CD
        ↓
Agent-as-a-Service
        ↓
Agent Registry
        ↓
سجل Registry
   ├── Agent Card
   └── بيانات وصفية للمؤسسة
        ↓
Agent Gateway
        ↓
اكتشاف مفوَّض/منقّى
        ↓
Backend
        ↓
Frontend / agents أخرى
```

يجيب Template Catalog عن:

```text
كيف ينبغي أن أبني Agent؟
```

ويجيب Registry عن:

```text
أي Agents تعمل حاليًا؟
```

ويجيب Gateway عن:

```text
من المسموح له باستخدام أي Agent؟
```

ويجيب Backend عن:

```text
كيف أتصل بأمان دون كشف infrastructure؟
```

وفي النهاية تجيب Identity Propagation عن:

```text
نيابةً عن مَن يتم تنفيذ هذا الإجراء؟
```

وهذا هو الأساس لقوة عمل رقمية قابلة لإعادة الاستخدام والحوكمة.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "تبدأ Governance بعد Deployment."

لا. يبدأ المصدر Governance عند إنشاء source code من خلال templates موحّدة.

### المفهوم الخاطئ 2
> "Template Catalog وAgent Registry هما الشيء نفسه."

لا. الأول يخزن blueprints/source scaffolding، بينما الثاني يخزن live deployed services.

### المفهوم الخاطئ 3
> "يجب عرض كل sub-agent داخلي كخدمة خارجية مستقلة."

لا. يمكن encapsulate نظام multi-agent خلف Agent Card واحدة/service boundary واحدة.

### المفهوم الخاطئ 4
> "يجب أن تخزن Agent Card كل enterprise metadata."

لا. قم بتغليفها داخل Registry Record أغنى بدلًا من تغيير standard protocol object.

### المفهوم الخاطئ 5
> "Display name هو security identity قوية."

لا. يمكن أن تتغير display names. استخدم Agent Identity مستقرة وغير قابلة للتغيير.

### المفهوم الخاطئ 6
> "يجب أن يتلقى browser الـ internal service URL الخاص بـ Agent."

لا. يجب أن يحل backend الـ infrastructure الداخلية وألا يعرض إلا حقول Public Facade الآمنة.

### المفهوم الخاطئ 7
> "إذا كان Agent موجودًا في Registry، فيمكن لكل user الوصول إليه."

لا. Discovery وpermission مسألتان منفصلتان.

### المفهوم الخاطئ 8
> "Agent-to-agent permissions تتعلق فقط بـ security."

لا. تقييد مجموعة Agents القابلة للاستدعاء يقلل أيضًا search space ويحسّن predictability/performance.

### المفهوم الخاطئ 9
> "Central admin واحد هو أفضل governance model على كل نطاق."

لا. قد يصبح bottleneck كبيرًا على مستوى المؤسسة.

### المفهوم الخاطئ 10
> "Group-based access يحل كل مشكلات governance."

لا. قد يكون جامدًا جدًا بالنسبة إلى cross-team access أو access المعتمد على استثناءات.

### المفهوم الخاطئ 11
> "Federated governance تعني عدم وجود معايير مركزية."

لا. فهي تجمع automation/common standards مع local owner accountability.

### المفهوم الخاطئ 12
> "تبقى Registry records صحيحة تلقائيًا إلى الأبد."

لا. تتطلب Registry Hygiene health automation وmetadata يحافظ عليها owner.

### المفهوم الخاطئ 13
> "يجب أن يغيّر browser disconnect أو rebrand الـ Agent Identity."

لا. يجب أن تظل operational identity مستقرة عبر التغييرات الشكلية أو تغييرات endpoint.

### المفهوم الخاطئ 14
> "إذا كان Agent A مسموحًا له باستدعاء Agent B، فقد حُل downstream data authorization."

لا. قد تظل user identity وdelegated authorization بحاجة إلى الانتقال إلى نظام البيانات النهائي.

### المفهوم الخاطئ 15
> "Agent Registry Portal مجرد صفحة search."

لا. فهي تدعم أيضًا access requests وowner approvals وتحديثات control-plane policy.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Agent غير موحّد (Snowflake Agent) | تنفيذ Agent غير موحّد ومكلف في الصيانة |
| فجوة الاكتشاف (Discovery Gap) | الفشل في العثور على Agents الموجودة وإعادة استخدامها |
| تضخم التحكم في الوصول (Access Control Sprawl) | النمو السريع لعلاقات permissions بين users وAgents |
| دليل قوالب Agent (Agent Template Catalog) | مكتبة من blueprints معتمدة لـ source code الخاص بـ Agents |
| قالب القطع القياسي (Cookie Cutter) | تشبيه المصدر للقوالب الموحّدة القابلة لإعادة الاستخدام |
| قالب Simple Chat (Simple Chat Template) | blueprint خفيف لـ conversational agent |
| قالب RAG Agent (RAG Agent Template) | blueprint لـ Agents المعتمدة على retrieval-grounded |
| قالب Action Agent (Action Agent Template) | blueprint لـ Agents التي تستخدم tools وتنفذ actions |
| بطاقة Agent (Agent Card) | metadata قياسية لـ capability/endpoint في A2A |
| ملف Agent Card (`.well-known/agent.json`) | الموقع التقليدي الموصوف في المصدر لـ Agent Card |
| إنشاء النسخة من القالب (Hydration) | إنشاء project repository جديد من template عام |
| Agent كخدمة (Agent-as-a-Service) | Agent منشور ومُعرّض كخدمة runtime مستقلة |
| سجل Agents (Agent Registry) | دليل مركزي حي لـ Agents المنشورة |
| سجل مغلّف (Registry Record) | enterprise wrapper يحتوي Agent Card بالإضافة إلى governance metadata |
| هوية Agent (Agent Identity) | identity مستقرة وغير قابلة للتغيير تُستخدم في policy وaudit |
| الاسم الرمزي الداخلي (Internal Code Name) | system identifier ثابت ومستقل عن branding |
| بيانات الحوكمة الوصفية (Governance Metadata) | حقول تشغيلية مثل owner وcompliance وcost center |
| الواجهة العامة (Public Facade) | policy تحدد أي حقول Registry يمكن كشفها لكل audience |
| نظافة Registry (Registry Hygiene) | إبقاء records حديثة ونشطة وموثوقة |
| Agent مهجور (Zombie Agent) | service مهجورة/ميتة ما تزال موجودة في Registry |
| بوابة Agents (Agent Gateway) | طبقة policy تتحكم في consumer-to-agent access |
| سياسة User-to-Agent | permission من user محدد إلى Agent |
| سياسة Group-to-Agent | permission من user group إلى Agent |
| سياسة Agent-to-Agent | permission من Agent identity إلى أخرى |
| دائرة الثقة (Circle of Trust) | مجموعة منتقاة من Agents يمكن لـ Agent آخر استدعاؤها |
| الوصول الافتراضي (Birthright Access) | group-based access افتراضي يُمنح تلقائيًا |
| سوق الاشتراك (Subscription Marketplace) | request/approval flow للوصول غير الافتراضي إلى Agents |
| انجراف policy (Policy Drift) | تحوّل access rules إلى حالة قديمة بمرور الوقت |
| تمرير الهوية (Identity Propagation) | تمرير user/service identity عبر downstream calls |
| التفويض (Delegation) | user يفوّض Agent للتصرف نيابةً عنه |

## احتفظ بهذه الفكرة

**يحتاج نظام Agents القابل للتوسع إلى ثلاثة أشكال مختلفة من governance: التوحيد وقت الإنشاء، والاكتشاف أثناء runtime، والتحكم في permission وقت التفاعل. يوحّد Agent Template Catalog طريقة ولادة Agents. ويتتبع Agent Registry أي Agents تعمل وكيف يمكن الوصول إليها. ويحدد Agent Gateway من المسموح له بالتفاعل معها. ويخفي backend الآمن infrastructure الداخلية، وتكشف Public Facades فقط metadata الآمنة، وتربط Agent Identities المستقرة policies، بينما توازن federated governance بين automation وowner accountability. ومعًا تحوّل هذه المكونات مشاريع Agents المعزولة إلى قوة عمل رقمية قابلة لإعادة الاستخدام والحوكمة.**
