## 1. بناء Context: المشكلة التي تحلها RAG و Agents

يحتاج Model إلى شيئين لتنفيذ Task جيدًا:

1. **التعليمات** — ما الذي ينبغي أن يفعله.
2. **المعلومات** — الحقائق أو السجلات أو Documents أو Observations اللازمة لهذه Query تحديدًا.

غالبًا ما تكون Instructions مشتركة عبر Queries كثيرة. أما Context فتكون عادةً خاصة بكل Query.

إذا كان Model يفتقد المعلومات اللازمة للإجابة عن سؤال، فمن المرجح أن يخمّن أو يخطئ أو ينتج Hallucination. وهذا ما يدفع إلى نمطين رئيسيين لبناء Context:

- **RAG:** استرجاع المعلومات ذات الصلة من External Memory.
- **Agents:** استخدام Tools لجمع المعلومات أو تنفيذ Actions داخل Environment.

تُعد RAG في الأساس تقنية لبناء Context. أما Agents فهي أوسع: يمكنها استرجاع المعلومات، وتشغيل Code، واستدعاء APIs، وكتابة البيانات، وتنفيذ Tasks متعددة الخطوات.

ومن التشبيهات المفيدة:

```text
ML التقليدي (Classical ML):     تمنح Feature Engineering الـ Model مدخلات مفيدة
Foundation Model: تمنح Context Construction الـ Model معلومات مفيدة
```

## 2. RAG: استرجع أولًا ثم ولّد

تعزز **RAG** عملية Generation عبر استرجاع معلومات ذات صلة أولًا من مصادر External Memory.

يمكن أن يكون مصدر External Memory:

- Database داخلية للـ Documents.
- محادثات سابقة.
- بيانات Product أو Customer.
- الإنترنت.
- أي External Store يستطيع التطبيق تنفيذ Query عليه.

النمط الأساسي هو:

```text
Query المستخدم (User query)
   -> استرجاع المعلومات ذات الصلة (retrieve relevant information)
   -> دمج Query + Retrieved Context
   -> Generative Model
   -> الإجابة (answer)
```

تكون RAG مفيدة عندما لا يمكن أو لا ينبغي وضع كل Knowledge المحتملة ذات الصلة داخل كل Prompt.

### لماذا لا تلغي Long Context الحاجة إلى RAG تلقائيًا

حتى إذا أصبحت Context Windows كبيرة جدًا:

- يمكن أن تنمو Application Data بسرعة أكبر.
- تكلف Inputs الأطول قدرًا أكبر من المعالجة.
- يمكن أن تضيف Inputs الأطول Latency.
- قد تفشل Models في استخدام كل جزء من Long Context بفاعلية.
- قد تشتت المعلومات غير ذات الصلة Model.

يسمح Retrieval باستخدام Context للمعلومات الأكثر صلة بالـ Query الحالية.

## 3. معمارية RAG: عمليتا Indexing و Querying

يحتوي نظام RAG الأساسي على:

- **Retriever:** يعثر على المعلومات ذات الصلة.
- **Generator:** يستخدم تلك المعلومات لإنتاج الإجابة.

يمتلك Retriever نفسه مهمتين رئيسيتين.

### عملية Indexing

جهّز External Data بحيث يمكن استرجاعها بسرعة لاحقًا.

بالنسبة إلى Document RAG، قد يشمل ذلك:

- Parsing للـ Documents.
- تقسيم Documents إلى Chunks.
- استخراج Terms أو Metadata.
- توليد Embeddings.
- بناء Search Indexes.

### عملية Querying

عند استلام Query من المستخدم، رتّب المعلومات المخزنة وفق Relevance واسترجع أفضل Candidates.

يعتمد نجاح نظام RAG بالكامل بدرجة كبيرة على Retrieval Quality. فلا يستطيع حتى Generator مثالي استخدام معلومات لم يعثر عليها Retriever أصلًا.

## 4. الاسترجاع القائم على المصطلحات (Term-based Retrieval)

تحسب أبسط عائلة من Retrieval Scores للـ Documents باستخدام الكلمات أو Terms المشتركة بينها وبين Query. ويُسمى ذلك أيضًا **Lexical Retrieval**.

### تكرار المصطلح (Term Frequency — TF)

إذا ظهر Query Term مرات كثيرة في Document، فقد تكون Document أكثر صلة بهذا Term.

```text
TF(term, document) = number of times the term appears in the document — عدد مرات ظهور Term داخل Document
```

### التكرار العكسي للوثائق (Inverse Document Frequency — IDF)

تظهر بعض الكلمات في كل مكان ولذلك تخبرنا بالقليل. أما Terms النادرة فتكون غالبًا أكثر إفادة.

يقدم الفصل الفكرة التالية:

```text
IDF(term) = total number of documents / number of documents containing term — عدد Documents الكلي مقسومًا على عدد Documents التي تحتوي على Term
```

تعني قيمة IDF الأعلى أن Term أكثر ندرة، وبالتالي قد تكون أكثر إفادة.

### مقياس TF-IDF

يجمع TF-IDF بين الأهمية المحلية داخل Document والندرة العامة عبر Collection.

تحصل Document على Score مرتفعة عندما تظهر Query Terms المهمة كثيرًا داخلها، لكنها تكون نادرة نسبيًا عبر Corpus.

### الفهرس المعكوس (Inverted Index)

يربط Inverted Index بين Terms والـ Documents التي تحتوي عليها.

```text
"machine" -> doc 1, doc 10, doc 38, doc 42 — Documents التي تحتوي على "machine"
"banana"  -> doc 5, doc 10 — Documents التي تحتوي على "banana"
```

يجعل ذلك Keyword Retrieval سريعًا.

### خوارزمية BM25

تُعد BM25 خوارزمية Ranking شائعة مشتقة من الأفكار العامة نفسها الموجودة في TF-IDF. ومن التحسينات المهمة فيها Normalization وفق طول Document، لأن Documents الأطول تحتوي طبيعيًا على مرات ظهور أكثر للـ Terms.

تظل BM25 خط أساس عمليًا قويًا حتى عند توفر Semantic Retrieval الحديثة.

## 5. أهمية Tokenization في Lexical Search

يتطلب Term-based Retrieval تحديد ما الذي يُعد Term.

قد يقسم Tokenizer بسيط النص حسب المسافات، لكن ذلك قد يدمر معنى العبارات متعددة الكلمات. على سبيل المثال:

```text
"hot dog" -> "hot" + "dog" — تقسيم العبارة إلى Term منفصلين
```

لا تحمل أي من الكلمتين منفردة المعنى نفسه الذي تحمله العبارة كاملة.

قد تشمل Preprocessing:

- تحويل النص إلى Lowercase.
- إزالة Punctuation.
- إزالة Stop Words.
- التعامل مع N-grams الشائعة بوصفها Terms منفردة.

يمكن أيضًا أن يدعم N-gram Overlap عملية Retrieval، رغم أنه يكون أقل قدرة على التمييز عندما تكون Documents أطول بكثير من Queries.

## 6. الاسترجاع القائم على Embeddings

ينظر Term Matching إلى الكلمات الظاهرة. أما **Embedding-based Retrieval** فيحاول مطابقة المعنى.

ويُسمى ذلك أيضًا **Semantic Retrieval**.

أثناء Indexing:

```text
مقطع المستند (Document Chunk) -> نموذج Embedding (Embedding Model) -> متجه (Vector) -> قاعدة بيانات المتجهات (Vector Database)
```

أثناء Querying:

```text
Query -> Embedding Model نفسه -> Query Vector
      -> العثور على أقرب Document Vectors
      -> استرجاع Top-k Chunks
```

يُعد Embedding Model عنصرًا حاسمًا. فإذا فشل في وضع المحتوى المتشابه دلاليًا بالقرب من بعضه، فسيفشل Retrieval حتى لو كانت Vector Database تعمل بصورة مثالية.

## 7. Vector Databases والبحث عن أقرب الجيران

يجب على Vector Database تنفيذ أكثر من مجرد تخزين Vectors. فمهمتها الصعبة هي العثور بسرعة على Vectors القريبة من Query Vector.

### أقرب `k` جيران بدقة (Exact k-nearest Neighbors — k-NN)

يمكن لـ Exact Search البسيطة أن:

1. تقارن Query Embedding بكل Vector مخزن.
2. ترتب جميع Vectors حسب Similarity.
3. تعيد أفضل `k`.

هذا دقيق لكنه مكلف مع Datasets الكبيرة.

### البحث التقريبي عن أقرب الجيران (Approximate Nearest Neighbors — ANN)

تتنازل Vector Stores الكبيرة عادةً عن قدر صغير من الدقة مقابل Search أسرع بكثير.

يقدم الفصل عدة عائلات مهمة من ANN:

- **LSH:** تضع Vectors المتشابهة في Buckets متشابهة باستخدام Hashing.
- **HNSW:** تبني Multi-layer Similarity Graph قابلة للتنقل.
- **Product Quantization:** تضغط Vectors إلى Representations أقل تكلفة.
- **IVF:** تجمع Vectors في Clusters وتبحث فقط في Clusters الواعدة.
- **Annoy:** تبني عدة Tree Structures للبحث عن Candidates.

تجمع Libraries و Systems هذه الأفكار بطرق مختلفة.

## 8. مقارنة Term-based Retrieval و Embedding-based Retrieval

لا توجد طريقة متفوقة في كل الحالات.

| الخاصية | الاسترجاع القائم على Terms | الاسترجاع القائم على Embeddings |
|---|---|---|
| نوع المطابقة | Lexical Terms | المعنى الدلالي |
| عملية Indexing | عادةً أقل تكلفة وأسرع | تتطلب توليد Embeddings |
| عملية Querying | عادةً سريعة | إنشاء Query Embedding ثم Vector Search |
| قوة خط الأساس | نعم، يوفر Baseline قويًا | غالبًا يحتاج إلى مكونات أكثر |
| Keywords أو Error Codes الدقيقة | غالبًا قوي | قد يفقد تفاصيل Lexical مهمة |
| فهم Intent باللغة الطبيعية | قد يفوّت Paraphrases | غالبًا أقوى |
| مسار التحسين | خيارات Tuning أقل | يمكن Finetune للـ Embeddings أو Retriever |
| التكلفة | عادةً أقل | قد تكون تكلفة Embedding و Storage و Search كبيرة |

من القيود المهمة في Semantic Search أن Embedding لـ Chunk قد يخفي Strings دقيقة مثل Product Identifiers أو Error Codes. وهذا سبب رئيسي لشيوع Hybrid Systems.

## 9. كيفية تقييم Retriever

ينبغي تقييم Retriever وفق جودة Documents التي يعيدها.

### دقة Context (Context Precision)

```text
من كل ما تم استرجاعه، ما النسبة ذات الصلة؟ (Of everything retrieved, what fraction is relevant?)
```

تعني Precision العالية أن كمية قليلة من المواد غير ذات الصلة تُضاف إلى Context.

### استدعاء Context (Context Recall)

```text
من كل ما هو ذو صلة، ما النسبة التي وجدها Retriever؟ (Of everything relevant, what fraction did the retriever find?)
```

تعني Recall العالية أن Evidence المهمة نادرًا ما تضيع.

يكون قياس Recall أصعب في Databases حقيقية كبيرة لأنك تحتاج إلى معرفة Relevance للـ Documents التي **لم** يُرجعها Retriever.

### مقاييس Ranking

عندما يكون الترتيب مهمًا، يذكر الفصل:

- مقياس NDCG.
- مقياس MAP.
- مقياس MRR.

تكافئ هذه Metrics الأنظمة التي تضع Evidence القوية بالقرب من أعلى النتائج.

### قيّم النظام كاملًا أيضًا

تأتي فائدة Retriever في النهاية من قدرة Evidence التي يعيدها على مساعدة Generator في إنتاج إجابات أفضل. لذلك قيّم:

1. جودة Retrieval.
2. جودة Embeddings عند استخدام Embeddings.
3. جودة الإجابات النهائية المولدة (Final Generated Answers).

## 10. المفاضلات بين سرعة Retrieval والتكلفة و Indexing

تمتلك Retrieval Systems قيودها الهندسية الخاصة.

يمكن لـ Embedding Retrieval إضافة تكلفة مقابل:

- توليد Document Embeddings.
- إعادة توليد Embeddings عند تغير البيانات.
- Vector Storage.
- استعلامات البحث بالمتجهات (Vector-search Queries).

كما ينشئ تصميم Index مفاضلة:

- يمكن لـ Index أغنى تحسين Query Accuracy والسرعة.
- لكنه قد يحتاج إلى Memory أكبر ووقت أطول للبناء أو التحديث.

تشمل Metrics المهمة لأنظمة ANN:

- مقياس Recall.
- معدل Queries per Second أو QPS.
- Build Time.
- Index Size.

الحل الذي يسترجع جيدًا لكنه لا يستطيع مواكبة Update Frequency أو Query Traffic لديك ليس حل Production جيدًا.

## 11. Hybrid Search و Reranking و Reciprocal Rank Fusion

غالبًا تجمع Production Retrieval Systems عدة Algorithms لأن Lexical Retrieval و Semantic Retrieval يعالجان Failure Modes مختلفة.

### الدمج التسلسلي أو Reranking

استخدم Retriever منخفض التكلفة للحصول على Candidates كثيرة، ثم استخدم Mechanism أكثر دقة لكنه أعلى تكلفة لإعادة ترتيبها.

```text
Query
 -> Retrieval أولي منخفض التكلفة (cheap candidate retrieval)
 -> Reranker أعلى تكلفة (expensive reranker)
 -> أفضل عدد قليل من Chunks (best few chunks)
```

### الدمج المتوازي أو Ensemble

شغّل عدة Retrievers في الوقت نفسه، ثم ادمج Rankings الخاصة بها.

### أسلوب Reciprocal Rank Fusion أو RRF

يعطي RRF وزنًا أعلى للـ Documents التي تظهر بالقرب من القمة عبر Retrievers مختلفة. وتُحسب Final Score الخاصة بـ Document اعتمادًا على مواضعها في جميع Ranked Lists.

الفكرة العملية بسيطة:

> ينبغي أن تصبح Documents التي تُرتب باستمرار في مراكز مرتفعة بواسطة طرق Retrieval مختلفة Candidates نهائية قوية.

## 12. استراتيجية Chunking

غالبًا تكون Documents كبيرة جدًا بحيث لا يمكن استرجاعها كوحدة واحدة. لذلك تُقسم إلى **Chunks** قبل Indexing.

تشمل الاستراتيجيات الشائعة:

- عدد ثابت من Characters.
- عدد ثابت من Words.
- التقسيم حسب Sentences.
- التقسيم حسب Paragraphs.
- التقسيم التكراري (Recursive Splitting): Section -> Paragraph -> Sentence.
- تقسيم خاص بـ Domain مثل Code Functions أو Q&A Pairs.

### لماذا يساعد Overlap

يمكن لـ Hard Boundary فصل فكرة واحدة بين Chunkين. يكرر Overlap مقدارًا صغيرًا من محتوى الحدود حتى تبقى Context المهمة داخل Chunk واحدة على الأقل.

### مقارنة Chunks الصغيرة والكبيرة

**Chunks الأصغر**

- تسمح بوضع عدد أكبر من القطع المختلفة داخل Context.
- قد تحسن Specificity الخاصة بـ Retrieval.
- تزيد عدد Embeddings و Search Candidates.
- قد تفقد Context الأوسع.

**Chunks الأكبر**

- تحافظ على Context محلية أكثر.
- تنتج عددًا أقل من Index Entries.
- قد تحتوي على مواد غير ذات صلة.
- قد تقلل عدد Sources المختلفة التي يمكن وضعها داخل Prompt.

لا يوجد Chunk Size أو Overlap مثالي عالميًا. يجب تقييمهما بالنسبة إلى التطبيق.

## 13. Reranking و Query Rewriting

### Reranking

لا يكون Ranking الأول الذي ينتجه Retriever هو الأفضل دائمًا. ويمكن لمرحلة ثانية استخدام Model أكثر دقة أو Features إضافية لإعادة ترتيب Candidates.

يكون Reranking مفيدًا بصورة خاصة عندما تريد عددًا صغيرًا فقط من Chunks عالية الجودة لتقليل Context Length والتكلفة.

يمكنك أيضًا تضمين Recency عندما ينبغي للمعلومات الأحدث أن تحتل ترتيبًا أعلى.

### إعادة صياغة Query (Query Rewriting)

غالبًا تكون Conversational Queries غير مكتملة بمفردها.

مثال:

```text
User: When did John Doe last buy from us?   — السؤال الأول
Assistant: ...
User: How about Emily Doe?   — سؤال متابعة يعتمد على السياق السابق
```

ينبغي إعادة صياغة Final Query إلى صيغة مستقلة بذاتها، مثل:

```text
When did Emily Doe last buy something from us?   — الاستعلام بعد إعادة صياغته ليصبح مستقلًا
```

يجب ألا يخترع Rewriter معلومات Identity مفقودة. فإذا تعذر حل Query بأمان، ينبغي أن يعترف بذلك بدلًا من Hallucinating تفاصيل.

## 14. Contextual Retrieval

تفقد Chunks أحيانًا Context التي تشرح معناها. وتقوم **Contextual Retrieval** بإثراء كل Chunk قبل Indexing.

قد تشمل الإضافات:

- عنوان Document.
- Summary.
- Tags.
- Keywords.
- Extracted Entities.
- Product Metadata أو Reviews.
- الأسئلة التي يمكن لـ Chunk الإجابة عنها.
- شرحًا قصيرًا مولدًا يوضح موضع Chunk داخل Document الأصلية.

يمكن لذلك مساعدة Semantic Retrieval في استعادة Concepts دقيقة قد تختفي أثناء Embedding.

## 16. Multimodal RAG

لا يشترط أن تسترجع RAG نصوصًا فقط.

إذا كان Generator يستطيع استخدام الصور أو Audio أو Video أو Modalities أخرى، فيمكن لـ Retriever توفير تلك Modalities بوصفها Context أيضًا.

بالنسبة إلى Image Retrieval، قد تكفي Metadata مثل Captions و Tags. أما Retrieval اعتمادًا على Visual Content فيحتاج إلى Shared Multimodal Embedding Space.

مفاهيميًا:

```text
Text Documents -> Multimodal Embeddings -> Vector DB
Images         -> Multimodal Embeddings -> Vector DB

Text Query -> Embedding Space نفسها -> أقرب Text + Images
```

يستخدم الفصل Model مثل CLIP مثالًا على تمثيل النصوص والصور داخل Joint Embedding Space.

## 17. RAG مع Tabular Data

غالبًا تتطلب Structured Tables Workflow مختلفة عن Document Retrieval.

افترض أن المستخدم يسأل:

```text
How many units of Fruity Fedora were sold in the last 7 days?   — سؤال بلغة طبيعية
```

قد يحتاج النظام إلى:

1. فهم Table و Columns ذات الصلة.
2. توليد SQL Query.
3. تنفيذ SQL.
4. استخدام Result بوصفها Context للإجابة النهائية.

```text
سؤال باللغة الطبيعية (natural-language question)
 -> Text-to-SQL
 -> تنفيذ SQL (SQL execution)
 -> نتيجة Structured (structured result)
 -> Response باللغة الطبيعية (natural-language response)
```

إذا كان عدد Tables كبيرًا جدًا بحيث لا يمكن وضع Schemas كلها في Prompt، فقد يحتاج النظام أولًا إلى استرجاع أو توقع Tables ذات الصلة.

## 18. ما هو Agent؟

يمكن فهم Agent بوصفه شيئًا:

1. يدرك Environment.
2. يختار Actions.
3. ينفذ Actions على Environment لتحقيق Goal.

تعتمد Environment على Task:

- يعمل Game Agent داخل Game.
- يعمل Coding Agent على Files و Repositories و Terminals.
- قد يعمل Research Agent على Web و Document Stores.
- قد يعمل Robot في العالم المادي.

يعمل Model بوصفه **Planner أو Brain** الذي يفسر Task ويختار Actions ويعالج Observations ويقرر ما إذا تم تحقيق Goal.

يمكن حتى النظر إلى نظام RAG بسيط على أنه Agent صغير يكون Retriever فيه Tool واحدة.

## 19. لماذا تكون Agents أصعب من التطبيقات أحادية الخطوة

غالبًا تحتاج Agents إلى خطوات كثيرة. وتتراكم الأخطاء عبر هذه الخطوات.

يوضح الفصل ذلك بفكرة ضرب بسيطة: حتى Probability نجاح مرتفعة لكل خطوة يمكن أن تؤدي إلى End-to-end Success ضعيفة عبر عدد كبير من الخطوات.

على سبيل المثال، مع نجاح مستقل قدره 95% لكل خطوة:

```text
10 خطوات  -> roughly 0.95^10 ≈ 60% success
100 خطوة -> roughly 0.95^100 ≈ 0.6% success
```

تكون Agents أيضًا أعلى خطورة لأن Tools يمكن أن تغير أنظمة حقيقية. الإجابة النصية الخاطئة سيئة، لكن Bank Transfer خاطئة أو Database Deletion خاطئة قد تكون أسوأ بكثير.

لهذا تحتاج Agents إلى Planning دقيق و Validation و Permissions و Reflection و Observability و Human Approval للـ Actions الخطرة.

## 20. أدوات Agent

توسع Tool ما يستطيع Model إدراكه أو فعله.

يجمع الفصل Tools المفيدة في ثلاث فئات عامة.

### 1. تعزيز المعرفة (Knowledge Augmentation)

Tools توفر معلومات:

- Document Retrievers.
- Image Retrievers.
- SQL Readers.
- Search APIs.
- Email Readers.
- Slack أو Internal Knowledge Search.
- News أو Web APIs.

تساعد هذه Tools الـ Models على الوصول إلى معلومات حديثة أو خاصة.

### 2. توسيع القدرات (Capability Extension)

Tools تعوض قيود Model:

- Calculator.
- Unit Converter.
- Calendar أو Timezone Tools.
- Translator.
- Code Interpreter.
- OCR أو Transcription.
- أدوات توليد الصور (Image-generation Tools).

بدلًا من إعادة تدريب Model لإجراء Arithmetic مثالي، يمكنه استدعاء Calculator.

### 3. إجراءات الكتابة (Write Actions)

يمكن لـ Tools تغيير Environment:

- إرسال Email.
- تحديث Database.
- إنشاء Order.
- تحويل أموال.
- دمج Code.

توفر Write Actions أكبر إمكانات Automation، وغالبًا أكبر Safety Risk أيضًا.

## 21. Planning: تحويل Goal إلى Actions

تحتوي Task على **Goal** وغالبًا **Constraints**.

مثال:

```text
Goal: التخطيط لرحلة لمدة أسبوعين
Constraint: البقاء ضمن Budget ثابتة
```

يعني Planning اختيار Sequence من Actions يُحتمل أن تحقق Goal مع الالتزام بـ Constraints.

يمكن لخطط صحيحة مختلفة أن تمتلك Efficiency مختلفة جدًا. وينبغي لـ Planner قوي تفضيل الخطط التي تقلل العمل غير الضروري.

### فصل Planning عن Execution

إذا أنشأ Agent خطة سيئة من 1,000 خطوة وبدأ تنفيذها فورًا، فقد يهدر الوقت والمال قبل أن يصبح الفشل واضحًا.

Architecture أكثر أمانًا هي:

```text
Task
 -> توليد Plan (generate plan)
 -> التحقق من Plan (validate plan)
 -> التنفيذ (execute)
 -> تقييم Outcome (evaluate outcome)
 -> إعادة Planning إذا لزم الأمر (replan if necessary)
```

يمكن لـ Plan Validators رفض Actions مستحيلة أو خطوات مفرطة أو Plans تخالف Constraints.

[[IMAGE_NEEDED: Decoupled planning and execution | A loop showing plan generation -> plan validation -> execution -> outcome evaluation -> replan, with invalid plans returning to the planner before any tool is called | Learner should notice that validation can prevent expensive or dangerous execution]]

## 22. Intent و Feasibility و Human Approval

يمكن لفهم User Intent مساعدة Agent في اختيار Tools الصحيحة.

قد تحتاج Support Query عن Billing إلى Payment Records. وقد يحتاج سؤال عن Password إلى Documentation Retrieval.

ينبغي لـ Intent Classifier أيضًا التعرف على Requests خارج Scope النظام حتى يستطيع Agent الرفض أو Redirect بدلًا من اختراع Plan.

يمكن للبشر المشاركة في عدة مراحل:

- توفير High-level Plan.
- التحقق من Plan مولدة.
- الموافقة على Actions خطرة.
- تنفيذ الخطوات الحساسة يدويًا.

ينبغي تحديد مستوى Automation **لكل Action**، خصوصًا للـ Write Operations غير القابلة للعكس أو عالية التأثير.

## 23. هل تستطيع Foundation Models تنفيذ Planning؟

يقدم الفصل Planning Ability بوصفها سؤالًا مفتوحًا لا حقيقة محسومة.

يرتبط Planning في الأساس بعملية Search:

- النظر في Actions الممكنة.
- توقع States الناتجة.
- مقارنة Paths المحتملة.
- تنفيذ Backtracking عندما يكون Path سيئًا.
- اختيار Path واعدة نحو Goal.

تولد Autoregressive Models إلى الأمام، مما ينشئ تحديات. لكنها تستطيع أحيانًا تقريب Backtracking عبر Critique أو Revision أو Restarting أو External Search أو State-tracking Mechanism.

حتى إذا لم يكن Foundation Model Planner كاملًا بمفرده، فيمكنه أن يكون Component داخل Planning System أكبر.

يقارن الفصل أيضًا بين Foundation-model Agents و Reinforcement-learning Agents. تتعلم RL عادةً Planner أو Policy من خلال RL Training، بينما تستخدم FM Agent غالبًا Foundation Model نفسها بوصفها Planner. ويمكن أيضًا الجمع بين النهجين.

## 24. توليد Plan و Function Calling

يمكن بناء Planner بسيط عبر إخبار Model بالـ Actions التي يستطيع استخدامها وطلب إعادة Action Sequence صالحة.

يأتي Planning الأفضل عادةً من:

- System Instructions أوضح.
- أمثلة أكثر.
- Tool Descriptions أفضل.
- Tool Interfaces أبسط.
- Models أقوى.
- Finetuning لـ Planning.

### استدعاء Functions (Function Calling)

تُعرض Tool عادةً كـ Function تحتوي على:

- اسم.
- Documentation.
- Parameters وأنواع Parameters.

يمكن لـ Model عندها إعادة Structured Tool Call مثل:

```text
الأداة (Tool): lbs_to_kg
المعاملات (Arguments): {"lbs": 40}
```

تسمح بعض APIs للمطورين باختيار ما إذا كان Tool Use:

- مطلوبًا.
- ممنوعًا.
- تلقائيًا أو يختاره Model.

سجّل وافحص Parameter Values دائمًا. فوجود Function Name صالح لا يضمن أن Arguments صالحة أو صحيحة.

## 25. Planning Granularity و Hierarchical Planning

تكون Plan التفصيلية أسهل في Execution لكنها أصعب في Generation بشكل موثوق. أما High-level Plan فهي أسهل في Generation لكنها تترك Decisions أكثر لوقت Execution.

أحد الحلول هو **Hierarchical Planning**:

```text
خطة عامة (high-level plan)
  -> Subplan للمرحلة 1
  -> Subplan للمرحلة 2
  -> ...
```

يمكن أيضًا التعبير عن Plans باللغة الطبيعية بدلًا من أسماء API Functions الدقيقة. وهذا يجعل Planner أقل ارتباطًا بإحكام بـ Tool API متغيرة.

يمكن لـ Translator منفصل بعد ذلك تحويل High-level Action مثل `retrieve product information` إلى Function قابلة للتنفيذ بدقة.

لكن المفاضلة هي أن Translator هذا يصبح Component إضافيًا يجب تقييمه.

## 26. Control Flows المعقدة في Agents

لا يجب أن تكون Plans مجرد قوائم تسلسلية بسيطة.

يسلط الفصل الضوء على أربعة أنماط من Control Flow:

### التنفيذ التسلسلي (Sequential)

تعمل B بعد A لأن B تعتمد على A.

### التنفيذ المتوازي (Parallel)

تعمل Operations المستقلة في الوقت نفسه، مما يقلل Latency.

### الشرط (If / Conditional)

اختر Action التالية بناءً على نتيجة Action سابقة.

### الحلقة (Loop)

كرر Action حتى يتحقق Condition.

تكون Plans غير التسلسلية أصعب لكل من Planner و Execution Layer. وعند اختيار Agent Framework، تحقق من Control Flows التي يدعمها.

## 27. Reflection وتصحيح الأخطاء

حتى Plan صالحة قد تفشل أثناء Execution. وتقيّم Reflection ما إذا كان النظام لا يزال على المسار الصحيح وما الذي ينبغي تغييره.

يمكن أن تحدث Reflection:

- قبل Planning: هل Request قابلة للتنفيذ؟
- بعد Plan Generation: هل Plan منطقية؟
- بعد كل Action: هل أعادت Tool ما توقعناه؟
- في النهاية: هل أنجزنا Task فعلًا؟

### حلقة بأسلوب ReAct

أحد الأنماط الشائعة يدمج Planning و Action بالتناوب:

```text
فكرة (Thought) -> إجراء (Action) -> ملاحظة (Observation)
فكرة (Thought) -> إجراء (Action) -> ملاحظة (Observation)
...
إنهاء (Finish)
```

### فصل Actor عن Evaluator

يمكن أيضًا تفويض Reflection إلى Model أخرى أو Specialized Scorer. يحدد Evaluator الفشل، ثم يستخدم Planner ذلك Feedback لإنشاء Trajectory أفضل.

الفائدة هي تحسين Error Correction. أما التكلفة فهي Tokens إضافية و Latency و Model Calls إضافية.

## 28. اختيار Tools وإدارة Tool Inventories

تزيد Tools الأكثر من Capability، لكنها تزيد أيضًا صعوبة Planning.

تنشئ Tool Inventory كبيرة تحديات:

- Tool Descriptions الأطول تستهلك Context.
- Tools المتشابهة قد تربك Planner.
- تزداد فرص Invalid Calls.

يوصي الفصل باختيار Tools بصورة تجريبية.

### تجارب مفيدة

- قارن Tool Sets مختلفة.
- نفذ **Ablation Study**: أزل Tool واحدة وقِس تغير Performance.
- حدد Tools ذات Error Rates المرتفعة.
- حلل Tools التي تُستخدم كثيرًا أو نادرًا.
- استبدل Tools التي تظل صعبة على Model في الاستخدام الصحيح.

قد تفضل Models مختلفة Tools مختلفة، وقد تحتاج Tasks مختلفة إلى Inventories مختلفة جدًا.

### انتقالات Tools والمهارات القابلة لإعادة الاستخدام

إذا كانت Tools معينة تُستخدم معًا بصورة متكررة، فيمكن دمجها في Tool أعلى مستوى. ويمكن لـ Agents أيضًا تخزين Skills جديدة قابلة لإعادة الاستخدام داخل Skill Library لمهام مستقبلية.

## 29. Failure Modes الخاصة بـ Agents

ترث Agents حالات الفشل العادية في Models وتضيف حالات فشل جديدة ناتجة عن Planning و Tools.

### إخفاقات Planning

تشمل الأمثلة:

- استدعاء Tool غير موجودة.
- استدعاء Tool صالحة بعدد أو نوع خاطئ من Parameters.
- استدعاء Tool صالحة بـ Parameter Values خاطئة.
- إنتاج Plan لا تحقق Goal.
- مخالفة Task Constraints مثل Budget أو Location.
- الانتهاء بعد Deadline مفيد.
- الاعتقاد بأن Task اكتملت بينما لم تكتمل.

### إخفاقات Tools

قد يستدعي Planner الـ Tool الصحيحة، لكن Tool نفسها تعيد Result خاطئة. كما يمكن أن يفشل Translator الذي يحول High-level Actions إلى Executable Calls.

ومن حالات الفشل الأخرى ببساطة **Missing Capability**: لا يمتلك Agent الـ Tool المطلوبة للمهمة.

لذلك ينبغي اختبار كل Tool بصورة مستقلة وجعل كل Tool Call قابلة للملاحظة.

### إخفاقات Efficiency

قد ينجح Agent لكنه يظل غير كفؤ.

تتبّع:

- عدد Steps لكل Completed Task.
- Cost لكل Completed Task.
- Total Time لكل Completed Task.
- Actions البطيئة أو المكلفة.

قد يكون Baseline المناسب Agent آخر أو Human Workflow.

- نسبة Plans المولدة الصالحة.

- نسبة Tool Calls الصالحة.

- معدل Invalid Parameters.

## 31. Memory: داخلية وقصيرة المدى وطويلة المدى

تتعامل RAG و Agents مع معلومات أكثر مما يمكن دائمًا وضعه داخل Context Window واحدة. يساعد Memory System على الاحتفاظ بالمعلومات واسترجاعها.

يصف الفصل ثلاثة Memory Mechanisms رئيسية.

### المعرفة الداخلية (Internal Knowledge)

Knowledge مخزنة داخل Model Weights عبر Training. تكون متاحة عبر Queries المختلفة لكنها لا تتغير إلا عندما يتغير Model.

### الذاكرة قصيرة المدى (Short-term Memory)

معلومات موضوعة داخل Model Context الحالية، مثل Messages الحديثة و Plans الحالية و Observations.

يكون الوصول إليها سريعًا، لكنها محدودة Capacity.

### الذاكرة طويلة المدى (Long-term Memory)

معلومات خارجية Persistent يتم استرجاعها عند الحاجة. يمكنها البقاء عبر Tasks المختلفة ويمكن تحديثها أو حذفها دون إعادة تدريب Model.

من مبادئ توزيع المعلومات العملية:

- المعلومات المطلوبة كثيرًا في معظم Tasks -> Internal Knowledge.
- المعلومات المطلوبة للـ Task الحالية -> Short-term Memory.
- المعلومات المطلوبة أحيانًا أو التي يجب أن تبقى -> Long-term Memory.

[[IMAGE_NEEDED: Three-level AI memory hierarchy | A hierarchy showing model weights as internal knowledge, active context as short-term memory, and external persistent stores as long-term memory | Learner should notice the tradeoff between persistence, capacity, and access]]

## 32. لماذا تهم Memory

يمكن لـ Memory مساعدة التطبيق في:

### إدارة فائض المعلومات (Manage Information Overflow)

انقل المعلومات التي لم تعد تتسع داخل Active Context إلى External Memory.

### الاستمرار عبر Sessions (Persist Across Sessions)

تذكر User Preferences أو العمل السابق أو History أو Project State.

### تحسين Consistency

يمكن للرجوع إلى Decisions سابقة مساعدة Model على البقاء متسقًا بمرور الوقت.

### الحفاظ على Structure

يمكن لـ External Memory تخزين Structured Artifacts مثل Tables و Queues و Files دون تحويل كل شيء إلى Unstructured Context Text.

## 33. إدارة Memory

يحتاج Memory System إلى وظيفتين عامتين:

1. **إدارة Memory:** تحديد ما الذي يجب تخزينه أو دمجه أو استبداله أو حذفه.
2. **استرجاع Memory:** جلب Long-term Information ذات الصلة بالـ Task الحالية.

يُعد استرجاع Long-term Memory في الأساس مشكلة RAG أخرى.

### نقل Overflow خارج Short-term Memory

يمكن حجز جزء من Context Window للمعلومات المسترجعة من Long-term Memory. وتحتفظ Capacity المتبقية بـ Active Short-term Memory.

عندما تتجاوز Active Memory الـ Capacity المخصصة، يجب ضغط بعض المعلومات أو نقلها أو التخلص منها.

### سياسة FIFO بسيطة لكنها خطرة

تزيل First-in-first-out أقدم Context أولًا. وهي سهلة التنفيذ، لكنها قد تتخلص من أهم المعلومات، مثل Goal الأصلية المذكورة في بداية محادثة طويلة.

### استخدام Summarization

اضغط History الأقدم في Summary مع الحفاظ على Entities و Constraints و Decisions الأساسية.

### تحديثات Memory القائمة على Reflection

بعد وصول معلومات جديدة، يمكن لـ Agent تحديد ما إذا كان ينبغي:

- إدراجها كـ Memory جديدة.
- دمجها مع Memory موجودة.
- استبدال معلومات قديمة بها.
- تجاهلها.

تحتاج Contradictions إلى Policy خاصة بالتطبيق. فقد يكون الاحتفاظ بأحدث Fact فقط صحيحًا في نظام، وخطيرًا في نظام آخر.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> تجعل Context Window كبيرة جدًا Retrieval غير ضروري.

**لماذا هذا خطأ:** يمكن للبيانات تجاوز أي Context ثابتة، وتضيف Tokens غير ذات الصلة تكلفة و Latency، كما أن Models لا تستخدم Long Context دائمًا بكفاءة.

### المفهوم الخاطئ 2

> Vector Search أفضل دائمًا من BM25.

**لماذا هذا خطأ:** يمكن لـ BM25 أن تكون سريعة ورخيصة وممتازة مع Terms الدقيقة، بينما تساعد Semantic Search في المعنى و Paraphrases. وغالبًا تجمع Production Systems الطريقتين.

### المفهوم الخاطئ 3

> بمجرد أن يصبح Retriever جيدًا، يصبح نظام RAG كاملًا جيدًا.

**لماذا هذا خطأ:** تؤثر Retrieval و Embeddings و Prompt Construction و Generation جميعها في End-to-end Quality.

### المفهوم الخاطئ 4

> Chunks الأصغر أفضل دائمًا لأنها أكثر دقة.

**لماذا هذا خطأ:** يمكن لـ Chunks الصغيرة أكثر من اللازم فقد Context أساسية وزيادة Overhead الخاصة بـ Embedding و Storage و Search بدرجة كبيرة.

### المفهوم الخاطئ 5

> إعطاء Agent المزيد من Tools يحسنه دائمًا.

**لماذا هذا خطأ:** تجعل Inventories الأكبر اختيار Tools أصعب، وتستهلك Context، وتخلق فرصًا أكثر للاستدعاءات الخاطئة.

### المفهوم الخاطئ 6

> Tool Call صالحة تعني أن Agent اتخذ القرار الصحيح.

**لماذا هذا خطأ:** قد تكون Function صالحة بينما Parameters خاطئة، أو قد يكون Action المختار بالكامل غير مناسب لـ Goal.

### المفهوم الخاطئ 7

> إذا كانت Final Answer صحيحة، فقد اكتملت Evaluation الخاصة بـ Agent.

**لماذا هذا خطأ:** يمكن للتكلفة و Latency وكثرة Steps و Unsafe Actions و Invalid Calls و Tool Failures أن تجعل النظام غير مناسب رغم ذلك.

### المفهوم الخاطئ 8

> تعني Memory الاحتفاظ بالمحادثة كاملة إلى الأبد داخل Prompt.

**لماذا هذا خطأ:** تتطلب Memory المفيدة Storage انتقائيًا و Compression و Retrieval و Lifecycle Management.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| تقنية RAG | Retrieval-Augmented Generation: استرجاع المعلومات الخارجية قبل Generation لتحسين Response. |
| مكوّن Retriever | Component يرتب المعلومات ذات الصلة بـ Query ويسترجعها. |
| مكوّن Generator | Model ينتج Final Response باستخدام Query و Retrieved Context. |
| عملية Indexing | تجهيز البيانات بحيث يمكن استرجاعها بكفاءة لاحقًا. |
| عملية Querying | استرجاع المعلومات وترتيبها لطلب محدد. |
| مقياس TF | Term Frequency: عدد مرات ظهور Term داخل Document. |
| مقياس IDF | Inverse Document Frequency: مقياس لمدى ندرة أو فائدة Term عبر Documents. |
| مقياس TF-IDF | Lexical Relevance Score تجمع بين Local Term Frequency والندرة العامة. |
| بنية Inverted Index | Mapping من Terms إلى Documents التي تحتوي عليها. |
| خوارزمية BM25 | خوارزمية Lexical Ranking شائعة مشتقة من أفكار شبيهة بـ TF-IDF. |
| الاسترجاع الدلالي (Semantic Retrieval) | Retrieval اعتمادًا على Embedding Similarity بدلًا من Exact Word Overlap. |
| قاعدة Vector Database | Store أو Index مصمم لدعم Vector Similarity Search. |
| أسلوب k-NN | Exact Nearest-neighbor Retrieval عبر المقارنة مع Candidate Vectors. |
| أسلوب ANN | Approximate Nearest-neighbor Search للحصول على Vector Retrieval أسرع على نطاق كبير. |
| أسلوب HNSW | نهج ANN قائم على Graph لعمليات Indexing و Search. |
| أسلوب IVF | نهج قائم على Clusters لاختيار Candidates في Vector Search. |
| تقنية Product Quantization | طريقة لضغط Vectors تقلل تكلفة Search و Storage. |
| مقياس Context Precision | نسبة Documents المسترجعة التي تكون ذات صلة. |
| مقياس Context Recall | نسبة جميع Documents ذات الصلة التي تم استرجاعها. |
| مقياس MRR | Ranking Metric يركز على موضع أول Result ذات صلة. |
| أسلوب Hybrid Search | الجمع بين Lexical Retrieval و Embedding-based Retrieval. |
| عملية Reranking | إعادة ترتيب Candidates المسترجعة أولًا باستخدام Mechanism أكثر دقة. |
| أسلوب RRF | Reciprocal Rank Fusion لدمج عدة Ranked Lists. |
| عملية Chunking | تقسيم Source Documents إلى وحدات قابلة للاسترجاع. |
| عملية Query Rewriting | تحويل Query غامضة أو معتمدة على Context إلى Retrieval Query مستقلة بذاتها. |
| أسلوب Contextual Retrieval | إثراء Chunks بـ Metadata أو Context قبل Indexing. |
| نظام Multimodal RAG | استرجاع Context عبر Modalities مثل النص والصور. |
| أسلوب Text-to-SQL | تحويل طلب باللغة الطبيعية إلى SQL لاسترجاع Structured Data. |
| نظام Agent | نظام يدرك Environment ويختار Actions لتحقيق Goal. |
| قائمة Tool Inventory | مجموعة External Actions أو Functions المتاحة لـ Agent. |
| آلية Function Calling | Structured Invocation تولدها Model لاستدعاء External Tool. |
| عملية Planning | اختيار Sequence أو Control Flow من Actions لتحقيق Goal تحت Constraints. |
| عملية Reflection | تقييم Plans و Actions و Outcomes لاكتشاف الأخطاء وتحسين السلوك التالي. |
| نمط ReAct | نمط يدمج Reasoning أو Planning و Actions و Observations بالتناوب. |
| دراسة Ablation Study | إزالة Component أو Tool وقياس تغير Performance الناتج. |
| المعرفة الداخلية (Internal Knowledge) | معلومات مشفرة داخل Model Parameters. |
| الذاكرة قصيرة المدى (Short-term Memory) | معلومات نشطة مخزنة في Model Context الحالية. |
| الذاكرة طويلة المدى (Long-term Memory) | معلومات خارجية Persistent يتم استرجاعها عند الحاجة. |
| سياسة FIFO | First-in-first-out Memory Policy تزيل أقدم Items أولًا. |
