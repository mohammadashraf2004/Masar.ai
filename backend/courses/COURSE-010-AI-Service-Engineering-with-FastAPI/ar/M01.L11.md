## نواتج التعلم (Learning outcomes)

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا تصبح testing أكثر أهمية كلما اقتربت AI service من production.
- التمييز بين unit وintegration وend-to-end وbehavioral وstatic testing.
- تعريف testing boundaries من دون الإفراط في اختبار implementation details.
- شرح verification مقابل validation.
- شرح لماذا لا تثبت 100% code coverage أن application تحل المشكلة الصحيحة.
- تطبيق shift-left testing وtest-driven-development loop مفاهيميًا.
- تخطيط test scope وcoverage وcomprehensiveness.
- تصميم valid وinvalid وboundary وhuge-data test cases.
- تنظيم tests باستخدام Given–When–Then أوArrange–Act–Assert–Cleanup.
- مقارنة testing pyramid وtrophy وhoneycomb وtesting anti-patterns الشائعة.
- شرح لماذا تجعل probabilistic GenAI outputs اختبارات equality deterministic غير كافية.
- التعرّف إلى model/output variability وperformance cost وregression وdrift وbias وadversarial risk وinput space غير المحدودة عمليًا باعتبارها تحديات في GenAI testing.
- تنظيم pytest test files وكتابة focused assertions.
- إنشاء pytest fixtures قابلة لإعادة الاستخدام مع scope مناسبة.
- استخدام parameterization لاختبار عدة inputs من دون تكرار test functions.
- استخدام `conftest.py` من أجل shared test configuration وfixtures.
- تنفيذ setup وteardown باستخدام yield fixtures.
- شرح لماذا تقلل isolation وidempotency من flaky tests.
- اختبار asynchronous code مع إدارة event-loop وI/O-related flakiness.
- التمييز بين fake وdummy وstub وspy وmock test doubles.
- شرح متى تساعد mocking ومتى تخفي over-mocking مشكلات integration.
- اختبار interactions مع real dependencies في integration tests.
- حساب retrieval precision وrecall في RAG وتفسيرهما.
- اختبار structured LLM decisions عبر representative input distributions.
- استخدام behavioral black-box tests للـ natural-language outputs المتغيرة.
- التمييز بين minimum functionality وinvariance وdirectional expectation tests.
- شرح auto-evaluation باستخدام evaluator/discriminator model.
- تصميم vertical وhorizontal E2E tests حول real user workflows.
- بناء GenAI test strategy متوازنة بدل تعظيم نوع test واحد.

## 1. لماذا تهم Testing؟

تستبدل Testing قدرًا من engineering effort بمزيد من الثقة.

من دون tests، تكتشف الفرق failures غالبًا فقط بعد أن:

- يبلغ المستخدمون عنها،
- تفشل payments،
- تصبح data غير متسقة،
- تتغير external integrations،
- تتفاعل عدة components بطرق غير متوقعة.

يصف المصدر payment/webhook system معقدًا أصبح صعبًا وغير مستقر إلى درجة أنه اضطر إلى إعادة الكتابة.

الدرس الأوسع هو:

> **تزداد قيمة Testing كلما ارتفعت تكلفة الفشل.**

قد يتحمل quick prototype قدرًا قليلًا من formal testing.

لكن نظامًا يتعامل مع:

- customer payments،
- authentication،
- sensitive information،
- multiple contributors،
- اعتماديات خارجية كثيرة

يحتاج إلى deliberate testing plan.

### مؤشرات على ضرورة زيادة Testing

يسلط الفصل الضوء على حالات مثل:

- several contributors يغيرون code،
- dependencies تتغير،
- تزايد interacting components،
- ارتفاع bug frequency،
- عواقب كبيرة إذا حدث failure.

### Testing هي Proactive Debugging

من دون tests:

```text
يحدث failure
    ↓
يلاحظه المستخدم
    ↓
يحقق الفريق
    ↓
يُكتب الإصلاح
```

مع tests جيدة:

```text
يحدث تغيير
    ↓
يكتشف test الـ regression
    ↓
يحدث الإصلاح قبل release
```

لا تثبت Testing أن software مثالية.

بل توفر evidence على أن expectations المعرفة ما تزال صحيحة.

## 2. Unit وIntegration وEnd-to-End Tests

يقدم الفصل ثلاثة أنواع شائعة من runtime tests.

### اختبار الوحدة (Unit Test)

تختبر component صغيرة واحدة في isolation.

مثال:

```text
chunk(tokens, chunk_size)    # توقيع الدالة
```

تنتهي unit-test boundary حول هذه function.

وعادة لا ينبغي أن تشارك external systems.

### اختبار التكامل (Integration Test)

تختبر interface بين components.

مثال:

```text
خدمة retrieval
    ↔
vector database
```

الهدف هو التحقق من أن الجزأين يتواصلان بصورة صحيحة.

### الاختبار الشامل (End-to-End Test)

تختبر user-facing workflow أكبر عبر عدة components.

مثال:

```text
تسجيل الدخول
→ رفع مستند
→ فهرسة المستند
→ طرح سؤال
→ استرجاع السياق
→ توليد الإجابة
→ حفظ النتيجة
```

### المفاضلة

كلما اتسع scope:

```text
الثقة ↑
التكلفة ↑
زمن التنفيذ ↑
الصيانة ↑
خطر عدم الاستقرار (flakiness) ↑
```

{{image:test-boundaries}}

### الفحوص الساكنة (Static Checks) تأتي أبكر

قبل runtime tests، تستطيع tools مثل static type checkers اكتشاف:

- type problems،
- بعض إساءة استخدام code،
- dead/unused code،
- style أوdata-flow issues.

في Python، تضيف static type checks قيمة عندما تستخدم code type hints.

وتلتقط runtime validation tools مثل Pydantic malformed data أثناء execution.

## 3. اختبر Behavior لا Implementation Details

أحد أصعب القرارات هو:

> **ما الذي ينبغي أن يؤكده test بالضبط؟**

افترض:

⟦CODE_0⟧

إذا أكد test على internal string-processing steps بدقة، فقد يكسر refactor غير ضار الـ test.

لكن إذا كان requirement هو:

```text
عند إعطاء هذا النص
→ أعد عدد tokens هذا
```

فينبغي عادة أن يركز test على input/output behavior.

### التفكير بأسلوب Black-box

تعامل مع component باعتبارها:

```text
المُدخل
→ النظام قيد الاختبار
→ المُخرج
```

لا تعتمد على internal implementation إلا إذا كان ذلك internal behavior نفسه requirement.

### علامتا تحذير

قد تكون tests مرتبطة أكثر من اللازم بـ implementation details عندما:

1. يكسر refactoring لا يغير behavior عددًا كبيرًا من tests؛
2. يمكن إدخال behavioral bug حقيقية بينما تظل tests ناجحة.

### عرّف Testing Boundary

تجيب boundary عن:

```text
ما الموجود داخل هذا test؟
ما الموجود خارج هذا test؟
```

مثال unit boundary:

```text
داخل test:
chunking logic

خارج test:
filesystem
vector DB
LLM API
```

تجعل boundaries الواضحة failures أسهل في التشخيص.

## 4. Verification مقابل Validation

يستخدم الفصل نموذج verification وvalidation.

### التحقق من صحة المتطلبات (Validation)

اسأل:

> **هل نبني النظام الصحيح؟**

يتعلق ذلك بـ requirements وbusiness needs.

### التحقق من التنفيذ (Verification)

اسأل:

> **هل بنينا النظام وفق تلك requirements؟**

تتحقق tests من implementation مقابل expectations المحددة.

### لماذا Code Coverage غير كافية؟

يمكنك الوصول إلى:

```text
تغطية شيفرة 100%
+
نجاح كل الاختبارات
```

ومع ذلك يكون product behavior خاطئًا.

مثال:

```text
يتم اختبار كل line في payment function،
لكن workflow لا تطابق طريقة وصول payment events فعليًا.
```

هذا validation failure.

### الحدس وراء V-model

يقدم المصدر V-shaped flow.

على اليسار:

```text
متطلبات العمل
→ تصميم النظام
→ التنفيذ
```

وعلى اليمين:

```text
اختبارات الوحدة
→ اختبارات التكامل
→ ثقة E2E/القبول
```

## 5. انقل Testing إلى اليسار واستخدم TDD عندما يكون مناسبًا

العملية reactive هي:

```text
ابنِ النظام
→ تظهر bugs متأخرًا
→ أنشئ tests بعد failure
```

تنقل shift-left testing عملية testing إلى وقت أبكر.

```text
المتطلبات
→ التصميم
→ الاختبارات
→ التنفيذ
```

### التطوير المدفوع بالاختبارات (Test-driven Development)

يقدم المصدر TDD باعتبارها loop تكرارية.

```text
اكتب failing test
    ↓
اكتب minimum code
    ↓
ينجح test
    ↓
نفّذ refactor
    ↓
حافظ على نجاح tests
```

### تطبيق GenAI: هندسة Prompt

يسلط الفصل الضوء على prompt engineering باعتبارها حالة مفيدة شبيهة بـ TDD.

يمكنك:

1. تعريف representative expected behaviors،
2. كتابة evaluation tests،
3. التكرار على prompt/model settings،
4. إعادة تشغيل test set نفسها،
5. فحص regressions عند تغيير Models.

ويحوّل ذلك prompt design إلى iterative measurable process بدل subjective trial and error فقط.

## 6. Scope وCoverage وComprehensiveness

يفصل الفصل بين ثلاثة أبعاد.

### النطاق (Scope)

ما الأنظمة والسيناريوهات الموجودة داخل الخطة؟

مثال:

```text
retrieval الخاص بـ RAG فقط
```

مقابل:

```text
منتج chatbot كامل
```

### التغطية (Coverage)

ما مقدار النظام المحدد الذي تمسه tests؟

وغالبًا ما تُناقش في صورة:

- code coverage،
- feature coverage،
- interface coverage.

### الشمولية (Comprehensiveness)

إلى أي عمق تختبر داخل scope؟

تشمل الأسئلة:

- success paths؟
- failure paths؟
- edge cases؟
- misuse؟
- performance extremes؟

### تشبيه هندسي مفيد

يصف المصدر هذه العناصر تقريبًا:

```text
النطاق (scope)
→ الحجم / الحدود

التغطية (coverage)
→ مساحة السطح

الشمول (comprehensiveness)
→ العمق
```

قد تكون test plan واسعة scope لكنها shallow depth، أوضيقة scope مع edge-case testing شديدة التفصيل.

## 7. صمّم Test Data بقصد

يحدد المصدر أربع فئات مفيدة.

### بيانات صالحة (Valid Data)

Inputs طبيعية متوقعة.

مثال:

```text
chunk_size = 100
```

### بيانات غير صالحة (Invalid Data)

Inputs خارج accepted rules.

مثال:

```text
chunk_size = -1
```

### بيانات الحدود (Boundary Data)

Inputs قرب minimum/maximum limits المسموحة.

مثال:

```text
max_upload_size
max_context_length
```

### بيانات ضخمة (Huge Data)

Workloads كبيرة لاستكشاف performance/resource limits.

مثال:

```text
100,000 chunk
ملف كبير جدًا
دفعة كبيرة
```

### لماذا تهم الفئات الأربع؟

اختبار happy path فقط ينشئ false confidence.

ينبغي لـ component قوية أن تتصرف بصورة متوقعة أيضًا عندما:

- تكون inputs فارغة،
- تكون values invalid،
- يتم الوصول إلى boundaries،
- يصبح workload size ضخمًا.

## 8. نظّم Tests باستخدام Given–When–Then

يصف الفصل نموذج Given–When–Then.

### الحالة المعطاة (Given)

حضّر initial state.

```text
tokens = [1, 2, 3, 4, 5]    # مدخلات الاختبار
chunk_size = 2
```

### عند التنفيذ (When)

استدعِ system under test.

```text
result = chunk(tokens, 2)    # استدعاء الدالة
```

### النتيجة المتوقعة (Then)

أكد behavior المتوقع.

```text
result == [[1, 2], [3, 4], [5]]    # النتيجة المتوقعة
```

### التنظيف (Cleanup)

أزل resources أوأعد state إذا لزم.

تستخدم Pytest غالبًا framing مشابهة:

```text
Arrange    # التهيئة
Act    # التنفيذ
Assert    # التحقق
Cleanup    # التنظيف
```

### لماذا تساعد Phases؟

تجعل phases الواضحة failures أسهل في القراءة.

ينبغي أن يوضح test:

```text
ما state التي كانت موجودة
ما action التي حدثت
ما outcome المتوقعة
```

## 9. اختبر عبر Static وBuild وRuntime Environments

لا تقتصر Testing على runtime endpoint calls.

### الفحوص الساكنة (Static Checks)

يمكن لـ Python استخدام tools مثل type checkers قبل execution.

وتستطيع اكتشاف فئات معينة من issues مبكرًا.

### فحوص وقت البناء (Build-time Checks)

قد تحتاج GenAI application إلى setup مثل:

- dependency installation،
- model downloads،
- model preloading،
- generated assets.

وقد تفشل build steps هذه أيضًا.

### اختبارات وقت التشغيل (Runtime Tests)

تنفذ unit وintegration وE2E tests سلوك application.

وقد تتحقق Pydantic من runtime data.

### التحقق متعدد الطبقات (Layered Verification)

تسلسل مفيد هو:

```text
فحوص ساكنة
→ فحوص البناء
→ اختبارات الوحدة
→ اختبارات التكامل
→ اختبارات E2E
→ Evaluation السلوكي/النموذج
```

تكتشف كل layer فئات مختلفة من defects.

## 10. Testing Pyramid وTrophy وHoneycomb

تحتاج test suites إلى balanced distribution.

### هرم الاختبارات (Testing Pyramid)

عدد كبير من unit tests.

وعدد أقل من integration tests.

وعدد أقل من E2E tests.

لماذا؟

```text
اختبارات الوحدة
→ سريعة ورخيصة

E2E
→ بطيئة ومكلفة
```

### كأس الاختبارات (Testing Trophy)

يسلط المصدر الضوء على هذه strategy لخدمات GenAI.

وتستخدم:

- static checks قوية،
- unit tests،
- تركيزًا كبيرًا على integration tests،
- E2E tests أقل.

لماذا integration tests؟

تعتمد GenAI applications عادة على:

- databases،
- model providers،
- vector stores،
- filesystems،
- APIs.

تحدث failures مهمة كثيرة عند interfaces.

### قرص العسل للاختبارات (Testing Honeycomb)

تعطي Attention أكثر توازنًا لفئات test متعددة، وقد تشمل:

- performance،
- security،
- exploratory testing.

وقد تناسب الأنظمة التي تحتاج comprehensive multi-dimensional testing.

### لا توجد Distribution عالمية

ينبغي أن تعكس test strategy:

- system risk،
- architecture،
- dependencies،
- CI budget،
- performance needs.

## 11. الأنماط السيئة في Testing (Testing Anti-patterns)

يحذر الفصل من عدة distributions.

### نمط مخروط الآيس كريم (Ice-cream Cone)

عدد كبير جدًا من:

- integration،
- E2E،
- manual tests.

وعدد قليل جدًا من unit tests.

النتيجة:

- suite بطيئة،
- maintenance مكلفة،
- tests هشة.

### نمط Cupcake

اختلال مشابه مع manual/GUI testing كبيرة وorganizational separation بين test types.

المشكلات المحتملة:

- communication overhead،
- slow feedback،
- brittle workflows.

### نمط الساعة الرملية (Hourglass)

عدد كبير من unit tests.

وعدد كبير من E2E tests.

لكن integration tests قليلة جدًا.

وقد ينشئ ذلك gap لا تُختبر فيها component interfaces بكفاءة.

### الدرس العام

لا تعظم test size.

استخدم أصغر test يوفر الثقة المطلوبة للـ behavior الذي تفحصه.

## 12. لماذا تختلف GenAI Testing؟

غالبًا ما تدعم deterministic code التقليدية assertions مثل:

```text
المُدخل X
→ المُخرج Y بالضبط
```

أما GenAI models فقد تنتج:

```text
المُدخل X
→ المُخرج A

المُدخل X نفسه
→ المُخرج B

المُدخل X نفسه
→ المُخرج C
```

وقد تكون outputs الثلاث كلها مقبولة.

ويغير ذلك test design.

يحدد الفصل عدة فئات من التحديات:

- variable/flaky outputs،
- high test cost وlatency،
- regression/model drift،
- bias،
- adversarial behavior،
- فضاء مدخلات/مخرجات غير محدود فعليًا.

التغيير الأساسي هو:

> **غالبًا ما تسأل GenAI model testing هل يقع behavior داخل acceptable region بدل السؤال هل output تساوي exact string واحدة.**

## 13. Probabilistic Output وStatistical Confidence

تأخذ language models samples من probability distributions.

وقد تتأثر output variability بإعدادات مثل temperature.

وهذا يجعل exact equality tests غير موثوقة لـ open-ended generation.

### Test خاطئ

⟦CODE_1⟧

ستفشل إجابة جيدة بصياغة مختلفة.

### Mental Model أفضل

اختبر properties عبر representative samples.

تشمل properties محتملة:

- relevance للـ input،
- valid format،
- low toxicity،
- grounded in context،
- appropriate length،
- acceptable readability.

### توزيع ممثل (Representative Distribution)

يوصي المصدر بـ test inputs تعكس الاستخدام المقصود الفعلي.

لا تأخذ samples من prompts عشوائية لا ترتبط بالـ product ثم تفترض أن resulting score تمثل production behavior.

### الثقة الإحصائية (Statistical Confidence)

لا تستطيع تعداد model input space كاملة.

بدلًا من ذلك:

```text
عيّنة ممثِّلة
+
مقاييس السلوك
+
العتبات
→ الدليل/الثقة
```

وليس proof مطلقة.

## 14. تحديات Cost وLatency وRegression

### قد تكون GenAI Tests مكلفة

إذا استدعى كل test Model مدفوعة:

```text
عدد الاختبارات ↑
→ استدعاءات API ↑
→ تكلفة token ↑
→ زمن المجموعة ↑
```

وتضاعف multi-model evaluator tests المشكلة.

يوصي المصدر بالتحكم في testing scope واستخدام تقنيات مثل:

- mocks،
- patching،
- dependency injection،
- expensive tests أقل تكرارًا،
- statistical approaches.

### الانحدار في الجودة (Regression)

حتى إذا لم تتغير application code، يمكن أن يتغير model behavior.

تشمل الأسباب المحتملة التي يناقشها المصدر:

- provider model updates،
- retraining/fine-tuning changes،
- changing user patterns،
- environmental changes.

### انجراف Model (Model Drift)

يتغير performance مع الوقت.

### انجراف المفهوم (Concept Drift)

تتغير العلاقة بين target concepts وreal-world behavior مع الوقت.

مثال:

```text
اللغة، الأحداث، الأعراف، المعرفة
→ تتغير مع الزمن
```

### انجراف Data (Data Drift)

تتغير input distributions.

قد تشمل الأسباب:

- population changes،
- sampling changes،
- seasonality،
- source changes،
- تغيّرات جودة المعالجة.

### أثر ذلك على Testing

حافظ على regression datasets وأعد تشغيلها عندما:

- تتغير provider models،
- تتغير prompts،
- تتغير retrieval،
- تتغير user traffic.

## 15. Bias وAdversarial Testing

### التحيز (Bias)

قد تحتوي foundation models أوتنتج unwanted bias.

يعطي المصدر أمثلة مرتبطة بـ demographic representation.

قد تحتاج bias testing إلى metrics وtest sets منفصلة لأبعاد مثل:

- gender،
- race،
- age،
- مجموعات أخرى ذات صلة.

النقطة المهمة هي:

> **لا يمكنك الادعاء أنك اختبرت bias dimension إذا لم تحدد كيف ستقيسها.**

## 28. قياس RAG Retrieval باستخدام Precision وRecall

يستخدم الفصل context precision وrecall لاختبار retrieval quality.

افترض:

```text
معرّفات المستندات ذات الصلة المتوقعة (IDs)
=
[1, 2, 3, 4, 5]

IDs المسترجعة
=
[2, 3, 6, 7]
```

العناصر المسترجعة بصورة صحيحة:

```text
{2, 3}
```

إذًا:

```text
الإيجابيات الصحيحة (true positives) = 2
```

### الاستدعاء (Recall)

ما مقدار relevant information المتوقعة التي تم استرجاعها؟

```text
الاستدعاء (recall)
=
المسترجَع الصحيح ذو الصلة
/
كل ما هو متوقع وذو صلة
```

في المثال:

```text
2 / 5 = 0.40
```

### الدقة (Precision)

ما مقدار retrieved set الذي كان relevant فعلًا؟

```text
الدقة (precision)
=
المسترجَع الصحيح ذو الصلة
/
كل المسترجَع
```

في المثال:

```text
2 / 4 = 0.50
```

### التفسير

Recall مرتفعة:

```text
تم فقد عدد قليل من العناصر relevant
```

Precision مرتفعة:

```text
تم استرجاع قدر قليل من noise غير ذات الصلة
```

[[IMAGE_NEEDED: RAG precision and recall sets | Venn-style diagram showing expected relevant documents and retrieved documents with overlap as true positives; annotate recall as overlap/expected and precision as overlap/retrieved | Learner should notice that recall measures completeness while precision measures signal-to-noise]]

قد تؤكد retrieval integration test:

ينبغي أن تتوافق thresholds مع متطلبات application.

### المفاضلة

قد يؤدي زيادة retrieval count إلى تحسين recall مع خفض precision.

ولهذا تهم metricان معًا.

→ التحويل/التقسيم
→ تخزين vectors
→ طرح سؤال
→ استرجاع السياق
→ استدعاء النموذج
→ إرجاع الإجابة
```

يعبر ذلك boundaries كثيرة.

### لماذا E2E Tests ذات قيمة؟

يمكن أن تكشف:

- integration gaps،
- unexpected component interaction،
- system-level behavior،
- assumptions مفقودة لا تظهر في unit tests.

### لماذا هي مكلفة؟

هي:

- أبطأ،
- أصعب في setup،
- أكثر هشاشة،
- أكثر اعتمادًا على external systems.

يوصي المصدر بتشغيلها بتكرار أقل من unit tests.

### Manual E2E ما تزال مفيدة

يمكن لإنسان يتفاعل مع real UI اكتشاف:

- usability problems،
- unexpected visual/flow issues،
- failures لم تتوقعها automated assertions.

ينبغي لـ automation تقليل repetitive manual work، وليس بالضرورة إزالة كل human check.

## 36. اختبارات E2E الرأسية (Vertical E2E Tests)

تختبر vertical test feature واحدة عبر عدة application layers.

مثال من الفصل:

    ↓

    ↓
معالجة الملف
    ↓
تخزين vectors
    ↓
التحقق من المستند المخزَّن
```

يعبر ذلك layers مع التركيز على workflow واحدة.

يمكن لـ global fixture كشف reusable test client.

يمكن لـ test التحقق من:

- API status،

- stored data.

## 37. اختبارات E2E الأفقية (Horizontal E2E Tests)

تتبع Horizontal E2E tests user scenario أوسع عبر integrated systems.

مثال:

```text
يرفع المستخدم document
    ↓
تتم index للـ document
    ↓
يسأل المستخدم سؤالًا
    ↓
يسترجع RAG معلومات الـ document المرفوعة
    ↓
تجيب LLM من تلك المعلومات
```

يمكن لـ test أن تؤكد:

```text
نجح upload
and
تحتوي answer على grounded fact متوقعة
```

### الحالة السلبية (Negative Case)

يقترح المصدر فحصًا تكميليًا ذا قيمة.

قبل رفع document:

```text
يسأل السؤال عن document-specific fact
→ ينبغي ألا تخترع Model الإجابة
```

بعد الرفع:

```text
same question
→ ينبغي أن تكون answer grounded في uploaded content
```

يختبر ذلك كلا من:

- retrieval behavior،
- سلوك hallucination/grounding.

## 38. ابنِ Test Strategy متوازنة لـ GenAI

ينبغي ألا تكون GenAI testing plan عملية:

```text
اختبارات الوحدة فقط
```

أو:

```text
اختبارات E2E المكلفة فقط
```

قد تتضمن خطة متوازنة:

### الطبقة الساكنة (Static Layer)

- typing،
- linting/static checks،
- schema validation.

### طبقة Unit

اختبر deterministic application logic:

- chunking،
- filtering،
- formatting،
- prompt construction helpers،
- authorization rules.

استخدم mock لـ external services عندما يكون ذلك مناسبًا.

### طبقة Integration

اختبر real interfaces:

- vector database retrieval،
- relational database contracts،
- provider response schema،
- توافق embedding/vector.

### طبقة Behavioral/Model

اختبر:

- relevance،
- groundedness،
- readability،
- toxicity،
- robustness،
- directional behavior.

### طبقة E2E

اختبر critical workflows:

- document upload وindexing،
- RAG Q&A،
- login → generation → persistence،
- رحلات مستخدم أخرى عالية القيمة.

### الانحدار في الجودة (Regression) Layer

حافظ على representative test datasets وأعد تشغيلها عندما:

- تتغير prompts،
- تتغير Models،
- تتغير retrieval،
- تتغير provider SDKs.

### صمّم من أجل Idempotency

ينبغي أن تتمكن كل test من التشغيل:

```text
مرة واحدة
أو
100 مرة
```

من دون الاعتماد على leftover state.

### السؤال النهائي في Test Design

لكل test، اسأل:

```text
ما behavior التي أكسب ثقة فيها؟
ما أصغر boundary تستطيع التحقق منها؟
ما dependency التي يجب أن تكون real؟
ما dependency التي ينبغي عزلها؟
ما failure التي ستكتشفها هذه test؟
```

هذا السؤال أكثر قيمة من تعظيم raw test count.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1

> لا تستحق Tests العناء إلا بعد اكتمال المنتج.

### لماذا هذا خطأ؟

يدافع الفصل عن testing المبكرة لأن failures المتأخرة تصبح أصعب وأكثر تكلفة في التشخيص.

### المفهوم الخاطئ 2

> تعني 100% code coverage أن النظام صحيح.

### لماذا هذا خطأ؟

تقيس Coverage code paths التي نُفذت، لا ما إذا كانت application تحقق business requirements الصحيحة.

### المفهوم الخاطئ 3

> تختلف Unit وIntegration وE2E Tests فقط في عدد Assertions التي تحتويها.

### لماذا هذا خطأ؟

تختلف أساسًا في testing boundary وعدد ونوع components المشاركة.

### المفهوم الخاطئ 4

> ينبغي لـ Tests التحقق من Internal Implementation حتى تكتشف كل Refactor.

### لماذا هذا خطأ؟

قد تفشل tests المرتبطة بـ implementation details حتى عندما يظل observable behavior صحيحًا.

### المفهوم الخاطئ 5

> Shared Mutable Global Fixtures آمنة لأن Tests تعمل بصورة منفصلة.

### لماذا هذا خطأ؟

يمكن لـ test واحدة تعديل shared state والتسبب في behavior تعتمد على order أوflaky.

### المفهوم الخاطئ 6

> Parameterization مجرد طريقة لتقليل Lines الخاصة بـ Test Code.

### لماذا هذا غير مكتمل؟

تشجع أيضًا على systematic coverage للحالات valid وinvalid وboundary وlarge-input عبر behavior contract واحدة متسقة.

### المفهوم الخاطئ 7

> Async Tests تصبح Flaky لأن Asyncio غير موثوقة.

### لماذا هذا خطأ؟

تأتي flakiness غالبًا من poor isolation أوexternal I/O timing أوunawaited operations أوshared state أوuncontrolled execution order.

### المفهوم الخاطئ 8

> استخدم Mock لكل Dependency في كل Test.

### لماذا هذا خطأ؟

يمكن لـ over-mocking إخفاء real interface وintegration failures.

### المفهوم الخاطئ 9

> Mock وStub هما المفهوم نفسه.

### لماذا هذا خطأ؟

توفر stub أساسًا predefined behavior، بينما تتحقق mock أيضًا من expected interactions.

### المفهوم الخاطئ 10

> ينبغي لـ Integration Tests تغطية Application بالكامل.

### لماذا هذا خطأ؟

يحصر المصدر integration tests حول interfaces بين عدد صغير من components.

### المفهوم الخاطئ 11

> RAG Recall وPrecision تقيسان الشيء نفسه.

### لماذا هذا خطأ؟

تقيس recall مقدار relevant information التي استُرجعت؛ بينما تقيس precision مقدار retrieved information التي كانت relevant.

### المفهوم الخاطئ 12

> ينبغي اختبار Natural-language LLM Output باستخدام Exact String Equality.

### لماذا هذا خطأ؟

يمكن أن تختلف valid model outputs. وغالبًا تكون behavioral properties وstatistical evaluation أنسب.

### المفهوم الخاطئ 13

> Model تنجح في عشر Prompts تصبح مثبتة الموثوقية لكل User Inputs.

### لماذا هذا خطأ؟

GenAI input space ضخمة جدًا؛ وتوفر tests statistical confidence عبر representative samples بدل complete coverage.

### المفهوم الخاطئ 14

> تتوقع Invariance Test أن تكون كل Output Strings متطابقة.

### لماذا هذا خطأ؟

تتحقق من أن behavior/properties المهمة تظل مستقرة تحت irrelevant input perturbations.

### المفهوم الخاطئ 15

> تعني Directional Expectation Test أن Output يجب ألا تتغير.

### لماذا هذا خطأ؟

تتحقق من أن output properties تتغير في الاتجاه المتوقع عندما تتغير input properties ذات المعنى.

### المفهوم الخاطئ 16

> توفر LLM-as-Judge Auto-evaluation Ground Truth موضوعية.

### لماذا هذا خطأ؟

الـ evaluator احتمالية أيضًا وتضيف cost وlatency وerror modes خاصة بها.

### المفهوم الخاطئ 17

> ينبغي تشغيل E2E Tests لكل تغيير صغير في Code لأنها توفر أعلى Confidence.

### لماذا هذا خطأ؟

هي مكلفة وهشة وبطيئة. ويوصي المصدر باستخدام عدد أقل منها وتشغيلها بتكرار أقل.

### المفهوم الخاطئ 18

> استدعاء FastAPI Endpoint واحدة يُعد دائمًا Integration Test.

### لماذا هذا خطأ؟

قد تستدعي endpoint عدة layers/services، لذلك كثيرًا ما يعبر endpoint-level invocation boundary بحجم E2E.

## احتفظ بهذه الفكرة (Retain this idea)

**تفصل GenAI test strategy قوية بين deterministic application logic وprobabilistic model behavior: استخدم unit tests صغيرة ومعزولة للـ code، وreal integration tests للـ interfaces المهمة، وbehavioral وstatistical evaluation للـ model outputs المتغيرة، وعددًا صغيرًا من critical E2E workflows لاكتساب ثقة على مستوى النظام. صمّم كل test حول boundary واضحة وrepresentative data وisolation وfailure محددة تريد اكتشافها.**
