# أنظمة الـ Live Agents المتكاملة و Long-Running Workflows

> **الدرس:** M01.L08  
> **مواءمة المصدر:** Chapters 12 و13 من مادة Early Release المقدمة.  
> يدمج هذا الدرس Reference Architecture مع امتدادها Production للمهام طويلة التشغيل داخل قصة تصميم واحدة متصلة.

---

## مخرجات التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يؤدي ربط كل Domain tool مباشرةً بـ Live user-facing agent إلى انهيار Architecture.
- وصف مسؤوليات Browser UI و Frontend service و FastAPI/ADK Live backend و Host agent و A2A specialists و MCP tool server.
- شرح لماذا ينبغي أن يبقى Domain parsing و Fallback logic في Layers downstream من Live host.
- تتبع Stock request واحدة عبر Browser و Backend و ADK Live و Host agent و A2A specialist و MCP tool server ثم عودتها.
- شرح لماذا ينبغي للـ Host تفويض Natural-language domain requests بدل تحويلها مبكرًا إلى Tool arguments ضيقة.
- شرح كيف ينبغي لـ Provenance و Fallback و Warning و Unavailable states الانتقال Upstream كـ Structured data.
- استخدام Service boundaries كخريطة Debugging.
- شرح لماذا Browser activity لا تعادل Full distributed tracing.
- وصف Bounded local reference app وتحديد Simplifications المقصودة فيها.
- شرح لماذا يجب تمثيل Long-running work كـ Task بدل Slow function call.
- تعريف Task identity و State و Progress و Ownership و Persistence و Cancellation و Retention و Recovery.
- شرح لماذا تصبح Task — لا Original HTTP request — هي وحدة Reliability.
- التمييز بين مسؤوليات ADK و A2A و MCP و Application-owned durable state.
- شرح لماذا لا ينبغي تشغيل Blocking work على Async event loop.
- التمييز بين Short blocking work التي يمكن تشغيلها داخل Executors وبين Truly long-running work التي تحتاج Durable task model.
- شرح الفرق بين Task initiation و Task completion.
- شرح لماذا يجب Persist للـ Remote A2A task IDs قبل وصول Updates لاحقة.
- مقارنة Polling و Streaming/Subscription و Push notifications للـ Long-running remote work.
- شرح لماذا تحسن Streaming الرؤية لكنها لا تستبدل Durable state.
- شرح كيف ينبغي التعامل مع Long-running MCP operations باعتبارها Capability-dependent task-style work.
- شرح Human-in-the-loop approval باعتبارها Asynchronous suspension.
- شرح لماذا يمكن لـ Authentication أيضًا أن تصبح Suspension point.
- شرح كيف ينبغي لـ Distributed input-required states إيقاف Workflows واستئنافها بأمان.
- تصميم Structured progress updates مفيدة لكل من User experience و Operations.
- شرح Cancellation propagation عبر Frontend و Backend و A2A و MCP boundaries.
- التمييز بين Browser disconnect و Explicit cancellation.
- شرح Timeout و Expiration و Retention و Stale-task sweeping.
- شرح لماذا تعد Idempotency أساسية في Asynchronous distributed systems.
- تعريف Correlation metadata للـ Observability عبر Frontend و ADK و A2A و MCP و Workers و Callbacks.
- شرح Security risks التي تظهر عندما تستمر Tasks بعد انتهاء User sessions و Tokens.
- تصميم Frontend state تستطيع Recovery بعد Refresh أو Disconnect أو Return-later behavior.
- تتبع Complete long-running market-report workflow من Live submission إلى Delegation و Approval و Artifact delivery و Cleanup.
- تحديد أهم Anti-patterns وعناصر Production checklist من المصدر.

## 1. لماذا يجب ألا يمتلك الـ Live agent كل شيء؟

يبدأ المصدر بحالة Failure واقعية.

يبدأ Live stock assistant بصورة بسيطة:

```text
Live Agent (الوكيل المباشر)
   ↓
get_stock_price("NVDA")
```

ينجح أول Demo.

ثم تتراكم المتطلبات:

```text
البحث عن اسم الشركة
سياق السوق
مصدر عرض السعر (provenance)
البحث عن الطقس
البحث عن العميل
البحث في المستندات
فحوص الامتثال
قواعد الاحتياط (fallback)
أخطاء المزوّد
مخططات الأدوات
سياسة المجال
```

ويصبح الـ Live agent تدريجيًا مسؤولًا عن:

- Microphone behavior،
- Turn-taking،
- Spoken response style،
- Domain parsing،
- Provider quirks،
- Routing،
- Fallbacks،
- قواعد Business.

هذا خطير لأن Live agent يمتلك أصلًا أكثر جزء حساس للـ Latency في النظام.

### رائحة معمارية (Architectural smell)

إذا كانت Component نفسها تمتلك:

```text
التفاعل المباشر
+
تفسير المجال
+
منطق المزوّد
+
قواعد الاحتياط (fallback)
+
تنفيذ الأدوات
```

فإن كل Domain change جديدة قد تهدد استقرار Live experience.

### المبدأ الأساسي

> أبقِ User-facing live agent ضيقة المسؤولية، ودع Specialists و Tool services تمتلك Domain complexity.

[[IMAGE_NEEDED: Overloaded live agent vs layered system | Left: one live agent connected directly to stock, weather, documents, customer lookup, compliance, and many rules; right: live host delegates to A2A specialists which use MCP tools | Learner should see why the live layer should not become a domain monolith]]

## 2. النظام المرجعي المتكامل

يجمع Chapter 12 مفاهيم المقرر السابقة داخل Bounded app واحدة.

مسار Request هو:

```text
UI المتصفح
   ↓
خدمة Frontend
   ↓
FastAPI Backend / ADK Live
   ↓
وكيل ADK المضيف
   ↓
متخصص A2A
   ↓

   ↓
مزوّد خارجي / احتياط حتمي
```

ثم تعود Result عبر المسار نفسه.

يستخدم المصدر Stock request التالية:

```text

وأعطني سياق السوق في جملة واحدة؟"
```

الهدف ليس بناء كل Production feature.

بل إنشاء Request path واحدة نظيفة، تمتلك فيها كل Component مسؤولية محددة.

## 3. مسؤوليات Browser UI

تمتلك Browser UI تفاعل المستخدم.

يسند المصدر إليها أمورًا مثل:

- Text fallback،
- Microphone input،
- Optional sampled frames،
- Audio playback،
- Captions،
- Controls،
- Provenance display،
- Local activity،
- التشخيصات (Diagnostics).

ما الذي لا ينبغي أن تمتلكه؟

```text
تحليل رمز السهم (ticker)
استدعاءات مزوّد البيانات المالية
توجيه المتخصص
```

ينبغي للـ Browser عرض ما يرسله النظام إليها.

ولا ينبغي أن تحاول Reverse-engineer للـ Domain meaning من Final sentences.

### مثال

Architecture سيئة للـ UI:

```text
Final sentence تحتوي "sample"
    ↓
Browser تخمن أن Data هي Fallback
```

الأفضل:

```text
Backend ترسل Structured provenance/fallback metadata
    ↓
Browser تعرضها مباشرةً
```

## 4. مسؤوليات Frontend service

تكون Frontend service بسيطة عن قصد.

وهي تخدم:

- Static assets،
- `/config.json`،
- صحة Frontend (Frontend health).

يستخدم Browser `/config.json` لمعرفة Live WebSocket URL الخاصة بالـ Backend.

لا ينبغي أن تمتلك Frontend service:

```text
بيئة تشغيل ADK Live
بيانات اعتماد النموذج
توجيه A2A
أدوات MCP
منطق المجال
```

وهذا يبقي Static delivery منفصلة عن Agent execution.

## 5. FastAPI backend و ADK Live host process

تمتلك Backend حد Browser-to-runtime.

ويسند المصدر إليها:

- `/health`،
- `/live`،
- WebSocket origin validation،
- ADK Live input queue،
- ADK Runner،
- تشكيل Events (Event shaping).

ولا ينبغي أن تمتلك:

- Static asset serving،
- Quote-provider policy،
- A2A specialist internals،
- تنفيذ MCP tools.

### تمييز مهم

تعرف Backend:

```text
How to move live input and output — كيف تنقل Live input وOutput
```

ولا تحتاج إلى معرفة:

```text
How finance works — كيف يعمل Finance domain
```

## 6. ADK Host Agent تمتلك User-facing intent

Host agent هي الوجه Conversational للنظام.

وهي تمتلك:

- User-facing conversation،
- Concise spoken relay،
- اختيار أي Specialist مكتشفة ينبغي أن تتولى Domain request.

ولا ينبغي أن تمتلك:

```text
البحث عن عرض السعر
البحث عن الطقس
جداول الأسماء البديلة للرموز
سياسة الاحتياط للمزوّد
سياسة عامة لسجل الخدمات
```

ينبغي للـ Host أن تعرف:

```text
"هذا سؤال في مجال الأسهم."
```

ولا ينبغي أن تعرف:

```text
"Nvidia -> NVDA"
"Google -> GOOGL"
"هذا المزوّد يحتاج إلى هذا الاحتياط"
```

هذه Domain details.

## 7. A2A specialists تمتلك Domain interpretation

يستخدم المصدر Stock specialist و Weather specialist منفصلتين.

تمتلك Specialist:

- Domain-specific language،
- تفسير User request،
- استدعاء MCP tool الصحيحة،
- تشكيل Structured domain results.

بالنسبة إلى Stocks، تستطيع Specialist فهم:

```text
"Nvidia"
"NVDA"
"سهم Google"
```

ولا ينبغي للـ Live host أن تحتاج هذه Mappings.

### لماذا هذا مهم؟

إذا تسربت Mappings إلى Host، فستتراكم فيها سريعًا:

- Ticker aliases،
- Weather location rules،
- Document permissions،
- حالات Compliance الخاصة.

وهذا هو Monolith الذي يحاول Chapter 12 منعه.

تمتلك MCP tool server أدنى Capability level.

في Stock path تمتلك:

```text
معالجة إخفاق المزوّد
مصدر البيانات (provenance)
وسم الاحتياط
حالة عدم التوفر
سياق سوق قصير
```

ينبغي لـ Tool أن تعيد Data، لا Final conversation.

## 9. حدود المسؤولية كعقد معماري

طريقة مفيدة لتذكر النظام:

| الطبقة | ما تمتلكه | ما لا ينبغي أن تمتلكه |
|---|---|---|
| Browser | Capture و Playback و UI و Provenance display | Domain rules |
| Frontend service | Static assets و Config | Runtime logic |
| Backend | نقل مباشر (Live transport) وتشكيل الأحداث | سلوك المالية/الطقس |
| Host Agent | Conversation و Routing | قواعد المزوّد/الاحتياط |
| A2A Specialist — المتخصص عبر A2A | تفسير Domain | لا تمتلك Browser/Live-session ownership |
| MCP Server — خادم MCP | سلوك Tool/Provider | لا تمتلك Conversation/Routing |

هذا أكثر من مجرد Documentation.

إنه Drift detector.

اسأل:

> هل بدأت هذه Component في امتلاك شيء من صف آخر؟

إذا كانت الإجابة نعم، فقد تكون Architecture بدأت تنهار.

## 16. الخطوة 6 — Specialist تضيق Request وتستدعي MCP

تفسر Stock Specialist:

```text
"Nvidia"
أو
"NVDA"
```

وتقرر Symbol.

فقط الآن تضيق Workflow إلى:

```text
get_stock_price(symbol="NVDA")    # استدعاء أداة السعر
```

تقوم MCP Server بـ:

- Validation/Normalization للـ Symbol،
- تجربة Provider path،
- إعادة Structured data،
- Label للـ Fallback/Unavailable cases.

هذه هي Layer الصحيحة لـ Provider behavior.

## 17. الخطوة 7 — حافظ على Structured domain results

لا ينبغي لـ Specialist التخلص من Metadata المفيدة.

يشدد المصدر على الحفاظ على Fields مثل:

```text
source    # المصدر
as_of    # وقت البيانات
warning    # تحذير
fallback    # احتياطي
unavailable    # غير متاح
```

تهم هذه Fields لأن المستخدم قد يسمع Fallback data كما لو كانت Live provider data إذا ضاعت Metadata.

### Architecture سيئة

```text
Tool تعيد Fallback
Specialist تحولها إلى Prose نظيفة
Host تفقد Warning
User يسمع False certainty
```

### الأفضل

```text
Structured result
    ↓
Metadata محفوظة
    ↓
Host/Model تستطيع التحدث بصدق
    ↓
Browser تستطيع عرض Provenance
```

## 20. Browser activity ليست Distributed tracing

يمكن للـ Browser عرض Activity مفيدة:

```text
الاستماع
التفكير
التفويض
الإجابة
```

لكن هذا لا يثبت تلقائيًا:

```text
تفاصيل A2A Task الداخلية
تفاصيل أداة MCP الداخلية
أحداث المزوّد
```

فهذه تحدث في Services منفصلة.

إذا احتجت Full proof، أضف:

- Correlated logs،
- Trace IDs،
- Instrumentation صريحة.

### مبدأ UI

> اعرض للمستخدم Progress ذات معنى، لا Raw protocol machinery.

## 21. تطبيق Chapter 12 محدود عن قصد

لا يقدم المصدر Reference app باعتبارها Production-complete.

بل يستخدم Simplifications مثل:

- Local processes،
- In-memory session state،
- Configured specialist URLs،
- Static stock/weather routing،
- Fast A2A response path،
- Deterministic fallback stock data،
- Deterministic mock weather،
- عدم وجود Production authorization،
- عدم وجود Durable Task workspace.

هذه Limits مقصودة.

وهي تبقي Architectural handoffs ظاهرة.

## 22. Anti-patterns في Bounded reference architecture

يسلط المصدر الضوء على عدة Anti-patterns.

### لا تربط كل Tool مباشرةً بالـ Host

هذا يعيد إنشاء Monolith.

### لا تنفذ Parse للـ Domain entities داخل Host

هذا يضعف Specialist boundaries.

### لا تخفِ Fallback/Mock data

يحتاج المستخدم إلى Data-quality labels صادقة.

### لا تعامل Browser diagnostics كـ Distributed tracing

تحتاج Deeper service activity إلى Explicit instrumentation.

### لا تعامل A2A كأنها Local function call

تحتاج Network calls إلى:

- Timeouts،
- Failure handling،
- ولاحقًا Durable lifecycle للأعمال الطويلة.

### لا تعرض Raw protocol vocabulary في UI

يحتاج المستخدمون State مفهومة، لا Implementation jargon.

## 24. Long-running work ليست Slow function call

نموذج ذهني شائع للمبتدئ:

⟦CODE_2⟧

بالنسبة إلى Tasks صغيرة، لا مشكلة.

أما الأعمال الطويلة فهذا خطير.

إذا بقي Request واحدة مفتوحة 20 دقيقة:

- قد تنتهي Infrastructure timeout،
- قد تنقطع Browser،
- يبقى Worker مشغولًا،
- تبدو UI Frozen،
- قد تكرر Retries العمل،
- وقد تفقد Process restart الـ State.

التحول الأساسي في المصدر:

> Long-running work هي Task لها Identity و Lifecycle.

## 25. Task تصبح وحدة Reliability

تحتاج Durable task إلى أكثر من ID.

تحتاج:

```text
الهوية
الحالة
التقدم
الملكية
الاستمرارية
الإلغاء
الاحتفاظ
التعافي
```

قد يربط Task record نموذجية بين:

```text
المستخدم
الجلسة
سير العمل
agent بعيد
A2A task بعيدة
عملية/مهمة MCP
artifact النتيجة
```

الفكرة الأساسية من المصدر:

```text
Request تبدأ العمل
Task تمتلك العمل
```

وهذا يغير Architecture بصورة جوهرية.

## 26. حالات Task الصريحة

## 27. ADK و A2A و MCP: مسؤوليات منفصلة

يفصل المصدر صراحةً بين ثلاث Layers.

### طبقة ADK

تدير:

- Local agent session،
- Tool invocation،
- Event flow،
- Working context،
- Local confirmation/Long-running tool features عند دعمها.

### طبقة A2A

تدير:

- Remote agent delegation،
- Remote Task identity،
- Messages،
- Status updates،
- Polling،
- Streaming،

### طبقة MCP

تدير:

- Host-to-tool-server capabilities،
- Tool/Resource/Prompt interactions،
- Progress/Cancellation utilities،
- Task-style features عند دعمها.

### الحالة الدائمة للتطبيق (Application durable state)

تربط كل هذه Layers.

```text
معرّفات عمليات MCP (IDs)
بيانات الربط (correlation)
```

## 29. افصل Task initiation عن Task completion

بالنسبة إلى Report تستغرق 20 دقيقة:

### مرحلة البدء (Initiation phase)

```text
التحقق من الطلب
إنشاء task/ID لسير العمل
حفظ الربط بالمستخدم/الجلسة
بدء عمل خارجي/في الخلفية
الإرجاع فورًا
```

### مرحلة الإكمال (Completion phase)

لاحقًا:

```text
استقبال/جلب تحديث المهمة
التحقق من الملكية
حفظ الحالة الجديدة
إرفاق النتيجة
استئناف agent المحلي عند الحاجة
إخطار UI
```

لا تحتاج Original network request إلى البقاء Alive.

## 30. In-memory state لا تكفي للـ Production

تكون In-memory stores مفيدة للتعلم.

لكنها تفشل عندما:

```text
إعادة تشغيل العملية
انتقال الـ container
انهيار الخادم
عودة المستخدم لاحقًا
```

تحتاج Production long-running work إلى Durable storage.

أمثلة:

- Relational database،
- Durable workflow store،
- Redis مهيأة بصورة مناسبة.

ينطبق المبدأ نفسه على:

- Tasks،
- Agent sessions،
- Approval state،
- مراجع Artifacts.

لا ينبغي لـ Paused workflow الاعتماد على Live Python object.

## 31. ينبغي لـ ADK long-running tools إعادة Receipt

يناقش المصدر دعم ADK للـ Long-running tools.

والقاعدة المعمارية أهم من Specific API.

ينبغي للـ Long-running tool أن:

```text
بدء عمل خارجي أو الإشارة إليه
إرجاع إيصال مهمة (job/task)
```

ولا ينبغي أن:

```text
تنفيذ 30 دقيقة من العمل بشكل متزامن
```

أمثلة:

```text
بدء مهمة تقرير -> job_id
إنشاء تذكرة موافقة -> pending
بدء تصدير سحابي -> operation_id
```

ينبغي أن يعيش العمل الفعلي داخل:

- Worker queue،
- Remote agent،
- Workflow engine،
- Cloud job،
- خدمة MCP تدعم Tasks.

## 32. حافظ على Original function-call identity

عندما تعود نتيجة Long-running بعد وقت، يحتاج النظام إلى Correlate لها مع Original function call.

تشمل Identifiers المفيدة:

```text
function_call_id
session_id
invocation_id
workflow_id
ID لـ A2A task البعيدة
ID لعملية/مهمة MCP
```

لكن المصدر يؤكد:

> Workflow/Task IDs لا تستبدل Original function-call identity عندما تتوقع Framework هذه Identity لاستئناف Operation.

وهذا يمنع Model/Runtime من إعادة بناء Operation سابقة بطريقة خاطئة.

## 33. ينبغي أن تعود A2A delegation سريعًا في Long work

عندما يستقبل Remote A2A agent عملًا طويلًا، لا ينبغي للـ Caller بالضرورة الانتظار حتى Completion.

مفاهيميًا:

```text
Orchestrator
   ↓ إرسال
Agent بعيد
   ↓
إنشاء Task
   ↓ إيصال فوري
Orchestrator يحفظ ID الـ Task البعيدة
```

ثم تصل Updates لاحقًا.

### قاعدة Durability حرجة

> Persist للـ Remote Task mapping قبل الاعتماد على Future updates.

وإلا فإن Crash بين:

```text
أُنشئت المهمة البعيدة
```

و:

```text
حُفظ الربط المحلي
```

قد يجعل العمل Orphaned.

## 34. Polling للحصول على Remote progress

تعد Polling أبسط Update strategy.

```text
العميل
  ↓ الحالة؟
الخادم
  ↓ قيد العمل

انتظار

العميل
  ↓ الحالة؟
الخادم
  ↓ مكتمل
```

تكون مناسبة عندما:

- لا تكون Task شديدة الحساسية للوقت،
- تكون Inbound webhooks صعبة،
- تكون البساطة مهمة.

استخدم:

- Backoff،
- فترات تكيفية (Adaptive intervals).

لا ترهق Remote agent بطلب Status كل ثانية لمهمة تستغرق عدة ساعات.

## 35. Streaming و Subscription

تكون Streaming مفيدة عندما يريد Caller رؤية Updates فورًا.

قد تشمل Updates:

- Task status،
- Partial Message،
- Artifact update،
- تقدم العمل (Progress).

لكن المصدر يوضح تمييزًا مهمًا:

> Stream تمنح Visibility، لكنها ليست Durable state.

إذا انقطع Stream، يجب أن تظل Application قادرة على Recovery انطلاقًا من Persisted Task state.

## 36. Push notifications و Webhooks

مع Push:

```text
Orchestrator يوفّر callback
Agent البعيد يعمل
Agent البعيد يرسل التحديث لاحقًا
```

ينبغي لـ Production callback receiver أن:

1. يتحقق من هوية Sender،
2. يتحقق من Task/Context IDs،
3. يتحقق من Expected remote agent،
4. يفحص Duplicate/Out-of-order updates،
5. يعمل Persist للـ Update،
6. يستأنف/يحدث Workflow عند الحاجة،
7. يعيد Acknowledgment سريعًا.

تجنب تنفيذ Expensive work داخل Webhook handler.

أرسل Follow-up processing إلى Queue بدلًا من ذلك.

## 37. Long-running work في MCP

قد تكون بعض MCP tool operations طويلة التشغيل أيضًا.

أمثلة:

- Large exports،
- File transformations،
- Indexing،
- Computation مكلفة.

```text
حفظ هوية المهمة
إرجاع الإيصال
```

## 38. Human-in-the-loop هو Asynchronous suspension

تنتظر بعض Workflows بسبب البشر، لا بسبب Computation.

أمثلة:

- Approve payment،
- Choose target environment،
- Authorize paid dataset،
- الإجابة عن سؤال Compliance.

النمط الصحيح:

```text
الوصول إلى نقطة قرار
حفظ سير العمل
تخزين الـ prompt المعلَّق
تحرير الموارد
انتظار
استقبال استجابة مرتبطة
استئناف
```

لا تترك Original request محجوزة لساعات.

## 39. Tool confirmation ما تزال تحتاج Durable correlation

يمكن لـ Framework confirmation features تبسيط Approval prompts.

لكن Production design ما تزال تحتاج:

- Persistent state،
- Correlation ID،
- Idempotency،
- Expiration،
- فحوص Ownership.

إذا ضغط المستخدم "Approve" مرتين، يجب ألا ينفذ النظام Sensitive action مرتين.

يجب أن ترتبط Approval بالـ Original operation المحددة بدقة.

## 40. Authentication يمكن أن توقف Workflow أيضًا

قد تصل Long-running work إلى Protected service بعد انتهاء صلاحية User token.

ينبغي للـ Workflow أن:

1. تكتشف Missing/Expired credentials،
2. تنتقل إلى `auth_required`،
3. تخزن Pending operation،
4. تعرض Authorization flow،
5. تستأنف بعد عودة Valid credentials،
6. تعيد فحص Authorization قبل Sensitive action.

لا تفترض أن Credentials ستظل صالحة لمجرد أن Task بدأت بينما كان المستخدم Authenticated.

## 44. يجب أن تنتشر Cancellation

إذا ضغط المستخدم Cancel، لا يكفي إخفاء Progress.

قد يكون Cancellation path:

```text

  ↓

  ↓
MCP operation cancellation عند دعمها
  ↓
Worker cleanup
  ↓
Final state: Canceled
```

- Files،
- Sockets،
- Cursors،

## 45. Disconnect ليست Cancellation

قد يعني إغلاق Browser tab:

```text
"سأعود لاحقًا."
```

ولا يعني بالضرورة:

```text
"أوقف العمل."
```

فقط Explicit cancel intent هي التي ينبغي أن توقف Underlying work.

وهذا سبب إضافي يجعل Task state تستمر بعد Browser connections.

## 46. Timeouts و Expiration و Retention أشياء مختلفة

تحتاج Production workflows إلى عدة Time controls مختلفة.

### مهلة Request (Request timeout)

كم من الوقت يمكن أن تظل Network request واحدة مفتوحة؟

### مهلة Task (Task timeout)

كم من الوقت يمكن أن تستمر Work نفسها؟

### الاحتفاظ بالنتيجة (Result retention)

كم من الوقت تُحفظ Completed artifacts؟

### انتهاء صلاحية Approval (Approval expiration)

كم تبقى Pending human decision صالحة؟

### فترة Polling (Polling interval)

كم مرة يفحص Callers الحالة؟

### سياسة Retry (Retry policy)

أي Failures يمكن Retry لها وكم مرة؟

هذه تحل Problems مختلفة ولا ينبغي اختزالها في Number واحدة.

## 47. Ghost tasks تحتاج Stale-task sweeper

تحدث Ghost task عندما:

```text
Local workflow تظن أن العمل ما يزال Pending
```

لكن:

```text
Remote worker اختفت
```

ينبغي لـ Sweeper أن تقوم دوريًا بـ:

1. العثور على Non-terminal tasks،
2. مقارنة Last update بـ Task TTL،
3. فحص ما إذا كانت Remote state ما تزال قابلة للاسترجاع،
4. وضع Unrecoverable tasks في Failed/Timed-out state،
5. Notify/Resume للـ Local workflow،
6. إصدار Logs/Metrics.

لا ينبغي أن ينتظر المستخدم للأبد لأن Worker ماتت بصمت.

## 48. Idempotency هي المتطلب الخفي

تقوم Asynchronous systems بإعادة المحاولة.

وتحدث Duplicates بسبب:

- Network retries،
- Webhooks تصل مرتين،
- User double-click،
- Streams تعيد الاتصال،
- Polling تتداخل مع Push،
- Workers تكرر Messages.

من دون Idempotency قد يقوم النظام بـ:

- إنشاء Duplicate reports،
- Charging مرتين،
- إرسال Duplicate emails،
- تكرار Destructive actions.

### مفتاح Idempotency

ينبغي أن تمثل Key User intent.

مثال:

```text
إنشاء تقرير
للجلسة X
الطلب Y
```

ينبغي أن تُطابق Repeated transport requests نفس Durable task.

## 52. توسع Long-running workflows سطح Security

- ينفصل المستخدم،
- تنتهي صلاحية Token،
- ينتقل العمل إلى Worker أخرى.

ينبغي للنظام تخزين:

```text
سياق التفويض
```

وليس Raw long-lived token فقط.

قبل Sensitive actions:

```text
إعادة فحص الصلاحية
```

- Service identities،
- Signed payloads،
- Private networking،
- mTLS عندما يكون مناسبًا.

ولا ينبغي أن تظهر Secrets داخل:

- Task IDs،
- URLs،
- Logs،
- نص Progress.

## 64. Anti-patterns في Long-running workflows

يسلط المصدر الضوء على أخطاء شائعة عديدة.

### إبقاء Original request مفتوحة

ينبغي للعمل الطويل أن يستمر بعد Initiating request.

### اعتبار Stream هي Storage

يجب ألا يؤدي Disconnected stream إلى فقد Workflow state.

### الاحتفاظ بـ Task state في Memory فقط

ينبغي ألا تدمر Process restart هوية Active work و Recovery state.

### افتراض Exactly-once webhook delivery

يجب تحمل Duplicates و Reordering.

### افتراض نجاح Cancellation دائمًا

قد تتجاوز بعض Operations نقطة Irreversible.

### إعادة بناء Approved operations من الصفر

استأنف باستخدام Original correlation/Function identity.

### الاعتماد على Private SDK internals

ينبغي لـ Architecture أن تتحمل SDK changes.

### افتراض وجود MCP Tasks في كل مكان

تعامل مع Task-style support باعتبارها Capability-dependent و Negotiated.

## 67. النموذج الذهني الكامل

يرتبط الفصلان بصورة طبيعية.

### Live turn محدودة (Bounded live turn)

```text
المتصفح
  ↓
Backend / ADK Live
  ↓
Agent المضيف
  ↓
متخصص A2A
  ↓
أداة MCP
  ↓
نتيجة منظَّمة
  ↓
المضيف
  ↓
إجابة منطوقة/نصية
```

### الامتداد طويل التشغيل (Long-running extension)

```text
طلب مباشر
  ↓
ID لسير عمل دائم
  ↓
ID لـ A2A Task البعيدة
  ↓
عمليات MCP
  ↓
أحداث التقدم
  ↓
تعليق اختياري للبشر/المصادقة
  ↓
استئناف
  ↓
Artifact النهائي
  ↓
التنظيف + الاحتفاظ
```

ما يزال المستخدم يختبر:

```text
مساعد واحد
```

لكن النظام موثوق لأن كل Boundary تمتلك:

```text
ملكية واضحة
هوية دائمة
حالة قابلة للاسترداد
تقدم صادق
ربط (correlation)
أمان
```

وهذا ما يسمح لنظام ذكي أن يظل Dependable عندما يصبح العمل بطيئًا أو Distributed أو Interruptible أو Human-dependent.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "ينبغي للـ Live host عمل Normalize لكل Domain entity قبل Delegation."

لا. ينبغي أن يبقى Domain interpretation داخل Specialist كلما كان ذلك ممكنًا.

### المفهوم الخاطئ 2
> "ينبغي للـ Browser استنتاج Provenance من نص Final answer."

لا. ينبغي أن تنتقل Provenance و Fallback status كـ Structured metadata.

### المفهوم الخاطئ 3
> "Browser activity events تثبت Full A2A/MCP execution trace."

لا. تحتاج Deeper service activity إلى Explicit instrumentation و Correlation.

### المفهوم الخاطئ 4
> "Long-running task مجرد Function call عادية ذات Timeout أكبر."

لا. تحتاج Durable identity و State و Progress و Cancellation و Recovery.

### المفهوم الخاطئ 5
> "إبقاء Stream مفتوحة يجعل Task state Durable."

لا. Streams هي Transport/Visibility وليست Source of truth.

### المفهوم الخاطئ 6
> "In-memory task state مناسبة للـ Production long-running work."

لا. ستفقد Process restart هوية Active task و Recovery state.

### المفهوم الخاطئ 7
> "ينبغي لـ ADK long-running tool تنفيذ Operation التي تستغرق ساعة كاملة داخل Agent process."

لا. ينبغي أن تبدأ أوتشير إلى Durable external work ثم تعيد Receipt.

### المفهوم الخاطئ 8
> "يمكن تخزين Remote A2A task ID لاحقًا."

لا. قم بـ Persist للـ Mapping فورًا قبل الاعتماد على Future updates.

### المفهوم الخاطئ 9
> "Streaming تستبدل Polling أو State retrieval."

لا. تحسن Streaming الـ Responsiveness؛ أما Durable state فتدعم Recovery.

### المفهوم الخاطئ 10
> "Human approval مجرد UI feature خاصة وليست جزءًا من Workflow state."

لا. إنها Asynchronous suspension point تحتاج Persistence و Correlation.

### المفهوم الخاطئ 11
> "إغلاق Browser ينبغي أن يلغي Underlying task."

لا. Disconnect و Cancellation نيتان مختلفتان.

### المفهوم الخاطئ 12
> "Webhook delivery تحدث Exactly once."

لا. يجب توقع Duplicate و Out-of-order delivery.

### المفهوم الخاطئ 13
> "Cancellation تعني أن كل Remote side effect يمكن التراجع عنها دائمًا."

لا. قد تتجاوز بعض Operations نقطة Irreversible.

### المفهوم الخاطئ 14
> "Timeout واحدة تستطيع التحكم في كل Aspect من Long-running workflow."

لا. Request timeout و Task timeout و Approval expiry و Retention و Retries و Polling intervals تحل Problems مختلفة.

### المفهوم الخاطئ 15
> "Task IDs وحدها تجعل Workflow قابلة للـ Observability."

لا. تحتاج Correlation عبر Session و Workflow و Remote task و Operation و Trace و Idempotency identifiers.

### المفهوم الخاطئ 16
> "Authorization التي تم فحصها عند إنشاء Task تكفي لـ Workflow تستمر ساعات."

لا. قد تحتاج Sensitive actions إلى Authorization re-checks لاحقًا.

### المفهوم الخاطئ 17
> "إذا أعادت Progress stream الاتصال، فكل Missing update مضمونة الإعادة."

لا. ينبغي أن تعتمد Recovery على Durable state، مع Replay فقط عندما يكون مدعومًا.

### المفهوم الخاطئ 18
> "ينبغي افتراض توفر MCP long-running task features في كل مكان."

لا. تعامل معها كميزات تعتمد على Capability و Version.
