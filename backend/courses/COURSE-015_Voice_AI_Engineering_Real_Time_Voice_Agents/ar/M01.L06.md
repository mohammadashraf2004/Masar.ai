## 1. لماذا ننتقل إلى ما بعد Agent واحدة؟

من السهل فهم Agent واحدة عندما تكون Problem صغيرة.

قد تبدأ بـ:

```text
Agent واحدة (One agent)
+ Prompt واحدة (one prompt)
+ عدة Tools (several tools)
```

كلما نما Application، يستمر Developers غالبًا في إضافة:

```text
Tools أكثر (more tools)
مسؤوليات أكثر (more responsibilities)
قواعد أكثر (more rules)
استثناءات أكثر (more exceptions)
Examples أكثر (more examples)
```

وفي النهاية تصبح Agent من النوع Monolith.

تخيل Teaching Agent واحدة تتعامل مع:

- Grammar،
- Mathematics،
- Summarization،
- Research،
- Writing،
- Scheduling،
- توصيات (Recommendations).

تصبح Prompt الخاصة بها و Tool list أكثر ازدحامًا باستمرار.

وقد يجعل ذلك Agent:

- أصعب في Testing،
- أصعب في Debugging،
- أصعب في Maintenance،
- أكثر عرضة لخلط المسؤوليات،
- أصعب في التطوير بصورة مستقلة.

يستخدم المصدر تشبيهًا من Software engineering:

```text
Software أحادي الكتلة (monolithic software)
      ↓
الخدمات المصغرة (Microservices)

Agent أحادية الكتلة (monolithic agent)
      ↓
Agents متخصصة (Specialized agents)
```

الفكرة الأساسية ليست "استخدم Agents كثيرة في كل مكان".

بل هي:

> عندما تكون المسؤوليات مختلفة بوضوح، فإن تقسيمها إلى Specialists مركزة يمكن أن يحسن Modularity.

## 2. قسّم Agents كما تقسّم Microservices

يكون Specialist الجيد ذا مهمة ضيقة.

يستخدم المصدر مثال Teaching Assistant.

### Agent الخاصة بـ Grammar (Grammar Agent)

المسؤولية:

```text
فحص Input الخاص بالمستخدم بحثًا عن أخطاء Grammar (Check the user's input for grammatical errors.)
```

Tool:

```text
check_grammar
```

### Agent الخاصة بـ Math (Math Agent)

المسؤولية:

```text
تنفيذ العمليات الرياضية (Perform mathematical operations.)
```

Tools:

```text
جمع (add)
طرح (subtract)
ضرب (multiply)
قسمة (divide)
```

### Agent الخاصة بـ Summary (Summary Agent)

المسؤولية:

```text
دمج نتائج الفريق في Response واحدة ودودة (Combine the team's findings into one friendly response.)
```

Tools:

```text
لا توجد حاجة إلى Tools (none required)
```

هذا Decomposition مفيد لأن كل Agent يمكن أن تمتلك:

- Prompt خاصة بها،
- Tools خاصة بها،
- Tests خاصة بها،
- Output contract خاصة بها.

سؤال Design مفيد هو:

> هل أستطيع وصف مسؤولية هذه Agent في جملة واضحة واحدة؟

إذا لم تستطع، فقد تكون مسؤوليتها ما تزال واسعة أكثر من اللازم.

## 3. خمسة أنماط للتعاون

ما زال فريق Agents يحتاج إلى Orchestration pattern.

### نمط Router

```text
             ┌-> Agent للفوترة (Billing Agent)
المستخدم (User) -> Router
             ├-> Agent للدعم (Support Agent)
             └-> Agent للطقس (Weather Agent)
```

يختار Router مركزي Specialist الأكثر صلة.

استخدمه عندما ينتمي Request واحد عادةً إلى Domain واحدة.

---

### نمط Parallel

```text
                 ┌-> Agent للرحلات (Flight Agent) --┐
مخطط السفر (Travel Planner) --|                  |-> الدمج (Combine)
                 └-> Agent للفنادق (Hotel Agent) ---┘
```

تعمل Tasks المستقلة بصورة Concurrent.

استخدمه عندما لا تعتمد Subtasks على بعضها.

---

### نمط Sequential

```text
وكيل A
   ↓
وكيل B
   ↓
وكيل C
```

تعمل كل Stage بترتيب ثابت.

استخدمه عندما تعتمد Stages اللاحقة على Outputs السابقة.

---

### نمط Circular

```text
الكاتب (Writer)
 ↓
المحرر (Editor)
 ↓
الكاتب (Writer)
 ↓
...
```

تعمل Agents بصورة متكررة على Refinement للعمل.

استخدمه في Critique و Revision loops.

---

### نمط Dynamic

```text
وكيل A <-> وكيل B
  ↕          ↕
وكيل C <-> وكيل D
```

تتواصل Agents بمرونة.

هذا Powerful لكنه أصعب في Reasoning بشأنه.

## 4. اختر Pattern من بنية Dependencies

يمتلك Teaching Assistant في المصدر ترتيب Dependencies واضحًا:

```text
1. تصحيح Grammar (Correct the grammar)
2. استخدام Query المصححة في Math (Use the corrected query for math)
3. تلخيص النتائج (Summarize the results)
```

لذلك:

```text
القواعد (Grammar)
  ↓
الرياضيات (Math)
  ↓
التلخيص (Summary)
```

هو Sequential workflow طبيعي.

دليل اختيار بسيط:

| السؤال | Pattern المحتمل |
|---|---|
| هل يطابق Request واحد Specialist واحدة؟ | Router |
| هل تستطيع عدة Specialists العمل بصورة مستقلة؟ | Parallel |
| هل تعتمد كل Stage على السابقة؟ | Sequential |
| هل يحتاج العمل إلى Refinement متكرر؟ | Circular |
| هل Communication مرنة ومتكيفة بدرجة كبيرة؟ | Dynamic |

## 8. Callbacks: Lifecycle hooks حول التنفيذ

يقدم المصدر Callbacks بوصفها Control points حول Agent lifecycle.

فكّر في Callbacks بوصفها:

```text
طبقة وسيطة (Middleware)
اعتراضات التنفيذ (Interceptors)

```

تسمح بتشغيل Custom Python code عند Execution boundaries محددة.

يصف المصدر ستة مواضع رئيسية للـ Callback:

```text
before_agent

before_model

before_tool
after_tool
```

## 9. Before-agent و After-agent callbacks

### Callback قبل Agent (Before-agent callback)

تعمل قبل أن تبدأ Agent عملها الرئيسي.

مفيدة في:

- تحميل Initial context،
- التحقق من Prerequisites،
- فرض Entry rules.

### Callback بعد Agent (After-agent callback)

تعمل بعد انتهاء Agent.

مفيدة في:

- Logging،
- Auditing،
- Output checks،
- تنظيف State (State cleanup).

مثال:

```text
قبل Math Agent (Before Math Agent):
هل grammar_response موجودة؟ (Does grammar_response exist?)
```

إذا لم تكن موجودة، فأوقف التنفيذ بدل الاستمرار بـ Invalid state.

---

## 10. Before-model و After-model callbacks

### قبل Model (Before-model)

تعمل قبل إرسال Context إلى Model.

مفيدة في:

- حقن Dynamic context،
- فحص Sensitive content،
- تطبيق Caching،
- تعديل Final request.

### بعد Model (After-model)

تعمل بعد عودة Raw model output.

مفيدة في:

- Filtering،
- Reformatting،
- Validation،
- إضافة Standard behavior.

ينشئ ذلك Application-controlled boundary حول Model.

---

## 11. Before-tool و After-tool callbacks

### قبل Tool (Before-tool)

تعمل بعد اختيار Tool ولكن قبل تنفيذها.

مثالية من أجل:

- Permission checks،
- Input validation،
- Safety checks،
- عمليات البحث في Cache (Cache lookups).

### بعد Tool (After-tool)

تعمل بعد Tool execution.

مفيدة في:

- Logging،
- Normalizing tool results،
- كتابة State جديدة،
- Caching.

وهذا مهم بصورة خاصة للـ Tools ذات Side effects.

---

## 12. ما الذي يمكن أن تنفذه Callbacks؟

يعطي المصدر عدة Patterns.

### حواجز الأمان والتحقق (Guardrails)

منع Operations التي تنتهك Policy.

### إدارة State الديناميكية (Dynamic State Management)

قراءة وكتابة State اعتمادًا على Current context.

### Logging و Monitoring

بناء Detailed execution traces.

### Caching

إعادة Cached result بدل تكرار Call مكلفة.

### تعديل Request/Response

حقن Context أو Normalize للنتائج.

### التجاوز الشرطي (Conditional Skipping)

تجاوز Model/Tool call عندما تمتلك Callback بالفعل النتيجة المطلوبة.

لذلك تنقل Callbacks التحكم المهم خارج Prompt text إلى Deterministic application code.

## 17. Debugging للـ Shared state خطوة بخطوة

إذا كانت Final output خاطئة، فقد لا تكون المشكلة في Final agent.

الأسباب المحتملة:

- Grammar Agent أنتجت Correction سيئة.
- Math Agent استقبلت State خاطئة.
- State key كانت مفقودة.
- Prompt templating أشارت إلى Key خاطئة.
- Summary Agent أساءت فهم Upstream results.

ينبغي لـ Multi-agent debugger جيدة أن تعرض:

```text
State قبل Agent (state before agent)
State بعد Agent (state after agent)
استدعاءات Tools (Tool calls)
نتائج Tools (Tool results)
Outputs الخاصة بـ Agent
```

يستخدم المصدر ADK Web لفحص Workbench بصريًا.

### قاعدة

> نفّذ Debugging للـ Pipeline عند كل Stage، لا عند Final answer فقط.

## 19. نمط Agent كـ Tool (Agent-as-a-tool)

يقدم المصدر Integration عملية:

```text
Agent مباشرة (Live Agent)
  ↓
تستدعي Teaching Assistant كـ Tool واحدة (calls Teaching Assistant as one tool)
  ↓
تنفذ Multi-agent pipeline (multi-agent pipeline executes)
  ↓
تعود Final result (final result returns)
  ↓
تتحدث Live Agent (Live Agent speaks)
```

### لماذا هي مفيدة؟

- مباشرة،
- سهلة Integration،
- تخفي Internal complexity.

### لماذا قد تصبح محدودة؟

يصبح الفريق كله Black box واحدة.

وقد تكون لدى Front agent Visibility محدودة داخل Specialists الداخلية.

لذلك يقدم المصدر هذا Pattern بوصفه عمليًا لـ Contained pipeline، لا بوصفه Final answer لكل Large systems.

## 21. لماذا يكون Live handoff صعبًا؟

- Tone،

- Timing،

- Conversation summary،
- Current task state،
- Preferences،

> كيف تتواصل Independent agents عبر Standard interface؟

## 22. مشكلة "Walled garden"

تخيل:

```text
المساعد التعليمي -> ADK
وكيل البحث -> LangGraph
وكيل التهيئة -> CrewAI
وكيل الرواتب -> LangChain
```

لكل Framework:

- Runtime،
- State،
- Tool format،
- Agent object،
- نموذج Message (Message model).

من دون Standard، قد يحتاج كل Pair إلى Custom integration.

يسمي المصدر هذا Tower-of-Babel problem.

الهدف هو تمكين Agents من التعاون حتى عندما تختلف Internal frameworks الخاصة بها.

---

## 23. A2A: لغة خارجية مشتركة للـ Agents

يقدم المصدر Agent2Agent (A2A) Protocol.

من حيث الفكرة:

```text
التنفيذ الداخلي (Internal implementation):
ADK / LangGraph / CrewAI / other

العقد الخارجي (External contract):
A2A
```

لا يحتاج Remote caller إلى معرفة كيف بُنيت Agent الأخرى.

بل يحتاج إلى معرفة:

- كيف يكتشفها،
- ما الذي تستطيع فعله،
- كيف ينفذ Authentication،
- كيف يرسل Work،
- كيف يستقبل Status/Results.

وهذا يتيح Model باسم "Agents as a Service".

---

## 24. خمسة مبادئ لـ A2A يصفها المصدر

### التنفيذ غير المكشوف داخليًا (Opaque Execution)

قد تخفي Remote agent الـ Internal implementation الخاص بها.

### أولوية Async (Async First)

يفترض Protocol أن بعض Tasks قد تستغرق وقتًا طويلًا.

### الاستقلال عن نوع Modality (Modality Agnostic)

يمكن لـ Protocol تمثيل أكثر من Plain text.

### الجاهزية للمؤسسات (Enterprise Ready)

Security و Privacy و Tracing و Monitoring مهمة.

### البساطة والاتساق (Simple and Consistent)

يبني A2A على Web concepts مألوفة بدل طلب Stack غير معتادة تمامًا.

[[IMAGE_NEEDED: Five A2A principles | Opaque Execution, Async First, Modality Agnostic, Enterprise Ready, and Simple & Consistent around an A2A hub | Learner should remember the protocol design goals]]

---

## 25. التنفيذ غير المكشوف داخليًا (Opaque Execution)

قد تنفذ Research Agent داخليًا:

- عدة Searches،
- فحص Documents،
- استدعاء Sub-agents،
- Revision للـ Answer.

لا يحتاج Client إلى كل هذه Internal details.

قد يحتاج فقط إلى:

```text
قيد العمل (working)
```

ثم لاحقًا:

```text
مكتمل + النتيجة
```

وهذا يحافظ على Encapsulation.

Opaque execution لا تعني "عدم وجود Observability".

يمكن لـ Developer مع ذلك كشف Useful status updates دون كشف Private prompts أو Implementation logic.

---

## 26. لماذا A2A من النوع Async-first؟

يمكن أن تختلف Agent tasks كثيرًا في Duration.

مثال:

```text
2 + 2
```

قد تكتمل فورًا.

لكن:

```text
راجع Contract وانتظر Human approval (review a contract and wait for human approval)
```

قد تستغرق ساعات.

Protocol يفترض أن كل Operation تنتهي داخل Connection قصيرة واحدة لن تتعامل جيدًا مع Agentic workloads.

ولهذا يشدد المصدر على Asynchronous task management.

## 27. أدوار A2A الثلاثة

### المستخدم النهائي (End-User)

ينشئ High-level goal.

وقد يكون:

- Human،
- Application،
- مهمة مجدولة (Scheduled job).

### الطرف المبادر (Client)

يعمل بوصفه Initiator/Orchestrator.

يمكن لـ Client:

- فهم Request،
- العثور على Specialist،
- Delegation للعمل.

### الطرف المنفذ (Server)

هي Remote agent التي تنفذ Delegated task.

تكشف Standardized external contract مع إبقاء Internal implementation خاصة.

## 28. Client و Server أدوار

يمكن لـ Agent أن تكون Server في علاقة و Client في علاقة أخرى.

مثال:

```text
Concierge -> Research Agent — Research Agent هنا هي Server
```

هنا Research Agent هي Server.

لكن Research Agent قد تستدعي:

```text
PDF Analysis Agent — Agent أخرى تُستدعى عن بُعد
```

الآن تعمل Research Agent بوصفها Client.

وهذا يسمح ببناء Agent networks عميقة.

## 29. Agent Card: بطاقة العمل الرقمية

كيف يعرف Client:

```text
أي Remote agent موجودة؟ (which remote agent exists?)
ما Skills التي تقدمها؟ (what skills it offers?)
كيف يصل إليها؟ (how to reach it?)
كيف ينفذ Authentication؟ (how to authenticate?)
```

يجيب المصدر باستخدام **Agent Card**.

وهي Standardized description للعقد العام الخاص بـ Agent.

فكر فيها بوصفها:

```text
الهوية (Identity)
+
القدرات (Capabilities)
+
معلومات الاتصال (Connection information)
+
متطلبات Security
```

## 30. ثلاثة أساليب لـ Discovery

يصف المصدر:

### الإعداد المباشر (Direct Configuration)

يعرف Client الـ Remote agent مسبقًا.

مفيد للـ Small static systems.

### الموقع القياسي المعروف (Well-known Location)

يعرف Client الـ Domain ويسترجع Agent Card من Standard location.

Exact URI pattern خاصة بإصدار Protocol وينبغي التحقق منها مقابل Current specification.

### السجل أو الكتالوج (Registry/Catalog)

يسمح Central directory للـ Clients بالبحث حسب Skill.

مثال:

```text
اعثر على Agent تستطيع تنفيذ Academic research (Find an agent that can perform academic research.)
```

وهذا يصبح مهمًا في Large organizations.

## 31. Fields مهمة في Agent Card

يصف المصدر عدة Categories.

### Name و Description

ما هي Agent.

### Interfaces المدعومة (Supported Interfaces)

كيف يمكن الاتصال بها.

### الإصدار (Version)

### القدرات (Capabilities)

قد تصف Features مثل Streaming أو Push notifications.

### مخططات Security (Security Schemes)

ما Authentication mechanisms المدعومة.

### متطلبات Security (Security Requirements)

أي Authentication combination مطلوبة.

### المهارات (Skills)

ما Jobs التي تستطيع Agent تنفيذها.

ينبغي لـ Client اختيار Remote Server بناءً على Published skill contract.

## 32. Direct Message مقابل Stateful Task

لا يحتاج كل Request إلى Long-running Task.

### رسالة مباشرة (Direct Message)

مناسبة لـ:

- Simple interaction،
- Clarification،
- Request بلا State (Stateless request).

### مهمة ذات State (Task)

مناسبة لـ:

- Multi-step work،
- Long-running activity،
- Trackable progress،
- Authorization أو Input pauses.

يمكن لـ Server تحديد Interaction style المناسبة.

---

## 33. Task: وحدة Work ذات State

تعطي Task للعمل Long-running هوية Persistent.

من حيث الفكرة:

```text
إرسال Request (submit request)
  ↓
إنشاء Task (create Task)
  ↓
تتبع Task state (track Task state)
  ↓
استقبال Final result (receive final result)
```

يصف المصدر IDs مثل Task ID و Context ID.

Exact field names خاصة بـ Protocol وينبغي مراجعتها مقابل Current A2A specification.

## 34. دورة حياة Task (Task Lifecycle)

يصف المصدر States تشمل:

```text
submitted    # حالات المهمة في A2A
working
input-required
auth-required
completed
failed
canceled
rejected
```

### حالة الإرسال (submitted)

قبل Server الـ Request.

### حالة العمل (working)

تعالج Agent الـ Request.

### حالة الحاجة إلى Input (input-required)

تحتاج Remote agent إلى Clarification.

### حالة الحاجة إلى Authorization (auth-required)

هناك حاجة إلى Authorization إضافية.

### حالة الاكتمال (completed)

اكتمل العمل بنجاح.

### حالات الفشل أو الإلغاء أو الرفض (failed / canceled / rejected)

توقفت Task دون إكمال ناجح.

تسمح Explicit status لـ Client بتحديد ما يجب فعله لاحقًا.

## 35. Messages و Artifacts تؤديان أغراضًا مختلفة

يفصل المصدر بين Process context و Deliverables.

### رسالة Context أو Status (Message)

تشرح ما يحدث.

أمثلة:


## 37. ثلاثة Communication patterns

## 38. Request/Response و Polling

بالنسبة إلى Work قصير جدًا:

```text
Client -> طلب (Request)
Server -> نتيجة (Result)
```

بالنسبة إلى Work أطول قليلًا:

```text
Client -> طلب (Request)
Server -> حالة Working + Task ID

Client -> فحص Status
Server -> حالة Working

Client -> فحص Status
Server -> حالة Completed
```

هذا سهل Implementation.

وهو أفضل عندما تكون Task قصيرة نسبيًا.

---

## 39. Streaming باستخدام Server-Sent Events

بالنسبة إلى Generative work، يمكن لـ Server عمل Streaming لـ Partial output.

من حيث الفكرة:

```text
Client يفتح Stream (Client opens stream)
Server ترسل Chunk (Server sends chunk)
Server ترسل Chunk (Server sends chunk)
Server ترسل Chunk (Server sends chunk)
Server تعلّم Final chunk (Server marks final chunk)
```

يحسن ذلك Perceived responsiveness.

### تمييز مهم

SSE هي أساسًا Server-to-client streaming.

وليست الشيء نفسه مثل Full-duplex WebSocket architecture المستخدمة سابقًا لـ Live audio.

---

## 40. Async push باستخدام Webhooks

بالنسبة إلى Task قد تستغرق وقتًا طويلًا:

```text
إنشاء Report (generate report)
Render لـ Video (render video)
تنفيذ Deep research (perform deep research)
```

قد لا يكون إبقاء Connection مفتوحة أمرًا مرغوبًا.

Webhook flow:

```text
Client يرسل task + callback URL
Server يستجيب: submitted
يُغلق الاتصال

... لاحقًا ...

Server يستدعي webhook
Client يتحقق من الإشعار
Client يسترجع النتيجة
```

وهذه Architecture من نوع "أخبرني عندما تصبح جاهزة".

## 41. اختر Transport وفق Workload

|---|---|
| حساب سريع | استجابة مباشرة / Polling |
| Generation تدريجية | SSE streaming |
| Background job طويلة | Webhook push |

- المدة المتوقعة،
- الحاجة إلى Partial output،
- مدى تحمل Open connections،

## 42. تصبح Security اهتمامًا من الدرجة الأولى

داخل Local application واحدة، قد تثق Agents ببعضها بالفعل.

عبر Internet، تتغير Assumptions.

تحتاج إلى أن تسأل:

```text
من الذي يتصل؟ (Who is calling?)
هل Connection مشفرة؟ (Is the connection encrypted?)
ما الذي يُسمح للمتصل بفعله؟ (What is the caller allowed to do?)
هل ينبغي أن يبقى Internal implementation خاصًا؟ (Should internal implementation stay private?)
هل يمكنني الوثوق بـ Callback؟ (Can I trust the callback?)
```

يصف المصدر خمس طبقات Security.

## 43. المصادقة (Authentication)

تجيب Authentication عن:

```text
من أنت؟ (Who are you?)
```

يناقش المصدر Standard web mechanisms مثل:

- OAuth 2.0،
- OpenID Connect،
- مفاتيح API (API keys).

يمكن لـ Agent Card الإعلان عن Methods المدعومة والمطلوبة.

الهدف هو إعادة استخدام Identity standards ناضجة بدل اختراع Custom agent login system.

---

## 44. أمان Transport (Transport Security)

ينبغي أن تنتقل Sensitive agent data عبر Channels مشفرة.

من حيث الفكرة:

```text
HTTPS + TLS
```

يحمي ذلك:

- Credentials،
- User data،
- Task content،
- نواتج Artifacts.

ينبغي التحقق من Exact protocol-version requirements مقابل Current A2A guidance وإرشادات Security الخاصة بالمؤسسة.

---

## 45. Authorization و Least privilege

تحدد Authentication هوية Caller.

أما Authorization فتحدد ما يُسمح للـ Caller بفعله.

مثال:

```text
وكيل المدير:
قراءة + حذف

وكيل المتدرب:
قراءة فقط
```

يعني Principle of Least Privilege:

> امنح كل Caller الصلاحيات التي يحتاج إليها فعليًا فقط.

---

## 46. Opaque execution تحمي Internal details أيضًا

لا تحتاج Remote clients إلى الوصول إلى:

- System prompts،
- Private memory،
- Proprietary algorithms،
- إعداد Model الداخلي (Internal model configuration).

هي تحتاج إلى:

```text
المهارات (Skills)
الحالة (Status)
النتائج (Results)
```

لذلك تعمل Opaque execution بوصفها Architectural boundary و Security boundary معًا.

## 47. تحقّق من Webhook callbacks

يمكن لـ Internet-facing webhook استقبال Requests مزورة.

ولذلك فإن Notification مثل:

```text
"اكتملت المهمة"
```

لا ينبغي الوثوق بها تلقائيًا.

يناقش المصدر Verification mechanisms مثل:

- Signatures،
- أسرار مشتركة (Shared secrets).

من حيث الفكرة:

```text
Server توقع Notification (Server signs notification)
Client يتحقق (Client verifies)
قبول أو رفض (accept or reject)
```

## 50. إرشادات Design عملية

### 1. قسّم حسب المسؤولية

أنشئ Specialists ذات Purpose واضح و Behavior يمكن اختبارها بصورة مستقلة.

### 2. رمّز الترتيب الثابت داخل Workflow logic

لا تعتمد على LLM لتذكر Deterministic business sequencing.

### 3. عرّف State contracts

لكل Agent:


### 5. احتفظ بواجهة حوارية واحدة

### 6. تعامل مع Remote agents بوصفها Services

اعتمد على Public contract الخاصة بها، لا على Internal implementation.

### 7. طابق Transport مع Task

قصيرة:

```text

```

تدريجية:

```text
Stream — Streaming تدريجي
```

Long-running:

```text
Webhook — Callback غير متزامنة
```

## 74. تفاصيل Implementation الخاصة بالمصدر التي يجب إعادة فحصها

Chapter 9 هو Hands-on Early Release chapter.

قد تتغير التفاصيل التالية مع تطور A2A و SDK الخاصة بها:

- Package import paths،
- Signatures الخاصة بـ `AgentExecutor`،
- APIs الخاصة بـ `RequestContext`،
- Methods الخاصة بـ `TaskUpdater`،
- Event queue APIs،
- `A2AStarletteApplication` / `A2AFastAPIApplication`،
- `A2AClient`،
- Agent Card resolver APIs،
- Message-send helper methods،
- بنية Task/Artifact/Part objects،
- CLI commands،
- Discovery URI conventions،
- إعداد Server wrapper.

Architecture الدائمة هي:

```text
جهة Server:
بطاقة Agent (Agent Card)
+ تطبيق Protocol (Protocol application)
+ Adapter للـ Executor
+ ترجمة Task/Event

جهة Client:
الاكتشاف (Discover)
+ فحص Contract
+ الاتصال (Connect)
+ الإرسال (Send)
+ تتبع Task
+ تحليل Artifact

جهة Orchestrator:
Compose remote calls داخل Workflow
```

لا تحفظ إصدار SDK واحدًا كما لو كان هو Protocol نفسها.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "عدد أكبر من Agents يعني دائمًا System أفضل."

لا. يكون Multi-agent design مفيدًا عندما تبرر المسؤوليات و Workflow boundaries التعقيد الإضافي.

### المفهوم الخاطئ 2
> "Dynamic orchestration أفضل دائمًا من Sequential."

لا. غالبًا تكون Deterministic workflows أكثر موثوقية عندما تكون Dependencies معروفة.

### المفهوم الخاطئ 3
> "Shared state و Direct agent calls متطابقتان."

لا. تفصل Shared state تبادل Information عن Caller-to-callee arguments الصريحة.

### المفهوم الخاطئ 4
> "Sequential orchestration تعني أن Guardrails غير ضرورية."

لا. ما تزال كل Stage بحاجة إلى التحقق من وجود State المطلوبة.

### المفهوم الخاطئ 5
> "Callbacks مخصصة فقط لـ Logging."

لا. يمكنها فرض Policy، والتحقق من Tools، وتعديل Requests، وإدارة Context، و Cache للنتائج، وتجاوز Steps.

### المفهوم الخاطئ 6
> "كل Specialist في Live system ينبغي أن تتحدث إلى المستخدم."

لا. يوصي المصدر بواجهة Live واحدة مواجهة للمستخدم لهذه Architecture.

### المفهوم الخاطئ 7
> "Agent-as-a-tool هي دائمًا Final architecture."

لا. هي عملية، لكنها قد تخفي فريقًا كاملًا خلف Black-box interface واحدة.

### المفهوم الخاطئ 8
> "يتطلب A2A استخدام Framework نفسها على الطرفين."

لا. هدفه هو Cross-framework interoperability.

### المفهوم الخاطئ 9
> "Opaque execution تعني عدم وجود Status information."

لا. يمكن كشف Status من دون كشف Internal implementation.

### المفهوم الخاطئ 10
> "كل Request تحتاج إلى Stateful Task."

لا. قد تستخدم Simple interactions رسائل Direct Messages.

### المفهوم الخاطئ 11
> "Artifacts هي Files فقط."

لا. يتعامل المصدر مع Artifacts بوصفها وسيلة Deliverables، بما فيها Text أو Structured results.

### المفهوم الخاطئ 12
> "SSE و WebSockets شيء واحد."

لا. SSE هي أساسًا Server-to-client streaming، بينما تدعم WebSockets Full-duplex messaging.

### المفهوم الخاطئ 13
> "إذا وصلت Callback إلى Webhook URL الخاص بي فهي موثوقة."

لا. تحقّق من Authenticity الخاصة بها.

### المفهوم الخاطئ 14
> "Authentication تعني أن Caller تستطيع تنفيذ أي Operation."

لا. تحدد Authorization ما الذي يُسمح للـ Authenticated caller بفعله.

### المفهوم الخاطئ 15
> "تفاصيل Protocol دائمة."

لا. A2A تتطور، ولذلك ينبغي التحقق من Current specification details قبل Implementation.

---

### المفهوم الخاطئ 16
> "A2A server تتطلب إعادة كتابة Internal agent باستخدام A2A-native logic."

لا. يوضح المصدر Adapter pattern تغلف فيها AgentExecutor الـ Framework-specific agent الموجودة بالفعل.

### المفهوم الخاطئ 17
> "ينبغي أن تحتوي AgentExecutor على Domain logic الخاصة بـ Agent."

لا. دورها الرئيسي هو ربط Protocol requests/events بالـ Internal runtime الموجودة وترجمة Results مرة أخرى.

### المفهوم الخاطئ 18
> "ينبغي لـ A2A client أن تثبت Assumptions عن Remote framework داخل Code."

لا. ينبغي أن تعتمد على Agent Card و A2A contract، لا على كون Server منفذة باستخدام ADK أو LangGraph أو Framework أخرى.

### المفهوم الخاطئ 19
> "يمكن Parse لكل Remote result بوصفها Text."

لا. قد تحتوي A2A Artifacts على FilePart أو DataPart، وينبغي للـ Clients فحص Part type.

### المفهوم الخاطئ 20
> "إذا فشلت Research Assistant كاملة، فابدأ Debugging للـ Distributed workflow كلها أولًا."

لا. اعزل كل Remote Server واختبرها بصورة مستقلة قبل Debugging للـ Orchestration عبر System كلها.
