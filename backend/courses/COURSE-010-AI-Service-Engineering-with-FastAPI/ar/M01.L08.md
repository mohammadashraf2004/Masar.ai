## 1. Authentication ليست Authorization

يبدأ الفصل بالفصل بين مصطلحين كثيرًا ما يحدث خلط بينهما.

### Authentication

تسأل Authentication:

> **من أنت؟**

فهي تتحقق من أن Actor هو فعلًا الهوية التي يدّعيها.

يمكن أن تشمل Authenticators الممكنة:

- Passwords،
- Access tokens،
- Security keys،
- ادعاءات (assertions) مزوّد الهوية.

### Authorization

تسأل Authorization:

> **ما الذي يُسمح لك بفعله؟**

بعد Authentication لـ User، ما يزال على Application تحديد ما إذا كان ذلك User يستطيع تنفيذ Action مطلوبة على Resource محددة.

### تشبيه المطار

يقدم المصدر تشبيهًا مفيدًا:

```text
Authentication — التحقق من الهوية
→ تقديم Passport وإثبات من أنت

Authorization — التحقق من الصلاحية
→ امتلاك Visa/Permission المطلوبة للنشاط أو الوجهة
```

### مثال من GenAI

لنفترض أن Mohammad سجّل الدخول بنجاح إلى AI application.

قد تثبت Authentication:

```text
المستخدم الحالي = Mohammad
```

لكن Authorization ما تزال بحاجة إلى الإجابة عن أسئلة مثل:

```text
هل يستطيع Mohammad استخدام Premium model؟
هل يستطيع Mohammad قراءة Conversation 42؟
هل يستطيع Mohammad حذف Conversation تخص User آخر؟
هل يستطيع Mohammad الوصول إلى Image generation؟
هل يستطيع Mohammad إدارة User accounts؟
```

### الفرق بين 401 و 403

تمييز عملي مفيد:

```text
401 Unauthorized
→ لم يمكن Authentication للهوية

403 Forbidden
→ الهوية معروفة، لكن Action غير مسموح بها
```

النموذج الذهني الأساسي هو:

```text
Request — الطلب
  ↓
Authentication للهوية
  ↓
Authorization للـ Action المطلوبة
  ↓
التنفيذ أو الرفض
```

## 2. طرق Authentication

يقدم الفصل أربعة أساليب عامة.

### Basic authentication

تستخدم Username و Password داخل Request.

نقطة القوة:

- بسيطة في الفهم والتنفيذ.

المشكلة الرئيسية:

- تُرسل Reusable credentials مع Requests، لذلك يجب التعامل مع Mechanism بحذر شديد، ويعرضها المصدر أساسًا لسيناريوهات Prototype/Internal بدلًا من Public production use.

### Token authentication

يقوم User أولًا بعملية Authentication ويتلقى Access token.

ثم ترسل Requests اللاحقة Token بدلًا من إعادة إرسال Password.

تشمل المزايا الواردة في الفصل:

- Scalability،
- الملاءمة لـ APIs،
- Decoupling بين Services،
- Claims قابلة للتخصيص،
- تقليل Database checks المتكررة في بعض Designs.

وتشمل التحديات:

- Token storage،
- Expiry،
- Refresh،
- Revocation،
- Theft risk،
- Token size.

### OAuth

يتم تفويض Authentication/Authorization إلى External identity provider.

تشمل الأمثلة المذكورة في المصدر Providers مثل:

- GitHub،
- Google،
- Microsoft،
- Apple،
- Meta،
- LinkedIn.

يمكن أن يقلل ذلك مقدار Credential-handling infrastructure التي تمتلكها Application.

### المصادقة القائمة على المفاتيح

تستخدم Cryptographic key pairs.

يقدم الفصل الفئة لكنه لا يتعمق في Cryptographic implementation الخاصة بها.

[[IMAGE_NEEDED: Authentication methods overview | Four-column diagram for Basic credentials, token/JWT, OAuth identity provider, and public/private-key authentication, each showing the client and server interaction at a high level | Learner should recognize that authentication mechanisms prove identity in different ways]]

### اختيار Mechanism

يوصي المصدر بمراعاة:

- Security requirements،
- Project environment،
- Implementation time،
- Budget،
- الحاجة إلى External identity/resource access،
- Client type.

تعتمد Mechanism المناسبة على النظام.

## 3. Basic authentication في FastAPI

ترسل Basic authentication HTTP header بالشكل:

```text
Authorization: Basic <encoded credentials>    # ترويسة المصادقة الأساسية
```

تحتوي Credentials مفاهيميًا على:


Encoding ليست الشيء نفسه مثل Encryption.

## 4. JSON Web Tokens (JWT)

JWT هي Token format مضغوطة تُستخدم لنقل Claims بين Systems.

يقسم الفصل JWT إلى ثلاثة أجزاء:

```text
header.payload.signature
```

### Header

يصف معلومات مثل:

- Token type،
- Signing algorithm.

### Payload

تحتوي Claims.

قد تشمل Claims:

- User identifier،
- Role،
- Issuer،
- Expiration،
- Token identifier.

### Signature

تحمي Integrity الخاصة بـ Token.

تسمح Signature لـ Server باكتشاف ما إذا كانت Signed token data قد عُدلت.

[[IMAGE_NEEDED: JWT anatomy | Diagram showing a JWT split into header, payload, and signature, with example claims such as user ID, role, issuer, and expiration | Learner should notice that Base64-style encoding makes token parts compact/readable but the signature is what protects integrity]]

### JWT ليست Encryption

تمييز أساسي للمبتدئين:

```text
الترميز (encoding)
≠ التشفير (encryption)
```

لا تضع Sensitive secrets داخل Token لمجرد أنها Encoded.

### لماذا Tokens مفيدة

بعد Login:

```text
Username/Password
      ↓
يتحقق Server من Credentials
      ↓
يصدر Server Access token
      ↓
يرسل Client الـ Token في Requests اللاحقة
```

لا تحتاج Password إلى إعادة الإرسال مع كل Protected API call.

## 5. نمذجة Users و Tokens في Database

يوسع الفصل Relational database من الدرس السابق.

### بيانات User

تتضمن User entity مفاهيم مثل:

- Unique identifier،
- Email/Username،
- Hashed password،
- Account active state،
- Role،
- Created timestamp،
- Updated timestamp.

### بيانات Token

تحتوي Token entity على:

- Token identifier،
- Linked user ID،
- Expiration،
- Active/revoked state،
- IP metadata،
- Timestamps.

### علاقة One-to-many

يمكن أن يمتلك User واحد عدة Token records.

```text
User — المستخدم
 ├── Token A
 ├── Token B
 └── Token C
```

يمكن أن يدعم ذلك:

- عدة Logged-in devices،
- Login tracking،
- Token revocation.

[[IMAGE_NEEDED: User-token entity relationship | ER diagram showing users → tokens as a one-to-many relationship, with user role/hashed password and token expiry/active state highlighted | Learner should notice that token records make revocation and session tracking possible]]

### لماذا نستخدم IDs غير متوقعة؟

يستخدم المصدر UUID-style identifiers للـ Sensitive entities.

الهدف هو جعل Identifiers أصعب في التخمين مقارنة بـ Sequential public IDs البسيطة.

### Indexes و Uniqueness

ينبغي عادة فرض Unique constraint على Email/Username.

يمكن لـ Indexes تحسين Queries شائعة مثل:

```text
العثور على User عبر Email
العثور على Tokens الخاصة بـ User
العثور على Tokens عبر IP
```

## 6. لا تخزن Raw passwords أبدًا

لا ينبغي تخزين Raw password مباشرة في Database.

لماذا؟

إذا تعرضت Database للاختراق:

```text
Plaintext passwords
→ قابلة للاستخدام فورًا بواسطة Attacker
```

بدلًا من ذلك، يستخدم الفصل Password hashing.

### Hashing

تحول Cryptographic hash الـ Password إلى Representation غير قابلة للعكس.

مفاهيميًا:

```text
كلمة المرور
   ↓
دالة التجزئة (hash)
   ↓
كلمة المرور المجزَّأة
```

تتحقق Application من Login عبر Hashing/Checking للـ Password المقدمة باستخدام Password-hash algorithm ومقارنة النتيجة بالشكل المناسب.

### Hashing مقابل Encoding

```text
Base64
→ Encoding
→ قابلة للعكس

Password hashing
→ One-way cryptographic transformation
```

يجب ألا يحدث خلط بينهما مطلقًا.

## 7. إضافة Salt إلى Password hashes

Hashing وحدها ليست القصة كاملة.

إذا اختار Userان Password نفسها، فإن Naïve deterministic hash ستنتج النتيجة نفسها.

يمكن أيضًا لـ Attackers استخدام Precomputed hash databases.

تضيف **Salt** قدرًا من Randomness.

مفاهيميًا:

```text
كلمة المرور
   +
salt عشوائي
   ↓
خوارزمية تجزئة لكلمات المرور
   ↓
تمثيل تجزئة مخزَّن فريد
```

حتى Passwords المتطابقة يمكن أن تنتج Stored hashes مختلفة.

[[IMAGE_NEEDED: Password hashing and salting | Registration path showing password + random salt → password-hash algorithm → stored salted hash, and login path showing candidate password verified against the stored hash | Learner should notice that the plain password is never stored and that the salt makes identical passwords produce different hash records]]

### ما الذي لا تحله Salting

يحذر المصدر أيضًا من أن Password hashing/Salting لا تلغي كل Attack.

ومن الأمثلة:

- Password spraying،
- Credential stuffing.

ولهذا يحتاج Authentication security أيضًا إلى:

- Rate limiting،
- MFA،
- Account lockouts،
- Monitoring،
- الوعي بكلمات المرور المخترقة.

## 9. دورة حياة Token: الإصدار والتحقق والإبطال والانتهاء

لدى Token service في الفصل عدة Responsibilities.

### 1. إصدار Token

بعد Login ناجح:

```text
User تم التحقق منه
   ↓
إنشاء Token metadata
   ↓
تحديد Expiration
   ↓
توقيع JWT
   ↓
إرجاع Access token
```

### 2. فك Token والتحقق منها

عندما ترسل Request لاحقة Token:

```text
Bearer token
   ↓
التحقق من Signature
   ↓
قراءة Claims
```

يتم رفض Invalid tokens.

### 3. التحقق من Active state

يخزن المصدر Token state في Database حتى يمكن إبطال Tokens.

```text
JWT صالحة Cryptographically
        +
Database token is_active == True
        ↓
قبول
```

### 4. Expire

ينبغي أن تكون Access tokens قصيرة العمر.

يستخدم مثال الفصل Expiration window محدودة.

المبدأ هو:

> كلما قصرت المدة التي تظل فيها Stolen token مفيدة، صغرت Attack window.

### 5. Revocation

عند Logout أو Security event:

```text
token.is_active = False    # إبطال الـ token
```

ينبغي رفض أي استخدام لاحق.

### Token claims

يتضمن المصدر Claim concepts مثل:

- `exp` — Expiry،
- `iss` — Issuer،
- `sub` — معرّف الموضوع/الـ token.

يجمع الفصل:

- User service،
- Password service،
- Token service

### Registration

```text
Registration request
    ↓
التحقق من Fields
    ↓
التأكد من أن User غير موجود
    ↓
Hash للـ Password
    ↓
تخزين User
```

### Login

```text
Username/Password
    ↓
تحميل User
    ↓

    ↓
```

```text

        ↓

        ↓
```

يسمح ذلك لـ Routes أو Routers كاملة أن تعلن:


## 12. Production authentication تحتاج أكثر من Login

يحتاج Authentication system قابل للاستخدام إلى أكثر من:

```text
register    # التسجيل
login    # تسجيل الدخول
```

يحدد المصدر عدة Flows إضافية.

### Email أو Identity verification

تساعد على تقليل:

- Spam accounts،
- Automated abuse،
- Fake identities.

### Password reset

ينبغي ألا تكشف عملية Reset ما إذا كان Account موجودًا.

نمط Response عام جيد:

```text
إذا كان Account موجودًا، فسيتم إرسال Reset instructions.
```

بعد Password reset، قد تحتاج Previously active tokens إلى Revocation.

### Forced logout

يمكن لعملية Security إبطال كل Active tokens.

تكون مفيدة عندما:

- يُعتقد أن Token مسروقة،
- تم اختراق Password،
- يطلب User Logout من كل الأجهزة.

### Disable account

ينبغي ألا يتمكن Inactive account من Authentication بنجاح.

### Delete account

قد تحتاج Applications إلى حذف Personally identifying information وفق Retention requirements الخاصة بها.

### Rate-limit لمحاولات Login الفاشلة

قد تؤدي Repeated failed login attempts إلى:

- Throttling،
- Temporary lockout،
- Monitoring.

### Refresh tokens

النمط:

```text
access token قصير العمر
        +
refresh token أطول عمرًا
```

عندما تنتهي Access token:

```text
Refresh token
→ طلب Access token جديدة
```

يقلل ذلك الحاجة المتكررة لإدخال Password مع إبقاء Access tokens قصيرة العمر.

### MFA / 2FA

تضيف Verification factor أخرى.

تشمل أمثلة المصدر:

- OTP،
- Authentication apps،
- آليات التحقق عبر البريد الإلكتروني/SMS.

## 13. Attack vectors في Authentication

ينبغي تصميم Security system حول Attacks المتوقعة.

### Credential stuffing

يستخدم Attackers تركيبات Username/Password مسربة من Services أخرى.

تشمل فئات الدفاع:

- MFA،
- Rate limits،
- Monitoring،
- ضوابط كلمات المرور المخترقة.

### Password spraying

يجرب Attackers عددًا صغيرًا من Common passwords على Accounts كثيرة.

يمكن أن يتجاوز ذلك Simple per-user brute-force limits.

### Timing attacks

يحلل Attackers الزمن الذي تستغرقه Comparisons.

يقدم الفصل Constant-time comparison كتخفيف أثناء Credential checks.

### Token theft

إذا سُرقت Token، فقد يستخدمها Attacker حتى:

- تنتهي،
- أو يتم إبطالها.

وهذا يحفز:

- Short lifetimes،
- Secure storage،
- Revocation،
- تعامل حذر مع المتصفح.

### Security متعددة الطبقات

لا يحل Measure واحد كل شيء.

يجمع Design واقعي:

```text
التعامل القوي مع كلمات المرور
+ ضوابط الـ token
+ MFA
+ تحديد المعدل (rate limiting)
+ المراقبة
+ النقل الآمن
+ التفويض
```

## 14. OAuth2 و Identity providers

يقدم الفصل بعد ذلك OAuth2.

يسمح OAuth2 لـ Application بالحصول على Limited delegated access إلى Resources على Service أخرى.

ويُستخدم عادة مع **Identity provider (IDP)**.

### لماذا نستخدم Identity provider؟

بدلًا من امتلاك كل Credential flow بنفسك:

```text
Application لديك
→ تعتمد على Authentication من External provider
```

يقوم Provider بعملية Authentication للـ User ويصدر Tokens/Claims وفق OAuth flow.

### أمثلة

يذكر المصدر Identity platforms مثل:

- GitHub،
- Google،
- Microsoft،
- Apple،
- Meta،
- LinkedIn.

### OAuth يتعلّق بـ Delegated access

قد تطلب Application Scopes مثل:

```text
قراءة User profile
قراءة Email
الوصول إلى Calendar
```

يوافق User على Permissions محددة.

### Scope

تصف **Scope** ما تطلبه Application من Access.

المبدأ:

## 15. تدفق Authorization code

```text

```

### الخطوة 2 — Redirect إلى Provider

### الخطوة 6 — Code exchange

## 16. حماية OAuth باستخدام State و Redirect validation

يتضمن OAuth عمليات Redirect.

يمكن مهاجمة Redirect flows إذا لم تتحقق Application من أن Callback traffic ينتمي إلى Flow التي بدأتها هي.

### CSRF

تجعل Cross-site request forgery الـ Authenticated user ينفذ Action لم يقصدها.

في OAuth flow، قد تكون Forged أو Substituted authorization sequence خطرة بصورة خاصة.

### State parameter

يستخدم الفصل State value فريدة.

مفاهيميًا:

```text
تبدأ Application عملية OAuth
→ تولد Random state
→ تحفظ Server-associated session state
→ ترسل State إلى Provider

يعيد Provider التوجيه
→ تعود State

تقارن Application:
Returned state == Expected state؟
```

إذا لم تتطابق:

```text
ارفض Callback
```

### Redirect URI validation

ينبغي للـ Provider إعادة التوجيه فقط إلى Registered/approved callback URLs.

يساعد ذلك على تقليل Open-redirect style abuse.

### Session middleware

يعرض المصدر Server-associated session state عبر Middleware.

مبدأ مهم:

> لا تثق في Arbitrary client-provided state لمجرد أنها عادت في Cookie أو Query parameter.

### حماية Provider access tokens

يحذر المصدر من كشف Provider access token إلى Browser code دون حاجة.

Architecture مفيدة هي:

```text
Provider access token
→ تبقى Server-side

Browser
→ يتلقى Short-lived session/access credential خاصة بتطبيقك
```

يقلل ذلك Damage إذا تعرضت Application token لديك للاختراق.

[[IMAGE_NEEDED: OAuth state/CSRF protection | Two OAuth callback paths: legitimate flow where stored state matches returned state and proceeds, and attacker/forged flow where state mismatches and is rejected | Learner should notice that state binds the callback to the original login attempt]]

## 17. أنواع OAuth2 flows المقدمة في الفصل

يصف المصدر عدة OAuth2 flows.

### تدفق Authorization code

مصممة لتطبيقات بها Backend قادر على التعامل مع:

- Client secrets،
- Code exchange،
- Provider tokens.

### Authorization code + PKCE

تضيف:

```text
code_verifier
+
code_challenge
```

لحماية Authorization code من Interception.

يسلط المصدر الضوء عليها لـ Clients يصعب فيها حماية Traditional client secret، مثل Mobile applications.

### Implicit flow

يعرض المصدر هذه Flow حيث تُعاد Access token من دون Intermediate authorization-code exchange.

لهذا المقرر، تذكرها أساسًا كواحدة من Historical/available flow patterns التي يناقشها المصدر؛ وينبغي مراجعة Actual provider guidance عند تنفيذ Authentication.

### تدفق Client credentials

تستخدم لـ Machine-to-machine communication.

لا يوجد End-user login.

```text
Credentials الخاصة بـ Service A
→ Token
→ Resource في Service B
```

### تدفق Resource owner password credentials

تستبدل Credentials الخاصة بـ User مباشرة بـ Token.

لا يشجع المصدر عليها بشدة إلا في Legacy/trusted situations.

### تدفق Device authorization

مفيدة للأجهزة ذات Input capability المحدودة.

نموذج ذهني:

```text
يعرض TV رمزًا
   ↓
يفتح User موقعًا على Phone
   ↓
ينفذ Authentication
   ↓
يتلقى TV الـ Authorization
```

### جدول اختيار Flow

| السيناريو | Flow المقدمة في المصدر |
|---|---|
| تطبيق ويب يعتمد على Backend | Authorization code |
| Mobile/public client يحتاج حماية من Interception | Authorization code + PKCE |
| Service-to-service | Client credentials |
| جهاز ذو Input محدود | Device authorization |
| تبادل مباشر قديم لبيانات الاعتماد | كلمة مرور مالك المورد (Resource owner password) |
| Browser-only simplified flow التي يناقشها المصدر | Implicit |

## 18. مشكلات OAuth integration الشائعة

يسرد الفصل عدة Failures متكررة.

### Invalid redirect URI

السبب:

```text
Callback URL لا تطابق Provider configuration
```

الحل:

```text
تسجيل/Allowlist لـ Redirect URI الصحيحة
```

### بيانات اعتماد عميل غير صالحة

السبب:

- Client ID خاطئ،
- Client secret خاطئ.

### access token منتهي الصلاحية

حل ممكن:

- الحصول على Token جديدة،
- استخدام Refresh-token flow عندما تكون مدعومة.

### Missing scope

لم تطلب Application الـ Permission اللازمة للـ Resource.

### token endpoint غير صحيح

يتم إرسال Code/Token exchange إلى Provider URL خاطئ.

### مشكلات CORS

وفقًا لـ Architecture، قد تُحجب Browser requests بواسطة Provider/Browser policy.

يمكن لـ Server-side exchange تجنب كشف Sensitive OAuth operations في Browser code.

### نوع grant خاطئ

يتوقع Provider Flow/Grant configuration محددة.

### الدرس العملي

OAuth failures كثيرًا ما تكون **Configuration failures** وليست Python syntax bugs.

تحقق دائمًا من:

- Provider documentation،
- Callback URL،
- Scopes،
- Credentials،
- Token endpoint،
- Selected flow.

## 22. التحكم في الوصول القائم على العلاقات (ReBAC)

تجعل ReBAC الـ Relationships بيانات Authorization من الدرجة الأولى.


### مثال

```text

  ├── عضو: المستخدم A
  └── المحادثات الخاصة
          ├── المحادثة 1
          └── المحادثة 2
```

```text

→ يمكنه قراءة Team conversations
```

## 26. تأمين طبقة GenAI نفسها

Authentication و Authorization ليستا منفصلتين عن AI product design.

فهما تتحكمان في:

- أي Model يمكن استدعاؤه،
- أي Documents يمكن استرجاعها،
- أي Conversation يمكن قراءتها،
- أي Tools يمكن تنفيذها،
- أي Output capabilities تكون متاحة.

### Model entitlement

مثال:

```text
مستخدم FREE
→ نموذج نصي صغير

مستخدم PAID
→ نموذج نصي premium

ADMIN
→ نموذج صور تجريبي
```

### Data authorization

ينبغي ألا يسترجع RAG كل Document لمجرد أن Semantic similarity عالية.

يجب أيضًا أن تستوفي Request الـ Permissions:

```text
تطابق دلالي
        +
مستخدم مخوَّل بالمستند

سياق مؤهَّل
```

إذا اقترح Model:

```text

إرسال بريد إلكتروني
```

```text
   ↓
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Authentication و Authorization مصطلحان قابلان للتبادل.

### لماذا هذا خطأ

تثبت Authentication الهوية. أما Authorization فتحدد ما الذي يُسمح لتلك الهوية بفعله.

### المفهوم الخاطئ 2

> Base64-encoding لـ Password يجعلها Encrypted.

### لماذا هذا خطأ

Encoding قابلة للعكس ولا توفر Encryption.

### المفهوم الخاطئ 3

> JWT صالحة تعني أنه ينبغي دائمًا منح User الوصول.

### لماذا هذا خطأ

يمكن لـ Authentication إثبات الهوية، لكن Authorization ما تزال بحاجة إلى الموافقة على Action/Resource المطلوبة.

### المفهوم الخاطئ 4

> ينبغي التعامل مع JWT payload data على أنها Secret لأن Token Encoded.

### لماذا هذا خطأ

Encoding ليست Confidentiality. لا ينبغي وضع Sensitive data في Token claims لمجرد أن Token مضغوطة.

### المفهوم الخاطئ 5

> Password hashing و Salting تمنع كل Password attacks.

### لماذا هذا خطأ

هي تساعد على حماية Stored credentials، لكن Password spraying و Credential stuffing و Phishing وغيرها من Attacks ما تزال تحتاج إلى Defenses إضافية.

### المفهوم الخاطئ 6

> Long-lived token أكثر ملاءمة، لذا هي أفضل تلقائيًا.

### لماذا هذا خطأ

يزيد Lifetime الأطول الفترة التي يمكن فيها إساءة استخدام Stolen token.

### المفهوم الخاطئ 7

> Logout مجرد Frontend action.

### لماذا هذا خطأ

إذا كان Server يتتبع Revocable tokens، ينبغي أن يُبطل Logout الـ Current credential حتى تُرفض Requests المستقبلية.

### المفهوم الخاطئ 8

> يعني OAuth أن Application تحصل على Provider password الخاصة بـ User.

### لماذا هذا خطأ

ينفذ Provider عملية Authentication للـ User. وتتلقى Application Authorization artifacts مثل Codes/Tokens وفق Flow.

### المفهوم الخاطئ 9

> OAuth state مجرد Decorative metadata.

### لماذا هذا خطأ

هي تساعد على ربط Callback بـ Login flow التي بدأتها Application وتحمي من Forged authorization sequences.

### المفهوم الخاطئ 10

> يمكن تفويض Authorization بأمان إلى LLM عبر System prompt.

### لماذا هذا خطأ

يمكن مهاجمة Model instructions أو تجاوزها. يجب فرض Permissions بواسطة Trusted application logic.

### المفهوم الخاطئ 11

> يمكن لـ RBAC التعبير عن كل Permission system بصورة نظيفة.

### لماذا هذا خطأ

قد تسبب Resource relationships و Dynamic attributes حدوث Role explosion أو تتطلب Rules أدق باستخدام ReBAC/ABAC.

### المفهوم الخاطئ 12

> ReBAC و ABAC أفضل دائمًا من RBAC.

### لماذا هذا خطأ

توفران Flexibility أكبر لكنهما تزيدان Policy complexity و Data requirements و Auditing cost.

### المفهوم الخاطئ 13

> إذا نُقل Authorization logic إلى Service أخرى، لم يعد GenAI API بحاجة إلى فرض Access.

### لماذا هذا خطأ

تنتج Policy service قرارًا؛ وما تزال Resource service مطالبة بفرضه.

## احتفظ بهذه الفكرة

**أمّن خدمات GenAI على Layers: نفّذ Authentication للـ Actor، واحمِ Credentials و Tokens طوال Lifecycle الخاصة بها، واستخدم OAuth flows موثوقة عند Delegating identity، ثم نفّذ Authorization لكل Sensitive action بالاعتماد على Roles و Relationships و Attributes و Resource ownership. لا تجعل Model نفسه Security boundary مطلقًا — يجب أن تحدد Trusted application logic أي Data و Models و Tools و Actions يُسمح لكل User بالوصول إليها.**
