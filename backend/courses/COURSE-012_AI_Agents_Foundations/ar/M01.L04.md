## 1. لماذا ظهرت الأنظمة متعددة الـ Agents؟

كان أول تصور في تطوير Agents بسيطًا غالبًا: إذا استطاعت Agent واحدة حل مشكلة، فيفترض أن عدة Agents تستطيع حل مشكلة أصعب. أظهرت الأنظمة المبكرة أن هذا صحيح جزئيًا فقط.

قد تزيد Agents الإضافية القدرة، لكنها تقدم أيضًا مشكلات جديدة:

- Coordination overhead،
- المزيد من LLM calls،
- Token cost أعلى،
- Latency أطول،
- Failure points أكثر،
- Debugging أصعب،
- Behavior أقل قابلية للتوقع.

التحول المهم هو الانتقال من سؤال:

```text
"كم Agent ينبغي أن أضيف؟"
```

إلى سؤال:

```text
"أي Architecture تمنح كل Agent المسؤولية والسياق والسلطة المناسبة؟"
```

وهذا هو الموضوع الأساسي لهذا الفصل.

## 2. أسئلة Architecture الأربعة: Decision-making وControl وCommunication وCoordination

قبل اختيار Multi-agent pattern، يطلب منا الفصل التفكير في أربعة مفاهيم.

### Decision-making

Decision-making هي سلطة اختيار ما سيحدث بعد ذلك.

مثال: يمتلك Research system عشرة Sources ويجب أن يختار ثلاثة منها للتلخيص. الـ Component التي تتخذ هذا الاختيار تملك Decision.

هناك سؤالان مهمان:

1. أي Agent تملك سلطة اتخاذ القرار؟
2. ما Context التي تراها أثناء اتخاذ القرار؟

قد تؤدي Context قليلة جدًا إلى قرارات غير مستنيرة. وقد تدفن Context كثيرة جدًا الـ Signal المهمة.

### Control

Control هي سلطة تنفيذ العمل.

قد يقرر Planner ما ينبغي أن يحدث دون استدعاء أي Tool مباشرة. وقد تنفذ Worker أداة دون السماح لها باختيار Task التالية.

لذلك:

```text
Decision-making = من يختار؟
Control         = من ينفذ؟
```

### Communication

تحدد Communication المعلومات التي تنتقل بين Agents.

قد يشارك Collaborative system سياقًا مشتركًا، بينما قد تعرض Hierarchical system لكل Worker فقط المعلومات التي اختارتها Orchestrator.

### Coordination

تحدد Coordination كيف يُرتب التنفيذ عبر الزمن:

- Sequentially،
- بالتوازي،
- Hierarchically،
- عبر Revision loops،
- عبر Branching أوRouting.

هذه الأسئلة الأربعة أكثر فائدة من البدء باسم Framework.

Who acts? What context moves? How does execution proceed? | Learner should use these four questions as an architecture checklist]]

## 3. ثلاث Architectures أساسية للأنظمة متعددة الـ Agents

يعيد الفصل النظر في ثلاث Architectures رئيسية.

### Agent flow

تُرتب Agents في Sequence محدد. وينتقل Control والمعلومات من Stage إلى التالية.

```text
البحث -> التخطيط -> الكتابة
```

نقاط القوة:

- سهلة الفهم،
- سهلة التتبع،
- مناسبة للأهداف القابلة للتقسيم،
- تعقيد Central decision منخفض.

نقاط الضعف:

- Failure واحدة قد تكسر Chain كاملة،
- قد تعمل Sequence كاملة حتى عندما تكون بعض Steps غير ضرورية،
- Dynamic decision-making محدودة.

### Orchestrator

تقرر Agent مركزية أي Workers يتم استدعاؤها ومتى.

```text
               -> وكيل Research
المستخدم -> Orchestrator -> وكيل Planning
               -> وكيل Filesystem
```

نقاط القوة:

- Dynamic decision-making،
- يمكنها تشغيل Workers المطلوبة فقط،
- مناسبة للأنظمة المواجهة للمستخدم،
- يمكنها التعافي من بعض Worker failures.

نقاط الضعف:

- أصعب في البناء والتقييم،
- أخطاء Central planner تؤثر في النظام،
- تحتاج Feedback وGuardrails أقوى.

### Collaboration

تتفاعل Agents بحرية أكبر وقد تتخذ قرارات أوتنتقد أوتتفاوض بصورة مشتركة.

نقاط القوة:

- مناسبة للمشكلات الغامضة أوالاستكشافية،
- يمكنها دمج وجهات نظر متنوعة.

نقاط الضعف:

- Token usage مرتفع،
- Latency مرتفعة،
- Evaluation أصعب،
- Communication complexity أكبر.

يوصي الفصل مرارًا بالبدء بـ Flows أبسط قبل إدخال تعقيد Centralized أوCollaborative.

## 4. Hierarchy من نوع Manager-worker

تمد Manager-worker structure الـ Orchestration إلى Hierarchy.

```text
المدير
  |
  +--> مدير فرعي A -> العاملون
  +--> مدير فرعي B -> العاملون
```

تمرر Manager الأوامر إلى الأسفل. وتحتفظ Workers بالـ Control على التنفيذ داخل مسؤولياتها المخصصة.

يمكن لذلك تحسين التنظيم في الأنظمة الكبيرة، لكن كل Management level تضيف Planning cost وLatency ومكانًا جديدًا قد تُشوَّه فيه المعلومات.

لا تكون Hierarchy الأكثر تعقيدًا مفيدة إلا عندما تكون Management work نفسها ذات قيمة.

## 5. Communication patterns: أرسل فقط ما يستحق الانتقال

يشدد الفصل على أن Communication ليست مجانية.

تزيد مشاركة Context أكبر من Token cost، كما يمكن لـ Irrelevant context أن تجعل من الصعب على Model تحديد المعلومات المهمة.

فكر في Competitive-analysis system تحتوي ثلاث Research agents وSynthesis agent واحدة.

قد تحتاج كل Research worker فقط إلى:

- اسم شركة واحدة،
- Research rubric،
- مخطط المخرجات المطلوب.

ولا تحتاج بالضرورة إلى:

- Full orchestrator history،
- Partial work الخاصة بـ Sibling agents،
- كل Intermediate planning note.

لدى Synthesis agent احتياجات مختلفة: ينبغي أن تستقبل Completed research outputs.

ينتج عن ذلك ثلاث Communication strategies.

### Message passing

مرر Object أوMessage مختصرة إلى Agent التالية.

المزايا: مركزة ورخيصة وسهلة الفهم.  
العيوب: Agent التالية تعرف فقط ما مررته السابقة.

### Shared thread أوShared memory

تستطيع كل Agent رؤية Conversation history مشتركة.

المزايا: Continuity غنية وقابلية تعافٍ.  
العيوب: Token usage متزايدة وContext dilution.

### التواصل عبر الأدوات

يمكن لـ Agent كشف Agent أخرى أوCapability عبر MCP أوFunction-like interface.

المزايا: Interface منظمة وضيقة.  
العيوب: لكل Exchange تكلفة Tool-call إضافية.

| Pattern | وضوح المعلومات | الفائدة الأساسية | التكلفة الأساسية |
|---|---|---|---|
| Message passing | Data مختارة صراحة | Focus واستخدام Tokens أقل | إغفال Upstream قد يضر Downstream work |
| Shared thread | Shared history واسعة | Context غنية | Cost وContext dilution |
| Tool exchange | Interface مضبوطة بـ Schema | حدود واضحة | Call/Protocol overhead إضافية |

## 6. نظرة عامة على Coordination strategies

لا تقتصر الأنظمة متعددة الـ Agents على Chain بسيطة. يصف الفصل عدة طرق لتنسيق التنفيذ.

### Sequential pipeline

تعمل Agents واحدة بعد أخرى. استخدم ذلك عندما تعتمد Stages اللاحقة فعلًا على Outputs السابقة.

### Parallel delegation

تعمل Subtasks مستقلة في الوقت نفسه ثم تُدمج لاحقًا.

### Hierarchical coordination

تنفذ Manager تخطيطًا حقيقيًا، وتُسند Roles مختلفة، وتراقب العمل، وتوفق بين Results.

### Iterative critique أوRefinement

تنشئ Worker Output، ثم تقيمها Critic، وتتكرر العملية حتى يتحقق Quality condition أويتم الوصول إلى Maximum rounds.

### Debate

تتحدى Agentان أوأكثر من Peer agents مقترحات بعضها وتحاول الوصول إلى تقارب.

### Voting / Best-of-N

يتم توليد عدة Candidate solutions ثم تختار Vote أوJudge من بينها.

### التعاون القائم على لعب الأدوار

تتبنى Agents أدوارًا متكاملة مثل Client/Developer أوTeacher/Student وتحسن Task عبر Interaction.

### Conditional routing

تصنف Router الـ Input وترسلها إلى Specialized agent أوWorkflow.

### شبكة ندّ لندّ (Peer-to-peer)

تتواصل Agents دون Central leader وتنسق بصورة Decentralized.

## 7. التنفيذ Sequential مقابل Parallel

أسهل قرار Coordination هو تحديد ما إذا كان العمل Dependent أوIndependent.

### Sequential صحيح عندما توجد Dependency

```text
توليد البيانات -> تحليل البيانات -> تلخيص التحليل
```

لا يمكنك تحليل Data لم يتم إنشاؤها بعد.

Sequential pipelines سهلة الفهم، لكنها تحمل ثلاث تكاليف مهمة:

1. **Latency:** يتراكم Total time عبر Stages.
2. **Fragility:** Failure واحدة قد توقف Pipeline.
3. **Limited revision:** يكون Flow باتجاه واحد طبيعيًا ما لم تُضف Revision logic.

### Parallel صحيح عندما تكون Tasks مستقلة

```text
            -> تحليل النص ---\
المدخل -----> تحليل الصورة ----> دمج
            -> تحليل الصوت ---/
```

يمكن لـ Parallel execution تقليل Wall-clock time، لكنها تضيف Merging وSynchronization work.

اختبار مفيد هو:

> هل تحتاج Task B إلى Result من Task A لكي تبدأ؟

إذا كانت الإجابة نعم، فأبقِ Dependency Sequential. وإذا كانت لا، فقد يكون Parallel execution مناسبًا.

## 8. Parallel flow ليست هي نفسها Hierarchical coordination

قد يبدو Patternان متشابهين لأن كليهما يمكن أن يعرض Component واحدة فوق عدة Workers.

الاختلاف هو مقدار Intelligence الموجودة في Manager.

### التفرّع المتوازي البسيط

تقسم Component مهمة موحدة، وتشغل Workers، ثم تدمج Results.

```text
تقسيم -> العاملون -> تجميع
```

غالبًا يمكن استبدال Central step بـ Fan-out/Fan-in code عادية.

### Hierarchical coordination

تنفذ Orchestrator تخطيطًا ذا معنى:

- تختار Subtasks مختلفة،
- تسند Role-specific instructions،
- تشرف على التنفيذ،
- توفق بين Conflicting outputs،
- تعدل Plan.

اختبار مفيد من الفصل هو:

> إذا كان من الممكن استبدال Orchestrator بـ Split-and-merge primitive بسيطة، فهي على الأرجح Parallel flow وليست Hierarchical coordination حقيقية.

## 9. Critique وDebate وRefinement loops

تكون Revision loops مفيدة عندما لا تكون أول Answer معقولة جيدة بما يكفي.

### حلقة العامل والناقد غير المتماثلة

```text
العامل -> المرشَّح -> الناقد
  ^                    |
  |------ تغذية راجعة ----|
```

تملك Critic سلطة قبول Output الخاصة بالـ Worker أو رفضها.

يناسب ذلك Tasks ذات Quality bar قابلة للقياس، مثل:

- Code يجتاز Tests،
- Plan تحقق Rubric،
- Response تستوفي Formatting constraints.

### Symmetric debate

تقترح Peer agents أفكارًا وتتحداها دون وجود Authority ثابتة واحدة.

يمكن لذلك المساعدة عندما تكون Task استكشافية أوغامضة.

### Stopping conditions أساسية

تحتاج كل Revision loop إلى Exit condition مثل:

- Maximum rounds،
- Critic approval،
- Convergence،
- عدم وجود Meaningful change.

من دون Hard maximum، يمكن لـ Agent loop استهلاك Tokens بلا نهاية.

## 10. Ensembles وRouting وRole-play وPeer networks

### Voting أوBest-of-N

أنشئ عدة Answers واختر واحدة باستخدام Majority vote أوWeighted voting أوJudge.

لا يفيد ذلك إلا إذا قدمت Candidates تنوعًا ذا معنى. قد تعيد عدة Agents متطابقة تستخدم Prompts متطابقة إنتاج الخطأ نفسه.

### التعاون القائم على لعب الأدوار

تنشئ Roles المتكاملة Interaction مفيدة. يمكن لـ Client agent توضيح Requirements بينما تنفذ Developer agent هذه Requirements.

يضيف Pattern قيمة محدودة إذا كانت Roles لا تقدم معلومات مختلفة.

### Conditional routing

تختار Router أي Expert ينبغي أن يتعامل مع Input.

```text
طلب المستخدم -> الموجِّه -> وكيل الفوترة
                      -> وكيل الدعم التقني
                      -> وكيل الشؤون القانونية
```

يكون Routing مفيدًا عندما يكون توزيع Tasks غير متجانس. ويصبح غير ضروري عندما تستطيع General agent واحدة التعامل بكفاءة مع كل Inputs.

### شبكة ندّ لندّ (Peer-to-peer)s

تتواصل Peers دون Central coordinator. يمكن لذلك تحسين Robustness، لكنه يجعل Global control وDebugging وConflict resolution أصعب.

## 11. Agency مقابل ملكية النظام

تحتاج Agent systems إلى قدر كافٍ من الحرية لاتخاذ قرارات مفيدة، لكن Unrestricted autonomy نادرًا ما تكون مناسبة لـ Production systems.

يصور الفصل Agency وConstraint كطيف.

### Lower-stakes work يمكنه تحمل Agency أكبر

تشمل الأمثلة Exploratory analysis وDraft-quality internal research.

### Higher-stakes work يحتاج حدودًا أقوى

تشمل الأمثلة:

- Irreversible actions،
- Customer-facing outputs،
- Regulated workflows،
- Production changes.

تشمل Constraint points المفيدة:

- Allowed tools،
- Output schemas،
- Action budgets،
- Deterministic business rules،
- Human approval.

استراتيجية عملية هي البدء بأقل Autonomy لازمة ثم توسيع الحدود فقط بعد إثبات Reliability.

## 12. متى ينبغي أن تتحول Agent واحدة إلى Flow؟

غالبًا ما تكون Agent واحدة هي نقطة البداية الصحيحة. يصبح Decomposition مفيدًا عندما تبدأ Agent في التحميل الزائد.

يحدد الفصل ثلاث Signals قوية.

### Overload

تمتلك Agent Tools كثيرة جدًا أوInstruction text كبيرة جدًا أوTool descriptions متداخلة.

### Specialization

تستفيد أجزاء مختلفة من Task من Roles مركزة.

### Cost وLatency

يمكن لـ Specialized agent استقبال Prompt أصغر وTool list أصغر وContext أضيق.

افترض أن Research assistant واحدة تملك حاليًا:

- Research-source tools،
- Planning tools،
- Filesystem tools.

Decomposition طبيعي هو:

```text
وكيل Research -> وكيل Planning -> وكيل Filesystem
```

أصبحت كل Agent تملك الآن مسؤولية أساسية واحدة.

## 15. ثلاث طرق لتمرير العمل بين Agents

يعرض الفصل ثلاث Communication styles عامة لـ Agent flows.

### تدفق المحادثة المشترك

تعمل Agents على Shared thread واحدة.

الفائدة: Continuity تلقائية.  
التكلفة: قد ترى كل Agent Noise لا تحتاج إليه.

### Explicit pass-off داخل Code

تتحكم Application بدقة فيما يتم إرساله إلى كل `Runner.run(...)` call.

الفائدة: Maximum control.  
التكلفة: Orchestration code أكثر.

### SDK handoffs

تنقل Framework الـ Control بين Agents configured.

الفائدة: Manual transition code أقل.  
التكلفة: تصبح Relationships أكثر Implicit ويجب أن تعرف Agents Handoff targets الخاصة بها.

يعتمد الاختيار الصحيح على ما إذا كنت تعطي الأولوية لسرعة Development أوFine-grained control.

## 19. Guardrails هي Semantic circuit breakers

Guardrail أكثر من Content filter. يتعامل معها الفصل بوصفها Control يمكنها إيقاف التنفيذ قبل أن تنتقل Result غير صالحة أوخطرة إلى أجزاء أخرى من النظام.

قد تقوم Guardrails بالتحقق من:

- User input،
- Agent output،
- Transfer بين Agents،
- حدّ الإجراءات عالية المخاطر.

### استخدم أرخص Validation موثوقة أولًا

يميز الفصل بين عدة Validation layers.

#### Deterministic checks

- Schemas،
- Type checks،
- Assertions،
- Business-rule predicates،
- Pattern matching.

استخدمها عندما يمكن التعبير عن Rule بدقة.

#### Small classifiers

مفيدة للمخاطر المنظمة مثل PII أوToxicity أوPrompt-injection detection.

#### LLM guardrails

مفيدة عندما تكون Rule Semantic أوFuzzy، مثل: «هل هذه Plan مفصلة بما يكفي؟»

تضيف LLM-based validation Model calls وLatency وCost، كما يمكن للـ Validator أن تخطئ أيضًا. لذلك لا ينبغي أن تستبدل تلقائيًا Deterministic checks الأرخص.

```text
      |

وكيل Guardrail
      |

      +--> تفعيل الحاجز
```

## 22. ثلاث حالات فشل مهمة عند Handoffs

حدود Agents هي حدود Security وReliability.

يسلط الفصل الضوء على ثلاث Failure modes متكررة.

### Shape failure

ترسل Agent بيانات ببنية لا تتوقعها Agent المستقبلة.

المعالجة: Typed schemas وValidation.

### Context leakage

يتم تمرير قدر أكبر من اللازم من Upstream history أوInternal planning أوIrrelevant context إلى Agent التالية.

المعالجة: Explicit pass-off objects وMinimal context.

### Instruction injection

تحتوي Tool result أوAgent output في Upstream على Text تتعامل معها Agent المستقبلة على أنها Authoritative instructions.

المعالجة: تعامل مع Transferred content كـ Untrusted data، وتحقق من High-risk boundaries، وافصل System instructions عن Payload data.

تستحق High-stakes handoffs أقوى Validation، خصوصًا قبل Writes أوSends أوDeletes أوأي Irreversible actions أخرى.

## 25. Playbook عملية للـ Architecture

عند تصميم Multi-agent system، مر بهذه الأسئلة بالترتيب.

### Step 1 — ابدأ بـ Agent واحدة

لا توزع العمل ما لم يكن لديك سبب حقيقي.

### Step 2 — حدد Overload أوRoles الطبيعية

قسّم المسؤوليات عندما تكون Prompts أوTools أوObjectives مختلفة بوضوح.

### Step 3 — اختر Communication boundary

مرر فقط المعلومات التي تحتاج إليها كل Worker.

### Step 4 — حدد أين توجد Authority

من يختار Step التالية؟ ومن يُسمح له بتنفيذها؟

### Step 5 — استخدم Deterministic code للـ Hard rules

لا تطلب من LLM فرض Rule احتماليًا عندما يستطيع Code عادي فرضها بدقة.

### Step 6 — استخدم Types في Handoffs

اجعل Outputs قابلة للتحقق آليًا قبل أن تصبح Downstream inputs.

### Step 7 — أضف Traces مبكرًا

راقب ما يحدث فعلًا بدل الاستنتاج من Code فقط.

### Step 8 — احمِ High-risk boundaries

تحقق من Writes وSends وIrreversible actions وData التي تعبر Trust boundaries.

### Step 9 — ضع حدودًا لـ Retries وBudgets

تحتاج كل Loop إلى Stopping condition.

### Step 10 — لا تضف Orchestration إلا إذا كانت تحل Limit حقيقية

يجب أن تتبع Architecture المشكلة، لا الرغبة في استخدام Agents أكثر.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Agents أكثر تعني Quality أفضل تلقائيًا

> Agents الأكثر تضيف أيضًا Communication وCost وLatency وFailure modes.

استخدم Agents إضافية فقط عندما توفر Specialization أوParallelism أوRouting أوEvaluation أوCoordination قيمة حقيقية.

### المفهوم الخاطئ 2: Decision-making وControl هما الشيء نفسه

> قد تقرر Agent دون أن تنفذ، أوتنفذ دون أن تختار ما سيحدث بعد ذلك.

فصل هاتين السلطتين أداة معمارية قوية.

### المفهوم الخاطئ 3: مشاركة كل Context هي الأكثر أمانًا

> Context الزائدة تزيد Cost ويمكن أن تقلل Focus.

أرسل لكل Agent الـ Context المطلوبة لمسؤوليتها.

### المفهوم الخاطئ 4: Handoff callback هي Guardrail

> Callback تراقب؛ Guardrail تفرض.

استخدم Mechanism المناسبة للمهمة.

### المفهوم الخاطئ 5: LLM guardrails أفضل دائمًا من Code checks

> Deterministic rules أرخص وأكثر موثوقية عندما تكون Condition صريحة.

استخدم Semantic LLM validation فقط عندما يكون الفهم مطلوبًا فعلًا.

### المفهوم الخاطئ 6: ينبغي أن تستمر Retries حتى تنجح Agent

> Unbounded retries تنشئ Cost وLatency خارج السيطرة.

تحتاج كل Retry loop إلى Maximum ومسار Failure واضح.
