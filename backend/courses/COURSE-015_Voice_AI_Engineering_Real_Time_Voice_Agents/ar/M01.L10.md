# تقييم Live Agents وإدارة Tools على نطاق واسع

> **الدرس:** M01.L10  
> **مواءمة المصدر:** الفصلان 16 و17 من مواد Early Release المورَّدة.  
> يربط هذا الدرس بين جانب الجودة في AgentOps وجانب حوكمة Tools.

---

## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح سبب كون Evaluation لـ Live Agent مستقل أكثر تعقيدًا من اختبار برمجيات deterministic أو LLM ثابت.
- شرح سبب ضرورة أن تبدأ Evaluation لـ Live Agent بالاستدلال الأساسي وسلوك Tool قبل جودة الصوت.
- بناء Golden record أحادي الدور يتضمن Tool المتوقعة، وparameters، ونتيجة Tool، والاستجابة النهائية.
- تقييم الاختيار الصحيح لـ Tool، وparameters الصحيحة، وسلوك no-tool الصحيح، وسلوك clarification، والاتساق.
- شرح Trajectory evaluation ولماذا لا تكفي جودة الاستجابة النهائية وحدها.
- شرح دور Autoraters وAdaptive Rubrics.
- تقييم Grounding بين نتائج Tool والاستجابات النهائية.
- تتبع المقاييس التشغيلية مثل تكلفة tokens، وlatency، وأحجام runtime/tool payload المفرطة.
- توسيع Golden dataset من Tool call واحدة إلى Trajectory متوقعة متعددة الخطوات.
- تقييم كفاءة Tool chain وسلوك circuit breaker وحدود الخطوات.
- تقييم Short-term memory من حيث صلة الموضوع والالتزام به.
- تقييم تلخيص Long-term memory واسترجاعها.
- شرح سبب كون استرجاع Long-term memory أيضًا مشكلة RAG evaluation.
- استخدام Simulator agents لتوليد تفاعلات Evaluation متنوعة على نطاق واسع.
- شرح سبب كون Simulator ممثلًا وليس حكمًا.
- تنظيم مقاييس Evaluation ضمن جودة generation/grounding، وtrajectory/execution، وmemory/context، والصحة التشغيلية.
- ربط إخفاقات المقاييس بأدوات التحسين مثل prompt optimization، وcontext engineering، وتحسين Tool schema، واختيار Model.
- دمج Evaluation في staging وCI/CD بوصفها بوابة deployment.
- شرح Evaluation الصوتية المعتمدة على transcript وحدودها.
- شرح سبب الحاجة إلى Evaluation مباشرة للصوت الخام من أجل emotion، وprosody، وhesitation، وديناميكيات المحادثة.
- شرح كيف يمكن لـ Simulators المدعومة بـ TTS توليد صوت اختباري يتضمن emotion وضوضاء خلفية.
- تقييم سلوك interruption/barge-in باستخدام latency، وcontext switching، وcontext retention.
- شرح رؤية المصدر بأن monitoring هي Evaluation في الوقت الحقيقي.
- تحديد متى ينبغي تشغيل مجموعة Evaluation الكاملة.
- شرح كيف تتحول user feedback إلى بيانات Golden Evaluation أغنى عند دمجها مع logs، وmemory، وTool trajectories.
- تصنيف Tools المؤسسية إلى Code Functions، أو Local VPC REST APIs، أو Public REST APIs.
- مقارنة مفاضلات latency، والملكية، وقابلية المشاركة، وmonitoring، والأمان، وversioning بين فئات Tools.
- شرح سبب تحوّل Tool Registry إلى مصدر حقيقة واحد.
- تعريف الوظائف الأساسية لـ Registry: metadata، وversioning، وsearch/discovery، وaccess control، وrobustness، وlineage، وauditability.
- مقارنة Generalist agents ذات الوصول الكامل إلى Registry مع Specialist agents ذات Tool Lists المنسقة.
- شرح سبب إمكان تحسين الأداء، وقابلية التنبؤ، والاختبار، والأمان عند تقليل مساحة البحث عن Tools.
- شرح Dynamic Tool Search بوصفه حلًا وسطًا بين التصاميم Generalist بالكامل وSpecialist الثابتة.
- شرح كيف يمكن أن تظل Tools موزعة بينما تبقى Registry/governance مركزية.
- تصميم مستودع Tools موحد يحتوي على tests وautomated registration.
- شرح استراتيجية API-first في المصدر لتحويل Code/Data Tools إلى خدمات محكومة.
- شرح كيف يمكن لـ MCP توحيد discovery وinvocation فوق deployment المعتمد على الخدمات.
- مقارنة النماذج التنظيمية decentralized وcentralized وfederated لحوكمة Tools.
- شرح سبب وجوب تغذية نتائج Evaluation لحوكمة Tool Registry، ولماذا ينبغي أن تُحسّن قيود Registry نتائج Evaluation.

## 1. لماذا تختلف Evaluation لـ Live Agents

غالبًا ما تسأل اختبارات البرمجيات التقليدية:

```text
هل أعادت هذه الدالة deterministic النتيجة المتوقعة؟
```

أما Evaluation لـ LLM ثابتة فتسأل شيئًا أكثر مرونة:

```text
هل طابقت المخرجات المُولَّدة المعنى المقصود؟
```

لكن Live Agent مستقل يضيف أبعادًا أكثر بكثير:

```text
الاستدلال (reasoning)
اختيار Tool
Tool parameters
تنفيذ متعدد الخطوات
memory
latency
الصوت (voice)
emotion
interruptions
السلوك في الوقت الحقيقي
```

يصف المصدر هذا التحول بأنه الانتقال من تقييم إجابة ثابتة إلى تقييم أداء حي.

### المبدأ الأساسي

> قيِّم Agent كنظام، لا كمُولِّد نص فقط.

## 2. جودة الصوت لا يمكنها إنقاذ استدلال سيئ

تخيل Math Tutor:

- يبدو ودودًا،
- يكتشف الإحباط،
- يستجيب فورًا،

لكنه يعطي معادلة هندسية خاطئة.

ما يزال النظام قد فشل.

لذلك ينبغي أن تبدأ Evaluation بـ:

```text
الذكاء الأساسي
صحة Tool
Trajectory
Grounding للإجابة النهائية
```

قبل الانتقال إلى:

```text
prosody
emotion
الضوضاء (noise)
barge-in
```

### القاعدة

> ثبّت الصحة المعرفية أولًا قبل تحسين واقعية المحادثة.

## 3. Evaluation أحادية الدور بوصفها الأساس

الدور الأحادي البسيط يكون:

```text
يسأل المستخدم
   ↓
يختار Agent أداة (Tool)
   ↓
تُنفَّذ Tool
   ↓
يجيب Agent
```

يقسم المصدر Evaluation الصارمة إلى تسلسل يبدأ باختبارات البرمجيات المعتادة وينتهي بالقياسات التشغيلية.

تسميات الخطوات الدقيقة أقل أهمية من الفكرة الطبقية:

```text
صحة Tool
→ التوقع Golden
→ Trajectory
→ الإجابة النهائية
→ الجودة التشغيلية
```

## 4. ابدأ باختبارات Unit Tests العادية لـ Tool

لا تبدأ Evaluation من LLM.

إذا كانت Tool معطلة، فلا يستطيع Agent التعويض عنها بصورة موثوقة.

مثال:

⟦CODE_0⟧

ينبغي أن تعيد النتيجة deterministic المتوقعة قبل أن تُعطى Tool إلى Agent أصلًا.

ينبغي أن تتحقق Unit tests من:

- منطق الدالة،
- parameters،
- تنسيق المخرجات،
- edge cases،
- سلوك الأخطاء.

يمنحك هذا ثقة بأن الإخفاقات اللاحقة هي بالفعل إخفاقات Agent وليست bugs برمجية أساسية.

## 5. مجموعة البيانات المرجعية (Golden dataset)

قد يحتوي سجل Evaluation العادي لـ chatbot على:

```text

المخرج المتوقع
```

لكن Golden record لـ Agent ينبغي أن يلتقط معلومات أكثر.

بنية مثال:

ويصبح هذا هو ground truth لمسار التنفيذ بالكامل.

### لماذا هذا مهم

يمكنك الآن التمييز بين:

```text
خطأ في اختيار Tool
خطأ في parameters
فشل Tool
خطأ Grounding
خطأ Generation
```

بدلًا من اعتبار كل فشل مجرد "Model أعطى إجابة سيئة".

## 6. تقييم المسار (Trajectory evaluation)

تسأل Trajectory evaluation:

> هل اتخذ Agent الإجراءات الصحيحة في طريقه إلى الإجابة؟

يؤكد المصدر عدة مقاييس.

### نجاح اختيار Tool

هل اختار Tool الصحيحة؟

### نجاح parameters

هل استخرج parameters ونسقها بصورة صحيحة؟

### نجاح no-tool

هل تجنب Tools غير الضرورية عندما كانت الاستجابة العادية كافية؟

### نجاح clarification

هل طلب المعلومات الناقصة بدلًا من اختلاقها؟

### الاتساق

هل يؤدي الإدخال نفسه إلى سلوك مستقر عبر التشغيلات المتكررة؟

تخبرك هذه المقاييس *أين* يفشل الاستقلال الذاتي.

## 7. قرار "No tool" قد يكون صحيحًا أيضًا

لنفترض أن المستخدم قال:

```text
"مرحبًا."
```

سيكون Tool call غير ضروري.

لذلك يجب أن تتضمن Evaluation توقعات سلبية:

```text
expected_tool = none — لا توجد Tool متوقعة
```

وهذا يمنع Agent من تطوير عادة استخدام Tools لمجرد أنها موجودة.

وينطبق المبدأ نفسه عندما لا يقدّم المستخدم معلومات كافية.

أحيانًا يكون الإجراء التالي الصحيح هو:

```text
اطلب سؤال توضيحي (ask a question)
```

وليس:

```text
خمّن argument
```

---

## 8. قيّم سلوك Clarification

المستخدم:

```text
"ما المساحة؟"
```

الـ parameter المطلوبة:

```text
radius — نصف القطر
```

ينبغي لـ Agent قوي أن يتعرف على القيمة المفقودة ويطلب clarification.

أما Agent ضعيف فقد:

- يختلق radius،
- يستدعي Tool باستخدام arguments غير صالحة،
- ينتج إجابة ملفقة وواثقة.

### هدف Evaluation

ينبغي أن تمثل Dataset الخاصة بك صراحةً الحالات التي يكون فيها السلوك المتوقع:

```text
لا تستدعِ Tool بعد
اطلب المعلومات الناقصة
```

## 9. قيّم الإجابة النهائية بعد Trajectory

بعد تقييم مسار Tool، قيّم الاستجابة النهائية.

تتضمن الأساليب المفيدة في المصدر:

- semantic similarity،
- مقاييس خاصة بالمهمة،
- LLM-as-a-judge/Autorater.

الهدف هو التحقق مما إذا كانت الإجابة النهائية:

```text
تطابق المعنى المقصود
تستخدم نتيجة Tool
تبقى Grounded
تفي بتوقعات الجودة
```

## 10. المقيمون الآليون (Autoraters)

Autorater هو Model/Agent آخر يُستخدم كمُقيِّم.

بدل exact string matching، يمكنه الحكم على أبعاد مثل:

```text
مدى المساعدة (helpfulness)
النبرة (tone)
القيمة التعليمية
Grounding
factuality
```

تكون Autoraters مفيدة عندما توجد مخرجات صحيحة متعددة.

وينبغي إعطاؤها:

- معايير صريحة،
- تعليمات scoring واضحة،
- أمثلة Evaluation عند الحاجة.

---

## 11. معايير التقييم التكيفية (Adaptive Rubrics)

يطبق rubric ثابت المعايير نفسها في كل مكان.

أما Adaptive Rubric فيغير التركيز بناءً على المهمة.

مثال:

### طلب Code generation

ضع وزنًا أكبر على:

```text
الصحة (correctness)
الكفاءة (efficiency)
قابلية التنفيذ
```

### طلب شرح إبداعي

ضع وزنًا أكبر على:

```text
التفاعل (engagement)
الوضوح (clarity)
النبرة (tone)
```

يعرض المصدر المعايير التكيفية بوصفها وسيلة لإبقاء Evaluation ذات معنى عبر intents مختلفة جدًا لـ Agent.

## 12. قيّم Grounding مقابل نتائج Tool

لنفترض أن calculator أعاد:

```text
78.54
```

ينبغي أن تستخدم الإجابة النهائية هذه القيمة.

Agent الذي يتجاهل Tool ويخمن قد فشل، حتى إذا بدت الإجابة المخمنة معقولة.

لذلك يسأل مقياس Grounding:

```text
إلى أي مدى تدعم Tool/context التي تم استرجاعها فعليًا الاستجابة النهائية؟
```

هذا ضروري لـ Agents التي تأتي قيمتها من قدرات خارجية.

## 13. المقاييس التشغيلية جزء من الجودة

قد يكون Agent صحيحًا لكنه غير قابل للاستخدام.

تتبع:

### التكلفة

Input/output tokens وإجمالي تكلفة التفاعل.

### Latency

كم ينتظر المستخدم.

### حمولة وقت التشغيل/السياق

حجم البيانات التي تعيدها Tools إلى runtime الخاص بـ Agent.

مثال على فشل:

```text
تعيد database tool مليار صف
```

فقط لحساب متوسط بسيط.

قد يؤدي ذلك إلى إرهاق:

- context window،
- container memory،
- الشبكة،
- ميزانية latency.

### القاعدة

> حجم مخرجات Tool هو أيضًا مقياس تشغيلي.

## 16. قيّم كفاءة Trajectory

لنفترض أن المسار Golden يحتاج إلى:

```text
3 tool calls — ثلاث استدعاءات Tool
```

لكن Agent يستخدم عادة:

```text
7 tool calls — سبع استدعاءات Tool
```

قبل النجاح.

قد يكون صحيحًا وظيفيًا لكنه غير كفء تشغيليًا.

مقاييس مفيدة:

```text
متوسط عدد الخطوات
Tool calls غير الضرورية
الفشل قبل حد max-step
معدل loop/circuit-breaker
```

يحمي maximum-step guard من دخول Agents في loops إلى الأبد.

## 17. قيّم Short-term memory

تعتمد Agents متعددة الأدوار على memory للجلسة الحالية.

قيّم:

### صلة الموضوع

هل state المخزنة مرتبطة بالمحادثة الفعلية؟

### الالتزام بالموضوع

هل يظل Agent على موضوع المستخدم الجاري؟

مثال:

إذا أمضى الطالب الجلسة في algebra، فلا ينبغي أن تصبح memory مهيمنًا عليها حقائق تاريخية غير مرتبطة.

يقترح المصدر استخدام evaluators لفحص Short-term memory في نهاية الجلسة.

---

## 18. قيّم تلخيص Long-term memory

لا تحفظ Agents المستمرة كل transcript خام بصورة عمياء.

قد تلخص جلسة إلى memory مفيدة.

مثال على تحديث profile:

```text
تم الإتقان: right triangles
نقطة الضعف: area formulas
التفضيل: visual real-world examples
```

سؤال Evaluation:

> هل التقط ملخص memory المعلومات المهمة بدقة؟

قارن memory المُولَّدة مع profile Golden.

قد يجعل الملخص الضعيف personalization المستقبلي أسوأ من عدم وجود memory أصلًا.

---

## 19. قيّم استرجاع Long-term memory

عندما يعود المستخدم لاحقًا، يجب على النظام استرجاع التاريخ الصحيح.

هذه مشكلة retrieval.

لذلك تتضمن Evaluation لـ Long-term memory أسئلة بأسلوب RAG:

```text
هل تم استرجاع memory الصحيحة؟
هل تم ترتيب التاريخ ذي الصلة جيدًا؟
هل تم استبعاد التاريخ غير ذي الصلة؟
```

يذكر المصدر أدوات متخصصة لـ retrieval evaluation بوصفها أمثلة.

تعامل مع أسماء Tools الدقيقة وscores على أنها خاصة بالمصدر وحساسة للزمن.

## 20. جودة Memory تشمل Latency

لا تكفي memory الصحيحة إذا استغرق استرجاعها وقتًا طويلًا جدًا.

يتوقع المستخدم العائد إلى live tutor استعادة context بسرعة.

لذلك قيّم:

```text
دقة retrieval
retrieval latency
payload size
```

ينبغي لـ Memory أن تحسن responsiveness، لا أن تجمد المحادثة.

## 22. اضبط سلوك Simulator

يصف المصدر مدخلات مثل:

### Target Agent

أي Agent يتم اختباره.

### Scenario

ما الهدف/المشكلة التي يجب تمثيلها.

### Context/persona

مثال:

```text
طالب في الصف العاشر (10th grade)
درجة منخفضة في الهندسة
يفضّل التعلّم البصري
```

### Turn limit

Single-turn أو multi-turn محدود.

### مؤشر تاريخي اختياري

يُستخدم لاختبار الاستمرارية عبر الجلسات السابقة.

تسمح هذه المدخلات للفرق بإنتاج variants منهجية بدل chats عشوائية.

## 23. Simulator ممثل وليس الحكم

هذا التمييز بالغ الأهمية.

يقوم Simulator بـ:

```text
تمثيل السيناريو
تسجيل التفاعل
```

ولا يقرر ما إذا كان Target Agent قد نجح.

تُنفَّذ Evaluation لاحقًا بواسطة:

- metrics،
- Autoraters،
- human reviewers،
- أنظمة Evaluation أخرى.

يقلل فصل الممثل عن الحكم الالتباس المفاهيمي.

## 24. أربع فئات لـ Evaluation

يجمع المصدر العديد من المقاييس في أربع مجموعات.

### 1. جودة Generation وGrounding

أمثلة:

- semantic similarity،
- factuality،
- safety،
- المعلومات Grounded.

### 2. Trajectory وExecution

أمثلة:

- دقة Tool،
- دقة parameters،
- سلوك no-tool،
- سلوك clarification،
- كفاءة الخطوات.

### 3. Memory وContext

أمثلة:

## 27. Live voice يغيّر مشكلة Evaluation

## 34. ثلاثة مقاييس لـ Interruption

### Barge-in latency

ما مدى سرعة توقف Agent عن الكلام؟

### Context retention

بعد الإجابة عن interruption، هل يتذكر الهدف الأصلي؟

تقيس هذه المقاييس الثلاثة ما إذا كانت interruption سلسة بدل أن تكون مدمرة.

## 41. دوال الكود (Code Functions)

تعمل Code Functions بالقرب من Agent.

المزايا:

```text

```

نقطة الضعف:

```text
قابلية مشاركة ضعيفة
```

- shared libraries،
- نشر الخدمة داخل containers.

## 42. واجهات Local VPC REST APIs

تعرض Internal APIs خدمات مملوكة للمؤسسة عبر حد شبكي.

المزايا:

- قابلية مشاركة أفضل،
- authentication مركزي،
- monitoring قياسي،
- ملكية خدمة واضحة.

المفاضلة:

```text
بنية تحتية أكثر
network latency
```

وغالبًا ما تكون واجهة مؤسسية جيدة للقدرات الداخلية.

## 43. واجهات Public REST APIs

يوفر المزودون الخارجيون قدرات مثل:

- الطقس،
- بيانات الأسهم،
- إجراءات SaaS.

لا تتحكم المؤسسة بها.

اعتبارات مهمة:

```text
authentication
network access
موثوقية المزود
provider versioning
security
```

ينبغي معاملتها على أنها black boxes خارجية ذات controls تشغيلية صريحة.

## 44. قارن فئات Tools

| البُعد | Code Function | Internal API | Public API |
|---|---|---|---|
| Latency | منخفضة جدًا | متوسطة | متغيرة/مرتفعة |
| الملكية | كاملة | تحكم مؤسسي كامل | خارجية |
| قابلية المشاركة | أضعف | قوية داخليًا | واسعة مع access |
| Monitoring | مخصص | أسهل باستخدام API tooling | محدودة من المزود |
| Versioning | repository | repository/service | تعتمد على المزود |
| Security | بيئة Agent | VPC/API policy | credentials/network خارجية |

لا توجد فئة هي الأفضل دائمًا.

ينبغي أن تطابق Architecture السياق التشغيلي لـ Tool.

## 45. Tool Registry بوصفها مصدر الحقيقة الواحد

من دون Registry، قد تبني الفرق مرارًا:

```text
get_customer_profile
```

من دون معرفة أن إصدارًا آخر موجود بالفعل.

Tool Registry هي catalog مركزي يصف القدرات المتاحة.

وهي تدعم:

```text
الاكتشاف (discover)
إعادة الاستخدام (reuse)
الحوكمة (govern)
version
التأمين (secure)
التدقيق (audit)
Evaluation
```

يقارنها المصدر بقائمة مطعم:

يرى Agent/developer ما هو موجود دون الدخول إلى كل "مطبخ".

## 46. الفوائد الأساسية لـ Tool Registry

### Reusability

اعثر على القدرات الموجودة وأعد استخدامها.

### Visibility/Shareability

يمكن للفرق المصرح لها اكتشاف ما هو موجود.

### Security/Accessibility

تحكم في أي Agents/users يمكنهم استدعاء Tool.

### Standardization

اطلب metadata وعقودًا متسقة.

### Robustness

خزّن Evaluation/testing/version lineage.

### Auditability

تتبع usage، وaccess، وdependencies، وlifecycle.

وهذا يحول مجموعة Tools إلى ecosystem محكوم.

```text
المخرجات (outputs)
الموقع (location)
طريقة invocation
المالك (owner)
version
نتائج Evaluation
قواعد access
documentation
lineage
```

يسمح Search/discovery للمطورين بالعثور على Tools حسب:

- keyword،
- category،
- capability.

ويحد Access control من Agents التي يمكنها استخدامها.

## 48. Registry أكثر من مجرد Documentation

يمكن لـ Registry قوية الإجابة عن:

```text

أي Agents تستخدمها؟
إلى أي data يمكنها الوصول؟
```

ويدعم هذا:

- compliance،
- debugging،
- dependency analysis،
- cleanup.

```text

```

و:

```text
Tools غير مستخدمة وجاهزة للتقاعد
```

## 49. الوصول Generalist مقابل Specialist إلى Tools

بمجرد وجود آلاف Tools، كم Tool ينبغي أن يراها Agent واحد؟

### Generalist

امنح Agent الوصول إلى Registry كاملة.

المزايا:


```text

اختيار أقل قابلية للتنبؤ
اختبار أصعب
```

```text

قابلية تنبؤ أفضل
اختبار أبسط
تقليل التعرض الأمني
```

التكلفة:

```text
مزيد من التصميم/التنسيق
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "إذا كانت الإجابة النهائية صحيحة، فقد نجح Agent."

لا. قد تظل Trajectory مُهدرة، أو غير آمنة، أو صحيحة بالمصادفة.

### المفهوم الخاطئ 2
> "Tool unit tests غير ضرورية لأن LLM ستتعامل مع الأخطاء."

لا. يجب إصلاح Tools deterministic المعطلة قبل Evaluation لـ Agent.

### المفهوم الخاطئ 3
> "السلوك الصحيح يتضمن دائمًا Tool call."

لا. يجب أيضًا تقييم سلوك no-tool وclarification.

### المفهوم الخاطئ 4
> "Autoraters تلغي الحاجة إلى Rubrics صريحة."

لا. تحتاج إلى معايير واضحة، ويمكن لـ Adaptive Rubrics جعل هذه المعايير خاصة بالمهمة.

### المفهوم الخاطئ 5
> "Golden dataset متعددة الأدوار ليست سوى عدة أمثلة single-turn مستقلة."

لا. يجب أن تمثل chains متوقعة وstate dependencies.

### المفهوم الخاطئ 6
> "إذا وصل Agent إلى الإجابة الصحيحة في سبع calls بدل ثلاث، فالأداء متكافئ."

لا. Step efficiency جزء من جودة Trajectory.

### المفهوم الخاطئ 7
> "Evaluation لـ Long-term memory تتحقق فقط مما إذا تم تخزين شيء ما."

لا. قيّم كلًا من summarization والاسترجاع اللاحق.

### المفهوم الخاطئ 8
> "Simulator هو المُقيِّم."

لا. Simulator يمثل؛ أما metrics/Autoraters/humans فتحكم.

### المفهوم الخاطئ 9
> "Transcript يمثل جودة Voice بالكامل."

لا. يفقد prosody، وemotion، وhesitation، وديناميكيات المحادثة.

### المفهوم الخاطئ 10
> "اختبار Barge-in يقيس فقط سرعة توقف الصوت."

لا. اختبر أيضًا context switching وretention.

### المفهوم الخاطئ 11
> "تنتهي Evaluation عند Deployment لـ Agent."

لا. يصوغ المصدر Monitoring على أنها Evaluation في الوقت الحقيقي، وProduction feedback بوصفها بيانات اختبار مستقبلية.

### المفهوم الخاطئ 12
> "كل Enterprise Tools متشابهة أساسًا."

لا. Local code وInternal APIs وPublic APIs لها خصائص تشغيلية مختلفة.

### المفهوم الخاطئ 13
> "Tool Registry مجرد Documentation."

لا. تدعم access، وEvaluation، وversions، وlineage، وdiscovery، وauditability، وGovernance.

### المفهوم الخاطئ 14
> "ينبغي دائمًا لـ Generalist agent أن يرى كل Tools المتاحة."

لا. قد تقلل مساحات البحث الكبيرة قابلية التنبؤ والدقة والأمان.

### المفهوم الخاطئ 15
> "Specialist agents هي الطريقة الوحيدة لتقليل مساحة البحث عن Tools."

لا. يمكن لـ Dynamic Tool Search تضييق candidates وقت runtime.

### المفهوم الخاطئ 16
> "Centralized governance تعني أن كل Tool يجب أن تعمل في بيئة مركزية واحدة."

لا. يمكن توزيع Tools بينما تكون رؤية Registry/Governance الخاصة بها مركزية.

### المفهوم الخاطئ 17
> "API-first وMCP متعارضان."

لا. يعرض المصدر Service deployment وMCP standardization بوصفهما متكاملين.

### المفهوم الخاطئ 18
> "Federated governance تعني عدم وجود معايير مركزية."

لا. تُدمج الاستقلالية المحلية مع معايير مشتركة وcentral curation.

## المصطلحات الأساسية

|---|---|
| Golden dataset | مجموعة سلوك Agent المتوقع المنسقة والمستخدمة بوصفها Evaluation ground truth |

| Parameter accuracy | ما إذا تم استخراج Tool arguments وتنسيقها بصورة صحيحة |

| Clarification success | طلب المعلومات الناقصة بدلًا من التخمين |
| Autorater | Model/Agent يُستخدم كمُقيِّم |
| Adaptive Rubric | معايير Evaluation تتكيف مع المهمة |

| Evaluation للـ memory قصيرة الأمد | اختبار احتفاظ الجلسة بالموضوع/context |
| Evaluation للـ memory طويلة الأمد | اختبار التلخيص والاسترجاع المستمرين |
