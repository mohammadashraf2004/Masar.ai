## 1. يربط CI/CD أدوات DevOps التي تعلّمتها

حتى هذه النقطة، حلّت كل أداة DevOps رئيسية جزءًا مختلفًا من مشكلة التسليم.

لقد تعلّمت:

```text
Git
→ إدارة الشيفرة المصدرية والتعاون عليها

Docker
→ تحزيم التطبيق باتساق

Terraform
→ تعريف البنية التحتية وإدارتها
```

والخطوة التالية هي ربطها.

**CI/CD pipeline** هو المسار الآلي الذي ينقل التغيير عبر عملية التسليم.

نموذج ذهني بسيط:

```text
المطوّر يغيّر الشيفرة
        ↓
Git push / Pull Request
        ↓
بناء واختبارات آلية
        ↓
تحزيم التطبيق
        ↓
نشر artifact أو image
        ↓
Deploy إلى بيئة
        ↓
تطبيق قيد التشغيل
```

وهنا تبدأ أدوات DevOps المنفصلة بالعمل كنظام واحد.

### لماذا تهمّ الـ pipelines

بدون أتمتة، قد يعتمد الإصدار على أن يتذكر شخص ما:

1. سحب أحدث شيفرة،
2. تثبيت الاعتماديات،
3. تشغيل الاختبارات،
4. بناء Docker image،
5. تسجيل الدخول إلى registry،
6. وسم الـ image بشكل صحيح،
7. دفعها،
8. تحديث البنية التحتية،
9. عمل الـ deploy لها.

كل خطوة يدوية تخلق فرصًا لـ:

- إجراءات منسية،
- تنفيذ غير متسق،
- تغذية راجعة بطيئة،
- أخطاء في الـ deployment.

ويحوّل الـ pipeline تلك الآليات المتكررة إلى عملية محددة.

## 2. التكامل المستمر: ادمج التغييرات الصغيرة واحصل على تغذية راجعة سريعة

**التكامل المستمر (Continuous Integration أو CI)** أكثر من "أداة تشغّل الاختبارات".

إنه انضباط تطويري.

يعرّف المصدر CI حول التكامل المتكرر للتغييرات في مستودع مشترك، غالبًا عدة مرات يوميًا.

وبعد حدث التكامل، تتحقق الأتمتة من صحة التغيير.

### المشكلة التي يحلها CI

تخيّل ثلاثة مطوّرين يعملون أسبوعين دون تكامل.

يتطور كل فرع بمعزل.

وفي النهاية:

```text
الفرع A ────────────────\
                         \
الفرع B ─────────────────> دمج ضخم
                         /
الفرع C ────────────────/
```

الآن يجب على الفريق حل تعارضات كثيرة وأخطاء تفاعل دفعة واحدة.

يسمى هذا غالبًا **جحيم الدمج (merge hell)**.

ويقلّل CI حجم المشكلة.

فبدلًا من:

```text
تكاملات كبيرة + نادرة
```

يشجّع CI على:

```text
تكاملات صغيرة + متكررة
```

المشكلات الصغيرة عادةً أسهل فهمًا وإصلاحًا.

### حلقة التغذية الراجعة في CI

يصف المصدر هذا التسلسل:

```text
1. المطوّر يودِع تغييرًا
        ↓
2. Push أو pull request
        ↓
3. يُطلَق نظام CI
        ↓
4. بناء + اختبارات آلية
        ↓
5. نتيجة فورية
        ↓
ناجح (Pass) → تابع
فاشل (Fail) → أصلح بسرعة
```

الهدف ليس مجرد "علامات خضراء".

الهدف هو:

> **اكتشاف مشكلات التكامل في أبكر وقت ممكن.**

### لماذا يحسّن CI الجودة

يوفّر CI بوابة جودة أساسية.

فإذا فشل الآن اختبار كان ينجح سابقًا، يعرف الفريق ذلك فورًا.

وهذا أفضل بكثير من اكتشاف حالة التراجع (regression) نفسها بعد أن تتراكم فوقها عدة تغييرات أخرى.

### CI بقدر قوة فحوصه

قد ينجح الـ pipeline تقنيًا ومع ذلك يوفّر ضمان جودة ضعيفًا إذا كانت الاختبارات ضعيفة.

ويذكر المصدر صراحةً:

> الـ CI pipeline بقدر جودة اختباراته.

لذلك يتطلب CI الأمرين معًا:

```text
أتمتة
+
اختبارات ذات معنى
```

## 3. Continuous Delivery مقابل Continuous Deployment

يمكن أن يشير الاختصار **CD** إلى ممارستين مترابطتين.

وهما ليستا الشيء نفسه.

### التسليم المستمر (Continuous Delivery)

في طرح المصدر، يؤتمت Continuous Delivery عملية إصدار البرمجيات بحيث يستطيع التغيير المُختبَر الوصول تلقائيًا إلى بيئة اختبار أو تجهيز (staging) ويبقى جاهزًا للإنتاج.

والإصدار النهائي إلى الإنتاج يظل قرارًا بشريًا.

من الناحية المفاهيمية:

```text
الشيفرة (Code)
 ↓
البناء (Build)
 ↓
الاختبار (Test)
 ↓
التحزيم (Package)
 ↓
Staging deployment
 ↓
جاهز للإنتاج
 ↓
قرار إصدار يدوي
 ↓
الإنتاج (Production)
```

يُحضّر الـ pipeline التقني نسخة قابلة للإصدار.

ويقرر العمل أو الفريق متى تُعرض على العملاء.

{{image:production-approval}}

### Continuous Deployment

يزيل Continuous Deployment بوابة الإنتاج اليدوية النهائية.

```text
الشيفرة (Code)
 ↓
البناء (Build)
 ↓
الاختبار (Test)
 ↓
اجتياز كل الفحوص
 ↓
Deployment تلقائي إلى الإنتاج
```

ويتطلب هذا ثقة قوية جدًا في:

- الاختبار الآلي،
- أمان الـ deployment،
- المراقبة،
- قدرة التراجع أو التعافي.

### الفرق الأساسي

| الممارسة | بناء/اختبار تلقائي | تحضير الـ staging/الإصدار تلقائيًا | القرار النهائي للإنتاج |
|---|---:|---:|---|
| Continuous Integration | نعم | ليس بالضرورة | ليس محور التركيز |
| Continuous Delivery | نعم | نعم | يتحكم فيه البشر |
| Continuous Deployment | نعم | نعم | مؤتمت |

يركّز المصدر بقية الفصل على **Continuous Delivery** لأنه يجمع بين أتمتة عالية وطبقة تحكم نهائية.

## 4. GitHub Actions: نموذج الأتمتة

يحتاج CI/CD pipeline إلى شيء ينفّذ الأتمتة.

يذكر المصدر بدائل مثل:

- Jenkins،
- CircleCI،
- GitLab CI.

وفي هذا الفصل، منصة الأتمتة هي **GitHub Actions**.

ميزتها الرئيسية في مسار التعلّم هذا أنها مدمجة مباشرةً في مستودع GitHub الذي يحتوي أصلًا شيفرة التطبيق.

### تعيش الـ workflows مع الشيفرة

الـ workflows في GitHub Actions ملفات YAML مخزَّنة تحت:

```text
.github/workflows/    # مجلد ملفات الـ workflows
```

وهذا مهم مفاهيميًا.

يصبح تعريف الأتمتة جزءًا من المستودع.

وهذا يعني أن الـ pipeline نفسه يمكن أن يكون:

- خاضعًا للإصدارات،
- قابلًا للمراجعة،
- قابلًا للتغيير عبر pull requests.

### المفاهيم الأساسية

يعرّف المصدر ستة مفاهيم.

### 4.1 الـ Workflow

**الـ workflow** هو العملية الآلية الكاملة.

مثال:

```text
Continuous Integration    # اسم الـ workflow
```

أو:

```text
Continuous Delivery    # اسم الـ workflow
```

يمكن أن يحتوي workflow واحد على job واحد أو أكثر.

### 4.2 الـ Event

**الـ event** يطلق workflow.

وتشمل الأمثلة من المصدر:

```text
push    # أحداث مُطلِقة
pull_request
مشغِّلات يدوية
مشغِّلات مجدولة
```

يجيب الـ workflow عن:

> "متى ينبغي أن تعمل هذه الأتمتة؟"

### 4.3 الـ Job

**الـ job** يجمع steps تُنفَّذ على الـ runner نفسه.

افتراضيًا، يمكن أن تعمل الـ jobs المنفصلة على التوازي.

ويمكنك أيضًا تعريف اعتماديات بحيث ينتظر job آخر.

ويصبح هذا مهمًا في CD pipeline.

مثلًا:

```text
build-and-push    # job البناء والدفع
      ↓
   deploy    # job الـ deploy
```

يجب ألا يبدأ الـ deployment حتى توجد الـ image.

### 4.4 الـ Step

**الـ step** مهمة واحدة داخل job.

أمثلة:

```text
سحب الشيفرة (check out code)
إعداد Python (set up Python)
تثبيت الاعتماديات
تشغيل الاختبارات
```

تُنفَّذ الـ steps داخل job بالترتيب.

### 4.5 الـ Action

**الـ action** مكوّن قابل لإعادة الاستخدام يستطيع تنفيذ مهمة شائعة.

وتتضمن أمثلة المصدر:

⟦CODE_0⟧

وبدلًا من إعادة كتابة منطق أتمتة شائع، تستطيع الـ workflows إعادة استخدام actions موجودة.

### 4.6 الـ Runner

**الـ runner** هو الجهاز الذي ينفّذ الـ job.

ويصف المصدر runners تستضيفها GitHub لـ:

- Ubuntu،
- Windows،
- macOS.

ويمكنك أيضًا استضافة runner خاص بك إذا كانت البيئة تحتاج إلى إعداد خاص.

### اجمع التسلسل الهرمي

```text
Workflow
│
├── Event يطلقه
│
├── Job A
│   ├── Runner
│   ├── Step 1
│   ├── Step 2
│   └── Step 3
│
└── Job B
    ├── Runner
    ├── Step 1
    └── Step 2
```

## 6. حوّل CI إلى بوابة جودة حقيقية

CI workflow مفيد.

لكنه يصبح أقوى عندما تعتمد قواعد الدمج في المستودع عليه.

### حماية الفروع

يوصي المصدر بحماية الفروع على `main`.

من الناحية المفاهيمية:

```text
Pull Request
     ↓
اختبارات CI
     ↓
ناجحة؟
 ┌───┴───┐
لا      نعم
↓         ↓
حظر    تستمر المراجعة/الدمج
```

وهذا يغيّر CI من:

> "إشعار مفيد"

إلى:

> "شرط مطلوب للدمج."

### لماذا يهمّ هذا

بدون فرض، يستطيع شخص تجاهل pipeline أحمر والدمج على أي حال.

ويحوّل الفحص المطلوب للحالة (required status check) نتيجة الاختبار الآلي إلى قاعدة حوكمة.

### راقب الـ workflow

بعد الإيداع:

⟦CODE_16⟧

والدفع:

⟦CODE_17⟧

يوجّه المصدر المتعلّم إلى تبويب **Actions** في GitHub.

وهناك تستطيع فحص:

- تشغيل الـ workflow،
- الـ job،
- الـ steps الفردية،
- السجلات.

### تصحيح الإخفاقات

الـ pipeline الفاشل تغذية راجعة مفيدة.

ويوصي المصدر بما يلي:

1. افتح تشغيل الـ workflow الفاشل،
2. وسّع الخطوة الفاشلة،
3. اقرأ السجل كاملًا،
4. حدّد الخطأ بدقة،
5. أصلح المشكلة،
6. ادفع commit جديدًا.

وبالنسبة إلى الإخفاقات العابرة، يشير المصدر أيضًا إلى خيار **Re-run jobs**.

### نموذج تصحيح منضبط

```text
workflow أحمر
    ↓
أي job فشل؟
    ↓
أي step فشل؟
    ↓
ماذا يقول السجل؟
    ↓
هل المشكلة في الشيفرة أم الإعداد أم الاعتمادية أم عابرة؟
    ↓
أصلح أو أعد التشغيل بما يناسب
```

لا تعامل الـ pipeline الأحمر على أنه "GitHub Actions معطّلة".

تعامل مع السجلات بوصفها دليلًا.

## 7. صمّم Continuous Delivery pipeline

يمدّ المصدر بعد ذلك CI إلى الـ deployment.

والتدفق المستهدف هو:

```text
دمج التغيير إلى main
        ↓
بناء Docker image
        ↓
دفع الـ image إلى AWS ECR
        ↓
تمرير عنوان image URI للأمام
        ↓
Terraform ينشر/يحدّث خدمة App Runner للـ staging
        ↓
التطبيق يعمل في AWS staging
```

يجمع هذا الدروس السابقة:

```text
GitHub    # الأدوات المتكاملة
+ GitHub Actions
+ Docker
+ AWS ECR
+ Terraform
+ AWS App Runner
```

### حدّ مهم في المصدر

يعرض الفصل المقدَّم بداية `cd.yml` فقط ويستبدل الباقي بـ:

```text
....
```

لذلك يعلّم هذا الدرس المعمارية وعلاقة الـ jobs الموصوفة صراحةً دون اختراع شيفرة الـ workflow المحذوفة.

### 7.1 AWS ECR: سجل الـ images

يختار المصدر **Amazon Elastic Container Registry (ECR)** بوصفه الـ registry لـ CD workflow.

تحتاج Docker image إلى موقع تستطيع بيئة AWS staging الوصول إليه.

من الناحية المفاهيمية:

```text

   |
   | image URI
   v
AWS App Runner
```

وتذكر المتطلبات التقنية في المصدر أيضًا حساب Docker Hub، لكن مسار CD deployment الظاهر يستخدم ECR تحديدًا.

```text
simple-flask-app    # اسم المستودع
```

لكن الـ workflow يستخدم اسمًا مختلفًا، فقد تفشل مرحلة الدفع.

وهذا مثال جيد على لماذا يهمّ اتساق الإعدادات في الـ pipelines.

### 7.2 بيانات اعتماد AWS عبر GitHub Secrets

يخزّن المصدر:

```text
AWS_ACCESS_KEY_ID
AWS_SECRET_ACCESS_KEY
```

بوصفها GitHub repository secrets.

والفكرة الرئيسية:

> لا ينبغي كتابة بيانات الاعتماد الحساسة مباشرة في ملفات الـ workflow.

يشير الـ workflow إلى الأسرار بأمان عند التنفيذ.

### أقل الامتيازات (Least privilege)

يوصي المصدر إضافةً بـ **مبدأ أقل الامتيازات**.

فبدلًا من منح الـ pipeline صلاحيات واسعة "احتياطًا"، امنحه فقط ما يحتاجه فعلًا.

ويعطي الفصل أمثلة مثل إجراءات ECR والحد الأدنى من صلاحيات App Runner المطلوبة.

لماذا؟

لأن بيانات اعتماد الـ pipeline المسرَّبة أو سيئة الاستخدام ينبغي أن يكون نطاق ضررها (blast radius) أصغر ما يمكن.

ثم يحدّث Terraform بنية الـ staging التحتية لاستخدامها.

## 8. افهم CD workflow ذا الـ jobين

يعرض المصدر بداية:

⟦CODE_22⟧

أما الباقي فمحذوف في المصدر المقدَّم.

لكن المصدر يشرح البنية.

### الـ Job 1 — البناء والدفع

يقوم job `build-and-push` بما يلي:

1. يبني Docker image،
2. يدفعها إلى ECR،
3. ينتج عنوان image URI الكامل بوصفه مخرجًا.

فكّر:

```text
المصدر
 ↓
Docker build
 ↓
Image
 ↓
دفع إلى ECR
 ↓
مخرج image URI
```

### الـ Job 2 — الـ deploy

يقوم job الـ deploy بما يلي:

1. ينتظر نجاح الـ job الأول،
2. يتلقى عنوان image URI،
3. يشغّل Terraform،
4. يمرّر ذلك العنوان بوصفه المتغير `ecr_image_identifier`،
5. ينشئ خدمة App Runner أو يحدّثها.

فكّر:

```text
Image URI    # عنوان الصورة
   ↓
Terraform apply
   ↓
App Runner staging
```

### لماذا تهمّ اعتمادية الـ jobs

إذا بدأ الـ deployment قبل نشر الـ image، فقد يوجّه Terraform خدمة App Runner إلى image غير موجودة بعد.

لذلك يجب أن يعبّر الـ pipeline عن:

```text
نجاح build-and-push
        ↓
يجوز أن يبدأ deploy
```

وهذا مبدأ عام في الـ pipelines:

> ينبغي أن يعتمد العمل اللاحق على الاكتمال الناجح للـ artifact السابق الذي يحتاجه.

### الـ artifacts والقيم في الـ pipeline

Docker image هي الـ artifact القابلة للنشر.

وعنوان image URI هو القيمة التي تُمرَّر بين مراحل الـ pipeline.

وهذا التمييز مفيد:

```text
Artifact:
container image

المرجع (Reference):
ECR image URI
```

## 9. الذكاء الاصطناعي التوليدي مساعدًا في أعمال CI/CD

يستكشف القسم الأخير من المصدر الذكاء الاصطناعي التوليدي.

ويحرص الفصل على دور AI:

> يستطيع AI تسريع عمل DevOps، لكنه لا يلغي الحاجة إلى فهم الأساسيات.

وهذا هو النموذج الذهني الصحيح.

### 9.1 توليد الإعدادات أو المساعدة فيها

يعطي المصدر GitHub Copilot مثالًا.

يستطيع AI المساعدة في اقتراح:

- خطوات YAML،
- الـ jobs،
- أسماء الـ actions،
- متغيرات البيئة،
- محتوى Dockerfile،
- مقاطع Terraform.

وهذا قد يقلّل أخطاء الصياغة ووقت البحث.

لكنك ما زلت بحاجة إلى فهم:

```text
ما الذي يطلق هذا الـ workflow؟
ما الصلاحيات التي يملكها؟
ما الذي يُنشَر (deploy)؟
ماذا يحدث إذا فشل؟
```

### 9.2 توليد الاختبارات

يستطيع AI المساعدة في صياغة اختبارات الوحدة.

وقد يحسّن ذلك تغطية الاختبارات ويقوّي بوابة جودة CI.

لكن الاختبارات المولَّدة ما زالت تحتاج إلى مراجعة.

فالاختبار المولَّد الذي يؤكد سلوكًا خاطئًا قد يعطي ثقة زائفة.

### 9.3 المراجعة بمساعدة AI وDevSecOps

يصف المصدر مراجعة بمساعدة AI قد تحدّد:

- الأخطاء الشائعة،
- مشكلات الأمان،
- عدم اتساق الأسلوب.

ويمكن أن يعمل هذا بوصفه بوابة جودة آلية مبكرة.

ويستطيع المراجعون البشر عندئذ التركيز على:

- المعمارية،
- منطق العمل،
- مقايضات النظام،
- القصد.

### 9.4 تحليل الإخفاقات

إذا فشل اختبار في الـ pipeline، فقد يساعد AI على تحليل:

- السجلات،
- تغييرات الشيفرة،
- السبب الجذري المحتمل.

القيمة ليست في استبدال الدليل.

القيمة في جعل الدليل أسهل تفسيرًا.

### 9.5 أتمتة التواصل

ويسرد المصدر أيضًا:

- توليد رسائل commit،
- صياغة أوصاف pull request،
- توليد ملاحظات الإصدار.

وهذه مفيدة لأن CI/CD ينتج قدرًا كبيرًا من البيانات الوصفية التقنية التي يجب على الفرق إيصالها بوضوح.

### نموذج ذهني آمن

```text
AI ينبغي أن يساعد في:
- الصياغة
- التلخيص
- الاقتراح
- المراجعة
- التشخيص

العملية البشرية/الهندسية لا تزال تملك:
- الصحة
- بيانات الاعتماد
- الصلاحيات
- قرارات الإصدار
- المعمارية
- أمان الإنتاج
```

## 10. اجمع الـ pipeline كاملًا

اجمع الآن الفصل كله.

يغيّر مطوّر تطبيق Flask.

### المرحلة 1 — التحكم بالمصدر

```text
المطوّر
   ↓
Git commit
   ↓
GitHub push / PR
```

### المرحلة 2 — CI

GitHub Actions:

```text
يسحب الشيفرة
    ↓
يعدّ Python
    ↓
يثبّت الاعتماديات
    ↓
يشغّل pytest
```

إذا فشلت الاختبارات:

```text
يتوقف الـ pipeline
↓
المطوّر يحقق في الأمر
```

وإذا نجحت الاختبارات، يمكن أن يواصل التغيير عبر قواعد المراجعة والدمج في المستودع.

### المرحلة 3 — مُطلِق CD

بعد وصول التغيير ذي الصلة إلى `main`، يعمل CD workflow.

### المرحلة 4 — بناء الـ container

```text
+

        ↓

```

### المرحلة 5 — الـ registry

```text
Docker image    # الصورة
     ↓
AWS ECR
```

### المرحلة 6 — التسليم بين الـ jobs

يعرض الـ job الأول:

```text
عنوان URI الكامل لصورة ECR
```

### المرحلة 7 — Terraform deploy

```text
var.ecr_image_identifier
```

### المرحلة 8 — بيئة الـ staging

ينشئ Terraform أو يحدّث:

```text
خدمة AWS App Runner للـ staging
```

### المرحلة 9 — المخرجات

يعرض Terraform:

```text
service_url
```

```text
المطوّر
   ↓
Git
   ↓

   ↓

   ├── إعداد Python

   └── pytest

   ↓

   ↓

   ↓

   ↓

   ↓

   ↓
```

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1

> "CI يعني نشر كل commit تلقائيًا."

### لماذا هذا خاطئ

يركّز CI على التكامل المتكرر والبناء/الاختبار الآلي والتغذية الراجعة السريعة.

أما الـ deployment فينتمي إلى مراحل التسليم اللاحقة.

---

### المفهوم الخاطئ 2

> "Continuous Delivery وContinuous Deployment متطابقان."

### لماذا هذا خاطئ

يميّز المصدر بينهما بقرار الإنتاج النهائي.

يُبقي Continuous Delivery البرمجيات جاهزة مع الاحتفاظ ببوابة إنتاج يدوية.

ويزيل Continuous Deployment تلك البوابة البشرية النهائية.

---

### المفهوم الخاطئ 3

> "GitHub Actions workflow هو الشيء نفسه كـ job."

### لماذا هذا خاطئ

يمكن أن يحتوي workflow على عدة jobs.

ويحتوي كل job على steps مرتبة ويعمل على runner.

---

### المفهوم الخاطئ 4

> "الـ action والـ step شيء واحد."

### لماذا هذا ناقص

الـ step مهمة واحدة داخل job.

ويمكن للـ step أن يستدعي action قابلة لإعادة الاستخدام أو ينفّذ أوامر shell مباشرة.

---

### المفهوم الخاطئ 5

> "إذا كان CI أخضر فالتطبيق لا بد أن يكون مثاليًا."

### لماذا هذا خاطئ

لا يتحقق CI إلا من الفحوص التي عرّفتها فعلًا.

والاختبارات الضعيفة أو غير الكاملة تعطي دليلًا ضعيفًا.

---

### المفهوم الخاطئ 6

> "ينبغي كتابة بيانات اعتماد الـ pipeline مباشرة في `cd.yml`."

### لماذا هذا خاطئ

يستخدم المصدر GitHub Secrets لبيانات اعتماد AWS.

ولا ينبغي إيداع القيم الحساسة في مصدر الـ workflow.

---

### المفهوم الخاطئ 7

> "يمكن لـ job الـ deploy في CD أن يعمل بمعزل عن بناء الـ image."

### لماذا هذا خاطئ

تحتاج خطوة الـ deploy إلى عنوان image URI الذي ينتجه job البناء والدفع الناجح.

---

### المفهوم الخاطئ 8

> "يقدّم المصدر YAML الكامل لـ CD."

### لماذا هذا خاطئ

يستبدل الفصل المقدَّم صراحةً بقية الـ workflow بـ `....` ويقول إن الباقي متاح في مستودع الكتاب.

لذلك يشرح هذا الدرس المعمارية وسلوك الـ workflow الذي يدعمه النص المقدَّم فقط.

---

### المفهوم الخاطئ 9

> "الذكاء الاصطناعي التوليدي يلغي الحاجة إلى فهم CI/CD."

### لماذا هذا خاطئ

يقدّم المصدر صراحةً AI بوصفه مسرِّعًا ومساعدًا، لا بديلًا عن فهم الـ pipeline.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| CI | التكامل المستمر (Continuous Integration)؛ تكامل متكرر مع تغذية راجعة آلية من البناء/الاختبار |
| CD | Continuous Delivery في سير العمل الرئيسي للفصل؛ أتمتة تُبقي البرمجيات جاهزة للإصدار |
| Continuous Deployment | إصدار تلقائي إلى الإنتاج بعد نجاح فحوص الـ pipeline |
| الـ Pipeline | تسلسل آلي ينقل تغيير البرمجيات عبر مراحل التسليم |
| GitHub Actions | منصة أتمتة سير العمل من GitHub المستخدمة في الفصل |
| الـ Workflow | عملية آلية معرَّفة بـ YAML تحت `.github/workflows/` |
| الـ Event | نشاط يطلق workflow |
| الـ Job | مجموعة steps تُنفَّذ على الـ runner نفسه |
| الـ Step | مهمة فردية داخل job |
| الـ Action | مكوّن أتمتة قابل لإعادة الاستخدام تستخدمه step |
| الـ Runner | الجهاز الذي ينفّذ job في GitHub Actions |
| `pytest` | testing framework لـ Python مستخدم في مثال CI |
| فحص الحالة (Status check) | نتيجة آلية يمكن جعلها مطلوبة قبل الدمج |
| حماية الفروع (Branch protection) | قاعدة في المستودع يمكنها حظر الدمج حتى تُستوفى الشروط المطلوبة |
| ECR | سجل Amazon Elastic Container Registry |
| الـ Registry | خدمة لتخزين صور الـ containers وتوزيعها |
| GitHub Secret | قيمة مشفَّرة في المستودع متاحة للـ workflows |
| أقل الامتيازات (Least privilege) | منح الصلاحيات المطلوبة للمهمة فقط |
| App Runner | خدمة AWS التي يستخدمها المصدر لـ staging deployment |
| عنوان الصورة (Image URI) | مرجع في الـ registry يحدّد Docker image المراد نشرها |
| DevSecOps | دمج فحوص الأمان واهتماماته في سير عمل تسليم البرمجيات |
