## 1. لماذا يوجد Knowledge-Enhanced RAG؟

يتميز Vector retrieval وHybrid retrieval بقدرتهما على العثور على Text متشابه دلاليًا، لكن Similarity ليست هي نفسها علاقة موثقة. قد يكون Query قريبًا موضوعيًا من Passages كثيرة، ومع ذلك يحتاج Answer تعتمد على Date محددة، أوتقاطع عدة Constraints، أوسلسلة علاقات عبر عدة Entities.

يضيف Knowledge-enhanced RAG طبقة علاقات صريحة. بدلًا من أن يسأل System فقط: «أي Chunks تبدو مشابهة لهذا Query؟»، يمكنه أيضًا أن يسأل: «أي Entities مرتبطة بالعلاقات الدقيقة المطلوبة للإجابة؟». يغير ذلك Retrieval من Matching احتمالي صرف باتجاه Traversal منظم للحقائق.

الفكرة المعمارية المركزية في الدرس ليست أن Graphs تستبدل RAG. بل تكمل Graphs الـ Semantic retrieval عندما تكون Relationships وConstraints وMulti-hop logic مهمة بما يكفي لتبرير تكلفتها التشغيلية.


## 2. Failure Mode 1: حقائق مرتبطة بزمن محدد

تضغط Embeddings المعنى، لكنها لا تفهم تلقائيًا أي Fact كانت صحيحة في نقطة زمنية معينة. قد تحتوي Corpus على عدة Statements صحيحة تاريخيًا عن Entity نفسها. وقد يسترجع Semantic search جميعها لأنها متشابهة مفاهيميًا.

في الأسئلة الحساسة للزمن، لا تكون المعلومة المهمة هي Entity فقط، بل فترة صلاحية Fact. يمكن لـ Graph تمثيل ذلك صراحة عبر إرفاق Temporal properties بـ Nodes أوRelationships، أوالاحتفاظ بعلاقات تاريخية منفصلة.

الدرس الهندسي هو أن Dates ليست مجرد Metadata تجميلية. إذا كان Application يجب أن يجيب عن «من كان يشغل Role X في Date Y؟»، فيجب على Data model تمثيل الزمن بطريقة قابلة للـ Query.


## 3. Failure Mode 2: تقاطع القيود

قد يطلب User Entities تحقق عدة شروط في الوقت نفسه. تستطيع Vector search غالبًا العثور على Chunks عن كل شرط بصورة مستقلة، لكنها لا تضمن أن Entity نفسها تحقق كل الشروط.

تتناسب Graph queries طبيعيًا مع Intersections لأن Query يمكن أن تشترط تحقق عدة Graph patterns معًا. وهذا مفيد بصورة خاصة في Domains مثل Compliance وPharmacology وSupply chains وOrganizational hierarchies، حيث تُعرَّف Answer بمجموعات دقيقة من العلاقات.

السؤال التشخيصي الأساسي هو: هل تعتمد Answer على Topical similarity، أم على تحقيق اقتران منطقي لمجموعة Constraints؟


## 4. Failure Mode 3: الاستدلال المتسلسل أوMulti-Hop

تتطلب Multi-hop questions اجتياز عدة Relationships بالتتابع. قد يسترجع Standard retrieval حقيقة أواثنتين ذواتي صلة، لكنه لا يضمن إمكانية تركيب هذه الحقائق في Path الدقيقة المطلوبة.

تشفّر Graph المسار مباشرة. يمكن اشتقاق Answer عبر Traversal من Entity إلى أخرى من خلال Typed edges، مع Filtering للـ Intermediate nodes حسب Properties مثل Year.

لا يجعل ذلك Graph reasoning معصومًا من الخطأ. يجب أن تكون Graph نفسها صحيحة، وأن تُربط Entities بصورة سليمة، وأن تعبّر Query عن Traversal المقصودة. لكن عندما تتحقق هذه الشروط، توفر Graph أساسًا للاستدلال أكثر Deterministic بكثير من Loose chunk similarity.

## 5. Knowledge Graphs: النموذج الذهني الأساسي

Knowledge graph هي شبكة من Entities متصلة بعلاقات ذات Types محددة. تكون Graph قابلة للقراءة آليًا لأن كل Node وEdge له Meaning صريح.

في Movie domain، قد تمثل Nodes أشخاصًا أوأفلامًا أوCharacters أوGenres أوText chunks. وقد تمثل Edges علاقات مثل `DIRECTED` و`ACTED_IN` و`HAS_GENRE` و`APPEARS_IN` و`MENTIONS`.

تصبح Graph ذات قيمة لأن Question يمكن تحويلها إلى Path. بدلًا من استرجاع Text يناقش Director، يمكن للنظام Traversal عبر علاقة `DIRECTED` من Person node إلى Movie nodes، ثم الاستمرار إلى Actor nodes. هذا الفرق — Path traversal بدل Similarity search — هو جوهر Graph retrieval.


{{exercise:M01.L09.EX02}}


## 6. Nodes وEntities وProperties

تمثل Node شيئًا داخل Domain: شخصًا أوOrganization أوProduct أوMovie أوDrug أوLocation أوEvent أوDocument أوConcept. وتحمل Nodes عادةً Properties تصفها.

يفصل Graph design الجيد بين Identity وAttributes. مثلًا، قد تُعرّف Movie node باستخدام Stable ID مع تخزين Title وRelease year كـ Properties. وتكون Stable identity مهمة بصورة خاصة لأن Titles وNames قد تتغير أوتتكرر.

عندما يفشل Graph-enhanced RAG، تكون Entity identity غالبًا من أول الأشياء التي ينبغي فحصها. تؤدي Duplicate nodes أوMissing identifiers أوOverloaded properties إلى Retrieval errors لاحقة يصعب على LLM إصلاحها.


## 7. Edges والعلاقات ذات Types محددة

تشفّر Edges كيفية ارتباط Entities ببعضها. الـ Edge ليست مجرد Connection؛ بل لها Type تمنح Connection معنى. تختلف `ACTED_IN` عن `DIRECTED`، كما تختلف `WORKS_AT` عن `OWNS`.

يهم Direction أيضًا. علاقة `Person -[:DIRECTED]-> Movie` تختلف دلاليًا عن Traversal العكسي، حتى لو كانت كلتا Nodes متصلتين.

Typed relationships هي ما يجعل Graphs مفيدة للأسئلة الدقيقة. فهي تسمح لـ Query engine بتقييد Traversal بالعلاقات المهمة فقط، بدل الاعتماد على Language model لاستنتاج العلاقة من Prose المحيطة.


## 8. Graph Databases ولماذا توجد

Graph databases متخصصة في تخزين Nodes وEdges واجتيازها. وتختلف عن Relational databases أساسًا في كيفية تمثيل Relationships والاستعلام عنها.

يناقش المصدر Systems مثل Neo4j وAmazon Neptune وKuzu وTigerGraph. يؤثر اختيار Database في Deployment وScaling وQuery language وOperational burden وIntegration options.

بالنسبة إلى RAG، النقطة المهمة ليست Brand. المهم أن يكون Graph traversal سريعًا بما يكفي ليقع داخل Interactive query path، وأن تدعم Database متطلبات Consistency وSecurity وLifecycle الخاصة بـ Application.

## 11. Ontology مقابل Schema

تعرّف Ontology القواعد المفاهيمية لـ Domain: ما Types الأشياء الموجودة، وأي Relationships ذات معنى، وما Constraints التي تصف الواقع. أما Schema فهي Implementation على مستوى Database لذلك Model.

مثلًا، قد تنص Ontology على أن Person يمكنه Direct لـ Movie، وأن Movie لها Release year. ثم تعرّف Schema الـ Node labels وRelationship types وProperty types المقابلة داخل Database.

يهم هذا التمييز في RAG لأن Ontology تساعد في تشكيل Reasoning model، بينما Concrete schema هي ما يجب أن يعرفه LLM لتوليد Cypher أوSPARQL صحيحة.

## 12. تصميم Movie Knowledge Graph

يجمع Working example في الفصل بين Structured movie metadata وUnstructured movie scripts. توفر Structured data الـ Entities والعلاقات الموثقة، بينما توفر Scripts الـ Text chunks والMentions.

قد تتضمن Schema مفيدة Nodes مثل `Movie` و`Person` و`Character` و`Genre` و`Chunk`، وعلاقات مثل `DIRECTED` و`ACTED_IN` و`HAS_GENRE` و`PORTRAYED_BY` و`BELONGS_TO` و`MENTIONS`.

يوضح التصميم Pattern أوسع: اجمع Structured sources القوية في Identity وRelationships مع Unstructured sources التي تحتوي Language وEvidence غنية.


## 13. Chunking للـ Unstructured Text قبل بناء Graph

لا تزال Unstructured source documents تحتاج Preprocessing المعتادة في RAG. في Movie example، يتم تنظيف Scripts وتقسيمها إلى Chunks قبل أن تصبح تلك Chunks Nodes داخل Graph.

الدرس الأساسي أن إضافة Graph لا تلغي Chunking. بدلًا من ذلك تصبح Chunks Graph entities من الدرجة الأولى يمكن ربطها بـ Higher-level objects.

يصبح Stable chunk ID مهمًا بصورة خاصة لأن Chunk نفسها قد توجد بالتزامن في Vector index وGraph. يعمل هذا Identifier بوصفه Join key بين Semantic retrieval وGraph enrichment.

## 14. اكتشاف Entity يعتمد على Domain

قبل أن تتمكن Graph من تشفير Relationships، يجب على Pipeline تحديد Entities. في Movie scripts، توفر Uppercase names Heuristic مريحة لاكتشاف Characters، لكن حتى هذه Signal النظيفة تنتج False positives.

يوضح ذلك قاعدة عامة: Entity extraction ليست مجرد «شغّل NER». تؤثر Domain formatting وAliases وAbbreviations وIDs وNoisy documents في Accuracy.

لذلك تجمع Production pipelines بين Model-based extraction وDeterministic rules وValidation. وكلما كانت Graph أكثر Business-critical، كان من غير المقبول بدرجة أكبر السماح لـ Noisy extraction model بإنشاء Authoritative nodes بصمت.


## 15. ربط Chunks بـ Domain entities

بعد تحديد Entities، يمكن ربط Chunks بها. مثلًا:

```text
(مقطع)-[:MENTIONS]->(شخصية)
(شخصية)-[:APPEARS_IN]->(فيلم)
(شخص)-[:ACTED_IN]->(فيلم)
(شخص)-[:DIRECTED]->(فيلم)
```

يسمح ذلك لـ Chunk بالعمل في الوقت نفسه كـ Evidence وكجسر إلى Structured context. يمكن لـ Retrieved chunk أن تخبر System بأي Character تم ذكره، ثم تستطيع Graph توفير Actor أوMovie أوDirector أوRelated entities.

هذا Pattern هو أساس Chunk enrichment.


## 16. نمطان رئيسيان أثناء Query time

يعرض الفصل طريقتين رئيسيتين لاستخدام Knowledge graph داخل RAG query flow:

1. **Chunk enrichment** تبدأ من Vector retrieval وتستخدم Graph لإضافة Structured context مفقودة إلى Retrieved chunks.
2. **Hybrid-graph retrieval** تشغل Graph retrieval كقناة Retrieval إضافية، وغالبًا عبر ترجمة User question إلى Cypher أوSPARQL.

تحل هاتان الطريقتان مشكلات مختلفة. تفترض Enrichment أن Semantic retrieval عثرت بالفعل على Evidence الصحيحة لكن Evidence فقيرة في Context. بينما تفترض Hybrid graph retrieval أن Question نفسها Relationship-heavy وتتطلب Graph traversal لاكتشاف Answer.


## 17. إثراء Chunks (Chunk Enrichment)

Chunk enrichment هي استراتيجية Metadata-first. ابدأ بـ Vector retrieval، ثم افحص Entities المرتبطة بـ Retrieved chunk واسترجع Structured facts من Graph.

افترض أن Retrieved dialogue chunk تحتوي اسم Character هو “Vincent” لكنها لا تحتوي Actor أوMovie. يمكن لـ Graph إثراؤها بحقائق مثل Canonical character identity وPerformer وMovie.

يحتوي Final prompt على Original chunk إضافة إلى Structured context packet. يحافظ ذلك على Vector search مسؤولة عن العثور على Text ذات صلة دلاليًا، بينما توفر Graph High-confidence facts اللازمة للإجابة بدقة.

## 18. لماذا تُعد Chunk Enrichment جذابة تشغيليًا؟

يمكن أن تكون Chunk enrichment منخفضة المخاطر نسبيًا لأنها لا تتطلب من LLM تركيب Graph query معقدة في كل Request. إذا كانت Vector search قد عثرت بالفعل على Chunk ID، فقد تكون Graph step مجرد Direct indexed lookup.

يعني ذلك أن Graph تضيف Context دون السيطرة على Retrieval path بالكامل. وهي أول Pattern مفيدة للـ Graph enhancement عندما يكون الفشل الأساسي هو Missing metadata أوNames أوDates أوIDs أوRelationships حول Text ذات صلة أصلًا.

المقايضة أن Enrichment لا يمكنها اكتشاف Evidence لم تسترجعها Vector search أصلًا. فهي تحسن Context حول Chunks التي تم العثور عليها بدلًا من استبدال Candidate generation.


## 19. الاسترجاع الهجين عبر Graph (Hybrid-Graph Retrieval)

تعامل Hybrid-graph retrieval الـ Graph بوصفها Parallel retrieval engine. تُترجم Natural-language question إلى Formal graph query، وتعيد Graph الـ Entities أوChunks ذات الصلة، ثم تُجمع هذه النتائج مع Evidence المسترجعة بواسطة Vectors.

هذا النهج قوي للأسئلة Multi-hop والمقيدة لأن Graph query تستطيع تشفير Relationship structure صراحة.

لكنه يقدم Failure surface جديدة: توليد Text-to-Cypher أوText-to-SPARQL. قد ينتج LLM Syntax غير صحيحة، أويشير إلى Labels غير موجودة، أوينشئ Traversals مكلفة، أويسيء تفسير User intent.


## 20. توليد Graph query مشروط بالـ Schema

لا يستطيع LLM توليد Graph queries موثوقة إذا لم يعرف Graph schema. يجب أن يكشف Prompt الـ Node labels وRelationships وProperties وImportant constraints المتاحة.

يشبه ذلك Text-to-SQL. يحتاج Model إلى Vocabulary وGrammar الخاصة بـ Database قبل أن يتمكن من كتابة Query صحيحة.

ينبغي لـ Production implementation التعامل مع Schema descriptions بوصفها Versioned application assets. إذا تطورت Graph بينما ظل Prompt يصف Schema القديمة، فقد تتدهور Query generation بصمت.

## 21. جعل Text-to-Cypher أكثر أمانًا

لأن Graph queries التي يولدها LLM هي Artifacts شبيهة بالكود ويتم تنفيذها ضد Database، فهي تحتاج Guardrails.

تشمل Controls المفيدة: Read-only database credentials، وQuery templates، وAllow-lists للـ Labels وRelationship types، وComplexity limits، وTimeouts، وRow limits، وSyntax validation، وRetry logic للأخطاء القابلة للتصحيح.

المبدأ هو نفسه المستخدم مع Tool-using agents: قد يقترح Model إجراءً، لكن يجب أن تقرر Deterministic execution layer ما إذا كان هذا الإجراء مسموحًا وآمنًا.

## 22. دمج Vector evidence وGraph evidence

ينبغي التعامل مع Graph results وVector results بوصفها Evidence channels متكاملة. تكون Graph قوية في Explicit structure والعلاقات الدقيقة؛ بينما يكون Vector index قويًا في Fuzzy semantic relevance واللغة غير المنظمة.

يمكن لـ Combined pipeline دمج Retrieved chunks، وإرفاق Provenance، وإزالة Duplicates، واختياريًا Rerank لمجموعة Candidates كاملة قبل Generation.

يجب أن يعرف Answer generator أي Facts جاءت من أي Channel. يجعل الحفاظ على Provenance الـ Debugging وتوليد Citations أسهل بكثير.


## 23. اختيار Enrichment أوHybrid Retrieval

اختر Chunk enrichment عندما تعثر Vector search عادةً على Text الصحيحة لكن Text تفتقد Structured context كافية للإجابة بشكل كامل.

واختر Hybrid graph retrieval عندما تكون Query نفسها Relational في جوهرها: عدة Hops، أوIntersections، أوGraph-wide constraints، أوDiscovery مبنية على Relationships.

ينبغي أن يأتي الاختيار من Evaluation data، لا من Preference. افحص Failure cases حقيقية من Standard RAG system، وصنّف ما إذا كانت المشكلة «Context مفقودة حول Chunk ذات صلة» أم «Semantic retrieval لا تستطيع اكتشاف Relationship path أصلًا».

## 24. أين ينبغي أن تعيش Embeddings؟

يمكن لـ Graph databases الحديثة تخزين Vectors مباشرة على Chunk nodes، مما يسمح بـ Semantic search وGraph traversal داخل Database واحدة. يقلل ذلك Synchronization problems ويمكن أن يوفر Atomic consistency.

بدلًا من ذلك، يمكن أن تبقى Embeddings في Vector database مخصصة بينما تخزن Graph الـ Structured relationships. عندها يُستخدم Retrieved chunk ID للعثور على Graph context.

يحافظ Split design على Retrieval stack متخصصة — Hybrid search وReranking وVector tuning — لكنه ينشئ التزامًا بالمزامنة. أما Unified design فيبسّط Data consistency لكنه قد يخلق Resource contention بين Vector search وGraph traversal.


## 25. الحفاظ على تزامن Vector store وGraph store

عندما تكون Vector store وGraph store منفصلتين، تصبح Chunk identity حاسمة. يجب أن ينعكس كل Insert وUpdate وDelete في النظامين.

Vector entry قديمة تشير إلى Graph node محذوفة تنشئ Enrichment مكسورة. وGraph node بلا Vector entry مقابلة قد تصبح غير قابلة للاكتشاف عبر Semantic channel.

لذلك تحتاج Production systems إلى Stable IDs وVersioning وIdempotent ingestion وReconciliation jobs وMonitoring للـ Orphaned records.

## 26. بناء Knowledge Graphs هو الجزء الأصعب

غالبًا ما يكون Querying لـ Knowledge graph نظيفة أسهل من بنائها. العمل الحقيقي هو تعريف Model مفيدة، واستخراج Entities، واكتشاف Relationships، وحل Aliases، وإزالة Duplicate nodes، والتحقق من Facts، والحفاظ على Graph حديثة.

يُعد Movie example سهلًا بصورة غير معتادة لأن Structured metadata موجودة بالفعل وScripts لها Formatting يمكن التعرف عليه. أما Enterprise corpora فهي أكثر فوضى بكثير.

لهذا فإن قرار إضافة Knowledge graph هو أساسًا قرار Data engineering، وليس مجرد قرار LLM.


## 27. أتمتة بناء KG من Text

تتكون Automated construction pipeline شائعة من ثلاث مراحل:

1. تحديد Entities.
2. استخراج Relationships بين تلك Entities.
3. ربط Surface forms متعددة بـ Canonical entities.

يمكن لـ LLMs الحديثة اقتراح Entities وRelation triples مباشرة من Unstructured text، مما يسهّل Bootstrapping. لكن Extraction quality تظل معتمدة على Domain.

تضيف Production pipeline عادةً Deterministic validators وClassical NLP checks وConfidence thresholds وHuman review للحقائق الحرجة.


## 28. تحديد Entities (Entity Identification)

يسأل Entity identification: أي Spans في Text تقابل أشياء ينبغي أن تصبح Nodes؟

التحدي ليس فقط اكتشاف Proper names. يجب على System تصنيف Entity type وتحديد ما إذا كان Mention مهمًا بما يكفي ليتم تمثيله.

تساعد Ontology قوية على تقييد المهمة. إذا كانت Graph تمثل فقط Companies وPeople وProducts وContracts، فلا يحتاج Extractor إلى اختراع Node types عشوائية لكل Noun phrase.


## 29. استخراج Relationships (Relation Extraction)

تحول Relation extraction الـ Language إلى Typed graph edges. من جملة مثل “Company A acquired Company B”، قد يقترح System علاقة `ACQUIRED` بين Company nodes.

يجب أن يأتي Edge type من Controlled relationship vocabulary إذا كان المطلوب أن تبقى Graph قابلة للـ Query ومتسقة.

تخلق Unconstrained relation labels حالة Schema drift: قد ينتج Extractor أول `FOUNDED_BY`، وآخر `HAS_FOUNDER`، وثالث `CREATED_BY`. لذلك تُعد Normalization جزءًا من Graph quality.


## 30. Entity Linking: شيء واحد وأسماء كثيرة

تحل Entity linking الـ Mentions المختلفة التي تشير إلى Real-world entity نفسها. وهذه من أصعب المراحل في Production KG construction.

قد تظهر Company باسمها القانوني، أوAbbreviation، أوBrand، أوLegacy name. وقد يظهر Drug باسم Brand أوGeneric أوChemical. وقد يظهر Product تحت Vendor-specific SKUs.

إذا أصبحت تلك Aliases Nodes منفصلة، فإن Graph تجزئ الواقع وتصبح Multi-hop queries غير موثوقة. لذلك يجب التعامل مع Entity resolution بوصفها Pipeline من الدرجة الأولى، لا Cleanup task.

## 31. استخدام Ontology لتوجيه Entity Linking

تعطي Ontology لـ Entity linking Target structure. فهي تحدد أي Canonical entity types موجودة، وأي Identifiers أوAliases متوقعة.

مثلًا، قد تمتلك Company entity اسمًا Canonical واحدًا ومجموعة Aliases. عندها يمكن مطابقة Mentions الجديدة مع Existing canonical record بدلًا من إنشاء Node جديدة تلقائيًا.

يقلل ذلك Entity explosion وينشئ أساسًا أكثر استقرارًا لـ Graph traversal.


## 32. Normalization وCandidate Generation

غالبًا ما تبدأ Entity resolution بـ Normalization: توحيد Case، وتوحيد Abbreviations، وتنظيف Punctuation، وتوحيد Formats المعروفة.

ثم تولد Pipeline مجموعة Candidate matches معقولة بدلًا من مقارنة كل Entity بكل Entity أخرى. يمكن لـ Candidate generation استخدام String similarity أوDomain identifiers أوEmbeddings أوDomain-specific rules.

يمكن لـ Final linking decision دمج عدة Signals، وتأجيل Low-confidence cases إلى Human review.


## 33. حل هوية Entities بمراجعة بشرية (Human-in-the-Loop Entity Resolution)

تكون Human review أكثر قيمة عندما تُستخدم بصورة انتقائية. يمكن قبول High-confidence matches تلقائيًا؛ بينما تُرسل Ambiguous matches إلى Queue لمراجعة Expert.

يحوّل ذلك Human effort إلى Quality-control mechanism بدلًا من أن يكون Construction method الأساسية.

ويمكن أن تصبح Reviewed decisions أيضًا Training أوCalibration data لـ Entity-linking models مستقبلية.

## 34. الاستفادة من Standard Ontologies

توفر Standard ontologies Conceptual model مصممة مسبقًا لـ Domain. وتقلل مخاطر اختراع Graph schema غير متسقة أوواسعة أكثر من اللازم.

يستشهد المصدر بأمثلة مثل FIBO في Finance. الدرس العام هو إعادة استخدام Established domain vocabularies عندما تتوافق مع Business problem.

لا تقوم Standard ontology بملء Graph نيابةً عنك، لكنها توفر Blueprint منضبطة لـ Entity types وRelationships.


## 35. الاستفادة من Curated أوLicensed Knowledge Graphs

أحيانًا يكون الجزء الأصعب في بناء Graph — Identity resolution — قد تم بالفعل بواسطة Specialist provider. يمكن لـ Curated datasets توفير Canonical identifiers وعلاقات Pre-resolved.

يمكن لذلك تقليل Internal entity-linking effort بدرجة كبيرة، لكنه يقدم Licensing cost وDependency وData-model lock-in.

يشبه القرار استخدام Managed RAG platform: اشترِ Operational leverage مقابل تحكم أقل وLong-term provider dependency.


## 36. Microsoft GraphRAG: استخدام مختلف للـ Graphs

يُستخدم مصطلح GraphRAG أحيانًا بصورة فضفاضة لأي Graph-enhanced RAG. يستخدمه الفصل بصورة أكثر تحديدًا لنهج Microsoft Research في الإجابة عن Broad sensemaking questions.

صُممت GraphRAG للأسئلة التي تحتاج Global view للـ Corpus بدلًا من استرجاع عدد قليل من Local chunks. فهي تبني Graph من Source documents، وتكتشف Communities، وتلخص هذه Communities، ثم تجيب عن Queries باستخدام Hierarchy من Summaries.

من الأفضل فهمها بوصفها Query-focused summarization فوق Graph-derived communities، لا بوصفها Graph traversal عادية.

## 37. Pipeline فهرسة GraphRAG

تُعد GraphRAG indexing مكلفة حسابيًا لأنها تنفذ عدة Steps كثيفة الـ Reasoning قبل وصول أي User query.

تستخرج Pipeline الـ Entities وRelationships، وتحلها أوتنظمها في Graph، وتشغل Community-detection algorithms، وتولد Summaries على عدة Levels.

الميزة أن Expensive understanding work ينتقل إلى Indexing، مما يمكّن Broad queries لاحقًا. والعيب أن Corpus updates قد تؤدي إلى Reprocessing مكلفة.


## 38. Community Detection وHierarchical Summaries

تجمع Community detection الأجزاء شديدة الاتصال في Graph داخل Coherent clusters. يمكن لكل Cluster أن تمثل Topic أوTheme أوLocal subnetwork داخل Corpus.

ثم ينتج LLM Summaries لهذه Communities. وتلخص Higher-level communities أجزاء أكبر من Graph، مما ينشئ Hierarchy تبدأ من Detailed local structure وتصل إلى Broad themes.

هذه Hierarchy هي ما يجعل Global sensemaking ممكنة: يمكن للنظام Reasoning فوق Summaries للـ Corpus كلها بدلًا من الأمل في أن تمثل Top-k retrieval set صغيرة الصورة العامة.


## 39. GraphRAG Local Search مقابل Global Search

تميز GraphRAG بين Local وGlobal query strategies.

**Local search** تبدأ من Seed entities وتتوسع حول Graph neighborhood الخاصة بها. وهي مناسبة للأسئلة التفصيلية حيث تكون Answer غالبًا قريبة من Entities محددة.

**Global search** تعمل فوق Community summaries أوسع، وهي مناسبة لـ High-level synthesis عبر Corpus.

يعكس هذا التمييز مبدأ Retrieval عامًا: اختر Search strategy تتوافق مع Scope السؤال.

## 40. تكلفة GraphRAG

قد تتطلب GraphRAG عددًا كبيرًا من LLM calls أثناء Indexing. حتى Demonstration الصغيرة في الفصل تتسبب في Cost وRuntime ملحوظتين، مما يوضح مدى سرعة نمو ذلك على Enterprise-scale corpora.

الدرس المهم ليس Dollar value الدقيقة لمثال واحد. بل إن GraphRAG تحول Indexing من Pipeline موجهة غالبًا إلى Embeddings إلى Multi-stage LLM processing job.

يجعل ذلك Cost estimation وBatching وRefresh strategy وEvaluation عناصر أساسية قبل تبنيها على نطاق واسع.

## 41. متى تكون GraphRAG الأداة الخاطئة؟

تكون GraphRAG غير مناسبة عندما تتغير Corpus بسرعة، أوعندما تكون Interactive latency حرجة، أوعندما تتطلب Queries Evidence حرفية دقيقة، أوعندما تكون معظم الأسئلة Simple factual lookups.

تكون Community summaries الخاصة بها Abstract عمدًا. وهذا مفيد للـ Broad themes، لكنه قد يكون Lossy أكثر من اللازم لـ Legal أوAudit أوCitation-heavy workflows.

لذلك يمكن لـ System استخدام GraphRAG بصورة انتقائية لـ Sensemaking، مع الاحتفاظ بـ Ordinary RAG لاسترجاع Evidence الدقيقة.

## 42. Graph Database Infrastructure التزام طويل الأجل

تضيف Graph database نظامًا Stateful جديدًا يجب Deploy له، وتأمينه، وMonitoring له، وأخذ Backups منه، وترقيته، والحفاظ على تزامنه مع Source data المتغيرة.

تستمر Operational cost بعد أول Demo ناجحة بوقت طويل. يعتمد Graph performance بدرجة كبيرة على Memory وIndex design وTraversal patterns وشكل Graph.

قبل إضافة Graph، ينبغي أن يسأل Team ما إذا كان يمتلك خبرة Data engineering وDatabase اللازمة لتشغيلها مع مرور الوقت.


## 43. نماذج نشر Graph (Graph Deployment Models)

يوضح الفصل ثلاثة Infrastructure models عامة.

يوفر **Traditional server or cluster** أقصى Control، لكنه يتطلب من Team إدارة Stateful infrastructure.

أما **Managed cloud graph service** فتنقل جزءًا كبيرًا من Operational burden إلى Provider، لكنها تضيف Cloud cost واعتمادًا على Provider.

وتعمل **Embedded graph library** داخل Application، وقد تكون جذابة لـ Graphs أصغر ومعظمها Read-only، لكنها تنقل التحدي إلى Build وDeployment lifecycle management.

يعتمد أفضل Model على Graph size وUpdate frequency وSecurity constraints وOperations maturity.

## 44. Knowledge-Graph ETL وIdempotency

تكون Graph ingestion معرضة لـ Partial failures لأنها غالبًا تتضمن عددًا كبيرًا من Node وEdge operations المترابطة.

ينبغي أن تكون Restartable pipeline قابلة لإعادة التنفيذ دون آثار جانبية: إعادة تشغيل Operation نفسها يجب أن تصل إلى Graph نفسها بدلًا من مضاعفة Entities أوRelationships.

في Cypher، تُعد `MERGE` أداة شائعة لذلك لأنها تتحقق من Matching pattern قبل إنشائها. ومع Batching، تسمح Idempotency لعمليات بناء Graph كبيرة بالتعافي من Failure دون Transaction واحدة ضخمة.

## 45. تطور Schema (Schema Evolution)

على الرغم من أن Graph databases توصف غالبًا بأنها Flexible أوSchema-light، فإن تطبيقات RAG تظل تعتمد على Graph structure يمكن توقعها.

إذا تغيرت Labels أوProperties أوRelationships، فيجب أن تتطور معها Logic الخاصة بـ Graph-query generation في LLM. وقد تحتاج Migrations إلى تحديث ملايين Nodes وEdges الموجودة.

لذلك تنتمي Schema versioning إلى Change-management discipline نفسها الخاصة بـ Code وPrompts.


## 46. Graph Performance وSupernodes

تعتمد Traversal cost على Graph depth وTopology. ترتبط بعض Nodes بعدد هائل من Neighbors — وتسمى Supernodes — ويمكنها جعل Traversals تبدو بسيطة لكنها مكلفة.

يشمل Performance engineering: Profiling للـ Queries، وIndexing للـ Properties التي يتم Filter عليها كثيرًا، وتقييد Traversal depth، وإعادة هيكلة Hot paths، وتوفير Memory كافية للـ Working graph.

هذا عمل Database متخصص وينبغي إدراجه في Staffing وCost model للمشروع.


## 47. Security وBackup وHigh Availability

قد تجمع Graph database علاقات حساسة من Systems كثيرة، مما يجعل Access control مهمًا بصورة خاصة.

يجب أن يشمل Security: Encryption وBackups وRestore testing وHigh availability وRole-based authorization. وفي بعض Applications قد يلزم تطبيق Permissions على مستوى Node أوRelationship أوProperty.

يمكن لـ Graph تسمح لـ LLM باجتياز Relationships عبر Departments أن تسبب Data leakage إذا لم تُفرض Permissions قبل وصول Information إلى Generation.


## 48. الحفاظ على Living Graph

يجب أن تتطور Production graph المفيدة مع العالم الحقيقي. تصبح Full rebuilds غير عملية مع نمو Graph واستمرار Source systems في التغير.

لذلك يحتاج System إلى Incremental update mechanisms تضيف Facts وتعدلها وتضعها خارج الخدمة وتدمجها دون إفساد Existing structure.

التحدي ليس Freshness فقط. فقد يلزم الحفاظ على Historical facts حتى عندما تتغير Current status الخاصة بها.


## 49. CDC مقابل Event-Driven Graph Updates

يمكن لـ Structured database sources استخدام Change Data Capture (CDC) لمراقبة Inserts وUpdates وDeletes وتحويلها إلى Graph operations.

وغالبًا ما تناسب Unstructured sources نمط Event-driven. فوصول New document إلى Object storage يمكن أن يطلق Extraction لذلك Document فقط، منتجًا Incremental nodes وEdges.

يتجنب النمطان إعادة بناء Graph بالكامل ويجعلان Freshness أسهل إدارة.

## 50. التعامل مع Entity Merges

ستكتشف Graph تعمل لفترة طويلة في النهاية أن Nodes اثنتين تمثلان Real-world entity نفسها. يجب على System دمجهما دون فقد Valid relationships.

عادةً يختار Merge واحدة Canonical survivor node، ثم يعيد توجيه Relationships الخاصة بالـ Node الأخرى، ويصالح Properties، ويزيل Duplicate أويوجهها.

ولأن Merges تغير Graph topology، فينبغي أن تكون Observable وقابلة للـ Audit.


## 51. Fact Lifecycle وTombstoning

لا ينبغي حذف بعض Facts عندما تتوقف عن كونها Current. فعلاقة Employment سابقة مثلًا قد تظل مفيدة تاريخيًا حتى بعد أن تصبح Inactive.

أحد الأنماط هو وسم Relationship بـ Status أوValidity metadata بدل حذفها. تستطيع Queries التي تسأل عن Present عندها Filter للعلاقات Active، بينما تحتفظ Historical queries بالوصول إلى Past.

هذا أساسي للأسئلة Time-bound ولـ Auditability.


## 52. المقايضة بين Accuracy وCost

Knowledge-enhanced RAG استثمار معماري. الفائدة المتوقعة هي Accuracy أعلى في Queries التي تعتمد على Relationships أوConstraints أوGlobal structure. أما Cost فهي Data modeling وETL وInfrastructure وEvaluation وSecurity وLong-term maintenance إضافية.

لذلك ليست Baseline الصحيحة «Graphs أكثر تقدمًا». بل «هل Standard أوHybrid RAG تلبي المتطلب بالفعل؟»

ينبغي فقط لـ Measured failure modes أن تبرر Graph layer الإضافية.


## 53. KG ROI Checklist عملية

يقترح الفصل تقييم عدة شروط قبل القيام باستثمار كبير في KG:

- هل يفشل Standard RAG بصورة متكررة في أسئلة Multi-hop أوTime-bound أومقيدة بشدة؟
- هل يحتاج Domain إلى Deterministic grounding حول Entities مهمة؟
- هل توجد Ontology أوCurated graph قائمة تقلل Construction effort؟
- هل يستمد Domain قيمة طبيعية من Relationships؟
- هل تستطيع المؤسسة امتلاك Graph modeling وETL على المدى الطويل؟
- هل ترتبط Accuracy gains المتوقعة بـ Concrete business value؟

تعمل هذه Checklist كأداة تفرض Architecture decisions منضبطة.

## 57. تشخيص حالات فشل Knowledge-Enhanced RAG

عندما تكون Answer خاطئة، اعزل Layer التي فشلت.

إذا كانت Correct relation غائبة عن Graph، فقد فشلت Construction pipeline. وإذا قسمت Duplicate entities الـ Relationship path، فقد فشلت Entity linking. وإذا كانت Graph تحتوي Answer لكن Generated Cypher لا تسترجعها، فقد فشلت Query generation. وإذا كانت Graph وQuery صحيحتين لكن Final answer خاطئة، فقد فشلت Generation layer.

يمنع هذا Layered diagnosis الـ Team من «إصلاح Prompt» عندما تكون المشكلة الحقيقية Data quality أوGraph maintenance.

## 58. مفاهيم خاطئة شائعة

**«Knowledge graph أدق تلقائيًا من Vector search.»**  
لا يمكن أن تكون Graph أكثر موثوقية من Entities وRelationships وUpdate pipeline الخاصة بها. يمكن لـ Graph خاطئة أومجزأة أن تنتج Answers Deterministic لكنها غير صحيحة.

**«GraphRAG تعني أي RAG system يستخدم Graph.»**  
يستخدم المصدر *GraphRAG* تحديدًا لنهج Microsoft Research المعتمد على Communities وQuery-focused summarization. أما KG-enhanced RAG العادية فتشمل Patterns أخرى مثل Chunk enrichment وHybrid graph retrieval.

**«إذا كان LLM يستطيع توليد Cypher، فقد حُل Graph retrieval.»**  
تضيف Text-to-Cypher Failure surface جديدة. يحتاج LLM إلى Current schema، وما تزال Execution layer تحتاج Validation وLeast privilege وTimeouts وLimits.

**«Entity extraction هي الجزء الصعب؛ Entity linking سهلة.»**  
في Enterprise data، يكون تحديد أن عدة Names تشير إلى Real-world entity نفسها غالبًا من أصعب المشكلات وأكثرها استمرارًا.

**«Graph تلغي الحاجة إلى Chunking وVector retrieval.»**  
غالبًا ما يحتفظ Knowledge-enhanced RAG بـ Ordinary chunking وEmbeddings وHybrid search وReranking. تضيف Graph Structure؛ ولا تمحو Text pipeline.

**«GraphRAG مثالية لكل Enterprise corpus واسعة.»**  
قد تكون GraphRAG مكلفة في Indexing وMaintenance، وقد تكون Summaries الخاصة بها Lossy أكثر من اللازم لـ Verbatim-citation workloads أوWorkloads التي تتغير بسرعة.

**«حذف Facts المنتهية هو دائمًا التصرف الصحيح.»**  
قد تحتاج Historical questions إلى Relationships قديمة. غالبًا تكون Status fields أوTemporal validity أكثر أمانًا من Destructive deletion.

**«Schema-less تعني أن Schema management غير مهمة.»**  
ما يزال Application وText-to-query prompt يعتمدان على Labels وRelationships وProperties مستقرة. تحتاج Schema changes إلى Versioning وMigration discipline.

| مصطلح SPARQL | Standard query language لـ RDF graphs وTriple stores |
| مصطلح Ontology | Conceptual model والقواعد التي تعرّف Domain |
| مصطلح Schema | Implementation على مستوى Database للـ Labels وRelationships وProperties |
| مصطلح Chunk enrichment | إضافة Structured context مشتقة من Graph إلى Chunk استرجعتها Ordinary RAG |
| مصطلح Hybrid graph retrieval | دمج Graph-query results مع Vector أوHybrid text retrieval |
| مصطلح Text-to-Cypher | ترجمة Natural-language questions إلى Cypher queries |
| مصطلح Entity identification | اكتشاف Entity mentions وTypes الخاصة بها في Source data |
| مصطلح Relation extraction | تحويل Statements إلى Typed relationships |
| مصطلح Entity linking | ربط Mentions أوAliases متعددة بـ Canonical entity واحدة |
| مصطلح Canonical entity | Authoritative graph node التي تمثل Real-world thing |
| مصطلح Community detection | تجميع Graph regions كثيفة الاتصال |
| مصطلح GraphRAG | في هذا الدرس، نهج Microsoft Research القائم على Graph/Communities وQuery-focused summarization |
| مصطلح Local search | بحث GraphRAG المتمركز حول Local graph neighborhoods |
| مصطلح Global search | بحث GraphRAG فوق Broad community summaries |
| مصطلح Idempotency | خاصية تسمح بإعادة محاولة Ingestion task دون إنشاء Duplicate side effects |
| مصطلح CDC | Change Data Capture التي تحول تغييرات Source database إلى Downstream update events |
| مصطلح Tombstoning | وسم Fact بأنها Inactive أوExpired دون حذف وجودها التاريخي |
| مصطلح Supernode | Graph node ذات عدد استثنائي من Connections قد تنشئ Traversal hotspots |
| مصطلح Provenance | Metadata توضح من أين جاءت Evidence وكيف تم Transform لها |

## 60. احتفظ بهذا النموذج الذهني

**تسأل Vector search:** *ما Text المتشابه دلاليًا؟*  
**وتسأل Keyword search:** *ما Text الذي يحتوي Terms الدقيقة؟*  
**وتسأل Knowledge graph:** *أي Entities متصلة بالعلاقات المطلوبة؟*  
**وتسأل GraphRAG:** *ما Global structure والThemes التي تظهر عبر Corpus؟*  
**وتسأل Agentic RAG:** *ما Sequence من Retrieval وTool-use steps التي ينبغي تنفيذها لحل هذه Task؟*

ينبغي لـ Production system توجيه كل Query نحو أبسط Mechanism تستطيع الإجابة عنها بصورة موثوقة.

تستحق Graph مكانها فقط عندما تكون Accuracy المكتسبة من Explicit structure جديرة بالهندسة المطلوبة لبناء هذا Structure وربطه وتحديثه وتأمينه وتشغيله.
