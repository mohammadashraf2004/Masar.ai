## 1. لماذا يهم تحسين Inference

يمكن أن تكون Model عالية الدقة ومع ذلك تفشل كمنتج إذا كانت بطيئة جدًا أو مكلفة جدًا عند الاستخدام.

يضع الفصل تحسين Inference حول هدفين عمليين:

- **أسرع:** تقليل Response Latency.
- **أقل تكلفة:** استخدام Hardware و Model Capacity بكفاءة أعلى.

يمكن أن يحدث Optimization على ثلاثة مستويات:

1. **مستوى Model** — تغيير Model أو Computation الخاصة بها.
2. **مستوى Hardware** — استخدام Hardware أكثر ملاءمة لـ Workload.
3. **مستوى Service** — توزيع Resources وجدولة Requests بكفاءة أعلى.

تتفاعل هذه المستويات. فقد تتسع Quantized Model على Hardware أقل تكلفة. وقد يزيد Serving Scheduler أفضل من Utilization دون تغيير Model Weights.

## 2. ما الذي تفعله Inference Service

يبني **Training** Model أو يحدّثها. أما **Inference** فتستخدم Model مدرَّبة لحساب Outputs من Inputs.

في Production، يستضيف **Inference Server** Models وينفذ Forward Passes الخاصة بها على Hardware المتاحة.

يمكن لـ **Inference Service** الأوسع أيضًا أن:

- تستقبل Requests.
- توجه Requests إلى Models أو Servers.
- تنفذ Preprocessing للـ Inputs.
- تجدول Work.
- تنفذ Streaming للـ Outputs.
- تتبع Resource Usage.

تُعد Commercial Model APIs أمثلة على Inference Services. وإذا نفذت Self-hosting لـ Model، فإنك تتحمل مسؤولية أكبر بكثير عن هذه الطبقة.

## 3. ابدأ بتحديد عنق الزجاجة

ينبغي أن يستهدف Optimization الجزء الذي يحد فعليًا من Performance.

يقدم الفصل نوعين رئيسيين من Computational Bottlenecks.

### مقيد بالحوسبة (Compute-bound)

يكون Runtime محدودًا أساسًا بكمية العمليات الحسابية التي تستطيع Hardware تنفيذها.

تشمل الاستجابات المفيدة:

- المزيد من Compute Units.
- Accelerators أسرع.
- Parallelism أكبر.
- Kernels أفضل.

### مقيد بـ Memory Bandwidth

يكون Runtime محدودًا أساسًا بسرعة نقل Data بين Memory و Compute Units.

تشمل الاستجابات المفيدة:

- Hardware ذات Bandwidth أعلى.
- Models أصغر أو Precision أقل.
- Caching أفضل.
- Memory Layout أفضل.
- عمليات نقل متكررة أقل للـ Memory.

يُستخدم مصطلح **Memory-bound** أحيانًا بصورة غامضة ليشير إما إلى قيود Bandwidth أو Capacity. ويؤكد الفصل أن حتى مشكلات Capacity غالبًا ما تتحول إلى مشكلات Bandwidth عندما يلزم نقل Data بين CPU Memory و GPU Memory.

## 4. Arithmetic Intensity وفكرة Roofline

تعني **Arithmetic Intensity** بصورة تقريبية:

```text
arithmetic operations / bytes of memory accessed — عدد العمليات الحسابية لكل Byte يتم الوصول إليه من Memory
```

تعني Arithmetic Intensity المنخفضة أن Hardware تقضي نسبة كبيرة من وقتها في نقل Data مقارنة بإجراء العمليات الحسابية. أما Arithmetic Intensity المرتفعة فتعني تنفيذ Computation أكثر لكل Byte يتم تحميله.

يساعد **Roofline Chart** على تحديد ما إذا كانت Workload محدودة بـ Compute أو Memory Bandwidth.

وهذا مهم لأن Arithmetic Unit أسرع لن تفيد كثيرًا Workload تنتظر Memory، كما أن Bandwidth إضافية قد لا تفيد كثيرًا Workload يهيمن عليها الحساب بالفعل.

[[IMAGE_NEEDED: Roofline model intuition | A simplified roofline graph with a bandwidth-limited rising region and compute-limited flat region | Learner should notice that optimization depends on which side of the bottleneck the workload occupies]]

## 5. تحتوي LLM Inference على مرحلتين مختلفتين جدًا

تنقسم Transformer-based Autoregressive Language-model Inference عادةً إلى:

### مرحلة Prefill

تعالج Model Input Tokens بدرجة كبيرة بالتوازي وتجهز Attention State المستخدمة في Generation.

تكون Prefill عادةً **Compute-bound**.

### مرحلة Decode

تولد Model Output Tokens واحدة تلو الأخرى.

في كل Step، يجب الوصول إلى Model Weights كبيرة و Attention State. ولذلك تكون Decode غالبًا **Memory-bandwidth-bound**.

يفسر هذا الفرق كثيرًا من التقنيات اللاحقة، ومنها:

- Prefill و Decode Servers منفصلة.
- Optimization لـ TTFT مقابل TPOT.
- Speculative Decoding.
- KV-cache Optimization.

[[IMAGE_NEEDED: Prefill versus decode | A two-phase LLM inference diagram showing parallel input processing during prefill and one-token-at-a-time generation during decode | Learner should notice the different compute profiles]]

## 6. Online APIs مقابل Batch APIs

تعرض Inference Systems غالبًا نمطين عامين من Service.

### Online Inference

تُحسن من أجل Latency منخفضة. وتُعالج Requests بمجرد أن يصبح ذلك عمليًا.

تشمل Use Cases الشائعة:

- Chatbots.
- مساعدو البرمجة التفاعليون (Interactive Coding Assistants).
- التوليد الفوري الموجّه للمستخدم (Real-time User-facing Generation).

### Batch Inference

تُحسن من أجل Cost و Throughput. ويمكن أن تنتظر Requests حتى تتمكن Service من استخدام Batches أكبر أو Hardware أقل تكلفة أو Scheduling أكثر مرونة.

تشمل Use Cases الشائعة:

- توليد البيانات الاصطناعية (Synthetic Data Generation).
- Periodic Reports.
- إعادة معالجة Documents كبيرة.
- مسارات تأهيل العملاء (Customer Onboarding Pipelines).
- Recommendation أو Newsletter Generation.
- إعادة فهرسة قاعدة المعرفة (Knowledge-base Reindexing).

الفرق المهم هو Optimization Objective: **Online -> Latency؛ Batch -> Throughput/Cost**.

## 7. Streaming يغير Latency المدركة

قد تستغرق Autoregressive Generation وقتًا طويلًا حتى تكتمل. يسمح Streaming للتطبيق بإرجاع Tokens فور توليدها بدلًا من انتظار Response كاملة.

الفوائد:

- يرى المستخدم تقدمًا أسرع.
- تتحسن Perceived Responsiveness.

المفاضلة:

- لا يمكن Scoring أو Screening للـ Response كاملة قبل إظهار أول Tokens.

لذلك يحسن Streaming Responsiveness لكنه قد يعقد Safety أو Post-generation Validation.

## 8. مقاييس Latency: TTFT و TPOT و Total Latency

بالنسبة إلى Autoregressive Models، يمكن تقسيم Total Latency إلى أجزاء مفيدة.

### الوقت حتى أول Token (Time to First Token — TTFT)

الوقت من وصول Request حتى ظهور أول Generated Token.

يتأثر TTFT بدرجة كبيرة بمرحلة Prefill، وبالتالي بطول Input.

### الوقت لكل Output Token (Time per Output Token — TPOT)

متوسط Generation Time لكل Token بعد أول Token.

### الوقت بين Tokens أو Inter-token Latency

يقيس الفجوات بين Streamed Tokens.

تقريب بسيط لـ Latency هو:

```text
total latency ≈ TTFT + TPOT × number_of_output_tokens   — زمن الاستجابة الكلي
```

يمكن لنظامين يمتلكان Total Latency نفسها أن يبدوا مختلفين للمستخدم: قد يبدأ أحدهما فورًا لكنه يولد ببطء، بينما ينتظر الآخر مدة أطول ثم يولد بسرعة.

[[IMAGE_NEEDED: TTFT and TPOT timeline | A request timeline marking request arrival, first token, subsequent tokens, and completion | Learner should notice how first-token delay and per-token generation contribute differently to total latency]]

## 9. Model Latency ليست دائمًا User-visible Latency

قد تولد Agentic Applications Plans أو Tool Calls أو Hidden Intermediate Tokens قبل إنتاج أي شيء مرئي للمستخدم.

من منظور Model، بدأت Token Generation بالفعل. ومن منظور المستخدم، لم يظهر شيء بعد.

ولهذا تتبع بعض الفرق Metric مثل **Time to Publish**: الوقت حتى ظهور أول User-visible Output.

قِس التجربة التي يراها المستخدم، لا Model Timings الداخلية فقط.

---

## 10. قِس Latency باعتبارها Distribution

يمكن لمتوسط Latency إخفاء Outliers خطيرة.

تشمل Percentiles المفيدة:

- **p50** — Median.
- **p90** — تكون 90% من Requests أسرع من هذه Value.
- **p95**.
- **p99** — تكشف Tail-latency Problems.

ارسم أيضًا Latency مقابل Workload Variables مثل Input Length. فقد تنتج Prompt طويلة TTFT مرتفعًا بصورة مشروعة، بينما قد تنتج Network Problem Outlier غير متوقعة.

ينبغي أن يهتم Production Optimization بالـ Tail، وليس Average فقط.

---

## 11. Throughput و Request Capacity

يقيس **Throughput** مقدار Work المكتمل لكل Unit Time.

تشمل المقاييس الشائعة:

- Output Tokens per Second أو TPS.
- Input Tokens لكل ثانية (Input Tokens per Second).
- Tokens/s/User.
- Requests per Second أو RPS.
- Completed Requests per Minute أو RPM.

ينبغي غالبًا تتبع Input Throughput و Output Throughput بصورة منفصلة لأن Prefill و Decode تمتلكان Bottlenecks مختلفة.

ترتبط Throughput ارتباطًا وثيقًا بالتكلفة. فإذا أنتجت Hardware نفسها Useful Tokens أكثر في الثانية، فعادةً تنخفض Cost per Token أو Request.

لكن Throughput الأعلى قد تزيد انتظار Requests وتضر Latency.

---

## 12. Goodput: Throughput التي تحقق SLO فعلًا

يمكن لـ Service الإعلان عن Throughput مثيرة للإعجاب بينما تقدم للمستخدمين Latency سيئة.

تحسب **Goodput** فقط Requests التي تحقق Service-level Objective أو SLO محددة.

مثال SLO:

```text
TTFT <= 200 ms
TPOT <= 100 ms
```

إذا أكملت Service عدد 100 Request في الدقيقة لكن 30 فقط حققت الهدفين:

```text
throughput = 100 requests/min   — الطلبات المعالَجة في الدقيقة
goodput    = 30 requests/min    — الطلبات التي حققت الـ SLO فقط
```

تجبر Goodput النظام على تحسين Capacity **وتجربة المستخدم** معًا.

[[IMAGE_NEEDED: Throughput versus goodput | A bar of all completed requests with only the SLO-satisfying portion highlighted as goodput | Learner should notice that raw throughput can overstate useful serving capacity]]

## 13. Utilization ليست رقمًا واحدًا

تقيس Utilization مدى كفاءة استخدام Hardware Capacity، لكن Metrics المختلفة تعني أشياء مختلفة.

توضح GPU Utilization Metric الشائعة عدد مرات نشاط GPU، لا مدى اقترابها من Peak Arithmetic Efficiency.

ولذلك قد تبدو GPU ذات "Utilization" مرتفعة بينما تعمل بأقل كثيرًا من Theoretical Compute Capacity.

هناك Metricان أكثر فائدة:

- **MFU** — Model FLOP/s Utilization.
- **MBU** — استخدام عرض نطاق Model (Model Bandwidth Utilization).

---

## 14. MFU: Model FLOP/s Utilization

تقارن MFU بين Observed Computational Throughput و Theoretical Maximum الخاصة بـ Hardware بالنسبة إلى Workload أو Model.

مفاهيميًا:

```text
MFU = observed model FLOP/s / theoretical peak model FLOP/s   — نسبة الأداء الفعلي إلى الذروة النظرية
```

تهتم Compute-bound Workloads بدرجة كبيرة بـ MFU.

غالبًا تظهر Prefill قيمة MFU أعلى من Decode لأن Decode كثيرًا ما تنتظر Memory Movement بدلًا من Saturating لـ Arithmetic Units.

---

## 15. MBU: استخدام عرض نطاق Model (Model Bandwidth Utilization)

تقيس MBU مقدار Achievable Memory Bandwidth الذي تستخدمه Workload.

يقدم الفصل التقريب المفيد:

```text
bandwidth_used ≈ parameter_count × bytes_per_parameter × tokens_per_second

MBU = bandwidth_used / theoretical_memory_bandwidth
```

مثال:

```text
7B parameters   — حجم Model
× 2 bytes/parameter
× 100 tokens/s
= 1400 GB/s   — عرض نطاق Memory المطلوب
```

الفكرة الأساسية هي أن **Quantization تقلل Bytes per Parameter**، وبالتالي يمكنها تقليل Bandwidth Pressure مباشرة أثناء Decode.

لا تحسن Utilization لمجرد التحسين. يظل الهدف الحقيقي هو Latency أفضل وتكلفة أقل لـ Workload.

## 16. AI Accelerators

الـ **Accelerator** عبارة عن Chip متخصصة لـ Computational Workload. أصبحت GPUs مركزية في Deep Learning لأن Neural-network Operations، وخاصة Matrix Multiplication، يمكن تنفيذها بالتوازي بدرجة عالية.

### الفكرة الأساسية لـ CPU

- عدد أقل من Cores قوية.
- قوية في Sequential أو Control-heavy Work.
- جيدة للسلوك General-purpose و I/O Orchestration.

### الفكرة الأساسية لـ GPU

- عدد كبير من Cores أصغر.
- مصممة لـ Massive Parallelism.
- قوية في Matrix أو Tensor Operations.

توجد AI Accelerators أخرى، وبعضها يتخصص بدرجة أكبر في Inference أو Model Operations محددة.

---

## 17. ما الذي تقارنه في Accelerator؟

يسلط الفصل الضوء على ثلاثة أبعاد رئيسية للقدرات إضافة إلى Power.

### القدرة الحسابية (Compute Capability)

تُمثل غالبًا بـ FLOP/s لمختلف Numerical Formats.

يمكن لـ Lower Precision السماح بعدد أكبر بكثير من Operations في الثانية على Hardware المتوافقة.

### حجم Memory

يحدد ما إذا كانت Model Weights و Caches و Batches تتسع.

### Memory Bandwidth

تحدد سرعة نقل Data بين Memory و Compute Units.

### استهلاك الطاقة (Power Consumption)

يؤثر في Infrastructure Cost و Cooling و Environmental Impact.

اختبار مفيد لاختيار Hardware هو:

1. هل تستطيع تشغيل Workload؟
2. كم تستغرق Workload؟
3. ما تكلفتها؟

---

## 18. التسلسل الهرمي لـ Accelerator Memory

تتعامل AI Accelerators مع عدة مستويات من Memory.

### CPU أو System Memory

- Capacity كبيرة.
- Bandwidth أقل.
- أبعد عن GPU Compute.

### GPU High-bandwidth Memory أو HBM

- أسرع بكثير.
- أصغر وأكثر تكلفة.
- تخزن Model Weights و Active Inference State.

### On-chip SRAM أو Cache أو Registers

- سريعة للغاية.
- صغيرة جدًا.
- مفيدة للـ Data التي يتم الوصول إليها بصورة متكررة.

يركز قدر كبير من GPU Optimization أساسًا على تقليل Data Movement المكلفة عبر هذا التسلسل الهرمي.

[[IMAGE_NEEDED: Accelerator memory hierarchy | A memory pyramid showing CPU DRAM at large/slow bottom, GPU HBM in the middle, and small/fast on-chip SRAM/registers at the top | Learner should notice the capacity-versus-bandwidth tradeoff across memory levels]]

## 19. اختر Hardware وفق Workload الفعلية

إذا كانت Workload Compute-bound، فقد تساعد FLOP/s إضافية.

أما إذا كانت Bandwidth-bound، فقد تكون Memory Bandwidth و Model Size أو Precision أهم من Advertised Peak Compute.

لا تشترِ Hardware بناءً على Headline Number واحدة. قِس Model نفسها و Precision و Sequence Lengths و Batch Sizes و Traffic Pattern التي تتوقع Serving لها.

## 20. Optimization على مستوى Model: Compression

تقلل Model Compression مقدار Computation أو Storage المطلوب لـ Inference.

يناقش الفصل ثلاث عائلات مهمة.

### Quantization

مثّل Weights باستخدام Bits أقل.

- Memory Footprint أقل.
- Bandwidth Pressure أقل.
- غالبًا Throughput أعلى.
- احتمال انخفاض الجودة.

### Distillation

درّب Student Model أصغر لتقليد Teacher أكبر.

### Pruning

أزل Network Components أو اجعل Parameters منخفضة القيمة تساوي صفرًا، مما ينشئ Model أصغر أو أكثر Sparse.

يبدو Pruning جذابًا نظريًا لكنه قد يكون أصعب في الاستفادة منه عمليًا لأن Hardware يجب أن تدعم Sparsity الناتجة بكفاءة.

## 21. عنق زجاجة Autoregressive Decoding

تنتج Autoregressive Language Model عادةً Token واحدة في كل مرة:

```text
token 1 -> token 2 -> token 3 -> ...   — توليد الرموز واحدًا تلو الآخر
```

تعتمد كل Token جديدة على Context السابقة. تجعل هذه Sequential Dependency عملية Output Generation مكلفة وبطيئة.

يمكن أن تكون Output Tokens مكلفة بصورة خاصة لأن Decode تصل مرارًا إلى Model كاملة بينما تولد Token جديدة واحدة فقط في كل Step.

يدفع هذا Bottleneck إلى تقنيات تحاول التحقق من عدة Tokens دفعة واحدة أو توليد Future-token Candidates متعددة بالتوازي.

## 22. Speculative Decoding

تستخدم Speculative Decoding Modelين:

- **Draft Model:** سريعة وأضعف.
- **Target Model:** أبطأ وأقوى؛ وسلوكها هو السلوك الذي تريده.

الحلقة الأساسية:

1. تقترح Draft Model عدد `K` من Tokens.
2. تتحقق Target Model من هذه Tokens بالتوازي.
3. اقبل أطول Prefix توافق عليها Target.
4. تنتج Target Token إضافية واحدة.
5. كرر.

يساعد ذلك لأن Verification لعدة Proposed Tokens يمكن أن يكون أكثر Parallel من توليدها بصورة Sequential.

يعمل الأسلوب أفضل عندما تمتلك Draft Model Acceptance Rate مرتفعة. وقد يكون Structured Text مثل Code مناسبًا بصورة خاصة لهذه الطريقة.

## 23. الـ Inference باستخدام Reference (Inference with Reference)

تظهر نسبة كبيرة من Output أحيانًا بالفعل داخل Input.

أمثلة:

- تعديل Code مع إبقاء معظم Lines دون تغيير.
- الاقتباس من Retrieved Document.
- متابعة Conversation مع Context متكررة.

بدلًا من مطالبة Model أخرى باقتراح Tokens، تحاول **Inference with Reference** إعادة استخدام Candidate Token Spans مباشرة من Input.

تتجنب Draft Model إضافية، لكنها تكون مفيدة أساسًا عندما يكون التداخل بين Input و Output مرتفعًا.

---

## 24. Parallel Decoding

تحاول Parallel-decoding Methods توقع عدة Future Tokens في الوقت نفسه، مما يقلل الاعتماد الصارم على Token واحدة في كل مرة.

تشمل أمثلة الفصل:

- Lookahead أو Jacobi-style Decoding.
- رؤوس فك ترميز إضافية بأسلوب Medusa (Medusa-style Extra Decoding Heads).

وبما أن Future Tokens يتم توقعها دون معرفة جميع Preceding Generated Tokens، تكون Verification Step مطلوبة.

النمط العام هو:

```text
توقّع عدة Future Tokens
 -> تحقّق من Consistency
 -> احتفظ بالـ Valid Tokens
 -> أصلح/أعد حساب Invalid Tokens
```

يمكن لهذه التقنيات توفير Speedups لكنها أكثر تعقيدًا في التنفيذ من Ordinary Autoregressive Decoding.

## 25. KV Cache

تحتاج Transformer Attention مرارًا إلى Key و Value Vectors من Tokens السابقة.

من دون Caching، كانت Model ستعيد حسابها مرة بعد أخرى أثناء Decoding.

تخزن **KV Cache** الـ Key أو Value Vectors السابقة حتى تحتاج كل Generation Step فقط إلى حساب Vectors جديدة لأحدث Token.

يسرّع KV Caching الـ Decode لكنه ينشئ مشكلة Memory:

- Context أطول -> Cache أكبر.
- Batches أكبر -> Cache أكبر.
- Layers أكثر -> Cache أكبر.
- Hidden Dimension أكبر -> Cache أكبر.

تُعد KV Cache من اهتمامات Inference؛ أما Training فيعرف Sequence كاملة ولا يستخدم Sequential Inference Cache نفسها.

[[IMAGE_NEEDED: KV-cache reuse | Several decoding steps where old K/V vectors remain cached and only the newest token's K/V is added | Learner should notice that caching removes recomputation but grows memory over the sequence]]

## 26. حساب Memory الخاصة بـ KV Cache

يقدم الفصل التقريب غير المحسن:

```text
KV cache bytes = 2 × B × S × L × H × M   — حجم KV Cache بالبايت
```

حيث:

- `B` = Batch Size.
- `S` = Sequence Length.
- `L` = عدد Transformer Layers.
- `H` = Model أو Hidden Dimension.
- `M` = Bytes لكل Cached Value.
- العامل `2` يمثل Keys و Values.

تجعل هذه المعادلة مشكلة Scaling واضحة. فمضاعفة Batch Size أو Context Length تضاعف KV-cache Memory.

بالنسبة إلى Long-context Serving، يمكن لـ KV-cache Memory أن تصبح بأهمية Model Weights نفسها أو حتى أكبر منها.

## 27. إعادة تصميم Attention لتقليل تكلفة KV

تغير بعض Optimizations الـ Model Architecture ولذلك يجب عمومًا إدخالها أثناء Training أو Finetuning.

### Local أو Windowed Attention

احضر فقط إلى Nearby Window ثابتة بدلًا من Entire History.

### الانتباه متعدد الاستعلامات (Multi-query Attention — MQA)

شارك Key أو Value Vectors عبر Query Heads.

### الانتباه بالاستعلامات المجمّعة (Grouped-query Attention — GQA)

اجمع Query Heads في Groups وشارك Key أو Value Pairs داخل كل Group، لتحقيق توازن بين توفير Memory و Representational Flexibility.

### الانتباه عبر الطبقات (Cross-layer Attention)

شارك Key أو Value Representations عبر Adjacent Layers.

تهاجم جميع هذه Methods المشكلة نفسها: تقليل عدد أو Lifetime الخاصة بـ Key أو Value States المطلوبة أثناء Inference.

## 28. إدارة KV Cache و PagedAttention

حتى دون إعادة تصميم Attention، تستطيع Serving System إدارة KV Memory بكفاءة أعلى.

### PagedAttention

قسّم KV-cache Memory إلى Blocks غير Contiguous بدلًا من طلب Contiguous Allocation كبيرة لكل Sequence.

تشمل الفوائد:

- Fragmentation أقل.
- Memory Sharing أفضل.
- Allocation أكثر مرونة مع نمو Sequences وانتهائها.

تشمل الأساليب الأخرى المذكورة:

- KV-cache Quantization.
- ضغط KV Cache التكيّفي (Adaptive KV-cache Compression).
- Selective KV Caching.

الهدف هو استيعاب Concurrent Useful Work أكبر داخل Accelerator Memory محدودة.

## 29. Attention Kernels و FlashAttention

يحافظ مسار Optimization آخر على Attention Algorithm نفسها مفاهيميًا لكنه يغير **كيفية تنفيذ Computation على Hardware**.

تُعد FlashAttention مثالًا معروفًا على Hardware-aware Attention Kernel. فهي تقلل Memory Movement غير الضرورية وتنفذ Fusion للـ Operations بحيث تعمل Attention بكفاءة أعلى على Modern Accelerators.

يوضح ذلك مبدأ Systems عامًا:

> يمكن لـ Mathematics متكافئة أن تعمل بسرعات مختلفة جدًا اعتمادًا على Memory Layout و Operation Ordering و Hardware-specific Implementation.

## 30. Kernels: Code محسنة قريبة من Hardware

الـ **Kernel** هي Code متخصصة ومحسنة لـ Accelerator و Computational Operation متكررة.

تشمل ML Kernels الشائعة:

- Matrix Multiplication.
- Attention.
- Convolution.

يتطلب Kernel Optimization فهم Hardware Memory Hierarchy و Threading و Movement الخاصة بالـ Data بين Registers و Caches و Shared Memory و Global Memory.

تشمل Languages أو Tools المذكورة في الفصل Low-level GPU Ecosystems مثل CUDA و Triton و ROCm.

---

## 31. أربع تقنيات شائعة لتحسين Kernels

### Vectorization

عالج عدة Data Values متجاورة لكل Instruction أو Operation بدلًا من Element واحدة في كل مرة.

### Parallelization

قسّم أجزاء Work المستقلة عبر Threads أو Cores.

### Loop Tiling

أعد ترتيب Computation وقسمها إلى Blocks بحيث تبقى Data المستخدمة بصورة متكررة داخل Memory أو Cache أسرع.

### Operator Fusion

ادمج عدة Operators في Hardware Pass واحدة حتى لا تضطر Intermediate Values إلى أن تُكتب مرارًا إلى Memory أبطأ ثم يعاد تحميلها.

تستهدف هذه التقنيات **Data Movement** بقدر استهدافها Arithmetic.

## 32. Compilers تربط Model Graphs بـ Hardware

يتم التعبير عن Model على هيئة Operations. أما Hardware فتنفذ Lower-level Instructions.

**Lowering** هي عملية تحويل High-level Model Operations إلى Code تستطيع Target Hardware Architecture تنفيذها بكفاءة.

يمكن لـ Compiler أن:

- تعيد كتابة Graphs.
- تدمج Operators.
- تختار Optimized Kernels.
- تخصص Execution وفق Shapes و Devices.

يذكر الفصل أنظمة Compiler مستقلة ومتكاملة، بما فيها `torch.compile`-style Compilation و XLA/OpenXLA و TensorRT-related Compilation و TVM و MLIR-style Infrastructure.

تهم Compilers لأن Hand-optimizing لكل Model أو Hardware Combination لا يمكن أن يتوسع بصورة عملية.

## 33. Optimization على مستوى Service

يركز Service-level Optimization على كيفية جدولة Requests فوق Compute و Memory Resources ثابتة.

وعلى خلاف Model-level Techniques، تترك Service-level Methods عادةً Model Weights وسلوكها دون تغيير.

تشمل Service-level Techniques المهمة في الفصل:

- Batching.
- Prefill أو Decode Disaggregation.
- Prompt Caching.
- Parallelism.

## 34. Batching: مشاركة Hardware بين Requests

تعالج Batching عدة Requests معًا، مما يزيد Hardware Efficiency.

المفاضلة مألوفة:

- Batches أكبر أو أكثر كفاءة -> Throughput أعلى أو Cost أقل.
- انتظار تكوين Batches -> احتمال Latency أعلى.

يناقش الفصل ثلاث Batching Strategies مهمة.

---

## 35. Static و Dynamic Batching

### Static Batching

انتظر حتى تمتلئ Batch Size ثابتة.

الميزة:

- Full Batches يمكن توقعها.

العيب:

- قد تنتظر Requests المبكرة وقتًا طويلًا حتى تصل Requests اللاحقة.

### Dynamic Batching

نفّذ المعالجة عندما:

- تمتلئ Batch، أو
- تنتهي Maximum Waiting Window.

يضع ذلك حدًا لـ Queueing Latency لكنه يشغّل أحيانًا Batches غير ممتلئة.

[[IMAGE_NEEDED: Static versus dynamic batching | A timeline of arriving requests where static waits for a full batch and dynamic launches when full or timeout occurs | Learner should notice the throughput-versus-queueing-latency tradeoff]]

---

## 36. Continuous Batching

يمكن لـ Naive Batching أن تجعل Generations القصيرة تنتظر Generations طويلة داخل Batch نفسها.

تسمح **Continuous Batching** للـ Requests المكتملة بالخروج فورًا، ولدخول Requests جديدة إلى Batch Slots المتاحة بينما تستمر Requests الأخرى في Decoding.

يحسن ذلك Occupancy دون إجبار كل Request على امتلاك Output Length نفسها.

وهو مهم بصورة خاصة لـ LLM Serving لأن أطوال Responses تختلف بدرجة كبيرة.

[[IMAGE_NEEDED: Continuous batching | A batch-slot timeline where one request finishes early and is immediately replaced by a new request while longer requests continue | Learner should notice why variable-length workloads benefit from in-flight batching]]

---

## 37. افصل Prefill عن Decode

تتنافس Prefill و Decode على Resources مختلفة:

- Prefill تريد Compute.
- Decode تريد Memory Bandwidth.

تشغيلهما على GPU واحدة مشبعة يمكن أن يسبب Interference.

تستخدم Disaggregated Serving Architecture Instances منفصلة للمرحلتين:

```text
Request -> Prefill Workers -> نقل Intermediate State -> Decode Workers
```

تعتمد النسبة الصحيحة بين Prefill Workers و Decode Workers على Input Length و Output Length وما إذا كان المنتج يعطي الأولوية لـ TTFT أو TPOT.

هذا مثال على تحسين Service حول Computational Profile الخاصة بـ Model.

---

## 38. Prompt Caching

تشترك Requests كثيرة في Prompt Prefixes كبيرة:

- System Prompts.
- Long Document نفسها.
- Messages السابقة في Conversation طويلة.
- Few-shot Examples مشتركة.

تخزن **Prompt Cache** أو **Prefix/Context Cache** الـ Processed State لهذه Segments حتى لا تعيد Service حسابها لكل Request.

يمكن لـ Prompt Caching تقليل Input-processing Latency و Cost بدرجة كبيرة للتطبيقات التي تحتوي على Prefixes طويلة ومتكررة.

المفاضلة هي Memory أو Storage: تستهلك Cached Context نفسها Resources ويجب إدارتها.

## 39. Replica Parallelism

أبسط Parallelism Strategy هي إنشاء عدة نسخ كاملة من Model.

تخدم كل Replica Requests مختلفة.

الفوائد:

- Requests متزامنة أكثر.
- Mental Model بسيطة.
- يمكن تقليل Queueing و Latency إذا كانت Hardware إضافية متاحة.

التكلفة:

- تستهلك كل Replica Memory و Hardware.

عندما تتعايش Models كثيرة و GPU Sizes مختلفة، يصبح تحديد أي Replicas توضع على أي Devices مشكلة Resource Placement أو Bin Packing.

---

## 40. Tensor Parallelism

إذا لم تتسع Model واحدة على Device واحدة، أو كنت تريد Latency أقل، فيمكنك تقسيم Tensor Operations الفردية عبر عدة Devices.

بالنسبة إلى Matrix Multiplication، يمكن تقسيم إحدى Matrices حسب Columns أو Rows بحيث تحسب Devices مختلفة أجزاء بالتوازي.

الفوائد:

- Serving لـ Models أكبر من Memory الخاصة بـ Device واحدة.
- احتمال تقليل Operation Latency.

التكلفة:

- يجب أن تتبادل Devices Intermediate Data.
- قد تمحو Communication بعض Speedup.

---

## 41. Pipeline Parallelism

يقسم Pipeline Parallelism الـ Model إلى Sequential Stages توضع على Devices مختلفة.

مفاهيميًا:

```text
دفعة صغيرة (Microbatch) -> الطبقات 1..N/4 -> الجهاز 1
                        -> الطبقات ...   -> الجهاز 2
                        -> الطبقات ...   -> الجهاز 3
                        -> الطبقات الأخيرة -> الجهاز 4
```

يمكن لـ Microbatches مختلفة شغل Stages مختلفة في الوقت نفسه.

يساعد Pipeline Parallelism على استيعاب Models كبيرة ويمكن أن يزيد Throughput، لكن Stage-to-stage Communication الإضافية تزيد Per-request Latency. ولهذا يشير الفصل إلى أنه غالبًا أقل جاذبية لـ Strict-latency Inference من Strategies أخرى.

---

## 42. Context و Sequence Parallelism

تستهدف هذه التقنيات Input Sequences الطويلة.

### Context Parallelism

قسّم أجزاء مختلفة من Input Sequence عبر Devices.

مثال:

```text
النصف الأول من Context  -> Device 1
النصف الثاني من Context -> Device 2
```

### Sequence Parallelism

قسّم Operations المرتبطة بـ Sequence Processing عبر Devices. يستخدم الفصل فكرة إسناد Whole-input Operators مختلفة، مثل Attention و Feedforward Work، إلى Machines مختلفة.

يوضح النهجان أن Long-context Inference يمكن تنفيذ Parallelization لها ليس فقط عبر Model Weights، بل أيضًا عبر Sequence-processing Dimension.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> GPU صاحبة أعلى FLOP/s هي دائمًا أسرع اختيار.

**لماذا هذا خطأ:** يمكن لـ Bandwidth-bound Workloads أن تقضي معظم وقتها في نقل Data بدلًا من تنفيذ Arithmetic.

### المفهوم الخاطئ 2

> وصول GPU Utilization إلى 100% يعني استخدام GPU بكفاءة.

**لماذا هذا خطأ:** لا توضح Activity Percentage مدى قرب Workload من Peak Compute أو Memory-bandwidth Efficiency.

### المفهوم الخاطئ 3

> تعظيم Throughput يعطي أفضل Product Experience تلقائيًا.

**لماذا هذا خطأ:** يمكن لـ Batching زيادة Throughput مع جعل TTFT أو TPOT أسوأ. وغالبًا تكون Goodput أكثر معنى.

### المفهوم الخاطئ 4

> Quantization تقلل Storage Size فقط.

**لماذا هذا خطأ:** يمكن لـ Bytes الأقل لكل Parameter أيضًا تقليل Bandwidth Pressure وزيادة Throughput.

### المفهوم الخاطئ 5

> تجعل Speculative Decoding الـ Target Model غير ضرورية.

**لماذا هذا خطأ:** ما زالت Target Model تتحقق من Draft Tokens وتحدد Output Behavior المقبولة.

### المفهوم الخاطئ 6

> يحل KV Caching مشكلة Long Context بالكامل.

**لماذا هذا خطأ:** يتجنب KV Caching إعادة الحساب، لكن Memory الخاصة به تنمو مع Sequence Length و Batch Size و Layers و Hidden Dimension.

### المفهوم الخاطئ 7

> Model-level Optimization و Service-level Optimization قابلان للاستبدال.

**لماذا هذا خطأ:** يمكن لـ Model-level Methods تغيير Model Behavior؛ بينما تغير Service-level Methods عادةً Scheduling أو Execution مع إبقاء Model نفسها.

### المفهوم الخاطئ 8

> Batches الأكبر أفضل دائمًا.

**لماذا هذا خطأ:** يمكنها تحسين Throughput لكنها تزيد Queueing و Memory Usage و Latency.
