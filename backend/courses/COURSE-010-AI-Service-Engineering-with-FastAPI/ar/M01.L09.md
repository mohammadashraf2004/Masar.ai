## نواتج التعلم (Learning outcomes)

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يمكن حتى للمستخدمين authenticated إساءة استخدام خدمة GenAI.
- تحديد فئات سوء الاستخدام الرئيسية التي تؤثر في مولدات text وimage وaudio وvideo.
- التعرّف إلى فئات الثغرات في LLM التي يقدمها المصدر.
- شرح ما guardrails وأين توضع داخل AI request/response pipeline.
- التمييز بين input guardrails وoutput guardrails.
- تصميم topical وprompt-injection وmoderation وattribute checks مفاهيميًا.
- شرح لماذا ينبغي عدم وضع secrets داخل prompts يمكن للـ Model رؤيتها.
- بناء LLM-based topical classifier بسيطة مع validated output contract.
- تشغيل guardrail وmodel call بصورة concurrent مع الحفاظ على fail-fast path.
- شرح مفاضلة false-positive وfalse-negative في guardrail thresholds.
- وصف evaluator-based output moderation باستخدام criteria وsteps وscores صريحة.
- شرح لماذا تظل guardrails احتمالية وغير مثالية.
- التمييز بين rate limiting وthrottling.
- مقارنة token-bucket وleaky-bucket وfixed-window وsliding-window rate-limiting strategies.
- تطبيق global وendpoint وIP-based وuser-based rate limits مفاهيميًا.
- شرح لماذا تحتاج عدة FastAPI instances موزعة إلى centralized usage counters.
- شرح كيفية تطبيق rate limiting بصورة منفصلة على WebSocket traffic.
- تنفيذ throttling لـ real-time model streams من دون حجب event loop.
- شرح اختلاف infrastructure-level traffic shaping عن application-level throttling.
- دمج security controls في layered defense بدل الاعتماد على mechanism واحدة.

## 1. Authentication لا تمنع سوء الاستخدام

أضافت الدروس السابقة:

- authentication،
- authorization،
- databases،
- concurrency،
- streaming.

تجيب هذه controls عن أسئلة مثل:

```text
من هو المستخدم؟ (Who is the user?)
ما الموارد التي يُسمح له بالوصول إليها؟ (What resources may they access?)
```

لكن يمكن لمستخدم authenticated صالح أن يسيء استخدام GenAI system رغم ذلك.

فمثلًا، قد يحاول مستخدم:

- توليد content مضلل،
- إساءة استخدام generation endpoints مكلفة،
- scrape لكميات كبيرة من output،
- overload للخدمة،
- التلاعب بسلوك Model،
- إرسال external content خبيثة.

إذًا تحتاج production security إلى طبقة أخرى:

> **إدارة الاستخدام والحماية من الإساءة (Usage moderation and abuse protection).**

يجمع المصدر الاستخدامات الخبيثة في فئات واسعة مثل:

- misinformation/disinformation،
- bias amplification/discrimination،
- malicious أوtoxic content generation،
- privacy attacks،
- automated cyberattacks،
- identity theft/social engineering،
- deepfakes/multimedia manipulation،
- الاحتيال والنصب.

يعتمد الخطر الدقيق على modality.

### Modality تغيّر Risk Profile

يشير المصدر إلى patterns مثل:

```text
audio/video
→ مخاطر قوية لانتحال الهوية

image/text
→ sockpuppeting وcontent farming والتزييف

image/video
→ التلاعب بالوسائط وhidden/encoded content
```

والنتيجة الهندسية هي:

> **ينبغي اختيار Guardrails وفق capabilities وأنماط الإساءة المحتملة للنظام الذي تبنيه.**

لا تمتلك text-only coding assistant وpublic deepfake-generation service سطح إساءة الاستخدام نفسه.

## 2. مخاطر Security الخاصة بأنظمة GenAI

يقدم الفصل مجموعة من فئات security risk الخاصة بـ LLM استنادًا إلى إطار OWASP الذي يستخدمه المصدر.

وتشمل:

- prompt injection،
- insecure output handling،
- training-data poisoning،
- model denial of service،
- supply-chain vulnerabilities،
- sensitive-information leakage،
- insecure plug-in/integration design،
- excessive agency،
- overreliance على LLM output،
- model theft.

### Prompt Injection

تحاول input خبيثة التلاعب بسلوك Model.

ويكون الخطر أكبر عندما تستطيع Model الوصول إلى:

- secrets،
- tools،
- databases،
- external systems،
- privileged actions.

### المعالجة غير الآمنة للمخرجات (Insecure Output Handling)

ينبغي عدم الوثوق تلقائيًا في model output.

مثلًا:

```text
مخرجات LLM
→ محلِّل/أداة لاحقة (downstream)
```

إذا افترض downstream system أن output آمنة وصحيحة، فقد تتسبب output malformed في failures أوsecurity problems.

### حجب الخدمة عن النموذج (Model Denial of Service)

قد يحاول attackers استهلاك موارد مفرطة عبر:

- inputs كبيرة،
- repeated requests،
- generations مكلفة،
- استدعاءات متزامنة كثيرة.

ويرتبط هذا مباشرة بـ rate limiting لاحقًا في الدرس.

### تسرّب المعلومات الحساسة

قد تكشف Model أوapplication المحيطة بها عن طريق الخطأ:

- private data،
- proprietary information،
- internal configuration،
- confidential context.

### Excessive Agency

قد يُسمح لـ Model المتصلة بأدوات قوية بأن تفعل أكثر مما ينبغي.

ينبغي لـ secure architecture إبقاء privileged actions خلف deterministic application controls.

### Overreliance

حتى Model محمية جيدًا يمكن أن تنتج output خاطئة.

ينبغي ألا تتعامل applications مع probabilistic model output باعتبارها حقيقة مضمونة.

## 3. ما هي Guardrails؟

يصف المصدر guardrails باعتبارها controls تهدف إلى توجيه application نحو behavior مقبولة.

Architecture مبسطة ومفيدة:

```text
مدخلات المستخدم
    ↓
Input guardrails
    ↓
النموذج
    ↓
Output guardrails
    ↓
المستخدم / نظام لاحق
```

### Input Guardrails

افحص data **قبل** أن تراها Model.

قد تشمل الأهداف:

- حجب requests غير المناسبة،
- اكتشاف topics غير المدعومة،
- رفض malformed payloads،
- اكتشاف prompt-injection patterns،
- sanitize للـ uploaded content.

### Output Guardrails

افحص model output **قبل** أن تصل إلى:

- المستخدم،
- tool،
- نظام آخر.

قد تشمل الأهداف:

- moderation،
- hallucination/fact checking،
- syntax validation،
- structured-output checks،
- فحوص اختيار الأدوات.

{{image:io-guardrails}}

### Guardrails ليست مثالية

يحذر المصدر صراحة من أن guardrails ما تزال مجالًا نشطًا للبحث.

قد تتجاوزها attack قوية.

وقد ترفض guardrail content صالحة أيضًا.

لذلك من الأفضل فهم guardrails باعتبارها:

```text
controls لتقليل المخاطر (risk-reduction controls)
```

وليس:

```text
حدود Security رياضية مثالية (perfect mathematical security boundary)
```

## 4. Input Guardrails

يجمع الفصل عدة أنواع من input guardrails.

### Topical Guardrails

تقيد application بالموضوعات المقصودة.

مثال:

```text
الموضوعات المسموحة (allowed):
- API development
- FastAPI
- building GenAI systems

الموضوعات الأخرى (other topics):
- reject or redirect
```

ويكون ذلك مفيدًا عندما يكون للنظام domain ضيق.

### فحوص Direct Prompt Injection

تحاول اكتشاف inputs التي تهدف إلى:

- override لـ system instructions،
- استخراج hidden prompts،
- كشف secrets/configuration،
- تغيير الدور المقصود للـ Model.

### Indirect Prompt Injection (الحقن غير المباشر)

قد تأتي content المعادية من:

- uploaded files،
- remote web pages،
- images،
- transcripts،
- retrieved documents.

وهذا مهم بصورة خاصة في RAG systems.

قد لا يكتب المستخدم malicious instruction مباشرة.

بل بدلًا من ذلك:

```text
محتوى مرفوع/مسترجع
        ↓
سياق النموذج
        ↓
تعليمات خبيثة تؤثر في النموذج
```

### Moderation

افحص content categories التي تنتهك:

- policy،
- brand constraints،
- legal requirements،
- application boundaries.

يعطي المصدر أمثلة تشمل:

- profanity،
- explicit content،
- PII،
- self-harm،
- قيود متعلقة بالمنافسين.

### Attribute Validation

هي deterministic checks مثل:

- query length،
- file size،
- allowed choices،
- numeric ranges،
- data format،
- structure.

مبدأ مفيد:

> **استخدم deterministic validation للقواعد deterministic. لا تطلب من LLM أن تقرر ما إذا كان integer داخل range ثابتة.**

## 5. لا تكشف Secrets للـ Model

يشير المصدر إلى نقطة مهمة:

حتى إذا بنيت prompt-injection guardrails، فإن architecture الأكثر أمانًا هي تجنب وضع secrets داخل context تستطيع Model الوصول إليها.

فكرة سيئة:

```text
الـ system prompt يحتوي على:
DATABASE_PASSWORD=...
API_SECRET=...
token داخلي خاص=...
```

ثم تعتمد application على:

```text
"لا تكشف هذه الأسرار أبدًا."
```

وهذا يجعل Model جزءًا من secret-protection boundary.

التصميم الأقوى هو:

```text
إعدادات التطبيق
→ تبقى خارج سياق النموذج

ما يتلقاه النموذج
→ الحد الأدنى من البيانات اللازمة فقط
```

### Least Exposure

تعامل مع model context باعتبارها قد تصبح قابلة للكشف.

إذا لم تكن Model تحتاج secret:

```text
لا ترسله
```

وهذا أقوى من محاولة اكتشاف كل prompt-injection attack.

## 7. تشغيل Guardrails وGeneration بالتوازي

قد تؤدي استدعاءات عدة evaluator models بصورة sequential إلى زيادة latency.

افترض:

```text
فحص الموضوع → 1.0 s
إجابة النموذج  → 3.0 s
```

Sequential:

```text
1.0 + 3.0 = نحو 4.0 s
```

إذا كان من الآمن بدء العمليتين معًا، يعرض المصدر concurrency.

مفاهيميًا:

⟦CODE_2⟧

ثم انتظر completion events.

### Fail Fast

إذا انتهت guardrail أولًا ورفضت request:

```text
guardrail → disallowed
        ↓
إلغاء مهمة المحادثة
        ↓
إرجاع استجابة ثابتة آمنة
```

وهذا يتجنب استمرار عمل مكلف بلا داعٍ.

### تحذير مهم

قد تعني parallel execution أن model generation تبدأ قبل أن يصبح guardrail decision نهائيًا.

لذلك:

- لا تطلق generated content قبل أن تسمح input check بذلك،
- ينبغي التعامل مع cancellation بصورة صحيحة،
- قد تظل provider API calls تستهلك capacity/cost،
- يمكن أن تصطدم evaluator calls الإضافية بـ provider rate limits.

### Async Guardrails تستبدل Latency بزيادة Request Volume

قد يقلل تشغيل checks بصورة concurrent من visible latency.

لكنه قد يزيد:

- simultaneous provider calls،
- cost،
- ضغط حدود المعدل.

لذلك يصف الفصل guardrail design باعتبارها مفاضلة **accuracy + latency + cost**.

## 8. Guardrails هي Controls احتمالية

يمكن لـ LLM-based evaluator أن تكون خاطئة.

### False Positive

تقول guardrail:

```text
unsafe    # غير آمن
```

لكن request/output كانت مقبولة فعليًا.

الأثر:

- يتم حجب valid users،
- تسوء user experience.

### False Negative

تقول guardrail:

```text
safe    # آمن
```

لكن كان ينبغي حجب content.

الأثر:

- تمر harmful/invalid output،
- يستمر abuse،
- يزداد reputation أوcost risk.

### ادمج Mechanisms

يوصي المصدر بالنظر في مجموعات مثل:

```text
مُقيِّم LLM
+
فحوص قائمة على القواعد
+
كشف تقليدي باستخدام ML
```

يمكن لتقنيات مختلفة اكتشاف أخطاء مختلفة.

### نطاق Recent Message

يشير الفصل كذلك إلى أن بعض guardrails قد تفحص latest message فقط لتقليل الارتباك الناتج عن conversation histories طويلة جدًا.

يعتمد التصميم الصحيح على threat model.

## 9. Output Guardrails

تقيّم output guardrails ما ولّدته Model قبل تسليمه أوتنفيذ action بناءً عليه.

### Hallucination / الفحوص الواقعية

يمكن أن تتضمن الاستراتيجيات تقييم:

- relevancy،
- coherence،
- consistency،
- fluency،
- alignment مع known source material.

في RAG application، يمكن مقارنة output مع trusted context.

### Moderation

افحص generated content مقابل:

- product rules،
- brand requirements،
- toxicity limits،
- sentiment constraints،
- mention policies.

### Syntax Checks

ينبغي التحقق من structured outputs.

أمثلة:

```text
JSON المتوقع
→ تحقق من الـ schema

استدعاء دالة
→ تحقق من اسم الدالة + المعاملات

اختيار الوكيل للأداة
→ تحقق من أن الأداة مسموح بها
```

وهذا مهم بصورة خاصة لأن downstream systems قد تتعامل مع structured model output باعتبارها executable instructions.

### Retry أوFail Safely

إذا كانت output invalid، فقد تقوم application بـ:

- reject،
- إعادة canned response،
- regenerate،
- repair/reformat،
- طلب clarification.

تعتمد الاستجابة الصحيحة على مستوى الخطر.

## 10. اختر Guardrail Thresholds بصورة مقصودة

تعيد guardrails كثيرة score.

مثلًا:

```text
درجة السمّية (toxicity)
درجة الـ hallucination
درجة الجودة
شدة الإشراف (moderation)
```

ثم تختار application threshold.

افترض:

```text
score >= 3
→ وسم المخرجات (flag)
```

### Threshold أقل

حجب أكثر شدة.

الأثر المحتمل:

```text
اكتشافات صحيحة أكثر
+
إيجابيات خاطئة (false positives) أكثر
```

### Threshold أعلى

أكثر تساهلًا.

الأثر المحتمل:

```text
إيجابيات خاطئة أقل
+
سلبيات خاطئة (false negatives) أكثر
```

[[IMAGE_NEEDED: Guardrail threshold trade-off | A horizontal score scale from low to high with a movable threshold; mark false-positive region on one side and false-negative risk on the other | Learner should notice that threshold selection trades user friction against safety/abuse risk]]

### اختيار Threshold خاص بالتطبيق

يمكن لـ low-risk writing assistant تحمل balance مختلفة عن:

- medical workflow،
- financial action system،
- خدمة عامة لتوليد الصور.

يشدد الفصل على تقييم:

- worst-case harm،
- user experience،
- reputation،
- cost.

## 11. بناء Evaluator-based Moderation Guardrail

يعرض المصدر G-Eval-style evaluation prompt.

تحدد evaluator:

1. **Domain**  
   ما نوع content الجاري تقييمها؟

2. **Criteria**  
   ما الذي يُعد valid أوinvalid؟

3. **Steps**  
   كيف ينبغي لـ evaluator التفكير في criteria؟

4. **Score**  
   أعد discrete value.

مثال conceptual scale:

```text
1 → مقبول
2 → مقبول في الغالب
3 → حدّي
4 → إشكالي
5 → ينتهك المعايير بقوة
```

### تحقق من Score

يمكن لـ Pydantic schema فرض:

```text
1 <= score <= 5    # نطاق الدرجة
```

لا تثق بأن evaluator ستعيد رقمًا صحيحًا دائمًا.

### طبّق Threshold

⟦CODE_3⟧

ثم:

```text
موسوم (flagged)
→ إرجاع استجابة آمنة

غير موسوم
→ تسليم مخرجات النموذج
```

### أساليب Evaluation أخرى

يذكر المصدر أيضًا approaches تقليدية مثل:

- ROUGE،
- BERTScore،
- SummEval.

الدرس الأكبر هو:

> **يمكن أن يكون تقييم Guardrail معتمدًا على Model أوrules أوmetrics أومزيج منها.**

## 12. أبقِ Guardrail Stack عملية

المزيد من guardrails ليس أفضل تلقائيًا.

كل check قد تضيف:

- latency،
- provider cost،
- infrastructure usage،
- implementation complexity.

يقترح المصدر عدة أفكار للتحسين.

### Fast Failure

اخرج بمجرد فشل guardrail حاسمة.

```text
المدخل غير صالح
→ توقف
→ لا تُشغّل الفحوص اللاحقة المكلفة
```

### اختر Guardrails ذات الصلة فقط

لا تشغل كل detector ممكنة على كل request.

اختر controls بناءً على مخاطر application.

### شغّل Checks المتوافقة بصورة Concurrent

يمكن لـ independent asynchronous checks التداخل زمنيًا.

### Sampling

يمكن تشغيل checks باهظة جدًا على sample فقط من requests عندما يكون ذلك مقبولًا لحالة الاستخدام.

السؤال التصميمي الأساسي هو:

```text
ما الضوابط الإلزامية في كل طلب؟
ما الذي يمكن أخذ عينات منه؟
ما الذي يمكن تشغيله بشكل غير متزامن؟
ما الذي يمكن أن يفشل سريعًا؟
```

## 13. Rate Limiting مقابل Throttling

تدير guardrails أساسًا **content وbehavior**.

لكن هناك مشكلة أخرى هي resource abuse.

يقدم الفصل controlين مترابطين.

### Rate Limiting

تتحكم في مقدار traffic المسموح به خلال فترة.

مثال:

```text
5 طلبات في الدقيقة
```

عند تجاوز quota:

```text
رفض الطلب
```

HTTP response نموذجية:

```text
429 Too Many Requests    # طلبات كثيرة جدًا
```

### Throttling

تبطئ processing أوdata transmission مؤقتًا لتثبيت النظام.

بدل الرفض الفوري:

```text
تقليل throughput
```

### لماذا تحتاج GenAI إلى الاثنين؟

قد تكون generation endpoints مكلفة.

من دون controls، يمكن لـ client واحدة احتكار:

- provider quota،
- GPU time،
- CPU،
- memory،
- bandwidth.

### الأهداف

يبرز المصدر:

- abuse prevention،
- fair usage،
- server stability،
- protection against scraping،
- الحماية من هجمات القوة الغاشمة/الحجم العالي.

## 14. أربع استراتيجيات لـ Rate Limiting

يقارن الفصل بين أربع strategies.

### Token Bucket

تخيل bucket تُملأ بـ tokens بمعدل ثابت.

```text
طلب وارد
→ يستهلك token

توفر tokens
→ قبول

لا يوجد token
→ رفض
```

نقطة القوة:

- تتعامل مع bursts أفضل من simple fixed quotas.

المفاضلة:

- implementation complexity أكبر.

### Leaky Bucket

تدخل incoming requests إلى queue.

وتُفرّغ queue بمعدل ثابت.

```text
مدخلات متقطعة بدفعات
      ↓
طابور
      ↓
مخرجات منتظمة
```

إذا امتلأت queue:

```text
رفض الطلب الجديد
```

وهي مناسبة عندما يهم consistent traffic flow.

### Fixed Window

مثال:

```text
100 طلب في الدقيقة
```

تُعاد counter إلى الصفر عند حدود الدقيقة.

بسيطة، لكن bursty traffic قرب boundary قد تكون مزعجة.

### Sliding Window

تتبع requests خلال rolling interval.

مثال:

```text
عدد الطلبات في آخر 60 ثانية
```

يوفر ذلك enforcement أكثر سلاسة لكنه يحتاج state أكبر.

{{image:rate-limit-strategies}}

### حالات استخدام موجهة بالمصدر

يقدم الفصل الاختيارات تقريبًا هكذا:

```text
token bucket
→ حركة تفاعلية غير منتظمة

leaky bucket
→ throughput منتظم لـ inference

fixed window
→ حصص بسيطة وصارمة/الطبقة المجانية

sliding window
→ وصول مرن للمحادثات/المميّز (premium)
```

## 15. تطبيق Rate Limits في FastAPI

يعرض المصدر rate-limiting library لـ FastAPI.

المهم ليس اسم library، بل architecture.

### Global Limits

مثال conceptual policy:

```text

60/ساعة
2 طلب لكل 5 ثوانٍ
```

يتتبع limiter الاستخدام ويرفض traffic الزائدة.

### Custom 429 Response

يمكن أن تتضمن rate-limit response جيدة:

وكذلك:

## 16. فضّل User-aware Quotas عندما توجد Identity

تُعد IP-based rate limits مفيدة لكنها غير مثالية.

يمكن لمستخدم تغيير IP عبر:

- VPN،
- proxy،
- mobile network،
- rotating addresses.

وفي الوقت نفسه قد يشترك عدة legitimate users في IP واحدة.

بعد وجود authentication، يمكن أيضًا ربط usage بهوية المستخدم.

مثال:

```text
المستخدم 123
→ 10 طلبات/دقيقة
```

وهذا يدعم account-level quotas.

### ادمج Keys

قد تستخدم production systems مزيجًا من:

- user ID،
- IP،
- subscription plan،
- API key،
- endpoint cost.

مثال:

```text
FREE
→ 5 طلبات نصية/دقيقة

PRO
→ 30 طلبًا نصيًا/دقيقة
```

يركز المصدر على IP وuser-based limits، لكن الفكرة الأعمق هي:

> **اختر quota identity التي تعكس من أوما الذي يستهلك المورد النادر فعلًا.**

## 17. Rate Limiting عبر عدة Application Instances

افترض أن production تشغل:

```text
نسخة FastAPI A
نسخة FastAPI B
نسخة FastAPI C
```

ويقوم load balancer بتوزيع requests.

إذا احتفظت كل instance بـ counters داخل local memory فقط:

```text
A يظن أن المستخدم استخدم 3 طلبات
B يظن أن المستخدم استخدم 4 طلبات
C يظن أن المستخدم استخدم 2 طلب
```

الاستخدام الحقيقي هو:

```text

```

```text
                ┌──────────────┐ │
طلب ───────────→│ FastAPI B    │─┼→ عدّادات Redis

                                 │
                ┌──────────────┐ │

                └──────────────┘
```

## 18. ضع Limits منفصلة لاستخدام WebSocket

تختلف WebSocket connections عن HTTP requests العادية.

فقد تبقى مفتوحة وقتًا طويلًا.

لذلك يقدم المصدر WebSocket-specific limiting.

قد تشمل controls:

- active connection count،
- messages per interval،
- per-user usage،
- معدل البيانات المبثوثة.

### محدِّد WebSocket على أساس المستخدم

مفاهيميًا:

```text

    ↓

    ↓

    ↓
كل prompt/رسالة
    ↓
```

إذا تم تجاوز limit:


ثم طبق connection policy المطلوبة.

### لماذا يهم ذلك؟

من دون limits، يمكن لمستخدم واحد إبقاء عدد كبير من connections مفتوحة أوإرسال prompts بسرعة كبيرة.

- server connection state،
- model capacity،
- bandwidth.

## 19. Throttle لـ Real-time Model Streams

قد تنتج Model chunks أسرع مما يستطيع client أوservice إرسالها بصورة مريحة.

يعرض المصدر إضافة nonblocking delay:

### لماذا `await asyncio.sleep(...)`؟

تبطئ producer من دون حجب event loop.

وهذا يعني أن async requests أخرى تستطيع الاستمرار في التقدم.

### فوائد محتملة

يمكن أن يساعد throttling على:

- إبطاء data transmission،
- تقليل network pressure،

- توزيع capacity على عدة clients.

### Dynamic Throttling

fixed throttle بسيطة.

## 20. Traffic Shaping على Infrastructure Layer

Application throttling ليست الطريقة الوحيدة للتحكم في flow.

يقدم الفصل **traffic shaping**.

تدير Traffic shaping عملية network transmission.

قد تشمل controls:

- bandwidth limits،
- intentional latency،
- packet-loss simulation/control،
- IP-based traffic limits،
- queueing/prioritization.

### لماذا نستخدمها؟

تفيد real-time services مثل:

- chat streaming،
- video streaming،
- bandwidth-sensitive AI applications أخرى.

### Application Throttle مقابل Traffic Shaping

```text
تقييد على مستوى التطبيق (Application throttling)
→ تُبطئ الشيفرة عمدًا إنتاج النموذج/الاستجابة

تشكيل الحركة (Traffic shaping)
→ تتحكم طبقة البنية التحتية/الشبكة في نقل البيانات
```

### المفاضلة

يمكن لـ traffic shaping تحسين stability لكنها تضيف:

- configuration complexity،
- monitoring requirements،
- queueing delay.

استخدمها عندما تحتاج network behavior نفسها إلى control.

## 21. بناء Layered Abuse Protection

تعمل تقنيات الفصل بصورة أفضل معًا.

يمكن لمسار request عملي أن يبدو هكذا:

```text
الطلب
   ↓
المصادقة
   ↓
التفويض
   ↓
تحديد المعدل / الحصة (quota)
   ↓
التحقق من الخصائص
   ↓
Input guardrails
   ↓
تنفيذ النموذج / الأداة
   ↓
Output guardrails
   ↓
تقييد البث (throttle)
   ↓
المستخدم
```

### كل Layer تحل مشكلة مختلفة

| Control | السؤال الرئيسي |
|---|---|
| Authentication | من أنت؟ |
| Authorization | هل يُسمح لك بفعل ذلك؟ |
| Rate limit | كم مقدار الاستخدام المسموح؟ |
| Input guardrail | هل هذه input مقبولة/آمنة لهذا application؟ |
| سياسة النموذج/الأداة | ما capabilities المسموح بتنفيذها؟ |
| Output guardrail | هل generated output مقبولة/صحيحة؟ |
| Throttle | ما السرعة التي ينبغي أن تتدفق بها output؟ |
| Traffic shaping | كيف ينبغي توزيع network capacity؟ |

### افشل مبكرًا حيثما أمكن

ينبغي أن تحدث cheap deterministic checks قبل expensive inference.

مثال:

```text
حمولة غير صالحة
→ ارفض فورًا

تجاوز الحصة
→ ارفض فورًا

طلب ممنوع بوضوح
→ توقف قبل توليد النموذج
```

### لا تعتمد على Control واحدة

يفترض النظام القوي أن:

```text
قد تفشل الضوابط الفردية
```

تقلل layering احتمال أن تتحول missed detection واحدة إلى security failure كاملة.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1

> إذا كان المستخدمون authenticated، فلا يمكنهم إساءة استخدام AI service.

### لماذا هذا خطأ؟

تحدد Authentication هوية المستخدمين. لكن المستخدمين authenticated يمكنهم مع ذلك إساءة استخدام capabilities أو استهلاك موارد مفرطة.

### المفهوم الخاطئ 2

> تضمن Guardrails أن prompt injection لن تنجح.

### لماذا هذا خطأ؟

يتعامل المصدر صراحة مع guardrails باعتبارها imperfect وprobabilistic. ويمكن للهجمات المتطورة تجاوزها.

### المفهوم الخاطئ 3

> يمكن الوثوق في output الخاصة بـ model-based guardrail من دون validation.

### لماذا هذا خطأ؟

الـ evaluator نفسها Model احتمالية وقد تعيد format غير متوقعة أونتيجة خاطئة.

### المفهوم الخاطئ 4

> أكثر طريقة أمانًا لحماية secrets هي وضعها داخل system prompt وإخبار Model ألا تكشفها أبدًا.

### لماذا هذا خطأ؟

Architecture الأقوى هي إبقاء secrets خارج context التي تستطيع Model رؤيتها كلما كان ذلك ممكنًا.

### المفهوم الخاطئ 5

> المزيد من Guardrails يجعل Application أكثر أمانًا دائمًا من دون أي تكلفة.

### لماذا هذا خطأ؟

تزيد Guardrails من latency وprovider usage وcost واحتمال false positives.

### المفهوم الخاطئ 6

> للـ False Positive وFalse Negative العاقبة نفسها.

### لماذا هذا خطأ؟

تحجب false positives المستخدمين الصالحين، بينما تسمح false negatives بـ content أوbehavior كان النظام يريد إيقافها.

### المفهوم الخاطئ 7

> Rate Limiting وThrottling الشيء نفسه.

### لماذا هذا خطأ؟

تتحكم Rate limiting في admission/allowed usage؛ بينما تبطئ throttling الـ processing أوtransmission.

### المفهوم الخاطئ 8

> ينبغي استخدام Request Limit ثابتة واحدة لكل AI endpoint.

### لماذا هذا خطأ؟

قد تكون resource costs مختلفة جذريًا بين endpoints.

### المفهوم الخاطئ 9

> Per-IP Limiting تمنع مستخدمًا واحدًا بالكامل من تجاوز Quotas.

### لماذا هذا خطأ؟

يمكن للمستخدمين تغيير IP addresses، وقد يشترك عدة مستخدمين في IP واحدة. ويمكن لـ authenticated user quotas توفير control أقوى على مستوى الهوية.

### المفهوم الخاطئ 10

> In-memory Rate-limit Counters تعمل بصورة صحيحة عبر عدة FastAPI Replicas.

### لماذا هذا خطأ؟

لكل process memory منفصلة. وتحتاج shared quota إلى centralized counter store أوinfrastructure-layer limit.

### المفهوم الخاطئ 11

> HTTP Rate Limiting تحمي تلقائيًا Long-lived WebSocket Usage.

### لماذا هذا خطأ؟

تحتاج WebSocket traffic إلى connection/message/data-rate controls مناسبة للاتصالات المستمرة.

### المفهوم الخاطئ 12

> Stream Throttling تحجب FastAPI Event Loop كلها.

### لماذا هذا خطأ؟

يسمح استخدام `await asyncio.sleep(...)` غير الحاجب للـ event loop بجدولة أعمال أخرى أثناء التأخير.

### المفهوم الخاطئ 13

> Traffic Shaping وModel-stream Throttling تعملان على الطبقة نفسها.

### لماذا هذا خطأ؟

تحدث stream throttling داخل application logic، بينما تعمل traffic shaping على network/infrastructure layer.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| سوء الاستخدام (Misuse) | استخدام النظام بطريقة غير مقصودة أوضارة |
| الحماية من الإساءة (Abuse protection) | Controls مصممة لتقليل الاستخدام الخبيث أوالمفرط |
| Prompt injection | Input مصممة للتلاعب بتعليمات Model أوسلوكها |
| Indirect prompt injection — حقن غير مباشر | تعليمات خبيثة تدخل عبر external content مثل files أوretrieved data |
| معالجة المخرجات غير الآمنة | الوثوق في model output من دون validation قبل downstream use |
| حجب الخدمة عن النموذج | Resource-exhaustion attack تستهدف model operations المكلفة |
| Guardrail | Control تقيّم أوتقيد model inputs/outputs |
| Input guardrail | Check تُطبق قبل وصول content إلى Model |
| Output guardrail | Check تُطبق على generated content قبل التسليم/الاستخدام |
| Topical guardrail | تقيد requests بالموضوعات المسموحة |
| Moderation guardrail | تقيّم content مقابل policy/quality criteria |
| Auto-evaluator | Model أوmechanism آلية تقيّم input/output أخرى |
| False positive | Content صالحة يتم تصنيفها خطأً باعتبارها invalid |
| False negative | Content غير صالحة يُسمح بها خطأً |
| Threshold | حد score يُستخدم لتحويل continuous/discrete metric إلى decision |
| Fast failure | إنهاء processing بمجرد اكتشاف failure حاسمة |
| Sampling | تشغيل check مكلفة على subset فقط من requests |
| Rate limiting | التحكم في عدد requests/operations المقبولة عبر الزمن |
| Throttling | إبطاء processing أوdata transmission |
| Token bucket | Rate limiter تستخدم tokens يعاد ملؤها وتستهلكها requests |
| Leaky bucket | Limiter قائمة على queue تخرج العمل بمعدل ثابت |
| Fixed window | Rate limiter تعد requests داخل time intervals ثابتة |
| Sliding window | Rate limiter تعد requests خلال moving interval |
| HTTP 429 | Response من نوع Too Many Requests |
| `Retry-After` | Header يحدد متى يمكن لـ client إعادة المحاولة |
| حصة على أساس المستخدم | Limit مرتبطة بهوية المستخدم authenticated |
| Redis | Centralized in-memory data store يستخدمها المصدر لحالة rate-limit المشتركة |
| WebSocket rate limit | Limit تُطبق على messages/usage في persistent connection |
| Stream throttle | Delay/rate control مقصودة تُطبق على generated chunks |
| Traffic shaping | Network-level control في bandwidth وdelay وpacket flow |
