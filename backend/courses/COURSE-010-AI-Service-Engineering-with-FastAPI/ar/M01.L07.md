## 1. هل تحتاج فعلًا إلى قاعدة بيانات؟

قاعدة البيانات مفيدة، لكنها ليست إلزامية لكل Application.

يبدأ الفصل بمبدأ معماري مهم:

> **لا تضف قاعدة بيانات لمجرد أن Production systems غالبًا تحتوي واحدة. أضفها عندما تكون لدى Application حالة Persistent أومتطلبات لإدارة Data تبرر هذا التعقيد.**

قد لا تكون قاعدة البيانات ضرورية عندما:

- يمكن لكل Session أن تبدأ من الصفر،
- يمكن إعادة حساب Data بتكلفة منخفضة،
- حجم Data صغير بما يكفي للـ memory،
- فقدان Data مقبول،
- لا يحتاج Users أوInstances إلى Shared state،
- المعلومات المطلوبة موجودة بالفعل في External systems،
- يمكن لـ Users تحمل إعادة الحساب،
- تكون Files أوBrowser storage أوCloud storage كافية،
- يكون المشروع مجرد Proof of concept.

### مثال: Demo مؤقتة لتوليد الصور

تخيل:

```text
User يُدخل Prompt
      ↓
Model تنشئ Image
      ↓
تُعرض Image
      ↓
تنتهي Session
```

إذا:

- لم يكن Login مطلوبًا،
- لا يتم تخزين Images،
- History غير مهمة،
- إعادة Generation رخيصة،

فقد تضيف Relational database عملًا إضافيًا دون قيمة حقيقية.

### متى تصبح قاعدة البيانات ضرورية؟

تصبح قاعدة البيانات أكثر قيمة عندما تحتاج خدمتك إلى:

- Persistence عبر Restarts،
- User accounts،
- Conversation history،
- Usage tracking،
- Billing records،
- Shared state،
- Reliable querying،
- Indexing،
- Concurrent access،
- Backups وRestoration،
- Authorization حول Stored data.

بالنسبة إلى Production conversational AI service، يُعد حفظ Conversations وUser data من الأسباب الشائعة لإضافة قاعدة بيانات.

## 2. نموذج ذهني لأنظمة قواعد البيانات

يقسم الفصل قواعد البيانات إلى فئتين عامتين:

```text
علائقية (Relational)
→ SQL

غير علائقية (Nonrelational)
→ NoSQL
```

الفرق ليس ببساطة «قديم مقابل جديد».

بل يرتبط أساسًا بـ:

- Data model،
- Schema behavior،
- Query style،
- خصائص Consistency/Scale،
- Use case.

### Hierarchy بنيوية شائعة

يقدم المصدر نموذجًا ذهنيًا عامًا مفيدًا:

```text
Database server
    ↓
واحدة أوأكثر من Databases
    ↓
واحدة أوأكثر من Schemas
    ↓
Tables أوCollections
    ↓
Rows أوDocuments/Items
```

تستخدم Relational systems عادةً:

```text
الجداول
الصفوف
الأعمدة
العلاقات
القيود
```

أما Nonrelational systems فقد تنظم المعلومات في صورة:

- Key-value pairs،
- Documents،
- Graph nodes/Edges،
- Vectors،
- سجلات الأعمدة العريضة (Wide-column).

## 3. قواعد البيانات Relational وNonrelational

### Relational databases

تنظم Relational databases الـ Data في Tables.

مثال:

```text
conversations    # جدول المحادثات
-----------------------------------------
id | title | model_type | created_at

messages    # جدول الرسائل
---------------------------------------------------------
id | conversation_id | prompt | response | created_at
```

يمكن لـ Relationships ربط Records ببعضها.

مثلًا:

```text
المحادثة 1
   ├── الرسالة 1
   ├── الرسالة 2
   └── الرسالة 3
```

تُستخدم SQL للاستعلام عن هذه Structured data والتعامل معها.

تكون Relational databases مناسبة بقوة عندما:

- تكون Relationships مهمة،
- تكون Consistency مهمة،
- تكون Transactions مهمة،
- يكون Structured querying مهمًا.

### Nonrelational databases

تستخدم NoSQL systems عدة Data models مختلفة.

يقدم الفصل عدة فئات.

| النوع | Data model | أمثلة Use cases |
|---|---|---|
| Key-value | Key → Value | Caching وSessions |
| Graph | Nodes + Edges | Relationships وRecommendations وFraud graphs |
| Document | Flexible documents | Content وFlexible schemas |
| Vector | vectors عالية الأبعاد | Semantic search وRAG |
| Wide-column | سجلات عائلات الأعمدة | Analytics وLogging وأحمال موجَّهة بالزمن |

### مخازن المفتاح-القيمة (Key-value)

نموذج ذهني:

```text
"session:123" → {...}    # بيانات جلسة
"cache:prompt_hash" → استجابة مخزّنة مؤقتًا (cached response)
```

تكون مفيدة عندما يكون Access أساسًا عبر Key.

### Graph databases

تمثل:

```text
عقدة ──حافة── عقدة
```

وتكون مفيدة عندما تكون Relationships نفسها مهمة.

### Document databases

تخزن Objects مرنة شبيهة بالـ Documents.

وهي مناسبة عندما يمكن أن تختلف Structure الخاصة بالـ Records أوتتطور بصورة متكررة.

### Vector databases

تخزن Embeddings وتدعم Similarity search.

وهذا مهم خصوصًا لـ:

- RAG،
- Semantic search،
- Recommendations.

### مخازن الأعمدة العريضة (Wide-column)

مصممة لـ Distributed datasets كبيرة وHigh-throughput patterns.

### يمكن لتطبيق واحد استخدام عدة قواعد بيانات

قد تجمع خدمة GenAI متقدمة:

```text
PostgreSQL
→ Users وConversations وUsage

Vector DB
→ Embeddings

Graph DB
→ Knowledge relationships

Redis
→ Cache/Session state

Document DB
→ Flexible prompts/Configuration
```

[[IMAGE_NEEDED: Multi-database GenAI architecture | Diagram showing a GenAI/RAG application connected to PostgreSQL for users/conversations, a vector database for embeddings, a graph database for document relationships, Redis for caching, and a document database for flexible prompt templates | Learner should notice that database choice is per problem rather than one database replacing every other type]]

### المبدأ

> **اختر قاعدة البيانات لأن Data model الخاصة بها تناسب المشكلة، لا لأن فئة واحدة من قواعد البيانات أفضل من غيرها بصورة مطلقة.**

## 5. ماذا يفعل ORM؟

يقوم **Object-Relational Mapper (ORM)** بربط مفاهيم Database بكود Object-oriented.

مفاهيميًا:

```text
جدول SQL
↔ class في Python

عمود SQL
↔ خاصية في الـ class

صف SQL
↔ نسخة (instance) من الـ class
```

بدلًا من كتابة:

⟦CODE_1⟧

يمكن لـ ORM أن يسمح لك بالتعبير عن Operations مكافئة باستخدام Python.

### لماذا نستخدم ORM؟

تشمل المزايا التي يذكرها الفصل:

- Abstraction فوق SQL،
- Development أسرع،
- Maintainability،
- أنماط تطبيق قابلة لإعادة الاستخدام.

وتشمل المقايضات:

- Learning curve،
- Direct control أقل،
- Debugging أصعب،
- مشكلات Performance محتملة في Complex queries.

### الدرس الأساسي

لا يجعل ORM **Database performance غير مهمة**.

لا يزال عليك فهم:

- Queries،
- Indexes،
- Relationships،
- Transactions،
- Joins،
- Pagination.

يغير ORM الـ Interface، لكنه لا يغير حقائق Database الأساسية.

### FastAPI dependency

يعبر هذا عن Resource lifecycle:

```text
تبدأ Request
    ↓
Open للـ Session
    ↓
Yield إلى Controller
    ↓
Controller/Repository تستخدم DB
    ↓
Commit أوRollback
    ↓
Close للـ Session
```

### لماذا `yield` مفيدة؟

يمكن لـ FastAPI معاملة Dependency كـ Context-managed resource.

ينفذ Code قبل `yield` عملية Setup.

وينفذ Code بعدها Cleanup.

### Rollback

إذا حدث Exception أثناء Transaction:

```text
Partial changes
    ↓
Rollback
    ↓
تعود Database إلى Previous consistent transaction state
```

### لماذا نعطل Autocommit؟

يفضل المصدر Explicit transaction control.

يسمح ذلك لـ Application بتحديد:

```text
متى تكتمل Unit of work
→ Commit
```

بدل كتابة Changes تلقائيًا في نقاط غير متوقعة.

## 12. إضافة Service layer لـ Business logic

يوسع الفصل Repository pattern بإضافة Services.

### Repository

تجيب عن:

```text
كيف أقرأ هذه Data أوأكتبها؟
```

### Service

تجيب عن:

```text
ما Business operation التي ينبغي أن تحدث؟
```

مثلًا:

```text
List للـ Messages في Conversation
```

قد تتطلب Domain-oriented operation تتجاوز Generic CRUD method أساسية.

يمكن لـ `ConversationService` تنسيق ذلك.

### لماذا نفصل Services؟

قد تحتاج Business operation مستقبلًا إلى:

```text
Check للـ User permission
    ↓
Read للـ Conversation
    ↓
Read للـ Messages
    ↓
Call للـ Model
    ↓
Update للـ Usage
    ↓
Persist للـ Result
```

هذا Workflow لا ينتمي داخل Low-level repository.

### تجنب الالتباس في Inheritance

يعرض المصدر Service ترث Repository للراحة.

أما Architectural principle الأوسع الذي ينبغي الاحتفاظ به فهو:

> Repositories تملك Persistence concerns؛ وServices تملك Business workflows.

يمكن أن تختلف Class relationship الفعلية.

### حافظ على ضيق المسؤوليات

يحذر الفصل من:

- Coupling شديد بين Services وImplementations،
- تحميل Services مسؤوليات أكثر من اللازم،
- وضع Business rules داخل Repositories.

### Pagination


عندما يحتاج Client إلى Page صغيرة فقط.

استخدم:

```text
offset    # الإزاحة
limit    # الحد الأقصى
```

### Indexes

تكون مفيدة للـ Fields المستخدمة كثيرًا في:

- Filters،
- Joins،
- Lookups.

لكن لكل Index تكلفة في Write وStorage.

### تقليل Lookups المكررة

إذا احتاجت Request الواحدة إلى Conversation نفسها عدة مرات، يمكن لإعادة استخدام Request-scoped dependency تجنب تكرار Database work نفسها.

### توخ الحذر مع Joins

يحذر الفصل من أن Complex queries التي تحتوي JOINs كثيرة قد تصبح مكلفة.

ولا يزيل ORM هذه التكلفة.

### دع قاعدة البيانات تنفذ عمل قواعد البيانات

تتميز Relational engines بكونها محسنة للغاية لـ:

- Filtering،
- Sorting،
- Joining،
- Indexing،
- Aggregation.

لا تسحب Massive datasets إلى Python فقط لإعادة تنفيذ Operations تستطيع Database تنفيذها بكفاءة أعلى.

## 14. لماذا Schema migrations ضرورية؟

أثناء Prototyping، يمكنك حذف Tables وإعادة إنشائها.

في Production، هذا غير مقبول.

افترض أن Application تحتوي بالفعل على:

```text
100,000 محادثة
500,000 رسالة
```

ثم قررت إضافة:

```text
messages.cost
```

لا يمكنك ببساطة Drop لكل شيء وإعادة إنشائه.

بل تحتاج إلى Controlled schema change.

### النموذج الذهني للـ Migration

يقارن الفصل Alembic بـ Version control لـ Database schemas.

```text
تاريخ الشيفرة
→ Git commits

تاريخ مخطط قاعدة البيانات
→ مراجعات الترحيل (migration revisions)
```

تسجل Migration:

- كيفية تحريك Schema إلى الأمام،
- كيفية عكسها عندما يكون ذلك ممكنًا.

### Structure الخاصة بـ Alembic

بعد Initialization:

```text
alembic.ini    # ملفات Alembic

alembic/
    env.py
    versions/
        migration_001.py
        migration_002.py
        ...
```

### `env.py`

تربط Alembic بـ:

- Database URL،
- SQLAlchemy metadata.

## 16. منع Code وSchema وData drift

تتطور عدة أشياء في الوقت نفسه:

```text
شيفرة التطبيق
مخطط قاعدة البيانات
تاريخ الترحيل
البيانات المخزَّنة فعليًا
```

إذا خرجت عن التزامن، قد تفشل Application بطرق مفاجئة.

### Schema drift

لم تعد Live database structure تطابق ما يتوقعه Code.

مثال:

```text
Code تتوقع Column: total_cost
Database لا تحتويها
```

### Migration drift

طبقت Environments المختلفة Migration histories مختلفة.

مثال:

```text
المطوّر A → المراجعة 5
staging → المراجعة 4
production → المراجعة 3
```

### Data drift

لم تعد Stored values تطابق Assumptions الجديدة.

مثال:

```text
Old records تسمح بـ NULL
New business logic تفترض Non-NULL
```

### انضباط Team

يشدد الفصل على:

- Commit للـ Migrations،
- إنشاء Migration files جديدة للتغييرات الجديدة،
- إبقاء Environments متوافقة،
- التعامل مع Transactions بعناية،
- تجنب Hard-coded configuration.

المبدأ الأساسي هو:

> **تغيير Database code بأمان يتطلب تنسيق Code وSchema وMigration history وExisting data معًا.**

## 17. حفظ Streamed LLM conversations

تخلق Streaming مشكلة Persistence خاصة.

تصل Response جزءًا بعد جزء:

```text
token 1    # تُبث فور توليدها
token 2
token 3
...
```

لكن Relational message record تريد عادةً:

```text
الـ prompt الكامل
الاستجابة الكاملة
conversation_id
بيانات وصفية
```

### لماذا لا نقوم Commit لكل Token؟

يجادل الفصل بأن Traditional relational transactions ليست مناسبة طبيعيًا للتعامل مع كل Streamed token على أنها جزء من Transaction واحدة طويلة العمر.

بدلًا من ذلك:

```text
Stream للـ Answer كاملة إلى User
        ↓
تجميع Final complete content
        ↓
Persist للـ Complete message
```

### نمط المهام في الخلفية

مفاهيميًا:

```text
LLM stream
  ├── Copy A → Client
  └── Copy B → جمع Complete answer
                 ↓
           Background database write
```

يستخدم المصدر Stream duplication حتى تذهب نسخة إلى `StreamingResponse` ويمكن تخزين النسخة الأخرى.

## 19. تجميع Database architecture كاملة

يمكن أن تبدو GenAI backend نظيفة من هذا الفصل هكذا:

```text
                         ┌───────────────────┐
                         │      العميل       │
                         └─────────┬─────────┘
                                   │
                                   ▼
                         ┌───────────────────┐
                         │ موجه FastAPI      │
                         └─────────┬─────────┘
                                   │
                                   ▼
                         ┌───────────────────┐
                         │ المتحكم/API       │
                         │ + Pydantic schema │
                         └─────────┬─────────┘
                                   │
                                   ▼
                         ┌───────────────────┐
                         │ طبقة الخدمة       │
                         └─────────┬─────────┘
                                   │
                       ┌───────────┴───────────┐
                       │                       │
                       ▼                       ▼
             ┌───────────────────┐    ┌───────────────────┐
             │ المستودع          │    │ مزود النموذج      │
             └─────────┬─────────┘    └───────────────────┘
                       │
                       ▼
             ┌───────────────────┐
             │ SQLAlchemy        │
             └─────────┬─────────┘
                       │
                       ▼
             ┌───────────────────┐
             │ PostgreSQL        │
             └───────────────────┘

تطور الـ schema:
نماذج SQLAlchemy → مراجعات Alembic → schema في PostgreSQL
```

### مثال على Request lifecycle

إنشاء Conversation:

```text
POST /conversations
      ↓
تحقق Pydantic
      ↓
المتحكم
      ↓
الخدمة/المستودع
      ↓
جلسة SQLAlchemy
      ↓
معاملة PostgreSQL
      ↓
استجابة Pydantic
```

### دورة حياة محادثة streaming

```text
User prompt
    ↓
LLM stream
    ├──→ Client في Real time
    │
    └──→ Complete response
             ↓
         Background persistence
             ↓
         Messages table
```

هذه هي قصة Integration الأساسية في الفصل:

> **ينبغي أن تعمل Database كطبقة Persistence موثوقة حول GenAI workflow، بينما تحافظ Application على Contracts واضحة وTransactions وAbstractions وMigration history.**

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> كل Production AI application تحتاج إلى قاعدة بيانات.

### لماذا هذا خطأ؟

قد لا تحتاج Stateless أوDisposable proof of concept إلى Persistence أصلًا.

### المفهوم الخاطئ 2

> SQL databases وNoSQL databases حلول متنافسة لا يمكن استخدام إلا واحدة منها.

### لماذا هذا خطأ؟

قد يستخدم GenAI application معقد Relational وVector وGraph وDocument وKey-value stores معًا لحل مشكلات مختلفة.

### المفهوم الخاطئ 3

> وجود ORM يعني أنني لم أعد بحاجة إلى فهم Database concepts.

### لماذا هذا خطأ؟

تظل Queries وRelationships وIndexing وTransactions وPerformance مهمة تحت ORM abstraction.

### المفهوم الخاطئ 4

> `create_all()` كافية لتطوير Production schema.

### لماذا هذا خطأ؟

يمكنها إنشاء Missing tables، لكنها ليست Controlled migration history لتطوير Production schemas نشطة.

### المفهوم الخاطئ 5

> يمكن فتح Database session ونسيانها.

### لماذا هذا خطأ؟

يجب Commit أوRollback للـ Sessions بصورة مناسبة وإغلاقها حتى يتم تحرير Resources.

### المفهوم الخاطئ 6

> Pydantic models وSQLAlchemy models نسخ مكررة غير ضرورية.

### لماذا هذا خطأ؟

تخدم Contracts مختلفة: API schemas مقابل Persistence schemas.

### المفهوم الخاطئ 7

> ينبغي أن تحتوي Repositories كل Business logic لأنها تتعامل بالفعل مع Database.

### لماذا هذا خطأ؟

ينبغي أن تركز Repositories على Persistence؛ بينما تنسق Services الأعلى Business workflows.

### المفهوم الخاطئ 8

> Pagination مهمة فقط لـ Frontend UX.

### لماذا هذا خطأ؟

تقلل Pagination أيضًا Database وNetwork load بمنع Result sets أكبر من اللازم.

### المفهوم الخاطئ 9

> بمجرد تطبيق Alembic migration، فإن تعديل Migration file نفسها يحدّث Database تلقائيًا.

### لماذا هذا خطأ؟

يتم تتبع Applied revision IDs. ينبغي تمثيل Schema changes الجديدة باستخدام Migration revisions جديدة.

### المفهوم الخاطئ 10

> Database schema changes تؤثر فقط في Database team.

### لماذا هذا خطأ؟

تؤثر Schema changes في ORM models وServices وAPIs وMigrations وTests وافتراضات Existing data.

### المفهوم الخاطئ 11

> ينبغي أن تكتب Streaming responses كل Token مباشرة داخل Relational transaction واحدة.

### لماذا هذا خطأ؟

يوصي الفصل بإكمال Stream ثم Persist للـ Full message بعدها.

### المفهوم الخاطئ 12

> إذا أنشأت LLM عنوان Conversation، فينبغي أن تكتب Title مباشرة إلى PostgreSQL.

### لماذا هذا خطأ؟

تقترح Model المحتوى؛ بينما تتولى Trusted application logic الـ Validation وPersistence.
