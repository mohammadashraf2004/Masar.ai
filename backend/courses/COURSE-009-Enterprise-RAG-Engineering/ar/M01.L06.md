## 1. لماذا يُعد تقييم RAG متطلبًا على مستوى النظام؟ (Why RAG evaluation is a system requirement)

قد يبدو تطبيق RAG مبهرًا أثناء demo ومع ذلك يفشل بشدة في production — بيئة الإنتاج. والسبب أن جودة RAG تنتج عن **pipeline**. تعتمد الإجابة النهائية على جودة source data و ingestion و retrieval و ranking و prompting و generation وعلى نظام production — بيئة الإنتاج المحيط بها. إجابة واحدة مبهرة لا تخبرك تقريبًا بأي شيء عن مدى موثوقية النظام.

لذلك فإن RAG evaluation هي عملية **قياس المواضع التي ينجح فيها النظام والمواضع التي يفشل فيها**. وعلى أقل تقدير، تريد الإجابة عن سؤالين:

1. **Retrieval quality:** هل وجد النظام chunks التي تحتوي فعلًا على المعلومات المطلوبة لهذا query؟
2. **جودة Generation (Generation quality):** بالنظر إلى evidence المسترجعة، هل أنتجت LLM إجابة مفيدة faithful وكاملة وذات صلة؟

ينبغي لفرق production — بيئة الإنتاج أن تذهب أبعد من ذلك وتضم سلوك النظام مثل latency و uptime و throughput و cost. فتطبيق RAG عالي الدقة لكنه يستغرق ثلاثين ثانية لكل request يظل نظام production — بيئة الإنتاج ضعيفًا. وبالمثل، النظام السريع الذي يسترجع evidence خاطئة بصورة متكررة ليس مفيدًا.

أفضل mental model هو **evaluation باعتبارها diagnosis**، لا باعتبارها leaderboard. تكون metric ذات قيمة عندما تخبرك *أي مكوّن ينبغي تحسينه بعد ذلك*.

## 2. Offline Evaluation مقابل Online Evaluation

يميز الفصل بين نمطين للتقييم.

تحدث **offline evaluation** أثناء development أو قبل release. أنت تتحكم في test queries و system configuration وعادةً evaluation dataset. ولأنها ليست على critical user path، يمكن أن تكون offline evaluation مكلفة وبطيئة. وهنا يمكنك تشغيل benchmark sets كبيرة، ومقارنة عدة embedding models، وتغيير chunking strategies، واختبار rerankers، أو استدعاء LLM judges مكلفة بصورة متكررة.

أما **online evaluation** فترصد النظام live. ميزتها هي الواقعية: تأتي queries من مستخدمين حقيقيين بدل benchmark مصممة يدويًا. أما تحديها فهو أن التقييم live يجب ألا يجعل user experience بطيئة أو مكلفة بصورة غير مقبولة.

يحتاج النظام الناضج إلى الاثنين. تُعد offline evaluation **محرك tuning** الرئيسي؛ بينما تُعد online evaluation **نظام الإنذار المبكر** الرئيسي.

```text
تغيير في Development (Development change)
     ↓
offline benchmark — معيار تقييم offline
     ↓
بوابة التقييم (evaluation gate)
     ↓
production — بيئة الإنتاج
     ↓
online telemetry + sampled evaluation + human feedback — telemetry مباشرة وتقييم بعينات و feedback بشرية
     ↓
ترقية failure cases الجديدة إلى offline benchmark — معيار تقييم offline
```

تُعد هذه الدورة من أهم أفكار الدرس: ينبغي أن تصبح evaluation عملية مستمرة، لا نشاطًا يُنفذ مرة واحدة قبل الإطلاق.

## 3. قيّم Pipeline وليس الإجابة النهائية فقط (Evaluate the pipeline, not only the final answer)

افترض أن مستخدمًا حصل على إجابة خاطئة. توجد تفسيرات كثيرة ومختلفة جدًا:

- لم يتم إدخال المعلومات المطلوبة أصلًا عبر ingestion.
- البيانات موجودة، لكن parsing دمّر بنيتها.
- أخفق retriever في العثور على chunk الصحيحة.
- وجد retriever الـ chunk الصحيحة، لكنه أعاد أيضًا قدرًا كبيرًا من noise.
- تجاهلت generator إحدى chunks المسترجعة المهمة.
- اختلقت generator ادعاءً لا يدعمه context.
- الإجابة faithful لكنها لا تعالج intent المستخدم فعلًا.
- النظام صحيح لكنه بطيء جدًا أوغير متاح.

تحتاج هذه الإخفاقات إلى إصلاحات مختلفة. لا تستطيع prompt engineering إصلاح documents المفقودة. ولا تستطيع LLM أقوى استعادة chunk لم يزودها بها retriever أصلًا. وقد تؤدي زيادة `top_k` إلى تحسين recall لكنها تضيف أيضًا context غير ذي صلة.

لهذا السبب، لا تبنِ dashboard تحتوي على "RAG score" واحدة فقط. احتفظ بـ metrics خاصة بكل stage حتى تستطيع تحديد موضع تغير الجودة. وهذا أساس tuning علمية.

## 4. إخفاق Retrieval: انخفاض Recall (Retrieval failure: low recall)

يعني **low recall** أن معلومات مفيدة موجودة داخل corpus المفهرسة، لكن retrieval stage تفشل في إعادتها داخل candidate set المستخدمة في المراحل اللاحقة.

يوجد شكلان شائعان:

- **إخفاق كامل (Complete miss):** لا يتم استرجاع أي من evidence المطلوبة.
- **إخفاق جزئي (Partial miss):** تظهر بعض evidence، لكن تغيب حقائق أخرى مطلوبة لإجابة كاملة.

الحالة الثانية خطيرة بصورة خاصة لأن الإجابة قد تبدو معقولة. تخيل سؤالًا يطلب كلًا من final approval step و filing deadline. إذا أعاد retrieval فقط approval chunk، فقد تجيب generator عن النصف الأول بصورة صحيحة وتفشل في deadline.

يشدد الفصل على أولوية عملية: **حسّن retrieval قبل محاولة إنقاذ النظام عبر generation**. فإذا كانت relevant evidence نادرًا ما تُسترجع، فلن يستطيع أي prompt التعويض عنها بصورة موثوقة.

تشمل أدوات تحسين recall عادة retrieval method و`k` و hybrid search و reranking candidate depth و query formulation و metadata filters وجودة indexed representation.

## 5. إخفاق Retrieval: انخفاض Precision (Retrieval failure: low precision)

يعني **low precision** أن retriever يعيد قدرًا كبيرًا جدًا من material غير ذي الصلة. قد يظل النظام يسترجع chunk الصحيحة، لكنه يحيط هذه evidence بـ chunks مشتتة أو مضللة.

تهم noise لسببين. أولًا، تستهلك chunks غير ذات الصلة context budget. ثانيًا، يمكن أن تؤثر في generator، وخصوصًا إذا احتوت vocabulary تبدو مرتبطة بـ query.

على سبيل المثال، query عن عملية الموافقة على إطلاق project لا ينبغي أن تحصل على chunk عن احتفال بعد الإطلاق لمجرد أن كليهما يحتوي كلمتي "project" و"launch". التطابق على مستوى keywords وحده لا يكفي لإثبات relevance.

غالبًا ما يمكن تحسين low precision باستخدام first-stage retrieval أقوى، أو metadata filtering، أو hybrid retrieval، أو reranker. لكن تذكر التوتر بين precision و recall: تصفية noise بقوة قد تزيل evidence ذات صلة عن طريق الخطأ. توجد evaluation لقياس هذه المفاضلة بدل التخمين.

## 6. بعض إخفاقات Retrieval معمارية (Some retrieval failures are architectural)

يعمل standard top-k RAG بأفضل صورة عندما يمكن العثور على الإجابة المطلوبة داخل passage واحدة أو بضع passages متشابهة semantic مع query. بعض الأسئلة تكسر هذا الافتراض.

قد يتطلب سؤال **multi-hop** استرجاع حقيقة، واستخدامها لتحديد entity ثانية، ثم استرجاع حقيقة أخرى. وقد يتطلب سؤال **sensemaking** دمج evidence عبر documents كثيرة لتلخيص pattern جماعي.

إذا أظهرت evaluation أن semantic أو hybrid retrieval المعتادة تفشل بصورة متكررة في هذه الفئات من queries، فقد لا تكون المشكلة threshold سيئة أو prompt ضعيفًا. قد تكون retrieval architecture نفسها غير كافية. ويشير الفصل إلى agentic RAG و knowledge graphs باعتبارهما أسلوبين أنسب لهذه المهام.

وهذا درس تشخيصي مهم: لا تواصل tuning لمكوّن بلا نهاية عندما تشير evidence الخاصة بالتقييم إلى أن الطريقة الأساسية لا تناسب فئة query.

## 7. يمكن لـ Generation أن تفشل حتى مع Retrieval جيدة (Generation can fail even with good retrieval)

بمجرد نجاح retrieval، تظل لدى generator مسؤوليات عدة: يجب أن تحترم evidence، وتستخدم evidence المهمة، وتجيب عن طلب المستخدم الفعلي.

يبرز الفصل ثلاثة إخفاقات رئيسية في generation:

1. **إخفاق Faithfulness (Faithfulness failure)** — تحتوي الإجابة claims لا يدعمها retrieved context أو تتناقض معه.
2. **إخفاق Context utilization (Context-utilization failure)** — تم توفير relevant evidence، لكن Model لم تستخدم كل الأجزاء المهمة.
3. **إخفاق Answer relevance (Answer-relevance failure)** — الإجابة grounded وربما كاملة، لكنها لا تحل سؤال المستخدم الفعلي.

تهم هذه الفروق لأن similarity score واحدة بين generated answer و reference answer لا تستطيع تفسير الحالات الثلاث جميعًا. لذلك تحتاج generation evaluation الجيدة إلى عدة metrics متكاملة.

## 8. Faithfulness و Hallucination

تكون الاستجابة **faithful** عندما تدعم retrieved chunks ادعاءاتها factual. ويحدث faithfulness failure عندما تضيف Model ادعاءات unsupported أومتناقضة.

بالنسبة إلى RAG، تُعد faithfulness محورية لأن وعد architecture هو grounding. فإذا قال retrieved context إن deadline هو July 31 ثم غيرته الإجابة إلى early August، يكون النظام قد خالف عقد grounding.

كما يقدم الفصل تمييزًا مهمًا عند troubleshooting:

- **خطأ غير Faithful (Unfaithful incorrectness):** كانت source chunks صحيحة، لكن generator انحرفت عنها.
- **خطأ Faithful (Faithful incorrectness):** عكست generator retrieved evidence بدقة، لكن evidence نفسها كانت stale أوخاطئة.

تشير الحالة الأولى إلى generator أو prompt أو hallucination controls. وتشير الثانية إلى المراحل upstream مثل ingestion و versioning و source governance أو استرجاع content قديم. يمنع هذا التمييز الفرق من إلقاء اللوم على LLM في failure ناتج عن data management.

## 9. Context Utilization: هل استخدمت Model كل Evidence الضرورية؟

يمكن لـ generator أن تكون faithful لـ chunk واحدة بينما تتجاهل chunk أخرى حرجة. وينتج عن ذلك إجابة grounded تقنيًا لكنها ناقصة بصورة خطرة.

تخيل سؤالًا يطلب كلًا من مخاطر project وفوائده. يزود retriever بصورة صحيحة chunk تصف expected revenue وأخرى تصف market volatility. إذا ناقشت generator الإيراد فقط، فإن الاستجابة تعاني **context-utilization failure**.

قد ينشأ هذا الإخفاق عن ordering effects أو prompts طويلة أو attention غير متوازن على chunks أو prompt design. وتُعد ظاهرة "lost in the middle" أحد أسباب عدم استخدام Model للأدلة الموضوعة في مواضع معينة بصورة كافية.

لذلك يطرح context utilization سؤالًا مختلفًا عن faithfulness. تسأل faithfulness: "هل ما قالته Model مدعوم؟" بينما يسأل context utilization: "هل ضمّنت Model الأشياء المهمة التي كان ينبغي أن تقولها؟"

## 10. Answer Relevance: هل حلت الاستجابة مشكلة المستخدم؟

يمكن أن تكون الاستجابة صحيحة factually و grounded بالكامل ومع ذلك تظل غير مفيدة.

إذا سأل مستخدم: "Is it safe to push the new update?" واكتفى النظام بسرد ثلاث features للـ update، فقد تكون الاستجابة دقيقة لكنها تفشل في الإجابة عن السؤال الموجه لاتخاذ قرار. وهكذا يعود عبء التفسير إلى المستخدم.

يوضح ذلك لماذا تختلف answer relevance عن factual consistency. تتطلب relevance فهم **intent السؤال**.

قد تفشل metrics المعتمدة على reference answer مثل ROUGE-L أو BERTScore في اكتشاف هذا النوع من failure لأن lexical أو semantic similarity مع reference لا تلتقط دائمًا ما إذا كان Assistant حقق المهمة المقصودة. وقد تكون rubric جيدة التصميم بأسلوب LLM-as-a-judge أكثر فائدة عندما يكون criterion semantic و task-specific بطبيعته.

## 11. يجب أن تمتد Evaluation إلى مرحلة Ingestion

تتبع RAG القاعدة المعروفة **garbage in, garbage out**. فإذا كان parsing أو cleaning أو document lifecycle management خاطئًا، ستعاني metrics الخاصة بـ retrieval و generation في المراحل downstream.

يحظى إخفاقان في ingestion باهتمام خاص في الفصل:

- **أخطاء Parsing البنيوية (Structural parsing errors):** تضيع tables أو images أو headings أو layout relationships. قد تظل الكلمات الخام موجودة، لكن يختفي المعنى الذي كانت البنية ترمزه.
- **تقادم Content (Content staleness):** تظل documents القديمة قابلة للبحث بعد وجود versions أحدث.

يمكن لهذه المشكلات أن تبدو كأنها retrieval أو generation failures. على سبيل المثال، لا يستطيع retriever إعادة table row مبنية بصورة صحيحة إذا قامت ingestion pipeline بتسطيحها إلى نص بلا معنى. وبالمثل، يمكن أن تكون generator faithful بصورة مثالية لـ version خاطئة من policy.

لذلك ينبغي أن تشمل evaluation فحوص data quality و ingestion logs واختبارات تراعي versioning، لا query-time metrics فقط.

## 12. Entity IDs و Versioning كعناصر تمكّن Evaluation

إحدى الاستراتيجيات العملية للتعامل مع staleness هي إسناد **entity ID** ثابت لكل document منطقية والحفاظ على versions صريحة. وعند ingestion لـ version أحدث، يمكن إزالة chunks التابعة للـ version المستبدلة أو استبعادها.

يدعم هذا التصميم اختبارًا استباقيًا مفيدًا: إذا كانت عدة versions نشطة لنفس entity موجودة في الوقت نفسه بينما يفترض أن تكون واحدة فقط current، فإن ingestion pipeline غير سليمة.

يوضح ذلك نقطة أوسع: بعض "evaluation metrics" ليست model scores أصلًا. بل هي **invariants** تخص البيانات والنظام. ويجمع برنامج جودة RAG قوي بين statistical metrics و deterministic checks.

## 13. ابنِ Failure Matrix قبل اختيار Metrics

قبل اختيار الأدوات، دوّن failure classes التي تهمك والقياس القادر على كشف كل منها.

| المرحلة | الإخفاق | الإشارة المفيدة |
|---|---|---|
| مرحلة Ingestion | فقدان معلومات table/layout | اختبارات parser و targeted retrieval tests |
| مرحلة Ingestion | versions قديمة | فحوص entity/version invariants |
| مرحلة Retrieval | فقدان relevant chunks | recall@k و rank-aware metrics |
| مرحلة Retrieval | noise مفرطة | precision@k و relevance judging |
| مرحلة Generation | claims غير مدعومة | مقياس faithfulness / hallucination |
| مرحلة Generation | حقائق متجاهلة | تغطية context-utilization / nuggets |
| مرحلة Generation | إجابة بعيدة عن الهدف | rubric لقياس answer relevance |
| مستوى System | استجابات بطيئة | latency و P95/P99 |
| مستوى System | عدم استقرار | uptime و error rate و response consistency |
| الجانب الاقتصادي (Economics) | cost غير مستدامة | cost لكل مكوّن و resource usage |

تمنع هذه mapping عملية "جمع metrics" بلا هدف تشخيصي.

## 14. LLM-as-a-Judge: الفكرة الأساسية

يستخدم **LLM-as-a-judge** Language Model باعتبارها evaluator بدل كونها user-facing generator. تستقبل judge evidence مثل user query و retrieved context و generated answer و rubric صريحة، ثم تعيد score أو category أو critique.

تكمن القوة الرئيسية في المرونة. تسمح natural-language rubrics بتقييم criteria يصعب ترميزها بصيغ بسيطة، مثل faithfulness و usefulness و concision و persona adherence و reasoning quality أو domain-specific requirements.

لذلك من الأفضل فهم judge باعتبارها **programmable semantic evaluator**. لكنها تظل Model لها biases و cost و latency و randomness. ولا ينبغي التعامل مع output الخاصة بها باعتبارها ground truth لا تقبل النقاش.

## 15. Pointwise Judging مقابل Pairwise Judging

تقيّم judge من نوع **pointwise** استجابة واحدة بصورة مستقلة، مثلًا من 1 إلى 5. وهذا بسيط ومفيد عندما تحتاج absolute thresholds.

أما judge من نوع **pairwise** فتقارن استجابتين وتختار أيهما يحقق rubric بصورة أفضل. ويشير الفصل إلى أن pairwise comparisons غالبًا ما تحقق alignment أكثر استقرارًا مع human preferences لأن judge تمتلك anchor صريحة.

المفاضلة هي interpretability: يمكن تتبع pointwise score كسلسلة زمنية، بينما تناسب pairwise evaluation طبيعيًا مقارنات A/B مثل "current reranker مقابل candidate reranker".

عمليًا، استخدم pointwise judging عندما تحتاج operational threshold، واستخدم pairwise judging عند مقارنة نسختين من النظام.

## 16. انحيازات Judge: Style و Verbosity و Self-reference

قد تكافئ LLM judges خصائص لا ترتبط بقوة بالصحة.

يناقش الفصل **self-referential bias**، حيث تفضل judge outputs تشبه styles تدربت على إنتاجها. وقد يظهر ذلك في صورة:

- **الأسلوب فوق المضمون (Style over substance):** تحصل صياغة مصقولة تشبه AI على score أعلى رغم facts أضعف.
- **انحياز الإطالة (Verbosity bias):** تُكافأ الاستجابات الأطول لمجرد أنها تبدو أكثر شمولًا.
- **نقاط عمياء منهجية (Systemic blind spots):** تشترك judge مع Model قيد التقييم في reasoning weakness، ولذلك تفشل في معاقبتها.

الحل هو calibration مقابل **human-verified golden set**. فإذا لم تتوافق judge scores مع human judgments موثوقة على أمثلة ممثلة، فلا ينبغي استخدام judge باعتبارها quality oracle.

## 17. Cost و Latency الخاصة بـ Judge جزء من تصميم Evaluation

يستهلك كل استدعاء لـ LLM judge inference capacity ووقتًا. وهذا مهم حتى offline عند تقييم آلاف queries، ويصبح حرجًا online.

لذلك ينبغي لتصميم production — بيئة الإنتاج evaluation الإجابة عن:

- أي metrics تحتاج فعلًا إلى judge؟
- هل تستطيع Model أصغر توفير جودة evaluation مقبولة؟
- هل ينبغي تقييم sample فقط من traffic؟
- هل يمكن تشغيل judging بصورة asynchronous بعد وصول الإجابة إلى المستخدم؟
- هل ينبغي حساب بعض deterministic metrics أولًا وحجز استدعاءات judge المكلفة للحالات غير المؤكدة؟

للتقييم **budget** خاصة به. تعامل مع هذه budget صراحة بدل ترك evaluation costs تختفي داخل إنفاق LLM العام.

## 18. يمكن لـ Stochastic Judges أن تغيّر رأيها

تتميز LLMs بسلوك stochastic. وحتى مع ضبط temperature على zero، يمكن أن تنتج inputs متطابقة outputs مختلفة أحيانًا. ولذلك قد تمنح judge الإجابة نفسها scores مختلفة عبر runs.

تشمل إجراءات التخفيف العملية الواردة في الفصل:

- تشغيل judge عدة مرات وحساب average أو aggregate للنتائج؛
- تفضيل structured rubrics؛
- استخدام pairwise comparisons عندما يكون ذلك مناسبًا؛
- تسجيل كامل judge input و output؛
- تنفيذ calibration مقابل human judgments؛
- عمل versioning لـ judge model و prompt.

الدرس دقيق لكنه مهم: يجب تقييم ومراقبة evaluation system نفسها.

## 20. Golden Chunks و Golden Answers

تحتاج كثير من traditional metrics إلى trusted reference.

تحدد **golden chunk set** أي chunks ينبغي اعتبارها relevant لـ query. وهي تمكّن حساب recall و precision و MRR و MAP و nDCG.

أما **golden answer** فهي trusted target answer تُستخدم عند مقارنة generated output باستخدام answer-similarity metrics أو correctness rubrics.

تتميز golden data بالقوة لأنها تربط evaluation بتوقعات بشرية صريحة. لكن نقطة ضعفها هي maintenance cost. ففي enterprise corpus ديناميكية، تتغير documents وتتغير chunk boundaries، وقد تصبح "correct" chunk IDs قديمة.

وينشئ ذلك تقسيمًا عمليًا:

- استخدم curated golden sets عندما يكون application مستقرًا بدرجة كافية وتكون أعلى ثقة مطلوبة.
- استخدم reference-free methods عندما تكون corpus ضخمة جدًا أو تتغير بسرعة تجعل continuous manual labeling غير عملية.

لا يتفوق أحد الأسلوبين عالميًا؛ فهما يحلان مشكلات تشغيلية مختلفة.

## 21. Precision@k: ما مدى نظافة Retrieved Context؟

تقيس **Precision@k** نسبة chunks ذات الصلة داخل أعلى `k` chunks تم استرجاعها.

\[
Precision@k = 
\frac{\text{الـ chunks ذات الصلة ضمن أعلى k}}{k}
\]

إذا أعاد retriever خمس chunks وكانت أربع منها relevant، فإن precision@5 تساوي `4/5 = 0.8`.

تعني precision المرتفعة أن generator تستقبل signal-to-noise ratio مرتفعة. وهذا مهم بصورة خاصة عندما تكون context windows محدودة أو عندما يشتت irrelevant text الـ Model بسهولة.

لا تخبرك Precision **هل أخفق retriever في العثور على chunks أخرى relevant في مكان آخر داخل corpus**. هذه وظيفة recall.

{{exercise:M01.L06.EX06}}

## 22. Recall@k: هل وجد Retriever الـ Evidence الموجودة؟

تقيس **Recall@k** نسبة كل relevant chunks التي تظهر ضمن أعلى `k` results.

\[
Recall@k = 
\frac{\text{الـ chunks ذات الصلة ضمن أعلى k}}{\text{كل الـ chunks ذات الصلة بالاستعلام}}
\]

افترض أن corpus تحتوي أربع chunks يعتبرها الإنسان relevant، لكن ثلاثًا فقط تظهر ضمن أعلى عشر نتائج. تكون Recall@10 هي `3/4 = 0.75`.

تُعد Recall حاسمة عندما تحتاج الإجابات إلى عدة أجزاء من evidence. فقد يتسبب retriever ذو low recall في إجابات ناقصة حتى إذا كانت كل chunk معادة عالية الجودة.

يتطلب حساب recall معرفة relevant set الكاملة، ولذلك يصبح مكلفًا على scale كبير.

{{exercise:M01.L06.EX07}}

## 23. المفاضلة بين Precision و Recall (The precision–recall trade-off)

غالبًا ما تؤدي زيادة `k` إلى رفع recall لأن عدد candidates المعادة يزداد، لكنها قد تخفض precision لأن النتائج الإضافية تتضمن noise أكثر. وقد يؤدي تقليل `k` إلى context نظيفة مع فقد facts ضرورية.

وهذا يعني أن `k` ليست latency parameter فقط، بل تشارك في quality trade-off.

إحدى تجارب tuning البسيطة هي تقييم عدة قيم لـ `k` على query set نفسها ورسم precision و recall. وبعد ذلك يمكنك اختيار operating point التي تناسب application. ففي حالات compliance أو research قد تستحق recall وزنًا أكبر، بينما في FAQ retrieval شديدة التركيز قد تكون precision هي الأهم.

## 24. F1@k: Score واحدة عندما تهم Precision و Recall معًا

**F1-score** هي harmonic mean لـ precision و recall:

\[
F1 = 2 \times 
\frac{\text{الدقة} \times \text{الاستدعاء}}{\text{الدقة} + \text{الاستدعاء}}
\]

تعاقب harmonic mean النظام غير المتوازن. فلن يحصل retriever لديه precision مقدارها 1.0 لكن recall مقدارها 0.1 على F1 score قوية.

تفيد F1 عندما تقدر use case كلًا من coverage و cleanliness. لكنها تخفي أيضًا المفاضلة الأساسية، لذلك أبقِ precision و recall ظاهرتين في dashboard بدل الإبلاغ عن F1 وحدها.

## 25. لماذا يهم Rank في RAG؟

تعامل Precision@k و recall@k كل موضع داخل أعلى `k` بالتساوي. لكن rank مهم عمليًا.

قد تؤثر chunk في position 1 على generator أكثر من chunk في position 10. كما قد تعاني prompts الطويلة ordering effects مثل "lost in the middle". لذلك ينبغي لـ retrieval evaluation أحيانًا مكافأة الأنظمة التي تضع أفضل evidence قرب القمة.

تلبي rank-aware metrics هذه الحاجة. ويناقش الفصل **MRR و MAP و nDCG**.

## 26. متوسط الرتبة العكسية (Mean Reciprocal Rank — MRR)

تركز MRR على rank الخاص بـ **أول نتيجة relevant**.

بالنسبة إلى query واحدة:

\[
RR = 
\frac{1}{\text{ترتيب أول نتيجة ذات صلة}}
\]

إذا كانت أول relevant chunk في rank 1، تكون score هي 1. وإذا كانت في rank 4، تكون 0.25. وإذا لم تظهر أي relevant chunk، تكون score هي 0.

ثم تُحسب MRR باعتبارها mean لـ reciprocal rank عبر جميع evaluation queries.

تكون MRR ممتازة عندما تكفي نتيجة واحدة قوية للإجابة عن السؤال. لكنها أقل إفادة عندما تتطلب الإجابة عدة relevant chunks.

{{exercise:M01.L06.EX08}}

## 27. متوسط Average Precision (Mean Average Precision — MAP)

تكافئ **Average Precision (AP)** الأنظمة التي تسترجع *عدة* relevant chunks وتضعها في مراكز مرتفعة من ranking. مفاهيميًا، تحسب precision في كل مرة تواجه item relevant، ثم تحسب average لقيم precision هذه بالنسبة إلى query. أما **MAP** فهي mean لقيمة AP عبر evaluation query set.

لذلك تلتقط MAP جزءًا أكبر من ranking مقارنة بـ MRR. وهي مفيدة عندما توجد عدة relevant passages وتهتم باسترجاع عدد كبير منها قرب القمة.

وعلى خلاف nDCG، تعامل MAP التقليدية relevance بصورة binary: relevant أو not relevant.

## 28. المكسب التراكمي المخصوم المطبّع (Normalized Discounted Cumulative Gain — nDCG)

تدعم **nDCG** مفهوم **graded relevance**. فبدل القول إن chunk relevant أو irrelevant فقط، يمكنك إسناد مستويات مثل 0 و1 و2 و3.

تكافئ DCG relevance الأعلى وتخفض وزن items التي تظهر لاحقًا. وتقسم nDCG قيمة DCG للنظام على أفضل DCG ممكنة لتلك query:

\[
nDCG@k = 
\frac{DCG@k}{IDCG@k}
\]

يجعل ذلك scores قابلة للمقارنة عبر queries ذات relevance distributions مختلفة.

تكون nDCG قوية عندما تكون ranking quality دقيقة ومتدرجة. وقد تكون overhead غير ضرورية لمجموعات retrieval صغيرة جدًا عندما يهمك فقط ظهور chunk صحيحة واحدة أو اثنتين.

## 29. اختيار Retrieval Metric

استخدم metric التي تتوافق مع retrieval objective.

| الهدف | Metric المفيدة |
|---|---|
| إبقاء context غير ذات الصلة خارج النتائج | مقياس Precision@k |
| ضمان العثور على كل evidence المهمة | مقياس Recall@k |
| موازنة precision و recall | مقياس F1@k |
| وضع إجابة جيدة واحدة في مركز مرتفع جدًا | مقياس MRR |
| ترتيب عدة relevant chunks بصورة جيدة | مقياس MAP |
| ترتيب chunks باستخدام graded relevance | مقياس nDCG |
| تجنب صيانة golden chunk labels | تقييم بأسلوب UMBRELA |

قد تستخدم evaluation suite ناضجة عدة metrics لأن metric واحدة لا تلتقط كل سلوك retrieval.

## 30. UMBRELA: Relevance للـ Retrieval دون Reference

يقدم الفصل **UMBRELA** كطريقة لتقييم retrieved chunks من دون manually curated golden chunk set.

تستقبل LLM judge كلًا من query و retrieved passage واحدة، ثم تسند integer relevance score:

- `0` — غير relevant؛
- `1` — مرتبطة بالموضوع لكنها لا تجيب عن query؛
- `2` — تحتوي answer information مفيدة ولكن مع ambiguity أو material إضافية؛
- `3` — تجيب عن query بصورة مباشرة ودقيقة.

يحول ذلك retrieval relevance إلى semantic judging task قابلة للتوسع. وهو جذاب بصورة خاصة في corpora الديناميكية حيث ستتقادم golden chunks المصانة يدويًا بسرعة.

المفاضلة واضحة: تستبدل جهد human labeling بـ inference cost وعدم يقين judge.

{{exercise:M01.L06.EX10}}

## 31. كيفية استخدام UMBRELA Scores

يمكن فحص UMBRELA score مباشرة باعتبارها relevance signal لكل chunk معادة. ويمكنك أيضًا استخدام graded scores كـ input لـ ranking metrics مثل nDCG.

لكن ما **لا** تحله UMBRELA بتكلفة منخفضة هو recall على corpus كاملة. فلكي تعرف أن retriever وجد كل relevant chunks، ستحتاج relevance judgments لكل chunk قد تكون relevant، وهو أمر غير عملي في collections كبيرة.

لذلك فإن reference-free retrieval judging ممتازة للإجابة عن "ما مدى جودة chunks التي استرجعتها؟" لكنها لا تجيب تلقائيًا عن "هل استرجعت كل relevant chunk موجودة؟"

## 32. Generation Evaluation تطرح سؤالًا مختلفًا

تخبرك retrieval metrics هل حصلت generator على ingredients جيدة. أما generation metrics فتسأل هل **استخدمت Model تلك ingredients بصورة صحيحة**.

تنظر generation evaluation suite قوية إلى عدة أبعاد:

- context utilization؛
- answer accuracy أو similarity؛
- answer relevance؛
- faithfulness / factual consistency؛
- citation accuracy؛
- response consistency؛
- safety و bias.

تتداخل هذه الأبعاد لكنها ليست قابلة للاستبدال.

## 33. Context Utilization باستخدام AutoNuggetizer

يصف الفصل **AutoNuggetizer** كمنهج structured لقياس ما إذا كانت الاستجابة تغطي facts المهمة المتاحة داخل evidence.

تبدأ العملية بتوليد **nuggets** ذرية من query و relevant chunks. ثم تُصنف nuggets حسب الأهمية:

- **Vital** — ضرورية لإجابة كاملة وصحيحة.
- **OK** — supporting detail مفيدة لكنها غير أساسية.

بعد ذلك تُفحص generated answer مقابل كل nugget وتُصنف على أنها supported أو partially supported أو not supported. ثم تُجمع هذه judgments في تقييم عام لـ context utilization.

يستهدف ذلك مباشرة نقطة ضعف لا تستطيع faithfulness وحدها اكتشافها. فقد لا تحتوي الاستجابة أي hallucinations ومع ذلك تحذف نصف vital facts.

## 34. Answer Similarity و Golden Answers

تقارن **answer similarity** generated answer مع trusted reference answer. ويذكر الفصل أساليب مثل **ROUGE-L** و**BERTScore**.

تنظر metric موجهة إلى surface مثل ROUGE-L إلى overlap داخل sequences، بينما تقارن الأساليب semantic مثل BERTScore المعنى باستخدام learned representations. وقد تكون هذه الطرق مفيدة عندما تمتلك الإجابات المقبولة صيغة مستقرة نسبيًا.

لكن similarity لها قيد: يمكن أن تكون إجابتان متشابهتين semantic بينما تفشل إحداهما في instruction مهمة، ويمكن لإجابتين صحيحتين بالقدر نفسه استخدام صياغات مختلفة جدًا. تعامل مع similarity باعتبارها إشارة واحدة، لا مقياسًا كاملًا لجودة الإجابة.

## 35. Answer Relevancy باعتبارها Metric لإنجاز Task

تسأل answer relevancy ما إذا كانت الاستجابة تعالج query الأصلية مباشرة. وهي تعاقب الاستجابات tangential أوالناقصة أوالممتلئة بتفاصيل غير ضرورية.

ولأن relevance تعتمد على intent، يمكن أن يكون LLM-as-a-judge مناسبًا طبيعيًا. تستطيع domain-specific rubric السؤال هل تصل الاستجابة إلى conclusion المطلوبة، وهل تشمل العناصر المطلوبة، وهل تتجنب content غير ذي الصلة.

على سبيل المثال، قد يتطلب incident-response assistant من الاستجابة تحديد severity و recommended action و escalation path. ولن تفرض generic semantic similarity هذه rubric بالضرورة.

## 36. Faithfulness باعتبارها Factual Consistency

تقيس Faithfulness ما إذا كانت generated claims مدعومة بـ retrieved context.

يمكنك تقدير faithfulness باستخدام:

- specialized hallucination detection model مثل HHEM؛
- LLM-as-a-judge prompt تتحقق من claims مقابل evidence المقدمة.

القاعدة الأساسية هي أن evaluator ينبغي أن تحكم مقابل **retrieved source text**، لا مقابل world knowledge الخاصة بها. وإلا فإنها تتوقف عن قياس RAG grounding وتبدأ تقييم external factuality.

## 37. دقة Citations: هل يستطيع المستخدم التحقق من Claim؟

لا تكون inline citations ذات قيمة إلا عندما تدعم فعلًا statement المرتبطة بها.

تسأل **citation precision** ما إذا كان cited source يدعم associated claim فعلًا. وتسمح إجابة RAG عالية الجودة للمستخدم باتباع citation والعثور بسهولة على supporting evidence.

يمكن أن تكون citations المنسوبة بصورة خاطئة أسوأ من عدم وجود citations لأنها تنشئ مظهرًا زائفًا للتحقق. لذلك ينبغي أن تكون citation evaluation جزءًا من production — بيئة الإنتاج testing عندما تكون citations user-facing trust feature.

## 38. Response Consistency وقابلية التكرار

شغّل query نفسها عدة مرات. هل يظل المحتوى factual مستقرًا؟

تتميز LLMs بأنها probabilistic، لذلك نتوقع اختلافات طفيفة في الصياغة. لكن المشكلة هي **semantic instability**: conclusions مختلفة أوأرقام مختلفة أو recommendations مختلفة لنفس evidence.

تُعد consistency مهمة بصورة خاصة في finance و healthcare و legal وغيرها من domains المنظمة. ويوصي الفصل بقياسها بصورة منهجية بدل افتراض أن temperature zero تضمن behavior حتميًا.

إحدى الطرق العملية هي تشغيل query عدد `N` من المرات وقياس distribution الخاصة بـ evaluation metrics الأخرى، مثل faithfulness أو relevance، عبر runs.


## 39. يجب أن تكون Safety و Bias جزءًا من Evaluation

يمكن لنظام RAG أن يكون relevant و faithful ومع ذلك ينتج content غير آمن أوتمييزيًا. لذلك ينبغي أن تتضمن evaluation فحوص safety لكل من retrieved evidence و generated output.

يذكر الفصل Models متخصصة مثل **Llama Guard** و**ShieldGemma**. وتستطيع هذه Models تصنيف content غير الآمن أوالمخالف للسياسات. وتعتمد safety policy الدقيقة على application.

بالنسبة إلى multimodal RAG، قد تحتاج safety evaluation إلى فحص كل من text و images. ولهذا ينبغي تصميم safety باعتبارها بُعدًا أوسع للتقييم، لا text-only filter واحدة.

## 40. Red Teaming يجد Failures لم تتخيلها Benchmark

تكون automated metrics أقوى في failure modes التي تعرف بالفعل كيف تقيسها. أما **red teaming** فيبحث عمدًا عن failures خارج هذه المسارات المألوفة.

يصمم human testers prompts خصومية أوذات nuances ثقافية أوغامضة أوصعبة أخلاقيًا لكشف bias أو unsafe behavior أو retrieval weaknesses أو combinations ضارة من evidence تبدو بريئة منفردة.

النتيجة الأعلى قيمة من red teaming ليست report فقط. بل ينبغي تحويل الهجمات الناجحة إلى:

- safety rules جديدة؛
- prompts محسنة؛
- تغييرات في data curation؛
- regression tests؛
- benchmark cases جديدة.

وهكذا تتحول weakness مكتشفة مرة واحدة إلى تحسين دائم في evaluation suite.

## 41. Evaluation Frameworks تحل مشكلات Workflow مختلفة

يستعرض الفصل عدة أدوات وعروض للتقييم. ولا تكمن قيمتها فقط في metrics التي تحسبها، بل في **workflow** التي تشجع عليها.

- يركز **Open RAG Eval** على reference-free evaluation مثل UMBRELA و AutoNuggetizer.
- يوفر **Ragas** ecosystem واسعة من metrics المعتمدة على LLM ويتكامل مع RAG frameworks الشائعة.
- يقدم **DeepEval** تقييم LLM بأسلوب يشبه software unit testing ويتكامل بقوة مع workflows بأسلوب pytest.
- يوفر **Amazon Bedrock evaluation** منهج managed مدمجًا في AWS ecosystem.

لا تختر framework فقط بناءً على عدد metrics في documentation الخاصة بها. اختر بناءً على transparency و ground truth المطلوبة و extensibility و CI/CD integration واحتياجات managed infrastructure وأنواع failures التي يجب أن يكتشفها application.

## 42. Open RAG Eval و Reference-free Workflows

يُقدَّم Open RAG Eval باعتباره open source approach مصممًا حول صعوبة الحفاظ على ground-truth labels على enterprise scale.

تشمل metrics الخاصة به:

- UMBRELA لقياس retrieval relevance؛
- AutoNuggetizer لقياس fact/nugget coverage؛
- hallucination scoring؛
- citation evaluation؛
- قياس consistency.

إحدى المزايا العملية هي أن evaluation يمكن أن تبدأ من query list بدل الحاجة إلى golden answers لكل query. تستطيع connectors الحصول على query و contexts و responses من نظام RAG، ثم تُحسب metrics المهيأة.

## 43. إطار Ragas

Ragas هي open source RAG evaluation framework ذات integrations قوية مع LLM ecosystem الأوسع. تبني workflow شائعة evaluation dataset تحتوي questions و generated answers و retrieved contexts؛ ويمكن أيضًا تضمين ground-truth answer.

يمكن لـ Ragas كذلك إنشاء synthetic test cases من source documents. وتفيد synthetic data في bootstrapping، لكن الفصل يحذر من أن generated queries قد لا تعكس real user behavior بدقة.

الدرس العام هو فحص كيفية تعريف metric بدل التعامل مع library score كما لو كانت self-explanatory. لا تصبح score المنخفضة قابلة لاتخاذ action إلا عندما تفهم evidence التي استخدمتها metric والسلوك الذي عاقبته.

## 44. DeepEval و Evaluation باعتبارها Unit Testing

تتوجه DeepEval إلى developers. وهي تشجع على تعريف test cases منفردة والتأكد من تجاوز metrics لـ thresholds المطلوبة، بصورة تشبه workflows التقليدية لـ `pytest`.

هذه mental model ذات قيمة لأنها تنقل RAG evaluation إلى الانضباط نفسه المستخدم في software regression testing. فلا ينبغي release لـ prompt أو reranker تم تغييرها حديثًا لمجرد أن code تعمل؛ بل يجب أن تحقق quality assertions.

كما تدعم DeepEval custom criteria-based evaluation، وهو مفيد عندما يمتلك application متطلبات لا تلتقطها generic metrics.

## 45. Managed Evaluation باستخدام Amazon Bedrock

يمكن لـ managed service إزالة كثير من infrastructure المطلوبة لتنسيق judge models وتجميع evaluation jobs. ويستخدم الفصل Amazon Bedrock مثالًا.

يمكن أن تغطي managed evaluation كلًا من retrieval و generation metrics، وقد تشمل responsible-AI dimensions مثل harmfulness أو refusal behavior.

المفاضلة هي platform trade-off المعتادة: operations أسهل و ecosystem integration أفضل مقابل vendor cost ورؤية أقل لبعض تفاصيل evaluation الأساسية مقارنة بـ tooling مفتوحة المصدر بالكامل.

## 46. Human Feedback ليست Telemetry اختيارية

تقرب automated evaluation قيمة المستخدم. أما user feedback الفعلية فتقيسها بصورة أكثر مباشرة.

يمكن لآلية بسيطة من thumbs-up/thumbs-down أن تنتج production — بيئة الإنتاج signal قوية إذا رُبطت بكامل interaction trace. لكل interaction، سجّل fields مثل:

- interaction ID؛
- query؛
- retrieved chunks؛
- generated answer؛
- user feedback؛
- timestamp؛
- user/session metadata عندما يكون ذلك مناسبًا.

القيمة ليست مجرد حساب global thumbs-up percentage. يمكنك تقسيم satisfaction حسب topic، وربط satisfaction بـ automated metrics، وفحص أسوأ interactions تقييمًا لتنفيذ root-cause analysis.

## 47. حوّل Feedback إلى Diagnosis

تدعم human feedback عدة تحليلات:

تعطي **overall satisfaction rate** مؤشر KPI بسيطًا عالي المستوى.

يمكن لـ **satisfaction by topic** أن تكشف أن knowledge domain واحدة سليمة بينما أخرى تفشل. فمثلًا قد تعمل feature questions جيدًا بينما تفشل billing questions لأن billing corpus ناقصة.

تقارن **correlation analysis** human ratings مع metrics مثل faithfulness أو answer relevance. فإذا تنبأت low faithfulness بقوة بـ thumbs-down feedback، تكون تلك metric proxy مفيدة. وإذا لم توجد علاقة، فقد لا تعكس metric ما يقدره المستخدمون.

تفحص **failure analysis** queries ذات التقييم السيئ وتصنف root cause: بيانات مفقودة، retrieval ضعيفة، hallucination، إجابة غير ذات صلة، formatting، latency، أو issue أخرى.

## 48. Measurement و Tuning مهمتان مختلفتان

يدعم برنامج evaluation ناضج كلًا من **measurement** و**tuning**.

تسأل Measurement: *ما مدى صحة نظام RAG الحالي؟* وتوفر baselines و dashboards ومقارنات release و production — بيئة الإنتاج alerts.

وتسأل Tuning: *أي configuration تحسن النظام؟* أنت تغير عمدًا chunking أو embedding model أو retrieval method أو`k` أو reranker أو prompt أو LLM، وتستخدم evaluation suite لمقارنة البدائل.

من دون measurement تصبح tuning تخمينًا. ومن دون tuning تتحول metrics إلى reporting سلبي. يتحسن النظام عندما يرتبط الاثنان.

## 49. شغّل Judge كمكوّن Production

إذا أثرت LLM judges في release decisions أو quality dashboards، فهي تحتاج operational discipline.

سجّل query و retrieved context و generated answer و judge prompt و judge model/version و score و textual reasoning. ويسمح ذلك بمراجعة سبب تغير score.

نفّذ versioning لـ judge prompts. فإذا تغيرت rubric من release إلى أخرى من دون versioning، تنشئ **evaluation drift**: تتغير measured score رغم أن نظام RAG لم يتغير.

يمكن لـ sampling و batching إبقاء judge cost تحت السيطرة. وينبغي عادة أن تعمل online judges خارج synchronous user path ما لم تكن النتيجة نفسها safety gate يجب أن تمنع delivery.

## 50. Offline Evaluation بوصفها CI/CD Quality Gate

قبل deployment لـ embedding model أو reranker أو prompt أو LLM أو chunking strategy تم تغييرها، شغّل evaluation suite الثابتة.

يمكن لفريق production — بيئة الإنتاج تعريف **no-regression policy**، مثلًا:

```text
faithfulness >= required threshold — يجب أن تتجاوز faithfulness الحد المطلوب
retrieval relevance >= required threshold — يجب أن تتجاوز retrieval relevance الحد المطلوب
critical safety tests = 100% pass — يجب أن تنجح اختبارات safety الحرجة بالكامل
P95 latency increase <= allowed budget — يجب ألا تتجاوز زيادة P95 latency الميزانية المسموحة
```

تعتمد thresholds الدقيقة على application. والفكرة المهمة هي أن تتحول quality criteria إلى release requirements بدل ملاحظات غير رسمية.

ينبغي أن تكون benchmark **living dataset**. عندما يكتشف real users query صعبة، أضفها إلى benchmark حتى لا يعود failure نفسه بصمت.

نفّذ versioning للـ benchmark بجانب code و configuration حتى يظل تاريخ evaluation قابلًا للمراجعة.

## 51. ينبغي أن تكون Online Evaluation Asynchronous افتراضيًا

تُعد live traffic قيمة لأنها تحتوي query patterns لم تتوقعها offline benchmark — معيار تقييم offline. لكن ينبغي ألا تجبر evaluation المكلفة المستخدم على الانتظار.

يوصي الفصل بـ architecture تعمل **out-of-band**:

```text
User → RAG → إعادة response فورًا
              ↓
       تسجيل query/context/answer
              ↓
       background evaluation worker — عامل evaluation في الخلفية
              ↓
       quality store / alerts / dashboards — مخزن الجودة والتنبيهات و dashboards
```

يسمح هذا التصميم لـ reference-free judges أو metrics أخرى مكلفة بالعمل من دون إضافة user-perceived latency.

كما أنك لا تحتاج إلى تقييم كل request. يمكن لـ sampling نسبة ممثلة من traffic توفير health signal قوية مع الحفاظ على cost قابلة للإدارة.

## 52. تقييم A/B بنمط Champion–Challenger

بالنسبة إلى candidate improvement، وجّه subset مضبوطة من traffic إلى **challenger** pipeline بينما يظل نظام production — بيئة الإنتاج الحالي هو **champion**.

قارن automated quality metrics و user feedback و latency و cost. ويختبر هذا مباشرة ما إذا كانت configuration تبدو أفضل offline تفيد real users فعلًا.

تكون A/B testing أكثر فائدة عندما يكون كلا variant ين آمنين بما يكفي لعرضهما على المستخدمين. وينبغي للتغييرات عالية الخطورة اجتياز offline gates و staged testing أولًا.

## 53. Latency و Throughput هما أيضًا Quality Metrics

يجب أن يكون نظام RAG في production — بيئة الإنتاج صحيحًا وسريع الاستجابة معًا.

تتبّع end-to-end latency وكذلك per-component latency لـ retrieval و reranking و generation. قد تخفي average latency وحدها تجارب سيئة، لذلك تتبع أيضًا **tail latency** مثل P95 أو P99.

تقيس **Throughput**، التي يُعبّر عنها غالبًا بـ queries per second (QPS)، مقدار concurrent workload التي تستطيع service دعمها.

يُعد تفكيك latency ضروريًا للتشخيص. فإذا ارتفعت P95 بعد إضافة reranker، ينبغي أن تعرف هل reranker نفسها مسؤولة أم أن candidate set جعلت generation أبطأ.

## 54. Reliability: Uptime و Error Rate

تقيس **Uptime** نسبة الوقت الذي يكون فيه application متاحًا. وغالبًا تستهدف enterprise services قيمًا مثل 99.9% أوأعلى بحسب متطلباتها.

تتبّع **error rate** بجانب uptime. قد تكشف HTTP 5xx responses و timeouts و dependency failures و model-provider errors نظامًا يظل "up" تقنيًا لكنه غير سليم.

تمتلك RAG dependencies خارجية عديدة، منها vector DB و reranker و LLM و evaluator و document store، لذلك ينبغي أن تحدد reliability dashboards أي مكوّن تسبب في كل failure.

## 55. Cost و Resource Efficiency

تتبّع الإنفاق حسب المكوّن بدل الاكتفاء بإجمالي cost الشهرية:

- vector database؛
- lexical search؛
- embedding service؛
- reranker؛
- generation LLM؛
- evaluation judge models؛
- compute و storage.

راقب أيضًا استخدام CPU و GPU و memory. تضيف evaluation نفسها cost layer ثانية لأن LLM judges تستهلك tokens و compute.

ولهذا يوصي الفصل بوجود **evaluation budget** بجانب production — بيئة الإنتاج budget. استخدم metrics المكلفة حيث تصنع decision value، واستخدم sampling للـ traffic عندما لا تكون full coverage ضرورية.

## 57. Workflow عملية للتقييم End-to-End

يمكن أن تبدو evaluation cycle منضبطة هكذا:

1. حدد business-critical query classes.
2. ابنِ representative offline query set.
3. أنشئ golden chunks/answers حيثما كان ذلك ممكنًا.
4. اختر stage-specific metrics مرتبطة بـ failure modes المعروفة.
5. أنشئ baseline system.
6. غيّر **متغيرًا رئيسيًا واحدًا في كل مرة** عندما يكون ذلك ممكنًا.
7. أعد تشغيل evaluation وافحص كلًا من aggregate و per-query results.
8. افحص latency و cost حتى لا تكون quality gains غير مقبولة اقتصاديًا.
9. اجعل releases تمر عبر non-regression criteria.
10. نفّذ sampling لـ production — بيئة الإنتاج interactions بصورة asynchronous.
11. ادمج automated metrics مع human feedback.
12. انقل failures المهمة إلى offline benchmark — معيار تقييم offline.

تغلق الخطوة الأخيرة الحلقة: تعمل production — بيئة الإنتاج experience باستمرار على تقوية future evaluation.

## 58. مفاهيم خاطئة شائعة (Common misconceptions)

**المفهوم الخاطئ 1: "يمكن لـ LLM جيدة تعويض Retrieval ضعيفة."**  
لا يمكنها الإجابة بصورة موثوقة من evidence لم تحصل عليها أصلًا.

**المفهوم الخاطئ 2: "Faithfulness مرتفعة تعني أن الإجابة صحيحة."**  
يمكن لـ Model أن تكون faithful تمامًا لـ source documents قديمة أوخاطئة.

**المفهوم الخاطئ 3: "Precision وحدها تكفي."**  
قد تظل context نظيفة لكنها تحذف evidence حرجة؛ لذلك recall مهمة أيضًا.

**المفهوم الخاطئ 4: "تكفي RAG score إجمالية واحدة."**  
تخفي aggregate scores المكوّن الذي فشل.

**المفهوم الخاطئ 5: "Temperature zero تجعل Judging حتمية."**  
قد يظل سلوك LLM غير deterministic.

**المفهوم الخاطئ 6: "Reference-free تعني أن Ground-truth Quality غير ضرورية إلى الأبد."**  
تظل الأمثلة human-calibrated ذات قيمة للتحقق من سلوك judge.

**المفهوم الخاطئ 7: "ينبغي لـ Online Evaluation أن تمنع كل إجابة حتى تنتهي."**  
يمكن تشغيل معظم quality evaluation بصورة asynchronous على sampled traffic.

**المفهوم الخاطئ 8: "Cost الخاصة بـ Evaluation مهملة."**  
يمكن أن تصبح LLM judging مصروفًا ثانويًا ملموسًا من token/compute.

## 59. المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى في هذا الدرس |
|---|---|
| التقييم خارج Production (Offline evaluation) | Evaluation أثناء development، عادة مقابل benchmark مضبوطة |
| التقييم داخل Production (Online evaluation) | Evaluation لـ live production — بيئة الإنتاج interactions |
| Chunk ذهبية (Golden chunk) | Chunk يحددها الإنسان باعتبارها relevant لـ query |
| إجابة ذهبية (Golden answer) | إجابة reference موثوقة |
| مقياس Precision@k | نسبة relevant chunks داخل أعلى top-k chunks معادة |
| مقياس Recall@k | نسبة كل relevant chunks الموجودة التي عُثر عليها ضمن top-k |
| مقياس F1 | Harmonic mean لـ precision و recall |
| مقياس MRR | Rank-sensitive metric تركز على أول relevant result |
| مقياس MAP | Ranking metric تكافئ several relevant results الموضوعة في مراكز مرتفعة |
| مقياس nDCG | Rank-aware metric تدعم graded relevance |
| أسلوب LLM-as-a-judge | استخدام LLM لتقييم output مقابل rubric |
| أسلوب UMBRELA | Reference-free LLM-based relevance scoring للـ retrieved passages |
| حقيقة ذرية (Nugget) | Fact ذرية تُستخدم في context-utilization evaluation |
| مقياس Faithfulness | درجة دعم retrieved context للـ generated claims |
| دقة Citation (Citation precision) | درجة دعم cited evidence للـ claims المرتبطة بها فعلًا |
| انجراف Evaluation (Evaluation drift) | تغيرات score الناتجة عن تغير evaluation criteria/model بدل تغير جودة RAG |
| بوابة Evaluation (Evaluation gate) | CI/CD quality threshold يجب أن يجتازها candidate release |
| زمن Tail latency | Latency عند percentiles مرتفعة مثل P95/P99 |
| مقياس QPS | Queries per second، وهي measure للـ throughput |

## 60. احتفظ بهذا Mental Model (Retain this mental model)

فكر في RAG evaluation باعتبارها **measurement stack تعكس RAG stack**.

```text
SOURCE / INGESTION — المصدر ومرحلة Ingestion
هل المعلومات الصحيحة موجودة ونظيفة ومنظمة وحديثة؟
        ↓
RETRIEVAL — الاسترجاع
هل وجدنا evidence الصحيحة ورتبناها جيدًا؟
        ↓
GENERATION — التوليد
هل استخدمنا تلك evidence بصورة faithful وكاملة وذات صلة؟
        ↓
USER — المستخدم
هل كانت النتيجة مفيدة وموثوقة؟
        ↓
SYSTEM — النظام
هل كان سريعًا ومتاحًا وقابلًا للتوسع ومقبول التكلفة؟
```

عندما تسوء metric، اسأل أولًا لأي layer تنتمي قبل تغيير أي شيء. تمنع هذه العادة random tuning وتحول evaluation إلى engineering discipline.

## ملخص الدرس (Lesson summary)

RAG evaluation هي engineering discipline مستمرة. شخّص ingestion و retrieval و generation و user outcomes و system health كلًا على حدة؛ واستخدم metrics تتوافق مع failure الذي تحاول اكتشافه؛ وادمج golden-data evaluation مع scalable reference-free techniques عندما يكون ذلك مناسبًا؛ ونفّذ calibration لـ LLM judges بدل الوثوق بها بصورة عمياء؛ وادمج offline evaluation داخل CI/CD؛ ونفّذ sampling وتقييمًا لـ production — بيئة الإنتاج traffic بصورة asynchronous؛ وأغلق الحلقة بتحويل real failures و human feedback إلى regression tests جديدة.
