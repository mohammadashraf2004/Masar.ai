## 1. ما هو FastAPI

FastAPI هو Web Framework بلغة Python لبناء APIs وخدمات Backend للويب.

يصفه الفصل بأنه **ASGI framework**. ويرمز ASGI إلى **Asynchronous Server Gateway Interface**.

وهذا مهم لأن خدمات Backend الحديثة تقضي كثيرًا من الوقت في انتظار أعمال خارجية مثل:

- استعلامات قواعد البيانات،
- طلبات HTTP،
- خدمات الشبكة،
- عمليات الملفات،
- التفاعل مع Model Servers خارجية.

يمكن للخادم غير المتزامن استخدام وقت الانتظار بكفاءة أكبر عبر العمل على Requests أخرى بدلًا من حجب الخادم بالكامل.

يوفّر FastAPI أيضًا عدة خصائص مفيدة بصورة خاصة لتطوير APIs:

- تعريف Routes باستخدام Python decorators،
- Request و Response validation،
- Data serialization،
- توليد مواصفات OpenAPI تلقائيًا،
- توثيق Swagger تفاعلي،
- نمط Dependency injection،
- دعم Handlers المتزامنة وغير المتزامنة،
- تكامل Middleware و Security،
- دعم WebSocket وأنماط اتصال أخرى غير REST.

يعتمد FastAPI نفسه على **Starlette**، بينما تمثل **Pydantic** جزءًا أساسيًا من تجربة Data validation و Serialization فيه.

### FastAPI و Uvicorn و Starlette و Pydantic

من المفيد فصل أدوار هذه المكونات:

| المكوّن | دوره في Stack |
|---|---|
| إطار FastAPI | Application framework الذي تكتب به API |
| مكتبة Starlette | ASGI toolkit/framework الأساسي الذي يستخدمه FastAPI |
| خادم Uvicorn | ASGI web server الذي يشغّل Application |
| مكتبة Pydantic | دعم Data parsing و Schema definition و Validation و Serialization |

من أخطاء المبتدئين الاعتقاد أن `FastAPI()` نفسه يفتح Network Port.

هو لا يفعل ذلك.

أنت تعرّف Application باستخدام FastAPI، ثم يشغّلها ASGI server مثل Uvicorn.

### لماذا هذا مهم لـ GenAI

غالبًا ما يحتاج Backend خاص بـ GenAI إلى تنسيق:

```text
طلب العميل
    ↓
المصادقة / التحقق
    ↓
قاعدة البيانات أو API خارجي
    ↓
تحضير الـ prompt/السياق
    ↓
استدعاء النموذج
    ↓
المعالجة اللاحقة
    ↓
الاستجابة
```

تتضمن كثير من هذه الخطوات I/O خارجيًا، لذلك يمثل Framework مصممًا لأحمال APIs الحديثة أساسًا مفيدًا.

## 4. التوثيق التلقائي و Serialization و Validation

من أقوى مزايا FastAPI للمبتدئين أن عدة أجزاء من بنية API التحتية تظهر تلقائيًا انطلاقًا من تعريفات Python التي تكتبها.

### توثيق OpenAPI و Swagger

ينشئ FastAPI **OpenAPI specification** لخدمتك.

ويمكن لهذه Specification تشغيل صفحة Swagger UI عند `/docs`.

تتيح لك الصفحة:

- فحص Endpoints،
- رؤية Parameters المتوقعة،
- رؤية Schemas،
- إرسال Test Requests،
- فحص Responses.

[[IMAGE_NEEDED: FastAPI Swagger UI | A screenshot or recreated local development view of a FastAPI `/docs` page showing at least two endpoints, their HTTP methods, parameters, and the interactive 'Try it out' workflow | Learner should notice that endpoint documentation and interactive testing are generated from the API definitions rather than being written manually]]

تُعد Interactive docs مفيدة أثناء التطوير، لكن الفصل يؤكد أنها **لا تستبدل Automated Tests**.

ما تزال الخدمة الناضجة تحتاج إلى Tests منهجية لأن النقر يدويًا على Endpoints لا يتحقق بصورة موثوقة من كل سلوك بعد كل تغيير في Code.

### عملية Serialization

لا ينقل HTTP كائنات Python حية وعشوائية مباشرة.

يجب تحويل Data إلى Representation قابلة للنقل مثل JSON.

مفاهيميًا:

```text
Python dictionary
      ↓
Serialization — التسلسل
      ↓
JSON
      ↓
HTTP
      ↓
Client — العميل
      ↓
Deserialization — فك التسلسل
      ↓
Client-side object — كائن لدى Client
```

إذا أعاد Route قاموس Python، يتولى FastAPI عملية Serialization نيابة عنك.

### عملية Validation

يسأل Validation:

> هل تستوفي Data الواردة القواعد التي يتطلبها هذا API؟

بالنسبة إلى Request لإنشاء User، قد تريد قواعد مثل:

- يجب أن يكون username نصًا،
- يجب أن تستوفي password متطلبات Policy،
- يجب أن يكون email بصيغة صحيحة.

تتيح لك Pydantic schemas التعبير عن هذه الأنواع من Runtime constraints وفرضها.

يبدو Model مفاهيمي كما يلي:

⟦CODE_9⟧

يمكن لـ FastAPI استخدام Schema لتحليل Request data الواردة والتحقق منها قبل أن تعمل Business logic عليها.

### Static typing ليس Runtime validation

يمكن لـ Type checker التحذير من Code أثناء التطوير.

أما Runtime validation فيحمي Application الجاري من Data واردة غير صحيحة.

هذان يحلان مشكلتين مختلفتين.

```text
Static type checking — فحص الأنواع الثابت
→ يحلل Code قبل Runtime

Runtime validation — التحقق أثناء Runtime
→ يفحص Data الفعلية الداخلة إلى الخدمة الجارية
```

يصبح كلاهما أكثر أهمية مع نمو API.

الدرس العملي هو:

> **تكون Concurrency أكثر فائدة عندما يقضي Request وقتًا في انتظار I/O.**

ومن الأمثلة:

- الوصول إلى Database،
- HTTP calls،
- External services،
- الاتصال عبر Network communication.

### Async لا يجعل الأعمال كثيفة CPU مجانية

هذه حدود مهمة جدًا.

لنفترض أن Route ينفّذ Model inference مكلفًا مباشرة داخل Web process.

هذا Workload ليس مجرد "انتظار".

قد يستهلك قدرًا كبيرًا من CPU أو GPU compute.

حتى Route مكتوب بـ `async def` يمكن أن يصبح Bottleneck إذا نفّذ عملًا Blocking وكثيف الحساب.

سنعود إلى ذلك في قسم قيود FastAPI.

### مهام Background tasks

بعض الأعمال لا تحتاج إلى الاكتمال قبل أن يتلقى Client إقرارًا بالاستلام.

ومن الأمثلة:

- إرسال Email،
- Post-processing لملف مرفوع،
- Indexing لمستند كبير،
- إدخال Embeddings في Vector database.

النمط المفيد هو:

```text
طلب Client (Client request)
      ↓
يتحقق Server من Request (Server validates request)
      ↓
يقبل Server العمل (Server accepts work)
      ↓
استجابة فورية إلى Client (Immediate response to client)
      ↓
تستمر Background operation
```

يستخدم الفصل تحديدًا معالجة المستندات للتخزين في Vector storage مثالًا من GenAI.

يساعد هذا على منع عملية طويلة من إبقاء User-facing request مفتوحًا دون حاجة.

### طبقة Middleware

تقع Middleware حول Request handling.

فكّر فيها كطبقة ترى Requests قبل وصولها إلى Endpoint وترى Responses قبل عودتها إلى Client.

```text
Client — العميل
  ↓
Middleware — البرمجيات الوسيطة
  ↓
Route handler — معالج Route
  ↓
Middleware — البرمجيات الوسيطة
  ↓
Client — العميل
```

يمكن لـ Middleware دعم مهام مثل:

- Logging،
- إضافة Headers أو تعديلها،
- Cookies،
- Request checks،
- Monitoring،
- سلوك CORS.

### إعداد CORS

يكون CORS مهمًا عندما يعمل Frontend و Backend عبر Origins مختلفة.

على سبيل المثال:

```text
Frontend: https://app.example.com    # عنوان واجهة المستخدم (Frontend)
Backend:  https://api.example.com
```

قد تتطلب قواعد أمان Browser أن يسمح Backend صراحةً بـ Frontend origin.

يدعم FastAPI Middleware لهذا النوع من Configuration.

### التخصيص

لأن FastAPI يعتمد على Starlette، يشير الفصل إلى أنه يمكنك تخصيص السلوك باستخدام آليات مثل:

- Custom exception handlers،
- ASGI middleware،
- Custom responses،
- تخصيص Custom serialization.

يمنحك هذا مرونة عندما لا يكون السلوك الافتراضي لـ Framework كافيًا.

### لماذا تهم Dependency injection

يمكن لـ Dependencies توحيد Concerns قابلة لإعادة الاستخدام مثل:

- Pagination،
- Database sessions،
- Authentication،
- Authorization،
- Shared request parsing،
- Feature checks،
- تحميل User.

يقلل ذلك التكرار ويجعل Responsibilities أسهل في الاختبار بصورة مستقلة.

### مثال Database session

يعرض الفصل Pattern تنشئ فيه Dependency جلسة Database، ثم تمنحها إلى Route باستخدام `yield`، وبعد ذلك تغلقها.

مفاهيميًا:

⟦CODE_14⟧

يصبح تدفق Request:

```text
يبدأ Request (Request begins)
    ↓
يفتح get_db() جلسة (get_db() opens session)
    ↓
يتلقى Route الجلسة (route receives session)
    ↓
ينفذ Route عمل Database (route performs database work)
    ↓
تكتمل Response (response completes)
    ↓
يغلق Cleanup في get_db() الجلسة (get_db() cleanup closes session)
```

يساعد ذلك على منع Resource leaks.

### Dependencies نطاقها Request وقابلة لإعادة الاستخدام

يشير الفصل إلى أن نتيجة Dependency يمكن أن تُخزَّن في Cache ضمن سياق Request واحد.

إذا اعتمدت عدة أجزاء من Request نفسه على Dependency نفسها، يمكن لـ FastAPI إعادة استخدام نتيجتها بدلًا من تكرار العمل بلا داعٍ.

في Request التالي، تعمل Dependency مرة أخرى.

### الرسوم الهرمية لـ Dependency graphs

يمكن لـ Dependency أن تعتمد على Dependency أخرى.

على سبيل المثال:

```text
get_db
  ↓
get_current_user
  ↓
require_admin
  ↓
Endpoint مخصص لـ Admin فقط (admin-only endpoint)
```

ينشئ هذا Dependency graph.

وهو مفيد بصورة خاصة لـ:

- Authentication،
- Authorization،
- Nested data retrieval،
- منطق Decision logic.

### Dependency injection ليست مجرد وسيلة للراحة

عند استخدامها جيدًا، فإنها تغيّر بنية Application.

بدلًا من أن ينشئ Controller كل ما يحتاج إليه يدويًا، يعلن Controller متطلباته.

وهذه خطوة مهمة نحو Layered architecture.

## 7. Lifespan events و Security وأنماط الاتصال

### أحداث Lifespan events

بعض Resources مكلفة إذا تم إنشاؤها لكل Request.

ومن الأمثلة:

- Database connection pools،
- AI models كبيرة،
- Shared clients،
- وحدات Caches.

تسمح FastAPI lifespan events بتهيئة Shared resources أثناء Application startup وتنظيفها أثناء Shutdown.

النمط هو:

```text
يبدأ Application (Application starts)
       ↓
تحميل Shared resources (Load shared resources)
       ↓
خدمة Requests عديدة (Serve many requests)
       ↓
يتوقف Application (Application stops)
       ↓
تنظيف Resources (Clean up resources)
```

بالنسبة إلى GenAI، يفيد ذلك بصورة خاصة عندما ينبغي تحميل Model مرة واحدة وإعادة استخدامه.

سيكون تحميل Model نفسه من Disk لكل Request غير فعّال.

### Security و Authentication

يوفّر FastAPI مكونات Security لكنه لا يفرض تنفيذ Authentication محددًا واحدًا.

يؤكد الفصل المرونة:

- يمكنك بناء Authentication layer خاصة بك،
- يمكنك استخدام Third-party packages،
- يمكنك التكامل مع External identity providers.

يتوافق ذلك مع أسلوب FastAPI غير الصارم عمومًا.

### نقاط REST endpoints

تستخدم REST عادة HTTP methods مثل:

```text
GET     → استرجاع
POST    → إنشاء
PUT     → استبدال/تحديث
PATCH   → تحديث جزئي
DELETE  → حذف
```

أمثلة على Resource routes:

```text
GET    /api/messages    # مسارات نقاط النهاية لإدارة الرسائل
POST   /api/messages
GET    /api/messages/{id}
PUT    /api/messages/{id}
PATCH  /api/messages/{id}
DELETE /api/messages/{id}
```

### WebSockets و SSE

لا يكون تبادل Request/Response العادي مثاليًا دائمًا لـ GenAI.

عند توليد Text token by token، قد يرغب Client في الحصول على Response تدريجيًا.

يشير الفصل إلى:

- **WebSockets (WS)** للاتصال المستمر ثنائي الاتجاه،
- **Server-Sent Events (SSE)** لتدفق Updates من Server إلى Client.

وهي مفيدة لواجهات AI في Real-time.

### واجهة GraphQL

يذكر الفصل أيضًا GraphQL باعتباره نهج API بديلًا يمكن فيه لـ Clients طلب Fields محددة وتجنب استرجاع Data غير ضرورية.

يمكن لـ FastAPI التكامل مع GraphQL عبر External packages، رغم أن GraphQL ليس محور الفصل.

### Python الحديثة ودعم IDE

لأن FastAPI يستخدم بقوة خصائص Python الحديثة مثل Type annotations، يمكن للمحررات و Developer tools توفير:

- Autocomplete،
- Type diagnostics،
- Formatting،
- Linting،
- Navigation أسهل.

يساهم ذلك في تحسين Developer experience مع نمو المشروع.

## 8. تنظيم مشروع FastAPI

من السهل فهم تطبيق FastAPI مكوّن من ملف واحد.

أما Production service فليست كذلك.

مع تراكم Features، قد يحتوي المشروع على:

- Routes،
- Schemas،
- Database models،
- Repositories،
- Business logic،
- Authentication،
- External APIs،
- AI model clients،
- Prompts،
- Retrieval logic،
- Background tasks،
- أدوات Utilities.

من دون تنظيم، قد ينتهي Developers إلى:

- ملفات ضخمة جدًا،
- Ownership غير واضح،
- Circular imports،
- دوال يصعب العثور عليها،
- تغييرات تؤثر بصورة غير متوقعة في ملفات كثيرة.

يقدّم الفصل ثلاثة هياكل للمشروعات: **Flat و Nested و Modular**.

### 8.1 البنية المسطحة (Flat structure)

يحافظ Flat project على عدد صغير من الملفات متقاربة.

```text
flat-project/    # مشروع ببنية مسطحة
├── app/
│   ├── services.py
│   ├── database.py
│   ├── models.py
│   ├── routers.py
│   └── main.py
├── requirements.txt
├── .env
└── .gitignore
```

تعمل هذه البنية جيدًا عندما:

- تكون الخدمة صغيرة،
- تنفّذ Prototype،
- لا تزال Architecture تتطور،
- يوجد عدد قليل فقط من الملفات.

الميزة هي البساطة.

تظهر المشكلة عندما ينمو كل ملف ليصبح Bucket عالميًا وضخمًا.

### 8.2 البنية المتداخلة (Nested structure)

تجمع Nested structure Code حسب الفئة التقنية.

```text
nested-project/    # مشروع ببنية متداخلة
├── app/
│   ├── main.py
│   ├── dependencies.py
│   ├── services/
│   │   ├── users.py
│   │   └── profiles.py
│   ├── models/
│   │   ├── users.py
│   │   └── profiles.py
│   └── routers/
│       ├── users.py
│       └── profiles.py
├── requirements.txt
├── .env
└── .gitignore
```

يسهّل ذلك تحديد موقع Code حسب دوره التقني.

ومع ذلك، قد تتوزع Feature واحدة عبر Directories عديدة.

وقد يتطلب تغيير Domain concept واحد تعديلات في عدة أماكن.

يصف الفصل التعديلات الواسعة المتتابعة باسم **shotgun updates**.

### 8.3 البنية المقسمة حسب المجال (Modular structure)

تجمع Modular structure المكونات شديدة الارتباط حسب Domain أو Feature.

```text
modular-project/    # مشروع ببنية معيارية (modular)
├── app/
│   ├── modules/
│   │   ├── auth/
│   │   │   ├── routers.py
│   │   │   ├── models.py
│   │   │   ├── dependencies.py
│   │   │   ├── guards.py
│   │   │   └── services.py
│   │   ├── users/
│   │   │   ├── router.py
│   │   │   ├── models.py
│   │   │   ├── dependencies.py
│   │   │   ├── services.py
│   │   │   ├── mappers.py
│   │   │   └── pipes.py
│   │   └── profiles/
│   ├── providers/
│   │   ├── email.py
│   │   └── stripe.py
│   ├── settings.py
│   ├── middlewares.py
│   ├── models.py
│   ├── exceptions.py
│   └── main.py
├── requirements.txt
├── .env
└── .gitignore
```

الفكرة الأساسية هي **Feature encapsulation**.

كل ما يرتبط بقوة بـ Authentication يبقى قريبًا من Authentication.

وكل ما يرتبط بقوة بـ Users يبقى قريبًا من Users.

قد يجعل ذلك من الأسهل توقع المكان الذي ينتمي إليه التغيير وما الذي يمكن أن يؤثر فيه.

### إعادة التنظيم تدريجيًا

لا يطلب منك الفصل أن تبدأ كل مشروع بأقصى قدر من Architecture.

بل يوصي بالسماح للبنية بالتطور:

```text
مسطحة (Flat)
  ↓
متداخلة (Nested)
  ↓
مقسمة إلى Modules (Modular)
```

قاعدة قرار مفيدة هي:

| حالة المشروع | البنية المناسبة |
|---|---|
| تجربة صغيرة أو First version | بنية Flat |
| Microservice نامية وبها عدة Technical areas | بنية Nested |
| Backend أكبر وبها Domains/Features متعددة | بنية Modular |

الدرس المهم ليس أن بنية واحدة صحيحة عالميًا.

بل هو:

> **ينبغي أن تجعل بنية مشروعك موقع Code ومسؤوليته وتأثيره سهلة الفهم.**

إذا لم يتمكن Developer آخر من فهم سبب وجود File في مكانه، فقد تحتاج البنية إلى إعادة نظر.

## 9. تصميم Application بأسلوب Onion/Layered

تخبرك Project structure **أين تعيش الملفات**.

أما Layered design فيخبرك **بالمسؤوليات التي ينبغي أن تمتلكها الأجزاء المختلفة من النظام وكيف ينبغي أن تعتمد على بعضها**.

يقدّم الفصل **onion design pattern**.

الفكرة الأساسية هي Separation of concerns.

في المركز توجد Domain concepts و Business rules.

أما الطبقات الخارجية فتتعامل مع تفاصيل مثل APIs و External services و Persistence و User interaction.

### مبدأ Dependency inversion

يربط الفصل Onion architecture بـ **dependency inversion principle**.

بدلًا من أن تنشئ High-level logic تنفيذات Low-level وتعتمد عليها مباشرة، تعلن Components ما تحتاج إليه وتتلقى Dependencies متوافقة.

يقلل هذا Coupling.

على سبيل المثال، لا ينبغي أن تحتاج Business service إلى معرفة كل تفاصيل إنشاء Database connection.

يمكنها الاعتماد على Repository interface توفّر Data operation التي تحتاج إليها.

### مسؤوليات Layers

لننتقل من حدود HTTP إلى الداخل.

### موجّهات API routers

تجمع Routers معالجات Routes المرتبطة ببعضها.

على سبيل المثال:

```text
/users    # مسارات الموارد
/users/{id}
/users/{id}/messages
```

قد تنتمي إلى Router واحدة.

يوفّر FastAPI `APIRouter` لهذا الغرض.

### مكوّنات Controllers / route handlers

تستقبل Controllers الـ Requests وتعيد Responses.

ينبغي أن ينسّق Controller الـ Request، لا أن يحتوي على كل تفاصيل التنفيذ.

مفاهيميًا:

```text
طلب HTTP
    ↓
المتحكم
    ↓
الخدمة
    ↓
المستودع/المزوّد
    ↓
النتيجة
    ↓
المتحكم
    ↓
استجابة HTTP
```

غالبًا ما يتلقى Controller النظيف Dependencies بدلًا من إنشائها يدويًا.

### طبقة Services

تنسّق Services العمليات الداخلية لتنفيذ Business logic.

على سبيل المثال، قد يحتاج Payment workflow إلى:

1. جلب User،
2. فحص Order،
3. استدعاء Payment provider،
4. تسجيل Result،
5. إرسال Confirmation.

تنسّق Service هذه الخطوات.

### طبقة Providers

تتواصل Providers مع External systems.

ومن الأمثلة Clients لـ:

- Email services،
- Payment gateways،
- Third-party APIs،
- Microservices أخرى،
- واجهات Model APIs.

التمييز مفيد:

```text
Service — الخدمة
→ تنفّذ Application/business workflow

Provider — المزوّد
→ يتعامل مع External system
```

### طبقة Repositories

تعزل Repositories منطق Data access و Mutation.

وقد تستخدم:

- ORM،
- Raw SQL،
- Memory store،
- Persistence mechanism أخرى.

تشمل عمليات Repository الشائعة CRUD:

- Create،
- Read،
- Update،
- عملية Delete.

تسمح Repository للطبقات الأعلى بطلب Data من دون نشر تفاصيل تنفيذ Database في كل مكان.

### مكوّنات Schemas / models

تساعد Schemas و Models على فرض:

- Data shape،
- Type safety،
- قواعد Validation.

وهي تحدد البنية المتوقعة للمعلومات أثناء انتقالها عبر Service.

### مكونات Cross-cutting

بعض Components لا تنتمي إلى Layer واحدة فقط.

#### طبقة Middleware

تعمل حول Requests و Responses.

#### مكوّنات Dependencies

دوال أو Resources قابلة لإعادة الاستخدام و Injection.

#### مكوّنات Pipes

تحوّل Data.

ومن الأمثلة:

- Cleaners،
- Parsers،
- Aggregators،
- مكوّنات Translators.

#### مكوّنات Mappers

تحول Data من Schema أو Representation إلى أخرى.

مثال:

```text
UserRequest
    ↓ mapper — تحويل عبر Mapper
UserInDB
```

#### مرشحات Exception filters

تتعامل مع Errors بصورة متسقة.

#### مكوّنات Guards

تحمي Routes أو Operations.

تُعد Authentication و Authorization checks أمثلة شائعة.

### لماذا يهم هذا في GenAI

يمكن أن يصبح Backend خاص بـ GenAI صعب الصيانة إذا احتوى Route واحد على كل شيء:

```text
مصادقة User (authenticate user)
+ استرجاع Data (retrieve data)
+ بناء Prompt (construct prompt)
+ استدعاء Model (call model)
+ استدعاء Payment API (call payment API)
+ كتابة Database record (write database record)
+ التقاط كل Error (catch every error)
+ تنسيق Response (format response)
```

يساعد Layering على فصل هذه Concerns.

قد يكون التصميم الأوضح:

```text
Router — الموجّه
  ↓
Controller — المتحكم
  ↓
خدمة GenAI (GenAI service)
  ├── Retrieval repository — مستودع الاسترجاع
  ├── Model provider — مزوّد Model
  ├── External API provider — مزوّد API خارجي
  └── Conversation repository — مستودع المحادثة
```

يسهل اختبار هذا التصميم وفهمه لأن لكل جزء مسؤولية أضيق.

## 10. مقارنة FastAPI مع Django و Flask

يضع الفصل اختيار Framework جزئيًا في إطار مدى كون Framework **opinionated**.

### Frameworks الصارمة نسبيًا (Opinionated frameworks)

تمنحك Opinionated framework مزيدًا من البنية والاتفاقيات الجاهزة.

يستخدم الفصل Django مثال Python الرئيسي.

تشمل المزايا:

- Features متكاملة كثيرة،
- توقعات Architecture مدمجة،
- Ecosystem ناضجة،
- حاجة أقل لاختيار كل Component بنفسك.

المفاضلة:

- تقبل قدرًا أكبر من بنية Framework.

### Frameworks المرنة (Nonopinionated frameworks)

يمنح FastAPI و Flask المطورين حرية Architecture أكبر.

المزايا:

- Flexibility،
- Services أخف،
- حرية اختيار Supporting components.

المفاضلة:

- قرارات أكثر،
- Integration work أكثر،
- مسؤولية أكبر للحفاظ على تنظيم Codebase.

### إطار Django

يسلط الفصل الضوء على إمكانات Django المتكاملة القوية، ومنها مجالات مثل:

- ORM،
- Migrations،
- Administration،
- Authentication،
- Authorization،
- Security features،
- Ecosystem ناضجة.

ويقدَّم بوصفه خيارًا قويًا لتطبيقات Web monolithic الأكبر حيث تكون Integrated stack ذات قيمة.

### إطار Flask

يُقدَّم Flask باعتباره Lightweight جدًا.

تفيد بساطته في Services الصغيرة، لكن الفصل يشير إلى أن Features مثل:

- Built-in schema validation،
- Automatic documentation،
- نمط Dependency injection

ليست مضمّنة بالطريقة نفسها الموجودة في FastAPI وقد تتطلب Packages إضافية أو Design work.

### WSGI مقابل ASGI

يقارن الفصل بين Serving model التقليدي لـ Flask المبني على WSGI وبين ASGI model في FastAPI.

تصور ذهني مبسط:

```text
WSGI
→ معالجة طلبات متزامنة تقليديًا

ASGI
→ مصمم لأنماط التطبيقات غير المتزامنة/المتوازية
```

يكون ASGI مفيدًا بصورة خاصة لـ Workloads التي تتضمن فترات انتظار I/O كثيرة وأنماط Connections طويلة العمر.

### اختيار Framework يعتمد على السياق

يمكن تلخيص مقارنة الفصل كما يلي:

| الحاجة | إطار الفصل |
|---|---|
| تطبيق Web monolithic متكامل | قد يكون Django جذابًا |
| API بسيط وخفيف جدًا | قد يكون Flask جذابًا |
| API حديث يدعم Validation و Docs و DI و Async و AI integrations | يكون FastAPI جذابًا |

الدرس ليس "FastAPI أفضل دائمًا."

بل هو:

> **اختر Framework تتناسب Defaults والمفاضلات الخاصة به مع النظام الذي تبنيه.**

## 11. قيود FastAPI لأحمال AI

يُعد FastAPI Framework ممتازًا لـ API، لكن الفصل حريص على عدم تقديمه كحل Model-serving كامل لكل Workload.

هذا أحد أهم أجزاء الفصل.

### 11.1 إدارة Model memory

تستهلك Models الكبيرة قدرًا كبيرًا من Memory.

عندما تتوسع Application workers عبر Processes أو Containers، قد يحتاج كل Worker إلى Model instance خاص به.

يمكن أن يضاعف ذلك استهلاك Memory.

مفاهيميًا:

```text
Worker 1 → نسخة Model (model copy)
Worker 2 → نسخة Model (model copy)
Worker 3 → نسخة Model (model copy)
Worker 4 → نسخة Model (model copy)
```

إذا كان Model الواحد كبيرًا بالفعل، فقد يصبح هذا مكلفًا.

### 11.2 Thread capacity محدودة

يمكن لـ FastAPI تشغيل الأعمال المتزامنة داخل Thread pool، لكن Thread pool محدودة.

يمكن للأعمال المتزامنة الثقيلة استهلاك Workers وتقليل Throughput.

### 11.3 Python GIL والأحمال كثيفة Compute

يناقش الفصل **Global Interpreter Lock (GIL)** بوصفه قيدًا في Python multithreading مع الأعمال كثيفة CPU.

تمييز أساسي:

```text
مهمة كثيفة I/O
→ تقضي وقتها في الانتظار
→ يمكن أن يفيد التزامن (concurrency) كثيرًا

Inference كثيف على CPU/GPU
→ يقضي وقته في الحساب
→ قد يظل يحجب معالجة الطلبات المفيدة
```

لهذا فإن مجرد إضافة `async` لا تحل Heavy inference.

### 11.4 غياب Micro-batching الفعّال تلقائيًا

غالبًا ما يكون Deep-learning inference أكثر كفاءة عندما تعالَج عدة Inputs ضمن Batch.

يتعامل نموذج Requests العام في FastAPI مع Requests بصورة مستقلة ولا يجمعها تلقائيًا في Optimized inference batches.

قد يؤدي ذلك إلى إهدار Accelerator capacity في Heavy serving workloads.

### 11.5 تقسيم Workload بين CPU و GPU

يمكن لـ Specialized model-serving architecture فصل المسؤوليات:

```text
CPU:
- Validation — التحقق
- Preprocessing — المعالجة المسبقة
- Request transformation — تحويل Request
- Post-processing — المعالجة اللاحقة

GPU:
- Neural-network inference — استدلال Neural network
```

يشير الفصل إلى أن FastAPI نفسه غير مصمم لتنظيم كل جوانب هذا التقسيم بكفاءة للأحمال الصعبة من Inference.

### 11.6 تعارض Dependencies

تعتمد ML systems غالبًا على:

- Hardware-specific libraries،
- CUDA versions،
- Native packages،
- Model runtimes،
- Python packages ذات Version relationships صارمة.

لذلك يمكن أن يكون Deployment أصعب من نشر Web API عادي.

### 11.7 Models كثيفة الموارد

بالنسبة إلى Models الكبيرة والمكلفة، قد لا يكون General-purpose API framework هو Model server المثالي.

يقدّم الفصل **BentoML** بوصفه Specialized ML-serving framework يمكنه التعامل مع Concerns مثل:

- Model runners،
- Dependency management،
- Model versioning،
- Deployment configuration،
- فصل Web request handling عن Model inference.

### Architecture هجينة

يقترح الفصل Production pattern مهمًا:

```text
العميل
  ↓
FastAPI
  ├── المصادقة (authentication)
  ├── التفويض (authorization)
  ├── caching
  ├── منطق الأعمال
  └── معالجة الطلب/الاستجابة
        ↓
خادم نماذج متخصص
        ↓
Inference ثقيل لـ AI
```

يحافظ هذا على FastAPI في المجالات التي يتفوق فيها مع تفويض Model serving المكلف إلى Infrastructure مصممة لهذه المهمة.

### الدرس الهندسي الأساسي

لا تخلط بين:

> **API framework جيد**

وبين:

> **High-performance inference platform كاملة**

يمكن أن يكون FastAPI طبقة Control و Application ممتازة حتى عندما تُخدَم Models الثقيلة في مكان آخر.

## 12. البيئات المُدارة و Tooling الاحترافي في Python

مع نمو المشروع، تصبح Code quality خاصية في النظام.

يوصي الفصل بإدارة Dependencies وإضافة Tools تكتشف الأخطاء قبل Production.

### خيارات Dependency management

يذكر المصدر:

- `requirements.txt` مع `pip` للمشروعات الأبسط،
- `uv` أو Conda لسير العمل القائم على pip،
- Poetry للمشروعات الأكثر تعقيدًا.

يمكن أن تختلف Tool المحددة.

المتطلب الأعمق هو Reproducibility:

> ينبغي أن يتمكن Developer آخر أو Deployment environment من إعادة إنشاء Dependencies التي تتوقعها خدمتك.

### أدوات Linters

تحلل Linters الـ Source code بحثًا عن مشكلات.

يسرد الفصل أمثلة مثل:

- Autoflake،
- Flake8،
- أداة Ruff.

يمكنها تحديد مشكلات تشمل:

- Unused imports،
- Style problems،
- Suspicious code،
- أنماط Inconsistent patterns.

### أدوات Formatters

تجعل Formatters عرض Code متسقًا.

يذكر الفصل:

- isort،
- Black،
- أداة Ruff.

يقلل Formatting المتسق ضوضاء Code review ويجعل Code أسهل في الفحص.

### نظام Logging

يذكر الفصل Loguru باعتبارها Logging tool بديلة.

يصبح Logging مهمًا عندما تحتوي Service على Layers متعددة متفاعلة و External systems.

قد يجيب Log مفيد عن:

```text
ما Request الذي فشل؟ (What request failed?)
أي Component فشل؟ (Which component failed?)
ما Operation التي كانت قيد التنفيذ؟ (What operation was being attempted?)
ما المعلومات التي تساعد على إعادة إنتاج المشكلة؟ (What information can help reproduce the issue?)
```

### أدوات Security scanners

يسمي الفصل:

- Bandit،
- أداة Safety.

تهدف هذه Tools إلى اكتشاف فئات من Code غير الآمن أو Dependencies الضعيفة.

هي لا تستبدل Secure architecture، لكنها قد تكتشف الأخطاء مبكرًا.

### أدوات Type checkers

يسرد الفصل:

- Mypy،
- أداة Pylance.

يصبح Type checking ذا قيمة خاصة عندما تتطور Schemas و Function interfaces.

على سبيل المثال، إذا تغير Data model من:

```text
user_id: int — معرّف User من نوع int
```

إلى:

```text
user_id: str — معرّف User من نوع str
```

قد تكشف Type-aware tooling الافتراضات اللاحقة التي تحتاج إلى تحديث.

### Git و `.gitignore`

يوفّر Git Version control.

يبقي ملف `.gitignore` ملفات محددة خارج Version tracking.

تشمل الأسباب المعتادة لاستبعاد Files:

- Local virtual environments،
- Generated caches،
- Machine-specific files،
- أسرار Local secrets.

### IDE integration و Automated checks

يشجع الفصل إعداد Editors مثل VS Code أو PyCharm لتشغيل Tools مفيدة أثناء التطوير.

ويوصي أيضًا بـ Automated checks قبل Commit أو Deployment.

قد يبدو Workflow احترافي مفاهيميًا هكذا:

```text
اكتب Code (Write code)
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> يجعل `async def` أي FastAPI route قابلة للتوسع تلقائيًا.

### لماذا هذا خطأ

يفيد Async أكثر عندما يقضي Code وقتًا في انتظار Asynchronous I/O. أما العمليات الكثيفة على CPU/GPU فما تزال قادرة على حجب المعالجة المفيدة وقد تحتاج إلى Processes أو Infrastructure متخصصة لـ Model serving.

### المفهوم الخاطئ 2

> وجود Swagger UI يعني أنك لم تعد بحاجة إلى Tests.

### لماذا هذا خطأ

تُعد Swagger UI ممتازة للاستكشاف التفاعلي و Debugging، لكن Automated tests ضرورية للتحقق منهجيًا من السلوك مع تغير Code.

### المفهوم الخاطئ 3

> Modular project structure هي دائمًا أفضل نقطة بداية.

### لماذا هذا خطأ

يوصي الفصل بإعادة التنظيم تدريجيًا. يمكن للمشروعات الصغيرة أن تبدأ Flat، ثم تصبح Nested مع نمو التعقيد التقني، ثم Modular عندما تبرر Domains و Features البنية الإضافية.

### المفهوم الخاطئ 4

> Dependency injection مجرد Shortcut لتقليل عدد أسطر Code.

### لماذا هذا خطأ

هي تقلل أيضًا Coupling، وتجمع Behavior القابل لإعادة الاستخدام، وتدير Resources، وتدعم Hierarchical dependencies، وتساعد على Separation of concerns.

### المفهوم الخاطئ 5

> ينبغي لـ FastAPI أن يخدم كل AI model مباشرة.

### لماذا هذا خطأ

FastAPI هو General-purpose API framework. قد تحتاج Models الثقيلة إلى Specialized serving infrastructure لإدارة Memory و Batching و Compute isolation وتنسيق CPU/GPU.

### المفهوم الخاطئ 6

> Project structure و Architecture شيء واحد.

### لماذا هذا خطأ

تحدد Project structure كيفية تنظيم Files و Packages. أما Architecture فتحدد مسؤوليات Components وحدودها و Dependencies بينها. ويمكنك تطبيق Layered architecture داخل Directory structures مختلفة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| إطار FastAPI | Framework بلغة Python لبناء APIs وخدمات Backend |
| معيار ASGI | معيار Asynchronous server interface تستخدمه تطبيقات Python الحديثة للويب |
| خادم Uvicorn | ASGI server يُستخدم عادة لتشغيل تطبيقات FastAPI |
| مسار Route | ربط بين HTTP path/method و Application logic |
| مكوّن Controller / route handler | دالة تتعامل مع Request واردة وتعيد Response |
| عملية Serialization | تحويل Application data إلى Format قابل للنقل مثل JSON |
| عملية Validation | فحص أن Data الواردة تستوفي القواعد والبنية المطلوبة |
| معيار OpenAPI | Specification قابلة للقراءة آليًا تصف API |
| واجهة Swagger UI | توثيق تفاعلي مولَّد من OpenAPI specification |
| مفهوم Concurrency | إحراز تقدم في Tasks متعددة خلال فترات زمنية متداخلة |
| مهمة Background task | عمل يُنفّذ بعد إمكان إعادة Response إلى Client |
| طبقة Middleware | Logic تعالج Requests/Responses حول Route handlers |
| إعداد CORS | Controls موجّهة للـ Browser خاصة بـ Cross-origin requests |
| نمط Dependency injection | تزويد Components بدوال/Resources قابلة لإعادة الاستخدام بعد إعلانها كـ Dependencies |
| حدث Lifespan event | Startup/shutdown logic لتهيئة Shared resources وتنظيفها |
| نمط REST | نمط API يُنظم عادة حول Resources و HTTP methods |
| بروتوكول WebSocket | اتصال Client-server مستمر وثنائي الاتجاه |
| تقنية SSE | event streaming من Server إلى Client عبر HTTP connection |
| بنية Flat structure | تنظيم مشروع بعدد صغير من Files قرب Root |
| بنية Nested structure | تنظيم حسب Technical categories مثل Routers و Models و Services |
| بنية Modular structure | تنظيم حسب Domain أو Feature مع إبقاء Code المرتبط قريبًا |
| معمارية Onion/layered architecture | Design يفصل المسؤوليات إلى Layers مع اتجاه Dependencies مضبوط |
| مكوّن Service | Component تنسّق Internal business operations |
| مكوّن Provider | Component تتواصل مع External systems |
| مكوّن Repository | Component مسؤولة عن Data access و Mutation |
| مكوّن Pipe | Component قابلة لإعادة الاستخدام لتحويل Data |
| مكوّن Mapper | Component تحول Data من Schema/Representation إلى أخرى |
| مكوّن Guard | Component تحمي Routes أو Operations، غالبًا عبر Authentication أو Authorization |
| قيد GIL | Global Interpreter Lock في Python، وله صلة بالأحمال متعددة Threads وكثيفة CPU |
| أسلوب Micro-batching | جمع Inference requests في Batches لتحسين كفاءة تنفيذ Model |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما الأدوار التي يؤديها كل من FastAPI و Starlette و Uvicorn و Pydantic؟
2. لماذا ينبغي لمشروع Python استخدام بيئة معزولة؟
3. ماذا يفعل `@app.get("/path")`؟
4. لماذا يجب تنفيذ Serialization لكائنات Python قبل نقلها عبر HTTP؟
5. ما الفرق بين Runtime validation و Static type checking؟
6. متى تكون Asynchronous request handling أكثر فائدة؟
7. لماذا يمكن لـ CPU/GPU-heavy inference أن تسبب مشكلات حتى داخل Async route؟
8. ما أنواع Tasks المناسبة لـ Background processing؟
9. ما هي Middleware؟
10. ما المشكلة التي تحلها Dependency injection؟
11. لماذا قد تستخدم Dependency كلمة `yield` مع Database session؟
12. ما هو Hierarchical dependency graph؟
13. متى يكون Lifespan event مفيدًا في خدمة GenAI؟
14. ما الفروق بين Flat و Nested و Modular project structures؟
15. ما المقصود بـ Shotgun updates؟
16. ما فكرة Dependency inversion وراء Onion architecture؟
17. ما مسؤوليات Controllers و Services و Providers و Repositories؟
18. كيف تختلف Django و Flask و FastAPI في مقارنة الفصل؟
19. لماذا لا يكون FastAPI كافيًا دائمًا بوصفه Heavy model-serving platform؟
20. لماذا قد يُستخدم FastAPI و Specialized model server معًا؟
21. ما Development tools التي تساعد على إبقاء Python backend قابلًا للصيانة؟
