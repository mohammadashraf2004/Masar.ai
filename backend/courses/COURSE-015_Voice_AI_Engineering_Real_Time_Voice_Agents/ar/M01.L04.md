## 1. لماذا توجد Agent frameworks



يمكن أن يكون Prototype بسيط لـ Agent قصيرًا بصورة مفاجئة.



في البداية، قد يبدو Flow هكذا:



```text
1. استقبل User input
2. استدعِ LLM
3. إذا طلبت Tool، نفّذ Tool
4. أعد Result إلى Model
5. أرجع Final answer
```



قد يكون ذلك كافيًا لـ Interaction بسيطة واحدة.



لكن Production systems تطرح أسئلة أصعب بكثير:



```text
ماذا لو احتاجت Agent عدة Tools؟
ماذا لو كانت Tool تعتمد على أخرى؟
ماذا لو فشلت Tool؟
ماذا لو احتاجت Agent إلى التوقف لانتظار شخص؟
ماذا لو احتاجت State عبر Steps كثيرة؟
ماذا لو تعاونت عدة Agents؟
ماذا لو أمكن تنفيذ Taskين بالتوازي؟
ماذا لو وجب استئناف Process غدًا؟
```



عند هذه النقطة، لم تعد المشكلة مجرد:



> "كيف أستدعي LLM؟"



بل تصبح:



> "كيف أدير بصورة موثوقة System ذات State و Reasoning متعدد الخطوات؟"



هذه هي المشكلة التي تحاول Agent framework حلها.



### Framework أكثر من مجرد LLM loop



يحدد المصدر عدة Capabilities على مستوى Framework:



| Capability | ما الذي تتعامل معه | لماذا تهم |
|---|---|---|
| Orchestration | Control flow و State و Execution | تمنع Manual loops المتشابكة |
| Memory | Short- و Long-term context | تمكّن Coherence و Recall |
| Tool Use | External capabilities | تسمح لـ Agent بالتصرف خارج Model |
| أنظمة متعددة الـ Agents | Coordination بين Specialists | تدعم Modular decomposition |
| مراجعة بشرية Human-in-the-Loop | التوقف من أجل مدخل/موافقة بشرية | تحسن Safety و Reliability |
| Streaming & Observability | Live feedback و Tracing و Monitoring | تساعد Users و Developers على فهم Execution |



إذًا توفر Framework بنية تشغيلية حول Model.

## 3. دورة التنفيذ Perceive–Reason–Act



السلوك الذي يعرّف Agent هو Cyclical.



Abstraction مفيدة هي:



```text
الإدراك (Perceive)
   ↓
الاستدلال (Reason)
   ↓
الفعل (Act)
   ↓
ملاحظة Result
   ↓
الاستدلال مرة أخرى
```



تحافظ Runtime على استمرار هذه Cycle حتى تصل Task إلى Stopping condition.



### مثال Graph صريح



يستخدم المصدر LangGraph لتوضيح Loop.



مفاهيميًا:



⟦CODE_2⟧



ثم:



```text
chatbot
   ↓
قرار شرطي (conditional decision)
   ├──> tools
   │      ↓
   └──── chatbot
```



هذا مفيد لأن Loop لم تعد مخفية داخل `while` مرتجلة.



بل أصبحت جزءًا من Workflow definition.



### لماذا يهم Explicit control flow



يمكن لـ Runtime أن تجعل هذه Transitions:



- Visible،

- Testable،

- Resumable،

- Traceable،

- وأسهل في التعديل.



يكون ذلك ذا قيمة خاصة عندما تحتوي Workflows على:



- Cycles،

- Branches،

- Retries،

- Approvals،

- عدة Agents (Multiple agents).

## 4. إدارة State: بيانات العمل الخاصة بـ Agent



Agent بلا State ليست أكثر بكثير من Function:



```text
المُدخل -> المُخرج
```



أما Agent حقيقية فقد تحتاج إلى تذكر Information أُنتجت أثناء Execution.



أمثلة:



```text
الرسائل
نتائج الأدوات
اسم المستخدم
الخطة المختارة
خطوة سير العمل الحالية
نتائج البحث
حالة الموافقة
```



لذلك تحتاج Framework إلى Structured state model.



### State أكثر من Dictionary



يمكن لـ Framework تعريف Rules لكيفية دمج Updates.



يستخدم المصدر مثال LangGraph مع Reducer:



⟦CODE_3⟧



المهم ليس Syntax.



المفهوم المهم هو:



> ينبغي دمج Update الخاصة بـ `messages` وفق Rule معروفة بدلًا من استبدال Old value عشوائيًا.



يقلل ذلك Corruption غير المقصودة للـ State.



### النموذج الذهني لـ Reducer



بدون Reducer:



```text
Messages قديمة
    ↓
Messages جديدة تستبدل كل شيء
```



مع Reducer:



```text
Messages قديمة
    +
Messages جديدة
    ↓
History مدمجة
```



تصبح Structured update rules أكثر أهمية مع نمو Workflows.

## 5. إدارة Lifecycle: Pause و Resume و Stop



بعض Tasks لا تنتهي في Run واحدة متصلة.



أمثلة:



```text
انتظار Human approval
انتظار External system
Research طويل المدى
Multi-stage business process
Workflow متوقفة حتى اليوم التالي
```



لدعم ذلك، تحتاج Runtime إلى **Checkpointing**.



### ما هي Checkpoint؟



Checkpoint هي Snapshot محفوظة من Execution state.



قد تتضمن:



- Data،

- Messages،

- Tool results،

- Workflow position،

- Pending actions،

- معرّفات Sessions (Session identifiers).



الفكرة الأساسية هي:



```text
احفظ State
   ↓
أوقف Execution
   ↓
أعد التحميل لاحقًا
   ↓
تابع من Workflow point نفسها
```



### Human-in-the-loop يعتمد على ذلك



لنفترض أن Agent وصلت إلى:



```text
"هل أرسل العقد إلى العميل؟"
```



قد يحتاج النظام إلى:



1. حفظ Workflow،

2. سؤال Human،

3. الانتظار،

4. تلقي Approval،

5. الاستئناف من المكان نفسه.



يصعب ذلك دون Persistent runtime.



يوضح المصدر هذه الفكرة باستخدام Session services في ADK، حيث يرتبط Session identifier بـ Persistent runtime state.



أسماء Classes الدقيقة Framework-specific.



أما المفهوم الدائم فهو Checkpointed lifecycle management.

## 6. لماذا تكون Agent runtimes Asynchronous



تقضي Agents قدرًا كبيرًا من الوقت في الانتظار.



قد تنتظر:



- LLM response،

- HTTP API،

- Database،

- Vector search،

- Agent أخرى،

- موافقة Human (Human approval).



هذه في الغالب I/O-bound operations.



إذا توقفت Application بالكامل أثناء كل انتظار، تُهدر Resources وتصبح Experience بطيئة.



### النموذج الذهني لـ Async



Synchronous:



```text
Task A تنتظر
كل شيء ينتظر
```



Asynchronous:



```text
Task A تنتظر API
        في الوقت نفسه
يمكن لـ Task B التقدم
```



يربط المصدر Async execution بعدة Capabilities.



### البث (Streaming)



يمكن للنظام Emit أحداث أو Partial output أثناء استمرار Work أخرى.



### التزامن (Concurrency)



يمكن لـ Independent tools أو Agents العمل في الوقت نفسه.



### الاستجابة (Responsiveness)



لا ينبغي لـ Waiting agent واحدة أن تجمّد Server process كاملة.



لهذا تعرض Agent runtimes كثيرة Methods تنفيذ `async`.

## 7. Control flow و Routing



بعد انتهاء Step، إلى أين ينبغي أن تنتقل Execution؟



توجد استراتيجيتان عامتان.



### 7.1 التوجيه الحتمي (Deterministic routing)



يعرّف Developer المسار.



مثال:



```text
المدير
   ↓
الباحث
   ↓
الكاتب
```



المزايا:



- Predictable،

- Testable،

- أسهل في Audit.



يستخدم المصدر Hierarchical و Sequential framework processes كأمثلة على Deterministic control.



### 7.2 التوجيه الديناميكي (Dynamic routing)



تساعد Model في تحديد الوجهة التالية.



مثال:



```text
طلب المستخدم
     ↓
المنسِّق
     ├── وكيل الفوترة
     └── وكيل الدعم
```



يفسر Coordinator الـ Request ويختار Specialist.



هذا أكثر Flexible، لكنه يضيف Uncertainty.



### قاعدة مفيدة



استخدم Deterministic routing عندما:



```text
تكون Workflow معروفة مسبقًا
```



واستخدم Dynamic routing عندما:



```text
تعتمد Step الصحيحة التالية على Semantic interpretation
```



تجمع أنظمة كثيرة بين الاثنين.

## 8. Concurrency و Parallelism



بعض Subtasks لا تعتمد على بعضها.



على سبيل المثال:



```text
اجلب Weather
اجلب News
```



يمكن تشغيلهما في الوقت نفسه.



Sequential execution:



```text
Weather -> انتظار -> News -> انتظار
```



Parallel execution:



```text
        ┌-> الطقس ->┐
البدء --|             |-> الدمج
        └-> الأخبار ---->┘
```



يمكن لـ Framework تجريد تعقيد:



- Scheduling،

- Async calls،

- Waiting for all results،

- دمج Outputs (Merging outputs).



يوضح المصدر ذلك باستخدام `ParallelAgent` في ADK.



الـ Class الدقيقة Framework-specific.



أما المفهوم الدائم فهو:



> لا ينبغي Serialization للـ Independent work دون ضرورة.

## 9. Memory نظام مهيكل، وليست Feature واحدة



يقسم المصدر Memory إلى فئتين:



```text
ذاكرة قصيرة المدى (Short-term memory)
ذاكرة طويلة المدى (Long-term memory)
```



وهما تحلان مشكلات مختلفة.



### الذاكرة قصيرة المدى (Short-term memory)



النطاق:



```text
Session أو Task الحالية
```



أمثلة:



- Chat history،

- Recent tool results،

- Intermediate calculations،

- حالة Workflow الحالية (Current workflow state).



### الذاكرة طويلة المدى (Long-term memory)



النطاق:



```text
عبر Sessions وعبر الزمن
```



أمثلة:



- User preferences،

- Persistent facts،

- Previous interactions،

- Knowledge دائمة (Durable knowledge).



الدرس المهم هو:



> "Memory" لا تعني ببساطة حفظ كل شيء.



يجب أن تقرر Framework قوية:



- ما الذي يُخزن،

- أين،

- لمدة كم،

- وكيف تُسترجع Relevant information.

## 10. Short-term memory: مساحة العمل Conversation



Short-term memory هي Working context الخاصة بـ Agent.



لنفترض أن User يقول:



```text
المستخدم: وحدة الـ temperature المفضلة لدي هي Celsius.
المستخدم: كيف الطقس في طوكيو؟
```



داخل Session نفسها، ينبغي أن تستطيع Agent استخدام Preference هذه.



قد تحتوي Short-term state على:



⟦CODE_4⟧



تدير Runtime الـ Updates بحيث تتلقى Reasoning step التالية Information التي تحتاجها.



### تحدي Context window



قد تستمر Naive implementation في إضافة كل شيء إلى Context إلى الأبد.



في النهاية:



- تكبر Context،

- تزيد Cost،

- تتراكم History غير ذات صلة،

- وقد يتم الوصول إلى Model limits.



لذلك تحتاج Production memory systems غالبًا إلى Policies لـ:



- Summarization،

- Trimming،

- Selective retention،

- Retrieval.



يؤكد المصدر على Framework-managed structured session state بدلًا من Manual list handling.

## 11. Long-term memory: Knowledge مستمرة



تحل Long-term memory مشكلة مختلفة.



مثال:



```text
الأسبوع 1:
"My shipping address is ..."

الأسبوع 2:
"Ship my order to my address."
```



تحتاج Conversation الثانية إلى Information من Session سابقة.



### التخزين ليس الجزء الأصعب



حفظ Data في Database أمر مباشر.



السؤال الأصعب هو:



> أي Memory ذات صلة الآن؟



لا يمكنك عادةً وضع History كاملة لحياة User داخل Prompt واحدة.



إذًا تصبح Long-term memory مشكلة Information retrieval.



### مسار Memory بأسلوب RAG (RAG-style memory pipeline)



يصف المصدر Flow شائعة:



```text
1. الاستيعاب (Ingest)
2. التضمين (Embed)
3. التخزين (Store)
4. البحث (Search)
```



#### الإدخال (Ingest)



حدد Information المفيدة التي تستحق الاحتفاظ بها.



#### التمثيل (Embed)



حوّلها إلى Semantic vector representation.



#### التخزين (Store)



خزّن Embedding و Original content بصورة مستمرة.



#### البحث (Search)



حوّل New query إلى Embedding واسترجع Similar memories.



مفاهيميًا:



```text
Memory سابقة:
"User prefers AI ethics articles"
        ↓ Embed
     [Vector]
        ↓ Store

Query جديدة:
"Recommend a topic for me"
        ↓ Embed
     [Vector]
        ↓ Similarity search
استرجاع Preference ذات صلة
```

## 12. كيف تعمل Short-term و Long-term memory معًا



تجمع Agent الأكثر فائدة بين نوعي Memory.



Flow نموذجية:



```text
User query جديدة
      ↓
Short-term session state
      ↓
تلاحظ Agent نقص Information
      ↓
البحث في Long-term memory
      ↓
استرجاع Fact ذات صلة
      ↓
إضافة Fact إلى Current working context
      ↓
توليد Response
```



مثال:



```text
المستخدم: اقترح عليّ شيئًا أستمتع بقراءته.
```



قد لا تحتوي Short-term memory على Preference.



فتبحث Agent في Long-term memory وتسترجع:



```text
الموضوع المفضل = أخلاقيات AI
```



ثم تصبح هذه Fact جزءًا من Current context.



المبدأ المهم هو:



> تكون Long-term memory مفيدة عادةً فقط بعد جلب الأجزاء ذات الصلة منها إلى Short-term working context.

## 13. Tooling interface: ربط Reasoning بالفعل



Agent لا تستطيع سوى توليد Text تكون محدودة.



تسمح Tooling interface للـ Agent بالتفاعل مع External systems.



أمثلة:



- Web search،

- Databases،

- Email،

- Calendars،

- Code execution،

- التحكم في Devices (Device control).



يحدد المصدر ثلاث مسؤوليات أساسية:



```text
1. تعريف Tool (Tool definition)
2. اختيار Tool (Tool selection)
3. التنفيذ الآمن (Secure execution)
```

## 16. التنفيذ الآمن للـ Tools



لا ينبغي لـ Tooling interface تنفيذ أي شيء تختلقه Model ببساطة.



يسلط المصدر الضوء على عدة مسؤوليات Safety.



### Tools المسجلة فقط (Registered tools only)



إذا لم تكن Function مسجلة، فلا ينبغي أن تكون قابلة للاستدعاء عبر Framework.



### التحقق من Arguments (Argument validation)



إذا كانت Schema تتوقع:



```text
city: string    # اسم المدينة
```



فينبغي اكتشاف Argument غير صالحة قبل Execution.



### العزل (Sandboxing)



قد تحتاج High-risk tools إلى Isolation.



على سبيل المثال، لا ينبغي لـ Code execution أن تمتلك Unrestricted access إلى Host system.



يقدم المصدر Example مفاهيمي خطير يتضمن Arbitrary `exec()` و System commands لتوضيح سبب أهمية Secure execution.



الدرس هو:



> Tool interfaces هي Security boundaries.



### ملاحظة مهمة حول الأمثلة



يعرض المصدر أيضًا Calculator example بسيطة تستخدم `eval()` لتوضيح Framework registration.



هذا المثال مفيد لفهم Tool wrapping، لكن الفصل نفسه يؤكد صراحة Sandboxing و Secure execution للـ Risky capabilities.



إذًا الخلاصة التعليمية ليست "استخدم unrestricted eval."



بل:



> ينبغي أن تجعل Frameworks تسجيل Tools سهلًا، بينما يظل Execution مضبوطًا ومتحققًا منه.

## 17. كيف تمثل Frameworks الـ Tools



يقارن المصدر Patternين عامين.



### Function بوصفها Tool



يمكن لـ Frameworks مثل CrewAI و ADK عرض Python functions العادية كـ Tools.



مفاهيميًا:



⟦CODE_7⟧



تتعامل Framework مع:



- Introspection،

- Schema generation،

- التوجيه للتنفيذ (Dispatch).



### عقدة Tool (Tool node)



تمثل LangGraph تنفيذ Tool كـ Graph node.



مفاهيميًا:



```text
Reasoning node
     ↓ Tool call؟
ToolNode
     ↓
Reasoning node
```



يناسب ذلك Philosophy الخاصة بـ LangGraph التي تضع Control flow أولًا.



لا يغيّر أي من التمثيلين Principle الأساسية:



```text

تعود Result إلى State
```

## 18. التواصل بين Agents (Multi-agent communication)



يمكن تفكيك Complex problem إلى Specialists.



مثال:



```text
نظام تقرير السوق (Market Report System)
├── Research Agent
├── Data Analysis Agent
└── Writing Agent
```



لكن Specialists لا تكون مفيدة إلا إذا استطاعت:



- تفويض Work،

- مشاركة Context،

- إعادة Results،

- تنسيق Control flow.



وهذا ما توفره Multi-agent communication layer.



### معضلة Developer



بدون Framework support، ستضطر إلى بناء ما يلي يدويًا:



- Routing،

- State passing،

- Cycle handling،

- Dependencies،

- استدعاء Specialist (Specialist invocation).



ويصبح ذلك Orchestration problem أخرى.

## 19. التفويض: تمرير Control



يصف المصدر نمطين عامين للـ Delegation.



### التوجيه الصريح (Explicit routing)



تكون Sequence محددة مسبقًا.



مثال:



```text
الباحث
   ↓
الكاتب
```



هذا مناسب عندما تكون Workflow معروفة.



ويستخدم المصدر CrewAI sequential process كمثال.



### الإشراف الديناميكي (Dynamic supervision)



يقرر Coordinator أي Specialist يستدعيه.



مثال:



```text
HelpDeskCoordinator
     ├── الفوترة
     └── الدعم
```



يمكن لـ Coordinator التعامل مع Agents كـ Callable capabilities.



يوضح المصدر ذلك باستخدام `AgentTool` في ADK.



مفاهيميًا:



```text
Parent agent
    ↓ تستدعي Specialist
Specialist agent
    ↓ تعيد Result
تواصل Parent العمل
```



يشبه ذلك Tool use العادي، باستثناء أن "Tool" هنا Agent أخرى.

## 20. مشاركة المعلومات بين Agents



يصبح Delegation بلا فائدة إذا لم تمتلك Agent التالية Context اللازمة.



لذلك تحتاج Frameworks إلى طريقة لمشاركة Outputs.



### State مشتركة (Shared state)



يستخدم المصدر مثال LangGraph:



⟦CODE_8⟧

يصف المصدر أيضًا Mechanism باسم `context` في Tasks داخل CrewAI.

Communication ليست فقط:


## 21. Instructions و Prompting: ميثاق Agent



ما تزال Runtime قوية تحتوي Tools و Memory تحتاج إلى Direction.



تعرف Prompting system:



- Identity،

- Goal،

- Rules،

- Boundaries،

- Task framing،

- Dynamic context،

- Tools المتاحة (Available tools).



يسمي المصدر ذلك **Charter** أو **Constitution** الخاصة بـ Agent.



### مشكلة Prompt عملاقة واحدة



يمكن أن تصبح Monolithic prompt:



- Brittle،

- صعبة التحديث،

- صعبة Debugging،

- غير متسقة،

- Tight coupling بين أجزائها.



تخيل String ضخمة واحدة تحتوي:



```text

بيانات المستخدم
الأدوات
تاريخ المحادثة
المهمة
memory
تعليمات التنسيق
```



قد يؤدي تغيير صغير إلى التأثير على Behavior غير مرتبطة.



لذلك تستفيد Framework من Modular prompt construction.

## 22. تعليمات Modular و Composable



تفصل Structured prompting system بين Concerns.

```text
قاعدة السلامة:
    "لا تقدّم نصائح مالية."

الحالة الديناميكية:
    user_name = ...

استعلام المستخدم الحالي:
    ...

الأدوات المتاحة:
    ...
```



تجمع Runtime هذه Pieces في Final model context.



### لماذا يساعد ذلك



يمكنك تغيير:



- Persona،

- Tools،

- User state،

- Task الحالية (Current task)



من دون إعادة كتابة Prompt واحدة عملاقة.



يحسن ذلك Maintainability.

## 23. حقن Context ديناميكيًا (Dynamic context injection)



تحتاج Agent غالبًا إلى Values من Current state.



مثال:



```text
topic = "الصداقة"
```



Instruction template:



```text
اكتب قصة قصيرة عن قطة، مع التركيز على {topic}.
```



تحل Runtime الـ Placeholder قبل استدعاء Model.



يستخدم المصدر Style باسم `{key}` في ADK لتوضيح Concept.



Syntax الدقيقة Framework-specific.



الفكرة الدائمة هي:



> ينبغي أن تكون Prompt construction قادرة على جلب Current state إلى Model context بصورة آمنة.



### لماذا لا نستخدم Ad-hoc f-strings في كل مكان؟



للبرامج الصغيرة جدًا، قد تكون Simple formatting كافية.



لكن Large systems تستفيد من Standardized prompt composition لأنها تقلل:



- Inconsistent injection،

- Duplicated logic،

- سهو غير مقصود (Accidental omissions).

## 26. ثلاث Philosophies للـ Frameworks في المصدر



يقارن الفصل بين:



- CrewAI،

- Google ADK،

- إطار LangGraph.



المقارنة لا تتعلق فقط بالـ Features.



بل تتعلق بـ **Development philosophy**.



### إطار CrewAI — Orchestration عالية المستوى و Declarative للـ Multi-agent



يصف المصدر CrewAI هكذا:



```text
عرّف WHO
عرّف WHAT
تتعامل Framework مع جزء كبير من HOW
```



أنت تعرّف:



- Agents،

- Roles،

- Tasks،

- Process التعاون (Collaboration process).



يفضل هذا Approach الـ Abstraction و Rapid setup.



### إطار Google ADK — Agent SDK مبنية على Components



يصف المصدر ADK على أنها أقرب إلى Traditional software engineering.



أنت تضبط:



- Agent objects،

- Tools،

- Services،

- Sessions،

- Memory،

- مكوّنات Runtime (Runtime components).



يمكن لـ Model توجيه جزء كبير من Loop، بينما توفر SDK الـ Infrastructure.



### إطار LangGraph — Orchestration تضع Explicit control flow أولًا



تجعل LangGraph الـ Control flow مرئيًا على شكل:



- Nodes،

- Edges،

- State،

- الشروط (Conditions).



يفضل هذا Approach الـ Fine-grained workflow control.

## 27. مقارنة Runtime



### إطار CrewAI



تكون Runtime عالية الـ Abstraction.



تعرّف Agents/Tasks و Process مثل:



```text
تسلسلي (sequential)
هرمي (hierarchical)
```



وتدير Framework جزءًا كبيرًا من Execution.



### إطار Google ADK



تكون Runtime Model-directed و Component-oriented.



تُضبط Agent باستخدام:



- Instructions،

- Tools،

- الخدمات (Services).



وتدير `Runner` دورة Execution.



### إطار LangGraph



يحدد Developer صراحة:



- Nodes،

- Transitions،

- Conditional edges،

- الحلقات (Loops).



وهذا يكشف Control flow مباشرة داخل Code.



### الأثر العملي (Practical implication)



اسأل:



> هل أريد من Framework إخفاء Workflow، أم أريد Workflow مرئية؟



يؤثر هذا السؤال بقوة في مدى ملاءمة Framework.

## 28. مقارنة Memory



### إطار CrewAI



يصف المصدر Experience عالية المستوى للـ Memory.



يتم دمج Short-term context داخل Task flow.



ويمكن تمكين Long-term memory عبر Framework-managed persistence و Retrieval.



### إطار Google ADK



يصف المصدر Memory بوصفها Pluggable infrastructure:



```text
SessionService -> قصير الأمد/الجلسة
MemoryService -> طويل الأمد
```



وقد يتم الوصول إلى Long-term memory صراحةً عبر Memory tool.



### إطار LangGraph



يصف المصدر Memory بوصفها جزءًا من Explicit stateful graph design:



```text
State    # الحالة
Checkpointer    # نقاط الحفظ
Store    # المخزن
```



يمنح ذلك Developer تحكمًا مباشرًا في State و Persistence.

## 29. مقارنة Tooling



### إطار CrewAI



يمكن تسجيل Tools بصورة Declarative، غالبًا عبر Decorators.



### إطار Google ADK



يمكن إرفاق Native Python functions بقائمة Tools الخاصة بـ Agent.



### إطار LangGraph



تُنفذ Tools غالبًا داخل `ToolNode` مخصصة.



تعكس الاختلافات Philosophies الأوسع نفسها:



```text
CrewAI -> تصريحي
ADK -> موجَّه بالمكوّنات
LangGraph -> سير عمل صريح
```

### إطار CrewAI

وتحرك Tasks و Process definitions الـ Communication.



### إطار Google ADK



يؤكد المصدر على Hierarchical delegation.



يمكن تمثيل Sub-agents كـ Callable capabilities.



### إطار LangGraph



يمكن بناء أي Topology باستخدام Nodes و Edges.



أمثلة:



- Supervisor،

- Pipeline،

## 32. اختيار Framework style



يوصي المصدر بالاختيار وفق احتياجات Project ومستوى Abstraction المطلوب.



Decision model مبسط:



### فضّل High-level declarative style عندما:



- تكون Collaboration structure معروفة،

- تريد Fast setup،

- تفضل Roles/Tasks على Explicit state machines.



### فضّل Component-based SDK style عندما:



- تريد Reusable services و Objects،

- تفضل ضبط Pre-built agent loop،

- تريد Traditional software-engineering feel.



### فضّل Explicit graph orchestration عندما:



- تكون Workflow logic معقدة،

- تكون Cycles مهمة،

- تكون Human approval points مهمة،

- يكون Custom routing مهمًا،

- تحتاج Fine-grained state transitions.



### لا تختَر اعتمادًا على Popularity فقط



اسأل بدلًا من ذلك:



```text
ما مقدار صراحة Control flow المطلوبة؟
ما مقدار Abstraction الذي أريده؟
ما مدى تعقيد State؟
هل أحتاج Custom loops؟
ما أهمية Human-in-the-loop؟
كم عدد Specialized agents المشاركة؟
```

## مفاهيم خاطئة مهمة



### المفهوم الخاطئ 1



> "Agent framework ليست سوى Convenience wrapper حول LLM call."



### لماذا هذا خطأ



يتعامل المصدر مع Frameworks بوصفها Infrastructure للـ State و Execution loops و Memory و Tools و Collaboration و Lifecycle management و Streaming و Observability.



---



### المفهوم الخاطئ 2



> "State هي Chat history فقط."



### لماذا هذا خطأ



قد تتضمن State رسائل و Tool results و Workflow outputs و User data و Control flags و Structured working data أخرى.



---



### المفهوم الخاطئ 3



> "Checkpointing يعني فقط حفظ Messages."



### لماذا هذا خطأ



يهدف Checkpointing إلى حفظ Execution state كافية لاستئناف Workflow، بما في ذلك مكان توقف Execution.



---



### المفهوم الخاطئ 4



> "Asynchronous execution مجرد Performance optimization."



### لماذا هذا خطأ



في Agent systems، تدعم Async execution الـ Streaming و Concurrency و Responsiveness و Non-blocking long-running operations.



---



### المفهوم الخاطئ 5



> "Long-term memory تعني إرسال كل Historical conversations إلى Model."



### لماذا هذا خطأ



Long-term memory هي في الأساس Retrieval problem. ينبغي اختيار Relevant memories وتحميلها إلى Current context عند الحاجة.



---



### المفهوم الخاطئ 6



> "إذا كانت Function موجودة في Python، تستطيع Model استدعاءها تلقائيًا."



### لماذا هذا خطأ



يجب تسجيل Function وتمثيلها عبر Schema/Tool interface تستطيع Model فهمها.



---



### المفهوم الخاطئ 7



> "Structured tool calling تزيل كل Security concerns."



### لماذا هذا خطأ



ما تزال Registered tools تحتاج Validation و Authorization و Safe execution و Sandboxing عند الحاجة.



---



### المفهوم الخاطئ 8



> "Multi-agent communication تتعلق فقط باستدعاء Agent أخرى."



### لماذا هذا خطأ



تحتاج Collaboration المفيدة أيضًا إلى تمرير Context الصحيحة ومشاركة Outputs عبر State أو Task dependencies.



---



### المفهوم الخاطئ 9



> "Prompting تعني كتابة System prompt كبيرة واحدة."



### لماذا هذا خطأ



يقدم الفصل Prompting كنظام مهيكل يركب Identity و Dynamic state و Tool schemas و Current task context و Rules.



---



### المفهوم الخاطئ 10



> "هناك Framework واحدة هي الأفضل دائمًا."



### لماذا هذا خطأ



يقدم المصدر اختيار Framework بوصفه Trade-off بين Abstraction و Control و Workflow complexity و Developer preference.

## التحقق الذاتي



قبل المتابعة، تأكد أنك تستطيع الإجابة عن:



1. لماذا تصبح Manual agent loop بسيطة صعبة الصيانة؟

2. ما المسؤوليات التي تنتمي إلى Runtime؟

3. ما دورة Perceive–Reason–Act؟

4. لماذا يكون Explicit workflow control مفيدًا للـ Loops و Branching؟

5. ما الغرض من Reducer في State management؟

6. ماذا يتيح Checkpointing؟

7. لماذا تكون Human-in-the-loop صعبة بدون Lifecycle persistence؟

8. لماذا تكون Agent runtimes غالبًا Async-native؟

9. ما الفرق بين Deterministic routing و Dynamic routing؟

10. متى يمكن لـ Parallel execution تحسين Latency؟

11. ما الذي ينتمي إلى Short-term memory؟

12. ما المشكلة التي تحلها Long-term memory؟

13. لماذا يكون Retrieval أصعب من مجرد تخزين Memories؟

14. ما المراحل الأربع لـ Long-term-memory RAG flow في المصدر؟

15. كيف تصبح Long-term memories مفيدة داخل Current session؟

16. ما المسؤوليات الثلاث الأساسية لـ Tooling interface؟

17. لماذا تكون Structured function calling أكثر موثوقية من Parsing للـ Model-generated strings؟

18. لماذا ينبغي ألا تكون سوى Registered tools قابلة للتنفيذ؟

19. متى يكون Sandboxing مهمًا؟

20. ما الفرق بين Delegation و Information sharing؟

21. كيف تساعد Shared state Agentين على Collaboration؟

22. لماذا يصعب الحفاظ على Monolithic prompt كبيرة؟

23. ماذا تفعل Dynamic context injection؟

24. كيف ترتبط Tool schemas بـ Prompt construction؟

25. كيف تختلف Abstraction philosophy الخاصة بـ CrewAI عن LangGraph؟

26. كيف يختلف Component model في ADK عن Explicit graph orchestration؟

27. أي Framework style تفضّل لـ Complex approval-heavy workflow، ولماذا؟

28. ما Pieces التي تجمعها Framework قبل كل LLM call؟

## احتفظ بهذه الفكرة



**Agent framework قوية هي نظام التشغيل المحيط بـ Model. تتحكم Runtime في Loop، وتوفر State الـ Working context، وتوفر Memory المعرفة السابقة ذات الصلة، وتربط Tools الـ Reasoning بـ External actions، وتمكّن Multi-agent communication التخصص، وتجمع Prompting system الـ Identity و Context و Capabilities داخل Working instructions الخاصة بـ Model. قيمة Framework ليست مجرد Convenience؛ بل إنها تحول Script هشة إلى Agent system مهيكلة وقابلة للاستئناف والمراقبة والتوسعة.**
