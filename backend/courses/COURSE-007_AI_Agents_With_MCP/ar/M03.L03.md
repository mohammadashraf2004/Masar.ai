## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- اختيار عمق اختبار مناسب استنادًا إلى مخاطر الخادم وسياق النشر.
- استخدام MCP Inspector كحلقة سريعة للتطوير اليدوي وDebugging.
- التمييز بين Unit testing وIntegration testing وEnd-to-end testing والاختبارات من نوع Evaluation.
- تصميم اختبارات آلية لوظائف الخادم وتفاعلات Client والاعتماديات الخارجية.
- تقييم Prompts وTools عبر عدة Models ومستويات تكلفة وسيناريوهات مهام.
- قياس دقة اختيار Tool والالتزام بـ Structured output.
- شرح لماذا تُكمل Evaluations اختبارات البرمجيات ولا تستبدلها.
- تحديد الفئات المهمة من ثغرات خوادم MCP وطرق التخفيف منها.
- تطبيق Sandboxing وLeast privilege وOAuth وRBAC وGateways وObservability وضوابط Supply chain.
- شرح مخاطر Token pass-through وConfused deputy على المستوى المفاهيمي.
- استخدام إطاري Lethal Trifecta وMCP Colors للتفكير في تركيبات Tools.
- تجهيز خوادم MCP المحلية للمستخدمين.
- إعداد الخوادم البعيدة لاستخدام Streamable HTTP وHorizontal scaling.
- تركيب خوادم MCP داخل تطبيقات ASGI.
- وضع خادم MCP داخل Container ونشره.
- شرح دور MCP Registry في الاكتشاف والتوزيع.

## 1. بناء الخادم ليس النهاية

في هذه المرحلة، قد يكون خادم MCP قد أصبح بالفعل يعرض Tools وPrompts وResources، ويدعم Utilities مفيدة، ويشارك في Workflows أكثر ثراءً على مستوى Client. ومع ذلك، فهذا لا يجعله جاهزًا للإنتاج بعد.

ينظم المصدر العمل المتبقي في أربع مسؤوليات رئيسية:

```text
بناء الخادم (Build server)
    ↓
اختبار الصحة (Test correctness)
    ↓
تقييم السلوك الموجّه إلى Model (Evaluate model-facing behavior)
    ↓
تأمين النظام (Secure the system)
    ↓
الحزم / النشر / الإتاحة
```

تحل هذه المسؤوليات مشكلات مختلفة:

| المجال | السؤال الرئيسي |
|---|---|
| Software testing | هل تتصرف الشيفرة بشكل صحيح؟ |
| Evaluations | هل تستخدم Models الخادم بفاعلية؟ |
| Security | هل يمكن لسلوك ضار أو غير آمن أن يسبب ضررًا أو كشفًا للبيانات؟ |
| Distribution | هل يستطيع المستخدمون الحقيقيون تثبيت الخادم والاتصال به وتشغيله بصورة موثوقة؟ |

يحتاج خادم Production إلى المنظورات الأربعة كلها.

## 2. ما مقدار الاختبار الذي يحتاجه خادم MCP؟

لا يوصي الفصل بهدف واحد ثابت لنسبة Test coverage. بل يعتمد عمق الاختبار على **المخاطر**.

تختلف تكلفة الفشل في تجربة خاصة تعرض Calculator tool اختلافًا كبيرًا عن خادم بعيد متعدد المستأجرين يتعامل مع بيانات سرية أو إجراءات مالية.

اطرح أسئلة مثل:

- من سيستخدم الخادم؟
- هل الخادم محلي أم مكشوف عن بُعد؟
- ما البيانات التي يستطيع الوصول إليها؟
- هل تستطيع Tools الخاصة به تعديل State؟
- هل يمكن للأخطاء أن تسبب ضررًا ماليًا أو متعلقًا بالخصوصية أو الامتثال أو التشغيل؟
- كم عدد الأنظمة الخارجية التي يعتمد عليها؟

### مستويات الاختبار

| المستوى | ما الذي يتحقق منه |
|---|---|
| Unit test | الدوال الفردية وBusiness logic |
| Integration test | التفاعلات مع Clients وقواعد البيانات والملفات وAPIs وAuthorization وغير ذلك |
| اختبار شامل (End-to-end test) | مسار الطلب الكامل عبر الخادم وClient أثناء التشغيل |
| Evaluation | ما إذا كانت Models تختار قدرات الخادم وتستخدمها بفاعلية |

ينبغي أن يكون الاختبار متناسبًا مع Risk profile للخادم، لا مدفوعًا بالرغبة في تعظيم نسبة Coverage لمجرد تعظيمها.

## 3. استخدام MCP Inspector كحلقة تطوير

يعمل MCP Inspector مثل Client تفاعلي لـ MCP صُمم للتطوير وDebugging. ويمكنه الاتصال بخادمك، واكتشاف قدراته، وتشغيل العمليات، وإظهار حركة Requests/Responses.

يوصي الفصل بـ Workflow تكراري:

```text
1. ابنِ هيكلًا أدنى للخادم يمكن الاتصال به (Build a minimal connectable server skeleton).
2. اتصل بـ MCP Inspector (Connect MCP Inspector).
3. تحقّق من اكتشاف Primitives (Verify primitive discovery).
4. نفّذ سلوكًا واحدًا (Implement one behavior).
5. حدّث Inspector (Refresh Inspector).
6. اختبر المسار الناجح (Test the happy path).
7. اختبر مسارات الحواف/الفشل.
8. افحص Notifications وسجل الرسائل (Inspect notifications and message history).
9. كرر مع السلوك التالي (Repeat for the next behavior).
10. اختبر النشر البعيد عندما تصبح جاهزًا (Test remote deployment when ready).
```

### لماذا يُعد Inspector ذا قيمة؟

قد تبدو دالة Python صحيحة عند اختبارها بمعزل، لكنها قد تعرض MCP schema أو Message أو Notification أو Capability metadata بصورة خاطئة. يختبر Inspector الواجهة التي يراها Client فعليًا.

### عروض متخصصة

يصف المصدر عروض Inspector لميزات مثل:

- عرض Tools،
- عرض Resources،
- عرض Prompts،
- عرض Sampling،
- عرض Elicitations،
- عرض Roots،
- عرض Authentication،
- عرض سجل الرسائل،
- عرض Server notifications.

في Sampling، يستطيع المطور فحص Request ومحاكاة الموافقة أو الرفض من دون الحاجة بالضرورة إلى استدعاء Model حقيقي. وبالنسبة إلى Elicitation، يستطيع Inspector عرض Schema في صورة Form واختبار مسارات القبول والرفض والإلغاء.

## 4. الاختبار الآلي: Unit tests وIntegration tests

يُعد اختبار Inspector اليدوي ممتازًا للحصول على Feedback سريع، لكنه لا يكفي للحماية من Regression.

### اختبارات Unit

اختبر كود MCP باستخدام أساليب البرمجيات المألوفة:

- استخدام `pytest`،
- استخدام Fixtures،
- استخدام Mocks/Fakes،
- كتابة Assertions للمسار الناجح،
- كتابة Assertions لمسار الفشل،
- قياس Coverage عندما يكون مفيدًا.

إذا كانت دالة Tool تحتوي على Business logic مثل التحقق من Input أو إجراء حسابات، فاختبر ذلك المنطق مباشرة.

### لماذا تُعد Mocking مهمة؟

تعتمد خوادم MCP كثيرًا على:

- قواعد البيانات،
- APIs خارجية،
- ملفات محلية،
- Identity providers،
- قدرات يوفرها Client.

ينبغي لاختبارات Unit أن تعزل كودك عن الاعتماديات غير المستقرة أو المكلفة عندما لا تكون الاعتمادية نفسها هي ما تختبره.

### اختبارات Integration

تتحقق اختبارات Integration من الحدود بين المكونات:

- سلوك الاتصال/قطع الاتصال،
- الوصول إلى قاعدة بيانات حقيقية أو مخصصة للاختبار،
- استدعاءات API،
- تحميل ملفات Resource،
- تدفقات Authorization،
- تفاعلات بسيطة بين MCP Client والخادم.

يمكن لـ Test client صغير إرسال Protocol requests إلى Test server يعمل والتحقق من النتائج، ما يجعل الاختبار أقرب إلى السلوك الذي تختبره التطبيقات الحقيقية.

### اختبار Integration باستخدام Client حقيقي

يستخدم المصدر أيضًا Claude Desktop مثالًا على الاختبار باستخدام Client حقيقي. والدرس الأوسع هو أن تختبر باستخدام Host environment واقعية واحدة على الأقل، لا باستخدام Test harness الخاص بك فقط.

## 5. لماذا تحتاج خوادم MCP إلى Evaluations؟

تجيب اختبارات البرمجيات التقليدية عن أسئلة Deterministic مثل:

> عند إعطاء هذه Inputs، هل أعادت الدالة النتيجة المتوقعة؟

لكن خوادم MCP تعرض واجهات موجّهة إلى Model. وقد تكون Tool مطبقة بصورة مثالية ومع ذلك يصعب على LLM اختيارها بصورة صحيحة بسبب اسم أو Description مربك.

تجيب Evaluations عن أسئلة مثل:

- هل تختار Model الـ Tool الصحيحة؟
- هل ينتج Prompt السلوك المقصود؟
- هل يتبع Output البنية المتوقعة؟
- هل يظل السلوك مقبولًا عبر Model families وأحجام مختلفة؟
- ما تكلفة التفاعل؟
- هل تستمر Guardrails في العمل؟

### تعمل Evaluations عادةً على تحسين الواجهة، لا Base model

بصفتك مطور خادم MCP، لا يمكنك عادةً إعادة تدريب Models الخاصة بالمستخدمين. وبدلًا من ذلك، تساعدك نتائج Evaluation على تحسين:

- أسماء Tools،
- أوصاف Tools،
- Argument schemas،
- Prompt templates،
- الأمثلة،
- Output formats،
- تصميم تفاعل الخادم.

## 6. تصميم Evaluations مفيدة لـ MCP

يحدد الفصل عدة أبعاد مفيدة لـ Evaluation:

- أداء اختيار Tool،
- تكلفة استخدام Tool،
- الالتزام بـ Guardrails،
- تكلفة Prompt،
- صحة Prompt،
- الالتزام بـ Structured output،
- استخدام LLM-as-a-judge للتقييم في المهام المناسبة،
- الأداء عبر Model families وأحجام مختلفة.

### Workflow لتقييم Prompt

يمكن أن تكون العملية العملية كما يلي:

```text
1. اختر Prompts/مهام تمثيلية.
2. شغّلها عدة مرات على Model واحد (Run them a few times on one model).
3. افحص حالات الفشل والتكاليف الواضحة (Inspect obvious failures and costs).
4. حسّن Prompt (Refine the prompt).
5. أضف فحوصات آلية (Add automated checks).
6. شغّل الاختبار عبر عدة Models ذات صلة (Run across several relevant models).
7. حلّل حالات الفشل (Analyze failures).
8. أضف Rubrics/Judges أقوى إذا كان ذلك مفيدًا.
9. كرر حتى يستقر السلوك (Repeat until behavior stabilizes).
```

هذا الفحص التكراري لأنماط الفشل هو أحد أشكال **Error analysis**.

### Assertions بسيطة مقابل Rubric grading

قد يتحقق Evaluation أساسي مما إذا كانت Response تحتوي على عبارة أو بنية مطلوبة. وهذا رخيص وDeterministic، لكنه قد ينتج False positives/negatives.

يستطيع LLM-as-a-judge التقييم استنادًا إلى Rubric، ما يلتقط جودة Semantic أكبر، لكنه أعلى تكلفة ويحتاج هو نفسه إلى Evaluation دقيق.

### أهمية Cross-model evaluation في MCP

يمكن لمطور تطبيق أن يختار Model واحدة ويضبط النظام لها تحديدًا. أما مؤلف خادم MCP قابل لإعادة الاستخدام فعادةً لا يستطيع ذلك. لذلك ينبغي تقييم تعريفات Tools وPrompts عبر Models يُحتمل أن يستخدمها مستخدموك.

## 7. تقييم سلوك اختيار Tool

يمكن أن تحتوي Dataset بسيطة لتقييم اختيار Tool على أزواج:

```text
(natural-language request, expected tool) — (طلب بلغة طبيعية، Tool متوقعة)
```

لكل مهمة، اسمح لـ Model برؤية تعريفات Tools المتاحة وسجل أي Tool تختارها.

مقياس بسيط هو:

```text
tool-choice accuracy = correct tool selections / total test tasks   — حساب دقة اختيار Tool
```

### ما الذي يمكن أن تكشفه نتيجة اختيار Tool؟

قد يشير الأداء المنخفض إلى:

- تداخل مسؤوليات Tools،
- أسماء غامضة،
- أوصاف مربكة،
- توثيق غير مكتمل لـ Parameters،
- عدد كبير جدًا من Tools النشطة،
- غموض المهمة.

### ما الذي لا يمكن أن تثبته؟

لا تثبت الدرجة المرتفعة لاختيار Tool أن النظام بالكامل موثوق. فقد لا تلتقط:

- سياق Multi-turn،
- تصحيحات المستخدم،
- System prompts الحقيقية الخاصة بـ Client،
- حالات الفشل داخل Tool نفسها،
- أعطال الاعتماديات الخارجية،
- Adversarial prompts.

لإجراء Evaluation أقوى من طرف إلى طرف، يقترح المصدر تشغيل المهام عبر MCP Client بسيط أو استخدام Frameworks لديها تكاملات MCP.

## 8. عقلية Security: افترض أن اللغة Attack surface

تجمع خوادم MCP بين مجالين صعبين في Security:

1. Security تقليدية للبرمجيات/الشبكات،
2. أنظمة LLM تستهلك محتوى Natural-language غير موثوق.

يجادل الفصل بأنه من غير الواقعي اكتشاف كل صياغة ضارة محتملة. والهدف الأفضل هو تصميم النظام بحيث **لا تستطيع التعليمات الخطرة النجاح بسهولة حتى إذا تأثرت Model**.

يقود هذا إلى استراتيجية متعددة الطبقات:

```text
التحقق على مستوى الكود (Code-level validation)
      +
أقل قدر من الصلاحيات (Least privilege)
      +
العزل/البيئة المقيدة
      +
Authorization قوي (Strong authorization)
      +
قابلية المراقبة (Observability)
      +
موافقة بشرية للإجراءات الحساسة (Human approval for sensitive actions)
```

## 9. ثغرات Injection والثغرات المتعلقة بالمسارات

يبدأ المصدر بفئات Injection المألوفة التي تظل ذات صلة في أنظمة MCP.

### حقن SQL (SQL injection)

إذا أدخلت Tool نصًا غير موثوق داخل Queries لقاعدة البيانات باستخدام Raw string interpolation، فقد يتمكن مهاجم من تغيير Query.

**الدفاع الأساسي:** Parameterized queries مع صلاحيات مقيدة لقاعدة البيانات.

### حقن الأوامر (Command injection)

إذا مُررت Strings يتحكم فيها المستخدم/Model إلى Shell بصورة غير آمنة، فقد يتم تنفيذ أوامر عشوائية.

**الدفاعات:** تجنب Shells عندما يكون ذلك ممكنًا، واستخدم أوامر/Arguments ضمن Allowlist، واعزل Process، وقلل صلاحيات OS.

### حقن Prompt (Prompt injection)

يختلف Prompt injection لأن التعليمات الضارة قد تصل داخل محتوى يُفترض أن تقرأه Model: مواقع ويب، ورسائل بريد إلكتروني، وملفات، وأوصاف Issues، ووثائق، ونتائج Tools أخرى.

لا يستطيع مطور الخادم حل Prompt injection بمجرد تصفية قائمة من العبارات السيئة. وبدلًا من ذلك، اسأل ما الضرر الذي قد يحدث إذا اتبعت Model تعليمات ضارة، ثم أزل تلك القدرة حيثما أمكن.

على سبيل المثال:

- اعزل الوصول إلى الملفات باستخدام Sandboxing،
- قلل Network reachability،
- قيّد Scopes الخاصة بـ Tools،
- اطلب Confirmation للإجراءات الحساسة،
- نظّف محتوى الويب وURLs التي يتم جلبها،
- افصل بين قدرات قراءة البيانات وقدرات الاتصال الخارجي.

### اجتياز المسارات (Path traversal)

ينبغي لأي Tool أو Resource تقبل Filesystem path أن تفترض أن المسار غير موثوق.

النمط القوي الوارد في المصدر هو:

```text
requested = Path(user_value).resolve() — حل المسار المطلوب إلى مسار مطلق
allowed = Path(base_dir).resolve() — حل الدليل المسموح إلى مسار مطلق
verify requested.is_relative_to(allowed) — تحقّق من بقاء المسار المطلوب داخل الدليل المسموح
```

يؤدي Resolve أولًا إلى التعامل مع Relative segments وSymlinks بأمان أكبر بكثير من String-prefix checks.

## 10. Access control وDenial of service وحدود Token

### ثغرات Access control

قد يكون خادم MCP البعيد Multitenant. ولا تكفي Authentication وحدها؛ يجب أن تضمن Authorization أن مستخدمًا لا يستطيع الوصول إلى Objects مستخدم آخر أو تنفيذ إجراءات Privileged.

قد يتطلب ذلك:

- Authorization على مستوى Object،
- صلاحيات لكل Tool،
- قيود Plan/Role،
- Credentials محددة الـ Scope.

### هجمات DoS/DDoS

قد تتعرض الخوادم البعيدة للإغراق بسبب حجم Requests. وتظل وسائل الدفاع القياسية ذات صلة:

- Rate limiting،
- Throttling،
- Quotas،
- أحجام Requests محدودة،
- ضوابط Traffic على مستوى Infrastructure.

### تمرير Token (Token pass-through)

يحذر المصدر من أخذ Authorization token يقدمه Client وتمريره بصورة عمياء إلى Third-party service غير ذي صلة.

لماذا هذا خطير؟

- ربما يكون Token قد صدر لجمهور Audience مختلف،
- تصبح حدود المسؤولية/Auditing غير واضحة،
- يمكن إساءة استخدام Tokens المسروقة أو زائدة الصلاحيات،
- قد يعمل الخادم من غير قصد بصلاحيات لا ينبغي أن يمتلكها.

تستخدم البنية الأنظف Credentials صادرة خصيصًا لعلاقة الخادم مع Downstream service. وإذا كان لا بد فعلًا من قبول Credentials يقدمها Client، فتحقق من Token ومن Scope الخاص به بدلًا من تمريره بصورة عمياء.

## 11. مشكلة Confused deputy

يُقصد بـ **Confused deputy** نظام أكثر صلاحية يتم خداعه كي يستخدم سلطته نيابةً عن Actor أقل صلاحية.

في Authorization flows المرتبطة بـ MCP، قد يظهر الخطر عندما يعمل الخادم Proxy للوصول إلى خدمة أخرى ويفشل في الحفاظ على الحدود بين Clients/Users مختلفين أثناء OAuth consent وRedirects.

تتمثل محاور التخفيف في المصدر في مبادئ OAuth الأمنية القياسية:

- الحفاظ على حدود Consent منفصلة لكل User/Client،
- عرض معلومات Consent واضحة،
- التحقق من Redirect URIs مقابل Allowed registry،
- استخدام OAuth `state` parameter والتحقق منه،
- حماية Consent pages من CSRF/Clickjacking،
- تجنب التصميمات التي تجعل Shared static identity تدمج مستخدمين مختلفين داخل Trust boundary واحدة.

الفكرة الأساسية أوسع من OAuth: **لا تسمح مطلقًا لـ Actor منخفض الصلاحية بأن يجعل خادمًا Privileged يعيد استخدام سلطته خارج Scope المشروع لذلك Actor.**

## 12. بنية Security من ثلاث طبقات

يجمع الفصل الدفاعات العملية في ثلاث طبقات.

### الطبقة 1 — أسس Infrastructure

الأداة الأساسية هي **Sandboxing**: اعزل الخادم عن Resources التي لا يحتاج إليها.

بالنسبة إلى الخوادم المحلية، قد يعني ذلك:

- استخدام Docker containers،
- استخدام Virtual machines،
- استخدام Filesystem mounts مقيدة،
- تقييد Network access،
- التشغيل باستخدام مستخدمين غير Privileged.

المبدأ بسيط: إذا لم تستطع Tool مخترقة الوصول إلى بيانات حساسة أو قدرات System خطرة، يصبح أثر الاختراق أصغر.

### الطبقة 2 — Access control

تطبق هذه الطبقة **مبدأ Least privilege**.

تشمل الآليات:

- OAuth 2.1،
- Access tokens محددة الـ Scope،
- Authorization على مستوى Object،
- Role-based access control (RBAC)،
- MCP gateways التي توحّد Authentication وAuthorization وRouting وPolicy.

### الطبقة 3 — Operational controls

تحتاج أيضًا إلى Visibility وقدرة على الاستجابة:

- Structured logging،
- Traces،
- Metrics،
- Alerts،
- فحص ثغرات Dependencies،
- مراقبة Supply chain،
- موافقة بشرية على الإجراءات الحساسة.

## 13. OAuth وRBAC وGateways للخوادم البعيدة

### خادم MCP بوصفه OAuth resource server

في النشر البعيد المحمي، يعمل خادم MCP عادةً بوصفه **Resource server**. ويقوم Authorization server منفصل بمصادقة المستخدمين وإصدار Tokens.

يتحقق الخادم من Access tokens الواردة قبل السماح بالوصول.

يستخدم نمط Python SDK الموصوف في المصدر:

- إعدادات Authorization،
- تنفيذ Token verifier،
- Scopes/Claims الخاصة بـ Token الذي تم التحقق منه.

### التحكم في الوصول القائم على الدور (RBAC)

يُسنِد RBAC الإجراءات المسموح بها بناءً على Role بدلًا من الهوية الفردية.

مثال:

| الدور | العمليات المسموح بها |
|---|---|
| Viewer | قراءة بيانات Project |
| Operator | القراءة + تشغيل Operational tools |
| Admin | إدارة Configuration والإجراءات الحساسة |

صمّم Roles دائمًا حول أقل صلاحيات مطلوبة لأداء العمل المشروع.

### بوابات MCP (MCP gateways)

تقع Gateway بين Clients وخادم MCP واحد أو أكثر بعد النشر. واعتمادًا على Implementation، يمكنها توحيد:

- Authentication،
- Authorization،
- Traffic management،
- Routing،
- Policy enforcement،
- Server administration.

ويكون هذا مفيدًا خصوصًا عند تشغيل عدة خوادم بدلًا من تضمين منطق Policy نفسه بشكل مستقل داخل كل Deployment.

## 14. Observability وSupply-chain security

تتطلب Security أن تعرف ما الذي يفعله نظامك.

### قابلية المراقبة (Observability)

ينبغي لأنظمة Production أن تراعي:

- Structured logs،
- Distributed tracing،
- Metrics،
- Alerting،
- Dashboards للـ Latency/Errors،
- مراقبة Authorization events.

يذكر المصدر أساليب Observability محايدة تجاه Vendor مثل OpenTelemetry، ومنصات Metrics مثل Prometheus، بوصفها أمثلة على النمط الأوسع.

### إدارة Supply chain

خادمك أكبر من Source code الذي كتبته بنفسك. إذ يمكن لـ Dependencies وBase images وDatabase software وBuild tooling أن تقدم ثغرات.

تتضمن العملية السليمة:

- تحديث Dependencies،
- Builds قابلة لإعادة الإنتاج ومثبتة الإصدارات،
- Vulnerability scans،
- Static analysis،
- فحوصات Security داخل CI/CD.

### مراقبة HITL

ينبغي غالبًا أن تحتفظ الإجراءات الحساسة بخطوة Human approval. وعادةً ما تمتلك Client UX الخاصة بـ MCP مربع حوار الموافقة، لكن ينبغي تصميم Workflows في الخادم بحيث تتعامل مع الرفض/الإلغاء بصورة سليمة.

## 15. إطار Security: Lethal Trifecta

يقدم المصدر طريقة مفيدة للتفكير في مخاطر Prompt injection. تصبح المخاطر خطيرة بصورة خاصة عندما يجمع Workflow واحد للـ Agent/Server القدرات الثلاث التالية:

1. **الوصول إلى بيانات خاصة**
2. **التعرض لمحتوى غير موثوق**
3. **القدرة على التواصل مع أطراف خارجية**

لماذا هذا التركيب خطير؟

```text
محتوى غير موثوق يتضمن تعليمات ضارة (Untrusted content contains malicious instructions)
          ↓
Agent يستطيع الوصول إلى بيانات سرية (Agent can access confidential data)
          ↓
Agent يستطيع إرسال البيانات خارج Trust boundary (Agent can send data outside the trust boundary)
          ↓
احتمال تسريب البيانات (Possible exfiltration)
```

يشجع الإطار على **إزالة ضلع واحد على الأقل من المثلث** في أي Workflow عالي المخاطر.

أمثلة على وسائل تخفيف بنيوية:

- تقييد Scope البيانات الخاصة،
- عزل معالجة المحتوى غير الموثوق،
- تعطيل الاتصال الصادر أو تقييده بشدة،
- فرض OAuth scopes لكل Resource،
- استخدام Gateway middleware لرفض Requests المشبوهة العابرة للحدود.

[[IMAGE_NEEDED: Lethal Trifecta triangle | A triangle labeled Private Data, Untrusted Content, and Third-Party Communication, with a warning in the center and examples of controls that remove one edge | Learner should notice that security can improve by structurally breaking the dangerous combination]]

## 16. إطار Security: MCP Colors

يقدم الفصل أيضًا تمرينًا لتصنيف Tools يسمى **MCP Colors**.

يستخدم الإطار:

- **Red** — Tools تتعامل مع محتوى غير موثوق.
- **Blue** — Tools تنفذ إجراءات حرجة.
- **Neither** — Tools لا تقع ضمن أي من الفئتين.

يوضح المصدر أن البيانات تُعامل على أنها خاصة افتراضيًا بدلًا من منحها لونًا ثالثًا.

### كيفية استخدام الإطار

لكل Tool منفردة:

1. صنفها Red أو Blue أو Neither.
2. اشرح السبب.
3. اسأل هل يمكنك إعادة تصميم Tool لإزالة الخاصية الخطرة.
4. تجنب خلط قدرات Red وBlue داخل Server/Agent workflow نفسه عندما يكون ذلك عمليًا.

تكمن القيمة في عملية التحليل: فهي تجبرك على التفكير بوضوح في Tools التي تقرأ بيانات Adversarial وتلك التي تستطيع اتخاذ إجراءات حساسة.

## 17. مشاركة خوادم MCP المحلية

يمكن غالبًا توزيع Server محلي ببساطة في صورة Source/package code مع تعليمات تثبيت واضحة لـ Clients المدعومة.

ينبغي أن توضح وثائق التوزيع الجيدة:

- المتطلبات المسبقة،
- أمر التثبيت،
- أمر تشغيل الخادم،
- Environment variables المطلوبة،
- Transport المتوقع،
- إعداد Client،
- توقعات Permissions/Security.

### حزم MCP (MCPB)

يصف المصدر MCP Bundle بأنه حزمة ZIP تحتوي على الخادم وملف `manifest.json`. ويستطيع Client متوافق تثبيت Bundle كArtifact واحدة قابلة للتوزيع.

تكون Bundle مفيدة عندما تريد تجربة تثبيت أبسط للمستخدم من Clone/Configuration يدويًا لـ Repository.

تحتاج الخوادم البعيدة إلى Streamable HTTP.

### السلوك عديم الحالة (Stateless behavior)

يؤدي فرض سلوك Stateless على Clients المتوافقة إلى تسهيل Horizontal scaling لأن Requests لا تعتمد على Session طويلة وثابتة على Server instance واحدة.

### Responses من نوع JSON فقط

## 20. وضع الخادم داخل Container

تخدم Containers غرضين مختلفين في الفصل:

- **الاستخدام المحلي:** عزل الخادم عن Host machine باستخدام Sandbox.
- **الاستخدام البعيد:** حزم التطبيق بصورة متسقة للنشر.

عادةً ما تقوم Minimal deployment image بما يلي:

1. تختار Python base image،
2. تنسخ Project،
3. تثبت Dependencies،
4. تعرض Web port للخوادم البعيدة،
5. تشغل Process الخاصة بـ ASGI/MCP.

### تظل Container security مهمة

لا تُعد Container تلقائيًا Sandbox مثالية. استمر في تطبيق Least privilege:

- تجنب Mounts غير الضرورية،
- تجنب Privileged mode،
- قيّد Network access عندما يكون ذلك ممكنًا،
- شغّل باستخدام Non-root user متى كان ذلك عمليًا،
- ثبّت إصدارات Dependencies/Base images،
- افحص Image.

## 21. النشر عبر MCP Registry

يصف المصدر MCP Registry على أنه نظام مركزي لاكتشاف الخوادم، يشبه من الناحية المفاهيمية Package index لتكاملات MCP.

بالنسبة إلى خادم Python، يكون Publishing flow في الفصل على المستوى المفاهيمي:

```text
حزم الخادم (Package server)
    ↓
نشر حزمة Python إلى PyPI (Publish Python package to PyPI)
    ↓
إنشاء server.json باستخدام Publisher tooling (Generate server.json with publisher tooling)
    ↓
تحديث Package metadata وتعريفات Environment variables (Update package metadata and environment-variable declarations)
    ↓
التحقق من ملكية Package/Server
    ↓
مصادقة Publisher (Authenticate publisher)
    ↓
نشر Registry entry (Publish registry entry)
    ↓
التحقق من نتيجة Discovery/Search
```

قد تتطور أدوات Registry الدقيقة، لكن الدرس الدائم هو أن Public discovery تتطلب:

- هوية واضحة،
- Package لها Version،
- Connection metadata،
- Ownership verification،
- Releases قابلة للتكرار.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: «إذا نجحت Unit tests، فإن خادم MCP جاهز للإنتاج.»

**لماذا هذا خطأ:** لا تقيس Unit tests اختيار Model للـ Tool أو جودة Prompt أو Network integration أو Security posture أو سلوك Deployment.

### المفهوم الخاطئ 2: «Evaluations تستبدل اختبارات البرمجيات.»

**لماذا هذا خطأ:** تقيس Evaluations سلوكًا Probabilistic موجّهًا إلى Model، بينما تتحقق Tests من صحة البرمجيات Deterministic.

### المفهوم الخاطئ 3: «يمكن حل Prompt injection بتصفية قائمة من العبارات السيئة.»

**لماذا هذا خطأ:** يمكن أن تأتي التعليمات غير الموثوقة بأشكال لا حصر لها. لذلك تُعد Structural isolation وLeast privilege أساسيين.

### المفهوم الخاطئ 4: «Authentication وحدها تكفي لـ Multitenant security.»

**لماذا هذا خطأ:** ما زال المستخدمون الذين تمت مصادقتهم بحاجة إلى حدود Authorization على مستوى Object وRole وAction.

### المفهوم الخاطئ 5: «يمكن تمرير Client token بأمان إلى أي Downstream API.»

**لماذا هذا خطأ:** تصدر Tokens لجماهير Audiences وScopes محددة، ولا ينبغي تمريرها بصورة عمياء.

### المفهوم الخاطئ 6: «تحل Docker container مشكلة Security في MCP بالكامل.»

**لماذا هذا خطأ:** تقلل Containers من Blast radius لكنها ما زالت تحتاج إلى Mounts وPrivileges وNetworks وCredentials مقيدة، وإدارة سليمة لـ Dependencies.

### المفهوم الخاطئ 7: «يعني Lethal Trifecta أن استخدام البيانات الخاصة نفسه غير آمن.»

**لماذا هذا خطأ:** الحالة الخطرة هي الجمع بين الوصول إلى البيانات الخاصة والمحتوى غير الموثوق والاتصال بطرف خارجي من دون Controls كافية.

### المفهوم الخاطئ 8: «النشر البعيد هو مجرد تشغيل `mcp.run()` على Public IP.»

**لماذا هذا خطأ:** تحتاج الأنظمة البعيدة إلى Authorization وRequest limits وObservability وScaling وInfrastructure آمنة وعمليات Deployment.

### المفهوم الخاطئ 9: «النشر في Registry يثبت أن الخادم آمن.»

**لماذا هذا خطأ:** لا تعد Discoverability وOwnership metadata بدائل لـ Code review وTesting وIsolation وضوابط Runtime security.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Unit test | اختبار Function/Class/Logic unit واحدة بمعزل |
| Integration test | اختبار التفاعلات بين الخادم ومكون/System آخر |
| اختبار شامل (End-to-end test) | اختبار مسار تشغيلي كامل عبر مكونات حقيقية أو واقعية |
| MCP Inspector | Client تفاعلي لـ MCP يُستخدم لاختبار سلوك الخادم وفحصه يدويًا |
| Evaluation | اختبار لسلوك Probabilistic موجّه إلى Model، مثل جودة Prompt أو اختيار Tool |
| دقة اختيار Tool (Tool-choice accuracy) | نسبة مهام Evaluation التي تختار فيها Model الـ Tool المتوقعة |
| LLM-as-a-judge | استخدام Model لتقييم Output مقابل Rubric أو معايير جودة |
| Error analysis | دراسة أنماط الفشل لتحسين Prompts أو Tools أو تصميم النظام |
| Prompt injection | تعليمات غير موثوقة تؤثر في سلوك Model من خلال محتوى مرئي لها |
| Path traversal | محاولة الوصول إلى ملفات خارج حدود Directory المقصود باستخدام Paths مصاغة بعناية |
| Least privilege | منح الحد الأدنى فقط من الوصول المطلوب للعمل المشروع |
| تمرير Token (Token pass-through) | تمرير Authorization tokens الخاصة بـ Client إلى Downstream services بدلًا من الحفاظ على Trust boundaries الصحيحة |
| Confused deputy | نظام Privileged يتم خداعه ليستخدم سلطته لصالح Actor أقل صلاحية |
| Sandboxing | عزل الخادم عن Host resources والأنظمة الأخرى |
| خادم موارد OAuth (OAuth resource server) | خادم محمي يتحقق من Access tokens الصادرة عن Authorization server |
| RBAC | Access control يعتمد على Roles؛ أي أن Permissions تُحدد حسب Roles |
| MCP gateway | وسيط شبكي يستطيع Routing وAuthentication وAuthorization وفرض Policies عبر خوادم MCP |
| Observability | Logs وTraces وMetrics وAlerts المستخدمة لفهم سلوك النظام |
| أمن سلسلة التوريد (Supply-chain security) | حماية Dependencies وImages وBuild systems ومكونات الأطراف الخارجية |
| Lethal Trifecta | تركيبة مخاطر تجمع البيانات الخاصة + المحتوى غير الموثوق + الاتصال بطرف خارجي |
| MCP Colors | إطار لتصنيف مخاطر Tools باستخدام Red للمحتوى غير الموثوق وBlue للإجراءات الحرجة |
| MCPB | MCP Bundle؛ خادم محزم مع Manifest لأدوات التثبيت المدعومة |
| Stateless HTTP | معالجة Requests من دون الاعتماد على State دائمة لكل Client داخل Server session |
| ASGI | واجهة تطبيق ويب Python غير متزامنة تستخدمها Frameworks مثل Starlette وFastAPI |
| MCP Registry | نظام Discovery/Publishing لخوادم MCP موصوف في المصدر |
