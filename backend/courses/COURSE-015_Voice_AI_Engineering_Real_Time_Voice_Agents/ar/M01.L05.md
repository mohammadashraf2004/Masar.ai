## 1. من نظرية Framework إلى تطوير Agent حقيقي

شرح الدرس السابق Anatomy الخاصة بـ Agent framework:

```text
بيئة التشغيل (Runtime)
Memory
Tools
التواصل بين عدة Agents (Multi-agent communication)
Instructions/Prompting
```

والآن ينتقل التركيز من Architecture إلى Implementation.

يختار المصدر **Google's Agent Development Kit (ADK)** بوصفه Framework العملي لهذا الفصل.

الهدف ليس مجرد تعلم Library واحدة.

مسار التعلم الأعمق هو:

```text
التصميم (Design)
   ↓
بناء Agent بسيط (Build a minimal agent)
   ↓
إضافة Tools (Add tools)
   ↓
مراقبة دورة التنفيذ (Observe the execution lifecycle)
   ↓
تحسين بنية Project (Improve project structure)
   ↓
تحويل Agent إلى Live Agent (Turn the agent into a live agent)
   ↓
Debug و Evaluation
```

يظل هذا Workflow مفيدًا حتى إذا استخدمت Framework أخرى لاحقًا.

### لماذا تساعد Framework؟

بناء Agent يدويًا يعلّم الأساسيات.

لكن Projects الحقيقية تستفيد من دعم Framework في:

- تسجيل Tools،
- Session management،
- Event handling،
- Live streaming،
- Memory integration،
- Orchestration.

وهذا يسمح للمطور بالتركيز أكثر على:

```text
هدف Agent (agent purpose)
السلوك (behavior)
القدرات (capabilities)
Context
الجودة (quality)
```

بدل إعادة بناء Infrastructure نفسها مرارًا.

## 3. الخطوة 1 — تحديد Purpose و Tools

ابدأ بـ Purpose.

بالنسبة إلى Math Agent:

```text
Purpose:
حل مسائل Arithmetic أساسية للمستخدم (Solve basic arithmetic problems for the user.)
```

يساعد Purpose الضيق على تحديد Capabilities التي تنتمي إلى Agent.

### من Purpose إلى Tools

اسأل:

> ما Actions التي يجب أن ينفذها Agent لتحقيق Goal؟

بالنسبة إلى Math Agent في المصدر:

```text
جمع (add)
طرح (subtract)
ضرب (multiply)
قسمة (divide)
```

وهذا يعطينا قاعدة تصميم بسيطة:

```text
Goal
 ↓
Actions المطلوبة (required actions)
 ↓
Tools
```

### لماذا هذا مهم؟

من دون Purpose واضحة، يضيف Developers غالبًا Tools لأنها تبدو مثيرة للاهتمام.

وقد يؤدي ذلك إلى:

- Tool lists أكبر،
- Tool selection أصعب،
- Security surface أوسع،
- سلوك أقل قابلية للتوقع.

يجب أن يمتلك Agent المصمم جيدًا Capabilities التي يحتاج إليها، لا كل Capability متاحة.

## 4. الخطوة 2 — تحديد Context المطلوبة

توفر Foundation models معرفة عامة واسعة.

لكن Application قد يحتاج إلى معلومات Specialized لا تعرفها Model بطبيعتها.

يستخدم Math Agent في المصدر **Student profile** بوصفها Context.

قد تتضمن Fields مثل:

```text
المرحلة الدراسية (grade level)
الفصل الحالي (current class)
الأداء الحديث (recent performance)
أهداف التعلم (learning goals)
أسلوب الشرح المفضل (preferred explanation style)
```

### لماذا تغيّر Context السلوك؟

تخيّل أن طالبين يطرحان السؤال نفسه.

Student A:

```text
Year 5
يحتاج إلى بناء الثقة (needs confidence)
يحب الأمثلة الواقعية (likes real-world examples)
```

Student B:

```text
طالب متقدم في High school (advanced high-school student)
يستعد لـ Competition math (preparing for competition math)
```

قد تكون النتيجة الرياضية نفسها.

لكن الشرح لا ينبغي أن يكون نفسه.

### Context ليست هي Instructions

تمييز مفيد:

```text
Context:
حقائق عن الموقف أو المستخدم (facts about the situation or user)

Instructions:
قواعد لكيفية تصرف Agent (rules for how the agent should behave)
```

مثال:

```text
Context:
grade_level = Year 5

Instruction:
اشرح باستخدام لغة مناسبة للعمر (Explain using age-appropriate language.)
```

يصبح هذا الفصل مهمًا لاحقًا عندما يُعاد تنظيم Agent إلى Modules.

## 5. الخطوة 3 — تصميم Core instructions

يسمي المصدر Instructions بأنها **Constitution** الخاصة بـ Agent.

وهي تحدد عدة أشياء.

### Persona

على سبيل المثال:

```text
أنت Math assistant متخصصة (You are a specialized math assistant.)
كن مفيدًا ومباشرًا (Be helpful and direct.)
```

### Boundaries

مثال:

```text
ارفض الطلبات غير الرياضية (Decline non-mathematical requests.)
```

تساعد Boundaries على منع Agent من الانحراف خارج دوره المقصود.

### إرشادات استخدام Tools

يعطي المصدر أمثلة مثل:

```text
"اجمع 3 و 5"
"اطرح 10 من 20"
"اضرب الأرقام بين 1 و 10"
```

يساعد ذلك على توضيح السلوك المتوقع.

### تنسيق Response

يعيد Math Agent لغة طبيعية بدل Structured JSON.

على سبيل المثال:

```text
"الإجابة هي 10."
```

### Checklist مفيدة للـ Instructions

اسأل:

```text
من هو Agent؟ (Who is the agent?)
ما Goal الخاصة به؟ (What is its goal?)
ما الذي ينبغي أن يرفضه؟ (What should it refuse?)
متى ينبغي أن يستخدم Tools؟ (When should it use tools?)
كيف ينبغي أن يستجيب؟ (How should it respond?)
```

## 6. الخطوة 4 — تقديم Examples للتنفيذ

تخبر Instructions الـ Agent بما تريده.

أما Examples فتريه كيف يبدو النجاح.

يقدم المصدر Scenario متكاملًا من البداية إلى النهاية.

### بنية Example

```text
Context:
الطالب في Year 5 (Student is Year 5)

User:
"multiply all the numbers between 1 and 10"

السلوك المتوقع (Expected behavior):
1. التعرف على Math task (Recognize math task)
2. اختيار Multiply tool (Choose multiply tool)
3. بناء Argument list صحيحة (Construct correct argument list)
4. استخدام Tool result (Use tool result)
5. إنتاج Response مناسبة لطفل (Produce child-friendly response)
```

هذا أغنى بكثير من Example يوضح Function syntax فقط.

فهو يوضح:

- تفسير Task،
- اختيار Tool،
- استخدام Context،
- Tone،
- أسلوب Final answer.

### التفكير بطريقة "Golden path"

يمكن أن تصبح Execution example سلوكًا مستهدفًا.

لاحقًا، تظهر الفكرة نفسها في Formal evaluation:

```text
Interaction مثالية (ideal interaction)
    ↓
Test case محفوظة (saved test case)
    ↓
Regression evaluation
```

لهذا تكون Examples مفيدة للـ Prompting وللاختبار أيضًا.

## 10. Session و Artifact Services

إنشاء `Agent` يكوّن Blueprint.

لكنه لا يدير Execution state بمفرده.

يقدم المصدر خدمتين.

### خدمة الجلسات داخل الذاكرة (In-memory Session Service)

الغرض:

```text
memory قصيرة الأمد/الجلسة
```

يمكنها تخزين:

- Messages،
- State،
- استمرارية المحادثة.

ولأنها In-memory، فهي مناسبة للتعلم و Local development.

لكنها ليست Durable عبر Process restarts.

### خدمة الـ Artifacts داخل الذاكرة (In-memory Artifact Service)

الغرض:

```text
تخزين الـ artifacts/الملفات المرتبطة بالـ agent
```

قد تشمل أمثلة ذلك:

- Generated files،
- Images،
- Text artifacts.

لا يستخدم المثال الأساسي في المصدر Artifacts بكثافة، لكن Runner يتوقع تهيئة Artifact service.

### لماذا هما منفصلتان؟

Conversation state وتخزين Files/Artifacts يحلان مشكلتين مختلفتين.

تحافظ Framework ناضجة عليهما بوصفهما Abstractions منفصلة.

## 11. `Runner`: إحياء Agent

إذا كانت `Agent` هي Blueprint، فإن `Runner` هي Execution engine.

يصف المصدر Runner بأنها مسؤولة عن Complete interaction lifecycle.

من حيث الفكرة:

```text
رسالة المستخدم (user message)
    ↓
Runner
    ↓
تحميل Session state (load session state)
    ↓
تجميع Agent context (assemble agent context)
    ↓
استدعاء Model (call model)
    ↓
تنفيذ Tools عند الحاجة (execute tools if needed)
    ↓
تحديث Session (update session)
    ↓
إصدار Events (emit events)
```

تربط Runner الـ Runtime النظري من الفصل السابق بـ Code فعلية.

### لماذا هذه Abstraction مهمة؟

من دون Component شبيهة بـ Runner، ستحتاج إلى تنفيذ ما يلي يدويًا:

- Prompt assembly،
- State loading،
- Tool dispatch،
- State updates،
- Model calls،
- Event streaming.

تجمع Framework هذه المسؤوليات في مكان مركزي.

## 17. Agents المزودة بـ Tools تنتج Events أغنى

بمجرد تفعيل Tools، تصبح Event stream أكثر فائدة.

يسلط المصدر الضوء على ثلاث Categories من Events:

### Function call

تطلب Model استخدام Tool.

وتحتوي معلومات مثل:

```text
اسم Function (function name)
Arguments
```

### Function response

تكون Tool قد نُفذت.

وتحتوي:

```text
اسم Function (function name)
Result
```

### Final response

تكون Agent قد حصلت على معلومات كافية وتعيد Natural language.

### لماذا نفحص الثلاثة؟

لأن Debugging لـ Agent يتطلب فهم:

```text
ماذا اختارت Model؟ (what did the model choose?)
بأي Arguments؟ (with what arguments?)
ماذا أعادت Tool؟ (what did the tool return?)
كيف استخدمت Final answer النتيجة؟ (how did the final answer use the result?)
```

من دون هذه Visibility، قد تبدو Tool failures كأنها Model failures.

## 18. Chaining لعدة Tools داخل Request واحدة

يستخدم المصدر هذا الطلب:

```text
اضرب الأرقام من 1 إلى 3 أولًا ثم أضف 4.
```

التنفيذ الصحيح هو:

```text
multiply([1, 2, 3])
    ↓
6
    ↓
add([6, 4])
    ↓
10
    ↓
الاستجابة النهائية
```

هذه مرحلة مهمة.

Agent لا تختار Tool واحدة فقط.

بل تستخدم Output الخاصة بـ Tool واحدة بوصفها Input لأخرى.

### Execution trace

```text
طلب المستخدم (User request)
    ↓
Function Call: multiply
    ↓
Function Response: 6
    ↓
Function Call: add
    ↓
Function Response: 10
    ↓
Final Response: 10
```

يوضح ذلك سبب فائدة Event-based execution.

## 28. Browser audio إلى Live Agent

يواصل Frontend إرسال Audio chunks إلى Backend.

```text

    ↓

    ↓

```

## 29. Events من Live Agent إلى Browser

يستمع Response handler في المصدر إلى Live event stream.

تشمل Event categories المهمة:

### Interruption

يبدأ المستخدم الكلام أثناء استجابة Agent.

يقوم Backend بعمل Forwarding لإشارة Interruption.

ينبغي لـ Frontend إيقاف Stale audio playback.

### Turn complete

تنتهي Agent من Current conversational turn.

يمكن لـ Frontend تحديث UI state.

### Audio content

تصدر Agent بيانات PCM audio.

يقوم Backend بترميزها Base64 ويرسلها إلى Browser.

### النموذج الذهني القائم على Events

```text
Live event
   ├── Interruption -> إيقاف Playback (stop playback)
   ├── Turn complete -> تحديث State (update state)
   └── Audio -> تشغيل Audio (play audio)
```

يحافظ Event protocol هذا على توافق سلوك UI مع Agent/Runtime state.

## 37. حدود مهمة خاصة بالمصدر و Production

الفصل Tutorial عملي من Early Release.

ينبغي التعامل مع عدة تفاصيل بوصفها Version-specific.

- Supported models،
- Supported live-streaming models،

- Language codes،

- ADK Web CLI commands،
- Evaluation UI و Metric names.

```text
Method signatures محددة (specific method signatures)

```

يستخدم Math Agent أدوات Arithmetic منخفضة المخاطر.

- Schema validation،

> "دعم Live Agent يغيّر Frontend فقط."

### لماذا هذا خطأ؟

التغيير Architectural الأساسي هو أن Framework/Runtime تستطيع تجريد جزء كبير من Provider-side live streaming ودمجه مع Agent state و Tools.

---

### المفهوم الخاطئ 9

> "Interactive chat testing كافٍ للتحقق من Agent."

### لماذا هذا خطأ؟

Manual testing مفيدة، لكن Repeatable evaluation datasets مطلوبة لاكتشاف Regressions بصورة منهجية.

---

### المفهوم الخاطئ 10

> "إذا كانت Final answer صحيحة، فلا يهم Execution path الخاص بـ Agent."

### لماذا هذا خطأ؟

Tool trajectory مهمة للموثوقية. قد تفشل نتيجة صحيحة تم الوصول إليها عبر Path غير آمنة أو خاطئة منطقيًا في حالات مستقبلية.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مخطط Agent (Agent blueprint) | Design قبل كتابة Code يصف Purpose و Tools و Context و Instructions و Examples |
| الهدف (Purpose) | المشكلة التي يُفترض أن يحلها Agent |
| السياق (Context) | معلومات Specialized تُقدم لمساعدة Agent على التكيف مع User/Task الحالية |
| التعليمات الأساسية (Core instruction) | Persistent behavioral rules وإرشادات Persona |
| مثال تنفيذ (Execution example) | Demonstration متكاملة للسلوك المطلوب من Agent |
| إطار ADK | Agent Development Kit المستخدم بوصفه Framework العملي في الفصل المصدر |
| كائن Agent | Framework object يحدد Identity و Instructions و Model و Tools الخاصة بـ Agent |
| خدمة Session Service | Service تدير State لكل Session و Short-term memory |
| خدمة Artifact Service | Service لتخزين Files/Artifacts المرتبطة بالتنفيذ |
| المشغل Runner | Runtime engine تنفذ Agent وتنسق Sessions و Tools و Events |
| الجلسة (Session) | Stateful interaction scope تحددها Application/User/Session identifiers |
| تدفق Events (Event Stream) | Sequence من Runtime events تصدر أثناء تنفيذ Agent |
| حدث Function Call Event | Event تشير إلى أن Model طلبت Tool |
| حدث Function Response Event | Event تحتوي Result الخاصة بـ Tool code التي نُفذت |
| حدث Final Response Event | Event تحتوي Natural-language answer المكتملة |
| توثيق Tool docstring | Documentation تستخدمها Framework كجزء من Model-facing description للـ Tool |
| تسلسل Tools (Tool chaining) | استخدام عدة Tools بالتتابع بحيث تؤثر Outputs المبكرة في Calls اللاحقة |
| بنية Modular agent structure | فصل Tools و Context و Examples و Prompt و Assembly إلى Modules مخصصة |
| المسار المثالي (Golden path) | Example interaction توضح Ideal behavior |
| طابور Live Request Queue | Queue تستقبل Live input لتنفيذ Real-time تديره Framework |
| تدفق Live Event Stream | Stream من Agent output/control events في الوقت الحقيقي |
| حدث Interruption event | Signal تشير إلى أن User input قاطعت Agent output |
| حدث Turn complete | Signal تشير إلى اكتمال Current conversational response |
| واجهة ADK Web | Visual development/debugging interface التي يصفها المصدر |
| حالة Golden test case | Ideal interaction محفوظة تُستخدم بوصفها Evaluation example |
| مسار Tool trajectory | Sequence من Tool actions التي اتخذتها Agent |
| تراجع Regression | تدهور Behavior كانت صحيحة سابقًا بعد Change |
