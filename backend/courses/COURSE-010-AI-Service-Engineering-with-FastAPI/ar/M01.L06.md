## 1. لماذا يهم الاتصال في الوقت الحقيقي في GenAI؟

تساعد Concurrency الـ Server على التعامل مع عدة Users.

لكن Concurrency لا تحسن تلقائيًا تجربة **User واحد ينتظر Generation بطيئة**.

افترض أن LLM يحتاج 20 ثانية لإنتاج Answer طويلة.

مع Traditional request-response flow:

```text
User يرسل Request
      ↓
Server يولد Answer كاملة
      ↓
تمر 20 ثانية
      ↓
تصل Answer كاملة دفعة واحدة
```

لا يرى User أي شيء حتى تنتهي Generation.

أما Real-time stream فتغير التجربة:

```text
User يرسل Request
      ↓
Model يبدأ Generation
      ↓
Chunk 1
      ↓
Chunk 2
      ↓
Chunk 3
      ↓
...
```

قد يظل Total generation time مشابهًا، لكن User يبدأ في تلقي Output مفيدة أبكر بكثير.

### Streaming تحسن الاستجابة المتصورة

في Generation البطيئة، يمكن للتسليم الجزئي أن:

- يقلل الشعور بالانتظار،
- يجعل Outputs الطويلة أسهل في القراءة،
- يوضح أن System يعمل بالفعل،
- يحافظ على تفاعل User.

وهذا مهم بصورة خاصة في:

- Chatbots،
- Live transcription،
- Speech interfaces،
- Long text generation،
- Progress updates.

### لكن Real-time ليست أفضل تلقائيًا

يحذر المصدر من أن Streaming تضيف تعقيدًا.

قد تحتاج إلى التعامل مع:

- Persistent connections،
- Dropped connections،
- Reconnection،
- Exception handling،
- State synchronization،
- عدد كبير من Concurrent open streams،
- Memory/Resource usage،
- Client compatibility.

وقد لا تدعم بعض Models أوProviders الـ Streaming أصلًا.

لذلك يكون أول سؤال هندسي هو:

> **هل تحتاج هذه Feature فعلًا إلى Real-time updates؟**

إذا كانت Task تنتهي خلال ثانية أوثانيتين، فقد تكون HTTP العادية أبسط وكافية تمامًا.

[[IMAGE_NEEDED: Traditional response versus streaming AI response | Side-by-side timeline showing a normal HTTP request where nothing appears until full completion, versus a streaming request where partial text chunks arrive throughout model generation | Learner should notice that streaming improves time-to-first-visible-output without necessarily reducing total generation time]]

## 2. خمسة أنماط للاتصال عبر Web

يقارن الفصل بين خمس Mechanisms:

1. HTTP request-response
2. الاستطلاع (polling) القصير/المنتظم
3. Long polling
4. أحداث يرسلها الخادم (SSE)
5. WebSocket (WS)

تحل كل واحدة مشكلة مختلفة قليلًا.

### مقارنة سريعة

| Mechanism | نمط Connection | الاتجاه | مناسبة لـ |
|---|---|---|---|
| HTTP request-response | Short-lived | Request ثم Response | APIs عادية |
| Short polling | طلبات قصيرة متكررة | Client يسأل بصورة متكررة | فحص Job/Status |
| Long polling | تبقى Request مفتوحة حتى وجود Update | Server يرد مرة واحدة لكل Request | تحديثات شبه فورية |
| SSE | Persistent HTTP stream | Server → Client | LLM output وFeeds وDashboards |
| WebSocket | اتصال دائم مُرقّى | كلا الاتجاهين | Voice وCollaboration وInteractive streams |

{{image:communication-mechanisms}}

يشدد المصدر على أن الاختيار يعتمد على:

- User experience،
- Latency needs،
- Scalability،
- Development cost،
- Maintainability،
- دعم المتصفح/العميل.

لا توجد Mechanism واحدة صحيحة في كل الحالات.

## 3. HTTP request-response التقليدية

نموذج Web API العادي بسيط:

```text
العميل
  ↓ طلب
الخادم
  ↓ استجابة
العميل
```

HTTP **Stateless**.

تُعالج كل Request بصورة مستقلة ما لم يخزن Application الـ State صراحة في مكان آخر.

مثلًا، قد يرسل Chatbot بلا Server-side conversation memory سجل Conversation كاملًا مع كل Request.

### نقاط القوة

HTTP request-response:

- بسيطة،
- مدعومة على نطاق واسع،
- سهلة الاختبار،
- مألوفة،
- مناسبة جيدًا لـ REST-style APIs.

### نقطة الضعف مع AI generation الطويلة

يعيد Server عادةً Response فقط بعد اكتمال Processing.

بالنسبة إلى Generation مكلفة:

```text
Request
→ انتظار
→ انتظار
→ انتظار
→ Result كاملة
```

هنا تصبح Real-time mechanisms ذات قيمة.

## 4. Short polling

تعني Short polling أن Client يسأل بصورة متكررة:

> هل يوجد شيء جديد الآن؟

مثال:

```text
POST /jobs
→ يُرجع job_id=42

GET /jobs/42
→ قيد الانتظار (pending)

GET /jobs/42
→ قيد الانتظار (pending)

GET /jobs/42
→ اكتمل (completed)
```

### لماذا هي مفيدة؟

هذا الأسلوب سهل الفهم والتنفيذ.

ويعمل جيدًا مع:

- Batch image jobs،
- Long asynchronous jobs،
- Occasional status checks،
- Systems التي تكون Updates فيها غير متكررة.

### المقايضة

إذا كان Client ينفذ Poll كل ثانية:

```text
طلب
طلب
طلب
طلب
طلب
```

فقد تعود Requests كثيرة دون أي معلومات جديدة.

ومع عدد كبير من Users، يهدر ذلك:

- Network traffic،
- Server capacity،
- موارد معالجة الطلبات.

### مقايضة Polling interval

```text
فاصل قصير
→ Updates أحدث
→ Traffic أكبر

فاصل طويل
→ Traffic أقل
→ Updates أبطأ
```

يمكن لـ Caching وRate limiting تقليل عمل Server غير الضروري.

## 5. Long polling

تحاول Long polling تقليل Requests المتكررة غير الضرورية.

بدلًا من أن يرد Server فورًا بـ:

```text
"لا جديد"
```

يبقي Server الـ Request مفتوحة حتى تتوفر Data.

```text
Client request
      ↓
Server ينتظر
      ↓
تظهر Data جديدة
      ↓
Server يرد
      ↓
Connection تُغلق
      ↓
Client يفتح Request أخرى فورًا
```

### لماذا قد تكون أفضل من Short polling؟

ينشئ Client عددًا أقل من Empty requests.

ويمكن لذلك تقليل Traffic وتحسين Near-real-time behavior.

### لماذا ما تزال غير مثالية؟

يجب على Server إبقاء Unfulfilled requests مفتوحة.

وهذا يستهلك Resources.

وتشمل التعقيدات الأخرى:

- Timeout handling،
- Multiple requests من Client واحد،
- Message ordering،
- Repeated reconnections.

يعرض الفصل SSE كبديل أحدث عندما تكون Persistent server-to-client stream متاحة.

## 6. أحداث يرسلها الخادم (SSE)

تنشئ **Server-Sent Events** اتصال HTTP مستمرًا يمكن من خلاله لـ Server دفع Events بصورة متكررة إلى Client.

Connection **Unidirectional**:

```text
العميل → طلب HTTP أولي
الخادم → حدث
الخادم → حدث
الخادم → حدث
الخادم → حدث
```

لا يستخدم Client الـ Stream نفسها لإرسال Messages عشوائية بصورة مستمرة إلى Server.

### SSE handshake

يطلب Client الـ Stream ويشير إلى:

```text
Accept: text/event-stream    # ترويسة الطلب
```

ويرد Server بـ:

```text
200 OK    # حالة الاستجابة
Content-Type: text/event-stream
```

ثم يبقى Connection مفتوحًا.

### تنسيق Events

تبدو SSE event بسيطة هكذا:

```text
data: hello    # حدث SSE واحد
```

ينهي Blank line الـ Event.

بالنسبة إلى Token streaming:

```text
data: Hello    # أحداث SSE متتالية

data:  world

data: !

data: [DONE]
```

### لماذا SSE جذابة لـ LLM output؟

غالبًا ما يكون نمط LLM conversation هكذا:

```text
Client يرسل Prompt واحدًا
Server يرسل Chunks مولدة كثيرة
```

هذا الاتجاه يناسب SSE بصورة طبيعية.

### دعم Browser المدمج

توفر Browsers واجهة `EventSource`.

ومن المزايا المهمة التي يذكرها المصدر سلوك Automatic reconnection.

### مزايا SSE

- مبنية فوق HTTP،
- مباشرة،
- Persistent،
- Automatic reconnection باستخدام `EventSource`،
- دعم Event IDs/Retry،
- مناسبة جيدًا لـ Text streams.

### قيد SSE

هي One-way.

إذا احتاج الطرفان إلى Continuous real-time messaging، تكون WebSocket أنسب.

## 12. Retries وإعادة الاتصال

قد تفشل Persistent connections بسبب:

- Network interruptions،
- Server restarts،
- Proxy issues،
- تغير اتصال Client.

ينبغي لـ Production client تحديد كيفية عمل Reconnection.

### EventSource

من مزايا SSE وجود Built-in reconnection behavior.

ويمكن لـ Server أيضًا إرسال Retry timing.

### Manual POST stream

عند استهلاك Stream يدويًا باستخدام `fetch`، تصبح Retry logic مسؤوليتك.

يعرض الفصل **Exponential backoff**.

```text
المحاولة 1 → انتظر 1 ثانية
المحاولة 2 → انتظر 2 ثانية
المحاولة 3 → انتظر 4 ثانية
...
```

يمنع ذلك ضرب Server الفاشل بطلبات متكررة فورًا.

### خطر State drift

تطرح Reconnection سؤالًا مهمًا:

> من أين ينبغي أن تستأنف Stream؟

إذا كان Client قد استقبل نصف Answer قبل Disconnect، فقد تؤدي Restart بصورة عمياء إلى:

- Duplicated content،
- Missing content،
- Stochastic continuation مختلفة.

قد يتطلب Reliable resume behavior:

- Event IDs،
- Persisted generation state،
- Message IDs،
- إزالة التكرار على جهة العميل.

لذلك Streaming ليست مجرد «أرسل Chunks».

إنها أيضًا مشكلة State management.

## 13. WebSocket: اتصال مستمر ثنائي الاتجاه

SSE هي Server → Client.

أما WebSocket فهي **Bidirectional**.

```text
العميل ⇄ الخادم
```

يمكن للطرفين إرسال Messages بينما يبقى Connection مفتوحًا.

يجعل ذلك WebSocket مفيدة لـ:

- Interactive chat،
- Speech-to-text،
- Text-to-speech،
- Speech-to-speech،
- Multiplayer applications،
- Collaboration،
- النسخ الفوري للكلام.

### WebSocket ليست Webhook

عادةً تكون **Webhook** آلية Server-to-server لإرسال Events.

```text
الخادم A
  ↓ استدعاء HTTP عكسي (callback)
نقطة webhook في الخادم B
```

ولا يوجد Persistent two-way socket.

أما **WebSocket** فهي:

```text
العميل ⇄ اتصال دائم ⇄ الخادم
```

لا تخلط بينهما.

### اختلاف Protocol

تبدأ WebSocket بـ HTTP upgrade handshake.

وبعد Upgrade، يستخدم الاتصال WebSocket protocol عبر Underlying TCP connection بدل Ordinary HTTP request-response messages.

### Secure WebSocket

في Production، يوصي المصدر باستخدام:

```text
wss://    # بروتوكول WebSocket الآمن
```

بدلًا من:

```text
ws://
```

توفر `wss\://` تشفير TLS بصورة مماثلة لـ HTTPS.

## 14. WebSocket handshake وLifecycle

تبدأ WebSocket بطلب **HTTP upgrade**.

يتضمن Simplified handshake Headers تشير إلى:

```text
Connection: Upgrade    # ترويسات ترقية الاتصال
Upgrade: websocket
```

يقبل Server الـ Upgrade أويرفضها.

### حالات Lifecycle

يصف الفصل Connection عبر حالات مثل:

```text
CONNECTING
    ↓
OPEN
    ↓
CLOSING
    ↓
CLOSED
```

{{image:websocket-lifecycle}}

### Message frames

بعد فتح Connection، ترسل WebSocket frames.

يناقش المصدر:

- Text frames،
- Binary frames،
- Fragmented messages،
- Control frames.

### Control frames

يشمل Control behavior المهم:

- Ping/Pong لفحص صحة Connection،
- Close frames للإنهاء بصورة سليمة.

### لماذا تهم State؟

يجب على WebSocket server إدارة:

- Active connections،
- Disconnects،
- Cleanup،
- Authentication،
- Resource limits.

بخلاف Independent stateless HTTP requests، تنشئ Open sockets حالة تظل مرتبطة بالـ Clients.

تُعد Manager الأساسية في الفصل مفيدة للتعلم، لكن لا ينبغي اعتبارها Complete distributed WebSocket architecture.

## 18. اختيار SSE أوWebSocket

بالنسبة إلى تطبيقات GenAI كثيرة، يكون الاختيار الأهم:

```text
SSE or WebSocket?
```

### اختر SSE عندما:

- يرسل Client طلبًا ويستقبل أساسًا Stream،
- يكون Text streaming هو Use case الرئيسية،
- تريد HTTP semantics أبسط،
- يكون دعم Browser لـ `EventSource` مفيدًا،
- تكون Built-in reconnection جذابة.

مثال:

```text
User يرسل LLM prompt
→ Model يبث Answer
```

### اختر WebSocket عندما:

- يحتاج الطرفان إلى Ongoing communication،
- يحمل Connection عددًا كبيرًا من Messages،
- تكون Binary data مهمة،
- يكون Real-time interaction شديد الديناميكية.

أمثلة:

```text
التعرّف على الكلام المباشر
مساعد صوتي من صوت إلى صوت
محرر AI تعاوني
محادثة تفاعلية متعددة المستخدمين
```

### لا تستخدم WebSocket فقط لأنها تبدو أكثر تقدمًا

يصف المصدر WebSocket صراحة بأنها قد تكون Excessive للـ Simple one-way model output.

وغالبًا يكون Protocol الأبسط أسهل في:

- Testing،
- Scaling،
- Observability،
- Recovery.

### جدول اختيار Mechanism

| المتطلب | الأفضل |
|---|---|
| لا توجد Real-time updates مطلوبة | HTTP |
| فحص دوري بسيط لحالة Job | Short polling |
| Near-real-time update مع Held request | Long polling |
| مخرجات streaming باتجاه واحد | SSE |
| تفاعل دائم باتجاهين | WebSocket |

## 19. صمّم Streaming APIs ببساطة

الدرس المعماري الأخير لا يرتبط بـ Protocol محددة.

يحذر المصدر من كشف عدد كبير جدًا من Specialized streaming endpoints.

Pattern سيئة:

```text
/stream/ask    # مسارات بث متعددة
/stream/search
/stream/summarize
/stream/tool
/stream/model-a
/stream/model-b
```

عندها يجب على Client فهم عدد كبير من Backend workflows والتنسيق بينها.

وهذا يدفع Business logic إلى Frontend.

### Pattern أبسط

اكشف Main streaming entry point واحدة.

استخدم:

- Request body،
- Headers،
- Query parameters،
- Conversation state،

لإبلاغ Backend بالسلوك المطلوب.

مفاهيميًا:

```text
العميل
  ↓
/stream
  ↓
router/service في الـ backend
  ├── اختيار prompt
  ├── اختيار النموذج
  ├── الاستعلام من قاعدة البيانات
  ├── استدعاء أداة
  └── بث الاستجابة
```

### لماذا هذا أسهل؟

يمتلك Backend بالفعل وصولًا إلى:

- Databases،
- Services،
- Prompts،
- Model providers،
- Authorization rules،
- Application state.

يمكن للاحتفاظ بـ Switching logic هناك تقليل تعقيد Frontend.

### النموذج الذهني المعماري النهائي

```text
                         ┌──────────────────┐
                         │      العميل      │
                         └────────┬─────────┘
                                  │
                   الطلب / الاتصال
                                  │
                                  ▼
                    ┌────────────────────────┐
                    │   طبقة Streaming API      │
                    ├────────────────────────┤
                    │ auth / الحالة / التوجيه│
                    │ اختيار النموذج         │
                    │ معالجة الأخطاء         │
                    │ إدارة الاتصالات        │
                    └───────────┬────────────┘
                                │
              ┌─────────────────┼─────────────────┐
              │                 │                 │
              ▼                 ▼                 ▼
           Model API     قاعدة البيانات        الأدوات
              │
              ▼
       chunks مولَّدة
              │
              ▼
     بث SSE أو WebSocket
```

Protocol ليست سوى جزء واحد من System.

تحتاج Reliable streaming service أيضًا إلى:

- إدارة جيدة لـ Connection lifecycle،
- Ownership واضح للـ State،
- Safe retries،
- Awareness للـ Backpressure،
- Authentication،
- Graceful errors.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Streaming تجعل Model تحسب Answer أسرع.

### لماذا هذا خطأ؟

تغير Streaming أساسًا **توقيت التسليم**. يرى User Output جزئية في وقت أبكر، لكن Total model compute قد تظل مشابهة.

### المفهوم الخاطئ 2

> يجب أن تستخدم كل AI endpoint الـ Streaming.

### لماذا هذا خطأ؟

تضيف Streaming تعقيد Connection وError وState وScalability. قد تكون Tasks القصيرة أبسط مع HTTP العادية.

### المفهوم الخاطئ 3

> Short polling هي Real-time وفعالة عند أي Scale.

### لماذا هذا خطأ؟

قد تنشئ Frequent polling عددًا كبيرًا من Requests التي لا تعيد Data جديدة.

### المفهوم الخاطئ 4

> Long polling تبقي Permanent connection واحدة مفتوحة إلى الأبد.

### لماذا هذا خطأ؟

يعيد Server Message واحدة ويغلق تلك Request، ثم يفتح Client Long-poll request أخرى.

### المفهوم الخاطئ 5

> SSE وWebSocket متماثلتان أساسًا لأن كلتيهما Persistent.

### لماذا هذا خطأ؟

SSE هي أساسًا Server-to-client عبر HTTP. أما WebSocket فهي Bidirectional بعد HTTP upgrade.

### المفهوم الخاطئ 6

> يمكن لـ `EventSource` طبيعيًا إرسال Large JSON POST body.

### لماذا هذا خطأ؟

تستخدم Native EventSource واجهة GET، ولذلك تحتاج Large أوStructured request payloads إلى Pattern أخرى.

### المفهوم الخاطئ 7

> POST streaming أبسط دائمًا من GET SSE.

### لماذا هذا خطأ؟

تسمح POST بـ Richer request bodies، لكن يجب على Client استهلاك Response stream وإدارتها يدويًا بدل الاعتماد على EventSource behavior.

### المفهوم الخاطئ 8

> WebSocket هي نفسها Webhook.

### لماذا هذا خطأ؟

Webhook هي Event-driven HTTP callback، وعادةً من Server إلى Server آخر. أما WebSocket فهي Persistent two-way connection.

### المفهوم الخاطئ 9

> بعد قبول WebSocket، تظل HTTP 4xx/5xx responses العادية هي Error mechanism الأساسية.

### لماذا هذا خطأ؟

بعد Upgrade، تُنقل Errors عادةً عبر Messages وسلوك/أكواد إغلاق WebSocket.

### المفهوم الخاطئ 10

> In-memory WebSocket connection list تتوسع تلقائيًا عبر عدة Server processes.

### لماذا هذا خطأ؟

لكل Process Memory منفصلة. تحتاج Distributed connection management إلى Architecture إضافية.

### المفهوم الخاطئ 11

> إذا Disconnect للـ Client، فلا يلزم أي شيء خاص.

### لماذا هذا خطأ؟

يجب على Server تنظيف Connection state وقد يحتاج أيضًا إلى التعامل مع Incomplete streams أوState drift.

### المفهوم الخاطئ 12

> زيادة عدد Streaming endpoints تمنح Frontend مرونة أكبر.

### لماذا يكون هذا خطأ غالبًا؟

قد تدفع Specialized endpoints كثيرة تعقيد Routing وConversation state إلى Client. ويمكن لـ Streaming entry point واحدة أن تُبقي Orchestration داخل Backend.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التواصل الفوري (Real-time) | تسليم Updates بأقل Delay ممكن أثناء استمرار Interaction |
| HTTP request-response | يرسل Client Request واحدة ويتلقى Response واحدة |
| Stateless | Requests مستقلة ما لم تُخزن Application state صراحة |
| Short polling | يقوم Client بفحص Data الجديدة بصورة متكررة وفق فواصل زمنية ثابتة |
| Long polling | يحتفظ Server بالـ Request حتى تتوفر Data ثم يعيد Client الاتصال |
| SSE | Server-Sent Events؛ Persistent HTTP-based server-to-client event stream |
| EventSource | واجهة Browser لاستهلاك SSE streams |
| `text/event-stream` | Media type المستخدمة لـ SSE |
| StreamingResponse | FastAPI response type ترسل Yielded/Iterated content تدريجيًا |
| Async generator | Async function تنتج Values عبر الزمن باستخدام Yield |
| Backpressure | حالة ينتج فيها Producer Data أسرع من قدرة Consumer على معالجتها |
| Reconnection | إعادة إنشاء Streaming connection بعد انقطاعها |
| Exponential backoff | Retry strategy تزيد مدة الانتظار بين المحاولات المتكررة |
| CORS | Browser security mechanism للتحكم في Cross-origin requests |
| WebSocket | Persistent full-duplex communication protocol يتم إنشاؤها عبر HTTP upgrade |
| Full-duplex | يستطيع الطرفان إرسال Data بصورة مستقلة عبر Open connection نفسها |
| Webhook | Event-driven HTTP callback، عادةً من Server إلى آخر |
| Handshake | Initial negotiation لإنشاء WebSocket connection |
| `ws\://` | WebSocket scheme غير مشفرة |
| `wss\://` | WebSocket scheme محمية بـ TLS |
| Message frame | Unit تستخدم لنقل WebSocket message data |
| Control frame | WebSocket frame تستخدم لـ Ping/Pong أوإغلاق Connection |
| Close code | WebSocket code تشرح سبب إغلاق Connection |
| Connection manager | Application component تتتبع Active WebSocket connections وتديرها |
| Broadcast | إرسال Message إلى عدد كبير من Clients المتصلين حاليًا |
| State drift | وصول Client وServer إلى Views غير متسقة عن Stream/Conversation state |
| الزمن حتى أول مخرجات | Delay قبل أن يتلقى User أول Generated chunk مرئية |
