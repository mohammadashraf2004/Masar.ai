## 1. من AI models إلى AI agents

أسهل طريقة لفهم AI agent هي أن نفهم أولًا ما الذي سبقها.

يمكن لـ Normal model أن **تنتج إجابة**. أما Agent فمصممة لكي **تعمل نحو هدف**.

قد يبدو الفرق صغيرًا، لكنه يغير Architecture الخاصة بالنظام بالكامل.

تدرج مفيد هو:

```text
وكيل ذاتي كلاسيكي (Classical autonomous agent)
        ↓
نموذج تأسيسي (Foundation model)
        ↓
نموذج تأسيسي + Retrieval
        ↓
نموذج تأسيسي + Retrieval + Actions
        ↓
وكلاء متعاونون (Collaborating agents)
```

تضيف كل مرحلة Capability لم تكن المرحلة السابقة توفرها بالكامل.

### المرحلة 0 — الوكلاء الكلاسيكيون أو Legacy agents

كان البحث في Agents موجودًا قبل Modern generative AI بوقت طويل.

وكان السؤال المركزي مألوفًا بالفعل:

> هل يستطيع Computational system أن يدرك Environment الخاصة به ويتصرف باستقلالية لتحقيق Goal؟

ظهرت ثلاث أفكار معمارية مهمة.

| Architecture | الفكرة الأساسية | نقطة القوة | نقطة الضعف |
|---|---|---|---|
| Deliberative | بناء Internal representation ثم Reasoning ثم Planning | يستطيع التفكير مسبقًا | قد يكون بطيئًا وصلبًا |
| Reactive | الاستجابة مباشرة للـ Environment بسلوكيات بسيطة | Response سريعة | Planning طويلة المدى ضعيفة |
| Hybrid | الجمع بين Planning و Reactive behavior السريع | يوازن بين الاستباق والاستجابة | Architecture أكثر تعقيدًا |

من الأفكار Deliberative الشهيرة نموذج **Belief-Desire-Intention (BDI)**:

- **Beliefs** تمثل ما تعتقد Agent أنه صحيح عن العالم.
- **Desires** تمثل Outcomes التي ترغب في تحقيقها.
- **Intentions** تمثل Plans أو Commitments التي تختار Agent متابعتها.

الدرس المهم ليس أن Modern agents تطبق BDI حرفيًا. بل أن المشكلات الأساسية—Perception و Planning و Autonomy و Coordination—ليست جديدة.

كانت Multi-agent systems موجودة أيضًا قبل Generative AI. درس الباحثون كيف يمكن لعدة Autonomous systems أن تتعاون أو تتنافس أو تتفاوض أو تقسّم العمل.

لم تُلغ Foundation models الحديثة هذه الأفكار. بل قدمت لها Reasoning engine جديدة.

### المرحلة 1 — Foundation models و Prompts

يمكن لـ Large language model استقبال Prompt وتوليد Response باستخدام Patterns تعلمتها أثناء Training.

توسع Foundation models هذه الفكرة. فهي General-purpose models يمكنها دعم Tasks كثيرة، واعتمادًا على Model قد تدعم أكثر من Modality واحدة.

في هذه المرحلة، تكون Model قوية لكنها في الغالب **Generic**.

تخيل AI teaching assistant.

تسأل:

> ما هو تعلّم الآلة (machine learning)؟

يمكن لـ Foundation model على الأرجح شرح ذلك جيدًا.

ثم تسأل:

> ماذا قال أستاذي عن الامتحان في محاضرة الأمس؟

لا تستطيع Model الإجابة بصورة موثوقة ما لم تُوفَّر لها Private course information هذه.

إذًا القيد ليس بالضرورة Intelligence. بل هو **Missing context**.

### المرحلة 2 — Foundation models مع Retrieval

تعالج Retrieval-Augmented Generation هذه المشكلة عبر استرجاع Information ذات صلة وتقديمها إلى Model عند الحاجة.

التدفق المبسط هو:

```text
سؤال User
    ↓
البحث في Data خاصة أو Domain-specific
    ↓
استرجاع أكثر الأجزاء صلة
    ↓
تقديمها كـ Model context
    ↓
توليد إجابة Grounded في تلك Context
```

تكون RAG مفيدة لسببين.

**Contextual relevance:** تتلقى Model Information مرتبطة بالسؤال الحالي بدلًا من الاعتماد فقط على Generic knowledge.

**Context-window management:** تستطيع Application استرجاع Subset مركزة بدلًا من وضع Knowledge base كاملة داخل كل Prompt.

يمكن لـ Teaching assistant الآن الإجابة عن أسئلة Grounded في Lecture notes أو Syllabi أو Required readings.

لكنها ما تزال في الأساس **تجيب**.

### المرحلة 3 — Agents تستطيع التنفيذ

تحدث القفزة التالية عندما يحصل النظام على Tools.

يمكن لـ Tool أن تسمح للتطبيق بـ:

- تنفيذ Calculation،
- استدعاء API،
- استرجاع Live information،
- كتابة Data أو تعديلها،
- جدولة Event،
- تنفيذ Code،
- استدعاء Service أخرى،
- أو تشغيل أي External operation أخرى.

الآن يمكن للنظام الانتقال من:

```text
"يمكنني أن أخبرك كيف تفعل ذلك."
```

إلى:

```text
"يمكنني اختيار Capability المناسبة وطلب تنفيذها من Application."
```

هذا الانتقال—من المعرفة إلى التنفيذ—محوري في Modern agentic systems.

### المرحلة 4 — Multi-agent systems

قد تصبح Agent واحدة مثقلة إذا كان عليها فهم كل Domain والاختيار من بين مئات Tools.

أما Multi-agent system فتقسّم العمل إلى Specialists.

على سبيل المثال:

```text
موجّه المساعد التعليمي (Teaching Assistant Router)
├── وكيل الرياضيات (Math Agent)
├── وكيل التاريخ (History Agent)
└── وكيل القواعد (Grammar Agent)
```

يقرر Router أي Specialist ينبغي أن يتعامل مع Request. ويرى كل Specialist فقط Tools و Knowledge المهمة لـ Domain الخاص به.

يعيدنا ذلك إلى فكرة قديمة في Agents مع Reasoning engine جديدة: **عدة Components ذاتية تتعاون نحو Goal أكبر**.

[[IMAGE_NEEDED: Five-stage evolution of AI agents | A left-to-right diagram showing Stage 0 classical agents, Stage 1 foundation models, Stage 2 foundation models plus RAG, Stage 3 tool-using agents, and Stage 4 multi-agent systems | Learner should notice that retrieval adds knowledge, tools add action, and multi-agent systems add specialization and collaboration]]

### Classical agents مقابل Agents المعتمدة على Foundation models

التحول أعمق من مجرد استبدال Rules بـ LLM.

| البُعد | Classical agents | Agents المعتمدة على FM |
|---|---|---|
| Reasoning | Rules صريحة و Search و Symbolic أو Formal logic | Learned model behavior تُوجّهها Prompts/Context |
| Knowledge | Databases منسقة و Hand-built rules | Broad learned knowledge + Retrieved context اختياريًا |
| Planning | غالبًا Fixed أو Formal | يمكنها توليد Flexible plans وقت Runtime |
| Tool selection | غالبًا Hard-coded | يمكنها اختيار Tools من Natural-language descriptions |
| Transparency | غالبًا يمكن فحص Logic مباشرة | Internal model reasoning أقل شفافية |
| Flexibility | قوية داخل Environment ضيقة ومصممة | تتكيف مع نطاق أوسع من Natural-language tasks |

تهم هذه Trade-off: تكسب Modern systems مرونة، لكن Developers يحتاجون Evaluation و Observability و Validation و Guardrails أقوى.

## 2. ما الذي يجعل النظام Agent فعلًا؟

إطلاق كلمة "Agent" على كل Chatbot يجعل المصطلح شبه عديم الفائدة.

نموذج ذهني أفضل يتكون من أربعة أجزاء.

### 2.1 الإدراك (Perception)

يستقبل النظام Information من Environment.

قد تكون:

- User message،
- Document،
- API result،
- Database record،
- Audio stream،
- Camera frame،
- أو Output من Agent أخرى.

تجيب Perception عن:

> ماذا يحدث الآن؟

### 2.2 الاستدلال واتخاذ القرار (Reasoning and decision-making)

يفسر النظام ما أدركه ويختار ما ينبغي فعله بعد ذلك.

قد يقرر:

- الإجابة مباشرة،
- استرجاع مزيد من Information،
- استدعاء Tool،
- سؤال User سؤال Clarifying،
- تفويض Task إلى Agent أخرى،
- أو التوقف لأن Goal اكتملت.

يجيب Reasoning عن:

> بالنظر إلى Goal و Current state، ماذا ينبغي أن يحدث بعد ذلك؟

### 2.3 الفعل (Action)

تحتاج Agent إلى طريقة تؤثر بها في Environment.

توفر Tools هذا الجسر.

أمثلة:

```text
calculator()
search_course_notes()
create_calendar_event()
run_python()
send_request_to_crm()
```

قد تقرر Model نفسها **أي Action مناسب**، لكن Application المحيطة تظل مسؤولة عن التنفيذ الفعلي والمنضبط للـ External actions.

### 2.4 الاستقلالية الموجهة بالهدف (Goal-directed autonomy)

لا يفترض أن تحتاج Agent إلى أن يحدد User كل Intermediate operation يدويًا.

بدلًا من:

```text
1. ابحث في Database هذه.
2. اقرأ Result رقم 4.
3. استدعِ API هذه.
4. نسّق Response.
```

يمكن لـ User تقديم Goal أعلى مستوى:

```text
اعثر على Course material الأكثر صلة واشرح لي Concept.
```

يقرر النظام Intermediate steps.

تعريف مفيد لهذا الدرس هو:

> **AI agent هي System تعتمد على Foundation model، تدرك Environment، وتتخذ Decisions، وتستخدم Tools المتاحة للعمل نحو Goal محددة بدرجة من Autonomy.**

[[IMAGE_NEEDED: Sense-think-act agent loop | A circular diagram with Environment -> Perception -> Foundation Model / Reasoning -> Tool or Action -> Environment, with Goal and Instructions influencing the reasoning step | Learner should notice that an agent is a loop interacting with an environment, not merely a single model response]]

### Model مقابل RAG مقابل Agent

هذه Concepts مرتبطة لكنها ليست قابلة للاستبدال.

| النظام | هل يستطيع Generation؟ | هل يستطيع Retrieval لـ Private context؟ | هل يستطيع تنفيذ External actions؟ |
|---|---:|---:|---:|
| Foundation model | نعم | ليس بمفردها | ليس بمفردها |
| RAG application | نعم | نعم | عادةً ليس مطلوبًا |
| Agent يستخدم الأدوات | نعم | ربما | نعم |
| نظام متعدد الـ Agents | نعم | ربما | نعم، عبر عدة Agents متعاونة |

يمنع هذا التمييز خطأ شائعًا:

> **RAG ليست Agent تلقائيًا. و Tool calling ليست Agent كاملة تلقائيًا أيضًا.**

ينشأ Agentic behavior من Loop الكاملة: Perception و Decision-making و Action و State و Goal pursuit.

## 3. Tools و Function declarations: منح Agent يدين

لنفترض أننا نريد Math Agent تجمع List من Integers.

نحتاج شيئين مختلفين:

1. **Description** تستطيع Model فهمها.
2. **Implementation حقيقية** تستطيع Application تنفيذها.

وهذان ليسا الشيء نفسه.

### 3.1 تعريف Function (Function declaration)

تعمل Declaration مثل User manual صغيرة.

تخبر Declaration الجيدة Model:

- اسم Function،
- ما الذي تفعله Function،
- Inputs التي تتوقعها،
- Input types،
- ما الذي تعيده،
- وأمثلة مفيدة.

على سبيل المثال:

```text
الدالة (Function): add

الغرض (Purpose):
    جمع List من Integers.

المدخل (Input):
    numbers: list[int]

المخرج (Output):
    مجموع Integers.

أمثلة (Examples):
    add([1, 2, 3]) -> 6
    add([-1, 0, 1]) -> 0
    add([]) -> 0
```

لماذا نضيف Examples؟

لأن Examples توضّح نمط الاستخدام الصحيح. ويمكن لمجموعة صغيرة من Demonstrations أن تساعد Model على استنتاج كيفية استدعاء Function.

### Tool مقابل Function

تمييز Formal مفيد هو:

```text
Tool
└── Function declaration واحدة أو أكثر
```

إذًا يمكن لـ Tool أن تكون Container لمجموعة Functions مترابطة.

على سبيل المثال:

```text
أداة الرياضيات (Math Tool)
├── add
├── subtract
├── multiply
└── divide
```

في النقاش اليومي، يستخدم Developers كلمتي *Tool* و *Function* بالتبادل كثيرًا. يصبح التمييز مفيدًا عندما تجمع Tool واحدة عدة Related actions.

### 3.2 Declarations القابلة للقراءة بشريًا مقابل Machine-readable

تكون Declaration شبيهة بـ Docstring سهلة القراءة للبشر.

لكن Production systems تحتاج غالبًا Structured schema أيضًا.

مفاهيميًا:

تقلل Structured formats الغموض ويسهل على Software التحقق منها و Parsing لها.

يستخدم المصدر المقدَّم تمثيلًا OpenAPI/JSON-style، ثم يوضح كيف تستطيع SDK تغليف Function declaration داخل Tool object.

قد يختلف Format بين SDKs، لكن Engineering principle ثابت:

> تحتاج Model إلى Structured description للـ Action قبل أن تستطيع طلب هذا Action بذكاء.

- نجحت Function،
- فشلت،
- أعادت Value،
- أو رفضت Application الـ Request.

```text
2. تقرر Model

6. تقرر Model مرة أخرى
```

### الاستدعاء التلقائي للـ Functions (Automatic function calling)

يمكن لبعض SDKs أتمتة أجزاء من هذه Cycle.

يمكن أن يقلل ذلك Code بدرجة كبيرة، لكن ما يزال ينبغي فهم Manual version لأنها تكشف:

- أين تنتمي Validation،
- أين ينتمي Authorization،
- أين يمكن أن تحدث Failures،
- وأي Component تنفذ Side effects فعليًا.

### نشر Agent منفصل عن Agent logic

Execution loop هي Application logic.

يمكن استضافتها بعدة طرق:

- Local أثناء Development،
- على Virtual machine،
- داخل Container،
- على Kubernetes،
- أو عبر Serverless infrastructure.

تغيير Deployment لا يغير Sense-decide-act loop الأساسية.

## 5. Multi-turn agents والذاكرة

تكون Single-turn agent مفيدة، لكن Conversation حقيقية تعتمد على State.

تأمل:

```text
المستخدم: كم يساوي 100 + 50؟
الوكيل: 150.
المستخدم: الآن اضرب الناتج في 2.
```

إلى ماذا تشير كلمة **that**؟

إنها تشير إلى Result السابقة: 150.

من دون Interaction السابقة، تكون Request الثانية غير مكتملة.

### 5.1 الذاكرة قصيرة المدى (Short-term memory)

Short-term memory هي Current conversation/session context.

يمكن أن تتضمن:

- User messages،
- Model replies،
- Tool requests،
- Tool results،
- Relevant media references،
- State أُنشئت أثناء Session.

قد يبدو History مبسط هكذا:

⟦CODE_6⟧

في كل Step، تفحص Model الـ Available history وتقرر هل:

1. تستدعي Tool أخرى،
2. تسأل User عن Information مفقودة،
3. أو تنتج Final answer.

### الطلبات متعددة الخطوات (Multi-step requests)

تكون Multi-turn loop مفيدة أيضًا عندما تحتوي User request واحدة عدة Operations:

```text
اطرح 10 من 50، ثم اقسم الناتج على 4.
```

تنفيذ محتمل:

```text
subtract(50, 10) -> 40    # استدعاءات الأدوات بالترتيب
divide(40, 4) -> 10
final answer -> 10
```

تصبح Intermediate result جزءًا من Working state.

### 5.2 أين يمكن أن تعيش Short-term memory

تشمل Approaches الشائعة:

| Storage | مناسب لـ | القيد الأساسي |
|---|---|---|
| In-memory variable | Local scripts و Prototypes | تُفقد عند انتهاء Process |
| Database | Production sessions دائمة | Operational overhead أكبر |
| Cache مثل Redis | Session state سريعة | تحتاج Retention strategy |
| تخزين من جهة العميل | تقليل حالة الجلسة على الخادم | تحكم أقل من Server وسعة محدودة |
| سجلات/تخزين سحابي | سجل تشغيلي و Artifacts أكبر | يجب التعامل مع Privacy و Retrieval بعناية |

في Multimodal applications، غالبًا تُخزن Media كبيرة مثل Audio أو Video بصورة منفصلة، بينما تخزن Conversation state References و Metadata.

### 5.3 الذاكرة طويلة المدى (Long-term memory)

تجيب Short-term memory عن:

> ماذا حدث في هذه Conversation؟

وتجيب Long-term memory عن:

> ما Information المفيدة التي ينبغي أن تستمر عبر Conversations؟

أمثلة:

- User preference،
- Project fact ثابتة،
- Summary مهمة،
- Constraint متكررة،
- أو Interaction سابقة أصبحت Relevant من جديد.

تشمل Storage strategies الممكنة:

**Vector databases**  
تخزن Embeddings وتسترجع Memories المرتبطة Semantic.

**Graph databases**  
تمثل Relationships مثل Users و Projects و Topics و Purchases أو Entities.

**قواعد البيانات التقليدية/تخزين الكائنات**  
تحافظ على Structured data أو Complete historical records.

ينبغي ألا تعني Long-term memory "تخزين كل شيء إلى الأبد".

يحتاج Production system إلى Decisions حول:

- ما الذي يستحق التذكر،
- Consent،
- Retention،
- Deletion،
- Access control،
- ومتى يكون Memory آمنًا لإعادة الاستخدام.

### 5.4 منع Infinite loops

يمكن أن تعلق Multi-turn execution loop.

على سبيل المثال:

```text
Tool A -> Result
Model -> Tool A مرة أخرى
Tool A -> Result مشابهة
Model -> Tool A مرة أخرى
...
```

Guardrail عملية هي Maximum iteration count.

⟦CODE_7⟧

يعتمد الرقم الدقيق على Application.

المبدأ عام:

> تحتاج Autonomous loop إلى Stopping policy.

ينبغي أيضًا تسجيل Operational metrics مثل:

- Tool-call count،
- Latency،
- Token usage،
- Failures،
- Retries،
- إجمالي وقت التنفيذ (Total execution time).

تساعد هذه Measurements في Debugging و Cost control و Optimization.

## 6. Agents تستدعي Agents

لماذا لا نبني Agent عملاقة واحدة تمتلك كل Capability ممكنة؟

لأن Monolithic agent قد تضطر إلى:

- Reasoning عبر Tools كثيرة جدًا،
- معالجة Instructions غير ذات صلة،
- الاحتفاظ بـ Context أكبر من اللازم،
- التعامل مع Domains غير مترابطة،
- و Debugging لمسارات Interaction كثيرة.

توفر Specialization خيارًا آخر.

### نموذج Specialist

تخيل Educational system:

```text
Student
   ↓
موجّه التعليم (Teaching Router)
   ├── Math Agent
   ├── History Agent
   └── Grammar Agent
```

يركز Router أساسًا على تحديد وجهة Work.

يمتلك كل Specialist:

- Narrow instructions،
- Limited tools،
- Relevant knowledge،
- Responsibility محددة بوضوح.

يشبه ذلك Microservice architecture: قسّم مشكلة كبيرة إلى Components أصغر لها Responsibilities صريحة.

### خمسة أنماط Collaboration شائعة

#### 6.1 نمط Router

```text
المستخدم
 ↓
الموجِّه (Router)
 ├─> متخصص A
 ├─> متخصص B
 └─> متخصص C
```

يختار Router الـ Specialist المناسب وقد يدمج Result.

استخدمه عندما تنتمي Requests إلى Domains منفصلة.

#### 6.2 النمط المتوازي (Parallel)

```text
          ┌─> وكيل الطيران ─┐
المستخدم ────>├─> وكيل الفنادق  ─┼─> المُجمِّع
          └─> وكيل الفعاليات ─┘
```

تعمل Independent tasks بصورة Concurrent.

استخدمه عندما لا تعتمد Subtasks على بعضها.

الفائدة هي تقليل Total latency.

#### 6.3 النمط المتسلسل (Sequential)

```text
وكيل الاستيعاب
      ↓
وكيل التنظيف
      ↓
وكيل التحليل
      ↓
وكيل التقارير
```

تعتمد كل Step على Previous output.

استخدمه للـ Predictable pipelines.

#### 6.4 النمط الدائري (Circular)

```text
الكاتب -> المحرر
  ↑        ↓
  └────────┘
```

تحسن Agents الـ Artifact بصورة تكرارية.

استخدمه لـ Iterative improvement.

ما تزال تحتاج إلى Stopping condition، وإلا فقد تستمر Collaboration إلى ما لا نهاية.

#### 6.5 النمط الديناميكي (Dynamic)

```text
وكيل A <--> وكيل B
   ^  \       /  ^
   |   \     /   |
   v    v   v    v
وكيل C <--> وكيل D
```

لا يوجد Route ثابت وحيد. تتواصل Agents وفق State الخاصة بالـ Task.

هذا Flexible لكنه أصعب كثيرًا في Reasoning و Debugging.

[[IMAGE_NEEDED: Five multi-agent orchestration patterns | One figure containing Router, Parallel, Sequential, Circular, and Dynamic patterns with small labeled node-and-arrow diagrams | Learner should compare how control flow differs across the five designs]]

### الفكرة الموحدة الأساسية

يمكن لـ Agent التعامل مع Agent أخرى باعتبارها Specialized capability.

من منظور Caller، قد يشبه ذلك Tool call:

```text
"أحتاج خبرة رياضية"
        ↓
استدعاء Math Agent
        ↓
استلام Result
        ↓
متابعة Reasoning
```

يجعل ذلك Complex systems أكثر Modular.

## 7. توسيع Perception إلى ما بعد Text

حتى الآن، تستطيع Agent إدراك Text و Structured information.

لكن Real world تحتوي أكثر بكثير من Text.

الـ **Modality** هي نوع Signal أو Communication channel.

تشمل Examples:

- Text،
- Audio،
- Images،
- الفيديو (Video).

تستطيع Multimodal agent استخدام أكثر من Modality واحدة داخل Task نفسها.

### عنق الزجاجة النصي (Text bottleneck)

Text فعالة، لكن تحويل كل شيء إلى Text يمكن أن يفقد Information.

لنفترض أن شخصًا يقول:

```text
"يا للروعة. إنها تمطر مجددًا."
```

يلتقط Transcript الكلمات.

لكنه قد يفشل في الحفاظ على:

- Sigh،
- Sarcasm،
- Stress غير عادي،
- Speaking speed،
- Background rain،
- أو Sound أخرى تحدث في الوقت نفسه.

تخيل الآن UI-debugging agent.

قد يحتاج User إلى شرح:

```text
الزر الثالث من الأعلى أخفض ببضع بكسلات من الزر المجاور له.
```

بينما يمكن لـ Visual model فحص Interface مباشرة.

المشكلة نفسها:

> عندما يضطر الناس إلى تحويل Sensory information إلى Text، قد يختفي جزء من Original signal.

### Multimodal perception تغير Agent loop

قد تدرك Text agent:

```text
prompt المستخدم + المستندات المسترجعة + نتائج API
```

أما Multimodal agent فقد تدرك:

```text
الكلام + صورة/إطار + نص + نتيجة أداة + حالة المحادثة
```

يجعل ذلك Perception stage أغنى، لكنه يقدم أيضًا Engineering concerns جديدة:

- Bandwidth،
- Synchronization،
- Media quality،
- Latency،
- Privacy،
- إدارة Context (Context management).

## 8. Cascaded voice systems مقابل Live multimodal interfaces

قبل Live multimodal systems، استخدمت Voice applications عادة Cascade.

### المسار المتسلسل (Cascaded pipeline)

Voice pipeline حديثة مبسطة هي:

```text
الميكروفون
   ↓
ASR / تحويل الكلام إلى نص
   ↓
نموذج نصي
   ↓
استجابة نصية
   ↓
TTS / تحويل النص إلى كلام
   ↓
مكبّر الصوت
```

هذه Architecture صحيحة ويمكن أن تعمل جيدًا جدًا.

المشكلة الأساسية هي أن لكل Boundary تكلفة.

### التكلفة 1 — Latency

قد يحتاج النظام إلى:

1. جمع مقدار كافٍ من Audio،
2. التعرف على Speech،
3. إرسال Text إلى Model،
4. انتظار Model output،
5. توليد Speech،
6. بدء Playback.

يمكن لـ Streaming تقليل Delay، لكن تظل Components متعددة منسقة معًا.

### التكلفة 2 — فقدان المعلومات (Information loss)

عندما تُختزل Audio إلى Text، قد لا يتلقى Downstream reasoning system كل Acoustic cues المفيدة.

يركز Transcript على Linguistic content.

قد تحتوي Original signal أيضًا على:

- Timing،
- Pitch،
- Stress،
- Emotion-related cues،
- Environmental sound،
- Overlap،
- الصمت (Silence).

### واجهة Live multimodal

يصف المصدر المقدَّم Developer-facing model تستطيع فيها Live session قبول خليط من:

- Continuous audio،
- Text،
- Sampled visual frames،

مع إعادة Streamed responses و Structured events.

مفاهيميًا:

```text
Audio ───────────┐
Images/frames ───┼──> جلسة Live multimodal ──> Audio/Text/Tool events
Text ────────────┘
```

النقطة المهمة ليست اختراع Hidden internal architecture.

الادعاء الهندسي المفيد يتعلق بالواجهة:

> لا تحتاج Application دائمًا إلى تحويل كل Input إلى Text transcript واحدة قبل أن تستطيع Model استخدامها.

يغير ذلك Design question.

بدلًا من السؤال:

> كيف أحول كل Signal إلى Text؟

يمكنك أن تسأل:

> أي Signals مفيدة، ومتى ينبغي إرسالها، وكيف أحافظ على Context التي تربطها؟

## 9. Tokens و Embeddings و Shared representations

كيف يمكن لـ Model واحدة العمل مع Inputs مختلفة إلى هذا الحد؟

نحتاج إلى Conceptual model.

### 9.1 النص (Text)

لا تقرأ Models الـ Text ببساطة على شكل Human words كاملة.

تحول Tokenizer الـ Text إلى Units تُسمى **Tokens**.

قد تمثل Token:

- Word،
- جزءًا من Word،
- Punctuation،
- Whitespace،
- أو Learned unit أخرى.

تُحوّل Token IDs إلى Vectors.

تسمى هذه Vectors **Embeddings**.

الـ Embedding هي Learned numerical representation يمكن لـ Model استخدامها في Computation.

### 9.2 الصور (Images)

تحتاج Raw pixel grids أيضًا إلى التحول إلى Model-readable representations.

نموذج مفيد من Vision Transformers هو:

```text
Image
 ↓
تقسيمها إلى Patches
 ↓
إسقاط Patches إلى Vectors
 ↓
معالجة Sequence
```

يستخدم Teaching example شائع Patches بحجم 16×16، رغم أن Real systems قد تستخدم Strategies مختلفة.

تُسمى هذه Vectors أحيانًا **Visual tokens**.

لا تتعامل مع هذه العبارة حرفيًا أكثر من اللازم.

الفكرة المفيدة هي:

> تتحول Image إلى Sequence من Learned representations تستطيع Model تنفيذ Reasoning عليها.

### 9.3 الصوت (Audio)

تبدأ Audio كـ Waveform.

تأخذ Digital audio عينات من هذه Waveform عبر الزمن.

يمكن للأنظمة اشتقاق Features مرتبطة بـ:

- Frequency،
- Timing،
- Energy،
- Pitch،
- Acoustic patterns أخرى.

يمكن لـ Modern models تحويل Signal إلى Learned audio representations مفيدة لـ Downstream reasoning.

### 9.4 مساحات Representation مشتركة أو متوافقة

بمجرد أن تتحول Modalities المختلفة إلى Learned representations، تستطيع Model تعلم Relationships بينها.

مثال تاريخي مفيد هو CLIP.

دُرّبت Image encoder و Text encoder فيه بحيث تصبح Matching image-text pairs أقرب داخل Representation space، بينما تصبح Mismatched pairs أبعد.

مفاهيميًا:

```text
صورة دراجة  ──قريبة──  "a bicycle"
صورة دراجة  ──بعيدة──  "a bowl of soup"
```

يوضح CLIP فكرة Cross-modal alignment.

تحتاج Live multimodal agent إلى Capability أوسع لأنها قد تحتاج إلى دمج:

- Speech،
- Visual context،
- Conversation state،
- Text،
- نتائج Tools (Tool results).

[[IMAGE_NEEDED: From raw modalities to learned representations | A diagram with Text -> Tokens/Embeddings, Image -> Patches/Visual Representations, and Audio -> Acoustic Features/Audio Representations, all feeding a shared reasoning context | Learner should notice that raw media is transformed before cross-modal reasoning occurs]]

### حدّ مهم لفهمنا (A careful boundary)

تُعد Tokens و Embeddings و Attention مفاهيم تعليمية مفيدة.

لكن لا ينبغي التعامل معها على أنها خريطة كاملة للـ Hidden internals الخاصة بـ Proprietary model.

يفصل الشرح الهندسي الجيد بين:

```text
ما تضمنه Public interface
        وبين
Conceptual model التي نستخدمها
        وبين
ما تفعله Proprietary implementation داخليًا فعليًا
```

## 10. منح Agent أذنين

تضيف Audio أكثر من Transcript.

### 10.1 رقمنة الصوت (Digitizing sound)

الصوت Pressure wave.

يقيس Digital system هذه Wave عدة مرات في الثانية ويمثل تلك Measurements رقميًا.

تشير المادة المقدَّمة إلى Implementation path لاحقة ترسل Raw PCM microphone audio مع Sample rate معلنة 16 kHz.

الفكرة المهمة في هذا الدرس أوسع:

```text
الصوت الفيزيائي (physical sound)
    ↓
عينات رقمية (digital samples)
    ↓
تمثيل صوتي (acoustic representation)
    ↓
Reasoning بواسطة Model
```

### 10.2 ما الذي تقدمه ASR

تركز Automatic Speech Recognition على تحويل Speech إلى Text.

وتكون Transcript مفيدة جدًا في:

- Captions،
- Logs،
- Indexing،
- Search،
- Auditing،
- أنظمة Downstream المعتمدة على Text.

لكن Transcription قد لا تحافظ على كل Non-verbal information.

### 10.3 ما الذي تضيفه Direct audio context

اعتمادًا على Model و Configuration المختارة، يمكن لـ Audio الحفاظ على Cues مرتبطة بـ:

**Prosody**  
Rhythm و Stress و Intonation و Pacing.

**Environmental context**  
Non-speech events مثل Music و Alarms و Background conversation أو Machinery.

**Multilingual conversation**  
قد تدعم Live audio interfaces تبديل Languages من دون فرض Transcription language ثابتة واحدة، لكن Performance تعتمد على Model الفعلية و Language و Accent و Audio quality و Deployment settings.

### 10.4 إخراج Audio أصلي (Native audio output)

غالبًا ينفذ Traditional system:

```text
نص النموذج -> TTS -> كلام
```

يمكن لـ Live audio model عرض Streamed speech output عبر Model interface.

ومن منظور Application، يمكن أن ينشئ ذلك Conversational loop أكثر إحكامًا.

لكن لا تفترض أن كل Advanced audio behavior معلنة متاحة على كل Model.

يجب التحقق من Model-specific capabilities للـ API و Model المحددتين فعليًا في Production.

## 11. منح Agent عينين

تضيف Images معلومات Spatial يصعب على Text وصفها أحيانًا.

### 11.1 من CNNs إلى Multimodal visual reasoning

ما تزال Convolutional Neural Networks مهمة في Computer vision.

فهي تكتشف Local visual patterns عبر Learned filters.

لكن Multimodal agent تحتاج غالبًا أكثر من Classification.

قد تحتاج إلى:

- قراءة Visible text،
- تحديد Object،
- الإجابة عن سؤال حول Region،
- فهم Layout،
- ربط Spoken instruction بعنصر مرئي،
- أو تحديد أن Visual evidence تتطلب Tool call.

### 11.2 قدرات Visual reasoning

قد يدعم Multimodal system مهام مثل:

**فهم Text المرئي (Visible text understanding)**  
قراءة Text الموجودة داخل Image.

**الاستدلال المكاني (Spatial reasoning)**  
فهم Relationships مثل Left/Right و Alignment و Connection أو Position.

**فهم المشهد (Scene understanding)**  
دمج Objects و Layout و Labels و User intent.

يمكن لنظام OCR أو Computer-vision مخصص أن يظل مفيدًا في Production.

لا تلغي Multimodal models الأدوات المتخصصة.

### 11.3 حدود الرؤية (Visual limitations)

قد تتدهور Vision performance بسبب:

- Small text،
- Poor lighting،
- Motion blur،
- Low resolution،
- Compression،
- Occlusion،
- فقدان تفاصيل مرئية (Missing visual detail).

وقد تزيد Visual detail الأكبر أيضًا:

- Token usage،
- Bandwidth،
- Latency،
- التكلفة (Cost).

إذًا Visual quality هي Engineering trade-off، وليست ببساطة "المزيد أفضل".

### 11.4 Video هي Images + Time

قد يحتوي Video عشرات Frames كل ثانية.

إرسال كل Frame إلى Model غالبًا غير ضروري.

Approach عملية لـ Live agent هي **Frame sampling**.

بدلًا من:

```text
30 أو 60 Frames كل ثانية
```

قد تختار Application Frames بصورة دورية.

ينص المصدر المقدَّم على أن Live API path الحالية فيه تستخدم JPEG/PNG frames بحد أقصى Frame واحدة في الثانية.

تعامل مع هذا كـ Implementation-specific constraint من المادة المقدَّمة، وليس Rule دائمة لكل Multimodal APIs.

تكون Frame sampling مفيدة لمهام مثل:

- سؤال "What am I looking at?"
- سؤال "Which button should I press?"
- سؤال "Does this chart match the report?"

وهي غير مناسبة جيدًا للمهام التي تتطلب:

- Precise high-speed motion analysis،
- Frame-by-frame sports analysis،
- Exact gesture timing،
- أو Visual signals سريعة التغير.

## 12. Multimodal fusion: ربط ما يقصده User

امتلاك Inputs متعددة لا يكفي.

يجب على النظام ربطها معًا.

تخيل:

1. يوجه User الكاميرا نحو Circuit board.
2. يشير User إلى Component تالفة.
3. يسأل User: "What is this part?"

Speech وحدها غير مكتملة.

```text
"ما هذا الجزء؟"
```

ماذا تعني كلمة **this**؟

Image وحدها أيضًا غير مكتملة.

يمكن لـ Model رؤية Components كثيرة، لكنها لا تعرف تلقائيًا أي واحدة يقصدها User.

تأتي القيمة من دمج Signals.

```text
المرجع المنطوق + المشهد البصري + سياق التفاعل
                       ↓
                المقصود بالإشارة
```

هذا هو **Multimodal fusion**.

### Attention كتفسير مفاهيمي

في Transformer، تساعد Attention على ربط أجزاء Information.

ولأغراض التعليم يمكن توسيع Intuition:

- Spoken phrase،
- Visible region،
- Gesture،
- Context الخاصة بالمحادثة السابقة (Previous conversation context)

يمكن لكل منها التأثير في الآخر أثناء Reasoning.

لا تخلط بين ذلك وبين امتلاك Access إلى Exact internal attention maps الخاصة بـ Proprietary model.

الدرس المعماري أبسط:

> يمكن لـ Cross-modal context الحفاظ على Relationships تضيع عندما تُعالج كل Modality بصورة مستقلة.

## 13. Multimodal output واستخدام Tools

Multimodality لا تتعلق بالـ Input فقط.

قد تنتج Agent مخرجات لجمهورين مختلفين تمامًا.

### 13.1 المخرجات الموجهة للبشر (Human-facing outputs)

هذه مخرجات مخصصة لشخص.

أمثلة:

- Spoken response،
- Text،
- Image،
- Visual highlight،
- Chart،
- طبقة واجهة مرئية (UI overlay).

تخيل Dashboard assistant.

يسأل User:

> أي مقياس تغيّر أكثر منذ الأمس؟

قد تقوم Interface مفيدة بـ:

1. الإجابة بصوت،
2. Highlight للـ Chart ذات الصلة،
3. وترك Text summary قصيرة.

استخدام Modalities أكثر ليس دائمًا أفضل تلقائيًا.

أفضل Output هي التي تقلل Ambiguity وتناسب Task.

### 13.2 المخرجات المهيكلة الموجهة للآلة (Machine-facing structured outputs)

هذه مخرجات مخصصة للـ Software.

على سبيل المثال، قد تنتج Agent تفحص Analog gauge:

⟦CODE_8⟧

أو قد تحول Scheduling agent الـ Speech + Visible calendar context إلى Tool arguments.

يعيد ذلك ربط Multimodal perception بـ Execution loop:

```text
Audio/Image/Text
      ↓
Multimodal reasoning
      ↓
Structured tool request
      ↓
تتحقق Host application
      ↓
تنفذ Tool
      ↓
تعود Result إلى Model
      ↓
Human-facing answer
```

لم يتغير Execution boundary.

حتى داخل Multimodal agent:

> **يمكن لـ Model طلب Action؛ وتظل Host application مسؤولة عن التنفيذ الآمن.**

## 14. تصميم Multimodal agent موثوقة

الجمع بين Agents و Multimodality ينشئ System قوية، لكنه يوسّع أيضًا مساحة الفشل.

### 14.1 التحقق من Tools (Tool validation)

لا تتعامل مع Model-generated arguments بوصفها موثوقة تلقائيًا.

تحقق من:

- Function name،
- Schema،
- Data type،
- Range،
- Authorization،
- الآثار الجانبية (Side effects).

للعمليات Sensitive، أضف Explicit confirmation أو Policy checks.

### 14.2 حدود Loop

ينبغي أن تحتوي كل Autonomous loop على Stopping rule.

تشمل Controls الممكنة:

```text
الحد الأقصى للخطوات (maximum steps)
الحد الأقصى للمحاولات (maximum retries)
الحد الأقصى لوقت التنفيذ (maximum execution time)
الحد الأقصى لاستدعاءات Tools (maximum tool calls)
حد Budget/Tokens
```

### 14.3 الخصوصية والموافقة (Privacy and consent)

تلتقط Microphones و Cameras معلومات حساسة من Environment.

ينبغي لـ Production application أن تجعل Recording state واضحة وأن تحدد:

- متى يبدأ Capture،
- ما الذي يُنقل،
- ما الذي يُخزن،
- مدة Retention،
- من يستطيع الوصول إليه،
- وكيف يمكن لـ Users إيقافه أو حذفه.

### 14.4 جودة Media

يعتمد Multimodal reasoning على جودة Signal.

راقب:

- Noisy microphones،
- Poor lighting،
- Tiny text،
- Weak network connections،
- Compression artifacts،
- Video ذات Sampling سيئة.

### 14.5 Latency

تملك Real-time experience ميزانية Latency.

قد تأتي Latency من:

```text
الالتقاط
+ النقل عبر الشبكة
+ معالجة النموذج
+ تنفيذ الأداة
+ أدوار إضافية للنموذج
+ تشغيل الوسائط
```

لذلك يحتاج Agent design إلى Architectural choices، وليس مجرد Prompt جيدة.

### 14.6 قابلية المراقبة (Observability)

سجّل ما يكفي لفهم System من دون انتهاك Privacy.

تشمل Operational information المفيدة:

- Session duration،
- Model latency،
- Tool latency،
- Number of tool calls،
- Error type،
- Token usage،
- Retries،
- User interruptions،
- عدد خطوات Agent (Agent step count).

### 14.7 ما يزال الحكم البشري مهمًا

قد تجعل Multimodal perception الـ Agent تبدو أكثر قدرة لأنها تستطيع الرؤية والسماع.

هذا لا يجعل استنتاجاتها معصومة.

ما تزال High-risk domains تتطلب:

- Validation،
- Appropriate safety policies،
- Constrained tools،
- Human oversight عند الحاجة.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> "إذا استطاعت LLM استدعاء Function، فهي تنفذ Python code الخاصة بي مباشرة."

### لماذا هذا خطأ

في Manual function-calling model التي يشرحها هذا الدرس، تنتج Foundation model Structured request. تقوم Host application بربط هذا Request بـ Executable code حقيقية وتقرر هل تنفذها.

---

### المفهوم الخاطئ 2

> "RAG و Agents هما الشيء نفسه."

### لماذا هذا خطأ

توفر RAG Relevant context. أما Agent فتتخذ Decisions أيضًا ويمكنها تنفيذ Actions عبر Tools أثناء متابعة Goal.

يمكن أن تكون RAG Component داخل Agent.

---

### المفهوم الخاطئ 3

> "Memory تعني إرسال كل Conversation سابقة إلى Model إلى الأبد."

### لماذا هذا خطأ

تحل Short-term session history و Durable long-term memory مشكلات مختلفة. وتحتاج Production systems إلى Retrieval و Summarization و Retention rules و Privacy controls.

---

### المفهوم الخاطئ 4

> "Multi-agent system أفضل دائمًا من Agent واحدة."

### لماذا هذا خطأ

تضيف Multi-agent systems تعقيد Communication و Coordination و State و Debugging. استخدم Specialization عندما تستفيد المشكلة من Decomposition.

---

### المفهوم الخاطئ 5

> "Multimodal تعني تحويل Audio و Images إلى Text أولًا."

### لماذا هذا خطأ

هذه Architecture ممكنة، لكن Modern live multimodal interfaces تستطيع عرض Audio و Images/Frames و Text داخل Interaction loop نفسها.

---

### المفهوم الخاطئ 6

> "إذا استطاعت Model رؤية Image، فهي ترى بصورة مثالية."

### لماذا هذا خطأ

يمكن لـ Resolution و Compression و Lighting و Motion و Occlusion و Tiny text كلها تقليل Visual accuracy.

---

### المفهوم الخاطئ 7

> "المزيد من Modalities ينتج Product أفضل دائمًا."

### لماذا هذا خطأ

تضيف كل Modality تكلفة و Bandwidth و Latency و Privacy concerns و Interface complexity. استخدم Modalities التي تحسن Task فعليًا.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Agent | System موجهة بالهدف تدرك وتقرر وتستخدم Actions/Tools المتاحة |
| Foundation Model (FM) | General-purpose model تستطيع دعم Downstream tasks كثيرة |
| LLM | Foundation model تركز بقوة على Language processing/generation |
| RAG | Retrieval-Augmented Generation؛ يوفر Retrieval Context خارجية ذات صلة للـ Generation |
| الإدراك (Perception) | Information التي تتلقاها Agent من Environment |
| Tool | Capability مجمعة ومتاحة لـ Agent |
| Function declaration | Structured description لـ Executable function متاحة لـ Model |
| Function call | Structured model request يطلب من Application استدعاء Function |
| Execution boundary | الفصل بين Action التي تطلبها Model وتنفيذ Host application |
| Agent loop | Cycle متكررة من Perceive/Decide/Act/Update |
| memory قصيرة المدى | الحالة/السجل المستخدمان داخل Conversation أو Session نشطة |
| memory طويلة المدى | معلومات تُخزن وتُسترجع عبر Sessions |
| نظام متعدد الـ Agents | عدة Specialized agents تتعاون في Task أكبر |
| Router pattern | Coordinator يفوض Tasks إلى Specialists المناسبة |
| Parallel pattern | Agent tasks مستقلة تعمل Concurrently |
| Sequential pattern | Output من Agent تغذي Agent التالية |
| Circular pattern | Agents تمرر Results تكراريًا داخل Feedback loop |
| Dynamic pattern | Agents تتواصل بمرونة دون Control path ثابتة واحدة |
| Modality | Data أو Communication channel مثل Text أو Audio أو Image أو Video |
| ASR | Automatic Speech Recognition؛ تحول Speech إلى Text |
| TTS | Text-to-Speech؛ تولد Speech من Text |
| Token | Model-processing unit مشتقة من Input data مثل Text |
| التمثيل المتجهي (Embedding) | Learned vector representation — تمثيل Vector متعلم |
| رمز/تمثيل بصري | تمثيل متجهي مشتق من محتوى الصورة |
| Prosody | Rhythm و Stress و Pitch و Timing و Intonation في Speech |
| Frame sampling | اختيار Frames دورية من Video بدلًا من معالجة كل Frame |
| Multimodal fusion | دمج Information من Modalities متعددة داخل Reasoning context واحدة |
| مخرجات موجهة للإنسان | Output مخصصة لكي يقرأها User أو يسمعها أو يراها |
| مخرجات موجهة للآلة | Structured output مخصصة للـ Software أو Tool execution |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما Capability التي تفصل Tool-using agent عن Plain foundation-model chatbot؟
2. ماذا تضيف RAG، وماذا لا تضيف تلقائيًا؟
3. لماذا تختلف Function declaration عن Real function implementation؟
4. من ينفذ Tool call فعليًا؟
5. لماذا يجب إعادة Tool result إلى Model؟
6. ما الاختيارات الثلاثة التي تتخذها Multi-turn agent غالبًا بعد مراجعة State؟
7. كيف تختلف Short-term memory عن Long-term memory؟
8. لماذا يمكن أن تصبح Monolithic agent صعبة الصيانة؟
9. متى تختار Parallel orchestration بدلًا من Sequential orchestration؟
10. لماذا يمكن أن يصبح Text عنق زجاجة لمعلومات Audio و Visual؟
11. ما العيوب الأساسية لـ Cascaded voice pipeline؟
12. ما هي Embedding؟
13. لماذا يكون Patch-based explanation مفيدًا لفهم Image representations؟
14. لماذا لا تحتاج Live video agent عادةً كل Camera frame؟
15. ما المشكلة التي يحلها Multimodal fusion؟
16. لماذا ينبغي أن تظل Capability claims الخاصة بـ Proprietary multimodal model مرتبطة بالـ API/Model التي تم اختبارها؟
17. لماذا تزيد Microphones و Cameras عبء Privacy في AI application؟
18. ما Safeguards التي ستضيفها قبل السماح لـ Agent بتنفيذ Destructive tool؟

## احتفظ بهذه الفكرة

**Modern AI agent ليست مجرد Language model مع Prompt ذكية. إنها Loop مضبوطة تدرك فيها Foundation model الـ Context، وتقرر ما ينبغي أن يحدث لاحقًا، وتطلب Tools عندما يلزم Action، وتتلقى Results، وتواصل العمل نحو Goal. توسع Memory هذه Loop عبر Turns، وتقسمها Multi-agent systems بين Specialists، وتوسع Multimodality الـ Perception إلى ما وراء Text لتشمل Signals مثل Audio و Vision.**
