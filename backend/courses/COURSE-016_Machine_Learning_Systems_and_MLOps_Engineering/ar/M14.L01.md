## 1. تخفي Azure ML صعوبة Infrastructure خلف Interfaces متعددة

يفتتح الفصل بمثال عملي: نشر Machine-learning model على Kubernetes يُعد عادةً مشكلة Infrastructure صعبة.

يمكن لـ Azure ML تقليل هذا التعقيد إلى اختيار Cluster مُعدة مسبقًا بوصفها Deployment target.

وتوفر Platform الأوسع عدة طرق للعمل:

- واجهة Azure ML Studio،
- واجهة Designer،
- دفاتر Jupyter Notebooks،

- واجهة CLI،

هذه المرونة مهمة لأن فرق MLOps لا تعمل كلها بالطريقة نفسها.

## 3. Authentication جزء أساسي من Automation وليست عقبة ينبغي إزالتها

يحذر الفصل بشدة من "إصلاح" Automation عبر إضعاف Permissions.

تشمل الاختصارات الخطرة:

- استخدام Account شبيهة بـ Root وتمتلك صلاحيات كاملة لمجرد سهولة ذلك،
- جعل Resources قابلة للقراءة أوالكتابة عالميًا،
- إزالة Authentication من Test systems فقط لتسهيل Development.

قد تزيل هذه الطرق Error فورية لكنها تنشئ مشكلة Security أخطر بكثير.

القاعدة التشغيلية هي:

> **نفّذ Automation للـ Authentication بصورة صحيحة. لا تنفذ Automation عبر إزالة Security constraints.**

[[IMAGE_NEEDED: Secure automation versus permission bypass | Two paths: service identity with scoped permissions versus a shortcut using overly broad permissions, with the second path leading to security exposure | Learner should notice that convenience and secure automation are not the same thing]]

## 8. اختر Deployment style من سلوك Inference

يميز الفصل بين حاجتين في Deployment.

### الاستدلال الدفعي (Batch Inference)

يسمح ذلك للفريق باستثمار مزيد من الجهد في Data quality وDeployment robustness.

## 11. Versioning الخاصة بـ Dataset لا تقل أهمية عن Model versioning

لا تتناسب Large datasets طبيعيًا مع Git-style source control.

لكن ML القابلة لإعادة الإنتاج تتطلب معرفة أي Data version أنتجت أي Model.

تعالج Azure dataset versioning هذه المشكلة عبر السماح بتسجيل Dataset وتعيين Versions لها.

يشدد المصدر على أن Data غالبًا ما تتغير عبر عدة Stages:

```text
Data خام (Raw data)
   ↓
تنظيف (cleaning)
   ↓
تحويل (transformation)
   ↓
Data جاهزة للـ Training (training-ready data)
```

يجعل Versioning هذه التحولات قابلة للتتبع.

ويشير المصدر أيضًا إلى أن Azure dataset version الجديدة يمكن أن تشير إلى Storage بدل نسخ Dataset ضخمة كاملة إلى Workspace.

## 12. ينبغي أن يطابق Training compute الـ Workload لا حدًا أقصى عشوائيًا

ينشئ الفصل Compute كجزء من AutoML run.

تشمل قرارات Cluster المهمة:

- نوع Machine،
- قدرة RAM/CPU،
- الحد الأدنى من Nodes،
- الحد الأقصى من Nodes،
- درجة Parallelism.

لا يمكن أن يتجاوز Maximum number of parallel runs عدد Maximum nodes المتاحة في Cluster ضمن Example المصدر.

يُعرض Sizing بوصفه Process تجريبية: ابدأ بموارد متواضعة وزدها عند الحاجة.

يستخدم Example حدًا أدنى من Nodes يساوي صفرًا لتجنب الدفع مقابل Idle nodes عندما لا تُستخدم Cluster.

## 13. Training compute وInference compute اهتمامان مختلفان

يحذر الفصل من أن كلمة **Cluster** قد تسبب Confusion.

Cluster المستخدمة في Training ليست بالضرورة Infrastructure نفسها المستخدمة لخدمة Live أوBatch predictions.

لهذه Workloads أنماط موارد مختلفة:

- قد يعطي Training الأولوية لـ Parallel model fitting وThroughput،
- قد يعطي Online inference الأولوية لـ Latency وAvailability،
- قد يعطي Batch inference الأولوية لـ Large-scale throughput على Immediate response.

لذلك ينبغي لتصميم MLOps اختيار Compute بناءً على Stage من Lifecycle.

## 16. تشير HTTP errors غالبًا مباشرةً إلى انتهاكات Contract

يعرض الفصل عدة Failure types شائعة.

### Input غير صالح للـ Model (Invalid Model Input)

قد تفشل Runtime لأن Required model input مفقودة.

### Content type خاطئ (Wrong Content Type)

قد ترفض Service طلبًا Body الخاصة به JSON لكن Headers لا تعلن JSON بصورة صحيحة.

### طريقة HTTP خاطئة (Wrong HTTP Method)

قد يؤدي استدعاء Scoring route باستخدام GET عندما تتوقع POST إلى Method error.

### Authorization مشوهة (Malformed Authorization)

يجب أن يطابق Authentication header الـ Required format.

لذلك فإن Model deployment ليست Model فقط، بل API contract إضافة إلى Runtime behavior.

## 17. Debugging الجيدة Method مُمارسة: اسأل وراقب وتحقق

يقارن الفصل Debugging بمحاولة العثور على طريقك في مدينة غير مألوفة.

العادات المفيدة هي:

- إيلاء Attention إلى Details،
- تسجيل ما لاحظته،
- إعادة تتبع المسار،
- التشكيك في Assumptions،
- الثقة في Suggestions فقط بعد Validation لها،
- الرجوع عندما تتعارض Evidence مع Hypothesis.

الشعار التشغيلي هو:

> **لا تفترض أبدًا. ثق، لكن تحقق. (Never assume. Trust, but verify.)**

يمكن نقل هذه Mindset عبر Clouds وTools مختلفة.

## 20. قد تكون Traceback عرضًا لا Root cause

يعطي المصدر Example من Distributed system.

لنفترض أن Python ترفع Error لأنها توقعت JSON payload.

قد يكون الاستنتاج الواضح: أصلح Python code.

لكن ماذا لو أن Upstream system أرسلت Empty file بدل JSON؟

تصبح Root cause في مكان آخر.

ولهذا ينبغي لـ Observability أن تروي Cross-component story.

قد تحتوي ML pipeline حقيقية على:

```text
استيعاب → تنظيف → إزالة الأعمدة → توحيد القياس → إصدار dataset → تدريب/تقديم
```

عندما تفشل Stage لاحقة، تحتاج Evidence من Stages السابقة أيضًا.

## 22. يجمع Local Azure ML deployment بين Model وEnvironment وScore script وInference config

يتكون Local deployment path في الفصل من عدة Components.

### Model مسجلة (Registered Model)

تُسجل Model artifact داخل Workspace.

### بيئة التشغيل (Environment)

تُعرّف Dependencies مثل ONNX runtime.

### Script للتقييم (Scoring Script)

يقول المصدر إن `score.py` خاص بالـ Model ويجب أن ينفذ Azure entry points المتوقعة مثل:

- `init()` — تهيئة/تحميل Model state،
- `run()` — استقبال Request data وإنتاج Scores.

### إعداد Inference (Inference Configuration)

تربط Inference configuration الـ Scoring script بالـ Environment.

### إعداد Local web service (Local Web-service Configuration)

يعرض Deployment الـ HTTP endpoint على Local port.

```text
النموذج + البيئة + score.py
          ↓
InferenceConfig
          ↓
LocalWebservice
          ↓
حاوية Docker محلية + نقطة HTTP
```

## 29. توجد Azure ML services لدعم Iterative model lifecycle

يختتم الفصل بوضع Tools الفردية كلها داخل ML lifecycle واحدة.

Flow مبسطة هي:

```text
Training
Notebooks / AutoML / SDK
     ↓
Validation
Studio / Designer / Evaluation
     ↓
تسجيل + إصدار Model/Data
     ↓
Deployment
ACI / AKS / Online أوBatch targets
     ↓
المراقبة (Observe)
Logs / Application Insights / Failures
     ↓
Feedback
تغييرات Data/Model/Deployment
     ↺
```

يرفض الفصل صراحةً تفسيرًا خطيًا بحتًا.

لا تضمن Monitoring وScaling checkboxes نجاح System. يجب تقييم System باستمرار، وينبغي للملاحظات إعادة الفريق إلى Stages سابقة عند الحاجة.

- إدارة Compute،
- Containerized deployment،
- Scalable inference،
- Monitoring،
- مسارات Pipelines.

الهدف هو بناء مسار موثوق يُدخل Models إلى Production ويستمر في تحسينها بعد ذلك.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: تتطلب Azure ML Workflow واحدة مفروضة

يعرض الفصل صراحةً Studio وDesigner وNotebooks وAutoML وCLI وSDK بوصفها Interfaces بديلة/مكملة.

### المفهوم الخاطئ 2: تبطئ Authentication الـ Automation، لذلك ينبغي تعطيلها في Test environments

يوصي المصدر بـ Authentication صحيحة وEnvironment parity بدل اختصارات غير آمنة.

### المفهوم الخاطئ 3: ينبغي دائمًا منح Service principal أوسع Role ممكنة

يوصي الفصل صراحةً بتقييد Access إلى Minimum required permissions.

### المفهوم الخاطئ 4: Reproducibility مهمة فقط في Production

يقدر المصدر Reproducible compute حتى للـ Notebooks والـ Experiments لأنها تقلل مفاجآت Collaboration.

### المفهوم الخاطئ 5: Model registration غير ضرورية لأن Deployment تعرف Model file بالفعل

تتيح Registration الـ Identity وMetadata وVersion history وRollback أسهل.

### المفهوم الخاطئ 6: Git نظام افتراضي جيد لإصدار Versions لـ Huge datasets

يعامل المصدر Source-code version control وDataset versioning بوصفهما مشكلتين مختلفتين.

### المفهوم الخاطئ 7: ينبغي افتراض أن Cluster المستخدمة في Training هي نفسها Production serving cluster

لـ Training وInference أنماط Compute مختلفة ويمكنهما استخدام Resources مختلفة.

### المفهوم الخاطئ 8: Model تم Training لها بنجاح هي تلقائيًا HTTP service صالحة

يجب أيضًا أن تعمل Request method وContent type وAuthentication وInput schema وRuntime وDeployment.

### المفهوم الخاطئ 9: Python traceback تثبت أن Python هي Root cause

يوضح نقاش Observability في الفصل أن Upstream system قد تكون أنتجت Invalid input.

### المفهوم الخاطئ 10: ينبغي تنفيذ Production debugging مباشرةً على Production server كلما أمكن

يوصي المصدر بإعادة إنتاج Containerized services داخل Local environments أكثر أمانًا عندما يكون ذلك ممكنًا.

### المفهوم الخاطئ 11: Pipeline مجرد Python script طويلة

تملك Pipeline steps Inputs وOutputs وCompute وRuntime configuration وOrchestration boundaries صريحة.

### المفهوم الخاطئ 12: Monitoring وKubernetes scaling تجعل ML system ناجحة تلقائيًا

يخلص المصدر إلى أن Continuous evaluation وFeedback ما تزالان مطلوبتين.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مساحة عمل Azure ML (Azure ML Workspace) | Cloud context تجمع ML assets وCompute وModels وDatasets والعمليات المرتبطة بها. |
| واجهة Azure CLI | Command-line interface تستخدم لـ Authentication وإدارة Azure resources/workflows. |
| مكتبة Python SDK | Programmatic interface يستخدمها الفصل للتعامل مع Azure ML resources. |
| هوية Service principal | Azure identity غير بشرية تُستخدم للوصول Automated إلى Resources. |
| مبدأ Least privilege | منح Permissions المطلوبة للمهمة فقط. |
| مثيل Compute (Compute Instance) | Managed cloud workstation/environment لتطوير ML. |
| عنقود Compute (Compute Cluster) | مجموعة Machines قابلة للتوسع تُستخدم للـ Training أوJobs أخرى. |
| الاستدلال الدفعي (Batch Inference) | إنتاج Predictions على Large datasets/Jobs بدل Interactive serving لكل Request. |
| الاستدلال عبر Endpoint (Online Inference) | خدمة Predictions عبر Live endpoint، غالبًا باستخدام HTTP. |
| تسجيل Model (Model Registration) | تخزين Model بوصفها Azure ML asset مُدارة وذات Versions مع Metadata. |
| إصدار Dataset (Dataset Versioning) | إدارة Named/versioned references للـ Data المستخدمة عبر ML workflows. |
| خدمة ACI | Azure Container Instances، يعرضها المصدر بوصفها Deployment option أبسط للاختبار. |
| خدمة AKS | Azure Kubernetes Service، يعرضها المصدر بوصفها Kubernetes-backed deployment option قابلة للتوسع. |
| Script للتقييم (Scoring Script) | Model-specific serving script يعرّف Initialization وRequest-scoring behavior. |
| إعداد InferenceConfig | Azure ML abstraction تجمع Scoring code وServing environment في SDK الخاصة بالمصدر. |
| خدمة Application Insights | Azure observability tooling للـ Requests وLatency وFailures وExceptions وDashboards والإشارات المرتبطة. |
| خدمة LocalWebservice | SDK abstraction في المصدر لتشغيل Azure ML-style model deployment محليًا داخل Container. |
| خطوة Pipeline (Pipeline Step) | Unit عمل صريحة تملك Inputs وOutputs وCode وExecution resources. |
| Pipeline منشورة (Published Pipeline) | Pipeline مكشوفة كـ Authenticated endpoint حتى تتمكن External systems من Trigger للـ Runs. |
| واجهة Designer | Visual Azure ML interface لبناء ML workflows وتشغيلها. |
