## 1. من الإجابة عن الأسئلة إلى تنفيذ الأفعال

يتميز تطبيق LLM أساسي بقدرته الكبيرة على إنتاج اللغة. تعطيه prompt، فيولد response، وقد ينتهي التفاعل عند هذه النقطة. وهذا مفيد لمهام مثل شرح موضوع أوصياغة نص أوالإجابة عن سؤال.

لكن كثيرًا من الأهداف الحقيقية لا تُحل عبر response واحدة. قارن بين الطلبين التاليين:

```text
الطلب A: اعرض الرحلات الجوية من القاهرة إلى Calgary.
الطلب B: رتّب رحلتي إلى Calgary.
```

يحتاج الطلب الأول بصورة أساسية إلى معلومات. أما الثاني فقد يتطلب عدة أفعال مترابطة: البحث عن رحلات، ومقارنة الخيارات، وحجز رحلة، وحجز فندق، وترتيب وسيلة نقل. والنظام القادر على متابعة هذا الهدف الأعلى مستوى يحتاج إلى أكثر من text generation. فهو يحتاج إلى طريقة لتحديد ما ينبغي فعله بعد ذلك، واختيار الأفعال، وملاحظة النتائج، والاستمرار حتى يكتمل الهدف.

وهذا هو الدافع المركزي وراء AI agents.

### تعريف عملي (A practical definition)

في هذا المقرر، فكّر في **AI agent** باعتباره software تقوم بما يلي:

1. **تستشعر (Perceives)** معلومات عن بيئتها أوالمهمة.
2. **تقرر (Decides)** ما الذي ينبغي أن يحدث بعد ذلك.
3. **تتصرف (Acts)** باستخدام الموارد المتاحة لها.
4. تواصل العمل نحو **هدف (goal)** بدل الاكتفاء بإنتاج response واحدة.

تمنح LLM النظام قدرة مرنة على تفسير اللغة، والاستدلال حول الأهداف، والاختيار بين الأفعال الممكنة. وتوسّع tools و memory و planning و feedback mechanisms ما يستطيع agent إنجازه فعليًا.

## 2. Agents و Agency و Agentic Thinking

فكرة agent أقدم من LLMs الحديثة. ففي مجالات مختلفة من AI، وُصفت agents بأنها كيانات تلاحظ بيئة، وتتخذ قرارات، وتتصرف نحو أهداف. وتُعد agents المدعومة بـ LLM implementation أحدث لهذه الفكرة الأوسع.

أما الكلمة المرتبطة **agentic** فتصف نظامًا أوسلوكًا يُظهر agency: أي أنه يستطيع perception واتخاذ القرار والتصرف بدرجة من autonomy أثناء متابعة هدف.

### لماذا تهم Autonomy؟

يتفاعل generative assistant تقليدي مع request. أما agent فيمكنها مواصلة العمل بعد request الأولى من خلال تحديد intermediate tasks المطلوبة.

افترض أن الهدف هو:

```text
اعثر على أهم خمس رسائل بريد إلكتروني وأبلغني بها.
```

قد تحتاج agent مفيدة إلى:

- فحص email data المتاحة،
- تحديد كيفية الحكم على الأهمية،
- ترتيب الرسائل،
- إعداد نتيجة مختصرة،
- استخدام notification tool.

يحدد المستخدم الهدف، لكن agent تقرر كثيرًا من الخطوات.

### Autonomy طيف وليست مبررًا لإزالة الإشراف

غالبًا ما توصف agents بأنها autonomous، لكن هذا **لا** يعني أن كل action ينبغي أن تُنفذ من دون human control. يمكن لـ production design استخدام مستويات متدرجة من approval:

- الخطوات منخفضة المخاطر والقابلة للعكس قد تعمل تلقائيًا،
- actions متوسطة المخاطر قد تتطلب confirmation،
- actions عالية المخاطر قد تُحجب صراحة قبل التنفيذ حتى يتم approval.

إذًا السؤال المفيد ليس ببساطة: "هل هذا النظام autonomous؟" بل السؤال الأفضل هو: "أي قرارات تستطيع agent اتخاذها بأمان، وأين ينبغي أن يبقى الإنسان داخل loop؟"

## 3. أربعة Patterns شائعة للتفاعل مع LLM

يصف الفصل تطورًا من تفاعل بسيط مع language model إلى autonomy على مستوى الهدف. والمصطلحات ليست موحدة تمامًا في الصناعة، لذلك ركز على **الفروق السلوكية**.

| النمط | استخدام Tools | Human approval | Autonomy | السلوك النموذجي |
|---|---|---|---|---|
| Direct LLM chat | لا يوجد | غير منطبق | لا توجد | تولد text من prompt |
| Tool-augmented LLM | غالبًا tool call واحدة | يبدأها user request | منخفضة | تستخدم tool لمهمة محددة مثل search أو image generation |
| المساعد (Assistant) | تستخدم tools | يرتبط approval غالبًا بكل task/action | متوسطة | تساعد في إكمال tasks يوجهها المستخدم لكنها لا تتابع هدفًا طويلًا بحرية |
| الوكيل (Agent) | تستخدم عدة tools عند الحاجة | Approval على مستوى الهدف مع gates للأفعال الحساسة | مرتفعة | تخطط وتنفذ عدة خطوات نحو objective |

### Assistant مقابل Agent

يرسم الفصل الحد الفاصل بصورة أساسية عند **autonomy**.

يمكن لـ assistant استخدام tools، لكن الإنسان يظل مشاركًا بدرجة كبيرة في تحديد أو approval لكل action. أما agent فتتلقى objective أعلى مستوى وتستطيع تحديد sequence الخاصة بالمهام اللازمة للوصول إليه.

أسهل طريقة لتذكر هذا الفرق:

```text
Assistant: "أخبرني بالمهمة التالية، وسأساعد على تنفيذها."
Agent:     "أخبرني بالهدف، وسأحدد المهام اللازمة للوصول إليه."
```

## 4. دورة Sense–Plan–Act–Learn

Mental model مفيدة لسلوك agent هي دورة **sense → plan → act → learn (SPAL)**.

### الخطوة 1 — Sense

تستقبل agent معلومات: هدف المستخدم، ونتائج tools، و feedback، أو context أخرى. ويجب أن تفهم الوضع الحالي قبل اختيار action.

### الخطوة 2 — Plan

تقرر agent المهام المطلوبة والترتيب الذي ينبغي تنفيذها به. قد تكون plan بسيطة أوتتضمن عدة subgoals.

### الخطوة 3 — Act

تنفذ agent tool أو action أخرى لازمة للمهمة الحالية.

### الخطوة 4 — Learn

تلاحظ agent النتيجة وتقيّم معناها. ثم تقرر ما إذا كان:

- الهدف قد اكتمل،
- هناك خطوة أخرى مطلوبة،
- ينبغي تغيير plan،
- هناك حاجة إلى retry أو fallback،
- human input ضرورية.

ثم يمكن أن تتكرر الدورة.

### مثال عملي: تخطيط رحلة (Worked example: planning a trip)

الهدف:

```text
السفر إلى Calgary (YYC).
```

أحد التقسيمات الممكنة:

```text
Sense: افهم الوجهة ومتطلبات السفر.
Plan:  ابحث عن رحلة -> احجز رحلة -> احجز فندقًا -> رتّب وسيلة نقل.
Act:   استدعِ search_flights.
Learn: افحص الخيارات وحدد ما إذا كانت النتيجة قابلة للاستخدام.
Act:   استدعِ book_flights باستخدام الخيار المحدد.
Learn: أكد نتيجة الحجز، ثم تابع إلى الفندق ووسيلة النقل.
```

الفكرة المهمة هي أن **output الخاصة بـ tool يمكن أن تصبح input للـ action التالية**. ويسمى هذا الاتصال **tool chaining**.

### Reasoning أصلية مقابل Reasoning منظمة (Native reasoning versus structured reasoning)

تستطيع modern reasoning-capable models غالبًا التعامل مع tasks قصيرة ومنخفضة المخاطر باستخدام reasoning المدمجة فيها. وتصبح البنية الإضافية مفيدة عندما تكون tasks طويلة، أوتتفرع إلى subgoals، أوتتضمن tools كثيرة، أوتنفذ تغييرات مكلفة أوغير قابلة للعكس.

ويميز الفصل أيضًا بين:

- **Single-path reasoning:** الالتزام بـ plan واحدة وتنفيذها sequentially. وهي أسرع وأقل تكلفة، لكنها أكثر هشاشة عندما تكون task غير مؤكدة.
- **Multipath reasoning:** استكشاف عدة candidate strategies واختيار branch أكثر وعدًا. وقد يحسن ذلك الخطط الصعبة لكنه يزيد token usage و latency.
- **External planning:** نقل sequencing إلى orchestration code أو workflow engine أو planning agent مخصصة.

## 5. Tools تحول Language إلى Action

من دون tools، تستطيع LLM توليد information لكنها لا تستطيع مباشرةً تعديل external system. وتسد tools هذه الفجوة.

غالبًا ما تغلف tool شيئًا تحتاج agent إلى الوصول إليه، مثل:

- API،
- database،
- search service،
- external application،
- knowledge store،
- callable capability أخرى.

لاستخدام tool، تحتاج agent إلى description قابلة للقراءة آليًا تشرح ما الذي تفعله tool، وما inputs التي تتوقعها، وما output التي تعيدها. وبعد ذلك تستطيع Model اختيار tool مناسبة وتوفير arguments، بصورة تشبه مفاهيميًا استدعاء function في البرمجة التقليدية.

### فئات Tools (Tool categories)

يجمع الفصل أدوار tools في عدة فئات مفيدة:

| دور Tool | الغرض | مثال |
|---|---|---|
| إكمال Task | تغيير العالم الخارجي أوالتصرف فيه | Create، send، update، book |
| استرجاع Context | جلب information لازمة للقرار التالي | Search، قراءة file، query لـ vector store |
| Reasoning و Planning | دعم decision أو sequencing | Planner أو reasoning helper |
| Knowledge و Memory | قراءة/كتابة information مستمرة | Memory store، knowledge retrieval |
| Evaluation و Feedback | فحص الجودة أوالصحة | Critic، scorer، validation tool |

### إخفاقات Tools جزء طبيعي من Control Flow

تفشل tools الحقيقية. قد تتعرض API لـ timeout. وقد تعيد database schema غير متوقعة. وقد تكون arguments malformed. وقد نصل إلى rate limits.

ينبغي لـ agent قوية ألا تعامل كل tool error باعتبارها fatal crash. بل ينبغي أن تصبح failure information جديدة للـ control loop. وبحسب الحالة، قد تعيد agent المحاولة، أوتستخدم fallback، أوتسأل المستخدم، أوتتوقف بأمان. وتُعد retry limits مهمة لأن retries غير المحدودة قد تنشئ runaway loops.

## 6. بروتوكول Model Context Protocol

مع حصول agents على tools أكثر، واجه developers مشكلة integration: قد تحتاج كل agent إلى wrappers خاصة بها للتقويمات، وأنظمة الرسائل، و databases، و project trackers، وخدمات كثيرة أخرى. ويخلق تكرار هذا العمل عبر agents كثيرة قدرًا كبيرًا من tool plumbing.

يعالج **Model Context Protocol** هذه المشكلة من خلال توفير طريقة موحدة لأنظمة AI للاتصال بـ external tool servers.

وفقًا للفصل، طورت Anthropic بروتوكول MCP وأصدرته في نوفمبر 2024. وهو open standard مبني على JSON-RPC 2.0.

### الفكرة الأساسية (The core idea)

بدل تضمين كل integration مباشرة داخل كل agent:

```text
قبل MCP
Agent A -> custom calendar wrapper
Agent A -> custom Slack wrapper
Agent B -> another calendar wrapper
Agent B -> another Slack wrapper

مع MCP
Agent A --\\
          -> MCP server -> reusable tools
Agent B --/
```

تعرض server tools عبر protocol متسق. ويمكن لـ agent الاتصال بـ server، واكتشاف tools المتاحة، وفهم descriptions الخاصة بها، ثم استدعاء tool المناسبة.

ويبدو interaction نموذجي هكذا:

1. إعداد وتشغيل MCP server.
2. تسجيل تلك server لدى agent.
3. طلب tools المتاحة من server، غالبًا عبر `list_tools`.
4. قراءة أسماء tools و descriptions الخاصة بها.
5. اختيار tool مناسبة للمهمة.
6. تنفيذها وملاحظة النتيجة.
7. مواصلة agent loop حسب الحاجة.

### المشكلات التي صُمم MCP لتقليلها

- **عدم اتساق الوصول إلى Tools:** تقلل protocol واحدة متسقة الحاجة إلى adaptation خاصة بكل provider.
- **عدم موثوقية التعامل مع Responses:** تقلل request/response structures الموحدة أخطاء integration.
- **تجزؤ Integrations:** تنتقل tool code إلى reusable servers بدل أن تتوزع عبر agents.
- **قيود Language/Codebase:** تسمح protocol boundary بتنفيذ server و agent بلغات مختلفة.
- **عبء Implementation:** يمكن إعادة استخدام servers موجودة بدل إعادة بناء كل connector.

### Security ما تزال مهمة

لا تجعل standardization الـ tools آمنة تلقائيًا. تعرض MCP server capabilities تستطيع agent استدعاءها، ولذلك تصبح trusted dependency. ويؤكد الفصل أهمية authentication و authorization و sandboxing و scoped credentials و human approval للأفعال عالية المخاطر و source vetting و version pinning و least-privilege execution بوصفها أجزاء أساسية من الاستخدام المسؤول.

## 7. الطبقات الوظيفية الخمس للـ Agent

ينظم الفصل قدرات agent في خمس طبقات وظيفية:

1. **الشخصية (Persona)**
2. **الأدوات والأفعال (Tools and actions)**
3. **الاستدلال والتخطيط (Reasoning and planning)**
4. **المعرفة والذاكرة (Knowledge and memory)**
5. **التقييم والتغذية الراجعة (Evaluation and feedback)**

من الأفضل فهم هذه بوصفها capabilities، لا خمس خطوات يجب أن تعمل دائمًا من أعلى إلى أسفل. أثناء تشغيل agent، تتفاعل باستمرار. فقد تستشير reasoning الـ persona، وقد يستدعي planning tools، وقد تحدث tool results الـ memory، وقد تعيد evaluation النظام إلى تعديل plan.

### Mental Model مختصرة

```text
Persona              -> من أنا وكيف ينبغي أن أتصرف؟
Tools & actions       -> ما الذي أستطيع فعله؟
Reasoning & planning  -> كيف أقرر ما الذي ينبغي فعله بعد ذلك؟
Knowledge & memory    -> ما المعلومات والخبرات التي أستطيع استخدامها؟
Evaluation & feedback -> كيف أحكم على النتيجة وأحسنها؟
```

## 8. Persona و Reasoning و Planning

### الشخصية (Persona)

الـ persona هي الوصف الأساسي لدور agent وسلوكها التشغيلي. وغالبًا تُعبّر عنها system instructions.

قد تحدد persona:

- role، مثل coder أو writer،
- domain focus،
- expertise level،
- communication style،
- operating constraints،
- تعليمات حول reasoning أو planning أو knowledge أو memory access.

Mental model جيدة هي أن persona لا تمنح agent قدرات خارجية جديدة. بل تحدد كيف تستخدم agent القدرات التي تمتلكها بالفعل.

### Reasoning و Planning

بمجرد توفر tools، تحتاج agent إلى تحديد أي tools تستخدم، وبأي ترتيب، وتحت أي شروط. قد تكون built-in model reasoning كافية لـ tasks قصيرة وبسيطة ومنخفضة التكلفة. وتصبح structured reasoning أكثر قيمة عندما يكون العمل طويلًا أومتفرعًا أوحساسًا من ناحية safety أوصعب التدقيق.

الدرس الهندسي المهم في الفصل هو أن **planning مشكلة control**، وليست مجرد prompt-writing trick. يجب أن تحدد مقدار الحرية التي تحصل عليها executing agent ومتى ينبغي تقييد planning أونقلها إلى external orchestration.

## 9. Knowledge و Memory و Evaluation و Feedback

### Knowledge و Memory مترابطتان لكنهما مختلفتان

**Knowledge** هي information خارجية تستخدمها agent لإنجاز عملها. وتشمل الأمثلة documents و manuals و schemas و code repositories و knowledge-base articles.

أما **Memory** فهي information خبراتية تتطور من خلال interaction. ويمكن أن تتضمن recent conversation turns و preferences و past decisions و observations سجلت خلال sessions سابقة.

| الجانب | المعرفة (Knowledge) | Memory |
|---|---|---|
| الطبيعة | معلومات مرجعية خارجية | خبرة مشتقة من interaction |
| نمط التحديث | تتغير عندما يتغير source الأساسي | تتغير أثناء الاستخدام |
| النطاق المعتاد | غالبًا مشتركة بين مستخدمين كثيرين | غالبًا خاصة بـ session أو user أو tenant |
| مثال | Product manual | المستخدم يفضل reports مختصرة |

### Short-term و Long-term Memory

- **Short-term memory** تشير عادةً إلى recent conversation turns و tool activity داخل current context window.
- **Long-term memory** تستمر بعد current session ويتم استرجاعها بصورة انتقائية عندما تكون relevant.

### إدارة Context Window

لا تستطيع Model attention إلا على مقدار محدود من information في الوقت نفسه. ولذلك يشمل تصميم agent قرارات حول ما ينبغي الاحتفاظ به، أوتلخيصه، أواسترجاعه، أو filter له، أو discard له. تقلل context windows الأكبر بعض الضغط لكنها لا تلغي المفاضلة: قد تزيد context الأطول cost و latency، وقد تجعل context غير الضرورية مهمة agent أصعب.

### التوليد المعزز بالاسترجاع (Retrieval-Augmented Generation — RAG)

يستخدم الفصل RAG باعتبارها pattern عامة من retrieve-then-generate لجلب knowledge أو memory ذات الصلة إلى context الخاصة بـ agent وقت اتخاذ القرار. والمبدأ بسيط:

```text
المهمة الحالية
    -> استرجع information ذات الصلة
    -> أضفها إلى context
    -> نفّذ reasoning/generation باستخدام تلك information grounded
```

### Evaluation و Feedback

تحتاج agent أيضًا إلى طرق للحكم على ما إذا كان عملها جيدًا بما يكفي. ويمكن تنفيذ evaluation من خلال:

- Model منفصلة تعمل judge،
- critic agent،
- validation tools،
- guardrails على inputs أو outputs،
- feedback تتولد أثناء learn phase من agent loop.

في ترتيب **actor-critic**، ينتج مكوّن candidate response أو plan، ثم يقيّم مكوّن آخر النتيجة أويراجعها قبل أن يلتزم النظام بها.

## 10. لماذا نستخدم أكثر من Agent واحدة؟

يمكن لـ agent واحدة إنجاز الكثير، لكن بعض المشكلات تصبح أسهل في الإدارة عندما تُقسّم المسؤولية بين عدة agents.

يعرض الفصل أربعة أسباب رئيسية:

### 1. التخصص (Specialization)

قد تصبح agent واحدة تحتوي كل tool وكل instruction وكل domain محملة أكثر من اللازم. ويمكن لـ focused agents أن تتولى كل منها مسؤولية أضيق، مثل triage أو billing أو technical support.

### 2. التوازي (Parallelism)

يمكن معالجة tasks مستقلة بصورة concurrent. فمثلًا، تستطيع عدة agents البحث في شركات مختلفة في الوقت نفسه بدل أن تنفذ agent واحدة ذلك sequentially.

### 3. إدارة Context

يمكن لكل agent الاحتفاظ فقط بالجزء من information الذي تحتاجه. وقد يساعد ذلك عندما تكون المشكلة الكاملة أكبر أوأكثر noise من أن تتسع داخل context window واحدة.

### 4. مشكلات متعددة الوكلاء بطبيعتها

تتضمن بعض tasks بطبيعتها عدة actors لهم أهداف أو roles مختلفة، مثل negotiations أو social simulations أو red-team/blue-team setups.

الدرس المهم ليس أن زيادة عدد agents أفضل دائمًا. تضيف multi-agent designs تنسيقًا إضافيًا و cost و latency. ويوصي الفصل باستخدام أرخص pattern ما دامت تحقق requirement.

## 11. ثلاثة Patterns أساسية للـ Multi-Agent

### النمط A — تدفق الوكلاء (Agent Flow — Assembly Line)

تُرتّب agents في sequence. تنفذ كل specialized agent الجزء الخاص بها ثم تمرر العمل إلى الأمام.

مثال:

```text
وكيل Planning -> وكيل Research -> وكيل Content
```

وهذا سهل نسبيًا في implementation و control، لذلك يفيد في multistep processes واضحة الأدوار.

يمكن لـ agents داخل flow مشاركة context بثلاث طرق أساسية:

- **Threaded:** تقرأ وتكتب الجميع في conversation thread نفسها. توفر context غنية، لكن thread قد تصبح كبيرة ومليئة بالـ noise.
- **Blackboard:** تكتب agents intermediate results منظمة تحت keys متفق عليها. وهي منظمة وانتقائية، لكنها تحتاج shared schema.
- **Chained:** تمرر كل agent فقط output المطلوبة للـ agent التالية. بسيطة وفعالة، لكن information التي لا تُمرر إلى الأمام تضيع.

### النمط B — التنسيق المركزي (Orchestration — Hub-and-Spoke)

تستقبل orchestrator مركزية الهدف، وتخطط العمل، وتفوض subgoals إلى specialized worker agents، وتجمع النتائج، وتحدد متى يكتمل الهدف العام.

```text
                  -> عامل A
المستخدم -> Orchestrator -> عامل B
                  -> عامل C
```

تفيد هذه pattern عندما تريد نقطة control رئيسية واحدة للـ inputs والـ outputs مع الاستفادة من specialized agents.

أحد القيود هو أن workers قد تكون مقيدة بدرجة كبيرة بالمهام المفوضة إليها، وقد تحصل على فرص أقل لـ peer-to-peer feedback.

### النمط C — التعاون (Collaboration — Team of Agents)

تعمل agents هنا بدرجة أكبر كـ peers. ويمكنها التواصل والنقد والتحقق وتحسين عمل بعضها بعضًا.

على سبيل المثال، قد يحتوي فريق coding على:

- product agent تفسر requirements،
- coding agent تنفذها،
- QA agent تتحقق من behavior وتنقد quality.

يمكن لهذا الأسلوب حل المشكلات المعقدة التي تستفيد من interaction و criticism، لكنه أيضًا أكثر chatty وتكرارًا وتكلفة وبطئًا.

### المقارنة (Comparison)

| Pattern | شكل Control | أفضل استخدام وفق الفصل | المفاضلة الرئيسية |
|---|---|---|---|
| تدفق الوكلاء (Agent flow) | Sequential pipeline | أعمال متعددة الخطوات واضحة التعريف | أقل مرونة عندما تحتاج downstream agents إلى upstream context مفقودة |
| التنسيق (Orchestration) | Hub مركزية مع workers | عدة subgoals تحت agent مسيطرة واحدة | قد يكون collaboration بين workers محدودًا |
| التعاون (Collaboration) | تفاعل بين peers/team | أعمال معقدة تحتاج critique أو joint problem solving | cost و repetition و latency أعلى |

## 12. جمع Architecture كاملة معًا

يمكنك الآن قراءة agent system باعتبارها مزيجًا من مجموعة أفكار متكررة.

تخيل goal-directed research agent:

```text
هدف من المستخدم
   |
   v
Persona/instructions
   |
   v
Reason + plan
   |
   +--> استرجع knowledge/memory
   +--> استدعِ tools أو MCP servers
   |
   v
راقب نتائج tools
   |
   v
Evaluate + learn
   |
   +--> تابع/عدّل عند الحاجة
   |
   v
النتيجة النهائية
```

إذا أصبح العمل أوسع من أن تتعامل معه agent واحدة، يمكنك تقسيم المسؤوليات باستخدام flow أو orchestrator أو collaborating team.

وهذا يمنحك عدسة معمارية قابلة لإعادة الاستخدام:

1. ما الهدف؟
2. ما الدور والقيود التي ينبغي أن تمتلكها agent؟
3. ما tools التي تستطيع استخدامها؟
4. كيف ينبغي أن تنفذ reasoning و planning؟
5. ما knowledge و memory التي تحتاجها؟
6. كيف ستُقيَّم النتائج؟
7. أين ينبغي للبشر approval على الأفعال؟
8. هل تكفي agent واحدة، أم أن multi-agent pattern مبررة؟

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: إذا استطاعت LLM استدعاء Tool فهي Agent تلقائيًا

> استخدام Tool وحده لا يعرّف agent.

قد تنفذ tool-augmented LLM action واحدة فقط يبدأها المستخدم. ويعتمد تمييز agent في الفصل بدرجة أكبر على goal-level autonomy و multistep planning واتخاذ القرار والاستمرار في التنفيذ.

### المفهوم الخاطئ 2: Autonomous تعني Unsupervised

> يمكن لـ agent أن تكون autonomous في planning مع استمرار استخدام human approval gates.

قد تحتاج actions عالية المخاطر إلى confirmation صريحة حتى عندما تعمل بقية workflow تلقائيًا.

### المفهوم الخاطئ 3: المزيد من Agents ينتج دائمًا نظامًا أفضل

> تضيف Multi-agent systems coordination cost و token usage و latency.

استخدمها عندما يبرر specialization أو parallelism أو context separation أوطبيعة المشكلة التعقيد الإضافي.

### المفهوم الخاطئ 4: الطبقات الخمس عبارة عن Execution Pipeline ثابتة

> هي فئات capabilities وليست ترتيب runtime إلزاميًا.

تتفاعل الطبقات بصورة متكررة طوال agent loop.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| الوكيل (Agent) | Software تستشعر وتقرر وتتصرف نحو goal بدرجة من autonomy |
| القدرة على الفعل (Agency) | القدرة على اتخاذ قرارات وتنفيذ أفعال نحو هدف |
| سلوك وكيل (Agentic) | يصف سلوكًا أوأنظمة تُظهر agency |
| المساعد (Assistant) | نظام LLM يستخدم tools لكنه يظل أكثر خضوعًا لـ user approvals |
| الأداة (Tool) | Callable capability تسمح لـ agent باسترجاع information أوالتصرف خارج Model |
| ربط الأدوات (Tool chaining) | استخدام output الخاصة بـ tool باعتبارها input لـ action لاحقة |
| دورة SPAL | Sense, Plan, Act, Learn — agent control loop متكررة |
| بروتوكول MCP | Model Context Protocol، protocol موحدة لربط أنظمة AI بـ external tool servers |
| الشخصية (Persona) | Instructions تحدد دور agent وسلوكها وأسلوبها وقيودها |
| المعرفة (Knowledge) | External reference information متاحة للـ agent |
| Memory | Information مشتقة من interaction ويتم الاحتفاظ بها للاستخدام لاحقًا |
| أسلوب RAG | استرجاع information ذات الصلة وإضافتها إلى context قبل generation/reasoning |
| Evaluation | Mechanisms تستخدم للحكم على جودة أوصحة نتائج agent |
| تدفق الوكلاء (Agent flow) | نمط خط التجميع المتسلسل متعدد الوكلاء |
| التنسيق (Orchestration) | Hub-and-spoke pattern مع agent تنسيق مركزية |
| التعاون (Collaboration) | Multi-agent pattern تتواصل فيها agents وتعمل كـ peers |

## اختبر نفسك (Self-check)

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما الذي تفعله agent ولا يفعله one-shot LLM application؟
2. لماذا من الأفضل فهم autonomy باعتبارها spectrum؟
3. ما الذي يميز assistant عن agent وفق مصطلحات هذا الفصل؟
4. ماذا يحدث في كل مرحلة من دورة SPAL؟
5. ما tool chaining؟
6. لماذا يقلل MCP أعمال integration المتكررة؟
7. ما الطبقات الوظيفية الخمس للـ agent؟
8. كيف تختلف knowledge عن memory؟
9. لماذا تهم إدارة context window؟
10. متى يمكن أن يكون multi-agent system مبررًا؟
11. كيف تختلف agent flow عن orchestration؟
12. لماذا قد تكون collaboration أكثر تكلفة من بقية multi-agent patterns؟

## احتفظ بهذه الفكرة (Retain this idea)

**AI agent ليست مجرد LLM مضافًا إليها بعض features. بل هي نظام goal-directed يستشعر context بصورة متكررة، ويخطط، ويتصرف عبر tools، ويقيّم ما حدث، ويواصل العمل حتى يكتمل الهدف — مع استخدام المقدار المناسب من memory و oversight و coordination للمهمة.**
