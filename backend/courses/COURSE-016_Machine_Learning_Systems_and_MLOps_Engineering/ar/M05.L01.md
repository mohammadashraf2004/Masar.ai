## 1. Learned features مقابل Engineered features

هندسة الخصائص هي عملية تحديد **ما Information التي ينبغي أن تستخدمها Model** وتحويل هذه Information إلى شكل تستطيع Model التعلم منه.

يمكن لـ Modern deep learning أن تتعلم Representations مفيدة كثيرة تلقائيًا، ولهذا توصف Deep learning أحيانًا بأنها **Feature learning**.

على سبيل المثال، كانت NLP pipelines الأقدم تحتاج غالبًا إلى Text-processing steps مصممة يدويًا مثل:

- تحويل Text إلى Lowercase،
- إزالة Punctuation،
- Lemmatization،
- توسيع Contractions،
- استخراج n-grams.

الـ **n-gram** هي Sequence متصلة من `n` Items.

بالنسبة إلى الجملة:

```text
I like food    # أنا أحب الطعام
```

فإن Word-level 1-grams هي:

```text
I, like, food    # كل كلمة وحدة مستقلة
```

أما Word-level 2-grams فهي:

```text
I like, like food    # أزواج من الكلمات المتتالية
```

يمكن لـ Classical model بعد ذلك تمثيل الجملة باستخدام Counts على Vocabulary من هذه n-grams.

تقلل Deep models الحاجة إلى كثير من Handcrafted text/image features، لكنها **لا** تلغي Feature engineering بالكامل.

فعلى سبيل المثال، قد تستفيد Spam-detection model من Information تتجاوز Comment text نفسها:

- عدد Upvotes أو Downvotes،
- عمر Account الخاصة بـ User،
- Posting frequency،
- Historical user reputation،
- Popularity الخاصة بـ Thread،
- Contextual information عن المكان الذي تظهر فيه Comment.

هذه Information ليست موجودة تلقائيًا داخل Raw text. ما يزال على شخص ما تحديد ما إذا كانت مهمة وكيف ينبغي تمثيلها.

## 2. Missing values ليست كلها متشابهة

تُعد Missing data شائعة في Production، لكن *سبب* فقدان Value هو المهم.

يصف الفصل ثلاثة أنواع.

### الفقد غير العشوائي (Missing Not At Random — MNAR)

تكون Value مفقودة بسبب يرتبط بالقيمة المفقودة نفسها.

مثال: قد يكون Respondents ذوو Income المرتفع أقل استعدادًا للكشف عن Income. في هذه الحالة، تحمل Missingness نفسها Information عن Income.

### الفقد العشوائي (Missing At Random — MAR)

تكون Value مفقودة بسبب Variable أخرى مرصودة.

مثال: قد تكون Age مفقودة بصورة أكثر تكرارًا لدى Demographic group معينة.

### الفقد العشوائي الكامل (Missing Completely At Random — MCAR)

لا يوجد Pattern ظاهر في Missingness.

مثال: ينسى الأشخاص أحيانًا إدخال Field دون سبب Systematic.

يؤكد الفصل أن MCAR نادرة نسبيًا؛ وغالبًا ما يكون لـ Missingness سبب.

[[IMAGE_NEEDED: MNAR versus MAR versus MCAR | Three small panels showing missing income caused by income itself, missing age explained by another observed group variable, and random missing job values with no visible pattern | Learner should notice that the mechanism causing missingness affects how safely data can be removed or imputed]]

## 3. الحذف (Deletion) مقابل التعويض (Imputation)

هناك استجابتان عامتان للـ Missing values:

1. حذف Rows أو Columns المتأثرة،
2. ملء Missing values باستخدام Imputation.

### حذف Columns (Column deletion)

إذا كانت Feature تحتوي Missing values كثيرة، فقد تحذف Feature كلها.

هذا بسيط، لكنه قد يهدر Predictive information مهمة. فقد تظل Field ذات Missingness مرتفعة مرتبطة بقوة بالـ Target.

### حذف Rows (Row deletion)

يمكنك حذف Examples التي تحتوي Missing values.

يقترح الفصل أن هذا يكون أكثر قابلية للدفاع عنه عندما تكون Missingness من نوع MCAR وتكون النسبة المتأثرة صغيرة جدًا.

إذا كانت Missingness من نوع MAR أو MNAR، فقد يؤدي حذف Rows إلى Bias أو إزالة Information مشفرة داخل Missingness نفسها.

### التعويض (Imputation)

تملأ Imputation الـ Missing values بقيمة Replacement مختارة.

تشمل الاختيارات الشائعة:

- Default values،
- Mean،
- Median،
- Mode،
- Values مشروطة بـ Variable أخرى، مثل Median لقيمة Temperature في شهر July.

ومع ذلك، قد تنشئ Imputation غير الحذرة Bugs خفية.

إذا تم ملء Missing age بالقيمة `0`، لكن Age `0` هي أيضًا Value صالحة أو لم تظهر مطلقًا أثناء Training، فقد تفسر Model الـ Replacement بصورة خاطئة.

من المبادئ المفيدة في الفصل:

> تجنب استخدام Value عادية وصالحة كعلامة للـ Missing value عندما يجعل ذلك القيم الحقيقية والمفقودة غير قابلة للتمييز.

لا يوجد حل Universal مثالي. قد تزيل Deletion Signal وتنشئ Bias؛ وقد تضيف Imputation افتراضات أو Noise أو Leakage.

## 4. Scaling و Standardization والـ Skewed features

لنفترض أن Feature واحدة تتراوح من 20 إلى 40، وأخرى من 10,000 إلى 150,000.

تعمل Models كثيرة بصورة أفضل عندما تكون Numerical features على Scales متقاربة. ويقدم الفصل Feature scaling بوصفها Preprocessing step شائعة.

### تحجيم Min-Max (Min-max scaling)

لتحويل Value باسم `x` إلى Range `[0, 1]`:

```text
x_scaled = (x - x_min) / (x_max - x_min)
```

تصبح Minimum مساوية لـ 0 و Maximum مساوية لـ 1.

### التحجيم إلى Range اختيارية

يمكن للفكرة نفسها Mapping للـ Data إلى Range أخرى مثل `[-1, 1]`.

### التوحيد القياسي (Standardization)

إذا عوملت Feature على أنها Approximately normal، فيمكن Standardization لها:

```text
z = (x - mean) / standard_deviation — صيغة Standardization
```

يعطي ذلك Feature المحولة Mean تقارب Zero و Unit variance تقريبًا.

### التحويل اللوغاريتمي (Log transformation)

قد تكون Highly skewed features صعبة على Models. وقد يقلل تطبيق Logarithmic transformation من Skewness أحيانًا.

ومع ذلك، ينبغي تفسير Transformed values بعناية؛ فالتحليل في Log space ليس مطابقًا للتحليل على Original scale.

### تحذير Production

تحتاج Scaling إلى Statistics مثل Min و Max و Mean أو Standard deviation. ويجب أن تأتي هذه Statistics من **Training split فقط** ثم يُعاد استخدامها أثناء Inference.

إذا تغيرت Production data بدرجة كبيرة، فقد تصبح Scaling statistics القديمة أقل تمثيلًا.

## 5. Discretization: تحويل Continuous values إلى Buckets

تحول **Discretization**، والتي تسمى أيضًا Binning أو Quantization، Feature مستمرة إلى Categories منفصلة.

مثال لـ Income buckets:

```text
Lower:  < 35,000 — الفئة المنخفضة
Middle: 35,000 to 100,000 — الفئة المتوسطة
Upper:  > 100,000 — الفئة المرتفعة
```

قد يجعل ذلك Problem أسهل عندما تكون Data محدودة لأن Model تتعلم عددًا أصغر من Categories بدلًا من Values فردية كثيرة.

لكن Discretization تدخل Boundaries حادة. فعلى سبيل المثال، تصبح 34,999 و35,000 ضمن Categories مختلفة رغم أنهما متقاربتان جدًا، بينما قد تشترك 35,000 و100,000 في Category واحدة.

لذلك يتطلب اختيار Boundaries حكمًا مناسبًا. ويقترح الفصل Common sense و Quantiles و Histograms و Domain expertise بوصفها Guides مفيدة.

## 6. ترميز Categorical features المتغيرة

تبدو Categorical variables بسيطة إلى أن تتغير Vocabulary الخاصة بها في Production.

لنفترض أن Recommender تستخدم **Brand** بوصفها Feature. أثناء Training، تقوم بترميز كل Brand معروفة كـ Integer. ثم تظهر Brand جديدة في Production.

إذا لم يمتلك Encoder تمثيلًا لها، فقد تفشل Pipeline.

### فئة `UNKNOWN`

أحد الحلول الشائعة هو Mapping للـ Categories غير المرئية إلى Bucket باسم `UNKNOWN`.

لكن ذلك ينشئ مشكلة أخرى: إذا لم تظهر `UNKNOWN` مطلقًا أثناء Training، فلن تكون Model قد تعلمت كيفية التعامل معها.

تتمثل Approach عملية يصفها الفصل في Mapping لجزء صغير من Rare training categories إلى `UNKNOWN` أيضًا، بحيث تتعلم Model بعض Behavior لهذه Bucket.

ومع ذلك، تنهار جميع Categories غير المرئية إلى Representation نفسها، رغم أنها قد تكون مختلفة جدًا.

### تجزئة Features (Feature hashing)

تقوم **Hashing trick** بعمل Mapping للـ Categories داخل Hash space ثابتة الحجم.

بالنسبة إلى Hash space ذات 18 bit:

```text
2^18 = 262,144 possible indices — عدد Indices الممكنة
```

يمكن Mapping لكل Category — بما في ذلك Categories غير المرئية — إلى تلك Space.

المفاضلة هي **Collision**: قد يتم Mapping لـ Categoryين إلى Index نفسها.

تقلل Hash space الأكبر من Collisions. ويشير الفصل أيضًا إلى أن Random collisions قد تكون أقل ضررًا بصورة Systematic من إجبار كل Categories الجديدة على الدخول في Bucket واحدة باسم UNKNOWN.

[[IMAGE_NEEDED: UNKNOWN bucket versus feature hashing | A categorical stream with old and new brands, showing one approach mapping all unseen brands to UNKNOWN and another hashing every brand into a fixed index space with occasional collisions | Learner should notice why hashing handles open-ended vocabularies more gracefully]]

## 7. Feature crossing والتفاعلات

تجمع **Feature crossing** بين Featureين أو أكثر لإنشاء Feature جديدة.

لنفترض أن House-buying behavior تعتمد ليس فقط على Marital status أو Number of children بصورة منفردة، بل على Combination بينهما.

يمكنك إنشاء:

```text
marital_status = Married — الحالة الاجتماعية
children = 2 — عدد الأطفال

crossed_feature = Married_2 — Feature متقاطعة
```

تكشف Feature crosses صراحة Interactions قد تفشل Models الأبسط في تعلمها جيدًا.

يشير الفصل إلى أن Explicit crossing مفيدة بصورة خاصة للـ Models الضعيفة في تعلم Nonlinear interactions، مع أنها قد تساعد Neural networks أيضًا في بعض الحالات.

### التكلفة التوافقية (Combinatorial cost)

إذا كانت Feature A تحتوي 100 Value محتملة وكانت Feature B تحتوي 100 Value محتملة:

```text
100 × 100 = 10,000 possible crossed values — عدد Values المتقاطعة الممكنة
```

يوسع ذلك Feature space، ويزيد كمية Data المطلوبة، وقد يزيد Risk الخاصة بـ Overfitting.

## 8. Embeddings والمعلومات الموضعية

الـ **Embedding** هي Vector representation لقطعة من Data.

الكلمات Example مألوفة، لكن Embeddings يمكنها أيضًا تمثيل:

- Products،
- Users،
- Images،
- Graph entities،
- الاستعلامات (Queries).

تمتلك كل Vectors داخل Embedding space واحدة Dimensionality نفسها.

### لماذا يهم Position؟

يجب أن تعرف Sequence model ترتيب العناصر.

الجملتان:

```text
a dog bites a child    # كلب يعض طفلًا
a child bites a dog    # طفل يعض كلبًا
```

تحتويان كلمات متشابهة لكن معناهما مختلف جدًا لأن Positions مختلفة.

تعالج Recurrent models الـ Tokens بصورة Sequential، لذلك يكون Order موجودًا طبيعيًا في Computation. أما Transformer-style processing فهي Parallel، ولذلك يجب حقن Positional information صراحة.

### Positional embeddings المتعلمة

تخصص إحدى Approaches لكل Position Vector قابلة للتعلم. ويمكن دمج Token embedding و Position embedding بحيث تستقبل Model معلومات Identity و Location معًا.

### Positional embeddings الثابتة

تستخدم Approach أخرى Sine و Cosine functions محددة مسبقًا لتوليد Position representation.

يربط الفصل هذه الأفكار أيضًا بـ **Fourier features** التي يمكنها تمثيل Continuous coordinates مثل Positions على 3D surface.

## 9. Data leakage: عندما تتعلم Model معلومات لا ينبغي أن تمتلكها

تحدث **Data leakage** عندما تدخل Information مرتبطة بالـ Target إلى Features أو Training process بطريقة لن تكون متاحة أثناء Real inference.

تكون Leakage خطيرة بصورة خاصة لأن Evaluation قد تبدو ممتازة بينما يفشل Production performance.

### مثال Hospital-scan

لنفترض أن Hospital ترسل Patients المشتبه في إصابتهم بالسرطان إلى Scan machine خاصة. قد تتعلم Model المدربة على هذه Scans الـ Visual signature الخاصة بالآلة بدلًا من Disease نفسها.

تعمل Model جيدًا على Data من Hospital نفسها لأن اختيار Machine مرتبط بالـ Diagnosis. لكن في Hospital أخرى حيث لا يرمز اختيار Machine إلى هذا Decision، ينهار Performance.

لقد تعلمت Model Shortcut غير متاح أو غير صالح عند Deployment.

تشمل أمثلة أخرى يذكرها الفصل Position الخاصة بـ Patient أو Text fonts الخاصة بـ Hospital والتي تكشف Clinical severity عن طريق الخطأ.

## 10. الأسباب الشائعة لـ Data leakage

### 1. التقسيم العشوائي لـ Data المترابطة زمنيًا

إذا كانت Data مترابطة زمنيًا، فقد يسرّب Random splitting ظروف Future إلى Training.

في Forecasting problem، درّب على الفترات الأقدم وقيّم على الفترات الأحدث.

مثال:

```text
Week 1 ─┐ — الأسبوع 1
Week 2  │ — الأسبوع 2
Week 3  ├── Training — الأسبوع 3 ضمن Training
Week 4 ─┘ — الأسبوع 4
Week 5 ─── Validation / Test — الأسبوع 5
```

يعكس ذلك Real deployment condition بصورة أفضل: Predict للـ Future باستخدام Information من Past.

### 2. تنفيذ Scaling قبل Splitting

إذا تم حساب Mean أو Variance أو Minimum أو Maximum باستخدام Data كلها قبل Splitting، فإن Information من Validation/Test examples تتسرب إلى Preprocessing.

الترتيب الصحيح:

```text
Split first — نفّذ Splitting أولًا
   ↓
Fit scaler on train only — نفّذ Fit للـ Scaler على Train فقط
   ↓
Apply train statistics to train/validation/test — طبّق Statistics الخاصة بـ Train على جميع Splits
```

### 3. تنفيذ Imputation باستخدام Test statistics

ينطبق المبدأ نفسه على Missing-value imputation. احسب Means أو Medians أو غيرها من Imputation statistics من Training split فقط.

### 4. Duplicates عبر Splits

إذا ظهرت Duplicates أو Near-duplicates في Train data و Test data معًا، فقد تكافئ Evaluation عملية Memorization.

تحقق من Duplicates قبل Splitting وبعده. وإذا نفذت Oversampling، فافعله **بعد** Splitting.

### 5. تسرب Groups (Group leakage)

ينبغي ألا تُوزَّع Examples المترابطة بدرجة كبيرة عبر Splits مختلفة.

أمثلة:

- Scanان من Patient نفسها،
- Video frames شبه متطابقة،
- Observations متكررة من Entity واحدة.

إذا كانت Example مترابطة في Training وأخرى في Testing، فقد تكون Test result متفائلة أكثر من اللازم.

### 6. Leakage من عملية توليد Data

مثال Scanner هو Data-generation leak. ويتطلب اكتشاف هذا النوع من المشكلات فهم كيفية جمع Data ومعالجتها.

ولهذا تكون Subject-matter experts و Data lineage مهمتين.

## 11. اكتشاف Features المشبوهة و Leakage

لا يوجد Detector عالمي للـ Leakage، ولذلك تحتاج Teams إلى عدة Checks.

### افحص Features ذات القوة التنبؤية غير المعتادة

إذا كانت Feature لديها Correlation قوي بصورة غير متوقعة مع Target، فاسأل:

- كيف تم توليدها؟
- هل كانت متاحة وقت Prediction؟
- هل يمكن أن تحتوي Target information بصورة غير مباشرة؟

أحيانًا لا تظهر Leakage إلا من **Combination** بين Features.

### نفّذ Ablation studies

احذف Feature أو Feature group وقِس تغير Performance.

إذا أدى حذف Feature واحدة إلى انهيار كبير بصورة غير متوقعة، فافحص لماذا تكون هذه Feature قوية إلى هذا الحد.

### راقب Features الجديدة بعناية

قد تعني قفزة كبيرة في Performance بعد إضافة Feature واحدة أحد أمرين:

1. Feature ممتازة فعلًا،
2. أو Feature تسرب Information عن Target.

### احمِ Test split

لا تستخدم Test set مرارًا لابتكار Features جديدة أو ضبط Hyperparameters. فكل استخدام من هذا النوع ينقل Information من Future evaluation set المفترضة إلى Development process.

## 12. المزيد من Features ليس أفضل دائمًا

غالبًا ما تنمو Production feature sets بمرور الوقت، لكن لكل Feature تكلفة.

قد تؤدي Features كثيرة جدًا إلى:

- إنشاء فرص أكثر للـ Leakage،
- زيادة Overfitting،
- زيادة Serving memory،
- زيادة Online inference latency،
- زيادة عبء صيانة Pipeline.

تتحول Feature عديمة الفائدة إلى Technical debt. وإذا تغيرت Upstream data، فيجب أن تتغير أيضًا كل Downstream logic التي تعتمد على هذه Feature.

يوصي الفصل بتقييم Features باستخدام بُعدين عامين:

1. **Feature importance**،
2. **Feature generalization**.

## 13. أهمية Feature (Feature importance)

تسأل Feature importance:

> إلى أي مدى تعتمد Model على هذه Feature؟

توفر بعض Model families مقاييس Feature importance مدمجة. ويذكر الفصل أيضًا Approaches مستقلة عن Model مثل SHAP.

Intuition مفيدة تعتمد على Ablation:

> إذا أدى حذف Feature إلى تدهور Performance بدرجة كبيرة، فغالبًا ما تكون Feature مهمة لهذه Model.

يمكن لـ SHAP أيضًا المساعدة في شرح كيفية مساهمة Features الفردية في Prediction محددة، وليس فقط في Global model behavior.

قد يكشف تحليل Feature importance أن عددًا صغيرًا من Features يحمل جزءًا كبيرًا من Predictive signal المفيدة، بينما تسهم Features كثيرة أخرى بقليل.

يجعل ذلك Importance مفيدة لكل من **Feature selection** و **Interpretability**.

## 14. تعميم Feature (Feature generalization)

قد تكون Feature شديدة القدرة على Prediction داخل Training data لكنها تفشل على Unseen data.

يقترح الفصل النظر في جانبين:

### التغطية (Coverage)

Coverage هي نسبة Examples التي تكون Feature موجودة فيها.

قد تكون Feature متاحة في 1% فقط من Examples قليلة الفائدة. لكن Missingness نفسها قد تكون Informative، خصوصًا في MNAR، ولذلك لا ينبغي الحكم على Coverage بصورة عمياء.

يمكن لـ Coverage أيضًا كشف Distribution mismatch. إذا ظهرت Feature في 90% من Training examples ولكن في 20% فقط من Test examples، فافحص Split و Collection process.

### توزيع Values

حتى Coverage بنسبة 100% لا تضمن Generalization.

لنفترض أنك تدرب Taxi ETA model باستخدام ستة أيام من Data وتختبرها في اليوم السابع.

Feature باسم `DAY_OF_WEEK` لديها Coverage بنسبة 100%، لكن Training values قد تحتوي Monday إلى Saturday بينما يحتوي Testing على Sunday فقط.

لا يوجد Overlap لهذه Categorical value.

في المقابل، قد تمتلك `HOUR_OF_DAY` Overlap جيدًا عبر جميع Splits ولذلك تعمم بصورة أكثر طبيعية.

### Generalization مقابل Specificity

قد تعمم Feature أوسع مثل `IS_RUSH_HOUR` بصورة أفضل من Exact-hour feature محددة، لكنها تفقد Detail أيضًا.

غالبًا ما تتضمن Feature engineering موازنة هاتين الخاصيتين.

## قائمة فحص عملية لهندسة Features

يختتم الفصل بعدة Best practices موجهة إلى Production:

1. فضّل Train/Validation/Test splits تراعي Time عندما يكون Time correlation مهمًا.
2. إذا كنت تستخدم Oversampling، فنفذه بعد Splitting.
3. نفّذ Fit للـ Scaling و Normalization بعد Splitting.
4. استخدم Statistics الخاصة بـ Training split فقط للـ Scaling و Missing-value imputation.
5. افهم كيف يتم توليد Data وجمعها ومعالجتها.
6. أشرك Domain experts متى أمكن.
7. احتفظ بـ Data lineage.
8. افهم Feature importance.
9. فضّل Features التي تعمم جيدًا.
10. أزل Features التي لم تعد تقدم Value مفيدة.

والأهم: Feature engineering ليست Phase تحدث مرة واحدة. بل تستمر ما دامت Production model و Data الخاصة بها تستمران في التطور.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Deep learning تلغي Feature engineering

تؤتمت Deep learning كثيرًا من مهام Representation learning، لكن Production systems تظل تعتمد على Contextual و Behavioral و User و System و Domain features.

### المفهوم الخاطئ 2: ينبغي حذف Missing values ببساطة

قد تزيل Deletion Signal مفيدة أو تدخل Bias، خصوصًا عندما تكون Missingness من نوع MAR أو MNAR.

### المفهوم الخاطئ 3: `UNKNOWN` تحل تمامًا مشكلة Categories غير المرئية

تمنع Bucket باسم `UNKNOWN` فشل Encoding، لكن Model ما تزال تحتاج Training examples لهذه Bucket وقد تعامل Categories جديدة ومختلفة جدًا بطريقة متطابقة.

### المفهوم الخاطئ 4: Validation performance الممتازة تعني عدم وجود Leakage

يمكن أن تجعل Leakage الـ Validation تبدو *أفضل* تحديدًا لأن Model تعلمت عن طريق الخطأ Information لن تكون متاحة لها في Production.

### المفهوم الخاطئ 5: Feature ذات Importance مرتفعة هي تلقائيًا Feature جيدة

قد تكون Feature مهمة لكنها تفشل في Generalization، أو تكون مهمة لأنها تحتوي Information مسربة.

### المفهوم الخاطئ 6: المزيد من Features يحسن Model دائمًا

قد تنشئ Features الإضافية Overfitting و Leakage و Memory cost و Latency و Maintenance debt.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| هندسة الخصائص (Feature engineering) | اختيار Information وتحويلها إلى Inputs مفيدة لـ ML models. |
| Learned feature | Representation تتعلمها Model تلقائيًا. |
| Engineered feature | Feature تُبنى عمدًا من Raw أو Contextual data. |
| n-gram | Sequence متصلة من `n` Items مثل Words أو Characters. |
| MNAR | Missingness ناتجة عن Missing value نفسها. |
| MAR | Missingness تفسرها Variable أخرى مرصودة. |
| MCAR | Missingness لا تتبع Pattern مرصودة Systematic. |
| التعويض (Imputation) | ملء Missing values بقيم Replacement مختارة. |
| تحجيم Features (Feature scaling) | تحويل Numerical features إلى Ranges قابلة للمقارنة. |
| التوحيد القياسي (Standardization) | تحويل Values إلى Mean تقارب Zero و Unit variance. |
| التحويل اللوغاريتمي (Log transformation) | تطبيق Logarithm لتقليل Skewness في بعض Distributions. |
| التقسيم إلى فئات (Discretization) | تحويل Continuous values إلى Buckets أو Categories. |
| Feature hashing | Hashing للـ Categories داخل Fixed-size index space. |
| Hash collision | Mapping لـ Categoryين إلى Hashed index نفسها. |
| Feature crossing | دمج Features لكشف Interactions. |
| التمثيل المتجهي (Embedding) | Fixed-length vector representation لعنصر. |
| Positional embedding | Vector signal تمثل Position داخل Sequence أو Coordinate space. |
| تسرب البيانات (Data leakage) | دخول Target-related information إلى Features أو Development بطريقة غير متاحة أثناء Inference. |
| Group leakage | ظهور أعضاء شديدة الترابط من Group نفسها عبر Train و Test splits. |
| Ablation study | حذف Feature أو Component لقياس مساهمتها. |
| Feature importance | مدى اعتماد Model على Feature من أجل Prediction. |
| Feature coverage | نسبة Examples التي تمتلك Value للـ Feature. |
| Feature generalization | قدرة Feature على البقاء مفيدة على Unseen data. |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. لماذا تقلل Deep learning الحاجة إلى Feature engineering لكنها لا تلغيها؟
2. ما الفرق بين MNAR و MAR و MCAR؟
3. متى يمكن أن ينشئ Row deletion الـ Bias؟
4. لماذا قد يكون تعويض Missing age بالقيمة 0 خطيرًا؟
5. ما الفرق بين Min-max scaling و Standardization؟
6. لماذا يجب أن تأتي Scaling statistics من Training split فقط؟
7. ما Information التي تفقدها Discretization؟
8. لماذا لا تكفي Bucket باسم `UNKNOWN` لبعض Categories المفتوحة؟
9. ما Trade-off التي تقدمها Feature hashing؟
10. لماذا يمكن أن تسبب Feature crossing الـ Overfitting؟
11. لماذا تحتاج Transformer-style models إلى Positional information؟
12. ما هي Data leakage؟
13. لماذا قد يكون Random splitting خاطئًا للـ Time-correlated data؟
14. لماذا ينبغي التعامل مع Duplicates قبل Splitting؟
15. كيف تساعد Ablation studies في اكتشاف Leakage أو قياس Importance؟
16. ما هي Feature coverage؟
17. لماذا قد تمتلك Feature Coverage بنسبة 100% وتظل تفشل في Generalization؟
18. لماذا تُعد Features غير المستخدمة شكلًا من Technical debt؟

## احتفظ بهذه الفكرة

**Feature الجيدة ليست مجرد Feature تتنبأ جيدًا على Training data الخاصة بالأمس. بل يجب أن تكون متاحة في الوقت الصحيح، ومشتقة دون Leakage، ومفيدة للـ Model، وقابلة للصيانة في Production، وقادرة على Generalization إلى Unseen data التي سيواجهها System فعلًا.**
