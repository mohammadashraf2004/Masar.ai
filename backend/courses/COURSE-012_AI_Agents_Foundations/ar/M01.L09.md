## 1. لماذا تهم Agentic loops؟

لا يمكن إكمال كثير من Agent tasks المفيدة في Model call واحدة.

تشمل الأمثلة:

- البحث في Topic غير مألوف،
- Debugging لنظام عبر عدة Observations،
- معالجة Queue من Documents،
- Refining لـ Answer بعد Critique،
- تنسيق عدة Specialist agents.

تحتاج هذه Tasks إلى أن **يكرر النظام عملًا هادفًا مع حمل ما تعلمه إلى الأمام**.

هذه البنية المتكررة هي Agentic loop.

يوسع الفصل SPAL loop من الفصل الأول إلى ثلاث Layers:

```text
Layer 1 -> حلقة SPAL داخلية
Layer 2 -> حلقة Task خارجية
Layer 3 -> حلقة Meta تتحكم في Agents/Loops
```

تضيف كل Layer أفق Control أوسع.

## 2. Layer 1: حلقة SPAL الداخلية

الطبقة الأولى هي دورة Sense-Plan-Act-Learn الأساسية.

```text
Sense -> Plan -> Act -> Learn/Evaluate -> قرر هل تستمر أم لا
```

تبدأ Agent بهدف وInternal state حالية.

ثم تقوم بما يلي:

1. **Senses** الـ State وContext الحالية.
2. **Plans** للخطوة التالية.
3. **Acts** باستخدام Tool أوGenerated action.
4. **Learns/evaluates** النتيجة.
5. **Decides** ما إذا كان Goal اكتمل أم أن Iteration أخرى مطلوبة.

تنمو Internal state مع استمرار Loop، ولذلك تستطيع Cycles اللاحقة استخدام Information تراكمت سابقًا.

الخاصية المحددة ليست أن Code تحتوي `while` loop. الخاصية المحددة هي أن **Agent تختار ما يجب فعله داخل Iteration**.

يوفر Developer الـ Goals وTools والBoundaries؛ وتقود Agent الـ Local decisions.

## 3. كل Loop تحتاج Goal وPlan وState وDecision

يختصر الفصل Agentic looping في أربعة عناصر أساسية.

### Goal

ما الذي يجب تحقيقه؟

### Plan

كيف ينبغي تحقيق Progress عبر Iterations؟

### State

ما الذي حدث بالفعل، وأي Context يجب أن تستمر إلى Iteration التالية؟

### القرار / شرط الإنهاء

هل ينبغي أن تستمر Loop أم تتوقف؟

عادةً ما تتصرف Loop بصورة سيئة إذا افتقدت أحد هذه العناصر.

مثلًا:

- لا Goal واضحة -> تنحرف Agent،
- لا Plan -> تكرر Agent Actions عشوائية،
- لا State -> تبدأ كل Iteration تقريبًا من الصفر،
- لا Termination condition -> Loop تنفلت بلا توقف.

## 4. Layer 2: إخراج Task loop إلى الخارج

تعمل Layer 1 جيدًا مع Short-horizon goals. لكن Long-horizon work يخلق مشكلة جديدة: لا ينبغي توقع أن تحتفظ Internal agent loop الواحدة بكامل Task المتطورة إلى الأبد.

تنقل Layer 2 عناصر Control الكبرى خارج Agent.

```text
Goal خارجية
Plan خارجية
State خارجية
Decision Logic خارجية
        |
        v
      Agent
```

تظل Agent تنفذ Internal reasoning الخاصة بها، لكن Deterministic controller تدير Task الأكبر.

يجعل ذلك Long-running work ممكنًا لأن:

- يمكن أن تستمر Plan state عبر Calls،
- يمكن تخزين Findings المتراكمة خارج Context window،
- تستطيع Code فرض Hard limits،
- يستطيع Controller تحديد أي Context تراها Agent بعد ذلك.

يمثل Deep-research system المثال الرئيسي في الفصل لهذا Pattern.

## 5. Deep research بوصفها Layer-2 loop

تعمل Deep-research agent عبر Searches صغيرة كثيرة للإجابة عن سؤال أكبر.

Architecture عالية المستوى هي:

```text
Long-horizon research goal
        |
        v
Initialize للـ State + Plan
        |
        v
اختيار Current question
        |
        v
تشغيل Research agent
        |
        v
تحديث Findings / Plan / Follow-up questions
        |
        v
Termination gate
   |           |
 stop      continue
   |           |
   v           +-----> Next iteration
Synthesis
```

{{image:deep-research-loop}}

تعتمد Quality الخاصة بالـ Loop بدرجة كبيرة على ثلاثة مجالات يشدد عليها الفصل:

1. **State management** بين Iterations.
2. **Termination conditions**.
3. **External tools** التي تستخدمها Agent.

إذا كانت هذه العناصر ضعيفة، فقد تهدر Loop الـ Tokens وهي تكرر نفسها.

## 7. تحكم فيما يدخل Context window من State

يمكن أن تنمو External state لتصبح أكبر كثيرًا مما ينبغي إرساله إلى Model في كل Iteration.

يستخدم الفصل Helper methods مثل `to_context()` لعمل Serialization للمعلومات المفيدة فقط.

يعطي ذلك Controller مسؤولية مهمة:

> خزّن أكثر مما تراه Model.

تشمل Strategies الممكنة:

- إرسال Recent findings فقط،
- Summarize للـ Older findings،
- تضمين Unfinished plan items فقط،
- حذف Redundant sources،
- تمرير Compact progress summary.

يحمي ذلك Context window ويبقي Agent مركزة.

تظل Full state متاحة للنظام حتى إذا تم تمرير Compact subset فقط إلى Call التالية.

## 10. Termination gate

يجب أن تنتهي كل Iteration بقرار: Stop أوContinue.

يوصي الفصل بـ **Layered termination conditions** بدل الاعتماد على Signal واحدة.

### حد صارم لعدد الدورات

أقصى عدد من الدورات.

هذه هي Safety net غير القابلة للتفاوض.

### Budget limit

Maximum token أوMonetary spend.

### Goal satisfaction

تعلن Agent أن Information كافية قد جُمعت.

### Quality threshold

تصل Confidence أوEvaluator score إلى المستوى المطلوب.

### Stagnation detection

لم تعد Iterations الأخيرة تنتج Information جديدة بصورة ذات معنى.

ينبغي عادةً أن تحتوي Production loop على أكثر من Condition واحدة من هذه الشروط.

[[IMAGE_NEEDED: Layered termination gate | Show an iteration result entering a decision gate with checks for hard limit, cost budget, goal satisfied, quality threshold, and stagnation. Any stop condition leads to exit; otherwise flow returns to the next iteration | Learner should notice that stopping is layered rather than delegated entirely to agent self-assessment]]

## 11. Stagnation تختلف عن Failure

قد تعيد Loop الفاشلة Exception أوEmpty result.

أما Stagnating loop فأكثر خفاءً: تنتج Output تبدو معقولة لكنها تضيف القليل من Information الجديدة.

مثلًا:

```text
Iteration 4: Battery costs تنخفض.
Iteration 5: Battery prices تتراجع.
Iteration 6: Battery costs تواصل الانخفاض.
```

يبدو Text منتجًا، لكن Loop لا تحقق Progress.

يقترح الفصل مقارنة Consecutive findings باستخدام Semantic similarity.

إذا ظلت Similarity مرتفعة جدًا عبر Iterations متكررة، يمكن إنهاء Loop لأن Marginal value أصبحت صغيرة جدًا.

ينتج عن ذلك Production rule مهمة:

> اكتشف غياب Progress، لا Explicit errors فقط.

## 12. Unconstrained loops هي Production incidents

تستهلك كل Cycle موارد:

- Input tokens،
- Output tokens،
- Tool/API calls،
- Elapsed time،
- حصص الخدمات الخارجية.

Loop تستمر حتى «تشعر» Agent أنها انتهت ليست Production design آمنة.

أقوى Rule في الفصل هي:

> افرض دائمًا Hard iteration limit وCost ceiling.

حتى لو عملت Goal satisfaction وQuality checks بصورة جيدة عادةً، تحمي Defensive ceilings من Edge cases تستمر فيها Model في Search أوReasoning داخل دوائر.

## 14. Breadth-first مقابل Depth-first exploration

يستخدم الفصل Queue من Follow-up questions.

إذا أزالت Controller الأسئلة من **المقدمة** وألحقت الجديدة في **النهاية**، فإنها تتصرف مثل Breadth-first exploration.

```text
Q1 -> Q2 -> Q3 -> ابن(Q1) -> ابن(Q2) -> ...
```

يوزع ذلك Attention عبر Branches متعددة.

إذا أزالت Controller أحدث سؤال من **النهاية**، تميل Agent إلى Depth-first exploration.

```text
Q1 -> ابن(Q1) -> ابن(ابن(Q1)) -> ...
```

يعتمد الاختيار الصحيح على Research goal.

يشبه هذا Tree-of-Thought search structure: تحدد Controller أي Branch يجب استكشافها بعد ذلك.

## 16. متى تكون Agentic loop مفيدة؟

استخدم Loop عندما يستفيد العمل من Interaction متكرر مع New state.

يحدد الفصل عدة حالات قوية.

### Iterative discovery

لا تستطيع Agent معرفة كل المعلومات المطلوبة مسبقًا.

### Progressive refinement

تتحسن Output عبر Drafts أوEvaluations متكررة.

### Batch processing

يجب معالجة Queue من Items بصورة متكررة.

### Conditional branching

تعتمد Action التالية على Result السابقة.

### Multisource aggregation

تكتشف Agent Relevant sources ديناميكيًا أثناء العمل.

تجنب Loops للمهام Simple single-pass مثل Straightforward classification أوSimple question answering أوPure format conversion.

تضيف Loops Latency وCost. ويجب أن تستحق هذا التعقيد.

## 17. حلقات المهام المتكررة

تكتشف Research loops ما ينبغي فعله بعد ذلك. أما Task loops فتعرف Work queue مسبقًا.

تشمل الأمثلة:

- معالجة Invoices،
- Transform للـ Documents،
- اختبار عدة Endpoints،
- Migration للـ Records،
- فحص Files واحدة تلو الأخرى.

Architecture هي:

```text
Task queue
   |
   v
اختيار Item
   |
   v
Agent تعالج Item
   |
   v
تسجيل Success/Failure
   |
   +--> Retry إذا كان Failure مؤقتًا
   |
   v
Next item
```

لأن Queue نفسها تحدد Work، قد لا يحتاج هذا Variation إلى Strategic plan object منفصلة.

## 18. Retries تنتمي إلى Task state

تواجه Task loops كثيرًا Transient errors.

ينبغي لـ Robust design تتبع:

- Pending items،
- Completed items،
- Failed items،
- Retry count،
- معلومات الخطأ السابق.

ينبغي أن تكون Previous error متاحة للمحاولة التالية حتى تستطيع Agent التكيف إذا لزم الأمر.

Hard retry ceiling ضرورية.

مثلًا:

```text
فشلت المهمة
  -> إعادة محاولة 1
  -> إعادة محاولة 2
  -> إعادة محاولة 3
  -> وسم فشل دائم
```

Retries جزء من Loop design وليست Afterthought.

## 20. Adaptive iteration budgets ما تزال تحتاج Hard ceilings

تحتاج بعض Goals بصورة طبيعية Iterations أكثر من غيرها.

يذكر الفصل أن Systems يمكنها السماح لـ Agent بتقدير أوطلب Iteration budget بناءً على Task complexity.

لكن ينبغي أن تظل Adaptive budget داخل Developer-defined boundaries.

```text
يطلب Agent: 12 دورات
سقف المطوّر: 8
الحد الأقصى الفعلي: 8
```

يحافظ ذلك على Flexibility دون التخلي عن Cost control.

## 21. Layer 3: الـ Meta-agentic loop

تكون Layer 2 محكومة غالبًا بواسطة Deterministic code.

تنقل Layer 3 قرار Control إلى Agent أوGroup of agents.

وهذا هو الاختلاف المحدد.

يقدم الفصل شكلين رئيسيين:

1. **Orchestration meta loop** — تتحكم Agent مركزية في Delegation وReplanning.
2. **Collaboration meta loop** — تساهم عدة Peer agents معًا وتحدد بصورة جماعية متى اكتمل Goal.

## 23. افصل Strategic reasoning عن Worker execution

تستخدم Orchestrator في الفصل Specialized workers.

أمثلة Roles:

- **Research Worker** — تجمع Information.
- **Analysis Worker** — تحدد Patterns وContradictions وGaps.
- **Research Orchestrator** — تختار Subtask التالية وWorker المناسبة.

ينتج عن ذلك فصل واضح:

```text
Orchestrator -> استراتيجية / تفويض / evaluation
Workers      -> تنفيذ تكتيكي
```

يمكن لـ Orchestrator أيضًا Re-plan عندما تكشف Findings جديدة أن Decomposition الأصلية غير مكتملة.

هذه Adaptability هي الميزة الرئيسية مقارنة بـ Static layer-2 dispatcher.

---

## 24. Orchestrators تضيف Overhead حقيقية

كل Orchestration decision هي Model call إضافية.

إذا استخدمت Loop مكونة من 15 Iteration، وفي كل Cycle توجد Orchestrator call واحدة وWorker call واحدة، فقد يحتاج النظام تقريبًا ضعف عدد Model interactions مقارنة بـ Deterministic controller أبسط.

استخدم Orchestrator عندما:

- تكون Decomposition غير مؤكدة،
- يتغير Worker choice ديناميكيًا،
- قد تتطلب Findings الجديدة Re-planning،
- تحتاج Strategy نفسها إلى Reasoning.

وفضّل Layer-2 deterministic controller عندما:

- تكون Task decomposition معروفة،
- تكون Routing rules بسيطة،
- تكون Cost وLatency أهم من Flexibility.

لا تدفع Cost الخاصة بـ LLM لاتخاذ Decisions تستطيع Code العادية اتخاذها بصورة موثوقة.

## 25. حلقات Meta التعاونية

تزيل Collaboration وجود Orchestrator مركزية واحدة.

بدلًا من ذلك، تشارك Peer agents الـ State وتأخذ أدوارًا متبادلة في تحسين Collective result.

يستخدم الفصل Trio شائعًا:

- Researcher،
- Critic،
- Synthesizer.

```text
Researcher -> تساهم Findings
Critic     -> تتحدى Gaps/Claims
Synthesizer-> تدمج وتحل Contradictions
                 |
                 v
              Next round
```

يكون هذا Pattern مفيدًا عندما تحسن Multiple perspectives وAdversarial review الـ Quality.

## 28. Orchestration مقابل Collaboration

استخدم **Orchestration** عندما يمكن تقسيم Goal إلى Specialist subtasks يمكن تعيينها بوضوح.

أمثلة:

- Batch pipelines،
- Parallel search،
- Document transformations،
- توجيه الأدوات المتخصصة.

استخدم **Collaboration** عندما تحسن Interdependent perspectives الـ Output.

أمثلة:

- Research synthesis،
- Strategic analysis،
- Document review،
- Adversarial critique.

إذا كنت غير متأكد، يوصي الفصل بالبدء بـ Orchestration لأنها أسهل في Debugging، ثم الانتقال إلى Collaboration فقط عندما تبرر Quality benefit الـ Coordination الإضافية.

## 29. Playbook عملية لتصميم Agentic loops

استخدم هذه Checklist كلما صممت Loop.

### Step 1 — حدد Loop layer

هل Goal قصيرة بما يكفي لـ Agent واحدة، أم طويلة بما يكفي لـ External task loop، أم Adaptive بما يكفي لـ Meta loop؟

### Step 2 — عرّف Goal بدقة

تحتاج Loop إلى Objective واضحة.

### Step 3 — عرّف State صراحة

ما الذي يجب أن يستمر بين Iterations؟

### Step 4 — عرّف Iteration strategy

ما الذي ينبغي أن تنجزه Cycle واحدة؟

### Step 5 — استخدم Typed iteration outputs

تحتاج Loop controllers إلى Machine-readable signals.

### Step 6 — قيّد ما يدخل Model context في كل مرة

خزّن Full history خارجيًا؛ وأرسل فقط ما تحتاج إليه Current step.

### Step 7 — طبّق Layered termination conditions

ضمّن دائمًا Hard iteration وCost limits.

### Step 8 — اكتشف Stagnation

Repeated plausible output ما تزال Failure mode.

### Step 9 — افصل Exploration عن Final synthesis

استخدم Roles مختلفة عندما تختلف Objectives.

### Step 10 — نفّذ Parallelism فقط للعمل المستقل

تكون Concurrency مفيدة فقط عندما تسمح Dependencies بذلك.

### Step 11 — استخدم Orchestration فقط عندما تحتاج Strategy إلى Reasoning

لا تستبدل Cheap deterministic code بـ Expensive model decisions دون حاجة.

### Step 12 — استخدم Collaboration عندما توجد Multi-perspective value حقيقية

Agents أكثر لا تعني تلقائيًا نتائج أفضل.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: أي `while` loop حول LLM هي Agentic loop

> يتطلب Agentic behavior أن تتخذ Agent Decisions ذات معنى داخل Cycle.

### المفهوم الخاطئ 2: يمكن أن تعيش Long-horizon goals بالكامل داخل Context window واحدة

> يحتاج Long-running work إلى External state وغالبًا External plan.

### المفهوم الخاطئ 3: ينبغي للـ Agent تحديد كل Termination conditions

> Agent self-assessment مفيدة، لكن Hard limits وCost ceilings ينبغي أن يفرضها النظام.

### المفهوم الخاطئ 4: تكون Loop صحية طالما أنها تواصل إنتاج Text

> قد تنتج Stagnation Output تبدو معقولة لكنها لا تتحسن.

### المفهوم الخاطئ 5: Free-form output كافية لأن LLM يمكنها Parsing لها لاحقًا

> ينبغي أن يعتمد Loop control على Strongly typed output بدل إضافة Probabilistic parsing step أخرى.

### المفهوم الخاطئ 6: ينبغي للـ Research agent كتابة Final report أيضًا

> Exploration وSynthesis تحسنان أهدافًا مختلفة ومن الأفضل فصلهما.

### المفهوم الخاطئ 7: Layer 3 أفضل دائمًا من Layer 2

> تضيف Meta loops Model calls وLatency وCost. استخدمها فقط عندما تضيف Adaptive strategy قيمة.

### المفهوم الخاطئ 8: ينبغي أن تستبدل Collaboration الـ Orchestration كلما شاركت أكثر من Agent

> تكون Collaboration أكثر قيمة عندما تحسن Interdependent perspectives وCritique الـ Result.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Agentic loop | تكرار Goal-directed لتنفيذ Agent مع حمل State إلى الأمام |
| SPAL | حلقة Sense-Plan-Act-Learn الداخلية الخاصة بالـ Agent |
| Layer 1 | Internal loop داخل Agent واحدة |
| Layer 2 | External task loop تتحكم فيها Program logic بدرجة أساسية |
| Layer 3 | Meta loop تتحكم فيها Orchestrator أوCollaborating agents |
| هدف بعيد الأفق (Long-horizon) | Goal تتطلب Iterations أوSubtasks كثيرة عبر Extended state |
| State | Information مستمرة يتم حملها بين Iterations |
| Plan | Strategy تصف كيف ينبغي أن يتقدم Work |
| Iteration | دورة Execution واحدة من Loop |
| Termination gate | Decision point تحدد هل تتوقف Loop أم تستمر |
| Hard limit | Maximum iteration count يفرضها النظام |
| Budget limit | Maximum cost/Token spend مسموح للـ Loop |
| Stagnation | استمرار Execution دون Progress ذات معنى |
| الاستكشاف بالعرض أولًا (Breadth-first) | استكشاف عدة Branches بعمق متقارب قبل الانتقال أعمق |
| الاستكشاف بالعمق أولًا (Depth-first) | اتباع Branch واحدة بعمق قبل العودة إلى Alternatives |
| Synthesis agent | Agent منفصلة تجمع Findings المتراكمة في Final output |
| Task loop | Loop تعالج Queue معروفة من Work items |
| Meta loop | Loop أعلى مستوى تتحكم في Workers أوLoops أخرى |
| Orchestrator | Agent مركزية تخطط وتفوض وتقيم وتعيد التخطيط |
| Collaboration loop | Peer-agent loop تستخدم Shared state وCollective refinement |
| Consensus threshold | Required level من Agent agreement قبل Collaborative termination |

## احتفظ بهذه الفكرة

**تكون Agentic loops مفيدة لأنها تسمح للأنظمة بالسعي وراء Goals تحتاج Actions متكررة وEvidence جديدة وState متطورة. وتبقى Architecture الآمنة في جوهرها واحدة دائمًا: عرّف Goal، واستمر في State، وتحكم في Plan، واطلب Structured iteration output، وافرض Explicit stopping conditions. انتقل من Internal loops إلى Task loops أوMeta loops فقط عندما يؤدي توسيع Control horizon إلى تحسين Task فعلًا.**
