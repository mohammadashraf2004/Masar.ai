# نشر بلا خوادم (Serverless) باستخدام AWS ECS Fargate

> **المقرر:** أسس الـ Deployment الآمن على السحابة  
> **الدرس:** M08.L10  
> **مواءمة المصدر:** BOOK-XXX، الفصل 10. يحافظ الدرس على معمارية ECS/Fargate في المصدر وإعداداته الخاصة. وبيانات الاعتماد الحرفية الظاهرة في المصدر **لا تُعاد كتابتها** عن قصد. وتُشار صراحةً إلى أخطاء صياغة الأوامر المنسوخة وعدم اتساق أسماء الملفات التعريفية (profiles).

## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح ما يتغير عند نقل حزمة AWS القائمة على الـ VM إلى ECS Fargate.
- شرح لماذا تختفي Jenkins وDocker Compose وNginx من بنية المستودع بلا خوادم في المصدر.
- إنشاء مستخدم/مجموعة IAM مخصصين على نمط المصدر لـ deployment عبر سطر الأوامر.
- شرح ملفات AWS CLI التعريفية (profiles) ولماذا يجب ألا تُودَع مفاتيح الوصول أبدًا.
- شرح دورة حياة صورة ECR: البناء والوسم والمصادقة والدفع.
- شرح لماذا تستخدم مجموعات أهداف Fargate أهداف IP دون تسجيل عناوين IP يدويًا.
- تصميم security groups منفصلة لـ ALB ولمهام ECS.
- شرح التوجيه المعتمد على المضيف في ALB للنطاقين الفرعيين لـ Flask وStreamlit.
- شرح لماذا يُرجع المصدر 403 افتراضيًا للطلبات غير المطابقة/الموجّهة إلى DNS الافتراضي.
- تعريف ECS cluster وtask definition وtask وservice.
- شرح تخصيصات CPU/memory المختلفة لكل من Flask وStreamlit في المصدر.
- ربط خدمات ECS بمجموعات أهداف ALB القائمة.
- قراءة سجلات الحاوية عبر CloudWatch أو وحدة تحكم ECS.
- تحديث DNS ليشير أسماء المضيفين المخصصة إلى ALB.
- استيراد الشهادة الحالية إلى ACM وإضافة HTTPS listener.
- شرح لماذا يعيد المصدر إنشاء خدمات ECS عند تبديل إعداد الـ listener.
- تغيير عدد المهام المطلوبة يدويًا وضبط التوسع التلقائي بتتبّع الهدف (target-tracking).

## 1. استبدل إدارة الخوادم بـ ECS Fargate

استخدمت فصول AWS السابقة:

```text
EC2    # المكوّنات السابقة
Docker Compose
Nginx
Jenkins
Flask
Streamlit
```

ويزيل الفصل 10 عدة مكوّنات.

### تغييرات المستودع

يقول المصدر:

```text
jenkins/
→ غير موجود

docker-compose.yml
→ غير موجود

nginx reverse proxy (وكيل عكسي)
→ غير موجود
```

لماذا؟

### Jenkins

يُبقي المصدر Jenkins خارجًا لأنه ذو حالة ويعتمد على تخزين دائم.

### Docker Compose

يتولى إعداد مهمة/خدمة ECS الآن تشغيل الحاوية وشبكتها.

### Nginx

يتولى AWS Application Load Balancer:

```text
إنهاء TLS (TLS termination)
التوجيه حسب المضيف (host routing)
نقطة الدخول العامة (public entry)
```

### التطبيقان المتبقيان

ينشر المصدر:

```text
flask-app    # التطبيقان المنشوران
streamlit-app
```

ويحتفظ Flask بـ:

```text
المنفذ 5000
```

ويحتفظ Streamlit بـ:

```text
المنفذ 8501
```

وعلى خلاف فصل Cloud Run، لا يعيد المصدر تعيين التطبيقين كليهما إلى 8080.


```text
serverless    # اسم المجموعة
```

يرفق المصدر سياسات مُدارة واسعة لمختبر التعلّم لديه، تشمل الوصول إلى:

- S3،
- EC2،


### الأمر `aws configure`


```text

      ↓
بناء Docker
      ↓
صورة محلية
      ↓
الوسم باستخدام عنوان ECR URI
      ↓
مصادقة Docker لدى ECR
      ↓
الدفع (push)
      ↓
صورة في ECR
```

### صادق Docker

```text

        ↓
سجل ECR
```

## 4. افصل حركة ALB العامة عن حركة المهام الخاصة

ينشئ المصدر security groups اثنتين.

### الـ security group الخاص بـ ALB

مثال:

```text
alb-sg    # اسم المجموعة
```

يسمح في البداية بـ:

```text
HTTP 80
من عنوان IP/32 موثوق لمحطة العمل
```

ثم ينتقل لاحقًا إلى:

```text
HTTPS 443
```

### الـ security group الخاص بمهام ECS

مثال:

```text
ecs-sg-tasks    # اسم المجموعة
```

يسمح بـ:

```text
8501 من alb-sg
5000 من alb-sg
```

### لماذا مصدر security group إلى security group؟

لا ينبغي أن تكون حاويات المهام قابلة للوصول مباشرةً من عملاء الإنترنت العشوائيين.

والمسار المقصود هو:

```text
عميل موثوق
   ↓
security group الخاص بـ ALB
   ↓
ALB
   ↓
ecs-sg-tasks يسمح بـ ALB
   ↓
مهمة Fargate
```

وهذا حد شبكي متعدد الطبقات.

[[IMAGE_NEEDED: ALB and ECS security-group boundary | A diagram showing internet/trusted client → alb-sg → ALB → ecs-sg-tasks → Flask:5000 and Streamlit:8501 Fargate tasks, with direct internet-to-task traffic blocked | Learner should notice that task security rules trust the ALB security group rather than public client IPs]]

## 5. أنشئ مجموعات أهداف IP ديناميكية لمهام Fargate

ينشئ المصدر:

```text
streamlit-tg    # مجموعتا الأهداف
flask-tg
```

مع:

```text
نوع الهدف (Target type): عناوين IP
```

### المنافذ

```text
streamlit-tg → HTTP 8501    # مجموعات الأهداف
flask-tg     → HTTP 5000
```

### لماذا نترك الأهداف فارغة؟

تتلقى مهام Fargate واجهات شبكة وعناوين IP تُرفق ديناميكيًا.

ولا ينبغي أن تثبّت عناوين IP للمهام يدويًا في تصميم المصدر.

بل:

```text
خدمة ECS
تبدأ المهمة
   ↓
تحصل المهمة على واجهة شبكة/IP
   ↓
تسجّل الخدمة IP المهمة في مجموعة الأهداف
```

وعندما تُستبدل مهمة:

```text
يُلغى تسجيل IP القديم
يُسجَّل IP الجديد
```

وهذا أساسي لفهم لماذا لا يمكن للحوسبة بلا خوادم وتنسيق حاويات (container orchestration) الاعتماد على عناوين backend ثابتة يدويًا.

## 6. أنشئ Application Load Balancer وقواعد المضيف

ينشئ المصدر:

```text
ecs-fargate-alb    # اسم موازن الحمل
```

بوصفه:

```text
Internet-facing (مواجه للإنترنت)
IPv4
مناطق توافر متعددة (Availability Zones)
```

### لماذا مناطق توافر متعددة؟

يريد المصدر أن تتمكن مهام Fargate المجدولة عبر الشبكات الفرعية/مناطق التوافر المفعّلة من التسجيل خلف الـ ALB.

### الـ listener الأولي

يبدأ بـ:

```text
HTTP :80
```

### امنع استخدام DNS الافتراضي لـ ALB

يغيّر المصدر الإجراء الافتراضي للـ listener إلى:

```text
إرجاع استجابة ثابتة (Return fixed response)
403
```

مع رسالة توجّه المستخدمين إلى النطاق المخصص الرسمي.

وهذا ينشئ:

```text
مضيف غير مطابق / عنوان DNS المباشر لـ ALB
→ 403
```

### التوجيه بحسب المضيف

يضيف المصدر:

```text
المضيف (Host) = streamlit.<domain>
→ streamlit-tg

المضيف (Host) = flask.<domain>
→ flask-tg
```

### نموذج التوجيه

```text
ALB :80
  |
  +-- المضيف flask.domain
  |      → flask-tg
  |
  +-- المضيف streamlit.domain
  |      → streamlit-tg
  |
  +-- أي شيء آخر
         → 403
```

[[IMAGE_NEEDED: ALB host-based routing | A diagram showing one ALB listener with three rules: flask hostname → flask-tg, streamlit hostname → streamlit-tg, default/unmatched → fixed 403 | Learner should notice that the ALB replaces the earlier Nginx host-routing layer]]

## 7. افهم ECS cluster وtask definitions وtasks وservices

ينشئ المصدر ECS cluster مع اختيار:

```text
Fargate    # نموذج الحوسبة المختار
```

نموذجًا للحوسبة.

### الـ Cluster

الـ cluster هو البيئة المنطقية التي تعمل فيها خدمات/مهام ECS.

### تعريف المهمة (Task definition)

يقارن المصدر تعريف المهمة بـ:

```text
تصريح على نمط docker-compose
```

لحِمل عمل واحد.

ويحدّد:

- عنوان URI للصورة،
- CPU،
- memory،
- منفذ الحاوية،
- دور التنفيذ (execution role).

### تعريف مهمة Streamlit

إعدادات المصدر:

```text
1 vCPU
3 GB من الـ memory
المنفذ 8501
```

### تعريف مهمة Flask

إعدادات المصدر:

```text
2 vCPU
4 GB من الـ memory
المنفذ 5000
```

### المهمة (Task)

**المهمة (task)** هي نسخة قيد التشغيل من تعريف المهمة.

### الخدمة (Service)

تُبقي الخدمة عددًا مطلوبًا من المهام قيد التشغيل وتدمجها مع الشبكات/موازنة الحمل.

النموذج الذهني:

```text
Task definition (تعريف المهمة)
   ↓ قالب للتشغيل
Task (المهمة)
   ↓ نسخة واحدة قيد التشغيل
Service (الخدمة)
   ↓ تحافظ على N نسخة + تسجيل ALB
Cluster
   ↓ بيئة ECS منطقية
```

## 8. أنشئ خدمات Fargate واربطها بـ ALB

ينشئ المصدر خدمة واحدة لكل تطبيق.

### خدمة Flask

الخيارات الأساسية في المصدر:

```text
تعريف المهمة (task definition): flask-app
مجموعة الأمان (security group): ecs-sg-tasks
موازن الحمل (load balancer): ecs-fargate-alb
مجموعة الأهداف (target group): flask-tg
```

### خدمة Streamlit

تستخدم:

```text
تعريف المهمة (task definition): streamlit-app
مجموعة الأمان (security group): ecs-sg-tasks
موازن الحمل (load balancer): ecs-fargate-alb
مجموعة الأهداف (target group): streamlit-tg
```

### التسجيل التلقائي

عندما تطلق الخدمة المهام:

```text
تبدأ المهمة
→ تحصل المهمة على IP
→ ECS يسجّل الهدف
→ يمكن لـ ALB استخدامه في فحوصات الصحة/التوجيه
```

ولهذا تُركت مجموعات الأهداف فارغة عند إنشائها.

## 9. راقب مخرجات الحاوية عبر CloudWatch

يشرح المصدر أن مخرجات الحاوية تُوجَّه إلى:

```text
CloudWatch Logs (سجلات CloudWatch)
```

وهذا يتضمن:

- رسائل بدء التشغيل،
- التحذيرات،
- سجلات الطلبات،
- الأخطاء،
- stdout،
- stderr.

### لماذا يهمّ هذا في Fargate

لا يوجد مضيف EC2 ينبغي أن تدخله عبر SSH لتصحيح التطبيقات الروتيني.

بل:

```text
مهمة Fargate
   ↓ stdout/stderr
CloudWatch Logs (سجلات CloudWatch)
   ↓
المهندس يحقق في الأمر
```

ويشير المصدر أيضًا إلى أن تبويب **Logs** في خدمة ECS يعرض مجرى السجلات نفسه للتيسير.

## 10. وجّه أسماء المضيفين المخصصة إلى ALB وأضف TLS عبر ACM

يحدّث المصدر DNS بحيث:

```text
flask    # اسما النطاقين الفرعيين
streamlit
```

يُحلّان إلى اسم DNS الذي يولّده ALB عبر أسلوب السجل الخاص بالمزوّد الموصوف في الفصل.

### دور DNS

يوصل DNS الطلب إلى ALB فقط.

وتقرر قواعد المضيف في ALB أي تطبيق يستقبله.

### استورد الشهادة إلى ACM

يعيد المصدر استخدام الشهادة المشتراة/المجهّزة سابقًا.

ويستورد:

```text
نص الشهادة (certificate body)
المفتاح الخاص (private key)
سلسلة الشهادات (certificate chain)
```

إلى AWS Certificate Manager.

### المتطلب الإقليمي

يؤكد المصدر:

> يجب أن توجد شهادة ACM في منطقة AWS نفسها التي يوجد فيها ALB.

وإلا فلن تظهر بوصفها شهادة متاحة للـ listener.

### أضف HTTPS listener

يضيف المصدر:

```text
HTTPS :443
```

ويربط شهادة ACM.

ويعيد إنشاء قواعد المضيف نفسها:

```text
flask.domain    # اسم المضيف
→ flask-tg

streamlit.domain
→ streamlit-tg
```

ويُبقي الافتراضي:

```text
403
```

### تحديث security group الخاص بـ ALB

يغيّر المصدر نقطة الدخول العامة من:

```text
HTTP 80
```

إلى:

```text
HTTPS 443
```

مع الحفاظ على نطاق CIDR المصدري الموثوق.

[[IMAGE_NEEDED: HTTPS ALB termination | A diagram showing browser HTTPS → ALB port 443 with ACM certificate → host rule → Flask or Streamlit target group → Fargate task over internal application port | Learner should notice that TLS terminates at the ALB rather than inside the application container]]

## 11. أعد إنشاء الخدمات عند التحول إلى HTTPS listener

يذكر المصدر أنه، في سير عمل وحدة التحكم لديه، لا يستطيع ببساطة استبدال listener موازن الحمل في الخدمة في مكانه.

لذلك ينفّذ:

```text
المهام المطلوبة (desired tasks) → 0
انتظر حتى 0/0
حذف الخدمة
إعادة إنشاء الخدمة
```

وتبقى مجموعات الأهداف كما هي.

وما يتغير فقط هو الـ listener المختار من:

```text
HTTP :80
```

إلى:

```text
HTTPS :443
```

### لماذا نخفض إلى الصفر أولًا؟

يستخدم المصدر ذلك لإيقاف المهام النشطة بسلاسة قبل حذف الخدمة/إعادة إنشائها.

### الاختبار النهائي

تصبح نقاط النهاية المتوقعة:

```text
https://flask.<domain>    # عناوين مثالية
https://streamlit.<domain>
```

## 12. وسّع Fargate بحجم المهمة وعدد المهام

للسعة في Fargate بُعدان في المصدر.

### التخصيص الرأسي لكل مهمة

يحدّد تعريف المهمة:

```text
vCPU
الـ memory
```

مثال:

```text
Flask:    # الحجم لكل مهمة
2 vCPU + 4 GB

Streamlit:
1 vCPU + 3 GB
```

### عدد المهام الأفقي

تحدّد الخدمة:

```text
المهام المطلوبة (desired tasks)
```

فإذا كان لدى Flask:

```text
مهمة واحدة (1 task)
→ إجمالي 2 vCPU + 4 GB
```

فإن:

```text
مهمتان (2 tasks)
→ إجمالي 4 vCPU + 8 GB
```

من الناحية المفاهيمية، بافتراض تعريف المهمة نفسه.

### التوسع اليدوي

غيّر:

```text
المهام المطلوبة (Desired tasks)
```

مباشرةً.

### التوسع التلقائي للخدمة

يفعّل المصدر التوسع التلقائي للخدمة مع:

```text
الحد الأدنى للمهام (minimum tasks)
الحد الأقصى للمهام (maximum tasks)
سياسة تتبّع الهدف (target-tracking policy)
```

ويستخدم:

```text
ECSServiceAverageCPUUtilization    # اسم المقياس
```

مقياسًا.

ويعطي المصدر مثالًا لهدف يقارب:

```text
50%
```

مع أن لقطة شاشة واحدة قد تعرض قيمة أخرى.

والمفهوم الدائم:

```text
متوسط CPU يرتفع فوق الهدف
→ إضافة مهام

متوسط CPU ينخفض بما يكفي
→ إزالة مهام
```

ضمن حدود الحد الأدنى/الأقصى المضبوطة.

### عدم اتساق في مقدمة المصدر

تصف مقدمة الفصل مرونة الحوسبة بلا خوادم بوجه عام بأنها تقليص إلى الصفر ثم توسع من جديد.

أما مثال التوسع التلقائي الفعلي لخدمة ECS لاحقًا فيضبط حدًّا أدنى لعدد المهام هو:

```text
1
```

اعتبر إعداد الخدمة الملموس هو المثال العملي.

## 13. اجمع معمارية AWS بلا خوادم الكاملة معًا

المعمارية الكاملة في المصدر هي:

```text
محطة عمل المطوّر
       ↓
بناء Docker
       ↓
مستودعات ECR
       ↓
تعريفات مهام ECS
       ↓
خدمات/مهام Fargate
       ↓
مجموعات الأهداف
       ↓
توجيه المضيف في ALB
       ↓
HTTPS listener + شهادة ACM
       ↓
نطاقات فرعية مخصصة
```

ضوابط داعمة:

```text
ملف IAM التعريفي
→ صلاحيات الـ deployment

alb-sg
→ نقطة دخول HTTPS العامة

ecs-sg-tasks
→ فقط ALB يستطيع الوصول إلى منافذ التطبيق

CloudWatch
→ سجلات التطبيق

توسع ECS التلقائي
→ يتكيّف عدد المهام مع الحمل
```

وهذا يحقق هدف المصدر في تشغيل Flask وStreamlit دون صيانة مضيفي تطبيقات EC2.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1
> "Fargate تعني أنه لا توجد حاويات."

تشغّل Fargate الحاويات؛ لكنها تزيل الحاجة إلى إدارة خوادم استضافة حاويات.

### المفهوم الخاطئ 2
> "ينبغي تسجيل عناوين IP للمهام يدويًا في مجموعات الأهداف."

يترك المصدر قوائم الأهداف فارغة لأن خدمات ECS تسجّل عناوين IP لمهام Fargate ديناميكيًا.

### المفهوم الخاطئ 3
> "ينبغي أن يسمح security group الخاص بمهام ECS للإنترنت كله."

يسمح المصدر بمنافذ التطبيقات من security group الخاص بـ ALB.

### المفهوم الخاطئ 4
> "تعريف مهمة ECS هو الشيء نفسه كمهمة قيد التشغيل."

تعريف المهمة هو المواصفة؛ أما المهمة فنسخة قيد التشغيل.

### المفهوم الخاطئ 5
> "التوجيه المعتمد على المضيف في ALB يتطلب Nginx."

يؤدي ALB نفسه التوجيه المعتمد على المضيف في هذه المعمارية.

### المفهوم الخاطئ 6
> "بيانات الاعتماد الظاهرة في المصدر المنسوخ آمنة لإعادة الاستخدام."

لا تعد استخدام بيانات اعتماد حرفية من أمثلة ولا تكشفها أبدًا. استخدم بيانات اعتماد أنشأتها بنفسك بأمان وعناصر نائبة في التوثيق.

### المفهوم الخاطئ 7
> "اسم الملف التعريفي لتسجيل الدخول إلى ECR متسق في كل أمر في المصدر."

يستخدم أحد الأوامر المنسوخة اسم ملف تعريفي مختلفًا. استخدم الملف التعريفي الذي ضبطته فعلًا.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| ECS | خدمة Amazon Elastic Container Service |
| Fargate | نموذج حوسبة بلا خوادم لمهام ECS |
| ECR | سجل حاويات مُدار من AWS |
| تعريف المهمة (Task definition) | مواصفة التشغيل لحِمل عمل في ECS |
| المهمة (Task) | نسخة قيد التشغيل من تعريف المهمة |
| خدمة ECS (ECS service) | متحكّم يحافظ على المهام المطلوبة وتكامل موازن الحمل |
| ALB | موازن الحمل للتطبيقات (Application Load Balancer) |
| مجموعة الأهداف (Target group) | مجموعة backend تتلقى حركة ALB |
| ACM | AWS Certificate Manager |
| سجلات CloudWatch (CloudWatch Logs) | نظام التسجيل المركزي الذي يستخدمه المصدر |
| تتبّع الهدف (Target tracking) | سياسة توسع تحاول إبقاء مقياس حول هدف |
| المهام المطلوبة (Desired tasks) | عدد نسخ مهام الخدمة التي تحاول ECS إبقاءها قيد التشغيل |
