## 1. ما تحليل البيانات حقًا؟ (What Data Analysis Really Is)

تحليل البيانات ليس مجرد تشغيل query والإبلاغ عن رقم. يبدأ التحليل المفيد بسؤال، ثم يبحث في الأدلة، ويفسر ما تعنيه هذه الأدلة، وينقل النتيجة بوضوح حتى يتمكن شخص أو نظام من اتخاذ قرار أفضل.

نموذج ذهني مفيد هو:

```text
سؤال (Question) -> بيانات (Data) -> استقصاء (Investigation) -> تفسير (Interpretation) -> تواصل (Communication) -> قرار (Decision)
```

الجزء التقني مهم، لكن التفكير المحيط بالعمل التقني مهم بالقدر نفسه. يحتاج analyst إلى الفضول: لماذا انخفضت المبيعات؟ لماذا يغادر المستخدمون؟ لماذا تحسن conversion في سوق وانخفض في سوق آخر؟ الأرقام أدلة، وليست استنتاجات نهائية.

يجمع تحليل البيانات الحديث بين computing وأفكار من statistics وغيرها من التخصصات الكمية. وفي الممارسة العملية، يتكون العمل غالبًا من ثلاثة أجزاء مترابطة:

1. **الاكتشاف (Discovery)** — العثور على patterns وanomalies وrelationships والتغيرات المفيدة في البيانات.
2. **التفسير (Interpretation)** — تحديد ما الذي قد تعنيه هذه الأنماط في السياق الواقعي الذي أنتج البيانات.
3. **التواصل (Communication)** — عرض النتيجة بوضوح كافٍ لكي يستطيع شخص ما التصرف بناءً عليها.

تستخدم المؤسسات تسميات مختلفة مثل **analytics** و**business intelligence (BI)** و**data science** و**decision science**. كما تختلف المسميات الوظيفية. المهم هو النشاط الأساسي نفسه: استخدام الأدلة لفهم ما حدث ودعم قرارات أفضل.

[[IMAGE_NEEDED: IMG-M01-L01-01 / Instructor Figure — Data analysis as a decision loop | A circular workflow showing business question -> collect or locate data -> explore/analyze -> interpret -> communicate -> decision/action -> new questions | Learner should notice that analysis is iterative and decision-oriented, not a one-time calculation]]

### البيانات التاريخية مفيدة، لكنها ليست سحرية

يعمل analysts عادةً مع observations حدثت بالفعل. تستطيع historical data كشف سلوك العملاء ونقاط الضعف في العمليات والفجوات التشغيلية وأنماط الاحتيال والفرص. كما يمكنها دعم forecasts ونطاقات للنتائج المحتملة.

لكن الماضي ليس مضمونًا أن يكرر نفسه. تتغير المنتجات والمنافسون والسياسات وتفضيلات المستخدمين، وتقع أحداث غير متوقعة. لذلك يفرّق analyst الجيد بين عبارتين:

- **تُظهر البيانات أن هذا حدث في الماضي.**
- **نتوقع أن يحدث شيء مشابه في المستقبل.**

يمكن دعم العبارة الأولى مباشرةً بواسطة historical data. أما الثانية فهي prediction وتتطلب assumptions.

### التحليل مهارة بشرية أيضًا

لا تكون query أنيقة ذات قيمة كبيرة إذا كانت النتيجة مربكة أو لا يمكن اتخاذ إجراء بناءً عليها. في المؤسسات الحقيقية، قد يحقق تحليل بسيط يُشرح بصورة مقنعة تأثيرًا أكبر من method متطورة لا يفهمها stakeholders. يعتمد analysts أيضًا على التعاون: يجب أن يثق شخص ما في النتيجة وأن يكون قادرًا على تنفيذ recommendation.

ينتمي ethics إلى هذا النموذج الذهني منذ البداية. ليس كل ما يمكن جمعه من data ينبغي جمعه. تؤثر المعلومات الحساسة وprivacy وconsent وretention واللوائح في شكل التحليل المسؤول.

## 2. SQL وبنية قاعدة البيانات

ترمز **SQL** إلى **Structured Query Language**. والغرض الأساسي منها هو التواصل مع البيانات المخزنة داخل database systems. ليست SQL general-purpose programming language مثل Python، لكنها قوية جدًا عند التعامل مع structured data داخل databases.

نشأت SQL من relational model، حيث تُمثل المعلومات من خلال tables مترابطة. أعطت standards اللغة أساسًا مشتركًا، لكن database vendors أضافوا functions وسلوكيات خاصة بهم. لهذا تبدو SQL المكتوبة لـ PostgreSQL أوSQL Server أوOracle أوSnowflake أوغيرها مألوفة، مع استمرار وجود اختلافات. تسمى هذه الاختلافات غالبًا **SQL dialects**.

لكي تعمل بثقة مع SQL، افهم أولًا الكائنات التي تتعامل معها.

| الكائن | ما معناه | لماذا يهم Analyst |
|---|---|---|
| قاعدة البيانات (Database) | بيئة مُدارة تحتوي على البيانات المخزنة والكائنات المرتبطة بها | هي النظام الأساسي الذي تتصل به SQL |
| المخطط (Schema) | حاوية منطقية لتنظيم database objects | تساعدك على العثور على tables الصحيحة وتجنب تعارض الأسماء |
| الجدول (Table) | rows وcolumns تخزن records فعليًا | المصدر الأكثر شيوعًا الذي يُستعلم منه أثناء التحليل |
| العرض (View) | query محفوظة تظهر كما لو كانت table | يمكنها تبسيط logic متكرر أوعرض data منسقة |
| الدالة (Function) | database logic أوcalculations قابلة لإعادة الاستخدام | تسمح للـ queries بإعادة استخدام عمليات تُنفذ داخل database |
| الفهرس (Index) | بنية تسرع بعض عمليات lookup | يمكن أن تجعل filters وjoins أسرع كثيرًا في row-oriented systems |

## 3. اللغات الفرعية الأربع في SQL

تُجمع أوامر SQL عادةً في أربع عائلات. يقضي analysts معظم وقتهم في querying، لكن فهم المجموعات الأربع يجعل التواصل مع database administrators وdata engineers أسهل كثيرًا.

| اللغة الفرعية | الغرض | الأوامر الشائعة |
|---|---|---|
| **DQL** — لغة الاستعلام عن البيانات (Data Query Language) | قراءة البيانات وتحليلها | `SELECT` |
| **DDL** — لغة تعريف البيانات (Data Definition Language) | إنشاء بنية database أو تغييرها | `CREATE`, `ALTER`, `DROP` |
| **DCL** — لغة التحكم في البيانات (Data Control Language) | إدارة permissions | `GRANT`, `REVOKE` |
| **DML** — لغة معالجة البيانات (Data Manipulation Language) | تغيير records المخزنة | `INSERT`, `UPDATE`, `DELETE` |

### DQL: طرح الأسئلة

تمثل DQL قلب SQL التحليلية. تستطيع query من نوع `SELECT` قراءة table واحدة، أو دمج tables كثيرة باستخدام joins، أوaggregate ملايين rows، ثم إعادة نتيجة صغيرة تجيب عن business question.

### DDL: تغيير البنية

تعمل DDL على objects وليس على business records الفردية. ومن الأمثلة العملية إنشاء temporary analysis table.

يغيّر `ALTER` بنية object موجود، بينما يحذف `DROP` الـ object نفسه.

### DCL: التحكم في الوصول

قد تحتوي database على table موجودة لكنها غير مرئية أوغير متاحة لحسابك. تحدد permissions ما إذا كان يمكنك قراءتها أوتعديلها. يضيف `GRANT` permission، بينما يزيلها `REVOKE`.

### DML: تغيير Records

تعمل DML على data داخل tables. يضيف `INSERT` rows، ويغير `UPDATE` القيم الموجودة، ويحذف `DELETE` rows. قد يستخدم analyst أوامر DML عند إدارة temporary tables أوsandboxes أوanalytical datasets التي يملكها.

### اختلافات SQL Dialects مهمة

البنية الأساسية لـ SQL مشتركة على نطاق واسع، لكن التفاصيل تختلف. عند الانتقال بين database systems، انتبه خصوصًا إلى:

- التعامل مع null
- date وtimestamp functions
- integer division
- case sensitivity
- vendor-specific functions وsyntax

يمنحك تعلم standard SQL أساسًا قابلًا للنقل؛ بينما يعلمك تعلم dialect كيف يعبر engine معين عن التفاصيل.

## 4. لماذا ما زالت SQL مفيدة جدًا للتحليل؟

استمرت SQL لعقود لأنها تحل عدة مشكلات عملية في الوقت نفسه.

### 4.1 غالبًا ما تكون البيانات موجودة بالفعل داخل Database

تنتج المؤسسات operational data باستمرار: orders وusers وpayments وevents وinventory وsupport tickets وغير ذلك. إذا كانت data موجودة بالفعل في database أوwarehouse، تعمل SQL بالقرب من المصدر بدلًا من إجبار analyst على export كل شيء أولًا.

### 4.2 تنفذ Database العمليات الحسابية الثقيلة

تعمل query عادةً على database server أوdata warehouse. وقد يمتلك هذا server ذاكرة وCPU وstorage bandwidth أكبر كثيرًا من laptop الخاص بـ analyst. بدلًا من تنزيل مليارات records ومعالجتها محليًا، تستطيع SQL إجراء aggregation بالقرب من data وإعادة النتيجة فقط.

### 4.3 تتصل SQL ببقية Analytics Ecosystem

يمكن لـ BI tools وspreadsheets وvisualization systems وPython وR جميعًا الاتصال بـ SQL databases. لهذا تصبح SQL غالبًا الطبقة المشتركة التي تجهز data قبل أن تعرضها أوتقوم بنمذجتها أداة أخرى.

### 4.4 Syntax صغيرة نسبيًا تستطيع التعبير عن أسئلة كثيرة

يمكن دمج مجموعة صغيرة نسبيًا من المفاهيم — selection وfiltering وgrouping وjoining وsorting وconditional logic وwindow calculations — بطرق كثيرة. كما أن SQL iterative بطبيعتها: اكتب query صغيرة، افحص النتيجة، ثم حسّنها.

### 4.5 SQL سهلة البدء

أول queries المفيدة بسيطة بما يكفي ليتعلمها المبتدئون بسرعة. ما زال mastery يحتاج وقتًا لأن datasets الحقيقية فوضوية وbusiness questions قد تكون غامضة، لكن حاجز البداية منخفض نسبيًا.

## 5. SQL مقابل Python أوR

السؤال الأكثر فائدة ليس *أي لغة هي الأفضل؟* بل *أي أداة تناسب هذا الجزء من العمل؟*

| الاعتبار | SQL | Python / R |
|---|---|---|
| مكان التنفيذ المعتاد | Database أوwarehouse | غالبًا local machine أوnotebook أوapplication server |
| بنية البيانات الطبيعية | Tables تحتوي rows وcolumns | Tables إلى جانب lists وdictionaries وarrays وobjects وغيرها |
| Aggregation لبيانات Database كبيرة | ممتازة | غالبًا الأفضل بعد query لاستخراج data المطلوبة فقط |
| Loops وgeneral program flow | محدودة في standard analytical SQL | طبيعية ومرنة |
| Statistics وmachine learning | من أساسية إلى متوسطة حسب vendor | ecosystems وlibraries غنية |
| العمل المباشر مع local files وweb APIs | غالبًا بصورة غير مباشرة | ممتاز |
| تحديث Dashboards بصورة متكررة | ممتاز عندما تكون data داخل database | غالبًا مكملة لـ SQL |

### أين يعمل Code؟

## 6. SQL داخل Workflow تحليل البيانات من البداية إلى النهاية

SQL قوية، لكنها جزء واحد فقط من workflow أوسع. يمر analysis المعتاد عبر عدة مراحل.

### المرحلة 1: صياغة السؤال

تشمل الأمثلة:

- كم عدد العملاء الجدد الذين اكتسبناهم هذا الشهر؟
- هل revenue تنمو أم تنخفض؟
- أي users يظلون active بعد 90 يومًا؟
- أين تزداد operational failures؟

السؤال الغامض ينتج analysis غامضًا. قبل كتابة SQL، عرّف metric وpopulation وtime range والقرار المقصود كلما أمكن.

### المرحلة 2: Source Systems تنتج Data

Source systems هي العمليات البشرية أوالآلية التي تنتج الأدلة الخام. من أمثلتها checkout applications وwebsite event trackers وmarketing systems وforms وsupport systems وoperational databases.

### المرحلة 3: نقل Data إلى Analytical Storage

تجمع المؤسسات data غالبًا داخل **data warehouse**. وقد تسمى warehouse أصغر مخصصة لموضوع واحد **data mart**. أما بيئة التخزين الأوسع المبنية على files أوdata قليلة التحويل فقد تسمى **data lake**.

تُوصف عملية النقل عادةً باسم **ETL** أو**ELT**:

```text
ETL: Extract -> Transform -> Load — استخلاص ثم تحويل ثم تحميل
ELT: Extract -> Load -> Transform — استخلاص ثم تحميل ثم تحويل
```

في ETL يحدث transformation قبل final load. أما في ELT فتُحمّل raw data أوdata المعالجة بدرجة بسيطة أولًا، ثم تُحوّل داخل destination system — وغالبًا باستخدام SQL.

{{image:data-analysis-process-steps}}

### المرحلة 4: Query والتحليل

بعد توفر data، يدور العمل التحليلي عادةً بين خمسة أنشطة:

1. **الاستكشاف (Explore)** — معرفة tables وfields وbusiness processes الموجودة.
2. **الفحص (Profile)** — فحص distributions وdistinct values وranges وmissingness وrecords المشبوهة.
3. **التنظيف (Clean)** — إصلاح الأخطاء وnulls وcategories غير المتسقة وrecords غير المكتملة أوالتعامل معها.
4. **التشكيل (Shape)** — ترتيب data في rows وcolumns وcategories وmetrics المطلوبة للسؤال.
5. **التحليل (Analyze)** — فحص patterns وإنتاج conclusions أوinsights.

{{image:query-analysis-stages}}

### المرحلة 5: عرض النتيجة

يحتاج stakeholders عادةً إلى explanation أوchart أوdashboard أوrecommendation أوdownstream dataset — وليس SQL source code نفسه. أحيانًا تُمرر نتيجة SQL إلى BI tool. وفي حالات أخرى، تصبح input لـ statistical software أوmachine learning workflow.

لذلك يميز workflow بين نوعين مختلفين من الجودة:

- **الصحة التقنية (Technical correctness):** تحسب query ما كنت تقصده فعلًا.
- **فائدة القرار (Decision usefulness):** تساعد المخرجات الجمهور على الفهم والتصرف.

## 7. قواعد بيانات Row-Store مقابل Column-Store

لفهم database performance، تحتاج إلى فكرة مادية واحدة: قد تبدو table لك كشبكة، لكن database يجب أن تسلسل هذه values من أجل التخزين. تؤثر طريقة تجميع القيم بقوة في أنواع workloads التي ستكون سريعة.

### قواعد بيانات Row-Store

يضع row-store القيم الخاصة بـ row واحدة بالقرب من بعضها. هذا ممتاز للأنظمة transactional التي تدخل applications فيها records كاملة أوتحدثها أوتحذفها أوتسترجعها باستمرار. PostgreSQL وMySQL مثالان شائعان على row-oriented systems.

```text
الصف 1: [order_id=101, customer=7, date=..., amount=120]
الصف 2: [order_id=102, customer=9, date=..., amount=85 ]
الصف 3: [order_id=103, customer=7, date=..., amount=210]
```

إذا أرادت application order واحدة، تكون قراءة row كاملة مناسبة. لكن إذا أراد analyst عمود `amount` فقط عبر مئات الملايين من rows، فقد يضطر النظام إلى قراءة data أخرى غير مرتبطة أكثر مما يلزم.

[[IMAGE_NEEDED: IMG-M01-L01-07 / Source Figure 1-4 — Row-wise physical storage | A table on the left and disk blocks on the right showing all values from each row stored together sequentially | Learner should notice why row-oriented storage is efficient for retrieving or updating complete records]]

### Normalization والتعقيد التحليلي

غالبًا ما تُنمذج transactional databases بحيث لا تُخزن الحقيقة نفسها إلا مرة واحدة. يقلل هذا duplication وعدم الاتساق، لكنه قد ينشئ tables كثيرة ضيقة ومترابطة. لذلك قد تحتاج analytical queries إلى عدة joins لإعادة بناء dataset سهلة الفهم للأعمال.

يحدد **primary key** record بصورة فريدة. وقد تمتلك table أيضًا **composite key** أو**business key** مكوّنًا من عدة columns ذات معنى. تسرع **indexes** بعض lookups وjoins، لكنها تستهلك storage وقد تجعل writes أغلى لأن index يجب أن تُحدّث.

### Star Schemas

تستخدم designs الموجهة إلى analytics غالبًا **star schema**:

- تسجل **fact table** events أوmeasurements مثل orders أوtransactions.
- تصف **dimension tables** الكيانات المحيطة بهذه events مثل customers وproducts وlocations.

توسع **snowflake schema** هذه الفكرة عبر زيادة normalization لبعض dimensions.

[[IMAGE_NEEDED: IMG-M01-L01-08 / Instructor Figure — Star schema for sales analytics | A central sales fact table connected to customer, product, date, and store dimension tables | Learner should notice that analytical models organize events in the center and descriptive context around them]]

### قواعد بيانات Column-Store

يضع column-store القيم الخاصة بالـ column نفسها معًا. يناسب هذا design analytical workloads التي تفحص records كثيرة لكنها تستخدم subset فقط من columns. ترتبط أنظمة مثل Snowflake وAmazon Redshift وVertica بالـ column-oriented analytical storage.

```text
order_id:    [101, 102, 103, ...] — قيم العمود متجاورة
customer_id: [7,   9,   7,   ...]
amount:      [120, 85,  210, ...]
```

يتيح column-oriented storage أيضًا compression قويًا لأن القيم المتجاورة غالبًا ما تتكرر أوتتبع patterns متشابهة. يمكن تمثيل categories المتكررة بصورة مضغوطة بدلًا من تخزين النص الطويل نفسه مرة بعد مرة.

[[IMAGE_NEEDED: IMG-M01-L01-09 / Instructor Figure — Row-store versus column-store | Side-by-side disk layouts of the same table: left stores complete rows together, right stores each column together; highlight an analytics query reading only the amount column | Learner should notice that the column-store reads far less irrelevant data for column-focused aggregation]]

تبادل column stores بعض سهولة الاستخدام transactional مقابل analytical speed. قد تكون updates وdeletes مكلفة، وتتطلب data quality عناية لأن analytical systems قد لا تفرض uniqueness بالطريقة نفسها التي تفعلها transactional databases. كما قد يعتمد performance على sort order وpartitioning وcompression وكيفية تنفيذ joins بين tables الكبيرة.

### المفاضلة الأساسية

| Workload | ما يلائمه Row-Store غالبًا | ما يلائمه Column-Store غالبًا |
|---|---|---|
| عمليات insert/update صغيرة ومتكررة | قوي | غالبًا أقل ملاءمة |
| استرجاع record كاملة واحدة | قوي | ليس عادةً هدف optimization الأساسي |
| فحص ملايين rows باستخدام بضعة columns | قد يكون مكلفًا | قوي |
| Aggregations كبيرة | ممكن وغالبًا يعتمد على tuning | ممتاز عادةً |
| Compression للقيم التحليلية المتكررة | متوسط | ممتاز غالبًا |

## 8. Data Lakes وHadoop وNoSQL وSearch-Oriented Stores

لا تعيش كل analytical data داخل relational database تقليدية. تستخدم المؤسسات الحديثة غالبًا عدة storage technologies لأن workloads المختلفة تحتاج إلى مفاضلات مختلفة.

### Data Lakes والتخزين الموزع للملفات

تخزن data lake عادةً أحجامًا كبيرة من files، وغالبًا قبل تحويل data إلى schemas المنسقة المتوقعة في warehouse. ساعدت distributed file systems مثل HDFS في Hadoop المؤسسات على تخزين datasets ضخمة عبر تقسيم files إلى blocks وتوزيعها على machines كثيرة. ثم يمكن إرسال computation إلى machines التي تحمل data حتى يُنفذ العمل بالتوازي.

جعل هذا النهج large-scale storage أقل تكلفة، رغم أن Hadoop ecosystems المبكرة احتاجت إلى مهارات متخصصة وقد تكون بطيئة في interactive analysis. أضافت أدوات لاحقة SQL أوSQL-like interfaces وحسّنت query performance.

### أنظمة NoSQL

يشير **NoSQL** إلى data systems غير المقيدة بنموذج relational tables فقط. تشمل العائلات المهمة:

- **Key-value stores** للوصول السريع جدًا باستخدام key.
- **Document stores** لـ records مرنة مثل JSON-like documents.
- **Graph databases** للعلاقات الممثلة في nodes وedges.

غالبًا ما تُصمم هذه الأنظمة من أجل application performance بدلًا من scan أعداد هائلة من records لحساب analytical summaries. لذلك قد تُنقل نسخ تحليلية من data الخاصة بها إلى warehouse. تمثل graph databases استثناءً للأسئلة المعتمدة بكثافة على العلاقات، حيث يمكن أن تكون specialized graph query languages مفيدة.

### مخازن موجهة للبحث (Search-Oriented Stores)

تستخدم أنظمة مثل Elasticsearch وSplunk كثيرًا للـ logs وmachine-generated events. تكمن قوتها في البحث والتحقيق السريع — العثور على events أوpatterns محددة داخل stream كبيرة. تستطيع دعم analytics، لكنها optimized بطريقة مختلفة عن warehouse تجمع tables كبيرة باستمرار.

[[IMAGE_NEEDED: IMG-M01-L01-10 / Instructor Figure — Modern analytical storage landscape | A comparison diagram with relational row-store, column-store warehouse, data lake/distributed files, NoSQL, and search store, each labeled with its typical strength | Learner should notice that storage technologies coexist because they optimize for different access patterns]]

### لماذا تظهر SQL مرة بعد مرة؟

من patterns المهمة في الصناعة أن storage systems التي أُنشئت خارج العالم relational التقليدي غالبًا ما تضيف SQL-compatible query layers. السبب عملي: SQL مألوفة، وقوية في tabular analysis، ومدمجة بالفعل مع ecosystem واسعة من analytical tools.

## مفاهيم خاطئة مهمة (Important Misconceptions)

### المفهوم الخاطئ 1

> تحليل البيانات يتعلق أساسًا بحساب metric الصحيحة.

### لماذا هذا خطأ؟

حتى metric الصحيحة قد تقود إلى قرار سيئ إذا كانت صياغة السؤال ضعيفة أوفهم data خاطئًا أوالتفسير ضعيفًا أوالتواصل سيئًا. التحليل reasoning process من البداية إلى النهاية.

### المفهوم الخاطئ 2

> تتنافس SQL وPython، لذلك ينبغي لـ analyst اختيار واحدة وتجنب الأخرى.

### لماذا هذا خطأ؟

غالبًا ما تحلان أجزاء مختلفة من workflow نفسها. SQL ممتازة لاسترجاع relational data وaggregation بالقرب من database. وتضيف Python وR general programming وstatistical وmachine-learning capabilities.

### المفهوم الخاطئ 3

> Database أسرع تعني أن SQL logic نفسها لا تهم.

### لماذا هذا خطأ؟

ما زالت physical storage وsorting وindexing وtable size وjoins وfilters وquery structure تؤثر في مقدار العمل الذي يجب على engine تنفيذه. يساعدك فهم النظام على كتابة analysis أكثر كفاءة.

## المصطلحات الأساسية (Key Terminology)

| المصطلح | المعنى |
|---|---|
| Data analysis | استخدام data لاكتشاف الأدلة وتفسيرها والتواصل بها من أجل اتخاذ القرارات |
| SQL | Structured Query Language المستخدمة للتعامل مع database systems |
| SQL dialect | اختلاف خاص بـ vendor في SQL syntax أوالسلوك |
| Schema | حاوية منطقية تنظم database objects |
| Table | data مخزنة في rows وcolumns |
| View | query محفوظة يمكن الاستعلام منها بطريقة مشابهة لـ table |
| Index | بنية مساعدة تسرع بعض lookups وjoins |
| DQL | عائلة querying، وبصورة أساسية `SELECT` |
| DDL | أوامر تنشئ database structure أوتغيرها |
| DCL | أوامر تدير database permissions |
| DML | أوامر تدخل records أوتحدثها أوتحذفها |
| ETL | Extract ثم Transform ثم Load للبيانات |
| ELT | Extract ثم Load ثم Transform داخل destination |
| Data warehouse | مستودع تحليلي مركزي يجمع data الخاصة بالمؤسسة |
| Data mart | مستودع تحليلي أصغر ومركز على موضوع محدد |
| Data lake | بيئة تخزين كبيرة، غالبًا مبنية على files وأقل تحويلًا من warehouse |
| Row-store | database layout تخزن القيم التابعة لـ row نفسها معًا |
| Column-store | database layout تخزن القيم التابعة لـ column نفسها معًا |
| Primary key | field أوfields تحدد row بصورة فريدة |
| Composite key | عدة fields يحدد اجتماعها row |
| Fact table | analytical table تحتوي events أوmeasurements |
| Dimension table | descriptive table توفر context للـ facts |
| NoSQL | تقنيات تخزين data غير relational أوnot-only-relational |

## المراجعة الذاتية (Self-Check)

قبل المتابعة، تأكد أنك تستطيع الإجابة عن الآتي:

1. لماذا تحليل البيانات أكثر من مجرد إنتاج رقم صحيح؟
2. ما الفرق بين table وview وindex؟
3. أي عائلة من أوامر SQL تستخدم للاستعلام عن data أوتعديل table structure أوإدارة permissions أوتغيير records؟
4. اذكر موقفًا تكون فيه SQL هي الاختيار الطبيعي الأول، وآخر تكون فيه Python أوR أنسب.
5. اشرح ETL وELT بكلماتك.
6. لماذا قد يكون column-store أسرع من row-store في query تجمع numeric column واحدة عبر ملايين rows؟
7. لماذا قد تُنسخ data من NoSQL application إلى relational warehouse من أجل التحليل؟
8. ما الفرق بين technical correctness وdecision usefulness؟
