## 1. نظام ML أكبر من Model نفسها

عندما يتعلم الناس Machine learning لأول مرة، من الطبيعي أن يركزوا على Algorithms مثل Logistic regression و Decision trees و Neural networks و Transformers وغيرها. لكن في Production، لا تكون Algorithm سوى Component واحدة داخل System أكبر بكثير.

يبدأ Production ML system بـ **Business أو Product requirement**. ثم يحتاج إلى Interface يتفاعل من خلالها Users أو Services أخرى، و Data stack تجمع المعلومات وتحولها، و Model-development logic، و Deployment infrastructure، و Monitoring، و Maintenance، و Process لتحديث Model عندما يتغير العالم أوتتغير Data.

نموذج ذهني مفيد هو:

```text
المشكلة / الهدف
       ↓
Data → تطوير Model → Deployment → خدمة Prediction
  ↘          ↓                ↓             ↙
   جودة Data         Monitoring / Maintenance
             ↘        ↓        ↙
             Updates وIteration
```

الفكرة المهمة هي أن Model شديدة الدقة قد تفشل رغم ذلك كـ Product إذا تعطلت Data pipeline، أووصلت Predictions ببطء شديد، أوعجز System عن Scaling، أولم يلاحظ أحد تدهور سلوكها.

[[IMAGE_NEEDED: Components of a production ML system | A clean systems diagram showing business requirements, user or API interface, data stack, model development, deployment infrastructure, prediction serving, monitoring, and model/data updates as connected components | Learner should notice that the ML algorithm is only one component inside a larger feedback-driven system]]

### MLOps و ML systems design

يصف الفصل **MLOps** بأنها Tools و Best practices لجلب ML إلى Production، بما يشمل Deployment و Monitoring و Maintenance. أما **ML systems design** فتتبنى رؤية أوسع للنظام: فهي تسأل كيف تعمل جميع Components و Stakeholders معًا لتحقيق Objectives و Requirements الخاصة بالنظام.

لذلك، بدل أن نسأل فقط *أي Model ينبغي أن أدرب؟*، تسأل Systems thinking أيضًا:

- ما Problem التي نحاول حلها؟
- ما Data المتاحة لدينا، وكيف ستتغير؟
- من يعتمد على Predictions؟
- ما السرعة المطلوبة لوصول Answer؟
- ماذا يحدث عندما تكون Model مخطئة؟
- كيف سنكتشف Degradation؟
- كيف سنحدّث System بأمان؟

## 2. متى تكون Machine learning مناسبة؟

Machine learning قوية، لكن الفصل يحذر بشدة من التعامل معها كحل شامل لكل Problem. السؤال الأول المفيد ليس *هل تستطيع ML حل هذا؟* بل *هل ML ضرورية وفعالة من حيث التكلفة لهذه Problem؟*

يقدم الفصل صياغة مختصرة:

> تتعلم Machine learning أنماطًا معقدة من Data موجودة وتستخدم تلك الأنماط لإجراء Predictions على Unseen data.

يفرض كل جزء من هذه الجملة Requirement.

### 2.1 يجب أن يكون System قادرًا على التعلم

Lookup table ليست ML system لأن العلاقة تُكتب صراحةً بواسطة Programmer. أما ML system فتستنتج Relationship من Examples.

في Supervised learning، تحتوي هذه Examples عادةً على Inputs مع Desired outputs. فإذا أردت Predict لسعر إيجار Property، فقد تتضمن Input الحجم وعدد الغرف والمنطقة و Amenities و Rating، بينما تكون Output هي Rental price المرصودة. تتعلم System Mapping من هذه Examples ثم تطبقها على Listing جديدة.

### 2.2 يجب أن يوجد Pattern، وأن تكون معقدة بما يكفي لتبرير ML

إذا لم توجد Learnable pattern، فلن تستطيع ML اختراعها. Predict للنتيجة التالية لنرد عادل غير مفيد لأن Sequence نفسها لا تحتوي Pattern قابلة للاستغلال.

وعلى الطرف الآخر، إذا كانت Pattern بسيطة ومعروفة، فقد تكون ML غير ضرورية. فإذا كان Zip code يرتبط Deterministically بولاية معروفة، تكون Lookup table أبسط وأرخص وأسهل في Verification من تدريب Model.

تصبح ML أكثر جاذبية عندما تكون Relationship معقدة أكثر من أن تُحدد يدويًا. مثلًا، قد يصعب ترميز العلاقة بين Rental price وخصائص Property الكثيرة كصيغة مكتوبة يدويًا.

[[IMAGE_NEEDED: Hand-written rules versus learned patterns | A side-by-side diagram where traditional software receives explicit rules plus inputs to produce outputs, while ML receives example inputs and outputs during training and learns a model used for future inputs | Learner should notice that ML replaces hand-specified decision logic with patterns learned from examples]]

### 2.3 يجب أن توجد Data، أويمكن جمعها

لأن ML تتعلم من Data، يحتاج Project إلى شيء تتعلم منه. لا يمكن تدريب Model لعمل Tax-related prediction إذا لم تكن Tax و Income information المطلوبة متاحة.

يشير الفصل أيضًا إلى نقطتين دقيقتين:

- **Zero-shot learning** يمكنها تنفيذ Task من دون Task-specific training examples، لكن Model ما تزال قد تعلمت من Data أثناء Training سابق.
- **Continual learning** يمكنها السماح لـ Model بالتعلم من Incoming production data، لكن نشر Model لم تُدرَّب بما يكفي قد يخلق User experience ضعيفة ومخاطر أخرى.

عندما لا تمتلك Organizations بعد Data كافية، يبدأ بعضها بقرارات يصنعها البشر ويستخدم Interactions الناتجة لجمع Training data لنظام ML لاحق.

### 2.4 يجب أن تكون Problem قابلة للصياغة كـ Prediction

تنتج ML model تقديرًا. ولا يلزم أن يصف هذا التقدير Future. يمكن للنظام Predict لـ Class أو Value أو Action أو Ranking أوالناتج المرجح لعملية Computational.

ولهذا يمكن إعادة صياغة بعض Computational tasks المكلفة كمشكلات Approximation: بدل حساب Result دقيقة، تقوم Model بـ Predict لإجابة جيدة بما يكفي للـ Application.

### 2.5 ينبغي أن تشترك Unseen data في Patterns مفيدة مع Training data

يكون Learning مفيدًا فقط عندما تشبه Future inputs الظروف الممثلة داخل Training. وقد تفشل Model مدرّبة على سلوك من Era أو Environment مختلف جدًا لأن Relationship بين Inputs و Outputs تغيّرت.

بلغة Technical، يقول الفصل إن Training data و Unseen data ينبغي أن تأتي من Distributions متشابهة. لا يمكننا معرفة Future distribution بيقين، لذلك تعتمد Production ML على Assumptions ثم تستخدم Monitoring لاكتشاف متى تتوقف هذه Assumptions عن الصحة.

## 3. إشارات إضافية تجعل ML جذابة

تصف الأفكار الخمس السابقة الشكل الأساسي لـ ML problem. ويضيف الفصل أربع خصائص عملية تجعل ML مفيدة بصورة خاصة غالبًا.

### 3.1 المهمة متكررة

تحتاج ML algorithms كثيرة إلى Examples كثيرة. وتنتج Repetitive tasks بصورة طبيعية Examples متكررة من الأنماط نفسها، ما يجعل Learning أسهل ويخلق فرصًا أكثر لإعادة استخدام Model.

### 3.2 Predictions الخاطئة مقبولة التكلفة، أو Benefit المتوقع يبرر Risk

سترتكب Models المفيدة أخطاء. Recommendation systems مثال كلاسيكي على بيئة متسامحة: قد يتم تجاهل Recommendation سيئة ببساطة. وفي Systems ذات Stakes أعلى، قد تظل Model مقبولة فقط إذا كانت Expected benefit كبيرة بما يكفي وصُمم System حول Cost الخاصة بالأخطاء.

لذلك لا يكون سؤال التصميم الأساسي فقط *ما مدى دقة Model؟* بل أيضًا:

> **ما تكلفة Prediction واحدة خاطئة، ومن يتحمل هذه التكلفة؟**

### 3.3 تعمل المهمة على Scale كبير

تتطلب ML عادةً Investment أولية كبيرة في Data و Compute و Infrastructure والعمل المتخصص. ويصبح تبرير هذا Investment أسهل عندما سيجري System عددًا كبيرًا من Predictions — مثل Routing لأعداد ضخمة من Support tickets أو Filtering لعدد هائل من Messages.

كما يميل Scale إلى إنتاج Data أكثر، ما يمكن أن يدعم Continued model development.

### 3.4 تتغير Patterns بمرور الوقت

قد تصبح Hard-coded rules مكلفة في Maintenance عندما تتطور Language أو User behavior أو Fraud strategies أو Patterns أخرى. ويمكن تحديث ML باستخدام Data جديدة، ما يجعلها مناسبة للبيئات المتغيرة — بشرط أن يمتلك System عمليات Monitoring و Update لاكتشاف التغير والاستجابة له.

### متى ينبغي تجنب ML؟

يحدد الفصل ثلاث إشارات تحذير عامة:

1. **الاستخدام غير أخلاقي.** كون Prediction ممكنة تقنيًا لا يعني أنها Product مقبولة تلقائيًا.
2. **يوجد حل أبسط يعمل بالفعل.** ابدأ بالنظر في Non-ML baselines أو Rules أو Lookup logic.
3. **Economics غير منطقية.** يجب أن تبرر قيمة Predictions تكاليف Data و Infrastructure و Compute و Development و Maintenance.

حل وسط مفيد هو Decomposition. قد تحتوي Problem واسعة أكثر من اللازم لاستخدام ML على أجزاء Predictive أصغر. على سبيل المثال، بدل بناء System يجيب عن كل Customer question ممكن، يمكن لـ ML أولًا Predict ما إذا كان Question يطابق FAQ معروفة، ثم Routing للحالات غير المطابقة فقط إلى Human.

## 4. ما الذي تُستخدم ML systems من أجله؟

يفصل الفصل بين Consumer applications المألوفة ومجموعة كبيرة من Enterprise uses. تتغير Products المحددة بمرور الوقت، لكن أنواع Problems الأساسية أكثر دوامًا.

### أمثلة موجهة للمستهلكين

تشمل الأمثلة الشائعة في الفصل:

- Search و Recommendation،
- Predictive typing،
- Photo enhancement،
- Fingerprint أو Face matching،
- Machine translation،
- Smart assistants،
- Home monitoring و Event detection.

### أمثلة Enterprise

تستخدم Enterprise systems ML كثيرًا لتحسين Internal processes أو Business decisions. تشمل الأمثلة:

| حالة الاستخدام | ما الذي تتنبأ به أوتكتشفه Model | لماذا يهم |
|---|---|---|
| Fraud detection | ما إذا كانت Transaction تبدو احتيالية | تقليل Financial loss و Manual review |
| Price optimization | Price مفيدة في Current conditions | تحسين Objective مختارة مثل Margin أو Revenue |
| Demand forecasting | Future demand | تخطيط Inventory و Budgets و Staffing و Pricing |
| Customer targeting | الأشخاص المرجح استجابتهم | تقليل Acquisition cost وتحسين Outreach |
| Churn prediction | Customers الذين قد يغادرون | دعم Retention actions |
| تصنيف تذاكر الدعم | الجهة التي ينبغي Routing للطلب إليها | تقليل Response time |
| Brand monitoring | Mentions و Sentiment | اكتشاف تغير Reputation |
| المساعدة في الرعاية الصحية | Patterns مرتبطة بـ Diagnosis أو Monitoring | مساعدة Qualified professionals ضمن Requirements صارمة |

ينبغي لـ Production engineer ملاحظة أن كل Use case تعني Costs مختلفة للأخطاء، و Latency needs مختلفة، و Privacy constraints مختلفة، و Requirements مختلفة للـ Human oversight.

## 5. ML research و ML production تحسّنان أشياء مختلفة

Model تبدو ممتازة في Paper أو Competition ليست تلقائيًا أفضل Model للنشر. يسلط الفصل الضوء على خمسة فروق رئيسية.

| البعد | التركيز في Research | التركيز في Production |
|---|---|---|
| Requirements | Benchmark performance قوية | Requirements متعددة من Stakeholders |
| Computation | Training سريع / Throughput مرتفعة | Inference سريع / Latency منخفضة |
| Data | غالبًا Static و Curated | Noisy و Incomplete و Changing |
| Fairness | قد تحصل على اهتمام أقل | يجب اعتبارها System requirement |
| Interpretability | قد تحصل على اهتمام أقل | يحتاجها غالبًا Users و Developers |

### قد يريد Stakeholders أشياء مختلفة

يستخدم الفصل مثال Restaurant recommendation. قد تحسن فرق مختلفة Objectives مختلفة:

- قد يريد ML engineers Recommendations هي الأكثر احتمالًا لأن يطلبها Users.
- قد تفضل Sales Recommendations تحقق Service fees أعلى.
- قد تتطلب Product وصول Recommendations خلال Latency target صارمة.
- قد يفضل Platform engineers Reliability و Scalability على تغييرات Model المتكررة.
- قد تهتم Management أكثر بالـ Overall margin.

هذه ليست خلافات Technical فقط، بل Definitions مختلفة للنجاح. قبل Model selection، يجب على Team تحديد أي Requirements هي **Must-have constraints** وأيها **Nice-to-have preferences**.

Model أدق قليلًا لكنها تنتهك Hard latency requirement ليست Candidate صالحة للـ Production.
وبالمثل، قد تحسن Technique مثل Ensembling Predictive performance لكنها تزيد أيضًا Serving cost و Latency و Operational complexity وصعوبة Interpretation.

### لماذا يمكن لنجاح Leaderboard أن يكون مضللًا؟

Benchmarks مفيدة، لكنها تبسط Environment. قد تكون Data preparation و Deployment و Scaling و Monitoring و Product trade-offs أزيلت بالفعل من Competition. كما أن Experimentation المتكررة على Test set نفسها قد تجعل فروق Leaderboard أقل معنى مما تبدو عليه في البداية.

الدرس الهندسي بسيط: **حسّن Objective الحقيقية للنظام، لا Metric بمعزل عن بقية النظام.**

[[IMAGE_NEEDED: Research ML versus production ML | A two-column visual contrasting benchmark performance, static data, training throughput, and limited stakeholder constraints with production requirements, changing data, inference latency, fairness, interpretability, monitoring, and reliability | Learner should see that deployment introduces objectives and constraints that are absent from many research settings]]

## 6. الأولويات الحسابية: Latency و Throughput و Batching

أثناء Experimentation، تكون Training غالبًا هي Bottleneck لأنك قد تدرب Models كثيرة على Data نفسها. بعد Deployment تصبح Inference هي Workload المتكررة لأن System يجب أن تجيب عن Requests من Users أو Services.

يغير هذا الانتقال ما تقوم بتحسينه.

### Latency

في المصطلحات المستخدمة داخل الفصل، **Latency** هي الزمن من إرسال Request حتى استلام Response.

مثال:

```text
المستخدم يضغط Translate
        ↓
Request تُرسل → Model/Service تعمل → Result تعود
<---------------- Latency ---------------->
```

### Throughput

**Throughput** هي عدد Requests التي تتم معالجتها خلال وحدة زمن.

إذا استغرقت Request واحدة 10 ms وكان System يعالج واحدة فقط في كل مرة:

```text
1 ثانية = 1000 ms
1000 / 10 = 100 طلب في الثانية
```

إذا استغرقت كل Request بدلًا من ذلك 100 ms، فإن System نفسه الذي يعالج واحدة في كل مرة يتعامل مع نحو 10 Requests per second فقط.

### Batching تغير الـ Trade-off

تستطيع Modern systems معالجة عدة Requests معًا. افترض أن Batch من 10 Requests تستغرق 10 ms. تظل Latency لهذه Batch نحو 10 ms، لكن Throughput تصبح نحو 1,000 Request per second. وإذا استغرقت Batch من 50 Request مدة 20 ms، تكون Latency قد ارتفعت، ومع ذلك تصبح Throughput نحو 2,500 Request per second.

ولهذا فإن Latency الأعلى لا تعني **دائمًا** Throughput أقل في System تستخدم Batching أو Concurrency.

[[IMAGE_NEEDED: Latency and throughput with batching | Two timelines: one processing requests sequentially and one processing requests in batches, annotated with per-request latency and total requests per second | Learner should notice that batching can increase throughput even when latency per batch also increases]]

تضيف Online batching مشكلة أخرى: قد تحتاج Service إلى الانتظار حتى تتجمع Requests كافية لتشكيل Batch، ويضاف وقت الانتظار هذا إلى Latency.

### Latency هي Distribution وليست رقمًا واحدًا

قد يخفي Average سلوكًا مهمًا. انظر إلى قيم Latency العشر التالية من الفصل:

```text
90, 95, 99, 100, 100, 100, 102, 104, 110, 3000 ms
```

تقع معظم Requests قرب 100 ms، لكن Request واحدة بطيئة جدًا ترفع Arithmetic mean إلى أعلى. ولذلك فإن النظر إلى Mean وحدها قد يعطي صورة مضللة.

تفحص Production teams غالبًا Percentiles:

- **p50**: Median؛ نصف Requests أسرع ونصفها أبطأ.
- **p90**: نسبة 90% من Requests تقع عند هذه Value أوأقل.
- **p95 / p99**: مفيدة لرؤية Slow tail الخاصة بالـ Distribution.

تهم High-percentile latency لأن Requests البطيئة النادرة قد تكشف Failures أوتؤثر بصورة غير متناسبة في Users مهمين.

## 7. Production data و Fairness و Interpretability

### 7.1 Production data فوضوية وتتغير باستمرار

غالبًا ما تكون Research datasets منظفة و Formatted وموثقة ويتم إبقاؤها Static عمدًا حتى تكون Experiments قابلة للمقارنة. أما Production data فأصعب؛ فقد تكون Noisy أو Unstructured أومنحازة بطرق غير معروفة أوناقصة أوموسومة بصورة خاطئة أوتُولد باستمرار بواسطة Users و External systems.

كما يمكن لتغير Business requirements أن يغير معنى Labels. وإذا كانت User data متضمنة، تصبح Privacy و Regulatory requirements جزءًا من System design.

[[IMAGE_NEEDED: Research data versus production data | A side-by-side data-flow illustration showing a clean static benchmark dataset on the research side and noisy, streaming, changing, partially labeled data with privacy checks on the production side | Learner should notice that production data is an evolving system dependency rather than a fixed file]]

### 7.2 لا يمكن تأجيل Fairness إلى ما بعد Deployment

تتعلم Model من Historical data، وقد تحتوي Historical data على Inequalities أو Biases موجودة بالفعل. وإذا أعادت Model إنتاج هذه Patterns على Scale كبير، فقد تتحول Problem كانت تؤثر في عدد صغير من Decisions إلى Problem مؤتمتة عبر Population ضخمة.

التحذير الأساسي في الفصل هو أن Fairness ليست Cosmetic check تُضاف بعد تحسين Accuracy. بل يجب التفكير فيها أثناء اختيار Data و Objectives و Evaluation metrics و Deployment safeguards. كما يمكن لـ Aggregate accuracy أن تخفي Performance ضعيفة لدى Groups أصغر.

### 7.3 Interpretability تخدم Users و Developers

تهم Interpretability لسببين على الأقل يصفهما الفصل:

1. **Users و Decision makers** قد يحتاجون إلى فهم سبب إنتاج Result حتى يستطيعوا الوثوق بها أو Challenge لها أو Audit لها.
2. **Developers** يحتاجون إلى Clues عن Model behavior حتى يستطيعوا Debug للـ Failures وتحسين System.

كلما زادت Consequence الخاصة بـ Prediction، أصبح من الأصعب اعتبار Explanation مجرد Optional feature.

## 8. ML systems مقابل Traditional software

ما تزال Machine learning نوعًا من Software engineering، لذلك تظل ممارسات Engineering التقليدية كثيرة مفيدة. الفرق هو أن ML application تضيف Moving parts جديدة.

غالبًا ما تتعامل Traditional software مع Code و Data باعتبارهما Concern ين منفصلين. أما في ML system فينتج Behavior من:

```text
الشيفرة + البيانات + artifacts النموذج المتعلَّم
```

وهذا يعني أن Teams يجب أن تختبر وتعمل Version لأكثر من Source code. يمكن لتغيرات Data أن تغير Model behavior حتى عندما تبقى Application code نفسها دون تغيير.

### Data نفسها تصبح Engineering dependency

ليست كل Training samples متساوية القيمة. إذا كانت Dataset تحتوي بالفعل أمثلة كثيرة من Class شائعة وأمثلة قليلة جدًا من Class نادرة لكنها مهمة، فقد يكون Example نادر إضافي أكثر إفادة بكثير من Example شائع إضافي. كما أن قبول Data بصورة عمياء قد يُدخل Samples ضعيفة أومصممة بصورة Malicious.

### Model size و Serving constraints مهمتان

قد تحتاج Large models إلى Memory و Compute كبيرتين. Model لا تتسع داخل Target hardware أوتعجز عن الإجابة بسرعة كافية قد تكون غير قابلة للاستخدام حتى لو كانت Offline accuracy ممتازة. ويكون ذلك صعبًا بصورة خاصة على Edge devices ذات Resources محدودة.

### Monitoring و Debugging أصعب

غالبًا ما تكون Failures في Traditional software عبارة عن Exceptions صريحة أو Bugs قابلة لإعادة الإنتاج. أما ML failures فقد تكون تدريجية وإحصائية: تتغير Input distributions أو Data quality أوتصبح Predictions أقل فائدة من دون أن يتعطل Program. ولذلك تحتاج Production systems إلى Monitoring تراقب Model behavior و Data behavior، لا Service uptime فقط.

رسالة الفصل الأوسع هي أن ML engineering تحتاج **Holistic system approach**. وجود Model code جيدة ضروري لكنه غير كافٍ.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: أفضل Offline model هي تلقائيًا أفضل Production model

> إذا حصلت Model A على أعلى Benchmark score، فينبغي نشر Model A.

**لماذا هذا خاطئ؟** لأن Production selection تعتمد أيضًا على Latency و Cost و Scalability و Interpretability و Fairness و Reliability و Objectives الخاصة بالـ Stakeholders.

### المفهوم الخاطئ 2: ML مناسبة كلما كانت Problem تتضمن Data

> لدينا Data كثيرة، إذًا ينبغي أن نستخدم ML.

**لماذا هذا خاطئ؟** تحتاج Problem أيضًا إلى Learnable pattern مفيدة، و Predictive framing، و Data ذات صلة بما يكفي، و Economics تبرر System.

### المفهوم الخاطئ 3: Latency الأقل تعني دائمًا Throughput أقل

> إذا استغرقت كل Request وقتًا أطول، فلا بد أن يعالج System دائمًا Requests أقل في الثانية.

**لماذا هذا خاطئ؟** يمكن لـ Batching و Concurrency زيادة Total throughput حتى مع زيادة Per-request أو Per-batch latency.

### المفهوم الخاطئ 4: إذا كانت Service تعمل، فإن ML system سليمة

> عدم وجود Errors في Server logs يعني أن Model بخير.

**لماذا هذا خاطئ؟** قد تظل ML system متاحة Technical بينما تتدهور Data أو Prediction quality بصمت.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| ML system | Production system الكاملة المحيطة بـ ML model، بما يشمل Data و Infrastructure و Serving و Monitoring و Maintenance و Requirements |
| MLOps | Tools وممارسات لتشغيل ML عبر Deployment و Monitoring و Maintenance |
| ML systems design | منهج Holistic لجعل جميع Components و Stakeholders في ML system تحقق Objectives و Requirements المحددة |
| Prediction | Output مقدَّرة تنتجها Model لـ Input |
| Unseen data | Inputs لم تُستخدم في تدريب Model |
| Data distribution | Pattern إحصائية تصف كيفية ظهور Data values |
| Latency | الزمن من إرسال Request إلى استلام Result وفق مصطلحات الفصل |
| Throughput | عدد Requests المعالجة لكل وحدة زمن |
| Batching | معالجة عدة Requests معًا |
| p50 | Median latency؛ نصف Requests أسرع ونصفها أبطأ |
| p90 / p95 / p99 | High-percentile latency measurements لفحص Slow tail |
| Fairness | الاهتمام بألا يسبب Model behavior وتأثيره ضررًا منهجيًا لـ Groups معينة |
| Interpretability | القدرة على فهم أوشرح العوامل وراء Model behavior أو Outputs |
| Continual learning | تحديث Model أوتعلمها من Data تصل حديثًا بمرور الوقت |
| Data poisoning | ضرر يحدث عند إدخال Training data خبيثة أوضارة في Learning process |

## التحقق الذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة:

1. لماذا تكون ML algorithm مجرد جزء واحد من Production ML system؟
2. ما الأفكار الخمس الموجودة في صياغة "تعلم Patterns معقدة من Existing data وإجراء Predictions على Unseen data"؟
3. أعط مثالًا واحدًا تكون فيه Lookup table أفضل من ML.
4. لماذا تكون Repetitive tasks ذات Scale مرتفع مناسبة كثيرًا لـ ML؟
5. لماذا قد تكون Research winner Production model ضعيفة؟
6. ما الفرق بين Latency و Throughput؟
7. لماذا يمكن لـ Batching رفع كل من Latency و Throughput؟
8. لماذا تعد p95 أو p99 مفيدة إلى جانب Average latency؟
9. كيف تختلف Production data عن Static research dataset؟
10. لماذا يجب مراعاة Fairness و Interpretability أثناء System design بدل تأجيلهما إلى ما بعد Deployment؟
11. ما الذي يجب عمل Version له أومراقبته في ML systems إلى جانب Application code؟
