## 1. Evaluation تجعل Robustness قابلة للقياس

لا تجعل Evaluation الـ Agent موثوقة تلقائيًا. يمكن لـ Agent سيئة التصميم أن تظل تفشل حتى لو أحطناها بـ Dashboards وEvaluators.

لكن ما تقدمه Evaluation هو شيء مهم بالقدر نفسه: **الرؤية**.

فهي تسمح لنا بالإجابة عن أسئلة مثل:

- هل تحل Agent الهدف بصورة موثوقة؟
- هل تستخدم Tool الصحيحة؟
- هل Answer مبنية على Evidence؟
- كم مرة تفشل؟
- ما مقدار Variability عبر Runs المتكررة؟
- ما تكلفة كل Run ناجحة؟
- ما الذي ينبغي تغييره بعد ذلك؟

تغلق Feedback الحلقة عبر تحويل هذه الملاحظات إلى تغييرات في Prompts أوTools أوModels أوPolicies أوArchitecture.

منظور هندسي مفيد هو:

```text
سلوك Agent
    |
    v
Observe / evaluate
    |
    v
تخزين Feedback
    |
    v
تحسين النظام
    |
    +------> Evaluate مرة أخرى
```

## 2. Evaluation الداخلية مقابل الخارجية

تمتلك Agents بالفعل مفهوم Feedback داخليًا في مرحلة **Learn** من دورة Sense-Plan-Act-Learn. بعد تنفيذ Action، تلاحظ Agent ما حدث وتقرر ما ينبغي فعله بعد ذلك.

تضيف External evaluation آليات مستقلة حول Agent.

تشمل الأمثلة:

- Deterministic tests،
- Benchmark suites،
- Red-team tests،
- Grounding checks،
- Critic agents،
- Human review،
- Feedback databases،
- Monitoring وAlerting.

يمكن أن تتبع External feedback مسارين عامين.

### In-loop feedback

تؤثر Result فورًا في Action التالية للـ Agent.

```text
Agent -> Critic -> Feedback -> إعادة محاولة من Agent
```

### Offline feedback

تُخزن Evaluation لتحليلها لاحقًا بدل تغيير Response الحالية.

```text
Agent -> مخزن Evaluation -> لوحة المعلومات / تحليل التراجع / أعمال التحسين
```

كلاهما مفيد. تتحكم In-loop evaluation في Current behavior؛ بينما تحسن Offline evaluation الإصدارات المستقبلية من النظام.

## 3. ثلاثة أنواع من Evaluation

يقسم الفصل Evaluation إلى ثلاثة أشكال عامة.

### Deterministic evaluation

استخدم Code عادية عندما تكون Correctness دقيقة.

أمثلة:

- Output تطابق Schema،
- Required field موجودة،
- تم استدعاء Tool X،
- Numeric value داخل Range،
- تم إرجاع Known label.

### LLM أوAgent evaluation

استخدم Model عندما تكون Quality غامضة أوSemantic.

أمثلة:

- هل Answer ذات صلة؟
- هل يحافظ Summary على Facts المهمة؟
- هل تستوفي Response الـ Tone rubric؟
- هل Generated plan مكتملة بما يكفي؟

### Human evaluation

يظل البشر مهمين في:

- Edge cases،
- Policy concerns،
- Tone والملاءمة الاجتماعية،
- Evaluator outcomes المتنازع عليها،
- الحكم في العالم الحقيقي.

تجمع الأنظمة الأكثر موثوقية هذه الأشكال بدل إجبار كل Quality question على المرور عبر Evaluator type واحدة.

## 4. Red teams وBenchmarks والبشر وGrounding وCritics

يحدد الفصل عدة Evaluation methods ملموسة.

### اختبار Red-team

تحاول العثور على Inputs أوPatterns تكسر النظام.

استخدمها لاختبار:

- Safety boundaries،
- Prompt injection،
- Unexpected tool usage،
- Policy failures،
- Adversarial inputs.

### Benchmark testing

تقيس مدى نجاح Agent في الوصول إلى Goal معروفة عبر Test set محددة.

### Human feedback

تكشف Ratings وComments وExpert reviews وManual labels أخطاء قد تفوت Automated evaluators.

يحذر الفصل أيضًا من أن Raw human feedback يمكن أن تكون Noisy. وتشمل Production practices المفيدة:

- Aggregation،
- Outlier detection،
- Expert-weighted أوStratified review،
- Manual follow-up للـ Flagged outputs.

### Grounding evaluation

تتحقق مما إذا كانت Claims مدعومة بواسطة Authoritative source أوRetrieved context.

### وكلاء Critic/Evaluation

تراجع Generated outputs أوPlans أوActions وتقدم Structured feedback.

تعتمد Method الصحيحة على نوع Failure الذي تحاول اكتشافه.

## 5. Evaluation agents تحتاج Governance أيضًا

يمكن لنظام Multi-agent أن يخلق وهمًا خطيرًا بوجود Independent verification.

افترض:

- Agent A تعطي Answer خاطئة.
- Evaluator B تستخدم Model family والAssumptions والContext نفسها.
- Evaluator B توافق على Answer الخاطئة.

الآن يبدو النظام Validated رغم أن Agentين تشتركان في Blind spot نفسها.

يصف الفصل ذلك على أنه **Collusion risk**: تعزز Agents متعددة الاستنتاج الخاطئ نفسه بدل تقديم Checks مستقلة.

تشمل Governance practices المفيدة:

- استخدام Models/Providers مختلفة للـ Evaluators عندما يكون ذلك عمليًا،
- استخدام Adversarial evaluator prompts بدل Confirmation-oriented prompts،
- أخذ Random samples من Supposedly good outputs للمراجعة البشرية،
- تحديد أي Evaluator تملك Final authority،
- تسجيل كل Agent-to-agent evaluation message،
- Escalate للخلافات غير المحلولة،
- تقييد Authority الخاصة بكل Agent بدورها.

قد تكون Evaluation layer تعطي False confidence أسوأ من عدم وجود Evaluator أصلًا.

## 6. التطوير الموجَّه بالاختبارات للوكلاء (TDAD)

تكيف Test-driven agent development انضباط Test-driven development مع Stochastic agents.

الفكرة الأساسية هي:

> حدد شكل Behavior الجيدة **قبل** أن تبدأ في Tuning لا ينتهي للـ Agent.

تبدو دورة TDAD هكذا:

```text
تعريف Goals وBenchmarks
        |
        v
تشغيل Tests وتوقع Failures
        |
        v
تنفيذ أصغر تغيير مفيد
        |
        v
إعادة تشغيل كل Benchmarks
        |
        v
Refactor ثم تكرار الدورة
```

بعكس Deterministic software tests، تحتاج Agent tests غالبًا إلى Runs متكررة لأن Outputs الـ LLM تختلف.

## 7. صمّم Benchmarks حول Behavior لا Final text فقط

تحتوي Benchmark بسيطة على:

- Input question،
- Expected answer،
- واختياريًا Known-bad answers.

لكن Benchmark كاملة لـ Agent يمكنها تقييم أشياء أكثر بكثير:

- Final correctness،
- Tool choice،
- Tool arguments،
- Grounding،
- Number of steps،
- Latency،
- Token usage،
- Cost،
- Error recovery.

Agent تصل إلى Answer الصحيحة عبر خمس Wrong tool calls غير الضرورية ليست مساوية لـ Agent تصل إليها عبر Callين مناسبين.

هذا تحول مهم عن Text-only evaluation التقليدية:

> قيّم **Trajectory**، لا Final sentence فقط.

## 9. Refactor باستخدام أصغر تغيير فعال

Anti-pattern شائعة هي Prompt inflation: كل Failure تؤدي إلى إضافة Paragraph جديدة إلى System prompt.

يوصي الفصل بتصعيد Changes تدريجيًا.

ترتيب عملي هو:

1. غيّر كلمة واحدة لتحسين Clarity أوTone.
2. أضف Clause قصيرة.
3. أضف Sentence واحدة.
4. أضف Prompt section صغيرة.
5. أضف Tool أوعدّلها.
6. غيّر Model أوGeneration settings.

الهدف ليس Minimalism لذاته. تساعد Lean changes على فهم Causality وتقليل احتمالية إدخال Instructions جديدة متعارضة.

وأزل أيضًا Prompt content التي لم تعد تستحق مكانها.

## 11. أحيانًا تكون Evaluator هي المخطئة

افترض أن Expected answer هي:

```text
الفوتونات
```

وتعيد Agent:

```text
الفوتونات.
```

Strict equality ستعتبر Answer خاطئة رغم أن المعنى صحيح.

مثال آخر:

```text
المتوقع: التيارات
الفعلي:   التيارات المائية
```

مرة أخرى، قد تسجل Evaluator هشة False failure.

كحد أدنى، قد تحتاج Deterministic natural-language comparisons إلى Normalization مثل:

- تحويل Text إلى Lowercase،
- إزالة Whitespace الزائدة،
- إزالة Punctuation غير المؤثرة،
- مراعاة Acceptable variants.

بالنسبة إلى Answers أكثر Open-ended، قد تكون LLM evaluator أوRubric أنسب.

الدرس الأوسع مهم جدًا:

> عندما تفشل Benchmark، شخص ما إذا كانت المشكلة في Agent أوRetrieval system أوBenchmark أوEvaluator.

## 13. Grounding وCritic وGeneral evaluation agents

تتداخل هذه الأدوار الثلاثة، لكنها تجيب عن أسئلة مختلفة.

### Grounding agent

السؤال:

```text
هل هذه Answer مدعومة بواسطة Authoritative context؟
```

Best fit:

- RAG،
- Citation verification،
- Memory verification،
- التحقق من نتيجة الأداة.

### Critic agent

السؤال:

```text
إلى أي مدى تستوفي هذه Generated output معايير Quality؟
```

Best fit:

- Plans،
- Reports،
- Images،
- Generated content،
- Iterative refinement.

### وكيل evaluation عام

السؤال:

```text
هل استوفت هذه Output الـ Benchmark أوTask requirement؟
```

Best fit:

- Test suites،
- Benchmark scoring،
- قرارات النجاح/الفشل المعقدة.

عادةً ما يجعل اختيار أضيق Evaluator تناسب Requirement النتيجة أسهل في الفهم.

- Explicit failure تُعاد إلى Internal pipeline،

## 17. استخدم Evaluation method المناسبة لنوع Output

تملك Structured outputs غالبًا Objective metrics.

أمثلة:

- Classification accuracy،
- Precision،
- Recall،
- F1،
- Exact schema validity،
- Numeric error.

أما Open-ended outputs فمختلفة.

قد يكون Summary صحيحًا بصيغ كثيرة مختلفة. وقد تكون Plan قوية في بعض الأبعاد وضعيفة في أبعاد أخرى.

تستفيد هذه الحالات من:

- Rubrics،
- LLM-as-judge،
- Human review.

لا تستخدم Rubric معقدة عندما تكفي Deterministic metric دقيقة. ولا تستخدم Strict equality عندما تكون Quality متعددة الأبعاد بطبيعتها.

## 18. بناء Rubrics مفيدة

تحول Rubric الـ Quality الغامضة إلى Criteria صريحة وPerformance levels.

عملية قوية لبناء Rubric هي:

1. حدد Purpose الخاصة بالـ Output.
2. حدد Measurable criteria.
3. اختر Rating scale.
4. صف معنى كل Score.
5. طبّق Rubric على Sample outputs.
6. اجمع أوWeight للـ Scores عند الحاجة.
7. تحقق من Evaluator consistency.
8. راجع Rubric بمرور الوقت.

قد تشمل Agent-quality criteria:

- Factual accuracy،
- Grounding،
- Completeness،
- Structural correctness،
- Tone،
- Tool usage correctness،
- Error recovery،
- Hallucination rate.

ينبغي Validation للـ Rubric نفسها مقابل Human judgment. فالـ Rubric المخطئة باستمرار تظل مخطئة.

## 20. Evaluation thresholds تحتاج Calibration

افترض أن Rubric score تتراوح من 1 إلى 5.

قد يسمح Threshold منخفض بمرور Content ضعيفة. وقد يرفض Threshold مرتفع Outputs مقبولة كثيرة ويستهلك Retry budgets.

لذلك ينبغي التعامل مع Pass threshold بوصفها Measurable decision.

عملية عملية هي:

1. اجمع Representative sample من Outputs.
2. اطلب من Humans تصنيف أي منها ينبغي أن Pass أوFail.
3. قيّم Outputs نفسها باستخدام Rubric/Evaluator.
4. قارن Agreement.
5. اختر Threshold توازن بين False passes وFalse rejections.
6. أعد Validation عندما تتغير Rubric أوModel أوAgent.

هذا هو Evaluator calibration.

## 21. لماذا تهم Observability؟

بمجرد أن تستخدم Agent عدة Model calls وTools وHandoffs وRetries وEvaluators، لا تعود Final output وحدها كافية لفهم ما حدث.

تساعد Trace-level observability في فحص:

- Model calls،
- Tool usage،
- Agent transitions،
- Token usage،
- Latency،
- Cost،
- Sessions،
- Evaluator decisions،
- Failure paths.

يستخدم الفصل **Arize Phoenix** بوصفها Open-source platform للـ Observability وEvaluation.

ويشير أيضًا إلى وجود بدائل؛ المفهوم المهم هو Observability pattern لا الاعتماد على Vendor واحدة.

## 24. حوّل Traces إلى Datasets وExperiments

تبدأ Outer loop الخاصة بالـ Evaluation عندما تُجمع Real trace spans داخل Reusable datasets.

Workflow عملية هي:

```text
Production/Dev traces
      |
      v
اختيار Representative spans
      |
      v
إنشاء Evaluation dataset
      |
      v

      v
مقارنة Evaluator scores + Operational metrics
```

هذا أقوى بكثير من الحكم على Prompt جديدة باستخدام عدد قليل من Hand-picked examples.

## 25. Annotations تحول Human judgment إلى Structured data

قد يلاحظ Developer أن Agent اختارت Tool خاطئة. وقد يلاحظ Domain expert خطأ Policy دقيقًا. وقد يصنف QA reviewer Answer بأنها ممتازة.

إذا بقيت هذه الملاحظات داخل Chat messages أوملاحظات Meetings، فإنها تختفي من Evaluation system.

تجعلها Annotations قابلة لإعادة الاستخدام.

أمثلة:

- `correctness=fail`،
- `tool_selection=wrong`،
- `needs_review=true`،
- `grounding=good`،
- `tone=poor`.

بمجرد تخزينها مع Trace data، يمكن Filtering وتحليل Annotations مقابل:

- Latency،
- Cost،
- Token usage،
- Tool choice،
- Model version،
- Prompt version.

ومع مرور الوقت، تصبح Flagged examples Regression suite طبيعية.

## 26. Playbook عملية للـ Evaluation

استخدم هذا التسلسل عند Hardening لـ Agent.

### Step 1 — حدد Success قبل Tuning

أنشئ Benchmark cases وExpected behavior وأمثلة Known-bad مهمة.

### Step 2 — اختبر بصورة متكررة

قس Variability، لا Lucky run واحدة فقط.

### Step 3 — شخص Layer التي فشلت

هل كانت المشكلة في Retrieval أوPrompt أوTool metadata أوModel أوEvaluator أوBenchmark؟

### Step 4 — نفذ أصغر تغيير مفيد

تجنب Prompt growth غير المنضبط.

### Step 5 — أعد تشغيل كل Benchmarks السابقة

قد تنشئ Fixes جديدة Regressions في أماكن أخرى.

### Step 6 — استخدم Typed evaluator output

اجعل Pass/Fail وFeedback قابلة للاستخدام Programmatically.

### Step 7 — قم بـ Grounding للـ Authoritative answers

استخدم Source-aware validation عندما يجب دعم Claims.

### Step 8 — أضف Rubric critics للـ Open-ended output

عرّف Criteria بدل طرح سؤال غامض على Judge: «هل هذا جيد؟».

### Step 9 — ضع حدودًا لـ Retries وحدد Escalation

تحتاج Evaluation loops إلى Explicit stopping rules.

### Step 10 — تتبع كل ما هو مهم

ضمّن Evaluator behavior، لا Generator behavior فقط.

### Step 11 — التقط Human feedback بصورة Structured

حوّل Review إلى Annotations وDatasets.

### Step 12 — أعد تقييم Evaluators

يمكن لـ Monitoring layer أن تنحرف أوتشترك في Blind spots نفسها مع النظام الذي تحكم عليه.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Evaluation تجعل Architecture ضعيفة Robust

> تكشف Evaluation الـ Behavior وتوجه Improvement؛ ولا تستطيع تعويض System design سيئة جذريًا.

### المفهوم الخاطئ 2: Run ناجحة في Benchmark تثبت أن Agent موثوقة

> Behavior الخاصة بـ LLM متغيرة، ولذلك نحتاج Runs متكررة لفهم Consistency.

### المفهوم الخاطئ 3: كل Failed benchmark تعني أن Agent مخطئة

> قد تكون Evaluator أوExpected answer أوRetrieval system أوBenchmark هي المشكلة الحقيقية.

### المفهوم الخاطئ 4: Agent ثانية هي تلقائيًا Independent judge

> قد تنشئ Models وTraining data وAssumptions وPrompts المشتركة Blind spots مشتركة.

### المفهوم الخاطئ 5: المزيد من Prompt instructions هو دائمًا أفضل Fix

> قد تكون Tool metadata أوTyped outputs أوModel settings أوRetrieval أوArchitecture مكانًا أفضل لتغيير Behavior.

### المفهوم الخاطئ 6: يمكن اختيار Rubric score thresholds اعتباطيًا

> ينبغي Calibration للـ Thresholds مقابل Representative human-labeled outputs.

### المفهوم الخاطئ 7: Observability مخصصة فقط لـ Debugging crashes

> Traces هي أيضًا Datasets لتقييم Quality وCost وLatency وModel behavior.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Evaluation | قياس ما إذا كان Behavior الخاص بالـ Agent يحقق Requirements |
| Feedback | معلومات تستخدم لتحسين Behavior الحالية أوالمستقبلية |
| Benchmark | Test case أوSuite محددة لقياس Agent performance |
| اختبار Red-team | Adversarial test مصممة لاكتشاف Failure modes |
| TDAD | تطوير الوكلاء الموجَّه بالاختبارات |
| Grounding evaluator | Checker تتحقق من Claims مقابل Authoritative context |
| Critic agent | Evaluator تقيّم Generated output مقابل Criteria/Rubric |
| Evaluation agent | General evaluator تستخدم للحكم على Benchmark/Task success |
| Guardrail | Enforcing validation boundary قادرة على Block أوRedirect للـ Output |
| Tripwire | Guardrail condition تشير إلى Failure |
| Rubric | Evaluation criteria صريحة مع Performance scale |
| Calibration | مواءمة Evaluator scores أوThresholds مع Human judgment |
| False positive | Evaluator تمرر Result سيئة بصورة خاطئة |
| False negative | Evaluator ترفض Result مقبولة بصورة خاطئة |
| Collusion risk | Agents متعددة تعزز Assumption أوBlind spot خاطئة نفسها |
| Trace | Execution path مسجلة عبر Model/Tool/Agent calls |
| Session | Grouping لتفاعلات مرتبطة داخل Observability data |
| Metadata | Structured labels مرتبطة بـ Traces لأغراض Filtering/Analysis |
| Annotation | Structured human أوProgrammatic label مرتبطة بـ Trace/Span |
| Regression dataset | مجموعة من Cases سابقة الإشكال أوRepresentative يعاد تشغيلها بعد Changes |

## تحقق ذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة:

1. ماذا توفر Evaluation ولا توفره Architecture وحدها؟
2. كيف تختلف In-loop feedback عن Offline evaluation؟
3. متى ينبغي تفضيل Deterministic evaluation على LLM judge؟
4. ماذا تقيس Red-team testing؟
5. لماذا ينبغي لـ Agent benchmarks فحص Intermediate behavior بالإضافة إلى Final output؟
6. ما TDAD؟
7. لماذا ينبغي إعادة تشغيل Stochastic benchmarks عدة مرات؟
8. ما الترتيب الموصى به لتصعيد Prompt/Tool/Model changes؟
9. لماذا قد تكون Strict string equality Evaluator سيئة للـ Natural language؟
10. كيف تختلف Grounding وCritic وEvaluation agents؟
11. كيف تجعل Output guardrail الـ Grounding check قابلة للفرض أثناء Runtime؟
12. لماذا تحتاج Critic loops إلى Retry ceilings؟
13. متى تكون Rubrics أنسب من Accuracy؟
14. لماذا يجب Validation للـ Rubrics والThresholds مقابل البشر؟
15. ما Evaluator collusion؟
16. لماذا ينبغي Logging لـ Evaluator traces أيضًا؟
17. ما الذي تضيفه Sessions وMetadata إلى Observability؟
18. كيف يمكن أن تتحول Annotations إلى Regression tests؟

## احتفظ بهذه الفكرة

**هندسة Agents الموثوقة هي Empirical loop: عرّف معنى Behavior الجيدة، واختبر Agent مرارًا، وراقب Trajectory كاملة، وغيّر أصغر جزء مسؤول، ثم اختبر مرة أخرى. تكون Grounding agents وCritics وRubrics وGuardrails وTraces وHuman feedback مفيدة فقط عندما تُقاس Quality الخاصة بها أيضًا، وعندما تتحول Signals التي تنتجها إلى Improvements قابلة للتنفيذ بدل أن تكون Decorative dashboards.**
