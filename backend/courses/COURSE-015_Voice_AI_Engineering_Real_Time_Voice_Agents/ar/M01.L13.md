# النشر والتوسّع وحلقة AgentOps اللانهائية

> **الدرس:** M01.L13  
> **مواءمة المصدر:** Chapter 20 من مواد Early Release المورَّدة.

---

## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا لا يُعد Agent يعمل محليًا نظام Production بعد.
- شرح الغرض من CI/CD في منصة AgentOps.
- التمييز بين Pipelines الخاصة بـ feature branch وPipelines الخاصة بـ Production على main branch.
- شرح لماذا تصبح بنية Repository عقدًا بين المطورين والمنصة.
- شرح الغرض من التحقق من Repository، والاختبارات على مستوى Code، وContainerization.
- شرح لماذا تقلل Containers من Environment drift ومشكلات "works on my machine".
- وصف الأماكن التي يمكن أن تعمل فيها CI/CD runners في البيئات cloud-native والبيئات air-gapped.
- تتبع Feedback loop الخاصة ببيئة Development.
- شرح لماذا يتطلب سلوك Generative AI اختبارًا يدويًا في Development حتى بعد نجاح اختبارات syntax وunit tests.
- شرح كيف تعمل Pull Requests وعمليات merge كمحفزات Promotion.
- التمييز بين Development وStaging.
- شرح لماذا ينبغي أن تحاكي Staging قيود Production الخاصة بالأمان، والشبكات، وشكل Data، وIdentity.
- شرح الغرض من أول Manual approval gate قبل Evaluation المكلفة.
- شرح كيف تندمج Static golden datasets وSimulators وAutoraters داخل Evaluation في Staging.
- شرح Trajectory evaluation داخل Deployment pipeline.
- شرح Registration as Code.
- شرح كيف تتتبع Agent Registry وTool Registry الإصدارات، والبيئات، والقدرات، والمقاييس، وحالة الموافقة.
- شرح لماذا تصبح Registry طبقة تحكم تشغيلية بدلًا من مجرد Catalog.
- شرح Final manual approval gate.
- شرح كيف يمتد Continuous monitoring بالحوكمة لما بعد Deployment.
- شرح كيف يمكن لـ OpenTelemetry ربط سلوك التطبيق بتاريخ Pipeline وDeployment.
- شرح كيف تعود End-user feedback إلى Agent Registry.
- مقارنة استراتيجيات الإصدار Blue/Green وCanary وA/B.
- شرح متى يكون Automatic rollback مناسبًا.
- شرح لماذا يجب أن يحدّث Rollback أيضًا حالة Governance/Registry.
- شرح لماذا يختلف A/B testing عن Canary deployment.
- شرح لماذا تفصل AgentOps الناضجة بين دورات حياة Data وTools/APIs وFrontend وAgent.
- شرح لماذا تحسن Repositories وPipelines المستقلة سرعة المؤسسة.
- شرح قاعدة "cross-layer production dependency" الواردة في المصدر.
- شرح لماذا تعد العقود القياسية ضرورية في الأنظمة المفصولة.
- شرح كيف تقلل Schemas الشبيهة بـ OpenAPI وMCP وA2A من الترابط.
- شرح لماذا ينبغي لـ CI/CD اختبار Backward compatibility.
- شرح لماذا قد تحتاج إصدارات متعددة من Agent إلى العمل في الوقت نفسه.
- شرح Application-side version pinning.
- شرح لماذا للاحتفاظ بإصدارات Live تكلفة فعلية للبنية التحتية.
- شرح سياسة Deprecation والأرشفة.
- شرح كيف تُوجَّه Production feedback إلى الفريق الصحيح.
- شرح AgentOps Infinity Loop بوصفها Iteration مستقلة ومستمرة.
- تصميم دورة نشر كاملة لـ Enterprise Agent من Code change حتى Production feedback.

## 1. المخطط ليس مبنى

في هذه المرحلة، قد يمتلك Agent بالفعل:

```text
prompts جيدة
Evaluation datasets
Tools محكومة
Agent Card
تكامل Agent Registry
ضوابط security
identity
خطط monitoring
```

ومع ذلك قد يظل موجودًا فقط:

```text
على laptop
داخل Repository واحدة
على server تم نشره يدويًا
```

وهذا لا يعني الجاهزية المؤسسية.

السؤال التشغيلي الأخير في المصدر هو:

> كيف نحول Agent قادرًا إلى Production service متكررة ومحكومة؟

---

## 2. لماذا ينهار Manual deployment على نطاق واسع

يعمل Manual deployment في Pilot.

لكنه يفشل عندما:

- تتغير Models،
- تتغير Prompts،
- تتغير Tools،
- تساهم فرق عديدة،
- يعتمد مئات المستخدمين على الخدمة.

تنشئ عملية Release بشرية بالكامل:

```text
تسليمًا بطيئًا
بيئات غير متسقة
اختبارات فائتة
Configuration drift
أخطاء Deployment
Rollback هش
```

### المبدأ الأساسي

> تأتي موثوقية Production من Automation قابلة للتكرار، لا من جهد يدوي بطولي.

## 4. رحلة البيئات

المسار العام هو:

```text
المطوّر
   ↓
CI/CD
   ↓
التطوير
   ↓
Staging
   ↓
الإنتاج
```

لكل بيئة دور مختلف.

### بيئة التطوير (Development)

Iteration سريعة وManual validation.

### بيئة ما قبل الإنتاج (Staging)

Automated quality assurance مشابهة لـ Production.

### بيئة الإنتاج (Production)

مستخدمون حقيقيون، وضوابط صارمة، وContinuous monitoring.

## 5. أساس CI/CD

تعني CI/CD:

```text
Continuous Integration (التكامل المستمر)
Continuous Deployment / Delivery (النشر أو التسليم المستمر)
```

وهي توفر الآلية التي تحول Source code إلى خدمة منشورة.

يحدد Pipeline configuration المهام المرتبة.

تتضمن أمثلة Pipeline systems في المصدر أدوات Cloud وأدوات Self-hosted.

تعامل مع أسماء Products الدقيقة كخيارات تنفيذ، لا كمتطلبات Architecture.

## 7. Branching يتحكم في سلوك Pipeline

يميز المصدر بين:

```text
feature branch — فرع الميزة
main branch — الفرع الرئيسي
```

وهما يمثلان مستويين مختلفين من الثقة ومسؤوليات Pipeline المختلفة.

Branch ليست مجرد تنظيم لـ Source control.

بل يمكن أن تكون Operational trigger.

---

## 8. Pipeline الخاصة بـ Feature branch

تدعم Feature branch التجربة.

مثال:

```text
improve_geometry_tone
```

قد يؤدي Push إلى:

```text
التحقق
البناء
نشر نسخة Development مؤقتة
```

الهدف هو السرعة.

يمكن للمهندس أن يفشل بأمان.

---

## 9. Pipeline الخاصة بـ Main branch

يعني Merge إلى `main`:

```text
هذا التغيير Production candidate
```

ولذلك ينبغي أن تكون Main pipeline أثقل.

قد تتضمن:

```text
تسلسل Deployment كامل
Evaluation على نطاق واسع
تحديثات Registry
Approval gates
Production rollout
```

## 10. تحقّق قبل Deployment

لا ينبغي لـ Pipeline أن تبدأ Deployment فورًا.

تحقق أولًا من Repository.

يتوقع المصدر بنية Project القياسية التي أُنشئت في الفصول السابقة.

أمثلة على الأصول المطلوبة:

```text
Agent Card
Tests
Evaluation assets
ملفات Agent الأساسية
Deployment definitions
```

يجب أن توقف المتطلبات البنيوية المفقودة Pipeline مبكرًا.

## 11. بنية Repository عقد مع Platform

يسمح Standardization لـ Pipeline واحدة بفهم Agents كثيرة.

على سبيل المثال، إذا اتبع كل Project:

```text
agent.py    # الـ agent
prompts.py
context.py
examples.py
tools.py
tests/
evaluation/
deploy/    # النشر
.well-known/agent.json
```

يمكن للمنصة تنفيذ Automation دون منطق خاص لكل حالة.

### المبدأ

> تحوّل البنية القابلة للتوقع Conventions إلى Automation.

## 12. اختبارات Code تسبق AI Evaluation

تجيب الاختبارات الأولى عن أسئلة Software عادية:

```text
هل يمكن Import للـ Code؟
هل Dependencies موجودة؟
هل تنجح Unit tests؟
هل ينجح Linting؟
هل تبدأ Service؟
```

لكنها لا تجيب عن:

```text
هل Tutor فعال تربويًا؟
هل Tone مناسبة؟
هل اختار Agent الـ Tool الصحيحة؟
```

هذه تتطلب AI Evaluation لاحقة.

## 13. ابنِ Container قياسية

بعد Validation، تغلف Pipeline التطبيق.

تتضمن Container:

```text
شيفرة الـ agent
المكتبات
تبعيات وقت التشغيل
تبعيات النظام
```

الهدف هو اتساق البيئة.

### فائدة Container

```text
نفس Artifact
يعمل في Dev
يعمل في Staging
يعمل في Prod
```

وهذا يقلل مشكلات:

```text
"it works on my machine" — "إنه يعمل على جهازي"
```

وما يشبهها من المشكلات.

## 14. يمكن أن تكون Pipeline نفسها Modular

يشير المصدر إلى أن خطوات Pipeline نفسها قد تعمل كـ Containers قصيرة العمر.

مفاهيميًا:

```text
container المُدقِّق
→ container الاختبار
→ container البناء
→ container النشر
```

لكل منها مسؤولية واحدة.

وهذا يجعل Pipeline:

- Modular،
- قابلة لإعادة الإنتاج،
- قابلة للتوسع.

## 15. أين تعمل CI/CD؟

تشمل البيئات الممكنة:

### Runners سحابية مُدارة

مفيدة من أجل:

- Elasticity،

مفيدة من أجل:

- Hardware متخصص،
- حدود تنظيمية.

يبقى المبدأ الأساسي نفسه:

> ينبغي توحيد Automation بغض النظر عن مكان تنفيذ Runner.

## 20. انشر Local tools مع Agent عند الحاجة

إذا كان Agent يعتمد على Local code tool، فينبغي أن يتضمن Development deployment هذه Tool.

لماذا؟

أنت تحتاج إلى اختبار:

```text
Agent + Prompt + Tool — النظام المتكامل
```

بوصفه Micro-ecosystem يعمل كوحدة واحدة.

وإلا فقد يتحقق Developer من Agent مقابل إعداد Tool لا يطابق Deployment الحقيقي.

## 21. لماذا ما تزال Development تحتاج إلى البشر

سلوك Generative غير deterministic.

يمكن لـ Unit test إثبات:

```text
Python يعمل
```

لكنها لا تثبت:

```text
الشرح صبور
الاستدلال جيد تربويًا
المحادثة تبدو طبيعية
```

في Development، يتفاعل AI وPrompt engineers يدويًا مع Candidate.

## 24. Merge إلى Main هو Promotion trigger

يعمل Merge إلى `main` مثل Tripwire.

ويبدأ Primary pipeline المتجهة نحو Production.

ينبغي أن تتعامل Pipeline مع Code بوصفه:

```text
Candidate للترقية المؤسسية
```

وليس مجرد:

```text
تجربة Developer
```

---

## 25. قد تعيد Main النشر إلى Development

يشير المصدر إلى أن النسخة المدمجة من Main branch قد تعود أولًا إلى Development.

لماذا؟

قد يتفاعل Code المدمج مع تغييرات حديثة أخرى.

نجاح Feature branch لا يضمن أن Main branch المجمعة سليمة.

---

## 26. لماذا توجد Staging

Development متساهلة عمدًا.

قد يمتلك Engineers:

- وصولًا مباشرًا،
- Debugging permissions،
- Network rules مخففة.

أما Production فينبغي أن تكون صارمة.

توجد Staging لإعادة إنتاج قيود Production قبل أن يرى المستخدمون Release.

---

## 27. ينبغي أن تحاكي Staging بيئة Production

تحاكي بيئة Staging قوية:

```text
قيود الشبكة
IAM
Service topology
شكل Data
Resource constraints
Guardrails
Monitoring
```

ينبغي أن تكون Data مشابهة لـ Production مع حمايتها/إخفاء هويتها حسب الحاجة.

### المبدأ

> تختبر Staging بنية Production، لا منطق التطبيق فقط.

---

## 28. لماذا يمكن أن يعمل Agent في Dev ويفشل في Prod

تشمل الأسباب المحتملة:

```text
Dev تمتلك Credentials واسعة
Prod تستخدم Least privilege

Dev يمكنها الوصول إلى Public internet
Prod تُرشّح Egress

Dev تستخدم Local data
Prod تستخدم Governed APIs

Dev تسمح بـ Debugging
Prod تمنع الوصول البشري المباشر
```

تكشف Staging هذه الاختلافات بأمان.

## 29. أول Manual approval gate

قبل AI Evaluation مكلفة، يمكن أن تتوقف Pipeline مؤقتًا.

يفحص QA lead/Product Owner:

```text
السلوك الأساسي
Regressions واضحة
صحة Deployment
```

لماذا؟

يمكن أن تستهلك AI Evaluation على نطاق واسع مقدارًا كبيرًا من:

```text
Tokens
Compute
الوقت
المال
```

يمكن لفحص بشري سريع تجنب إهدار هذه الميزانية.

## 30. Deployment إلى Staging

بعد Approval:

```text
صورة مرشّحة
→ Staging
```

ينبغي أن تكون هذه هي النسخة التي تستهدفها Automated evaluation.

وبذلك تقيس Evaluation الـ Candidate المنشور تحت بنية تحتية واقعية.

## 31. Datasets ذهبية ثابتة

يمكن لـ Pipeline قراءة:

```text
evaluation/dataset.jsonl — ملف Golden dataset
```

وتشغيل حالات معروفة.

وهذه مفيدة من أجل:

- Regression tests،
- السلوكيات المتوقعة الحرجة،
- Edge cases المعروفة.

لكنها محدودة.

لا يمكن للأمثلة الثابتة تمثيل كل تفاعل Multi-turn ديناميكي.

---

## 32. Simulators تولد تفاعلات ديناميكية

يتصرف Simulator مثل المستخدم.

مثال Persona:

```text
طالب ثانوي محبط
يعاني مع Fractions
```

ويتفاعل ديناميكيًا مع Candidate agent.

ويساعد ذلك على كشف مسارات غير متوقعة.

Simulator هو الممثل.

وليس الحكم.

---

## 33. Autoraters تقيّم التفاعل

بعد الجلسة المحاكاة، يقوم Autorater بتقييمها.

معايير محتملة:

```text
مدى المساعدة
الصحة
Tone
Grounding
Tool behavior
Safety
```

وهذا يتيح AI-on-AI evaluation على نطاق واسع.

ويمكن الاستمرار في استخدام Human validation للمعايرة.

---

## 34. قيّم Execution trajectory

لا ينبغي لـ Pipeline أن تقيّم الإجابة النهائية فقط.

ينبغي أن تفحص:

```text
Tool المختارة
Arguments
Sequence
Retries
Timeout behavior
Clarification behavior
Final response
```

مثال:

```text
هل استخدم Tutor أداة calculus_solver؟
هل مرر JSON صحيحًا؟
هل تعامل مع API timeout؟
```

وهذا يربط Deployment مباشرة بمنهج Evaluation من Chapter 16.

---

## 35. Promotion thresholds

يمكن لـ Center of Excellence أو Platform team تعريف حدود دنيا.

أمثلة:

```text
Tool accuracy >= target — دقة Tool عند الهدف أو أعلى
Safety >= target — السلامة عند الهدف أو أعلى
Helpfulness >= target — مدى المساعدة عند الهدف أو أعلى
Latency <= target — زمن الاستجابة عند الهدف أو أقل
Cost <= target — التكلفة عند الهدف أو أقل
```

إذا فشل Candidate:

```text
Pipeline تتوقف
```

ولا يتابع لأنه يوجد Human "يشعر" أن الأمور غالبًا جيدة.

## 38. تصبح Registry مركز قيادة

لا ينبغي لـ Registry أن تجيب فقط عن:

```text
ما Agents الموجودة؟
```

بل يمكنها أيضًا الإجابة عن:

```text
أي Version موجودة في Dev؟
أي Version موجودة في Staging؟
```

## 47. يحتاج Production release إلى Traffic strategy

## 48. النشر الأزرق/الأخضر (Blue/Green deployment)

احتفظ ببيئتي Production متكافئتين:

```text
Blue = Current live version — النسخة الحالية المباشرة
Green = New candidate — النسخة المرشحة الجديدة
```

انشر Version الجديدة إلى Green.

نفّذ Health checks.

ثم حوّل Traffic.

### الميزة الأساسية

Rollback سريع جدًا:

```text
Green تفشل
→ أعد التوجيه إلى Blue
```

تبقى Version السابقة سليمة.

---

## 49. متى يكون Blue/Green مفيدًا

استخدمه عندما تريد:

```text
تبديلًا نظيفًا بين البيئات
Rollback بسيط
استبدال Version كاملة
```

ويكون مفيدًا خصوصًا عندما تكون Infrastructure-level compatibility هي الاهتمام الأساسي.

المفاضلة:

```text
سعة Environment مكررة
```

أثناء الانتقال.

---

## 50. النشر التدريجي (Canary deployment)

يبقي Canary الإصدارات القديمة والجديدة Live معًا.

ويذهب جزء صغير فقط من Traffic إلى Candidate.

مثال على Progression:

```text
نسبة صغيرة %
→ نسبة أكبر %
→ نسبة أكبر %
→ 100%
```

النسب الدقيقة اختيارات Policy.

وأرقام المصدر أمثلة.

---

## 51. يحتاج Canary إلى مراقبة نشطة

ينبغي مراقبة Candidate cohort عن قرب.

إشارات محتملة:

```text
معدل الانهيار
latency
درجة Autorater
معدل hallucination
إخفاقات الأدوات
التكلفة
```

إذا تدهورت الجودة:

```text
أوقف Rollout
أعد توجيه Traffic
```

وهذا يحد Blast radius.

---

## 52. Rollback هو أيضًا حدث Governance

لا ينبغي لـ Rollback أن يغير Load balancer فقط.

ينبغي لـ Pipeline أيضًا تحديث:

```text
حالة Agent Registry
حالة Tool Registry إذا كانت ذات صلة
Approval state
Release history
Owner notifications
```

وهذا يبقي Control-plane state متوافقة مع Production state الحقيقية.

---

## 53. ينبغي لـ Rollback توضيح السبب

يتضمن Failure notification جيد Evidence.

أمثلة:

```text
انخفاض Autorater
Latency spike
Error trace
Tool failure
Resource exhaustion
```

ينبغي أن يعرف Engineer التالي ما الذي يجب إصلاحه.

Rollback دون Evidence لا يفعل سوى تأجيل Diagnosis.

---

## 54. اختبار A/B (A/B testing)

يختلف A/B testing.

هدفه الأساسي ليس Technical safety.

بل يسأل:

```text
أي Version تحقق Outcomes أفضل؟
```

مثال:

```text
Version A = Tutor مشجع
Version B = Tutor سقراطي
```

يتم تقسيم المستخدمين بين Variants.

ثم تتم مقارنة Quality/business outcomes.

---

## 55. قرارات A/B غالبًا يقودها البشر

قد يوقف Canary تلقائيًا Release عند فشل Technical/safety thresholds.

أما A/B tests فغالبًا تحتاج مراقبة أطول.

قد يراجع Product Owner:

```text
نواتج التعلّم
تقييمات المستخدمين
درجات Autorater
المشاركة
```

ويختار Variant الأفضل.

## 56. قارن Release strategies

| الاستراتيجية | الهدف الأساسي | Traffic | Rollback/Decision |
|---|---|---|---|
| النشر الأزرق/الأخضر (Blue/Green) | استبدال آمن | تبديل 0/100 | عودة سريعة |
| النشر التدريجي (Canary) | تقليل Technical blast radius | جزء يتزايد تدريجيًا | غالبًا آلي |
| اختبار A/B (A/B Test) | مقارنة جودة Product/AI | Cohorts مقصودة | غالبًا قرار بشري قائم على Data |

لا تستخدم هذه المصطلحات بالتبادل.

## 65. قاعدة Cross-layer production dependency

مثال:

```text

تستخدم
Production Data
```

### نقطة مهمة

## 66. الفرق المستقلة تنشئ Compatibility risk

## 82. مبادئ Production التي يجب الاحتفاظ بها

### 1. لا تنشر مباشرة من Laptop الخاص بـ Developer

### 2. تحقّق من Software العادية قبل AI Evaluation المكلفة

افشل مبكرًا.

### 3. افصل Development عن Staging

لكل منهما أهداف مختلفة.

### 4. تعامل مع AI quality كـ Deployable gate

لا تعتمد على Syntax/unit tests فقط.

### 5. أتمت Registration

ينبغي أن تعكس Registry state الواقع.

### 6. ما تزال Human approval مهمة

Automation لا تلغي Accountability.

### 7. استخدم Safe release strategies

قلل Downtime وBlast radius.

### 8. راقب بعد Deployment

Production هي بيئة Evaluation أخرى.

### 9. افصل الفرق باستخدام Stable contracts

يتطلب Independent delivery توافقًا.

### 10. احكم Versions

للخدمات Live القديمة Cost فعلية.

- User feedback،
- Autorater monitoring،
- Resource/cost monitoring،
- Owner alerts.

### التوسع متعدد الفرق

- Lifecycles منفصلة،
- Contract tests،
- MCP/A2A compatibility،
- Version pinning،
- Deprecation policy.

## 84. تفاصيل خاصة بالمصدر يجب إعادة التحقق منها

هذا الفصل من مواد Early Release.

أعد التحقق قبل Implementation من:

- Syntax الدقيقة لمنتجات CI/CD،
- Cloud build systems الحالية،
- Folder conventions الدقيقة،
- Paths/fields المحددة لـ Agent Card،
- أدوات Simulator/Autorater الدقيقة،
- Registry APIs الدقيقة،
- تنفيذ Approval portal المحدد،
- نسب Canary traffic،
- مدة Deprecation،
- OpenTelemetry AI conventions،
- Schemas الحالية لـ MCP/A2A،
- نماذج Security الخاصة بـ Cloud runner.

تعامل مع النسب المحددة وفترات Retention الواردة في المصدر كأمثلة توضيحية ما لم تعتمدها مؤسستك صراحةً.

```text
مراقبة مستمرة
دورات حياة منفصلة
عقود قياسية
حوكمة الإصدارات
feedback مستمر
```

## 85. النموذج الذهني الكامل

تعمل منصة AgentOps النهائية هكذا:

```text
تغيير Developer
   ↓
Feature branch
   ↓
Lightweight Dev pipeline
   ↓
Manual iteration
   ↓
Pull Request
   ↓
Main branch
   ↓
Validated build
   ↓
Development
   ↓
Approval
   ↓
Staging
   ↓
Golden + Simulator + Autorater evaluation
   ↓
Registration as Code
   ↓
Final approval
   ↓
Blue/Green / Canary / A/B
   ↓
Production
   ↓
OpenTelemetry + User feedback + Autoraters
   ↓
Agent Registry
   ↓
Issue triage
   ↓
Feature branch التالية
```

على Enterprise scale، تصبح هذه الحلقة الواحدة عدة حلقات متوازية:

```text
Data — البيانات
Tools/APIs — الأدوات والواجهات
Frontend — الواجهة
Agent — الوكيل
```

يتحرك كل فريق بصورة مستقلة.

وتظل متوافقة من خلال:

```text
العقود
السجلات (registries)
MCP
A2A
سياسة الإصدارات
الحوكمة
```

وهذه هي AgentOps Infinity Loop.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "Agent يعمل محليًا جاهز لـ Production."

لا. تتطلب Production readiness Build وTest وDeployment وGovernance وMonitoring وRollback قابلة للتكرار.

### المفهوم الخاطئ 2
> "كل Push إلى Feature branch يجب أن يصل إلى Production."

لا. تنتمي Feature branches إلى Workflows آمنة في Development.

### المفهوم الخاطئ 3
> "Syntax وUnit tests تثبت أن Agent جيد."

لا. تثبت صحة Software، لا الجودة المعرفية/السلوكية.

### المفهوم الخاطئ 4
> "Development وStaging قابلتان للتبادل."

لا. ينبغي لـ Staging إعادة إنتاج قيود Production ودعم Automated quality gates.

### المفهوم الخاطئ 5
> "Human approval يجعل CI/CD غير Automated."

لا. Approval خطوة Gate مقصودة داخل نظام آلي في ما عداها.

### المفهوم الخاطئ 6
> "Simulator هو المُقيِّم."

لا. Simulator يولد التفاعل؛ أما Autorater أو Evaluator آخر فيحكم عليه.

### المفهوم الخاطئ 7
> "Registration تنتمي إلى النهاية كأعمال ورقية يدوية."

لا. يمكن أتمت Registration وتحديثها خلال Lifecycle كلها.

### المفهوم الخاطئ 8
> "Agent Registry مجرد Directory قابلة للبحث."

لا. يمكن أن تصبح Live command center للإصدارات، والبيئات، والمقاييس، والموافقات، وحالة Deployment.

### المفهوم الخاطئ 9
> "Deployment ينهي Governance."

لا. Production monitoring تبدأ دورة التحسين التالية.

### المفهوم الخاطئ 10
> "Blue/Green وCanary وA/B متكافئة."

لا. كل منها يحسن هدفًا مختلفًا.

### المفهوم الخاطئ 11
> "Rollback يغير Network traffic فقط."

لا. ينبغي أيضًا تصحيح Governance وRegistry state.

### المفهوم الخاطئ 12
> "Canary وA/B يجيبان كلاهما عن أي Persona يفضلها المستخدمون."

لا. Canary يدير أساسًا Technical release risk؛ أما A/B فيقارن Product/behavior outcomes.

### المفهوم الخاطئ 13
> "Repository وPipeline ضخمتان تجعل الأنظمة المؤسسية أسهل."

ليس بالضرورة. قد تقللان سرعة الفرق المستقلة.

### المفهوم الخاطئ 14
> "يمكن للفرق المستقلة تغيير Interfaces متى شاءت بأمان."

لا. يعتمد Decoupling على Contracts قوية وCompatibility testing.

### المفهوم الخاطئ 15
> "Version pinning بلا تكلفة."

لا. تستهلك إصدارات Agent الحية بنية تحتية وموارد تشغيلية فعلية.

### المفهوم الخاطئ 16
> "ينبغي أن تختفي إصدارات Agent القديمة تمامًا."

قد يتوقف Execution، لكن يمكن أن تبقى Metadata وAudit history مؤرشفة.

### المفهوم الخاطئ 17
> "Production feedback تنتمي فقط إلى Dashboards."

لا. ينبغي أن تنتج عملًا قابلًا للتنفيذ وحالات Evaluation جديدة.

### المفهوم الخاطئ 18
> "لـ AgentOps نقطة نهاية مستقرة ونهائية."

لا. النموذج النهائي في المصدر Infinity Loop من التحسين المستمر.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| CI/CD | Workflow آلية للتكامل والاختبار والبناء وDeployment |
| فرع الميزة (Feature Branch) | Branch معزولة تُستخدم للتجربة |
| الفرع الرئيسي (Main Branch) | Branch تكامل لمرشحي Production |
| Pipeline as Code | عملية Deployment خاضعة لـ Version control |
| عقد Repository (Repository Contract) | بنية Project قياسية تتوقعها Automation |
| Container | Runtime artifact محمولة ومغلفة |
| بيئة التطوير (Development) | بيئة سريعة ومتساهلة لـ Manual engineering iteration |
| بيئة ما قبل الإنتاج (Staging) | بيئة شبيهة بـ Production للتحقق الآلي |
| بيئة الإنتاج (Production) | بيئة End-user الحية |
| بوابة الجودة (Quality Gate) | شرط يجب اجتيازه قبل Promotion |
| Golden Dataset | حالات Evaluation معروفة ومنسقة |
| Simulator | Agent يولد Test interactions |
| Autorater | AI evaluator يقيّم تفاعلًا |
| Trajectory Evaluation | تقييم تسلسل Tool/action، لا Final output فقط |
| Registration as Code | تحديثات Registry برمجية تنفذها CI/CD |
| Agent Registry | سجل تشغيلي لـ Agents المنشورة |
| Tool Registry | سجل تشغيلي لـ Tools المحكومة |
| بوابة موافقة يدوية | نقطة فحص بشرية داخل Automated promotion |
| OpenTelemetry | معيار لـ Distributed telemetry |
| النشر الأزرق/الأخضر (Blue/Green) | Release ببيئتين مع تبديل Traffic دفعة واحدة |
| النشر التدريجي (Canary) | Live rollout تدريجي على جزء صغير من Traffic |
| اختبار A/B (A/B Test) | تجربة متوازية تقارن Product/behavior outcomes |
| Rollback | إعادة Traffic/Service state إلى Stable version السابقة |
| Blast Radius | عدد/نطاق المستخدمين المتأثرين بفشل |
| Contract Testing | التحقق من بقاء تغييرات Interface/Schema متوافقة |
| MCP | Protocol موحد لـ Tool/context يُستخدم كعقد Integration |
| A2A | Protocol موحد Agent-to-agent يُستخدم كعقد Service |
| Version Pinning | طلب Consumer إصدار Agent محدد |
| Deprecation | التقاعد المخطط لإصدار |
| تبعية إنتاج عبر الطبقات | مبدأ المصدر لاختبار Layer متغيرة واحدة مقابل Dependencies مستقرة بدرجة Production |
| Infinity Loop | دورة مستمرة من Feedback وIteration وEvaluation وDeployment |

**تحويل AgentOps إلى Production هو Loop محكومة وقابلة للتكرار، وليس Deployment لمرة واحدة. يتحرك Source code عبر Pipelines خاضعة لـ Version control، وValidation موحدة، وDevelopment feedback، وStaging شبيهة بـ Production، وAI-specific evaluation، وتحديثات Registry آلية، وHuman governance gates، وSafe release strategies، وContinuous production monitoring. وعلى Enterprise scale، تتطور فرق Data وTool وFrontend وAgent بصورة مستقلة، لذلك تصبح عقود MCP/A2A/API الموحدة ودورات حياة Version المحكومة ضرورية. ثم تنشئ Production feedback الـ Feature branch التالية، لتكتمل Infinity Loop من التحسين المستمر.**
