بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- التمييز بين correlation وcausation والتعرف على تفسيرات متعددة للعلاقة التي نلاحظها.
- تعريف experiment hypothesis واضحة.
- اختيار primary success metric وguardrail metrics مناسبة.
- شرح لماذا يؤدي استخدام عدد كبير من success metrics إلى زيادة خطر false discoveries.
- وصف random assignment وشرح أهميتها لصحة experiment.
- بناء SQL summaries لتجارب binary outcomes.
- بناء SQL summaries لتجارب continuous outcomes.
- شرح دور chi-squared tests وtwo-sample t-tests في workflow تحليل التجارب في هذا الفصل.
- الحفاظ بصورة صحيحة على المستخدمين ذوي zero outcomes باستخدام `LEFT JOIN` و`COALESCE`.
- تشخيص مشكلات assignment وeligibility وsample size.
- اكتشاف experiment contamination مثل ظهور user نفسه في أكثر من variant.
- التعرف على كيفية تشويه outliers لمقاييس التجارب المستمرة.
- تطبيق time boxing بحيث يحصل المشاركون على observation windows قابلة للمقارنة.
- شرح novelty effects وregression to the mean وlong-term holdouts في repeated-exposure experiments.
- استخدام pre/post analysis وnatural experiments وthreshold-based analysis عندما لا تكون randomized experiments ممكنة.
- توضيح متى يكون الدليل causal ومتى يكون suggestive فقط.

## 1. لماذا تهم التجارب: Correlation لا تعني Causation

قدر كبير من تحليل البيانات يكون observational.

قد تكتشف مثلًا:

```text
المستخدمون الذين يستخدمون Feature X يحتفظون لمدة أطول (users who use Feature X retain longer)
العملاء الذين يتواصلون مع الدعم ينفقون أكثر (customers who contact support spend more)
الأشخاص الذين يفتحون رسائل البريد يشترون أكثر (people who open emails purchase more)
```

قد تكون هذه observations مفيدة.

لكنها لا تثبت تلقائيًا:

```text
Feature X تسبب Retention (Feature X causes retention)
الدعم يسبب زيادة الإنفاق (support causes spending)
فتح البريد يسبب الشراء (email opening causes purchasing)
```

### خمسة تفسيرات محتملة للعلاقة

إذا تحرك المتغيران `X` و`Y` معًا، فهناك عدة تفسيرات محتملة.

#### 1. X يسبب Y

```text
X -> Y
```

هذه هي causal relationship التي تحاول experiment غالبًا إثباتها.

#### 2. Y يسبب X

```text
Y -> X
```

العلاقة حقيقية، لكن الاتجاه معكوس.

مثال:

```text
المطر (rain) -> المظلات (umbrellas)
```

وليس:

```text
المظلات (umbrellas) -> المطر (rain)
```

#### 3. متغير ثالث يسبب الاثنين

```text
      Z
     /     X   Y
```

مثال:

```text
الطقس الحار -> مبيعات الآيس كريم
الطقس الحار -> استخدام مكيفات الهواء
```

قد تكون ice-cream sales وair-conditioner usage مترابطتين دون أن تسبب إحداهما الأخرى.

#### 4. توجد Feedback Loop

```text
X -> Y -> X -> Y ...
```

مثال:

```text
تفاعل أقل
-> توصيات أقل
-> تفاعل أقل
```

يصبح فصل اتجاه السببية observationally صعبًا.

#### 5. العلاقة الظاهرة عشوائية

مع وجود metrics كثيرة وcomparisons كثيرة، ستظهر بعض correlations بالمصادفة.

[[IMAGE_NEEDED: IMG-M01-L07-01 / Instructor Figure — Five explanations for correlation | Show X and Y with five small relationship diagrams: X causes Y, Y causes X, common cause Z points to both, feedback loop between X and Y, and no real relationship/random coincidence | Learner should notice that observing correlation alone cannot identify which causal structure produced it]]

### لماذا تساعد Randomization؟

تحاول randomized experiment جعل treatment assignment مستقلة عن خصائص المستخدم.

إذا عملت randomization بصورة جيدة:

```text
control — المجموعة الضابطة
```

و:

```text
variant — النسخة التجريبية
```

ينبغي أن يكونا متشابهين قبل treatment.

ويجب أن يكون الاختلاف المنهجي المهم هو:

```text
أي تجربة تلقاها المستخدم (which experience they received)
```

يعطينا ذلك أساسًا أقوى بكثير لنسب الاختلافات في outcomes إلى treatment.

## 2. الأجزاء الثلاثة المطلوبة في Experiment

تحتاج online experiment مفيدة إلى ثلاثة أشياء على الأقل.

### 1. Hypothesis

Hypothesis هي prediction محددة لما سيحدث عند تغيير شيء ما.

ضعيفة:

```text
التجربة الجديدة لبدء الاستخدام أفضل. (The new onboarding is better.)
```

أفضل:

```text
تقليل onboarding من ست شاشات إلى أربع سيزيد نسبة
المستخدمين الجدد الذين يكملون onboarding.
```

تتضمن hypothesis الجيدة:

```text
التغيير (change)
-> الأثر السلوكي المتوقع (expected behavioral effect)
```

### 2. Success Metric

يجب أن تقيس metric السلوك الذي تتناوله hypothesis.

أمثلة:

```text
معدل إتمام الدفع (checkout completion rate)
معدل النقر (click-through rate)
الوقت اللازم لإتمام الإعداد الأولي (onboarding)
التحويل إلى شراء (purchase conversion)
عدد المقالات المقروءة
المبلغ المنفَق
```

ينبغي أن تكون success metric الجيدة:

- قابلة للقياس؛
- حساسة بصورة معقولة لـ treatment؛
- مفهومة؛
- مرتبطة بالسلوك محل الاهتمام.

قد تكون metric بعيدة مثل long-term satisfaction مهمة استراتيجيًا، لكنها noisy بدرجة كبيرة لاكتشاف أثر UI experiment صغيرة.

### 3. Random Assignment

يجب توزيع users — أو أي experimental unit مختارة — على:

```text
control — المجموعة الضابطة
variant A — النسخة A
variant B — النسخة B
...
```

من خلال random assignment system.

يجب أن تتوفر assignment data للتحليل.

يحتوي data model المعتاد على:

```text
experiment_assignment — جدول تعيين التجربة
---------------------
experiment_name
user_id
variant
assignment_time
```

وجداول behavior منفصلة مثل:

```text
events — الأحداث
purchases — المشتريات
sessions — الجلسات
```

[[IMAGE_NEEDED: IMG-M01-L07-02 / Instructor Figure — Anatomy of an online experiment | Show eligible users entering a random-assignment step, splitting into Control and Variant, each receiving a different experience, then both producing behavior events that flow into the same success-metric calculation; add a small guardrail-metrics branch beneath | Learner should notice that the analysis depends on a predefined hypothesis, random assignment, and the same measurement logic for both groups]]

## 3. Primary Metrics وGuardrails ومشكلة Multiple Comparisons

من السهل حساب metrics كثيرة باستخدام SQL.

لكن هذا لا يعني أن كل metric يجب اعتبارها success metric.

### Primary Metric

تجيب **primary success metric** عن hypothesis الرئيسية.

مثال:

```text
الفرضية (Hypothesis):
الإعداد الأولي الجديد يزيد معدل الإتمام.

المقياس الأساسي (Primary metric):
معدل إتمام الإعداد الأولي (Onboarding).
```

### Guardrail Metrics

تحمي guardrails من الأضرار غير المقصودة.

مثال:

```text
المقياس الأساسي:
التحويل في صفحة الدفع (checkout)

مقاييس الحماية (Guardrails):
زمن تحميل الصفحة
معدل الاسترداد
طلبات الدعم
```

قد تحسن experiment الـ primary metric بينما تضر شيئًا آخر.

### كثرة Metrics تخلق مشكلة

إذا اختبرت metrics كثيرة بما يكفي، فقد يبدو بعضها significant بالمصادفة.

هذه هي **multiple comparisons problem**.

قاعدة عملية من الفصل هي إبقاء عدد primary metrics صغيرًا — غالبًا واحدة أواثنتين — مع مجموعة محدودة من guardrails.

### اختر Metrics قبل رؤية النتيجة

إذا اختار analysts الـ metric بعد الاطلاع على data، فقد يختارون دون قصد metric تجعل experiment تبدو ناجحة.

workflow أفضل هو:

```text
الفرضية
-> المقياس الأساسي
-> مقاييس الحماية (guardrails)
-> التجربة
-> التحليل
```

وليس:

```text
التجربة
-> حساب 40 مقياسًا
-> اختيار أجمل نتيجة
```

## 4. تجارب Binary Outcomes

Binary outcome لها حالتان:

```text
أكمل / لم يكمل
نقر / لم ينقر
اشترى / لم يشترِ
تخرّج / لم يتخرّج
```

عادةً ما تكون metric الأساسية rate:

```text
عدد النجاحات / عدد الوحدات المعرَّضة للتجربة
```

### مثال على السؤال

افترض أننا نختبر onboarding flow جديدة.

يحتوي experiment table على:

```text
user_id — معرّف المستخدم
experiment_name — اسم التجربة
variant — النسخة
```

ويحتوي event table على:

```text
user_id — معرّف المستخدم
action — الإجراء
event_time — وقت الحدث
```

النتيجة المطلوبة هي:

```text
variant      total_users      completions      completion_rate — رؤوس الأعمدة
control      ...              ...              ...
variant      ...              ...              ...
```

### استخدم `LEFT JOIN`

هذا أمر حاسم.

إذا استخدمت inner join مع success event، فستحتفظ فقط بالمستخدمين الذين نجحوا.

وعندها:

```text
معدل الإتمام = 100%
```

بحكم البناء نفسه.

النمط الصحيح:

⟦CODE_0⟧

توفر assignment table الـ denominator.

وتوفر event table الـ numerator.

### Contingency Table

يمكن أيضًا تمثيل binary experiment كالتالي:

| Variant | Completed | Not completed |
|---|---:|---:|
| Control | ... | ... |
| Variant | ... | ... |

هذه هي البنية الشائعة المستخدمة في chi-squared comparison للنتائج categorical.

### في Workflow الفصل

تجهز SQL:

```text
عدد المعيَّنين
عدد الناجحين
معدل النجاح
```

ويُنفذ حساب statistical significance خارج SQL باستخدام statistical tool أوcalculator مناسبة.

### Statistical Significance ليست Practical Significance

افترض:

```text
control = 40.00% — المجموعة الضابطة
variant = 40.08% — النسخة التجريبية
```

قد تجعل sample ضخمة هذا الفرق statistically detectable.

لكن business question يظل:

```text
هل يستحق فرق +0.08 نقطة مئوية إطلاق التغيير؟
```

فسر دائمًا الاثنين معًا:

```text
الدليل الإحصائي (statistical evidence)
```

و:

```text
حجم الأثر / القيمة التجارية
```

## 5. تجارب Continuous Outcomes

يمكن لـ continuous metric أخذ قيم رقمية كثيرة.

أمثلة:

```text
الإيراد لكل مستخدم
مدة الجلسة
عدد المقالات المقروءة
عدد الأيام النشطة
الوقت اللازم لإتمام عملية
```

في هذه التجارب، نقارن غالبًا **mean** بين variants.

### احسب قيمة واحدة لكل Experimental Unit أولًا

افترض أن users يمكنهم إجراء purchases متعددة.

لا تحسب average لصفوف purchases وتعتبرها average user spending.

أولًا اجمع data على مستوى user:

⟦CODE_1⟧

experimental unit هي user.

إذًا يجب حساب success metric **لكل user أولًا**.

### لماذا تهم Zeroes؟

user الذي لم يجرِ purchase ينبغي عادةً أن يساهم بقيمة:

```text
0
```

في spend per user.

إذا بقيت القيمة `NULL`، فإن functions مثل `AVG` تتجاهلها عادةً.

وهذا يغير السؤال من:

```text
كم ينفق المستخدم المعيّن في المتوسط؟ (How much does the average assigned user spend?)
```

إلى:

```text
كم ينفق المشتري في المتوسط؟ (How much does the average purchaser spend?)
```

وهاتان metric مختلفتان.

استخدم:

⟦CODE_2⟧

عندما تكون zero هي business meaning الصحيحة.

### اختبار t لعينتين (Two-Sample T-Test)

بالنسبة إلى continuous outcomes، يستخدم الفصل workflow لـ two-sample t-test.

summary inputs هي:

```text
المتوسط (mean)
الانحراف المعياري
عدد المشاهدات
```

لكل variant.

[[IMAGE_NEEDED: IMG-M01-L07-03 / Instructor Figure — Binary versus continuous experiment analysis | Split into two paths: Binary outcome -> successes + total exposed -> conversion rate -> chi-squared-style significance test; Continuous outcome -> one metric value per user -> mean + standard deviation + count -> two-sample t-test; beneath both paths show final interpretation as statistical evidence + effect size + business meaning | Learner should notice that the SQL summary required depends on the type of outcome being measured]]

### لا تغيّر Success Metric بعد رؤية النتيجة

تخيل:

```text
النسخة التجريبية تحسّن إتمام الإعداد الأولي.
النسخة التجريبية لا تحسّن الإنفاق الإجمالي.
بين من أكملوا الإعداد، ينفق مستخدمو control أكثر.
```

أي نتيجة تحدد النجاح؟

تعتمد الإجابة على hypothesis وprimary metric اللتين حُددتا قبل experiment.

إذا كانت hypothesis:

```text
تحسين إتمام الإعداد الأولي
```

فإن completion هي primary test.

أما إذا كانت hypothesis:

```text
زيادة الإيراد عبر رفع معدل إتمام الإعداد الأولي
```

فإن revenue result تهم مباشرةً.

تعريف metric جزء من experiment design، وليس إضافة بعد التحليل.

## 6. تحقق من Variant Assignment قبل الوثوق بالنتيجة

تمثل randomization أساس صحة experiment.

قبل قراءة outcome، اعمل profile لـ assignment data.

### افحص أحجام Variants

⟦CODE_3⟧

عدم تساوي المجموعات لا يعني تلقائيًا أن experiment غير صالحة.

لكن imbalance غير المتوقع يستحق التحقيق.

### افحص Users المعينين إلى أكثر من Variant

⟦CODE_4⟧

ظهور user في control وtreatment معًا قد يلوث experiment.

### افحص Eligibility

قد تستهدف experiment مثلًا:

```text
المستخدمون الجدد فقط
```

بينما يضيف assignment system كل users بالخطأ.

يمكن لـ SQL تقييد analysis بالمستخدمين المؤهلين المقصودين:

⟦CODE_5⟧

لكن انتبه.

filtering بعد وقوع المشكلة لا يصلح كل experimental flaws.

### عدد Assigned Users قليل جدًا

إذا كانت sample صغيرة جدًا، فقد لا تملك experiment معلومات كافية لاكتشاف meaningful differences.

قد تكون الاستجابة الصحيحة:

```text
مواصلة التجربة أو إعادة تشغيلها
```

بدلًا من إجبار analysis على conclusion.

### Populations مفقودة بصورة غير عشوائية

افترض أن الإصدارات القديمة من app لا تستطيع الدخول إلى experiment.

إذا اختلف هؤلاء users بصورة منهجية عن included users، فقد لا تعمم النتيجة على population كلها.

اسأل:

```text
من الذي استُبعد؟
لماذا؟
ما حجم هذه المجموعة؟
هل يختلف سلوكها؟
```

### اختبارات A/A

يقسم **A/A test** المستخدمين إلى مجموعتين randomized، لكن المجموعتين تحصلان على التجربة نفسها.

النتيجة المتوقعة:

```text
لا يوجد فرق منهجي ذو معنى
```

إذا اختلفت المجموعتان باستمرار، افحص:

- assignment logic؛
- tracking؛
- metric calculation؛
- experiment infrastructure.

A/A tests مفيدة لفحص experimentation system نفسها.

## 7. يمكن لـ Outliers تشويه Continuous Experiment Metrics

تعتمد continuous metrics غالبًا على averages.

يمكن لعدد قليل من القيم المتطرفة التأثير بشدة.

مثال:

```text
مجموعة Control:
معظم المستخدمين ينفقون 0–20
مستخدم واحد ينفق 20,000

مجموعة Variant:
معظم المستخدمين ينفقون 0–20
```

قد يغير user واحد في control الـ mean بصورة كبيرة.

### طبق تقنيات Anomaly Detection

يمكنك:

- فحص percentile distributions؛
- حساب z-scores؛
- مقارنة means مع extreme observations وبدونها؛
- استخدام winsorize؛
- transform الـ metric إذا كان ذلك مبررًا.

### لا تحذف Outliers فقط لأنها تضر النتيجة

اسأل:

```text
هل القيمة صالحة؟
هل هي جزء من الفئة التي قُصد أن تؤثر فيها التجربة؟
هل ستُطبَّق القاعدة نفسها على النسختين؟
هل تقرر أسلوب المعالجة بصورة متسقة؟
```

### حوّل Continuous Metric إلى Binary Metric عندما يكون ذلك مفيدًا

بدلًا من:

```text
متوسط الإنفاق
```

قد تقيس:

```text
هل اشترى المستخدم؟ نعم/لا
```

هذا يجيب عن سؤال مختلف، لكنه قد يكون أقل حساسية لعدد قليل من purchases الضخمة.

وقد تكون threshold metric أخرى مثل:

```text
قرأ 3 مقالات على الأقل
استخدم التطبيق مرتين على الأقل هذا الأسبوع
أنفق 100 EGP على الأقل
```

يجب أن تكون threshold ذات معنى، لا مختارة فقط لصناعة significance.

## 8. ينشئ Time Boxing Observation Windows عادلة

افترض أن experiment تستمر ثلاثة أسابيع.

يدخل User A في اليوم 1.

ويدخل User B في اليوم 20.

إذا قست total purchases حتى اليوم 21:

```text
المستخدم A كان لديه 21 يومًا
المستخدم B كان لديه يوم واحد (1)
```

هذه ليست مقارنة عادلة.

### عرّف Window ثابتة من Assignment

مثال:

```text
7 أيام بعد التعيين
```

نمط SQL:

⟦CODE_6⟧

يحصل كل user على opportunity window نفسها.

### اختر Window وفق Behavior

أمثلة:

```text
نقرة إعلان -> دقائق أو ساعات
إتمام الدفع -> ساعات أو أيام
الشراء -> عدة أيام
تجديد الاشتراك -> مدة أطول بكثير
```

تعطي window الأقصر نتائج أسرع لكنها قد تفوّت behavior يحتاج وقتًا أطول.

أما window الأطول فهي أكثر اكتمالًا لكنها تؤخر analysis.

### انتظر حتى يحصل Users على Window كاملة

إذا كانت metric هي seven-day revenue، فإن users الذين عُينوا أمس لم يحصلوا بعد على seven-day outcome.

إما:

- تنتظر؛
- تستبعد users الذين لم يمروا بعد بالـ full window؛
- أوتحدد بوضوح أن outcomes الخاصة بهم غير مكتملة.

يجب أن تكون time-boxing logic جزءًا من metric definition.

## 9. تحتاج Repeated-Exposure Experiments إلى تفكير أطول مدى

بعض experiments هي **one-and-done**.

أمثلة:

```text
مسار التسجيل
تسجيل يحدث مرة واحدة
الإعداد الأولي لأول مرة
```

يرى user الـ treatment مرة واحدة.

أما experiments أخرى فتخلق **repeated exposure**.

أمثلة:

- navigation design؛
- button placement؛
- recommendation interface؛
- recurring email campaigns؛
- repeated promotions.

يتعرض user للـ treatment مرات كثيرة.

### Novelty Effect

قد تجذب interface جديدة الانتباه ببساطة لأنها جديدة.

قد يرتفع behavior مبدئيًا حتى لو لم يكن design أفضل فعلًا على المدى الطويل.

### الارتداد نحو المتوسط (Regression to the Mean)

قد تعود metric مرتفعة أومنخفضة بشكل غير معتاد نحو مستوى أكثر اعتيادية مع الوقت.

قد تنتج treatment:

```text
الأسبوع 1: تحسّن كبير
الأسبوع 2: تحسّن أصغر
الأسبوع 4: قريب من خط الأساس
```

السؤال المهم هو:

```text
ما الأثر المستقر على المدى الطويل؟
```

### اسمح بوقت كافٍ

في repeated exposure، قد يؤدي القياس المبكر جدًا إلى الخلط بين novelty والتحسن الدائم.

تعتمد المدة الصحيحة على المنتج والسلوك.

### مجموعات Holdout طويلة الأمد

long-term holdout هي مجموعة randomized لا تتلقى treatment المستمرة.

في marketing program:

```text
Treatment -> تتلقى حملات متكررة
Holdout   -> لا تتلقى أي حملة
```

يساعد ذلك في تقدير cumulative incremental value للبرنامج كاملًا.

لا تستبدل:

```text
الأشخاص الذين اختاروا عدم المشاركة (opted out)
```

بـ randomized holdout.

opt-out users اختاروا أنفسهم وقد يختلفون منهجيًا.

### يمكن لـ Cohort Analysis توسيع Experiment Analysis

يمكنك متابعة control وtreatment cohorts على مدار أسابيع أوأشهر ومقارنة:

- retention؛
- cumulative revenue؛
- repeated usage؛
- التفاعل طويل الأمد (long-term engagement).

غالبًا ما تعمل experimentation وcohort analysis معًا.

## 10. ما الذي تستطيع SQL إنقاذه — وما الذي لا تستطيع — في Experiment معيبة؟

تكلف experiments:

- engineering time؛
- design time؛
- marketing effort؛
- user exposure؛
- opportunity cost.

لذلك يرغب analysts طبيعيًا في إنقاذ experiments غير المثالية.

أحيانًا يكون ذلك ممكنًا.

وأحيانًا لا يكون.

### مشكلات قد تكون قابلة للاسترداد

أمثلة:

```text
عُيِّن عدد زائد من المستخدمين، لكن يمكن تحديد الأهلية بدقة
مجموعة فرعية معروفة لم تُتح لها فرصة رؤية المعالجة (treatment)
عدد صغير من صفوف البيانات غير الصالحة بوضوح يمكن تصحيحه
```

يمكن لـ SQL أحيانًا تعريف analysis population الصحيحة.

### مشكلات قد تكون قاتلة للتجربة

أمثلة:

```text
التعيين لم يكن عشوائيًا
مستخدمو control تلقوا المعالجة (treatment)
مستخدمو treatment ظهروا أيضًا في control
التتبع يختلف بصورة منهجية حسب النسخة
```

إذا انهار الأساس causal للتجربة، فلن تستطيع filtering دائمًا إصلاحه.

### كن واضحًا بشأن Limitations

لا تحوّل:

```text
أنقذنا مجموعة فرعية صالحة للاستخدام
```

إلى:

```text
التجربة الأصلية كانت صحيحة
```

بل أبلغ عن:

- ما الذي حدث خطأ؛
- ما الذي استُبعد؛
- لماذا تُعتبر population المعدلة قابلة للاستخدام؛
- ما uncertainty التي ما زالت قائمة.

## 11. عندما لا تكون Randomized Experiments ممكنة

لا تكون randomized experiments ممكنة دائمًا.

تشمل الأسباب:

- ethics؛
- regulation؛
- operational constraints؛
- historical changes حدثت بالفعل؛
- outages أوbugs؛
- natural events؛
- عدم إمكانية withholding treatment.

في هذه الحالات، يمكن للـ analysts استخدام أساليب **quasi-experimental** أضعف لكنها مفيدة.

تحاول هذه الأساليب إنشاء treatment وcomparison groups من observational data.

## 12. تحليل Pre/Post

يقارن **pre/post analysis** behavior قبل change محددة التوقيت وبعدها.

مثال:

```text
قبل:
تصميم الموافقة القديم على رسائل البريد (opt-in)

بعد:
تصميم موافقة جديد خاضع للتنظيم
```

### أنشئ Synthetic Variants

⟦CODE_7⟧

### استخدم Windows متقاربة الطول

إذا قارنت:

```text
أسبوعان (2) قبل التغيير
```

فاستخدم تقريبًا:

```text
أسبوعان (2) بعد التغيير
```

حتى تكون exposure opportunity قابلة للمقارنة.

يمكنك تكرار analysis باستخدام:

```text
نافذة طولها 1 أسبوع
نافذة طولها 2 أسبوع
نافذة طولها 3 أسابيع
نافذة طولها 4 أسابيع
```

إذا بقي conclusion مستقرًا عبر عدة windows معقولة، تزداد الثقة.

### القيد الأساسي

يمكن أن تتغير أشياء كثيرة عبر الزمن:

- seasonality؛
- marketing؛
- holidays؛
- economic conditions؛
- external events؛
- product changes.

إذًا:

```text
post != pre — ما بعد التغيير يختلف عما قبله
```

لا يثبت:

```text
التغيير المستهدف هو سبب الفرق
```

يمكن لـ pre/post analysis دعم hypothesis، لكن causal evidence أضعف من randomized experimentation.

## 13. Natural Experiments

تحدث **natural experiment** عندما تحصل مجموعات مختلفة على تجارب مختلفة من خلال عملية تشبه random exposure تقريبًا.

أمثلة:

- software bug يؤثر على دولة واحدة؛
- outage يؤثر على region واحدة؛
- policy تتغير في jurisdiction واحدة؛
- feature تصل إلى platform واحدة بالخطأ أولًا.

### المتطلبات

تحتاج إلى:

1. exposed group واضحة؛
2. comparison group؛
3. مجموعات متشابهة بدرجة معقولة قبل event.

### اختر Comparison Group بعناية

لا تقارن تلقائيًا:

```text
البلد المتأثر
```

مع:

```text
كل الآخرين
```

قد تكون المقارنة الأفضل دولة محددة لديها:

- user behavior متشابه؛
- language متشابهة؛
- product penetration متشابه؛
- demographics متشابهة.

أصعب جزء غالبًا ليس SQL.

بل تبرير:

```text
لماذا تُعد مجموعة المقارنة هذه موثوقة؟
```

### ما زالت SQL تجهز Outcome Summaries نفسها

بالنسبة إلى binary outcomes:

```text
group — المجموعة
total exposed — إجمالي المعرَّضين للتجربة
successes — النجاحات
success rate — معدل النجاح
```

وبالنسبة إلى continuous outcomes:

```text
group — المجموعة
count — العدد
mean — المتوسط
standard deviation — الانحراف المعياري
```

قد تشبه statistical mechanics الخاصة بـ A/B test، لكن causal interpretation يجب أن تكون أكثر حذرًا.

## 14. التحليل حول Treatment Threshold

أحيانًا يُعيَّن treatment باستخدام threshold.

أمثلة:

```text
GPA >= العتبة -> منحة دراسية
الدخل < العتبة -> دعم مالي
درجة churn > العتبة -> تدخل من فريق المبيعات
```

قد يكون الأشخاص فوق threshold مباشرةً وتحتها مباشرةً متشابهين جدًا.

وهذا يخلق فرصة لمقارنة near-boundary groups.

الطريقة الرسمية التي يناقشها الفصل هي **regression discontinuity design (RDD)**.

### الفكرة الأساسية

افترض أن treatment يبدأ عند score 80.

بدلًا من مقارنة:

```text
كل الأشخاص دون 80
مقابل (vs)
كل الأشخاص فوق 80
```

قارن:

```text
75–79.99
vs
80–84.99
```

قد تكون populations هذه أكثر قابلية للمقارنة.

### Bandwidth مهمة

ما عرض النطاق الذي ينبغي استخدامه؟

لا توجد إجابة عالمية.

قد تقارن:

```text
±5%
±7.5%
±10%
```

حول threshold.

إذا كانت conclusions متسقة عبر bands معقولة، تزداد الثقة.

أما إذا تغيرت كثيرًا، فقد تكون النتيجة inconclusive.

### Confounding ما زال مهمًا

افترض أن high-risk customers يتلقون:

```text
مكالمة مبيعات
خصم
بريد إلكتروني خاص
دعم ذو أولوية
```

عند threshold نفسها.

عندها يصعب نسب observed effect إلى sales call فقط.

يمكن لـ RDD-style analysis تقوية observational evidence، لكنها ما زالت تحتاج assumptions حذرة.

## 15. Workflow عملية لتحليل Experiment

استخدم هذا التسلسل قبل إعلان winner.

### الخطوة 1 — اكتب Hypothesis

مثال:

```text
تقليل الإعداد الأولي من ست شاشات إلى أربع
سيزيد معدل إتمام الإعداد الأولي.
```

### الخطوة 2 — عرّف Experimental Unit

أمثلة:

```text
user — المستخدم
account — الحساب
session — الجلسة
store — المتجر
device — الجهاز
```

لا تخلط بين units بالخطأ.

### الخطوة 3 — عرّف Primary Metric

اكتب numerator وdenominator أوper-unit measure بدقة.

مثال:

```text
completion_rate =
المستخدمون الذين لديهم onboarding_complete
/
كل المستخدمين المؤهلين المعيَّنين
```

### الخطوة 4 — عرّف Guardrails

أمثلة:

```text
معدل الأعطال (crash rate)
زمن تحميل الصفحة
معدل الاسترداد
طلبات الدعم
```

### الخطوة 5 — تحقق من Assignment

افحص:

- group sizes؛
- duplicate assignments؛
- users في أكثر من variant؛
- eligibility؛
- بيانات التعيين المفقودة (missing assignment data).

### الخطوة 6 — ابنِ Metric Value واحدة لكل Unit

Binary:

```text
success = 0 أو 1 لكل مستخدم
```

Continuous:

```text
revenue = إجمالي الإيراد لكل مستخدم
```

### الخطوة 7 — طبق Observation Window عادلة

استخدم assignment time كنقطة البداية.

وتأكد أن كل analyzed unit حصلت على وقت كافٍ.

### الخطوة 8 — اعمل Profile للـ Outliers

خصوصًا في continuous metrics.

لا تتعامل معها بصورة مختلفة حسب variant.

### الخطوة 9 — أنشئ Statistical Inputs

Binary:

```text
successes — النجاحات
total units — إجمالي الوحدات
rate — المعدل
```

Continuous:

```text
mean — المتوسط
standard deviation — الانحراف المعياري
count — العدد
```

### الخطوة 10 — قيّم Statistical Evidence

استخدم statistical method المناسبة لنوع outcome.

### الخطوة 11 — فسّر Practical Value

اسأل:

```text
ما حجم الأثر؟
هل يهم ذلك للعمل التجاري؟
هل ساءت مقاييس الحماية (guardrails)؟
```

### الخطوة 12 — اذكر Conclusion بالقوة المناسبة

جيدة:

```text
النسخة المعيَّنة عشوائيًا زادت إتمام الإعداد الأولي في هذه التجربة.
```

مبالغ فيها:

```text
هذا التصميم سيحسّن كل مقاييس المستخدمين في المستقبل.
```

### الخطوة 13 — إذا كانت Experiment معيبة، اذكر العيب

لا تخفِ:

- assignment problems؛
- incomplete windows؛
- exclusion rules؛
- contamination؛
- external events.

تحليل التجارب الجيد يتعلق بالمصداقية بقدر ما يتعلق بالحساب.

## مفاهيم خاطئة مهمة (Important Misconceptions)

### المفهوم الخاطئ 1

> إذا تحركت metric مع أخرى، فلا بد أن إحداهما تسبب الأخرى.

يمكن أن ينشأ correlation من reverse causality أوcommon causes أوfeedback loops أوchance.

### المفهوم الخاطئ 2

> المزيد من Success Metrics يجعل Experiment أكثر إفادة.

كثرة comparisons تزيد احتمال العثور على نتائج تبدو significant بالمصادفة.

### المفهوم الخاطئ 3

> Users الذين نفذوا success action فقط هم من ينتمون إلى denominator.

يشمل denominator عادةً جميع eligible assigned units، بما في ذلك failures.

### المفهوم الخاطئ 4

> Effect statistically significant تعني تلقائيًا أنها ذات قيمة.

قد يكون effect صغيرًا جدًا لكنه statistically detectable وغير مهم عمليًا.

### المفهوم الخاطئ 5

> User بلا Purchases يجب أن يظل `NULL` في Spend-Per-User Analysis.

إذا كانت zero purchases تعني zero spend، فإن استخدام `NULL` قد يستبعد nonbuyers بصورة خاطئة من average.

### المفهوم الخاطئ 6

> Filtering للـ Bad Assignments يصلح دائمًا Experiment المعيبة.

بعض assignment failures تدمر randomization وبالتالي causal validity.

### المفهوم الخاطئ 7

> ينبغي تحليل Repeated-Exposure Experiments بأسرع ما يمكن.

قد تعكس early effects novelty بدلًا من behavior change دائمة.

### المفهوم الخاطئ 8

> Pre/Post Analysis تثبت Causality إذا كان الفرق Statistically Significant.

دون randomization، قد تفسر عوامل أخرى متغيرة مع الوقت الفرق.

## المصطلحات الأساسية (Key Terminology)

| المصطلح | المعنى |
|---|---|
| Experiment | مقارنة مضبوطة بين تجارب مختلفة |
| A/B test | experiment تقارن control بواحد أو أكثر من variants |
| Hypothesis | prediction عن كيفية تغيير treatment للسلوك |
| Control | التجربة الأساسية baseline |
| Variant / treatment | التجربة المعدلة التي يتم اختبارها |
| Experimental unit | الكيان الذي يتم randomize له، مثل user أوaccount |
| Primary metric | outcome الرئيسية المستخدمة للحكم على hypothesis |
| Guardrail metric | metric تُستخدم لاكتشاف ضرر غير مقصود |
| Random assignment | توزيع variants بالصدفة بدلًا من خصائص المستخدم |
| Binary outcome | outcome لها حالتان مثل success/failure |
| Continuous outcome | outcome رقمية يمكن أن تأخذ قيمًا كثيرة |
| Contingency table | جدول counts عبر categorical outcomes وvariants |
| اختبار Chi-squared | statistical test للمقارنات categorical/binary-style |
| اختبار t لعينتين (Two-sample t-test) | statistical test تقارن means بين مجموعتين |
| Statistical significance | دليل على أن observed difference غير محتملة تحت null hypothesis محددة |
| Effect size | مقدار الفرق بين المجموعات |
| A/A test | اختبار للبنية التحتية لـ experiment تحصل فيه مجموعتان randomized على التجربة نفسها |
| Time boxing | تقييد outcome measurement إلى elapsed window نفسها بعد assignment |
| Novelty effect | تغير مؤقت في السلوك بسبب كون الشيء جديدًا |
| الارتداد نحو المتوسط (Regression to the mean) | ميل measurements المتطرفة بصورة غير معتادة إلى العودة نحو مستوى أكثر اعتيادية |
| Holdout | مجموعة لا تتعرض عمدًا لـ ongoing treatment |
| Quasi-experiment | design غير randomized تهدف إلى تقريب controlled comparison |
| تحليل قبل/بعد (Pre/post analysis) | مقارنة outcomes قبل change وبعدها |
| Natural experiment | observational setting تختلف فيه exposure بطريقة تشبه العشوائية |
| تصميم انقطاع الانحدار (Regression discontinuity design) | مقارنة units فوق treatment threshold وتحتها مباشرةً |
| Confounder | متغير مرتبط بكل من treatment/exposure وoutcome ويمكنه تشويه التفسير |

## المراجعة الذاتية (Self-Check)

قبل المتابعة، تأكد أنك تستطيع الإجابة عن الآتي:

1. لماذا لا يثبت correlation وجود causation؟
2. ما المكونات الثلاثة الأساسية المطلوبة لـ experiment؟
3. لماذا ينبغي اختيار primary metric قبل رؤية النتائج؟
4. ما guardrail metric؟
5. لماذا تحتاج binary-outcome query عادةً إلى `LEFT JOIN` من assignments إلى success events؟
6. لماذا ينبغي حساب continuous metrics أولًا على مستوى experimental unit؟
7. لماذا ينبغي أن يساهم nonpurchasers غالبًا بقيمة zero في spend-per-user؟
8. ما inputs المطلوبة لـ binary significance workflow في الفصل؟
9. ما inputs المطلوبة لـ continuous significance workflow؟
10. ماذا يمكن أن يكشف A/A test؟
11. لماذا تكون continuous outcomes حساسة للـ outliers؟
12. ما المشكلة التي يحلها time boxing؟
13. لماذا تكون repeated-exposure experiments عرضة لـ novelty effects؟
14. لماذا لا تعادل opt-out population randomized holdout؟
15. لماذا تكون pre/post analysis أضعف من A/B test في causal inference؟
16. ما الذي يجعل natural experiment comparison موثوقة؟
17. ما الفكرة الأساسية وراء regression discontinuity design؟
