## 1. لماذا يُعد تجهيز البيانات عملًا تحليليًا

يتوقع المبتدئ غالبًا أن يبدأ التحليل عندما تبدأ العملية الحسابية "الحقيقية". لكن في الواقع يحدث قدر كبير من العمل التحليلي قبل ذلك: فهم معنى Fields، والتحقق مما إذا كانت Data موثوقة، وتحديد Rows التي تنتمي إلى التحليل، وإصلاح القيم غير المنتظمة أوتوثيقها، وترتيب Data في شكل قابل للاستخدام.

يُسمى هذا العمل عادة **data preparation** أو**data wrangling** أو**data munging** أو**data prep**.

الفكرة المهمة أن Preparation ليست تنظيفًا آليًا بلا تفكير. كل قرار Preparation يتضمن افتراضات تحليلية.

على سبيل المثال، لنفترض أن Sales table تحتوي على:

```text
order_id | status     | amount — رؤوس الأعمدة
---------|------------|-------
101      | completed  | 120
102      | cancelled  | 95
103      | completed  | NULL
104      | test       | 500 — طلب تجريبي
```

قبل حساب "إجمالي المبيعات"، تحتاج بالفعل إلى الإجابة عن عدة أسئلة:

- هل ينبغي تضمين Cancelled orders؟
- هل ينبغي تضمين Test transactions؟
- لماذا Amount مفقودة للطلب `103`؟
- هل تعني `NULL` صفرًا أم Unknown أم Data-quality failure؟
- هل تمثل كل Row دائمًا Order حقيقيًا واحدًا؟

إذا أُجيب عن هذه الأسئلة بصورة خاطئة، فقد تنتج `SUM()` صحيحة نحويًا إجابة مضللة.

حلقة Preparation مفيدة هي:

```text
افهم -> نفّذ Profiling -> اسأل -> نظّف -> شكّل -> تحقّق -> حلّل
                               ^                         |
                               |_________________________|
```

الحلقة مهمة لأن الخطوات اللاحقة تكشف غالبًا مشكلات تجبرك على العودة إلى خطوات سابقة.

[[IMAGE_NEEDED: IMG-M01-L02-01 / Instructor Figure — Data preparation as an iterative analysis loop | Show Understand -> Profile -> Question -> Clean -> Shape -> Check -> Analyze in a loop, with arrows returning from Check and Analyze to Profile/Clean | Learner should notice that data preparation is iterative and analytical rather than a one-time preprocessing stage]]

### استخدم Data dictionary عندما تكون موجودة

توثّق **data dictionary** الـ Fields ومعانيها والقيم الممكنة وقواعد Collection وعلاقاتها ببيانات أخرى. ويمكنها توفير ساعات من إعادة الاكتشاف.

يظل Analyst الجيد ينفذ Profiling للبيانات الفعلية حتى عند وجود Documentation، لأن Documentation قد تكون ناقصة أوقديمة. ينبغي أن يدعم Profiling وDocumentation كل منهما الآخر:

- تخبرك Data dictionary بما ينبغي أن يكون موجودًا؛
- يخبرك Profiling بما هو موجود فعلًا؛
- وتخبرك الاختلافات بما يجب التحقيق فيه.

عندما لا توجد Dictionary مفيدة، يكون توثيق ما تتعلمه أثناء Profiling عملًا ذا قيمة لفريقك ولنفسك مستقبلًا.

## 2. أنواع بيانات Database: ما الذي تعتقد SQL أن القيمة تمثله

لكل Field في Database **data type**. يحدد Type القيم التي يمكن للـ Field تخزينها والعمليات التي يكون تنفيذها عليها منطقيًا.

أهم العائلات في التحليل هي Strings وNumerics وBooleans وDate/time types.

| العائلة | الأنواع الشائعة | قيم نموذجية | الاستخدام التحليلي المهم |
|---|---|---|---|
| نصوص (String) | `CHAR`, `VARCHAR`, `TEXT` | أسماء، Codes، Free text | Grouping وParsing وMatching |
| أرقام (Numeric) | `INT`, `BIGINT`, `FLOAT`, `DOUBLE`, `DECIMAL` | Counts، Prices، Scores | Arithmetic وAggregation |
| منطقي (Logical) | `BOOLEAN` | `TRUE`, `FALSE` | Flags وConditions |
| تاريخ/وقت (Date/time) | `DATE`, `TIMESTAMP`, `TIME` | Dates وEvent times | Time-series وCohort analysis |

تدعم بعض Databases أيضًا Types مثل JSON والقيم Geographic.

[[IMAGE_NEEDED: IMG-M01-L02-02 / Instructor Figure — Database data type map | Four main branches from a field: String, Numeric, Boolean, Date/Time, each with representative SQL types and one example value; show JSON/geographic as optional extended types | Learner should notice that a value's database type controls which operations and functions are valid]]

### النصوص (Strings)

يمكن أن تحتوي Strings على Letters وDigits وSymbols وWhitespace ومحارف أخرى. قد يناسب `CHAR` ثابت الطول Code بطول ثابت، بينما يسمح `VARCHAR` بطول متغير. وقد يُخزّن Text طويل جدًا داخل Types مثل `TEXT` أو`CLOB` أو`BLOB` حسب Database.

القيمة التي تبدو Numeric ليست بالضرورة Numeric. على سبيل المثال:

```text
'$19.99'
```

هي String إذا كان Dollar sign مخزنًا داخل Field. لا يمكن الوثوق بـ Mathematical aggregation حتى يتم تنظيف Text وتحويله.

### القيم الرقمية

تخزن Integers أعدادًا صحيحة. أما Types التي تدعم Decimals فتخزن قيمًا مثل Prices وRatios وMeasurements.

انتبه إلى سلوك Arithmetic. تتعامل بعض Database systems مع Integer division بطريقة تختلف عن Decimal division. إذا كان Inputان كلاهما Integer، فقد تختصر نتيجة توقعت أن تكون `2.5` إلى Integer ما لم تنفذ Cast لأحد Inputs.

### Booleans وFlags

يخزن `BOOLEAN` القيمة `TRUE` أو`FALSE`. وهو مفيد لخصائص مثل:

```text
has_opened_email
is_active
is_test_account
```

كما تستخدم Analytical data sets بصورة شائعة `1` و`0` كـ Flags عندما تستفيد Aggregation أوModeling workflows من قيم Numeric.

### Dates وTimestamps

ينبغي تخزين Dates وTimestamps باستخدام Date/time types في Database متى أمكن. يسمح ذلك لـ SQL باستخدام Date-aware functions بدل إجبارك على Parsing للـ Strings يدويًا.

Dates أساسية في التحليلات اللاحقة لأن أسئلة Business كثيرة تعتمد على:

- متى وقع Event؛
- كم استغرق شيء ما؛
- ما إذا كان Activity قد تغير عبر الزمن؛
- إلى أي Cohort ينتمي Entity.

## 3. كيف يصنف Analysts البيانات بعيدًا عن Database types

تصف Database types طريقة التخزين. كما يصنف Analysts البيانات مفاهيميًا لأن Source وStructure يؤثران في كيفية تفسير Data.

### Structured وSemistructured وUnstructured

تتبع **Structured data** نموذجًا محددًا مسبقًا. ويُعد Relational table أوضح مثال: تمثل كل Row كيانًا أوحدثًا، ولكل Column معنى وType محددان.

لا تتلاءم **Unstructured data** طبيعيًا مع نموذج Rows وColumns ثابت. وتشمل الأمثلة Documents وImages وAudio وVideo.

تقع **Semistructured data** بين النوعين. فالـ Email مثلًا يحتوي Structured metadata مثل Sender وRecipient وSubject وTimestamp، لكنه يحتوي أيضًا Free-form body text.

[[IMAGE_NEEDED: IMG-M01-L02-03 / Instructor Figure — Structured to unstructured spectrum | Three panels: structured relational table, semistructured email/JSON-like record with metadata plus free text, and unstructured image/audio/document; include an arrow from easiest to hardest for direct relational SQL querying | Learner should notice that 'unstructured' data may still contain structured metadata that SQL can use]]

### Quantitative وQualitative

تمثل **Quantitative data** كميات قابلة للقياس. وتشمل الأمثلة Revenue وQuantity وDuration وWeight وScore وCounts.

تلتقط **Qualitative data** أوصافًا أوآراء أوCategories ليست Numeric بطبيعتها. ومن أمثلتها Survey comments وSupport messages وSocial posts.

تحوّل Analytical workflows المعلومات Qualitative غالبًا إلى Summaries رقمية. على سبيل المثال، قد يصنف Analyst التعليقات إلى Categories ثم يحسب مدى تكرار كل Category.

### First-party وSecond-party وThird-party data

يؤثر Source الخاص بالبيانات في مقدار التحكم الذي تملكه في توليدها وجودتها.

| الفئة | المصدر | تحكم Analyst المعتاد |
|---|---|---|
| بيانات الطرف الأول (First-party) | تجمعها مؤسستك | الأعلى |
| بيانات الطرف الثاني (Second-party) | يولدها Vendor يخدم مؤسستك | متوسط إلى منخفض |
| بيانات الطرف الثالث (Third-party) | تُشترى أوتُحصل من Source خارجي | منخفض عادة |

قرار مفيد بشأن Vendor data هو ما إذا كان دمجها مع بيانات المؤسسة الأخرى ينشئ قيمة تحليلية كافية لتبرير Import لها وصيانتها.

### البيانات المتناثرة (Sparse data)

تحتوي **Sparse data** قدرًا قليلًا نسبيًا من المعلومات داخل مساحة ممكنة أكبر بكثير. فقد يحتوي Column على Nulls في معظمه، أوقد يحدث Event بصورة نادرة جدًا.

تتطلب Sparse data حذرًا لأن Patterns الظاهرة قد تكون غير مستقرة عندما تكون Observations نادرة. تشمل الاستجابات الممكنة:

- دمج Categories قليلة التكرار؛
- استبعاد Period شديدة الندرة بالنسبة للسؤال؛
- عرض Descriptive statistics مع تحذير واضح؛
- انتظار مزيد من Observations.

تعتمد الاستجابة الصحيحة على سبب Sparsity.

## 8. جودة البيانات واكتشاف Duplicates

لا تستطيع SQL الجيدة إنقاذ افتراض خاطئ عن Data.

يقارن Quality check قوي Data بـ **ground truth** عندما تكون Ground truth موجودة.

أمثلة:

- Production row counts المتوقعة؛
- Monthly sales totals معروفة؛
- Operational report موثوق؛
- Source system معروف باحتوائه القيمة Authoritative.

## 13. تشكيل البيانات: اختر Grain قبل اختيار Columns

يعني **Shaping data** تغيير كيفية تمثيل المعلومات داخل Rows وColumns.

المفهوم المركزي هو **granularity** أوGrain:

> ماذا تمثل Row واحدة؟

تشمل Grains الممكنة:

```text
Row واحدة لكل Country
Row واحدة لكل Customer
Row واحدة لكل Order
Row واحدة لكل Order item
Row واحدة لكل Customer في كل Month
```

يغير تغيير Grain معنى كل Metric.

### التسطيح (Flattening)

يقلل Flattening عدد Rows متعددة أوTables متعددة إلى Analytical structure أكثر إحكامًا.

أمثلة:

- Join لـ Customer attributes إلى Transactions؛
- Aggregation لعدد كبير من Orders إلى Customer row واحدة؛
- Pivoting للـ Categories إلى Columns.

[[IMAGE_NEEDED: IMG-M01-L02-12 / Instructor Figure — Analytical grain and flattening | Show the same business data at four levels: order item -> order -> customer-month -> customer, with arrows labeled aggregation/flattening | Learner should notice that shaping is fundamentally a choice about what one output row should represent]]

### شكّل Data بما يناسب Destination

لا يوجد شكل تحليلي واحد هو الأفضل دائمًا.

بالنسبة إلى **BI dashboards**، قد تدعم Data set مفصلة Interactive slicing، بينما قد تعمل Executive dashboard بصورة أفضل مع Table صغيرة Pre-aggregated.

بالنسبة إلى **Visualization**، تكون نتيجة مدمجة عند Plotting grain الدقيقة غالبًا أسهل في الاستخدام.

بالنسبة إلى **Statistics أوMachine learning**، حدد Modeled entity والـ Features المطلوبة. قد يحتاج Model إلى:

- Row واحدة لكل Customer؛
- Row واحدة لكل Transaction؛
- Row واحدة لكل Customer-month.

نموذج ذهني مفيد لـ Tidy data هو:

```text
كل Variable -> Column واحدة
كل Observation -> Row واحدة
كل Value -> Cell واحدة
```

يتبع الشكل الصحيح السؤال التحليلي وDownstream tool.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> تنظيف البيانات يعني استبدال كل `NULL` بصفر.

### لماذا هذا خطأ

يمكن أن تعني `NULL` Unknown أوMissing أوNot applicable أوNot yet loaded أوNot collected. أما Zero فهي Numeric value معروفة. استبدال إحداهما بالأخرى يغير معنى Data وقد يغير Counts وAverages والاستنتاجات.

### المفهوم الخاطئ 2

> `DISTINCT` هي الحل الطبيعي كلما أنشأت Join عددًا أكبر من Rows.

### لماذا هذا خطأ

قد تكون Rows الإضافية دليلًا على One-to-many أوMany-to-many relationship. ويمكن لـ `DISTINCT` إخفاء العرض دون تصحيح Analytical grain أوJoin logic.

### المفهوم الخاطئ 3

> Sample التي تجعل Query تعمل تكفي للإجابة النهائية.

### لماذا هذا خطأ

يمكن لـ Samples حذف Rare values وEdge cases. استخدمها لتطوير Logic، ثم شغّل Query التي تم التحقق منها على Population المطلوبة.

### المفهوم الخاطئ 4

> Pivoting يغير Data نفسها.

### لماذا هذا خطأ

يغير Pivoting تمثيل Data. وتظل Facts نفسها مرتبة بصورة مختلفة عبر Rows وColumns.
