## 1. لماذا تهم هندسة البيانات لـ ML

لا تبدأ أنظمة Machine Learning بـ Model. بل تبدأ ببيانات يجب جمعها والتحقق منها وتخزينها ونقلها وتحويلها واسترجاعها ومعالجتها قبل أن تتمكن Model من استخدامها.

في Production، تمتد هذه العمليات غالبًا عبر أنظمة وخدمات متعددة. قد تحوّل Feature engineering service الأحداث الخام إلى Features، بينما تستهلك Prediction service هذه Features لإنتاج Predictions. ويجب أن تنتقل البيانات بينهما بصورة موثوقة.

وهذا يعني أن Data engineering تجيب عن أسئلة عملية مثل:

- من أين تأتي البيانات؟
- بأي Format ينبغي تخزينها؟
- كيف ينبغي تمثيل بنيتها؟
- أي Storage engine ينبغي استخدامه؟
- كيف تمرر Service البيانات إلى Service أخرى؟
- هل ينبغي معالجة البيانات دوريًا أم بصورة مستمرة؟

نموذج ذهني مفيد لهذا الفصل هو:

```text
المصادر (Sources) → الصيغ (Formats) → النماذج (Models) → التخزين/المعالجة → تدفق البيانات (Dataflow) → ميزات ML
```

## 2. مصادر البيانات في أنظمة ML داخل Production

تختلف مصادر البيانات في الجودة وLatency والخصوصية وخصائص المعالجة. يساعدك فهم المصدر على تحديد كيفية التحقق من البيانات ومعالجتها.

### بيانات إدخال المستخدم (User input data)

قد يقدّم المستخدمون نصًا أو صورًا أو فيديو أو ملفات أو حقولًا رقمية أو أنواعًا أخرى من المدخلات.

ينبغي التعامل مع User input باعتبارها قد تكون غير صالحة. فقد يقوم المستخدم بـ:

- إدخال نص حيث يُتوقع رقم،
- رفع ملف بصيغة خاطئة،
- تقديم نص قصير جدًا أو طويل جدًا،
- إرسال قيم غير متوقعة.

ولأن المستخدمين يتوقعون عادة Feedback فورية، فإن User input تحتاج غالبًا إلى **Validation قوية** و**معالجة منخفضة Latency**.

### البيانات الناتجة عن النظام (System-generated data)

تولّد الأنظمة Logs وModel predictions وJob results وMetrics وEvents تصف سلوك المستخدم.

يمكن أن تسجل Logs معلومات مثل:

- Memory usage،
- Service calls،
- إصدارات Packages أوDependencies،
- نتائج Training jobs،
- نتائج Batch processing،
- أخطاء Application.

تكون Logs عادة أكثر انتظامًا من User input لأن Software هو الذي ينشئها. لكن حجمها قد يصبح هائلًا. وقد يجعل تسجيل كل شيء Debugging أصعب لأن الإشارات المفيدة تختفي وسط الضوضاء.

ويهم أيضًا Log retention. فالـ Logs القديمة التي نادرًا ما يتم الوصول إليها يمكن غالبًا نقلها إلى Storage أرخص أو حذفها عندما لا تعود مفيدة.

### Behavioral data تظل بيانات مستخدم

قد يتم إنشاء Clicks وScrolling والوقت المستغرق على الصفحات وPopups التي تم تجاهلها وسجل الشراء تلقائيًا بواسطة النظام، لكنها ما تزال تصف سلوك المستخدم. ويؤكد الفصل أن مثل هذه البيانات قد تخضع لمتطلبات الخصوصية.

### Databases الداخلية

تحتفظ المؤسسات بـ Databases داخلية للمخزون والمستخدمين وعلاقات العملاء والأصول والمعاملات وغيرها من بيانات الأعمال.

قد تعتمد ML Model مباشرة على هذه Databases. فعلى سبيل المثال، يمكن لنظام Search فهم Query لكنه يظل بحاجة إلى بيانات المخزون قبل ترتيب المنتجات المتاحة فعليًا.

### بيانات First-party وSecond-party وThird-party

- **بيانات First-party:** تجمعها مؤسستك مباشرة من مستخدميك أو عملائك.
- **بيانات Second-party:** تجمعها مؤسسة أخرى من عملائها وتتيحها لك.
- **بيانات Third-party:** تجمعها مؤسسات عن أشخاص ليسوا بالضرورة عملاء مباشرين لها.

يشير الفصل إلى أن تغييرات الخصوصية قللت بعض أشكال Third-party tracking وزادت أهمية First-party data.

## 3. تسلسل البيانات والصيغ الشائعة (Data serialization and common formats)

بمجرد وجود البيانات، تحتاج غالبًا إلى حفظها أو نقلها.

**Data serialization** هي عملية تحويل بنية بيانات أو حالة Object إلى Format يمكن تخزينها أو نقلها ثم إعادة بنائها لاحقًا.

عند اختيار Format، اسأل:

- هل هي Human-readable؟
- هل هي Text أم Binary؟
- ما حجم البيانات بعد التخزين؟
- كيف سيتم الوصول إلى البيانات عادة؟
- هل يجب أن تدعم Format كائنات معقدة أو Nested objects؟

يقدم الفصل عدة Formats شائعة:

| الصيغة | Text/Binary | قابلة للقراءة البشرية | الاستخدام المعتاد |
|---|---|---|---|
| صيغة JSON | Text | نعم | APIs وتبادل البيانات العام |
| صيغة CSV | Text | نعم | البيانات الجدولية |
| صيغة Parquet | Binary | لا | البيانات التحليلية ذات Column-oriented storage |
| صيغة Avro | Binary في الأساس | لا | أنظمة البيانات مثل Hadoop |
| صيغة Protobuf | Binary في الأساس | لا | Serialization مضغوطة تعتمد على Schema |
| صيغة Pickle | Binary | لا | Serialization لكائنات Python |

### صيغة JSON

تشتهر JSON لأنها بسيطة وHuman-readable ومستقلة عمليًا عن لغة البرمجة، كما يمكنها تمثيل Nested structures.

مثال:

⟦CODE_0⟧

لكن JSON تعتمد على Text، لذلك قد تستهلك مساحة أكبر من Binary formats. كما يمكن أن تصبح تغييرات Schema مؤلمة عندما تعتمد Applications كثيرة على بنية JSON مستقرة.

## 4. تخزين Row-major مقابل Column-major

توضح CSV وParquet فكرتين مختلفتين في Storage.

### تخزين Row-major

في Row-major storage، تُخزن القيم التي تنتمي إلى Row نفسها بالقرب من بعضها.

مفاهيميًا:

```text
الصف 1 (Row 1): id, time, location, distance, price
الصف 2 (Row 2): id, time, location, distance, price
الصف 3 (Row 3): id, time, location, distance, price
```

هذا مفيد عندما تقرأ أو تكتب Records كاملة كثيرًا.

### تخزين Column-major

في Column-major storage، تُخزن القيم من Column نفسها بالقرب من بعضها.

مفاهيميًا:

```text
المعرف (id):       1, 2, 3, ...
الوقت (time):     t1, t2, t3, ...
الموقع (location): A, B, C, ...
السعر (price):    20, 25, 18, ...
```

هذا مفيد عندما تقرأ Analytical workloads مجموعة فرعية فقط من Columns.

### مثال

لنفترض أن جدول Ride-sharing يحتوي على 1,000 Feature، لكن Analysis تحتاج أربعًا فقط: time وlocation وdistance وprice.

يمكن لـ Column-oriented format قراءة هذه Columns فقط. أما Row-oriented format فقد تحتاج إلى قراءة جزء أكبر بكثير من كل Row قبل Filter إلى القيم المطلوبة.

### القاعدة العامة من الفصل

- تميل Row-major formats إلى أن تكون جذابة عند الكتابة المتكررة لـ Records كاملة.
- تميل Column-major formats إلى أن تكون جذابة عند القراءة المعتمدة على Columns وفي Analytical workloads.

[[IMAGE_NEEDED: Row-major versus column-major memory layout | A small table shown beside two storage layouts: one grouped by rows and one grouped by columns | Learner should notice why selecting a few columns is efficient in column-major storage while writing full rows fits naturally with row-major storage]]

### الحدس العملي في NumPy مقابل pandas

يشير الفصل إلى أن pandas منظمة حول DataFrame وعمليات تعتمد على Columns. أما NumPy arrays فهي Row-major افتراضيًا ما لم يتم تحديد ترتيب آخر.

ويساعد ذلك في تفسير لماذا قد يكون التكرار المستمر عبر Rows في pandas أبطأ من العمليات Vectorized أو Column-oriented.

## 5. صيغ Text مقابل Binary

يمكن للبشر فتح وقراءة Text formats مثل JSON وCSV مباشرة. أما Binary formats مثل Parquet فهي مصممة لتفسيرها بواسطة Software يفهم Byte layout الخاص بها.

تكون Binary formats غالبًا أكثر ضغطًا.

على سبيل المثال، يتطلب تخزين الرقم `1000000` كنص سبعة Characters. وإذا كان Character الواحد يستهلك Byte واحدًا، فهذا يعني سبعة Bytes. أما كعدد صحيح 32-bit فيمكن للقيمة نفسها أن تشغل أربعة Bytes.

يعطي الفصل مثالًا تحولت فيه نسخة CSV بحجم 14 MB من Dataset إلى 6 MB عند تخزينها بصيغة Parquet.

المفاضلة المهمة ليست ببساطة أن "Binary أفضل". فالاختيار يعتمد على Readability وInteroperability وتكلفة Storage وAccess patterns.

## 6. نماذج البيانات: Relational وDocument وGraph

يصف **Data model** كيف يتم تمثيل معلومات العالم الحقيقي.

يمكن تمثيل الكائن الحقيقي نفسه بطرق مختلفة حسب الأسئلة التي يحتاج Application إلى الإجابة عنها.

على سبيل المثال، يمكن تمثيل سيارة باستخدام:

- Make وModel وYear وColor وPrice، أو
- Owner وLicense plate وRegistered addresses.

قد يساعد التمثيل الأول المشترين على البحث عن السيارات. وقد يساعد الثاني على تتبع سجل الملكية.

### النموذج العلائقي (Relational model)

ينظم Relational model البيانات في Relations. وتعد Tables التمثيل المرئي الشائع، ويقابل كل Row قيمة Tuple.

إحدى الأفكار الأساسية هي **Normalization**: تقسيم المعلومات المتكررة إلى Relations منفصلة لتقليل التكرار وتحسين الاتساق.

لنفترض أن جدول Books يكرر اسم Publisher وCountry في كل Book row. إذا غير Publisher اسمه، فيجب تحديث Rows كثيرة.

يمكن لـ Normalization فصل معلومات Publisher:

```text
الكتب (BOOK)
title | author | format | publisher_id | price

الناشرون (PUBLISHER)
publisher_id | publisher_name | country
```

يمكن الآن تحديث معلومات Publisher في مكان واحد.

لكن التكلفة هي أن البيانات قد تحتاج إلى Join عبر Tables متعددة، وقد تكون Joins مكلفة في Datasets الكبيرة.

### لغة SQL وصفية (Declarative)

لغة SQL **Declarative** في الأساس: تصف النتيجة التي تريدها، بينما تقرر Database كيفية تنفيذ Query.

في المقابل، يصف Imperative program عادة تسلسل الخطوات التي يجب اتباعها.

يفحص Query optimizer في Database استراتيجيات تنفيذ محتملة ويحاول اختيار استراتيجية فعالة.

### Declarative ML

يرسم الفصل تشبيهًا مع أنظمة Declarative ML. فبدل بناء كل Model وضبطها يدويًا، يمكن للمستخدمين تحديد Features وTask بينما يستكشف النظام Model choices.

لكن هذا **لا** يزيل أصعب تحديات Production: ما تزال Feature engineering وData processing وEvaluation وDistribution shift وContinual learning موجودة.

### نموذج المستندات (Document model)

تخزن Document database مستندات مستقلة، وغالبًا ما تكون مشفرة بصيغة JSON أوXML أوBSON أوFormat أخرى. ولكل Document مفتاح.

بعكس Relational table، يمكن أن تكون Documents داخل Collection واحدة ذات بنى مختلفة.

وصف ذلك بأنه "Schemaless" بالكامل مضلل. فما يزال Application الذي يقرأ Documents يتوقع بنية معينة. الذي يتغير فقط هو الجهة المسؤولة عن فرض هذه البنية.

يوفر Document storage **Locality** قوية عندما يمكن أن تعيش المعلومات التي تنتمي معًا داخل Document واحدة.

أما العيب فهو أن العلاقات عبر Documents وعمليات Join قد تكون أصعب أو أقل كفاءة مقارنة بالأنظمة Relational.

### نموذج الرسوم البيانية (Graph model)

يتكون Graph من **Nodes** و**Edges**. وتمثل Edges العلاقات بين Nodes بصورة صريحة.

تكون Graph databases ذات قيمة عندما تكون العلاقات نفسها محور Query.

تشمل الأمثلة:

- Social networks،
- علاقات Recommendation،
- شبكات المؤسسات،
- كيانات مترابطة عبر Hops متعددة.

يناسب Query مثل "اعثر على كل الأشخاص المرتبطين بهذه الدولة عبر عدد غير معروف من Relationship hops" نموذج Graph بصورة طبيعية أكثر من بنية Relational joins ثابتة.

## 7. Structured data وUnstructured data

**Structured data** تتبع Schema معرفة مسبقًا.

مثال:

```text
الاسم (name): string up to 50 characters
العمر (age): integer between 0 and 200
```

تجعل البنية المعرفة مسبقًا Querying وAnalysis أسهل. فعلى سبيل المثال، يكون حساب متوسط العمر مباشرًا عندما يحتوي كل Record على Age field معرفة.

أما الجانب السلبي فهو Schema evolution. فإذا أضفت Field جديدة أو غيرت Field قديمة، فقد تتطلب Historical records عملية Migration. ويمكن لاختيارات Migration السيئة أن تنشئ ML bugs دقيقة — مثل استبدال Age غير المعروفة بالقيمة `0`، مما قد يجعل Model تتعامل مع Missing values كما لو كانت لمواليد جدد.

**Unstructured data** لا يلزمها الالتزام بـ Schema واحدة معرفة مسبقًا. ويمكن أن تشمل Text أوLogs أوImages أوAudio أوDates أوMixed content.

ولا تعني Unstructured أنها بلا Pattern. فقد يحتوي Log file على بنية متكررة، لكن Storage system لا يضمن أن كل Item تتبع Schema نفسها.

### Data warehouse مقابل Data lake

يستخدم الفصل التمييز العام التالي:

| مستودع البيانات | الدور المعتاد |
|---|---|
| Data warehouse | تخزن Structured data معالجة وجاهزة للتحليل |
| Data lake | تخزن Raw data أوبيانات أقل تنظيمًا قبل المعالجة لاحقًا |

غالبًا ما يكون سؤال التصميم الأساسي هو: **من يتحمل عبء Structure — الكاتب أم القارئ؟**

## 8. محركات التخزين: Transactional وAnalytical workloads

تحدد Data format كيف تُشفَّر المعلومات. ويحدد Data model كيف تُنمذج المعلومات. أما **Storage engine** أوDatabase فتحدد كيف يتم تخزين تلك المعلومات واسترجاعها على Machines.

فئتان تاريخيتان مهمتان من Workloads هما Transactional processing وAnalytical processing.

### معالجة المعاملات (OLTP)

تشمل Transactions إجراءات مثل:

- طلب Ride،
- رفع Model،
- نشر Content،
- شراء Item.

تحتاج هذه العمليات عادة Latency منخفضة وHigh availability لأن المستخدمين ينتظرونها.

ترتبط Transactional systems غالبًا بـ **ACID**:

| الخاصية | المعنى |
|---|---|
| Atomicity | تنجح جميع خطوات Transaction معًا أوتفشل معًا. |
| Consistency | تلتزم Transactions بقواعد معرفة مسبقًا وتحافظ على State صالحة. |
| Isolation | تتصرف Transactions المتزامنة كما لو كانت معزولة بصورة مناسبة عن بعضها. |
| Durability | بمجرد Commit لـ Transaction تظل محفوظة رغم الأعطال. |

مثال: إذا فشل Payment الخاص بالمستخدم، فلا ينبغي أن يخصص النظام Driver رغم ذلك. وهذا يوضح Atomicity.

### المعالجة التحليلية (OLAP)

تطرح Analytical workloads أسئلة Aggregate عبر كميات كبيرة من البيانات، مثل:

> ما متوسط سعر Ride في مدينة خلال September؟

تستفيد هذه Workloads غالبًا من Column-oriented access لأنها تجمع Fields مختارة عبر Records كثيرة.

### الحدود أصبحت أقل صرامة

يؤكد الفصل أن OLTP وOLAP مفهومان تاريخيان مفيدان، لكن الأنظمة الحديثة تمزج الحدود بينهما بصورة متزايدة.

هناك اتجاه رئيسي آخر هو **فصل Storage عن Compute**. فبدل الحاجة إلى Engine واحدة مترابطة بإحكام لكليهما، يمكن للمؤسسات إبقاء البيانات في Shared storage مع استخدام Processing layers مختلفة لـ Workloads مختلفة.

## 9. ETL وELT وفكرة Lakehouse

### ETL

تعني **ETL**:

```text
الاستخراج (Extract) → التحويل (Transform) → التحميل (Load)
```

#### الاستخراج (Extract)

اجمع البيانات المطلوبة من Source systems. وينبغي لهذه المرحلة أيضًا Validation للبيانات الواردة ورفض Records غير الصالحة أوغير المقبولة قبل أن تنشئ مشكلات Downstream.

#### التحويل (Transform)

هنا تحدث معظم عمليات Data processing. وقد تشمل Transformations:

- Join لمصادر متعددة،
- تنظيف القيم،
- توحيد Representations،
- Deduplication،
- Sorting،
- Aggregation،
- اشتقاق Features،
- تنفيذ Validation إضافية.

#### التحميل (Load)

اكتب النتيجة المحولة إلى Destination مثل File أوDatabase أوWarehouse بالتكرار المطلوب.

[[IMAGE_NEEDED: ETL pipeline | A simple three-stage pipeline showing raw sources entering Extract, then Transform with cleaning/joining/validation, then Load into a warehouse or database | Learner should notice that transformation happens before data reaches the target store]]

### ELT

مع زيادة حجم البيانات وتنوعها، تبنت بعض المؤسسات:

```text
الاستخراج (Extract) → التحميل (Load) → التحويل (Transform)
```

يتم تحميل Raw data إلى Storage أولًا ثم تحويلها لاحقًا عندما يحتاج Application إليها. وهذا يتيح Ingestion سريعًا ويقلل الحاجة إلى تعريف كل Structure مسبقًا.

لكن Data lake خام وضخم قد يصبح صعب البحث والإدارة بكفاءة.

### Lakehouse

تحاول التصاميم الهجينة المسماة **Data lakehouses** الجمع بين مرونة Data lakes وإدارة وبنية Data warehouses.

## 10. كيف تنتقل البيانات بين Processes

تحتوي أنظمة Production على Processes كثيرة لا تشترك في Memory. لذلك يجب أن تتدفق البيانات من Process أوService إلى أخرى.

يصف الفصل ثلاثة Modes رئيسية:

1. تمرير البيانات عبر Database،
2. تمرير البيانات عبر Services باستخدام Requests،
3. تمرير البيانات عبر Real-time transport.

### تمرير البيانات عبر Database

تكتب Process A البيانات إلى Database. ثم تقرؤها Process B.

هذا النهج بسيط، لكنه يتطلب وصول كلتا العمليتين إلى Database نفسها، وقد تكون Reads/Writes في Database بطيئة جدًا بالنسبة لمتطلبات Latency الصارمة.

### تمرير البيانات عبر Services

ترسل Service طلبًا إلى Service أخرى وتنتظر Response.

هذا نمط **Request-driven**.

REST وRPC أسلوبان شائعان. ويشير الفصل إلى أن REST شائعة في Public APIs، بينما تُستخدم RPC كثيرًا للتواصل بين Services المملوكة للمؤسسة نفسها.

يسمح Service-oriented design بتطوير Components مختلفة وصيانتها بصورة مستقلة، مما يؤدي إلى Microservice architectures.

### مثال Ride-sharing

تخيل ثلاث Services:

- **Driver management:** تتنبأ بـ Drivers المتاحين.
- **Ride management:** تتنبأ بطلب Rides.
- **Price optimization:** تتنبأ بسعر Ride مناسب.

تحتاج Price optimization service إلى Predictions من كل من Supply وDemand services.

مع وجود Services قليلة، تكون Direct requests قابلة للإدارة. أما مع مئات Services المترابطة، تصبح Communication graph معقدة.

## 11. Real-time transports والأنظمة Event-driven

الاتصال المباشر Service-to-service متزامن: يجب أن تكون Target service متاحة لكي ينجح Request. وإذا توقفت Dependent service، فقد تنتشر الإخفاقات.

يقدم نهج مختلف **Broker** أوReal-time transport.

بدل أن تتحدث كل Service مباشرة إلى كل Service أخرى:

```text
الخدمة A (Service A) ─┐
الخدمة B (Service B) ─┼──> الوسيط / ناقل الأحداث ───> المستهلكون (Consumers)
الخدمة C (Service C) ─┘
```

ينشر Producer البيانات إلى Transport. وتستهلك Services الأخرى هذه البيانات عند الحاجة.

تسمى قطعة البيانات المنشورة إلى Transport من هذا النوع **Event**. ولهذا تسمى Architecture **Event-driven**.

يقارن الفصل بين الأسلوبين بصورة عامة:

- تناسب Request-driven systems الأنظمة التي يهيمن عليها Direct logic وتفاعلات Request/Response الفورية.
- تكون Event-driven systems مفيدة خصوصًا في الأنظمة كثيفة البيانات ذات Producers وConsumers الكثيرين.

### النشر والاشتراك (Publish-subscribe)

في Pubsub، تنشر Services أحداثًا إلى Topics. ويمكن لأي Service مشتركة في Topic استهلاك Events من ذلك Topic.

ولا يحتاج Producer إلى معرفة أي Consumers ستستخدم البيانات.

تتضمن أمثلة الفصل Apache Kafka وAmazon Kinesis.

### Message queue

في Message queue، تكون Message غالبًا موجهة إلى Consumer أوSet من Consumers، وتكون Queue مسؤولة عن توصيلها بصورة مناسبة.

تتضمن الأمثلة Apache RocketMQ وRabbitMQ.

## 12. Batch processing مقابل Stream processing

بمجرد تخزين البيانات في Databases أوLakes أوWarehouses، تصبح Historical data. وتتم معالجة Historical data عادة في Scheduled batch jobs.

### Batch processing

تعالج Batch job مجموعة من البيانات دوريًا.

أمثلة:

- حساب متوسط Surge price لليوم السابق مرة يوميًا،
- إعادة بناء Reporting table كل ليلة،
- حساب Features تتغير ببطء.

تم تطوير أنظمة موزعة مثل MapReduce وSpark لمعالجة Batches كبيرة بكفاءة.

### Stream processing

Streaming data ما تزال تصل عبر Real-time transports مثل Kafka أوKinesis. وتنفذ Stream processing العمليات على هذه البيانات بصورة مستمرة أوعلى فترات قصيرة.

أمثلة:

- عدد Drivers المتاحين الآن،
- عدد Rides المطلوبة في الدقيقة الأخيرة،
- Median price لأحدث Rides،
- Recent activity المستخدمة في Fraud detection.

يمكن لـ Stream processing تقليل Latency لأن البيانات يمكن معالجتها أثناء وصولها بدل انتظار Long-term storage ثم Batch job لاحقة.

### Stateful streaming

يمكن لـ Stream processing الاحتفاظ بـ Intermediate state. افترض أنك تحتاج Engagement statistic لمدة 30 يومًا.

قد تعيد Batch job يومية ساذجة حساب جزء كبير من سجل 30 يومًا نفسه مرارًا. أما Stateful stream processor فيمكنها تحديث State الخاصة بالأمس باستخدام البيانات الجديدة الواصلة فقط.

### Static features مقابل Dynamic features

يربط الفصل Processing mode بسلوك Feature:

| نوع Feature | المصدر المعتاد | مثال |
|---|---|---|
| ميزة ثابتة / دفعية | Batch processing | التقييم طويل الأجل لـ Driver |
| ميزة ديناميكية / متدفقة | Stream processing | Drivers المتاحون الآن |

تحتاج أنظمة ML كثيرة في Production إلى النوعين من Features.

فعلى سبيل المثال، قد تجمع Price optimization model تقييم Driver الذي يتغير ببطء مع معلومات Supply وDemand سريعة التغير.

### Stream processing أصعب

تتعامل Streaming systems مع بيانات غير محدودة تصل بمعدلات متغيرة. وقد تتطلب تطبيقات ML المعقدة مئات أوآلاف Streaming features وJoins وAggregations وStateful computations.

يسمي الفصل تقنيات مثل Apache Flink وKSQL وSpark Streaming كأمثلة لأدوات Stream processing.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Data format وData model هما الشيء نفسه

هما مختلفان. تصف Format كيفية Encoding أوSerialization للبيانات، بينما يصف Model كيفية تنظيم المعلومات مفاهيميًا.

### المفهوم الخاطئ 2: Schemaless تعني عدم وجود Structure

قد لا تفرض Document databases Schema واحدة صارمة عند Write time، لكن Applications التي تقرأ Documents تظل تضع افتراضات عن Structure الخاصة بها. تنتقل المسؤولية بدلًا من أن تختفي.

### المفهوم الخاطئ 3: OLTP وOLAP تصفان عالمين حديثين منفصلين تمامًا

تظلان فئتين مفيدتين لـ Workloads، لكن الأنظمة الحديثة تدعم الأسلوبين بصورة متزايدة، أوتفصل Storage عن Compute حتى تعمل Engines متعددة على البيانات نفسها.

### المفهوم الخاطئ 4: Event-driven architecture تعني أن البيانات لا تحتاج Storage أبدًا

عادة تحتفظ Real-time transports بالأحداث لفترة، ويمكنها نقلها إلى Durable storage. فهي تكمل Databases ولا تجعل Persistent storage غير ضرورية.

### المفهوم الخاطئ 5: Streaming تستبدل Batch processing في كل حالة

تتغير Features كثيرة ببطء ويمكن حسابها بكفاءة في Batch. وغالبًا ما تجمع أنظمة Production بين Batch وStreaming pipelines.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مفهوم Data serialization | تحويل البيانات إلى شكل يمكن تخزينه أونقله ثم إعادة بنائه لاحقًا. |
| مفهوم Access pattern | الطريقة المعتادة التي يقرأ أويكتب بها النظام البيانات. |
| تخطيط Row-major | Storage layout يبقي قيم Row نفسها معًا. |
| تخطيط Column-major | Storage layout يبقي قيم Column نفسها معًا. |
| مفهوم Data model | تمثيل مفاهيمي لكيفية تنظيم البيانات والعلاقات. |
| نموذج Relational | Data model قائم على Relations، وتمثل عادة في شكل Tables. |
| مفهوم Normalization | تنظيم Relational data لتقليل التكرار وتحسين Integrity. |
| نموذج Document | Model قائم على مستندات مستقلة مثل JSON أوBSON documents. |
| نموذج Graph | Model قائم على Nodes وEdges تكون فيه العلاقات كائنات أساسية. |
| بيانات Structured | بيانات تلتزم بـ Schema معرفة مسبقًا. |
| بيانات Unstructured | بيانات لا يلزمها الالتزام بـ Schema واحدة معرفة مسبقًا. |
| مستودع Data warehouse | Repository تُستخدم عادة لبيانات Structured ومعالجة وجاهزة للتحليل. |
| مستودع Data lake | Repository تُستخدم عادة لـ Raw data أوبيانات أقل تنظيمًا. |
| معالجة OLTP | Processing محسنة للمعاملات المتكررة المواجهة للمستخدم. |
| معالجة OLAP | Processing محسنة لـ Analytical queries عبر كميات كبيرة من البيانات. |
| خصائص ACID | خصائص Atomicity وConsistency وIsolation وDurability المرتبطة بأنظمة Transactions. |
| عملية ETL | Extract ثم Transform ثم Load. |
| عملية ELT | Extract ثم Load ثم Transform. |
| بنية Lakehouse | نهج هجين يجمع أفكارًا من Data lakes وData warehouses. |
| نمط Request-driven | اتصال تطلب فيه Service البيانات مباشرة من Service أخرى. |
| نمط Event-driven | اتصال ينشر فيه Producers أحداثًا يمكن لـ Consumers معالجتها عبر Broker. |
| نمط Pubsub | نموذج Publish-subscribe يشترك فيه Consumers في Topics. |
| Message queue | Messaging model تُسلَّم فيه Messages إلى Consumers المقصودين. |
| معالجة Batch | معالجة دورية لمجموعات محدودة من Historical data. |
| معالجة Stream | معالجة البيانات أثناء وصولها باستمرار. |
| Static feature | Feature تتغير ببطء نسبيًا وعادة تُحسب في Batch. |
| Dynamic feature | Feature تمثل State سريعة التغير وعادة تُحسب من Streams. |

## التحقق الذاتي

قبل المتابعة، تأكد من أنك تستطيع الإجابة عن:

1. لماذا تتطلب User input عادة Validation أقوى من System-generated logs؟
2. ما Serialization؟
3. متى يكون Column-major storage أكثر جاذبية من Row-major storage؟
4. لماذا تكون Binary formats غالبًا أصغر من Text formats؟
5. ما المشكلة التي تحلها Normalization، وما التكلفة التي قد تقدمها؟
6. متى يكون Document model أكثر ملاءمة من Relational model؟
7. متى يكون Graph model مفيدًا بصورة خاصة؟
8. من يتحمل مسؤولية Structure في Structured storage مقابل Unstructured storage؟
9. ماذا تعني Atomicity وDurability؟
10. ما الفرق بين ETL وELT؟
11. لماذا قد يصبح Direct request-driven communication صعبًا مع مئات Services؟
12. كيف يقلل Broker من Coupling بين Services؟
13. ما الفرق العام بين Pubsub وMessage queue؟
14. لماذا قد تحتاج Model إلى كل من Static features وDynamic features؟
