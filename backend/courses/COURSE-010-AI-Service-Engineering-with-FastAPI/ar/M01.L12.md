## 1. يبدأ Deployment باختيار Hosting model المناسب

بمجرد أن تعمل خدمة GenAI محليًا، لا يزال المستخدمون غير قادرين على الوصول إليها حتى تتم استضافتها في مكان يمكن الوصول إليه.

يقدم الفصل أربع استراتيجيات Deployment شائعة:

1. Virtual machines،
2. Serverless functions،
3. Managed application platforms،
4. Containers.

هذه الخيارات ليست متعارضة.

قد يستخدم نظام واقعي:

```text
VM
  ↓
Docker runtime
  ↓
خدمة FastAPI داخل Container
```

أو:

```text
Managed platform
  ↓
نشر Container image
```

أو:

```text
دوال serverless
  ↓
أحمال API صغيرة مدفوعة بالأحداث
```

السؤال المهم ليس:

> ما Deployment technology الأكثر تقدمًا؟

بل:

> ما Deployment model الذي يطابق Resource needs و Scale و Operational budget و Isolation requirements و Model-hosting strategy لهذه الخدمة؟

### مقارنة سريعة (Quick comparison)

| الخيار | نقطة القوة الرئيسية | Trade-off الرئيسية |
|---|---|---|
| VM | تحكم في OS/Hardware/GPU | Maintenance أكبر |
| Serverless | Event-driven scaling و Pay-for-use | قيود Resources/Time |
| منصة تطبيقات مُدارة | Deployment و Operations سهلة | Abstraction/Cost أعلى |
| Containers | Portability و Repeatable environments | تحتاج معرفة بالـ Containers |

## 2. النشر على Virtual machines

الـ Virtual machine هي Computer يتم محاكاتها برمجيًا.

تحتوي على:

- Guest operating system،
- Virtual CPU،
- Virtual memory،
- Virtual storage،
- Applications تعمل بداخلها.

تسمى Physical machine الأساسية **Host**.

ويخصص **Hypervisor** موارد Host للـ VMs.

من الناحية المفاهيمية:

```text
الخادم المادي
    ↓
Hypervisor
    ├── VM A → OS ضيف → تطبيق
    ├── VM B → OS ضيف → تطبيق
    └── VM C → OS ضيف → تطبيق
```

### لماذا يمكن أن تكون VMs مفيدة لـ GenAI؟

يسلط الفصل الضوء على التحكم المباشر في:

- OS configuration،
- CPU/Memory/Disk،
- GPU drivers،
- Networking،
- Security environment.

يمكن أن يكون هذا مهمًا عند Self-hosting للـ Models أوعندما تكون Strong environment isolation مطلوبة.

### التكلفة التشغيلية (Operational cost)

مع التحكم تأتي المسؤولية.

قد تحتاج إلى إدارة:

- Security patches،
- OS upgrades،
- Packages،
- GPU drivers،
- Network configuration،
- Disk capacity،
- Monitoring،
- Uptime.

كما تبقى VMs عادةً قيد التشغيل باستمرار ما لم تتم أتمتة Startup/Shutdown.

### Deployment عملي على VM

نهج بسيط هو:

```text
أنشئ VM
→ Clone للـ Repository
→ ثبّت Dependencies
→ اضبط Environment
→ شغّل Application
```

يوصي الفصل باستخدام Containers فوق VM لجعل Deployment process أكثر Repeatability.

## 3. النشر باستخدام Serverless functions

تشغّل Serverless computing الـ Code استجابةً لـ Events.

أمثلة:

- HTTP request،
- Queue message،
- Storage/Blob event،
- Database event.

يوفر Developer الـ Code بينما يدير Cloud provider الـ Compute infrastructure.

### "Serverless" لا تزال تستخدم Servers

يعني المصطلح:

```text
أنت لا تدير Server مباشرةً
```

ولا يعني:

```text
لا توجد Server
```

### حالات مناسبة وفق الفصل

تكون Serverless functions مفيدة عندما:

- تكون Workloads Event-driven،
- تكون Functions قصيرة العمر،
- تريد Pay-for-use behavior،
- تحتاج Batch/Event automation،
- يمكن للـ Traffic أن يتوسع ديناميكيًا.

### القيود

يحذر المصدر من أن Functions تمتلك عادةً:

- Resources محدودة،
- Execution-time limits،
- Allocation/Startup latency،
- قيود وقت تشغيل خاصة بالمزوّد.

بالنسبة إلى Self-hosted model ثقيلة الموارد أوطويلة التشغيل، يوصي الفصل بالنظر في Deployment approach أخرى.

### نمط Model مدعومة عبر API

يمكن لخدمة FastAPI خفيفة الاستمرار في استدعاء External model provider:

```text
طلب HTTP
    ↓
FastAPI/دالة serverless
    ↓
API نموذج خارجي
    ↓
الاستجابة
```

يبقي هذا Heavy inference خارج Function runtime.

### قسّم حسب Endpoint عندما يكون ذلك مناسبًا

يشير المصدر إلى أنه يمكن أحيانًا نشر Endpoints منفصلة كـ Functions منفصلة.

وقد يقلل ذلك مقدار Application الذي يجب تشغيله داخل Continuously provisioned environment.

## 5. منصات التطبيقات المُدارة

تزيل Managed application platforms كثيرًا من Infrastructure decisions.

يمكنها توفير Tools من أجل:

- Deployment،
- Networking،
- Scaling،
- SSL certificates،
- Custom domains،
- Monitoring،
- Staging environments.

يقدم الفصل أمثلة عبر Major cloud providers و Third-party application platforms.

### لماذا تستخدم واحدة؟

بالنسبة إلى Prototype أو CPU-based backend، قد تكون التجربة:

```text
اربط Repository
→ اضبط Runtime
→ Deploy
```

وقد يكون هذا أسرع بكثير من إدارة VM يدويًا.

### الـ Trade-off

تدير Platform المزيد نيابةً عنك.

وعادةً تدفع مقابل هذه Convenience.

### اعتبار GPU

يحذر المصدر من أن General managed application platforms قد لا توفر GPU resources اللازمة لـ Self-hosting للـ Large AI models.

قد يدفع ذلك Model inference نحو:

- Dedicated VMs،
- On-premises GPU servers،
- Specialized AI hosting platforms،
- APIs نماذج خارجية.

### Runtime compatibility

تدعم Managed platforms إصدارات محددة من Runtimes/Frameworks.

وقد يفشل Deployment إذا اعتمدت Application على Versions أو System libraries غير مدعومة.

وهذا أحد أسباب جاذبية Containers: فهي تحزم Runtime و Dependencies مع Application.

## 6. لماذا تكون Containers مفيدة للـ Deployment؟

تحزم Container:

```text
شيفرة التطبيق
+
بيئة التشغيل
+
الاعتماديات
+
محتوى نظام الملفات المطلوب
```

داخل وحدة معزولة.

يساعد ذلك Application نفسها على التصرف بصورة متسقة عبر:

- Developer machines،
- VMs،
- Cloud hosts،
- Container platforms.

### Containerization مقابل Virtualization

Virtualization:

```text
العتاد المادي
→ hypervisor
→ VM
→ OS ضيف
→ تطبيق
```

Containerization:

```text
نواة OS المضيف
→ container runtime
→ containers معزولة
→ تطبيقات + اعتماديات
```

تشترك Containers في Host kernel بدل حمل Guest OS كاملة لكل Application.

### الفوائد التي يؤكدها الفصل

- Portability،
- Footprint أصغر،
- Startup سريع،
- Repeatable runtime environment،
- Horizontal scaling أسهل.

### Docker daemon

يدير Daemon:

النموذج الذهني:

```text

   ↓ بناء (build)
```

Remote system يخزن Images ويوزعها.

الأمثلة تشمل:

- Public registries،
- Private cloud registries،
- سجلات مستضافة ذاتيًا.

## 9. Tag و Push و Pull للـ Images باستخدام Registries

تخزن Container registry الـ Images حتى يمكن إعادة استخدامها على Machines أو Deployment platforms أخرى.

Typical lifecycle:

```text
Build image
    ↓
Tag image
    ↓
Authenticate إلى Registry
    ↓
Push image
    ↓
يسحب Deployment host الـ Image
    ↓
Run container
```

### Image tags

تستخدم Images صيغة Name/Tag:

```text
repository/image:tag    # صيغة اسم الصورة
```

مثال مفاهيمي:

```text
genai-service:v1    # مثال لاسم صورة ووسمها
```

### تجنب إعادة استخدام Tags بلا حذر

يحذر المصدر من أن Mutable tag مثل:

```text
latest    # وسم افتراضي
```

يمكن استبدالها بـ Build أخرى.

بالنسبة إلى Reproducible deployments، تتبع بالضبط أي Image/Version يتم Deploy لها.

### لماذا تهم Registries في Scaling؟

تحتاج Orchestration/Deployment systems إلى مكان تستطيع منه Fetch للـ Image نفسها بصورة متكررة.

```text
السجل (registry)
  ↓
نسخة 1
نسخة 2
نسخة 3
```

وهذا يدعم Horizontal scaling متسقًا.

## 10. Docker images مبنية من Layers

تبني Docker الـ Images في Layers.

Build مبسطة:

```text
صورة Python الأساسية
    ↓
ملف المتطلبات
    ↓
الاعتماديات المثبّتة
    ↓
شيفرة التطبيق
```

تضيف Final container Writable runtime layer فوقها.

### لماذا تساعد Layers؟

يمكن إعادة استخدام Shared image layers بدل نسخها بصورة مستقلة لكل Container.

ويساعد ذلك في:

- Disk efficiency،
- Startup أسرع،
- Rebuilds أسرع.

### Build cache

إذا لم تتغير Layer أو Inputs الخاصة بها، يمكن لـ Docker إعادة استخدام Cached build results.

إذا تغيرت Layer:

```text

+
Later dependent layers
→ Rebuild
```

## 11. Writable layer الخاصة بالـ Container مؤقتة

يمكن لـ Container كتابة Files أثناء التشغيل.

لكن Data المكتوبة فقط داخل Default writable container layer ليست استراتيجية Durable persistence.

إذا تم Destroy/Recreate للـ Container:

```text
Runtime files
→ قد تختفي
```

أمثلة على Data لا ينبغي تركها ببساطة داخل Writable layer فقط:

- Database files،
- Uploaded user files،
- Important logs،
- Generated artifacts التي يجب أن تستمر.

### افصل Application lifecycle عن Data lifecycle

ينبغي أن تكون Containers قابلة للاستبدال.

```text
احذف Old container
→ ابدأ New container
→ تظل Important data موجودة في مكان آخر
```

يتطلب ذلك Explicit storage design.

## 12. خيارات Docker storage

يقدم الفصل ثلاثة Approaches للتخزين/الـ Mount:

1. Volumes،
2. Bind mounts،
3. tmpfs mounts.

### مقارنة

| نوع التخزين | أين تُخزن؟ | هل تستمر؟ | حالة استخدام قوية |
|---|---|---:|---|
| Volume | تخزين على المضيف يديره Docker | نعم | بيانات container دائمة/مشتركة |
| Bind mount | مسار صريح على المضيف | نعم | تطوير محلي/مشاركة الشيفرة |
| tmpfs | RAM المضيف | لا | بيانات مؤقتة سريعة/حساسة |

## 13. Docker volumes

الـ Volume هي Docker-managed persistent storage.

ترى Container Mounted directory.

وتملك Docker Host-side storage location.

تشمل حالات الاستخدام:

- Database data،
- State مشتركة عبر Container recreations،
- Data مشتركة بين Containers.

### نموذج الاستمرارية (Persistence model)

```text
تتم إزالة Container A
    ↓
تبقى Volume
    ↓
تقوم Container B بعمل Mount لنفس Volume
    ↓
تظل Data متاحة
```

### تنبيه Lifecycle

تستمر Volumes حتى تتم إزالتها صراحةً.

إعادة إنشاء Database container لا تعني بالضرورة Reset للـ Underlying database state إذا استمرت في استخدام Volume نفسها.

هذا مفيد في Normal operation لكنه قد يفاجئ Developers عند تغيير Database configuration.

## 15. tmpfs mounts

تخزن tmpfs mount الـ Data داخل Host memory (RAM).

لا تتم كتابة شيء بصورة دائمة إلى Disk.

عندما تتوقف Container:

```text
tmpfs data
→ تختفي
```

تشمل GenAI use cases المحتملة من الفصل:

- Temporary caches،
- Intermediate model computations،
- Temporary files،
- Session-specific logs،
- Test data،
- ملفات النموذج المؤقتة (artifacts).

### المزايا

- Fast I/O،
- لا توجد Permanent disk write،
- مفيدة لـ Temporary أو Sensitive state.

### القيود

يشير المصدر إلى أن tmpfs:

- مؤقتة،
- Linux-specific،
- لا تتم مشاركتها بين Containers بالطريقة نفسها مثل Normal volumes.

## 17. فهم Linux permissions داخل Container workflows

قد يبدو Permission listing هكذا:

```text
drwxr-xr-x    # صلاحيات مجلد في Linux
```

يشير أول Character إلى Object type.

بعد ذلك تُجمع Permissions من أجل:

1. Owner،
2. Group،
3. Others.

رموز Permission:

```text
r → قراءة
w → كتابة
x → تنفيذ
```

### الصيغة الرقمية (Numeric form)

يقدم المصدر Mapping الشائعة:

| القيمة | Permission |
|---:|---|
| 7 | `rwx` |
| 6 | `rw-` |
| 5 | `r-x` |
| 4 | `r--` |
| 3 | `-wx` |
| 2 | `-w-` |
| 1 | `--x` |
| 0 | `---` |

إذًا:

```text
755
```

تعني:

```text
المالك  = rwx
المجموعة  = r-x
الآخرون = r-x
```

### الأمر `chown`

يغير Ownership.

### الأمر `chmod`

يغير Permissions.

تكون هذه Tools مهمة عندما تنشئ Containers Files أوتعمل Mount لها.

### تحذير خاص بالـ Mount

قد تستبدل Bind mount فعليًا Permissions المرئية عند Mounted container path بـ Host filesystem permissions.

وهذا يعني أن Dockerfile permissions وحدها قد لا تفسر Runtime permission problem.

## 19. مشغّلات شبكة Docker (network drivers)

يقدم الفصل عدة Network drivers.

### Driver من نوع Bridge

يربط Containers على Docker host نفسها.

وهو Common local/multicontainer default.

### Driver من نوع Host

تستخدم Container Host network namespace بصورة أكثر مباشرة.

قد تشمل الفوائد انخفاض Networking overhead.

الـ Trade-off:

- Network isolation أقل.

### Driver من نوع None

يعطل External networking للـ Container.

مفيد عندما يجب أن تكون Process معزولة.

### Driver من نوع Overlay

يربط Containers عبر عدة Docker hosts/engines في Orchestration scenarios.

### Driver من نوع Macvlan

يمكن أن يجعل Containers تظهر بصورة أقرب إلى Physical devices على Network مع MAC addresses خاصة بها.

### Driver من نوع IPvlan

يوفر تحكمًا أكثر مباشرةً في Container IP addressing.

### التركيز العملي

بالنسبة إلى أغلب Local GenAI development، يشدد الفصل على فهم:

```text
bridge    # الافتراضي
host
none
```

قبل Advanced drivers.

## 22. Host networking و None networking

### Host networking

تشارك Container Host network namespace.

فائدة محتملة:

- Networking أبسط/أكثر مباشرة،
- NAT/Port-forwarding overhead أقل.

الـ Trade-off:

- Isolation أقل،
- Platform behavior مختلف،
- Published-port behavior يتغير.

### None networking

لا تمتلك Container سوى Local loopback interface.

هذا مفيد من أجل:

- Isolated computation،
- Sensitive jobs،
- Network-outage testing،
- Short-lived processes لا تحتاج External systems.

### مبدأ التصميم

اختر أضيق Network access مطلوب.

إذا لم تحتج Process إلى Network:

```text
لا تمنحها Network access
```

## 30. اختر Minimal base image

تصبح Base image أساس كل Later layer.

قد تتضمن Full OS image أدوات كثيرة لا تستخدمها Application مطلقًا.

يقارن الفصل بين:

- Standard/Full distributions،
- Slim Python images،
- صور مبنية على Alpine.

### Slim

حل وسط.

غالبًا تكون أسهل مع Python packages مع بقائها أصغر من Full distributions.

### Alpine

صغيرة جدًا.

لكن Minimal environment الخاصة بها يمكن أن تجعل تثبيت بعض Python/Native packages أكثر صعوبة.

### Decision rule من المصدر

```text
إذا كنت تهتم أكثر بـ Compatibility/Build convenience
→ قد تكون Slim أسهل

إذا كنت تهتم بشدة بـ Image size
→ قد تكون Alpine جذابة
```

أصغر Base ممكنة ليست دائمًا أفضل خيار من ناحية Productivity.

## 31. تجنب GPU inference runtimes عندما لا تحتاج إليها

يمكن لـ GPU-enabled model serving زيادة حجم Image بدرجة كبيرة لأنها قد تحتاج:

- Deep-learning frameworks،
- GPU runtime libraries،
- Accelerator dependencies.

إذا كان Workload يستطيع استخدام CPU inference، يناقش المصدر نهجًا أخف مثل:

```text
تصدير النموذج
→ ONNX
→ بيئة تشغيل موجَّهة لـ CPU
→ quantization اختياري
```

يربط الفصل هذا بمفاهيم Quantization من الدرس السابق.

### Trade-off مهمة

لا تُزل GPU support إذا كان Performance requirement يحتاج GPU فعلًا.

لا تُعد Image-size optimization ناجحة إذا أصبح Inference بطيئًا بصورة غير مقبولة.

لا يزال القرار يعتمد على:

- Latency،
- Throughput،
- Cost،
- Image size،
- Hardware availability.

```text
و
```


عندها يصبح Deployment:

```text
استبدل Container
من دون فقد Data
ومن دون إعادة بناء Configuration يدويًا
```

### تدفق قرار الـ Deployment

```text
هل تحتاج تحكمًا كاملًا في OS/GPU؟
→ VM / مضيف متخصص

هل لديك حمل قصير مدفوع بالأحداث؟
→ قد يناسبك serverless

هل تريد deployment مُدارًا سريعًا؟
→ منصة مُدارة

هل تحتاج تحزيمًا قابلًا للنقل والتكرار؟
→ containerize

هل تحتاج عدة containers منسَّقة محليًا؟
→ Compose

هل تحتاج بيانات دائمة؟
→ تخزين خارجي / volume

هل تحتاج GPU؟
→ GPU المضيف + وصول GPU من الـ container

الصورة كبيرة/بطيئة جدًا؟
→ حسّن الصورة الأساسية والسياق والطبقات والـ cache والمراحل
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Deployment تعني ببساطة تشغيل `uvicorn` على Computer آخر.

### لماذا هذا غير مكتمل؟

يتضمن Production deployment أيضًا Runtime dependencies و Networking و Persistence و Secrets و Scaling و Monitoring و Repeatability.

### المفهوم الخاطئ 2

> Serverless تعني عدم وجود Servers.

### لماذا هذا خاطئ؟

يدير Cloud provider الـ Server infrastructure؛ لكن Hardware لا تزال موجودة.

### المفهوم الخاطئ 3

> Serverless functions مثالية لكل AI workload.

### لماذا هذا خاطئ؟

يحذر المصدر من Limited resources و Execution-time constraints، خصوصًا مع Heavy self-hosted model inference.

### المفهوم الخاطئ 4

> Containers و Virtual machines هما Technology نفسها.

### لماذا هذا خاطئ؟

تعمل VMs على Virtualize للـ Hardware وتتضمن Guest operating systems؛ بينما تشترك Containers في Host kernel عبر Container runtime.

### المفهوم الخاطئ 5

> Docker image و Docker container هما الشيء نفسه.

### لماذا هذا خاطئ؟

Image هي Immutable package/template؛ أما Container فهي Running instance.

### المفهوم الخاطئ 6

> `EXPOSE 8000` تجعل Port 8000 قابلة للوصول Publicly.

### لماذا هذا خاطئ؟

هي توثق Intended container port؛ أما Runtime port publishing فتقوم بعمل Host mapping الفعلي.

### المفهوم الخاطئ 7

> Data المكتوبة داخل Container تستمر تلقائيًا بعد استبدالها.

### لماذا هذا خاطئ؟

Default writable layer مؤقتة من منظور Durable application state.

### المفهوم الخاطئ 8

> Bind mounts و`COPY` تفعلان الشيء نفسه.

### لماذا هذا خاطئ؟

تخزن `COPY` نسخة منفصلة داخل Image وقت Build؛ بينما تربط Bind mount Live host path وقت Runtime.

### المفهوم الخاطئ 9

> tmpfs مكان جيد لـ Durable database files.

### لماذا هذا خاطئ؟

تخزن tmpfs الـ Data في Memory وهي Nonpersistent عمدًا.

### المفهوم الخاطئ 10

> تشغيل Containers كـ Root غير ضار لأن Containers معزولة.

### لماذا هذا خاطئ؟

يزيد Root execution من Security risk ويمكن أن ينشئ Host filesystem ownership problems مع Mounts.

### المفهوم الخاطئ 11

> تحتاج Containers على Bridge network إلى نشر كل Database port إلى Public.

### لماذا هذا خاطئ؟

تستطيع Containers داخل Internal network نفسها التواصل مباشرةً باستخدام Internal ports.

### المفهوم الخاطئ 12

> Container DNS names مثل `db` يمكن Resolve لها دائمًا من Host machine.

### لماذا هذا خاطئ؟

يصف المصدر Docker embedded DNS داخل User-defined container networks، وليس Host DNS mechanism عامة.

### المفهوم الخاطئ 13

> Host networking تعطي Isolation نفسها مثل User-defined bridge.

### لماذا هذا خاطئ؟

تزيل Host networking حدًا مهمًا من Network isolation.

### المفهوم الخاطئ 14

> تستطيع Docker توفير GPU acceleration حتى لو لم يمتلك Host Compatible GPU environment.

### لماذا هذا خاطئ؟

يجب أن يوفر Host Compatible hardware و Drivers/Tooling؛ وتقوم Docker بإتاحة هذه Resources للـ Container.

### المفهوم الخاطئ 15

> Compose ليست سوى نسخة أقصر من `docker run`.

### لماذا هذا غير مكتمل؟

تنسق Compose بصورة Declarative الـ Services و Networks و Volumes و Variables و Secrets و Commands و Environment-specific configuration.

### المفهوم الخاطئ 16

> وضع Secret داخل Dockerfile آمن لأن Images غير قابلة للتغيير.

### لماذا هذا خاطئ؟

يمكن توزيع Image layers وفحصها. ينبغي حقن Secrets عبر Runtime secret/configuration mechanisms المناسبة.

### المفهوم الخاطئ 17

> أصغر Base image ممكنة هي دائمًا أفضل اختيار.

### لماذا هذا خاطئ؟

قد تنشئ Minimal distributions Compatibility و Build-complexity trade-offs.

### المفهوم الخاطئ 18

> ينبغي دائمًا أن تكون `COPY . .` أول Dockerfile step بعد `FROM`.

### لماذا هذا خاطئ؟

قد يؤدي نسخ Frequently changing source مبكرًا إلى إبطال Expensive cached dependency layers.

### المفهوم الخاطئ 19

> `.dockerignore` تجعل Builds أنظف قليلًا فقط.

### لماذا هذا غير مكتمل؟

يمكنها تقليل Build context و Image size و Cache invalidation وإدراج Local secrets/artifacts دون قصد.

### المفهوم الخاطئ 20

> تعطيل كل Package cache يجعل Builds أسرع دائمًا.

### لماذا هذا خاطئ؟

قد يقلل Final image size لكنه يجبر على Repeated downloads. تختلف Build-cache strategy عن Final-image strategy.

### المفهوم الخاطئ 21

> يجب أن تُشحن Development compilers/Debugging tools داخل Production image.

### لماذا هذا خاطئ؟

يمكن لـ Multi-stage builds إبقاء Build/Development tooling خارج Final runtime image.
