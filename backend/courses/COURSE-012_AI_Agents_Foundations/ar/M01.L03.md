## 1. لماذا يوجد MCP

في الفصل 2، أعطينا Agents أدوات مباشرة داخل Code الخاص بها. يعمل ذلك جيدًا في الأنظمة الصغيرة، لكن هذا الأسلوب يصبح صعب الصيانة عندما تحتاج Agents كثيرة إلى الوصول إلى External systems كثيرة.

تخيل Research agent واحدة تحتاج إلى الاتصال بـ:

- Filesystem،
- Database،
- Web-search API،
- Calendar،
- GitHub،
- و Agent أخرى.

من دون Shared protocol، قد يحتاج كل Integration إلى Schema خاصة به و Request format و Authentication logic و Error handling و Result parser.

صُمم Model Context Protocol لتوحيد Boundary الخاصة بهذا Integration.

يصف المصدر MCP بأنه Open standard أنشأته Anthropic ويعتمد على JSON-RPC 2.0. والغرض منه هو السماح لأنظمة AI بالاتصال بالقدرات الخارجية بصورة متسقة وآمنة وفعالة.

تشبيه مفيد يقدمه الفصل هو **USB-C لأنظمة AI**: بدلًا من بناء Connector مختلف لكل Service، يتفق Clients و Servers على Protocol واحدة.

## 2. مشكلات Standardization التي يعالجها MCP

يحدد الفصل عدة مشكلات متكررة كانت موجودة قبل أن تصبح Standardization الشبيهة بـ MCP شائعة.

### تكامل Tools المتجزئ

قد تمثل Model providers و Agent frameworks المختلفة الـ Tools بطرق مختلفة. ويمكن أن ينتهي Developer إلى إعادة كتابة Schemas و Parameters و Response envelopes و Parsing logic للقدرة الأساسية نفسها.

### الوصول غير المتسق إلى Data

تتطلب Filesystems و Databases و Web APIs و Cloud applications تقليديًا Custom interfaces مختلفة. ويصعب إعادة استخدام Integrations هذه عبر Agents مختلفة.

### اتصال Multi-agent بطريقة مخصصة

إذا احتاجت Agent إلى كشف Capability لـ Agent أخرى، فغالبًا ما يلزم Custom plumbing ما لم يتفق الطرفان على Protocol مشتركة.

### تفاوت Security و Control

عندما يُبنى كل Integration بطريقة مختلفة، يصبح تطبيق Access rules و Auditing و Monitoring بصورة متسقة أصعب.

لا يزيل MCP كل Production concern. يوضح الفصل صراحة أن Authentication و Authorization و Versioning و Server availability و Error handling تظل مهمة. ما يزيله MCP هو جزء كبير من Provider-specific tool wiring المتكرر.

## 3. Architecture الخاصة بـ MCP: Client و Server و Service

يعرض الفصل MCP باستخدام ثلاثة مكونات عملية:

1. **MCP client**
2. **MCP server**
3. **Underlying service**

### عميل MCP (MCP client)

الـ Client هو Application التي تتصل بـ MCP server. وتُعد AI agent نوعًا من MCP clients، لكن Desktop assistants و IDEs وتطبيقات LLM الأخرى يمكنها أيضًا العمل كـ Clients.

يكتشف Client الـ Capabilities ويستدعيها عبر Protocol.

### خادم MCP (MCP server)

يكشف Server الـ Capabilities للـ Clients ويتعامل مع MCP requests و Responses.

### الخدمة (Service)

يستخدم الفصل كلمة **Service** كمصطلح مناسب للنظام الفعلي الموجود خلف MCP server، مثل:

- Database،
- Filesystem،
- Web API،
- SaaS platform،
- أو Agent أخرى.

يعطينا ذلك Abstraction واضحة:

```text
Agent / تطبيق LLM
      |
      v
   عميل MCP (MCP client)
      |
      v
   خادم MCP (MCP server)
      |
      v
Database / API / Filesystem / Agent — خدمات خارجية
```

لا ينبغي أن تحتاج Agent إلى معرفة كيفية تنفيذ Underlying service. كل ما تحتاج إليه هو فهم Interface التي يكشفها Server.

## 4. قدرات MCP: Tools و Resources و Prompts

يصف الفصل ثلاثة Capability primitives يمكن لـ MCP server كشفها.

### الأدوات (Tools)

تمثل **Tools** إجراءات يمكن لـ Model أو Agent استدعاؤها.

أمثلة:

- إنشاء Issue،
- تشغيل Database query،
- إرسال Message،
- عرض Files،
- استرجاع URL.

تكون Tools عادة **Model-controlled**: يقرر Model ما إذا كان سيستخدمها ومتى.

### الموارد (Resources)

تمثل **Resources** Data أو Objects خارجية مثل Files أو Configuration أو معلومات يمكن الوصول إليها عبر Database.

### القوالب (Prompts)

تمثل **Prompts** Templates قابلة لإعادة الاستخدام يوفرها Server للتفاعلات أو Workflows الشائعة.

يقدم الفصل تمييزًا مهمًا حول Control:

- تختار Model عادة Tools،
- أما Resources و Prompts فعادة ما تُعرض أو تُختار بواسطة User/Application.

يركز الكتاب في الغالب على Tools لأنها Capability الأكثر استخدامًا مباشرة في Actions الخاصة بالـ Agent ضمن أمثلته.

| العنصر في MCP | الغرض الأساسي | المتحكم المعتاد |
|---|---|---|
| الأداة (Tool) | تنفيذ Action | Model/Agent — النموذج/Agent |
| المورد (Resource) | توفير الوصول إلى Data/Object | User أو Application |
| Prompt | توفير Interaction template قابلة لإعادة الاستخدام | User أو Application |

## 5. JSON-RPC 2.0 كأساس للاتصال

يعتمد Communication في MCP على JSON-RPC 2.0 وفق وصف الفصل.

الفائدة الهندسية هي الاتساق. سواء كُتب Underlying server بلغة Python أو TypeScript أو Go أو لغة أخرى، فإن Requests و Responses تتبع Shared message protocol.

وهذا ما يجعل MCP مفيدًا بوصفه Language-independent integration boundary.

يمكن لـ Python agent استهلاك Server مكتوب بلغة أخرى دون الحاجة إلى Language-specific bridge، ما دام الطرفان يتحدثان MCP.

## 6. أنماط Deployment في MCP

يعرض الفصل إعدادات Deployment محلية وبعيدة ومختلطة.

### Server محلي

يمكن تشغيل Server على Machine نفسها التي يعمل عليها Client، وغالبًا في صورة Subprocess.

تشمل المزايا التي يصفها الفصل:

- Latency منخفضة،
- لا توجد Network hop،
- Development setup بسيط،
- مفيد للعمليات المحلية أو الحساسة.

### Server بعيد

يمكن تشغيل Server كـ Network service ومشاركته بين Clients أو Agents متعددة.

ويكون ذلك مفيدًا لـ:

- Shared services،
- Distributed architectures،
- Cloud deployment،
- Multiclient access،
- Remote APIs أو Agent services.

### Deployment مختلط

قد تتصل Agent حقيقية بعدة Servers في الوقت نفسه. يمكن أن يكون بعضها Local وبعضها Remote.

على سبيل المثال:

```text
Agent — الوكيل
  +--> Local filesystem MCP server — خادم MCP لنظام الملفات المحلي
  +--> Local Git MCP server — خادم MCP محلي لـ Git
  +--> Remote GitHub MCP server — خادم MCP بعيد لـ GitHub
  +--> Remote Slack MCP server — خادم MCP بعيد لـ Slack
```

يشير الفصل بعناية إلى أن كل Server منفردة تكون إما Local أو Remote؛ أما Agent setup الكاملة فهي التي تصبح Mixed.

## 7. Transport عبر STDIO و SSE في الفصل

يركز المصدر على نمطين من MCP transport: STDIO و SSE.

### النقل عبر STDIO

مع STDIO، يشغل Client الـ Server في صورة Subprocess على Host نفسها ويتواصل معه عبر Standard input/output pipes.

يضع الفصل STDIO بوصفه مناسبًا جدًا لـ:

- Local development،
- Helper processes،
- Command-line experiments،
- تكامل Process-to-process بسيط مع Client واحدة.

### النقل عبر SSE

في أمثلة Remote server داخل الفصل، يُستخدم SSE عبر HTTP. ويمكن أن يظل Server يعمل بصورة مستقلة، وتتصل Clients متعددة به عبر URL.

يضع الفصل هذا النمط مناسبًا لـ:

- Remote أو Cloud deployment،
- Shared servers،
- Network-addressable tools،
- وصول متعدد الـ Clients (Multiclient access).

| الخاصية | نقل STDIO | نقل SSE في الفصل |
|---|---|---|
| الموقع المعتاد | Host نفسها | Local أو Remote HTTP service |
| اتصال Client | أنابيب Process (Process pipes) | اتصال URL/Network |
| دورة حياة Server | غالبًا يشغله Client | غالبًا يعمل بصورة مستقلة |
| المشاركة | عادة Parent client واحدة | يمكن أن يدعم Clients متعددة |
| الاستخدام المناسب | Local tools و Development | Shared أو Remote services |

## 8. يمكن لـ MCP دعم Layers متعددة داخل Agent

من السهل التفكير في MCP على أنه مجرد طريقة لإضافة Action tools. لكن الفصل يوسع هذه الرؤية عبر ربط MCP-hosted capabilities بالـ Functional layers التي قُدمت سابقًا.

### الأدوات (Tools) و Actions

تشمل الأمثلة عمليات GitHub و Slack و Filesystem.

### Reasoning و Planning

قد يكشف Server عن Specialized planning أو Structured-thinking capabilities.

### Knowledge و Memory

قد يكشف Server عن Databases أو Vector stores أو Cloud documents أو Persistent memory.

### Evaluation و Feedback

قد يكشف Server عن Scoring أو Judging أو Benchmarking أو Human-approval routing.

الدرس المعماري هو أن MCP **Connection pattern**، وليس مجرد Category من Action tools.

## 12. MCP مع Assistants مقابل Agents

يقدم الفصل تمييزًا معماريًا مفيدًا: Permission prompts وحدها لا تحدد ما إذا كان الشيء Assistant أم Agent.

التمييز الأقوى هو Execution loop.

### تفاعل شبيه بـ Assistant

```text
User request -> اختيار Action -> تنفيذ Action -> إعادة Result -> التوقف
```

### حلقة Agent (Agent loop)

```text
Goal -> اختيار Tool -> ملاحظة Result -> تحديد Next step -> استدعاء Tool أخرى -> ...
```

هذا مهم لأن Tool mistake داخل One-step assistant قد ينتج Result سيئة واحدة. أما Tool mistake داخل Autonomous loop فقد تتضخم عبر عدة Steps لاحقة.

ولهذا تصبح MCP tool access مشكلة Security و Reliability بمجرد أن تعمل Agents بدرجة حقيقية من Autonomy.

## 13. أمان MCP: Autonomy ترفع مستوى المخاطر

يحذر الفصل بقوة من أن Agent قد تسيء استخدام أي Capability تمنحها لها.

ويبرز عدة Risk categories.

### Actions مدمرة

يمكن لـ Write و Delete و Version-control و Database و Cloud-resource tools تغيير State أو تدميرها.

### تسريب Data

إذا استطاعت Agent قراءة Sensitive information وإرسال Information إلى مكان آخر، فقد يحاول Attacker إعادة توجيه تلك Data.

### انتهاكات Privacy

قد تعمل Tool باستخدام User credentials قوية وتكشف Information أكثر مما يدرك User أنها تتم مشاركتها مع Agent system الأوسع.

### تضخم Cost

يمكن لـ Looping agent استدعاء APIs أو Models مكلفة بصورة متكررة ما لم تُفرض Budgets و Rate limits.

### Prompt injection عبر Tool output

قد يحتوي External content المُعاد من Websites أو Files أو Messages على Malicious instructions تدخل Model context.

يوصي الفصل بـ Defense-in-depth تشمل:

- Tool allowlisting،
- Sandboxing،
- Output validation،
- Rate limiting،
- Budget caps،
- Human approval للـ High-stakes actions.

مبدأ تصميم حاسم هو:

> تعامل مع كل Tool قوية على أنها Capability قد تستخدمها Agent بطريقة خاطئة في النهاية.

## 17. متى تستحق MCP إضافة Layer إضافية

يقدم الفصل مفاضلة هندسية مهمة: يضيف MCP مستوى من Abstraction، لكنه يضيف أيضًا Process أو Network connection إضافية، و Protocol layer أخرى، و Failure mode محتملة أخرى.

قاعدة تقريبية مفيدة من المصدر هي:

### فضّل MCP عندما

- تكون Capability خارجية فعلًا،
- يمتلك Team آخر Implementation،
- تكون Tool وحدة Deployment منفصلة،
- تحتاج Agents متعددة إلى مشاركتها،
- تكون Language/Runtime independence ذات قيمة،
- يكون Isolation مفيدًا.

### فضّل In-process function عندما

- تنتمي Logic إلى Agent هذه فقط،
- تعمل بالفعل داخل Process نفسها،
- لا تمنح Protocol abstraction فائدة Reuse كبيرة.

يمنع ذلك تحويل كل Helper function صغيرة إلى Distributed service.

## 19. Shared state تغيّر Architecture

يستخدم الفصل In-memory journal لأغراض تعليمية، لكنه يبرز فرقًا مهمًا بين Local subprocess execution و Shared remote server.

إذا كانت كل Local agent تشغل Server process خاصة بها، فيمكن لكل Process امتلاك In-memory state منفصلة.

أما إذا اتصلت Agents متعددة بـ Long-running server واحدة، فقد تشترك كلها في Module-level list نفسها.

وقد ينتج عن ذلك سلوك مفاجئ مثل Journal entries مكررة أو مختلطة.

يعلّمنا ذلك Systems lesson أوسع:

> نقل Capability خلف Shared server يغيّر افتراضات State ownership و Isolation و Concurrency.

لذلك قد يحتاج Production design إلى:

- User/Session identifiers،
- Tenant isolation،
- Transactional storage،
- Locking أو Concurrency control،
- قواعد Persistence صريحة.

القائمة البسيطة تعليمية عن قصد، وليست Production storage design.

## 20. وضع MCP داخل Architecture الكاملة للـ Agent

يمكنك الآن قراءة MCP-enabled agent system هكذا:

```text
Goal الخاصة بـ User
   |
   v
تعليمات Agent + LLM
   |
   v
اتصال عميل MCP (MCP client connection)
   |
   +--> اكتشاف Tools
   +--> فحص Schemas/Descriptions
   +--> استدعاء Capability المختارة
   |
   v
خادم MCP (MCP server)
   |
   v
خدمة خارجية / Data / Agent
   |
   v
نتيجة مهيكلة (Structured result)
   |
   v
تقيّم Agent النتيجة وتتابع
```

أصبحت Design questions المهمة الآن:

1. هل تنتمي هذه Capability داخل Process أم خلف MCP؟
2. هل ينبغي أن تكون Server Local أم Remote؟
3. ما Capabilities التي ينبغي أن تكشفها Server؟
4. هل Descriptions و Schemas دقيقة بما يكفي لـ Safe model selection؟
5. ما Permissions التي تمتلكها Server؟
6. ما الذي قد يحدث إذا أساءت Agent استخدام Tool؟
7. ما State المشتركة عبر Clients؟
8. كيف ستفحص Execution وتتتبعه وتتحقق منه وتقيّده؟

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: يلغي MCP الحاجة إلى فهم Underlying service

> يوحد MCP الـ Interface، لكن Production concerns تظل موجودة.

ما تزال Authentication و Authorization و Failures و Server uptime و Versioning و Service-specific behavior تحتاج إلى Attention هندسي.

### المفهوم الخاطئ 2: MCP مخصص فقط لـ Action tools

> يمكن لـ MCP كشف Tools و Resources و Prompts، كما يمكن لـ MCP-hosted capabilities دعم Layers مثل Reasoning و Memory و Knowledge و Evaluation أيضًا.

### المفهوم الخاطئ 3: إذا عملت Tool داخل Assistant فهي آمنة تلقائيًا داخل Agent

> تضخّم Autonomous loops الأخطاء.

يمكن لـ Destructive أو Misleading tool result التأثير في Actions لاحقة كثيرة.

### المفهوم الخاطئ 4: ينبغي تحويل كل Internal function إلى خادم MCP (MCP server)

> يضيف MCP Indirection و Latency و Deployment work و Failure modes.

استخدمه عندما تبرر Reuse أو Isolation أو External ownership أو Distribution هذه التكلفة.

### المفهوم الخاطئ 5: نقل State خلف Server لا يغيّر السلوك

> يمكن لـ Shared servers تحويل Per-process state إلى Shared multi-client state.

يجب تصميم State isolation بصورة صريحة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| البروتوكول MCP | Model Context Protocol؛ Interface معيارية بين أنظمة AI والـ External capabilities |
| عميل MCP (MCP client) | Application تتصل بـ MCP server وتستهلك Capabilities الخاصة بها |
| خادم MCP (MCP server) | Process/Service تكشف Tools أو Resources أو Prompts عبر MCP |
| الخدمة (Service) | مصطلح الفصل للـ API أو Database أو Filesystem أو SaaS app أو Capability أخرى موجودة خلف Server |
| بروتوكول JSON-RPC 2.0 | Structured request-response protocol تُستخدم كأساس Communication في MCP وفق الفصل |
| الأداة (Tool) | External action يمكن لـ Model استدعاؤها |
| المورد (Resource) | Data أو Object خارجية مكشوفة عبر MCP |
| Prompt | قالب تفاعل قابل لإعادة الاستخدام يوفّره Server |
| أداة FastMCP | Python helper تستخدم في الفصل لبناء MCP servers |
| نقل STDIO | Local subprocess transport تستخدم Standard input/output pipes |
| نقل SSE | Server-sent-events HTTP transport المستخدمة في أمثلة Remote داخل الفصل |
| أداة MCP Inspector | Tool لفحص Schemas و Capabilities و Initialization و Live tool execution |
| قائمة السماح للأدوات (Tool allowlist) | مجموعة Capabilities محددة صراحة يُسمح لـ Agent بالوصول إليها |
| العزل (Sandboxing) | عزل Risky tool execution عن Access الأوسع للنظام |
| الحالة المشتركة (Shared state) | Data يمكن لـ Clients متعددة متصلة بـ Long-running server نفسها الوصول إليها |
| فصل المسؤوليات (Separation of concerns) | إبقاء Agent logic منفصلة عن External tool implementation |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما مشكلات Integration التي يحاول MCP توحيدها؟
2. ما أدوار MCP client و MCP server و Underlying service؟
3. كيف تختلف Tools و Resources و Prompts؟
4. لماذا تُعد JSON-RPC مهمة لـ Portability في MCP؟
5. متى تكون STDIO مناسبة طبيعيًا؟
6. متى تكون Remote server connection أنسب؟
7. كيف يمكن لـ MCP دعم Knowledge أو Evaluation، وليس Actions فقط؟
8. ما المعلومات التي تكشفها `@mcp.tool()` لـ Model؟
9. لماذا تهم Tool docstrings؟
10. ما الذي ينبغي فحصه قبل ربط Server بـ Agent؟
11. لماذا قد يكون Autonomous MCP tool use أكثر خطورة من One-shot assistant tool use؟
12. اذكر أربعة Defense-in-depth controls من هذا الدرس.
13. لماذا قد تكون In-process function أفضل من MCP لـ Private helper؟
14. ما الفائدة المعمارية التي تظهر عند نقل Tools إلى Standalone MCP server؟
15. لماذا قد تصبح Module-level in-memory state خطرة داخل Shared server؟
