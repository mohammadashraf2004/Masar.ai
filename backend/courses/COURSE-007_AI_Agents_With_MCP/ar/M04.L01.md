## 1. أين تقع Transport layer داخل MCP؟

تعمل معظم شيفرة MCP على مستوى عالٍ: `call_tool()` و`list_resources()` و`get_prompt()` وSDK methods مشابهة. تخفي هذه Methods عدة Layers أسفلها.

Stack مفيدة هي:

```text
تطبيق المضيف / كود خادم MCP
              ↓
كائنات بروتوكول MCP ومعالجاتها
              ↓
ClientSession / ServerSession + dispatcher   — جلسات ومرسل الرسائل
              ↓
طبقة النقل (Transport)
              ↓
أنابيب العمليات / HTTP / وسيلة نقل مخصصة
```

يحدد Protocol **ما معنى Messages وكيف يكون شكلها**. وتحدد Transport **كيف تنتقل هذه Messages**.

هذا الفصل بين المسؤوليات هو ما يسمح لنفس Client/Server logic بالعمل عبر Local stdio أو Remote Streamable HTTP أو Custom transport دون إعادة كتابة Application نفسها.

{{image:mcp-abstraction-stack}}

### مسؤوليات Transport

بغض النظر عن Implementation، يجب على Transport التعامل مع أمور مثل:

- إنشاء Communication،
- Serialization/Deserialization للـ Messages،
- Framing/Deframing للـ Messages،
- نقل Bytes عبر Underlying medium،
- إظهار Connection errors/Timeouts،
- الإغلاق والتنظيف.

## 2. JSON-RPC: طبقة Data في MCP

يستخدم MCP معيار JSON-RPC 2.0 كأساس لتبادل Messages. JSON-RPC صغير عمدًا: Messages هي JSON objects تمثل Remote procedure calls ونتائجها وإخفاقاتها وOne-way notifications.

يعامل الفصل هذه Messages بوصفها **Data layer** في MCP.

### ملاحظات مهمة خاصة بـ MCP

يسلط المصدر الضوء على تفصيلين مرتبطين بإصدارات Protocol:

- يتطلب MCP Request IDs غير Null حتى يمكن ربط Responses بالـ Requests.
- كانت JSON-RPC batching موجودة في JSON-RPC specification الأساسية، لكن MCP أزال دعم Batch في Protocol revision بتاريخ 2025-06-18 كما يصف المصدر.

### أربع عائلات من Messages ينبغي فهمها

```text
Request      → يطلب من Peer تنفيذ شيء ويتوقع Response
Result       → Response ناجحة لـ Request
Error        → Response خطأ على مستوى Protocol لـ Request
Notification → Message أحادية الاتجاه؛ لا يُتوقع Response
```

هذه الأشكال القليلة تكفي للتعبير عن جميع MCP methods عالية المستوى التي استخدمتها بالفعل.

## 6. Progress وCancellation على مستوى Message

### Progress

يمكن لـ Requester تضمين `progressToken` داخل Request metadata. وتنسخ Progress notifications التي ترسل أثناء تلك العملية Token نفسها، مما يمنح Receiver طريقة لتوجيه كل Progress event إلى In-flight request أو UI callback الصحيحة.

مفاهيميًا:

```text
Request id=4, progressToken=P123   — الطلب ورمز التقدم
      ↓
progress(P123, 20/100)   — تقدم أولي
progress(P123, 50/100)   — منتصف التنفيذ
progress(P123, 90/100)   — اقتراب الانتهاء
      ↓
Result id=4   — النتيجة النهائية
```

Progress اختيارية. ويوصي المصدر بأن يقوم Peerان كلاهما بـ Rate limiting للـ Progress traffic لتجنب إغراق الطرف الآخر.

### Cancellation

يمكن للـ Cancellation الأقدم أوالمرتبطة بـ stdio استخدام One-way notification تحمل Request ID وReason اختياريًا.

ينبغي للـ Receiver إيقاف العملية المطابقة إذا كانت لا تزال تعمل وتحرير Resources.

### Race conditions

يمكن أن تتسابق Cancellation مع Completion. فقد تُرسل Result قبل وصول Cancellation بلحظة. ينبغي أن يكون Requester قادرًا على تجاهل Late result، وألا يعامل Receiver إلغاء Request انتهت بالفعل كخطأ Fatal.

### اختلاف Streamable HTTP الحديثة

ينص المصدر على أنه في Streamable HTTP الحديثة، يتحقق Client cancellation عبر Abort للـ In-flight POST request بدلًا من إرسال Client-originated cancellation notification.

## 7. Text وBinary data وResource links

يمكن لـ MCP content blocks حمل Text وأنواع موجهة إلى Binary data مثل Image أو Audio content.

### Base64 overhead

يُنقل Binary data المضمّن مباشرة داخل JSON في صورة Base64. ويشير الفصل إلى التكلفة المعروفة: تتحول كل 3 Bytes تقريبًا إلى 4 ASCII bytes — أي نحو **33% زيادة في الحجم**.

يجعل ذلك Direct message embedding غير جذاب بدرجة متزايدة للـ Payloads الكبيرة.

### Resource links كبديل

تصف `ResourceLink` الـ Data دون تضمين Data blob نفسها.

تشمل الفوائد:

- **Lazy loading** — اجلب Data فقط عند الحاجة،
- **Out-of-band retrieval** — يمكن لـ Application تتبع URI خارج MCP payload الأساسية،
- **توفير Context** — يمكن لـ Metadata إعلام Model دون إدخال File كاملة في Context window.

بالنسبة إلى Data الكبيرة، يذكر المصدر أن HTTP URLs أصبحت URI pattern شائعة.

### انضباط عملي في Message size

لا يحدد Protocol حدًا عالميًا واحدًا لحجم Message، بينما قد تفرض Platforms حدودها الخاصة. لذلك يوصي المصدر بإبقاء Messages صغيرة نسبيًا واستخدام Patterns مثل Pagination أو Resource links عندما تكبر Data.

[[IMAGE_NEEDED: Embedded binary versus ResourceLink | A comparison showing image bytes Base64-encoded inside a JSON-RPC payload versus a lightweight resource link containing URI/metadata and deferred retrieval | Learner should notice the payload and context savings of lazy/out-of-band loading]]

## 8. Session objects: الحد الفاصل فوق Transport

يستخدم Python SDK كائنات Session كواجهة مستقرة بين MCP application code وUnderlying transport.

- يُستخدم `ClientSession` على جانب Client.
- يُستخدم `ServerSession` على جانب Server/Request path.

تتحول High-level call مثل `call_tool()` في النهاية إلى JSON-RPC request تُرسل عبر Write stream تديرها Session.

### مسار الإرسال

```text
Application تستدعي call_tool()
        ↓
Session تنشئ JSON-RPC request
        ↓
Dispatcher يعيّن/يسجل Request ID
        ↓
SessionMessage تُكتب إلى In-memory write stream
        ↓
Transport تقوم Serialization/Framing/Send
```

### مسار الاستقبال

```text
Transport تستقبل Bytes
        ↓
Deframe + Validate لـ JSON-RPC
        ↓
SessionMessage توضع في Read stream
        ↓
Dispatcher توجهها حسب Message type
```

هذا هو Abstraction الأساسي: Sessions تهتم بدلالات MCP messages؛ بينما Transports تهتم بنقل هذه Messages عبر Wire.

## 9. Dispatcher: Correlation وConcurrency وCancellation

JSON-RPC dispatcher هي المكون الأساسي الذي يوجه Received messages ويدير حالة In-flight requests.

### Routing

تميز Dispatcher بين:

- Request،
- Notification،
- Successful response،
- Error response،
- Transport exception.

تستخدم Responses وErrors الـ ID الخاصة بها لحل Entry في Pending-request table.

إذا وصلت Response لـ ID غير معروفة أوغير Pending، يصف المصدر تسجيلها وإسقاطها بدلًا من Crash للـ Loop بالكامل.

### لماذا تحصل كل Request على Execution state مستقلة؟

بالنسبة إلى Incoming request، تستطيع Dispatcher:

1. قراءة Metadata مثل Progress token،
2. بناء Dispatch context،
3. إنشاء `anyio.CancelScope`،
4. تسجيل Request في In-flight dictionary،
5. تشغيل Handler داخل Task group،
6. إرسال Result/Error الخاصة بـ Handler باستخدام Request ID نفسها.

يسمح ذلك بمعالجة Requests كثيرة بالتوازي دون أن تمنع Tool بطيئة حركة Wire.

### Cancellation تصل إلى Task الصحيحة

يستخدم Cancellation event الـ Request ID للعثور على In-flight entry المطابقة وإلغاء Scope الخاصة بتلك Request.

### إغلاق Connection

إذا أُغلق Underlying connection أثناء انتظار Requests، يجب ألا تترك Session الـ Callers ينتظرون إلى الأبد. يصف المصدر توزيع Local connection-closed error على جميع Pending requests ومسح Pending table.

## 10. ما الذي يجب على كل Transport فعله؟

قبل مقارنة stdio وHTTP، افصل بين **Connection establishment** وProtocol initialization.

### Connection establishment

تنشئ Transport قناة Communication — Launch لعملية، أوفتح HTTP communication، أوإنشاء Socket، أوأي شيء تتطلبه Medium المستخدمة.

### Initialization تعتمد على Version

يصف المصدر أسلوب التشغيل الحديث بنمط 2026-07-28 على أنه لا يتضمن Capability/Version handshake منفصلة. تنتقل Client identity وProtocol version وCapabilities مع Metadata الخاصة بكل Request.

كانت Versions الأقدم تستخدم Initialize request/response تتبعها Initialized notification.

بالنسبة إلى stdio، يظل بدء Subprocess وإنشاء Read/Write channels خطوة Setup شبيهة بالـ Initialization على مستوى Transport/Process حتى مع اختفاء Protocol handshake القديمة.

### الحد الأدنى من مسؤوليات Transport

يجب على أي Transport أن تكون قادرة على:

- إنشاء Communication،
- إرسال JSON-RPC messages،
- استقبال JSON-RPC messages،
- التعامل مع Errors وTimeouts،
- الإغلاق بصورة سليمة.

## 11. stdio: Transport خاصة بالعمليات المحلية

stdio هي Local-process transport في MCP. يشغّل Client الـ MCP server بوصفه Subprocess ويتواصل عبر Standard input وStandard output الخاصة بهذه العملية.

```text
Host / MCP Client
      │
      ├── يكتب JSON-RPC lines → Server stdin
      └── يقرأ JSON-RPC lines ← Server stdout
```

### Message framing

تستخدم stdio رسائل JSON-RPC محددة بفاصل Newline. تنتهي كل JSON message مكتملة بسطر جديد.

توفر Request IDs عملية Correlation حتى عند معالجة Messages متعددة بصورة متزامنة.

### فتح اتصال stdio

تنفذ Client-side transport تقريبًا ما يلي:

```text
1. تحديد Command + Arguments.
2. تشغيل Server subprocess.
3. إنشاء In-memory read/write stream pairs بسعة صفرية.
4. تشغيل Task لقراءة stdout.
5. تشغيل Task للكتابة إلى stdin.
6. تسليم read_stream + write_stream إلى ClientSession.
```

تنشئ Zero-capacity memory streams حالة Backpressure: تنتظر عملية Send حتى يكون Receiving side مستعدًا.

[[IMAGE_NEEDED: stdio transport internals | A diagram showing ClientSession connected via two anyio memory stream pairs to stdin_writer/stdout_reader tasks, which in turn connect to the server subprocess's stdin/stdout | Learner should notice the separation between in-memory session streams and OS process pipes]]

### File descriptors على جانب Server

جانب Server هو أصلًا Subprocess، لذلك لا يشغّل Process أخرى. بل يلف/يمتلك stdin/stdout descriptors الخاصة به لاستخدام Transport.

لهذا **يجب ألا تُطبع Logs الخاصة بالـ Server عشوائيًا إلى stdout**: لأن stdout تحمل JSON-RPC wire protocol. ينبغي أن تذهب Diagnostics إلى stderr أو Logging channel أخرى.

## 12. كيف ترسل stdio Messages وتستقبلها؟

### مسار Client → Server

تكتب Session كائن `SessionMessage` إلى Write stream الخاصة بها. وتقوم Writer task في Transport بما يلي:

1. تستقبل Message،
2. تحولها إلى JSON عبر Serialization،
3. تضيف Newline كـ Frame delimiter،
4. تقوم Encoding للـ Text،
5. تكتب Bytes إلى stdin الخاصة بـ Server subprocess.

### مسار Server → Client

يقوم Server بعملية Serialization للـ Message وتحديد Frame باستخدام Newline، ثم يكتبها إلى stdout، ويقوم Flush لـ stdout صراحة حتى لا تؤخر Buffering عملية Delivery.

### مسار Server → Client للاستقبال

يقرأ Client أجزاء من Server stdout. وقد يحتوي Chunk على:

- جزء من Message واحدة،
- Message مكتملة واحدة،
- عدة Messages.

لذلك يحافظ Reader على Buffer، ويقسّم عند Newline delimiters، ويتحقق من JSON-RPC messages المكتملة، ويلفها في `SessionMessage`، ثم يدفعها إلى Session read stream.

### مسار Client → Server للاستقبال

على جانب Server، تكون stdin Line-oriented بالفعل، لذلك يمكن Validate لكل Line وتسليمها إلى Dispatcher مع حاجة أقل إلى Manual buffering.

### تسلسل فصل stdio

يصف الفصل Graceful shutdown sequence:

```text
إغلاق Server stdin
     ↓
الانتظار لفترة قصيرة لخروج Process بصورة سليمة
     ↓
إنهاء Process tree إذا لزم
     ↓
إغلاق Memory streams/Tasks
```

تعمل Cleanup داخل مسار `finally` حتى لا يؤدي Caller cancellation إلى تسريب Subprocess.

## 13. Streamable HTTP: Transport الحديثة للاتصال Remote

Streamable HTTP هي Remote transport التي يركز عليها المصدر. في النموذج الحديث هي:

- **Single endpoint**،
- **POST-oriented**،
- **Stateless بين Requests**،
- قادرة على إعادة JSON عادية أو SSE stream محددة لنفس Request.

### HTTP request نفسها هي Frame

بخلاف stdio، لا تحتاج Transport إلى Newline delimiter. تعيش كل Outbound MCP message داخل HTTP POST request واحدة.

قد تكون Response:

- JSON body واحدة، أو
- Per-request SSE stream تحتوي واحدة أوأكثر من MCP events.

### لماذا تهم Statelessness؟

لا تعتمد Modern requests على Durable server-side MCP session. وهذا يجعل Horizontal scaling خلف Load balancers أكثر طبيعية.

[[IMAGE_NEEDED: Modern Streamable HTTP lifecycle | A diagram showing ClientSession write stream → post_writer → multiple independent POST request tasks → /mcp endpoint → JSON or per-request SSE responses → read stream | Learner should notice that each request owns its own HTTP exchange rather than sharing one permanent connection]]

## 14. فتح Streamable HTTP والإرسال عبرها

يأخذ Client context manager عنوان Server URL، واختياريًا Async HTTP client تم إعدادها مسبقًا.

تتيح Custom HTTP client لـ Application التحكم في جوانب مثل:

- Authentication،
- Headers،
- Timeouts،
- TLS/Proxy settings.

### Opening flow

يمكن تلخيص Lifecycle الحديثة هكذا:

```text
1. إنشاء/قبول Async HTTP client.
2. إنشاء MCP read/write memory streams.
3. إنشاء StreamableHTTPTransport للـ URL.
4. تشغيل post_writer task طويلة العمر.
5. تسليم Read/Write streams إلى ClientSession.
6. كل Outbound SessionMessage تشغّل Ephemeral POST task.
```

يذكر المصدر أن Legacy connection code قد يحتوي ما يزال على Session-ID وGET-stream compatibility behavior، لكن Modern operation لا تتطلب هذه Mechanisms.

### Metadata في Modern requests

تحمل Modern requests معلومات Version/Client/Capability مع Request حتى يستطيع Server معالجة كل Stateless request بصورة مستقلة.

### Responses الخاصة بالـ Notifications

لا تتوقع Client notification المُرسلة عبر HTTP MCP response body بالمعنى نفسه للـ Request. يناقش المصدر التعامل مع HTTP 202 للـ Accepted notifications، واعتبار 202 غير المتوقعة لـ Request خطأ بدل الانتظار إلى الأبد.

## 15. كيف يرد Server عبر Streamable HTTP؟

بالنسبة إلى Incoming request، يختار Server شكل Response مناسبًا للعملية.

### JSON response mode

بالنسبة إلى Operation قصيرة، يستطيع Server إعادة JSON-RPC result/error واحدة داخل HTTP response عادية.

### نمط استجابة SSE لكل طلب (Per-request SSE response mode)

بالنسبة إلى عمل طويل، يمكن لـ SSE response حمل Events متعددة — مثل Progress — قبل أن تنهي JSON-RPC response/error النهائية الـ Stream.

توجد SSE stream فقط لذلك POST/Request المحدد. وهي ليست الشيء نفسه مثل Old global long-lived HTTP SSE connection.

### منطق الاستقبال في الـ Client (Client receive logic)

يفحص Client نوع HTTP content:

```text
application/json   → Parse لـ JSON-RPC response واحدة
text/event-stream  → Iterate عبر SSE events وParse لكل Message
unexpected type    → مسار Transport error
```

تُلف Parsed responses في Session messages وتُرسل إلى Read stream نفسها التي تستخدمها كل Transports.

هذا هو Transport abstraction عمليًا: لا تحتاج Session إلى معرفة ما إذا كانت Response جاءت من Process stdout أو HTTP SSE.

## 16. احتياجات Server-to-Client الحديثة: input_required وSubscriptions

تغير MCP الحديثة كيفية حصول Server على معلومات إضافية أثناء Operation.

### Server يحتاج Input إضافية

بدلًا من بدء Unsolicited request جديدة تمامًا عبر Permanent reverse channel، يستطيع Server إعادة Result تشير إلى `input_required`. يجمع Client الـ Input المطلوبة أويوفرها ثم يرسل Request جديدة.

```text
Client POST request
      ↓
Server result: input_required
      ↓
Client يحصل على Information المطلوبة
      ↓
Client يرسل Follow-up POST
      ↓
Server يكمل Operation
```

### Long-lived notifications تظل Opt-in

يحدد المصدر Long-lived modern stream مقصودة واحدة: يمكن لـ Client استدعاء `subscriptions/listen`، ويمكن لـ Server إبقاء SSE response الخاصة بتلك Request مفتوحة لإرسال Subscribed change notifications.

وهذا مختلف تمامًا عن التصميم القديم حيث كان كل Initialized client يفتح Broad GET stream لرسائل Server غير المطلوبة.

[[IMAGE_NEEDED: Modern input_required versus subscriptions/listen | Two side-by-side sequences: one showing input_required then a client follow-up POST, and one showing an explicitly requested subscriptions/listen POST whose SSE response stays open for change events | Learner should notice that both preserve client initiation]]

## 17. Legacy HTTP SSE ولماذا تم استبدالها

قبل Streamable HTTP، استخدم MCP Remote HTTP/SSE transport ذات Long-lived event stream.

يحدد المصدر عدة مشكلات.

### Endpointان

استخدمت Requests وServer responses Endpoints/Paths مختلفة، مما زاد تعقيد Implementation وCorrelation.

### الاتصالات طويلة العمر (Long-lived connections)

تكون Permanent SSE connections غير مريحة ومكلفة لـ Serverless infrastructure وScaling-to-zero environments.

### عمر Authentication

يمكن أن تجعل Long-lived sessions إعادة التحقق من Credentials في كل Operation أكثر صعوبة.

### ضعف Resumability

قد تؤدي SSE connections المنقطعة إلى فقد In-flight responses.

يذكر المصدر أن HTTP SSE تم Deprecate لها لصالح Streamable HTTP ابتداءً من Protocol revision بتاريخ 2025-03-26، مع احتمال احتفاظ SDKs بمسارات Compatibility للأنظمة الأقدم.

## 18. بناء Custom transport

لا يفرض MCP عليك استخدام Standard transports فقط. قد تبرر Specialized environment استخدام gRPC أو WebSocket أو Compliance-specific channel أو Communication mechanism أخرى.

في Python SDK، يكون Custom transport contract ضمنيًا إلى حد كبير: تتوقع Session زوجًا من Memory-stream endpoints بسلوك محدد.

### Pattern عامة لـ Custom transport

```text
1. أنشئ Read stream pair:
      Transport تملك read_stream_writer
      Session تستقبل read_stream

2. أنشئ Write stream pair:
      Session تستقبل write_stream
      Transport تملك write_stream_reader

3. أنشئ Underlying connection.

4. شغّل Read task:
      Wire → Deframe → Deserialize → SessionMessage → read_stream_writer

5. شغّل Write task:
      write_stream_reader → Serialize → Frame → Wire

6. سلّم read_stream + write_stream إلى Session.

7. داخل finally:
      أغلق Wire connection
      ألغِ Task group
      أغلق Memory streams
```

يحافظ هذا التصميم على أهم خاصية معمارية في الفصل: **تظل Sessions غير معتمدة على Transport**.

## 19. Security على مستوى Transport تعتمد على نوع Transport

لا توجد Threat model واحدة لكل MCP transports. تعيش stdio وStreamable HTTP في بيئات مختلفة.

### Threat model الخاصة بـ stdio

ينفذ Client ملف Server binary/Process محليًا. إذا كانت هذه Process ضارة أومخترقة، فإنها تعمل بأي Privileges/Environment يمنحها Host لها.

Themes الخاصة بالMitigation في المصدر هي:

- تثبيت Servers موثوقة فقط،
- Pin للإصدارات،
- التشغيل بأقل Privilege،
- Sandbox/Containerize عند الملاءمة،
- تجنب إعطاء Server كامل Environment المليئة بالـ Secrets الخاصة بـ Host،
- تمرير Secrets/Variables التي يحتاج إليها Server فقط.

### Threat model الخاصة بـ Streamable HTTP

يعبر Connection حدود Network.

يركز المصدر على:

- TLS في Production،
- Authentication في كل Stateless request،
- توخي الحذر في Compatibility behavior إذا كانت Legacy session IDs ما تزال مقبولة،
- Localhost binding للـ Local HTTP deployments،
- Origin validation لتقليل DNS-rebinding-style attacks.

### Statelessness تغير بعض المخاطر

لا تحتوي Streamable HTTP الحديثة Stateless على Durable MCP session ID يمكن Hijack أو Fixate لها. أما Legacy-compatible stateful behavior فتحتفظ بمخاطر إضافية مرتبطة بـ Session management.

[[IMAGE_NEEDED: stdio versus HTTP transport threat models | Two panels: stdio risks centered on local process privileges/environment/secrets, Streamable HTTP risks centered on network interception/authentication/origin exposure | Learner should notice that transport choice changes which security controls matter most]]

## 20. اختيار Transport المناسبة

يقارن المصدر بين Standard transports من حيث Deployment وAuthentication وLatency وScalability.

| الاعتبار | stdio | Streamable HTTP |
|---|---|---|
| Local server | مناسبة جدًا | ممكنة أيضًا |
| خادم بعيد أو شبكي (Remote/Network server) | غير مناسبة | مصممة لهذا |
| Trust/Authentication | حدود العملية المحلية (Local process boundary) | Network authentication مثل OAuth/API keys |
| Latency | منخفضة جدًا عبر Local pipes | تعتمد على Network |
| Horizontal scale | Server process واحدة لكل Client | مناسبة طبيعيًا لـ Stateless load-balanced deployments |
| الاستخدام المعتاد | أدوات محلية وتطوير ومشاريع شخصية (Local tools/Development/Personal projects) | خدمات بعيدة للإنتاج والمؤسسات (Production/Enterprise remote services) |

### Decision tree عملية

```text
هل يحتاج Server إلى العمل Remote؟
    ├── نعم → Streamable HTTP (أو Custom transport مبررة)
    └── لا
         ↓
هل هي Local user-installed/developer tool؟
    ├── نعم → stdio غالبًا الأبسط
    └── ربما → يمكن أن تكون HTTP مفيدة أيضًا لـ Local network/container workflows
```

بالنسبة إلى Production remote deployment، يفضل المصدر بشدة Streamable HTTP على Legacy SSE أو stdio.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: «Transport هي التي تحدد معنى tools/call request.»

**لماذا هذا خطأ:** تفهم Protocol/Session layer دلالات MCP؛ أما Transport فتنقل Messages بعد Framing/Serialization.

### المفهوم الخاطئ 2: «Request IDs مجرد Logging metadata.»

**لماذا هذا خطأ:** IDs أساسية لربط Concurrent responses بالـ Requests التي أنشأتها.

### المفهوم الخاطئ 3: «Tool exception تصبح دائمًا JSON-RPC error response.»

**لماذا هذا خطأ:** يميز المصدر بين Application errors التي يمكن إعادتها كـ Normal result messages مع `isError=true` وبين Protocol-level JSON-RPC errors.

### المفهوم الخاطئ 4: «Notifications تحتاج Acknowledgment responses.»

**لماذا هذا خطأ:** Notifications أحادية الاتجاه عمدًا، ولذلك لا تحمل Request ID.

### المفهوم الخاطئ 5: «Base64 بلا تكلفة.»

**لماذا هذا خطأ:** تزيد Base64 حجم Payload بنحو الثلث، ولذلك لا تناسب Large blobs جيدًا.

### المفهوم الخاطئ 6: «يجب أن تعرف ClientSession ما إذا كانت Message تستخدم stdio أو HTTP.»

**لماذا هذا خطأ:** تتفاعل Session عبر Abstract read/write streams، لذلك تبقى تفاصيل Transport مخفية.

### المفهوم الخاطئ 7: «يمكن لـ stdio استخدام stdout بأمان لرسائل Debug.»

**لماذا هذا خطأ:** تحمل stdout رسائل JSON-RPC التي تم Framing لها؛ ويمكن لأي Output غير مرتبطة أن تفسد Wire stream.

### المفهوم الخاطئ 8: «Streamable HTTP الحديثة هي Permanent SSE connection واحدة.»

**لماذا هذا خطأ:** كل Client message هي POST exchange مستقلة؛ وقد تحصل Request على JSON أو Ephemeral SSE response stream.

### المفهوم الخاطئ 9: «HTTP SSE القديمة وSSE responses داخل Streamable HTTP هما Architecture نفسها.»

**لماذا هذا خطأ:** اعتمدت SSE القديمة على Long-lived transport connection؛ بينما قد تستخدم Streamable HTTP الحديثة SSE فقط كـ Response body لـ Request محددة أو Explicit subscription.

### المفهوم الخاطئ 10: «Custom transport تتطلب إعادة كتابة ClientSession.»

**لماذا هذا خطأ:** إذا أوفت Transport بعقد Streams الخاص بالـ SDK، يمكن أن تظل Session layer الحالية دون تغيير.

### المفهوم الخاطئ 11: «Local HTTP server مرتبطة بكل Interfaces تعادل stdio من حيث Security.»

**لماذا هذا خطأ:** بمجرد كشف HTTP، تصبح مخاطر Network origin وDNS rebinding ذات صلة حتى لو كان Service مقصودًا للاستخدام Local فقط.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Transport | Layer تنقل JSON-RPC messages بعد Serialization/Framing بين MCP peers |
| JSON-RPC | Lightweight RPC message format تُستخدم كأساس Message/Data في MCP |
| Request | Message تحمل ID وتستدعي Method وتتوقع Response |
| Result response | JSON-RPC response ناجحة مرتبطة بواسطة Request ID |
| Error response | JSON-RPC response تصف Failure على مستوى Protocol |
| Notification | One-way JSON-RPC message بلا Request ID |
| `isError` result | Application-level failure مشفرة داخل Normal result message |
| `structuredContent` | Machine-readable JSON object يُعاد إلى جانب Tool content |
| `input_required` | Result state تشير إلى أن Client input إضافية مطلوبة قبل Completion |
| Progress token | Correlation token تُستخدم لتوجيه Progress notifications الخاصة بعملية واحدة |
| ResourceLink | Metadata/URI reference إلى Data يمكن تحميلها لاحقًا بدل تضمينها مباشرة |
| Base64 | Text encoding لنقل Binary content داخل JSON مع زيادة في الحجم تقارب 33% |
| `ClientSession` | Client-side SDK abstraction فوق Transport |
| `ServerSession` | Server-side/Request communication abstraction فوق Transport |
| Dispatcher | Component توجه Messages وتدير حالة Pending/In-flight requests |
| Pending request | Outbound request تنتظر Response/Error تحمل ID مطابقة |
| In-flight request | Request يجري تنفيذها حاليًا ويمكن إلغاؤها |
| Cancel scope | AnyIO construct تُستخدم لإلغاء Running request task واحدة |
| Framing | تحديد أين تنتهي Message وتبدأ أخرى داخل Byte/Message stream |
| stdio | Local transport تستخدم Subprocess stdin/stdout وNewline-delimited JSON-RPC |
| Streamable HTTP | Modern remote transport تستخدم Independent POST requests مع JSON أو Per-request SSE responses |
| SSE | Server-Sent Events؛ Streaming HTTP event format مستخدمة في Legacy transport وPer-request streaming responses |
| `subscriptions/listen` | Explicit modern operation يمكن أن تُبقي Response stream مفتوحة لـ Subscribed change events |
| Custom transport | Nonstandard transport تنفذ Session-facing contract الخاصة بالـ SDK |
| TLS | Transport Layer Security لحماية Network HTTP communication |
| DNS rebinding | Browser/Network attack ذات صلة بخدمات Local HTTP المكشوفة بصورة غير صحيحة |
