- شرح Kubernetes بوصفه منصة إدارة على مستوى الـ cluster.
- التمييز بين دوري الـ control plane والـ Nodes.
- شرح لماذا تُعدّ الـ Pods أصغر وحدة قابلة للنشر (deployable) في Kubernetes.
- وصف كيف تحافظ الـ Deployments على الحالة المطلوبة عبر المطابقة (reconciliation).
- شرح لماذا تلزم الـ Services عندما تكون الـ Pods مؤقتة.
- تثبيت `kubectl` وminikube واستخدامهما في سير عمل cluster محلي.
- قراءة Deployment manifest وشرحه.
- قراءة Service manifest وشرحه.
- استخدام labels وselectors لربط الـ Services بالـ Pods.
- شرح `port` و`targetPort` و`NodePort`.
- تطبيق الـ manifests بشكل تصريحي باستخدام `kubectl apply`.
- فحص الـ Deployments والـ Pods والـ Services.
- توسيع Deployment مباشرةً.
- شرح التحديثات المتدرجة (rolling updates) والتراجع (rollback) في Kubernetes.
- وصف مسار الحركة من NodePort إلى Service إلى Pod.
- شرح غرض ConfigMaps وSecrets والـ probes وطلبات/حدود الموارد بوصفها امتدادات موجهة للإنتاج يقدّمها المصدر.
- شرح لماذا يصبح Helm مفيدًا مع نمو إعدادات تطبيقات Kubernetes.
- التمييز بين Helm Charts والـ repositories والـ releases والـ templates وملف `values.yaml`.

## 1. لماذا يصبح الـ orchestration ضروريًا

يحل Docker مشكلة كبرى:

> حزّم تطبيقًا واعتمادياته في container قابل للنقل.

وهذا قوي عندما يكون لديك container واحد.

لكن أنظمة الإنتاج تنمو عادةً إلى ما هو أبعد من ذلك.

تخيّل منصة تجارة إلكترونية فيها:

```text
frontend
API المستخدمين
API المنتجات
خدمة الدفع
قاعدة البيانات
cache
عمّال الخلفية (background workers)
وكلاء المراقبة
```

والآن تخيّل عدة نسخ (replicas) من كلٍّ منها.

لم تعد المشكلة:

> "هل أستطيع بدء container؟"

بل أصبحت المشكلة:

> **"كيف أُبقي كثيرًا من الـ containers سليمة ومتصلة وقابلة للتوسع ومحدَّثة مع الزمن؟"**

يصف المصدر هذا بأنه **مشكلة اليوم الثاني (Day 2 problem)**.

اليوم الأول:

```text
شغّل التطبيق.
```

اليوم الثاني:

```text
أبقِه يعمل بموثوقية.
وسّعه.
حدّثه.
تعافَ من الإخفاقات.
اربط الخدمات.
```

### أربع مشكلات تشغيلية رئيسية

يصوغ الفصل الـ orchestration عبر أربعة أسئلة عملية.

### المرونة (Resilience)

ماذا يحدث إذا:

- انهار container،
- فشل خادم،
- أصبحت عملية غير سليمة؟

بدون orchestration، قد يحتاج شخص ما إلى ملاحظة ذلك وإعادة تشغيل أحمال العمل يدويًا.

وعلى نطاق الإنتاج، هذا غير مقبول.

### قابلية التوسع (Scalability)

افترض أن الحركة ارتفعت فجأة.

قد تحتاج إلى:

```text
2 containers    # حاويتان
→ 10 containers
→ 30 containers
```

ثم، عندما ينخفض الطلب:

```text
30
→ 5
```

القيام بذلك يدويًا بطيء ومكلف.

### الشبكات (Networking)

الـ containers ديناميكية.

وقد تتغير العناوين عند إعادة تشغيل النسخ.

تثبيت:

```text
10.0.0.23
```

داخل خدمة أخرى هش.

وتحتاج التطبيقات إلى اكتشاف خدمات (service discovery) مستقر.

### التحديثات (Updates)

تتغير برمجيات الإنتاج باستمرار.

وتحتاج إلى الإجابة عن:

- كيف أنشر image جديدة دون توقف؟
- كيف أستبدل الـ containers تدريجيًا؟
- كيف أتراجع إذا كانت النسخة الجديدة سيئة؟

### الـ Container orchestration

**منسّق الـ containers (container orchestrator)** يؤتمت هذه الاهتمامات التشغيلية.

ويعرّف المصدر Kubernetes بأنه منصة الـ orchestration المهيمنة لهذه المهمة.

نموذج ذهني مفيد:

```text
Docker
= حزّم وشغّل container

Kubernetes
= نسّق عددًا كبيرًا من الـ containers عبر cluster
```

## 2. Kubernetes بوصفه منصة تشغيل للـ cluster

**Kubernetes**، ويُختصر عادةً **K8s**، منصة orchestration مفتوحة المصدر صمّمتها Google أصلًا وتُصان ضمن منظومة Cloud Native Computing Foundation.

ويستخدم المصدر تشبيهًا قويًا:

> Kubernetes أشبه بنظام تشغيل لمركز بيانات أو cluster.

يدير نظام التشغيل العادي الموارد على جهاز واحد:

```text
CPU
memory
التخزين
العمليات (processes)
```

أما Kubernetes فيدير الموارد عبر أجهزة كثيرة.

وبدلًا من التفكير:

```text
"شغّل هذا على server-2."
```

تصف:

```text
"أحتاج إلى خمس نسخ من هذا التطبيق."
```

ثم يقرر Kubernetes أين يضعها.

### التحكم التصريحي

أنت تخبر Kubernetes بما تريد.

مثال:

```text
الحالة المطلوبة (Desired state):
5 replicas لتطبيق الويب
```

يعمل Kubernetes باستمرار نحو تلك الحالة.

وهذا يشبه النموذج الذهني التصريحي في Terraform من الدرس السابق.

أنت تعلن:

```text
ما ينبغي أن يوجد
```

ويتولى نظام التحكم:

```text
كيف نوفّق الواقع مع ذلك الإعلان
```

### القدرات التي يبرزها المصدر

#### الإصلاح الذاتي (Self-healing)

إذا فشل حمل عمل، يستطيع Kubernetes استبداله.

وإذا أصبح Node غير متاح، يمكن إعادة جدولة أحمال العمل.

#### التوسع الأفقي (Horizontal scaling)

تستطيع زيادة عدد الـ replicas أو إنقاصه.

ويشير المصدر أيضًا إلى التوسع التلقائي بحسب مقاييس مثل استخدام CPU.

#### اكتشاف الخدمات وموازنة الحمل

يمنح Kubernetes التطبيقات أسماء ثابتة ويستطيع توزيع الحركة عبر الـ replicas.

#### الطرح والتراجع الآليان (Automated rollouts and rollbacks)

يمكن إدخال النسخ الجديدة تدريجيًا.

وإذا حدث خطأ، يمكن استعادة نسخة سابقة.

#### إدارة الأسرار والإعدادات

يقدّم المصدر آليات في Kubernetes لإبقاء الإعدادات والقيم الحساسة منفصلة عن image التطبيق.

### فكرة Kubernetes الأساسية

```text
أنت تعلن حالة التطبيق المطلوبة.
Kubernetes يحاول باستمرار جعل الحالة الفعلية تطابقها.
```

ستفسّر هذه الجملة كثيرًا من سلوكيات Kubernetes لاحقًا في الدرس.

## 3. معمارية الـ cluster: الـ control plane والـ Nodes

تسمى بيئة Kubernetes العاملة **cluster**.

ويصف المصدر الـ cluster بأنه مجموعة من الحواسيب المتصلة بالشبكة تسمى **Nodes**.

### الـ Nodes

**الـ Node** هو جهاز عامل (worker).

ويمكن أن يكون:

- جهازًا افتراضيًا سحابيًا،
- خادمًا ماديًا،
- تجريدًا لجهاز محلي في cluster تطوير.

الـ Nodes هي حيث تعمل أحمال التطبيق.

فكّر:

```text
Node = عامل (worker)
```

### الـ Control plane

**الـ control plane** هو العقل الإداري.

وهو مسؤول عن الحالة المطلوبة للـ cluster والقرارات العامة.

ويبرز المصدر مسؤوليات مثل:

- جدولة أحمال العمل،
- مراقبة حالة الـ cluster،
- الاستجابة للأحداث.

فكّر:

```text
Control plane = مدير (manager)
Nodes         = عمّال (workers)
```

### معمارية مبسّطة

```text
                Kubernetes API
                     |
                     v
               Control Plane
                     |
        -----------------------------
        |             |             |
        v             v             v
      Node 1        Node 2        Node 3
        |             |             |
        أحمال          أحمال          أحمال
        التطبيق        التطبيق        التطبيق
```

تتعامل عادةً عبر Kubernetes API باستخدام:

⟦CODE_0⟧

بدلًا من تعيين العمل يدويًا إلى كل Node على حدة.

## 4. الـ Pods: أصغر وحدة قابلة للنشر في Kubernetes

يعلّمك Docker أن تفكّر بالـ containers.

ويضيف Kubernetes تجريدًا آخر:

> **Pod**

**الـ Pod** أصغر كائن قابل للنشر في Kubernetes.

يدير Kubernetes عادةً الـ Pods لا الـ containers الفردية مباشرةً.

### ما الموجود داخل Pod؟

يستطيع الـ Pod أن يحتوي:

```text
حاوية واحدة
```

أو:

```text
عدة حاويات مترابطة بإحكام
```

ومعظم Pods التطبيقات للمبتدئين تحتوي container تطبيق رئيسيًا واحدًا.

### لماذا يوجد غلاف Pod؟

يشرح المصدر أن الـ containers داخل Pod واحد:

- تعمل على الـ Node نفسه،
- تتشارك network namespace،
- تستطيع التواصل عبر `localhost`،
- تستطيع مشاركة volumes التخزين.

وهذا مفيد للـ containers المترابطة بإحكام.

مثلًا:

```text
Pod
├── container التطبيق الرئيسي
└── container جانبي (sidecar) للتسجيل
```

### عمر الـ Pod

مفهوم حاسم:

> الـ Pods مؤقتة (ephemeral).

يمكن أن:

- تُنشأ،
- تُدمَّر،
- تُستبدل.

لذلك فإن عناوين IP الخاصة بها ليست مستقرة بما يكفي لتُستخدم نقاط نهاية طويلة الأمد للتطبيقات.

### لا تدر Pods التطبيقات مباشرةً

يؤكد المصدر:

> تكاد لا تنشئ Pods مباشرةً في إدارة التطبيقات العادية.

بل استخدم متحكمًا أعلى مستوى مثل **Deployment**.

يُنشئ ذلك المتحكم الـ Pods ويستبدلها نيابةً عنك.

## 5. الـ Deployments وحلقة المطابقة

**الـ Deployment** يدير مجموعة مطلوبة من Pods التطبيق.

افترض أنك أعلنت:

```text
replicas = 3    # عدد النسخ
```

الحالة المطلوبة هي:

```text
3 من الـ Pods
```

لكن الـ cluster فيه الآن:

```text
0 من الـ Pods
```

يلاحظ Kubernetes:

```text
المطلوب (desired) = 3
الفعلي (actual)  = 0
```

وينشئ ثلاث Pods.

الآن افترض أن Pod انهار.

تصبح الحالة الفعلية:

```text
2
```

وتبقى الحالة المطلوبة:

```text
3
```

ينشئ متحكم الـ Deployment Pod آخر.

هذه المقارنة المستمرة هي **حلقة المطابقة (reconciliation loop)**.

### نموذج ذهني للمطابقة

```text
الحالة المطلوبة
    3 من الـ Pods
      |
      v
مقارنة
      |
      v
الحالة الفعلية
    2 من الـ Pods
      |
      v
الفرق
   ينقص 1
      |
      v
إنشاء بديل
```

[[IMAGE_NEEDED: Kubernetes reconciliation loop | A circular diagram showing desired state = 3 Pods, actual state = 2 Pods, controller detects difference, creates replacement Pod, actual state returns to 3 | Learner should notice that self-healing comes from continuous desired-vs-actual reconciliation]]

### تقدّم الـ Deployments أكثر من التكرار (replication)

ويقدّم المصدر أيضًا الـ Deployments بوصفها الكائن المستخدم لـ:

- التحديثات المتدرجة،
- الحفاظ على التوفر،
- استبدال الـ Pods الفاشلة.

إذن الـ Deployment ليس مجرد:

> "أنشئ ثلاث Pods"

بل هو:

> **أدِر باستمرار حالة Pods التطبيق المعلنة.**

## 6. الـ Services: شبكات مستقرة لـ Pods غير مستقرة

الـ Pods قابلة للاستبدال.

وعناوينها غير مستقرة.

لذلك لا ينبغي أن يعتمد تطبيق آخر مباشرةً على IP لـ Pod واحد.

وهذا ما تحله **الـ Service**.

### نقطة نهاية مستقرة

توفّر الـ Service تجريدًا شبكيًا مستقرًا فوق مجموعة منطقية من الـ Pods.

فكّر:

```text
العميل
  |
  v
Service
  |
  +--> Pod A
  +--> Pod B
  +--> Pod C
```

يتواصل العميل مع الـ Service.

وتوجّه الـ Service الحركة إلى الـ Pods السليمة المطابقة.

### الـ Labels والـ selectors

كيف تعرف الـ Service أي Pods تنتمي إليها؟

باستخدام **الـ labels**.

مثال على label لـ Pod:

⟦CODE_1⟧

مثال على selector لـ Service:

⟦CODE_2⟧

وهذا ينشئ الاتصال.

### تشبيه مكتب الاستقبال

يقارن المصدر الـ Service بمكتب الاستقبال في شركة.

لا تحتاج إلى معرفة التحويلة المتغيرة لكل موظف.

تتصل برقم واحد ثابت.

ويوجّهك مكتب الاستقبال إلى شخص متاح.

وفي Kubernetes:

```text
Service = مكتب استقبال ثابت
Pods    = عمّال قابلون للاستبدال
```

### لماذا يهمّ هذا الفصل

يمكن للـ Pods أن:

- تُعاد تشغيلها،
- تُستبدل،
- تتوسع زيادةً،
- تتوسع نقصانًا.

وتبقى الـ Service طبقة الشبكة المستقرة.

## 11. Helm: تحزيم تطبيقات Kubernetes

يمكن إدارة ملفي YAML.

لكن التطبيق الحقيقي قد يحتاج إلى:

```text
Deployment
Service
ConfigMap
Secret
Ingress
PersistentVolume
سياسات الموارد (resource policies)
إعدادات خاصة بكل بيئة
```

والآن تخيّل:

```text
dev    # البيئات
staging
production
```

قد تصبح إدارة ملفات YAML منفصلة كثيرة متكررة وعرضة للأخطاء.

وهذه المشكلة التي يقدّم المصدر **Helm** لحلها.

### Helm بوصفه مدير حزم

يسمّي المصدر Helm:

> "مدير الحزم لـ Kubernetes."

والتشبيه:

```text
apt / brew
→ حزم نظام التشغيل

Helm
→ حزم تطبيقات Kubernetes
```

### مفاهيم Helm الأساسية

### الـ Chart

**الـ Chart** مجموعة محزَّمة من قوالب موارد Kubernetes والملفات الداعمة.

وبدلًا من ملفات YAML متفرقة:

```text
deployment.yml
service.yml
configmap.yml
secret.yml
```

تستطيع إدارتها بوصفها chart واحدًا.

### الـ Repository

يخزّن **repository** في Helm الـ Charts ويوزّعها.

وهو يشبه في غرضه مستودعات حزم البرمجيات.

### الـ Release

**الـ release** هو نسخة واحدة مثبّتة من Chart في cluster.

ويمكن تثبيت الـ Chart نفسه عدة مرات بأسماء release أو إعدادات مختلفة.

### القوالب (Templates) و`values.yaml`

وهنا يصبح Helm مفيدًا بشكل خاص.

يمكن أن يحتوي YAML الخاص بـ Kubernetes داخل Chart على قوالب.

وتعيش الإعدادات في:

```text
values.yaml
```

مثلًا:

```text
عدد الـ replicas
وسم الـ image
حدود الموارد
إعدادات البيئة
```

يجمع Helm بين:

```text
القوالب (templates)
+
القيم (values)
```

لتوليد manifests Kubernetes النهائية.

[[IMAGE_NEEDED: Helm chart templating model | A diagram showing Helm Chart templates + values.yaml → Helm render/install → generated Deployment, Service, ConfigMap, and other Kubernetes resources → Kubernetes cluster | Learner should notice that the same templates can be reused with different environment-specific values]]

### إعادة الاستخدام عبر البيئات

يمكن مفاهيميًا اقتران الـ Chart نفسه بـ:

```text
values-dev.yaml    # ملفات القيم
values-staging.yaml
values-prod.yaml
```

وهذا يقلّل التكرار.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1

> "Kubernetes يحل محل Docker."

### لماذا هذا خاطئ

أدوات Docker/الـ containers تحزّم الـ containers وتشغّلها.

أما Kubernetes فينسّق أحمال العمل المحزَّمة في containers عبر cluster.

وهما يحلان طبقتين مختلفتين من المشكلة.

---

### المفهوم الخاطئ 2

> "Kubernetes موجود أساسًا لبدء الـ containers."

### لماذا هذا ناقص

يؤكد المصدر عمليات اليوم الثاني:

- الإصلاح الذاتي،
- التوسع،
- الشبكات،
- الطرح (rollouts)،
- التراجع،
- الإعدادات.

---

### المفهوم الخاطئ 3

> "الـ Pod هو الشيء نفسه تمامًا كـ container."

### لماذا هذا خاطئ

الـ Pod هو الغلاف القابل للنشر في Kubernetes حول container واحد أو أكثر، ويوفّر سياق شبكة وتخزين مشتركًا.

---

### المفهوم الخاطئ 4

> "ينبغي أن أنشئ Pods التطبيقات مباشرةً عادةً."

### لماذا هذا خاطئ

يوصي المصدر باستخدام كائنات أعلى مستوى مثل الـ Deployments لإدارة الـ Pods.

---

### المفهوم الخاطئ 5

> "إذا انهار Pod فقد فشل الـ Deployment نفسه."

### لماذا هذا خاطئ

يطابق الـ Deployment باستمرار الحالة الفعلية مع عدد الـ replicas المطلوب ويستطيع إنشاء Pods بديلة.

---

### المفهوم الخاطئ 6

> "ينبغي أن تتصل التطبيقات مباشرةً بعناوين IP الخاصة بالـ Pods."

### لماذا هذا خاطئ

عناوين الـ Pods مؤقتة.

وتوفّر الـ Services عنونة مستقرة وتوزيعًا للحركة.

---

### المفهوم الخاطئ 7

> "الـ selector في Service وlabels في Deployment لا علاقة بينهما."

### لماذا هذا خاطئ

تنشئ الـ selectors والـ labels العلاقة بين الـ Services والـ Pods والمتحكمات.

وإذا لم تتطابق، فقد تفشل الحركة أو الإدارة.

---

### المفهوم الخاطئ 8

> "`port: 80` و`targetPort: 8080` يصفان نقطة النهاية نفسها."

### لماذا هذا خاطئ

`port` هو المنفذ المواجه للـ Service.

و`targetPort` هو المكان الذي يستقبل فيه التطبيق الحركة داخل الـ Pods المختارة.

---

### المفهوم الخاطئ 9

> "Helm بيئة تشغيل container أخرى."

### لماذا هذا خاطئ

يحزّم Helm تعريفات موارد Kubernetes ويحوّلها إلى قوالب.

وهو لا يحل محل بيئة التشغيل.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Container orchestration | إدارة آلية لـ deployment التطبيقات المحزَّمة في containers وتوسعها وشبكاتها ودورة حياتها |
| مشكلة اليوم الثاني (Day 2 problem) | تشغيل تطبيق بموثوقية بعد الـ deployment الأولي |
| Kubernetes / K8s | منصة container orchestration التي قُدّمت في الفصل |
| Cluster | بيئة Kubernetes تتألف من وظائف الـ control plane والـ Nodes |
| Node | جهاز عامل يشغّل أحمال التطبيق |
| Control plane | طبقة إدارية تحافظ على الحالة المطلوبة للـ cluster وتجدول العمل |
| Pod | أصغر كائن قابل للنشر في Kubernetes؛ يحتوي container واحدًا أو أكثر |
| Deployment | كائن أعلى مستوى يدير Pods مكرَّرة وحالة التطبيق المطلوبة |
| حلقة المطابقة (Reconciliation loop) | مقارنة مستمرة بين الحالتين المطلوبة والفعلية يتبعها إجراء تصحيحي |
| Service | تجريد شبكي مستقر فوق مجموعة مختارة من Pods |
| Label | بيانات وصفية بصيغة مفتاح-قيمة تُرفق بكائنات Kubernetes |
| Selector | قاعدة تُستخدم لتحديد الكائنات بحسب الـ labels |
| `kubectl` | عميل سطر الأوامر لـ Kubernetes |
| minikube | أداة cluster محلي لـ Kubernetes مستخدمة في الدرس |
| Manifest | تعريف تصريحي بصيغة YAML لمورد Kubernetes |
| Replica | نسخة واحدة مُدارة من قالب Pod |
| NodePort | نوع Service يكشف الـ Service عبر منفذ على كل Node |
| LoadBalancer | نوع Service يُستخدم عادةً في البيئات السحابية لتوفير موازنة حمل خارجية |
| التحديث المتدرج (Rolling update) | استبدال تدريجي للـ Pods القديمة بنسخة جديدة |
| التراجع (Rollback) | العودة إلى مراجعة سابقة من الـ Deployment |
| ConfigMap | كائن Kubernetes يُستخدم للإعدادات غير السرية |
| Secret | كائن Kubernetes يُستخدم للإعدادات الحساسة |
| Liveness probe | فحص صحة يساعد على تحديد هل ينبغي إعادة تشغيل container |
| Readiness probe | فحص يحدّد هل ينبغي أن يتلقى Pod حركة |
| Helm | مدير حزم Kubernetes الذي قدّمه المصدر |
| Chart | حزمة Helm تحتوي قوالب وملفات ذات صلة |
| مستودع Helm (Helm repository) | موقع توزيع للـ Charts |
| Release | نسخة مثبّتة من Helm Chart |
| `values.yaml` | قيم إعداد Helm المستخدمة لتوليد القوالب |
