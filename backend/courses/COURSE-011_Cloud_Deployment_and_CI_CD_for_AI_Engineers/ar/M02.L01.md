## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح Git بوصفه نظام تحكم بالإصدارات موزَّعًا قائمًا على اللقطات (snapshots).
- التمييز بين مجلد العمل (working directory) ومنطقة التجهيز (staging area) والمستودع المحلي.
- استخدام `git status` و`git add` و`git commit` لإنشاء تاريخ مشروع مركّز.
- شرح غرض `git diff` و`git log` قبل مشاركة التغييرات.
- التمييز بين المستودعات المحلية والمستودعات البعيدة.
- شرح ما يفعله `git push` و`git pull` و`git fetch`.
- وصف لماذا تتيح الفروع للفرق العمل بأمان على التوازي.
- شرح الفروع main وdevelop وfeature وrelease وhotfix المستخدمة في GitFlow.
- استنساخ مستودع GitHub وإنشاء فرع ميزة.
- دفع فرع ميزة إلى GitHub وفتح pull request.
- شرح لماذا تحسّن مراجعة الشيفرة الجودة وتبادل المعرفة والاتساق.
- حل تعارض دمج أساسي بقراءة علامات التعارض في Git واختيار المحتوى النهائي المقصود.
- تطبيق قائمة تحقق احترافية لـ Git تقلّل أخطاء التعاون الشائعة.

## 1. Git نظام تاريخ، لا مجرد زر حفظ

المجلد العادي يتذكّر حالته الحالية فقط.

فإذا عدّلت `index.html` وحفظته وأغلقت المحرر، يعطيك نظام التشغيل أحدث ملف. وما لم تنشئ نسخًا احتياطية يدويًا، فإنه لا يوفّر بطبيعته قصة منظّمة عن كيفية تطوّر ذلك الملف.

يضيف Git هذا التاريخ.

تعريف مفيد للمبتدئين:

> **Git نظام تحكم بالإصدارات موزَّع يسجّل لقطات ذات معنى لحالة المشروع عبر الزمن.**

وهذا مهم لأن البرمجيات في تغيّر مستمر.

وقد يحتاج الفريق إلى الإجابة عن:

- من غيّر هذا السطر؟
- لماذا عُدّل هذا الملف؟
- أي إصدار أدخل الخطأ؟
- كيف كان المشروع يبدو الأسبوع الماضي؟
- هل نستطيع التجريب بأمان دون إتلاف النسخة المستقرة؟
- كيف يدمج عدة مطوّرين أعمالهم؟

يوفّر Git طريقة منظّمة للإجابة عن هذه الأسئلة.

### يفكّر Git باللقطات

يؤكد المصدر أن النموذج الذهني لـ Git أقرب إلى تسلسل من اللقطات منه إلى قائمة بسيطة من تعديلات الملفات المستقلة.

تخيّل مشروعًا صغيرًا:

```text
اللقطة A
README.md
index.html

        ↓ commit جديد

اللقطة B
README.md
index.html
style.css

        ↓ commit جديد

اللقطة C
README.md
index.html
style.css
app.js
```

يحدّد كل commit حالة مشروع ذات معنى.

وهذا **لا** يعني أن Git ينسخ المجلد كله نسخًا أعمى وغير فعّال في كل مرة. الفكرة المهمة الموجهة للمتعلّم هي أن Git يتيح لك التفكير في كل commit على أنه لقطة للمشروع.

### التاريخ المحلي مفيد أصلًا

لا تحتاج إلى GitHub حتى يعمل Git.

فالمستودع المحلي في Git يستطيع أصلًا:

- تسجيل الـ commits،
- إنشاء الفروع،
- فحص التاريخ،
- مقارنة الإصدارات،
- دمج الأعمال.

وتصبح GitHub مهمة عندما تريد مستودعًا بعيدًا مستضافًا وميزات تعاون مثل pull requests ومراجعة الشيفرة.

وسيهمّ هذا التمييز طوال الدرس:

```text
Git    = نظام تحكم بالإصدارات
GitHub = منصة تعاون مستضافة مبنية حول مستودعات Git
```

## 2. الأشجار الثلاث: كيف تنتقل التغييرات عبر Git

من أهم مفاهيم Git أن عملك يوجد في ثلاث مناطق رئيسية.

وتسمى غالبًا **الأشجار الثلاث (three trees)** في Git:

1. مجلد العمل (Working Directory)
2. منطقة التجهيز (Staging Area)
3. المستودع (Repository)

### 2.1 مجلد العمل (Working Directory)

**مجلد العمل (working directory)** هو مجلد المشروع الذي تحرّره فعليًا.

افترض أن مشروعك يحتوي على:

```text
my-project/    # مجلد المشروع
├── README.md
├── index.html
└── style.css
```

عندما تفتح `index.html` في VS Code وتغيّر عنوانًا، يوجد هذا التعديل في مجلد العمل.

في هذه المرحلة يستطيع Git اكتشاف التغيير، لكن التغيير ليس بعدُ جزءًا من اللقطة التالية المُودَعة.

فكّر:

> **مجلد العمل = ما أحرّره حاليًا.**

### 2.2 منطقة التجهيز (Staging Area)

تتيح **منطقة التجهيز (staging area)**، وتسمى أيضًا **الفهرس (index)**، اختيار ما يجب أن يدخل في الـ commit التالي بالضبط.

وهذه من أكثر ميزات Git فائدة.

افترض أنك غيّرت ملفين:

```text
index.html  -> ميزة مكتملة
style.css   -> تجربة غير مكتملة
```

لا يجب أن تودِع الاثنين.

يمكنك تجهيز (stage) هذا فقط:

والآن يمكن أن يحتوي الـ commit التالي على تغيير HTML المكتمل بينما يبقى عمل CSS غير المكتمل خارج الـ commit.

فكّر:

> **منطقة التجهيز = ما اخترته للّقطة التالية.**

### 2.3 المستودع (Repository)

يُخزَّن **المستودع** المحلي داخل المجلد المخفي `.git`.

وهو يحتوي تاريخ المشروع وبياناته الوصفية في Git، ومنها:

- الـ commits،
- الفروع،
- الوسوم (tags)،
- المراجع (references).

عندما تشغّل:

⟦CODE_1⟧

يسجّل Git المحتوى المجهَّز بوصفه commit جديدًا في المستودع.

فكّر:

> **المستودع = ما سجّلته بشكل دائم في تاريخ المشروع المحلي.**

### التدفق

```text
تحرير الملفات
   ↓
Working Directory
   |
   | git add
   v
Staging Area
   |
   | git commit
   v
Local Repository
```

يمنع هذا النموذج الذهني قدرًا كبيرًا من ارتباك المبتدئين.

يمكن أن يكون الملف:

- غير متتبَّع (untracked)،
- معدَّلًا لكن غير مجهَّز،
- مجهَّزًا (staged)،
- مُودَعًا ونظيفًا.

والأمر الذي يساعدك على فهم الحالة الحالية هو `git status`.

## 4. المستودعات المحلية والبعيدة: push وpull وfetch

التاريخ المحلي في Git قوي، لكن التعاون يحتاج إلى مكان مشترك.

**المستودع البعيد (remote repository)** نسخة أخرى من المستودع مخزَّنة في مكان آخر، عادةً على منصة مثل GitHub.

علاقة شائعة:

```text
جهازك
المستودع المحلي
      ⇅
GitHub
المستودع البعيد
```

### 4.1 Push: أرسل commits الخاصة بك إلى الخارج

يرسل `git push` الـ commits المحلية إلى مستودع بعيد.

فكّر:

```text

```

### 4.2 Pull: اجلب التغييرات البعيدة إلى فرعك

يحدّث `git pull` فرعك المحلي الحالي بالأعمال البعيدة.

فكّر:

```text
تغييرات بعيدة → الفرع المحلي الحالي
```

```text

```

### Pull مقابل fetch

| الأمر | هل ينزّل التغييرات البعيدة؟ | هل يدمجها فورًا في الفرع الحالي؟ |
|---|---:|---:|
| `git fetch` | نعم | لا |
| `git pull` | نعم | نعم |

### ملاحظة عن merge وrebase

يقدّم الفصل **rebase** باختصار فقط.

والتمييز الأساسي المعروض هو:

- **merge** يحافظ على تواريخ الفروع ويجمعها،
- **rebase** يعيد تشغيل الـ commits فوق أساس آخر لإنشاء تاريخ أكثر خطية.

في هذا الدرس للمبتدئين، استخدم الدمج (merge) بوصفه سير العمل الأساسي. ويُفهم rebase بشكل أفضل بعد أن تتقن الفروع والـ commits وعمليات الدمج.

## 5. التفريع: اعزل العمل دون زعزعة الشيفرة الرئيسية

إذا كانت الـ commits تجيب عن:

> "كيف أسجّل التاريخ؟"

فإن الفروع تجيب عن:

> "كيف تتعايش عدة مجاري عمل معًا؟"

**الفرع (branch)** خط تطوير مستقل يُمثَّل بمرجع متحرك إلى commits.

### لماذا تهمّ الفروع

تخيّل ثلاثة مطوّرين يعملون مباشرة على `main`:

```text
المطوّر A → ميزة دفع نصف مكتملة
المطوّر B → إصلاح عاجل لتسجيل الدخول
المطوّر C → إعادة هيكلة (refactor) كبيرة
```

إذا اختلطت كل التغييرات فورًا في فرع مشترك واحد، فقد يصعب تثبيت الشيفرة.

تعزل الفروع العمل.

```text
main    # الفرع المستقر
 |
 +---- feature/payment
 |
 +---- fix/login
 |
 +---- feature/refactor
```

يستطيع كل فرع التقدّم دون تغيير الخط الرئيسي المستقر فورًا.

وبعد مراجعة الفرع وجاهزيته، يمكن دمج تغييراته.

### GitFlow بوصفه نموذج تفريع منظّمًا

يقدّم المصدر **GitFlow** بوصفه استراتيجية منظّمة.

ويشير أيضًا إلى فارق دقيق مهم: بعض الفرق الحديثة، خصوصًا المحسَّنة لـ continuous deployment، تستخدم نماذج تفريع أبسط.

لذلك لا تفسّر GitFlow على أنها الاستراتيجية الصحيحة الوحيدة.

وقيمتها هنا أنها تعلّم أدوارًا واضحة لأنواع الفروع المختلفة.

### 5.1 `main`

يمثّل `main` الشيفرة المستقرة المُصدَرة في نموذج GitFlow الذي يصفه المصدر.

وقاعدة ذهنية مفيدة:

> ينبغي أن يبقى `main` موثوقًا.

ولهذا تتجنب الفرق المتعاونة غالبًا إيداع الميزات اليومية مباشرة في `main`.

### 5.2 `develop`

`develop` هو فرع التكامل للأعمال المقصودة للإصدار التالي.

تُدمج أعمال الميزات هنا قبل تحضير الإصدار.

### 5.3 فروع الميزات (Feature branches)

مثال:

```text
feature/add-login-page    # مثال لفرع ميزة
```

فرع الميزة:

- يبدأ من `develop`،
- يحتوي عمل ميزة واحدة،
- يعود إلى `develop` عند الاكتمال.

من الناحية المفاهيمية:

```text
develop
   \
    feature/add-login-page
             |
             | عمل + commits
             v
         دمج في develop
```

### 5.4 فروع الإصدار (Release branches)

مثال:

```text
release/v1.2.0    # مثال لفرع إصدار
```

يُستخدم فرع الإصدار لتحضير إصدار.

ويؤكد المصدر:

- لا ينبغي إضافة ميزات جديدة،
- تحدث هنا إصلاحات الأخطاء الأخيرة ومهام الإصدار،
- يُدمج الإصدار المكتمل في `main`،
- وتعود الإصلاحات ذات الصلة أيضًا إلى `develop`.

### 5.5 فروع الإصلاح العاجل (Hotfix branches)

مثال:

```text
hotfix/fix-critical-bug    # مثال لفرع إصلاح عاجل
```

يبدأ الـ hotfix من `main` لأنه يعالج مشكلة في الإنتاج.

بعد الإصلاح:

- يُدمج في `main`،
- ويُدمج أيضًا في `develop`.

لماذا الاثنان؟

لأن إصلاح الإنتاج لا ينبغي أن يختفي من التطوير المستقبلي.

### ملخص GitFlow

| الفرع | يبدأ من | الغرض الرئيسي | يُدمج عادةً في |
|---|---|---|---|
| `main` | طويل العمر | شيفرة مستقرة مُصدَرة | — |
| `develop` | طويل العمر | تكامل الإصدار التالي | — |
| `feature/*` | `develop` | عمل ميزة جديدة | `develop` |
| `release/*` | `develop` | تثبيت الإصدار التالي | `main` و`develop` |

## 7. Pull requests ومراجعة الشيفرة

**طلب السحب (Pull Request أو PR)** مقترح لدمج تغييرات من فرع إلى آخر.

في مثال الفصل:

```text
feature/add-homepage    # فرع الميزة
        ↓
      PR
        ↓
      main
```

الـ PR ليس مجرد "زر دمج".

إنه ينشئ مساحة تعاون يستطيع الفريق فيها:

- شرح التغيير،
- فحص الفروقات (diff)،
- مناقشة خيارات التنفيذ،
- طلب مراجعات،
- تشغيل فحوص آلية،
- الموافقة على الدمج أو رفضه.

### 7.1 اكتب وصفًا مفيدًا للـ PR

يشرح الـ PR المفيد:

- **ماذا** تغيّر،
- **لماذا** تغيّر،
- **كيف** تختبره.

مثلًا:

```text
هذا الـ PR يضيف الصفحة الرئيسية الأولية للمشروع.

لماذا:
نحتاج إلى صفحة هبوط أساسية قبل إضافة التنقل.

كيفية الاختبار:
افتح index.html وتأكد من عرض العنوان والنص التمهيدي بشكل صحيح.
```

يساعد الوصف المراجعين على فهم القصد قبل قراءة تفاصيل التنفيذ.

### 7.2 لماذا تهمّ مراجعة الشيفرة

يحدّد المصدر عدة فوائد رئيسية.

#### تحسين جودة الشيفرة

قد يلتقط شخص آخر:

- منطقًا خاطئًا،
- أخطاء،
- تسمية غير واضحة،
- مشكلات أداء،
- حالات حدّية مفقودة.

#### تبادل المعرفة

تنشر المراجعة الفهم عبر الفريق.

فبدون مراجعة، قد يصبح مطوّر واحد الشخص الوحيد الذي يفهم جزءًا حرجًا من النظام.

#### الحفاظ على الاتساق

تساعد المراجعة الفرق على فرض أنماط مشتركة.

أمثلة:

- اصطلاحات التسمية،
- القرارات المعمارية،
- التنسيق،
- توقعات الاختبار.

#### تقوية التعاون

يحوّل الـ PR الشيفرة إلى حوار فريق.

ويؤكد الفصل أن المراجعة الجيدة ينبغي أن تكون بنّاءة.

أقل فائدة:

```text
هذا خطأ.
```

أكثر فائدة:

```text
هل يمكننا استخراج هذا التحقق إلى دالة مساعدة؟
قد يجعل ذلك المعالج أسهل في الاختبار وإعادة الاستخدام.
```

الهدف ليس "الفوز" بالمراجعة.

الهدف هو تحسين قاعدة الشيفرة المشتركة.

### 7.3 الفحوص الآلية

يربط الفصل أيضًا الـ PRs بـ CI.

قد يتطلب المستودع فحوصًا آلية مثل:

- الاختبارات،
- أدوات الفحص الساكن (linters)،
- التحقق من البناء،

قبل الدمج.

وهذا يخلق طبقة أمان:

```text
فرع الميزة
      ↓
Pull Request
      ↓
مراجعة بشرية
      +
فحوص آلية
      ↓
يُسمح بالدمج
```

### 7.4 فروع main المحمية

يصف المصدر حماية الفروع بوصفها نمطًا احترافيًا.

قد يتطلب `main` المحمي:

- pull requests،
- موافقات،
- نجاح فحوص CI،

بدلًا من السماح بعمليات push المباشرة غير المقيّدة.

ويدعم هذا هدف DevOps المتمثل في التسليم السريع **مع guardrails**.

### 7.5 ادمج ونظّف

بمجرد الموافقة على الـ PR واجتياز الفحوص المطلوبة، ادمجه.

تصبح الميزة المكتملة جزءًا من `main`.

ويمكن بعدها حذف فرع الميزة المؤقت للحفاظ على نظافة قائمة الفروع.

## 8. تعارضات الدمج: عندما يحتاج Git إلى قرار بشري

تعارض الدمج ليس علامة على أن Git معطّل.

إنه يعني أن Git وجد تغييرين متنافسين ولا يستطيع أن يستنتج بأمان أيّ نتيجة نهائية تريدها.

### كيف يحدث التعارض

افترض أن الملف الأصلي يحتوي:

```text
مرحبًا بكم في مشروعنا
```


## 9. عادات Git الاحترافية التي تمنع الأخطاء الشائعة

يختتم الفصل بمجموعة موجزة من العادات التي تستحق أن تتحول إلى ذاكرة عضلية (muscle memory).

### العادة 1 — شغّل `git status`

قبل الإيداع أو الدمج أو تغيير السياق:

⟦CODE_32⟧

تأكد من:

- الفرع الحالي،
- الملفات المعدَّلة،
- الملفات المجهَّزة،
- الملفات غير المتتبَّعة.

يمنع هذا الفحص البسيط كثيرًا من الأخطاء التي يمكن تجنبها.

### العادة 2 — اكتب رسائل commit ذات معنى

التاريخ توثيق.

بعد ستة أشهر:

```text
stuff    # رسالة سيئة
```

لا تخبرك بشيء تقريبًا.

لكن:

```text
fix: resolve null handling in login flow    # رسالة ذات معنى
```

تعطي القارئ المستقبلي سياقًا مفيدًا.

### العادة 3 — أبقِ فرعك محدَّثًا قبل المشاركة

يوصي المصدر بالسحب (pull) قبل الدفع (push) حتى تظهر التعارضات محليًا.

والمبدأ الكامن:

> ادمج تغييرات زملائك عن قصد بدلًا من افتراض أن فرعك هو مصدر الحقيقة الوحيد.

### العادة 4 — تجنّب العمل المباشر على الميزات في `main`

استخدم فروعًا مخصصة.

ثم ادمج عبر pull request خاضع للمراجعة.

وهذا يُبقي `main` متوقَّعًا ويمنح التغييرات مكانًا للمراجعة.

### العادة 5 — اجعل الـ commits مركّزة

يمثّل الـ commit القوي وحدة تغيير واحدة مفهومة.

أقل فائدة:

```text
Commit:
- إضافة تسجيل الدخول
- تغيير مخطط قاعدة البيانات
- إعادة تسمية 40 ملفًا
- إعادة كتابة README
- اختبار تجربة عشوائية
```

أفضل:

```text
commit 1: feat: add login form    # أمثلة
commit 2: feat: validate login credentials
commit 3: docs: document login setup
```

الـ commits المركّزة أسهل في:

- المراجعة،
- الفهم،
- التراجع (revert)،
- تصحيح الأخطاء.

### العادة 6 — افحص قبل أن تتصرف

حلقة Git عملية:

```text
git status
    ↓
git diff
    ↓
git add <الملفات المقصودة>
    ↓
git status
    ↓
git commit
    ↓
git log
```

عند التعاون:

```text
حدّث الفرع
    ↓
أجرِ تغييرًا مركّزًا
    ↓
commit
    ↓
ادفع فرع الميزة
    ↓
افتح PR
    ↓
مراجعة + فحوص
    ↓
دمج
```

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1

> "حفظ الملف يعني أن Git حفظه."

### لماذا هذا خاطئ

يحدّث الحفظ ملف مجلد العمل.

ولا يسجّل Git التغيير في تاريخ المستودع حتى تجهّزه وتودِعه.

---

### المفهوم الخاطئ 2

> "`git add` يحفظ عملي بشكل دائم."

### لماذا هذا خاطئ

يضع `git add` التغييرات المختارة في منطقة التجهيز.

ويسجّل `git commit` اللقطة المجهَّزة في التاريخ المحلي.

---

### المفهوم الخاطئ 3

> "Git وGitHub منتج واحد."

### لماذا هذا خاطئ

Git هو نظام التحكم بالإصدارات.

أما GitHub فتستضيف مستودعات Git وتضيف ميزات تعاون مثل pull requests ومراجعات الشيفرة والـ issues والصلاحيات والفحوص الآلية.

---

### المفهوم الخاطئ 4

> "`git pull` و`git fetch` يفعلان الشيء نفسه تمامًا."

### لماذا هذا خاطئ

كلاهما يستطيع تنزيل معلومات بعيدة، لكن `git pull` يدمج أيضًا تلك التغييرات في الفرع الحالي، بينما يتيح لك `git fetch` فحصها أولًا.

---

### المفهوم الخاطئ 5

> "تعارض الدمج يعني أن أحد المطوّرين أخطأ."

### لماذا هذا خاطئ

قد يحدث التعارض أثناء تطوير متوازٍ طبيعي تمامًا عندما يغيّر فرعان محتوى متداخلًا.

يطلب Git قرارًا بشريًا لأنه لا يستطيع استنتاج القصد بأمان.

---

### المفهوم الخاطئ 6

> "GitFlow هي استراتيجية التفريع الاحترافية الوحيدة."

### لماذا هذا خاطئ

يقدّم المصدر GitFlow بوصفها نموذجًا منظّمًا قيّمًا، مع الإشارة إلى أن بعض الفرق الحديثة تستخدم استراتيجيات أبسط، خصوصًا في بيئات continuous deployment.

والمهارة المهمة هي فهم لماذا يستخدم الفريق نموذج التفريع الذي اختاره.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| نظام التحكم بالإصدارات (VCS) | نظام لتتبّع التغييرات في ملفات المشروع وإدارتها عبر الزمن |
| Git | نظام تحكم بالإصدارات موزَّع يُستخدم لتتبّع تاريخ المشروع |
| GitHub | منصة مستضافة لمستودعات Git وتعاون الفرق |
| مجلد العمل (Working Directory) | ملفات المشروع التي تحرّرها حاليًا |
| منطقة التجهيز / الفهرس (Staging Area / Index) | تغييرات مختارة جُهّزت للـ commit التالي |
| المستودع (Repository) | تاريخ المشروع المخزَّن في Git وبياناته الوصفية |
| `.git` | مجلد مخفي يحتوي بيانات مستودع Git المحلي |
| Commit | لقطة مسجّلة في تاريخ المستودع |
| تجزئة الـ commit (Commit hash) | معرّف فريد لـ commit |
| `git status` | أمر يبلّغ عن الفرع وحالة العمل/التجهيز |
| `git diff` | أمر لفحص التغييرات على مستوى الأسطر |
| `git log` | أمر لتصفّح تاريخ الـ commits |
| المستودع البعيد (Remote) | موقع مستودع خارج المستودع المحلي الحالي |
| `origin` | الاسم الافتراضي الشائع للمستودع البعيد الناتج عن الاستنساخ |
| Push | إرسال commits محلية إلى مستودع بعيد |
| Pull | تنزيل التغييرات البعيدة ودمجها في الفرع المحلي الحالي |
| Fetch | تنزيل التغييرات البعيدة دون دمجها فورًا |
| الفرع (Branch) | خط تطوير مستقل يُمثَّل بمرجع متحرك |
| `main` | الاسم الشائع للفرع الرئيسي المستقر |
| `develop` | فرع التكامل في GitFlow للتطوير القادم |
| فرع الميزة (Feature branch) | فرع مؤقت لميزة جديدة |
| فرع الإصدار (Release branch) | فرع في GitFlow لتثبيت إصدار |
| فرع الإصلاح العاجل (Hotfix branch) | فرع في GitFlow لإصلاحات الإنتاج العاجلة |
| الاستنساخ (Clone) | إنشاء نسخة محلية من مستودع Git بعيد |
| طلب السحب (Pull Request أو PR) | مقترح وسير مراجعة لدمج فرع في آخر |
| مراجعة الشيفرة (Code review) | فحص بشري ومناقشة لتغييرات الشيفرة المقترحة |
| حماية الفروع (Branch protection) | قاعدة في المستودع تقيّد كيفية وصول التغييرات إلى الفروع المحمية |
| تعارض الدمج (Merge conflict) | حالة لا يستطيع فيها Git الجمع التلقائي بين تغييرين متنافسين |
| `HEAD` | مرجع إلى الموضع/سياق الفرع المسحوب حاليًا |

7. ما هو المستودع البعيد؟
8. ما الفرق بين `git fetch` و`git pull`؟
9. لماذا تستخدم الفرق فروع الميزات؟
10. في GitFlow، أين يبدأ فرع الميزة عادةً وإلى أين يعود؟
11. لماذا يُدمج الـ hotfix في كل من `main` و`develop`؟
12. إلى ماذا يشير `origin` عادةً بعد الاستنساخ؟
13. ما المشكلة التي يحلها pull request غير مجرد دمج الشيفرة؟
14. لماذا تفيد مراجعات الشيفرة حتى عندما تنجح الاختبارات الآلية؟
15. ما الذي يسبب تعارض الدمج؟
16. ماذا تعني العلامات `<<<<<<<` و`=======` و`>>>>>>>`؟
17. بعد إصلاح ملف متعارض يدويًا، لماذا تشغّل `git add` مرة أخرى؟
18. لماذا تُعدّ الـ commits الصغيرة المركّزة أسهل صيانةً من commit واحد ضخم؟
