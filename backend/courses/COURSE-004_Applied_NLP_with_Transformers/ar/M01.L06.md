## 1. قد تكون الـ Model ممتازة ومع ذلك سيئة في Production

أثناء تطوير الـ Model، من السهل التركيز فقط على Task Metric مثل Accuracy أو F1 أو ROUGE أو BLEU أوأي Quality Score أخرى.

لكن Production تضيف قيودًا أخرى.

قد تكون الـ Model دقيقة جدًا ومع ذلك غير قابلة للاستخدام إذا:

- كانت كل Prediction بطيئة جدًا،
- كانت تستهلك RAM كبيرة،
- كان Model File كبيرًا جدًا بالنسبة إلى Target Device،
- أصبحت Serving Cost مرتفعة جدًا،
- كان التطبيق يحتاج إلى Real-time Response.

يركز الفصل على أربع تقنيات متكاملة:

1. **Knowledge Distillation**
2. **Quantization**
3. **تحسين الرسم الحسابي (ONNX / ONNX Runtime Graph Optimization)**
4. **Pruning**

هذه الأساليب لا تحل المشكلة نفسها بالطريقة نفسها.

| التقنية | الفكرة الرئيسية |
|---|---|
| Distillation | تدريب Model أصغر لتقليد Model أكبر |
| Quantization | استخدام Numerical Representations أقل Precision |
| ONNX Runtime | تحسين وتشغيل Standardized Computation Graph بكفاءة |
| Pruning | إزالة Weights/Connections أقل أهمية لخلق Sparsity |

## 5. Knowledge Distillation: Teacher وStudent

تدرّب Knowledge Distillation Model أصغر تسمى Student لتقليد Model أكبر وأقوى تسمى Teacher.

أوضح معلومة متاحة للـ Student هي Ground-truth Label.

مثلًا:

```text
التصنيف الصحيح (True Label) = car_rental
```

لكن Teacher تستطيع توفير معلومات أغنى:

```text
car_rental       0.70   — الفئة الأعلى احتمالًا
travel_booking   0.18
car_payment      0.07
other            0.05
```

تكشف الاحتمالات الثانوية علاقات تعلّمتها Teacher. ويطلق الفصل على هذه المعلومات غير الظاهرة في Hard Label اسم Dark Knowledge.

لذلك يمكن للـ Student أن تتعلم من إشارتين:

```text
التصنيفات الصحيحة (Ground-truth Labels)
        +
توزيع احتمالات الـ Teacher (Teacher Probability Distribution)
```

[[IMAGE_NEEDED: Teacher-student knowledge distillation | One input branching into a large teacher and smaller student; teacher produces soft class probabilities, student produces its own probabilities, and the final student loss combines label loss with teacher-student distribution matching | Learner should notice that the teacher guides training but is not needed for student inference after training]]

## 6. Temperature وKL Divergence وDistillation Loss

قد تنتج Teacher الواثقة Probability Distribution قريبة جدًا من One-hot Distribution، وهذا يخفي علاقات مفيدة بين Classes الأقل احتمالًا.

لهذا تستخدم Distillation Temperature نرمز لها بـ `T` لتليين الـ Distributions.

مفاهيميًا:

```text
soft_probs = softmax(logits / T)   — احتمالات ناعمة تنتج عن قسمة logits على درجة الحرارة T
```

عندما ترتفع `T` تصبح الـ Distribution أكثر نعومة، وتكشف معلومات إضافية عن Relative Preferences الخاصة بالـ Teacher بين Classes.

بعد ذلك نقارن Teacher Distribution وStudent Distribution باستخدام KL Divergence.

تجمع Student Objective الكلية بين:

- Cross-entropy عادية مقابل True Labels،
- Distillation Loss مقابل Teacher Distribution.

صورة مبسطة:

```text
student_loss    — خسارة الـ Student
=
alpha × label_loss    — خسارة التصنيفات الصحيحة بوزن alpha
+
(1 - alpha) × distillation_loss    — خسارة التقطير بالوزن المتبقي
```

تتحكم `alpha` في مقدار اعتماد الـ Student على Ordinary Labels مقابل Teacher Signal.

[[IMAGE_NEEDED: Hard labels versus soft teacher probabilities | Three side-by-side bar charts: one-hot hard label, normal teacher softmax, and temperature-softened teacher probabilities | Learner should notice that higher temperature reveals relative probabilities among non-winning classes]]

## 9. Quantization: استخدم عدد Bits أقل للأرقام

تغيّر Distillation Architecture/Size الخاصة بالـ Model. أما Quantization فتستهدف مصدرًا مختلفًا للتكلفة: Numerical Precision.

تخزّن Models كثيرة Weights كقيم Floating-point ذات 32 bit (`FP32`).

تقوم Quantization بتحويل هذه القيم إلى Representation أقل Precision مثل 8-bit Integers (`INT8`).

مفاهيميًا:

```text
FP32 Weight Values
   ↓ التحويل باستخدام Scale + Zero Point
INT8 Integer Levels
```

لماذا قد يساعد ذلك؟

- INT8 تستخدم Bits أقل لكل قيمة.
- يمكن أن يصبح Weight Storage أصغر بكثير.
- Integer Arithmetic قد تكون أسرع على Hardware المدعومة.
- قد نحتاج إلى نقل بيانات أقل عبر Memory.

الـ Trade-off هي أن عددًا كبيرًا من Floating-point Values يجب أن يُمثّل بنفس Integer Level، ما يضيف Quantization Error.

[[IMAGE_NEEDED: FP32 to INT8 quantization | A continuous number line of floating-point weight values mapped onto a smaller set of discrete INT8 levels using a scale and zero point | Learner should notice that quantization saves precision by grouping nearby floating-point values into shared integer levels]]

## 10. Dynamic وStatic وQuantization-aware Approaches

يصف الفصل ثلاث Quantization Strategies شائعة.

### Dynamic Quantization

- يتم Quantize للـ Model Weights قبل Inference،
- ويتم Quantize للـ Activations ديناميكيًا أثناء Inference،
- وهي أبسط الأساليب الثلاثة في الفصل،
- ومفيدة لـ Transformer Inference على CPUs.

### Static Quantization

- تستخدم Representative Data لتقدير Activation Ranges قبل Deployment،
- تخزن Fixed Quantization Scheme،
- تتجنب بعض Runtime Conversion Overhead،
- لكنها تتطلب Calibration Stage إضافية.

### التدريب الواعي بالتكميم (Quantization-aware Training)

- تحاكي تأثيرات Quantization أثناء Training،
- تسمح للـ Model بالتكيف مع Reduced Precision،
- وقد تحافظ على الجودة بصورة أفضل عندما يكون Quantization Error مهمًا.

## 11. ONNX: تمثيل الـ Model على هيئة Standardized Graph

ONNX هو Open Model Representation Format مبني على Standardized Operators وComputational Graph.

بدلًا من التفكير فقط في Python Model Class، تمثل ONNX عملية Inference على هيئة Nodes مثل:

```text
المدخلات (Input)
  ↓
ضرب المصفوفات (MatMul)
  ↓
الجمع (Add)
  ↓
الدالة التنشيطية (Activation)
  ↓
...
```

يساعد هذا Intermediate Representation على فصل Model Execution عن Training Framework الأصلية.

[[IMAGE_NEEDED: Simplified ONNX computational graph | A small directed graph of model operators such as input, MatMul, Add, LayerNorm, and output, shown as connected nodes | Learner should notice that ONNX describes the inference computation as a graph of standardized operations rather than a high-level Python model class]]

## 12. ONNX Runtime: تحسين الـ Graph وتشغيلها

ONNX Runtime (ORT) هي Inference Engine لتشغيل ONNX Graphs.

يسلط الفصل الضوء على Graph Optimizations مثل:

- Operator Fusion — دمج Operations حتى لا نحتاج إلى نقل Intermediate Results دون داعٍ،
- Constant Folding — حساب Constant Expressions مسبقًا قبل Runtime،
- Optimized Execution Providers لـ Hardware محددة.

Mental Model مفيدة:

```text
نموذج PyTorch المدرَّب (Trained PyTorch Model)
       ↓ تصدير (Export)
رسم ONNX الحسابي (ONNX Graph)
       ↓ تحسين (Optimize)
ONNX Runtime
       ↓
واجهة Inference أسرع (Faster Inference Backend)
```

Benchmark الخاصة بـ Distilled ONNX Model في الفصل:

| Model | Size | Avg. Latency | Test Accuracy |
|---|---:|---:|---:|
| Distillation + ORT | 255.88 MB | 21.02 ms | 0.868 |

يبقى Model Size شبه ثابت، لكن Graph/Runtime Optimization تحسن Latency مقارنة بالـ Distilled Model العادية.

## 14. Pruning: اجعل الـ Network Sparse

تحافظ Quantization على Network نفسها تقريبًا، لكنها تخزن الأرقام بعدد Bits أقل.

أما Pruning فتحاول إزالة بعض Connections بالكامل.

النتيجة هي Sparse Model تحتوي على عدد كبير من Zero-valued Weights.

مفاهيميًا:

```text
Dense Weights
● ● ● ● ●
● ● ● ● ●
● ● ● ● ●

بعد Pruning
● · · ● ·
· ● · · ●
● · · · ·
```

تحتاج Pruning Method إلى تعريف ما لـ Importance حتى تستطيع تحديد أي Weights يجب الإبقاء عليها وأيها يتم Mask لها.

## 15. Magnitude Pruning مقابل Movement Pruning

### Magnitude Pruning

تتعامل Magnitude Pruning مع Weights صغيرة Absolute Magnitude باعتبارها أقل أهمية.

عملية شائعة هي:

```text
درّب الـ Model
   ↓
أزل Low-magnitude Weights
   ↓
أعد التدريب
   ↓
نفّذ Pruning إضافية
```

يناقش الفصل زيادة Sparsity تدريجيًا بدلًا من إزالة نسبة ضخمة من Weights دفعة واحدة.

أحد القيود في Transfer Learning هو أن Weight Magnitude تعكس في الأساس ما حدث أثناء Pretraining؛ فالـ Weight الصغيرة ليست بالضرورة غير مهمة للـ Downstream Task.

### Movement Pruning

أما Movement Pruning فتتعلّم Importance Scores أثناء Fine-tuning.

الفكرة هي الحفاظ على Weights التي يشير اتجاه تغيرها أثناء التدريب إلى أنها أصبحت مهمة للـ Downstream Task.

وبذلك يصبح Importance Criterion مرتبطًا بصورة أوضح بسلوك Fine-tuning، بدلًا من الاعتماد فقط على Current Absolute Weight Size.

[[IMAGE_NEEDED: Magnitude versus movement pruning | A side-by-side conceptual comparison where magnitude pruning ranks weights by absolute size and movement pruning ranks them using learned movement/importance scores during fine-tuning | Learner should understand that the two methods answer 'which weights matter?' using different signals]]

### قيد عملي مهم

Sparse Model ليست أسرع تلقائيًا على Hardware الحقيقية. يشير الفصل إلى أن دعم Hardware وRuntime لـ Sparse Matrix Operations قد يحد من Speed Benefit الفعلية حتى إذا تم تقليل Storage.

## 16. Production Optimization Workflow عملية

يمكن تحويل الفصل إلى Engineering Loop قابلة للتكرار:

```text
1. حدّد Product Requirements
       ↓
2. اعمل Benchmark للـ Full Model
   Quality + Latency + Memory
       ↓
3. جرّب Student أصغر / Distillation
       ↓
4. أعد Benchmark
       ↓
5. طبّق Quantization
       ↓
6. أعد Benchmark
       ↓
7. صدّر / حسّن باستخدام ONNX Runtime
       ↓
8. أعد Benchmark
       ↓
9. فكّر في Pruning إذا كانت Storage/Sparsity مهمة
       ↓
10. اختبر على Production Hardware وInputs واقعية
```

أهم عادة هنا هي خطوة إعادة الـ Benchmark المتكررة.

لا تكون Optimization ذات قيمة إلا إذا حسنت القيود المهمة فعلًا من دون خفض الجودة إلى مستوى غير مقبول.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: أكثر Model دقة هي تلقائيًا أفضل Production Model

> إذا فازت Model في Test Metric، تصبح Deployment Concerns ثانوية.

### لماذا هذا خطأ

يمكن لـ Latency وMemory وCost وHardware Constraints أن تجعل Model دقيقة جدًا غير عملية. Production Decisions تحتاج إلى عدة Metrics.

### المفهوم الخاطئ 2: Distillation تعني نسخ Final Class الخاصة بالـ Teacher فقط

> تتدرب Student ببساطة على Argmax Prediction الخاصة بالـ Teacher.

### لماذا هذا خطأ

يمكن لـ Soft Probability Distribution أن تكشف علاقات بين Classes لا تحتوي عليها Hard Label وحدها.

### المفهوم الخاطئ 3: Quantization تقلل Accuracy بدرجة كبيرة دائمًا

> INT8 تدمر Model Quality بالضرورة.

### لماذا هذا خطأ

يجب قياس التأثير الفعلي. في تجربة Intent Classification في الفصل، تحافظ INT8 Quantization على Task Metric بصورة جيدة جدًا.

### المفهوم الخاطئ 4: التصدير إلى ONNX يجعل الـ Model أصغر تلقائيًا

> ONNX Conversion نفسها هي Compression.

### لماذا هذا خطأ

ONNX توفر أساسًا Standardized Graph Representation. يمكن لـ Runtime Graph Optimization تحسين Execution Speed، بينما Quantization أو Pruning آليتان منفصلتان لتقليل Numerical/Storage Cost.

### المفهوم الخاطئ 5: Sparse تعني Fast دائمًا

> إزالة Weights تضمن تحسنًا متناسبًا في Latency.

### لماذا هذا خطأ

تعتمد السرعة على قدرة Target Hardware/Runtime على استغلال Sparse Operations بكفاءة.

## المصطلحات الرئيسية

| المصطلح | المعنى |
|---|---|
| Latency | الزمن اللازم لإنتاج Prediction |
| Throughput | عدد Predictions التي يستطيع النظام معالجتها خلال فترة زمنية |
| Model Footprint | تكلفة Storage/RAM المرتبطة بالـ Model |
| Benchmark | إجراء ثابت لمقارنة Production-relevant Metrics |
| Knowledge Distillation | تدريب Student أصغر باستخدام Guidance من Teacher أكبر |
| Teacher | Model أكبر تنتج Soft Predictions أثناء Distillation |
| Student | Model أصغر تُدرَّب لتقليد Teacher |
| Soft Target | Probability Distribution على Classes بدل Hard Class Label واحدة |
| Temperature | Parameter تُستخدم لتليين Class Probability Distributions |
| KL Divergence | Measure لمقارنة Teacher وStudent Probability Distributions |
| Quantization | تحويل Model Values إلى Numerical Representations أقل Precision |
| FP32 | تمثيل Floating-point بطول 32-bit |
| INT8 | 8-bit Integer Representation شائعة في Quantized Inference |
| Dynamic Quantization | Quantization تُعالج فيها Activations ديناميكيًا أثناء Inference |
| Static Quantization | Quantization تتم معايرتها مسبقًا باستخدام Representative Activation Data |
| التدريب الواعي بالتكميم (Quantization-aware Training) | Training مع محاكاة Reduced Precision |

| ONNX Runtime | Inference Engine تعمل على تحسين وتشغيل ONNX Graphs |

| Magnitude Pruning | Pruning تعتمد أساسًا على Absolute Weight Magnitude |
| Movement Pruning | Pruning تعتمد على Learned Importance/Movement أثناء Fine-tuning |

## اختبر نفسك

قبل المتابعة، تأكد أنك تستطيع الإجابة عن الأسئلة التالية:

1. لماذا لا تكفي Accuracy وحدها لاختيار Production Model؟
2. لماذا يجب قياس Latency على Runs كثيرة بعد Warm-up؟
3. ما المعلومات الإضافية التي قد توفرها Soft Distribution الخاصة بالـ Teacher؟
4. ماذا تتحكم Temperature وalpha في Knowledge Distillation؟
5. لماذا تكون DistilBERT Student منطقية لـ BERT Teacher؟
6. كيف تختلف Quantization عن Distillation؟
7. ما الفرق بين Dynamic Quantization وStatic Quantization؟
8. ماذا تمثل ONNX؟
9. ما الذي يمكن لـ ONNX Runtime تحسينه؟
10. لماذا قد يكون الجمع بين Distillation وORT وQuantization مفيدًا؟
11. كيف تحدد Magnitude Pruning وMovement Pruning مفهوم Importance بطرق مختلفة؟
12. لماذا قد لا تحقق Sparse Model بدرجة كبيرة Speedup المتوقع؟
