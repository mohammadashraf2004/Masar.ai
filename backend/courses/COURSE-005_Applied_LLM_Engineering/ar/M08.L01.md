## 1. لماذا غيّرت Language Models البحث؟

يعتمد البحث التقليدي كثيرًا على الكلمات التي تظهر في query والمستندات.

لكن البشر لا يعبّرون دائمًا عن المعنى نفسه باستخدام الكلمات نفسها.

على سبيل المثال:

```text
الاستعلام (Query):
how precise was the science
```

قد يقول مقطع شديد الصلة:

```text
praised for its scientific accuracy — مقطع يصف الدقة العلمية
```

الكلمات مختلفة، لكن المعنى مترابط بقوة.

هذه هي الفكرة الأساسية لـ **semantic search**:

> ابحث بالمعنى، وليس فقط من خلال التطابق الحرفي للكلمات.

يوضح الفصل أن Language Models حسّنت أنظمة البحث الناضجة لأنها تستطيع إنشاء contextual representations تلتقط أكثر من raw keywords.

## 2. لماذا أصبح البحث مهمًا أيضًا لـ Text Generation؟

تستطيع generative models الإجابة عن الأسئلة بطلاقة.

لكن الطلاقة ليست هي نفسها الدقة الواقعية.

يسلط الفصل الضوء على مشكلة شائعة:

```text
يجيب Model بثقة (model answers confidently)
لكن
قد تكون الإجابة خاطئة أو قديمة (the answer may be wrong or outdated)
```

إحدى طرق التعامل مع هذه المشكلة هي retrieval للمعلومات ذات الصلة أولًا ثم تقديمها إلى generator.

وهذا يقود إلى **Retrieval-Augmented Generation**، أو:

```text
RAG
```

الفكرة بسيطة:

```text
السؤال (Question)
   ↓
البحث / الاسترجاع
   ↓
الأدلة ذات الصلة (Relevant evidence)
   ↓
LLM
   ↓
إجابة مستندة إلى الأدلة (Grounded answer)
```

تكون RAG مفيدة خصوصًا عندما تريد من Model الإجابة اعتمادًا على:

- knowledge base محددة،
- بيانات داخلية لشركة،
- كتاب،
- product documentation،
- external dataset تتغير مع الوقت.

## 3. ثلاثة مكونات رئيسية: Retrieval و Reranking و RAG

ينظم الفصل أنظمة semantic search الحديثة في ثلاث فئات رئيسية.

### الاسترجاع الكثيف (Dense retrieval)

```text
الاستعلام (query)
→ embedding
→ أقرب المستندات في embedding space
```

### Reranking

```text
الاستعلام (query)
+
نتائج البحث المرشحة (candidate search results)
→ نموذج الصلة (relevance model)
→ إعادة ترتيب المرشحين (reorder candidates)
```

### RAG

```text
الاستعلام (query)
→ استرجاع الأدلة (retrieve evidence)
→ توليد الإجابة باستخدام الأدلة (generate answer using evidence)
```

يمكن دمج هذه المكونات في pipeline واحدة:

```text
الاستعلام (Query)
  ↓
الاسترجاع في المرحلة الأولى (First-stage retrieval)
  ↓
النتائج المرشحة (Candidate results)
  ↓
إعادة الترتيب (Reranker)
  ↓
أفضل الأدلة (Best evidence)
  ↓
النموذج التوليدي (Generative model)
  ↓
إجابة مستندة إلى الأدلة (Grounded answer)
```

[[IMAGE_NEEDED: Retrieval reranking RAG stack | Show a three-stage pipeline with dense/lexical retrieval producing candidates, reranker reordering them, and a generative model answering from the top evidence | Learner should see retrieval, reranking, and generation as distinct jobs]]

## 4. Dense Retrieval: البحث داخل Embedding Space

تذكّر من الدروس السابقة:

```text
النص (text)
→ نموذج Embedding
→ vector
```

تميل النصوص المرتبطة دلاليًا إلى الحصول على representations قريبة من بعضها.

تستخدم dense retrieval هذه الخاصية.

افترض أننا أنشأنا embeddings لثلاثة مستندات:

```text
Document A → vector A   — المستند ومتجهه
Document B → vector B
Document C → vector C
```

ثم أنشأنا embedding لـ query:

```text
Query → query vector   — الاستعلام يتحول إلى متجه
```

نقارن الآن query vector بكل document vector.

تصبح vectors الأقرب هي نتائج البحث.

من الناحية المفاهيمية:

```text
التشابه الدلالي (semantic similarity)
≈
القرب داخل embedding space
```

[[IMAGE_NEEDED: Dense retrieval embedding space | Show query and several document points in a vector space, with the nearest two documents highlighted as retrieved results | Learner should connect semantic similarity with nearest-neighbor retrieval]]

### سؤال تصميم مهم

هل يجب أن يعيد النظام نتيجة دائمًا؟

ليس بالضرورة.

إذا كانت كل النتائج المرشحة ضعيفة الصلة، فقد يفضّل نظام بحث جيد:

```text
"No sufficiently relevant result found." — لم يتم العثور على نتيجة ذات صلة كافية
```

بدلًا من إعادة أقل نتيجة سوءًا وكأنها جيدة.

لهذا السبب يذكر الفصل استخدام distance أو similarity threshold.

## 5. Queries و Documents ليست دائمًا متماثلة دلاليًا

هناك نقطة دقيقة في الفصل وهي أن:

> لا تبدو query وأفضل نتيجة لها دائمًا متشابهتين دلاليًا بالطريقة نفسها التي يتشابه بها مستندان عاديان.

مثال:

```text
Query:   — الاستعلام
When did Interstellar premiere?

Relevant passage:   — المقطع ذو الصلة
Interstellar premiered on October 26, 2014, in Los Angeles.
```

Query هي سؤال.

أما passage فهي إجابة.

لكل منهما دور مختلف.

ولهذا السبب غالبًا ما يتم training لـ retrieval embedding models باستخدام:

```text
الاستعلام (query)
+
النتيجة ذات الصلة (relevant result)
+
النتيجة غير ذات الصلة (irrelevant result)
```

وليس باستخدام التشابه العادي بين الجمل فقط.

يتعلم training objective ما يلي:

```text
زوج query-document ذو الصلة (relevant query-document pair)
→ يصبح أقرب (move closer)

زوج query-document غير ذي الصلة (irrelevant query-document pair)
→ يصبح أبعد (move farther apart)
```

## 6. بناء Vector Index قابل للبحث

pipeline شائعة لـ dense retrieval هي:

```text
قاعدة المعرفة (Knowledge base)
    ↓
تقسيم المستندات إلى Chunks (Chunk documents)
    ↓
إنشاء Embedding لكل Chunk (Embed every chunk)
    ↓
تخزين Vectors داخل Index (Store vectors in an index)
```

ثم أثناء query time:

```text
استعلام المستخدم (User query)
    ↓
إنشاء Embedding للاستعلام (Embed query)
    ↓
البحث عن أقرب Vectors (Search nearest vectors)
    ↓
إرجاع Chunks المطابقة (Return matching chunks)
```

[[IMAGE_NEEDED: Vector indexing and retrieval | Two phases: indexing phase with documents → chunks → embeddings → vector index, and query phase with query → embedding → nearest-neighbor lookup → retrieved chunks | Learner should distinguish offline indexing from online query retrieval]]

هذا الفصل بين المرحلتين مهم.

فأنت عمومًا **لا** تريد إعادة إنشاء embeddings لكل corpus في كل مرة يبحث فيها شخص ما.

```text
1. إنشاء Embedding للاستعلام (Embed the query)
2. البحث عن Nearest neighbors (Search nearest neighbors)
3. استرجاع Chunks النصية المطابقة (Retrieve matching text chunks)

```

من الناحية المفاهيمية:

⟦CODE_2⟧

بالنسبة إلى query:

```text
how precise was the science   — استعلام المستخدم
```


رغم أن الصياغة لا تكرر query مباشرةً.

وهذا تحديدًا هو السلوك الذي تهدف semantic search إلى توفيره.

## 10. مقارنة Dense Retrieval مع BM25 Keyword Search

يقارن الفصل semantic retrieval مع BM25.

BM25 هي lexical retrieval method.

فهي تكافئ word overlap وأهمية المصطلحات.

بالنسبة إلى query نفسها:

```text
how precise was the science   — الاستعلام نفسه
```

قد يرتب النظام lexical نصًا يحتوي على:

```text
science fiction   — عبارة مفتاحية
```

بسبب الكلمة المشتركة:

```text
science   — كلمة مفتاحية
```

حتى إذا لم يكن ذلك passage يجيب عن المقصود.

أما dense retrieval فيمكنها العثور على:

```text
scientific accuracy   — عبارة مفتاحية
```

رغم عدم وجود الصياغة الحرفية نفسها.

[[IMAGE_NEEDED: BM25 versus dense retrieval example | Show the same query with BM25 selecting a passage that shares the word “science,” while dense retrieval selects a passage about “scientific accuracy” | Learner should understand lexical overlap versus semantic relevance]]

### هل يعني ذلك أن Dense Retrieval تستبدل Keyword Search؟

لا.

يذكر الفصل بوضوح حالات تظل فيها keyword matching ذات قيمة، خصوصًا:

```text
البحث عن عبارة مطابقة (exact phrase lookup)
المعرّفات الدقيقة (exact identifiers)
الأسماء المحددة (specific names)
التطابق الحرفي للنص (literal text matching)
```

وهذا يقود طبيعيًا إلى hybrid search.

## 11. Hybrid Search: استخدام Lexical و Semantic Signals معًا

تتميز dense search في:

```text
المعنى (meaning)
إعادة الصياغة (paraphrases)
التشابه المفاهيمي (conceptual similarity)
```

وتتميز keyword/BM25 search في:

```text
المصطلحات الدقيقة (exact terms)
المعرّفات النادرة (rare identifiers)
مطابقات العبارات الدقيقة (precise phrase matches)
```

لذلك يجمع النظام القوي بينهما غالبًا.

من الناحية المفاهيمية:

```text
الاستعلام (Query)
 ├─ BM25
 │    ↓
 │ المرشحون Lexical (lexical candidates)
 │
 └─ Dense retrieval
      ↓
    المرشحون Semantic (semantic candidates)
        ↓
      الدمج (merge)
        ↓
      إعادة الترتيب (rerank)
```

[[IMAGE_NEEDED: Hybrid search architecture | Show one query branching to BM25 and dense retrieval, candidate lists being merged, then sent to reranking | Learner should see hybrid search as combining complementary retrieval signals]]

ينصح الفصل باستخدام hybrid search بدلًا من الاعتماد فقط على dense retrieval.

## 12. التحذير الأول: Dense Retrieval ما زالت تعيد شيئًا عندما لا توجد نتيجة ذات صلة

افترض أن corpus كلها عن *Interstellar* فقط.

والآن اسأل:

```text
What is the mass of the moon?   — استعلام المستخدم
```

ستظل embedding search تعيد nearest neighbors.

لكن:

```text
الأقرب (nearest)
≠
ذو صلة (relevant)
```

قد تكون vectors الأقرب ببساطة أقل الخيارات عدمًا للصلة.

لهذا السبب تحتاج production retrieval غالبًا إلى:

- similarity thresholds،
- سلوك “no result”،
- confidence heuristics،
- downstream validation.

يجب ألا يُجبر retriever على التظاهر بأن corpus تحتوي على إجابة.

## 13. التحذير الثاني: قد تنخفض Retrieval Quality في Domain جديدة

قد يعمل embedding model تم تدريبه أساسًا على نصوص عامة من الإنترنت أو نصوص شبيهة بـ Wikipedia بصورة أسوأ على:

```text
المستندات القانونية (legal documents)
السجلات الطبية (medical records)
الأدلة التقنية (technical manuals)
المصطلحات الداخلية المتخصصة للشركة (specialized internal company terminology)
```

إذا اختلفت هذه الأنماط بصورة كبيرة عن training data الخاصة به.

هذه صورة من domain mismatch.

ويربط الفصل ذلك لاحقًا بـ retrieval fine-tuning.

الدرس العملي هو:

> قيّم retrieval على الـ domain التي تخطط فعلًا للبحث فيها.

لا تفترض أن general semantic embeddings القوية تحل تلقائيًا كل corpus متخصصة.

## 14. لماذا تحتاج المستندات الطويلة إلى Chunking؟

تمتلك Transformer models حدود context محدودة.

كما أن إنشاء embedding لمستند طويل كامل قد يضغط أفكارًا كثيرة غير مترابطة في vector واحدة.

افترض أن تقريرًا طويلًا يحتوي على أقسام عن:

```text
الإيرادات (revenue)
التوظيف (hiring)
الأمان (security)
خارطة طريق المنتج (product roadmap)
المخاطر القانونية (legal risks)
```

تخلط vector واحدة للتقرير كاملًا كل هذه المفاهيم معًا.

إذا سأل المستخدم:

```text
What were the security risks?   — استعلام المستخدم
```

فقد يكون security chunk أكثر تركيزًا وأسهل بكثير في retrieval.

وهذا يقود إلى مبدأ chunking:

> يعمل البحث بصورة أفضل عندما تتوافق الوحدة المفهرسة مع وحدة المعلومات التي يُحتمل أن يسأل عنها المستخدمون.

## 15. Vector واحدة لكل Document

يصف الفصل طريقتين عامتين لإنشاء vector واحدة لمستند طويل.

### الخيار A — إنشاء Embedding لجزء ممثل فقط

على سبيل المثال:

```text
العنوان (title)
الفقرة الأولى (first paragraph)
الملخص (abstract)
```

الميزة:

```text
بسيط وسريع (simple and fast)
```

العيب:

```text
المحتوى الذي لم يُنشأ له Embedding يصبح غير قابل للبحث (unembedded content becomes unsearchable)
```

### الخيار B — إنشاء Embeddings لعدة Chunks ثم أخذ المتوسط

من الناحية المفاهيمية:

```text
vector الخاصة بـ chunk 1
vector الخاصة بـ chunk 2
vector الخاصة بـ chunk 3
        ↓
      المتوسط (average)
        ↓
vector واحدة للمستند (one document vector)
```

الميزة:

```text
يساهم المستند كله (the whole document contributes)
```

العيب:

```text
تُضغط مفاهيم كثيرة في vector واحدة (many concepts are compressed into one vector)
```

وقد تصبح التفاصيل المحددة أصعب في retrieval.

---

## 16. عدة Vectors لكل Document

نهج أقوى في كثير من أنظمة البحث هو:

```text
المستند (document)
→ chunk 1 → vector 1
→ chunk 2 → vector 2
→ chunk 3 → vector 3
```

يخزن index الآن chunk vectors بدلًا من document-level vectors فقط.

الفوائد:

- تغطية النص الكامل،
- مفاهيم أكثر تحديدًا محليًا،
- retrieval أفضل للمعلومات المحددة،
- search index أكثر ثراءً.

لكن chunking نفسها تصبح مشكلة تصميم.

## 17. استراتيجيات Chunking

يعرض الفصل عدة خيارات.

### Chunks على مستوى الجملة (Sentence chunks)

```text
جملة واحدة (one sentence)
→ embedding واحدة
```

المزايا:

```text
شديد التركيز (very focused)
```

العيوب:

```text
قد يفقد السياق المحيط (may lose surrounding context)
```

### Chunks على مستوى الفقرة (Paragraph chunks)

غالبًا ما تكون خيارًا طبيعيًا عندما تكون الفقرات قصيرة ومتماسكة.

### Chunks متعددة الجمل (Multi-sentence chunks)

يقترح الفصل تجميع عدة جمل عند الحاجة.

### إضافة عنوان المستند (Add document title)

قد تحصل chunk على سياق مفيد إذا أضيف إليها في البداية:

```text
عنوان المستند (document title)
```

### جعل Chunks المتجاورة متداخلة (Overlap adjacent chunks)

مثال:

```text
Chunk A:   — المقطع الأول
sentences 1–5

Chunk B:   — المقطع الثاني
sentences 4–8   — يتداخل مع المقطع الأول
```

## 20. Reranking: تحسين الترتيب بعد Retrieval

يجب أن يكون retriever سريعًا بما يكفي للبحث داخل corpus كبيرة.

أما reranker فيمكنه أن يكون أبطأ لأنه يرى shortlist فقط.

بحث نموذجي من مرحلتين:

```text
ملايين المستندات (millions of documents)
      ↓
استرجاع سريع في المرحلة الأولى (fast first-stage retrieval)
      ↓
أفضل 100 مرشح (top 100 candidates)
      ↓
Reranker أبطأ (slower reranker)
      ↓
أفضل 10 نتائج مرتبة (top 10 best-ranked results)
```

يمكن أن تكون المرحلة الأولى:

- BM25،
- dense retrieval،
- hybrid search.

## 21. مثال على Reranker


إلى reranking model.

```text

+
```

يمكن أن ينقذ ذلك ترتيبًا ضعيفًا من المرحلة الأولى.

> تحسّن first-stage retrieval أساسًا recall والسرعة؛ بينما يمكن لـ reranking تحسين precision بالقرب من أعلى القائمة.

## 24. Precision عند الموضع k

تخيل أن النتائج المرتبة هي:

```text
Rank 1: relevant   — الترتيب الأول ذو صلة
Rank 2: irrelevant   — الثاني غير ذي صلة
Rank 3: relevant   — الثالث ذو صلة
```

عند rank 1:

```text
precision@1 = 1 / 1 = 1.0   — الدقة عند أول نتيجة
```

عند rank 3:

```text
relevant results so far = 2   — النتائج ذات الصلة حتى الآن
results examined = 3   — النتائج التي فُحصت

precision@3 = 2 / 3
```

الترتيب مهم.

وجود نتيجة ذات صلة في الموضع 1 أكثر فائدة من دفن النتيجة ذاتها في الموضع 10.

وهذا يحفز استخدام average precision.

## 25. متوسط Precision (Average Precision — AP)

تكافئ Average Precision الأنظمة التي تضع النتائج ذات الصلة مبكرًا.

إجراء مبسط:

```text
1. تحرك نزولًا عبر القائمة المرتبة.
2. كلما كانت النتيجة ذات صلة، احسب Precision عند ذلك الموضع.
3. خذ متوسط قيم Precision تلك عبر المستندات ذات الصلة.
```

مثال:

```text
Rank 1: relevant   — الترتيب الأول ذو صلة
Rank 2: irrelevant   — الثاني غير ذي صلة
Rank 3: relevant   — الثالث ذو صلة
```

إذًا:

```text
precision@1 = 1/1 = 1.0   — الدقة عند أول نتيجة
precision@3 = 2/3 ≈ 0.67   — الدقة عند أول ثلاث نتائج
```

تلخص AP جودة الترتيب لـ query واحدة.

## 26. متوسط Average Precision (Mean Average Precision — MAP)

تقيس Average Precision query واحدة.

أما Mean Average Precision فتقيس النظام عبر عدة test queries.

من الناحية المفاهيمية:

```text
Query 1 → AP1
Query 2 → AP2
Query 3 → AP3
...
        ↓
      المتوسط (average)
        ↓
MAP
```

تعطي MAP رقمًا واحدًا يمكن استخدامه لمقارنة retrieval systems على evaluation set نفسها.

### nDCG

يذكر الفصل أيضًا:

```text
normalized discounted cumulative gain — الاسم الكامل لمقياس nDCG
```

أو:

```text
nDCG
```

والفرق الأساسي هو أن relevance يمكن أن تكون متدرجة.

بدلًا من:

```text
ذو صلة / غير ذي صلة
```

يمكن أن يكون لديك:

```text
شديد الصلة (highly relevant)
ذو صلة إلى حد ما (somewhat relevant)
ضعيف الصلة (weakly relevant)
غير ذي صلة (not relevant)
```

وهذا مفيد عندما لا تكون relevance binary.

```text

+

```

ويُطلب منه الإجابة باستخدام تلك الأدلة.

### لماذا تساعد RAG؟

لم يعد generator مضطرًا للاعتماد فقط على ما هو مخزن داخل model parameters.

بل يمكنه استخدام معلومات خارجية تُقدَّم أثناء runtime.

يساعد ذلك مع:

- البيانات الخاصة/الداخلية،
- المعرفة الأحدث،
- المعلومات المتخصصة في domain،

## 28. Grounded Generation

تستقبل مرحلة generation:

```text
السؤال (Question):
...

chunk C
```

هذا هو **grounded generation**.


يمكن أن يختلف prompt الدقيق.

المهم هو الفصل بوضوح بين:


وتحديد كيفية استخدام الأدلة.

## 33. يمكن أن تفشل RAG في عدة مواضع

طريقة مفيدة لتصحيح RAG هي فصل مراحل الفشل.

### فشل Retrieval

لم يتم retrieval للأدلة الصحيحة أصلًا.

الأسباب المحتملة:

- chunks سيئة،
- embedding model غير مناسب،
- domain mismatch،
- query سيئة،
- candidate count غير كافٍ.

### فشل Reranking

تم retrieval للـ document الصحيح، لكنه رُتب في موضع منخفض جدًا.

### فشل بناء Context

توجد أدلة جيدة، لكن:

- تم تضمين context غير ذي صلة بدرجة كبيرة،
- chunks مكررة،
- context تم truncation له.

### فشل Generation

يرى Model الأدلة الصحيحة، لكنه:

- يتجاهلها،
- يسيء قراءتها،
- يضيف unsupported claims،
- يجيب بما يتجاوز context.

وهذا يقود إلى عادة هندسية مهمة:

> قيّم retrieval و generation كلًا على حدة قبل الحكم على نظام RAG بالكامل.

## 36. RAG المتقدمة: Multi-Hop Retrieval

يناقش الفصل عدة أبعاد للتقييم.

### الطلاقة (Fluency)

هل الإجابة المولدة قابلة للقراءة ومتماسكة؟

### الفائدة المتصورة (Perceived utility)

هل هي مفيدة وغنية بالمعلومات؟

### استدعاء الاستشهادات (Citation recall)

من بين claims المتعلقة بالعالم الخارجي، كم منها مدعوم بـ citations؟

### دقة الاستشهادات (Citation precision)

هل تدعم citations فعليًا claims المرتبطة بها؟

### الالتزام بالسياق (Faithfulness)

هل تتوافق الإجابة مع context المقدم؟

### صلة الإجابة (Answer relevance)

هل تجيب الإجابة فعليًا عن سؤال المستخدم؟

## 40. قيّم Retrieval و Generation بشكل منفصل

افترض أن final answer خاطئة.

هناك احتمالان مختلفان على الأقل.

### الحالة A — فشلت Retrieval

لم تحتوِ الأدلة أصلًا على الإجابة.

لن يؤدي إصلاح generator إلى حل ذلك.

### الحالة B — نجحت Retrieval

كانت الأدلة الصحيحة موجودة، لكن Model تجاهلها أو أساء تفسيرها.

قد لا يؤدي إصلاح retriever إلى حل ذلك.

لذلك يسأل تقييم RAG قوي بشكل منفصل:

```text
هل قمنا بـ Retrieval لأدلة مفيدة؟ (Did we retrieve useful evidence?)

هل استخدم Generator تلك الأدلة بصورة صحيحة؟ (Did the generator use that evidence correctly?)
```

يجعل هذا الفصل تحسين النظام أكثر استهدافًا.

## 41. ضع Pipeline الكاملة لـ Semantic Search و RAG معًا

يمكن أن تبدو pipeline حديثة قوية كما يلي:

### Offline Indexing

```text
المستندات (Documents)
  ↓
Chunking
  ↓
نموذج Embedding
  ↓
Vector index/database
```

### مسار الاستعلام أثناء التشغيل (Online Query Path)

```text
سؤال المستخدم (User question)
  ↓
إعادة كتابة Query اختياريًا (Optional query rewrite)
  ↓
Hybrid first-stage retrieval
  ↓
المستندات المرشحة (Candidate documents)
  ↓
Reranker
  ↓
أفضل Evidence chunks
  ↓
RAG prompt
  ↓
Generative model
  ↓
إجابة مستندة إلى الأدلة + المصادر
```

### Extensions متقدمة

```text
multi-query   — استعلامات متعددة
multi-hop   — قفزات استدلال متعددة
routing   — التوجيه
agentic tool selection   — اختيار الأدوات بصورة وكيلية
```

### Evaluation

```text
مقاييس الاسترجاع (retrieval metrics)
+
مقاييس التوليد/الإسناد
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> تعني Semantic search أن keyword search أصبحت قديمة وغير ضرورية.

### لماذا هذا خطأ؟

غالبًا ما تتعامل lexical retrieval بصورة ممتازة مع exact phrases و identifiers و names و literal terms. ويوصي الفصل باستخدام hybrid approaches.

---

### المفهوم الخاطئ 2

> أقرب vector هي دائمًا إجابة ذات صلة.

### لماذا هذا خطأ؟

تعيد nearest-neighbor search دائمًا أقرب العناصر المتاحة، حتى عندما لا تحتوي corpus على إجابة حقيقية.

---

### المفهوم الخاطئ 3

> يجب أن يمتلك كل document دائمًا embedding واحدة فقط.

### لماذا هذا خطأ؟

تستفيد المستندات الطويلة غالبًا من عدة chunk embeddings حتى تظل المفاهيم المحددة قابلة للـ retrieval.

---

### المفهوم الخاطئ 4

> Chunks الأصغر أفضل دائمًا.

### لماذا هذا خطأ؟

قد تفقد chunks الصغيرة جدًا السياق الضروري. ويجب أن توازن chunking بين التركيز والسياق.

---

### المفهوم الخاطئ 5

> Dense retrieval و reranking تؤديان الوظيفة نفسها.

### لماذا هذا خطأ؟

تجد dense retrieval المستندات المرشحة بكفاءة. أما reranking فتقيّم candidate set أصغر بصورة أدق وتغير ترتيبها.

---

### المفهوم الخاطئ 6

> ينبغي لـ Rerankers تقييم كل document داخل corpus تحتوي على مليون document.

### لماذا هذا خطأ؟

تكون reranking بأسلوب cross-encoder عادةً مكلفة جدًا لتطبيقها على corpus كاملة، لذلك تُطبق بعد first-stage retrieval.

---

### المفهوم الخاطئ 7

> تضمن RAG إجابات واقعية صحيحة.

### لماذا هذا خطأ؟

ما زالت retrieval السيئة أو context assembly السيئة أو generation غير الصحيحة قادرة على إنتاج إجابات خاطئة.

---

### المفهوم الخاطئ 8

> إذا كانت إجابة RAG سلسة، فهذا يعني أن نظام RAG يعمل جيدًا.

### لماذا هذا خطأ؟

الطلاقة ليست سوى بُعد واحد. كما تهم evidence support و relevance و citations و retrieval quality.

---

### المفهوم الخاطئ 9

> Query rewriting تغيّر intent المستخدم.

### لماذا هذا خطأ؟

هدفها هو التعبير عن information need نفسها بصيغة يسهل على retriever التعامل معها.

---

### المفهوم الخاطئ 10

> Multi-query و multi-hop RAG متطابقتان.

### لماذا هذا خطأ؟

يمكن لـ multi-query إصدار عدة عمليات بحث مترابطة بالتوازي، بينما تُنشئ multi-hop retrieval queries لاحقة اعتمادًا على معلومات تم اكتشافها في مراحل retrieval سابقة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Semantic search | Retrieval يعتمد على المعنى بدلًا من الاعتماد فقط على word overlap |
| Dense retrieval | Retrieval باستخدام dense query/document embeddings |
| Lexical search | Retrieval يعتمد على الكلمات/tokens وظهورها |
| BM25 | طريقة lexical ranking شائعة الاستخدام |
| Hybrid search | Search يجمع بين lexical و semantic retrieval signals |
| Embedding | Dense vector representation للنص |
| البحث عن أقرب الجيران (Nearest-neighbor search) | العثور على vectors الأقرب إلى query vector |
| FAISS | مكتبة تُستخدم في efficient vector similarity search |
| Vector database | Database مصممة لتخزين/query vector representations مع persistence و filtering features |
| Chunk | وحدة أصغر من document يتم فهرستها بصورة مستقلة |
| Chunk overlap | سياق حدودي مكرر تشترك فيه chunks المتجاورة |
| Retriever | مكون يختار documents/chunks التي يُحتمل أن تكون ذات صلة |
| Reranker | Model يعيد تقييم candidates اعتمادًا على relevance لـ query |
| Cross-encoder | Model يعالج query و candidate معًا لتحديد relevance |
| Precision@k | نسبة top-k results التي تكون ذات صلة |
| Average Precision | Ranking metric يأخذ متوسط precision عند المواضع التي تحتوي على نتائج ذات صلة |
| MAP | Mean Average Precision عبر عدة queries |
| nDCG | Ranking metric يدعم graded relevance و position discounting |
| RAG | التوليد المعزز بالاسترجاع |
| Grounded generation | Generation مشروط بأدلة خارجية تم retrieval لها |
| Query rewriting | إعادة صياغة user request إلى query محسّنة للبحث |
| Multi-query RAG | Retrieval للأدلة باستخدام عدة queries لسؤال مستخدم واحد |
| Multi-hop RAG | Retrieval متسلسل تعتمد فيه queries اللاحقة على معلومات تم retrieval لها سابقًا |
| Query routing | اختيار data source/retriever الذي يجب أن يتعامل مع query |
| Agentic RAG | Retrieval system يقرر فيه LLM إجراءات retrieval/tools بصورة ديناميكية |
| Citation recall | عدد claims المرتبطة بالعالم الخارجي التي تدعمها citations |
| Citation precision | مدى دعم citations فعليًا للـ claims المرتبطة بها |
| Faithfulness | اتساق الإجابة المولدة مع context المقدم |
| Answer relevance | درجة استجابة الإجابة المولدة لسؤال المستخدم |

## احتفظ بهذه الفكرة

**تجمع أنظمة البحث الحديثة بصورة متزايدة عدة مراحل متكاملة. تجد dense retrieval مرشحين مرتبطين دلاليًا، وتحافظ lexical search على قوة exact-match، وتحسن reranking ترتيب shortlist من النتائج، وتضيف RAG generator يجيب اعتمادًا على retrieved evidence. ولا تعتمد جودة النظام النهائي على LLM فقط، بل تعتمد أيضًا على chunking وجودة embeddings و candidate retrieval و reranking وبناء context وتعليمات grounding والتقييم. لذلك تعني هندسة RAG القوية تصميم وقياس pipeline الكاملة لـ retrieval و generation بدلًا من التعامل مع retrieval باعتبارها مجرد استدعاء واحد لـ vector search.**
