## 1. لماذا تحتاج مسارات عمل Machine Learning إلى pipelines

لا يقتصر نظام Machine Learning الواقعي عادةً على ضبط model واحد على بيانات خام.

وقد يبدو مسار العمل النموذجي هكذا:

```text
البيانات الخام (raw data)
   ↓
تغيير المقياس (scaling)
   ↓
استخراج الـ features (feature extraction)
   ↓
اختيار الـ features (feature selection)
   ↓
مصنّف أو model انحدار (classifier or regressor)
   ↓
التنبؤ (prediction)
```

يسمّي الفصل خطوات المعالجة المتصلة هذه **algorithm chain (سلسلة خوارزميات)**.

والمشكلة الرئيسية ليست كتابة شيفرة أقل فحسب. بل المشكلة الأهم هي التأكد من أن كل خطوة معالجة تتعلّم من البيانات الصحيحة.

### مثال: تغيير المقياس قبل SVM

لنفترض أننا نريد تدريب SVM على dataset سرطان الثدي (breast-cancer). ولأن الـ features المُدخَلة على مقاييس مختلفة، نطبّق أولًا `MinMaxScaler`.

وتبدو النسخة اليدوية هكذا:

⟦CODE_0⟧

والنمط المهم هو:

```text
اضبط (fit) الـ scaler على بيانات التدريب
حوّل (transform) بيانات التدريب
اضبط (fit) الـ model
transform لبيانات الاختبار بالـ scaler نفسه (SAME scaler)
قيّم (evaluate) الـ model
```

وهذا آمن في حالة تقسيم واحد إلى train/test.

وتظهر الصعوبة حين نجمع المعالجة المسبقة مع **cross-validation** أو **grid search**.

### الاختصار الخطِر

مسار عمل مغرٍ هو:

```text
1. اضبط الـ scaler على كل بيانات التدريب
2. حوّل كل بيانات التدريب
3. شغّل GridSearchCV على البيانات التي جرى تغيير مقياسها بالفعل
```

يبدو هذا صحيحًا في البداية لأن مجموعة الاختبار الخارجية لم تُستخدم.

لكن cross-validation ينشئ folds تدريب وتحقق داخلية خاصة به. فإذا ضُبط الـ scaler قبل إنشاء تلك الـ folds، فقد رأى الـ scaler بالفعل معلومات من كل fold.

وهذا يعني أن كل fold تحقق أثّر في المعالجة المسبقة قبل أن يُستخدم للتحقق.

وهذا هو **Information leakage (تسرّب المعلومات)**.

### المبدأ الصحيح

أي خطوة تتعلّم شيئًا من البيانات ينبغي أن تُضبط على جزء التدريب فقط من كل تقسيم cross-validation.

لذلك فالترتيب الصحيح مفاهيميًا هو:

```text
تقسيم Cross-validation رقم 1
    ├─ fold التدريب (training fold) -> fit للـ scaler -> fit للـ model
    └─ fold التحقق (validation fold) -> transform بالـ scaler المضبوط -> score

تقسيم Cross-validation رقم 2
    ├─ fold التدريب (training fold) -> fit لـ scaler جديد (NEW) -> fit لـ model جديد (NEW)
    └─ fold التحقق (validation fold) -> transform بالـ scaler المضبوط -> score

... كرّر لكل fold ...
```

وهذا بالضبط نوع العملية الذي صُمّم `Pipeline` لإدارته بأمان.


```text

هدف عشوائي (random target)
```

لكن إذا ضُبط اختيار الـ features على الـ dataset كاملًا **قبل** cross-validation، فقد يجد عن غير قصد features عشوائية تبدو مرتبطة بالهدف.

وعندها قد يعرض cross-validation درجة قوية بصورة غير واقعية.

والمشكلة ليست أن Ridge تعلّم فجأة نمطًا حقيقيًا. بل إن folds التحقق هي التي أثّرت في الـ features التي اختيرت.


- أخطاء أقل في المعالجة المسبقة
- تحويلات متسقة بين التدريب والاختبار
- cross-validation أكثر أمانًا
- اختيار features أكثر أمانًا
- grid search أسهل
- شيفرة أقصر وأوضح
- تجريب أسهل لمسارات العمل الكاملة

## مغالطات شائعة

### المغالطة 1

> إذا لم ألمس مجموعة الاختبار النهائية أبدًا، فلا يمكن أن تسرّب المعالجة المسبقة لكل بيانات التدريب قبل cross-validation أي معلومات.

### لماذا هذا خطأ

ينشئ cross-validation folds تحقق داخل مجموعة التدريب. فإذا ضُبطت المعالجة المسبقة على كل بيانات التدريب أولًا، فإن كل fold تحقق أثّر في تلك المعالجة. ولذلك لم تعد عملية التحقق مستقلة.

### المغالطة 2

> الـ Pipelines هي في الأساس طريقة أقصر لكتابة شيفرة المعالجة المسبقة.

### لماذا هذا خطأ

الشيفرة الأقصر مفيدة، لكن الفائدة الحاسمة أن الضبط (fitting) والتحويل (transforming) يحدثان في المكان الصحيح أثناء cross-validation والبحث في المعاملات.

### المغالطة 3

> يستطيع GridSearchCV ضبط معاملات الـ model النهائي فقط.

### لماذا هذا خطأ

يمكن ضبط معاملات الـ pipeline من أي خطوة بصيغة `step__parameter`. كما يمكن استبدال estimators كاملة وخطوات معالجة مسبقة أثناء البحث.

## المصطلحات الرئيسية

| المصطلح | المعنى |
|---|---|
| Algorithm chain | تسلسل من خطوات المعالجة المسبقة والتحويل والنمذجة |
| Pipeline | كائن في scikit-learn يجمع عدة خطوات معالجة في estimator واحد |
| Transformer | خطوة تتعلّم من البيانات وتنتج تمثيلًا محوَّلًا |
| Estimator | كائن يمكن ضبطه (fit) على البيانات |
| Information leakage | تأثير معلومات التحقق أو الاختبار في قرارات تُتخذ وقت التدريب |
| Cross-validation fold (جزء من التحقق المتقاطع) | تقسيم واحد تدريب/تحقق يُستخدم أثناء cross-validation |
| GridSearchCV | بحث مع cross-validation في تركيبات من الـ hyperparameters |
| `step__parameter` | صيغة تُستخدم للإشارة إلى معامل ينتمي إلى خطوة في pipeline |
| `named_steps` | تعيين يُستخدم للوصول إلى الـ estimators المضبوطة داخل pipeline |
| `best_estimator_` | أفضل estimator مضبوط وجده GridSearchCV |
| `make_pipeline` | دالة مساعدة تنشئ pipeline بأسماء خطوات تلقائية |
| Caching | إعادة استخدام الحسابات الوسيطة لتقليل العمل المكلف المتكرر |

## اختبر نفسك

قبل المتابعة، تأكّد أنك تستطيع الإجابة عن:

1. لماذا قد يسبب ضبط scaler قبل cross-validation تسرّبًا؟
2. ماذا تفعل `pipe.fit(X_train, y_train)` بالـ transformers الوسيطة؟
3. ما الفرق بين الضبط (fitting) والتحويل (transforming) أثناء التنبؤ؟
4. كيف تشير إلى المعامل `C` لخطوة في pipeline اسمها `svm`؟
5. لماذا ينبغي أن يكون اختيار الـ features داخل الـ pipeline أثناء cross-validation؟
6. كيف تستطيع فحص المعاملات (coefficients) من أفضل model وجده GridSearchCV؟
7. كيف يمكن لـ grid search أن يقارن بين خطوات معالجة مسبقة مختلفة أو عائلات models مختلفة؟
8. لماذا قد تصبح شبكة pipeline كبيرة جدًا مكلفة حسابيًا؟
9. متى يكون التخزين المؤقت للـ pipeline أنفع ما يكون؟
