## 1. عرّف المهمة قبل بناء الـ model

تبدأ الدروس التعليمية غالبًا بـ dataset نظيف ومهمة تنبؤ محددة بوضوح.

أما المشاريع الحقيقية فعادةً لا تبدأ هكذا.

فأنت تبدأ عادةً بمشكلة مثل:

```text
اكتشاف المعاملات الاحتيالية.
التوصية بالموسيقى للمستخدمين.
تحديد الرسائل المزعجة (spam).
التنبؤ بما إذا كان شخص ما سينقر على إعلان.
إيجاد المنتجات المعيبة على خط إنتاج.
```

وقبل تدريب أي شيء، عليك ترجمة مشكلة العالم الحقيقي إلى مسألة Machine Learning دقيقة.

ومسار عمل عالي المستوى مفيد هو:

```text
مشكلة العالم الحقيقي
      ↓
عرّف المُدخَلات والأهداف
      ↓
اختر نوع المهمة
      ↓
اجمع البيانات وافهمها
      ↓
اختر مقياس النجاح
```

### ابدأ بسياق العمل

اسأل لماذا تهم المشكلة.

ومن الأسئلة التي ينبغي بحثها:

- ما القيمة التي سيصنعها حل هذه المشكلة؟
- من سيستخدم الـ model؟
- كيف ستؤثر التنبؤات في عملية قائمة؟
- ما بيانات المُدخَل المتاحة؟
- ما البيانات التي يمكن جمعها فعلًا بصورة واقعية؟
- ما قيود الـ latency والخصوصية والكلفة والعتاد؟
- هل Machine Learning هو الحل المناسب أصلًا؟

وقد يكون model مبهرًا تقنيًا عديم الفائدة إذا كان يحل المشكلة الخطأ.

### عرّف المُدخَلات والأهداف

يتطلب كل مشروع تعلّم خاضع للإشراف (supervised learning) أمثلة تحتوي:

```text
المُدخَل X
→ المعلومات المتاحة للـ model

الهدف Y
→ ما يُتوقَّع أن يتنبأ به الـ model
```

مثلًا:

```text
كاشف الرسائل المزعجة

المُدخَل:
محتوى الرسالة أو features مشتقة من الرسالة

الهدف:
بريد مزعج (spam) / ليس بريدًا مزعجًا
```

ولا تستطيع تعلّم مهمة تنبؤ إلا حين تكون الأمثلة والأهداف المناسبة موجودة أو يمكن جمعها.

### حدّد نوع المهمة

بعد أن تفهم المُدخَل والهدف، اربط المشكلة بمهمة Machine Learning المناسبة.

وتشمل الأمثلة:

```text
اكتشاف الرسائل المزعجة
→ تصنيف ثنائي

صورة تحتوي مفاهيم متعددة
→ تصنيف متعدد الفئات ومتعدد الوسوم

التنبؤ بمعدّل النقر على الإعلان
→ انحدار قياسي

استرجاع صور أقمار صناعية مشابهة لمواقع معروفة
→ مسألة ترتيب (ranking) / تشابه
```

ولا تُجبر كل مشكلة على نوع model واحد.

وأحيانًا تكون طريقة لا تعتمد على Deep Learning — أو حتى التحليل الإحصائي العادي — أنسب.

### افهم الحلول القائمة

قبل استبدال عملية، تعلّم كيف تعمل اليوم.

فلعل المؤسسة تستخدم بالفعل:

- مراجعة يدوية،
- نظامًا قائمًا على القواعد،
- model إحصائيًا،
- أو model تعلّم آلة آخر.

وقد يصبح هذا الحل القائم خط أساسك لاحقًا.

### افهم القيود مبكرًا

يمكن لبيئة تشغيل الـ model أن تغيّر خياراتك التقنية تغييرًا جذريًا.

مثلًا:

```text
رسائل خاصة مشفَّرة
→ قد لا يُسمح للخادم برؤية المُدخَل
→ قد يلزم inference على الجهاز

فحص المصانع
→ يجب أن يحدث التنبؤ فورًا
→ قد يكون الـ latency المنخفض أهم من أقصى حجم للـ model
```

### تعرّف على افتراضاتك

في بداية المشروع، يوجد افتراضان رئيسيان:

1. يمكن التنبؤ بالهدف من المُدخَلات المقترحة.
2. تحتوي البيانات المتاحة معلومات كافية لتعلّم تلك العلاقة.

وهذان فرضيتان، لا ضمانان.

وإذا لم تكن المعلومات المطلوبة موجودة في المُدخَل، فلن تخلقها شبكة عصبية أقوى بصورة سحرية.

### ضع العواقب الأخلاقية في الحسبان

ليس مشروع Machine Learning صالحًا تلقائيًا لمجرد أن بناء model ممكن تقنيًا.

وينبغي أن تسأل:

- هل الهدف ذو معنى وصالح؟
- هل يمكن أن ترمّز التسميات تحيّزًا بشريًا؟
- من قد يتضرر من التنبؤات الخاطئة؟
- هل يجعل الـ deployment أحكامًا مشكوكًا فيها تبدو أكثر موضوعية لمجرد أن خوارزمية أنتجتها؟

فقد تكون لخيارات التصميم التقنية عواقب في العالم الحقيقي.

### جمع البيانات غالبًا هو الجزء الأصعب

حين تتحدد المهمة، تحتاج إلى بيانات.

وهذا يعني غالبًا:

```text
اجمع الأمثلة
      ↓
أنشئ التوسيمات (annotations)
      ↓
تحقق من جودة التوسيمات
      ↓
خزّن الـ dataset وأدِر إصداراته
```

وفي التعلّم الخاضع للإشراف، قد تأتي التسميات من:

- سجلات تاريخية قائمة،
- سلوك المستخدمين،
- المستشعرات،
- المُوسِّمين البشر (human annotators)،
- خبراء المجال،
- أو خدمات توسيم متخصصة.

### جودة التوسيم مهمة

تؤثر جودة تسمياتك تأثيرًا مباشرًا في ما يستطيع الـ model تعلّمه.

فقد يتطلب dataset طبي متخصصين مؤهلين، بينما قد لا يتطلب dataset بسيط للقطط مقابل الكلاب ذلك.

وتنشئ التوسيمات الضعيفة أو غير المتسقة أهدافًا مشوَّشة.

وإذا كانت الأهداف نفسها غير موثوقة، فقد ينتج حتى model محسَّن جدًا نتائج ضعيفة.

### البيانات التمثيلية

ينبغي أن تشبه بيانات التدريب البيانات التي سيصادفها الـ model بعد deployment.

تخيّل تدريب model للتعرّف على الطعام باستخدام صور مطاعم احترافية الإضاءة.

ثم يرفع مستخدمو الإنتاج:

```text
صور هاتف مظلمة
زوايا كاميرا غير معتادة
وجبات أُكل جزء منها
ضبابية حركة
إضاءة مختلفة
```

وقد يحقق model دقة اختبار ممتازة على بيانات تشبه مجموعة تدريبه ومع ذلك يؤدي أداءً سيئًا في الإنتاج.

والمشكلة ليست بالضرورة في الشبكة العصبية.

فقد لا يمثّل الـ dataset الواقع ببساطة.

### انجراف المفهوم (Concept drift)

وحتى البيانات التمثيلية لا تبقى تمثيلية إلى الأبد.

فقد يتغير سلوك الإنتاج مع الزمن.

ويُسمّى هذا **انجراف المفهوم (concept drift)**.

وتشمل الأمثلة:

```text
تتغير استراتيجيات الاحتيال
تتغير اللغة
تتغير تفضيلات المستهلكين
تتغير كتالوجات المنتجات
تتغير أذواق الموسيقى
```

ويفترض model دُرِّب على بيانات ماضية أن البيانات المستقبلية ستحتفظ بتشابهات مفيدة مع الماضي.

ويجب مراقبة هذا الافتراض بعد deployment.

### تحيّز العيّنات (Sampling bias)

يحدث تحيّز العيّنات حين لا تمثّل الأمثلة التي تجمعها عيّنة ممثِّلة للمجتمع أو البيئة التي تهمك.

مفاهيميًا:

```text
المجتمع الذي يهمك
        ≠
المجتمع الذي يمثّله الـ dataset
```

وإذا كان الـ dataset يستبعد مجموعات معينة باستمرار أو يبالغ في تمثيلها، فقد تصبح قياساتك وسلوك الـ model متحيّزة.

### افهم الـ dataset قبل التدريب

لا تعامل البيانات كصندوق أسود.

وقبل تطوير الـ model:

- افحص الأمثلة الخام،
- افحص تسمياتها،
- صوّر التوزيعات العددية،
- ادرس القيم المفقودة،
- تحقق من توازن الفئات،
- افحص الأنماط الجغرافية حين يهم الموقع،
- وتحرَّ عن الـ features المشبوهة.

### تسريب الهدف (Target leakage)

تحدث مشكلة خطرة حين تحتوي feature معلومات عن الهدف لن تكون متاحة فعليًا عند استخدام الـ model.

مثلًا، لنفترض أنك تريد التنبؤ بما إذا كان مريض سيُشخَّص لاحقًا بمرض، لكن إحدى features التدريب تسجّل ذلك التشخيص مباشرةً.

يبدو الـ model ممتازًا أثناء التطوير لأن الإجابة مخبأة فعليًا داخل المُدخَل.

وفي الإنتاج قد لا تكون تلك المعلومة موجودة بعدُ.

اسأل دائمًا:

> هل ستكون هذه الـ feature بعينها متاحة وقت التنبؤ؟

### عرّف النجاح قبل التدريب

لا تستطيع تحسين مشروع بفاعلية دون تحديد كيف سيُقاس النجاح.

وتشمل المقاييس الممكنة:

```text
الدقة (accuracy)
precision
recall
ROC AUC
معدّل الإيجابيات الكاذبة (false-positive rate)
معدّل السلبيات الكاذبة (false-negative rate)
الاحتفاظ بالعملاء
إيرادات العمل
```

وينبغي أن يعكس المقياس المختار الهدف الحقيقي للمشروع.

مثلًا، في اكتشاف الاحتيال، قد تهم السلبيات الكاذبة والإيجابيات الكاذبة أكثر بكثير من رقم دقة إجمالي مجرد.

## 2. طوّر model يعمّم فعلًا

حين تتضح المشكلة والبيانات ومعايير النجاح، يمكن أن يبدأ تطوير الـ model.

ويمكن تلخيص عملية التطوير هكذا:

```text
جهّز البيانات
    ↓
اختر بروتوكول التحقق
    ↓
تفوّق على خط أساس بسيط
    ↓
زد السعة حتى يظهر overfitting
    ↓
نظّم (regularize) واضبط
    ↓
درّب الـ model النهائي
    ↓
قيّم مرة واحدة على بيانات الاختبار
```

### تحويل البيانات إلى vectors (Data vectorization)

تعمل الشبكات العصبية على tensors.

ولذلك يجب تحويل البيانات الخام إلى تمثيلات عددية مناسبة للـ model.

وتُسمّى هذه العملية **vectorization**.

وتشمل الأمثلة:

```text
نص
→ تمثيلات token عددية

صورة
→ tensor من قيم البكسل

سجل جدولي
→ feature vector
```

### تطبيع القيم (Value normalization)

تتدرّب الشبكات العصبية عمومًا بسهولة أكبر حين تكون للمُدخَلات العددية مقاييس معقولة ومتجانسة نسبيًا.

مُدخَل إشكالي:

```text
feature A → من 0.1 إلى 0.8
feature B → من 500 إلى 50,000
feature C → من -3 إلى 4
```

وإجراء تطبيع شائع هو:

⟦CODE_0⟧

وبعد ذلك تتمركز كل feature تقريبًا حول الصفر بانحراف معياري قريب من واحد.

وحالة شائعة أخرى هي تحجيم الصور:

```text
قيم البكسل 0–255
       ↓ اقسم على 255
قيم 0–1
```

### معالجة القيم المفقودة

تحتوي الـ datasets الحقيقية غالبًا على سجلات غير مكتملة.

وبالنسبة إلى الـ features التصنيفية (categorical)، من الاستراتيجيات الممكنة إدخال فئة مخصصة تمثّل القيمة المفقودة.

وبالنسبة إلى الـ features العددية، تشمل الاستراتيجيات الممكنة استبدال القيمة المفقودة باستخدام إحصاءات مثل المتوسط أو الوسيط.

والمبدأ المهم هو معالجة الفقد عمدًا بدلًا من التظاهر بأنه غير موجود.

وإذا كانت قيم مفقودة ستحدث في الإنتاج، فينبغي أن يعرّض التدريب الـ model لحالات مشابهة كلما أمكن.

### اختر بروتوكول evaluation

الغرض من التحقق هو تقدير مدى تعميم الـ model على بيانات إنتاج لم يرها.

وثلاث استراتيجيات شائعة هي:

```text
التحقق بالاحتجاز (Hold-out validation)
→ مفيد حين تتوفر بيانات كثيرة

التحقق المتقاطع بطريقة K-fold
→ مفيد حين يكون الـ dataset صغيرًا

التحقق المتكرر بطريقة K-fold
→ مفيد حين تحتاج إلى تقدير أكثر موثوقية من بيانات محدودة
```

وأيًّا كانت الطريقة، ينبغي أن تمثّل بيانات التحقق توزيع الإنتاج وألا تحتوي أمثلة مكررة أو شبه مكررة من مجموعة التدريب.

### تفوّق على خط الأساس أولًا

هدف النمذجة الأول لديك ليس بناء أعقد شبكة ممكنة.

بل هو التفوق على خط أساس معقول.

وقد يكون خط الأساس:

- تخمينًا عشوائيًا،
- التنبؤ بالفئة الأغلبية،
- التنبؤ بمتوسط الهدف،
- نظامًا قائمًا على القواعد،
- أو model إحصائيًا بسيطًا.

وإذا لم يستطع model لك التفوق على خط أساس بسيط، فقد لا تحل زيادة تعقيد الـ model المشكلة الحقيقية.

فلعل المُدخَلات لا تحتوي ببساطة معلومات مفيدة كافية.

### القوة الإحصائية (Statistical power)

حين يؤدي model أداءً أفضل من خط أساس ذي معنى بصورة موثوقة، فهذا يثبت وجود إشارة تنبؤية مفيدة.

ويشير الفصل إلى هذا بتحقيق **القوة الإحصائية (statistical power)**.

وعند هذه النقطة تعرف أن تعلّم شيء مفيد من البيانات ممكن.

### الافتراضات المسبقة للمعمار (Architecture priors)

ينبغي أن يعكس اختيار معمار الـ model بنية المسألة.

وبحسب المهمة، قد تفكر في:

```text
شبكة Dense
ConvNet
معمار recurrent
Transformer
أو حتى نهج لا يعتمد على Deep Learning
```

ويمكن لبحث الأساليب الناجحة السابقة في مسائل مماثلة أن يوفّر وقتًا كبيرًا.

### دوال الخسارة ليست دائمًا مقاييس عمل

لا يصلح المقياس المستخدم لتقييم نجاح المشروع دائمًا ليكون خسارة تدريب قابلة للاشتقاق.

مثلًا، قد يُقيَّم مشروع باستخدام ROC AUC، لكن قد يُدرَّب الـ model باستخدام crossentropy لأن crossentropy تعمل جيدًا مع التحسين القائم على التدرّجات.

ولذلك تكون الخسارة أحيانًا بديلًا قابلًا للتدريب للمقياس الذي يهمك في النهاية.

### إعدادات المخرَج الشائعة

| المهمة | دالة التنشيط الأخيرة | الخسارة الشائعة | مقياس مثال |
|---|---|---|---|
| تصنيف ثنائي | Sigmoid | Binary crossentropy | الدقة / ROC AUC |
| تصنيف متعدد الفئات بوسم واحد | Softmax | Categorical crossentropy | الدقة / دقة top-k |
| تصنيف متعدد الوسوم | Sigmoid | Binary crossentropy | الدقة الثنائية / ROC AUC |
| انحدار | لا شيء | Mean squared error (متوسط مربعات الخطأ) | Mean absolute error (متوسط الخطأ المطلق) |

### لماذا ننشئ عمدًا model يعاني overfitting؟

بمجرد أن يتفوق model صغير لديك على خط الأساس، تحتاج إلى معرفة ما إذا كانت له سعة كافية.

واستراتيجية مفيدة هي زيادة سعة الـ model حتى تستطيع ملاحظة overfitting بوضوح.

ويمكنك ذلك بـ:

```text
إضافة مزيد من الطبقات
جعل الطبقات أكبر
التدريب لعدد أكبر من epochs
```

وأنت تبحث عن سلوك مثل:

```text
أداء التدريب يواصل التحسن
أداء التحقق يبدأ في التدهور
```

لماذا نعبر عمدًا إلى overfitting؟

لأنك تعرف الآن أن للـ model سعة كافية لملاءمة مسألة التدريب.

وتقع سعة الـ model المفيدة قرب الحدّ بين:

```text
underfitting
        ↕
تعميم جيد
        ↕
overfitting
```

### التنظيم والضبط (Regularization and tuning)

حين يستطيع الـ model عمل overfit، يكون الهدف التالي تعظيم التعميم.

وتشمل التجارب الممكنة:

- تغيير عدد الطبقات،
- تغيير عدد الوحدات،
- إضافة dropout،
- إضافة تنظيم L1 أو L2،
- تغيير معدّل التعلّم،
- تغيير hyperparameters أخرى،
- تحسين هندسة الـ features،
- إزالة الـ features عديمة الفائدة،
- جمع مزيد من البيانات،
- تحسين جودة التوسيم.

ويجب الحكم على كل تجربة باستخدام بيانات التحقق — لا مجموعة الاختبار النهائية.

### Overfitting على بيانات التحقق

يوجد هنا خطر خفي.

فإذا اتخذت قرارات متكررة بناءً على مجموعة تحقق واحدة، فأنت تكيّف عملية التطوير كلها تدريجيًا مع مجموعة التحقق تلك.

مفاهيميًا:

```text
درّب الـ model
   ↓
افحص التحقق
   ↓
غيّر المعمار
   ↓
افحص التحقق
   ↓
غيّر الـ hyperparameters
   ↓
افحص التحقق
   ↓
كرّر مرات كثيرة
```

وفي النهاية قد تعمل عملية التطوير نفسها overfit على بيانات التحقق.

ولهذا ما تزال هناك حاجة إلى مجموعة اختبار منفصلة.

### evaluation الـ model النهائي

بعد اختيار الإعداد النهائي:

1. درّب الـ model النهائي باستخدام بيانات التطوير المتاحة.
2. قيّمه مرة أخيرة على مجموعة الاختبار التي لم تُمَس.

وإذا كان أداء الاختبار أسوأ بكثير من أداء التحقق، فقد يكون إجراء التحقق لديك غير موثوق أو قد تكون عملية التطوير لديك قد عملت overfit على بيانات التحقق.

## 3. انشر الـ model بوصفه جزءًا من نظام حقيقي

الـ model الموجود داخل notebook ليس بعدُ نظام Machine Learning للإنتاج.

وبعد نجاح الـ evaluation النهائي، يجب دمج الـ model في البيئة التي سيستخدم فيها الناس أو البرمجيات تنبؤاته فعليًا.

### ضع توقعات واقعية

قد يفترض أصحاب المصلحة أن نظام AI يفهم المشكلة مثل الإنسان أو أن رقم دقة عاليًا يعني سلوكًا قريبًا من الكمال.

وينبغي أن تشرح:

- ما يستطيع الـ model فعله،
- ما لا يستطيع فعله،
- أين يميل إلى الإخفاق،
- كيف تبدو الأخطاء،
- وما العواقب التشغيلية لتلك الأخطاء.

فبدلًا من أن تقول فقط:

```text
دقة الـ model 98%.
```

قد يكون من الأنفع أن تنقل:

```text
كم حالة صالحة تُرفَض خطأً؟
كم حالة احتيالية تفوتنا؟
كم حالة تتطلب مراجعة يدوية كل يوم؟
```

وهذا يربط المقاييس التقنية بعواقب العمل.

### عتبات التنبؤ قرارات عمل أيضًا

لنفترض أن مصنِّف احتيال ينتج احتمالًا.

وما يزال عليك اختيار العتبة التي تُعلَّم عندها المعاملة بوصفها مشبوهة.

وتغيّر العتبات المختلفة التوازن بين:

```text
الإيجابيات الكاذبة
و
السلبيات الكاذبة
```

وليس هذا قرارًا رياضيًا بحتًا. فالمفاضلة الصحيحة تعتمد على سياق العمل.

### التدريب مقابل inference

أثناء التطوير، يؤدي الـ model عمليات تدريب.

وبعد deployment، يؤدي model الإنتاج عادةً **inference** فقط:

```text
مُدخَل جديد
   ↓
model مدرَّب
   ↓
تنبؤ
```

ولأن artifact الإنتاج لم يعد يحتاج إلى التدريب، يمكن غالبًا تحسينه للسرعة واستهلاك memory.

### الخيار 1: تقديم الـ model عبر API

معمار شائع هو:

```text
التطبيق
    ↓ طلب شبكة
خادم الـ model
    ↓
التنبؤ
    ↓ استجابة شبكة
التطبيق
```

ويمكن أن يعمل هذا النهج جيدًا حين:

- يتوفر اتصال إنترنت موثوق،
- يكون latency الشبكة مقبولًا،
- يُسمح للخادم بالوصول إلى المُدخَل،
- وتكون موارد الحوسبة المركزية مرغوبة.

ويمكن تصدير الـ models إلى صيغ موجَّهة لـ deployment بدلًا من ربطها بعملية تدريب Python الأصلية.

وتشمل الأمثلة المذكورة في المصدر TensorFlow SavedModel وONNX.

### الخيار 2: تشغيل الـ model على الجهاز

أحيانًا ينبغي أن يعمل الـ model مباشرةً على:

```text
هاتف ذكي
كاميرا
روبوت
حاسوب مدمج
متحكم دقيق (microcontroller)
```

ويفيد deployment على الجهاز حين:

- يجب أن يكون الـ latency منخفضًا جدًا،
- قد لا يتوفر اتصال إنترنت،
- تكون بيانات المُدخَل حساسة،
- أو يجب أن يعمل التطبيق دون اتصال.

لكن للأجهزة حدودًا في:

- memory،
- الحوسبة،
- طاقة البطارية،
- وحجم الـ model.

وهذا ينشئ مفاضلة بين جودة الـ model وكفاءة التشغيل.

### الخيار 3: تشغيل الـ model في المتصفح

إمكانية أخرى هي inference من جهة العميل في المتصفح.

وقد تشمل المزايا:

- تقليل كلفة الحوسبة على الخادم،
- إبقاء بيانات المستخدم على جهازه،
- تجنّب latency الذهاب والإياب عبر الشبكة،
- والسماح بالاستخدام دون اتصال بعد تنزيل الأصول.

وما يزال يجب أن يكون الـ model صغيرًا بما يكفي لتجنّب استهلاك مفرط لـ CPU أو GPU أو memory.

### الـ deployment قرار على مستوى الأنظمة

جدول قرار مفيد:

| المتطلب | الاتجاه المرجَّح |
|---|---|
| حوسبة مركزية كبيرة | الخادم/API |
| يجب أن يعمل دون اتصال | الجهاز/المتصفح |
| مُدخَل شديد الحساسية | الجهاز/المتصفح |
| latency صارم جدًا | الجهاز/inference محلي |
| عتاد صغير جدًا | model محسَّن على الجهاز |
| تحديثات مركزية سهلة | الخادم/API |

ولا يوجد خيار deployment صحيح عالميًا.

### تحسين inference

تتطلب بيئات deployment غالبًا models أصغر وأسرع.

وتقنيتان قدّمهما الفصل هما التقليم (pruning) وquantization.

#### تقليم الأوزان (Weight pruning)

لا يساهم كل معامل متعلَّم بالقدر نفسه في التنبؤ النهائي.

ويزيل التقليم الأوزان الأقل أهمية بحيث قد يتطلب الـ model memory وحوسبة أقل.

والمفاضلة هي:

```text
model أصغر / أسرع
        ↕
احتمال انخفاض في الأداء التنبؤي
```

#### Weight quantization (تكميم الأوزان)

تُدرَّب الـ models غالبًا بأوزان `float32`.

ويمكن للتكميم تمثيل الأوزان بقيم أقل دقة مثل `int8` أثناء inference.

مفاهيميًا:

```text
وزن float32
→ 32 بت

وزن int8
→ 8 بت
```

ويمكن لاستخدام عدد أقل من البتات أن يقلّل حجم الـ model تقليلًا كبيرًا.

## 4. راقب الـ model وصُنه بعد الإطلاق

ليس الـ deployment نهاية دورة حياة Machine Learning.

بل هو بداية حياة الـ model في العالم الحقيقي.

وبعد الإطلاق، راقب:

```text
تنبؤات الـ model
موثوقية النظام
بيانات الإنتاج
سلوك المستخدمين
نتائج العمل
```

### مقاييس الإنتاج مهمة

قد يملك model دقة جيدة خارج الإنتاج (offline) لكنه يخفق في تحسين المنتج الفعلي.

مثلًا، بعد نشر نظام توصية، قد يهمك ما إذا كان:

- المستخدمون يستمعون لفترة أطول،
- التفاعل يزداد،
- الاحتفاظ يتغير،
- أو الإيرادات تتحسن.

وقد تهم هذه النتائج أكثر من مقياس الـ model الأصلي خارج الإنتاج.

### اختبار A/B

إحدى طرق تقدير ما إذا كان model جديد يحسّن المنتج فعلًا هي اختبار A/B العشوائي.

مفاهيميًا:

```text
مستخدمو الإنتاج
      ↓
إسناد عشوائي
   ↙       ↘
النظام القديم  model جديد
   ↓          ↓
قارن النتائج الحقيقية
```

وتواصل مجموعة التحكم استخدام العملية السابقة بينما تستخدم المجموعة التجريبية الـ model الجديد.

ويمكن أن توفّر الفروق في النتائج حينئذٍ دليلًا على أثر الـ model في العالم الحقيقي.

### المراجعات اليدوية

حين يكون ذلك ممكنًا، افحص دوريًا تنبؤات الـ model على بيانات إنتاج جديدة.

ويمكنك أخذ عيّنة من حالات جديدة، والحصول على توسيمات بشرية موثوقة، ومقارنتها بتنبؤات الـ model.

وقد يكشف هذا أخطاء لم تكن موجودة في مجموعة الاختبار الأصلية.

### راقب بيانات الإنتاج

ينبغي أن تراقب أيضًا ما إذا كان توزيع المُدخَل يتغير.

مثلًا:

```text
تظهر عامية جديدة
تظهر استراتيجية احتيال جديدة
عتاد جديد يغيّر مظهر الصور
يتغير كتالوج المنتجات
يصل مجتمع مستخدمين جديد
```

وقد تجعل هذه التغيرات توزيع التدريب مختلفًا عن الإنتاج بصورة متزايدة.

### انجراف المفهوم يعني أن الـ models تشيخ

لا ينبغي افتراض أن model منشورًا سيبقى مفيدًا إلى الأبد.

فمع تغيّر سلوك الإنتاج، قد يتراجع الأداء تدريجيًا.

وتنجرف المجالات المختلفة بسرعات مختلفة.

وقد يتطلب اكتشاف الاحتيال تحديثات متكررة جدًا لأن الخصوم يغيّرون سلوكهم بنشاط.

وقد تبقى أنظمة أخرى مفيدة لمدة أطول بكثير.

### ابدأ جمع بيانات الـ model التالي فورًا

حلقة إنتاج قوية تبدو هكذا:

```text
انشر model v1 في الإنتاج
     ↓
اجمع بيانات الإنتاج
     ↓
حدّد الأمثلة الصعبة
     ↓
وسّم البيانات الجديدة
     ↓
درّب model v2
     ↓
قيّم
     ↓
انشر model v2 في الإنتاج
     ↓
كرّر
```

وقد تكون العيّنات التي يجدها الـ model الحالي صعبة قيّمة بصفة خاصة لأنها تكشف نقاط ضعف في حدّ القرار أو التمثيل الحاليين.

### مسار العمل العام الكامل

يمكن الآن تلخيص دورة الحياة كلها هكذا:

```text
1. DEFINE THE TASK (عرّف المهمة)

افهم مشكلة العمل
→ عرّف المُدخَلات والأهداف
→ اختر نوع المهمة
→ اجمع البيانات ووسّمها
→ افحص الـ dataset
→ اختر مقياس النجاح

2. DEVELOP THE MODEL (طوّر الـ model)

جهّز البيانات
→ اختر بروتوكول التحقق
→ تفوّق على خط أساس
→ كبّر الـ model حتى يستطيع عمل overfit
→ نظّم (regularize) واضبط
→ اختر الإعداد النهائي
→ قيّم على بيانات الاختبار

3. DEPLOY AND OPERATE (انشر وشغّل)

ضع التوقعات
→ صدّر model الـ inference
→ اختر بيئة التقديم
→ حسّن inference
→ راقب الإنتاج
→ اجمع بيانات جديدة
→ أعد تدريب الـ models المستقبلية
```

ولهذا فتدريب الـ model ليس إلا جزءًا واحدًا من هندسة Machine Learning.

ويعتمد نظام Machine Learning الناجح على مسار العمل كله.

## مغالطات مهمة

### المغالطة 1

> يبدأ مشروع Machine Learning باختيار معمار الشبكة العصبية.

### لماذا هذا خطأ

يبدأ المشروع الحقيقي بفهم المشكلة والبيانات المتاحة والأهداف والقيود ومقياس النجاح. أما اختيار الـ model فيأتي لاحقًا.

### المغالطة 2

> إذا كانت دقة الاختبار عالية، فسيعمل الـ model جيدًا تلقائيًا في الإنتاج.

### لماذا هذا خطأ

قد لا تمثّل مجموعة الاختبار بيانات الإنتاج. ويمكن أن تتسبب فروق التوزيع أو تحيّز العيّنات أو انجراف المفهوم في أداء إنتاج أسوأ بكثير.

### المغالطة 3

> يمكن لتعقيد أكبر في الـ model أن يعوّض دائمًا عن البيانات السيئة.

### لماذا هذا خطأ

لا يستطيع model أن يتعلّم إلا الأنماط الموجودة في البيانات المتاحة. ولا يمكن إصلاح المعلومات التنبؤية المفقودة أو التسميات المشوَّشة أو العيّنات غير التمثيلية تلقائيًا بإضافة مزيد من الطبقات.

### المغالطة 4

> مجموعة التحقق ومجموعة الاختبار تؤديان الغرض نفسه.

### لماذا هذا خطأ

تقود بيانات التحقق قرارات تطوير الـ model. وينبغي أن تبقى مجموعة الاختبار دون مساس حتى الـ evaluation النهائي لتوفّر تقديرًا أقل تحيّزًا للتعميم.

### المغالطة 5

> لا ينبغي أن يحدث overfitting أثناء التطوير أبدًا.

### لماذا هذا خطأ

يشجّع مسار العمل عمدًا على زيادة السعة حتى يظهر overfitting. وهذا يثبت أن للـ model سعة كافية. والخطوة التالية هي التنظيم والضبط عودةً نحو أفضل نقطة تعميم.

### المغالطة 6

> الـ deployment هو الخطوة الأخيرة، وبعده يكتمل المشروع.

### لماذا هذا خطأ

تتغير بيانات الإنتاج، ويحدث انجراف المفهوم، ويتغير سلوك المستخدمين. وتتطلب الـ models المنشورة مراقبة ومراجعة وجمع بيانات جديدة وإعادة تدريب في نهاية المطاف.

## المصطلحات الرئيسية

| المصطلح | المعنى |
|---|---|
| Problem framing | ترجمة حاجة من العالم الحقيقي إلى مهمة تنبؤ دقيقة |
| Input | المعلومات المتاحة للـ model وقت التنبؤ |
| Target | القيمة أو الفئة التي يُتوقع أن يتنبأ بها الـ model |
| Annotation | هدف يوفّره إنسان أو نظام ويرتبط بعيّنة |
| Representative data | بيانات تشبه التوزيع الذي سيواجهه الـ model في الإنتاج |
| Sampling bias | عدم تطابق منهجي ناتج عن طريقة جمع الـ dataset |
| Concept drift | تغيّر في بيانات الإنتاج أو علاقاتها مع الزمن |
| Target leakage | معلومات مُدخَل تكشف الهدف على نحو غير سليم ولن تكون متاحة في الإنتاج |
| Success metric | قياس يُستخدم لتحديد ما إذا كان المشروع يحقق هدفه |
| Vectorization | تحويل البيانات الخام إلى tensors عددية مناسبة للـ model |
| Normalization | إعادة تحجيم القيم العددية لتسهيل التحسين |
| Hold-out validation (التحقق بالاحتجاز) | حجز جزء ثابت من البيانات للتحقق |
| K-fold validation | تدريب متكرر مع أجزاء مختلفة تُستخدم للتحقق |
| Baseline | أداء مرجعي بسيط ينبغي أن يتفوق عليه الـ model |
| Statistical power | دليل على أن الـ model يستطيع تعلّم إشارة تنبؤية مفيدة تتجاوز خط الأساس البسيط |
| Architecture prior | اختيار عائلة model بناءً على افتراضات عن بنية المهمة |
| Hyperparameter | إعداد يختاره المطوّر ولا يُتعلَّم مباشرةً أثناء التدريب |
| Regularization | تقنية تُستخدم لتقليل overfitting وتحسين التعميم |
| Inference | استخدام model مدرَّب لإنتاج تنبؤات |
| Pruning | إزالة أوزان الـ model الأقل أهمية لتقليل الحوسبة والـ memory |
| Quantization | تمثيل معاملات الـ model بدقة عددية أقل |
| A/B testing | مقارنة نظام جديد بنظام تحكم باستخدام مجموعات إنتاج عشوائية |
| Production monitoring | تتبّع سلوك الـ model والبيانات والنظام والعمل بعد deployment |

6. ما تسريب الهدف (target leakage)؟
7. لماذا يجب أن يعكس مقياس نجاح المشروع هدف العالم الحقيقي؟
8. ما الـ vectorization؟
9. لماذا تُطبَّع الـ features العددية غالبًا؟
10. متى يكون التحقق بطريقة K-fold أفضل من مجموعة احتجاز بسيطة؟
11. ما الغرض من خط الأساس؟
12. لماذا قد تزيد حجم الـ model عمدًا حتى يعمل overfit؟
13. لماذا ينبغي أن تستند قرارات الضبط إلى بيانات التحقق لا بيانات الاختبار؟
14. متى قد يكون inference على الجهاز أفضل من API بعيدة؟
15. ما الفرق بين التقليم (pruning) وquantization؟
16. لماذا ينبغي أن يواصل model منشور جمع بيانات جديدة؟

## احتفظ بهذه الفكرة

**Machine Learning ليس مجرد تدريب model. يبدأ المشروع الناجح بتعريف المشكلة الحقيقية وبناء dataset تمثيلي، ويتواصل عبر تحقق دقيق وتطوير model، ويمتد بعد deployment عبر المراقبة وجمع البيانات والتحسين المستمر للـ model.**

تذكّر مسار العمل الكامل:

```text
DEFINE (عرّف)
المشكلة
→ البيانات
→ المقياس

DEVELOP (طوّر)
المعالجة المسبقة
→ التحقق
→ خط الأساس
→ overfit
→ التنظيم
→ الاختبار

DEPLOY (انشر)
اشحن
→ راقب
→ اجمع بيانات جديدة
→ أعد التدريب
```
