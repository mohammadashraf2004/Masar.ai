# نشر متقدم في GCP: التوسع التلقائي وموازنة الحمل عبر مناطق عالمية

> **المقرر:** أسس الـ Deployment الآمن على السحابة  
> **الدرس:** M08.L08  
> **مواءمة المصدر:** BOOK-XXX، الفصل 8. يتبع هذا الدرس إعدادات الفصل المرجعي في الصورة المخصصة (custom image) والقالب ومجموعة النسخ المُدارة والتوسع التلقائي وفحص الصحة وجدار الحماية وSSL وموازن الحمل العالمي وDNS.

---

## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح لماذا يحوّل المصدر قرص الـ VM المضبوط إلى صورة قابلة لإعادة الاستخدام.
- شرح لماذا يغيّر المصدر قاعدة حذف قرص الـ VM إلى `Keep disk`.
- بناء العلاقة المفاهيمية بين الصورة وقالب النسخة (instance template) ومجموعة النسخ المُدارة.
- شرح دور وسوم الشبكة في قوالب النسخ القابلة لإعادة الاستخدام.
- وصف مجموعتي النسخ المُدارتين في أوروبا والولايات المتحدة في المصدر.
- شرح الحدين الأدنى والأقصى لعدد النسخ والتوسع التلقائي بحسب استخدام موازن الحمل.
- شرح فحص الصحة العالمي عبر TCP على المنفذ 443 في المصدر.
- التمييز بين التوسع التلقائي (autoscaling) والإصلاح التلقائي (autohealing).
- شرح قاعدة جدار الحماية في المصدر التي تستهدف HTTPS ووسم شبكة.
- فهم أمثلة CIDR في المصدر: `/32` و`/24` والنطاقات الأوسع.
- رفع شهادة TLS والمفتاح الخاص الحاليين إلى مورد شهادة SSL عالمي في GCP.
- شرح جانبي الـ frontend والـ backend في Application Load Balancer الخارجي العالمي.
- شرح كيف تصبح مجموعتا النسخ المُدارتان الإقليميتان backends لموازن الحمل.
- شرح إعداد معدل الـ backend في المصدر وربط فحص الصحة.
- تحديث سجلات DNS من نوع A لتشير كل أسماء التطبيقات إلى عنوان IP العالمي لموازن الحمل.

## 1. انتقل من VM واحدة مضبوطة إلى صورة جهاز قابلة لإعادة الاستخدام

أنتج الفصل 7 VM واحدة تعمل.

ويسأل الفصل 8:

> كيف ننشئ نسخًا كثيرة متطابقة دون ضبط كل VM يدويًا؟

وجواب المصدر هو **صورة جهاز مخصصة (custom machine image)** مشتقة من قرص الـ VM الحالي.

### احتفظ بالقرص أولًا

قبل حذف الـ VM القديمة، يغيّر المصدر:

```text
قاعدة الحذف (Deletion rule)
حذف القرص (Delete disk)
→
الإبقاء على القرص (Keep disk)
```

ثم:

1. يوقف الـ VM،
2. يحذف نسخة الـ VM،
3. يُبقي القرص،
4. ينشئ صورة من ذلك القرص.

### لماذا نصوّر القرص؟

يحتوي القرص الأصلي أصلًا على:

```text
البرمجيات المثبّتة
ملفات المستودع
إعداد Docker
إعدادات التطبيق
حالة الـ deployment بالنطاقات الفرعية
```

وتلتقط الصورة القابلة لإعادة الاستخدام حالة الجهاز المجهّز هذه.

من الناحية المفاهيمية:

```text
قرص VM مضبوط
      ↓
صورة مخصصة (Custom image)
      ↓
نسخ VM مستقبلية كثيرة
```

### إعدادات الصورة في المصدر

يستخدم المثال:

```text
الاسم (Name): webserver-image-with-subdomains
المصدر (Source): Disk
الموقع (Location): Multi-regional
الموقع المختار (Selected location): eu
```

## 2. غلّف الصورة في قالب نسخة (instance template)

تصف الصورة المخصصة محتوى القرص.

أما **قالب النسخة (instance template)** فيصف كيف ينبغي إنشاء نسخ الـ VM الجديدة.

ينشئ المصدر:

```text
webserver-template-with-subdomains    # اسم القالب
```

مع:

```text
الموقع (Location): Global
نوع الجهاز (Machine type): e2-standard-4
صورة الإقلاع المخصصة (Custom boot image): webserver-image-with-subdomains
وسم الشبكة (Network tag): vm-network-tag
```

ويصف المصدر `e2-standard-4` بأنه:

```text
4 vCPUs
16 GB من الـ memory
```

### لماذا تهمّ القوالب؟

يوحّد القالب إعداد النسخ.

وبدلًا من إنشاء الـ VMs واحدة تلو أخرى، تستطيع أنظمة أعلى مستوى أن تقول:

> أنشئ نسخًا من هذا القالب.

### وراثة وسم الشبكة

يحمل القالب:

```text
vm-network-tag    # وسم الشبكة
```

حتى تطابق الـ VMs المنشأة منه قاعدة جدار الحماية القائمة.

وهذا مفهوم مهم يشبه البنية التحتية بوصفها شيفرة:

```text
عرّف مرة واحدة في القالب
→ كرّر بشكل متسق
```

## 3. أنشئ مجموعات نسخ مُدارة في منطقتين

ينشئ المصدر مجموعتي نسخ مُدارتين.

### مجموعة أوروبا

مثال:

```text
webserver-instance-group-europe    # اسم المجموعة
```

باستخدام:

```text
webserver-template-with-subdomains    # اسم القالب
```

في منطقة أوروبية متعددة النطاقات (multi-zone).

### مجموعة الولايات المتحدة

مثال:

```text
webserver-instance-group-us    # اسم المجموعة
```

باستخدام القالب نفسه في:

```text
us-east4    # منطقة الولايات المتحدة
```

### لماذا القالب نفسه؟

ينبغي أن تشغّل المنطقتان خوادم تطبيقات متكافئة.

ويضمن القالب شكل VM وصورة قرص متسقين.

من الناحية المفاهيمية:

```text
                 قالب عام (Global template)
                    /      \
                   /        \
          MIG أوروبا       MIG أمريكا (US)
          VM VM ...        VM VM ...
```

وهذه بداية التوزيع الجغرافي.

## 4. توسّع تلقائيًا بحسب استخدام موازنة حمل HTTP

لكل مجموعة نسخ مُدارة، يفعّل المصدر:

```text
إضافة النسخ وإزالتها تلقائيًا
```

مع:

```text
الحد الأدنى للنسخ (minimum instances): 1
الحد الأقصى للنسخ (maximum instances): 2
```

ثم يختار المصدر:

```text
نوع الإشارة (Signal type):
استخدام موازنة الحمل HTTP (HTTP load balancing utilization)
```

ويضبط الاستخدام المستهدف على:

```text
80%
```

### السلوك المطلوب

من الناحية المفاهيمية:

```text
تزداد الحركة/الحمل
      ↓
يقترب استخدام موازن الحمل من الهدف
      ↓
تضيف المجموعة المُدارة نسخة
```

وعندما ينخفض الطلب، يمكن للمجموعة تقليل النسخ ضمن الحدود المضبوطة.

### التوسع التلقائي محدود

وهو لا يعني:

```text
إنشاء عدد غير محدود من الأجهزة الافتراضية (VMs)
```

يقيّد المصدر المجموعة:

```text
1 ≤ النسخ ≤ 2
```

في التمرين.

### التوسع التلقائي مقابل التوسع اليدوي

يدويًا:

```text
المشغّل يراقب الحمل
المشغّل ينشئ VM
المشغّل يضمّه إلى الـ backend
```

أما التوسع التلقائي:

```text
المنصة تراقب الإشارة
المجموعة المُدارة تعدّل نفسها تلقائيًا
```

## 5. الإصلاح التلقائي بفحص صحة عالمي

يجيب التوسع التلقائي عن السؤال:

> كم نسخة ينبغي أن توجد؟

وتجيب فحوصات الصحة عن:

> أي النسخ سليمة بما يكفي لتقديم الخدمة؟

ينشئ المصدر:

```text
https-health-check    # اسم فحص الصحة
```

مع:

```text
النطاق (Scope): Global
البروتوكول (Protocol): TCP
المنفذ (Port): 443
```

### معايير الصحة

يضبط المصدر:

```text
فاصل الفحص (Check interval): 10 ثوانٍ
المهلة (Timeout): 5 ثوانٍ
عتبة السلامة (Healthy threshold): 2 نجاحات
عتبة العطب (Unhealthy threshold): 3 إخفاقات
التأخير الأولي (Initial delay): 60 ثانية
```

{{image:gcp-instance-group-health-check}}

### لماذا التأخير الأولي؟

قد تحتاج الـ VM الجديدة إلى وقت لتهيئة خدماتها.

وقد يؤدي الفحص المبكر جدًا إلى تصنيفها خطأً على أنها فاشلة.

### الإصلاح التلقائي (Autohealing)

تستخدم المجموعة المُدارة فحص الصحة لاستبدال الأعضاء غير السليمين.

### التمييز بين التوسع التلقائي والإصلاح التلقائي

```text
Autoscaling
→ تعديل العدد بحسب الحمل

Autohealing
→ استبدال النسخ غير السليمة
```

وهما يحلان مشكلتين مختلفتين.

## 6. اسمح بحركة HTTPS إلى النسخ المكرَّرة

يحدّث المصدر قاعدة جدار الحماية في GCP حتى تقبل النسخ الجديدة حركة HTTPS.

وهي تستهدف:

```text
vm-network-tag    # وسم الشبكة
```

وتسمح بـ:

```text
TCP 443
```

من نطاق المصدر المختار.

ويذكر أيضًا إمكانية التعامل مع SSH على المنفذ 22 اختياريًا.

### شرح CIDR في المصدر

يشرح المصدر:

```text
/32 → عنوان IPv4 واحد
/31 → عنوانان
/30 → أربعة عناوين
/24 → 256 عنوانًا
/16 → 65,536 عنوانًا
```

والفكرة الأساسية:

> كلما صغر رقم البادئة (prefix) اتسع نطاق العناوين.

ويوصي المصدر بتقييد الوصول بدلًا من فتحه عالميًا إلا إذا اقتضى السيناريو ذلك.

## 7. ارفع مادة TLS الحالية إلى Google Cloud

قبل إنشاء موازن حمل HTTPS العالمي، يرفع المصدر:

```text
الشهادة المدمجة (combined certificate)
المفتاح الخاص (private key)
```

إلى Cloud Shell.

وبنية مجلداته:

```text
~/config/lb-webserver_pro_combined.crt    # ملف الشهادة المدمجة
~/config/private/private.key
```

ثم ينشئ مورد شهادة SSL عالميًا:

⟦CODE_0⟧

وهذا يجعل الشهادة متاحة للـ frontend الخاص بموازن الحمل.

### دور الشهادة ينتقل إلى الخارج

في الفصل 7، كان Nginx على كل VM يتولى TLS.

ويقدّم الفصل 8 frontend لموازن حمل عالمي يمكنه أن يستخدم مورد الشهادة المرفوع بنفسه.

ويُضبط الـ backend في المصدر أيضًا باستخدام HTTPS.

## 8. أنشئ Application Load Balancer الخارجي العالمي بـ HTTPS

يختار المصدر:

```text
Application Load Balancer (HTTP/HTTPS)
مواجه للعامة (Public facing)
الأفضل لأحمال العمل العالمية (Best for global workloads)
Global external Application Load Balancer (الخارجي العالمي)
```

ويصبح هذا نقطة الدخول العالمية للتطبيق متعدد المناطق.

### إعداد الـ frontend

يضبط المصدر:

```text
البروتوكول (Protocol): HTTPS
إصدار IP (IP version): IPv4
عنوان IP محجوز للـ frontend (Reserved frontend IP)
المنفذ (Port): 443
الشهادة (Certificate): lb-webserver-cert
```

ويجيب الـ frontend عن السؤال:

> كيف يتصل العملاء؟

### خدمة الـ backend

ينشئ المصدر:

```text
https-lb-backend-webserver    # اسم خدمة الـ backend
```

مع:

```text
نوع الـ backend (Backend type): Instance group
البروتوكول (Protocol): HTTPS
المنفذ المسمّى (Named port): https-port
المهلة (Timeout): 30 ثانية
```

ثم يضيف:

```text
مجموعة النسخ المُدارة في أوروبا (Europe managed instance group)
مجموعة النسخ المُدارة في أمريكا (US managed instance group)
```

بوصفهما backends.

### إعدادات الحمل في الـ backend

لكل backend، يستخدم المصدر وضع موازنة **Rate** مع:

```text
الحد الأقصى لـ RPS (Maximum RPS): 50
النطاق (Scope): لكل نسخة
السعة (Capacity): 100
```

ويشير إلى أن الاستخدام (utilization) بديل.

### فحص الصحة

تربط خدمة الـ backend:

```text
https-health-check    # اسم فحص الصحة
```

حتى يمكن استبعاد/إصلاح النسخ غير السليمة.

### نموذج الطلب العالمي

```text
العميل
  ↓
Global HTTPS LB :443
  ↓
شهادة الـ frontend
  ↓
خدمة الـ backend
  ├── MIG أوروبا
  └── MIG الولايات المتحدة (US)
       ↓
نسخة سليمة
       ↓
حزمة التطبيق
```

## 9. انقل DNS من IP الثابت للـ VM إلى IP موازن الحمل

بعد إنشاء موازن الحمل العالمي، يحصل المصدر على عنوان IP الخارجي الخاص به.

ثم يحدّث سجلات Namecheap من نوع A:

```text
@         → عنوان IP لموازن الحمل
flask     → عنوان IP لموازن الحمل
jenkins   → عنوان IP لموازن الحمل
streamlit → عنوان IP لموازن الحمل
```

### تحول معماري مهم

قبل:

```text
DNS
 ↓
عنوان IP ثابت لـ VM واحدة
```

بعد:

```text
DNS
 ↓
عنوان IP لموازن الحمل العالمي
 ↓
مجموعات backend متعددة المناطق
```

تبقى الهوية العامة نفسها.

وتصبح البنية التحتية خلفها قابلة للتوسع وموزعة جغرافيًا.

### تحقق

يفحص المصدر:

```text
streamlit.domain
flask.domain
jenkins.domain
```

بعد انتشار DNS.

## 10. اجمع معمارية الفصل 8 الكاملة معًا

يمكن قراءة التصميم النهائي في المصدر على شكل طبقات.

### الطبقة 1 — الجهاز القابل لإعادة الاستخدام

```text
القرص المضبوط
→ صورة مخصصة
→ قالب نسخة عالمي
```

### الطبقة 2 — السعة الإقليمية

```text
قالب النسخة
→ مجموعة نسخ مُدارة في أوروبا
→ مجموعة نسخ مُدارة في الولايات المتحدة (US)
```

### الطبقة 3 — المرونة

```text
استخدام HTTP LB
→ توسع تلقائي 1..2
```

### الطبقة 4 — الصحة

```text
فحص صحة TCP 443
→ إصلاح تلقائي / صحة الـ backend
```

### الطبقة 5 — الأمان

```text
جدار الحماية
→ وسم الهدف vm-network-tag
→ HTTPS 443
```

### الطبقة 6 — نقطة الدخول العالمية

```text
frontend عالمي بـ HTTPS
→ الشهادة
→ خدمة الـ backend
→ مجموعتا أوروبا + US
```

### الطبقة 7 — التسمية المستقرة

```text
سجلات DNS من نوع A
→ عنوان IP لموازن الحمل العالمي
```

وهذا تطور كبير عن الـ deployment الأصلي على EC2/VM واحدة.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1
> "الصورة المخصصة وقالب النسخة شيء واحد."

تلتقط الصورة محتوى قرص الجهاز؛ أما القالب فيصف كيف ينبغي إنشاء الـ VMs الجديدة.

### المفهوم الخاطئ 2
> "التوسع التلقائي والإصلاح التلقائي متطابقان."

التوسع التلقائي يغيّر السعة. أما الإصلاح التلقائي فيستبدل النسخ غير السليمة.

### المفهوم الخاطئ 3
> "موازن الحمل العالمي يشير مباشرة إلى VM واحدة."

يستخدم المصدر مجموعات النسخ المُدارة بوصفها backends.

### المفهوم الخاطئ 4
> "يجب أن يعرف DNS أي منطقة ينبغي أن تخدم المستخدم."

يشير DNS إلى IP العالمي لموازن الحمل؛ ويتولى موازن الحمل/نظام الـ backend توزيع الحركة.

### المفهوم الخاطئ 5
> "يبقى IP الثابت للـ VM القديمة هو وجهة التطبيق العامة."

يغيّر الفصل 8 سجلات DNS إلى IP موازن الحمل.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| الصورة المخصصة (Custom image) | صورة جهاز قابلة لإعادة الاستخدام تُنشأ من قرص مضبوط |
| قالب النسخة (Instance template) | مواصفة قابلة لإعادة الاستخدام لإنشاء الـ VMs |
| مجموعة النسخ المُدارة (MIG) | مجموعة من نسخ الـ VM تُدار كوحدة واحدة |
| التوسع التلقائي (Autoscaling) | تعديل تلقائي لعدد النسخ |
| الإصلاح التلقائي (Autohealing) | استبدال/استرداد النسخ غير السليمة |
| فحص الصحة (Health check) | مسبار يُستخدم لتحديد صحة الـ backend |
| استخدام موازن الحمل (Load-balancer utilization) | إشارة التوسع التي يستخدمها المصدر |
| موازن الحمل العالمي الخارجي (Global external Application Load Balancer) | خدمة موازنة حمل HTTP/HTTPS عالمية وعامة يستخدمها المصدر |
| الـ Frontend | إعداد البروتوكول/IP/المنفذ/الشهادة المواجه للعميل |
| خدمة الـ Backend (Backend service) | إعداد يربط موازن الحمل بمجموعات النسخ |
| RPS | عدد الطلبات في الثانية |

4. لماذا نضمّن `vm-network-tag` في القالب؟
5. ما مجموعتا النسخ الجغرافيتان اللتان تُنشآن؟
6. ما الحدان الأدنى والأقصى لعدد النسخ في المصدر؟
7. ما إشارة التوسع والهدف اللذان يستخدمهما المصدر؟
8. ما فاصل فحص الصحة والمهلة والعتبات؟
9. ما الفرق بين التوسع التلقائي والإصلاح التلقائي؟
10. أي منفذ يستخدمه فحص الصحة؟
11. كيف تُرفع شهادة TLS إلى GCP؟
12. ماذا يضبط الـ frontend في موازن الحمل؟
13. ماذا تضبط خدمة الـ backend؟
14. أي المجموعات المُدارة تصبح backends؟
15. لماذا تتغير سجلات DNS من نوع A من IP الـ VM إلى IP موازن الحمل؟
16. تتبّع طلبًا واحدًا من المتصفح عبر المعمارية العالمية النهائية.
