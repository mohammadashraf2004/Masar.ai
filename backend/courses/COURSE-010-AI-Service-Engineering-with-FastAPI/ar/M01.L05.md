## 1. لماذا تصبح خدمات AI محجوبة

يمكن أن يخفي Demo لمستخدم واحد مشكلة Production مهمة.

لنفترض وصول Request واحدة:

```text
المستخدم A (User A)
  ↓
FastAPI
  ↓
Model inference — استدلال Model
  ↓
Response — الاستجابة
```

إذا استغرق Inference خمس ثوانٍ، ينتظر User خمس ثوانٍ.

قد يكون ذلك مقبولًا.

والآن تخيل Users كثيرين:

```text
المستخدم A (User A) ─┐
المستخدم B (User B) ─┼→ الخدمة نفسها (same service)
المستخدم C (User C) ─┤
المستخدم D (User D) ─┘
```

إذا لم تستطع Service إحراز تقدم في أعمال متداخلة، تبدأ Requests في الانتظار خلف بعضها.

يصنف الفصل Blocking operations إلى مجموعتين رئيسيتين.

### العمليات المقيدة بـ I/O (I/O-bound operations)

يكون Program في انتظار انتقال Data إلى الداخل أو الخارج.

ومن الأمثلة:

- قراءة Files أو كتابتها،
- Network requests،
- External API calls،
- Database queries،
- انتظار User input.

قد لا يكون لدى CPU سوى قدر ضئيل جدًا من العمل المفيد أثناء الانتظار.

### العمليات المقيدة بالحساب (Compute-bound operations)

يكون Program منشغلًا بتنفيذ Calculations مكلفة.

ومن الأمثلة:

- AI model inference،
- Training،
- Large data transformations،
- Simulation،
- التصيير ثلاثي الأبعاد (3D rendering).

هنا يكون CPU أو GPU مشغولًا فعليًا.

### فئة عملية ثالثة: Model serving المقيد بالذاكرة (memory-bound)

لاحقًا في الفصل، يشرح المصدر أن Large-model serving يمكن أن يصبح أيضًا **memory-bound**.

قد يكون Bottleneck هو نقل Model parameters و Caches الضخمة عبر GPU memory بدلًا من Arithmetic وحده.

لذلك، بالنسبة إلى أنظمة GenAI، يكون التصنيف المفيد:

```text
I/O-bound
→ تنتظر حركة البيانات أو أنظمة خارجية

Compute-bound
→ تنتظر حسابًا مكلفًا

Memory-bound
→ تنتظر نقل/الوصول إلى حالة النموذج الكبيرة وذاكرات caches
```

### لماذا يهم هذا التصنيف

يعتمد Optimization الصحيح على Bottleneck.

```text
I/O-bound
→ async I/O أو threading

حوسبة كثيفة على CPU
→ multiprocessing / عمّال منفصلون

inference لنماذج كبيرة
→ خادم inference متخصص + تحسينات النموذج

مهمة مستخدم طويلة التشغيل
→ سير عمل في الخلفية/طابور
```

لا تستخدم `async` لمجرد أن شيئًا ما بطيء.

حدد أولًا **لماذا** هو بطيء.

## 2. Concurrency مقابل Parallelism

هذان المصطلحان مرتبطان، لكنهما ليسا متطابقين.

### التزامن (Concurrency)

تعني Concurrency أن Tasks متعددة تحرز تقدمًا خلال فترات زمنية متداخلة.

ولا يلزم أن تعمل في اللحظة نفسها بالضبط.

تخيل Worker واحدًا يتعامل مع Tasks متعددة:

```text
الزمن ───────────────────────────→

Task A: ███ انتظار      ███
Task B:     ███ انتظار      ███
Task C:         ███ انتظار
```

ينتقل Worker إلى Task أخرى عندما تكون Task ما في حالة انتظار.

### التوازي (Parallelism)

تعني Parallelism أن Tasks تعمل فعليًا في الوقت نفسه على Compute resources منفصلة.

```text
نواة CPU 1: المهمة A █████████
نواة CPU 2: المهمة B █████████
نواة CPU 3: المهمة C █████████
```

### تشبيه المطعم

يستخدم المصدر تشبيهًا مفيدًا.

**Concurrency:**

شخص واحد:

```text
يأخذ الطلب (take order)
→ يبدأ الطهي (start cooking)
→ أثناء الطهي، يأخذ طلبًا آخر
→ يعود إلى الطهي
```

**Parallelism:**

عدة Workers:

```text
Worker 1 → يأخذ الطلبات
Worker 2 → يطهو
Worker 3 → يحضّر المشروبات
```

يحدث العمل فعلًا في الوقت نفسه.

{{image:concurrency-vs-parallelism}}

### لماذا تحتاج خدمات GenAI إلى المفهومين

قد تستخدم Service في الوقت نفسه:

```text
Async concurrency — تزامن Async
→ انتظار Databases و APIs

Parallel workers — Workers متوازية
→ CPU-heavy preprocessing

Specialized GPU server — خادم GPU متخصص
→ Parallelized model inference
```

غالبًا ما تجمع الأنظمة الكبيرة هذه Strategies بدلًا من اختيار واحدة فقط.

## 3. GIL و Threads و Processes

### الخيوط (Threads)

الـ **Thread** هو Execution flow داخل Process.

تشارك Threads داخل Process نفسه Memory.

يجعل ذلك Communication مناسبًا، لكن Shared memory تقدم Concerns مثل:

- Race conditions،
- Deadlocks،
- Resource contention،
- أمان Threads (Thread safety).

### GIL في Python

يقدّم الفصل **Global Interpreter Lock (GIL)**.

في Python runtime التقليدي الذي يناقشه المصدر، يعني GIL أن Thread واحدة فقط في كل مرة تنفذ Python bytecode داخل Process واحدة.

لذلك لا تمنحك Threads تلقائيًا CPU parallelism حقيقيًا.

ومع ذلك، ما يزال Threading مفيدًا مع Workloads كثيفة I/O.

لماذا؟

بينما تنتظر Thread عملية I/O، يمكن لأخرى إحراز تقدم.

### المعالجة متعددة العمليات (Multiprocessing)

تمتلك **Process** مساحة Memory معزولة خاصة بها.

مع Processes عديدة على CPU cores متعددة، يمكن تنفيذ Tasks بالتوازي.

```text
العملية 1 → نواة CPU 1
العملية 2 → نواة CPU 2
العملية 3 → نواة CPU 3
```

هذا مفيد للأعمال كثيفة Compute.

لكن العزل له تكلفة.

لا تستطيع Processes مشاركة Arbitrary in-memory objects بسهولة.

### لماذا يصبح ذلك مؤلمًا مع AI models كبيرة

لنفترض أن Model واحدًا يشغل قدرًا ضخمًا من Memory.

إذا حملت أربع Worker processes كل منها نسختها الخاصة:

```text
Worker 1 → نسخة Model (model copy)
Worker 2 → نسخة Model (model copy)
Worker 3 → نسخة Model (model copy)
Worker 4 → نسخة Model (model copy)
```

فقد يصبح استهلاك Memory هائلًا.

ولهذا فإن مجرد إضافة FastAPI worker processes أكثر ليست دائمًا وسيلة جيدة لتوسيع Large self-hosted models.

### Threading مقابل Multiprocessing

| الخاصية | Threads | Processes |
|---|---|---|
| Memory | مشتركة داخل Process | معزولة |
| Python CPU parallelism | محدودة بـ GIL في نموذج الفصل | يمكنها استخدام Cores متعددة |
| Communication | أسهل | أكثر تعقيدًا |
| أفضل استخدام هنا | انتظارات I/O / توافق الشيفرة المتزامنة | عمل متوازٍ كثيف على CPU |
| Concern مع AI model | قد تكون Shared state معقدة | قد تتكرر Large model |

### الدرس الأساسي

> **الطريقة التي توسع بها Web work العادي ليست تلقائيًا الطريقة التي ينبغي أن توسع بها Large model.**

غالبًا ما تحتاج Heavy models إلى Specialized serving infrastructure.

## 4. اختر Concurrency strategy وفق Workload

يقارن الفصل بين أربعة Execution styles عامة.

### من دون Concurrency

Code متسلسل وبسيط.

```text
المهمة A
  ↓
المهمة B
  ↓
المهمة C
```

المزايا:

- بسيط،
- قابل للتوقع،
- سهل Debugging.

العيب:

- كل Blocking operation تؤخر كل ما بعدها.

مناسب لـ:

- Tools صغيرة،
- Tasks غير متكررة،
- Single-user flows حيث يكون الانتظار مقبولًا.

### الإدخال/الإخراج غير المتزامن (Async I/O)

تدير Event loop واحدة Tasks كثيرة.

مناسب لـ:

- APIs،
- Database calls،
- Async file I/O،
- Web scraping،
- واجهات Provider model APIs.

المتطلب الرئيسي:

> يجب أن تتعاون كل Operation داخل Async path عبر كونها Nonblocking.

### تعدد Threads (Multithreading)

عدة Threads داخل Process واحدة.

مفيد عندما:

- لديك Blocking synchronous I/O libraries،
- يكون استبدال Library بنسخة Async غير عملي،
- يستطيع Framework نقل Sync work إلى Thread pool.

تشمل المفاضلات:

- Thread overhead،
- Race conditions،
- Deadlocks،
- تعقيد Shared state.

### المعالجة متعددة العمليات (Multiprocessing)

عدة Processes معزولة.

مفيد لـ:

- Compute-heavy CPU work،
- Independent chunks of processing،
- توزيع Workload عبر CPU cores.

المفاضلات:

- Process startup cost،
- Isolated memory،
- Inter-process communication complexity،
- Model duplication إذا حمّل كل Worker Model كبيرة.

### اختصار لاتخاذ القرار

اسأل:

```text
هل المهمة في الغالب تنتظر؟
→ استخدم async إذا كانت المكتبة تدعمه

هل هو I/O متزامن لا يمكن استبداله؟
→ قد يفيد thread pool

هل هي كثيفة على CPU؟
→ قد تفيد العمليات (processes)

هل هو GPU inference لنموذج كبير؟
→ قد يكون Model Serving خارجي متخصص أفضل
```

## 6. Event loop و Coroutines

تُعد **Event loop** الـ Scheduler المركزي في `asyncio`.

نموذج ذهني مناسب للمبتدئين هو:

```text
while Application يعمل:
    ابحث عن Tasks التي يمكنها إحراز تقدم
    شغّل واحدة
    إذا Await لعملية I/O:
        أوقفها مؤقتًا
        شغّل Task جاهزة أخرى
    استأنف Tasks المتوقفة عند اكتمال Events الخاصة بها
```

### يمكن لـ Coroutines التوقف دون فقد State

يمكن لـ Coroutine التوقف عند `await` ثم الاستئناف لاحقًا من المكان نفسه.

مفاهيميًا:

```text
تبدأ Coroutine
    ↓
تنفذ بعض العمل
    ↓
Await لطلب Network
    ↓
يُحفظ State
    ↓
تشغّل Event loop أعمالًا أخرى
    ↓
تكتمل Network
    ↓
تستأنف Coroutine
```

### تجميع العمليات باستخدام `asyncio.gather`

تكون `asyncio.gather(...)` مفيدة عندما يمكن بدء عدة Asynchronous operations مستقلة معًا.

على سبيل المثال:

⟦CODE_5⟧

بدلًا من:

```text

انتظر
اجلب B (fetch B)
انتظر

```

يمكنك تداخل فترات الانتظار الخاصة بها.

### التزامن (Concurrency) primitives

يشير المصدر أيضًا إلى أن asyncio تتضمن Tools مثل:

- Futures،
- Semaphores،
- أقفال (Locks).

لن تحتاج إلى إتقانها في هذا الدرس التمهيدي.

الفكرة المهمة هي أن البرامج Concurrent الحقيقية تحتاج في النهاية إلى Controls حول:

- عدد Tasks التي تعمل،
- كيفية الوصول إلى Shared state،
- كيفية تمثيل Completion.

## 7. واجهات Model-provider غير المتزامنة (Async model-provider APIs)

قد تكون Self-hosted model compute-bound على Hardware لديك.

لكن Hosted provider يغيّر طبيعة العمل **من منظور Application لديك**.

```text

انتظار Provider
      ↓
استلام Response
```

من منظور FastAPI process لديك، تكون Operation في الأساس Network I/O.

وهذا يجعل Async programming مفيدة جدًا.

### استدعاء Provider غير متزامن

⟦CODE_7⟧

أثناء الانتظار، يمكن لـ Event loop العمل على Requests أخرى.

### حدود المعدل (Rate limits)

لا تعني Concurrency:

```text
إرسال Requests غير محدودة فورًا
```

تفرض External providers حدودًا.

يقدّم الفصل Strategies مثل:

- Throttling،
- Exponential backoff،
- الانتظار قبل Retry،
- طلب Limits أعلى عندما يكون ذلك مناسبًا.

### فكرة Exponential backoff

```text
Failure 1 → Delay قصير
Failure 2 → Delay أطول
Failure 3 → أطول مرة أخرى
```

يقلل هذا الضغط على API مثقل أو Rate-limited.

### أخطاء Async الشائعة

يسلط المصدر الضوء على عدة أخطاء:

- خلط Blocking sync libraries داخل Async code،
- نسيان `await`،
- Await لشيء غير Awaitable،
- استخدام Sync HTTP client عندما تحتاج إلى Async،
- عدم إغلاق Network/Database resources،
- إنشاء Concurrent work غير محدود،
- جعل Debugging أصعب بسبب Control flow معقد وغير خطي.

### منهج التعلم الموصى به في المصدر

افهم Synchronous logic أولًا.

ثم حوّل I/O boundaries المناسبة إلى Async.

يجعل ذلك Control flow أسهل في الفهم.

## 8. Event loop و Thread pool في FastAPI

يدعم FastAPI كليهما:

و:

### Route غير متزامنة (Async route)

تعمل Async handler على Event loop الرئيسية.

وينبغي أن تنفذ Nonblocking asynchronous work.

```text
Async route — Route غير متزامنة
   ↓
Event loop
```

### Route متزامنة (Sync route)

يمكن أن تحتوي Synchronous route عادية على Blocking synchronous work.

يمكن لـ FastAPI/Starlette تفويضها إلى Internal thread pool حتى لا تُحجب Event loop الرئيسية مباشرة.

```text
Sync route — Route متزامنة
   ↓
Thread pool worker
```

### لماذا تكون Async أكثر كفاءة غالبًا مع I/O

تضيف Threads قدرًا من Overhead:

- Scheduling،
- Thread switching،
- اكتساب GIL (GIL acquisition).

إذا وُجدت Async-compatible library، يمكن لـ Event loop غالبًا إدارة I/O waits بقدر أقل من Overhead.

### لكن Sync routes ليست سيئة تلقائيًا

قد تكون Synchronous route خيارًا منطقيًا إذا كان Code متزامنًا.

يمكن لـ FastAPI عزلها في Thread pool.

الخطأ الخطر هو وضع Blocking code داخل Async route.

```text
        ↓
تحليل Text المفيد
        ↓

        ↓
```

## 11. مشروع: التحدث إلى المستندات باستخدام RAG

يبني الفصل بعد ذلك Module بسيطًا لـ **RAG**.

يضيف RAG معلومات خارجية إلى Prompt قبل Generation.

الفكرة العامة:

```text
سؤال User
     ↓
استرجاع Source content ذات صلة
     ↓
إضافة Content إلى Prompt
     ↓
LLM
     ↓
Answer — الإجابة
```

يحفّز المصدر استخدام RAG في Knowledge-intensive tasks حيث ينبغي لـ Model استخدام معلومات مخصصة بدلًا من الاعتماد فقط على Patterns من Training.

### لا يضمن RAG الصحة

هذا أساسي.

يمكن لـ RAG توفير Factual context ذات صلة.

لكن ما يزال بإمكان Model:

- إساءة فهم Context،
- تجاهل Instructions،
- استرجاع Evidence خاطئة،
- إنتاج Hallucinations.

لذلك RAG هو Grounding technique، وليس Proof system.

### Pipeline الكاملة لـ RAG

يقسم الفصل Pipeline إلى:

1. **Extraction**  
   الحصول على Text من Documents.

2. **Transformation**  
   تنظيف Text وتقسيمه.

3. **Embedding**  
   تحويل Text chunks إلى Vectors.

4. **Storage**  
   حفظ Vectors و Metadata في Vector database.

5. **Retrieval**  
   إنشاء Embedding لـ Query والعثور على Vectors ذات صلة دلاليًا.

6. **Augmentation**  
   إضافة Original text المسترجع إلى Prompt.

7. **Generation**  
   إرسال Question + Retrieved context إلى Language model.

## 14. Semantic search و Asynchronous vector storage

يستخدم المصدر Qdrant مثالًا لـ Vector database.

### ما الذي يُخزن؟

لكل Chunk، تحتفظ Database بـ:

- Embedding vector،
- Source information،
- النص الأصلي (Original text).

الاحتفاظ بـ Original text أساسي لأن Embedding تُستخدم لـ Similarity search، لكن LLM تحتاج Context قابلة للقراءة.

### تشابه Cosine (Cosine similarity)

يستخدم المصدر Cosine similarity لمقارنة Vectors.

التفسير للمبتدئين:

```text
Similarity أعلى
→ تتجه Vectors في Directions أكثر تشابهًا
→ يكون Text أكثر ترابطًا دلاليًا
```

تدفق Query:

```text
سؤال User
   ↓
Query embedding
   ↓
مقارنة مع Stored vectors
   ↓
ترتيب حسب Similarity
   ↓
إرجاع أعلى Matching chunks
```

### حد الاسترجاع (Retrieval limit)

قد تطلب:

```text
أفضل 3 نتائج (top 3 results)
```

بدلًا من كل Match.

### عتبة التشابه (Similarity threshold)

يمكنك أيضًا رفض Weak matches أسفل Threshold.

يمنع هذا Content غير المرتبطة بوضوح من الدخول تلقائيًا إلى Prompt.

### عميل Database غير المتزامن (Async database client)

الاتصال بـ Database هو I/O.

لذلك يستخدم المصدر Asynchronous Qdrant client.

تعرض Repository abstraction عمليات مثل:

- Create collection،

- Insert vector،
- البحث (Search).


يحافظ ذلك على Layered architecture المقدمة سابقًا.

```text

    ↓

    ↓
```

## 19. Latency مقابل Throughput

يوجد Metricان مهمان في Model serving طوال بقية الفصل.

### Latency

هي المدة التي تنتظرها Request واحدة للحصول على Output مفيد.

على سبيل المثال:

```text
تم إرسال Request
→ 2.3 seconds
→ وصلت أول Response
```

تشعر Latency الأقل عادة بمزيد من Responsiveness.

### معدل المعالجة (Throughput)

هو مقدار Work الذي يمكن لـ Server معالجته بمرور الوقت.

بالنسبة إلى LLMs، يمكن أن تشمل الأمثلة:

- Requests per unit time،
- Tokens في الدقيقة (Tokens per minute).

تعني Throughput الأعلى أن Service تتعامل مع Total work أكبر.

### المفاضلة

قد يحتاج Large high-quality model إلى Compute و Memory أكثر.

قد يعني ذلك:

```text
Model أكبر
→ ربما جودة Output أعلى
→ غالبًا Latency أكبر
→ غالبًا Throughput أقل
→ Infrastructure cost أعلى
```

لذلك لا يتعلق Model selection فقط بجودة Benchmark.

يسأل Production design أيضًا:

```text
كم عدد Users؟
ما السرعة المطلوبة لوصول Output؟
كم Hardware متاح؟
```

## 20. KV caching: تجنب إعادة حساب Attention state

تعمل Autoregressive LLM generation Token by token.

في كل Step:

```text
Sequence الحالية
    ↓
Attention computation
    ↓
Next token
    ↓
إضافة Token
    ↓
التكرار
```

سيكون من غير الفعال إعادة حساب كل Previous attention state من الصفر.

لذلك تحتفظ Serving systems بـ **key-value cache** أو **KV cache**.

### تبسيط الفكرة

يحسب Model Intermediate values مرتبطة بـ Attention لـ Tokens السابقة.

وبدلًا من التخلص منها:

```text
Previous attention state
        ↓
تخزين في GPU memory
        ↓
إعادة الاستخدام في Generation step التالية
```

يوفر ذلك Computation.

### التكلفة

تستهلك Cache مساحة GPU memory.

Sequences الأطول:

```text
Tokens أكثر
→ KV cache أكبر
```

Users المتزامنون الأكثر:

```text
Sequences أكثر
→ KV caches أكثر
```

ينشئ ذلك توترًا بين:

- Long context windows،
- Large batch sizes،
- Model size،
- سعة Users المتزامنين (Concurrent-user capacity).

ولهذا تصبح Memory optimization محورية في LLM serving.

## 21. Static batching مقابل Continuous batching

تُعد GPUs جيدة جدًا في Parallel matrix computation.

بدلًا من معالجة Request واحدة في كل مرة، يمكن لـ Inference server تجميع Work.

### التجميع الثابت (Static batching)

انتظر حتى يتكوّن Batch ثابت الحجم.

```text
Request A ┐
Request B ├→ Batch من 4 → Model
Request C ┤
Request D ┘
```

المشكلة:

تنتج Requests Output lengths مختلفة.

لنفترض:

```text
A تنتهي بعد 20 Tokens
B بعد 100
C بعد 35
D بعد 200
```

إذا عولج Batch بصورة جامدة، فقد تظل Slots المكتملة Idle بينما تستمر أطول Sequence.

### التجميع المستمر (Continuous batching)

يتغير Batch ديناميكيًا.

عندما تنتهي Request:

```text
تنتهي A
   ↓
تملأ Request جديدة E الـ Slot المتاحة
```

وبذلك يبقى Inference server الـ GPU أكثر انشغالًا.

{{image:continuous-batching}}

### لماذا يحسن ذلك Serving

تهدف Continuous batching إلى:

- GPU utilization أعلى،
- Throughput أعلى،
- Waiting time أقل،
- Resource use أكثر كفاءة.

يشير المصدر إلى أن Specialized servers مثل vLLM يمكن أن توفر هذه Mechanism تلقائيًا.

## 22. Paged attention: إدارة KV-cache memory بكفاءة أكبر

تنمو KV cache مع نمو Sequences.

يمكن أن يؤدي Traditional contiguous allocation إلى إهدار GPU memory بسبب Fragmentation.

يقدّم الفصل **paged attention** بوصفها Memory-management strategy.

### تشبيه Operating system

فكّر في Virtual memory pages.

بدلًا من اشتراط Physical block واحد كبير ومتصل:

```text
Logical sequence
→ Block table
→ عدة Physical pages
```

يفصل Mapping بين Logical order وموقع Physical storage.

### خطوات Paged attention

يصف المصدر تدفقًا مثل:

1. تقسيم KV cache إلى Fixed-size pages.
2. الحفاظ على Mapping/lookup structure.
3. تخصيص/تحميل Pages المطلوبة فقط.
4. استخدام Key/value blocks تلك أثناء Attention computation.

### لماذا يساعد ذلك

يمكن أن يقلل GPU memory المهدرة ويحسن القدرة على خدمة Variable-length sequences كثيرة.

نموذج ذهني مفيد هو:

```text
من دون Paging:
حجز KV regions كبيرة ومتجاورة
→ Fragmentation/waste

مع Paging:
تخصيص Blocks أصغر ديناميكيًا
→ Memory use أكثر مرونة
```

[[IMAGE_NEEDED: Paged attention memory mapping | Diagram showing a logical KV-cache sequence divided into blocks, a block table mapping those logical blocks to noncontiguous physical GPU-memory pages, and only required pages being accessed during attention | Learner should notice the analogy to virtual memory and the reduction of contiguous-memory waste]]

### التجميع المستمر (Continuous batching) + Paged attention

يكمل Optimizationان بعضهما:

```text
Continuous batching
→ Compute utilization أفضل

Paged attention
→ KV-cache memory utilization أفضل
```

يساعدان معًا Serving engine على التعامل بكفاءة مع Concurrent generation أكثر.

```text
يرسل User Job
       ↓
يقبل Server الـ Job
       ↓
Acknowledgement فوري
       ↓
يستمر Work
       ↓
تُخزن Result
       ↓
يفحص Client الـ Status / يتلقى Update
```

### مهام FastAPI الخلفية (FastAPI BackgroundTasks)

للمهام البسيطة، يوفر FastAPI Mechanism ملائمة.

مفاهيميًا:

⟦CODE_22⟧

يتلقى Client استجابة قبل اكتمال Work كله.

### أنماط ممكنة لتسليم Result

يقترح الفصل أفكارًا مثل:

- تخزين Results لاسترجاعها لاحقًا،
- توفير Polling endpoint،
- تحديث Client عبر Live connection،
- إشعار User عند الاكتمال.

### قيد مهم

لا تنشئ Background tasks **Parallelism حقيقية**.

إذا عملت Background task كثيفة Compute مباشرة على Event loop، فما يزال بإمكانها حجب Server.

وبالمثل، يمكن لـ Async background function تستخدم Blocking operations داخليًا أن تحجب.

### Background tasks المتزامنة (Synchronous background tasks)

يمكن لـ FastAPI وضع Sync background functions العادية في Thread pool.

يساعد ذلك مع Blocking operations المناسبة، لكنه لا يحول CPU-intensive inference إلى Parallel model serving فعالة.

## 24. متى لا تكون BackgroundTasks كافية

تُعد FastAPI background tasks ملائمة لـ Jobs بسيطة.

لكن Production workloads قد تحتاج إلى:

- Retries،
- Durable queues،
- Failure handling،
- Task status،
- Multiple workers،
- Distributed processing،
- Scheduling،
- التحكم في Backpressure.

يذكر المصدر Infrastructure أكثر تخصصًا مثل:

- Celery،
- Redis،
- RabbitMQ،
- Ray Serve،
- BentoML،
- خادم vLLM.

تهم Categories أكثر من حفظ أسماء Products.

### Framework لخدمة Model (Model-serving framework)

الأفضل لـ:


```text
Retries

```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Concurrency و Parallelism تعنيان الشيء نفسه.

### لماذا هذا خطأ

تعني Concurrency إحراز تقدم متداخل في Tasks متعددة. وتعني Parallelism أن Tasks تعمل فعليًا في الوقت نفسه على Compute resources منفصلة.

### المفهوم الخاطئ 2

> تمنح Threads في Python CPU parallelism غير محدودة.

### لماذا هذا خطأ

في Execution model الذي يصفه المصدر، يمنع GIL Threads متعددة داخل Python process واحدة من تنفيذ Python bytecode في الوقت نفسه.

### المفهوم الخاطئ 3

> تجعل `async def` أي Function بطيئة Nonblocking.

### لماذا هذا خطأ

ما تزال Synchronous blocking operation داخل Async route تحجب Event loop.

### المفهوم الخاطئ 4

> ينبغي حل كل Task بطيئة باستخدام Async I/O.

### لماذا هذا خطأ

تكون Async ذات قيمة أساسًا عندما ينتظر Work عمليات I/O. أما CPU/GPU-heavy compute فتحتاج Strategies مختلفة.

### المفهوم الخاطئ 5

> Hosted LLM API هي Compute-bound داخل FastAPI process لدي.

### لماذا هذا خطأ

من منظور Service لديك، يحدث Heavy inference عن بُعد. وتنتظر Process لديك في الغالب Network I/O.

### المفهوم الخاطئ 6

> يلغي RAG الـ Hallucinations.

### لماذا هذا خطأ

يمكن لـ RAG إضافة Evidence ذات صلة، لكن Retrieval قد تفشل وما يزال Language model قادرًا على إنتاج Unsupported output.

### المفهوم الخاطئ 7

> تحتاج Vector database إلى Embeddings فقط.

### لماذا هذا خطأ

تحتاج RAG pipeline أيضًا إلى Metadata/Original text قابلة للقراءة حتى توفر Vectors المسترجعة Context فعلية لـ Model و Sources للمستخدمين.

### المفهوم الخاطئ 8

> إضافة المزيد من FastAPI worker processes هي دائمًا أفضل طريقة لتوسيع Large model.

### لماذا هذا خطأ

قد تحتاج كل Process إلى Model copy خاصة بها، ما يستنزف Memory بسرعة.

### المفهوم الخاطئ 9

> يعني وجود GPU كبيرة أن Inference لن تكون Memory-bound أبدًا.

### لماذا هذا خطأ

تنقل Large models و KV caches كميات ضخمة من Data عبر GPU memory؛ وقد تصبح Memory bandwidth و Capacity من Bottlenecks الرئيسية.

### المفهوم الخاطئ 10

> يزيد Batching دائمًا Latency.

### لماذا هذا خطأ

يمكن لـ Naive static batching أن تضيف Waiting و Idle capacity، بينما صُممت Continuous batching لإعادة ملء Work ديناميكيًا وتحسين Overall utilization.

### المفهوم الخاطئ 11

> KV caching مجانية.

### لماذا هذا خطأ

هي تتجنب إعادة الحساب لكنها تستهلك قدرًا كبيرًا من GPU memory، خصوصًا مع Long sequences و Concurrent users كثيرين.

### المفهوم الخاطئ 12

> تشغّل FastAPI BackgroundTasks الـ Heavy inference بالتوازي تلقائيًا.

### لماذا هذا خطأ

هي توفر Mechanism مريحة للتنفيذ بعد Response، لكن Heavy compute ما تزال قادرة على الحجب ما لم تُنقل إلى External workers/model servers المناسبة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| العملية الحاجبة (Blocking operation) | عمل يمنع Execution flow من التقدم حتى يكتمل |
| المقيد بـ I/O (I/O-bound) | عمل يهيمن عليه انتظار Files أو Networks أو Databases أو Users أو I/O أخرى |
| المقيد بالحساب (Compute-bound) | عمل يهيمن عليه CPU/GPU computation |
| المقيد بالذاكرة (Memory-bound) | عمل تحده بدرجة كبيرة Memory movement/access بدلًا من Arithmetic وحده |
| التزامن (Concurrency) | إدارة Tasks متعددة خلال فترات متداخلة |
| التوازي (Parallelism) | تنفيذ Tasks في الوقت نفسه على Compute resources منفصلة |
| الخيط (Thread) | Execution flow داخل Process تشارك Memory الخاصة بها |
| العملية (Process) | Program منفذ ومعزول وله Memory space خاصة به |
| قفل GIL | Global Interpreter Lock الذي يصفه المصدر بأنه يحد تنفيذ Python bytecode المتزامن عبر Threads داخل Process واحدة |
| تقسيم الزمن (Time slicing) | تبديل CPU time بين Tasks لإحراز تقدم متداخل |
| الإدخال/الإخراج غير المتزامن (Async I/O) | Cooperative concurrency تسمح لـ Tasks بالتخلي عن Control أثناء انتظار I/O |
| الدالة القابلة للإيقاف والاستئناف (Coroutine) | كائن تنفيذ Async function يمكنه التوقف ثم الاستئناف لاحقًا |
| حلقة الأحداث (Event loop) | Scheduler تشغّل/تستأنف Asynchronous tasks |
| الكلمة `await` | تسلّم Control أثناء انتظار Awaitable operation |
| تجمع Threads (Thread pool) | Worker threads مُنشأة مسبقًا تُستخدم للعمليات Synchronous/blocking |
| تعدد العمليات (Multiprocessing) | تشغيل Work في Processes مستقلة متعددة، غالبًا عبر CPU cores |
| التراجع الأُسّي (Exponential backoff) | Retry strategy تزيد Waiting time بعد Failures المتكررة |
| نظام RAG | Retrieval-augmented generation: استرجاع Context خارجية قبل Generation |
| التمثيل المتجهي (Embedding) | Vector representation تُستخدم لمقارنة Semantic content |
| Semantic search | Retrieval قائم على Vector meaning/similarity بدلًا من Exact keywords |
| تشابه Cosine (Cosine similarity) | Vector similarity measure المستخدمة في أمثلة Semantic search في الفصل |
| قاعدة بيانات Vector (Vector database) | Database محسنة لتخزين Vector representations والبحث فيها |
| مكوّن Repository | Data-access abstraction بين Services و Database client |
| Generator غير متزامن (Async generator) | Generator يمكن لتكراراته Await عمليات غير متزامنة |
| Latency | Delay الذي تواجهه Request واحدة قبل استلام Output |
| معدل المعالجة (Throughput) | مقدار Model-serving work المكتمل لكل وحدة زمن |
| ذاكرة KV المؤقتة (KV cache) | Transformer key/value attention state مخزنة يُعاد استخدامها أثناء Autoregressive generation |
| التجميع الثابت (Static batching) | تجميع Requests في Fixed-size batches |
| التجميع المستمر (Continuous batching) | ملء/استبدال Request slots ديناميكيًا مع بدء Generations وانتهائها |
| Attention مقسمة إلى Pages (Paged attention) | KV-cache memory-management strategy باستخدام Page/block mappings |
| خادم Model (Model server) | Service منفصلة ومتخصصة في تشغيل Model inference |
| مهمة خلفية (Background task) | Work يبدأ بعد إمكان إعادة Main HTTP response |
| طابور مهام (Task queue) | Infrastructure لـ Durable asynchronous jobs و Retries و Worker distribution |
