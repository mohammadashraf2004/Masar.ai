# Model Context Protocol: البنية والتنفيذ

> **الدرس:** M01.L07  
> **مواءمة المصدر:** الفصلان 10 و11 من مادة Early Release المقدَّمة.  
> يدمج هذا الدرس الجانب النظري والتنفيذ العملي في مسار تعلم واحد متصل.

---

## مخرجات التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يمكن لعدد قليل من Tools المكتوبة مباشرة داخل الكود أن يصبح غير قابل للإدارة عند التوسع إلى بيئة production.
- وصف المعضلات الأربع السابقة لـ MCP التي يؤكد عليها المصدر.
- شرح كيف تُنشئ APIs الخاصة بـ function calling لكل مزوّد نوعًا من الارتباط على مستوى التنفيذ.
- شرح لماذا لا يحل structured function calling وحده مشكلات sandboxing أو orchestration أو dynamic discovery.
- وصف أدوار `Host` و`Client` و`Server` في MCP.
- شرح لماذا ينشئ `Host` واحد `Client` مخصصًا لكل `Server` متصل.
- تتبع runtime discovery بدءًا من configuration مرورًا بـ `tools/list` وصولًا إلى toolset مجمَّعة.
- شرح كيف يتيح MCP نموذج capabilities بنمط plug-and-play.
- التمييز بين `Tools` و`Resources` و`Prompts` في MCP.
- شرح لماذا تكون `Tools` تحت تحكم Model، و`Resources` تحت تحكم application، و`Prompts` تحت تحكم المستخدم وفق صياغة المصدر.
- شرح `Sampling` في MCP باعتباره طلبًا من `Server` إلى `Host` للاستعانة بقدرات reasoning المركزية للـ Model.
- شرح `Elicitation` باعتباره توقف `Server` لطلب إدخال منظَّم من المستخدم.
- مقارنة `Stdio` و`Streamable HTTP` بوصفهما transports محلية وبعيدة لـ MCP.
- شرح لماذا يُعد `Stdio` مناسبًا للـ Tools المحلية، ولماذا تحتاج الخدمات البعيدة إلى network security أقوى.
- بناء `MCP Server` بسيط على المستوى المفاهيمي باستخدام `FastMCP`.
- شرح كيف تتحول decorators وtype hints وdocstrings إلى JSON schemas يراها Model.
- شرح دور `MCPToolset` في ADK كما يصفه المصدر.
- تتبع MCP handshake: التشغيل، initialization، عرض Tools، ثم adaptation.
- شرح كيف يلغي dynamic discovery الحاجة إلى تكرار Tool schemas يدويًا داخل `Host`.
- تتبع طلب مستخدم من `ADK Runner` عبر `MCPToolset` إلى process معزولة للـ Server ثم عودته.
- شرح كيف يمكن لـ `MCP Server` إرجاع image content وكيف يمكن لـ `Host` أو Agent متعدد الوسائط استهلاكه.
- شرح لماذا قد تحتاج واجهات المستخدم إلى اعتراض events الخاصة بنتائج Tool لعرض binary/media output مباشرة.
- استخدام مفهوم `MCP Inspector` لعزل `Server` وتصحيح أخطائه قبل دمجه مع `Host`.
- شرح لماذا يمكن لمخرجات `print()` العشوائية إفساد protocol stream يعمل عبر stdio.
- تطبيق ممارسات security الواردة في المصدر على subprocess commands وenvironment variables.
- الاختيار بين `Stdio` وremote HTTP-style transports وفق deployment topology.
- شرح وعد "اكتب مرة واستخدم في كل مكان" الذي يقدمه Tool Server موحَّد بالمعيار.

## 1. لماذا وُجد MCP

أوضحت الدروس السابقة كيف يمكن لـ Agent استدعاء Python function.

في prototype صغير، قد يكون هذا كافيًا:

```text
Agent — الوكيل
  ↓
get_weather() — استدعاء Tool للطقس
  ↓
Weather API — واجهة الطقس
```

تظهر المشكلة عندما يكبر النظام.

تخيّل Agent يمتلك:

```text
10 tools — 10 أدوات
50 tools — 50 أداة
100 tools — 100 أداة
```

قد تكون لكل Tool:

- API خاصة بها،
- credentials،
- معالجة أخطاء خاصة،
- schema،
- قواعد شبكة،
- متطلبات security.

يقدّم المصدر MCP باعتباره الانتقال من:

```text
isolated custom integrations — تكاملات مخصّصة ومعزولة
```

إلى:

```text
a standardized capability ecosystem — منظومة capabilities موحَّدة بالمعيار
```

فالهدف ليس مجرد جعل **Tool Calling** أكثر أناقة.

بل هو فصل:

```text
agent intelligence — ذكاء Agent
```

عن:

```text
tool implementation and connectivity — تنفيذ Tool وآلية اتصالها
```

## 2. أربع معضلات للتوسع قبل MCP

يسلط المصدر الضوء على أربع مشكلات رئيسية.

### 2.1 كتلة Glue Code أحادية (Glue Code Monolith)

تضيف كل Tool منطق routing جديدًا.

مفاهيميًا:

⟦CODE_0⟧

كلما زاد عدد Tools، أصبح التطبيق المركزي شديد الارتباط بها جميعًا.

### 2.2 كابوس Security (Security Nightmare)

لا تجعل طلبات Tool المنظَّمة عملية التنفيذ آمنة تلقائيًا.

إذا طلب Model:

```text
execute_python(...)
```

فلا يزال التطبيق يحتاج إلى:

- sandboxing،
- permission checks،
- isolation،
- الموافقة (approval).

### 2.3 State Machine مرتجلة (Ad-Hoc State Machine)

غالبًا ما تتحول workflows متعددة الخطوات إلى loop يدوية:

```text
call model — استدعِ Model
inspect tool request — افحص طلب Tool
execute tool — نفّذ Tool
append result — أضف النتيجة
call model again — استدعِ Model مرة أخرى
repeat — كرر
```

ويصبح الحفاظ على هذا الأسلوب أصعب مع ازدياد التعقيد.

### 2.4 Toolset ثابتة (Static Toolset)

إذا جرى تضمين Tools مباشرة داخل كود Agent:

⟦CODE_1⟧

فإن إضافة capability جديدة تتطلب:

1. تعديل كود Agent،
2. تعديل قائمة Tools،
3. إعادة نشر التطبيق.

وهذه ليست بنية plug-in حقيقية.

## 3. Tool أحادية هشة

يفحص المصدر أولًا Tool نفسها.

قد تحتوي Weather function على:

```text
API endpoint — عنوان API
API key — مفتاح API
provider-specific JSON parsing — تحليل JSON خاص بالمزوّد
provider-specific errors — أخطاء خاصة بالمزوّد
```

ينتج عن ذلك ثلاث مشكلات.

### الهشاشة (Brittleness)

إذا غيّر المزوّد response schema، تتعطل function.

### ضعف قابلية التوسع (Lack of scalability)

كل capability خارجية جديدة تحتاج إلى implementation مخصص جديد.

### نقص المرونة (Inflexibility)

يصبح التطبيق مرتبطًا ضمنيًا بالمزوّد.

يُحسن وجود حد موحَّد للـ `Server` هذا الوضع.

ينبغي أن يهتم Agent فقط بأن:

```text
There is a tool called get_weather. — توجد Tool اسمها get_weather.
```

ويمكن للـ `Server` أن يقرر داخليًا أي مزوّد سينفذها.

## 4. الارتباط بالمزوّد في function calling

حسّن native function calling موثوقية Agents لأن Model يستطيع إخراج طلبات Tool منظَّمة.

لكن مزوّدي Models يعرضون هذه الطلبات بطرق مختلفة.

قد يعرض أحد المزوّدين:

```text
response.choices[...].tool_calls
```

بينما يعرض آخر:

```text
response.content[...] type=tool_use — مسار مختلف لطلب Tool
```

حتى عندما يكون طلب Tool نفسه متطابقًا مفاهيميًا، قد يحتاج كود التطبيق إلى التغيير.

وهذا يعني وجود نوعين من الارتباط:

```text
Agent ↔ Tools — ارتباط Agent بالـ Tools
Agent ↔ LLM provider API — ارتباط Agent بـ API مزوّد LLM
```

يهدف MCP إلى توحيد جانب الاتصال بين `Host` وTool بحيث يستطيع `Host` العمل كـ universal adapter.

## 5. لماذا لا يكفي function calling وحده

يحل function calling سؤال:

```text
How does the model express a structured request? — كيف يعبّر Model عن طلب منظَّم؟
```

لكنه لا يحل تلقائيًا:

```text
How do tools get discovered? — كيف تُكتشف Tools؟
How are they routed? — كيف يُوجَّه كل طلب؟
How are they sandboxed? — كيف تُعزل داخل sandbox؟
How is state managed? — كيف تُدار state؟
How can new tools be added dynamically? — كيف يمكن إضافة Tools جديدة ديناميكيًا؟
How can one tool ecosystem work across model vendors? — كيف تعمل منظومة Tools واحدة عبر مزوّدي Models مختلفين؟
```

هذا التمييز مهم.

> function calling جزء واحد من التفاعل. أما MCP فيحدد بنية اتصال أوسع حول capabilities.

## 6. بنية MCP: التطبيق المضيف والعميل والخادم (Host, Client, Server)

يصف المصدر ثلاثة أدوار أساسية.

### التطبيق المضيف (Host)

هو التطبيق الرئيسي الموثوق.

ومن أمثلته وفق صياغة المصدر:

- تطبيق AI لسطح المكتب،
- امتداد IDE،
- Agent framework مخصص.

يقوم `Host` بـ:

- تشغيل orchestration،
- إدارة تفاعل Model،
- إدارة user state،
- تحديد وقت اكتمال المهام،
- فرض security،
- قراءة configuration الخاصة بالـ Servers.

### الخادم (Server)

هو مزوّد capability متخصص.

أمثلة:

```text
Git Server — خادم Git
Filesystem Server — خادم نظام الملفات
GitHub Server — خادم GitHub
Stock Data Server — خادم بيانات الأسهم
```

ينبغي أن يركز كل `Server` على capability domain واحدة.

### العميل (Client)

هو مكوّن protocol يعيش داخل `Host`.

ينشئ `Host` `Client` مخصصًا لكل `Server`.

مفاهيميًا:

```text
Host — التطبيق المضيف
├── Client A -> Git Server — عميل A إلى خادم Git
├── Client B -> Filesystem Server — عميل B إلى خادم نظام الملفات
└── Client C -> GitHub Server — عميل C إلى خادم GitHub
```

## 7. Host هو المنسّق الموثوق

يتولى `Host` مسؤوليات كانت موزعة سابقًا داخل custom code.

### تشغيل orchestration engine

يمكنه إدارة:

```text
conversation state — حالة المحادثة
model calls — استدعاءات Model
tool loop — حلقة Tool
termination — الإنهاء
```

### فرض Security

يمكن لـ `Server` طلب إجراء حساس.

ويستطيع `Host` أن يقرر:

```text
allow? — هل يسمح؟
deny? — هل يرفض؟
ask user? — هل يسأل المستخدم؟
```

وبذلك تصبح الثقة مركزية.

### إدارة Configuration

يعرف `Host` أي Servers متصلة.

وهذا ما يسمح بجعل capabilities قابلة للتهيئة بدلًا من تضمينها مباشرة في source code الخاص بالـ Agent.

## 8. Server هو المتخصص في Tools

ينبغي أن يكون `Server` مستقلًا عن منطق Model الخاص بالـ Agent.

مثال:

```text
Stock Server — خادم الأسهم
```

يعرف:

```text
stock prices — أسعار الأسهم
company metadata — metadata الخاصة بالشركات
financial API details — تفاصيل API المالية
```

ولا ينبغي أن يحتاج إلى معرفة:

```text
which LLM is being used — أي LLM يُستخدم
what the user's conversation history contains — ماذا يحتوي سجل محادثة المستخدم
how the Host orchestrates the task — كيف ينسق Host المهمة
```

يعني هذا الفصل أن `Server` نفسه يمكنه خدمة عدة `Hosts`.

---

## 9. Client هو قناة الاتصال الآمنة

يعيش `Client` داخل `Host`.

يؤكد المصدر علاقة one-to-one:

```text
one Client — Client واحد
    ↔
one Server — Server واحد
```

لماذا يفيد ذلك؟

لأن:

```text
Git Client — عميل Git
```

لا يحصل تلقائيًا على وصول إلى:

```text
GitHub Server — خادم GitHub
Filesystem Server — خادم نظام الملفات
```

وهذا يقلل cross-server coupling.

كما يمنح `Host` تحكمًا أوضح في capabilities المتصلة.

## 10. اكتشاف capabilities بنمط plug-and-play

ينقل المصدر capabilities من قائمة Tools المكتوبة مباشرة داخل Agent إلى configuration.

مفاهيميًا:

⟦CODE_2⟧

عند runtime:

```text
1. Host reads configuration — يقرأ Host الـ configuration
2. Host launches/connects to Servers — يشغّل Host الـ Servers أو يتصل بها
3. Host creates a Client per Server — ينشئ Host Client لكل Server
4. Host asks each Server for available tools — يسأل Host كل Server عن Tools المتاحة
5. Host aggregates all discovered capabilities — يجمع Host كل capabilities المكتشفة
6. Host provides them to the model — يقدّمها Host إلى Model
```

لإضافة capability:

```text
start/configure another Server — شغّل أو هيّئ Server إضافيًا
```

بدلًا من:

```text
rewrite core agent code — أعد كتابة الكود الأساسي للـ Agent
```

## 11. primitives في MCP: اللغة المشتركة

تحدد architecture من يتواصل.

أما primitives فتحدد ما الذي يتواصلون بشأنه.

يقسم المصدر primitives إلى اتجاهين.

### primitives التي يقدمها Server

ما يقدمه `Server` إلى `Host`:

```text
Tools — أدوات تنفيذية
Resources — بيانات ومصادر
Prompts — workflows قابلة لإعادة الاستخدام
```

### طلبات Client-side من Server

ما يمكن لـ `Server` أن يطلبه من `Host`:

```text
Sampling — استعانة بالـ reasoning المركزي
Elicitation — طلب إدخال منظَّم من المستخدم
```

وهذا يجعل MCP ثنائي الاتجاه.

## 12. Tools: يدا Agent

تمثل `Tool` سلوكًا قابلًا للتنفيذ.

يعرض `Server`:

```text
name — الاسم
description — الوصف
JSON Schema — مخطط JSON
```

وقد يقرر Model استخدامها.

يستقبل `Host` طلب Tool بصيغة خاصة بالمزوّد ثم يترجمه إلى استدعاء MCP موحَّد.

مفاهيميًا:

```text
LLM-specific request — طلب بصيغة خاصة بالـ LLM
     ↓
Host adapter — محوّل Host
     ↓
tools/call — استدعاء Tool
     ↓
Server — الخادم
```

يفصل ذلك implementation الخاص بالـ `Server` عن مزوّد Model.

### نموذج التحكم وفق المصدر

يصف المصدر `Tools` بأنها:

```text
model-controlled — تحت تحكم Model
```

لأن Model قد يختار وقت استدعائها.

## 13. Resources: مكتبة Agent

يمثل `Resource` بيانات خاملة.

أمثلة:

```text
file://... — Resource ملف
git://... — Resource من Git
database-like URI — URI شبيه بمصدر قاعدة بيانات
```

يمكن لـ `Host` اكتشاف `Resources`.

ويقرر `Host`:

```text
which resource to read — أي Resource يقرأ
when to read it — متى يقرأه
how much to include — ما مقدار المحتوى الذي يضمّه
```

لذلك يصف المصدر `Resources` بأنها:

```text
application-controlled — تحت تحكم التطبيق
```

### لماذا يهم ذلك لنافذة context

لا ينبغي أن يرسل `Server` كميات ضخمة من البيانات تلقائيًا.

يمكن لـ `Host` استخدام retrieval strategies مثل:

```text
search — البحث
RAG — استرجاع مدعوم بالسياق
metadata filtering — التصفية باستخدام metadata
```

ثم يجلب المحتوى ذي الصلة فقط.

وهذا يحافظ على كفاءة context.

---

## 14. Prompts: دليل عمل Agent

يمكن لـ `MCP Server` عرض `Prompts` قابلة لإعادة الاستخدام ومزوّدة parameters.

أمثلة:

```text
Generate Unit Test — إنشاء Unit Test
Plan Vacation — تخطيط إجازة
Review Pull Request — مراجعة Pull Request
```

يمكن لـ `Host` إظهارها على هيئة:

- أزرار،
- slash commands،
- نماذج (forms).

ويختار المستخدم workflow.

لذلك يصف المصدر `Prompts` بأنها:

```text
user-controlled — تحت تحكم المستخدم
```

ويمكن للـ `Server` إرجاع تسلسل محدد مسبقًا من الرسائل بعد أن يقدّم المستخدم parameters.

## 15. تحكم Model وapplication والمستخدم

هذه طريقة مفيدة لتذكر العروض الثلاثة الرئيسية التي يقدمها `Server`.

| Primitive | جهة التحكم الأساسية وفق المصدر | الغرض |
|---|---|---|
| Tool تنفيذية | Model | تنفيذ إجراء |
| Resource للبيانات | Host/application | قراءة بيانات context |
| Prompt قابل لإعادة الاستخدام | المستخدم | بدء workflow قابلة لإعادة الاستخدام |

يساعد هذا الفصل على منع الخلط المفاهيمي.

## 16. Sampling: استعانة Server بقدرات reasoning لدى Host

يُعد `Sampling` من أكثر primitives في MCP إثارة للاهتمام.

قد يكون `Server` جيدًا في:

```text
fetching data — جلب البيانات
performing API operations — تنفيذ عمليات API
```

لكنه لا يحتوي على LLM خاص به.

افترض أن `Flight Server` يسترجع 50 رحلة.

يمكنه جلب البيانات.

لكن تحديد أي رحلة هي "الأفضل" قد يحتاج إلى reasoning.

بدلًا من تضمين Model آخر داخل `Server`، يمكنه طلب المساعدة من `Host`.

### نموذج ذهني لمحادثة متداخلة (Nested conversation)

المحادثة 1:

```text
Host -> Server: — من Host إلى Server
find_best_flight(...) — استدعاء البحث عن أفضل رحلة
```

يجلب `Server` عدد 50 خيارًا.

ثم المحادثة 2:

```text
Server -> Host: — من Server إلى Host
Please reason over these 50 options. — حلّل هذه الخيارات الخمسين باستخدام reasoning.
```

يستخدم `Host` الـ LLM المركزي لديه.

ثم يعيد توصية.

ويستأنف `Server` المحادثة 1 ويعيد النتيجة النهائية للـ Tool.

هذا يبقي:

```text
intelligence — الذكاء
cost control — التحكم في التكلفة
security control — التحكم في security
```

مركزيًا داخل `Host`.

## 17. Sampling خطوة بخطوة

### استدعاء Tool الأصلي

```text
Host — التطبيق المضيف
  ↓
tools/call: find_best_flight — استدعاء Tool للبحث عن أفضل رحلة
  ↓
Flight Server — خادم الرحلات
```

### مواجهة Server لحاجة إلى reasoning

لديه:

```text
50 raw flights — 50 رحلة خام
```

لكنه يحتاج إلى حكم مقارن.

### طلب Server لعملية Sampling

مفاهيميًا:

```text
sampling/createMessage — طلب إنشاء رسالة Sampling
```

مع:

- messages،
- system guidance،
- البيانات المطلوب تحليلها.

### تحديد Host ما إذا كان سيسمح

يظل `Host` هو trust boundary.


## 20. Stdio للاتصال المحلي

مع `Stdio`:

```text
Host launches Server as child process — يشغّل Host الـ Server كـ child process
```

ثم:

```text
Host -> Server stdin — يرسل Host إلى stdin الخاص بالـ Server
Server -> Host stdout — يعيد Server عبر stdout إلى Host
```

المزايا:

- بسيط،
- سريع،
- لا يحتاج network port،
- مفيد للـ Tools المحلية.

استخدامات مناسبة:

- desktop agents،
- coding assistants،
- عمليات Git المحلية،
- filesystem tools،
- قواعد البيانات المحلية.

### ميزة Security

يبقى الاتصال على الجهاز المحلي.

ولا توجد حاجة إلى TCP port مكشوف لمجرد وصل `Host` و`Server`.

## 21. Streamable HTTP للـ capabilities البعيدة

بالنسبة إلى Servers البعيدة:

```text
Host — التطبيق المضيف
  ↓ HTTPS — اتصال آمن عبر HTTPS
Remote MCP Server — خادم MCP بعيد
```

استخدامات مناسبة:

- تكاملات SaaS،
- خدمات الشركات،
- cloud microservices،
- خوادم معرفة مشتركة (shared knowledge servers).

يناقش المصدر `HTTP POST` إلى جانب streaming mechanisms للتحديثات التي يبدأها `Server`.

تتطلب transports البعيدة اهتمامًا أقوى بـ:

- authentication،
- authorization،
- TLS،
- التعامل مع عدة Clients،
- أعطال الشبكة (network failures).

## 29. MCP handshake وdynamic discovery

يصف المصدر startup flow تقريبًا كما يلي:

```text
1. Launch Server — شغّل Server
2. Initialize protocol — هيّئ protocol
3. List available tools — اعرض Tools المتاحة
4. Adapt discovered schemas — كيّف schemas المكتشفة
```

### التشغيل (Launch)

يشغّل `Host` process الخاصة بالـ `Server`.

### التهيئة (Initialize)

ينشئ `Client` و`Server` capabilities الخاصة بالـ protocol.

### عرض Tools (List Tools)

يسأل `Host`:

```text
What tools do you expose? — ما Tools التي تعرضها؟
```

### التكييف (Adapt)

تتحول Tool schemas إلى function declarations يمكن للـ Model استخدامها داخل Agent framework.

وهذا يعني أن إضافة Tool جديدة إلى `Server` يمكن أن تصبح:

```text
change Server — عدّل Server
restart/reconnect — أعد التشغيل أو الاتصال
discover automatically — اكتشف تلقائيًا
```

بدلًا من:

```text
copy schema into Host — انسخ schema إلى Host
edit agent code — عدّل كود Agent
redeploy core logic — أعد نشر المنطق الأساسي
```

## 38. Security: حماية parameters الخاصة بتشغيل process

يسمح `Stdio` لـ `Host` بتشغيل processes.

وهذه قدرة قوية.

لكنها تُنشئ مخاطر أيضًا.

يحذر المصدر من بناء:

```text
command — أمر التشغيل
args — معاملات التشغيل
```

مباشرة من user strings غير موثوقة.

لماذا؟

لأن process invocation قد تتحول إلى command injection.

### تصميم أكثر أمانًا

- اكتب trusted executable بشكل ثابت،
- اكتب arguments بشكل ثابت أو تحقّق منها بصرامة،
- استخدم allow-lists،
- تجنب shell interpolation،
- لا تمرر user strings عشوائية إلى process launch.

---

## 39. Security: التحكم في inheritance للـ environment

قد ترث child processes متغيرات environment من `Host`.

وقد تتضمن secrets مثل:

- model API keys،
- database credentials،
- رموز خدمات داخلية (internal service tokens).

لا ينبغي أن يحصل `MCP Server` غير الموثوق على جميع secrets الخاصة بالـ `Host` تلقائيًا.

يوصي المصدر بالتعامل عمدًا وبحذر مع child environment.

المبدأ العام:

> امنح `Server` فقط environment variables التي يحتاج إليها فعليًا.

وهذا تطبيق آخر لمبدأ least privilege.

## 40. اختيار Stdio أو remote HTTP وفق topology

### فضّل Stdio عندما:

- يكون `Server` محليًا،
- يمتلك `Host` الـ process،
- يكون الاستخدام داخل desktop app،
- يكون العمل local development،
- تكون Tool خاصة بـ private repo،
- لا توجد حاجة إلى shared multi-client service.

### فضّل remote HTTP-style transport عندما:

- يعمل `Host` و`Server` على جهازين مختلفين،
- يكون `Server` خدمة مشتركة داخل المؤسسة،
- تكون هناك حاجة إلى independent scaling،
- يتطلب الأمر cloud deployment.

هذا قرار deployment وليس مجرد تفضيل في كتابة الكود.

## 41. لماذا يهم remote transport للخدمات المشتركة

يعني `Stdio` عادةً:

```text
one Host launches one Server process — Host واحد يشغّل process واحدة لـ Server
```

أما بالنسبة إلى Tool مركزية لمعرفة الشركة، فقد ترغب بدلًا من ذلك في:

```text
many Hosts — عدة Hosts
   ↓
one scalable remote MCP service — خدمة MCP بعيدة واحدة قابلة للتوسع
```

ويتيح ذلك:

- independent scaling،
- central governance،
- shared maintenance،
- مصادقة موحَّدة (common authentication).

لكنه يضيف أيضًا:

- network security،
- concurrency،
- availability،
- observability.

## 42. اكتب مرة واستخدم في كل مكان

يختتم المصدر بأهم وعد يتعلق بـ interoperability.

لا ينبغي أن ينتمي `MCP Server` المصمم جيدًا إلى Agent framework واحد فقط.

إذا كان يتحدث MCP، فيمكن نظريًا أن تتصل به:

```text
ADK Host — Host يعمل مع ADK
IDE Host — Host داخل IDE
Desktop AI Host — Host لتطبيق AI على سطح المكتب
Custom Agent Host — Host مخصص لـ Agent
```

جميعها عبر `Server` نفسه دون إعادة كتابة المنطق الداخلي للـ `Server`.

وهذا هو المعنى الأعمق لتشبيه المصدر MCP بـ "USB-C for AI".

فالحد الموحَّد يسمح لـ:

```text
tool implementation — تنفيذ Tool
```

بأن يعيش أطول من:

```text
one agent — Agent واحد
one model — Model واحد
one framework — framework واحد
```

ويمكن أن يتعايش البروتوكولان.

قد يستخدم نظام متعدد Agents:

```text
A2A between agents — A2A بين Agents
MCP between each Host and its capability Servers — MCP بين كل Host وServers الخاصة بـ capabilities لديه
```

## 44. قائمة تحقق قبل Production

قبل نشر نظام يعتمد MCP، اسأل:

### Contract الخاصة بالـ Server

- هل أسماء Tools واضحة؟
- هل schemas محددة وذات types واضحة؟
- هل `Resources` read-only حيث ينبغي؟
- هل `Prompts` تستخدم parameters واضحة؟

### الأمان (Security)

- هل subprocess commands موثوقة؟
- هل environment variables محدودة لأقل قدر ممكن؟
- هل الإجراءات الخطرة تحتاج إلى user approval؟
- هل remote endpoints تستخدم authentication؟

### وقت التشغيل (Runtime)

- هل يستطيع `Host` اكتشاف Tools بصورة موثوقة؟
- ماذا يحدث إذا تعطل `Server`؟
- هل timeouts/retries محددة؟
- هل cleanup مُدار؟

### النقل (Transport)

- هل `Stdio` مناسب؟
- هل يحتاج النظام إلى shared remote service؟
- هل TLS/authentication مهيأ للـ remote deployment؟

### النتائج متعددة الوسائط

- هل يستطيع `Host` أو Model معالجة محتوى image/file؟
- هل تستطيع UI عرضه؟

### تصحيح الأخطاء (Debugging)

- هل يعمل `Server` بصورة مستقلة؟
- هل يمكن لـ `Inspector` أو diagnostics إظهار schemas وprotocol traffic؟
- هل logs منفصلة عن protocol stream؟

## 46. النموذج الذهني الكامل

ابدأ بالنظام السابق لـ MCP:

```text
Agent — الوكيل
├── hard-coded tools — Tools مكتوبة مباشرة داخل الكود
├── vendor-specific function parsing — تحليل function خاص بكل مزوّد
├── manual state loop — حلقة state يدوية
└── direct API secrets — secrets مباشرة لـ API
```

ثم انتقل إلى MCP:

```text
Host — التطبيق المضيف
├── orchestration — التنسيق
├── LLM — النموذج
├── security — الأمان
├── configuration — الإعدادات
│
├── Client -> Git Server — Client إلى خادم Git
├── Client -> Filesystem Server — Client إلى خادم نظام الملفات
└── Client -> Stock Server — Client إلى خادم الأسهم
```

تعرض Servers primitives موحَّدة:

```text
Tools — أدوات تنفيذية
Resources — بيانات ومصادر
Prompts — workflows قابلة لإعادة الاستخدام
```

وقد تطلب Servers من `Host`:

```text
Sampling — استعانة بالـ reasoning
Elicitation — طلب input منظَّم
```

وتربطها transports:

```text
Stdio — نقل محلي
or — أو
remote HTTP-style transport — نقل شبكي بعيد بأسلوب HTTP
```

ومسار implementation هو:

```text
build Server — ابنِ Server
    ↓
describe capabilities — صِف capabilities
    ↓
connect Host — صِل Host
    ↓
discover dynamically — اكتشف ديناميكيًا
    ↓
model chooses tool — يختار Model الـ Tool
    ↓
Host translates request — يترجم Host الطلب
    ↓
Server executes — ينفّذ Server
    ↓
typed result returns — تعود نتيجة محددة النوع
    ↓
agent continues reasoning — يواصل Agent عملية reasoning
```

وهذا هو الفرق بين demo موصول مباشرة بالكود ومنظومة capabilities قابلة لإعادة الاستخدام.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "MCP مجرد تنسيق آخر لـ function calling."

لا. يقدّم المصدر MCP باعتباره architecture أوسع من `Host/Client/Server` تشمل discovery وresources وprompts والمساعدة ثنائية الاتجاه وtransports.

### المفهوم الخاطئ 2
> "structured function calling يحل أمن Tools بالفعل."

لا. لا يزال التنفيذ الآمن يحتاج إلى trusted orchestration وsandboxing وpermissions وapproval.

### المفهوم الخاطئ 3
> "Host وClient هما المفهوم نفسه."

لا. `Host` هو التطبيق الرئيسي الموثوق؛ أما `Clients` فهي protocol connections داخله، وعادةً يوجد واحد لكل `Server`.

### المفهوم الخاطئ 4
> "ينبغي أن يعرف Server أي LLM يستخدمه."

لا. يهدف MCP إلى فصل implementation الخاص بالـ capability عن Model أو المزوّد.

### المفهوم الخاطئ 5
> "Resources مجرد Tools تعيد Text."

لا. `Resources` بيانات خاملة، بينما تمثل `Tools` إجراءات قابلة للتنفيذ.

### المفهوم الخاطئ 6
> "يختار Model الـ Prompts تلقائيًا مثل Tools."

لا. وفق صياغة المصدر، `Prompts` عبارة عن workflows قابلة لإعادة الاستخدام يبدأها المستخدم.

### المفهوم الخاطئ 7
> "Sampling يعني أن Server يحتوي على LLM خاص به."

لا. يسمح `Sampling` للـ `Server` بطلب reasoning من Model المركزي لدى `Host`.

### المفهوم الخاطئ 8
> "Elicitation تعني حدوث فشل."

لا. تسمح للـ `Server` بالتوقف وطلب user input منظَّم ومفقود.

### المفهوم الخاطئ 9
> "إضافة MCP Tool جديدة تتطلب دائمًا تغيير source code الخاص بالـ Agent."

لا. يسمح dynamic discovery للـ `Host` باكتشاف capabilities جديدة من `Server`.

### المفهوم الخاطئ 10
> "Stdio يفتح network port محليًا."

لا. فهو يتواصل عبر standard input/output بين processes.

### المفهوم الخاطئ 11
> "يمكنني طباعة debug messages بحرية إلى stdout داخل Stdio MCP Server."

لا. يحمل stdout protocol data وقد تفسده مخرجات عشوائية.

### المفهوم الخاطئ 12
> "إذا استطاع Model استهلاك نتيجة صورة من Tool، فستعرضها UI تلقائيًا."

لا. قد يتطلب عرض UI اعتراض media result وعرضها بصورة منفصلة.

### المفهوم الخاطئ 13
> "ينبغي أن يرث child MCP Server جميع environment variables من Host."

لا. يعني least privilege الحد الصريح من secrets والـ environment التي تُكشف.

### المفهوم الخاطئ 14
> "Stdio هو أفضل transport لخدمة cloud مشتركة."

لا. تحتاج الخدمات البعيدة أو المشتركة عادةً إلى network transport وauthentication مناسب.

### المفهوم الخاطئ 15
> "A2A وMCP يحلان المشكلة نفسها تمامًا."

لا. يوحّد A2A أساسًا تفاعل Agent-to-Agent، بينما يوحّد MCP تفاعل Host-to-capability.

| نقل Stdio | نقل محلي عبر stdin/stdout |

| محوّل MCPToolset | ADK adapter لـ MCP Servers كما يصفه المصدر |
| الاكتشاف الديناميكي (Dynamic discovery) | اكتشاف capabilities الخاصة بالـ Server عند runtime |

## الفكرة التي ينبغي الاحتفاظ بها

**يحوّل MCP تكامل Tools من كود تطبيق موصول مباشرة إلى منظومة capabilities قائمة على protocol. يظل `Host` هو المنسق الموثوق، ويتخصص كل `Server` في domain محدد، وتعزل `Clients` المخصصة الاتصالات، وتجعل primitives الموحَّدة Tools والبيانات وPrompts وطلبات reasoning وطلبات user input قابلة للاكتشاف وإعادة الاستخدام. ويثبت فصل implementation الوعد المعماري عمليًا: يستطيع `Host` اكتساب capabilities ديناميكيًا من `Server` معزول دون تضمين business logic الخاصة بهذه capability داخل Agent نفسه.**
