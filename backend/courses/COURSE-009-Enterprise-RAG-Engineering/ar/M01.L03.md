## نتائج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يغيّر حجم documents وحجم كل document وحمل queries وضوضاء Retrieval بنية RAG عند التوسع.
- تصميم مسارات Ingestion قابلة لإعادة التشغيل وObservable وIdempotent من أجل corpora كبيرة ومتغيرة.
- تشخيص مشكلات Ingestion المتعلقة بـ OCR وboilerplate وencoding وmetadata والـ documents شديدة الضخامة.
- شرح Incremental Refresh وChange Detection وAsynchronous Ingestion وNear-real-time Indexing.
- تصميم مسار Retrieval من مرحلتين والتمييز بين Candidate Generation الموجّه نحو Recall وReranking الموجّه نحو Precision.

- وضع Guardrails عبر Query Flow وتحليل مخاطر Prompt Injection المباشرة وغير المباشرة.

- مقارنة LLM-as-a-judge مع نماذج Faithfulness المتخصصة، وتصميم سياسات Correction أو Refusal.

## 1. يغيّر توسيع RAG المشكلة الهندسية

قد يبدو Prototype لـ RAG مقنعًا مع عدد قليل من documents ومجموعة صغيرة من المستخدمين. لكن على Enterprise Scale يتعرض التصميم نفسه لمجموعات documents أكبر بكثير، وصيغ أكثر، وبيانات تتغير بسرعة، وعدد كبير من queries المتزامنة. لذلك يغيّر Scale السؤال من "هل يمكن أن يعمل Retrieval؟" إلى "هل يمكن أن يظل Retrieval دقيقًا وحديثًا وسريعًا وObservable وآمنًا ومقبول التكلفة تحت حمل مستمر؟"

من المفيد التفكير في Scale عبر فصل أربعة ضغوط:

```text
حجم البيانات (data volume)      → المزيد من documents و chunks و vectors و metadata
حجم الاستعلامات (query volume) → المزيد من أعمال Retrieval وGeneration المتزامنة
تعقيد البيانات (data complexity)  → المزيد من الصيغ و OCR والجداول والصور والحالات الطرفية
ضغط الجودة (quality pressure) → Retrieval أصعب، وGuardrails أكثر، وEvaluation أشد صرامة
```

الدرس المركزي هو أن توسيع RAG لا يتحقق بمجرد زيادة حجم جهاز واحد. بل يتطلب إعادة تصميم Ingestion وRetrieval وضوابط Generation وتجربة المستخدم باعتبارها أنظمة فرعية منسقة.

## 2. حجم documents وحجم كل document وحمل queries

تنمو ثلاثة أبعاد بصورة مستقلة. أولًا، قد يحتوي corpus على مئات الآلاف أو ملايين documents. ثانيًا، قد يحتوي document واحد على آلاف الصفحات، ما ينتج أعدادًا هائلة من chunks. ثالثًا، قد يرتفع Query Traffic إلى معدل مرتفع من الاستعلامات في الثانية (QPS).

يضغط كل بُعد على جزء مختلف من Stack. زيادة documents ترفع وقت Indexing وصعوبة Search. والملفات الأكبر تخلق مشكلات Parsing وMemory. أما ارتفاع QPS فينشئ متطلبات Concurrency وRate Limiting وCaching وHorizontal Scaling. يجب أن يحدد التصميم الإنتاجي أي بُعد يقيّد النظام فعليًا بدلًا من التعامل مع "Scale" كمشكلة عامة واحدة.

## 3. لماذا يصبح Retrieval أصعب مع نمو corpus

مع corpus صغير، يواجه الـ chunk الصحيح عددًا قليلًا نسبيًا من المنافسين. ومع نمو corpus، تصبح chunks كثيرة متشابهة سطحيًا مع Query. لذلك قد تحتوي نتائج Top-k على ضوضاء أكثر، أو معلومات مكررة، أو مقاطع تطابق الموضوع لكنها لا تطابق Intent الفعلي.

يخلق ذلك مشكلة Signal-to-noise: قد يظل الـ chunk الذي يحمل الإجابة موجودًا في Index، لكنه قد يهبط أسفل Retrieval Cutoff. لا يستطيع Generator إصلاح دليل لم يتم Retrieval له أصلًا. لهذا تنتقل الأنظمة الكبيرة غالبًا من Vector Similarity Search واحد إلى Metadata Filters وHybrid Search وCandidate Generation وReranking.

## 4. حداثة Index وIncremental Updates

لا يكون نظام RAG أحدث من Searchable Index الذي يعتمد عليه. وتصبح إعادة بناء Index من الصفر كلما تغير document واحد غير عملية عندما يحتوي corpus على ملايين السجلات.

البديل القابل للتوسع هو مسار Incremental Update. يكتشف المصادر الجديدة أو المعدلة أو المحذوفة، ثم يعيد معالجة documents أو chunks المتأثرة فقط. ويجب أن يزيل المسار أيضًا vectors وmetadata القديمة عندما يُحذف محتوى المصدر.

Invariant مفيد هو:

```text
حالة المصدر (source state) ≈ حالة Index (indexed state)
```

كلما قل التأخير بين هاتين الحالتين، زادت Freshness لنظام RAG. لذلك فإن Freshness خاصية تشغيلية وليست مجرد اختيار لخوارزمية Retrieval.

## 5. فهم تكلفة RAG كنظام

عند Scale كبير، تأتي التكلفة من طبقات متعددة: التخزين الخام والمعالج، وإنشاء Embeddings، وVector وLexical Indexes، وCompute الخاص بـ Retrieval، وLLM Inference، وNetwork Traffic، وMonitoring، وأدوات التشغيل. النظر إلى سعر LLM API وحده يخفي جزءًا كبيرًا من التكلفة الإجمالية.

يوضح الفصل المصدر ذلك باستخدام corpus كبير لدعم العملاء. والدرس المهم ليس قيمة الدولار الدقيقة، لأنها تعتمد على الزمن وأسعار Provider، بل طريقة المحاسبة: قدّر إجمالي Source Tokens، وتكلفة Embedding لمرة واحدة أو عند Refresh، وPrompt وOutput Tokens لكل Query، وبنية Index التحتية، وتكاليف DevOps الداعمة كلًّا على حدة.

ينبغي أن يجيب Cost Model عن الأسئلة التالية: أي التكاليف تتوسع مع حجم corpus؟ وأيها تتوسع مع Query Traffic؟ وأيها يُدفع مرة واحدة؟ وأيها يتكرر كلما تغيرت البيانات؟

## 6. اقتصاد Tokens وCaching وModel Routing

غالبًا ما تصبح Generation أكبر تكلفة متكررة لأن كل Query قد يرسل آلاف Context Tokens إلى LLM. وهناك ضابطان معماريان مهمان بوجه خاص.

يمكن لـ **Multilevel Caching** إعادة استخدام المخرجات في مراحل متعددة: Query Embeddings أو Retrieval Results أو Reranking Outputs أو Final Responses. أما **Dynamic Model Routing** فيرسل الطلبات المباشرة إلى Models أرخص وأسرع، مع حجز Models الاستدلال المكلفة للحالات الصعبة.

المبدأ العام هو تجنب إعادة حساب عمل لم تتغير Inputs الخاصة به تغيرًا جوهريًا، وتجنب دفع تكلفة Inference مرتفعة عندما لا تحتاج المهمة إلى Capability مرتفعة.

## 7. تعامل مع Ingestion كبنية بيانات إنتاجية

يكفي Script يمر على الملفات في مرحلة التجربة، لكن نظام Ingestion كبيرًا يتصرف بصورة أقرب إلى ETL Platform. فهو يحتاج Scheduling وRetries وProgress Tracking وVersioning وObservability وFailure Isolation وControlled Rollout لتغييرات Parsing أو Chunking.

هذا التحول مهم لأن أخطاء Ingestion أخطاء Upstream. فبمجرد Embed وIndex نص مشوه أو Metadata مفقودة أو محتوى قديم، يعمل Retrieval اللاحق على أدلة تالفة. لذلك يستحق Production Ingestion الانضباط الهندسي نفسه الذي تستحقه أي Data Pipeline حرجة.

---

## 8. مسار Ingestion كبير الحجم

يتكون Ingestion واسع النطاق من سلسلة Transformations مكلفة:

```text
قراءة المصدر (read source)
→ التحليل / الاستخراج (Parsing and Extraction)
→ التنظيف وNormalization
→ التقسيم إلى أجزاء (Chunking)
→ استخراج Metadata
→ إنشاء Embeddings للـ chunks
→ كتابة vectors + text + metadata
→ بناء Indexes أو تحديثها
```

غالبًا ما تكون مرحلة Embedding كثيفة Compute، بينما قد يكون Parsing كثيف I/O ومختلفًا حسب Format. يضيف استخراج Metadata عملًا إضافيًا لكنه ضروري لاحقًا لـ Filtering وCitations. كما تصبح عمليات كتابة Index أبطأ مع نمو Indexes. لذلك يجب قياس Pipeline مرحلة بمرحلة بدلًا من قياسه Job واحدًا ضخمًا فقط.

## 9. Metadata جزء من جودة Retrieval

Metadata مثل Source URL وDocument ID ورقم الصفحة والمؤلف والتاريخ والقسم وSection Heading ليست للزينة. فهي تتيح Structured Filtering وSource Attribution وAccess Control ومنطق Freshness وContext أفضل أثناء Generation.

يجب أن يحافظ Pipeline القابل للتوسع على العلاقة بين كل chunk وMetadata الخاصة به عبر كل Transformation. وإذا فقد chunk هوية المصدر أو معلومات الصفحة، فقد يظل النظام قادرًا على Retrieval للنص لكنه سيواجه صعوبة في Filtering الصحيح أو تقديم Citations موثوقة.

## 10. الهشاشة: لماذا لا تُقبل إعادة البدء من الصفر

افترض أن عملية Ingestion تعالج مئات الآلاف من documents ثم تفشل قرب النهاية بسبب ملف تالف واحد أو Network Timeout. إذا كان Pipeline لا يستطيع إلا البدء من البداية، فقد يهدر فشل صغير ساعات أو أيامًا من العمل.

لذلك يحتاج Pipeline القابل للتوسع إلى Checkpoints وحالة مهام Durable وFailure Isolation وقدرة على Resume. الهدف ليس تصميم Pipeline لا يفشل أبدًا؛ ففي Scale كبير يُتوقع حدوث بعض الفشل. الهدف هو جعل حالات الفشل محلية ومرئية وقابلة للتعافي ومنخفضة التكلفة.

---

## 11. Parallel وDistributed Processing

يمكن غالبًا Parsing أو Chunking أو Embedding لـ documents مستقلة بصورة متزامنة. يقلل Parallel Processing زمن التنفيذ الفعلي عبر توزيع العمل على CPU Processes أو Machines أو GPUs. ويمكن لأطر مثل Ray وDask وSpark أو أنظمة مشابهة تنسيق هذا العمل بحسب Workload.

يستفيد إنشاء Embeddings بشدة من Batching لأن Accelerators تكون أكثر كفاءة عند معالجة عدة نصوص معًا. ويمكن أيضًا Parallelize لـ Parsing واستخراج Metadata، لكن يجب الحذر من Shared Resources وحدود APIs وضغط Memory.

يرفع Parallelism قيمة Throughput، لكنه لا يلغي الحاجة إلى Correctness وCheckpointing وRetries.

---

## 12. Orchestration للـ Pipeline وإدارة Dependencies

يمثل Workflow Orchestrator عملية Ingestion كمراحل مترابطة Dependencies بدلًا من Script طويل واحد. مثلًا، لا ينبغي أن يبدأ Embedding قبل وجود chunks المقابلة، بينما يمكن معالجة documents المستقلة بالتوازي.

يمكن لـ Orchestrator جدولة Tasks وإعادة محاولة Failures وعزل Inputs الإشكالية وتشغيل Alerts وعرض Progress. وهذا مهم خصوصًا عندما يجب تشغيل Pipeline نفسه مرارًا من أجل Refresh Jobs.

النموذج الذهني المهم هو Workflow موجّه من Tasks قابلة لإعادة التشغيل، وليس Process واحدة ذات Call Stack طويل.

## 13. Idempotency: إعادات محاولة آمنة دون تكرار

تكون Task **Idempotent** عندما ينتج عن تكرارها الحالة المقصودة نفسها بدلًا من تكرار Side Effects. في RAG Ingestion قد يعني ذلك أن إعادة محاولة Task خاصة بـ Chunk Indexing تقوم Update أو Upsert لهوية chunk نفسها بدلًا من إدخال نسخة ثانية.

تحوّل Idempotency الـ Retries من آلية طوارئ خطرة إلى ميزة Reliability طبيعية. وتُعد Stable Document IDs وStable Chunk IDs وVersion Fields وUpsert Semantics لبنات شائعة.

من دون Idempotency، يمكن لـ Automatic Retry إنشاء chunks مكررة بصمت، فتلوّث Retrieval وتشوه Ranking.

## 14. Deep Observability لمسار Ingestion

يحتاج Pipeline السليم إلى أكثر من Exception Logs. ينبغي أن يعرض Throughput مثل documents per second وchunks per second، واستخدام Resources، وQueue Depth، وعدد Retries، وعدد Failed Documents، وLatency لكل Stage.

وينبغي أن يكشف أيضًا حالات Silent Failure: سجلات عالقة لا تنتهي، أو documents تمت تصفيتها دون توقع، أو Stage تنجح تقنيًا لكنها تنتج صفر chunks. قد لا ترفع هذه المشكلات Exceptions، لكنها تضر Knowledge Base.

لذلك ينبغي أن تجيب Observability عن سؤالين: "هل تعطلت Task؟" و"هل أنتجت Task البيانات المتوقعة؟".

## 15. عدم اتساق جودة البيانات هو الوضع الطبيعي في الإنتاج

تحتوي Enterprise Corpora على PDFs ممسوحة ضوئيًا، وBoilerplate متكرر، وEncodings مشوهة، وLayouts غير متسقة، وVersions قديمة، وملفات تالفة. ونادرًا ما يكفي Parser واحد Universal.

تنتشر جودة Input الضعيفة إلى بقية النظام: يتم Chunking للنص المشوش ثم Embedding له وتخزينه، ما يلوث Retrieval. والاستجابة الصحيحة هي Conditional Preprocessing Pipeline يفحص document أولًا ثم يختار المسار المناسب.

```text
فحص document (inspect document)
→ تصنيف Format / Quality
→ اختيار مسار Parser أو OCR
→ التنظيف / التطبيع (Cleaning and Normalization)
→ Validation للمخرجات
→ متابعة Ingestion
```

## 16. أعطال OCR وBoilerplate وEncoding

قد يخلط OCR بين أحرف متشابهة بصريًا، وهو أمر ضار خصوصًا لـ IDs وCodes والأسماء الدقيقة. وقد تهيمن Boilerplate المكررة في كل صفحة على Embeddings وتسبب Retrieval غير ذي صلة. كما يمكن لأخطاء Character Encoding تحويل علامات الترقيم أو النص المقروء إلى Symbols تالفة.

هذه ليست عيوبًا تجميلية؛ فهي تغير Strings التي تستقبلها Chunkers وEmbedding Models. لذلك يحتاج Quality Pipeline إلى Cleaning Rules، وإزالة Duplicates أو Boilerplate، وEncoding Normalization، وValidation Checks قبل Indexing.

---

## 17. Document Triage وConditional Routing

يمكن أن يبدأ Pipeline القابل للتوسع بمرحلة Triage. فقد يستخدم PDF أصلي ذو نص قابل للاستخراج Parser سريعًا، بينما قد يحتاج PDF قائم على الصور فقط إلى OCR. وقد يحتاج HTML إلى إزالة Navigation وBoilerplate، بينما قد يحتاج Form معقد إلى Parser أكثر تخصصًا.

الفكرة الأساسية هي **أرخص مسار صحيح أولًا**: لا تطبق أغلى Parser على كل document. اكتشف ما يحتاجه الملف، وRoute له بالشكل المناسب، واحتفظ بالتقنيات المكلفة للحالات الصعبة.

## 18. تحتاج documents شديدة الضخامة إلى Streamed Processing

تحميل document يحتوي على آلاف الصفحات إلى Memory أمر خطِر وغير ضروري. والاستراتيجية الأفضل هي Incremental Processing: اقرأ صفحة أو نطاق صفحات، واستخرج المحتوى، ونفّذ Chunking، واحفظ النتائج، وحرر Memory، ثم تابع.

يقلل Streaming ذروة Memory ويسمح بظهور Output مفيد قبل انتهاء الملف كاملًا. كما يجعل Checkpoints أكثر طبيعية. ويجب أن يحافظ التصميم على Structures العابرة للصفحات عند الحاجة؛ مثلًا، لا ينبغي تقسيم Table أو Section يمتد عبر Boundary بصورة عمياء.

## 20. Refresh للـ documents وNear-real-time Indexing

تتغير المعرفة في الإنتاج. تصل documents جديدة، وتُراجع documents موجودة، وتُحذف أخرى قديمة. يجب أن ينقل نظام Refresh هذه التغييرات إلى Searchable Index.

في بعض التطبيقات، لا يُقبل تأخير دقائق أو ساعات. يهدف Near-real-time Indexing إلى جعل المعرفة الجديدة قابلة للبحث خلال ثوانٍ. وهذا يتطلب مراحل Ingestion سريعة، وAsynchronous Processing، وStorage Layer تقبل Incremental Updates بكفاءة.

يجب تحديد متطلبات Freshness صراحة لأنها تؤثر بقوة في Architecture والتكلفة.

## 21. Change Detection وAsynchronous Indexing

تبدأ Incremental Updates باكتشاف التغيير. يمكن لـ Change Data Capture أو CDC، وأحداث المصدر، وTimestamps، وVersion Hashes، أو Database Transaction Logs أن تخبر Pipeline بما تغير.

نمط Service شائع هو:

```text
تحديث المصدر (source update)
→ قبول Event / Upload
→ تأكيد الاستلام (acknowledge receipt)
→ إضافة عمل Indexing إلى Queue
→ Parsing + Chunking + Embedding بصورة Asynchronous
→ تحديث Index
→ تعليم Version بأنها قابلة للبحث
```

فصل تأكيد الاستلام عن إكمال Indexing يمنع أعمال Ingestion طويلة المدة من حجب APIs الموجهة للمستخدم.

## 22. التصميم من أجل تحديثات Index سريعة

لا يقتصر Instant أو Near-real-time Indexing على Ingestion وحده. يجب أن تدعم Vector Database ونوع Index عمليات Insert أو Update متكررة دون فرض Rebuild طويل. وتقدم الأنظمة المختلفة مفاضلات مختلفة بين Update Latency وQuery Latency وMemory وPersistence وجودة Index.

لذلك يجب أن يتضمن اختيار Vector Database سلوك Update كمتطلب أساسي، لا مجرد Query Speed مقاس في Benchmark.

## 23. لماذا لا يكفي Basic Vector Search عند Scale كبير

يُعد Dense Vector Search Baseline قويًا، لكن مع زيادة عدد chunks قد يعيد مقاطع مترابطة دلاليًا دون Precision كافية. وغالبًا ما يضيف Enterprise Retrieval فلاتر وLexical Matching وFusion وReranking.

الهدف ليس أقصى Sophistication خوارزمي، بل الحفاظ على كل من **Recall** — عدم فقدان الأدلة المفيدة — و**Precision** — عدم إهدار Final Context Window على أدلة ضعيفة.

## 24. بنية Retrieval من مرحلتين

يفصل Two-stage Retrieval Pipeline بين Search واسع ورخيص ومرحلة Ranking دقيقة ومكلفة.

```text
Corpus كبير (large corpus)
→ المرحلة 1: Candidate Generation — سريعة وذات Recall مرتفع
→ عشرات / مئات Candidates
→ المرحلة 2: Reranking — أبطأ وذات Precision مرتفع
→ عدد قليل من أفضل chunks
→ Context الخاص بـ LLM
```

هذا Structure شائع لأن تطبيق Relevance Model مكلف على كل chunk غير عملي. تضيق المرحلة 1 نطاق المشكلة، بينما تنفق المرحلة 2 Compute أكبر حيث يكون مهمًا.

## 25. المرحلة 1: حسّن Candidate Generation من أجل Recall

تطبق المرحلة الأولى غالبًا Metadata Filters أو Vector Search أو Lexical Search أو Hybrid Search. ومهمتها الرئيسية تجنب False Negatives. ويمكن قبول بعض Candidates غير ذات الصلة لأن المرحلة الثانية قادرة على إزالتها.

القيد الحاسم غير قابل للعكس: إذا غاب chunk ذي صلة عن Candidate Set، فلن يستطيع Reranking استعادته. لذلك ينبغي تقييم Tuning الخاص بـ Candidate Generation باستخدام Metrics موجهة نحو Recall وQueries واقعية.

---

## 26. المرحلة 2: Reranking من أجل Precision

يستقبل Reranking مجموعة Candidates أصغر بكثير ويقيّم كل Candidate بعناية أكبر. تستطيع Transformer Cross-encoders معالجة Query وCandidate Text معًا، والتقاط علاقات قد تفوت Embeddings المستقلة.

لأن هذه المرحلة أثقل Computationally، فلا تُطبق إلا بعد Candidate Generation. وهدفها ترتيب الأدلة النهائية بحيث تبقى chunks الأكثر احتواءً للإجابة والأكثر تحديدًا وفائدة بعد Context Cutoff.

---

## 27. يجمع Hybrid Search بين الأدلة Semantic وLexical

يتفوق Semantic Search عندما تختلف الصياغة مع تشابه المعنى. ويتفوق Lexical Search عندما تكون Exact Tokens مهمة، مثل Product Codes أو Statute Numbers أو Error Messages أو Names أو Jargon. يشغّل Hybrid Search الطريقتين ويجمع نتائجهما.

نموذج ذهني مفيد هو:

```text
Semantic Search → تطابق المعنى (meaning match)
Lexical Search  → تطابق Exact/Term
Hybrid Search   → أدلة من المنظورين
```

يجعل ذلك Retrieval أكثر Robust لأن نقاط ضعف إحدى الطريقتين يمكن أن تعوضها الأخرى.

## 28. Inverted Indexes وBM25

يستخدم Lexical Search بنية Inverted Index: يشير كل Term إلى documents أو chunks التي تحتويه. ثم تستخدم Ranking Function مثل BM25 لتقدير مدى إفادة تطابقات Term.

Lexical Retrieval سريع ومنخفض التكلفة نسبيًا وقابل للتفسير لأنك تستطيع تحديد Terms التي تطابقت. وتكمن نقطة ضعفه في أن Surface-form Matching لا يفهم Semantic Equivalence تلقائيًا. قد تعبر "Car issues" و"automobile problems" عن الفكرة نفسها دون مشاركة Token مهم.

---

## 29. دمج الرتب المتبادلة (RRF)

غالبًا ما تنتج الأنظمة Semantic وLexical درجات على Scales غير متوافقة. يتجنب RRF معايرة Scores عبر دمج **Ranks** بدلًا من Raw Scores. ويحصل document يظهر قرب أعلى أي قائمة Results على مساهمة Fused قوية.

الفكرة هي:

```text
Semantic Rank مرتفع + Lexical Rank متوسط → Candidate قوي
Semantic Rank متوسط + Lexical Rank مرتفع → Candidate قوي
Rank منخفض في القائمتين                     → Candidate ضعيف
```

يتميز RRF بالبساطة ولا يتطلب أن يتفق نظاما Retrieval على وحدات Score.

{{exercise:M01.L03.EX10}}

---

## 30. دمج الدرجات الموزونة (Weighted Score Fusion)

خيار آخر هو Normalize للـ Semantic وLexical Scores إلى Ranges قابلة للمقارنة ثم حساب Weighted Combination، مثل إعطاء Semantic Evidence تأثيرًا أكبر من Lexical Evidence.

يوفر ذلك تحكمًا مباشرًا في التوازن، لكن Score Normalization مهم. فقد يجعل Normalization سيئ المعايرة أحد نظامي Search مهيمنًا حتى لو أوحت Numeric Weights المختارة بغير ذلك. لذلك يجب Validate للـ Weights على Retrieval Data تمثيلية بدلًا من اختيارها بالحدس وحده.

---

## 31. متى يكون Hybrid Search أكثر أهمية

يكون Hybrid Retrieval مفيدًا خصوصًا عندما تمزج Query بين Intent على مستوى Concept وExact Identifiers. فقد يجمع Technical Troubleshooting بين Symptom بلغة طبيعية وError Code. وقد يحتاج Legal Research إلى Statute Number مع Case Reasoning مرتبط دلاليًا. وقد يجمع Medical Retrieval بين Drug Name وSymptom Description. وقد يجمع Enterprise Search بين Internal Project Codes وأسئلة عامة.

النمط المتكرر هو: **تحمل Exact Tokens هوية مهمة، بينما تحمل اللغة المحيطة Intent.**

## 32. Relevance Reranking باستخدام Cross-encoders

يقيّم Relevance Reranker الـ Query مع كل Candidate. هذه المعالجة المشتركة أغلى من مقارنة Embeddings مولدة بصورة مستقلة، لكنها تستطيع التمييز بين Passage يذكر كلمات متشابهة فقط وآخر يجيب طلب المستخدم مباشرة.

على سبيل المثال، قد تحتوي HR Documents كثيرة على كلمتي "performance" و"review"، لكن واحدًا فقط قد يحتوي Procedure الفعلية لمراجعة منتصف العام. يستطيع Reranker رفع ذلك الدليل الإجرائي فوق Policy أو Blog Content ذي صلة سطحية.

## 34. Maximum Marginal Relevance: الصلة مع التنوع

قد تكون النتائج الأعلى Ranking متكررة. فإذا كررت خمس chunks الحقيقة نفسها، فإن إرسالها جميعًا يهدر Context Space. توازن Maximum Marginal Relevance أو MMR بين هدفين: إبقاء chunks ذات صلة بالـ Query، ومعاقبة chunks المتشابهة جدًا مع الأدلة التي تم اختيارها بالفعل.

يتحكم Trade-off Parameter في مقدار تفضيل Selection لـ Relevance الخالصة مقابل Diversity. ويكون MMR مفيدًا خصوصًا عندما تستفيد الإجابة من Perspectives متعددة، مثل تلخيص Customer Feedback أو مقارنة عدة مصادر.

## 35. Custom Reranking باستخدام Business Rules

قد يحتاج تطبيق RAG إلى Ranking Criteria ليست Semantic بحتة. قد تستحق Support Solutions الحديثة أولوية على القديمة. وفي Ecommerce قد يلزم استبعاد Products غير المتاحة. وقد يعطي تطبيق منظم أولوية لـ Source Types المعتمدة.

يمكن لـ Custom Reranking دمج Metadata وBusiness Rules بعد تقدير Semantic Relevance. وهذا يجعل Retrieval متوافقًا مع الأهداف التشغيلية للتطبيق بدلًا من Language Similarity وحدها.

---

## 36. ربط Rerankers في Chain

يمكن تركيب مراحل Reranking معًا. قد يستخدم Pipeline أولًا Cross-encoder من أجل Relevance، ثم MMR من أجل Diversity، ثم Business Rule من أجل Recency أو Availability.

```text
المرشحون (Candidates)
→ معيد ترتيب الصلة (Relevance Reranker)
→ معيد ترتيب التنوع (Diversity Reranker)
→ معيد الترتيب المخصص للأعمال (Custom Business Reranker)
→ السياق النهائي (Final Context)
```

يجب أن تكون لكل Stage غاية واضحة. تؤدي إضافة Rerankers بلا هدف إلى زيادة Latency وComplexity. ويجب تبرير Chain بتحسن مقاس على Evaluation Set الخاصة بالتطبيق.

---

## 37. Guardrails هي ضوابط حول Query Flow كاملًا

Guardrails آليات تقيّد Inputs أو Retrieved Evidence أو Generation أو Outputs حتى يتصرف النظام ضمن حدود Safety وPolicy المحددة. وليست مجرد Final Filter يُلحق بعد LLM.

يمكن لتصميم Layered أن Validate لـ User Input، وFilter للـ Retrieved Chunks، ويقوي Instructions في Prompt، ويقيّم Generated Text، ويمنع أو يحول Unsafe Output. ومن الأفضل معالجة المخاطر المختلفة في مراحل مختلفة.

---

## 38. Bias والمحتوى الضار وSource Curation

يمكن لـ RAG إعادة إنتاج محتوى إشكالي من مصادره. يبدأ أحد الدفاعات قبل Retrieval: قم بـ Curation للـ corpus بحيث يلائم التطبيق، وعند الحاجة يمثل النطاق الضروري من Perspectives.

يمكن لـ Classifiers إضافية منح Retrieved Passages درجات للمحتوى Unsafe أو Biased والتأثير في Filtering أو Reranking. كما يمكن لـ Post-generation Auditors فحص Final Answer. والدرس الأساسي هو أن Grounding لا يجعل الإجابة آمنة تلقائيًا؛ بل يجعلها Grounded فقط في البيانات التي اخترت Retrieval لها.

## 39. أماكن وضع Guardrails

فكّر في Guardrails كنقاط فحص:

```text
إدخال المستخدم (user input)
→ التحقق من Input / Sanitization
→ الاسترجاع (Retrieval)
→ ترشيح Evidence / فحوص Policy
→ Prompt الخاص بـ Generation
→ استجابة LLM
→ فحوص أمان Output / Faithfulness
→ المستخدم (user)
```

إسناد المسؤولية كلها إلى Prompt واحد أمر هش. يستخدم النظام الأقوى ضوابط متعددة حتى لا يتحول فشل واحد تلقائيًا إلى فشل مرئي للمستخدم.

## 40. Safety Models متخصصة بوصفها Output Auditors

يوضح الفصل استخدام Safety Model متخصص لتصنيف Generated Content وفق Policy. نمط الإنتاج أهم من Model المحدد:

```text
إنشاء Candidate Answer
→ تقييم Candidate وفق Policy
→ السماح أو الحجب أو الاستبدال
```

يمكن لـ Dedicated Auditor أن يكون أرخص وأكثر اتساقًا من استخدام Main Generative Model لكل Policy Check. وينبغي أن تكون Policy نفسها صريحة وVersioned وقابلة للاختبار.

## 41. Prompt Injection المباشر وغير المباشر

تحاول Prompt Injection جعل Model يتعامل مع نص غير موثوق باعتباره Instructions تتجاوز قواعد التطبيق المقصودة. تأتي **Direct Injection** من User Query. وتُزرع **Indirect Injection** داخل External Content يدخل لاحقًا إلى Model على هيئة Retrieved Context.

يزيد RAG من Attack Surface لأن Retrieved Documents Inputs غير موثوقة أيضًا. قد يحتوي document نصًا يبدو كأنه Instruction رغم أن التطبيق قصده Evidence. يجب أن يحافظ النظام على Trust Boundary واضح بين System Instructions وUser Requests وRetrieved Data.

## 42. Sanitization للـ Input والـ Documents

تفحص Sanitization كلًا من User Inputs وIngested Documents بحثًا عن Patterns مشبوهة أو Hidden Instructions أو Malformed Content أو Attack Signatures معروفة. ويؤكد الفصل أن Malicious Text قد يكون مخفيًا بصريًا داخل documents.

ليست Sanitization دفاعًا كاملًا لأن المهاجمين يمكنهم إعادة صياغة Instructions بلا نهاية. إنها Layer تقلل الهجمات الواضحة وتنتج Signals تسمح بمعالجة Downstream أكثر صرامة.

---

## 43. الدفاع عن Instructions باستخدام Delimiters صريحة

ينبغي أن يفصل Prompt بوضوح بين Trusted Instructions وUntrusted Content. يمكن لـ Delimiters شبيهة بـ XML أو Markers أخرى وسم Query وRetrieved Context، بينما تخبر System Instruction الـ Model صراحة أن النص داخل هذه Blocks بيانات وليس Instructions ذات أولوية أعلى.

```text
SYSTEM: اتبع Policy الخاصة بالتطبيق
<query>نص مستخدم غير موثوق (untrusted user text)</query>
<context>أدلة Retrieved غير موثوقة (untrusted retrieved evidence)</context>
TASK: أجب باستخدام Context مع الالتزام بـ System Policy
```

لا يجعل ذلك Prompt Injection مستحيلة، لكنه يقلل Ambiguity ويجب دمجه مع Tool Permissions مقيدة وMonitoring.

---

## 44. لماذا يمكن لـ RAG أن Hallucinate رغم ذلك

يقلل RAG خطر Hallucination عبر توفير Evidence، لكنه لا يضمن Faithfulness. فقد يسيء Model قراءة Evidence أو يدمج مصادر متعارضة أو يفرط في Extrapolation أو يفضّل Parametric Knowledge لديه على Retrieved Text.

لذلك ليس سؤال Debugging الصحيح ببساطة "هل Hallucinate الـ LLM؟" بل "في أي Stage انهار دعم هذا Claim؟"

---

## 45. ثلاثة أسباب رئيسية لـ Hallucination في RAG

يحدد الفصل ثلاثة أسباب واسعة. **Retrieval Failure:** تم فقد Evidence المطلوبة أو اختيار chunks مشوشة/متعارضة. **Data-quality Failure:** وجد Retrieval المحتوى المفهرس بصورة صحيحة، لكن المحتوى المفهرس كان خاطئًا أو قديمًا أو ناقصًا أو مكررًا. **Generation Failure:** كانت Evidence الصحيحة موجودة، لكن LLM تجاهلها أو أساء تفسيرها أو ناقضها.

تتطلب هذه الأسباب إصلاحات مختلفة. تحسين Prompt لن يصلح بيانات قديمة، وتحسين Vector Index لن يصلح LLM يتجاهل Context واضحًا.

## 46. Hallucinations المشكوك فيها والحميدة وغير المرغوبة

ليست كل عبارة Unsupported متساوية الأثر. يميّز الفصل بين حالات **Questionable** يكون دعمها Ambiguous، وإضافات **Benign** غير مدعومة لكنها غير ضارة أو معقولة، وHallucinations **Unwanted** تشوه المصدر أو تنشئ حقائق مضللة.

هذا Taxonomy مفيد لأن Action Threshold يعتمد على التطبيق. قد يرفض نظام طبي أو قانوني أي إضافة Unsupported، بينما قد تتسامح واجهة Creative Summarization مع Inference حميد بسيط إذا تم توضيحه بجلاء.

## 47. اكتشاف Hallucination باستخدام LLM Judge

يمكن Prompt لـ LLM كي يقارن Generated Response مع Retrieved Evidence ويمنح Faithfulness أو Consistency Score. يسهل دمج ذلك لأن التطبيق يتعامل بالفعل مع LLM Calls.

تشمل المفاضلات Latency إضافية وتكلفة إضافية واحتمال Hallucination من Judge ومعايرة Score. وقد تخفي درجة تقريبية من 1–5 عدم اليقين. لذلك يكون LLM-as-a-judge مفيدًا، لكن يجب تقييمه هو نفسه بدل افتراض أنه Oracle.

---

## 48. Models متخصصة لتقييم Hallucination

يستقبل Hallucination أو Entailment Model متخصص Source Text وGenerated Claim أو Summary، ثم يتنبأ بمدى دعم Output. وتكون هذه Models عادة أصغر وأرخص من General LLM Judge ويمكنها إرجاع Continuous Scores.

يوضح الفصل هذا النمط باستخدام HHEM. والفكرة التشغيلية الأساسية هي التعامل مع Faithfulness Checking بوصفها Classification Problem يمكن إدراجها بعد Generation ومراقبتها بصورة مستقلة.

## 49. من Detection إلى Hallucination Correction

يخبرك Detection فقط بأن الإجابة Risky. ويجب أن يقرر نظام الإنتاج ما يفعله بعد ذلك. تشمل الخيارات رفض الإجابة، أو إظهار Warning، أو إعادة محاولة Retrieval، أو Regenerate باستخدام Instructions أشد صرامة، أو استدعاء Dedicated Correction Model مع Suspect Answer وSupporting Context.

يمكن تمثيل Correction Flow هكذا:

```text
Query → إجابة RAG → Faithfulness Check
                     ├─ Pass → إرجاع الإجابة
                     └─ فشل (Fail) → التصحيح / إعادة التوليد / الرفض (Correction, Regeneration, Refusal)
```

يحسن Correction الـ Reliability لكنه يضيف Latency وCompute، لذا يجب اختيار Thresholds وفق Risk.

## 50. مثلث الجودة–Latency–التكلفة

نادرًا ما تكون تحسينات Scale مجانية. يضيف Hybrid Retrieval عملًا، ويضيف Reranking عملًا، وتضيف Safety Checks عملًا، ويضيف Hallucination Detection عملًا، وقد يضيف Correction Model Call أخرى.

ينشئ ذلك مفاضلة هندسية متكررة بين الجودة وLatency والتكلفة. ليس الهدف تعظيم كل Control في كل Request، بل تخصيص Checks المكلفة حيث يبررها Risk أو Uncertainty، والحفاظ على كفاءة Common Path.

## 51. تجربة المستخدم جزء من جودة RAG

قد يفشل Backend دقيق تقنيًا كمنتج إذا لم يستطع المستخدمون التعبير عن هدفهم أو فهم الإجابة أو التحقق من مصادرها أو التعافي من الأخطاء. لذلك يتعامل الفصل مع Frontend كجزء من نظام RAG لا كطبقة تجميلية.

تظهر Latency بوضوح للمستخدمين. ومع تضاعف مراحل Retrieval وGuardrails، يمكن لـ Streaming وProgress Indicators والعرض المدروس جعل الانتظار مفهومًا دون إخفاء الحالة الحقيقية للنظام.

---

## 52. تصميم تجربة Input

ينبغي أن يتمكن المستخدمون من التعبير عن الطلبات بصورة طبيعية. وبحسب التطبيق، قد يشمل ذلك Text أو File Uploads أو Images أو Voice. ويمكن لـ Suggested Queries وAuto-completion تعليم المستخدمين ما يستطيع النظام الإجابة عنه دون إجبارهم على تعلم Query Syntax.

ينبغي أن تحفظ Multiturn Interfaces سجل Conversation بشكل مرئي وتستخدم Prior Turns بطريقة مناسبة. ويجب أن تساعد الواجهة في Refinement للطلبات Ambiguous بدل إجبار Retrieval Layer على التخمين بصمت.

---

## 53. Query Refinement وضوابط Source Scope

تستفيد بعض التطبيقات من السماح للمستخدمين بتضييق Retrieval Scope، مثل اختيار Repository أو Source Family معينة فقط. يمنح ذلك المستخدم طريقة مباشرة للتعبير عن Constraints كان سيُضطر النظام إلى Infer لها من النص.

تكون Source Controls مهمة خصوصًا في Enterprise Knowledge Systems حيث قد تختلف إجابة السؤال نفسه حسب ما إذا كان المستخدم يريد معلومات من Project Documentation أو Chat History أو Tickets أو Policy Documents.

---

## 54. اعرض Generated Answers مع Evidence معًا

تحتوي استجابة RAG على أكثر من Generated Prose. قد تحتوي أيضًا Citations وSource Snippets وConfidence أو Hallucination Signals وProcess Metadata. تدمج UI جيدة هذه العناصر بدل إلقائها في Panels غير مترابطة.

ينبغي أن يستطيع المستخدم التمييز بين Generated Synthesis وEvidence الداعمة لها، والانتقال سريعًا من Claim إلى Source. يقلل ذلك تكلفة Verification ويزيد Trust.

## 55. Source Attribution وLineage

تكشف Citations من أين حصل النظام على Evidence. وقد يتضمن Source Attribution الجيد عنوان document وLink والصفحة أو Section والSupporting Passage المحدد عند توفره.

تُفيد Lineage فيما هو أكثر من Trust. فعندما تبدو إجابة خاطئة، يستطيع المستخدم أو المطور تحديد ما إذا كانت المشكلة ناتجة عن Source سيئ أو Retrieval Choice سيئة أو Generation سيئة. لذلك تدعم Citations كلًا من User Verification وSystem Debugging.

## 56. اشرح من Process ما يكفي لبناء الثقة

يمكن لـ Interface Cues صغيرة أن توضح أن التطبيق يقوم بـ Retrieval للأدلة ثم Generation للاستجابة. ويمكن لـ Progress Messages إظهار مراحل Retrieval أو Reranking أو Generation دون كشف Implementation Noise.

الهدف ليس كشف Internal Chain-of-thought. بل إعطاء المستخدمين Operational Explanation مفيدًا: ماذا يفعل النظام، وهل عُثر على Sources، وهل طُبقت Checks إضافية.

## 57. User Feedback بوصفها Evaluation Data

يمكن لـ Thumbs-up/down Controls أو Comments أو Issue-reporting Mechanisms التقاط الإجابات التي وجدها المستخدمون مفيدة أو إشكالية. ولا تصبح Feedback قيمة إلا إذا خُزنت مع Context كافٍ للتحليل لاحقًا: Query وRetrieved Sources وAnswer وModel/Version وUser Signal.

يمكن بعد ذلك أن تغذي Feedback مجموعات Evaluation وFailure Analysis وPrioritization. وبالتالي تُعد UI أيضًا Data-collection Surface من أجل التحسين المستمر لـ RAG.

## 58. Graceful Failure ميزة

عندما يجد Retrieval أدلة غير كافية، لا ينبغي لواجهة جيدة أن تخفي Uncertainty وراء Prose واثقة. بل يجب أن توضح أن المعلومات لم تُعثر عليها، وتقترح كيفية Refinement للطلب، أو تعرض Source Scopes بديلة.

وبالمثل، إذا منعت Safety أو Faithfulness Check إجابة، فينبغي أن يتلقى المستخدم Status واضحًا ومفيدًا بدل Generic Application Error. يحافظ Error Handling الجيد على Trust تحديدًا عندما لا يستطيع النظام تلبية الطلب.

## 59. Multimodal Evidence في الواجهة

## 61. تجميع Enterprise RAG Stack

يمكن الآن رؤية التصميم القابل للتوسع كنظام واحد مستمر:

```text
المصادر (SOURCES)
→ Ingestion مرن (Resilient Ingestion)
→ فحص الجودة / Parsing (Quality Triage and Parsing)
→ Chunking + Metadata مع الحفاظ على البنية
→ Embeddings + Indexes للبحث
→ Refresh تدريجي (Incremental Refresh)
→ توليد Candidates (Candidate Generation)
→ دمج Hybrid (Hybrid Fusion)
→ إعادة ترتيب النتائج (Reranking)
→ Generation مؤسس على الأدلة (Grounded Generation)
→ فحوص Safety + Faithfulness
→ Correction / Refusal عند الحاجة
→ Citations + UX شفافة
→ Feedback من المستخدم (User Feedback)
→ Evaluation وIteration
```

لا يعمل أي Component بمعزل. يعتمد Retrieval الأفضل على Ingestion جيد، وتعتمد Generation الجيدة على Retrieval. وتعتمد Trust على Guardrails وProvenance وUX. لذلك يعني توسيع RAG هندسة Interactions بين Components، لا مجرد ترقية Model واحد.

## مفاهيم خاطئة مهمة

### مفهوم خاطئ 1: توسيع RAG يعني فقط شراء Vector Database أكبر

يؤثر Scale في Ingestion Throughput وجودة documents وحداثة Updates ودقة Retrieval وتكلفة Generation وSafety Controls وFrontend Latency. وسعة Database بُعد واحد فقط.

### مفهوم خاطئ 2: Pipeline قابل لإعادة المحاولة آمن تلقائيًا

تكون Retries خطرة ما لم تكن Tasks ذات Idempotency. فتكرار Indexing Task غير Idempotent قد ينشئ chunks مكررة ويضعف Retrieval.

### مفهوم خاطئ 3: Hybrid Search هو مجرد Vector Search مع Results أكثر

يجمع Hybrid Search إشارات Retrieval مختلفة — Semantic وLexical — ثم يدمج Rankings أو Normalized Scores الخاصة بها. وهو ليس مجرد زيادة `k`.

### مفهوم خاطئ 4: يمكن لـ Reranking استعادة chunk فاتت Candidate Generation

لا يمكنه ذلك. فالمرحلة 2 لا ترى إلا Candidates التي تنتجها المرحلة 1، لذلك يضع Recall في المرحلة الأولى حدًا أعلى لأداء Retrieval Pipeline كاملًا.

### مفهوم خاطئ 5: يزيل RAG الـ Hallucinations

يقلل RAG الخطر عبر توفير Evidence، لكن Hallucinations قد تظل ناتجة عن Retrieval سيئ أو Source Data سيئة أو Generation غير Faithful.

### مفهوم خاطئ 6: تأتي Prompt Injection من المستخدم فقط

يمكن إخفاء Indirect Prompt Injection داخل Retrieved Documents أو Webpages، لذلك يُعد Ingested Content أيضًا Input غير موثوق.

### مفهوم خاطئ 7: Backend جيد يضمن منتج RAG جيدًا

يحتاج المستخدمون أيضًا إلى Latency مفهومة وSource Attribution وحالات Error وFeedback Controls وInterfaces تساعدهم على التعبير عن Intent وتحسينه.

## احتفظ بهذه الفكرة

**ينجح Enterprise RAG عندما تتم هندسة مسار Evidence كاملًا بوصفه نظامًا موثوقًا واحدًا.** عند Scale كبير، يجب إبقاء البيانات Fresh ونظيفة، وجعل Ingestion قابلًا لإعادة التشغيل، والحفاظ على Recall قبل Reranking من أجل Precision، والجمع بين Semantic وLexical Signals عندما يكون ذلك مفيدًا، والتعامل مع Retrieved Text باعتباره Input غير موثوق، والتحقق من Faithfulness بعد Generation، وعرض Evidence بوضوح للمستخدمين. كل Component إضافي يقدم Latency وتكلفة، لذلك تأتي جودة الإنتاج من مفاضلات مقاسة وEnd-to-end Observability، لا من إضافة Sophistication بلا قياس.
