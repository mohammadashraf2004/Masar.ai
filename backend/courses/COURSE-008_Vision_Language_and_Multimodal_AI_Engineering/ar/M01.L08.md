## لماذا تُعد المستندات مشكلة Multimodal مثالية؟

المستند ليس مجرد نص.

قد تحتوي الصفحة الواحدة على:

```text
فقرات (paragraphs)
جداول (tables)
أشكال (figures)
مخططات (charts)
حقول نماذج (form fields)
معادلات (equations)
شعارات (logos)
تسميات توضيحية (captions)
عناوين (headings)
تخطيط مكاني (spatial layout)
```

قد يعتمد المعنى على **موضع** المحتوى، وليس فقط على الكلمات.

على سبيل المثال:

```text
"Total: 1,240" — الإجمالي: 1,240
```

يعني شيئًا مختلفًا إذا ظهر:

- أسفل قسم subtotal؛
- داخل جدول tax؛
- بجوار تسمية invoice total.

وهذا يجعل المستندات Multimodal بطبيعتها.

يقدم المصدر عدة طرق لمعالجتها:

```text
1. اسأل Model مباشرةً عن الصفحة
2. حلّل المستند إلى نص/بنية قابلة للمعالجة آليًا
3. نفّذ مهامًا مركزة مثل classification أو field extraction أو layout analysis
4. استرجع الصفحة/المستند الأكثر صلة، ثم أجب اعتمادًا عليه
```

هذه ليست حلولًا متنافسة.

بل هي أدوات مختلفة لمتطلبات مختلفة.

## 1. خريطة مشكلات Document AI

ينظّم المصدر Document AI حول عدة أنواع رئيسية من workloads.

### الاستخراج المباشر للمعلومات (Direct information extraction)

```text
صورة المستند (document image)
+
سؤال (question)
→
إجابة (answer)
```

### التحليل (Parsing)

```text
صورة المستند (document image)
→
Markdown / HTML / تمثيل منظّم (structured representation)
```

### التصنيف (Classification)

```text
مستند (document)
→
فاتورة (invoice) / نموذج (form) / إيصال (receipt) / تقرير (report) / ...
```

### تحليل التخطيط (Layout analysis)

```text
مستند (document)
→
عنوان (title) / فقرة (paragraph) / جدول (table) / شكل (figure) / مناطق حقول (field regions)
```

### استخراج Token أو حقل (Token or field extraction)

```text
مستند (document)
→
الاسم (name)
العنوان (address)
التاريخ (date)
رقم الفاتورة (invoice number)
الإجمالي (total)
...
```

### Retrieval

```text
استعلام (query)
+
مجموعة مستندات كبيرة (large document collection)
→
الصفحة / المستند الأكثر صلة (most relevant page or document)
```

### الاسترجاع والتوليد متعدد الوسائط (Multimodal RAG)

```text
استعلام (query)
→ استرجاع الصفحة
→ تمرير صورة الصفحة + الاستعلام إلى VLM
→ إجابة grounded
```

توجد طريقتان واسعتان لاستخدام محتوى المستند.

### الاستراتيجية A — البقاء في Image modality

```text
صورة الصفحة (page image)
+
سؤال (question)
→
نموذج VLM
→
إجابة (answer)
```

المزايا:

- تحافظ على layout؛
- تحافظ على charts وfigures؛
- تتجنب الاعتماد على OCR preprocessing؛
- مناسبة للأسئلة الفردية.

### الاستراتيجية B — التحليل أولًا (Parse first)

```text
PDF/صفحة
→ OCR + تحويل الجداول/الأشكال/المعادلات
→ Markdown / HTML / نص منظّم
→ معالجة نصية / بحث / RAG
```

المزايا:

- تمثيل قابل لإعادة الاستخدام؛
- text indexing أسهل؛
- تكامل سهل مع text-only LLM pipelines؛
- downstream search وstorage أسهل.

يعتمد الاختيار الصحيح على ما تحتاج إليه بعد الاستخراج.

إذا كنت تريد طرح سؤال بصري واحد، فقد يكفي direct VLM inference.

أما إذا كنت تريد:

- فهرسة آلاف الصفحات؛
- البحث فيها مرارًا؛
- إنشاء knowledge base؛
- تمرير المحتوى إلى أنظمة نصية أخرى؛

فتصبح عملية parsing ذات قيمة.

## 3. Generative مقابل Extractive information extraction

يميز المصدر بين نمطين للإجابة.

### المعالجة التوليدية (Generative processing)

يرى General VLM المستند ثم **يولّد** استجابة.

مثال:

```text
السؤال (Question):
"What is the capital of France?"

الإجابة المولدة (Generated answer):
"The capital of France is Paris."
```

يكون Model حرًا في تكوين اللغة.

### المعالجة الاستخراجية (Extractive processing)

يحدد Model متخصص الإجابة مباشرةً من محتوى المستند.

مثال:

```text
الإجابة المستخرجة (Extracted answer):
"Paris"
```

يقدم المصدر هذا بوصفه localization/extraction
بدل open-ended generation.

### المفاضلة الأساسية (Core trade-off)

Generative model:

```text
أكثر مرونة (more flexible)
يمكنه الاستدلال (can reason)
يمكنه الشرح (can explain)
يمكنه الإجابة عن أسئلة مفتوحة (can answer open-ended questions)
لكنه قد يهلوس (but can hallucinate)
```

Extractive model:

```text
أضيق نطاقًا (narrower)
يعيد spans/labels موجزة
أكثر ارتباطًا مباشرةً بمحتوى المستند المرئي
غالبًا أقل تكلفة/أصغر
```

### تنبيه تعليمي بشأن صياغة المصدر

يصف الفصل المهام extractive بأنها "hallucination proof."

تعامل مع ذلك بوصفه تبسيطًا للمقارنة مع free-form
generation، **وليس** ضمانًا حرفيًا لصحة كاملة.

يمكن أن يعيد extractive pipeline span خاطئًا إذا:

- كان OCR خاطئًا؛
- كان localization خاطئًا؛
- اختار Model المنطقة الخاطئة.

وتظل الفكرة المهمة المستمدة من المصدر:

> تقيّد الأنظمة Extractive المخرجات بدرجة أكبر بكثير بما هو موجود في المستند.

## 10. SmolDocling وDocTags

يقدم المصدر نظام end-to-end document
conversion ينتج **DocTags**.

فكّر في DocTags بوصفها structural markup.

تتضمن الأمثلة مفاهيم مثل:

```text

```

يسمح ذلك بتحويل التمثيل المُولَّد


```text

هذا Token ينتمي إلى الصف 2

هذا المحتوى caption
```

## 12. اختيار Document Model المناسب

يرفض المصدر بشدة فكرة وجود Model واحد هو الأفضل عالميًا.

ابدأ من المهمة.

### المهام البسيطة للاستخراج/التصنيف (Simple extractive/classification tasks)

تشمل المرشحات Document Models متخصصة وأصغر.

الفوائد:

- serving أقل تكلفة؛
- سريعة؛
- أسهل في self-hosting؛
- عملية للمهام الضيقة.

### الاستدلال البصري المعقد (Complex visual reasoning)

استخدم modern generalist VLM عندما تحتاج إلى:

- chart reasoning؛
- open-ended QA؛
- mixed text/image understanding؛
- التعميم الواسع (broad generalization).

### التحليل الكامل للمستند (Full document parsing)

استخدم OCR/document-conversion specialists.

### Retrieval

استخدم dedicated document retrievers.

### قيّم أكثر من Benchmark accuracy

يقترح المصدر النظر في:

```text
الدقة (accuracy)
التكلفة لكل صفحة (cost per page)
المفاضلة بينهما (trade-off between both)
```

وضَع في الاعتبار أيضًا:

- latency؛
- memory؛
- self-hosting complexity؛
- language support؛
- target document type؛
- تحمل الهلوسة (hallucination tolerance).

## 14. استرجاع المستندات متعدد الوسائط (Multimodal document retrieval)

افترض أن لديك:

```text
10,000 pages — 10,000 صفحة
```

والسؤال:

```text
"How much has world temperature changed?" — كم تغيّرت درجة حرارة العالم؟
```

أنت لا تريد تمرير كل صفحة إلى Answer Model.

بدلًا من ذلك:

```text
استعلام (query)
   ↓
مسترجع المستندات (Document retriever)
   ↓
أكثر صفحة أو صفحات صلة
   ↓
Model الإجابة (Answering Model)
```

هذه هي retrieval stage في document RAG.

يقسم المصدر Document Retrievers إلى:

```text
single-vector — متجه واحد
multivector — عدة متجهات
```

## 15. استرجاع المستندات باستخدام متجه واحد (Single-vector document retrieval)

يضغط single-vector retriever مستندًا/صفحة كاملة إلى embedding واحد.

من الناحية المفاهيمية:

```text
صفحة المستند
→ مُشفّر مستند VLM (VLM document encoder)
→ متجه واحد

استعلام نصي
→ مُشفّر نص (text encoder)
→ متجه واحد

تشابه cosine (cosine similarity)
→ درجة الصلة (relevance)
```

يسمي المصدر أنظمة Document Screenshot Embedding-style مثالًا.

### الميزة

Index شديد الصغر.

إذا كان لدينا:

```text
1,000,000 documents — مليون مستند
× 1,024 dimensions — عدد الأبعاد
× 4 bytes — أربعة بايت لكل قيمة
```

فإن مساحة تخزين embedding التقريبية هي:

```text
4,096,000,000 bytes — إجمالي البايتات
≈ 4.1 GB decimal — نحو 4.1 جيجابايت عشريًا
```

قبل database/index overhead.

وهذا حجم يمكن التعامل معه على نطاق واسع.

### القيد

يجب أن يلخص متجه واحد:

- كل النص؛
- كل المناطق؛
- كل figures؛
- كل layout.

وقد تضيع معلومات دقيقة.

## 16. استرجاع المستندات بعدة متجهات (Multivector document retrieval)

يحافظ multivector retriever على عدد كبير من token-level embeddings.

من الناحية المفاهيمية:

```text
مستند (document)
→ Tokens بصرية/خاصة بالمستند
→ متجه واحد لكل Token

استعلام (query)
→ Embeddings لـ Query Tokens
```

بدل مقارنة متجه واحد بمتجه واحد،
ينفذ retriever **late interaction**.

وهذا يبقي تفاصيل المستند المحلية متاحة وقت retrieval.

## 17. Late interaction وMaxSim

يصف المصدر عملية scoring بأسلوب MaxSim.

لكل Query Token:

```text
ابحث عن Document Token الأكثر تشابهًا (find the most similar document token)
```

ثم اجمع أفضل المطابقات.

من الناحية المفاهيمية:

```text
Query Token q1 — Token الاستعلام q1
→ أفضل Document Token similarity

Query Token q2 — Token الاستعلام q2
→ أفضل Document Token similarity

Query Token q3 — Token الاستعلام q3
→ أفضل Document Token similarity

المجموع (sum)
→ درجة صلة المستند (Document relevance score)
```

يسمح ذلك لأجزاء مختلفة من السؤال بمطابقة مناطق مختلفة من الصفحة.

مثال على Query:

```text
"temperature change since the 19th century" — تغير درجة الحرارة منذ القرن التاسع عشر
```

قد تطابق Query Tokens المختلفة:

- temperature label؛
- historical-period text؛
- القيمة الرقمية (numeric value).

ومن الصعب الحفاظ على ذلك في global embedding واحد.

## 18. تكلفة Memory في Multivector retrieval

مساحة single-vector storage:

```text
عدد المستندات (documents)
× عدد الأبعاد (dimensions)
× عدد البايتات (bytes)
```

مساحة multivector storage:

```text
عدد المستندات (documents)
× عدد Tokens لكل مستند
× عدد الأبعاد (dimensions)
× عدد البايتات (bytes)
```

يقدم المصدر مثالًا توضيحيًا:

```text
1M documents — مليون مستند
× 200 tokens — مئتا Token لكل مستند
× 128 dimensions — 128 بُعدًا
× 4 bytes — أربعة بايت لكل قيمة
≈ 102.4 GB decimal — نحو 102.4 جيجابايت عشريًا
```

قبل index overhead.

قارن ذلك بمثال single-vector البالغ نحو 4 GB.

### المفاضلة (Trade-off)

Single vector:

```text
Memory أقل
Similarity أسرع
تفاصيل أقل دقة
```

Multivector:

```text
Memory أعلى
Retrieval أبطأ
مطابقة تفصيلية أفضل للمستند
```

قد تضيف Vector databases تحسينات compression وindexing، لذلك
تعتمد الأرقام الفعلية في production على implementation.

## 28. يجب أن تتطابق Coordinate systems مع مدخل Model

قد يكون dataset bounding box معرّفًا في coordinates الصورة الأصلية.

لكن processor قد يغير حجم الصورة.

افترض:

```text
الأصل (original):
W_original × H_original — أبعاد الصورة الأصلية

بعد المعالجة (processed):
W_target × H_target — أبعاد الصورة المستهدفة
```

Scale factors:

```text
scale_x = W_target / W_original
scale_y = H_target / H_original
```

ثم:

```text
x_target = x_original × scale_x
y_target = y_original × scale_y
```

يستخدم المصدر ذلك لإنشاء model-specific location tokens.

وهذا مبدأ حاسم في Spatial VLM training:

> يجب أن تعيش Grounding labels في Coordinate system نفسها التي يُدرَّب Model على
> التنبؤ بها.

```text
Token classification — تصنيف Tokens
```

### هل تحتاج إلى شرح مفتوح؟

استخدم:

```text
Generative VLM — VLM توليدي
```

### هل تحتاج إلى تحويل المستند كاملًا؟

استخدم:

```text
OCR/Document parser — OCR أو محلل مستندات
```

### هل تحتاج إلى مواقع الحقول؟

استخدم:

```text
Layout-aware model — Model مدرك للـ Layout
أو
Grounded OCR — OCR مرتبط بالموقع
```

### هل تحتاج إلى البحث في عدد كبير من المستندات؟

استخدم:

```text
مسترجع المستندات (Document retriever)
```

### هل تحتاج إلى البحث + إجابة نهائية؟

استخدم:

```text
Multimodal document RAG — RAG متعدد الوسائط للمستندات
```

### هل تحتاج إلى Serving cost منخفض لمهمة ضيقة؟

فكّر في:

```text
Small specialized model — Model صغير ومتخصص
```

قبل اختيار VLM كبير افتراضيًا.

## 43. Single-vector أم Multivector retrieval؟

اختر Single-vector عندما:

- يكون لديك ملايين المستندات؛
- تكون مساحة التخزين محدودة؛
- تكون latency حرجة؛
- تكون Queries عامة نسبيًا.

اختر Multivector عندما:

- يكون فهم الصفحة الدقيق مهمًا؛
- تكون المستندات معقدة بصريًا؛
- تكون Retrieval accuracy أهم من حجم Index؛
- يمكنك تحمل Storage وCompute أكبر.

المفاضلة الأساسية:

```text
Compression — الضغط
vs — مقابل
Fine-grained matching — المطابقة الدقيقة
```

## 44. قيّم كل مرحلة على حدة

قد يفشل نظام Document RAG بعدة طرق.

### فشل Retrieval

لا تصل الصفحة الصحيحة إلى VLM.

### فشل Parsing

يكون OCR أو table conversion خاطئًا.

### فشل Generation

تُسترجع الصفحة الصحيحة، لكن Answer Model يهلوس.

### فشل Grounding

يتم التعرف على النص، لكن موقعه يكون خاطئًا.

### فشل Task format

لا تطابق المخرجات JSON/Markdown/tag schema المطلوبة.

لذلك قيّم كل مرحلة على حدة.

أمثلة على Metrics:

```text
Retrieval: — الاسترجاع
Recall@k / NDCG — مقاييس جودة Retrieval

Extractive QA: — سؤال وجواب استخراجي
Exact match / F1 — تطابق تام ومقياس F1

OCR: — التعرّف الضوئي على الحروف
Character/word error — خطأ الأحرف أو الكلمات

Grounding: — الربط المكاني
Box overlap / Localization quality — تداخل Box وجودة تحديد الموقع

Generation: — التوليد
Task-specific QA accuracy + Manual inspection — دقة QA الخاصة بالمهمة مع فحص يدوي

Cost: — التكلفة
Latency / Memory / Cost per page — زمن الاستجابة والذاكرة والتكلفة لكل صفحة
```

يشدد المصدر خصوصًا على Model benchmarks وcost per
page عند اختيار Production document systems.

## 46. النموذج الذهني الكامل لـ Document AI

يمكن تلخيص الفصل كله هكذا:

```text
المستند (DOCUMENT)
   ↓
ماذا تحتاج؟ (WHAT DO YOU NEED?)

A. إجابة واحدة (ONE ANSWER)
   ├─ Model استخراجي (Extractive model)
   └─ VLM توليدي (Generative VLM)

B. المحتوى كاملًا (FULL CONTENT)
   ├─ OCR — التعرّف الضوئي على الحروف
   └─ محلل مستند منظّم (Structured document parser)

C. حقول منظّمة وتخطيط (STRUCTURED FIELDS / LAYOUT)
   ├─ Model بأسلوب LayoutLM
   └─ Model لـ Grounded OCR

D. بحث (SEARCH)
   ├─ مسترجع Single-vector
   └─ مسترجع Multivector

E. بحث وإجابة (SEARCH + ANSWER)
   └─ RAG متعدد الوسائط (Multimodal RAG)

التخصيص (CUSTOMIZATION)
   ↓
Fine-tuning لـ Grounded OCR
أو
DocVQA SFT — تدريب SFT لـ DocVQA

PRODUCTION DECISION   — قرار الإنتاج
   ↓
Accuracy — الدقة
Cost per page — التكلفة لكل صفحة
Latency — زمن الاستجابة
Memory — الذاكرة
Hallucination tolerance — تحمل الهلوسة
Document complexity — تعقيد المستند
```

أهم فكرة هي:

> **Document AI ليس اختيار Model واحدًا، بل هو مشكلة تفكيك للمهمة.**
> حدّد أولًا ما إذا كنت تحتاج إلى extraction أو parsing أو layout أو retrieval أو
> generation. ثم اختر أصغر Architecture وأكثرها موثوقية
> لحل هذا الاحتياج.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: "ملف PDF هو في الأساس نص عادي."

لا.

يمكن أن ترمّز المستندات معنى مهمًا داخل layout وcharts وtables وfigures و
spatial relationships.

### المفهوم الخاطئ 2: "OCR وفهم المستند هما الشيء نفسه."

يجيب OCR عن:

```text
ما الأحرف المرئية؟ (what characters are visible?)
```

أما فهم المستند فقد يتطلب أيضًا:

```text
ماذا يعني هذا الحقل؟ (what does this field mean?)
أي خلية في الجدول تجيب عن السؤال؟ (which table cell answers the question?)
كيف ترتبط هذه المناطق البصرية ببعضها؟ (how are these visual regions related?)
```

### المفهوم الخاطئ 3: "Generative VLM هو دائمًا أفضل Document Model."

لا.

قد يكون Model صغير ومتخصص أقل تكلفة وأكثر موثوقية للمهام الضيقة.

### المفهوم الخاطئ 4: "Extractive QA لا يمكن أن يخطئ أبدًا."

يقارنه المصدر بـ hallucinating generation، لكن extraction
قد يفشل أيضًا بسبب أخطاء OCR/localization/model.

### المفهوم الخاطئ 5: "Parsing يعني استخراج الكلمات فقط."

قد يحافظ Modern parsing على:

- tables؛
- equations؛
- figures؛
- captions؛
- hierarchy؛
- ترتيب القراءة (reading order).

### المفهوم الخاطئ 6: "يختلف Single-vector وMultivector retrieval فقط في حجم Model."

الاختلاف الجوهري بينهما هو مقدار تمثيل
المستند الذي يحتفظ به Index.

### المفهوم الخاطئ 7: "Multivector retrieval يمنح Accuracy مجانية."

قد يتطلب قدرًا أكبر بكثير من:

- storage؛
- retrieval compute؛
- فهرسة متخصصة (specialized indexing).

### المفهوم الخاطئ 8: "OCR-free يعني أن Model لا يتعرف على النص."

يعني فقط عدم وجود external OCR stage إلزامي.

### المفهوم الخاطئ 9: "يمكن استخدام Bounding boxes دون تغيير بعد Resize للصورة."

لا.

يجب تحويل Coordinate systems بصورة متسقة.

### المفهوم الخاطئ 10: "استدعاء Trainer هو الجزء الصعب في Grounded OCR."

العمل الصعب هو إعداد Spatial targets الصحيحة.

### المفهوم الخاطئ 11: "يتطلب Document RAG تحويل كل شيء إلى نص."

يعرض المصدر استرجاع page-image ثم Generation باستخدام VLM.

### المفهوم الخاطئ 12: "إذا أعطى Generator إجابة خاطئة، فالمشكلة دائمًا في Generator."

قد يكون Retriever قد قدم الصفحة الخاطئة.

قيّم المكونات كلًا على حدة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| ذكاء المستندات (Document AI) | أنظمة ML لفهم المستندات أو استخراجها أو تحليلها أو تصنيفها أو استرجاعها |
| الاستخراج التوليدي (Generative extraction) | يولّد Model إجابة من Document context |
| الاستخراج الاستخراجي (Extractive extraction) | يحدد/يعيد Model محتوى مرتبطًا مباشرةً بنص المستند أو مناطقه |
| أسئلة وأجوبة المستندات (DocVQA) | Visual question answering على المستندات |
| أسئلة وأجوبة الرسوم البيانية (ChartQA) | Question answering على charts |
| أسئلة وأجوبة Infographics (InfoVQA) | Question answering على infographics |
| تقنية OCR | التعرّف الضوئي على الحروف |
| تحليل المستند (Document parsing) | تحويل المستند إلى نص/تمثيل منظّم |
| تحويل Markdown (Markdown conversion) | Serialization لمحتوى الصفحة إلى Markdown |
| وسوم DocTags | Structured tags لتمثيل محتوى/تخطيط المستند |
| تحليل التخطيط (Layout analysis) | تحديد مناطق بنيوية مثل العناوين والجداول والأشكال والحقول |
| Model معتمد على OCR (OCR-dependent model) | Model يستهلك نص OCR ومواضعه إلى جانب المستند |
| Model دون OCR خارجي (OCR-free model) | Model يعالج صورة المستند دون external OCR stage |
| نموذج LayoutLMv3 | Layout-aware encoder model يجمع text وimage وbounding boxes |
| نموذج Donut | Model من نوع OCR-free document encoder-decoder |
| تقنية Grounded OCR | OCR ينتج أيضًا spatial locations |
| مربع الإحاطة (Bounding box) | مستطيل يحدد موقع المحتوى على الصفحة |
| تحجيم الإحداثيات (Coordinate scaling) | تحويل boxes بين حجم الصورة الأصلية والمعالَجة |
| إخفاء Prompt (Prompt masking) | استبعاد instruction/input tokens من target loss |
| استرجاع بمتجه واحد (Single-vector retrieval) | Embedding واحد يمثل صفحة/مستندًا واحدًا |
| استرجاع بعدة متجهات (Multivector retrieval) | عدة Embeddings تمثل صفحة/مستندًا واحدًا |
| التفاعل المتأخر (Late interaction) | مقارنة Query/Document token embeddings وقت retrieval |
| مقياس MaxSim | مطابقة أعلى similarity لكل Query Token ثم تجميعها في relevance score |
| نموذج ColPali | نهج/عائلة Models لاسترجاع المستندات Multivector وMultimodal |
| نظام DSE | استرجاع Single-vector بأسلوب Document Screenshot Embedding |
| نظام Multimodal RAG | Retrieval ثم Answer generation باستخدام Multimodal evidence |
| التكلفة لكل صفحة (Cost per page) | Production cost metric لمعالجة المستندات |
| مقياس Recall@k | ما إذا كان Evidence ذي الصلة يظهر ضمن أعلى k نتائج Retrieval |
| مقياس NDCG | Ranking metric يكافئ النتائج ذات الصلة عندما تكون قرب القمة |

تتطلب Strict extraction.**
