## 1. من LLM أساسي إلى Agent

من الطرق المفيدة لفهم Agents أن تبدأ بما **لم تكن** تطبيقات LLM المبكرة قادرة على فعله.

يستقبل تطبيق محادثة LLM أساسي نصًا وينتج نصًا. ويكون سلوكه محدودًا بالمعلومات المتاحة في training وبأي context مضمن في الطلب الحالي. يمكنه الشرح أو التلخيص أو إنشاء المحتوى، لكنه بمفرده لا يستطيع الوصول إلى ملفاتك، أو الاستعلام من database حية، أو تشغيل test suite، أو تحديث خدمة خارجية.

كانت أول خطوة كبيرة لتجاوز هذا القيد هي **Retrieval-Augmented Generation**. في تدفق RAG مبكر نموذجي، يعترض middleware استعلام المستخدم، ويبحث في vector database عن معلومات مرتبطة دلاليًا، ويضيف المعلومات المسترجعة إلى prompt، ثم يرسل prompt المُعزّز إلى LLM.

يغيّر RAG ما يمكن لـ Model **معرفته وقت الطلب**، لكنه لا يغيّر بالضرورة ما يمكنه **فعله**.

كانت الخطوة الكبيرة الثانية هي **function calling**. فبدلًا من إعطاء Model نصًا فقط، يمكن للتطبيق عرض تعريفات Tool منظمة. وبعد ذلك يمكن لـ Model إرجاع تعليمات منظمة تحدد function والـ arguments التي يريد من التطبيق استخدامها. تنفّذ بيئة compute المحيطة تلك function ثم ترسل النتيجة مرة أخرى إلى Model.

يقودنا هذا إلى فكرة **augmented LLM**: أي LLM محاط بقدرات مثل retrieval و tools و memory. وتشكل هذه القدرات الأساس الذي تُبنى عليه Agents.

### النموذج الذهني (Mental model)

فكّر في هذا التطور بهذه الصورة:

```text
LLM أساسي (Plain LLM)
    ↓
LLM + الاسترجاع (Retrieval, RAG)
    ↓
LLM + استدعاء Tool منظم (Structured Tool Calling)
    ↓
LLM معزّز (Augmented LLM) = الاسترجاع (Retrieval) + الأدوات (Tools) + الذاكرة (Memory)
    ↓
Agent = LLM معزّز (Augmented LLM) + حلقات تنفيذ/feedback متعددة الخطوات وموجّهة ذاتيًا
```

[[IMAGE_NEEDED: Evolution from chatbot to augmented LLM | A four-stage diagram showing basic LLM chat, RAG with a vector database, function calling with an execution environment, and an augmented LLM with retrieval, tools, and memory | Learner should notice that each stage adds capability around the model rather than replacing the model itself]]

التحول الأساسي ليس مجرد أن 'Model لديه Tools.' بل إن التحول الأساسي هو قدرة Model على استخدام هذه Tools داخل عملية تكرارية تغيّر فيها كل نتيجة ما يقرر فعله بعد ذلك.

## 2. ما الذي يجعل النظام Agent؟

في فصلي المصدر، يُتعامل مع Agent بوصفه نظامًا يوجّه فيه LLM عمليته واستخدامه لـ Tools بصورة ديناميكية. لا يكتفي Model بالإجابة عن prompt مرة واحدة؛ بل يقرر كيفية إكمال المهمة.

الـ **Tool** هو code خارج LLM يستطيع LLM اختيار استدعائه. ومن الأمثلة قراءة file، أو تشغيل tests، أو الاستعلام من service، أو تنفيذ إجراء deterministic آخر.

### حلقة Reason → Act → Observe

يربط المصدر حلقة action-feedback الخاصة بـ Agent بنمط ReAct:

1. **Reason** — حدّد الهدف الحالي، وافحص الحالة الحالية، وقرر الإجراء التالي.
2. **Act** — استخدم شيئًا متاحًا في البيئة، مثل Tool أو file أو input من المستخدم أو قدرة أخرى.
3. **Observe** — استقبل نتيجة الإجراء، وأضف هذا feedback إلى working context، وقرر ما سيحدث بعد ذلك.

ثم تتكرر الدورة حتى يقرر Model أن المهمة اكتملت، أو أنه يحتاج إلى إجراء آخر، أو يحتاج إلى مزيد من المعلومات من المستخدم.

[[IMAGE_NEEDED: Agent Reason-Act-Observe loop | A circular diagram with Reason → Act → Observe → Reason, with environment inputs such as tools, files, prompt, and history feeding the Act stage and tool results feeding Observe | Learner should notice that the next action depends on observed feedback, which is what makes the process adaptive]]

### مثال تطبيقي: Agent للبرمجة يكتب tests

افترض أن المستخدم يطلب من Agent كتابة unit tests للملف `feature.py`.

**الحلقة 1 — فحص الهدف**

```text
الهدف (Goal): كتابة tests
الاستدلال (Reason): أحتاج إلى فهم feature.py أولًا.
التنفيذ (Act): استدعاء Tool لقراءة file.
الملاحظة (Observe): استلام source code أو تمثيل مفيد له.
```

**الحلقة 2 — إنشاء tests**

```text
الاستدلال (Reason): أعرف الآن السلوك الذي يحتاج إلى coverage.
التنفيذ (Act): كتابة test file باستخدام قدرة كتابة files المتاحة.
الملاحظة (Observe): استلام محتوى test المكتوب أو تأكيد الكتابة.
```

**الحلقة 3 — التحقق من النتيجة**

```text
الاستدلال (Reason): كتابة tests وحدها لا تكفي؛ أحتاج إلى دليل على أنها تعمل.
التنفيذ (Act): تشغيل test suite.
الملاحظة (Observe): استلام tests الناجحة/الفاشلة أو coverage أو diagnostics أخرى.
```

إذا فشلت tests، يمكن لـ Agent أن يقرر تعديل tests أو code وتشغيلها مرة أخرى. والفكرة المهمة هي أن سلوك Agent **مدفوع بـ feedback**.

### حد فاصل مهم

وجود LLM مع Tool واحد لا يجعله Agent تلقائيًا. السلوك المميز هو القدرة على تنفيذ حلقات موجّهة ذاتيًا تُعاد فيها نتائج Tool إلى Model وتؤثر في القرارات اللاحقة.

## 3. Agents مقابل Agentic workflows

يُعد هذا التمييز من أهم الأفكار في الفصلين.

يسمح **Agent** لـ LLM بأن يقرر الإجراءات التي سيتخذها و Tools التي سيستخدمها عبر حلقة واحدة أو أكثر.

أما **Agentic workflow** فيمكنه أيضًا استخدام LLMs و tools، لكن **code هو الذي يحدد المسار**. إذ يحدد المطور التسلسل والفروع والشروط مسبقًا.

### مقارنة جنبًا إلى جنب

| السؤال | النظام (Agent) | مسار العمل (Agentic workflow) |
|---|---|---|
| من يقرر الخطوة التالية؟ | LLM بصورة أساسية | code الخاص بالتطبيق بصورة أساسية |
| هل يمكن أن يتغير المسار استجابةً لـ feedback؟ | نعم، بصورة ديناميكية | فقط عبر فروع محددة مسبقًا |
| اختيار Tool | يختاره Model من Tools المتاحة | يختاره التدفق المبرمج |
| التحكم | استقلالية أكبر لـ Model | حتمية أكبر يحددها المطور |
| نقطة القوة المعتادة | مهام مفتوحة تتطلب planning تكيفيًا | مهام تستفيد من منطق يمكن التنبؤ به |

### نمط Workflow 1: تسلسل prompts (prompt chaining)

ينفذ Workflow من نوع prompt chaining عدة استدعاءات لـ LLM في تسلسل محدد مسبقًا، بحيث تستخدم prompts اللاحقة outputs السابقة. فعلى سبيل المثال، يمكن لـ Workflow لترجمة code أن يكتشف language، ويختار مسار ترجمة، وينفذ الترجمة، ثم يتحقق منها. يساعد LLM في الخطوات الفردية، لكن التطبيق هو الذي يملك المسار.

### نمط Workflow 2: التنفيذ المتوازي (parallelization)

تُنفّذ عدة استدعاءات مستقلة لـ LLM في الوقت نفسه ثم تُدمج outputs الخاصة بها. ويكون ذلك مفيدًا عندما لا تعتمد المهام الفرعية بعضها على بعض.

### نمط Workflow 3: التوجيه (routing)

يصنّف LLM أحد inputs، ثم يرسل التطبيق هذا input إلى واحد من عدة مسارات متخصصة. فقد يذهب طلب ترجمة إلى مسار، بينما يذهب طلب فحص grammar إلى مسار آخر.

### نمط Workflow 4: المنسّق والعامل (orchestrator-worker)

يقسم LLM واحد المهمة إلى أجزاء أصغر، وتعالج LLMs العاملة تلك الأجزاء، ثم يجمع aggregator outputs الخاصة بها.

### نمط Workflow 5: المقيّم والمحسّن (evaluator-optimizer)

ينتج Model إجابة، ويقيّمها Model آخر، ثم إما تُقبل النتيجة أو تُعاد للتحسين.

## 4. ما الذي تتيحه Agents؟

تكون Agents مفيدة عندما تتطلب المهمة أكثر من مجرد إنتاج نص. فمن خلال الجمع بين LLM و retrieval و tools و memory واتخاذ القرار التكراري، يستطيع Agent التفاعل مع بيئة وتكييف خطوته التالية وفقًا لما يحدث.

يسلط الفصلان الضوء على عدة فئات شائعة:

- **Coding agents** تفحص files، وتعدّل code، وتشغّل tests.
- **Research agents** تستخدم search و memory و scratchpads وأحيانًا subagents.
- **Customer-service agents** تجمع بين knowledge retrieval والإجراءات و escalation.
- **Software-specific copilots** تعرض قدرات خاصة بالتطبيق من خلال tools.

ينبغي ألا يخلط المتعلم بين user interface و architecture. فقد يظل Agent متقدمًا ظاهرًا كأنه chat box عادي. والفرق هو ما يحدث خلف هذه الواجهة: يمكن للنظام اختيار الإجراءات، واستدعاء tools، واسترجاع معلومات جديدة، وتذكر context مفيد، وربما التنسيق مع Agents أخرى.

## 5. لماذا أُنشئ MCP؟

مع اكتساب Agents القدرة على استخدام tools، ظهرت مشكلة أخرى بوضوح: قد ينتهي الأمر بكل تطبيق و Model إلى الحاجة لموصل مخصص خاص به لكل Tool أو data source.

إذا كان لديك `M` من بيئات Model/application و`N` من integrations، فإن التكامل المخصص الساذج ينشئ تقريبًا:

```text
M × N موصلات — صيغة عدد الموصلات
```

على سبيل المثال:

```text
3 بيئات Model × 4 Tools = 12 موصلًا — مثال على عدد الموصلات
```

يكرر هذا العمل ويزيد تكلفة maintenance و debugging.

يقدم MCP بروتوكولًا مشتركًا بين تطبيقات AI و integrations. ينفذ جانب Model مكوّن MCP client، بينما ينفذ جانب integration مكوّن MCP server. وبذلك تصبح مشكلة التكامل من الناحية المفاهيمية:

```text
M + N موصلات — صيغة عدد الموصلات
```

وفي المثال نفسه:

```text
3 موصلات Model/application + 4 موصلات integration = 7 — النتيجة بعد استخدام البروتوكول المشترك
```

[[IMAGE_NEEDED: M×N integration problem transformed into M+N with MCP | First panel shows three model applications each connected separately to four tools, producing twelve links; second panel shows the applications connecting through MCP clients to MCP servers so each side needs only its protocol connection | Learner should notice how a shared protocol removes repeated pairwise connectors]]

### لماذا يهم اسم Model Context Protocol؟

كلمة **context** محورية. فالـ Context هو المعلومات المتاحة لـ Model أثناء عمله على طلب. ويمكن لـ MCP توفير context بعدة صور: أسماء Tools وتعريفاتها، و prompts، ومعرّفات resources، و data، وغير ذلك.

ويربط هذا MCP بمفهوم **context engineering**: أي اتخاذ قرار مقصود بشأن المعلومات والقدرات التي ينبغي إتاحتها لـ Model في اللحظة المناسبة حتى يتمكن من اتخاذ قرارات أفضل.

### الإلهام من LSP

استُلهم MCP من LSP. فقد وحّد LSP طريقة تواصل IDEs مع language servers من خلال بروتوكول مشترك، متجنبًا الحاجة إلى implementation منفصل لكل تركيبة من editor و language. ويطبق MCP فكرة معمارية مشابهة على تطبيقات AI و integrations.

## 6. المشكلات التي يعالجها MCP

لا يقتصر MCP على جعل استدعاءات Tool ممكنة. بل يؤكد المصدر عدة مشكلات أوسع.

### 6.1 التكامل (Integration)

تاريخيًا، كانت tools مرتبطة غالبًا بصورة وثيقة بـ codebase الخاص بالتطبيق. ويوفر MCP interface مشتركًا لاكتشاف integrations واستخدامها، بحيث لا تحتاج التطبيقات إلى موصل فريد لكل تركيبة Model-Tool.

### 6.2 التوزيع (Distribution)

عندما تُفصل integrations عن code الخاص بالتطبيق، تصبح مشاركتها أسهل. ويمكن للفرق توزيع tools و prompts و resources من خلال code أو في صورة MCP servers تعمل ويمكن للتطبيقات المتوافقة الاتصال بها.

### 6.3 الاتصال ثنائي الاتجاه (Two-way communication)

MCP ثنائي الاتجاه. يمكن للـ client طلب capabilities أو actions من server، ويمكن لـ server إعادة data والمشاركة في التفاعلات المدعومة على جانب client. ويُعد الاتصال ثنائي الاتجاه ضروريًا في Workflows التي يحتاج فيها الطرفان إلى تبادل state و results.

### 6.4 MCP بروتوكول، وليس مجرد غلاف API

يؤكد الفصلان أن MCP أقرب في فكرته إلى LSP من مجرد عرض REST API آخر. فهو يوحّد كيفية تبادل clients و servers للـ capabilities والرسائل، ولا يرتبط بـ implementation واحدة لـ SDK.

### مقارنة MCP و CLI و Agent skills

لا يدعي المصدر أن MCP هو دائمًا أفضل أداة. بل يقدم قاعدة أكثر عملية: اختر الآلية التي تناسب use case.

| الخيار | أنسب استخدام موضح في المصدر |
|---|---|
| خيار CLI | Workflows محلية للمطورين عندما تكون هناك command-line tool ناضجة وموثقة جيدًا بالفعل |
| مهارة Agent | تعليم Agent كيفية تنفيذ مهمة متخصصة من خلال تعليمات موجهة و progressive disclosure |
| بروتوكول MCP | توزيع قابل لإعادة الاستخدام لـ tool/data/prompt، وخدمات بعيدة، و integrations تراعي authentication، ووصول Agents في production |

يمكن لـ Agent skills أيضًا أن تكمل MCP بمساعدة Model على تحميل معلومات Tool التفصيلية عند الحاجة فقط، مما يقلل الاستخدام غير الضروري لـ context.

## 7. معمارية MCP: المضيف والعميل والخادم ووسيلة النقل

على المستوى العام، يتبع MCP معمارية client/server.

```text
المستخدم (User)
  ↓
التطبيق المضيف (Host Application) + LLM
  ↓
عميل MCP (MCP Client)
  ↓
وسيلة النقل (Transport) / JSON-RPC
  ↓
خادم MCP (MCP Server)
  ↓
الأدوات (Tools) / الموارد (Resources) / الموجهات (Prompts) / الأنظمة الخارجية (External Systems)
```

[[IMAGE_NEEDED: MCP host-client-server architecture | A diagram showing a host application containing an LLM and MCP client, the client communicating across a transport with an MCP server, and the server exposing tools, resources, and prompts | Learner should notice that the MCP client belongs to the host side, while capabilities are exposed by the server side]]

### التطبيق المضيف (Host application)

الـ **host application** هو التطبيق الذي يتعامل معه المستخدم ويحتوي على LLM أو يعمل معه، كما يستضيف code الخاص بـ MCP client. وتشمل الأمثلة في المصدر IDEs وتطبيقات chat على سطح المكتب و Agent frameworks و terminals مدعومة بـ AI.

وجود host ضروري لاستخدام MCP، حتى مع تمييز المصدر له عن مكونات البروتوكول الأساسية.

### عميل MCP (MCP client)

الـ **MCP client** هو code داخل host application الذي يتصل بـ MCP server وينقل الرسائل بين host/LLM وذلك server. ويصف المصدر instance من client بأنها تحافظ على اتصال one-to-one مع server واحد.

يمكن للـ client أيضًا تحديد capabilities الخاصة بـ server التي تصبح متاحة لـ host. فقد يعرض client واحد tools فقط، بينما يعرض آخر tools و prompts و resources.

### خادم MCP (MCP server)

يعرض **MCP server** capabilities من خلال interface قياسي. ويمكن أن يعمل محليًا أو عن بُعد، وعادةً ما يكون المكان الذي تنفذ فيه tools وتُقدَّم فيه resources و prompts.

### وسيلة نقل MCP (MCP transport)

يتولى **transport** قناة الاتصال بين client و server. وهو مسؤول عن نقل الرسائل وإدارة آلية الاتصال الأساسية.

## 8. مكونات MCP server الأساسية: Tools و Resources و Prompts

يمكن تنظيم capabilities الرئيسية لـ server في ثلاثة primitives.

| المكوّن الأساسي | فكّر فيه بوصفه | ما الذي يقدمه |
|---|---|---|
| **الأدوات (Tools)** | إجراءات / أفعال | functions قابلة للتنفيذ يمكن لـ Model اختيار استدعائها |
| **الموارد (Resources)** | بيانات / أسماء | files و text و schemas و documentation و blobs و data أخرى |
| **الموجهات (Prompts)** | إرشادات تفاعل قابلة لإعادة الاستخدام | prompts يوفرها server ويمكن لـ host أو المستخدم اختيار استخدامها |

### الأدوات (Tools)

تمثل Tools الإجراءات. وتصبح أسماؤها وأوصافها متاحة لـ LLM من خلال client. وإذا اختار Model إحدى Tools، تُنفذ Tool في المكان الذي يعمل فيه MCP server، ثم تعود نتيجتها عبر client إلى التطبيق.

### الموارد (Resources)

تمثل Resources البيانات. ويقدم المصدر أمثلة مثل text files و PDFs و database schemas و documentation. ويمكن وضع Resource مباشرة في model context، أو استخدامها بواسطة Tool، أو استخدامها كجزء من caching strategy.

### الموجهات (Prompts)

Prompts هي تعريفات prompt قابلة لإعادة الاستخدام يمكن لـ host application أو المستخدم اختيار تطبيقها. والحد المهم هنا هو أن prompts التي يوفرها server ليست الشيء نفسه مثل استدعاء server مباشرةً لـ LLM الخاص بـ host.

### ميزات جانب client: Sampling و Roots و Elicitation

يصف الفصلان أيضًا capabilities يمكن لـ clients توفيرها لـ servers:

- يتيح **Sampling** لـ server طلب أن ينفذ Model الخاص بـ host application استدعاء LLM.
- تتيح **Roots** لـ client تحديد مواقع filesystem المقصود إتاحتها لـ server.
- يتيح **Elicitation** لـ server أن يطلب من host application الحصول على input إضافي من المستخدم.

هناك تحذير أمني مهم هنا: لا ينبغي التعامل مع Roots على أنها security boundary كاملة. يذكر المصدر أنه يُتوقع من servers احترام Roots، لكن Roots ليست بديلًا عن access control الصحيح.

> **ملاحظة الإصدار من الفصل المقدم:** يصف الفصل Sampling و Roots بأنهما في مسار deprecation، مع ذكر استمرار الدعم حتى يوليو 2027 على الأقل. كما يصف Logging بأنه في مسار deprecation ضمن أفق الدعم نفسه. تعامل مع هذه التفاصيل بوصفها معلومات خاصة بإصدار البروتوكول عند دراسة MCP أو تنفيذه.

### أدوات مساعدة لـ server (Server utilities)

إلى جانب primitives الثلاثة الرئيسية، يناقش المصدر utilities مثل completions و logging و pagination. وتكون Pagination مفيدة بصورة خاصة عندما يجب على server إرجاع result sets كبيرة في أجزاء يمكن التعامل معها.

## 9. وسائل النقل ورسائل JSON-RPC

تُنفّذ طبقة الاتصال في MCP بواسطة transports. ويركز المصدر على نوعين مدمجين من transport:

### النقل عبر stdio

يُستخدم `stdio` بصورة أساسية مع **MCP servers المحلية**. يقوم host بتشغيل process محلية أو الاتصال بها، وتتدفق الرسائل عبر standard input/output.

### النقل عبر Streamable HTTP

يُستخدم Streamable HTTP مع **MCP servers البعيدة**. ويمكن استضافة servers البعيدة لدى third party أو داخل network مؤسسة، كما يمكنها دعم authentication واتصالات خارجية متعددة.

### أنواع رسائل JSON-RPC

بغض النظر عن transport، تُمثل رسائل MCP في صورة رسائل JSON-RPC. ويصف الفصل ثلاثة أنواع رئيسية من الرسائل:

1. **Request** — يطلب من الطرف المتصل تنفيذ operation.
2. **Response** — يحمل result أو error لطلب.
3. **Notification** — رسالة one-way لا تتطلب response.

[[IMAGE_NEEDED: Local and remote MCP transports | A split diagram showing a local host and MCP server connected through stdio on one side, and a host connecting to a remote MCP server through Streamable HTTP on the other; annotate that JSON-RPC messages travel through either transport | Learner should notice that the protocol message model stays consistent even though the transport changes]]

### Transport بوصفه حدًا أمنيًا

يشجع المصدر صراحةً على التفكير في transport بوصفه security boundary. ويمكن إنشاء transports مخصصة عندما تكون لدى التطبيق متطلبات غير معتادة تتعلق بـ performance أو security أو messaging قائم بالفعل.

## 10. دورة حياة اتصال MCP والنموذج Stateless

يميّز المصدر بين سلوك lifecycle القديم والنموذج الذي قدمته **مواصفة 2026-07-28**.

### دورة الحياة السابقة (Earlier lifecycle)

كانت اتصالات MCP الأقدم توصف بثلاث مراحل:

1. **Initialization** — يتفاوض client و server على protocol version و capabilities وتفاصيل implementation.
2. **Operation** — تنفذ requests و responses العمل الفعلي.
3. **Shutdown** — يغلق client اتصال البروتوكول.

### نموذج Stateless الموصوف في المصدر

وفق مواصفة 2026-07-28 التي يصفها الفصل، يصبح نموذج الاتصال stateless. وتختفي مرحلة initialization المنفصلة. تنتقل protocol compatibility و capabilities مع requests، ويوفر server endpoint باسم `server/discover` يستطيع client استخدامه لفحص compatibility قبل الاعتماد على capability.

بالنسبة إلى Streamable HTTP، لا يوجد اتصال دائم يجب أن يبقى مفتوحًا بالمعنى القديم؛ إذ يمكن للـ client ببساطة التوقف عن إرسال requests عندما ينتهي.

تتعامل transports المدمجة و SDK session managers مع قدر كبير من هذا التعقيد نيابةً عن المطورين.

### التفويض (Authorization)

يذكر الفصل أيضًا أن authorization يمكن تنفيذه على مستوى transport، ويصف OAuth 2.1 بأنه نهج authorization المطلوب في implementations الخاصة بـ transport التي تتضمن authorization.

### أدوات البروتوكول المساعدة (Protocol utilities)

يناقش المصدر cancellation و progress reporting. كما يذكر أن ping كان جزءًا من النموذج stateful السابق ولم يعد جزءًا من السلوك stateless الحديث، رغم أن implementations القديمة قد تظل تدعمه.

## 11. دروس عملية في تصميم MCP

فهم architecture وحده لا يكفي. يقدم المصدر عدة تحذيرات تصميمية مهمة بصورة خاصة عند بناء أنظمة Agent حقيقية.

### التحذير 1: زيادة Tools قد تجعل اختيار Tool أسوأ

يمكن أن تؤدي إضافة عدد كبير من servers و tools إلى أسماء وأوصاف متداخلة. وقد يقلل ذلك دقة اختيار Tool، ويتسبب في أن يختار Model الأداة الخطأ، أو يهلوس arguments، أو يدخل في loop متكررة، أو يتنقل دوريًا بين Tools متشابهة.

الدرس العملي هو تقييم اختيار Tool قبل إضافة capabilities وبعدها، بدلًا من افتراض أن زيادة Tools تجعل Agent أفضل دائمًا.

### التحذير 2: لا تغلّف كل REST endpoint آليًا بوصفه MCP tool

تُصمم REST APIs التقليدية عادةً في صورة endpoints صغيرة كثيرة قابلة للتركيب. وقد يكون ذلك ممتازًا للبرمجيات التي يكتبها البشر، لكنه غير مناسب لـ LLM لأن أسماء Tools وأوصافها تستهلك context، كما أن كثرة Tools الدقيقة تجعل الاختيار أصعب.

التصميم الأفضل لـ MCP هو عرض **عدد أقل من Tools الموجهة نحو المهمة** والتي تمثل إجراءات ذات معنى ينبغي لـ Agent تنفيذها.

### مثال: مقدم خدمة

يمكن لمقدم SaaS عرض MCP server يمنح Agents المتوافقة وصولًا إلى tools و prompts و resources مختارة، مع الاستمرار في فرض authentication و authorization و throttling و scaling عند حد الخدمة البعيدة.

### مثال: فريق هندسي

يمكن لفريق توصيل Coding agents بـ MCP server لنظام tickets. وتستطيع Agents تحديث tickets أثناء تنفيذ العمل، مما يقلل حاجة المطورين إلى تكرار تحديثات تتبع المشروع نفسها يدويًا.

### مثال: بيئة المطور

يمكن للمطور الجمع بين IDE مدعوم بـ AI و MCP servers مختارة بعناية من أجل documentation و infrastructure tools و APIs و language intelligence أو capabilities أخرى. والكلمة المهمة هي **بعناية**: فجودة Tool ودقة الاختيار أهم من مجرد زيادة عدد servers المتصلة إلى أقصى حد.

## 12. MCP وبروتوكولات Agents الأخرى

يركز MCP على كيفية حصول Models وتطبيقات Agentic على **tools و prompts و data resources**.

ويقارن المصدر ذلك ببروتوكولات مثل **A2A** و**ACP** التي تركز بدرجة أكبر على **التواصل بين Agents**. وهذه الأفكار متكاملة وليست متعارضة: يمكن لبروتوكول أن يساعد Agent على استخدام tools، بينما يساعد بروتوكول آخر Agents على التواصل بعضها مع بعض.

يمنحك ذلك فصلًا معماريًا مفيدًا:

```text
MCP: الـ Agent/التطبيق ↔ الأدوات (Tools)، الموجهات (Prompts)، الموارد (Resources)
A2A / ACP: الـ Agent ↔ تواصل بين Agents
```

والدرس الأوسع هو أن الأنظمة Agentic قد تعتمد في النهاية على stack من البروتوكولات المتخصصة بدلًا من بروتوكول واحد يحل كل مشكلة.

### أدوات المطور (Developer tooling)

يسلط الفصل الضوء أيضًا على SDKs الرسمية و MCP Inspector. يعمل MCP Inspector بوصفه client للاختبار و debugging، ويتيح للمطورين فحص capabilities الخاصة بـ server وتجربة سلوك MCP يدويًا. وهذا مهم لأن MCP server ينبغي اختباره بوصفه مشاركًا فعليًا في البروتوكول، لا مجرد مجموعة من functions عادية.

## مفاهيم خاطئة مهمة

### الفكرة الخاطئة 1: 'إذا كان LLM يستطيع استدعاء Tool واحد، فهو Agent.'

**لماذا هذا خطأ:** الوصول إلى Tool وحده لا ينشئ agency. السلوك المهم هو تسلسل موجّه ذاتيًا يقرر فيه Model ما الذي سيفعله، ثم ينفذ، ويراقب feedback، وقد يكرر الحلقة.

### الفكرة الخاطئة 2: 'Agentic workflow و Agent يعنيان الشيء نفسه.'

**لماذا هذا خطأ:** يختار Agent الإجراءات بصورة ديناميكية؛ أما Agentic workflow فيمكن أن يظل خاضعًا بالكامل لتحكم code.

### الفكرة الخاطئة 3: 'MCP يستبدل APIs.'

**لماذا هذا خطأ:** يقدم المصدر MCP بوصفه بروتوكولًا لـ integrations الموجهة إلى Models. وقد تظل الخدمة تستخدم APIs عادية داخليًا أو إلى جانب MCP. والتحذير يتعلق تحديدًا بتحويل كل REST endpoint بشكل أعمى إلى Tool منفصلة.

### الفكرة الخاطئة 4: 'زيادة MCP tools تجعل Agent أكثر قدرة دائمًا.'

**لماذا هذا خطأ:** يمكن لكثرة Tools المتداخلة أن تقلل دقة اختيار Tool وتهدر context.

### الفكرة الخاطئة 5: 'Roots هي security sandbox كاملة لـ filesystem.'

**لماذا هذا خطأ:** يحذر الفصل المقدم صراحةً من أن Roots ليست بديلًا عن access control.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مصطلح LLM | Model لغوي يعالج context وينتج output لغويًا |
| تقنية RAG | تسترجع معلومات خارجية ذات صلة وتضيفها إلى model context |
| نظام Augmented LLM | LLM ممتد بقدرات مثل retrieval و tools و memory |
| نظام Agent | نظام يتمحور حول LLM ويوجّه الإجراءات واستخدام Tool ديناميكيًا عبر حلقات مدفوعة بـ feedback |
| كود Tool | code خارجي deterministic يمكن لـ Model اختيار استدعائه |
| نمط ReAct | نمط Reason → Act → Observe لحل المشكلات بصورة تكرارية |
| حلقة Action-feedback | دورة متكررة تصبح فيها نتيجة الإجراء feedback لقرار Model التالي |
| مسار Agentic workflow | Workflow قائم على LLM يتحكم code في مساره بصورة أساسية |
| بروتوكول MCP | بروتوكول مشترك لتوفير tools و prompts و resources و context ذي صلة للتطبيقات المدفوعة بـ Models |
| ممارسة Context engineering | تصميم المعلومات والقدرات التي تدخل working context الخاص بـ Model |
| تطبيق Host application | تطبيق يتعامل معه المستخدم ويستضيف تفاعل LLM و code الخاص بـ MCP client |
| موصل MCP client | موصل على جانب host يتواصل مع instance واحدة من MCP server |
| مكوّن MCP server | مكوّن يعرض capabilities مثل tools و resources و prompts |
| مكوّن Tool primitive | مكوّن أساسي في MCP يمثل action |
| مكوّن Resource primitive | مكوّن أساسي في MCP يمثل data |
| مكوّن Prompt primitive | مكوّن أساسي في MCP يمثل prompts قابلة لإعادة الاستخدام لـ Model |
| آلية Transport | آلية اتصال تحمل رسائل MCP بين client و server |
| نقل stdio | Transport محلي يعتمد على standard input/output |
| نقل Streamable HTTP | Transport يُستخدم للاتصال بـ MCP server بعيد |
| بروتوكول JSON-RPC | صيغة/بروتوكول للرسائل يُستخدم مع requests و responses و notifications في MCP |
| رسالة Request | رسالة تطلب من الطرف المتصل تنفيذ operation |
| رسالة Response | رد يحتوي على result لعملية أو error |
| رسالة Notification | رسالة one-way لا تتطلب response |
| ميزة Sampling | ميزة في client تسمح لـ server بطلب استخدام LLM الخاص بـ host؛ ويصفها الفصل المقدم بأنها في مسار deprecation |
| نطاقات Roots | تلميحات لنطاق filesystem يقدمها client؛ وليست security boundary كاملة |
| طلب Elicitation | طلب من server للحصول على input إضافي من المستخدم عبر host application |

## التحقق الذاتي

قبل المتابعة، تأكد من أنك تستطيع الإجابة عن الآتي:

1. ما القدرة التي يضيفها RAG ولا يمتلكها LLM أساسي بمفرده؟
2. لماذا تجعل function calling الـ LLM أقرب إلى أن يصبح Agent؟
3. ماذا يحدث في مراحل Reason و Act و Observe؟
4. لماذا لا يصبح chatbot مزود بـ Tool عبارة عن Agent تلقائيًا؟
5. من يتحكم في المسار في Agent مقارنةً بـ Agentic workflow؟
6. ما الفرق بين Workflows من نوع routing و orchestrator-worker؟
7. ما مشكلة التكامل M × N؟
8. كيف يقلل MCP من M × N إلى M + N من الناحية المفاهيمية؟
9. ما مسؤوليات host و client و server و transport؟
10. كيف تختلف tools و resources و prompts؟
11. متى يكون stdio أنسب من Streamable HTTP؟
12. لماذا يمكن أن يضر عرض عدد كبير جدًا من Tools الصغيرة بأداء Agent؟
13. ما الذي تغير في lifecycle الخاص بـ MCP في النموذج stateless الموصوف في المصدر؟
14. لماذا لا ينبغي التعامل مع Roots بوصفها security sandbox؟

## احتفظ بهذه الفكرة

**Agent ليس مجرد LLM لديه tools: بل هو augmented LLM يستطيع بصورة متكررة أن يقرر، وينفذ، ويراقب feedback، ويتكيف. ولا ينشئ MCP هذه agency بمفرده؛ بل يوحّد كيفية اكتشاف التطبيق Agentic للـ tools و data و prompts الخارجية واستخدامها من خلال بروتوكول client-server.**
