## 1. ابدأ بالمشكلة، لا بالخوارزمية

لا ينبغي أن يبدأ مشروع Machine Learning حقيقي بالسؤال:

> “أي Model ينبغي أن أدرب؟”

بل ينبغي أن يبدأ بالسؤال:

> **“ما المشكلة التي نحلها، وكيف سيُستخدم Prediction، وما معنى النجاح؟”**

يستخدم الفصل مشروع California housing. الهدف هو التنبؤ بـ **median house value لمنطقة سكنية** اعتمادًا على معلومات أخرى عن تلك المنطقة، مثل Location وPopulation وعمر المساكن وMedian income.

قد يبدو هذا Prediction task مباشرًا، لكن Business context مهم. Prediction ليس القرار التجاري النهائي، بل يصبح Input داخل نظام Downstream لتحليل الاستثمار.

وهذا يغير مدى الجدية التي ينبغي أن نفكر بها في:

- Prediction accuracy،
- Failure modes،
- Update frequency،
- Reproducibility،
- Interfaces بين Components،
- وMonitoring.

{{image:housing-business-ml-pipeline}}

### صياغة Learning problem

اطرح أسئلة تصنيف ML الأساسية:

**هل هي Supervised؟**

نعم. لكل District مجموعة Input features وTarget معروفة هي `median_house_value`.

**Classification أم Regression؟**

Regression، لأن Target قيمة رقمية.

**Feature واحدة أم Features متعددة؟**

يتم استخدام Features متعددة، ولذلك فهذه **multiple regression**.

**Target واحدة أم Targets متعددة؟**

يتم التنبؤ بقيمة واحدة فقط لكل District، ولذلك فهي مشكلة **univariate regression**.

**Batch learning أم Online learning؟**

Data صغيرة بما يكفي لتناسب Memory، ولا يوجد Continuous high-speed stream، ولا توجد حاجة لتكيف سريع. لذلك يُعد Batch learning مناسبًا.

هذا التصنيف البسيط يضيّق Design space مباشرة.

### افهم الحل الحالي

قبل استبدال Process قائمة، افهمها أولًا.

في الفصل، يقدّر Experts أسعار المناطق يدويًا وقد يخطئون بأكثر من 30%. وهذا يمنحنا:

- Business baseline،
- سببًا لـ Automation،
- ومرجعًا تقريبيًا لتحديد ما إذا كان ML solution ذا قيمة.

لا يحتاج Machine Learning model إلى أن يكون مبهرًا أكاديميًا ليكون مفيدًا. بل يجب أن يحسن Workflow الحقيقية بدرجة تكفي لتبرير Cost وRisk.

### Pipelines جزء من النظام

**Data pipeline** هي سلسلة من Processing components.

مفاهيميًا:

```text
البيانات الخام (raw data)
   |
الإدخال (ingestion)
   |
التحقق (validation)
   |
المعالجة المسبقة (preprocessing)
   |
النموذج (model)
   |
التنبؤ (prediction)
   |
التطبيق اللاحق (downstream application)
```

غالبًا ما تُفصل Pipeline components حتى تتمكن فرق مختلفة من تطويرها وتشغيلها بصورة مستقلة.

يمكن أن يجعل ذلك النظام Robust، لكنه يخلق خطرًا: فقد يستمر Upstream component معطل في إنتاج Outputs قديمة أوفاسدة بينما تستمر Downstream components في العمل.

لذلك Pipeline بلا Monitoring ليست موثوقة حقًا.

### اختر Performance measure قبل التدريب

بالنسبة إلى Regression task، يركز الفصل على **root mean squared error (RMSE)**.

للتنبؤات `ŷ(i)` والـ Targets الحقيقية `y(i)`:

```text
RMSE = sqrt(
    متوسط (prediction - target)^2
)
```

تعاقب RMSE الأخطاء الكبيرة بصورة أقوى لأن Errors يتم تربيعها.

على سبيل المثال:

```text
true price      = $200,000 — السعر الحقيقي
predicted price = $230,000 — السعر المتوقع
error           = $30,000 — الخطأ
```

إذا احتوت عدة Predictions على أخطاء كبيرة جدًا، ترتفع RMSE بوضوح.

مقياس شائع آخر هو **mean absolute error (MAE)**:

```text
MAE = متوسط |prediction - target|
```

تكون MAE عادة أقل حساسية للـ Large outliers.

تفسير عملي:

```text
RMSE -> تهتم أكثر بالأخطاء الكبيرة
MAE  -> تعامل حجم الخطأ بصورة أكثر خطية
```

يربط المصدر RMSE بـ `L2` norm وMAE بـ `L1` norm. لا تحتاج إلى حفظ كل Norm notation الآن، لكن يجب أن تفهم الفرق العملي: **اختيار Metric يغير ما يكافأ عليه Model أويعاقب بسببه.**

### تحقق من الافتراضات قبل Coding

لنفترض أن Downstream system يحتاج فقط إلى ثلاث Categories:

```text
cheap — رخيص
medium — متوسط
expensive — غالٍ
```

حينها قد يكون بناء Regression system عالي الدقة غير ضروري. وقد يكون من الأفضل صياغة Project كمشكلة Classification.

لهذا يجب التحقق من Assumptions مع Stakeholders قبل قضاء أشهر في Modeling.

الحل الصحيح تقنيًا للمشكلة الخطأ يظل مشروعًا فاشلًا.

هل تتحسن Validation performance؟

4. كرر حتى تعمل كل Fold كـ Validation مرة واحدة،
5. لخّص Scores.

- يمكنك اختيار Computational budget مباشرة باستخدام `n_iter`.

```text

Errors غير مترابطة

 |

```

ينبغي عادة تحميل Model مرة واحدة عند بدء Service، لا إعادة تحميلها من Disk لكل Prediction.

### راقب Live performance

Deployment لا تجمد العالم.

قد يتدهور Performance لأن:

- Data distribution تتغير،
- User behavior يتغير،
- Upstream feature تصبح قديمة،
- Sensor أوData source تتعطل،
- Categories جديدة تظهر،
- Missing-value rates ترتفع.

لهذا تحتاج Production ML إلى **monitoring**.

تشمل Signals الممكنة:

```text
مقياس جودة النموذج
مقياس العمل اللاحق (business metric)
معدل القيم المفقودة في المدخلات
انجراف متوسط/انحراف الـ Features
قيم فئوية جديدة
توزيع التنبؤات
زمن الاستجابة (latency)
معدل الأخطاء
```

أحيانًا تصل Ground-truth labels متأخرة أوقد لا تصل إطلاقًا. في هذه الحالات، يمكن لـ Downstream business metrics أوHuman review المساعدة على تقدير Quality.

### قد يكون Human evaluation جزءًا من Monitoring

لا يمكن مراقبة بعض المشكلات بصورة موثوقة باستخدام Automatic metrics فقط.

قد تحتاج Sample من Predictions إلى Expert أوHuman review.

الفكرة المهمة أن Monitoring plan يجب تصميمها للمهمة الفعلية، لا نسخها ميكانيكيًا من نظام آخر.

### أتمت Retraining بحذر

إذا تغيرت Data باستمرار، يوصي الفصل بأتمتة جزء كبير من Lifecycle:

```text
اجمع Fresh data
      |
تحقق / أضف Labels
      |
درّب Candidate model
      |
نفّذ Tuning
      |
قيّمها مقابل Current model
      |
Deploy فقط إذا كانت مقبولة
```

Automatic retraining لا يجب أن تعني Automatic blind deployment.

يمكن أن تكون New model أسوأ.

### راقب Inputs وكذلك Outputs

انتظار انهيار Final model accuracy قد يكون متأخرًا جدًا.

يمكن لـ Input monitoring اكتشاف المشكلات مبكرًا.

أمثلة:

- ارتفاع مفاجئ في Missing fields،
- تغير Mean أوStandard deviation للـ Feature،
- توقف Upstream source عن التحديث،
- ظهور Unseen categories داخل Categorical feature.

يكون هذا غالبًا أول مؤشر على ابتعاد النظام عن Training conditions.

### احتفظ بـ Model وDataset versions

احتفظ بنسخ احتياطية من:

- Trained models،
- Configuration،
- Evaluation results،
- Datasets،
- منطق Preprocessing.

لماذا؟

لأنك قد تحتاج إلى الإجابة عن:

```text
أي Model كانت تعمل الأسبوع الماضي؟
أي Dataset دربتها؟
ما الذي تغير؟
هل يمكن تنفيذ Rollback فورًا؟
هل يمكن مقارنة New model بالـ Old data؟
```

Rollback متطلب تشغيلي، وليس فكرة لاحقة.

### عمليات تعلم الآلة (MLOps)

كل هذه الجوانب — Training automation وDeployment وMonitoring وVersioning وRollback وReproducibility وReliable data/model pipelines — تنتمي إلى المجال الأوسع **MLOps**.

أحد أهم دروس الفصل أن Learning algorithm ليست سوى جزء صغير من النظام الحقيقي.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> أول خطوة في ML project هي اختيار Algorithm.

### لماذا هذا خطأ

يحدد Business objective وDownstream use كيف ينبغي صياغة المشكلة، وأي Metric مهم، وما Data المطلوبة، وحتى ما إذا كان Machine Learning مناسبًا أصلًا.

### المفهوم الخاطئ 2

> يمكنني استكشاف Test set طالما أنني لا أدرب عليها مباشرة.

### لماذا هذا خطأ

يمكن للقرارات البشرية أيضًا أن Overfit. قد تؤثر رؤية Patterns داخل Test set على Feature engineering وModel selection وHyperparameter choices، مما يؤدي إلى Data snooping bias.

### المفهوم الخاطئ 3

> Training RMSE تساوي Zero تعني أن Model مثالي.

### لماذا هذا خطأ

قد تعني أن Model حفظ Training set. نحتاج إلى Validation أوCross-validation لتحديد ما إذا كان Model يعمم.

### المفهوم الخاطئ 4

> Scaling وإصلاح Skewed distributions هما العملية نفسها.

### لماذا هذا خطأ

يغير Scaling الـ Numerical scale. أما Log أوSquare-root أوBucket أوأي Distributional transformation أخرى فتغير Shape أوRepresentation الخاصة بـ Feature. وقد تحتاج إلى كليهما.

### المفهوم الخاطئ 5

> يمكن كتابة Preprocessing كـ Ad-hoc code منفصلة للتدريب وProduction.

### لماذا هذا خطأ

تؤدي Duplicated preprocessing بسهولة إلى Training-serving mismatch. تحافظ Fitted pipeline على Transformations وModel معًا وتضمن أن New data تتبع Preprocessing التي تم تعلمها.

### المفهوم الخاطئ 6

> بمجرد Deploy للـ Final model، يكون Project قد انتهى.

### لماذا هذا خطأ

تحتاج Production models إلى Monitoring وRetraining strategies وData-quality checks وVersioning وRollback وأحيانًا Human evaluation.

| Grid search | تقييم Exhaustive لمجموعات Hyperparameters المدرجة |
| Randomized search | تقييم عدد محدد من Hyperparameter combinations المأخوذة عشوائيًا |
| Feature importance | تقدير لمقدار اعتماد Fitted model على Features مختلفة |
| Model serialization | حفظ Fitted model/Pipeline لتحميلها لاحقًا |
| Data drift | تغير Production data بطريقة قد تقلل Model performance |
| Rollback | الرجوع بسرعة إلى Model أوDataset سابقة معروفة بأنها جيدة |
| MLOps | Practices لنشر ML systems ومراقبتها وإعادة تدريبها وVersioning لها وتشغيلها بصورة موثوقة |

## التحقق الذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة:

1. لماذا ينبغي أن يبدأ Machine Learning project بـ Business objective بدل Model selection؟
2. لماذا تمت صياغة Housing project كمشكلة Supervised وMultiple وUnivariate regression مع Batch learning؟
3. متى تكون MAE أكثر جاذبية من RMSE؟
4. ما Data snooping bias، ولماذا يجب إنشاء Test set مبكرًا؟
5. لماذا قد يكون Stratified sampling أفضل من Purely random train/test split؟
6. ماذا يمكن أن يكشف Histogram قد لا تكشفه `describe()` وحدها؟
7. لماذا يمكن لـ Pearson correlation أن تفوّت Relationship مهمة؟
8. لماذا يجب Fit للـ Imputers والـ Scalers على Training data فقط؟
9. لماذا يكون One-hot encoding مناسبًا لـ Unordered category مثل `ocean_proximity`؟
10. ما المشكلة التي تحلها Scikit-Learn pipelines؟
11. لماذا لا تثبت Zero training error في Decision tree أنها Model جيدة؟
12. ماذا تخبرك Cross-validation لا تستطيع Training score واحدة إخبارك به؟
13. متى تكون Randomized search أفضل من Grid search؟
14. لماذا لا ينبغي استخدام Final test set في Hyperparameter tuning متكرر؟
15. ما الذي ينبغي Monitoring له بعد Deploy لـ ML model؟
