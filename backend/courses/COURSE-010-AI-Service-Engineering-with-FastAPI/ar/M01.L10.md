## مخرجات التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- فصل تحسين الأداء (Performance optimization) عن تحسين جودة المخرجات.
- شرح متى تكون Batch processing أفضل من إرسال عدد كبير من Model requests منفردة.
- تصميم Structured batch requests وفهم Provider batch-job workflows.
- شرح ما الذي توفره Caching ولماذا تهم Cache freshness.
- التمييز بين Keyword caching وSemantic caching وContext/Prompt caching.
- شرح كيف يمكن لـ Redis توحيد Application caches عبر عدة FastAPI instances.
- تصميم Semantic cache حول Embeddings وSimilarity search وVector store.
- شرح لماذا يمكن لـ Semantic cache إنشاء Hits خاطئة حتى عندما تكون Queryان متشابهتين.
- ضبط Semantic-cache thresholds واختيار Eviction policy.
- شرح كيف تختلف Prompt/Context caching عن Response caching.
- شرح العلاقة بين Model precision وMemory requirements وQuantization.
- مقارنة FP32 وFP16 وBF16 وINT8 وINT4 وLower-precision formats بصورة مفاهيمية.
- وصف هدف GPTQ-style post-training quantization.
- استخدام Schema-driven structured outputs لتكامل موثوق بين Model وApplication.
- شرح لماذا تكون Structured outputs أقوى من مجرد قول "please return JSON".
- بناء Prompts باستخدام بنية Role-Context-Task.
- التمييز بين Zero-shot وFew-shot وDynamic few-shot prompting.
- شرح عائلات Prompting التي يقدمها الفصل: Thought generation وDecomposition وEnsembling وSelf-criticism وAgentic prompting.
- شرح كيف تحوّل Tool/Function calling الـ LLM إلى Component داخل Agentic workflow.
- معرفة متى قد تساعد Fine-tuning ولماذا ينبغي ألا تكون عادةً أول Optimization تتم تجربتها.
- وصف Workflow الأساسي للـ Fine-tuning: إعداد البيانات، التدريب، التقييم، ثم Deployment.
- اختيار Optimization technique بناءً على ما إذا كانت Bottleneck هي Cost أوLatency أوThroughput أوMemory أوOutput quality.

## 1. ابدأ بتحديد ما الذي تحاول تحسينه (Start by identifying what you are optimizing)

يبدأ الفصل بتمييز مهم:

```text
Optimization لا تعني شيئًا واحدًا.
```

قد تحتاج خدمة AI إلى تحسين:

- Latency،
- Throughput،
- Operating cost،
- Memory usage،
- Output quality،
- Output consistency،
- Downstream reliability.

يجمع المصدر Techniques في فئتين واسعتين.

### تحسينات موجهة للأداء (Performance-oriented optimizations)

- Batch processing،
- Caching،
- Model quantization.

### تحسينات موجهة للجودة (Quality-oriented optimizations)

- Structured outputs،
- Prompt engineering،
- Fine-tuning.

قد تؤثر Technique واحدة في أكثر من Dimension، لكن هذا التصنيف يمنحك نقطة بداية مفيدة.

### شخّص المشكلة قبل التحسين (Diagnose before optimizing)

افترض أن Application مكلفة أكثر من اللازم.

أسباب محتملة:

```text
تتكرر Queries نفسها
→ مشكلة Caching

آلاف العناصر غير التفاعلية
→ مشكلة Batching

Model كبيرة Self-hosted بالكاد تتسع في GPU
→ مشكلة Quantization

Prompt ضخمة ومتكررة
→ مشكلة Context cache
```

والآن افترض أن Responses غير موثوقة.

أسباب محتملة:

```text
JSON غير صالح
→ مشكلة Structured output

Instructions غامضة
→ مشكلة Prompt design

سلوك متخصص لم تتعلمه Model جيدًا بما يكفي
→ ربما مشكلة تحتاج Fine-tuning
```

### Optimization هي إدارة للمفاضلات (Trade-off management)

قاعدة Engineering مفيدة هي:

> **يجب أن تمتلك كل Optimization مقياسًا مستهدفًا وTrade-off مقبولة.**

على سبيل المثال:

```text
Quantization
→ Memory أقل
↔ Trade-off محتملة في Quality/Speed

Semantic cache
→ عدد أقل من Retrieval/Model calls المكلفة
↔ Cache hits قديمة أوخاطئة

Ensembling
→ إجابات قد تكون أكثر موثوقية
↔ Model calls أكثر وCost أعلى
```

## 2. Batch processing: توقف عن إرسال Request منفردة لكل عنصر

تخيّل أنك تحتاج إلى Classification لـ:

```text
10,000 document titles — عشرة آلاف عنوان مستند
```

التصميم Naive هو:

```text
المستند 1 → استدعاء API
المستند 2 → استدعاء API
المستند 3 → استدعاء API
...
المستند 10,000 → استدعاء API
```

تشمل المشكلات:

- Request volume كبيرة،
- ضغط على Rate limits،
- Network overhead،
- Cost أعلى،
- Total processing time أطول.

يقدم الفصل استراتيجيتين للـ Batching.

### الاستراتيجية A — إعادة عدة Outputs في Request عادية واحدة

بدل Schema تمثل Classification واحدة:

⟦CODE_0⟧

عرّف Batch schema:

⟦CODE_1⟧

بعد ذلك تستطيع Model request واحدة معالجة عدة Inputs.

### الاستراتيجية B — استخدام Provider batch API

بالنسبة إلى Offline jobs الكبيرة، قد يوفر Provider خدمة Batch مخصصة.

من الناحية المفاهيمية:

```text
تجهيز ملف الدُفعة
    ↓
رفع الملف
    ↓
إرسال مهمة دفعة في الخلفية
    ↓
يضع المزوّد العمل في طابور/يعالجه
    ↓
استعلام/جلب حالة المهمة
    ↓
تنزيل النتائج
```

يكون ذلك مناسبًا بصورة خاصة عندما **لا** يحتاج المستخدمون إلى إجابة فورية.

أمثلة:

- Document classification،
- Large translation jobs،
- Offline extraction،
- Bulk summarization.

### صيغة JSONL

ينشئ المصدر ملف JSON Lines.

كل Line هي Request object واحدة.

مثال مفاهيمي:

```text
{"custom_id": "request-1", ...}    # أسطر JSONL لطلبات الدفعة
{"custom_id": "request-2", ...}
{"custom_id": "request-3", ...}
```

تسمح لك `custom_id` بربط Results المُعادة بالعناصر الأصلية.

### Batch work مقابل Interactive work

تمييز مفيد هو:

```text
Interactive request
→ المستخدم ينتظر
→ حسّن Response latency

Offline batch
→ المستخدم لا يحتاج Output فورية
→ حسّن Cost/Throughput
```

لا تُجبر Offline workload على المرور عبر Interactive endpoint إذا كانت هناك Batch mechanism مناسبة.

## 3. Caching: أعد استخدام العمل المكلف

كثير من عمليات GenAI مكلفة.

أمثلة:

- Model generation،
- Semantic retrieval،
- Parsing للمستندات،
- حساب Embeddings،
- الوصول إلى External services.

إذا طلبت عدة Requests النتيجة نفسها، فإن إعادة حسابها تهدر الموارد.

تحول Caching هذا:

```text
Request
→ Computation مكلفة
→ Response
```

إلى:

```text
Request
→ Cache lookup

Cache hit
→ أعد Stored result

Cache miss
→ نفّذ Computation
→ خزّن Result
→ أعدها
```

### الفوائد

يشدد المصدر على:

- Latency أقل،
- Server load أقل،
- Bandwidth usage أقل،
- Operating cost أقل.

### التقادم (Staleness)

قد تصبح Cached data قديمة.

لذلك تحتاج كل Cache إلى Freshness policy.

اسأل:

```text
كم من الوقت يمكن أن تظل هذه الإجابة صالحة؟
```

قد تتحمل Public FAQ مدة Cache أطول.

أما إجابة شديدة التخصيص وسريعة التغير فقد تحتاج إلى:

- Lifetime قصيرة،
- Active invalidation،
- عدم استخدام Cache.

### ثلاث فئات للـ Cache في الفصل

1. Keyword/Exact caching،
2. Semantic caching،
3. Caching للسياق/الـ prompt.

تعمل هذه الفئات على Cache **أشياء مختلفة**، ولا ينبغي الخلط بينها.

## 4. Keyword caching: Input مطابق، Key مطابق

Keyword caching هي أبسط صورة.

من الناحية المفاهيمية:

```text
Key = Input المطابق حرفيًا
Value = Cached result
```

مثال:

```text
"What is FastAPI?" — ما FastAPI؟
→ Cached answer
```

قد تفشل Input مختلفة:

```text
"Explain FastAPI." — اشرح FastAPI.
```

في Cache lookup حتى لو كان Intent مشابهًا.

### حالات استخدام جيدة

- Exact API calls متكررة بكثرة،
- Deterministic helper functions،
- Stable endpoint results،
- Requests متطابقة ومتكررة.

### نمط FastAPI cache

يعرض المصدر تهيئة Shared cache أثناء Application lifespan.

من الناحية المفاهيمية:

⟦CODE_2⟧

ثم:

⟦CODE_3⟧

### لماذا Redis؟

إذا كان لديك عدة Application replicas:

```text
FastAPI A
FastAPI B
FastAPI C
```

فإن Local process memory ليست مشتركة.

تسمح Centralized Redis cache لكل Instances بالوصول إلى Entries نفسها.

### ترويسات Cache-Control

يقدم المصدر HTTP cache directives شائعة.

| Directive | المعنى |
|---|---|
| `max-age` | تظل Response Fresh لمدة محددة |
| `no-cache` | ينبغي لـ Client عمل Revalidate قبل إعادة الاستخدام |
| `no-store` | لا تخزّن Response |
| `private` | خزّن فقط في Private cache مثل Browser |

### قيد Exact caching

تعمل Keyword caching بأفضل صورة عندما تكون Queries المتكررة متطابقة حرفيًا.

لكن Natural-language interfaces تنتج غالبًا صيغًا كثيرة متكافئة دلاليًا.

وهذا يحفز Semantic caching.

## 5. Semantic caching: Cache حسب المعنى

تستخدم Semantic caching تمثيلات Vector.

بدل سؤال:

```text
هل Strings متطابقة؟
```

تسأل:

```text
هل Queries متشابهة دلاليًا بما يكفي؟
```

مثال:

```text
How do you build generative services with FastAPI? — كيف تبني خدمات Generative باستخدام FastAPI؟

What is the process of developing FastAPI services for GenAI? — ما عملية تطوير خدمات FastAPI لـ GenAI؟
```

هذان نصان مختلفان لكن Intent متشابه.

### Pipeline

```text
Query جديدة
   ↓
Embedding model
   ↓
Query vector
   ↓
ابحث في Cache vectors
   ↓
هل التشابه كافٍ؟
   ├── نعم → Cache hit
   └── لا  → نفّذ العملية المكلفة
                ↓
             خزّن Result في Cache
```

[[IMAGE_NEEDED: Keyword versus semantic cache | Side-by-side flow: keyword cache compares exact text keys, semantic cache embeds queries and compares vectors; show two differently worded but equivalent questions missing exact cache yet hitting semantic cache | Learner should notice that semantic caching uses meaning rather than exact wording]]

### لماذا يمكن أن توفر عملًا كبيرًا؟

قد يتلقى Q&A system بصورة متكررة Variations للأسئلة نفسها.

يمكن لـ Semantic cache تجنب تكرار:

- Vector-store search،
- Document retrieval،
- Model generation.

### لكن Semantic similarity ليست Task equivalence

هذا هو أهم خطر.

تأمل:

```text
Summarize this text in 100 words. — لخّص هذا النص في 100 كلمة.

Summarize this text in 50 words. — لخّص هذا النص في 50 كلمة.
```

Queries متقاربة دلاليًا.

لكن إعادة Cached output نفسها تخالف أحد الطلبين.

لذلك:

> **Semantic similarity لا تعني تلقائيًا أن Cached result قابلة لإعادة الاستخدام.**

ولهذا يختار المصدر عرض Semantic cache لـ **Retrieved RAG documents** بدل عمل Cache عمياء لكل Final model responses في كل الحالات.

## 6. ضع Semantic caching داخل RAG pipeline

يحدد الفصل موقعين مفيدين للـ Cache.

### الخيار A — قبل LLM

```text
Query
→ Semantic response cache
→ هل توجد Cached final answer؟
```

فائدة محتملة:

- تجاوز Retrieval وGeneration معًا.

المخاطرة:

- قد تتطلب Queries المتشابهة Outputs مختلفة.

### الخيار B — قبل Vector store

```text
Query
→ Semantic retrieval cache
→ هل توجد Cached relevant documents؟
```

فائدة محتملة:

- تجاوز Vector-store searches المتكررة،
- مع السماح لـ Model بتوليد Response جديدة.

ينفذ المصدر النهج الثاني.

### Architecture

```text
User query
   ↓
Query embedding
   ↓
Semantic cache
   ├── Hit → Cached documents
   │
   └── Miss
         ↓
       Vector DB
         ↓
       Relevant documents
         ↓
       أدخل Documents في Cache
         ↓
يتلقى LLM الـ Context
```

[[IMAGE_NEEDED: Semantic cache in RAG | Diagram showing user query → embedding → semantic cache; cache hit returns documents directly, cache miss queries document vector store and stores retrieved documents in cache before prompt augmentation and LLM generation | Learner should notice that this cache avoids repeated retrieval while preserving fresh generation]]

### مسؤوليات Cache client

تحتفظ Custom cache في المصدر بـ:

- Query vector،
- حمولة المستند المخزَّنة مؤقتًا (cached).

العمليات:

```text
initialize    # التهيئة
insert    # الإدراج
search    # البحث
```

### مسؤوليات Document store

تحتوي Vector store على Knowledge المفهرسة الفعلية.

العمليات:

```text
تهيئة المستندات
البحث باستخدام query vector
إرجاع أفضل المستندات
```

### خدمة Semantic cache

تنفذ Orchestration layer:

1. عمل Embedding للـ Query،
2. البحث في Cache،
3. فحص Distance/Threshold،
4. إعادة Cached documents عند Hit،
5. وإلا البحث في Document store،
6. تخزين Retrieved documents في Cache،
7. إعادة Documents.

هذا مثال واضح على الجمع بين:

- Embeddings،
- Vector search،
- Cache policy،
- استدعاءات قاعدة بيانات async.

## 7. ضبط Semantic-cache thresholds

تحتاج Semantic cache إلى Decision boundary.

تسأل Cache:

```text
هل Query الجديدة مشابهة بما يكفي لإعادة استخدام Stored value؟
```

تعتمد الإجابة على Similarity/Distance metric.

في مثال Euclidean-distance في المصدر:

```text
Distance أصغر
→ تشابه أكبر

distance <= chosen threshold
→ Cache hit
```

قد تعرض Libraries أخرى Similarity score باتجاه معاكس.

لذلك افهم Metric دائمًا قبل تعيين Threshold.

### Threshold متساهلة أكثر من اللازم

قد تضرب Queries غير مرتبطة أو مختلفة بشكل مهم Cache entry نفسها.

النتيجة:

- Wrong answer،
- تجاهل User constraints،
- Behavior تبدو قديمة.

### Threshold صارمة أكثر من اللازم

قد تفشل Queries المتكافئة فعليًا في الوصول إلى Hit.

النتيجة:

- Cache hit rate أقل،
- Savings أقل في Cost/Latency.

### اضبطها تجريبيًا

اجمع Representative queries.

بالنسبة إلى Candidate thresholds، قِس:

- Hit rate،
- False-hit rate،
- Latency،
- Saved requests،
- Output quality.

لا تختر Semantic threshold لمجرد أن هناك Library default.

## 8. سياسات Cache eviction

Cache memory محدودة.

وفي النهاية يجب إزالة Entries.

يقدم الفصل عدة Policies.

### FIFO — الداخل أولًا يخرج أولًا

أزل أقدم Entry.

مفيدة عندما تكون كل العناصر ذات قيمة متقاربة.

### LRU — الأقل استخدامًا مؤخرًا

أزل Item التي لم يتم الوصول إليها لأطول مدة.

اختيار شائع كبداية.

### LFU — الأقل استخدامًا تكرارًا

أزل Items ذات أقل Access count.

مفيدة عندما يجب الاحتفاظ بالعناصر كثيرة الاستخدام.

### MRU — الأكثر استخدامًا مؤخرًا

أزل أحدث Item تم الوصول إليها.

أقل شيوعًا، لكنها مفيدة لأنماط Access خاصة.

### Random replacement

أزل Entry عشوائية.

بسيطة ومنخفضة Overhead.

### اختيار Policy

اسأل:

```text
هل يتنبأ الاستخدام الحديث بالاستخدام المستقبلي؟
هل Frequency مهمة؟
هل كل Entries متساوية؟
ما تكلفة تتبع Metadata؟
```

يقترح المصدر LRU كنقطة بداية معقولة قبل اختبار Alternatives.

## 9. Context/Prompt caching: أعد استخدام Prefixes كبيرة ومتكررة

تختلف Prompt caching عن Output caching.

هي **لا** تعني:

```text
Prompt نفسها → Answer نفسها
```

بل تعيد استخدام العمل المرتبط بـ Context كبيرة ومتكررة.

حالة استخدام:

```text
System prompt/Document ضخمة
       +
User question جديدة وصغيرة
```

إعادة معالجة Huge context كل مرة هدر.

### Architecture مفاهيمية

```text
Context كبيرة قابلة لإعادة الاستخدام
      ↓
يحسب Provider/Model Internal state قابلة لإعادة الاستخدام
      ↓
Cache
      ↓
Question A → إعادة استخدام Cached context
Question B → إعادة استخدام Cached context
Question C → إعادة استخدام Cached context
```

{{image:context-caching}}

### سيناريوهات مناسبة من الفصل

- Long system instructions،
- Long multiturn context،
- Repeated analysis لملفات كبيرة،
- Repeated queries على Document sets،
- Codebase analysis،
- Long-form document summarization،
- عدد كبير من In-context examples.

### TTL

قد تمتلك Cache Time-to-live.

```text
TTL
→ المدة التي تظل فيها Cached context متاحة
```

TTL أطول:

- Reuse أكثر،
- Retained state/storage أكبر.

TTL أقصر:

- Staleness/State أقل،
- فرص Reuse أقل.

### Stateful behavior

يحذر المصدر من أن تبني Provider-side context caching يدخل Stateful behavior عبر Requests.

قد يعيد Provider استخدام Content تم تقديمها سابقًا.

وهذا قد يهم في:

- Privacy،
- Retention،
- Data lifecycle،
- Architecture.

### Prompt caching لا تعمل Cache للـ Output

حتى إذا تمت إعادة استخدام Cached context نفسها والسؤال نفسه، يمكن لـ LLM إنتاج Response مختلفة لأن Generation غير حتمية.

هذا التمييز أساسي.

## 10. اختر Caching layer الصحيحة

استخدم هذه المقارنة:

| Cache | Key/Trigger | ما الذي يُعاد استخدامه؟ | الفائدة الرئيسية | الخطر الرئيسي |
|---|---|---|---|---|
| Keyword | Request/Input مطابقة | نتيجة نهائية/نتيجة دالة | بسيطة وسريعة | Hit rate منخفضة مع اختلاف اللغة |
| Semantic | معنى Vector مشابه | Response أوRetrieved context | تتعامل مع Paraphrases | إصابات دلالية خاطئة (False semantic hits) |
| Context/Prompt | Large input prefix/Context متكررة | حساب مدخلات المزوّد/النموذج | تقلل عمل Long-context المتكرر وCost | Stateful provider cache ومخاوف TTL/Privacy |

### أمثلة قرارات

**FAQ endpoint بأسئلة متطابقة ومتكررة**

```text
Keyword cache — Cache بالمفتاح المطابق
```

**RAG app بها Queries كثيرة معاد صياغتها**

```text
Semantic retrieval cache — Cache استرجاع دلالية
```

**Book Q&A مع Context نفسها من 300 صفحة لأسئلة كثيرة**

```text
Prompt/Context cache — Cache للسياق المتكرر
```

### Cache invalidation تظل مركزية

تكون Cache مفيدة فقط ما دام Content الخاص بها صالحًا.

ينبغي لكل Caching design الإجابة عن:

```text
متى يتم إنشاء Cache؟
```

## 11. Model quantization: تقليل Numerical precision

عند Self-hosting لـ Large models، تستهلك Model weights مقدارًا كبيرًا من Memory.

تقلل Quantization الـ Numerical precision المستخدمة لتمثيل Model parameters وأحيانًا Activations.

من الناحية المفاهيمية:

```text
Weights بدقة أعلى
       ↓
Quantization/Calibration
       ↓
تمثيل بدقة أقل
       ↓
Memory footprint أصغر
```

### لماذا تساعد Lower precision؟

إذا استخدمت Parameter واحدة Bits أقل:

```text
Storage أقل لكل Parameter
→ استخدام RAM/VRAM أقل
```

وقد تحسن Lower-precision arithmetic بعض Operations أيضًا وتمكّن Deployment على Hardware أكثر تقييدًا.

### مثال لفهم Memory

تستخدم 32-bit float:

```text
32 bits = 4 bytes — أربعة Bytes
```

لذلك تقريبًا:

```text
1 مليار معامل FP32
→ نحو 4 GB للأوزان الخام فقط
```

يتطلب Training Memory أكبر بكثير لأنه قد يحتفظ أيضًا بـ:

- Gradients،
- Optimizer states،
- Activations،
- Temporary buffers.

لذلك يكون Inference أقل استهلاكًا للـ Memory بكثير من Training.

[[IMAGE_NEEDED: Model quantization pipeline | Flow showing FP32/high-precision model weights → calibration/scaling/quantization → lower-precision INT8/INT4 model → inference, with memory footprint decreasing along the path | Learner should notice that quantization changes numeric representation rather than deleting model layers]]

## 12. Precision مقابل Memory وQuality

يقارن الفصل بين عدة Numerical formats.

### صيغة FP32

Precision عالية.

Memory requirement كبيرة.

### صيغة FP16

تستخدم نصف عدد Bits مقارنة بـ FP32.

يمكن أن تقلل Memory بدرجة كبيرة مع الحفاظ غالبًا على Quality مفيدة.

### صيغة BF16

تستخدم 16 bits لكنها تحافظ على Exponent range واسعة.

يقدمها المصدر بوصفها Balance أخرى بين Memory وNumerical behavior.

### صيغة INT8

تمثيل Integer بـ Eight bits.

توفر Memory كبيرة.

تعتمد نتيجة Quality/Performance على Model وQuantization method.

### صيغة INT4

تمثيل بـ Four bits.

تخفيض أكبر للـ Memory.

مفيدة عندما تكون Aggressive compression مطلوبة.

### دقة منخفضة جدًا (Very low precision)

يستمر Research على Models بأقل من ذلك من Bits.

كلما انخفضت Precision، وجب تقييم Quality وHardware performance بعناية أكبر.

### الـ Trade-off تُقاس تجريبيًا

لا تفترض:

```text
Bits أقل = Speed أعلى دائمًا
```

يذكر المصدر أن Quantization يمكن أن توفر Memory ومع ذلك تقلل Inference speed أحيانًا حسب Implementation/Hardware.

التقييم الصحيح هو:

```text
memory
latency
throughput
الجودة
توافق العتاد
```

## 13. لماذا تغير Lower precision استخدام Memory؟

يشرح المصدر بإيجاز Floating-point representation.

تتضمن Floating-point value:

- Sign،
- Exponent،
- Mantissa/Fraction.

من الناحية المفاهيمية:

```text
Sign
→ موجب/سالب

Exponent
→ Scale/Range

Mantissa
→ Precision
```

يؤدي الانتقال من Format إلى أخرى إلى تقليل أوإعادة توزيع Bits المتاحة.

وهذا يغير:

- Representable range،
- Precision،
- Memory footprint.

لا تحتاج إلى حفظ كل Bit layout في هذا المقرر.

System insight المهم هو:

> **Model parameters هي Numbers. تغيير عدد Bits المستخدمة لتمثيل هذه Numbers يغير مقدار Memory التي تحتاجها Model وقد يؤثر في Numerical accuracy.**

## 16. Prompt engineering بوصفها Discipline للتحسين

Prompt engineering هي ممارسة تحسين Model instructions للحصول على Outputs أكثر فائدة.

يشدد الفصل على تشبيه بالتواصل.

تعامل مع Model كما لو كانت:

```text
زميلًا لديه معرفة واسعة
+
لكن معرفته محدودة بـ Local context الدقيقة الخاصة بك
```

يجب أن تشرح:

- ما Role التي ينبغي أن تلعبها،
- ما المعلومات المهمة،
- ما Task التي ينبغي تنفيذها،
- ما Output المتوقع.

طلب غامض:

```text
"Analyze this." — حلّل هذا.
```

طلب محدد:

```text
"Act as a document classifier. Using the policy below, assign exactly one category and return the result in the required schema." — تصرّف كـ Document classifier. باستخدام Policy أدناه، حدّد Category واحدة بالضبط وأعد Result وفق Schema المطلوبة.
```

الثاني يمنح Model Target أوضح.

### يمكن اختبار Prompting

يقترح المصدر التعامل مع Prompt refinement بطريقة أقرب إلى Software engineering.

من الناحية المفاهيمية:

```text
إصدار الـ prompt 1
→ تقييم

إصدار الـ prompt 2
→ تقييم

إصدار الـ prompt 3
→ تقييم
```

استخدم Representative test cases بدل اختيار Prompts اعتمادًا على Intuition فقط.

## 17. Role وContext وTask (RCT)

يوصي الفصل ببنية Systematic للـ Prompt.

### الدور (Role)

كيف ينبغي أن تتصرف Model؟

مثال:

```text

```

تغيّر Role الـ Perspective والسلوك المتوقعين.

مثال:

```text

أعد ثلاث Violations وتوصية واحدة.
```

### القالب (Template)

```text
Role:
أنت ...

Context:
...

Task:
...
```

## 18. In-context learning: Zero-shot وFew-shot

إحدى الخصائص القوية لـ Foundation models هي تكييف السلوك انطلاقًا من Examples موضوعة داخل Prompt.

### Zero-shot

لا توجد Examples.

```text
صنّف هذا Document على أنه A أوB أوC.
```

استخدمه عندما تكون Task مفهومة جيدًا بالفعل.

### Few-shot

قدّم عدة Demonstrations.

```text
Input A → Category 1
Input B → Category 2
Input C → Category 1

الآن صنّف:
Input D
```

مفيد عندما:

- Labels دقيقة أوNuanced،
- Output format مهمة،
- Examples توضح Intent أفضل من Prose.

### Few-shot ديناميكي (Dynamic)

يتم Retrieve للـ Examples وقت التشغيل.

Pipeline:

```text
Input جديدة
    ↓
ابحث في Example store/Vector DB
    ↓
اختر Examples ذات صلة
    ↓
أدرجها في Prompt
    ↓
Model
```

يمكن أن يخصص أو يكيّف Examples لكل Query.

### In-context learning مقابل Fine-tuning

In-context learning:

```text
يغير Prompt/Context
ولا يعدّل Model weights
```

Fine-tuning:

```text
تغير Model parameters
```

سيصبح هذا التمييز مهمًا لاحقًا.

## 19. Prompts لتوليد التفكير وتفكيك المهام (Thought-generation and decomposition prompts)

يجمع المصدر عدة Advanced prompting techniques حول Reasoning وتفكيك Tasks.

### عائلة Thought-generation

يناقش الفصل Approaches مثل:

- Zero-shot chain-of-thought،
- Few-shot chain-of-thought،
- Thread-of-thought.

الهدف العام هو تشجيع التعامل مع Problem صعبة عبر Intermediate reasoning stages بدل القفز مباشرةً إلى Final answer واحدة.

### عائلة Decomposition

قسّم Task صعبة إلى Tasks أصغر.

يقدم المصدر:

#### أسلوب Least-to-most

```text
قسّم Problem إلى Subproblems أصغر
→ حل الأجزاء الأبسط
→ ابنِ الحل وصولًا إلى Problem النهائية
```

#### أسلوب Plan-and-solve

```text
أنشئ Plan
→ نفّذ Plan
```

#### أسلوب Tree of thoughts

```text
أنشئ عدة Branches محتملة
→ قيّم Branches
→ واصل Branches الواعدة
```

### متى تساعد Decomposition؟

- Software design،
- Complex analysis،
- Multi-step planning،
- Problems لها عدة Paths معقولة.

### المفاضلة

يمكن للخطوات الإضافية زيادة:

- Model calls،
- Tokens،
- Latency،
- Implementation complexity.

استخدمها عندما يبرر تحسن Quality العمل الإضافي.

## 20. Ensembling: استخدم عدة Candidate outputs

ينتج Ensembling عدة Outputs ثم يدمجها.

الهدف هو تقليل Response variance وتحسين Reliability.

### الاتساق الذاتي (Self-consistency)

أنشئ عدة Candidate reasoning paths/answers.

ثم اختر Result الأكثر اتساقًا أوشيوعًا.

### مزيج خبراء الاستدلال (Mixture of reasoning experts — MoRE)

استخدم Specialized prompts/models كمراجعين أوExperts مختلفين.

مثال:

```text
Expert A → مراجعة Factual
Expert B → مراجعة Logical
Expert C → مراجعة Domain
      ↓
اجمع Results
```

### Demonstration ensembling

استخدم Few-shot example sets مختلفة ثم اجمع Results.

### Prompt paraphrasing

اطرح أسئلة متكافئة بعدة Formulations.

ثم قارن/ادمج Outputs.

### مفاضلة Cost

ينفذ Ensembling عمدًا المزيد من Generation.

لذلك:

```text
Potential quality gain
↔
Token/API cost أعلى
+
Latency أعلى
```

استخدمه فقط عندما تكون Reliability مهمة بما يكفي لتبرير Multiple calls.

## 21. Self-criticism وVerification prompts

يقدم الفصل عدة Prompting strategies تقوم فيها Model بتقييم أوتحسين Candidate output.

### Self-calibration

اطلب تقييمًا لمدى صحة/Confidence الـ Response.

### Self-refine

النمط:

```text
أنشئ Draft
→ انتقد Draft
→ حسّن Draft
```

### عكس Chain-of-Thought

أعد بناء Problem الأصلية انطلاقًا من Generated answer وقارن بحثًا عن Inconsistencies.

### Self-verification

أنشئ Candidate solutions، ثم قيّمها مقابل نسخ Modified/Partial من Problem.

### Chain of verification

النمط:

```text
الإجابة
→ توليد أسئلة تحقق
→ الإجابة عن أسئلة التحقق
→ مراجعة/اختيار الإجابة النهائية
```

### Cumulative reasoning

أنشئ Steps، وقيّم ما إذا كانت كل Step مفيدة، وواصل حتى الوصول إلى Answer مرضية.

### درس Engineering

تحوّل هذه Methods Model call واحدة إلى Workflow.

وهذا يعني أن عليك قياس:

- Quality gain،
- Latency،
- Token usage،
- Failure modes.

لا تفترض أن إضافة "Judge" call تحسن Truthfulness دائمًا.

## 22. Agentic prompting وTools

تتجاوز Agentic systems مجرد إنتاج Text.

فهي تجمع Language models مع External tools.

```text
يختار LLM Action
   ↓
Tool call
   ↓
Observation

يواصل LLM
   ↓
```

### نمط CRITIC

- Authorization،
- Input validation،

## 23. Fine-tuning: تغيير Model parameters

يغير Prompting الـ Model inputs.

أما Fine-tuning فتغير Model weights/parameters باستخدام Training examples.

يشدد المصدر على:

> **ينبغي ألا تكون Fine-tuning عادةً أول Optimization تجربها.**

لماذا؟

لأنها تتطلب:

- Dataset collection،
- Data preparation،
- Training jobs،
- Evaluation،
- إدارة النماذج/الإصدارات المستمرة.

تمتلك Prompt changes Feedback loop أسرع بكثير.

### حالات قد تساعد فيها Fine-tuning

يسرد الفصل أمثلة مثل:

- Specialized domain behavior،
- Tone أوBrand style متسقة،
- Output format شديدة الاتساق،
- Nuanced classification،
- التعامل مع Edge cases،
- Skills يصعب تحديدها بوضوح عبر Prompts،
- تقليل Large repeated prompt/example overhead،
- تحسين أداء Lower-cost model لـ Task محددة،
- تعليم Patterns لاستخدام Tool/API.

### Fine-tuning والمعرفة

يذكر المصدر Private-domain learning ضمن Motivations المحتملة.

في Practical system design، مع ذلك ميّز بين:

```text
Behavior/Style adaptation
و
Fresh retrievable knowledge
```

ويظل مبدأ Decision المركزي في الفصل:

```text
جرّب Prompt/Architecture optimizations أولًا
ثم برر Fine-tuning إذا بقيت الحاجة
```

## 25. اختر Optimization التي تطابق Bottleneck

لا تبدأ بالسؤال:

```text
أي Optimization technique هي الأكثر إثارة؟
```

ابدأ بـ:

```text
أي Metric تفشل؟
```

### إذا كانت Cost عالية بسبب تكرار Requests

جرّب:

- Keyword caching،
- Semantic caching،
- Context caching.

### إذا كانت Offline workload ضخمة

جرّب:

- Batch schemas،
- APIs الدفعات لدى المزوّد.

### إذا كانت Self-hosted model لا تتسع براحة

قيّم:

- Smaller model،
- Quantized model،
- External serving.

### إذا فشل Downstream parsing

استخدم:

- Structured outputs،
- Validation schemas.

### إذا أساءت Model فهم Task

جرّب:

1. Role/Context/Task أوضح،
2. تجارب Zero-shot/Few-shot،
3. Decomposition،
4. Verification/Ensembling فقط عندما يكون ذلك مبررًا.

### إذا وصلت Prompt engineering إلى سقف

عندها قيّم ما إذا كانت Fine-tuning مبررة.

```text
المشكلة؟

  ├── Offline workload كبيرة

  ├── Structured output غير صالحة
  │      └── Structured output schema
  │
  ├── Task alignment ضعيف
  │      └── Prompt engineering
  │
  └── Specialized behavior gap مستمرة
         └── قيّم Fine-tuning
```

### قِس قبل وبعد

بالنسبة إلى كل Optimization، سجّل Metrics ذات الصلة.

Performance metrics محتملة:

- p50/p95 latency،
- Time to first token،
- Throughput،
- Cache hit rate،
- Provider requests،
- Tokens/request،
- GPU memory،
- Cost/request.

Quality metrics محتملة:

- Task accuracy،
- Schema-validity rate،
- Groundedness،
- Human evaluation،
- درجات خاصة بالمجال.

تنجح Optimization فقط إذا تحسنت Metric المستهدفة دون Regression غير مقبولة في مكان آخر.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Optimization تعني دائمًا جعل Model أسرع.

### لماذا هذا خاطئ؟

يحسن الفصل أيضًا Cost وThroughput وMemory usage وResponse structure وAlignment وOutput quality.

### المفهوم الخاطئ 2

> Batching مثالية لـ Interactive chat.

### لماذا هذا خاطئ؟

تكون Batch jobs مفيدة بصورة خاصة لـ Asynchronous/Offline workloads حيث لا تكون Immediate response مطلوبة.

### المفهوم الخاطئ 3

> Cache hit صحيحة دائمًا.

### لماذا هذا خاطئ؟

قد تصبح Cached information قديمة، ويمكن لـ Semantic caches مطابقة Queries متشابهة لكنها تتطلب Outputs مختلفة.

### المفهوم الخاطئ 4

> Semantic caching تتطلب Exact text matches.

### لماذا هذا خاطئ؟

تستخدم Embeddings/Similarity بحيث يمكن لـ Queries مختلفة في الصياغة Mapping إلى Cached item نفسها.

### المفهوم الخاطئ 5

> Prompt caching تخزن Generated answer وتعيد استخدامها.

### لماذا هذا خاطئ؟

تعيد Prompt/Context caching استخدام Repeated input/context computation. وقد تختلف Model output مع ذلك.

### المفهوم الخاطئ 6

> ينبغي أن تعيش Cache entries إلى الأبد بعد حسابها.

### لماذا هذا خاطئ؟

تحتاج Caches إلى TTL/Invalidation وFinite-capacity eviction policies.

### المفهوم الخاطئ 7

> Semantic threshold أكثر تساهلًا تحسن Cache دائمًا.

### لماذا هذا خاطئ؟

قد ترفع Hit rate لكنها قد تزيد Incorrect semantic matches.

### المفهوم الخاطئ 8

> Quantization تحذف ببساطة Model layers غير المهمة.

### لماذا هذا خاطئ؟

تغيّر Quantization طريقة تمثيل Numerical parameters، عادةً باستخدام Bits أقل.

### المفهوم الخاطئ 9

> Lower precision تضمن دائمًا Inference أسرع.

### لماذا هذا خاطئ؟

Memory savings شائعة، لكن Speed الفعلية تعتمد على Hardware وKernels وQuantization method وServing stack.

### المفهوم الخاطئ 10

> إذا كانت Quantized model تتسع في Memory فلا حاجة إلى Evaluation.

### لماذا هذا خاطئ؟

يمكن للضغط أن يؤثر في Task quality وPerformance.

### المفهوم الخاطئ 11

> طلب "return JSON" من LLM يضمن Structured output صالحة.

### لماذا هذا خاطئ؟

يمكن لـ Free-form generation مخالفة Syntax أوSchema المطلوبة.

### المفهوم الخاطئ 12

> Prompt طويلة جدًا هي تلقائيًا Prompt جيدة.

### لماذا هذا خاطئ؟

تأتي Prompt quality من Relevant context وExplicit instructions وUseful examples — وليس Length وحدها.

### المفهوم الخاطئ 13

> Few-shot prompting تعدّل Model weights.

### لماذا هذا خاطئ؟

تعيش Examples داخل Input context. وتظل Underlying model parameters دون تغيير.

### المفهوم الخاطئ 14

> Calls الإضافية للـ Reasoning/Ensemble هي تحسينات Quality مجانية.

### لماذا هذا خاطئ؟

تستهلك Tokens ووقتًا ومالًا إضافيًا، وقد تستمر في إنتاج Errors.

### المفهوم الخاطئ 15

> إعطاء LLM Tools يعني أنه ينبغي الثقة بها لتنفيذ أي شيء تقترحه.

### لماذا هذا خاطئ؟

يجب على Application logic عمل Validate وAuthorize لـ Tool calls قبل التنفيذ.

### المفهوم الخاطئ 16

> ينبغي أن تكون Fine-tuning أول استجابة لـ Model output متوسطة الجودة.

### لماذا هذا خاطئ؟

تمتلك Prompt refinement وArchitecture changes Feedback loops أسرع، وغالبًا تحل المشكلة بتكلفة أقل.

### المفهوم الخاطئ 17

> بمجرد Fine-tuning لـ Model، ستستفيد تلقائيًا من كل Improvement جديدة في Base model.

### لماذا هذا خاطئ؟

قد ترتبط Fine-tuned versions بـ Base models أقدم وتحتاج إلى Retraining/Migration.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التحسين (Optimization) | تغيير مقصود لتحسين Performance أوQuality المقاسة |
| المعالجة على دفعات (Batch processing) | معالجة عناصر كثيرة معًا بدل Interactive request منفردة لكل عنصر |
| Batch API | Provider service تضع مجموعات Requests في Queue وتعالجها Asynchronously |
| JSONL | صيغة JSON Lines تحتوي Object من JSON في كل Line |
| Cache | Store لبيانات/Results سبق حسابها ويمكن إعادة استخدامها |
| Cache hit | العثور على Item المطلوبة وإعادة استخدامها |
| Cache miss | عدم توفر Item المطلوبة والحاجة إلى إعادة حسابها |
| إبطال Cache (Cache invalidation) | إزالة/إنهاء صلاحية Data التي لم يعد ينبغي إعادة استخدامها |
| Keyword cache | Cache تعتمد على Exact input/key |
| Semantic cache | Cache lookup تعتمد على Embedding similarity |
| Similarity threshold | Boundary لتقرير ما إذا كانت Semantic cache lookup قريبة بما يكفي |
| Eviction policy | Rule تحدد أي Cache item تتم إزالتها عند بلوغ Capacity |
| FIFO | إخراج (eviction) الداخل أولًا يخرج أولًا |
| LRU | إخراج (eviction) الأقل استخدامًا مؤخرًا |
| LFU | إخراج (eviction) الأقل استخدامًا تكرارًا |
| MRU | إخراج (eviction) الأكثر استخدامًا مؤخرًا |
| cache الـ Prompt/Context | Cache لـ Large input context/Model computation قابلة لإعادة الاستخدام |
| TTL | Time to live قبل انتهاء Cached data |
| Quantization | تقليل Numerical precision للـ Model parameters/activations |
| FP32 | صيغة فاصلة عائمة 32 بت |
| FP16 | صيغة فاصلة عائمة 16 بت |
| BF16 | صيغة brain floating-point 16 بت |
| INT8 | تمثيل عدد صحيح 8 بت |
| INT4 | تمثيل عدد صحيح 4 بت |
| المعايرة (Calibration) | استخدام Representative data لتوجيه Quantization mapping |
| GPTQ | Post-training quantization approach يقدمها الفصل |
| Structured output | Model response مقيدة بـ Declared schema/format |
| Prompt engineering | تصميم وتحسين Model instructions بصورة منهجية |
| RCT | بنية Prompt من Role وContext وTask |
| Zero-shot | Task instruction بلا Examples |
| Few-shot | Task instruction مع مجموعة صغيرة من Examples |
| Few-shot ديناميكي | Retrieval/Injection للـ Relevant examples وقت التشغيل |
| In-context learning | تكييف السلوك باستخدام معلومات/Examples داخل Prompt |
| Decomposition | تقسيم Complex problem إلى Tasks أصغر |
| Ensembling | دمج عدة Model outputs |
| Self-consistency | توليد عدة Candidates واختيار Result متسقة |
| Self-refine | نقد Response وتحسينها Iteratively |
| Agentic system | LLM workflow تستطيع التخطيط واستخدام External tools/actions |
| Function calling | Mechanism منظمة لطلب LLM Application-defined tool |
| Fine-tuning | تحديث Model parameters باستخدام Task/Domain training examples |

## احتفظ بهذه الفكرة

**حسّن Bottleneck التي لديك فعلًا: اجمع في Batch العمل الذي لا يحتاج Answers فورية، واستخدم Cache للعمل المتكرر في Layer المناسبة، ونفّذ Quantization للـ Self-hosted models عندما تكون Memory هي القيد، واستخدم Schemas وSystematic prompting عندما تكون Output quality أوStructure ضعيفة، واحتفظ بـ Fine-tuning للفجوات السلوكية المستمرة التي لا تستطيع Techniques الأقل تكلفة والأسرع حلها. يجب قياس كل Optimization مقابل Latency وThroughput وCost وMemory وQuality — لا أن تُتبنى لمجرد أنها متاحة.**
