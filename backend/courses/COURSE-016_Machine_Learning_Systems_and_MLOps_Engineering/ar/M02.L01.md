## 1. ابدأ بالهدف، لا بالـ Model

من الأخطاء الشائعة في Machine Learning أن تبدأ بالسؤال:

> أي Model ينبغي أن ندرّب؟

يأتي هذا السؤال مبكرًا جدًا. قبل اختيار Model، ينبغي أن تفهم **لماذا يحتاج System إلى الوجود أصلًا**.

عادةً يكون مشروع ML في Production جزءًا من Organization أكبر. وتهتم تلك Organization بنتائج مثل Revenue و Cost و Retention و Customer satisfaction و Safety و Operational efficiency أو أي Goal أخرى قابلة للقياس. ولا يكون ML system مفيدًا إلا إذا ساهم في واحدة أو أكثر من هذه Outcomes.

ينشئ ذلك Chain مهمة:

```text
الهدف التجاري (Business objective)
      ↓
هدف Product أو Operations
      ↓
هدف ML
      ↓
Model metric / System metric — مقياس Model و System
```

على سبيل المثال، لنفترض أن شركة Ecommerce تريد زيادة نسبة Visits التي تنتهي بعملية Purchase.

- **Business objective:** زيادة Purchase-through rate.
- **Product idea:** التوصية بمنتجات أكثر صلة بالـ User الحالي.
- **ML objective:** ترتيب Products بحيث تظهر Items التي يُرجح أن يشتريها User قرب أعلى القائمة.
- **Possible ML metrics:** Ranking quality و Precision و Recall أو Predictive measure أخرى.

لا يكون تحسين ML metric مهمًا إلا إذا ساعد ذلك التحسين Business outcome. انتقال Accuracy الخاصة بـ Model من 94.0% إلى 94.2% لا يجعلها أكثر قيمة تلقائيًا إذا لم يتحسن Customer behavior أو Revenue أو Cost.

### الارتباط وحده لا يكفي (Correlation is not enough)

قد تكون العلاقة بين Model metrics و Business metrics غير مباشرة بصورة مفاجئة. قد يحسن Recommender أكثر دقة Customer satisfaction، لكنه قد يساعد Users أيضًا على العثور على ما يحتاجونه أسرع، وبالتالي يقضون وقتًا أقل داخل Service.

لهذا السبب تحتاج Teams غالبًا إلى Controlled experiments مثل A/B tests لقياس ما إذا كانت Model الجديدة تحسن فعلًا Business outcome المطلوبة.

[[IMAGE_NEEDED: From business objective to ML metric | A layered diagram showing a business goal at the top, followed by a product goal, an ML objective, and finally model/system metrics | Learner should notice that model metrics are proxies for a higher-level goal, not the final goal themselves]]

### مثال: اكتشاف Fraud

تُعد Fraud detection مناسبة لـ ML لأن العلاقة بين Technical performance و Business value قد تكون مباشرة نسبيًا. إذا منع System معاملات Fraudulent بصورة صحيحة، يمكن للشركة توفير المال. ومع ذلك، تظل False positives مهمة لأن منع Customers شرعيين قد ينشئ Business cost أيضًا.

## 2. أربعة متطلبات أساسية لنظام ML

بعد أن يصبح Objective واضحًا، لا يكون السؤال التالي ببساطة: "أي Algorithm هي الأفضل؟" بل يجب على Production system تلبية Engineering requirements أيضًا.

هناك أربعة متطلبات عامة مفيدة بصورة خاصة:

| المتطلب | السؤال الأساسي |
|---|---|
| الموثوقية (Reliability) | هل يواصل System أداء المهمة الصحيحة رغم Faults و Uncertainty؟ |
| قابلية التوسع (Scalability) | هل يستطيع التعامل مع نمو Traffic أو Models أو Data أو Complexity؟ |
| قابلية الصيانة (Maintainability) | هل يستطيع الأشخاص فهمه وإعادة إنتاجه وتعديله وتشغيله بمرور الوقت؟ |
| قابلية التكيف (Adaptability) | هل يستطيع الاستجابة لتغير Data وتغير Business needs؟ |

### الموثوقية (Reliability)

يواصل System الموثوق أداء Function المقصودة بمستوى مقبول حتى عند حدوث مشكلات: Hardware failures و Software bugs و Bad inputs و Human mistakes أو Unexpected conditions.

تجعل ML الـ Reliability أصعب لأن Failure قد تكون **صامتة**. قد يعيد Web server خطأ 500 مرئيًا، لكن ML model قد تستمر في إعادة Predictions تبدو Valid بينما أصبحت Quality ضعيفة. وإذا لم يعرف Users Correct answer، فقد لا يلاحظون المشكلة أبدًا.

وهذا يعني أن Reliability في ML تتضمن أكثر من Uptime. فهي تشمل Monitoring لـ Prediction quality و Data quality و System behavior.

### قابلية التوسع (Scalability)

قد يحتاج ML system إلى التوسع عبر عدة Dimensions مختلفة:

- **Traffic:** قد تتحول 10,000 Prediction يوميًا إلى 10 ملايين.
- **Model complexity:** قد تُستبدل Model صغيرة بأخرى أكبر كثيرًا لها احتياجات Memory و Compute أعلى.
- **Model count:** قد تتحول Model واحدة إلى مئات أو آلاف Models خاصة بـ Customers أو Tasks.
- **Data:** قد تنمو Datasets الخاصة بـ Training و Features و Monitoring بسرعة.

إذًا Scalability تعني أكثر من إضافة Servers. فالنظام الذي يحتوي مئات Models يحتاج أيضًا إلى Automated tracking و Monitoring و Retraining و Versioning و Reproducibility.

### قابلية الصيانة (Maintainability)

عادةً ما تبني ML systems عدة مجموعات: ML engineers و Software engineers و Platform/DevOps engineers و Data engineers و Product teams و Subject-matter experts.

تتحسن Maintainability عندما:

- تكون Code موثقة،
- تكون Code و Data و Model artifacts خاضعة للـ Versioning،
- يمكن إعادة إنتاج Experiments،
- تكون Interfaces بين Components واضحة،
- يستطيع Contributors تشخيص المشكلات معًا،
- لا تختفي Knowledge عندما يغادر شخص Team.

### قابلية التكيف (Adaptability)

يتغير العالم الحقيقي. يتغير User behavior وتتغير Markets وتتغير Input distributions وقد تغير Business أهدافها.

يُصمم ML system القابل للتكيف بحيث يستطيع اكتشاف تدهور Performance ويمكن تحديثه دون الحاجة إلى إعادة بناء Service كاملة من الصفر.

## 3. تطوير ML system دورة تكرارية

غالبًا ما يتخيل المبتدئ Workflow بهذه الصورة:

```text
اجمع Data → درّب Model → انشرها → انتهى
```

نادرًا ما تعمل Real ML systems بهذه الطريقة.

Lifecycle أكثر واقعية هي:

```text
1. تحديد نطاق Project
2. هندسة البيانات (Data engineering)
3. تطوير Model (Model development)
4. النشر (Deployment)
5. Monitoring و Continual learning
6. تحليل Business (Business analysis)
             ↓
        العودة إلى Scoping
```

### لماذا تتكرر الدورة؟

تخيل بناء System يقرر ما إذا كان سيعرض Ad لـ Search query.

قد تبدأ بتحسين عدد مرات عرض Ad. ثم تكتشف أثناء Error analysis أن بعض Labels خاطئة. فتُعيد Labeling للـ Data وتُعيد Training.

بعد ذلك تكتشف أن معظم Examples تقريبًا Negative، فتتعلم Model أن تتنبأ بـ "do not show" في معظم الوقت. تحتاج إلى Data أفضل ثم تعيد Training مرة أخرى.

لاحقًا، تعمل Model جيدًا على Test set قديمة لكنها تعمل بصورة سيئة على Traffic الأمس. لقد تغير Data distribution، وبالتالي أصبحت Model قديمة.

وأخيرًا، قد تعمل Model جيدًا تقنيًا بينما ينخفض Revenue. عندها تغير Business الـ Optimization target من Impressions إلى Click-through rate.

الدرس مهم:

> **Model development جزء داخل Feedback loop أكبر.**

## 4. حوّل Real-world problem إلى ML problem

Business problem ليست تلقائيًا ML problem.

لنفترض أن Bank تقول:

> "استخدم تعلّم الآلة لجعل دعم العملاء أسرع."

لا تخبرنا هذه Request بعد بما ينبغي للـ Model استقباله أو Predict له أو Optimize له.

بعد Investigation، لنفترض أن Bottleneck الحقيقية هي Routing لطلبات Support إلى Department الصحيحة: Accounting أو Inventory أو HR أو IT.

الآن يمكننا صياغة ML problem:

- **Input:** Text الخاصة بـ Customer request.
- **Output:** واحدة من أربع Departments.
- **المهمة (Task):** Multiclass classification.
- **Objective:** جعل Predicted department تطابق Correct department بأكبر قدر ممكن.

صياغة عامة مفيدة هي:

```text
ML problem = Inputs + Outputs + Learning objective — صياغة مشكلة ML
```

إذا كان أي من هذه غير واضح، فإن ML problem نفسها لا تزال غير واضحة.

### لماذا تهم الصياغة؟

قد تبدأ Teamان من Business problem نفسها وتبنيان ML systems مختلفتين جدًا فقط لأنهما صاغتا Problem بصورة مختلفة. يمكن للصياغة الجيدة أن تجعل System أسهل في Training وأسهل في Update وأكثر Scalability.

## 5. Classification و Regression وبنية Labels

نوع Output التي تريدها يؤثر بقوة في نوع ML task.

### Classification مقابل Regression

تتنبأ **Classification** بفئة.

أمثلة:

- Spam / Not spam،
- Fraud / Legitimate،
- أقسام Accounting / Inventory / HR / IT.

تتنبأ **Regression** بقيمة عددية Continuous.

أمثلة:

- House price،
- Expected demand،
- Probability أن ينقر User على Item.

يمكن أحيانًا صياغة Problem نفسها بأي من الطريقتين. House-price prediction هي Regression طبيعيًا، لكن يمكنك بدلًا من ذلك إنشاء Price buckets والتنبؤ بالـ Bucket. وبالمثل، يمكن لـ Spam classifier إنتاج Continuous score بين 0 و1 ثم تطبيق Threshold.

### التصنيف الثنائي (Binary classification)

هناك فئتان Possible فقط.

تشمل الأمثلة Fraud/Not fraud أو Toxic/Not toxic.

### التصنيف متعدد الفئات (Multiclass classification)

هناك أكثر من فئتين، لكن كل Example تنتمي إلى فئة واحدة فقط.

على سبيل المثال، قد تذهب Ticket إلى Department واحدة فقط.

### التصنيف عالي عدد الفئات (High-cardinality classification)

عندما يصبح عدد Classes كبيرًا جدًا، تصبح Task أصعب بكثير. قد تنشئ آلاف Product categories أو Disease classes ندرة Data للـ Rare classes.

إحدى الاستراتيجيات المفيدة هي **Hierarchical classification**:

```text
Product — المنتج
  ↓
Fashion — الأزياء
  ↓
Shoes / Shirts / Jeans / Accessories — أحذية وقمصان وجينز وإكسسوارات
```

تختار Classifier الأولى Group عامة، ثم تختار Classifier أخرى Subgroup.

### التصنيف متعدد Labels (Multilabel classification)

يمكن لـ Example الانتماء إلى عدة Classes في الوقت نفسه.

على سبيل المثال، قد تكون Article ضمن **Technology** و **Finance** معًا.

يمكن تمثيل Multilabel target هكذا:

```text
[tech, entertainment, finance, politics] — Labels مرتبة
[  1 ,      0       ,    1   ,    0    ] — تمثيل Multilabel
```

تضيف Multilabel systems تحديات إضافية لأن System يجب أن تحدد ليس فقط *أي* Labels محتملة، بل أيضًا *كم* Label ينبغي إخراجها.

## 6. يمكن صياغة المشكلة نفسها بعدة طرق

لنفترض أنك تريد Predict لأي App سيفتحها Phone user بعد ذلك.

### الصياغة A: Multiclass classification

Input:

- User features،
- Context مثل Time و Environment.

Output:

- Probability واحدة لكل App ممكنة.

إذا كان هناك `N` Apps، فإن Output حجمها `N`.

نقطة الضعف هي أن Model architecture قد تعتمد على عدد Apps. لذلك قد يتطلب إضافة App جديدة تغييرات في Model أو Retraining.

### الصياغة B: إعطاء Score لكل App

بدلًا من ذلك، اجعل Candidate app جزءًا من Input:

```text
Input = User features + Context + App features — Input الخاصة بالـ Model
Output = Likelihood of opening this app — Output هي احتمالية فتح App
```

الآن تعيد Model Score واحدة لـ Candidate app واحدة. ولمقارنة `N` Apps، شغّل Model `N` مرات أو قيّم Candidates داخل Batch.

لهذه الصياغة ميزة Systems مهمة: يمكن تقييم App جديدة من خلال Features الخاصة بها دون إعادة تصميم Output layer يعتمد حجمها على عدد Apps.

### الدرس العام (General lesson)

> **Problem framing قرار هندسي، وليس مجرد Label رياضية.**

تؤثر Framing في Data requirements و Model architecture و Evaluation و Serving cost و Scalability ومدى سهولة Evolution للنظام.

## 7. Objective functions تخبر Model بما ينبغي تحسينه

بعد صياغة Task، تحتاج Learning algorithm إلى Mathematical signal يخبرها بمدى خطأ Predictions.

هذا هو دور **Objective function**، والتي تُسمى غالبًا **Loss function**.

في Supervised learning، تقارن Loss عادة Prediction الخاصة بـ Model مع Ground-truth target.

تشمل الأمثلة الشائعة:

| المهمة | Loss شائعة |
|---|---|
| الانحدار (Regression) | Mean squared error (MSE/RMSE) أو Mean absolute error (MAE) |
| التصنيف الثنائي (Binary classification) | Loss من نوع Logistic / Log loss |
| التصنيف متعدد الفئات (Multiclass classification) | Loss من نوع Cross-entropy |

### مثال Cross-entropy

لنفترض أن ترتيب Classes هو:

```text
[tech, entertainment, finance, politics] — Labels مرتبة
```

الفئة الصحيحة هي Politics:

```text
p = [0, 0, 0, 1]
```

وتتنبأ Model:

```text
q = [0.45, 0.20, 0.02, 0.33]
```

أعطت Model Probability مقدارها 0.33 فقط للفئة الصحيحة، لذلك تنتج Cross-entropy قيمة Loss تعاقب هذا Mismatch.

لأن Position الخاصة بـ Politics فقط لها Target value تساوي 1، فإن Result فعليًا هي `-log(0.33)`. Prediction أفضل تضع Probability أعلى على Class الصحيحة ستنتج Loss أصغر.

### لا تخلط بين ثلاث أفكار مختلفة

1. **Business objective:** ما الذي تريده Organization.
2. **ML objective:** ما Predictive behavior التي ينبغي لـ ML system إنتاجها.
3. **Objective/Loss function:** Mathematical function التي يجري Optimize لها أثناء Training.

هي مترابطة، لكنها ليست الشيء نفسه.

## 8. أهداف متعددة ولماذا يساعد فصلها

غالبًا ما تحسن Real systems عدة Goals في الوقت نفسه.

تخيل Ranking لمنشورات Newsfeed. قد ترغب في:

- Filter للـ Spam،
- Filter للمحتوى Unsafe،
- تقليل Misinformation،
- Ranking حسب Quality،
- Ranking حسب Expected engagement.

قد تتعارض بعض Objectives. فالمحتوى شديد Engagement ليس دائمًا عالي Quality.

### Approach 1: دمج Losses داخل Model واحدة

يمكنك Optimize:

```text
loss = α × quality_loss + β × engagement_loss — Loss مركبة
```

تحدد `α` و `β` مدى أهمية كل Objective.

المشكلة تشغيلية: تغيير Trade-off قد يتطلب Retraining للـ Model.

### Approach 2: فصل Objectives

درّب Models منفصلة:

```text
quality_model    → quality_score
engagement_model → engagement_score
```

ثم ادمج Outputs:

```text
final_score = α × quality_score + β × engagement_score
```

الآن يمكن للـ Team تعديل `α` و `β` دون Retraining للـ Models الأساسية.

ويساعد ذلك أيضًا في Maintenance لأن Objectives المختلفة قد تتغير بسرعات مختلفة. قد يتطور Spam behavior بسرعة، بينما قد تحتاج Quality signal أخرى إلى Updates أقل تكرارًا.

## 9. Data جزء أساسي من System design

اعتمد تقدم Modern ML بدرجة كبيرة على Data. وفي كثير من Organizations العملية، قد يكون تحسين Data pipeline مهمًا بقدر البحث عن Algorithm أذكى أو أكثر.

يقدم الفصل Debate مستمرة:

- رأي يركز على **Inductive biases و Structure و Algorithmic intelligence أفضل** لكي تتعلم Systems بكفاءة أكبر.
- ورأي آخر يركز على **General methods و Large-scale computation و Large datasets**.

الاستنتاج العملي لمصممي Systems أبسط من Debate الفلسفية:

> **Data أساسية، لكن المزيد من Data ليس تلقائيًا Data أفضل.**

قد تضر Dataset أكبر إذا احتوت على:

- Examples قديمة،
- Labels غير صحيحة،
- Samples غير ذات صلة،
- Observations متحيزة أو غير ممثلة.

إذًا الهدف الحقيقي ليس Maximum quantity ببساطة. تحتاج إلى Data كافية وذات صلة وممثلة وعالية الجودة بما يكفي للمشكلة التي تحاول حلها.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Model metrics الأفضل تعني دائمًا Business results أفضل

> "إذا تحسنت الدقة، يصبح مشروع ML تلقائيًا أكثر قيمة."

هذا خطأ لأن ML metric عادة Proxy. ولا تهم إلا بقدر ما تحسن Outcome الحقيقية التي تهتم بها Organization. وقد تحتاج إلى Experiments لإثبات هذه العلاقة.

### المفهوم الخاطئ 2: Deployment هي الخطوة الأخيرة

> "بمجرد نشر النموذج، ينتهي المشروع."

تقدم Production تغير Traffic و Data متغيرة و Failures و Requirements جديدة و Business feedback. Monitoring و Updating جزء من System lifecycle.

### المفهوم الخاطئ 3: Business request تعرّف ML problem بالفعل

> "استخدم AI لتحسين دعم العملاء" كافٍ لبدء التدريب.

ليست كافية. ما زلت تحتاج إلى تحديد Model inputs و Outputs و Task type و Training target و Objective و Evaluation strategy.

### المفهوم الخاطئ 4: المزيد من Data يساعد دائمًا

قد تجعل Data كثيرة لكن منخفضة الجودة أو قديمة أو Incorrectly labeled أو غير ذات صلة الـ Model أسوأ. يجب التفكير في Quantity و Quality معًا.

| هدف ML (ML objective) | Predictive behavior أو ML goal قابلة للقياس مختارة لدعم Business objective. |
| دالة الهدف (Objective function) | Mathematical function يجري Optimize لها أثناء Model training؛ وتُسمى غالبًا Loss function. |
| الموثوقية (Reliability) | القدرة على مواصلة أداء Function المقصودة بمستوى مقبول رغم Faults أو Uncertainty. |
| قابلية التوسع (Scalability) | القدرة على التعامل مع نمو Traffic أو Data أو Model complexity أو Model count أو Resource demand. |
| قابلية الصيانة (Maintainability) | سهولة فهم System وإعادة إنتاجها وتغييرها و Debugging لها وتشغيلها بمرور الوقت. |
| قابلية التكيف (Adaptability) | قدرة System على الاستجابة لتغير Data distributions و Requirements. |
| التصنيف (Classification) | ML task تتنبأ بـ Categories. |
| الانحدار (Regression) | ML task تتنبأ بقيم عددية Continuous. |
| التصنيف الثنائي (Binary classification) | Classification بفئتين Possible فقط. |
| التصنيف متعدد الفئات (Multiclass classification) | Classification بأكثر من فئتين Mutually exclusive. |
| التصنيف متعدد Labels (Multilabel classification) | Classification يمكن أن تنتمي فيها Example إلى عدة Classes. |
| العدد الكبير من الفئات (High cardinality) | Classification problem بعدد كبير جدًا من Classes الممكنة. |
| التصنيف الهرمي (Hierarchical classification) | Classification على مراحل، من Categories عامة إلى Subcategories أكثر تحديدًا. |
| خسارة Cross entropy | Loss شائعة لـ Multiclass classification تعاقب Probability الموضوعة بعيدًا عن Correct class. |
| أهداف منفصلة (Decoupled objectives) | Models أو Components منفصلة تحسن Goals مختلفة قبل دمج Outputs الخاصة بها. |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. لماذا لا يكفي تحسين Accuracy لإثبات نجاح مشروع ML؟
2. ما الفرق بين Reliability و Scalability؟
3. لماذا قد يفشل ML system رغم أن Service نفسها تعمل تقنيًا؟
4. لماذا يكون ML development تكراريًا عادة بدلًا من Linear؟
5. ما العناصر الثلاثة التي يجب أن تكون واضحة عند صياغة ML problem؟
6. كيف تختلف Multilabel classification عن Multiclass classification؟
7. لماذا قد يكون Scoring لكل Candidate بصورة مستقلة أسهل في Evolution من Predict على Fixed set من Candidates؟
8. ما الفرق بين Business objective و ML objective و Loss function؟
9. لماذا يمكن أن يسهل Decoupling للـ Multiple objectives عملية Maintenance؟
10. لماذا قد تؤدي إضافة المزيد من Training data أحيانًا إلى خفض Model quality؟
