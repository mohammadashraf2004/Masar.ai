## 1. ما الذي يأتي بعد تعلم Core الخاص بـ MCP؟

غطت الفصول السابقة البروتوكول نفسه: Clients وServers وPrimitives وUtilities وSecurity وDeployment وTransports.

يطرح الفصل الأخير سؤالًا مختلفًا:

> **كيف نبني MCP ونشغله ونكتشفه ونحكمه ونوسعه ونطوره على مستوى المنظومة؟**

يجمع المصدر المنظومة الناشئة حول مشكلتين مهمتين على نحو خاص:

### الحوكمة (Governance)

تساعد أدوات Governance المؤسسات على الإجابة عن أسئلة مثل:

- ما Servers المعتمدة؟
- كيف يتم نشرها؟
- من يمكنه الوصول إليها؟
- كيف يتم فرض Authentication وAuthorization؟
- كيف تتم مراقبة النشاط وحالات الفشل؟
- هل يمكن عرض عدة Servers عبر Managed endpoint واحدة؟

### إدارة السياق (Context management)

تطرح أدوات Context management أسئلة مثل:

- كيف نتجنب إرسال مئات تعريفات Tools إلى Model؟
- كيف نعرض API ضخمة من دون إرباك عملية اختيار Tool؟
- كيف نقلل استخدام Tokens مع الحفاظ على القدرة؟
- ما العمل الذي ينبغي تنفيذه بصورة Deterministic داخل Code بدلًا من إجراء Round trip عبر Model؟

## 2. اكتشاف Servers على مستوى المنظومة (MCP Registry)

يجعل MCP القدرات قابلة للاكتشاف **داخل Server متصل**، لكن MCP في مراحله المبكرة لم يحل مشكلة اكتشاف Servers نفسها.

يعالج MCP Registry هذه الفجوة من خلال العمل كمستودع مركزي قابل للبرمجة لـ **Server metadata**.

### Registry بوصفه Metaregistry

يصف المصدر Registry الرسمي بأنه يخزن Metadata تشير إلى Code أو Binaries موجودة في أماكن أخرى، مثل Package registries.

على المستوى المفاهيمي:

```text
مطور Server (Server developer)
      ↓
نشر Package إلى Package registry (Publish package to package registry)
      ↓
إرسال Metadata إلى MCP Registry الرسمي (Submit metadata to official MCP Registry)
      ↓
Clients / Agents / Subregistries تستعلم من Registry API موحدة
```

تتضمن Metadata النموذجية:

- الاسم (name)،
- العنوان (title)،
- الوصف (description)،
- مستودع Source code،
- مواقع Packages،
- حقول Metadata مرنة.

### لماذا تهم API؟

الفكرة التصميمية المهمة ليست مجرد امتلاك Website. فوجود API موحدة يعني أن البشر والبرمجيات العادية وAutonomous agents يستطيعون البحث في Server metadata واستهلاكها برمجيًا.

[[IMAGE_NEEDED: Official MCP Registry discovery flow | A diagram showing server publisher → package registry + official MCP Registry metadata → clients/agents querying the Registry | Learner should notice that the official Registry points to distributable artifacts rather than necessarily hosting the server code itself]]

## 3. الاكتشاف مع الانتقاء والسياسات (Subregistries)

الفكرة الأكثر إثارة للاهتمام في Registry وفق المصدر هي **Subregistry**.

يمكن لـ Subregistry استهلاك Entries من:

- Registry الرسمي،
- Subregistries أخرى،
- Entries خاصة/داخلية بها.

ثم يمكنها انتقاء هذه Entries وإضافة Annotations إليها وإعادة نشرها باستخدام نموذج Registry API العام نفسه.

### لماذا تهم Subregistries؟

قد يرغب مجتمع عام في Ratings وComments. وقد ترغب مؤسسة في Servers خضعت فقط لمراجعة Security. وقد يرغب فريق في Servers معتمدة فقط لـ Workflow محددة.

يتيح الحقل المرن `_meta` الذي يصفه المصدر Annotations خاصة بـ Registry مثل:

- Ratings،
- Comments،
- Trust labels،
- حالة Approval،
- Ownership metadata،
- خصائص Policy خاصة بالمؤسسة.

يحوّل ذلك بنية Registry إلى جزء من **طبقة Governance**.

[[IMAGE_NEEDED: MCP Registry and subregistry ecosystem | Official Registry at top, several public/private subregistries beneath it, and multiple clients connected downstream; include an enterprise private subregistry with vetted-only entries | Learner should notice that subregistries can filter and enrich upstream data rather than simply copy it]]

## 4. منصات Governance وMCP gateways

نادراً ما تحتاج المؤسسات إلى Server واحدة مع قاعدة Authentication واحدة فقط. فهي تحتاج غالبًا إلى Fleet مُدارة.

يصف الفصل منظومة من أدوات Governance قد تجمع بين:

- Deployment،
- Hosting،
- Authentication،
- Authorization،
- Observability،
- Server registries،
- Gateway routing،
- Agent governance.

### بوابة MCP (MCP gateway)

توفر Gateway نقطة دخول محكومة أمام عدة خوادم MCP.

```text
Clients
  ↓
بوابة MCP (MCP Gateway)
  ├── المصادقة / السياسة
  ├── التوجيه (routing)
  ├── قابلية المراقبة (observability)
  ├── تصفية Tools (tool filtering)
  └── اكتشاف Servers (server discovery)
        ↓
Server A   Server B   Server C — خوادم متعددة
```

يمكن لهذا أن يوحّد Controls كان سيتعين تكرارها عبر كل Server.

### تقليل Tools عند Gateway

يصف المصدر أنماط Gateway/Portal التي لا تُظهر المجموعة الكاملة من Tools مقدمًا. وبدلًا من ذلك، قد يحصل Agent المتصل على واجهة Search/Execute صغيرة فقط أو يطلب التعريفات الكاملة عند الحاجة.

يجمع هذا بين Governance وContext management: تتحكم Gateway فيما هو مرئي **و** تمنع Tool catalog ضخمة من ملء Context window.

## 5. عكس نموذج الشبكة الواردة (MCP tunnels)

يتطلب Self-hosting لخادم MCP بعيد عادةً Inbound connection يمكن الوصول إليها علنًا.

يصف المصدر بنية Tunnel بديلة:

```text
النموذج التقليدي (Traditional)
Internet client → open inbound port → MCP server

نموذج Tunnel (Tunnel model)
MCP server → outbound tunnel → edge proxy ← client
```

يبدأ Server الداخلي الاتصال إلى الخارج، ما يقلل الحاجة إلى كشف Inbound port جديدة مباشرة للإنترنت العام.

يؤكد المصدر مزايا Security مثل:

- Attack surface أصغر للاتصالات الواردة،
- Connection validation،
- Traffic مشفرة بين Client وServer.

يبقى درس Architecture الأوسع مهمًا حتى إذا تغير منتج Tunnel محدد: **يمكن أن يكون الاتصال الذي يبدأ من الخارج Outbound-initiated أكثر أمانًا وأسهل تشغيليًا من كشف الخدمات الداخلية مباشرة.**

## 6. ضغط تنسيق Tools إلى Code حتمي (Code Mode)

إحدى مشكلات MCP المتكررة هي Tool overload. تخيل وجود مئات أو آلاف العمليات المتاحة. إرسال كل Schema إلى Model مكلف وقد يضر باختيار Tool.

يعالج **Code Mode** ذلك بتحويل قدرة Tools إلى Programming interface مدمجة وطلب توليد Code من Model مقابل هذه الواجهة.

على المستوى المفاهيمي:

```text
Tool catalog كبيرة (Large tool catalog)
      ↓
API typed مدمجة / واجهة قابلة للبحث
      ↓
LLM يكتب Code (LLM writes code)
      ↓
تشغيل Code داخل Sandbox معزولة (Code runs in isolated sandbox)
      ↓
Sandbox تنفذ عمليات حتمية مترابطة (Sandbox performs deterministic chained operations)
```

### لماذا يمكن أن يوفر ذلك Tokens؟

لا تحتاج Model إلى كل Tool schema المطولة داخل Context الخاص بها. وقد تتجنب أيضًا Model round trip بعد كل خطوة Tool حتمية.

### Code Mode على جانب Client

تشغّل إحدى البنى Code المولدة داخل Sandbox قرب Client. ويمكن أن تعمل Sandbox نفسها كـ MCP client آخر وترسل Protocol messages المطلوبة.

### Code Mode على جانب Server

تضع بنية أخرى Sandbox داخل Server وتعرض Tool surface صغيرة جدًا، مثل:

```text
search(...) — البحث عن العمليات المناسبة
execute(...) — تنفيذ العمليات المختارة
```

تبحث Model عن العمليات المناسبة ثم تكتب Code يربطها داخل عملية تنفيذ معزولة واحدة.

### متطلب Security

لا يكون Code execution جذابًا إلا إذا كانت Sandbox معزولة فعلًا. يصف المصدر مثالًا على جانب Server بلا Filesystem access ولا Environment variables ومع Outbound networking مقيدة.

[[IMAGE_NEEDED: Code Mode architecture | A diagram showing LLM receiving compact API → generating code → isolated sandbox → multiple MCP/API calls internally → final result returned to model | Learner should notice that multiple deterministic operations can happen without repeated model round trips]]

## 7. متى يفيد Code Mode ومتى لا يفيد؟

ليس Code Mode أفضل تلقائيًا من التصميم الجيد لـ Tools.

يكون أكثر فائدة عندما:

- تكون API/Tool catalog ضخمة،
- يمكن تركيب عدة Calls بصورة Deterministic،
- لا تحتاج Intermediate outputs إلى Semantic interpretation بواسطة LLM،
- توجد Sandbox قوية بالفعل.

وقد يقدم قيمة قليلة عندما:

- لا توجد سوى Tools قليلة مصممة لغرض محدد،
- تمثل Tools بالفعل سلوكيات End-to-end،
- يعتمد الإجراء التالي على فهم Semantic meaning للنتيجة السابقة،
- يتجاوز تعقيد Sandboxing وفورات Tokens.

يرتبط هذا مباشرة بمبدأ تصميم Server السابق:

> **فضّل العمل Deterministic داخل عملية واحدة مترابطة عندما لا تحتاج Model إلى Reasoning بين كل خطوة صغيرة.**

## 8. أطر MCP البديلة (Alternative MCP frameworks)

تعرض SDKs الرسمية البروتوكول مباشرة، لكن Frameworks في المنظومة تضيف Developer experience موجهة وميزات Production.

يناقش المصدر مثالين رئيسيين.

### إطار FastMCP

يصف المصدر FastMCP بأنه يركز على Developer experience مع إضافة ميزات حول Clients وProxies وMiddleware وAuthentication وProductionization.

ومن التفاصيل التاريخية المهمة في الفصل أن أفكارًا من إصدارات FastMCP المبكرة أثرت في أسلوب تطوير Server عالي المستوى داخل Python SDK.

### إطار arcade-mcp

يصف المصدر arcade-mcp بأنه يركز على بناء Server، وتكامل Deployment/Authorization، ودعم خفيف لتقييم Tool calling.

### الدرس ليس «استخدم Framework بدلًا من SDK»

مسار مفيد هو:

```text
تعلم أساسيات SDK / Protocol القياسية
          ↓
افهم أين يظهر تعقيد Production (Understand where production complexity appears)
          ↓
اعتمد ميزات Framework/Platform بصورة مقصودة
```

يمكن لـ Frameworks تقليل العمل التشغيلي، لكنها لا تلغي الحاجة إلى فهم MCP semantics وSecurity وTransports.

## 10. تطوير MCP من دون تضخيم Core (MCP extensions)

ليست كل ميزة مفيدة بحاجة إلى أن تكون ضمن MCP core protocol.

تسمح **MCP extensions** لميزات مطورة بصورة مستقلة بأن توسع MCP مع بقائها خارج Core protocol specification.

### معرفات Extension (Extension identifiers)

يصف المصدر Identifiers بالشكل العام:

```text
<vendor-id>/<extension-name>   — معرّف الناشر ثم اسم الامتداد
```

مع تشجيع قوي لاستخدام Vendor identifiers بأسلوب Reverse domain.

مثال من المصدر:

```text
io.modelcontextprotocol/ui
```

### لماذا يهم Extension framework؟

يسمح بالتجريب واعتماد قدرات متخصصة من دون إجبار كل Implementation لـ MCP على دعمها باعتبارها ميزات Core protocol.

يسرد المصدر أربعة Extensions رسمية في وقت الكتابة:

- MCP Apps،
- بيانات اعتماد OAuth للـ Client (OAuth Client Credentials)،
- التفويض المُدار مؤسسيًا (Enterprise-Managed Authorization)،
- MCP Tasks.

## 11. Tools بواجهات مستخدم يحددها Server (MCP Apps)

يوسع MCP Apps الـ Tools/Resources بحيث يستطيع Server تعريف UI يعرضها Client متوافق.

يمكن أن يتضمن Description الخاص بـ Tool UI metadata تشير إلى Resource تحتوي على الواجهة.

على المستوى المفاهيمي:

```text
تعريف Tool (Tool definition)
  └── _meta.ui.resourceUri
          ↓
Resource تحتوي على HTML/CSS/JavaScript UI
          ↓
Client متوافق يعرض App داخل Sandboxed iframe (Compatible client renders app in sandboxed iframe)
```

### لماذا نجمع Tools وResources؟

تنفذ Tool العملية. وتوفر Resource الـ UI artifact.

تشمل حالات الاستخدام التي يصفها المصدر:

- Visualization لبيانات Server،
- عرض Media،
- بناء Interactive reports،
- توفير تجارب أغنى للبيانات المحلية.

### أهمية Sandboxing

يشير المصدر إلى أن Apps تعمل داخل Sandboxed iframe بحيث لا تستطيع UI المقدمة الوصول بحرية إلى بيانات Host application/User.

## 12. امتدادات Authentication في MCP (MCP Auth Extensions)

يميز الفصل بين Interactive OAuth في Core وحالات استخدام Authorization القائمة على Extensions.

### بيانات اعتماد OAuth للـ Client (OAuth Client Credentials)

يكون هذا مفيدًا لـ **Machine-to-machine authorization** عندما لا يكون Interactive human login/consent flow مناسبًا.

على المستوى المفاهيمي:

```text
بيانات اعتماد تطبيق Client (Client application credentials)
        ↓
خادم Authorization (Authorization server)
        ↓
Access token
        ↓
طلب MCP تمت مصادقته (Authenticated MCP request)
```

يصف المصدر Provider في Python SDK يمكن ربطه بـ Async HTTP client يستخدمه MCP transport.

### التفويض المُدار مؤسسيًا (Enterprise-Managed Authorization)

يُقصد بهذا Extension المؤسسات التي تريد Enterprise identity مُدارة مركزيًا بدلًا من مطالبة كل موظف بإجراء Authorization مستقل لكل Server.

يصف المصدر متطلبات مثل:

- إعلان Client عن دعم Extension،
- تكامل SSO،
- استخدام Enterprise identity assertions/tokens،
- Configuration تتحكم فيها المؤسسة،
- معالجة Scope.

> **تحذير الدعم من المصدر:** كان دعم Clients لهذه Auth extensions محدودًا وقت كتابة الفصل. تعامل مع Compatibility على أنها أمر يجب التحقق منه، لا افتراضه.

## 13. التنفيذ غير المتزامن الدائم (MCP Tasks)

ينبغي ألا تُبقي بعض عمليات Tool طلبًا واحدًا مفتوحًا حتى الاكتمال.

تشمل الأمثلة:

- CI/CD pipelines،
- Downloads كبيرة،
- Model training،
- Batch computations،
- Jobs خارجية أخرى طويلة التشغيل.

يسمح MCP Tasks extension لـ Tool بإرجاع Placeholder result تحتوي على `taskId` بدلًا من Blocking حتى الاكتمال النهائي.

### دورة الحياة الأساسية (Basic lifecycle)

```text
Client → tools/call — يبدأ استدعاء Tool
Server → CreateTaskResult(taskId) — ينشئ Task ويعيد taskId
Client يواصل عملًا آخر (Client continues other work)
      ↓
Client → tasks/get(taskId) — يستعلم عن Task
Server → status — يعيد الحالة
      ↓
... الاستعلام مرة أخرى (poll again) ...
      ↓
Server → completed + final result — اكتمال مع النتيجة النهائية
```

### آلة حالات Task (Task state machine)

يسرد المصدر خمس حالات:

| الحالة | المعنى |
|---|---|
| `working` | ما زالت Task قيد التنفيذ |
| `input_required` | Task متوقفة مؤقتًا حتى يرسل Client المعلومات المطلوبة |
| `completed` | انتهت بنجاح |
| `failed` | انتهت من دون نجاح |
| `cancelled` | أُلغيَت بواسطة Client |

يمكن لـ Task الانتقال بين `working` و`input_required` قبل الوصول في النهاية إلى Terminal state.

### Durability هي الفكرة الأساسية

ترتبط State الخاصة بـ Task بـ `taskId` على Server بدلًا من ارتباطها بـ Network connection واحدة. ويمكن لـ Client إعادة الاتصال لاحقًا ومواصلة Polling إذا كان قد حفظ Task ID بصورة دائمة.

[[IMAGE_NEEDED: MCP Tasks durable state machine | A state diagram with working ↔ input_required and terminal states completed, failed, cancelled; show client polling tasks/get using taskId | Learner should notice that task durability is independent of one connection staying alive]]

> **ملاحظة دعم SDK من المصدر:** وقت الكتابة، يذكر الفصل أن دعم Tasks في Python SDK لم يكن متاحًا بعد، وكان ما يزال ضمن Roadmap.

## 14. المساهمة في MCP: عملية SEP

يتطور MCP من خلال عملية Proposal رسمية تتمحور حول **Specification Enhancement Proposals (SEPs)**.

يكون SEP مناسبًا لتغييرات مثل:

- إضافة Protocol features،
- تغيير سلوك Protocol الحالي،
- إزالة/Deprecating ميزات Protocol،
- تغيير Governance/Process،
- اقتراح/تغيير Protocol extensions.

لا تحتاج إصلاحات Documentation الصغيرة أو Implementation bugs عادةً إلى SEP.

### قبل الكتابة

ينبغي لـ Proposal قوية أن:

- تحل مشكلة يواجهها آخرون فعليًا،
- تكون مبنية على Research،
- تتوافق مع مبادئ تصميم MCP،
- يُفضّل أن تُناقش أولًا مع Contributor groups ذات الصلة.

الدرس أوسع من MCP: ينبغي أن تبدأ تغييرات Protocol من حاجة مثبتة داخل المنظومة، لا من مجرد فكرة شخصية مثيرة للاهتمام.

---

## 15. مسارات SEP

يسرد المصدر أربعة مسارات لـ Proposal.

| المسار | الاستخدام المقصود |
|---|---|
| Standards | ميزات Protocol جديدة أو تغييرات في مجموعة الميزات |
| Informational | إرشادات غير ملزمة للمستخدمين/Maintainers |
| Process | تغييرات Governance وProcess |
| Extensions | Extensions جديدة أو تعديلات على Extension specifications |

يهم اختيار Track لأنه يغير التزامات Review/Implementation.

يشير المصدر تحديدًا إلى أن **Proposals من نوع Standards وExtensions تتطلب Prototype implementation وConformance testing قبل Final approval**.

---

## 16. ما الذي يدخل في SEP قوية؟

يصف المصدر بنية قياسية لوثيقة SEP تتضمن:

- Preamble/Metadata،
- Abstract،
- Motivation،
- Detailed specification،
- Rationale والبدائل التي جرى النظر فيها،
- Backward compatibility،
- Reference implementation،
- Security implications.

تجبر هذه البنية مؤلفي Proposal على الإجابة عن أسئلة حاسمة في تصميم Protocol:

```text
ما المشكلة الموجودة؟ (What problem exists?)
لماذا لا يكفي Protocol الحالي؟ (Why is the current protocol insufficient?)
ما الذي سيتغير تحديدًا؟ (What exactly changes?)
لماذا هذا التصميم بدلًا من البدائل؟ (Why this design instead of alternatives?)
ما الذي سيتعطل؟ (What breaks?)
هل يمكن تنفيذه؟ (Can it be implemented?)
هل يمكن اختبار Compatibility؟ (Can compatibility be tested?)
ما مخاطر Security الجديدة التي تظهر؟ (What new security risks appear?)
```

لذلك فإن Protocol proposal أكثر بكثير من مجرد API sketch.

---

## 17. مراجعة SEP ورعايتها وتنفيذها وإنهاؤها

يصف المصدر Lifecycle تقريبًا كما يلي:

```text
بحث / نقاش
      ↓
كتابة SEP + فتح Pull request
      ↓
العثور على Maintainer sponsor (Find maintainer sponsor)
      ↓
مراجعة Draft (Draft review)
      ↓
مرحلة In-review رسمية (Formal in-review stage)
      ↓
مقبول / مرفوض / مطلوب تعديل
      ↓
Reference implementation
      ↓
Conformance tests عند الحاجة (Conformance tests when required)
      ↓
الحالة النهائية + إصدار Protocol مستقبلي
```

### دور Sponsor

يساعد Sponsor على توجيه Proposal خلال عمليات Review وMaintainership.

### لماذا تهم Reference implementations؟

قد يبدو التصميم أنيقًا على الورق لكنه يفشل تحت قيود Implementation الحقيقية الخاصة بـ SDK/Client/Server. تثبت Reference implementation قابلية التنفيذ العملية.

### لماذا تهم Conformance tests؟

يوجد Protocol لتمكين Interoperability. وتحول Conformance tests المتطلبات النصية إلى فحوصات قابلة للتكرار تستطيع SDKs وClients وServers تشغيلها.

[[IMAGE_NEEDED: SEP lifecycle | A flowchart from idea → discussion → PR → sponsor → draft → review → accepted → reference implementation → conformance tests → final → future release | Learner should notice that implementation and interoperability testing are part of specification work, not an afterthought]]

{{exercise:M05.L01.EX04}}

## 18. المساهمة خارج Protocol specification

ليست كل مساهمة تغييرًا في Protocol.

يشير المصدر أيضًا إلى المساهمات عبر:

- Issues وPull requests الخاصة بـ SDKs الرسمية،
- إصلاحات Documentation،
- Working groups،
- Interest groups،
- مناقشات Community،
- Implementations للـ Extensions،
- أدوات Conformance.

هذا مهم لأن Protocol ecosystems تعتمد على أكثر بكثير من Specification repository واحدة. فـ Documentation وTest suites وجودة SDK وSecurity research وخبرة Production كلها تعود لتغذي نضج Protocol.

## 19. Roadmap الخاصة بـ MCP واتجاه التطور

يختتم المصدر بالتأكيد أن MCP يتغير بسرعة.

في الوقت الذي يصفه الفصل، شملت مجالات أولوية Roadmap:

- تطور Transport وSecurity،
- اتصال Agents،
- نضج Governance،
- الجاهزية للمؤسسات.

ويذكر المصدر أيضًا مجالات اهتمام أوسع مثل:

- Event-driven updates،
- معالجة Results بمرونة/Streaming أكبر،
- تحسينات Authorization،
- نضج المنظومة.

### Skills فوق MCP

يستكشف اتجاه تجريبي يصفه الفصل توزيع **Skills/Know-how**، لا Raw tools فقط. وتتمثل الفكرة في السماح لـ Servers بمشاركة تعليمات لتنسيق القدرات نحو Goal، وربما باستخدام Resource primitives الموجودة للاكتشاف والتحديثات.

الدرس الأوسع هو أن تطور Protocol يتحرك إلى أعلى من مجرد عرض القدرات نحو Coordination وGovernance أكثر ثراءً.

## 20. النموذج الذهني النهائي للكتاب بالكامل

يمكنك الآن النظر إلى MCP باعتباره Stack كاملة لا مجرد ميزة Tool calling.

```text
Agent / تطبيق Host
        ↓
عميل MCP (MCP client)
        ↓
Transport + Sessions + JSON-RPC
        ↓
خادم MCP (MCP server)
        ↓
Tools / Resources / Prompts / Extensions
        ↓
أنظمة خارجية وبيانات وWorkflows (External systems, data, workflows)

حول Stack (Around the stack):
Registry → الاكتشاف (discovery)
Gateway → الحوكمة (governance)
Evals/testing → الموثوقية (reliability)
Sandbox/auth → الأمان (security)
Extensions → قدرات جديدة (new capabilities)
SEPs/conformance → تطور Protocol (protocol evolution)
```

أهم تحول مفاهيمي هو الآتي:

**MCP ليس مجرد طريقة لاستدعاء Tools. بل هو طبقة Interoperability تحيط بها منظومة من Discovery وGovernance وTesting وSecurity وExtensions وتطور Protocol المفتوح.**

---

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: «يستضيف Registry الرسمي كل MCP server.»

**لماذا هذا خطأ:** يصفه المصدر في المقام الأول بأنه Metadata metaregistry تشير إلى Code/Packages مستضافة في أماكن أخرى.

### المفهوم الخاطئ 2: «Subregistry مجرد Mirror.»

**لماذا هذا خطأ:** يمكنها الانتقاء والتصفية والإثراء وإضافة Entries خاصة وMetadata خاصة بالمؤسسة.

### المفهوم الخاطئ 3: «MCP gateway مجرد Reverse proxy.»

**لماذا هذا خطأ:** يمكن لـ Gateways أيضًا توحيد Auth وPolicy وRouting وObservability وDiscovery وتصفية Tools.

### المفهوم الخاطئ 4: «Code Mode أكثر كفاءة دائمًا من Tools.»

**لماذا هذا خطأ:** قد تستفيد مجموعات Tools الصغيرة المصممة لغرض محدد بدرجة قليلة، وقد تظل نقاط القرار Semantic بين Calls بحاجة إلى Model round trips.

### المفهوم الخاطئ 5: «تعني Frameworks البديلة أنني لم أعد بحاجة إلى فهم MCP SDK.»

**لماذا هذا خطأ:** تضيف Frameworks سهولة، لكن معرفة Protocol/Security/Transport تظل مطلوبة لأنظمة Production صحيحة.

### المفهوم الخاطئ 6: «يخبرني MCP Inspector ما إذا كانت كل Model ستختار Tools الخاصة بي بصورة صحيحة.»

**لماذا هذا خطأ:** يتحقق Inspector من سلوك Server/Protocol. أما Evaluations المتصلة بـ Model فتختبر كيف تستخدم Models الحقيقية Server.

### المفهوم الخاطئ 7: «تصبح Extensions تلقائيًا جزءًا من Core MCP.»

**لماذا هذا خطأ:** Extensions قدرات منفصلة صراحةً يمكنها التطور باستقلالية.

### المفهوم الخاطئ 8: «MCP Tasks مجرد Progress notifications.»

**لماذا هذا خطأ:** تمثل Tasks حالة Asynchronous دائمة مرتبطة بـ `taskId` ويمكنها الاستمرار بعد فقدان Connection/Restart.

### المفهوم الخاطئ 9: «كل مساهمة تحتاج إلى SEP.»

**لماذا هذا خطأ:** تستخدم إصلاحات Documentation الصغيرة وSDK bugs ومساهمات Code العادية مسارات المساهمة المعتادة للمشروع.

### المفهوم الخاطئ 10: «ينتهي SEP المقبول بمجرد الموافقة على النص.»

**لماذا هذا خطأ:** تتطلب Tracks ذات الصلة أيضًا Reference implementation وConformance testing قبل Finalization.

### المفهوم الخاطئ 11: «Roadmap عقد دائم.»

**لماذا هذا خطأ:** يعرض الفصل MCP صراحةً على أنه سريع التغير؛ لذلك يمكن أن تتغير أولويات Roadmap ودعم Implementation.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| MCP Registry | Registry مركزي قابل للبرمجة لـ MCP server metadata كما يصفه المصدر |
| Metaregistry | Registry تفهرس Metadata تشير إلى Packages/Code مستضافة في Registries أخرى |
| Subregistry | Registry منتقاة تستهلك بيانات Registry upstream وتضيف/تصفّي Entries/Metadata |
| Governance tool | Platform/Tooling لنشر بنية MCP وتأمينها وتفويض الوصول إليها ومراقبتها وتشغيلها |
| MCP gateway | نقطة دخول مُدارة تستطيع Routing وفرض Policy عبر عدة خوادم MCP |
| MCP tunnel | بنية اتصال تبدأ Outbound وتتجنب الكشف المباشر لـ Inbound server port |
| Context management | تقنيات لتقليل تكلفة Context/Tokens مع الحفاظ على القدرة |
| Code Mode | نمط تكتب فيه Models Code مقابل واجهات Tool/API مدمجة وتنفذه داخل Sandbox معزولة |
| FastMCP | إطار MCP بديل يناقشه المصدر مع التركيز على Developer experience وميزات Production |
| arcade-mcp | إطار بديل يركز على Server كما يناقشه المصدر |
| MCP Inspector | Debugger/Client تفاعلي مباشر لاختبار MCP server |
| MCPJam | بيئة اختبار MCP متصلة بـ Model يصفها المصدر |
| MCP extension | قدرة مطورة خارج Core protocol باستخدام Extension identifier ضمن Namespace |
| MCP Apps | Extension يسمح لـ Server tools بتوفير UI resources تعرضها Clients المتوافقة |
| بيانات اعتماد OAuth للـ Client (OAuth Client Credentials) | Extension لـ Machine-to-machine authorization |
| التفويض المُدار مؤسسيًا (Enterprise-Managed Authorization) | Extension لـ Enterprise identity/authorization المُدارة مركزيًا |
| MCP Tasks | Extension لتنفيذ Tools بصورة Asynchronous ودائمة باستخدام Task IDs وPolling |
| `taskId` | Identifier دائم يستخدمه Client للاستعلام عن State/Result الخاصة بـ Task |
| SEP | Specification Enhancement Proposal يُستخدم لاقتراح تغييرات في Protocol/Governance/Extensions |
| Standards track | مسار SEP لتغييرات ميزات Core MCP |
| Informational track | مسار SEP لإرشادات غير ملزمة |
| Process track | مسار SEP لتغييرات Governance/Process |
| Extensions track | مسار SEP لمواصفات Extensions |
| Sponsor | Maintainer يوجّه SEP خلال عملية Review |
| Reference implementation | Implementation عاملة تُستخدم لإثبات قابلية تنفيذ تغيير مقترح في Specification |
| Conformance test | اختبار قابل للتكرار يتحقق من اتباع Implementation لمواصفات Protocol |
| Roadmap | اتجاه/أولويات منشورة للعمل المستقبلي على MCP وقابلة للتغيير |

## احتفظ بهذه الفكرة

**لا ينتهي تعلم MCP عند Tools أو Clients أو Servers. تحتاج أنظمة MCP الواقعية إلى Discovery وGovernance وContext management وTesting وSecurity وExtensibility وعملية مساهمة مفتوحة. وفهم هذه المنظومة هو ما يحول معرفة Protocol إلى قدرة Production، ويمنحك مسارًا للمساعدة في تطوير Protocol نفسه.**
