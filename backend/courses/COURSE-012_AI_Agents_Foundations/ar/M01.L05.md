## 1. Decomposition و Planning مهارتان مختلفتان

يبدأ الفصل بتمييز يسهل تجاهله لكنه بالغ الأهمية.

### يسأل Decomposition: ما الأجزاء؟

يعني Decomposition تقسيم Task كبيرة إلى Subproblems أصغر.

مثال لهدف:

```text
إعداد تقرير لأبحاث السوق.
```

Decomposition محتملة:

```text
1. حدّد السوق.
2. ابحث عن المنافسين.
3. اجمع بيانات الأسعار.
4. حلّل الاتجاهات.
5. اكتب الاستنتاجات.
```

### يسأل Planning: بأي ترتيب، ومع أي Dependencies، وبأي Approach؟

يأخذ Planning تلك الأجزاء ويحدد كيف ينبغي تنفيذها.

على سبيل المثال:

```text
حدّد السوق أولًا.
ثم ابحث عن المنافسين والأسعار بالتوازي.
حلّل الاتجاهات فقط بعد جمع Evidence.
اكتب الاستنتاجات بعد اكتمال Analysis.
```

يمكن أن تفشل العمليتان بصورة مستقلة.

- قد يتبع Decomposition جيد Plan سيئ.
- وقد يفشل Plan مرتب جيدًا إذا كان Decomposition الأصلي قد أغفل Subtask مهمة.

هذا مهم لأن طريقة الإصلاح تعتمد على ما الذي فشل.

## 2. الاستدلال في Language Models

تولد Language model الـ Output Token بعد Token. وغالبًا ما يكون ذلك كافيًا للمهام البسيطة.

لكن في المهام الأصعب متعددة الخطوات، قد تقفز Model بسرعة كبيرة إلى إجابة تبدو معقولة دون معالجة Dependencies بصورة كافية.

يميز الفصل بين سلوكين واسعين:

### التوليد العام (General-purpose generation)

قد تجيب Model مباشرةً دون مرحلة Deliberation مخصصة.

هذا سريع ومنخفض التكلفة، ولذلك يكون مثاليًا لـ:

- عمليات Lookup بسيطة،
- Transformations قصيرة،
- Responses ذات Format ثابتة،
- Tasks قليلة الغموض.

### التنفيذ الموجَّه للاستدلال (Reasoning-oriented execution)

تخصص Reasoning-capable systems مقدارًا إضافيًا من Compute أو Structured steps قبل Final answer. قد يحسن ذلك الأداء في Hard multistep tasks، لكنه يزيد عادةً Latency و Token usage.

السؤال العملي ليس ببساطة:

```text
"هل تقوم هذه Model بالاستدلال؟"
```

السؤال الهندسي الأفضل هو:

```text
"هل يحسن الاستدلال الإضافي المهام التي أهتم بها بما يكفي لتبرير تكلفته؟"
```

## 3. الاستدلال بأسلوب Chain-of-Thought

Chain-of-Thought هي Linear reasoning strategy. يتم تشجيع Model على معالجة Problem عبر Intermediate stages قبل الالتزام بالـ Final result.

في Production systems، **لا** تحتاج عادةً إلى عرض Private internal reasoning للمستخدم. الفكرة الهندسية المفيدة هي **Structured decomposition**، وليست نشر Hidden model thoughts.

أسلوب Prompting آمن وعملي هو:

```text
حلّل المشكلة بعناية.
استخدم نقاط التحقق التالية:
1. حدّد القيم المعروفة.
2. حدّد القيمة غير المعروفة.
3. طبّق التحويلات المطلوبة بالترتيب.
4. تحقّق من النتيجة النهائية.
أعد إجابة موجزة تتضمن خطوات الحساب المهمة.
```

### لماذا تساعد بنية CoT-style؟

تقلل احتمال تخطي Model لـ Intermediate step ضرورية.

### المفاضلات الرئيسية

- Tokens أكثر،
- Latency أعلى،
- Outputs أطول إذا لم يتم تقييدها،
- تظل Probabilistic،
- لا تستطيع تعويض Model ضعيفة جوهريًا في كل Task.

الدرس ليس "اطلب دائمًا مزيدًا من الاستدلال." بل استخدم Structured reasoning عندما تحتوي Task فعلًا على عدة خطوات مترابطة.

## 4. ReAct: Reason ثم Act ثم Observe ثم Repeat

تبقى CoT بصورة أساسية داخل Reasoning pass واحدة. أما ReAct فتضيف Interaction مع العالم الخارجي.

النمط هو:

```text
استدلال (Reason) -> تنفيذ (Act) -> ملاحظة (Observe) -> استدلال (Reason) -> تنفيذ (Act) -> ملاحظة (Observe) -> ...
```

### مرحلة Reason

يحدد Agent ما المعلومات أو Action المطلوبة بعد ذلك.

### مرحلة Act

يستدعي Agent Tool أو API أو Database أو MCP server أو Capability أخرى.

### مرحلة Observe

يتلقى Agent النتيجة ويستخدمها لتحديد ما سيحدث بعد ذلك.

حلقة Feedback هي ما يجعل ReAct مختلفة عن One-shot response تحتوي بالصدفة على Tool call واحدة.

تسمح حلقة ReAct حقيقية للـ Observations بتعديل القرارات اللاحقة.

## 6. يتجاوز Planning حلقة Reasoning واحدة

تتسم ReAct بأنها Reactive: فهي تحدد Action التالية باستخدام أحدث Observation.

يضيف Long-horizon planning **Global plan** تنسق عدة Steps أوعدة ReAct loops نحو Objective أكبر.

مثال:

```text
الهدف: بناء برنامج رحلة لمدة ثلاثة أيام.

الخطة:
اليوم 1 -> النشاط A
اليوم 2 -> النشاط B
اليوم 3 -> النشاط C
```

إذا ظهرت معلومات جديدة، يمكن تعديل Plan.

على سبيل المثال:

```text
Observation: النشاط A غير متاح.
Updated plan: استبدل النشاط A مع الحفاظ على القيود الأخرى.
```

يوضح هذا فكرة Architecture مهمة:

> ينبغي أن توجد Plan في مكان خارج Model call واحدة إذا كان Agent يحتاج إلى الرجوع إليها لاحقًا.

## 8. ليس كل Agent بحاجة إلى Reasoning framework

يحذر الفصل صراحةً من Overengineering للمهام البسيطة.

غالبًا **لا** يستفيد Agent مباشر ينفذ Operation صغيرة واحدة من CoT أو ReAct أو ToT أو Reflexion.

أمثلة:

- البحث عن Value،
- استدعاء Tool واحدة،
- إعادة تنسيق Document،
- تصنيف Input بسيطة،
- إنتاج Fixed schema من Data واضحة.

تستحق Reasoning patterns تكلفتها عندما يوجد:

- أكثر من قرار ذي معنى،
- اعتماد على Intermediate results،
- Uncertainty،
- Branching،
- Revision،
- Difficulty كافية تجعل Direct generation غير موثوقة.

## 9. Tree-of-Thought: البحث عبر Alternatives

تتبع Chain-of-Thought Reasoning path واحدة. أما Tree-of-Thought (ToT) فتستكشف عدة Paths.

عملية ToT مبسطة هي:

1. أنشئ عدة Candidate next steps.
2. وسّع كل Candidate.
3. قيّم Branches الناتجة.
4. اعمل Prune للـ Branches الضعيفة.
5. استمر في توسيع Branches الواعدة.
6. توقّف عند العثور على Solution مرضية أوبلوغ Search limit.

```text
                  البداية
               /    |    \\
             A      B      C
            / \\    / \\    / \\
          ... ... ... ... ... ...
                ^
                |
         تقييم + Prune
```

### أفضل استخدام

تكون ToT مفيدة عندما تستفيد Problem من **Lookahead و Search**، مثل:

- Planning puzzles،
- Games،
- Strategic search،
- Problems ذات عدة Paths محتملة.

### التكلفة

قد يتطلب كل Branch Model calls إضافية و Evaluation و Expansion. ويمكن أن تزداد Token cost بسرعة.

### تفصيل تنفيذي مهم

يحتاج نظام ToT كامل عادةً إلى Orchestration code. يمكن لـ Prompt واحدة طلب عدة Candidates، لكن Pruning و Backtracking الحقيقيين هما External control-flow operations.

## 11. Reflexion: التحسين عبر Critique و Retry

تستخدم Reflexion استراتيجية مختلفة. بدل استكشاف Branches كثيرة، تتبع Path واحدة وتحسنها من خلال Repeated feedback.

الحلقة هي:

```text
محاولة (Attempt) -> تقييم (Evaluate) -> نقد (Critique) -> إعادة المحاولة (Retry)
```

ينشئ Solver إجابة. يحدد Critic مشكلة ويقدم Feedback. ثم يحاول Solver مرة أخرى مع تضمين هذا Feedback داخل Context.

### توضيح مهم

لا يقوم Agent بتحديث Model weights. فهو لا يتعلم حرفيًا بمعنى Training.

تتحسن المحاولة التالية لأن Input أصبحت تحتوي Context أكثر فائدة.

### أفضل استخدام

تعمل Reflexion جيدًا عندما:

- قد تكون المحاولة الأولى خاطئة،
- يكون Failure مفيدًا،
- يستطيع Feedback مفيد توجيه المحاولة التالية،
- تستحق Path واحدة Refinement أعمق.

### ToT مقابل Reflexion

```text
ToT       = Breadth: استكشف عدة Paths
Reflexion = Depth: حسّن Path واحدة عبر عدة Attempts
```

## 13. اختيار Reasoning strategy المناسبة

يلخص الفصل Reasoning strategies حسب Use case و Cost.

| الاستراتيجية | أفضل استخدام | التكلفة النسبية | تجنبها عندما |
|---|---|---:|---|
| الاستدلال الخطي بأسلوب CoT (Linear CoT-style reasoning) | المنطق والاستدلال متعدد الخطوات (Logic and multistep inference) | منخفضة | مهام واقعية بسيطة (Simple factual tasks) |
| نمط ReAct | مهام كثيفة استخدام Tools والبحث عن المعلومات | متوسطة | عندما لا تحتاج إلى External action أو Observation |
| شجرة الأفكار (Tree-of-Thought) | البحث المتفرع والتخطيط الاستراتيجي | مرتفعة | Workflows منخفضة Latency أو منخفضة Cost |
| نمط Reflexion | تحسين تكراري باستخدام Feedback مفيد | متوسطة إلى مرتفعة | مهام One-shot بسيطة جدًا |

عملية قرار عملية هي:

```text
هل Task بسيطة؟
  -> نعم: استخدم Direct agent.

هل تحتاج عدة Internal reasoning steps دون Tools؟
  -> استخدم Linear structured reasoning.

هل تحتاج Tools و Observation-driven adaptation؟
  -> استخدم ReAct.

هل تحتاج Search عبر عدة Candidate approaches؟
  -> فكّر في ToT.

هل تستفيد من Critique و Retry؟
  -> فكّر في Reflexion.
```

كلما كانت Pattern أكثر تقدمًا، وجب أن يكون مبرر استخدامها أقوى.

- ما الذي أخذه بالفعل في الاعتبار،
- ما Assumptions التي تم تعديلها،
- أي Branch يستكشفها،
- هل يحتاج إلى Analysis إضافية،
- كم Step ما زالت متبقية.

## 16. ما الذي تتتبعه Sequential Thinking scratchpad؟

يصف الفصل Metadata تسمح للـ Scratchpad بتمثيل Flexible reasoning process.

تشمل الأمثلة:

- Current thought text،
- Thought number،
- Estimated total thoughts،
- ما إذا كانت هناك Thought أخرى مطلوبة،
- ما إذا كانت Current thought تعدّل Thought سابقة،
- أي Thought سابقة يتم تعديلها،
- Branch point،
- معرّف Branch (Branch identifier).

مفاهيميًا، يدعم ذلك Operations مثل:

```text
سجّل Thought
عدّل Thought
أنشئ Branch من Thought
زد/قلل عدد Steps المتوقع
ضع علامة أن Analysis اكتملت
```

لذلك تدعم Scratchpad أكثر من Purely linear chain.

## 17. دمج Sequential Thinking مع ReAct

يجمع الفصل Scratchpad مع Action tools.

على سبيل المثال:

```text
1. يسجّل Agent خطوة Planning في Sequential Thinking.
2. يستدعي Agent الدالة travel_back(...).
3. يلاحظ Agent النتيجة.
4. يسجّل Agent خطوة Planning جديدة أومعدلة.
5. يستدعي Agent الدالة travel_forward(...).
6. يلاحظ Agent مرة أخرى.
7. ينتهي Agent عندما يتحقق Goal.
```

ينشئ ذلك Combination عملية:

```text
Sequential Thinking = Scratchpad خارجية
ReAct              = حلقة تحكم Action/Observation
Tools              = قدرات Deterministic أو External
```

يكون Tracing مفيدًا بصورة خاصة هنا لأن Final answer وحدها قد تخفي عدد Reasoning و Tool calls التي حدثت.

## 18. دمج عدة Reasoning patterns

بالنسبة إلى Difficult tasks، يعرض الفصل دمج عدة Strategies.

Architecture مفاهيمية هي:

```text
Structured reasoning -> أنشئ Initial plan
ReAct               -> نفّذ Actions و Observe
ToT                 -> استكشف Alternative branches عند الحاجة
Reflexion           -> انتقد Failed attempts وأعد المحاولة
```

يمكن أن يحسن ذلك Robustness في Difficult problems، لكن Cost قد تصبح مرتفعة جدًا.

قد تضيف كل Strategy إضافية:

- Model calls أكثر،
- Tool calls أكثر،
- Context أكثر،
- Evaluation أكثر،
- Latency أعلى،
- Failure paths أكثر.

لذلك ينبغي حجز Complex reasoning stacks للمهام التي تستحق فيها Reliability الإضافية هذه التكلفة.

## 19. لا تزال Reasoning outputs بحاجة إلى Validation

لا تضمن Reasoning process طويلة إجابة صحيحة.

يوضح الفصل ذلك عبر دمج Reasoning patterns مع Explicit checks.

نمط Production مفيد هو:

```text
استدلال وخطة (Reason / Plan)
    |
    v
تنفيذ (Execute)
    |
    v
تحقق (Validate)
    |
    +--> نجاح (Pass) -> إنهاء (Finish)
    |
    +--> فشل (Fail) -> تعديل (Revise) (محدود Bounded)
```

يمكن أن تأتي Validation من:

- Deterministic checks،
- Typed schemas،
- Tests،
- Judge أو Critic،
- Domain-specific constraints،
- التحقق باستخدام Tools (Tool-based verification).

يربط هذا Chapter 5 مرة أخرى بـ Chapter 4: يحسن Reasoning القرارات، بينما تمنع Guardrails و Validation هذه القرارات من التحول إلى Uncontrolled failures متتابعة.

## 20. دليل عملي للاستدلال والتخطيط (Practical reasoning and planning playbook)

استخدم هذا التسلسل عند تصميم Reasoning agent.

### الخطوة 1 — حدّد ما إذا كان Reasoning مطلوبًا فعلًا

لا تضف Complex pattern إلى One-step task.

### الخطوة 2 — افصل Decomposition عن Planning

تحقق من كليهما بصورة مستقلة.

### الخطوة 3 — استخدم Tools للعمل Deterministic

دع Code ينفذ Exact calculations أو Retrieval كلما كان ذلك ممكنًا.

### الخطوة 4 — استخدم ReAct عندما ينبغي للـ Observations تغيير Action التالية

هذه هي Default structure لكثير من Production agents.

### الخطوة 5 — خزّن Global plans خارج Model call واحدة

استخدم Application state أو Memory أو Scratchpad.

### الخطوة 6 — أضف Search فقط عندما لا تكفي Path واحدة

استخدم ToT بصورة انتقائية.

### الخطوة 7 — أضف Critique عندما يستطيع Feedback تحسين المحاولة التالية

استخدم Reflexion-style loops مع Hard attempt limits.

### الخطوة 8 — تتبّع Tool و Planning behavior

لا تعتمد فقط على Final response عند Debugging.

### الخطوة 9 — تحقّق من Outputs

طول Reasoning ليس دليلًا على الصحة.

### الخطوة 10 — حسّن Cost بعد تحقيق Correctness

بمجرد أن يعمل Workflow، قلّل Reasoning و Tools و Branches و Retries غير الضرورية.

---

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Decomposition و Planning هما الشيء نفسه

> يحدد Decomposition الأجزاء؛ بينما يحدد Planning بنية التنفيذ.

يمكن أن يكون أي منهما خاطئًا حتى عندما يكون الآخر صحيحًا.

### المفهوم الخاطئ 2: المزيد من Reasoning الظاهر يعني دائمًا Intelligence أكبر

> قد تساعد Steps الإضافية في Difficult tasks، لكنها تضيف أيضًا Noise و Latency و Cost.

المقياس المهم هو ما إذا كان Task performance يتحسن.

### المفهوم الخاطئ 3: Tool call واحدة تجعل Workflow من نوع ReAct

> تتطلب ReAct Observation-feedback loop تؤثر في القرارات اللاحقة.

Tool call واحدة معزولة ليست كافية.

### المفهوم الخاطئ 4: Tree-of-Thought مجرد Prompt طويلة

> تتطلب ToT الحقيقية Branch generation و Evaluation و Pruning و Control flow.

تكون External orchestration مطلوبة عادةً.

### المفهوم الخاطئ 5: Reflexion تحدّث Model

> لا تتغير Model weights.

يأتي التحسن من تمرير Critique مرة أخرى إلى Context الخاصة بالمحاولة التالية.

### المفهوم الخاطئ 6: Sequential Thinking تنفذ Reasoning نيابةً عن Agent

> هي أساسًا Structured scratchpad و Thought-state tracker.

يظل Agent هو Component الذي يتخذ القرارات.

### المفهوم الخاطئ 7: ينبغي دمج Reasoning patterns المتقدمة افتراضيًا

> قد يكون دمج CoT و ReAct و ToT و Reflexion مكلفًا للغاية.

استخدم فقط مقدار Complexity الذي تبرره Task.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التفكيك (Decomposition) | تقسيم Goal كبيرة إلى Subproblems أصغر |
| التخطيط (Planning) | اختيار Order و Dependencies و Resources و Strategy لحل Subproblems |
| CoT | Linear structured reasoning عبر Intermediate steps |
| نمط ReAct | Loop تدمج Reasoning و Action و Observation |
| الملاحظة (Observation) | معلومات تُعاد بعد Action/Tool call |
| الخطة طويلة المدى (Long-horizon plan) | Global strategy تنسق عدة Steps نحو Goal أكبر |
| مساحة العمل المؤقتة (Scratchpad) | مكان خارجي لتخزين Intermediate reasoning أو Planning state |
| شجرة الأفكار (Tree-of-Thought) | Search procedure تستكشف عدة Reasoning branches وتقيّمها وتعمل Prune لها |
| نمط Reflexion | Iterative solver-critic pattern تعيد المحاولة باستخدام Critique كـ Context جديدة |
| الناقد (Critic) | Component تقيّم Candidate result وتعيد Feedback |
| التفكير المتسلسل (Sequential Thinking) | MCP scratchpad/server لتتبع Structured thought state |
| الفرع (Branch) | Alternative reasoning path يتم استكشافها أثناء Search |
| التقليم (Pruning) | إزالة Low-value branches من الاستكشاف اللاحق |
| إعادة المحاولة المحدودة (Bounded retry) | Retry loop لها Maximum ثابت لعدد Attempts |
| التحقق (Validation) | التحقق من أن Reasoning output تحقق Deterministic أو Semantic requirements |

## التحقق الذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة:

1. كيف يختلف Decomposition عن Planning؟
2. لماذا يمكن أن يفشل الاثنان بصورة مستقلة؟
3. متى تكون Direct generation أفضل من Explicit reasoning pattern؟
4. ما المشكلة التي يحلها Linear structured reasoning؟
5. ما الذي يجعل ReAct حلقة بدل One-shot tool call؟
6. لماذا ينبغي تخزين Long-horizon plan خارج Model call واحدة؟
7. متى تستحق Tree-of-Thought تكلفتها؟
8. ماذا يعني Pruning في ToT؟
9. كيف تختلف Reflexion عن ToT؟
10. لماذا لا تُعد Reflexion نوعًا من Model training؟
11. ما أنواع Tasks التي تناسب ReAct أكثر؟
12. ماذا يوفر Sequential Thinking MCP server فعليًا؟
13. لماذا يكون Tracing مفيدًا عند استخدام Sequential Thinking مع Tools؟
14. لماذا يجب أن تكون Retries محدودة دائمًا؟
15. لماذا يجب أن تظل Reasoning outputs خاضعة للـ Validation؟

## احتفظ بهذه الفكرة

**تصبح Reasoning agents أكثر موثوقية عندما تفصل Architecture أربعة أشياء: نفّذ Decomposition للـ Goal، وخطط للعمل، ونفّذ Actions من خلال Tools، وتحقق من Observations. استخدم أبسط Reasoning pattern تحل Problem، وخزّن Long-lived plans خارج Model call واحدة، ولا تضف Branching أو Critique إلا عندما تستحق Task هذه Cost الإضافية.**
