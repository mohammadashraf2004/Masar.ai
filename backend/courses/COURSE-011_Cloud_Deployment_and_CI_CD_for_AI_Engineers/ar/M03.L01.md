## 1. لماذا توجد الـ containers: مشكلة الانحراف البيئي

قبل تعلّم أوامر Docker، تحتاج إلى فهم المشكلة التي يحلها Docker.

فشل شائع جدًا في تطوير البرمجيات يبدو هكذا:

> "تعمل على جهازي."

قد يكون المطوّر صادقًا.

فقد يعمل التطبيق فعلًا على حاسوبه المحمول.

لكن خادم الاختبار أو خادم الإنتاج قد يكون مختلفًا.

مثلًا:

```text
حاسوب المطوّر
Python 3.9
Library A مثبّتة
متغير البيئة مضبوط
مستوى ترقيع OS هو X

خادم الإنتاج
Python 3.8
Library A غير موجودة
متغير البيئة غير موجود
مستوى ترقيع OS هو Y
```

قد تكون شيفرة التطبيق متطابقة، لكن بيئة التشغيل ليست كذلك.

يسمي المصدر هذا **الانحراف البيئي (environmental drift)**.

### ما الذي يسبب الانحراف البيئي؟

قد تظهر الاختلافات في:

- إصدارات اللغة/بيئة التشغيل،
- المكتبات المثبّتة،
- حزم النظام،
- متغيرات البيئة،
- إعدادات نظام التشغيل،
- مستويات الترقيع،
- الأدوات والمرافق المحلية.

وكلما زاد ضبط البيئة يدويًا، سهل أن ينحرف نظامان أحدهما عن الآخر.

وهذا يخلق عدة مشكلات:

- يتصرف التطوير والإنتاج بشكل مختلف،
- يصعب إعادة إنتاج الأخطاء،
- تطول تعليمات الإعداد،
- يصبح الـ deployment هشًّا،
- يقضي المهندسون وقتهم في تصحيح البيئة بدلًا من التطبيق.

### فكرة الحاوية

تعالج الـ containers هذا بتحزيم التطبيق مع اعتماديات فضاء المستخدم (user-space) التي يحتاجها.

وبدلًا من القول:

```text
"ثبّت هذه الحزم،
واستخدم إصدار بيئة التشغيل هذا،
واضبط هذه الملفات،
ونأمل أن تعمل."
```

تبني حزمة تطبيق موحّدة.

نموذج ذهني مفيد:

```text
التطبيق
+
المكتبات المطلوبة
+
توقعات بيئة التشغيل
+
أمر البدء
=
container image
```

عندها يستطيع أي جهاز قادر على تشغيل منصة الـ containers تشغيل تلك البيئة المحزَّمة بقدر أكبر من الاتساق.

الفائدة الرئيسية في DevOps هي **قابلية إعادة الإنتاج (reproducibility)**.

أنت تريد أن ينتقل الـ artifact نفسه للتطبيق عبر:

```text
جهاز المطوّر
        ↓
CI pipeline
        ↓
بيئة الاختبار
        ↓
الإنتاج
```

مع مفاجآت أقل خاصة بكل بيئة.

## 2. الـ containers مقابل الأجهزة الافتراضية

قبل أن تنتشر الـ containers، كانت الأجهزة الافتراضية وسيلة رئيسية لعزل أحمال العمل.

كلتا التقنيتين توفّر العزل، لكن بطريقتين مختلفتين.

### 2.1 الأجهزة الافتراضية

يحاكي **الجهاز الافتراضي (Virtual Machine أو VM)** نظام حاسوب كاملًا.

يشغّل جهاز المضيف **hypervisor**، ويحتوي كل VM على نظام تشغيل ضيف (guest OS) خاص به.

من الناحية المفاهيمية:

```text
المضيف المادي (Physical Host)
│
├── Host OS / Hypervisor
│
├── VM 1
│   ├── Guest OS
│   ├── المكتبات (Libraries)
│   └── التطبيق (Application)
│
├── VM 2
│   ├── Guest OS
│   ├── المكتبات (Libraries)
│   └── التطبيق (Application)
│
└── VM 3
    ├── Guest OS
    ├── المكتبات (Libraries)
    └── التطبيق (Application)
```

يوفّر هذا عزلًا قويًا، لكن كل VM تتضمن نظام تشغيل ضيفًا كاملًا.

وهذا يجعل الـ VMs ثقيلة نسبيًا في:

- استخدام القرص،
- الـ RAM،
- حمل المعالج،
- زمن بدء التشغيل.

### 2.2 الـ containers

تتشارك الـ containers نواة (kernel) نظام تشغيل المضيف.

وتحزّم كل حاوية اعتماديات فضاء المستخدم الخاصة بالتطبيق بدلًا من نظام تشغيل ضيف كامل.

من الناحية المفاهيمية:

```text
جهاز المضيف (Host Machine)
│
├── Host OS
│
├── محرك الـ containers (Container Engine)
│
├── Container 1
│   ├── التطبيق (App)
│   └── المكتبات (Libraries)
│
├── Container 2
│   ├── التطبيق (App)
│   └── المكتبات (Libraries)
│
└── Container 3
    ├── التطبيق (App)
    └── المكتبات (Libraries)
```

[[IMAGE_NEEDED: Containers versus virtual machines | A side-by-side architecture diagram. VM side: hardware/host, hypervisor, multiple guest OS layers, each with libraries and app. Container side: hardware/host OS, container engine, multiple containers sharing the host kernel, each with libraries and app | Learner should notice that VMs repeat the guest operating system while containers share the host kernel]]

### لماذا يهمّ هذا

يبرز المصدر ثلاث مزايا رئيسية.

#### السرعة

لا تحتاج الـ containers إلى إقلاع نظام تشغيل ضيف كامل.

ويمكنها أن تبدأ وتتوقف بسرعة.

#### الكفاءة

ولأنها تتشارك نواة المضيف، يمكن غالبًا تشغيل حاويات كثيرة على مضيف لا يدعم إلا عددًا أقل من الـ VMs الكاملة.

#### قابلية النقل

يمكن تحزيم بيئة التطبيق في image قابلة لإعادة الاستخدام.

وهذا يقلل احتمال أن يتصرف التطبيق بشكل مختلف بسبب اعتماديات محلية مفقودة.

### تشبيه مفيد

يقارن المصدر:

```text
VM        → بيت مستقل لعائلة واحدة
Container → شقة في مبنى مشترك
```

البيت قائم بذاته.

أما الشقة فلها مساحة معيشة خاصة لكنها تتشارك البنية التحتية الأساسية للمبنى.

التشبيه ليس دقيقًا تقنيًا تمامًا، لكنه يلتقط فكرة كفاءة الموارد.

### حدّ مهم

الـ containers والأجهزة الافتراضية ليست مجرد "قديم مقابل جديد".

وهدف الفصل التعليمي أضيق:

> الـ containers أخف لأنها تتشارك نواة نظام تشغيل المضيف بدلًا من تحزيم نظام تشغيل ضيف كامل لكل حمل عمل.

## 3. الـ Image والحاوية وDockerfile: ثلاث أفكار يجب أن تفصل بينها

يخلط المبتدئون غالبًا بين هذه المصطلحات الثلاثة.

### Docker image

**Docker image** قالب للقراءة فقط يحتوي ما يلزم لتشغيل تطبيق.

وفي مثال المصدر يتضمن ذلك:

- بيئة تشغيل Python،
- اعتماديات التطبيق،
- شيفرة التطبيق،
- أمر البدء.

فكّر:

> **الـ Image = المخطط المحزَّم.**

### الحاوية (Container)

**الحاوية (container)** نسخة قيد التشغيل من image.

فكّر:

> **الحاوية = نسخة قيد التشغيل أُنشئت من المخطط.**

يمكنك إنشاء حاويات كثيرة من الـ image نفسها.

```text
الصورة (Image): simple-flask-app
        |
        +--> حاوية A
        |
        +--> حاوية B
        |
        +--> حاوية C
```

### Dockerfile

**Dockerfile** ملف نصي يحتوي تعليمات البناء التي يستخدمها Docker لإنشاء image.

فكّر:

> **Dockerfile = الوصفة المستخدمة لإنشاء الـ image.**

والعلاقة هي:

```text
Dockerfile
    |
    | docker build
    v
Docker Image
    |
    | docker run
    v
حاوية قيد التشغيل
```

[[IMAGE_NEEDED: Dockerfile to image to container | A three-stage flow: Dockerfile instructions → `docker build` → Docker image → `docker run` → running container, with one image branching to multiple containers | Learner should notice that a Dockerfile builds an image and an image can create multiple containers]]

- الصورة الأساسية `python:3.9-slim`.

### أزل صورة

⟦CODE_24⟧

إذا كانت حاوية ما لا تزال تشير إلى الـ image، حتى لو كانت تلك الحاوية متوقفة، فقد يمنع Docker الإزالة العادية للـ image.

لذلك يحدث التنظيف غالبًا بهذا الترتيب:

```text
أوقف الحاوية
    ↓

    ↓

```

### مجموعة الأوامر اليومية

يؤكد الفصل هذه الأوامر الشائعة:

```text
docker run    # الأوامر اليومية
docker ps
docker logs
docker stop
docker start
docker rm
docker images
docker rmi
```

لا تحفظها كأوامر عشوائية.

بل جمّعها ذهنيًا:

```text
إنشاء/تشغيل   → docker run
الفحص         → docker ps / docker logs
دورة الحياة   → docker stop / docker start / docker rm
الصور         → docker images / docker rmi
```

يقدّم المصدر Docker Hub بوصفه السجل العام الشائع.

```text

تخزّن مستودعات Git وتشاركها
```

### 9.1 وسم الـ image

### نمط تسليم Docker الأساسي

```text

   ↓
```

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1

> "Docker image تطبيق قيد التشغيل."

### لماذا هذا خاطئ

الـ image هي القالب القابل لإعادة الاستخدام.

أما الحاوية فهي نسخة قيد التشغيل أُنشئت من تلك الـ image.

---

### المفهوم الخاطئ 2

> "`EXPOSE 8080` يجعل التطبيق متاحًا على localhost تلقائيًا."

### لماذا هذا خاطئ

يميّز المصدر صراحةً بين توثيق منفذ الحاوية ونشره.

ويُنشأ ربط المضيف بالحاوية بشيء مثل:

⟦CODE_45⟧

---

### المفهوم الخاطئ 3

> "الـ containers مجرد أجهزة افتراضية أصغر."

### لماذا هذا ناقص

التمييز المعماري في الفصل أن الـ VMs تتضمن أنظمة تشغيل ضيفة منفصلة، بينما تتشارك الـ containers نواة نظام تشغيل المضيف وتحزّم بيئة فضاء المستخدم الخاصة بالتطبيق.

---

### المفهوم الخاطئ 4

> "`COPY . .` غير ضار دائمًا."

### لماذا هذا خاطئ

بدون `.dockerignore`، قد يتضمن سياق البناء ملفات محلية غير ضرورية أو حساسة مثل:

- `.git`،
- البيئات الافتراضية،
- الـ bytecode،
- `.env`.

---

### المفهوم الخاطئ 5

> "Docker Compose مفيد فقط عندما تكون هناك حاويات كثيرة."

### لماذا هذا ناقص

يوضّح المصدر Compose حتى بخدمة واحدة لأنه يركّز إعدادات مثل:

- تعليمات البناء،
- ربط المنافذ،
- الـ volumes.

وتزداد قيمته مع ازدياد الخدمات.

---

### المفهوم الخاطئ 6

> "`docker-compose` هو الأمر الحديث المفضَّل."

### لماذا هذا خاطئ

يذكر الفصل صراحةً أن التثبيتات الحديثة تستخدم:

```text
docker compose    # الأمر الحديث
```

بينما الأمر المستقل ذو الشرطة قديم.

---

### المفهوم الخاطئ 7

> "وسم Docker Hub ينشئ بناء image مستقلًا جديدًا."

### لماذا هذا خاطئ

ينشئ الوسم اسمًا/مرجعًا آخر لمحتوى الـ image الأساسي نفسه ما لم تبنِ محتوى image جديدًا.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Containerization | تحزيم تطبيق واعتماديات تشغيله في وحدة معزولة وقابلة للنقل |
| الانحراف البيئي (Environmental drift) | اختلافات بين البيئات تسبب سلوكًا غير متسق للتطبيق |
| الجهاز الافتراضي (VM) | حاسوب افتراضي يحتوي نظام تشغيل ضيفًا خاصًا به |
| Hypervisor | طبقة برمجية تُستخدم لإنشاء الأجهزة الافتراضية وتشغيلها |
| الحاوية (Container) | نسخة قيد التشغيل من container image |
| Docker | منصة وأدوات لبناء الـ containers وتشغيلها ومشاركتها |
| Docker image | قالب تطبيق للقراءة فقط يُستخدم لإنشاء الـ containers |
| Dockerfile | ملف نصي يحتوي تعليمات بناء Docker image |
| الصورة الأساسية (Base image) | الصورة الابتدائية التي يسمّيها `FROM` |
| سياق البناء (Build context) | الملفات التي يستطيع Docker الوصول إليها أثناء البناء من المسار المحدَّد |
| `.dockerignore` | ملف يستبعد مسارات من سياق البناء |
| الطبقة (Layer) | نتيجة بناء قابلة لإعادة الاستخدام مرتبطة بخطوات Dockerfile |
| `EXPOSE` | تعليمة Dockerfile توثّق منفذ الاستماع المقصود للحاوية |
| ربط المنافذ (Port mapping) | ربط بين منفذ على المضيف ومنفذ في الحاوية |
| الوضع المنفصل (Detached mode) | تشغيل حاوية في الخلفية باستخدام `-d` |
| Docker Compose | أداة لتعريف التطبيقات وتشغيلها باستخدام إعدادات YAML |
| الخدمة (Service) | مكوّن تطبيق مسمّى في ملف Compose |
| الـ Volume / bind mount | آلية لجعل بيانات المضيف أو البيانات الدائمة متاحة داخل حاوية |
| سجل الصور (Image registry) | خدمة تخزين/توزيع لصور الـ containers |
| Docker Hub | سجل صور Docker العام الذي قُدّم في الفصل |
| وسم الصورة (Image tag) | مرجع اسم/إصدار للصورة مقروء للبشر |
| `origin` | ليس مصطلح Docker؛ هو من درس Git السابق، الاسم البعيد الافتراضي بعد الاستنساخ |
| CI | سير عمل تكامل آلي يمكنه بناء الصور واختبارها ونشرها |

## اختبر نفسك

قبل أن تنتقل، تأكد من قدرتك على الإجابة عن:

1. ما هو الانحراف البيئي؟
2. لماذا قد يعمل تطبيق محليًا ويفشل في الإنتاج؟
3. ما الفرق المعماري بين الـ containers والـ VMs كما يصفه الفصل؟
4. ما الفرق بين Dockerfile والـ image والحاوية؟
5. ماذا يفعل `FROM python:3.9-slim`؟
6. لماذا ينسخ الـ Dockerfile الملف `requirements.txt` قبل نسخ المصدر كاملًا؟
7. لماذا ينبغي أن يستخدم المشروع `.dockerignore`؟
8. ماذا يفعل `EXPOSE 8080` وماذا لا يفعل؟
9. ماذا تعني النقطة `.` الأخيرة في `docker build -t simple-flask-app .`؟
10. اشرح `-p 4000:8080`.
11. ما هو الوضع المنفصل؟
12. كيف يختلف `docker ps` عن `docker ps -a`؟
13. ماذا ستفحص أولًا إذا خرجت حاوية بشكل غير متوقع؟
14. لماذا يجب غالبًا إزالة الـ containers قبل أن تُحذف الـ image الخاصة بها؟
15. لماذا يفيد Docker Compose؟
16. ماذا تعني `build` و`ports` و`volumes` في ملف Compose المقدَّم؟
17. ما صيغة أمر Compose الحديثة؟
18. ماذا ينبغي أن تفعل إذا كان منفذ المضيف في Compose قيد الاستخدام أصلًا؟
19. لماذا قد يكون `docker compose up --build` ضروريًا؟
20. ما هو سجل الصور؟
21. ماذا يوصل `yourusername/simple-flask-app:1.0.0`؟
22. لماذا يفيد وسم الإصدار؟
23. كيف يرتبط سير عمل Docker بـ CI/CD؟
