> **المقرر:** أسس الـ Deployment الآمن على السحابة  
> **الدرس:** M08.L09  
> **مواءمة المصدر:** BOOK-XXX، الفصل 9. يتبع الدرس سير عمل المصدر في Cloud Run وموازنة الحمل وIAP وCloud Armor. وتُعامل تفاصيل واجهة المزوّد والحصص والأمثلة على أنها خاصة بالمصدر.

## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح الحوسبة بلا خوادم (serverless) بمصطلحات المصدر.
- التمييز بين سلوك التطبيق ذي الحالة (stateful) وعديم الحالة (stateless) والمؤقت (ephemeral).
- شرح لماذا يُبقي المصدر Jenkins على VMs بدلًا من Cloud Run.
- شرح متطلب المصدر بأن تستمع حاويات تطبيقات Cloud Run على المنفذ 8080.
- بناء Flask وStreamlit ونشرهما كلًّا على حدة باستخدام `gcloud`.
- شرح الفرق بين بناء الصورة ونشر خدمة Cloud Run.
- شرح الحد الأدنى للنسخ في Cloud Run ومقايضة الـ latency.
- تعريف Network Endpoint Group (NEG) بلا خوادم.
- شرح كيف تربط الـ serverless NEGs خدمات Cloud Run بموازن حمل عالمي.
- بناء خدمات backend منفصلة لكل من Flask وStreamlit.
- توجيه الحركة بحسب اسم المضيف إلى الـ backend الصحيح.
- تحديث DNS ليشير النطاقان الفرعيان لـ Flask وStreamlit إلى موازن الحمل.
- تقييد الوصول المباشر إلى عناوين Cloud Run URL.
- شرح Identity-Aware Proxy للوصول الموثَّق عبر المتصفح.
- شرح Cloud Armor بوصفه خيار قائمة السماح بعناوين IP في المصدر للوصول بين الآلات.
- فهم مسار استكشاف أخطاء حصة Cloud Armor في المصدر.

## 1. بلا خوادم تعني أنك تدير التطبيق لا الخوادم

استخدمت معمارية GCP السابقة:

```text
أجهزة افتراضية (virtual machines)
+
مجموعات نسخ مُدارة (managed instance groups)
+
فحوصات صحة (health checks)
+
موازن حمل عالمي (global load balancer)
```

وينقل الفصل 9 كلًّا من Flask وStreamlit إلى نموذج **serverless**.

ويصف المصدر الحوسبة بلا خوادم بأنها بنية تحتية يتولى فيها مزوّد السحابة إدارة:

```text
توفير الخوادم
إدارة نظام التشغيل
التوسع
دورة حياة الحاويات
```

بينما يركّز المطوّر أساسًا على:

```text
شيفرة التطبيق
صورة الحاوية
إعداد الخدمة
```

### النموذج الذهني للـ VM

مع الـ VM:

```text
أنت تدير:
OS
الحزم (packages)
Docker
تشغيل الخدمة
تحديد حجم الجهاز
الترقيع (patching)
```

### النموذج الذهني بلا خوادم

مع Cloud Run:

```text
أنت تقدّم:
صورة الحاوية

Google تدير:
الخوادم الأساسية
دورة حياة النسخ
بنية التوسع التحتية
```

وهذا **لا** يعني أنه لا توجد خوادم حرفيًا.

بل يعني أن الخوادم مجرَّدة عنك.

[[IMAGE_NEEDED: VM deployment versus serverless deployment | A side-by-side diagram showing VM deployment where the engineer manages OS, Docker, services, scaling, and application versus Cloud Run where the engineer provides a container and Google manages infrastructure and scaling | Learner should notice that serverless removes infrastructure-management responsibility rather than eliminating physical servers]]

## 2. التطبيقات ذات الحالة وعديمة الحالة والمؤقتة

يقدّم المصدر ثلاثة مصطلحات قبل الـ deployment.

### ذو حالة (Stateful)

يعتمد التطبيق **ذو الحالة (stateful)** على بيانات أو حالة جلسة تبقى بعد طلب واحد.

وتشمل الأمثلة من الناحية المفاهيمية:

```text
ملفات محلية دائمة
حالة الإعدادات
حالة جلسة المستخدم
تاريخ التطبيق
```

### عديم الحالة (Stateless)

يعامل التطبيق **عديم الحالة (stateless)** كل طلب باستقلالية.

ويمكن عادةً تكراره بسهولة أكبر لأن أي نسخة متوافقة تستطيع معالجة الطلب التالي.

### مؤقت (Ephemeral)

البيئة **المؤقتة (ephemeral)** بيئة عابرة.

وقد تقوم نسخة الحاوية بما يلي:

```text
تبدأ
تعالج العمل
تتوقف
تُستبدل
```

دون أن تتحكم في دورة حياة نظام الملفات المحلي طويلة الأمد لديها.

### لماذا يُستبعد Jenkins

يشرح المصدر تحديدًا أن Jenkins لا يناسب الـ deployment بلا خوادم في الفصل لأنه يعتمد بشدة على:

- تخزين دائم،
- صلاحيات الملفات،
- إعدادات ذات حالة،
- حالة نظام ملفات طويلة العمر.

وقد أبقت الفصول السابقة عن قصد على:

```text
/var/jenkins_home    # مجلد Jenkins الدائم
```

ويتعارض نموذج الحاوية المؤقتة في Cloud Run مع هذه المعمارية في المصدر.

لذلك لا ينشر الفصل 9 سوى:

```text
Flask    # التطبيقان المنشوران
Streamlit
```

### بدائل المصدر للأعمال المجدولة الشبيهة بـ Jenkins

يذكر المصدر الدوال بلا خوادم مع مجدوِل (scheduler) لبعض المهام المجدولة بأسلوب ETL.

والدرس الأوسع:

> اختر معمارية الـ deployment بحسب متطلبات حالة التطبيق.

## 5. افهم الحد الأدنى للنسخ في Cloud Run

يقول المصدر إن الحد الأدنى لعدد نسخ Cloud Run يكون افتراضيًا:

```text
0
```

في مثاله.

وهذا يعني أنه قد لا توجد نسخة تطبيق نشطة في المنصة أثناء الخمول.

وعند وصول طلب، قد تحتاج نسخة إلى أن تبدأ.

### مقايضة البدء البارد (Cold-start)

من الناحية المفاهيمية:

```text
الحد الأدنى = 0
→ تكلفة خمول أقل محتملًا
→ قد ينتظر أول طلب بدء التشغيل
```

مقابل:

```text
الحد الأدنى >= 1
→ تبقى النسخة دافئة
→ استجابة أولية أسرع
→ تكلفة خمول إضافية
```

وينصح المصدر تحديدًا بالنظر في:

```text
الحد الأدنى للنسخ = 1
```

للتطبيقات الحساسة للـ latency.

وهذه مقايضة تصميمية في الحوسبة بلا خوادم لا قيمة صحيحة عالميًا لها.

## 7. ابنِ موازن حمل HTTPS العالمي

ينشئ المصدر:

```text
Global external Application Load Balancer (الخارجي العالمي)
```

مع frontend بـ HTTPS.

### الـ Frontend

تتضمن إعدادات المصدر:

```text
البروتوكول (Protocol): HTTPS
IPv4
عنوان IP محجوز للـ frontend (Reserved frontend IP)
المنفذ (Port): 443
شهادة SSL موجودة (Existing SSL certificate)
```

### خدمات backend منفصلة

ينشئ المصدر:

```text
lb-https-backend-flask    # أسماء خدمات الـ backend
lb-https-backend-streamlit
```

ويستخدم كل backend:

```text
نوع الـ backend (Backend type):
مجموعة نقاط نهاية شبكة بلا خوادم (Serverless network endpoint group)
```

ويشير إلى:

```text
flask-neg    # أسماء الـ NEG
streamlit-neg
```

على التوالي.

### لماذا backendان؟

لأن التوجيه بحسب اسم المضيف يحتاج إلى اختيار وجهات تطبيقات مختلفة.

### خيار Cloud CDN في المصدر

يعطّل المصدر Cloud CDN لأنه يريد لاحقًا استخدام IAP في المعمارية الموصوفة.

### قواعد التوجيه

يعرّف المصدر قواعد مضيف مثل:

```text
streamlit.lb-webserver.pro    # قاعدة المضيف
  → lb-https-backend-streamlit

flask.lb-webserver.pro
  → lb-https-backend-flask
```

وتلتقط القاعدة الافتراضية الحركة غير المطابقة.

## 8. وجّه DNS إلى موازن الحمل وعطّل الوصول المباشر إلى Cloud Run

بعد إنشاء موازن الحمل، يحصل المصدر على عنوان IP الخاص بالـ frontend.

ويحدّث سجلات DNS للتطبيقات المعنية فقط:

```text
flask    # اسما النطاقين الفرعيين
streamlit
```

لتستخدم عنوان IP الجديد لموازن الحمل.

ويقول صراحةً ألا تغيّر خدمات غير ذات صلة مثل Jenkins لأن Jenkins لا يعمل على Cloud Run.

### لماذا نعطّل عناوين Cloud Run الافتراضية؟

في البداية نُشرت الخدمات بعناوين URL عامة مباشرة.

وإذا أردت ألا يدخل المستخدمون إلا عبر موازن الحمل، فإن تلك العناوين المباشرة تخلق مسار التفاف.

ويغيّر المصدر الـ ingress باستخدام:

```text
internal-and-cloud-load-balancing    # قيمة الـ ingress
```

للخدمتين معًا.

من الناحية المفاهيمية:

```text
قبل:
الإنترنت ──────────→ عنوان Cloud Run URL
   └──────────────→ Load Balancer → Cloud Run

بعد:
الإنترنت ─X───────→ عنوان Cloud Run URL المباشر
   └──────────────→ Load Balancer → Cloud Run
```

وهذا يركّز:

- نقطة TLS،
- التوجيه بحسب اسم المضيف،
- ضوابط الوصول.

## 9. استخدم Identity-Aware Proxy لمصادقة المتصفح

تقييد الوصول المباشر إلى Cloud Run لا يعني تلقائيًا أن المستخدمين المعتمدين وحدهم يستطيعون استخدام التطبيق.

ويقدّم المصدر **Identity-Aware Proxy (IAP)**.

### نموذج IAP

```text
المتصفح
  ↓
Load Balancer
  ↓
تسجيل دخول IAP
  ↓
مستخدم مصرَّح له؟
  ├── no → deny
  └── yes → خدمة الـ backend
```

### منح الوصول

يضيف المصدر مستخدمين (principals) ويمنحهم الدور:

```text
IAP-secured Web App User    # اسم الدور
```

للـ backend المعني.

### أنسب استخدام في المصدر

يقدّم الفصل IAP على أنه مفيد لـ:

```text
تطبيقات تعمل عبر المتصفح
```

مثل Streamlit وصفحة Flask موجهة للبشر.

### تنبيه بخصوص الوصول بين الآلات

بالنسبة إلى استدعاءات الـ API مثل:

```text
POST /predict    # مسار التنبؤ
```

يقول المصدر إن IAP قد يكون مرهقًا.

وهذا ما يدفع إلى الخيار الأمني التالي.

## 10. استخدم Cloud Armor لتقييدات عنوان IP المصدر

يقدّم المصدر **Cloud Armor** بديلًا عندما تريد:

```text
السماح بعناوين IP محددة
منع الجميع
```

### بنية السياسة

ينشئ المصدر:

```text
سياسة أمان للـ backend (Backend security policy)
النطاق (Scope): Global
الطبقة (Layer): Application
الإجراء الافتراضي (Default action): Deny 403
```

ثم يضيف قاعدة سماح ذات أولوية أعلى مثل:

```text
عنوان IP المصدر /32
→ Allow
```

ويربط السياسة بخدمتي الـ backend لـ Flask وStreamlit.

### فكرة الـ evaluation للقواعد

```text
قاعدة سماح محددة
       ↓
مطابقة؟
  yes → allow
  no  → الرفض الافتراضي 403
```

### لماذا يناسب هذا الوصول بين الآلات في المصدر

النظام الخارجي الموثوق ذو عنوان IP المعروف لا يحتاج إلى صفحة تسجيل دخول Google تفاعلية.

ويمكن أن تكون هويته الشبكية هي شرط الوصول.

### مشكلة حصة Cloud Armor

يوثّق المصدر فشلًا عمليًا:

```text
حصة SECURITY_POLICY_RULES = 0
```

في بعض المشاريع الجديدة.

وتسلسل استكشاف الأخطاء فيه:

1. ابحث في الحصص عن `security_policy_rules`،
2. حدّد الحصة العالمية،
3. أكّد القيمة،
4. اطلب زيادة عبر مسار المزوّد الذي يصفه المصدر،
5. تحقق من أن الحصة تغيّرت.

اعتبر عملية دعم المزوّد الدقيقة خاصة بالمصدر.

[[IMAGE_NEEDED: IAP versus Cloud Armor access models | A split diagram. Left: human browser → Google sign-in/IAP → backend. Right: trusted machine IP → Cloud Armor allow rule → backend, all other IPs → 403 | Learner should notice that authentication and IP allow-listing solve different access-control problems]]

## 11. اجمع معمارية Cloud Run الكاملة معًا

التصميم النهائي في المصدر هو:

```text
المطوّر
   ↓
Cloud Build
   ↓
سجل الحاويات (container registry)
   ↓
خدمات Cloud Run
   ├── flask-app
   └── streamlit-app
        ↓
serverless NEGs
        ↓
خدمات backend منفصلة
        ↓
توجيه معتمد على المضيف
        ↓
Global HTTPS Load Balancer
        ↓
DNS مخصص
```

وتُضاف طبقة الأمان فوق ذلك:

```text
عنوان Cloud Run URL المباشر
→ محجوب بسياسة الـ ingress

مستخدمو المتصفح
→ تتم مصادقتهم اختياريًا عبر IAP

عملاء الآلات/الـ API الموثوقون
→ تتم تصفيتهم اختياريًا عبر Cloud Armor
```

وهذا هو المكافئ بلا خوادم للـ deployment السابق القائم على VMs، لكن بإدارة مباشرة أقل بكثير للبنية التحتية.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1
> "بلا خوادم تعني أنه لا توجد خوادم."

يدير المزوّد الخوادم؛ ولم تعد أنت تديرها مباشرة.

### المفهوم الخاطئ 2
> "كل تطبيق مرشح جيد للنشر بلا خوادم."

يستبعد المصدر Jenkins لأن توقعات حالته ونظام ملفاته تتعارض مع نموذج الحاوية المؤقتة في الفصل.

### المفهوم الخاطئ 3
> "تصبح خدمات Cloud Run تلقائيًا backends لموازن الحمل."

ينشئ المصدر serverless NEGs وخدمات backend أولًا.

### المفهوم الخاطئ 4
> "تغيير DNS إلى موازن الحمل يحجب تلقائيًا عنوان Cloud Run URL المباشر."

يغيّر المصدر الـ ingress صراحةً لمنع الالتفاف.

### المفهوم الخاطئ 5
> "IAP وCloud Armor ضابط أمني واحد."

يصادق IAP المستخدمين؛ أما Cloud Armor فيستخدمه المصدر للسماح/المنع بحسب شروط عنوان IP.

| بلا خوادم (Serverless) | نموذج تشغيل مُدار يجرّد إدارة البنية التحتية |
| عديم الحالة (Stateless) | معالجة الطلبات دون الاعتماد على حالة جلسة محلية دائمة |
| مؤقت (Ephemeral) | نسخة تشغيل عابرة يمكن إنشاؤها وإزالتها |
| Cloud Run | خدمة حاويات بلا خوادم في GCP التي يستخدمها المصدر |
| Cloud Build | خدمة بناء تُستخدم لإنشاء صور الحاوية |
| Serverless NEG | كائن ربط في موازن الحمل لخدمة بلا خوادم |
| خدمة الـ Backend (Backend service) | إعداد backend في موازن الحمل |
| Ingress | قواعد تتحكم في كيفية الوصول إلى الخدمة |
| IAP | وكيل مدرك للهوية (Identity-Aware Proxy) |
| Cloud Armor | منتج سياسات الأمان في GCP المستخدم لتقييدات IP في المصدر |

## اختبر نفسك

1. ماذا تجرّد الحوسبة بلا خوادم؟
2. لماذا يُستبعد Jenkins من الـ deployment على Cloud Run؟
3. كيف يختلف التطبيق ذو الحالة عن عديم الحالة؟
4. ما المنفذ الداخلي الذي يستخدمه المصدر لحاويات Cloud Run؟
5. ما الفرق بين `gcloud builds submit` و`gcloud run deploy`؟
6. لماذا قد يقلّل الحد الأدنى للنسخ بقيمة 1 الـ latency؟
7. ما هي الـ serverless NEG؟
8. لماذا ينشئ المصدر خدمتي backend؟
9. كيف يعرف موازن الحمل هل يرسل الطلب إلى Flask أم Streamlit؟
10. لماذا يحجب المصدر عناوين Cloud Run URL المباشرة؟
11. ما المشكلة التي يحلها IAP؟
12. لماذا قد يكون Cloud Armor أكثر ملاءمة لعميل آلي؟
13. ماذا تفعل سياسة Cloud Armor بالرفض الافتراضي؟
14. ما مشكلة الحصة التي يوثّقها المصدر؟
15. تتبّع طلبًا واحدًا من `https://flask.<domain>` إلى خدمة Flask على Cloud Run.

## الفكرة التي تحتفظ بها

**الـ deployment بلا خوادم لا يلغي المعمارية؛ بل ينقل مسؤولية البنية التحتية إلى المزوّد. ما زلت تصمّم الصور وسلوك التوسع وتوجيه موازن الحمل وDNS والـ ingress والمصادقة، لكنك لم تعد تدير أسطول الـ VMs الأساسي بنفسك.**
