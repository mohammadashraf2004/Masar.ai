يمكن لـ Static type checker اكتشاف الاستدعاء الثاني قبل أن يصل البرنامج إلى Production.

### ما Type safety؟

**Type safety** هي ممارسة التأكد من استخدام Values بطرق متوافقة مع Types المتوقعة لها.

على سبيل المثال:

```text
تتوقع Function نوع int
        ↓
يمرر Caller قيمة int
        ↓
العملية متوافقة
```

مقابل:

```text
تتوقع Function نوع int
        ↓
يمرر Caller قيمة str
        ↓
Bug محتمل
```

### لماذا يزداد هذا أهمية مع نمو التعقيد؟

في Script صغير، قد تتذكر كل Variable.

أما في Production service فقد يكون لديك:

```text
المسار
  ↓
schema
  ↓
الخدمة
  ↓
المزوّد
  ↓
قاعدة البيانات
  ↓
API خارجي
```

قد ينتقل Field واحد عبر Layers كثيرة.

إذا تغير Database column، أو غيّرت API شكل Response الخاص بها، أو حدّث Developer آخر Model object، فقد يفشل Untyped code بعد ذلك بكثير داخل Component غير مرتبط ظاهريًا.

تمنح Type information الأدوات خريطة لتدفق البيانات المتوقع.

### Type safety هي Feedback مبكرة

يشدد المصدر على ميزة عملية:

> **يمكن للـ Types تحويل بعض Production failures إلى Development-time warnings.**

وهذا قد يوفر وقت Debugging لأن المشكلة تُكتشف بالقرب من المكان الذي أُدخل فيه التغيير غير المتوافق.

## 2. Python الديناميكية وStatic type analysis

Python هي **Dynamically typed language**.

وهذا يعني أن Python لا تطلب منك تعريف Type لكل Variable قبل تشغيل البرنامج.

على سبيل المثال:

⟦CODE_3⟧

تسمح Python لاسم Variable بالإشارة إلى Types مختلفة وقت التشغيل.

تساعد هذه المرونة Developers على إنشاء Prototypes بسرعة.

لكن المرونة قد تتحول إلى عدم يقين مع نمو النظام.

### اللغات Static typing مقابل Optional typing في Python

يقارن الفصل بين أسلوبين عامين.

```text
لغة Statically typed
→ يتم فرض Type rules بقوة قبل التنفيذ

Python
→ يظل Runtime ديناميكيًا
→ يمكن للأدوات تحليل Optional type annotations
```

لا تحول Python type annotations اللغة إلى Fully statically typed runtime.

بل تنشئ معلومات يمكن للأدوات تحليلها.

### أدوات الفحص الساكن للأنواع (Static type checkers)

- أداة pyre.

يمكن لـ Type checker إخبارك بأن Function تستقبل `int`.

لكنه لا يستطيع إثبات أن Integer تحمل Business meaning الصحيحة.

## 13. Dataclasses أم Pydantic models في FastAPI؟

يمكن لـ FastAPI العمل مع الاثنين.

### Dataclass عادية (Vanilla dataclass)

⟦CODE_44⟧

يشرح الفصل أن FastAPI تستطيع تكييف Dataclasses عبر Pydantic integration لمعالجة Requests/Responses.

وهذا مفيد إذا كان لديك Existing codebase مليئة بالـ Dataclasses.

### نموذج Pydantic

⟦CODE_45⟧

بالنسبة إلى API project جديدة، يفضل المصدر استخدام Pydantic مباشرةً لأنها تعرض Rich features بصورة طبيعية.

### المقارنة

| القدرة (Capability) | Dataclass عادية (Vanilla dataclass) | نموذج Pydantic |
|---|---|---|
| حقول Typed | نعم | نعم |
| Class مختصرة متمحورة حول البيانات | نعم | نعم |
| Parsing وقت التشغيل | محدود دون Logic إضافية | مدمج |
| قيود Fields غنية | ليست Native بالطريقة نفسها | مدمجة |
| Validation مخصصة | تحتاج Manual logic | مدمجة |
| التحكم في Serialization | أكثر Manual | مدمجة |
| توليد JSON schema | ليست Native feature في Dataclass | مدمجة |
| التكامل مع FastAPI | مدعومة | Native / متكاملة بقوة |

لذلك القرار ليس:

```text
Dataclass سيئة
Pydantic جيدة
```

بل:

```text
استخدم Tool التي تناسب Features الخاصة بالـ Boundary
```

بالنسبة إلى Internal structured data، قد تكون Dataclass كافية.

أما API contracts التي تستقبل Untrusted input، فغالبًا تكون Pydantic أكثر ملاءمة.

## 15. تقليل عدم اليقين عندما تتغير Schemas

الهدف الأعمق للفصل ليس مجرد "تعلم Pydantic syntax".

بل جعل الأنظمة المتغيرة أكثر أمانًا.

### تغيّر External API

افترض أن Application تتوقع:

⟦CODE_49⟧

ثم يغير Provider الـ SDK أوSchema.

مع Typed clients وModels، يمكن أن يصبح الاستخدام المتأثر ظاهرًا من خلال:

- Type-checker errors،
- Validation failures،
- حالات فشل Tests.

بدون Explicit contracts، قد ينتقل التغيير لمسافة أبعد قبل الفشل.

### تغيّر Database schema

تخيّل أن Field يتغير من:

```text
user_id: int — User ID من نوع Integer
```

إلى:

```text
user_id: str — User ID من نوع String
```

إذا كانت Services وRepositories typed، يمكن لـ Static analysis كشف المواقع التي لا تزال تفترض Integer.

### عدم اليقين في Model response

تضيف GenAI systems Boundary أخرى غير مستقرة.

يمكن لـ Model إنتاج Probabilistic output.

إذا كانت Application تتوقع Structured information، يمنحك نهج Pydantic في الفصل طريقة للتحقق من أن Result تطابق Required schema قبل أن يثق بها Downstream code.

### تجعل Types الـ Refactoring مرئيًا

فكّر في Typed codebase باعتبارها شبكة Contracts.

```text
Schema A
   ↓
دالة B
   ↓
خدمة C
   ↓
مزوّد D
```

إذا تغير Contract، تستطيع Tools إظهار الأجزاء المتصلة التي لم تعد متطابقة.

ويكون هذا ذا قيمة خاصة في Codebases التي تحتوي على:

- Contributors متعددين،
- External systems كثيرة،
- Prompts متغيرة،
- Providers متغيرين،
- Database schemas متغيرة.

### أضف Checks إلى Delivery pipeline

يوصي الفصل بأخذ Static checks إلى ما بعد Editor.

يمكن أن تتضمن Development pipeline:

```text
اكتب Change
   ↓
Format/Lint
   ↓
Static type check
   ↓
Tests
   ↓
Build/Deploy checks
   ↓
Production
```

إذا فشل Type check، يمكن إيقاف Change قبل Deployment.

### نموذج الحماية الكامل

ينبغي لـ Mature GenAI backend الجمع بين:

```text
Type annotations
    ↓
التحليل الساكن
    ↓
تحقق Pydantic وقت التشغيل
    ↓
معالجة صريحة للأخطاء
    ↓
اختبارات آلية
    ↓
فحوص Deployment
```

كل Layer تلتقط Class مختلفة من المشكلات.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Python type annotations تفرض Types تلقائيًا وقت التشغيل.

### لماذا هذا خاطئ؟

تظل Python dynamically typed. تصف Type annotations بصورة أساسية التوقعات التي تستطيع Static analysis tools وEditors وFastAPI والمكتبات الداعمة استخدامها.

### المفهوم الخاطئ 2

> إذا نجح mypy، فكل API data الواردة صالحة.

### لماذا هذا خاطئ؟

يفحص Static type checking الـ Code الخاص بك. أما External HTTP data فتصل وقت التشغيل ولا تزال تحتاج إلى Validation.

### المفهوم الخاطئ 3

> Dataclass تمنح تلقائيًا Runtime validation نفسها التي يوفرها Pydantic model.

### لماذا هذا خاطئ؟

تعد Standard dataclasses ممتازة لتنظيم Typed data، لكنها لا توفر بصورة Native مجموعة Parsing وValidation وFiltering وSerialization الكاملة الموصوفة لـ Pydantic.

### المفهوم الخاطئ 4

> `float` كافية لتمثيل Model temperature صالحة.

### لماذا هذا خاطئ؟

يقول Type ما نوع Value. أما Field constraint فتعبر عن Numeric range التي تقبلها Application.

### المفهوم الخاطئ 5

> ينبغي تنفيذ Validation بعد Model inference.

### لماذا هذا خاطئ؟

ينبغي رفض Requests غير الصالحة قبل Model work المكلفة متى أمكن.

### المفهوم الخاطئ 6

> Validation الخاصة بـ Field واحدة تستطيع التعبير عن كل Business rule.

### لماذا هذا خاطئ؟

تعتمد بعض Requirements على Combinations من Fields، مثل دعم Model معين لـ Inference-step range مختلفة عن Model آخر.

### المفهوم الخاطئ 7

> Environment variables آمنة لمجرد أنها خارج Source code.

### لماذا هذا خاطئ؟

يمكن أن تكون مفقودة أوMalformed أيضًا. توفر Pydantic Settings Typed validation boundary للـ Configuration.

### المفهوم الخاطئ 8

> Response schemas تساعد Documentation فقط.

### لماذا هذا خاطئ؟

تجعل أيضًا Return contracts صريحة، وتدعم Serialization، ويمكنها كشف تغيّرات غير متوقعة في Response shape.

### المفهوم الخاطئ 9

> Type safety تلغي الحاجة إلى Tests.

### لماذا هذا خاطئ؟

تلتقط Types مشكلات Compatibility؛ بينما تتحقق Tests من Behavior الفعلي وBusiness rules. تحل كل منهما مشكلات متداخلة لكنها مختلفة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| النوع (Type) | Category تصف نوع Value التي يمثلها Variable أوField |
| أمان الأنواع (Type safety) | ممارسة الحفاظ على توافق Values مع التوقعات المعلنة |
| الأنواع الديناميكية (Dynamic typing) | Runtime typing model لا يُطلب فيه من Variables امتلاك Types معلنة وثابتة |
| التحليل الساكن للأنواع (Static type analysis) | فحص توافق Types المعلنة دون تنفيذ كل Code path |
| تعريف النوع (Type annotation) | Python syntax يصرّح بـ Type متوقعة |
| اتحاد الأنواع (Union) | Type تسمح بأكثر من Alternative مثل `str | None` |
| القيم الحرفية المحددة (Literal) | Type مقيّدة بمجموعة محددة مسبقًا من Literal values |
| الاسم المستعار للنوع (Type alias) | اسم قابل لإعادة الاستخدام لـ Type expression أخرى |
| النوع المرفق ببيانات وصفية (Annotated) | Type wrapper يرفق Metadata بـ Type |
| فئة البيانات (Dataclass) | Python data-centric class مع Boilerplate مولّدة تلقائيًا للـ Structured fields |
| مكتبة Pydantic | مكتبة Python لـ Data validation وSerialization مدفوعة بـ Type annotations |
| الفئة الأساسية BaseModel | Pydantic base class المستخدمة لتعريف Validated data models |
| المخطط (Schema) | بنية رسمية تحدد Data fields وTypes المتوقعة |
| قيد الحقل (Field constraint) | Rule مثل Minimum length أوAllowed numeric range |
| أداة التحقق (Validator) | Function أوModel logic تتحقق من Data بما يتجاوز Basic type compatibility |
| أداة التحقق من Field واحدة (Field validator) | Validation تركز على Field واحدة |
| أداة التحقق من Model (Model validator) | Validation تستطيع reasoning على عدة Fields معًا |
| الحقل المحسوب (Computed field) | Output field مشتقة من Model values أخرى |
| التسلسل (Serialization) | تحويل Model data إلى Structures قابلة للنقل مثل Dictionaries أوJSON |
| فك التسلسل والتحليل (Deserialization/parsing) | تحويل External representation إلى Application data structures |
| دالة `model_dump()` | تصدير بأسلوب Pydantic إلى Python data |
| دالة `model_dump_json()` | تصدير بأسلوب Pydantic إلى JSON |
| الفئة BaseSettings | Pydantic Settings base class المستخدمة لقراءة Application configuration |
| متغير Environment | External key/value configuration يتم توفيرها إلى Application قيد التشغيل |
| معيار OpenAPI | Machine-readable API description تستطيع FastAPI اشتقاقها من Typed schemas |
| التحقق وقت التشغيل (Runtime validation) | فحص Values الفعلية أثناء تشغيل Application |
| عقد البيانات (Data contract) | اتفاق صريح حول Shape وType وConstraints الخاصة بالبيانات المتبادلة |
