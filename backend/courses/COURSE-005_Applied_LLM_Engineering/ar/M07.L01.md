## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- شرح لماذا يحتاج تطبيق LLM مفيد عادةً إلى أكثر من Model و Prompt فقط.
- وصف أدوار **model I/O و chains و memory و agents و tools**.
- شرح الفكرة وراء **Quantization** والمقايضة بين Memory والدقة.
- شرح لماذا قد تفشل chat/instruction models إذا لم يُستخدم Prompt template المتوقع منها.
- بناء نموذج ذهني لـ **single chain**: Prompt template → LLM.
- شرح لماذا تكون Prompt variables القابلة لإعادة الاستخدام أفضل من كتابة Prompts كاملة بصورة ثابتة كل مرة.
- تقسيم workflow معقد إلى **sequential chains** ذات intermediate outputs مسماة.
- شرح لماذا يكون LLM المجرد فعليًا stateless بين الاستدعاءات المنفصلة ما لم يتم تمرير History إليه.
- مقارنة **conversation buffer و windowed buffer و conversation summary memory**.
- شرح المقايضات المتعلقة بـ tokens والسرعة والاحتفاظ بالمعلومات بين استراتيجيات Memory المختلفة.
- تعريف **agent** بوصفه نظامًا يساعد فيه LLM على تحديد Actions/Tools التي ينبغي استخدامها وترتيبها.
- شرح كيف توسع external tools قدرات LLM إلى ما هو أبعد من text generation.
- شرح دورة **ReAct** في الفصل: planning/thought ثم action ثم observation.
- وصف كيفية دمج search tool و calculator داخل tool-using agent.
- شرح لماذا تؤدي زيادة autonomy أيضًا إلى زيادة الحاجة إلى validation و observability والإشراف البشري.
- التمييز بين deterministic chains وبين agentic action selection.

## 3. تقليل الدقة لتصغير Model باستخدام Quantization

قبل استخدام framework، يحمّل الفصل Phi-3 بصيغة GGUF ويقدّم مفهوم **Quantization**.

يحتوي Model على أعداد هائلة من numerical parameters.

ويمكن تخزين هذه parameters بدرجات مختلفة من numerical precision.

من الناحية المفاهيمية:

```text
عدد bits أكبر لكل parameter
→ تمثيل أكثر دقة
→ Memory أكبر

عدد bits أقل لكل parameter
→ تمثيل أقل دقة
→ Memory أقل
```

يستخدم الفصل تشبيه الوقت.

إذا سألك شخص عن الوقت، فقد تقول:

```text
14:16
```

بدلًا من:

```text
14:16:12.384
```

يفقد التمثيل الأقصر بعض الدقة، لكنه غالبًا يحتفظ بالمعلومة المهمة.

تطبق Quantization فكرة مشابهة على Model parameters.

[[IMAGE_NEEDED: Quantization intuition | Show the same numerical value represented with high precision and reduced precision, followed by a large model shrinking in memory footprint | Learner should understand quantization as reduced parameter precision rather than deleting entire model layers]]

### لماذا نستخدم Quantization؟

تشمل الفوائد المحتملة:

- متطلبات VRAM أقل،
- متطلبات RAM أقل،
- local inference أسرع أو أكثر عملية،
- إمكانية تشغيل Models أكبر على hardware محدود.

أما التكلفة المحتملة فهي:

- فقدان بعض numerical precision،
- احتمال انخفاض الجودة.

القاعدة العملية التي يذكرها الفصل هي أن Quantization شديدة الانخفاض في عدد bits قد تضر الأداء بدرجة تجعل Model أصغر بدقة أفضل خيارًا أنسب.

### تفصيل مهم من المصدر

يناقش المصدر عدة quantized variants، بينما يستخدم مثال التنزيل العملي ملف GGUF من نوع FP16.

والدرس القابل للتعميم هو المقايضة بين format/precision، وليس حفظ اسم ذلك الملف تحديدًا.

## 8. Chain ليست مجرد Prompt string طويلة

Prompt هو content.

أما chain فهي **workflow connection**.

على سبيل المثال:

```text
متغير (variable)
→ Prompt template
→ LLM
```

أو لاحقًا:

```text
المدخل (input)
→ سلسلة A (chain A)
→ سلسلة B (chain B)
→ سلسلة C (chain C)
```

ولذلك يمكن لـ chain حمل:

- المدخلات (inputs)،
- المخرجات (outputs)،
- القيم الوسيطة (intermediate values)،
- Memory،
- الأدوات (tools)،
- سلاسل أخرى (other chains).

وهذا يجعل التفكير في application أسهل مقارنةً بـ Prompt عملاق واحد يحمل كل المسؤوليات.

## 9. تقسيم مهمة صعبة إلى مهام أصغر باستخدام Sequential chains

افترض أنك تريد من LLM إنشاء:

```text
عنوان (title)
الشخصية الرئيسية (main character)
قصة (story)
```

انطلاقًا من summary قصيرة واحدة.

يمكنك طلب كل شيء في Prompt واحد.

لكن الفصل يقسم workflow بدلًا من ذلك:

```text
Summary
 ↓
توليد Title
 ↓
Title + Summary
 ↓
توليد Character
 ↓
Summary + Title + Character
 ↓
توليد Story
```

- الاستبدال،
- validation،
- فحص intermediate outputs.

## 13. لماذا لا يتذكر LLM تلقائيًا الاستدعاء السابق؟

يوضح الفصل مفاجأة شائعة.



## 17. ضغط السجل القديم بدلًا من حذفه باستخدام Conversation summary

تقوم الاستراتيجية الثالثة بتلخيص المحادثة.

بدلًا من:

```text
كل الرسائل الأصلية (all original messages)
```

يستقبل Model:

```text
ملخصًا موجزًا لما حدث (a concise summary of what happened)
```

ويتم تحديث Summary باستمرار مع وصول turns جديدة.

من الناحية المفاهيمية:

```text
Summary قديم
+
أسطر المحادثة الجديدة
      ↓
Summarizer LLM
      ↓
Summary محدث
      ↓
Prompt الخاص بـ Main LLM
```

[[IMAGE_NEEDED: Conversation summary memory | Show raw chat turns going into a summarizer LLM, producing a compact running summary that is inserted into the main assistant prompt | Learner should see summary memory as compression rather than simple deletion]]

### لماذا يساعد ذلك؟

يمكن تمثيل محادثة طويلة باستخدام tokens أقل.

لكن Compression لها نتائج.

قد يحتفظ Summary بـ:

```text
الحقائق الرئيسية (main facts)
الأهداف الرئيسية (main goals)
الأحداث المهمة (important events)
```

بينما قد يفقد:

```text
الصياغة الدقيقة (exact wording)
التفاصيل الصغيرة (minor details)
أسئلة سابقة محددة (specific earlier questions)
```

يوضح المصدر صراحةً أن Model قد يضطر إلى استنتاج تفاصيل لم تعد محفوظة حرفيًا.

## 18. تتطلب Summary memory حوسبة إضافية

لا يظهر Summary تلقائيًا.

يستخدم الفصل Model call إضافيًا لتحديثه.

لكل conversational interaction، قد يصبح لديك الآن:

```text
1. استدعاء الاستجابة الرئيسي (Main response call)
2. استدعاء التلخيص/التحديث
```

وهذا يعني:

```text
Prompt tokens أقل
لكن
Model calls أكثر
```

وهذه مقايضة نظامية كلاسيكية.

### Memory ليست مشكلة Context length فقط

يوازن اختيار Memory architecture بين:

- استخدام tokens (token usage)،
- Latency،
- تكلفة compute/API،
- الاحتفاظ بالمعلومات (information retention)،
- جودة retrieval،
- تعقيد implementation.

وتعتمد “أفضل” Memory على application.

## 19. مقارنة أنواع Memory الثلاثة

مقارنة بسيطة:

| الاستراتيجية | هل تحتفظ بالنص القديم الدقيق؟ | نمو Prompt | Model calls إضافية | الخطر الرئيسي |
|---|---:|---:|---:|---|
| Full buffer | نعم، ما دام Context يتسع | مرتفع | لا | يصبح Context كبيرًا جدًا |
| Windowed buffer | فقط turns الحديثة | محدود | لا | تختفي الحقائق القديمة |
| Summary memory | نسخة مضغوطة | أقل | نعم | قد يفقد Summary تفاصيل |

### طريقة عملية للاختيار

استخدم Full buffer عندما:

```text
تكون المحادثة قصيرة
تكون الصياغة الدقيقة مهمة
يكون Context budget كافيًا
```

استخدم recent window عندما:

```text
يكون Recent context هو الأهم
يمكن نسيان turns الأقدم
```

استخدم Summarization عندما:

```text
يمكن أن تصبح المحادثة طويلة
تريد استمرارية عامة
تكون الصياغة التاريخية الدقيقة أقل أهمية
```

يمكن للأنظمة الحقيقية أيضًا دمج استراتيجيات متعددة.

والدرس الأعمق في الفصل هو المقايضة بين:

```text
السرعة (speed)
استهلاك Memory (memory usage)
الدقة / الاحتفاظ بالمعلومات
```

## 20. تنفذ Chains مسارًا مصممًا، بينما يمكن لـ Agents اختيار المسار

## 21. توسيع قدرات Model باستخدام Tools

يقوم language model أساسًا بتوليد tokens.

ولا يستطيع تلقائيًا:

- الاستعلام من live web،
- إجراء الحسابات باستخدام calculator موثوقة،
- إرسال email،
- الاستعلام من database،
- استدعاء weather API.

**Tool** هي capability خارجية يستطيع النظام استدعاءها.

تشمل أمثلة الفصل:

```text
البحث على الويب (web search)
الآلة الحاسبة (calculator)
```

إذا احتاج Model إلى current price، فيمكن لـ search tool توفير البيانات.

وإذا احتاج إلى arithmetic، فيمكن لـ calculator إنتاج نتيجة دقيقة.

تصبح agent architecture:

```text
سؤال المستخدم (User question)
      ↓
Agent / LLM
      ↓
اختيار Tool
      ↓
تنفيذ Tool
      ↓
Observation / Result
      ↓
يواصل LLM
```

[[IMAGE_NEEDED: LLM tool use | Show an agent receiving a user question and selecting among a web search tool, calculator, and direct answer path, then receiving tool results back | Learner should see tools as external capabilities selected by orchestration logic]]

### لا تجعل Tools الإجابات صحيحة تلقائيًا

لا يزال بإمكان Agent أن:

- يختار Tool خاطئة،
- يصيغ Tool query سيئة،
- يسيء قراءة النتيجة،
- يدمج القيم بصورة غير صحيحة،
- يثق في مصدر سيئ.

يزيد Tool access القدرة، لكنه لا يضمن correctness.

## 22. ربط Planning و Action و Observation باستخدام ReAct

يعرض الفصل ReAct باعتباره framework يجمع reasoning/planning behavior مع external actions.

والحلقة المتكررة فيه هي:

```text
Thought / Plan
      ↓
Action
      ↓
Observation
      ↓
الخطة/Action التالية
      ↓
...
      ↓
Final answer
```

في هذا الدرس، تعامل مع حقل “Thought” الظاهر في الفصل باعتباره **planning trace يستخدمه Agent prompt**، وليس بوصفه وصولًا مضمونًا إلى hidden internal reasoning الخاص بـ Model.

الفكرة النظامية هي المهمة:

> يتناوب Agent بين تحديد ما يجب فعله، وتنفيذ Action عبر Tool، واستخدام النتيجة المعادة لتحديد الخطوة التالية.

## 28. Autonomy سلاح ذو حدين

يحذر الفصل صراحةً من أنه بمجرد أن يختار Agent الـ Actions بنفسه، لن يعود الإنسان يشرف يدويًا على كل intermediate step.

وهذا يخلق مخاطر.

قد يقوم النظام بـ:

- البحث في source سيئ،
- استخدام بيانات stale،
- اختيار Tool غير صحيحة،
- الفشل في التحقق من units،
- إساءة تفسير Observation،
- إنتاج Final answer واثقة لكنها غير صحيحة.

يقترح الفصل تحسينات للموثوقية مثل إرجاع source URL أو التحقق من intermediate outputs.

الدرس العام هو:

> كلما زادت autonomy في النظام، أصبحت validation و oversight أكثر أهمية، لا أقل.

## 29. جمع Architecture patterns في الفصل

قدم الفصل الآن عدة system patterns قابلة لإعادة الاستخدام.

### النمط A — Model + Prompt template

```text
متغيرات الإدخال (input variables)
→ prompt
→ LLM
```

استخدمه عندما:

```text
تكفي خطوة Generation واحدة
```

### النمط B — Sequential chain

```text
المدخل (input)
→ LLM الخطوة A (LLM step A)
→ LLM الخطوة B (LLM step B)
→ LLM الخطوة C (LLM step C)
```

استخدمه عندما:

```text
يكون ترتيب Workflow معروفًا
وتنقسم المهمة طبيعيًا
```

### النمط C — Chain + Memory

```text
المدخل الحالي (current input)
+
السجل ذو الصلة (relevant history)
→ prompt
→ LLM
```

استخدمه عندما:

```text
تعتمد turns اللاحقة على المحادثة السابقة
```

### النمط D — Agent + Tools

```text
الهدف (goal)
→ يقرر الـ Agent (agent decides)
→ الأداة (tool)
→ الملاحظة (observation)
→ يقرر الـ Agent (agent decides)
→ ...
```

استخدمه عندما:

```text
يصعب تثبيت Action sequence الصحيحة مسبقًا
```

### يمكن دمج هذه الأنماط

على سبيل المثال:

```text
Agent
├── الذاكرة (memory)
├── قالب Prompt (prompt template)
├── أداة البحث (search tool)
├── أداة الحاسبة (calculator tool)
└── سلسلة التحقق (validation chain)
```

وهذه هي الرسالة الأعمق في الفصل:

> تصبح تطبيقات LLM قوية من خلال composition.

## 31. مقايضات Engineering التي يجب تذكرها

### يمكن لـ Context الأكبر تحسين الاستمرارية

لكن:

```text
Context أكبر
→ Tokens أكثر
→ Compute أكثر
```

### توفر Summaries عددًا من Tokens

لكن:

```text
Compression
→ احتمال فقدان التفاصيل
```

### تزيد مراحل Chain الإضافية من Modularity

لكن:

```text
Calls أكثر
→ Latency أكبر
→ Failure points أكثر
```

### تزيد Tools من Capability

لكن:

```text
Tool errors + Selection errors
→ Failure modes جديدة
```

### تزيد Agents من Flexibility

لكن:

```text
Autonomy أكبر
→ Predictability أصعب
→ حاجة أقوى إلى Monitoring
```

لا توجد capability مجانية.

كل تحسين يقدم مقايضة نظامية.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> يجعل LangChain الـ LLM الأساسي أكثر ذكاءً.

### لماذا هذا خطأ؟

ينظم framework الـ prompts و memory و tools و workflows. ولا يزيد مباشرةً parameters أو knowledge الخاصة بـ pretrained model.

---

### المفهوم الخاطئ 2

> تعني Quantization حذف layers غير المهمة من Model.

### لماذا هذا خطأ؟

يقدم الفصل Quantization باعتبارها تقليل numerical precision لتمثيلات parameters.

---

### المفهوم الخاطئ 3

> إذا تم تحميل Model بنجاح، فلن يعود Prompt format مهمًا.

### لماذا هذا خطأ؟

قد تعتمد instruction/chat models بدرجة كبيرة على template الذي استُخدم أثناء training.

---

### المفهوم الخاطئ 4

> تعني Memory أن LLM يغير weights الخاصة به بصورة دائمة بعد كل محادثة.

### لماذا هذا خطأ؟

تخزن تقنيات Memory في الفصل conversation السابقة خارجيًا وتدخل نسخة من ذلك History في Prompts اللاحقة.

---

### المفهوم الخاطئ 5

> Full buffer memory هي الأفضل دائمًا لأنها لا تفقد أي معلومات.

### لماذا هذا خطأ؟

يمكنها استهلاك أجزاء متزايدة من Context وزيادة inference cost.

---

### المفهوم الخاطئ 6

> تحفظ Summary memory كل تفصيل أصلي.

### لماذا هذا خطأ؟

Summarization هي lossy compression. وقد يتم حذف تفاصيل مهمة أو إعادة صياغتها.

---

### المفهوم الخاطئ 7

> Chain و Agent هما الشيء نفسه.

### لماذا هذا خطأ؟

عادةً ما تتبع chain تسلسلًا يصممه developer، بينما يختار agent ديناميكيًا بين actions/tools.

---

### المفهوم الخاطئ 8

> منح Agent أداة Calculator يضمن إجابات رقمية صحيحة.

### لماذا هذا خطأ؟

لا يزال Agent بحاجة إلى اختيار Tool، وإعطائها input الصحيح، وتفسير observation، ودمج النتائج بصورة صحيحة.

---

### المفهوم الخاطئ 9

> تحتاج Agents الأكثر استقلالًا إلى Monitoring أقل.

### لماذا هذا خطأ؟

تزيد autonomy عدد intermediate decisions التي يمكن أن تفشل. ولذلك تصبح logging و validation و permissions و review أكثر أهمية.

**تطبيق LLM المفيد هو نظام، وليس Model فقط. تنشئ Prompt templates واجهات قابلة لإعادة الاستخدام، وتربط chains مراحل deterministic، وتعيد memory إدخال أجزاء مختارة من history في calls المستقبلية، وتوفر tools قدرات لا يمتلكها Model بمفرده، وتسمح agents لـ Model بالمشاركة في اختيار Actions. كل capability إضافية تقدم مقايضات جديدة في tokens و latency وفقد المعلومات والتكلفة و observability و reliability، ولذلك تحتاج الأنظمة الأقوى إلى orchestration و validation أقوى.**
