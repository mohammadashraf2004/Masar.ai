## 1. لماذا تكون مخاطر Agent security أعلى؟

قد يعيد Static chatbot إجابة خاطئة.

أما Agent فقد:

```text
تعدّل Database (modify a database)
ترسل Email (send an email)
تصدر Refund (issue a refund)
تجدول Meeting (schedule a meeting)
تطلق Payment (trigger a payment)
تحذف Data (delete data)
```

يستخدم المصدر تشبيهًا مفيدًا:

```text
Traditional app = مكتبة (library)
Agentic app = مساعد يحمل مفاتيح المكتب (assistant with the keys to the office)
```

لذلك قد تكون تكلفة Failure:

```text
Action خاطئة (wrong action)
```

وليس فقط:

```text
Text خاطئ (wrong text)
```

### المبدأ الأساسي (Core Principle)

> تحوّل Autonomy أخطاء Model إلى Operational risk.

## 2. Security هي Stack وليست Toggle

ينظم المصدر Security في ثماني طبقات:

```text
1. أمان Infrastructure (Infrastructure Security)
2. أمان Network (Network Security)
3. أمان Data (Data Security)
4. أمان AI Application (AI Application Security)
5. أمان AI Agent (AI Agent Security)
6. إدارة Identity و Access (Identity & Access Management)
7. Logging و Monitoring
8. Governance و Risk و Compliance
```

تحمي كل طبقة الطبقة التالية.

إذا فشلت طبقة، فقد تحتوي طبقة أخرى الضرر.

وهذا يسمى:

```text
الدفاع متعدد الطبقات (Defense in Depth)
```

## 3. الطبقة 1 — أمان Infrastructure (Infrastructure Security)

تحمي Infrastructure security الـ Physical و Virtual compute التي تعمل عليها Agents.

يقسم المصدر هذه الطبقة إلى:

```text
التقوية الفيزيائية (Physical Hardening)
سلامة Hardware (Hardware Integrity)
عزل Compute (Compute Isolation)
```

إذا جرى Compromise للـ Host machine، فلن تستطيع Prompt-level controls إنقاذ System.

---

## 4. التقوية الفيزيائية (Physical Hardening)

تشمل Physical security ضوابط مثل:

- حواجز المحيط،
- دخول مضبوط،
- Surveillance،
- Security personnel،
- Mantraps،
- وصول Biometric (Biometric access).

بالنسبة إلى Cloud users، تنتقل مسؤولية كبيرة من ذلك إلى Cloud provider.

الدرس المهم هو:

> Cloud security تتضمن Physical trust assumptions، لا Software فقط.

---

## 5. سلامة Hardware (Hardware Integrity)

يسلط المصدر الضوء على عدة Mechanisms.

### وحدة TPM

توفر Trusted Platform Module جذر ثقة Hardware.

يمكنها المساعدة في التحقق من أن System أقلعت من دون Unauthorized tampering.

### وحدة HSM

صُممت Hardware Security Module لعمليات Cryptographic عالية القيمة وتخزين Keys.

تشمل Use cases حماية Keys المستخدمة في:

```text
هوية Agent (agent identity)
التوقيع (signing)
التشفير (encryption)
```

### SBOM ورؤية Supply chain

تتتبع Software Bill of Materials مكونات Software و Dependencies.

يساعد ذلك على اكتشاف Supply-chain components المخترقة أو الضعيفة.

---

## 6. عزل Compute (Compute Isolation)

لا تحمي Encryption at rest و Encryption in transit الـ Data أثناء معالجتها فعليًا.

يناقش المصدر:

### الحوسبة السرية (Confidential Computing)

تحمي Trusted Execution Environments الـ Data أثناء الاستخدام.

### الأنظمة المعزولة عن الشبكة (Air-gapped Systems)

في Environments شديدة الحساسية، قد تعمل Systems من دون اتصال Public Internet.

وقد يتطلب ذلك:

```text
Models محلية (local models)
Tools محلية (local tools)
Infrastructure محلية (local infrastructure)
```

### المبدأ (Principle)

> قد يحتاج Reasoning الخاص بـ Agent الحساسة إلى الحماية حتى من Infrastructure operators.

---

## 7. الطبقة 2 — أمان Network (Network Security)

إذا كانت Infrastructure هي المبنى، فإن Network security هي نظام الممرات.

تنقل Agent networks:

- Prompts،
- Retrieved data،
- A2A traffic،
- MCP traffic،
- External API calls،
- Responses متدفقة (Streaming responses).

يركز المصدر على:

```text
العزل (Isolation)
التحكم في Traffic (Traffic Control)
الوصول الخاص إلى Model (Private Model Access)
الربط البيني (Interconnectivity)
```

---

## 8. عزل VPC

توفر Virtual Private Cloud شبكة Private محددة بالـ Software.

يمكن لـ Agents استخدام Private IPs و Private routing بدل أن تكون مكشوفة مباشرةً للـ Public Internet.

### النموذج الذهني (Mental Model)

```text
حساب Cloud عام (public cloud account)
    !=
تعرض Network للعامة (public network exposure)
```

قد يظل Cloud deployment مصممًا بصورة Private إذا أُعد بصورة صحيحة.

---

## 9. التحكم في Ingress

يحدد Ingress:

```text
من يُسمح له بالوصول إلى Agent (who may reach the agent)
```

أمثلة:

- Internal dashboard فقط،
- Approved gateway،
- Known source ranges،
- Reverse proxy موثقة (Authenticated reverse proxy).

ليس من الضروري عادةً كشف كل Agent endpoint للعامة.

---

## 10. Egress مضبوط

غالبًا ما تحتاج Autonomous agents إلى External access.

أمثلة:

- Public APIs،
- Package repositories،
- خدمات SaaS خارجية.

يصف المصدر NAT بوصفها طريقة للسماح لـ Private agents بتنفيذ Outbound requests من دون كشف Private addresses الخاصة بها مباشرة.

لكن NAT وحدها ليست كافية.

---

## 11. ترشيح Egress (Egress Filtering)

تتحكم Egress filtering في:

```text
إلى أين يُسمح لـ Agent بإرسال Data (where the agent is allowed to send data)
```

وهذا مهم لأن Compromised agent قد تقوم Exfiltration للمعلومات.

مثال:

```text
HR Agent
مسموح (allowed):
Payroll API

غير مسموح (not allowed):
Random external host
```

### المبدأ (Principle)

> ينطبق Least privilege على Network destinations أيضًا.

---

## 12. الوصول الخاص إلى Model (Private Model Access)

يصف المصدر استراتيجيتين High-level.

### وصول Managed خاص أو VPC-native (VPC-native/private managed access)

أبقِ Model traffic على Provider/private networking.

### استضافة On-premise/Open-weight

للـ Strict sovereignty/privacy requirements، استضف Models محليًا.

Trade-off يكون بين:

```text
القدرة
التعقيد التشغيلي
الخصوصية
المتطلبات التنظيمية
```

---

## 13. الربط البيني الخاص (Private Interconnectivity)

قد تمتد Distributed enterprises عبر:

```text
عدة VPCs (multiple VPCs)
عدة Clouds (multiple clouds)
On-premise systems
```

يناقش المصدر:

- VPC peering،
- روابط مخصصة بين Clouds وأنظمة On-premise.

الفكرة الدائمة هي:

> Sensitive east-west traffic لا ينبغي أن يعبر Public Internet تلقائيًا.

---

## 14. الطبقة 3 — أمان Data (Data Security)

ينظم المصدر Data security حول:

```text
التشفير (Encryption)
التنقية (Sanitization)
الحوكمة (Governance)
```

تتضمن Agent data:

- Prompts،
- Memories،
- Tool results،
- Embeddings،
- Logs،
- Files،
- محتوى Vector store.

---

## 15. التشفير أثناء النقل (Encryption in Transit)

ينبغي أن تستخدم Traffic بروتوكول TLS.

بالنسبة إلى Internal service-to-service communication، يناقش المصدر mTLS.

مع mTLS:

```text
Server يتحقق من هوية Client (server authenticates client)
Client يتحقق من هوية Server (client authenticates server)
```

وهذا يضيف Mutual identity إلى Encrypted channel.

---

## 16. التشفير أثناء التخزين (Encryption at Rest)

تشمل Stored data:

```text
بيانات SQL
قواعد بيانات المتجهات (vector databases)
السجلات
memory طويلة الأمد
artifacts
```

يناقش المصدر Customer-Managed Encryption Keys بوصفها Option للمؤسسات التي تحتاج تحكمًا أقوى في Encryption keys.

النقطة الأساسية ليست Product name.

بل Ownership لدورة حياة Key و Revocation.

---

## 17. Sanitization قبل Model أو Memory

بمجرد دخول Sensitive data إلى:

```text
سياق النموذج
مخزن المتجهات (vector store)
memory طويلة الأمد
```

تصبح إزالتها صعبة.

يوصي المصدر بـ DLP-style pipelines لاكتشاف وحجب معلومات مثل:

- PII،
- PHI،
- بيانات الدفع (Payment data).

### المبدأ (Principle)

> أرخص Sensitive datum في الحماية هي التي لم تُدخلها أصلًا.

---

## 18. سلامة Vector store (Vector-store Hygiene)

لا ينبغي التعامل مع Embeddings كأنها Anonymous بطريقة سحرية.

يحذر المصدر من أن Embeddings قد تظل تحمل Reconstruction/Privacy risks.

لذلك:

```text
Vector store — مخزن Embeddings و Content المسترجع
```

ينبغي حمايتها بطريقة مشابهة لمخازن Sensitive data الأخرى.

طبّق:

- Access control،
- Encryption،
- Retention،
- Lineage،
- سياسة الحذف (Deletion policy).

---

## 19. نسب Data وتتبع أصلها (Data Lineage)

بالنسبة إلى High-stakes decisions، تحتاج إلى Paper trail.

إذا اتخذت Agent قرارًا بناءً على Retrieved information، فينبغي أن تستطيع الإجابة عن:

```text
أي Document؟ (which document?)
أي Database row؟ (which database row?)
أي Source؟ (which source?)
أي Version؟ (which version?)
```

تدعم Lineage:

- Audits،
- Grounding،
- Incident review،
- التفسير (Explanation).

---

## 20. Retention و Deletion

لا تحتفظ بكل Interaction إلى الأبد.

ينبغي أن تحدد Retention policy:

```text
ما الذي يُخزن؟ (what is stored)
إلى متى؟ (how long)
لماذا؟ (why)
متى يُحذف؟ (when it is deleted)
```

أمثلة:

```text
memory جلسة مؤقتة
سجلات ضمان الجودة
تفضيلات طويلة الأمد
سجلات منظَّمة بالتشريعات
```

قد تصبح Long-term memory Liability إذا تراكمت Data قديمة أو Sensitive إلى ما لا نهاية.

## 21. الطبقة 4 — أمان AI Application (AI Application Security)

تحمي هذه الطبقة Application logic المحيطة بـ Model.

قد لا يهاجم Attacker صياغة Server.

بل قد يهاجم تفسير Model للغة.

وهذا ينشئ Semantic security threats.

---

## 22. حقن Prompt (Prompt Injection)

قد يقدم Malicious user تعليمات تهدف إلى تجاوز Behavior المقصود لـ System.

نمط Example:

```text
"تجاهل التعليمات السابقة..."
```

String المحددة ليست المشكلة كلها.

المشكلة الأعمق هي:

```text
Content غير موثوقة تحاول أن تصبح Control instructions (untrusted content attempting to become control instructions)
```

---

## 23. تجاوز قيود Model (Jailbreaking)

تحاول Jailbreaking تجاوز Model safety behavior.

قد تستخدم:

- Personas،
- Reframing،
- Roleplay،
- تلاعب متعدد الخطوات (Multi-step manipulation).

يعطي المصدر Persona-based attacks كمثال.

الدرس هو:

> لا تعتمد على System prompt واحدة بوصفها Security perimeter بالكامل.

---

## 24. كشف المعلومات الحساسة (Sensitive-information Disclosure)

قد تكشف Model أو Application:

- Private context،
- Secrets،
- Previous-session information،
- بيانات مسترجعة حساسة (Sensitive retrieved data).

يمكن أن يحدث ذلك حتى من دون Traditional infrastructure breach.

لذلك يجب أن تتضمن AI application security Explicit leakage prevention.

---

## 25. حواجز Input (Input Guardrails)

تفحص Input guardrails الـ Requests قبل وصولها إلى Model.

قد تشمل Functions:

```text
اكتشاف prompt injection
اكتشاف jailbreak
سياسة المواضيع
اكتشاف PII
فحص البرمجيات الخبيثة/المحتوى
```

يقدم المصدر هذه Guardrails بوصفها Deterministic enforcement layer حول Model.

---

## 26. حواجز Output (Output Guardrails)

تفحص Output guardrails الـ Generated content قبل وصولها إلى User.

قد تشمل Checks:

```text
السمّية
التعليمات غير الآمنة
البيانات الحساسة
انتهاكات السياسة
الإجراءات عالية الخطورة المتوهَّمة
```

لذلك لا تُعتبر Response الخاصة بـ Model موثوقة تلقائيًا لمجرد أنها صادرة من Approved model.

---

## 27. أمان Model و Supply chain

تضيف Self-hosted models مخاوف أخرى.

### أوزان Model (Model Weights)

تعامل معها بوصفها Valuable IP.

طبّق:

- Encryption،
- Access control،
- توزيع مضبوط (Controlled distribution).

### Models وArtifacts من أطراف خارجية (Third-party Models/Artifacts)

تحقق من Provenance وتجنب Untrusted serialized artifacts.

يشدد المصدر على Software/Model supply-chain security.

---

## 28. Observability و Kill switches

قد تعمل Agent workflows لعدة دقائق.

يحتاج System إلى طريقة للتدخل عندما:

```text
Agent تدخل Loop (agent loops)
Cost يتضخم (cost explodes)
Unsafe output تتكرر (unsafe output repeats)
Tool calls تصبح خطرة (tool calls become dangerous)
```

قد تشمل Controls:

```text
تحذير (warning)
Circuit breaker
Kill switch
```

Kill switch هي Last resort، لا First response.

## 29. الطبقة 5 — أمان AI Agent (AI Agent Security)

يركز Agent security على المخاطر الفريدة الناتجة عن:

```text
memory
الأدوات
الاستدلال
التخطيط
الاستقلالية
```

يقسمها المصدر إلى:

```text
أمان Context (Context Security)
أمان Tools (Tool Security)
تقوية Framework (Framework Hardening)
```

---

## 30. عزل Session (Session Isolation)

يجب ألا تتسرب Short-term state الخاصة بـ User A إلى User B.

تشمل المخاطر:

- Global variables،
- Shared cache keys،
- Incorrect session IDs،
- مخازن State مقسمة بصورة غير صحيحة.

### القاعدة (Rule)

> Conversation state هي Data محددة النطاق حسب Tenant/User/Session.

---

## 31. حقن Prompt غير المباشر (Indirect Prompt Injection)

قد لا يكون Attacker هو User.

قد تحتوي Retrieved webpage أو Document على Malicious instructions.

Example من حيث الفكرة:

```text
Research Agent تقرأ Webpage (Research Agent reads webpage)
Webpage تحتوي Hidden instruction (webpage contains hidden instruction)
Agent تتبعها كما لو كانت موثوقة (agent follows it as if trusted)
```

لذلك:

```text
Retrieved content = Data غير موثوقة (untrusted data)
```

وليس:

```text
المحتوى المسترجَع = تعليمة نظام موثوقة
```

استخدم Separation و Scanning و Instruction hierarchy واضحة.

---

## 32. Least privilege للـ Tools

لا تعطِ Agent الـ Master credential.

إذا كانت Agent تحتاج فقط إلى:

```text
قراءة Balance (read balance)
```

فلا تمنحها:

```text
تعديل Balance (modify balance)
حذف Account (delete account)
```

ينبغي أن تكون Permissions:

- Task-specific،
- Minimal،
- Time-bounded عندما يكون ذلك ممكنًا.

---

## 33. Human-in-the-loop للـ High-risk actions

أمثلة:

```text
رد مبلغ لطالب (refund student)
تغيير Grade (change grade)
إرسال Payment (send payment)
حذف Production data (delete production data)
```

يمكن لـ Agent اقتراح Action.

أما Execution فتنتظر Explicit human approval.

يفصل ذلك بين:

```text
صلاحية Reasoning (reasoning authority)
```

و:

```text
صلاحية Final execution (final execution authority)
```

---

## 34. تحقّق من Tool schemas قبل Execution

يمكن لـ LLMs أن تهلوس Arguments.

ينبغي أن تمر Tool call عبر Strict validation قبل Execution.

أمثلة:

- JSON Schema،
- Typed models،
- قوائم سماح للـ Parameters.

يمكن لـ MCP المساعدة في Standardize لـ Tool contracts.

### المبدأ (Principle)

> Model-generated arguments هي Untrusted input.

---

## 35. تقوية Framework (Framework Hardening)

Agent frameworks هي Dependencies.

تعامل معها مثل أي Production software أخرى.

طبّق:

- Vulnerability scanning،
- Patching،
- Dependency pinning،
- مراجعة Security.

لا تفترض أن Agent framework شهيرة آمنة تلقائيًا.

---

## 36. تشغيل Code داخل Sandbox

يجب ألا تعمل Generated code مباشرة على Host.

استخدم:

```text
sandbox مؤقتة
حدود الموارد
بلا شبكة/شبكة محدودة
نظام ملفات مؤقت
التدمير بعد التنفيذ
```

وهذا مهم بصورة خاصة لـ Python/Terminal tools.

## 37. الطبقة 6 — إدارة الهوية والوصول (Identity & Access Management)

تجيب IAM عن سؤالين مختلفين.

### المصادقة (Authentication)

```text
من أنت؟ (Who are you?)
```

### التفويض (Authorization)

```text
ما الذي يُسمح لك بفعله؟ (What are you allowed to do?)
```

لا تعني Valid identity وجود Unlimited permission.

---

## 38. تطور Credentials

يصف المصدر تطورًا على النحو الآتي:

```text
اسم المستخدم/كلمة المرور
→ مفتاح API
→ token وصول قصير الأمد
```

### كلمات المرور (Passwords)

ليست مناسبة للـ Autonomous systems وخطيرة عند Hard-coding.

### مفاتيح API (API Keys)

أفضل للوصول إلى Services، لكنها غالبًا:

- Long-lived،
- واسعة النطاق من حيث Scopes.

### رموز الوصول (Access Tokens)

يمكن أن تكون:

- Short-lived،
- Signed،
- Scoped،
- محدودة لغرض معين.

---

## 39. رموز وصول JWT (JWT Access Tokens)

يستخدم المصدر JWTs كمثال حديث لـ Agent credential.

هناك خاصيتان مهمتان:

### نطاق الصلاحيات (Scope)

ما الذي يُسمح لحامل Token بفعله.

مثال:

```text
read:grades    # قراءة الدرجات
```

وليس:

```text
write:grades    # كتابة الدرجات
```

### انتهاء الصلاحية (Expiration)

المدة التي تظل Token خلالها Valid.

تحد Short-lived credentials من الضرر إذا سُرقت.

---

## 40. بروتوكول OAuth 2.0

توفر OAuth Standardized authorization flows للحصول على Access tokens.

تختلف Exact provider configuration.

يركز المصدر على Patternين عامين:

```text
Authorization Code ثلاثي الأطراف (3-legged)
Client Credentials ثنائي الأطراف (2-legged)
```

---

## 41. 3-legged OAuth — تفويض Human

استخدم هذا عندما تحتاج Agent إلى التصرف نيابةً عن Human.

مثال:

```text
Personal Assistant
تحتاج إلى Calendar access الخاصة بالمستخدم (needs user's Calendar access)
```

Actors:

```text
المستخدم
Agent/التطبيق
Authorization Server / Identity Provider
```

يشارك User في Flow.

---

## 42. 3-legged flow خطوة بخطوة

### إعادة التوجيه (Redirect)

يُرسل User إلى Trusted identity provider.

### المصادقة (Authenticate)

يسجل User الدخول لدى Identity provider.

ولا تستقبل Agent الـ Raw password.

### الموافقة (Consent)

يرى User الـ Requested scopes.

### رمز Authorization (Authorization Code)

ترسل Identity provider Temporary code إلى Approved redirect URI.

### تبادل Token (Token Exchange)

يستبدل Backend الـ Code بـ User access token.

تمثل هذه Token:

```text
Agent تعمل نيابةً عن User (Agent acting on behalf of User)
```

---

## 43. ثلاثة عناصر مهمة في OAuth configuration

### Client ID و Secret

يحددان هوية Application.

لا تكشف Secret أبدًا داخل Browser/Client code.

### عنوان Redirect URI المصرح به

تحدد المكان الذي يمكن لـ Identity provider إعادة Authorization result إليه.

### نطاق الصلاحيات (Scope)s

تحدد Requested permissions.

تطبق Scopes مبدأ Least privilege.

## 44. 2-legged OAuth — هوية Machine

استخدم هذا عندما:

```text
Agent A
تستدعي (calls)
Service/Agent B
```

من دون Human consent step.

Actors:

```text
Agent / Client    # العميل ثم خادم التفويض
Authorization Server
```

يقدم المصدر ذلك بوصفه Establishing:

```text
هوية الـ Agent
هوية غير بشرية (Non-Human Identity)
```

---

## 45. تدفق Client Credentials (Client Credentials Flow)

من حيث الفكرة:

```text
Agent تقدم Client identity (Agent presents client identity)
   ↓
Authorization Server تتحقق (Authorization Server validates)
   ↓
Short-lived access token
   ↓
Agent تستدعي Service (Agent calls service)
```

لا يوجد:

- Browser redirect،
- نافذة Human تفاعلية.

تُعد Permissions عادةً مسبقًا على المستوى Administrative.

---

## 46. 2-legged مقابل 3-legged

| البعد | تدفق 2-legged | تدفق 3-legged |
|---|---|---|
| الاستخدام الرئيسي | اتصال Machine-to-machine | تفويض User (User delegation) |
| وجود Human | لا | نعم |
| سياق Identity | "أنا Agent X" | "أنا Agent X أتصرف نيابةً عن User Y" |
| الصلاحية (Permission) | محددة إداريًا مسبقًا (Admin/Preassigned) | يوافق عليها User (User-consented) |
| نمط Interaction | تنفيذ في الخلفية (Background) | تفاعل مباشر (Interactive) |

يصبح هذا الفرق حاسمًا لاحقًا عندما يجب أن تتدفق Identities عبر Multi-agent chains.

---

## 47. توجد أنماط Identity متقدمة، لكن أتقن Core أولًا

يذكر المصدر Patterns أكثر تقدمًا مثل:

- Token exchange،
- Verifiable credentials،
- أنماط Identity لمدفوعات Agents.

لكن 2-legged و 3-legged OAuth تغطيان معظم السيناريوهات الشائعة ضمن إطار الفصل.

التحدي التالي ليس الحصول على Token واحدة.

بل Propagation للهوية الصحيحة عبر عدة Agents.

## 51. تسجيل Audit الآمن (Safe Audit Logging)

- Sensitive fields،
- تنقية Data (Sanitization).

### بعد استدعاء Agent (After Agent Call)

تحقق من:

- Final logging،
- Cost،
- تنظيف State/Resources.

## 75. فجوة Identity في Multi-agent systems

لنفترض:

```text
Alice    # تمرير هوية المستخدم عبر سلسلة الـ agents
→ Tutor Agent
→ Registrar Agent
→ Database Agent
```

إذا كانت Downstream services ترى فقط:

```text
Tutor Agent — Agent الوسيطة فقط
```

فقد تضيع Permissions الخاصة بـ Alice.

وقد تتصرف Tutor بالخطأ كأنها Super-user.

```text

```

## 76. Approach الأولى — تدفق On-Behalf-Of

Approach الأولى هي Chained token exchange.

من حيث الفكرة:

```text
Alice تعطي Token إلى Tutor (Alice gives token to Tutor)
Tutor تسأل IdP: (Tutor asks IdP:)
"أعطني Token لـ Registrar ("Give me a token for Registrar)
نيابةً عن Alice." (on behalf of Alice.")
```

تستقبل Registrar Token مقيدة بالـ Audience الخاصة بها وما تزال مرتبطة بـ Alice.

الفوائد:

```text
Least privilege
Permissions خاصة بالمستخدم (user-specific permissions)
Boundaries بأسلوب Zero-trust (zero-trust style boundaries)
```

لكن هذه Architecture تقدم مسؤولية خطرة.

## 80. خطر Custom vault

إذا خزنت Authority عددًا كبيرًا من Refresh tokens، فإنها تصبح Infrastructure شديدة الحساسية.

إذا جرى Compromise لها:

```text
هويات كثيرة (many identities)
Providers كثيرة (many providers)
Permissions طويلة العمر كثيرة (many long-lived permissions)
```

قد تُكشف.

لذلك فإن بناء Identity provider/Token vault مخصص مهمة Engineering عالية المخاطر.

وهذا يحفز استخدام Standards-based broker.

---

## 81. Approach الثالثة — RFC 8693 Token Exchange

يقدم المصدر Broker architecture ناضجة تعتمد على Standardized Token Exchange.

تصبح Authority Identity broker بدل Custom password manager.

وهذا مفيد خصوصًا عندما يمتلك User واحد Identities عبر:

```text
Google
GitHub
Providers أخرى (other providers)
```

يمكن لـ Broker ربط Provider identities هذه بـ Logical user context واحدة.

---

## 82. التفويض التدريجي (Incremental Authorization)

لنفترض أن Alice ربطت Google بالفعل.

لاحقًا تحتاج Agent إلى GitHub.

يمكن لـ Workflow:

```text
إيقاف Task مؤقتًا (pause task)
عرض "Connect GitHub" (show "Connect GitHub")
إعادة توجيه Alice إلى GitHub authorization (redirect Alice to GitHub authorization)
استقبال Provider token (receive provider token)
ربطها بـ Session الخاصة بـ Alice (link it to Alice's session)
استئناف Original task (resume original task)
```

لا يُطلب من User Authorization لكل Provider محتمل مقدمًا.

وهذا Just-in-time permission expansion.

---

## 83. Multi-provider identity كـ Keyring

نموذج ذهني مفيد هو:

```text
Session الخاصة بـ Alice (Alice's session)
├── Google token
├── GitHub token
└── Tokens من Providers أخرى (other provider tokens)
```

عندما تحتاج Agent إلى Service:

```text
اطلب من Broker الـ Token الصحيحة (ask broker for correct token)
```

لا تنفذ Agent قواعد Identity linking الخاصة بكل Provider بنفسها.

---

## 84. Managed Agent Identities: نحو Secretless agents

User identity ليست سوى نصف المشكلة.

تحتاج Agents نفسها أيضًا إلى Credentials.

تعتمد Traditional 2-legged OAuth غالبًا على:

```text
معرّف العميل (client ID)
سرّ العميل (client secret)
```

المخزنة داخل Agent configuration.

وهذا ينشئ:

```text
انتشار Secrets (Secret Sprawl)
```

ينقل المصدر هذه Secrets إلى Authority.

---

## 85. Workflow للـ Agent بلا Secrets طويلة العمر (Secretless-agent Workflow)

### التسجيل (Registration)

يربط Admin الـ Sensitive client credentials بـ Agent Identity داخل Authority.

### التهيئة الأولية (Bootstrap)

تثبت Agent العاملة Infrastructure identity الخاصة بها.

### الطلب (Request)

تطلب Agent Token لـ Target service.

### التفويض (Authorization)

تتحقق Authority من Agent-to-service policy.

### الإصدار (Issuance)

تنفذ Authority الـ OAuth exchange.

### الإرجاع (Return)

تتلقى Agent Short-lived access token فقط.

ولا تعيش Long-lived client secret أبدًا داخل Application source/config.

---

## 86. فوائد Secretless identities

### تدوير Secrets مركزيًا دون تدخل (Zero-touch Rotation)

قم Rotate للـ Secret مركزيًا.

لا حاجة إلى Redeploy لكل Agent instance.

### رؤية Service map (Service-map Visibility)

يعرض كل Token request:

```text
أي Agent (which agent)
تريد استدعاء (wants to call)
أي Service (which service)
```

يمكن لـ Authority بناء Dependency map.

### تقليل Credential leakage

لا يتعامل Developers مباشرةً مع Long-lived secrets.

---

## 87. كيف تنفذ Agent Authentication لدى Authority؟

هذه هي Bootstrap problem.

يقترح المصدر Infrastructure identity مثل:

```text
شهادة mTLS
هوية الخدمة
```

تحتاج Agent إلى طريقة لإثبات:

```text
"أنا Authorized production workload." ("I am the authorized production workload.")
```

قبل أن تعطيها Authority أي Tokens.

---

## 88. سلطة الشهادات الداخلية (Internal Certificate Authority)

توقع Internal CA شهادات Trusted internal workloads.

تحتوي Certificate معلومات مثل:

```text
الموضوع / هوية workload
المُصدِر (issuer)
المفتاح العام
```

لا تحتاج Workload إلى Hard-code لهذه Certificate داخل Source.

يمكن لـ Infrastructure حقنها.

---

## 89. تهيئة mTLS الأولية (mTLS Bootstrap)

في TLS العادي:

```text
Server تثبت هويتها (server proves identity)
```

في mTLS:

```text
Server تثبت هويتها (server proves identity)
Client تثبت هويتها (client proves identity)
```

عندما تستدعي Agent الـ Authority:

1. يقدم الطرفان Certificates,
2. تتحقق Authority من Certificate الخاصة بـ Agent مقابل Trusted CA,
3. تُنشأ Secure connection,
4. ويمكن أن يبدأ Token issuance.

---

## 90. لماذا يستخدم Humans الـ OAuth بينما قد تستخدم Agents الـ mTLS؟

يتفاعل Humans عبر:

- Browsers،
- Phones،
- Biometric/Password login،
- شاشات الموافقة (Consent screens).

تثبيت Workload certificates على جهاز كل User سيخلق Poor usability.

أما Agents فهي Software workloads ويمكنها تلقي Infrastructure-injected certificates بأمان.

لذلك:

```text
هوية بشرية
→ تدفقات تفاعلية بنمط OAuth/OIDC

هوية workload للـ agent
→ هوية mTLS/البنية التحتية
```

تحل Mechanisms الاثنتان مشكلتين مختلفتين في Identity.

---

## 91. توحيد هوية User وAgent (Unified User and Agent Identity)

تجمع Final identity architecture في المصدر بين:

```text
نشر هوية المستخدم (User Identity Propagation)
+
هوية Agent (Agent Identity)
```

يمكن فهم Downstream action مفاهيميًا بأنها:

```text
Agent X
تتصرف نيابةً عن (acting on behalf of)
User Y
ضد (against)
Resource Z
```

وهذا يعطي:

- Authorization أقوى،
- Auditability أقوى،
- Least privilege أفضل،
- Traceability أفضل.

## 95. النموذج الذهني الكامل

لا ينبغي الوثوق بـ Enterprise agent لمجرد أن:

```text
Model جيدة (the model is good)
```

تنشأ Trust من System كاملة.

المسار الآمن هو:

```text
حوسبة آمنة
   ↓
شبكة خاصة
   ↓
بيانات محمية
   ↓
guardrails المدخلات/التطبيق
   ↓
سياق agent معزول
   ↓
أدوات مفوَّضة ومتحقَّق منها
   ↓
هوية المستخدم + الـ agent موثَّقة
   ↓
تنفيذ قابل للمراقبة
   ↓
حوكمة بشرية/امتثال
```

بالنسبة إلى Live multimodal interaction:

```text
Frontend
  ↓
Backend
  ↓
Model Gateway
  ├── بوابة الخصوصية / المدخلات
  ├── Guardrail Agent
  └── بوابة المخرجات
  ↓
نموذج الاستدلال
```

بالنسبة إلى Multi-agent identity:

```text
المستخدم
  ↓ هوية مفوَّضة
Agent A
  ↓ token exchange
Agent B
  ↓ سياق المستخدم المنشور
المورد
```

بينما تثبت Agents نفسها Workload identity من خلال Trusted infrastructure.

وهذا هو الفرق بين Intelligent agent و Trustworthy enterprise agent.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1
> "Security هي في الأساس Prompt engineering."

لا. يبدأ المصدر من Hardware و Networking وينتهي بـ Governance.

### المفهوم الخاطئ 2
> "VPC تمنع Data exfiltration تلقائيًا."

لا. ما تزال Egress policy مهمة.

### المفهوم الخاطئ 3
> "Embeddings آمنة لأنها ليست Text قابلة للقراءة."

لا. تعامل مع Vector stores بوصفها Sensitive data stores.

### المفهوم الخاطئ 4
> "إذا كانت Model لديها Safety training، فلا حاجة إلى External guardrails."

لا. يستخدم المصدر Independent enforcement حول Model.

### المفهوم الخاطئ 5
> "نجاح Login يعني أن User يستطيع تنفيذ أي شيء."

لا. Authentication و Authorization مختلفتان.

### المفهوم الخاطئ 6
> "API keys مثالية كـ Long-term agent credentials."

لا. هي غالبًا Long-lived و Broadly scoped.

### المفهوم الخاطئ 7
> "3-legged OAuth مخصصة لـ Agent-to-agent background traffic."

لا. تُستخدم عندما يفوض Human الوصول.

### المفهوم الخاطئ 8
> "2-legged OAuth تحمل هوية Human user."

لا. هي تثبت أساسًا Machine/Agent identity.

### المفهوم الخاطئ 9
> "Logging أكثر يعني أمانًا أكبر دائمًا."

لا. يمكن لـ Logs تسريب PII أو Credentials.

### المفهوم الخاطئ 10
> "Kill switch يجب أن تكون أول Response لأي Anomaly."

لا. ينبغي أن تسبقها Tiered warnings و Circuit breakers عندما يكون ذلك مناسبًا.

### المفهوم الخاطئ 11
> "Retrieved documents موثوقة لأنها جاءت من RAG."

لا. يمكن أن تحتوي Retrieved content على Indirect prompt injection.

### المفهوم الخاطئ 12
> "Tool call من Model آمنة إذا نجح Parse للـ JSON."

لا. ما تزال Authorization و Schema validation و Policy checks مطلوبة.

### المفهوم الخاطئ 13
> "إيقاف Unsafe output كافٍ لخصوصية Live audio."

لا. قد تكون Main model قد استقبلت Sensitive input بالفعل.

### المفهوم الخاطئ 14
> "Transcription-based guardrails تكتشف كل Safety signal."

لا. قد تفوت Tone و Sounds و Gestures و Visual threats.

### المفهوم الخاطئ 15
> "Agent Identity هي نفسها User Identity."

لا. قد تكون الاثنتان مطلوبتين في الوقت نفسه.

### المفهوم الخاطئ 16
> "تمرير User token نفسها عبر كل Agent هو دائمًا Propagation model الصحيح."

لا. قد يكون Audience-constrained exchange أكثر أمانًا.

### المفهوم الخاطئ 17
> "مركزة Refresh tokens داخل Custom vault تحسن Security تلقائيًا."

لا. قد تنشئ تركيزًا كارثيًا لـ Sensitive credentials.

### المفهوم الخاطئ 18
> "Secretless agent identity تعني عدم وجود أي Credentials في أي مكان."

لا. تُزال Long-lived secrets من App code/Runtime، بينما تظل Trusted infrastructure/Authority تدير Credentials و Certificates.

## احتفظ بهذه الفكرة

**تتطلب Agents الجديرة بالثقة Defense in depth. يجب حماية Infrastructure وNetworks وData قبل التفكير حتى في Model. بعد ذلك يحتاج Application إلى Guardrails، وتحتاج Agent إلى Context معزولة وTools تعمل وفق Least privilege، ويجب أن تميز Identity بين Human وSoftware agent، ويجب أن تكشف Observability الـ Cost والـ Behavior من دون تسريب Secrets، كما يجب أن توفر Governance مسؤولية بشرية. تضيف Live audio وVideo متطلبًا جديدًا: يجب أن تعمل Safety controls على Stream نفسها، ويفضل قبل أن تصل Sensitive data إلى Reasoning model. وفي Multi-agent systems، يكون التحدي الأمني الأخير هو Identity propagation، أي ضمان أن تعرف كل Downstream service ليس فقط أي Agent تتصل، بل نيابةً عن من تتصرف هذه Agent.**
