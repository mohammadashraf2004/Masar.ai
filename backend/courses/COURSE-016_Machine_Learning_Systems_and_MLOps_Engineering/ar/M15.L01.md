## 1. تجمع GCP بين Cloud infrastructure وتقنيات مؤثرة في ML والأنظمة الموزعة

يقدم الفصل Google Cloud بوصفها غير معتادة لأن Google أنشأت أو أثرت بقوة في تقنيات واسعة الانتشار مثل:

- Kubernetes،
- TensorFlow،
- لغة Go.

يناقش المصدر أيضًا عيوبًا تاريخية مثل حصة Cloud market أصغر في ذلك الوقت، وعدد أقل من Certified practitioners، ومخاوف حول تاريخ Google في Products و Customer service.

هذه النقاط جزء من Framing التاريخية للفصل، وليست حقائق تقنية خالدة.

الفكرة الدائمة في MLOps هي أن تقنيات مثل Kubernetes و TensorFlow يمكن أن تقلل Cloud lock-in لأنها تستطيع العمل خارج Provider واحدة.

## 2. نظّم GCP إلى أربع فئات عامة من Services

يقسم الفصل Platform إلى أربع فئات رئيسية:

1. **الحوسبة (Compute)**
2. **التخزين (Storage)**
3. **البيانات الضخمة (Big Data)**
4. **Machine Learning**

هذا Mental model مفيد لـ MLOps لأن End-to-end system تحتاج عادةً Capabilities من عدة فئات.

على سبيل المثال:

```text
التخزين (Storage) → Training data
الحوسبة (Compute) → Data/Model workloads
البيانات الضخمة (Big Data) → Transformations و Analytics واسعة النطاق
Machine Learning → Training و Model management و Deployment و Prediction
```

## 3. طابق Compute Engine machines مع Workload الفعلية

توفر Compute Engine أجهزة Virtual machines بملفات Resource profiles مختلفة.

يسمي المصدر فئات مثل:

- Compute intensive — كثيفة Compute،
- Memory intensive — كثيفة Memory،
- Accelerator optimized — محسّنة للـ Accelerators،
- General purpose — للأغراض العامة.

الدرس في MLOps هو مطابقة Resources مع Workload.

يمكن أن تكون GPU-heavy accelerator instance ذات قيمة للـ Workloads التي تستفيد من Massively parallel computation.

استخدام Instance مكلفة نفسها لـ Workload لا تستطيع الاستفادة من GPU بكفاءة هو هدر.

يهم توقع Cost في Real production systems لأن Infrastructure spend قد تحدد هل ML product قابلة للاستمرار اقتصاديًا.

---

## 4. يمكن للـ Interruptible compute خفض تكلفة Batch عندما تتحمل Workload الانقطاع

يناقش المصدر Preemptible VMs بوصفها Resources قصيرة العمر وأقل تكلفة قد تناسب Batch jobs.

المبدأ المهم على مستوى Systems هو:

> **تكون Cheap interruptible compute مفيدة فقط عندما تستطيع Workload النجاة من الانقطاع.**

قد يُعاد تصميم Batch training أو Data-processing jobs بحيث تنفذ Checkpoint أو Restart أو Repeat للعمل بأمان.

يأتي Economic gain من مطابقة Reliability requirements الخاصة بالـ Workload مع Compute class أرخص.

## 5. تعرض GKE و Cloud Run الـ Containers عند مستويين مختلفين من Abstraction

يقارن المصدر بين مسارين مهمين للـ Containers على GCP.

### خدمة Kubernetes المُدارة (Google Kubernetes Engine — GKE)

بيئة Kubernetes مُدارة ومناسبة عندما تحتاج Teams إلى Kubernetes features وتحكم أكبر.

### خدمة Containers المُدارة (Cloud Run)

Service أعلى مستوى تخفي قدرًا أكبر من تعقيد تشغيل Containers.

يوصي الفصل بـ Cloud Run كنقطة بداية عملية للمؤسسات التي تريد طريقة بسيطة لنشر Containerized ML application.

هذه هي Trade-off نفسها في Abstraction التي ظهرت في فصلي AWS و Azure:

```text
تحكم أكبر في Orchestration → GKE
عمل أقل على Infrastructure   → Cloud Run
```

## 6. توفر App Engine و Cloud Functions أنماط Applications أعلى مستوى

### منصة Applications المُدارة (App Engine)

يقدم الفصل App Engine بوصفها Fully managed platform-as-a-service تستطيع استضافة Applications بعدة Languages.

يمكن لـ MLOps workflow استخدام Cloud Build لنشر API service إلى App Engine بصورة Continuous.

### Functions مُدارة للـ Events (Cloud Functions)

توفر Cloud Functions نمط Functions-as-a-service مناسبًا للـ Event-driven systems.

قد تقوم Function بـ:

- بدء Batch training job،
- الاستجابة لـ Data event،
- استدعاء Managed AI API،
- إعادة Prediction.

تقلل هذه Services مقدار Infrastructure التي يجب إدارتها مباشرة.

## 7. يمكن لـ Cloud Storage أن تكون أساس Data lake

يضع الفصل Cloud Storage بوصفها Storage layer مهمة في MLOps للـ Structured و Unstructured data.

بالنسبة إلى Batch-oriented ML systems، توفر Data lake مكانًا تعيش فيه Raw أو Transformed data قبل أن تستهلكها Jobs كبيرة للـ Processing أو Training.

لذلك تدعم Storage layer بقية MLOps workflow بدلًا من أن توجد منفصلة عنها.

بالنسبة إلى GCP، ينظر المصدر إلى خيارين رئيسيين:

- Cloud Build الأصلية على GCP.

المبدأ المهم ليس اختيار Brand. بل أن ML software ينبغي أن تتلقى Automated quality feedback بصورة مستمرة.

## 14. افهم Hierarchy الخاصة بنشر Kubernetes

يصف المصدر Control plane تدير Worker nodes، مع تجميع Containers داخل Pods.

الإجراءات التشغيلية الرئيسية هي:

1. إنشاء Cluster،
2. نشر Application،
3. عرض Ports/Services،
4. Scale للـ Application،
5. Update للـ Application.

Mental model مبسطة هي:

```text
العنقود (Cluster)
  ├── مستوى التحكم (Control plane)
  └── عقد العمل (Worker nodes)
        └── وحدات Pods
              └── Containers — الحاويات
```

## 15. يغلق Horizontal Pod Autoscaler الحلقة بين Metrics و Capacity

يسلط المصدر الضوء على Kubernetes Horizontal Pod Autoscaler (HPA) بوصفها Feature رئيسية.

يمكن لـ HPA تعديل عدد Pods اعتمادًا على Signals مثل:

- CPU utilization،
- Memory،
- Metrics مخصصة (Custom metrics).

مفاهيميًا:

```text
راقب Metric
      ↓
قارنها مع Target
      ↓
زد / قلل Pods
      ↓
راقب مرة أخرى
```

هذه MLOps feedback loop أخرى: Measurements الخاصة بالنظام تقود Automated operational action.

## 17. ابنِ Container على Existing images موثوقة عندما يكون ذلك مناسبًا

```text

      ↓
Dependencies الخاصة بك
      ↓
Application الخاصة بك
      ↓
Image ذات Version محددة
```

بعد ذلك يختبر Developer الـ Image محليًا ويوزعها عبر Registry.

## 27. توفر Managed MLOps platforms أكثر من مجرد الوصول إلى GPUs

تتحدى خاتمة الفصل Misconception شائعة: امتلاك Hardware قوية لا يساوي امتلاك Mature MLOps platform.

تتضمن Platform خدمات منسقة من أجل:

- Data و Model management،
- Training workflows،
- Deployment،
- Endpoints،
- Monitoring،
- Explainability،
- الأتمتة (Automation).

يستخدم المصدر مفهوم **Comparative advantage** ليجادل بأن Organizations ينبغي أن تتجنب إعادة بناء Version أدنى من Capability تستطيع Managed service ناضجة توفيرها بتكلفة معقولة.

يبقى Decision معتمدًا على Context، لكن Cost comparison يجب أن تتضمن Engineering effort و Time، وليس Hardware ownership فقط.

## 30. اجمع الفصل كله في GCP MLOps system واحدة

يمكن جمع أجزاء الفصل داخل Mental model واحدة:

```text
التحكم في المصدر (Source control)
   ↓
GitHub Actions / Cloud Build — أتمتة التكامل والنشر
   ↓
طبقة Data (Data layer)
Cloud Storage / BigQuery / DataOps — مكونات طبقة Data
   ↓
طبقة Modeling (Modeling layer)
BigQuery ML / Managed AI / Vertex AI — مكونات طبقة Modeling
   ↓
Packaging / Serving — التغليف والتقديم
Cloud Functions / App Engine / Cloud Run / GKE — خيارات Serving
   ↓
Monitoring + Quality + Explainability — المراقبة والجودة والتفسير
   ↓
Feedback و Iteration
```

لا تحتاج كل Project إلى كل Box.

يشجع الفصل مرارًا على البدء بأبسط Architecture تنشئ Value وإضافة Complexity فقط عندما تتطلب Operational problem ذلك.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: أقوى VM هي دائمًا أفضل خيار Compute للـ ML

ينبغي أن تتطابق Compute مع Workload؛ وتكون Accelerators المكلفة مهدرة عندما لا تستطيع Workload استخدامها بكفاءة.

### المفهوم الخاطئ 2: Cheap interruptible compute مناسبة لكل Workload

يجب أن تتحمل Workload الانقطاع وأن تكون مصممة للتعافي أو Restart.

### المفهوم الخاطئ 3: GKE و Cloud Run متكافئتان في Operational responsibility

كلتاهما تشغل Containers، لكن Cloud Run تجرد قدرًا أكبر من Infrastructure بينما تعرض GKE قدرات Kubernetes.

### المفهوم الخاطئ 4: CI منفصلة عن MLOps

يتعامل المصدر مع Testing و Continuous integration بوصفهما أجزاء أساسية وغير اختيارية من Production ML engineering.

### المفهوم الخاطئ 5: يجب على CI/CD tool واحدة تنفيذ كل Automation task

يقترح المصدر صراحة GitHub Actions للـ Developer feedback و Cloud Build للـ Cloud deployment.

### المفهوم الخاطئ 6: ينبغي تعلم Kubernetes بالبدء فورًا بـ Complex ML model

يبدأ الفصل عمدًا بـ Flask service صغيرة حتى يمكن تعلم مشكلات Container/Orchestration بصورة مستقلة.

### المفهوم الخاطئ 7: BigQuery ليست سوى Traditional SQL database

يؤكد الفصل على Serverless analytics و Public datasets كبيرة و Inline ML capabilities.

### المفهوم الخاطئ 8: Serverless functions مخصصة فقط لـ Toy applications

يستخدمها المصدر كـ Event-driven DataOps/ML building blocks ويوصي بها للـ Initial workflows السريعة.

### المفهوم الخاطئ 9: كل GCP ML project تحتاج إلى Full Vertex AI platform

يميز الفصل صراحة بين Light و Heavy workflows.

### المفهوم الخاطئ 10: امتلاك GPUs يعني أن Organization بنت MLOps platform

Hardware ليست سوى Component واحدة؛ تنسق Mature platforms الـ Data و Models و Deployment و Monitoring و Lifecycle automation.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Compute Engine | خدمة Virtual machines في GCP لتشغيل Workloads بملفات Resource profiles مختلفة. |
| Preemptible VM | نوع VM أقل تكلفة وقابل للانقطاع يناقشه المصدر للـ Batch workloads المناسبة. |
| GKE | Google Kubernetes Engine، خدمة Kubernetes المُدارة في GCP. |
| Cloud Run | Managed service عالية المستوى للـ Containerized applications. |
| App Engine | Fully managed application platform تُستخدم في Deployment examples الخاصة بالمصدر. |
| Cloud Functions | Functions-as-a-service offering في GCP للـ Event-driven workflows. |
| Cloud Storage | Object-storage service يضعها المصدر كأساس لـ Data lake. |
| BigQuery | Serverless analytics/warehouse platform بقدرات SQL و ML. |
| Vertex AI | GCP platform شاملة تجمع عدة Capabilities لدورة حياة ML و MLOps. |
| Cloud Build | خدمة أصلية في GCP لأتمتة Build و Deployment. |
| Horizontal Pod Autoscaler (المقيِّس الأفقي للـ Pods) | Kubernetes controller يضبط عدد Pods اعتمادًا على CPU أو Memory أو Custom metrics. |
| Pod | وحدة Execution في Kubernetes يمكن أن تحتوي Container واحدة أو أكثر. |
| Deployment | Kubernetes resource تُستخدم لإدارة Replicated application pods. |
| Service | Kubernetes abstraction تُستخدم لعرض/الوصول إلى Application، بما يشمل Load-balanced access. |
| DataOps | Discipline تشغيلية لجعل Data movement و Transformation و Availability موثوقة وآلية. |
| Managed AI API | Cloud API تعرض Pretrained AI capability مثل Translation. |
| Feature Store | Managed capability لإعادة استخدام Model features، ويبرزها المصدر كجزء من Vertex AI MLOps الأوسع. |
| Explainable AI | Platform capability لفحص/شرح Model behavior. |
| Light MLOps | نمط Deployment الأبسط في المصدر باستخدام عدد صغير من Managed services. |
| Heavy MLOps | نمط Platform أوسع يستخدم Comprehensive lifecycle capabilities عندما تبرر Organizational needs ذلك. |
| Comparative advantage | Reasoning حول ما إذا كان من الأفضل قضاء Internal engineering time في بناء Capability أو استخدام Existing service. |
