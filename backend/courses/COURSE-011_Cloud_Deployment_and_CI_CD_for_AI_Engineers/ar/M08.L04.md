# النطاق وشهادات SSL وNginx ونشر HTTPS

> **المقرر:** أسس الـ Deployment الآمن على AWS  
> **الدرس:** M08.L04  
> **مواءمة المصدر:** BOOK-XXX، الفصل 4. يستخدم الفصل المرجعي Namecheap وشهادة PositiveSSL مشتراة، وتحققًا يدويًا عبر CSR وDNS، وسجل A، وDocker Compose وNginx. هذه خيارات سير عمل خاصة بالمصدر، وليست ادعاءً بأنها الطريقة الوحيدة لنشر HTTPS.

## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح لماذا يحسّن اسم النطاق سهولة الاستخدام مقارنةً بعناوين IP الخام.
- شرح غرض TLS/SSL في معمارية المصدر.
- توليد طلب توقيع شهادة (CSR) ومفتاح خاص باستخدام OpenSSL.
- شرح أي حقول CSR تحدّد صاحب الشهادة.
- شرح لماذا يجب أن يبقى المفتاح الخاص محميًا.
- وصف تفعيل الشهادة في المصدر والتحقق من ملكية النطاق عبر CNAME.
- شرح غرض سجلات DNS من نوع A وCNAME في سير عمل المصدر.
- شرح كيف يدمج المصدر شهادة الخادم مع حزمة CA.
- قراءة علاقة Docker Compose بين Streamlit وNginx في المصدر.
- شرح إعادة توجيه Nginx من HTTP إلى HTTPS.
- شرح توجيهات شهادة/مفتاح TLS.
- شرح الوكيل العكسي (reverse proxy) في Nginx من حركة HTTPS إلى `streamlit_calc:8501`.
- تتبّع مسار الطلب النهائي من اسم النطاق إلى Streamlit.

## 1. انتقل من عناوين البنية التحتية إلى نطاق احترافي وHTTPS

حتى الآن كان المستخدمون يصلون إلى التطبيق عبر نقاط تقنية مثل:

```text
عنوان Elastic IP:8501
```

أو:

```text
DNS الخاص بموازن الحمل:8501
```

ويضيف الفصل 4 تحسينين موجّهين للمستخدم:

```text
نطاق مخصص (custom domain)
+
تشفير TLS/SSL
```

وتصبح النتيجة من حيث المفهوم:

```text
https://your-domain:8501    # عنوان مثالي
```

### اسم النطاق

يمنح النطاق المستخدمين اسمًا ثابتًا مقروءًا للبشر.

وبدلًا من تذكّر اسم مضيف تولّده AWS أو عنوان IP، يستطيعون استخدام عنوان خاص بالعلامة التجارية أو بالتطبيق.

### TLS/SSL

يستخدم الفصل شهادة SSL لتمكين اتصال HTTPS مشفّر.

والفكرة الأساسية:

```text
HTTP
→ بروتوكول تطبيقات بنص صريح غير مشفّر

HTTPS
→ HTTP محمي بتشفير/مصادقة TLS
```

ينفّذ المصدر TLS عبر Nginx.

[[IMAGE_NEEDED: Final domain and HTTPS architecture | A high-level flow showing Browser → custom domain DNS → AWS load-balancer layer → EC2 → Nginx TLS termination → Streamlit container | Learner should notice that the custom domain identifies the service while Nginx presents the certificate and proxies to the application]]

## 2. سير عمل النطاق ومزوّد الشهادة في المصدر

يستخدم الفصل المرجعي:

```text
Namecheap    # مزوّد النطاقات والشهادات
```

من أجل:

- تسجيل النطاق،
- شراء شهادة SSL،
- إدارة DNS.

ويختار منتج شهادة أساسيًا اسمه:

```text
PositiveSSL
```

هذا هو سير العمل الخاص بمزوّد بعينه في المصدر.

ولا يعامل هذا الدرس الأسعار وواجهة المزوّد الظاهرة في الفصل على أنها حقائق تقنية خالدة.

والمفاهيم التقنية الباقية هي:

```text
امتلاك/التحكم بنطاق
        +
الحصول على شهادة لذلك النطاق
        +
إثبات التحكم بالنطاق
        +
ضبط DNS
        +
تثبيت الشهادة/المفتاح الخاص على نقطة TLS
```

## 3. ولّد CSR ومفتاحًا خاصًا باستخدام OpenSSL

يولّد المصدر طلب توقيع الشهادة على مضيف EC2.

وأمره هو:

⟦CODE_0⟧

### ناتجان

ينتج عن ذلك:

```text
private.key
```

و:

```text
your_domain_csr.crt    # ملف طلب التوقيع
```

ولهما غرضان مختلفان.

### المفتاح الخاص

```text
private.key
```

يجب أن يبقى خاصًا.

ويُضبط لاحقًا في Nginx بوصفه مفتاح TLS الخاص.

### طلب التوقيع (CSR)

يحتوي الـ CSR على معلومات طلب الشهادة التي تُرسل إلى مزوّد الشهادات.

### الحقول التي يطلبها المصدر

تتضمن أسئلة OpenSSL:

- الدولة،
- الولاية/المقاطعة،
- المنطقة/المدينة،
- المؤسسة،
- الاسم الشائع (common name)،
- البريد الإلكتروني،
- حقول التحدي/الشركة الاختيارية.

وأهم حقل متعلق بالنطاق في المصدر هو **الاسم الشائع (common name)** الذي يستخدم النطاق المشترى.

### لماذا يهمّ التعامل مع المفتاح الخاص؟

يمكن توزيع الشهادة علنًا.

أما المفتاح الخاص فلا.

من الناحية المفاهيمية:

```text
الشهادة
→ مادة هوية عامة

المفتاح الخاص
→ يثبت التحكم بهوية تلك الشهادة
```

لا تودِع المفتاح الخاص في التحكم بالمصدر (source control).

[[IMAGE_NEEDED: CSR and private-key relationship | A diagram showing OpenSSL generating `private.key` (keep secret) and `your_domain_csr.crt` (send to certificate provider), then the provider issuing a certificate that will later be paired with the private key in Nginx | Learner should notice that the private key never needs to be sent to the certificate provider]]

## 4. فعّل الشهادة وأثبت التحكم بالنطاق

يفعّل المصدر الشهادة المشتراة بلصق الـ CSR في سير عمل الشهادة لدى المزوّد.

ثم يختار:

```text
CNAME record (سجل CNAME)
```

للتحقق من التحكم بالنطاق.

### لماذا يوجد التحقق؟

تحتاج جهة إصدار الشهادات (CA) إلى دليل على أن الطالب يتحكم بالنطاق.

ويولّد مزوّد المصدر قيمتين:

```text
Host (المضيف)
Target (الهدف)
```

لسجل CNAME.

ثم يضيف المتعلّم ذلك السجل إلى إعدادات DNS الخاصة بالنطاق.

من الناحية المفاهيمية:

```text
مزوّد الشهادة
        ↓ يعطي validation token
سجل DNS من نوع CNAME
        ↓ يثبت التحكم علنًا
مزوّد الشهادة يفحص DNS
        ↓
تصبح الشهادة فعّالة
```

### TTL

يخفّض المصدر قيمة TTL في DNS أثناء الإعداد لتسريع حلقة التغذية الراجعة.

وهذه راحة عملية في الـ deployment ضمن الفصل.

### المضيف والهدف

يميّز المصدر بين:

```text
Host
→ اسم سجل التحقق

Target
→ الوجهة/القيمة التي يحدّدها المزوّد
```

ويجب نسخ كليهما بدقة.

## 5. وجّه النطاق نحو نقطة الدخول في AWS

بعد التحقق من الشهادة، يضبط المصدر سجل A.

وإعداده من حيث المفهوم:

```text
Type (النوع): A
Host (المضيف): @
Value (القيمة): <عنوان IP العام لموازن الحمل>
```

هذا هو نموذج التوجيه بالضبط كما يصفه الفصل المرجعي.

### ماذا يعني `@` في هذا السياق؟

في واجهة DNS الخاصة بالمصدر، يمثّل `@` النطاق الجذر (apex).

إذن:

```text
@
```

يعني النطاق نفسه وليس نطاقًا فرعيًا مثل:

```text
www    # نطاق فرعي
```

### مفهوم تحليل DNS

```text
المستخدم يدخل النطاق
        ↓
بحث DNS
        ↓
سجل A
        ↓
عنوان موازن الحمل في AWS
```

وهذا يغني المستخدمين عن كتابة عنوان خام يدويًا.

### ملاحظة خاصة بالمصدر

يوجّه الفصل صراحةً إلى ربط النطاق بعنوان IP عام لموازن الحمل كما في إعداد AWS/Namecheap الظاهر فيه.

ويحافظ هذا الدرس على سير العمل هذا بدلًا من استبدال معمارية DNS مختلفة به.

## 6. جهّز ملفات الشهادة لـ Nginx

بعد تفعيل الشهادة، يحصل المصدر على ملفات الشهادة من المزوّد.

ثم ينشئ ملف شهادة مدمجًا.

من الناحية المفاهيمية:

```text
your_domain.crt
      +
your_domain.ca-bundle
      ↓
your_domain_combined.crt    # الملف المدمج
```

ويخزّن المصدر المفتاح الخاص منفصلًا ضمن مجلد خاص.

وبنيته المقصودة من حيث المفهوم:

```text
config/    # مجلد الإعدادات
├── your_domain_combined.crt
└── private/
    └── private.key
```

### لماذا ندمج الشهادة وحزمة CA؟

يحتاج الخادم إلى تقديم معلومات سلسلة شهادات كافية ليتحقق العملاء من مسار الشهادة.

ويحقق المصدر ذلك بضمّ الشهادة الصادرة وحزمة CA في ملف واحد لـ Nginx.

## 7. ضع Nginx أمام Streamlit باستخدام Docker Compose

يحتوي ملف Compose في المصدر على خدمتين رئيسيتين:

```text
streamlit_calc    # حاوية التطبيق
nginx    # حاوية الوكيل العكسي
```

### خدمة Streamlit

تعرض حاوية التطبيق المنفذ:

```text
8501
```

داخل شبكة Compose.

### خدمة Nginx

يحمّل Nginx (mount):

- `nginx.conf`،
- الشهادة المدمجة،
- المفتاح الخاص،
- معاملات الوكيل (proxy parameters).

وهي تعتمد على خدمة Streamlit.

ويفتح المضيف المنفذ:

```text
8501:8501
```

لخدمة Nginx في deployment الاختبار في المصدر.

### المعمارية المفاهيمية

```text
متصفح HTTPS
    ↓
حاوية Nginx
    ↓ وكيل عكسي (reverse proxy)
حاوية Streamlit
```

يصبح Nginx الوكيل الذي يواجه TLS.

## 9. نفّذ تطبيق HTTPS وتحقق منه

ثم يشغّل المصدر عملية Compose من جذر المستودع.

ويظهر أمره المنسوخ بالشكل:

```text
docker-compose up -d –build    # كما وردت في المصدر
```

الشرطة قبل `build` في النص المنسوخ هي بوضوح شرطة طباعية/Unicode.

وقصد الفصل واضح:

> شغّل Docker Compose في الوضع المنفصل (detached) وأعد بناء الخدمات.

اعتبر ملف المصدر في المستودع النسخة المرجعية لصياغة النسخ واللصق.

### الاختبار النهائي في المتصفح

يتحقق الفصل بعنوان يشبه من حيث المفهوم:

```text
https://your-domain:8501    # عنوان مثالي
```

### ما الذي تثبته الصفحة الناجحة؟

إذا تم تحميل الصفحة بأمان، فإن كل ما يلي يعمل:

```text
DNS
+
مسار موازن الحمل
+
قواعد الأمان
+
EC2
+
Docker Compose
+
Nginx
+
الشهادة/المفتاح الخاص
+
الوكيل العكسي
+
Streamlit
```

### مسار الطلب النهائي

```text
المتصفح
  ↓ https://your-domain:8501
تحليل DNS
  ↓
طبقة load balancer في AWS
  ↓
EC2
  ↓
Nginx :8501 TLS
  ↓
proxy_pass
  ↓
streamlit_calc:8501
  ↓
استجابة التطبيق
```

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1
> "يحتوي الـ CSR على المفتاح الخاص."

ينشئ المصدر الـ CSR والمفتاح الخاص في ملفين منفصلين.

### المفهوم الخاطئ 2
> "ينبغي لصق المفتاح الخاص في نموذج CSR لدى مزوّد الشهادة."

لا. يُشارَك الـ CSR، ويبقى المفتاح الخاص خاصًا.

### المفهوم الخاطئ 3
> "سجل CNAME للتحقق وسجل A للتطبيق لهما الغرض نفسه."

لكل منهما وظيفة مختلفة في المصدر: أحدهما يثبت التحكم بالنطاق لإصدار الشهادة، والآخر يوجّه حركة المستخدمين.

### المفهوم الخاطئ 4
> "Streamlit هو من ينهي TLS في هذه المعمارية."

ينهي Nginx الـ TLS ويعمل وكيلًا عكسيًا نحو Streamlit.

### المفهوم الخاطئ 5
> "الشهادة وحدها تكفي لـ Nginx."

يضبط المصدر مادة سلسلة الشهادات والمفتاح الخاص المقابل لها معًا.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| اسم النطاق (Domain name) | اسم DNS مقروء للبشر للتطبيق |
| TLS/SSL | طبقة التشفير/المصادقة التي يستخدمها HTTPS |
| CSR | طلب توقيع شهادة (Certificate Signing Request) |
| المفتاح الخاص (Private key) | مفتاح تشفير سري مقترن بالشهادة الصادرة |
| سجل CNAME | سجل DNS من نوع الاسم المستعار يستخدمه المصدر للتحقق من ملكية النطاق |
| سجل A | سجل DNS يربط اسمًا بعنوان IPv4 في سير عمل المصدر |
| TTL | مدة الـ caching في DNS |
| حزمة CA (CA bundle) | مادة سلسلة الشهادات من مزوّد الشهادة |
| Nginx | خادم ويب/وكيل عكسي يستخدمه المصدر لإنهاء TLS |
| الوكيل العكسي (Reverse proxy) | خادم يستقبل طلبات العملاء ويوجّهها إلى تطبيق داخلي |
| `proxy_pass` | توجيه في Nginx يمرّر الحركة إلى خدمة upstream |

## الفكرة التي تحتفظ بها

**الـ deployment عبر HTTPS سلسلة من الثقة والتوجيه: أثبت التحكم بالنطاق، واحصل على مادة الشهادة واحمِها، ووجّه النطاق إلى بنيتك التحتية، وأنهِ TLS عند Nginx، ومرّر الطلب بعد فك تشفيره إلى خدمة التطبيق.**
