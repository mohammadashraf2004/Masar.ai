## 1. من Web API إلى خدمة GenAI متعددة الوسائط (From a web API to a multimodal GenAI service)

في الدرس السابق، عملت FastAPI بوصفها application layer حول Model.

يوسع هذا الفصل الفكرة عبر عدة data modalities.

يبني المصدر أمثلة لـ Models تتعامل مع:

- text،
- audio،
- images،
- video،
- 3D geometry.

تنتج كل عائلة من Models output representation مختلفة، لذلك يجب أن تعيد كل FastAPI endpoint response مناسبة لتلك modality.

نظرة عامة مفيدة:

| Modality | مثال على Input | Model Output قبل HTTP formatting | HTTP Response نموذجية |
|---|---|---|---|
| Text | Text prompt | String/tokens | Text أوJSON |
| الصوت | prompt نصي | مصفوفة الموجة الصوتية | بايتات WAV متدفقة |
| Image | Text prompt | Image object | PNG/JPEG bytes |
| Video | Image أوprompt | Sequence من frames | MP4 bytes متدفقة |
| 3D | Text prompt | Mesh representation | OBJ أو3D file أخرى متدفقة |

وهذا يعطينا أول مبدأ رئيسي في model serving:

> **Output الخاصة بـ Model وAPI response ليستا الشيء نفسه.**

قد تعيد Model tensors أوarrays أوframes أوmesh. وغالبًا يجب على application تحويل هذا internal representation إلى شيء يستطيع browser أوclient فهمه.

يستخدم الفصل Hugging Face model libraries لعدة local models وStreamlit من أجل lightweight UI prototyping.

النمط الكامل هو:

```text
المستخدم (User)
  ↓
Streamlit / client آخر
  ↓
FastAPI endpoint
  ↓
إعداد Input
  ↓
Generative model
  ↓
Model-native output
  ↓
Conversion / encoding
  ↓
HTTP response
  ↓
Client renderer
```

## 2. Transformers مقابل Recurrent Neural Networks

قبل كشف language model عبر FastAPI، من المفيد فهم لماذا أصبحت Transformer models مهمة إلى هذا الحد.

### الفكرة التسلسلية الأقدم: RNNs

تعالج recurrent neural network الـ sequence خطوة بخطوة.

بالنسبة إلى text، تكون العملية التقريبية:

```text
token 1 → الحالة
           ↓
token 2 → الحالة المحدَّثة
           ↓
token 3 → الحالة المحدَّثة
           ↓
...
```

يحمل **state vector** المعلومات من tokens السابقة إلى الأمام.

وهذا ينشئ مشكلة مع sequences الطويلة.

يجب أن تبقى المعلومات القادمة من بداية document محفوظة عبر عدد كبير من sequential updates قبل أن تؤثر في prediction بعيدة لاحقًا.

وكما يشرح الفصل، يجعل هذا من الصعب على RNNs التقاط long-range relationships بصورة موثوقة.

### فكرة Transformer

تستخدم Transformers **self-attention** بدل الاعتماد على recurrent hidden state واحدة تتحرك خلال sequence.

تسمح self-attention للـ tokens بتمثيل علاقاتها مباشرة مع tokens أخرى داخل input.

بدل التفكير في المواضع المتجاورة فقط:

```text
كلمة 1 → كلمة 2 → كلمة 3 → كلمة 4
```

تستطيع Transformer نمذجة pairwise relationships عبر sequence كلها.

وهذا يعني أن كلمة قرب النهاية يمكن أن ترتبط بقوة بكلمة أقدم إذا كان context يتطلب ذلك.

[[IMAGE_NEEDED: RNN versus transformer sequence processing | Side-by-side diagram: an RNN processing tokens sequentially through a carried state vector, and a transformer processing the whole sequence with attention connections between distant tokens | Learner should notice that RNN information flows step-by-step while transformer attention can directly represent long-range token relationships]]

### رؤوس Attention (Attention Heads)

تحتوي Transformer على **attention heads**.

تتعلم كل head نمط attention خاصًا بها.

قد تركز head على نوع من العلاقة بينما تتعلم head أخرى pattern مختلفًا.

وتسمح عدة attention heads مجتمعة للـ Model بفحص sequence نفسها من عدة perspectives متعلمة.

مفاهيميًا:

```text
تسلسل الإدخال
   ├── attention head 1 → نمط العلاقة A
   ├── attention head 2 → نمط العلاقة B
   ├── attention head 3 → نمط العلاقة C
   └── ...
```

تسهم النتائج المنفصلة في representation الخاصة بالـ context داخل Model.

[[IMAGE_NEEDED: Multi-head attention map | A sentence with several words connected by weighted lines in multiple small attention-head panels; line thickness should represent stronger or weaker learned relationships | Learner should notice that different heads can focus on different contextual relationships within the same sequence]]

### لماذا تتوسع Transformers بصورة أفضل؟

حساب RNN تسلسلي بطبيعته: تعتمد الخطوات اللاحقة على hidden-state computations السابقة.

أما Transformers فيمكنها معالجة جزء كبير من sequence بصورة parallel أثناء training.

وهذا يجعلها أنسب لـ modern accelerator hardware وlarge-scale training.

وقد ساعدت هذه scalability في جعل large language models الضخمة ممكنة.

## 3. Tokens وEmbeddings ومعلومات Position

تعمل neural networks على الأرقام، لا الكلمات.

لذلك يجب أن يمر text بعدة مراحل من representation قبل أن تستطيع Transformer معالجته.

### الخطوة 1: Tokenization

تقسم **Tokenization** الـ text إلى أجزاء.

قد تمثل tokens:

- كلمات كاملة،
- أجزاء من الكلمات،
- punctuation،
- symbols.

ثم تُربط كل token بـ integer identifier.

مفاهيميًا:

```text
"FastAPI is useful."    # جملة مثال
        ↓
tokenizer
        ↓
["Fast", "API", " is", " useful", "."]
        ↓
[421, 918, 27, 6302, 13]    # معرّفات الـ tokens
```

تعتمد tokenization الدقيقة على tokenizer المستخدمة بواسطة Model.

### الخطوة 2: Embeddings

Token IDs ما تزال identifiers فقط.

تحتاج Model إلى representation يمكن تعلم العلاقات داخله.

تقوم **embedding layer** بتحويل كل token إلى dense vector من floating-point values.

مثلًا:

```text
معرّف الـ token 421
     ↓
طبقة embedding
     ↓
[0.12, -0.84, 0.07, ..., 0.31]
```

للـ vector أبعاد كثيرة.

أثناء training، تضبط Model parameters بحيث تصبح هذه numerical representations مفيدة لنمذجة language.

يستخدم الفصل حدسًا هندسيًا: قد تنتهي tokens المستخدمة في contexts متشابهة بـ vectors أقرب داخل learned space.

إحدى الطرق الشائعة لمقارنة اتجاهات vectors هي **cosine similarity**.

في هذه المرحلة، تذكر العلاقة المفاهيمية:

> **Tokenization تعطي symbols معرّفات IDs؛ أما embeddings فتعطي تلك tokens continuous representations متعلمة.**

[[IMAGE_NEEDED: Tokenization to embeddings | A pipeline showing a sentence split into tokens, tokens mapped to integer IDs, and each ID mapped to a multi-dimensional floating-point embedding vector; optionally show a small 2D embedding plot with semantically related tokens closer together | Learner should notice the transformation from human-readable language to numeric model representations]]

### الخطوة 3: Positional Encoding

تستطيع Transformers معالجة token representations بصورة parallel.

وهذا يطرح سؤالًا جديدًا:

> إذا عولجت كل tokens معًا، فكيف تعرف Model ترتيبها؟

يقدم المصدر **positional encoding**.

يُدمج position representation مع token embedding حتى يحمل representation كلا الأمرين:

- ماذا تعني token داخل learned representation،
- وأين تظهر داخل sequence.

مفاهيميًا:

```text
embedding للـ token
      +
embedding للموضع
      =
تمثيل تستخدمه attention
```

وهذا مهم لأن:

```text
"dog bites man"    # كلب يعض رجلًا
```

و:

```text
"man bites dog"    # رجل يعض كلبًا
```

تحتويان tokens متشابهة لكن بترتيب ومعنى مختلفين.

### من Representations إلى Attention

تُمرر representations الناتجة عبر Transformer attention وبقية network layers.

المسار عالي المستوى هو:

```text
النص
  ↓
Tokens
  ↓
Token IDs
  ↓
Token embeddings
  +
معلومات الموضع
  ↓
طبقات Transformer / attention
  ↓
احتمالات الـ Token
```

## 4. Autoregressive Generation وContext Window

تولد decoder-style language model النص بصورة **autoregressive**.

وهذا يعني أن كل prediction جديدة تعتمد على المعلومات الموجودة بالفعل داخل sequence.

افترض أن Model ترى:

```text
FastAPI is a Python web    # بداية جملة غير مكتملة
```

تحسب probabilities للـ next tokens المحتملة.

ثم تختار أوتأخذ sample من token واحدة.

قد تصبح sequence الجديدة:

```text
FastAPI is a Python web framework    # الجملة بعد توليد كلمة إضافية
```

ثم تتنبأ Model بالـ next token مرة أخرى.

وتتكرر العملية حتى:

- الوصول إلى end-of-sequence condition،
- ظهور stop token،
- الوصول إلى generation limit.

### حلقة Generation (Generation Loop)

```text
tokens الإدخال
    ↓
التنبؤ باحتمالات الـ token التالي
    ↓
اختيار/أخذ عينة للـ token التالي
    ↓
إضافة الـ token
    ↓
تشغيل التنبؤ التالي
    ↓
التكرار
```

### Context Window

لا تستطيع language model التفكير إلا في عدد محدود من tokens في الوقت نفسه.

يسمي الفصل ذلك **context window**.

يمكن أن تشمل context window:

- system instructions،
- user messages،
- conversation history،
- retrieved documents،
- generated tokens.

إذا تم تجاوز usable context، يجب على application أوModel implementation إزالة بعض المعلومات أوتلخيصها أوtruncation لها أوإدارتها بطريقة أخرى.

المفاضلة الهندسية مهمة.

قد تحافظ context window الأكبر على information أكثر، لكنها قد تتطلب أيضًا:

- memory أكبر،
- computation أكبر،
- latency أعلى،
- serving cost أكبر.

لذلك ينبغي ألا يعتمد اختيار Model على قاعدة "largest context wins".

بدلًا من ذلك اسأل:

> **كم مقدار context الذي تحتاجه use case فعلًا، وما latency/cost التي تستطيع service تحملها؟**

## 5. حجم Model وMemory وHardware

يمكن أن تختلف open-source language models بصورة كبيرة في parameter count.

تحتاج Model الأكبر عادة memory أكثر لمجرد تحميل weights الخاصة بها.

يبرز الفصل الفرق العملي بين:

- lightweight models التي يمكن تشغيلها على consumer hardware،
- Models أكبر تتطلب GPU VRAM كبيرة،
- Models ضخمة جدًا قد تتطلب عدة data-center GPUs.

### Parameters تستهلك Memory

Mental model تقريبية:

```text
معاملات أكثر
        ↓
تخزين أوزان أكثر
        ↓
متطلبات RAM / VRAM أعلى
```

قد يحتاج training أوfine-tuning إلى memory أكبر أيضًا لأن النظام يجب أن يحتفظ بـ states وقيم intermediate إضافية.

### Quantization

يقدم المصدر **quantization** باعتبارها طريقة لضغط representation الخاصة بـ Model حتى تتسع داخل memory أقل.

تُترك التفاصيل لفصل لاحق، لكن الدرس المهم الآن هو:

> تقلل Quantization numerical precision وقد تغيّر quality/performance characteristics مقابل خفض استخدام memory.

### Local Model مقابل Provider API

ينشئ hardware requirement قرارًا معماريًا مهمًا.

يمكنك:

```text
A. استضافة النموذج ذاتيًا
   → تحكم أكبر بالبنية التحتية
   → مسؤولية أكبر عن العتاد/العمليات

B. استخدام API مزوّد
   → بنية تحتية أقل للنموذج
   → اعتماد خارجي واعتبارات مشاركة البيانات
```

لا يوجد خيار صحيح تلقائيًا.

يعتمد القرار على:

- privacy،
- cost،
- latency،
- expected traffic،
- model quality،
- available hardware،
- operational expertise.

### System Messages وUser Messages

تستخدم conversational models غالبًا structured messages مثل:

⟦CODE_1⟧

تصف system message سلوك Assistant المطلوب.

وتحمل user message الـ request الحالية.

يمكن لـ model-specific tokenizer تحويل هذه structured conversation إلى input format الدقيقة التي تتوقعها Model.

### معاملات Generation (Generation Parameters)

يقدم المصدر عدة controls مهمة.

#### الحد الأقصى للـ Tokens الجديدة (`max_new_tokens`)

الحد الأقصى لعدد tokens الجديدة التي يتم توليدها.

يتحكم في output length، لا عدد input tokens.

#### تفعيل Sampling (`do_sample`)

يتحكم فيما إذا كانت generation تأخذ sample من candidate probabilities أو تختار بصورة deterministic من أعلى probability option بحسب implementation.

#### درجة Temperature (`temperature`)

تتحكم في sharpness/randomness الخاصة بـ sampling.

Mental model للمبتدئ:

```text
Temperature أقل
→ توزيع أكثر تحفظًا

Temperature أعلى
→ أخذ عينات أكثر تنوعًا
```

ليست "creativity guarantee". بل تغير sampling behavior.

#### معامل Top-k (`top_k`)

تقيد candidate selection إلى أعلى `k` token options ترتيبًا.

مثال:

```text
top_k = 50
→ تبقى مؤهلة فقط أعلى 50 من الـ tokens المرشحة الحالية
```

#### معامل Top-p (`top_p`)

تستخدم cumulative probability mass.

مثال:

```text
top_p = 0.95
→ تُضمَّن الـ tokens الأعلى احتمالًا حتى يبلغ احتمالها التراكمي نحو 95%
```

يسمى ذلك عادة **nucleus sampling**.

نسخة تعليمية:

⟦CODE_2⟧

مسار request:

```text

      ↓
قراءة الـ prompt
      ↓
تمرير الـ prompt إلى النموذج
      ↓
```

### Hallucination ما تزال ممكنة

ينتج عرض TinyLlama المحلي في المصدر statement غير صحيحة في أحد الأمثلة.

وهذه نقطة تعليمية مفيدة.

Operational success:

```text

```

```text

```

لذلك يشدد الفصل على تنبيه المستخدمين إلى أن language-model output قد تحتاج fact-checking.

### أنواع Transformer

يميز المصدر بين ثلاثة configurations من Transformer.

#### بنية Encoder-Decoder

مفيدة عند تحويل sequence إلى أخرى.

تشمل الأمثلة في المصدر:

- translation،
- summarization،
- مهام الإجابة عن الأسئلة.

#### بنية Encoder-Only

قوية في تمثيل وفهم input.

أمثلة:

- sentiment analysis،
- entity extraction،
- classification.

#### بنية Decoder-Only

قوية في autoregressive generation.

أمثلة:

- text generation،
- chat،
- language modeling.

وسيلة مساعدة للذاكرة:

| Variant | Mental model الرئيسية |
|---|---|
| Encoder-decoder | حوّل input sequence إلى output sequence |
| Encoder-only | افهم/مثّل input |
| Decoder-only | تابع/ولّد sequence |

ينبغي أن تتوافق Model architecture مع task.

## 8. توليد Audio وStreaming Responses

يضيف audio generation فكرتين جديدتين:

1. يمكن أن تحتوي model pipeline على عدة stages؛
2. غالبًا تحتاج API إلى stream لـ binary media بدل إعادة text.

### مسار Bark (Bark Pipeline)

يستخدم المصدر Bark باعتبارها المثال التعليمي.

ويصف multi-stage pipeline:

1. **نموذج النص الدلالي**  
   تحول text إلى semantic representation.

2. **نموذج الصوتيات الخشنة**  
   تولد broad audio features.

3. **نموذج الصوتيات الدقيقة**  
   تحسن هذه features بإضافة مزيد من التفاصيل.

4. **نموذج ترميز الصوت (audio codec)**  
   تفك generated codes إلى playable waveform.

Mental model:

```text
النص
  ↓
semantic tokens
  ↓
تمثيل صوتي خشن
  ↓
تمثيل صوتي دقيق
  ↓
audio codec
  ↓
الموجة الصوتية (waveform)
```

[[IMAGE_NEEDED: Text-to-audio synthesis pipeline | A four-stage diagram showing text entering a semantic model, then coarse acoustics, then fine acoustics, then an audio codec that produces a waveform | Learner should notice that audio generation is a pipeline of representations rather than a single direct text-to-file conversion]]

### ماذا تعيد Model؟

يمكن لـ audio model إنتاج array من floating-point values تمثل waveform amplitude عبر الزمن.

وهذا ليس WAV file بعد.

تحتاج service إلى:

- waveform،
- sample rate،
- encoding step.

### Memory مقابل Disk

يبرز المصدر أيضًا systems trade-off مفيدة.

**In-memory buffer**

- disk overhead أقل،
- latency أقل غالبًا،
- تستهلك RAM.

**الكتابة إلى File أولًا**

- قد تقلل memory pressure،
- تضيف disk I/O وlatency.

لا يوجد فائز عالمي.

يعتمد الأمر على output size وresource constraints.

### Rendering في Streamlit

يمكن لـ Streamlit client عرض binary audio content المعادة باستخدام audio component الخاصة بها.

ويظل backend pattern نفسه:

```text
مصفوفة مخرجات النموذج
      ↓
ترميز WAV
      ↓
بث FastAPI (stream)
      ↓
مشغّل الصوت لدى العميل
```

## 9. Stable Diffusion وEndpoints الخاصة بخدمة Images

يستخدم الفصل Stable Diffusion باعتبارها architecture الرئيسية لتوليد الصور.

### الحدس وراء Diffusion

الفكرة المهمة هي العلاقة بين:

- noise،
- latent representations،
- denoising.

أثناء conceptual diffusion process، يتعلم النظام كيف ترتبط noisy representations بصور ذات معنى.

وأثناء generation، يمكن تحسين noisy representation تدريجيًا.

تساعد text conditioning على توجيه هذه العملية نحو concept المطلوبة.

```text
    ↓
تمثيل النص
    ↓
تهيئة عملية إزالة الضوضاء
    ↓
تمثيل latent مشوّش
    ↓
إزالة ضوضاء تكرارية
    ↓
الصورة المفكوكة
```

كما يسرد limitations قد تظهر في image-generation systems، منها:

- coherence غير مثالية،
- output sizes محدودة،

## 11. Large Vision Models وTemporal Consistency

يناقش المصدر بعد ذلك architecture كبيرة لتوليد text/video باعتبارها example مفاهيمية لدمج أفكار Transformer وdiffusion.

النقطة التعليمية المهمة ليست اسم product.

بل architecture pattern:

```text
نمذجة التسلسل بأسلوب Transformer
              +
تحسين تكراري بأسلوب Diffusion
              ↓
توليد بصري عالي الأبعاد
```

### لماذا يكون Video صعبًا؟

يبرز الفصل عدة تحديات.

#### الاتساق الزمني (Temporal Consistency)

ينبغي أن تظل objects consistent من frame إلى أخرى.

إذا تغيرت هوية شخص أوcar أوobject بصورة غير متوقعة، ينهار illusion الخاص بعالم coherent.

#### الاتساق المكاني (Spatial Consistency)

يجب أن تحافظ scene على geometry والعلاقات أثناء تحرك camera أوobjects.

#### بيانات Training (Training Data)

يتطلب high-quality video training:

- data volumes كبيرة،
- descriptions/captions مفيدة،
- temporal information،
- metadata ذات معنى.

### الأجزاء البصرية (Visual Patches)

يصف المصدر تمثيل visual information في صورة patches، على نحو مشابه عالي المستوى لكيفية تعامل text models مع tokens.

Mental model:

```text
نموذج نصي
→ تسلسل من text tokens

Vision Transformer
→ تسلسل من الرقع البصرية/المكانية-الزمانية
```

### Emergent Behaviors التي يصفها المصدر

يناقش الفصل capabilities مثل:

- 3D consistency،
- object permanence،
- long-range temporal coherence،
- interaction مع generated environment،
- behavior يشبه simulation.

في هذا الدرس، تعامل معها باعتبارها capabilities يناقشها المصدر، لا ضمانًا بأن كل video model أوكل generated video ستظهرها بصورة موثوقة.

### Licensing جزء من Engineering

يحذر المصدر صراحة من أن بعض open-source models قد لا تسمح بكل أشكال commercial use.

لذلك:

> **اختيار Model ليس قرارًا تقنيًا فقط؛ بل تهم license terms أيضًا.**

قبل commercial deployment، افحص license/model card الخاصة بـ Model.

## 12. توليد 3D Geometry

يضيف three-dimensional generation مفهوم spatial geometry.

### أساسيات Mesh

يمكن وصف mesh باستخدام:

- **vertices** — نقاط في 3D space،
- **edges** — وصلات بين vertices،
- **faces** — surfaces تتكون من edges/vertices متصلة.

يمكن لـ vertex أن تمتلك coordinates:

```text
(x, y, z)
```

وتكوّن faces المتصلة الكثيرة surface الخاصة بـ 3D object.

[[IMAGE_NEEDED: Vertices, edges, and faces in a 3D mesh | A simple low-poly 3D object with individual vertices marked as points, selected edges highlighted as line segments, and one or two polygon faces filled or shaded | Learner should notice how points connect into edges and edges form surface polygons]]

### لماذا يكون Token-by-Token Geometry الساذج مكلفًا؟

قد يتطلب object مفصل آلافًا كثيرة من vertices وfaces.

وقد يصبح توليد كل coordinate بصورة sequential بطيئًا.

لذلك يقدم الفصل **implicit functions** باعتبارها طريقة أخرى لتمثيل 3D surfaces.

بدل تخزين كل surface point صراحة، تعرّف implicit representation الـ shape بصورة continuous من خلال learned function.

### الحدس وراء NeRF

يصف الفصل **Neural Radiance Fields (NeRF)** باعتبارها جزءًا من فكرة rendering.

على مستوى عام، تربط function معلومات مثل:

- position داخل 3D space،
- viewing direction

بقيم مثل:

- density،
- color.

وهذا يسمح بإنشاء novel views لمشهد 3D متعلم.

### دوال Signed Distance (Signed Distance Functions)

توضح **signed distance function (SDF)** مدى بُعد point عن surface.

Mental model بسيطة:

```text
سالب   → داخل الجسم
صفر    → على السطح
موجب   → خارج الجسم
```

تمثل zero-valued boundary الـ surface.

### مسار Shap-E في المصدر

يستخدم المصدر Shap-E باعتبارها المثال العملي لـ text-to-3D.

مفاهيميًا:

```text
prompt نصي
   ↓
pipeline توليدي 3D
   ↓
تمثيل mesh
   ↓
تحويل tensors الـ mesh
   ↓
مخزن OBJ
   ↓
FastAPI StreamingResponse
   ↓
تطبيق نمذجة 3D
```

قد تحتوي generated mesh على:

- vertices،
- faces،
- color information.

### خدمة OBJ

يمكن لـ FastAPI endpoint تحديد 3D media type وتعيين response باعتبارها attachment.

ثم يستطيع client حفظ generated object وفتحه في software مثل Blender.

### سحب النقاط (Point Clouds)

يقارن الفصل كذلك meshes بـ **point clouds**.

Point cloud هي collection كبيرة من 3D coordinates تمثل sampled points داخل space.

ويشير المصدر إلى أن scanning technologies مثل LiDAR تستطيع إنتاج point clouds.

الفرق عالي المستوى:

```text
mesh
→ بنية سطح متصلة صريحة

سحابة نقاط (point cloud)
→ مجموعة نقاط 3D مأخوذة كعينات
```

## 13. ثلاث استراتيجيات لخدمة Models (Three model-serving strategies)

بعد بناء endpoints لعدة modalities، يطرح الفصل أهم سؤال production:

> **أين ومتى ينبغي تحميل Model؟**

ويقدم ثلاث strategies.

### الاستراتيجية A — Model-agnostic: Load/Swap لكل Request

النمط:

```text
الطلب
  ↓
تحميل النموذج المطلوب
  ↓
التوليد
  ↓
تحرير/تبديل
  ↓
الاستجابة
```

يوفر هذا flexibility.

وقد يكون مفيدًا عندما:

- تكون memory محدودة،
- لا يصل إلى service سوى عدد قليل من المستخدمين،
- تريد التجربة بـ Models مختلفة،
- لا تكون latency حرجة.

العيب هو model-load latency.

قد تستغرق Models الكبيرة وقتًا ملحوظًا في التحميل، لذلك يمكن أن يهيمن repeated loading على request time.

### الاستراتيجية B — Compute-efficient: Preload باستخدام Lifespan

النمط:

```text
بدء تشغيل التطبيق
        ↓
تحميل النموذج مرة واحدة
        ↓
الطلب 1 → إعادة استخدام النموذج
الطلب 2 → إعادة استخدام النموذج
الطلب 3 → إعادة استخدام النموذج
        ↓
إيقاف التطبيق
        ↓
تنظيف / تحرير النموذج
```

تستبدل هذه الاستراتيجية memory بـ request latency أقل.

### الاستراتيجية C — Lean Application: خدمة Models خارجيًا

النمط:

```text
العميل
  ↓
تطبيق FastAPI
  ↓
خادم/مزوّد نماذج خارجي
  ↓
inference للنموذج
  ↓
FastAPI
  ↓
العميل
```

تظل FastAPI مسؤولة عن application concerns مثل:

- users،
- security،
- business logic،
- prompt enrichment،
- content filtering،
- coordination،
- monitoring.

وتركز external model layer على inference.

{{image:lifespan-model-preloading}}
{{image:model-lifespan-startup-shutdown}}

### جدول القرار (Decision table)

| Strategy | الميزة الرئيسية | المفاضلة الرئيسية |
|---|---|---|
| Load/swap لكل request | مرنة واستخدام persistent memory أقل | latency مرتفعة بسبب repeated loading |
| Preload باستخدام lifespan | inference متكررة سريعة | تشغل Model RAM/VRAM باستمرار |
| Model Serving خارجي | تفصل application concerns عن inference | تكامل أكبر مع البنية التحتية/الشبكة |

## 17. جمع الفصل كله معًا (Putting the entire chapter together)

يبدأ الفصل بـ Models منفردة لكنه ينتهي بـ system design.

وهذا progression مهم.

Production GenAI service ليست:

```text
FastAPI + استدعاء نموذج واحد
```

Mental model أدق هي:

```text
                           ┌─────────────────┐
                           │    المستخدم     │
                           └────────┬────────┘
                                    │
                                    ▼
                           ┌─────────────────┐
                           │ العميل / UI     │
                           │ e.g. Streamlit  │
                           └────────┬────────┘
                                    │
                                    ▼
                     ┌─────────────────────────┐
                     │       FastAPI API       │
                     ├─────────────────────────┤
                     │ التحقق                  │
                     │ التوجيه                 │
                     │ المصادقة                │
                     │ منطق الأعمال            │
                     │ تحويل المحتوى           │
                     │ استجابات streaming      │
                     │ مراقبة middleware       │
                     └──────────┬──────────────┘
                                │
           ┌────────────────────┼────────────────────┐
           │                    │                    │
           ▼                    ▼                    ▼
     نموذج محلي           نموذج خارجي          Provider API
     محمَّل مسبقًا              (خادم)
           │                    │                    │
           └────────────────────┼────────────────────┘
                                │
                                ▼
                 نص / صوت / صورة / فيديو / 3D
```

### خمسة أسئلة قبل خدمة Model

عند دمج Model جديدة، اسأل:

1. **ما input representation التي تتوقعها؟**
2. **ما native output التي تنتجها؟**
3. **كيف ينبغي encoding لهذه output من أجل HTTP؟**
4. **أين ينبغي أن تعيش Model — لكل request، أمpreloaded، أمexternal؟**
5. **كيف سأقيس latency وfailures وusage بأمان؟**

إذا استطعت الإجابة عن هذه الأسئلة الخمسة، تكون قد انتقلت من مجرد "تشغيل Model" إلى **خدمة Model باعتبارها جزءًا من application حقيقية**.

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1

> Language model تقرأ الكلمات البشرية مباشرة.

### لماذا هذا خطأ؟

يتم tokenization للـ text وتحويله إلى numerical representations قبل معالجته بواسطة neural network.

### المفهوم الخاطئ 2

> Embeddings هي مجرد Token IDs تحتوي أرقامًا أكثر.

### لماذا هذا خطأ؟

Token IDs مجرد identifiers. أما embeddings فهي dense numerical vectors متعلمة تستخدمها Model لتمثيل properties وعلاقات مفيدة.

### المفهوم الخاطئ 3

> Context window الأكبر أفضل دائمًا.

### لماذا هذا خطأ؟

يمكن للـ contexts الأكبر استهلاك memory وcomputation وlatency وcost أكثر. ويعتمد حجم context المفيد على application.

### المفهوم الخاطئ 4

> إذا أعادت FastAPI حالة HTTP 200، فلا بد أن إجابة Model صحيحة.

### لماذا هذا خطأ؟

نجاح HTTP يعني فقط أن request تمت معالجتها بنجاح. وما تزال language model قادرة على hallucination أوإنتاج content منخفض الجودة.

### المفهوم الخاطئ 5

> يمكن لـ audio وimage وvideo و3D endpoints إعادة JSON عادية كلها من دون conversion إضافية.

### لماذا هذا خطأ؟

غالبًا ما تنتج هذه Models arrays أوimage objects أوframe sequences أوmeshes. ويجب على service encoding لها إلى byte/file formats وmedia types مناسبة.

### المفهوم الخاطئ 6

> `StreamingResponse` تجعل model inference نفسها أسرع.

### لماذا هذا خطأ؟

يغير Streaming طريقة توصيل response data. ولا يقلل تلقائيًا computation المطلوبة لتوليد content.

### المفهوم الخاطئ 7

> تحميل Model كبيرة داخل كل request هو production default معقول.

### لماذا هذا خطأ؟

قد يهيمن repeated model loading على latency. وغالبًا يكون preloading أوexternal serving أنسب لـ heavy models المستخدمة باستمرار.

### المفهوم الخاطئ 8

> Preloading لكل Models هو الأفضل دائمًا.

### لماذا هذا خطأ؟

يحسن Preloading latency الخاصة بالطلبات المتكررة لكنه يستهلك RAM/VRAM بصورة مستمرة. وقد لا تتسع عدة Models كبيرة في memory.

### المفهوم الخاطئ 9

> FastAPI وBentoML خياران متعارضان ولا يمكن استخدامهما معًا.

### لماذا هذا خطأ؟

يعرض المصدر architecture متكاملة: تتعامل FastAPI مع application concerns، بينما يمكن لـ BentoML التخصص في inference serving.

### المفهوم الخاطئ 10

> المزيد من Logging أفضل دائمًا.

### لماذا هذا خطأ؟

يمكن أن يؤدي logging لـ prompt وresponse content إلى privacy وsecurity وstorage وperformance risks. ويجب تصميم monitoring بصورة مقصودة.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| RNN | Recurrent neural network تعالج sequences باستخدام recurrent state |
| Transformer | Neural architecture تستخدم attention mechanisms لنمذجة علاقات sequence |
| Self-attention | آلية تمثل العلاقات بين العناصر داخل input sequence نفسها |
| Attention head | آلية attention متعلمة واحدة داخل multi-head attention block |
| Token | جزء خاص بالـ Model من text مثل word أوsubword أوsymbol أوpunctuation |
| Token ID | Integer identifier يُسند إلى token |
| Embedding | Dense numerical vector representation تستخدمها Model |
| Cosine similarity | مقياس vector similarity قائم على الزاوية بين vectors |
| Positional encoding | Representation تُضاف/تُدمج مع token representations لترميز sequence position |
| Autoregressive generation | توليد كل عنصر جديد باستخدام عناصر sequence المتاحة سابقًا |
| Context window | أقصى مقدار من token context تستطيع Model استخدامه في وقت واحد |
| Parameter | قيمة متعلمة داخل Model مثل weight أوbias |
| VRAM | GPU memory المستخدمة لتخزين model weights وinference data |
| Quantization | تقليل numerical precision/representation لتقليل resource requirements الخاصة بـ Model |
| Temperature | Sampling control تغير probability distribution المستخدمة أثناء generation |
| Top-k sampling | Sampling من أعلى `k` candidate tokens ترتيبًا فقط |
| Top-p sampling | Sampling من أصغر مجموعة عالية الاحتمال يصل cumulative mass الخاص بها إلى threshold |
| Transformer من نوع Encoder-only | Transformer configuration تُستخدم أساسًا لمهام input representation/understanding |
| Transformer من نوع Decoder-only | Transformer configuration مناسبة لـ autoregressive generation |
| Transformer من نوع Encoder-decoder | Transformer configuration تحول input sequence إلى output sequence |
| Waveform | Numerical representation لـ audio amplitude عبر الزمن |
| Sample rate | عدد audio samples الممثلة لكل وحدة زمن |
| Stable Diffusion | Diffusion-based image-generation approach تستخدم latent representations وiterative denoising |
| Inference step | خطوة generation/refinement تكرارية واحدة داخل diffusion-style process |
| LoRA | Fine-tuning approach تدرب مجموعة صغيرة من added low-rank parameters مع إبقاء معظم base weights ثابتة |
| Frame | Still image واحدة داخل video sequence |
| Temporal consistency | الحفاظ على coherence للأجسام/events عبر video frames متتابعة |
| Visual patch | جزء من visual/spatiotemporal information يستخدم باعتباره model representation |
| Vertex | نقطة داخل 3D space |
| Edge | وصلة بين vertices |
| Face | Polygon surface مبنية من vertices/edges متصلة |
| Mesh | Connected geometric representation تتكون من vertices وedges وfaces |
| Point cloud | Collection من sampled 3D coordinates لا تعرّف بالضرورة connected faces |
| NeRF | Neural radiance field approach لتمثيل/rendering views لمشاهد 3D |
| SDF | Signed distance function تصف distance بالنسبة إلى surface |
| Model swapping | تحميل Models مختلفة عند الحاجة بدل إبقائها كلها resident |
| Model preloading | تحميل Model أثناء application startup حتى تعيد requests استخدامها |
| Lifespan | FastAPI startup/shutdown context لتهيئة وتنظيف shared resources |
| خادم نموذج خارجي (External model server) | Service منفصلة مسؤولة أساسًا عن model inference |
| Middleware | Code تعمل حول request handling ومفيدة لـ shared concerns مثل monitoring |
| Request ID | Unique identifier لتتبع request واحدة عبر service |

## اختبر نفسك (Self-check)

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. لماذا تتعامل Transformers مع long-range token relationships بطريقة مختلفة عن RNNs؟
2. ماذا تتعلم attention head؟
3. ما الفرق بين token ID وembedding؟
4. لماذا تحتاج Transformer إلى position information؟
5. ماذا يعني autoregressive generation؟
6. ما context window، وما trade-offs الناتجة عن تكبيرها؟
7. لماذا يؤثر حجم Model في RAM/VRAM requirements؟
8. ما المشكلة التي تحاول quantization معالجتها؟
9. فيمَ تؤثر `temperature` و`top_k` و`top_p`؟
10. لماذا يمكن لـ API تعمل بصورة صحيحة أن تعيد مع ذلك Model answer خاطئة؟
11. لأي مهام تناسب encoder-only وdecoder-only وencoder-decoder Transformers؟
12. ما المراحل التي تستخدمها Bark pipeline مفاهيميًا؟
13. لماذا لا تكون audio waveform ملف WAV تلقائيًا؟
14. لماذا تكون streaming responses مفيدة مع media outputs الأكبر؟
15. كيف تولد Stable Diffusion-style model صورة من noise وtext conditioning مفاهيميًا؟
16. ما trade-off التي تنشئها زيادة inference steps؟
17. ما المشكلة التي تعالجها LoRA؟
18. لماذا يكون video generation أكثر استهلاكًا للموارد من still-image generation؟
19. ما temporal consistency وspatial consistency؟
20. ما vertices وedges وfaces وmeshes وpoint clouds؟
21. ما الحدس الأساسي وراء SDF؟
22. متى يكون model swapping مفيدًا؟
23. ما الميزة التي يوفرها lifespan preloading؟
24. لماذا قد تحتاج عدة Models كبيرة إلى processes/GPUs منفصلة؟
25. لماذا قد تستدعي FastAPI خدمة BentoML أوmodel server أخرى بدل تنفيذ inference مباشرة؟
26. ما privacy concern التي تظهر عند استخدام external model providers؟
27. لماذا تُعد middleware مكانًا جيدًا لـ shared service monitoring؟
28. لماذا ينبغي ألا تعتمد production logs فقط على ephemeral local files؟
29. ما privacy risks الناتجة عن logging لـ prompt وresponse bodies؟
30. ما الأسئلة الخمسة التي ينبغي الإجابة عنها قبل كشف Model جديدة عبر API؟
