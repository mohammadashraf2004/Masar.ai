## 1. لماذا تُعد LLMs عقل Agents الحديثة

في الدرس السابق، تعلمت أن Agent يحتاج إلى تفسير Goal واتخاذ Decisions والتخطيط واستخدام Tools. في Agents الحديثة المعتمدة على LLMs، يوفر Language model جزءًا كبيرًا من هذه القدرة المرنة على Reasoning واللغة.

لكن قبل بناء Agents، من المفيد فهم ما الذي تفعله LLM بالفعل.

لا تقرأ LLM الـ Prompt ثم تسترجع جملة جاهزة من Database مخفية. بدلًا من ذلك، تتنبأ بصورة متكررة بالـ Token التي ينبغي أن تأتي بعد ذلك.

على مستوى عام:

```text
Prompt — الموجّه
  -> Tokenization
  -> يعالج Model الـ Tokens
  -> Probability distribution للـ Next token
  -> Sampling/decoding تختار Token واحدة
  -> إضافة Token إلى Context
  -> التكرار
```

تنتج هذه العملية المتكررة إجابات كاملة Token واحدة في كل مرة.

[[IMAGE_NEEDED: LLM training versus inference | A two-part diagram. Left: training text -> tokenization -> prediction -> loss -> backpropagation -> updated weights. Right: prompt -> tokenization -> model -> next-token probabilities -> sampling -> generated token -> repeated generation | Learner should notice that training changes model weights, while inference uses the already-trained weights to generate tokens]]

## 2. LLMs هي متنبئات احتمالية بالـ Tokens

يتلقى Model مدخلًا بعد Tokenization وينتج Probability distribution على Vocabulary الخاصة به. وتجيب هذه Distribution عن سؤال مثل:

```text
بالنظر إلى كل ما رأيته حتى الآن، ما احتمال أن تكون كل Token ممكنة هي الـ Next token؟
```

ثم تختار عملية Decoding أو Sampling منفصلة الـ Next token الفعلية.

وهذا التمييز مهم:

- يقوم **Model** بحساب احتمالات Tokens،
- وتختار **Sampling strategy** أي Token تصبح Output.

بالنسبة إلى Model state و Input نفسيهما، يمكن أن تكون Probability distribution نفسها بينما تنتج Sampling strategies مختلفة Outputs مختلفة.

### ما الذي يتغير أثناء Training

أثناء Base training، يتنبأ Model مرارًا بـ Next token ويقارن Prediction بالـ Expected token. يُمثَّل عدم التطابق بقيمة Loss. وتستخدم Backpropagation هذه Loss لتعديل Internal weights الخاصة بـ Model.

عبر Training datasets ضخمة وعدد كبير من Iterations، تتعلم هذه Weights أنماطًا حول اللغة والمفاهيم والعلاقات وبنية Tasks.

تصحيح مفيد لنموذج ذهني شائع لدى المبتدئين هو:

> لا يخزن Model المعرفة على شكل Lookup table ضخمة.

ينشأ سلوكه من Learned parameters داخل Transformer attention و Feedforward layers. أثناء Inference، تحول هذه Learned weights الـ Current context إلى Next-token probability distribution.

### Alignment بعد Base training

يفصل الفصل أيضًا بين Base training و Alignment. تُستخدم Alignment methods مثل RLHF لتحسين Instruction following والسلوك الحواري المفيد. ويؤكد المصدر أن هذا يختلف عن Techniques المصممة تحديدًا لتحسين Reasoning behavior.

## 3. ما هي Token؟

لا تستهلك LLMs الأحرف الخام أو الجمل الكاملة مباشرة. يُقسَّم Text أولًا إلى **Tokens**. ويمكن أن تمثل Token:

- كلمة كاملة،
- جزءًا من كلمة،
- Punctuation،
- بنية مرتبطة بـ Whitespace،
- أو Fragment أخرى من Vocabulary.

ترتبط كل Token بـ Numeric index في Vocabulary الخاصة بـ Model.

### لماذا يختلف Token count عن طول Text

قد يكون لكتلتين من Text طول مرئي متشابه جدًا لكن Token counts مختلفة بدرجة كبيرة.

على سبيل المثال، تحتوي Structured formats مثل JSON على Braces و Quotation marks و Keys و Colons وأسماء Fields متكررة. ويمكن لهذه Structural elements زيادة Token usage حتى عندما تكون المعلومات نفسها بسيطة.

⟦CODE_0⟧

قد تستخدم Tokens أكثر من جملة مكافئة مثل:

```text
Ada is a researcher. — آدا باحثة.
```

الدرس ليس "لا تستخدم JSON أبدًا". فـ JSON مفيدة جدًا في Structured agent workflows. الدرس هو أن **Structure لها Token cost**.

### لماذا يهم Token counting في Agents

يؤثر Token count في:

- API cost،
- Context-window usage،
- Latency،
- مقدار المساحة المتبقية لـ Tool descriptions و Conversation history،
- مقدار Output الذي يستطيع Model توليده.

ويصبح هذا مهمًا بصورة خاصة في Agent systems التي قد تستدعي LLM عدة مرات خلال Task واحدة.

يذكر الفصل Token-counting utilities مثل `tiktoken` و SDK telemetry بوصفها وسائل عملية لقياس Input و Output usage بدلًا من التخمين من طول Text.

## 4. التحكم في Generation باستخدام Model parameters

ليست صياغة Prompt هي العامل الوحيد الذي يؤثر في Model output. تتحكم Generation parameters في كيفية Sampling أو تقييد Tokens.

| المعامل (Parameter) | التأثير الأساسي | سبب شائع لتغييره |
|---|---|---|
| Temperature | تغيّر مقدار العشوائية في اختيار Token | قيمة أقل للاتساق؛ قيمة أعلى للتنوع الإبداعي |
| حد الاحتمال التراكمي (top-p) | تقصر Sampling على كتلة احتمالية من Tokens المرجحة | تضييق أو توسيع Variation |
| الحد الأقصى للـ Tokens (max tokens) | تضع حدًا أقصى لطول Response | التحكم في Output size والتكلفة |
| عقوبة الظهور (presence penalty) | تعاقب Tokens بعد ظهورها مرة | تشجيع إدخال Material جديدة |
| عقوبة التكرار (frequency penalty) | تزيد العقوبة على Tokens كلما تكررت | تقليل العبارات المتكررة أو Loops |

### Temperature

تعيد Temperature تشكيل Probability distribution قبل Sampling.

- تجعل Temperature المنخفضة High-probability tokens أكثر هيمنة.
- تجعل Temperature المرتفعة Distribution أكثر تسطحًا، ما يسمح بمزيد من Variation.

بالنسبة إلى Coding agent أو Planning agent، قد تكون Temperature منخفضة مفيدة لأن Consistency والتنسيق القابل للتوقع مهمان. أما في Creative writing، فقد تشجع Temperature أعلى على مزيد من التنوع.

ومع ذلك، Temperature هي **عامل تأثير** وليست ضمانًا مطلقًا. حتى عند قيمة منخفضة جدًا، قد تظل Outputs مختلفة.

### حد الاحتمال التراكمي (top-p)

تحافظ top-p، وتسمى أيضًا Nucleus sampling، على مجموعة من Likely tokens يصل مجموع احتمالاتها إلى Threshold المحددة، ثم تنفذ Sampling من تلك المجموعة.

ينصح الفصل بعدم ضبط Temperature و top-p بصورة عدوانية في الوقت نفسه لأن تفاعلهما قد يجعل السلوك أصعب في التوقع.

### الحد الأقصى للـ Tokens (max tokens)

توفر `max_tokens` حدًا أقصى صريحًا لطول Response. وفي Agent systems تكون مفيدة بصورة خاصة كـ Guardrail للتكلفة والـ Verbosity.

### Seed وقابلية التكرار

يذكر الفصل أيضًا Seed parameter باعتبارها مفيدة في Debugging و Evaluation. الهدف هو تقليل Variation غير المضبوطة عند مقارنة Runs.

### مستوى جهد Reasoning

يشير المصدر أيضًا إلى أن بعض Models الحديثة توفر Reasoning-effort أو Thinking parameter. وتوصية الفصل هي تجنب إنفاق أقصى Reasoning effort على كل Agent step صغيرة. استخدم Deliberation أكبر بصورة انتقائية في Planning الصعب أو Tool selection المعقد أو Debugging.

## 5. Prompt engineering هي طبقة تصميم سلوك Agent

في الفصل 1، قُدمت Persona كإحدى طبقات Agent الأساسية. وتمثل Prompt engineering العملية العملية لتصميم تلك Persona وتعليمات التشغيل الخاصة بها.

تجعل Prompts الجيدة Agent أكثر قابلية للتوقع. كما تقلل Retries المهدرة و Tokens غير الضرورية والسلوك الغامض.

### تقنيات Prompt الأساسية

يقدم الفصل عدة Techniques تظل مفيدة عبر Models مختلفة.

#### 1. عيّن Role واضحة

أخبر Model من المفترض أن يتصرف بصفته، ونوع Expertise أو Perspective التي ينبغي أن يستخدمها.

```text
أنت مهندس DevOps خبير. — You are a senior DevOps engineer.
```

يمكن للـ Role تشكيل Vocabulary و Tone و Assumptions و Depth.

#### 2. ضع Instructions المهمة في البداية

ضع Task و Constraints المهمة مبكرًا. ثم افصل بوضوح User-provided data عن Instructions.

#### 3. استخدم Delimiters

تجعل Delimiters من الواضح أي Text يمثل Data وأي Text يمثل Instruction.

```text
Task: لخّص المقال التالي.

<<<ARTICLE
<article text>
ARTICLE>>>
```

#### 4. كن محددًا

تخلق التعليمات الغامضة مساحة لتفسير غير قابل للتوقع. فضّل Requirements ملموسة مثل Audience و Length وعدد Items و Objective.

#### 5. عرّف Structure عند الحاجة

إذا لم يوفر Framework Typed output، يمكنك وصف JSON أو Markdown أو CSV أو Structure أخرى مطلوبة داخل Prompt.

وعندما يفرض SDK بالفعل Typed output schema، يمكن غالبًا تقليل تعليمات Formatting الصارمة.

#### 6. استخدم Examples

توضح Few-shot examples النمط الذي ينبغي أن يتبعه Model. وتفيد عندما يصعب التعبير عن Labels أو Style أو Decision behavior بالقواعد وحدها.

#### 7. استخدم Positive instructions

أخبر Model بما ينبغي أن يفعله بدلًا من ملء Prompt بالممنوعات.

```text
فضّل: اشرح باستخدام لغة مناسبة لطلاب المرحلة الثانوية.
بدلًا من الاكتفاء بـ: لا تستخدم Jargon.
```

#### 8. أزل Ambiguity

استبدل التعبيرات الغامضة مثل "مختصر" أو "بضعة" بحدود قابلة للقياس عندما تكون مهمة.

#### 9. اختر Model و Settings المناسبة

يرتبط Prompt design بقدرة Model والتكلفة و Latency و Generation parameters.

#### 10. كرر التحسين

تعامل مع Prompt development كعملية Engineering: شغّلها، وافحص Failures، وشدد Instructions، وأضف Examples عند الحاجة، ثم اختبر مرة أخرى.

### التخزين المؤقت للـ Prompt (Prompt caching)

يسلط الفصل الضوء أيضًا على Production optimization: يمكن غالبًا أن تستفيد Stable prompt content من Provider-side prompt caching. وقد يؤدي فصل Stable system instructions و Tool definitions عن User content المتغيرة باستمرار إلى تقليل Repeated processing.

## 6. تحويل Workflows إلى Prompts

من الطرق المفيدة لكتابة Agent instructions أن تتخيل أنك تستقبل موظفًا جديدًا لديه Skill لكنه يفتقر إلى Context.

لا تحتاج إلى شرح كل حقيقة في العالم. لكن يجب أن تجعل Workflow واضحة بما يكفي بحيث يستطيع الشخص العمل دون تخمين Requirements حرجة.

على سبيل المثال، تخيل Search agent تستطيع الاختيار بين Internal knowledge base و Public web.

يمكن أن تحدد Structured prompt:

```text
Role: وكيل بحث في المعرفة الداخلية

Task:
- اختر Source A أو B.
- ابحث في Source المختارة.
- إذا لم تجد شيئًا، جرّب Source الأخرى مرة واحدة.
- إذا استمر الفشل، نفّذ Escalation.

Constraints:
- Source واحدة مختارة في كل مرة.
- حتى ثلاث Findings.
- لغة واضحة وبسيطة.
```

الفكرة المهمة هي أن Prompts يمكنها ترميز **Decision points**، وليس فقط One-step instructions.

ومع ذلك، فإن Loop الموصوفة داخل Prompt ليست هي نفسها Durable agent runtime. يشير الفصل إلى أن Plain LLM prompting قد يوقف Loops مبكرًا، بينما يمكن تصميم Agent system لتستمر في التنفيذ حتى يكتمل Goal أو يُحكم بأنه غير قابل للتحقيق.

## 7. أخطاء Prompt engineering الشائعة

لا يؤدي المزيد من Instructions تلقائيًا إلى Prompt أفضل.

| المشكلة | لماذا تضر | الأسلوب الأفضل |
|---|---|---|
| معقدة أكثر من اللازم | Context أكثر، Conflicts أكثر، و Token cost أعلى | تقسيمها إلى Steps أو Roles مركزة |
| متناقضة | على Model تخمين أي Instruction لها الأولوية | إزالة القواعد المتعارضة أو ترتيبها حسب الأولوية |
| بسيطة أكثر من اللازم | تنشئ Round-trips غير ضرورية كثيرة | دمج Micro-tasks المرتبطة عند الملاءمة |
| Delimiters غير متسقة | يصبح تفسير Structure أصعب على Model و Parsers | استخدام Delimiter style واحدة ومتسقة |
| صريحة أكثر من اللازم | كثرة Rules تزيد احتمال تجاهل بعضها | الاحتفاظ بالقواعد الحرجة والتحقق باستخدام Guardrails |
| Output متغيرة | Temperature المنخفضة وحدها لا تضمن الاتساق | تحسين Instructions و Structure و Schemas و Constraints |

### قاعدة عملية

إذا أصبحت Prompt لديك Operating manual ضخمة، فاسأل ما إذا كان جزء من Logic ينتمي إلى مكان آخر:

- Typed schemas،
- Workflow engine،
- Validation step،
- Specialized agent منفصلة،
- قيود على مستوى Tool (Tool-level constraints).

Prompt engineering قوية، لكن لا ينبغي أن تحمل كل مسؤولية في النظام.

## 12. منح Agents أدوات (Tools)

يمتلك Model الذي ينتج Text فقط Agency محدودة. تسمح Tools للنظام باسترجاع Information أو تنفيذ Actions خارج Model نفسه.

يميّز الفصل بين:

- **Tools:** قدرات متاحة لـ Agent.
- **Actions:** ما تفعله Agent فعليًا باستخدام تلك القدرات.

قد تكون Tool:

- Internal Python function،
- External service متاحة عبر MCP،
- Handoff إلى Agent أخرى.

يجعل ذلك Tool جزءًا من Reasoning و Workflow الخاصين بـ Agent بدلًا من كونها مجرد Capability غير مستخدمة داخل Registry.

## 13. لماذا لا تكون Tools الأكثر أفضل دائمًا

قد يبدو منح Agent عشرات Tools أمرًا قويًا، لكن لكل Tool تكلفة.

يؤكد الفصل أربعة تأثيرات مهمة.

### 1. Tools تضيف Token overhead

تُرسل Tool descriptions عادةً مع LLM calls حتى يعرف Model القدرات المتاحة. وتعني Tool schemas الأكثر عددًا Input tokens أكثر.

### 2. Tools تزيد تعقيد القرار

يجب على Model تحديد Tool المناسبة. وتجعل Tools المتشابهة أو ضعيفة الوصف عملية Selection أصعب.

### 3. Tools تنشئ نقاط فشل

قد تتجاوز Tools المهلة (Timeout)، أو تبلغ Rate limits، أو تعيد Malformed data، أو تفشل كليًا.

يسلط الفصل الضوء على Recovery patterns شائعة:

- Retries مع Backoff للأخطاء المؤقتة،
- Structured errors يمكن لـ Model Reasoning بشأنها،
- Fallback tools أو Alternate paths،
- Timeouts للعمليات العالقة.

### 4. Tools تمنح قوة

Search tool منخفضة المخاطر نسبيًا. أما Delete-files tool فيمكنها إنشاء نتائج مدمرة.

مبدأ التصميم بسيط:

> امنح Agent فقط القدرات التي تحتاج إليها فعلًا، وصمم النظام على أساس أنها قد تستخدم في النهاية كل Capability تكشفها لها.

## 14. Tool chaining و Parallel calls

غالبًا ما تحتاج Agents إلى أكثر من Tool call واحدة.

### التسلسل المتتابع للـ Tools (Sequential tool chaining)

توجد Chain عندما تعتمد Tool لاحقة على Output من Tool سابقة.

مثال:

```text
get_research_sources()    # يعيد قائمة المصادر
        |
        v
["Wikipedia", "Google", "YouTube"]
        |
        v
get_resource_url("Wikipedia")    # يعيد رابط المصدر
        |
        v
"https://www.wikipedia.org"
```

لا يمكن تحديد Call الثانية بالكامل حتى تعود Call الأولى.

### استدعاءات Tools المتوازية (Parallel tool calls)

عندما تكون Tool calls مستقلة، يمكن لـ Agent قادرة إصدار عدة Calls بالتوازي.

```text
             -> search_web()
خطوة Agent  -> query_calendar()
             -> lookup_knowledge_base()
```

يمكن لـ Parallel calls تقليل Latency، ولكن فقط عندما لا تعتمد Calls على بعضها.

### لماذا تهم Traces هنا

بمجرد أن تحتوي Workflow على عدة Model calls و Tool calls، يتيح لك Tracing فحص:

- الترتيب الذي حدثت به Calls،
- Calls التي اعتمدت على Results سابقة،
- المدة التي استغرقتها كل Step،
- مكان وقوع Failures أو Calls غير الضرورية.

## 15. تجميع أفكار الفصل

تبدو الصورة الكاملة الآن هكذا:

```text
Goal الخاصة بـ User
   |
   v
Prompt / Persona
   |
   v
LLM
   |
   +--> Generation settings
   +--> Typed output contract
   +--> Registered tools
   |
   v
Agent runtime
   |
   +--> Tool calls
   +--> Tool chains / Parallel calls
   +--> Traces
   |
   v
Validated result
```

تحل كل Layer مشكلة مختلفة:

- **LLM:** توفر Probabilistic language generation وقدرة Reasoning.
- **Prompt:** تحدد Task و Role و Constraints وإرشادات Workflow.
- **Model settings:** تضبط Variability والطول والتكلفة.
- **Typed output:** تنشئ Stable data contracts.
- **Tools:** تتيح لـ Agent استرجاع Information وتنفيذ Actions.
- **Tracing:** تجعل Execution قابلة للملاحظة و Debugging.

وهذا هو الجسر بين "Prompting لـ Model" وبين Engineering لنظام Agent فعلي.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: تخزن LLM الحقائق مثل Database

> لا يقوم Model ببساطة بعمل Lookup لجملة مخزنة.

تحول Learned weights الخاصة به Current context وتنتج Probability distribution للـ Next token.

### المفهوم الخاطئ 2: Temperature بقيمة 0 تضمن إجابات متطابقة

> تقلل Temperature المنخفضة Variation لكنها لا تجعل النظام كله متطابقًا رياضيًا في كل Run.

تظل Prompt clarity و Model behavior و Tool results وعوامل Runtime أخرى مهمة.

### المفهوم الخاطئ 3: المزيد من Prompt rules يحسن Reliability دائمًا

> قد تنشئ Rules المفرطة Conflicts وتزيد Token cost وتجعل Priorities أصعب في الاتباع.

استخدم Schemas و Guardrails و Workflows و Specialized steps عندما يكون ذلك مناسبًا.

### المفهوم الخاطئ 4: Prompt step هي Agent كاملة تلقائيًا

> يمكن أن تكون Prompted model خطوة داخل Agent workflow، لكن Agency الأقوى تظهر عندما يستطيع النظام اتخاذ Decisions واستخدام Tools لمتابعة Goal.

### المفهوم الخاطئ 5: امنح Agent كل Tool متاحة

> تضيف كل Tool قدرًا من Token overhead والتعقيد و Failure modes والسلطة.

اختر Tool set بعناية وفق ما تحتاج إليه Agent فعلًا.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| وحدة Token | وحدة Vocabulary يستهلكها Model أو يولدها |
| عملية Tokenization | تحويل Text إلى Token IDs يستطيع Model معالجتها |
| التوزيع الاحتمالي (Probability distribution) | Scores تمثل مدى احتمال أن تكون كل Token هي التالية |
| عملية Sampling | اختيار Next token فعلية من Distribution الخاصة بـ Model |
| Temperature | Parameter تتحكم في مقدار Randomness أثناء اختيار Token |
| حد الاحتمال التراكمي (top-p) | Nucleus-sampling threshold تحد كتلة الاحتمال المرشحة |
| الحد الأقصى للـ Tokens (max tokens) | أقصى عدد من Output tokens يستطيع Model توليدها |
| هندسة Prompt (Prompt engineering) | تصميم Instructions التي تشكل سلوك Model أو Agent |
| الشخصية التشغيلية (Persona) | Role والسلوك وتعليمات التشغيل المعينة لـ Agent |
| التوجيه بأمثلة قليلة (Few-shot prompting) | تقديم Examples توضح السلوك المطلوب |
| المخرجات المهيكلة (Typed output) | Validated data structure تُستخدم كـ Response contract للـ Agent |
| المخطط الصارم (Strict schema) | Schema ترفض Output غير المتوقعة أو غير الصحيحة بنيويًا |
| سجل التتبع (Trace) | معلومات تنفيذ مسجلة حول Model calls و Tool calls |
| الأداة (Tool) | Capability قابلة للاستدعاء ومتاحة لـ Agent |
| الإجراء (Action) | استخدام فعلي لـ Tool أو Capability أخرى |
| تسلسل الأدوات (Tool chaining) | تمرير Result من Tool سابقة إلى Tool call لاحقة |
| استدعاءات الأدوات المتوازية (Parallel tool calls) | Tool calls مستقلة تُنفذ في المرحلة نفسها لتقليل Latency |

## التحقق الذاتي

قبل المتابعة، تأكد أنك تستطيع الإجابة عن:

1. ما الذي تتنبأ به LLM في كل Generation step؟
2. ما الفرق بين Model prediction و Sampling؟
3. لماذا قد يستخدم JSON Tokens أكثر من Prose مكافئ؟
4. ماذا يحدث عند رفع Temperature أو خفضها؟
5. لماذا ينبغي التعامل مع max tokens كـ Guardrail للتكلفة والـ Verbosity؟
6. اذكر خمس تقنيات Prompt engineering من هذا الدرس.
7. لماذا قد تصبح Prompt ضخمة أقل موثوقية بدلًا من أكثر موثوقية؟
8. ما أقل Moving parts مطلوبة في مثال Agent الأول في الفصل؟
9. لماذا تكون Typed outputs مفيدة بين Workflow steps؟
10. لماذا يكون تعطيل Strict schema validation عادة حلًا أضعف من تصحيح Schema؟
11. ما المعلومات التي يمكن أن يكشفها Tracing؟
12. ما الذي يتغير عندما تُعرض Function كـ Tool؟
13. لماذا ينبغي أن تمتلك Agent مجموعة Tools محدودة؟
14. متى ينبغي Chaining للـ Tools بصورة Sequential؟
15. متى يمكن استدعاء Tools بصورة Parallel؟
