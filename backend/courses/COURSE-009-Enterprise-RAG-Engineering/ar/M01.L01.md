## 1. لماذا توجد RAG

يمكن أن تكون Large language model ممتازة في اللغة، ومع ذلك تكون غير قادرة على الوصول إلى الحقائق التي يحتاجها تطبيقك فعليًا.

تخيل Assistant داخليًا في شركة. قد تكتب Base LLM إجابات بطلاقة، وتلخص Documents، وتنتج Code. لكن سؤالًا مثل:

```text
ما سياسة الاسترداد لدينا بعد يناير من العام المقبل؟
```

يعتمد على معلومات خاصة بالشركة وحساسة للوقت. ربما لم تظهر هذه Information مطلقًا في Training data الخاصة بـ Model، وحتى إذا ظهر إصدار أقدم منها فقد تكون Policy قد تغيرت.

يكشف ذلك قيدًا أساسيًا: لا يمكن لـ Training الخاصة بـ LLM أن تتضمن كل Fact عامة، وكل Document خاصة، وكل Row في Database، وكل Update مستقبلية. Training هي Snapshot. أما المؤسسات الحقيقية فتتغير باستمرار.

عندما تفتقر Model إلى Evidence اللازمة، فقد تولد رغم ذلك إجابة واثقة. يستخدم الفصل مصطلح **Hallucination** للمحتوى المولد الذي لا تدعمه Data حقيقية متاحة لتبريره.

نموذج ذهني مفيد هو:

```text
الطلاقة (Fluency) ليست هي نفسها الوصول إلى الحقائق (factual access).

قد تعرف Model كيفية الإجابة
من دون أن تعرف الحقائق المطلوبة لهذه الإجابة.
```

تعالج RAG هذه الفجوة عبر منح Model طريقة للحصول على Information خارجية ذات صلة وقت طرح السؤال.

## 2. حلقة RAG الأساسية: Retrieve و Augment و Generate

يتكون Retrieval-augmented generation من مرحلتين أساسيتين:

1. **Retrieval (R):** العثور على Information ذات صلة بـ Query الخاصة بـ User.
2. **Generation (G):** إعطاء Query و Information المسترجعة إلى LLM كي تنتج إجابة Grounded.

تعبّر كلمة **Augmented** عن الجسر بينهما: تُضاف Facts المسترجعة إلى Prompt الخاصة بـ Model، فتزيد ما تستطيع Model استخدامه أثناء Generation.

يبدو Basic flow هكذا:

```text
سؤال User
    |
    v
استرجاع Facts ذات صلة
    |
    v
إضافة Facts إلى Prompt
    |
    v
تولد LLM إجابة Grounded في تلك Facts
```

[[IMAGE_NEEDED: Basic RAG architecture | A user query flowing first to a retrieval component that fetches relevant information from a private knowledge source, then to an LLM that receives both the query and retrieved context and produces the final answer | Learner should notice that retrieval happens before generation and that the LLM is grounded by external context]]

### مثال: سؤال طبي Grounded

لنفترض أن نظام RAG متصل بمجموعة خاصة من Medical books و Journal papers. يسأل User:

```text
ما العلاجات الفعّالة لمرض السكري؟
```

ينبغي ألا يطلب النظام من LLM الاعتماد على Internal memory فقط. بل:

```text
السؤال (Question)
  -> استرجاع Passages عن علاج Diabetes
  -> وضع تلك Passages داخل Prompt
  -> طلب الإجابة من LLM اعتمادًا على تلك Evidence
```

يمكن التعبير عن Minimal prompt pattern هكذا:

```text
أنت تجيب عن سؤال اعتمادًا على أدلة مسترجعة.

السؤال:
{question}

السياق المسترجع:
{context}

أجب باستخدام السياق. وإذا لم يحتوِ السياق على الإجابة،
فقل إنك لا تعرف.
```

هذه هي الفكرة المركزية في RAG. يوفر Retrieval الـ Evidence؛ وتحول Generation تلك Evidence إلى Response مفيدة.

## 3. Parametric Knowledge مقابل Retrieved Knowledge

يقارن الفصل الاستخدام العادي لـ LLM بـ **Closed-book test**، وRAG بـ **Open-book test**.

### الكتاب المغلق (Closed-book): Parametric knowledge

تغيّر Training الخاصة بـ Model قيم Neural-network parameters الخاصة بها، أو **Weights**. وتسمى Information الممثلة عبر تلك Parameters المتعلمة **Parametric knowledge**.

في استخدام Closed-book:

```text
السؤال (Question) -> أوزان LLM (LLM weights) -> الإجابة (Answer)
```

لا تستطيع Model الاعتماد إلا على ما أتاحته Training و Post-training عبر تلك Parameters.

### الكتاب المفتوح (Open-book): Retrieved knowledge

في RAG:

```text
السؤال (Question)
   -> استرجاع Evidence خارجية
   -> السؤال + Evidence
   -> النموذج (LLM)
   -> الإجابة (Answer)
```

تتلقى Model Information إضافية في Real time. وهذا يعني أن Application يمكنها استخدام Facts خاصة أو محدثة حديثًا أو شديدة التخصص بحيث لا يُتوقع وجودها في Base model.

يهم هذا التمييز لأن RAG لا تتطلب حفظ كل Fact داخل Model. يمكن أن تبقى Model محركًا عامًا للغة و Reasoning، بينما يوفر External knowledge system الـ Task-specific evidence.

## 4. المخطط الأساسي لـ RAG Stack

يحتوي نظام RAG العملي على Flowين مختلفين:

```text
مسار الإدخال (INGESTION FLOW)
بيانات المصدر (Source data)
  -> استخراج / Parsing
  -> تجهيز
  -> التقسيم (Chunking)
  -> Embedding / Indexing — التمثيل والفهرسة
  -> تخزين Representations قابلة للبحث + Original text

مسار الاستعلام (QUERY FLOW)
استعلام User
  -> تمثيل / Search
  -> استرجاع Candidate facts
  -> تحسين Ranking اختياريًا
  -> بناء Prompt
  -> توليد LLM (LLM generation)
  -> Citations / Guardrails — الاستشهادات والحواجز
  -> الاستجابة النهائية (Final response)
```

يحل Flowان مشكلتين مختلفتين. يسأل Ingestion: **"كيف نجعل Knowledge قابلة للبحث؟"** وتسأل Query processing: **"كيف نجد Evidence الصحيحة لهذا السؤال ونحولها إلى Answer؟"**

## 5. مسار Ingestion

يجهّز Ingestion الـ Source data لعملية Retrieval.

قد تشمل Sources قواعد بيانات أو PDF files أو Object storage أو Knowledge-management systems. المصدر نفسه أقل أهمية من Transformation:

```text
المصدر الخام (Raw source)
  -> استخراج Content قابلة للاستخدام
  -> تنظيف / تجهيز
  -> تقسيم إلى Pieces يمكن التعامل معها
  -> إنشاء Representations للبحث
  -> تخزين Representations و Original text
```

### Embeddings و Indexing

الـ **Embedding** هي Vector representation تهدف إلى التقاط Semantic meaning. أثناء Ingestion، يمكن تحويل Text إلى Embeddings وتخزينها في **Vector database**.

ويحتاج النظام أيضًا إلى Actual text المرتبط بكل Vector. الـ Vector وحدها مفيدة للمطابقة، لكن Generation step تحتاج Facts قابلة للقراءة لوضعها في LLM prompt.

يمثل Record مبسط مخزنًا مفاهيميًا هكذا:

```text
{
  vector: [ ... semantic representation ... ], — Vector representation دلالية
  text:   "The policy states that ...", — النص الأصلي
  metadata: { ... optional source or permission fields ... } — بيانات وصفية اختيارية
}
```

يشير الفصل إلى أن Production ingestion تصبح أكثر تعقيدًا بكثير. وتشمل الاعتبارات المهمة:

- Document preprocessing،
- Chunking،
- Embedding،
- Data validation،
- Multimodal inputs،
- التحديثات التدريجية (Incremental updates).

### Dataset و Corpus و Index

تُستخدم هذه المصطلحات أحيانًا بصورة فضفاضة، لكن الفصل يقدم تمييزًا مفيدًا:

| المصطلح | النموذج الذهني الدقيق |
|---|---|
| Dataset / مجموعة المستندات | المجموعة الخام الأولية من Source files أو Records |
| Corpus | Body من Content منظم ومنظف ومنسق |
| Index | Data structure محسنة للبحث ومبنية من Corpus |

إذًا الـ **Index** ليست مجرد "كل Documents". بل هي Structure أُنشئت لجعل Retrieval سريعة وفعالة.

## 6. Retrieval: Embeddings و Semantic Search و Search الأفضل

وقت Query، يحاول Retrieval العثور على Facts الأكثر فائدة للإجابة عن سؤال User.

مسار Semantic retrieval أساسي هو:

```text
استعلام User
  -> Query embedding — Embedding للاستعلام
  -> Similarity search في Vector database
  -> أعلى Text chunks مطابقة
```

### Semantic search

تستخدم **Semantic search** الـ Embeddings لمطابقة Meaning بدلًا من الاعتماد فقط على Exact wording.

على سبيل المثال، Query مثل:

```text
كيف يمكن للموظف استرداد تكاليف السفر؟
```

قد تطابق Passage بعنوان:

```text
إجراء سداد مصروفات العمل
```

مع أن Exact words مختلفة، لأن Representations يمكنها التقاط معنى مرتبط.

[[IMAGE_NEEDED: Semantic retrieval in embedding space | A conceptual diagram with one query point and several document-chunk points, highlighting nearby semantically related chunks and distant unrelated chunks | Learner should notice that semantic similarity is based on vector proximity rather than exact word overlap]]

### البحث اللفظي (Lexical search)

تقوم **Lexical search** بالمطابقة بصورة مباشرة أكثر اعتمادًا على Written forms و Words و Terms. ويمكن أن تكون مفيدة عندما تهم Exact terminology.

### Hybrid search و Reranking

يؤكد الفصل أن Semantic vector search ليست سوى Basic retrieval method، وقد لا تكفي لـ High-quality production RAG.

هناك تحسينان مهمان:

- **Hybrid search:** تجمع Semantic search مع Lexical search.
- **Reranking:** تأخذ Candidate results وتعيد ترتيبها بحيث ترتفع Evidence الأكثر صلة إلى أعلى.

الهدف ليس استرجاع Text كثيرة. الهدف هو استرجاع **Facts الصحيحة**.

يمكن تلخيص Retrieval pipeline أفضل هكذا:

```text
الاستعلام (Query)
  -> استرجاع Candidates
  -> دمج Search signals متكاملة
  -> إعادة ترتيب Candidates
  -> الاحتفاظ بأقوى Evidence
```

## 7. Generation: Grounding للـ LLM باستخدام Retrieved Facts

بعد Retrieval، يبني النظام Prompt تحتوي:

- Original query الخاصة بـ User،
- Retrieved facts،
- Instructions تصف كيف ينبغي أن تجيب LLM.

هنا يتحول Retrieval إلى **Augmented generation**.

لا يُسأل Model فقط:

```text
أجب عن هذا السؤال.
```

بل يُطلب منه شيء أقرب إلى:

```text
أجب عن هذا السؤال باستخدام الأدلة المسترجعة أدناه.
إذا كانت الأدلة لا تدعم إجابة، فاذكر ذلك.
```

تهم Grounding instruction لأن مجرد إرفاق Context لا يضمن Good behavior. ينبغي أن توضّح Prompt العلاقة بين Question و Evidence و Answer.

### عقد Generation مفيد

فكّر في Generation step كـ Contract:

```text
المدخل (Input):
  السؤال + Retrieved evidence

السلوك المتوقع (Expected behavior):
  صياغة Answer من تلك Evidence

سلوك الفشل (Failure behavior):
  إذا كانت Evidence غير كافية، فلا تخترع Facts مفقودة
```

ينقل ذلك Task من "استرجع أي شيء تعرفه" إلى "نفّذ Reasoning على Evidence المقدَّمة لهذه Query".

## 8. Citations و Hallucination Detection و Guardrails

ينبغي غالبًا لـ Production-quality RAG answer إظهار مصدر Claims الخاصة بها.

### الاستشهادات (Citations)

تسمح Citations لـ User بتتبع Answer إلى Retrieved sources. وهذا يحسن Explainability بطريقتين:

1. يستطيع User التحقق من Claim.
2. يستطيع Team التمييز بين مشكلة Model generation ومشكلة Source data.

إذا كانت Document المستشهد بها نفسها تحتوي Information غير صحيحة، فالفشل يختلف عن اختراع LLM لمحتوى بلا Supporting source.

### اكتشاف Hallucination (Hallucination detection)

بعد Generation، يمكن لـ RAG pipeline التحقق مما إذا كانت Answer متوافقة مع Retrieved facts. وهذا شكل من **Hallucination detection**.

مفاهيميًا:

```text
Retrieved facts + Generated answer — Facts مسترجعة مع إجابة مولدة
          |
          v
التحقق مما إذا كانت Claims مدعومة
          |
          +--> مقبولة (acceptable) -> إرجاعها
          |
          +--> غير مدعومة (unsupported) -> حظرها أو مراجعتها أو تعليمها
```

### Guardrails أخرى

يذكر الفصل أيضًا Guardrails من أجل:

- Bias،
- Toxic أو Harmful responses،
- المحتوى غير المسموح به (Disallowed content).

الدرس الأساسي هو أن Generation ليست بالضرورة آخر Step. يستطيع Robust system التحقق من Response و Filter لها قبل وصولها إلى User.

## 9. من Prototype إلى Production RAG

يمكن أن يكون Proof of concept صغيرًا. أما Mission-critical RAG system فيجب أيضًا أن يكون قابلًا للتشغيل والقياس والتأمين والتوسع.

يجمع الفصل هذه الاعتبارات في عدة Areas.

### 9.1 Retrieval أفضل و Data أوسع

قد تحتاج Production systems إلى:

- Hybrid retrieval،
- Reranking،
- Multimodal information مثل Tables و Images و Flowcharts،
- Knowledge graphs،
- مسارات Agentic (Agentic workflows).

### 9.2 التقييم المستمر (Continuous evaluation)

تحتاج إلى قياس أكثر من مجرد أن Demo question واحدة "تبدو جيدة". يمكن أن يشمل Evaluation:

```text
جودة Retrieval (retrieval quality)
جودة Generation (generation quality)
Hallucination / Faithfulness — الهلوسة والأمانة للأدلة
جودة Citations (citation quality)
```

ينبغي أن يستمر Evaluation مع تغير النظام.

### 9.3 CI/CD والتحديث الآلي للبيانات

عندما تتغير Source data، يمكن لعملية Event-driven ingestion تحديث RAG knowledge base:

```text
تحديث المصدر (Source update)
  -> تشغيل ETL
  -> Preprocess / Chunk — تجهيز وتقسيم
  -> Embed — إنشاء Embeddings
  -> Index — فهرسة
  -> Knowledge محدثة قابلة للبحث
```

يمكن أيضًا دمج Automated RAG evaluation في CI/CD بحيث يُكتشف أي تغيير في Model أو Prompt أو Data يؤدي إلى تراجع Quality قبل Deployment.

### 9.4 Version control وقابلية إعادة الإنتاج

ينبغي التعامل مع Prompts بوصفها Versioned artifacts. ويوصي الفصل أيضًا بعمل Versioning لمكونات مثل:

- Embedding models،
- Chunking logic،
- LLM توليدية (Generative LLM).

يدعم ذلك Reproducibility و Rollback.

### 9.5 Observability ومراقبة التكلفة

يساعد Tracing لطلب واحد عبر RAG pipeline على تفسير سبب حدوث Response سيئة.

تشمل Measurements المفيدة:

- Ingestion performance،
- Retrieval performance،
- LLM generation performance،
- Token usage،
- Total cost لكل Query.

### 9.6 الأداء وقابلية التوسع

يسلط الفصل الضوء على:

- Database indexing strategies،
- Sharding،
- Caching،
- Optimized inference،
- نقاط Inference ذات Autoscaling.

كما يوضح تمييزًا مهمًا: قد تتوسع Retrieval algorithm بكفاءة، لكن Overall system يمكن أن تظل محدودة بسبب Database concurrency أو Network latency أو Engineering bottlenecks أخرى.

### 9.7 Security و Governance

يجب تطبيق Security على Data path، لا على User interface فقط.

يشير الفصل إلى:

- Granular role-based access controls على مستوى Data،
- Encryption at rest،
- Encryption in motion،
- Prompt/Input sanitization،
- Output filtering،
- Redaction للـ Personally identifiable information (PII).

قاعدة حاسمة هي:

```text
ينبغي ألا يعيد Retriever أي Document
لا يملك User الحالي Authorization للوصول إليها.
```

Permission-aware retrieval جزء من Architecture.

## 12. RAG مقابل "Chat with PDF" و Long-Context Prompting

قد تبدو RAG مشابهة لـ "Chat with PDF"، لكن Strategy الأساسية يمكن أن تكون مختلفة جدًا.

يمكن لنظام Document-chat بسيط وضع Document كاملة داخل Prompt:

```text
نص PDF كامل (Full PDF text)
+ السؤال (question)
-> النموذج (LLM)
```

يشير الفصل إلى أن Context windows الكبيرة جدًا قد تجعل ذلك عمليًا للمجموعات الصغيرة أو المتوسطة. لكن Approach تصبح إشكالية على Enterprise scale.

### القيد 1: التكلفة (Cost)

إذا كانت Prompt تحتوي كل شيء، تعالج Model كميات كبيرة من Text قد لا تكون ذات صلة بالسؤال.

تحاول RAG بدلًا من ذلك إرسال Evidence الأكثر صلة فقط.

### القيد 2: Latency

تتطلب Prompts الطويلة Processing أكبر. وحتى عندما تدخل تقنيًا داخل Context window الخاصة بـ Model، يمكنها زيادة Response latency.

### القيد 3: اختيار المستندات (Document selection)

إذا كانت Organization لديها Data موزعة عبر Google Drive و Notion و SharePoint و PDFs وأنظمة أخرى، فما يزال على شخص أو شيء ما تحديد Content التي ينبغي وضعها داخل Prompt.

بمجرد أن يبدأ النظام تلقائيًا في اختيار Documents ذات الصلة، فقد أعدت إدخال Retrieval.

### المقارنة الأساسية

| أسلوب Full-context | RAG |
|---|---|
| يرسل كميات كبيرة من Text المتاحة | يختار Evidence ذات الصلة |
| يمكن أن يعمل جيدًا مع Collections صغيرة | مصمم للتوسع إلى Collections كبيرة |
| يدفع Processing cost لـ Context غير ذات صلة | يحاول تقليل Context غير الضرورية |
| يحتاج طريقة لاختيار Documents على Scale | Retrieval هي آلية الاختيار |

## 13. RAG مقابل Fine-Tuning

تكيّف Fine-tuning نموذجًا Pre-trained عبر مواصلة Training على Data إضافية. وهذا يغيّر Internal parameters الخاصة بـ Model.

تتخذ RAG Approach مختلفة: أبقِ Knowledge قابلة للاسترجاع خارجيًا وقدم Facts ذات صلة وقت Query.

### 13.1 فجوة الخبرة (Expertise gap)

يحذر الفصل من أن Fine-tuning تتطلب إعداد Data بعناية وخبرة في Deep learning. وتشمل Risks:

- Overfitting،
- Regression في General model capabilities،
- إدخال Bias من Data الجديدة،
- تراجعات الأمان (Safety regressions).

كما يشير إلى أن Modern models تمر عادةً بـ Post-training مثل Supervised fine-tuning (SFT) و RLHF. ويمكن لـ Additional fine-tuning أن تتداخل مع تلك Behaviors إذا أُديرت بصورة سيئة.

### 13.2 التكلفة والبيانات المتغيرة

لـ Fine-tuning تكلفة Training. كما تنشئ Update frequency تحديًا آخر:

```text
إذا كانت Enterprise data تتغير كل يوم،
فكم مرة ستعيد Training؟
```

يمكن لـ RAG بدلًا من ذلك تحديث External knowledge store.

### 13.3 التحكم في الوصول (Access control)

هذه واحدة من أقوى الفروق التي يوضحها الفصل.

لنفترض أن Training data تخلط:

```text
Engineering — الهندسة
HR — الموارد البشرية
Finance — المالية
Legal — الشؤون القانونية
```

بعد Fine-tuning، تختلط Information المتعلمة داخل Model weights. ويصبح من الصعب فصل "Knowledge مسموح بها لـ HR" عن "Knowledge مسموح بها للجميع" وقت Answer.

مع RAG، يمكن تخزين Permission metadata مع Documents واستخدامها كـ Retrieval filter.

```text
استعلام User + صلاحيات User
          |
          v
Retrieval واعٍ بالصلاحيات (permission-aware retrieval)
          |
          v
Evidence مصرح بها فقط
```

### 13.4 ليستا متعارضتين

يشير الفصل صراحة إلى أن Fine-tuned LLM يمكن أن تُستخدم داخل RAG system.

الخيار ليس:

```text
RAG XOR fine-tuning — RAG أو Fine-tuning ليستا خيارين متعارضين
```

قد يستخدم النظام Fine-tuning لـ Model behavior أو Domain adaptation بينما يستخدم RAG أيضًا لتوفير External knowledge حديثة وقابلة للتحكم.

## 14. الفوائد الأساسية لـ RAG

يسلط الفصل الضوء على عدة Benefits.

### 14.1 قابلية التوسع والكفاءة

يمكن لـ Retrieval engine البحث في Collections تحتوي أعدادًا هائلة من Documents من دون وضع Collection كاملة داخل كل LLM prompt.

يقارن الفصل ذلك بتكلفة Self-attention في LLM، والتي تنمو Quadratically مع Sequence length.

لكن Retrieval efficiency لا تضمن تلقائيًا Whole-system scalability. ما تزال Database concurrency و Network latency و Production bottlenecks أخرى مهمة.

### 14.2 تقليل Hallucination

توفر RAG Facts ذات صلة لكي تستخدمها Model.

إذا صُممت Application للرد بـ "I don't know" عند غياب Evidence، فيمكنها تجنب فرض Unsupported answer.

تُقلل RAG **Hallucination risk**؛ لكنها لا تضمن منطقيًا اختفاء Hallucinations. قد يكون Retrieval خاطئًا، وقد تكون Source data خاطئة، وقد تسيء Model استخدام Context. ولهذا تبقى Evaluation و Guardrails ضرورية.

### 14.3 القابلية للتفسير (Explainability)

لأن Retrieved evidence يمكن الاستشهاد بها، يستطيع Users فحص Source وراء Claims.

وهذا أكثر قابلية للتتبع بكثير من محاولة إعادة بناء Training examples التي أدت إلى تمثيل Fact معينة داخل Model weights.

### 14.4 تحديثات Knowledge السريعة

يمكن تحديث External RAG data باستخدام ETL-style processes عادية.

```text
تغيير Document
 -> إعادة معالجة Knowledge المتأثرة
 -> تحديث Index
 -> يمكن لـ Queries الجديدة استرجاع Version الجديدة
```

لا تحتاج LLM إلى حفظ Update.

### 14.5 ضوابط الوصول (Access controls)

يمكن إرفاق Permission information بالمستندات أثناء Ingestion وتطبيقها أثناء Retrieval.

وهذا يجعل RAG جذابة للأنظمة المؤسسية التي تحتاج إلى Grounding و Data-level authorization معًا.

## 15. المساعدون الافتراضيون و Chatbots والتعليم

- Support logs،
- FAQs،

                                  |

## 16. Enterprise Search وإنشاء Content مؤسَّس على Evidence

### إدارة Knowledge المؤسسية

غالبًا ما توزع المؤسسات Information عبر أنظمة كثيرة. قد تعيد Traditional search قائمة Documents يجب على Employee فتحها وقراءتها ودمجها ذهنيًا.

تضيف RAG طبقة Generation:

```text
سؤال Employee
 -> استرجاع Passages ذات صلة عبر Enterprise sources
 -> تلخيص ودمج Passages
 -> إنتاج إجابة مباشرة
```

يمكن أن يقلل ذلك الوقت المستهلك في قراءة Search results كثيرة يدويًا.

### إنشاء Content وتلخيصها آليًا

غالبًا ما تتطلب Enterprise writing عمليات Research و Fact-checking.

يمكن لـ RAG workflow أن:

```text
طلب Content
 -> استرجاع Information حديثة ذات صلة
 -> توليد Draft أو Summary
 -> Human review عند الحاجة
```

تأتي القيمة من Grounding للـ Generation في أحدث Enterprise material المتاحة بدلًا من الاعتماد فقط على Parametric knowledge الخاصة بـ LLM.

## 17. الإجابة عن الأسئلة و Healthcare و Legal Research

### أنظمة الإجابة عن الأسئلة (Question-answering systems)

قد يكون RAG question-answering system أبسط في Interaction style من Chatbot:

```text
سؤال واحد -> إجابة واحدة Grounded
```

يقدم الفصل Requests for proposals (RFPs) و Requests for information (RFIs) كمثال. يستطيع النظام استرجاع:

- Historical responses،
- Product specifications،
- Pricing،
- Customer interactions،

ثم Synthesizing لـ Tailored response.

### الرعاية الصحية (Healthcare)

قد يجمع Healthcare RAG system بين:

- Patient medical records،
- Physician notes،
- Treatment guidelines،
- المقالات البحثية (Research articles).

يؤكد الفصل شرطين غير قابلين للتنازل في Life-critical use:

- متطلبات Privacy/Compliance مثل HIPAA في Context الموصوف،
- التحقق بواسطة **Human-in-the-loop** من Clinician مؤهل.

لا تُعد AI output بديلًا عن Clinical validation.

### البحث القانوني و Compliance

يمكن لـ RAG المساعدة في استرجاع:

- Case law،
- Statutes،
- مستندات Compliance الداخلية.

الهدف هو تسريع Research مع إبقاء Answers مرتبطة بـ Source material، وهو مهم عندما تهم Precision و Traceability.

## 19. RAG الوكيلة (Agentic RAG)

تُعرض Basic RAG غالبًا كـ One-shot pipeline:

```text
استرجاع مرة واحدة -> توليد مرة واحدة
```

تسمح **Agentic RAG** لـ AI agent بتنظيم Retrieval بصورة أكثر Dynamic.

### Retrieval تكراري ومتعدد الخطوات

إذا كان Retrieval الأول غير كافٍ، يمكن لـ Agent إعادة صياغة Query أو تنفيذ Retrieval مرة أخرى.

```text
السؤال (Question)
 -> الاسترجاع (Retrieval)
 -> هل Evidence غير كافية؟
      | نعم
      v
   تحسين Query
      |
      +-> Retrieval مرة أخرى
```

### التكامل الديناميكي مع Tools

يمكن أن تصبح Retrieval نفسها Tool تستدعيها Model عند الحاجة. وقد تستخدم Agent أيضًا Tools أخرى مثل Web search أو APIs بدلًا من الاعتماد فقط على Knowledge تم Ingestion لها مسبقًا.

### Reasoning متقدم وقابلية التكيف

يصف الفصل Agents تستطيع:

- تفكيك Complex queries،
- التخطيط لـ Retrieval strategies،
- التحقق من Information،
- تنسيق Specialized subagents.

[[IMAGE_NEEDED: Agentic RAG loop | An agent receiving a complex question, planning, calling retrieval as a tool, evaluating returned evidence, optionally reformulating the query and retrieving again, then producing a final response | Learner should notice the feedback loop and that retrieval can occur multiple times rather than only once]]

تكون Agentic RAG مفيدة عندما لا تستطيع Retrieval step واحدة جمع كل ما يلزم لمشكلة متعددة الأجزاء بصورة موثوقة.

## 20. RAG متعددة الوسائط (Multimodal RAG)

بدأت RAG أساسًا مع Text، لكن Enterprise knowledge المفيدة تعيش أيضًا في:

- Tables،
- Diagrams،
- Charts،
- Images،
- صفحات Documents كاملة.

يقدم الفصل Approachين عامين.

### الأسلوب 1: تحويل Modalities إلى Text

على سبيل المثال:

```text
Image -> Caption / Extracted text -> Text RAG pipeline — تحويل الصورة إلى نص داخل مسار RAG نصي
```

يبقي ذلك Downstream pipeline قائمة على Text.

### الأسلوب 2: الاحتفاظ بـ Original modality

يمكن لـ Multimodal embedding models و Vision-language أو Multimodal language models العمل مباشرة أكثر مع Non-text data.

```text
Text + Image/Table/Page — نص مع صورة وجدول وصفحة
 -> Multimodal representations / Retrieval — تمثيلات متعددة الوسائط مع استرجاع
 -> Multimodal model وقت Query
```

هناك اتجاه End-to-end أحدث يصفه الفصل، وهو Embedding للصفحات كاملة وإرسال Relevant pages إلى Multimodal LLM.

## 21. RAG مع Knowledge Graphs

قد تواجه Flat text retrieval صعوبة عندما تتطلب الإجابة ربط Facts عبر Documents متعددة.

تمثل **Knowledge graph (KG)** الـ Entities والعلاقات بينها.

قد يبدو Graph مبسط هكذا:

```text
[Customer A] --owns--> [Account 17] — العميل A يملك الحساب 17
[Account 17] --belongs_to--> [Region East] — الحساب 17 يتبع المنطقة East
[Region East] --managed_by--> [Team Delta] — المنطقة East يديرها فريق Delta
```

قد يتطلب سؤال اتباع عدة Relationships. وهذا هو **Multi-hop reasoning**.

يصف الفصل Pipeline تُعالَج فيها Unstructured documents لاستخراج Entities و Relationships، ثم تُستخدم لبناء Knowledge graph.

[[IMAGE_NEEDED: Knowledge-graph-enhanced RAG | A small graph of entities connected by labeled relationships, with a query requiring two or more hops across the graph before evidence is supplied to an LLM | Learner should notice how explicit relationships help connect facts that may be scattered across different documents]]

كما يقدم **GraphRAG**، الذي شاع عبر Microsoft، كـ Approach يعالج Unstructured documents لاستخراج Entities و Relationships ويبني Graph تلتقط Connections داخل Data.

الغرض ليس مجرد استبدال Vector search. بل إضافة Structured relationships تساعد في الأسئلة التي يهم فيها "Connecting the dots".

## 22. النموذج الذهني للنظام الذي ينبغي الاحتفاظ به

أهم تحول في الفصل هو التوقف عن التفكير في LLM application على أنها "Model تعرف أشياء" والبدء في التفكير فيها بوصفها **System يجب أن يوفر Evidence**.

نموذج ذهني End-to-end مفيد هو:

```text
تجهيز Knowledge (KNOWLEDGE PREPARATION)
المصادر (Sources)
 -> الاستخراج (Extraction)
 -> التنظيف / التنظيم (Cleaning and Organization)
 -> Chunking
 -> Embeddings / Indexes
 -> مخازن قابلة للبحث (Searchable stores)

معالجة السؤال (QUESTION PROCESSING)
سؤال User
 -> الاسترجاع (Retrieval)
 -> Hybrid search / Reranking اختياريًا
 -> Evidence مصرح بها
 -> بناء Prompt
 -> LLM generation
 -> Citations
 -> Guardrails
 -> Final response

العمليات المحيطة بكلا المسارين (OPERATIONS AROUND BOTH FLOWS)
التقييم (Evaluation)
المراقبة (Monitoring)
الأمان (Security)
إدارة الإصدارات (Versioning)
التحكم في التكلفة (Cost control)
قابلية التوسع (Scaling)
تحديث البيانات المستمر (Continuous data refresh)
```

لذلك لا تُعد RAG مجرد Prompt pattern. على Production scale، هي Data system و Search system و LLM system و Security boundary و Operational pipeline تعمل معًا.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> إذا كانت LLM كبيرة بما يكفي، فينبغي أن تعرف بالفعل Data الخاصة والحالية لمؤسستي.

### لماذا هذا خطأ

لا يمكن أن تتضمن Training معلومات كانت خاصة أو غير متاحة أو أُنشئت بعد Training. توجد RAG تحديدًا لتوفير مثل هذه External information وقت Query.

### المفهوم الخاطئ 2

> تعني RAG وضع كل Document متاحة داخل Prompt.

### لماذا هذا خطأ

صُممت Retrieval step لاختيار Evidence ذات الصلة. إرسال كل Documents أقرب إلى Full-context prompting، وينشئ مشكلات Cost و Latency و Scaling.

### المفهوم الخاطئ 3

> Vector search و RAG هما الشيء نفسه.

### لماذا هذا خطأ

Vector search هي Retrieval technique واحدة. يتضمن RAG system أيضًا Generation، وقد يستخدم Production retrieval أساليب Lexical search و Hybrid search و Reranking أو Methods أخرى.

### المفهوم الخاطئ 4

> إذا استخدمت RAG، تصبح Hallucinations مستحيلة.

### لماذا هذا خطأ

يمكن لـ RAG تقليل Hallucinations عبر توفير Evidence، لكن Poor retrieval أو Incorrect source data أو Generation errors يمكن أن تنتج Answers سيئة. ما تزال Evaluation و Guardrails مطلوبة.

### المفهوم الخاطئ 5

> Fine-tuning و RAG متعارضتان.

### لماذا هذا خطأ

يمكن استخدام Fine-tuned model بوصفها Generative LLM داخل RAG pipeline. تحل التقنيتان جوانب مختلفة من المشكلة.

### المفهوم الخاطئ 6

> تحديث RAG knowledge يعني إعادة Training للـ LLM.

### لماذا هذا خطأ

تُخزن Retrieved knowledge خارج LLM ويمكن Refresh لها عبر Ingestion و Indexing workflows.

### المفهوم الخاطئ 7

> يمكن معالجة Access control فقط بعد أن تولد LLM الإجابة.

### لماذا هذا خطأ

ينبغي Filter للمستندات Sensitive أثناء Retrieval حتى لا تُقدَّم Evidence غير مصرح بها إلى Model من الأساس.

### المفهوم الخاطئ 8

> RAG مخصصة فقط لـ Question-answering chatbots.

### لماذا هذا خطأ

يصف الفصل Enterprise search و Content creation و Personalized advertising و Education و Healthcare و Legal research وتطبيقات أخرى تجمع Retrieval مع Generation.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التوليد المعزز بالاسترجاع (Retrieval-augmented generation — RAG) | نمط يسترجع External information ويقدمها إلى LLM من أجل Grounded generation |
| Retrieval | العثور على Information ذات صلة بـ Query الخاصة بـ User |
| التوليد (Generation) | إنتاج Final response باستخدام LLM اعتمادًا على Query و Retrieved evidence |
| التعزيز (Augmentation) | إضافة Retrieved information إلى Prompt أو Working context الخاصة بـ LLM |
| Hallucination | Generated content لا تدعمها Evidence أو Knowledge المتاحة لتبريرها |
| المعرفة البارامترية (Parametric knowledge) | Knowledge ممثلة عبر Learned parameters أو Weights الخاصة بـ Model |
| التمثيل المتجهي (Embedding) | Vector representation تُستخدم لالتقاط Semantic properties للـ Content |
| قاعدة بيانات Vector (Vector database) | Database مصممة لتخزين Vector representations والبحث فيها، غالبًا مع Source text و Metadata |
| الفهرسة (Indexing) | بناء Representations أو Structures موجهة للبحث انطلاقًا من Source content |
| Dataset / مجموعة المستندات | المجموعة الخام الأولية من Source data |
| Corpus | Body من Content منظم ومنظف ومنسق |
| Index | Structure عالية الأداء ومحسنة للبحث و Retrieval |
| Semantic search | Retrieval اعتمادًا على تشابه Meaning الممثل داخل Embedding space |
| البحث اللفظي (Lexical search) | Retrieval اعتمادًا على التشابه في Words أو Written form |
| Hybrid search | Retrieval تجمع Semantic و Lexical methods |
| Reranking | إعادة ترتيب Retrieved candidates لوضع Evidence الأكثر صلة أولًا |
| التأصيل بالأدلة (Grounding) | تقييد Generation أو دعمها باستخدام Retrieved evidence |
| الاستشهاد (Citation) | Reference تربط Claim داخل Answer بـ Source evidence الخاصة بها |
| حاجز الأمان (Guardrail) | Validation أو Filtering step لفرض توقعات Quality أو Safety أو Policy |
| RBAC | Role-based access control تُستخدم لتقييد Data access وفق Authorization |
| ETL | عمليات Extract و Transform و Load المستخدمة لنقل Data وتجهيزها |
| LLMOps / MLOps | Operational practices لنشر Model-based systems وتقييمها ومراقبتها وصيانتها |
| Agentic RAG | RAG تستطيع فيها Agent التخطيط واستدعاء Retrieval/Tools وتنفيذ Retrieval تكراري أو متعدد الخطوات |
| Multimodal RAG | RAG تتضمن Information غير نصية مثل Images و Tables و Diagrams أو Pages |
| Knowledge graph | تمثيل Structured للـ Entities والعلاقات بينها |
| التفكير متعدد القفزات (Multi-hop reasoning) | ربط عدة Facts مترابطة أو Graph edges للإجابة عن سؤال |
| GraphRAG | Approach موجهة بالـ Graph تبني Entity-and-relationship structures من Unstructured data |
| HITL | Human-in-the-loop validation يراجع فيه شخص مؤهل أو يتحكم في AI-assisted decisions المهمة |

## احتفظ بهذه الفكرة

**تحول RAG الـ LLM من Closed-book generator إلى Component داخل System مدفوع بالأدلة: جهّز External knowledge بحيث يمكن البحث فيها، واسترجع Facts الصحيحة والمصرح بها لكل سؤال، وقدّم تلك Facts إلى Model من أجل Grounded generation، ثم تحقّق من Result واستشهد بمصادرها وراقبها وشغّلها. لذلك لا تعتمد Quality الخاصة بتطبيق RAG على LLM وحدها، بل على السلسلة كاملة من Data ingestion و Retrieval مرورًا بـ Security و Prompting و Generation و Evaluation وصولًا إلى Production operations.**
