## 1. ما Machine Learning — ولماذا نستخدمها؟

أسهل طريقة لفهم Machine Learning هي البدء بفكرة بسيطة:

**يتحسن Machine-learning system في تنفيذ Task من خلال التعلم من Experience، والتي تمثل عادةً في صورة Data، بدل أن يحتاج Programmer إلى كتابة كل Rule صراحةً.**

يتكون هذا التعريف من ثلاثة أجزاء مهمة:

- **Task:** ما المطلوب من System أن تفعله.
- **Experience:** Examples أوInteractions التي تتعلم منها.
- **Performance measure:** الطريقة التي نحدد بها هل تتحسن أم لا.

بالنسبة إلى Spam filter:

```text
المهمة Task (T): تصنيف رسالة بريد جديدة على أنها spam أو ليست spam
الخبرة Experience (E): رسائل بريد مصنّفة مسبقًا
الأداء Performance (P): مقياس مثل دقة التصنيف (accuracy)
```

تسمى Examples المستخدمة للتعلم **training set**. ويُسمى كل Example منفرد **training instance** أو**sample**. أما Component المتعلمة التي تنتج Predictions فهي **model**.

هذا التمييز مهم. مجرد تخزين كمية ضخمة من Information لا يساوي Learning. قد يحتوي Computer على كل مقالات Wikipedia، لكنه لا يكون قد تعلم بمعنى Machine Learning ما لم تستخدم Process هذه Data لتحسين Performance في Task معينة.

### البرمجة التقليدية مقابل Machine Learning

تخيل بناء Spam filter باستخدام Rules عادية. تفحص Spam messages، وتكتشف كلمات أوPatterns مشبوهة، وتحوّلها إلى Rules، ثم تختبرها وتضيف Exceptions باستمرار.

قد ينجح ذلك، لكن Rule base تميل إلى النمو:

```text
إذا احتوت الرسالة على "free" -> مشبوهة
إذا بدا المرسل غير معتاد -> مشبوهة
إذا احتوت الرسالة على "credit card" -> مشبوهة
...
```

المشكلة ليست فقط في عدد Rules. Environment نفسها تتغير. يغيّر Spammers صياغتهم، وتظهر Patterns جديدة، وتصبح Rules القديمة أقل فائدة.

تغير Machine-learning approach طبيعة العمل. بدل أن تحدد كل Spam pattern يدويًا، توفر Examples وتسمح لـ Learning algorithm باكتشاف Predictive patterns من Data.

### لماذا Machine Learning مفيدة؟

تكون Machine Learning ذات قيمة خاصة في أربع حالات.

**1. مشكلات تعتمد على Rules كثيرة**

إذا احتاج System مفيد إلى مئات أوآلاف Rules الهشة، فقد تكون Learned model أقصر وأسهل في الصيانة وأكثر دقة.

**2. مشكلات لا يوجد لها حل عملي مكتوب يدويًا**

Speech recognition مثال جيد. من غير الواقعي كتابة Rules يدويًا تغطي آلاف الكلمات والأصوات واللهجات والميكروفونات وظروف Noise واللغات.

**3. Environments تتغير**

يمكن إعادة Training لـ System باستخدام Data حديثة عندما يتغير User behavior أوFraud patterns أوMarket conditions أوأي جزء آخر من العالم.

**4. مشكلات تكون Patterns نفسها ذات قيمة**

قد تكشف Machine Learning عن Correlations أوSegments أوUnusual cases أوStructures أخرى لم يلاحظها Humans. ويُسمى البحث داخل Datasets كبيرة عن Patterns مفيدة غالبًا **data mining**.

### ما أنواع المشكلات التي يمكن لـ ML حلها؟

يغطي Chapter أنواع Applications كثيرة. الدرس الأهم الآن ليس حفظ كل Algorithm، بل تعلم التعرف على *نوع Task*.

| التطبيق | مهمة ML |
|---|---|
| تصنيف Products من Camera images | Image classification |
| تحديد Tumor Pixel by Pixel | Semantic segmentation |
| تصنيف News أوOffensive comments | Text classification |
| اختصار Document طويلة | Text summarization |
| تقدير Numeric quantity مثل Revenue | Regression |
| الاستجابة لـ Spoken commands | Speech recognition |
| اكتشاف Suspicious credit-card transactions | Anomaly detection |
| تجميع Customers حسب Behavior | Clustering |
| ضغط High-dimensional data لأجل Visualization | Dimensionality reduction |
| اقتراح Product مرجح | Recommender system |
| تدريب Agent للعب Game أوControl | Reinforcement learning |

قد يحتوي Real system واحد على عدة Tasks. فـ Personal assistant مثلًا قد تحتاج إلى Speech processing وLanguage understanding وRetrieval وQuestion answering وGeneration.

### نموذج ذهني مفيد

لا تسأل فقط:

> “أي Algorithm ينبغي أن أستخدم؟”

اسأل أولًا:

```text
ما المهمة؟
ما البيانات المتاحة لدي؟
ما الـ Feedback أو الـ Labels المتاحة؟
ما مدى سرعة تغيّر العالم؟
كيف سأقيس النجاح على حالات لم يرها النموذج؟
```

هذه الأسئلة تحدد Family الخاصة بـ Learning system التي تحتاجها.

## 2. التعلم حسب نوع الإشراف: ما Feedback التي تستقبلها Model؟

إحدى الطرق الرئيسية لتصنيف Machine-learning systems هي نوع Guidance التي تستقبلها أثناء Learning.

Categories الأساسية في هذا Chapter هي:

- supervised learning
- unsupervised learning
- semi-supervised learning: التعلم شبه الخاضع للإشراف
- self-supervised learning: التعلم ذاتي الإشراف
- reinforcement learning

وهي إجابات مختلفة عن السؤال:

**من أين تأتي Learning signal؟**

### Supervised Learning

في **supervised learning**، يأتي كل Training example ومعه Desired answer.

قد يبدو Labeled email مفاهيميًا هكذا:

```text
المدخل (Input): نص البريد
التسمية (Label): spam
```

وقد يبدو Example لتوقع Car price هكذا:

```text
الـ Input features:
- المسافة المقطوعة (mileage)
- العمر
- العلامة التجارية
- سعة المحرك

الهدف (Target):
- السعر
```

أكثر نوعين شيوعًا من Supervised tasks هما **classification** و**regression**.

**Classification** تتنبأ بـ Category:

```text
spam / ليست spam
قطة / كلب
احتيال / مشروع
```

**Regression** تتنبأ بقيمة Numeric:

```text
سعر المنزل
الإيراد
درجة الحرارة
درجة الرضا عن الحياة
```

غالبًا يُستخدم مصطلحا **label** و**target** بصورة متقاربة، لكن "label" شائع أكثر في Classification و"target" شائع أكثر في Regression.

**Feature** هي Input variable تستخدمها Model لإنتاج Prediction. وتُسمى Features أحيانًا Predictors أوAttributes.

هناك Naming trap مهم: **logistic regression تستخدم غالبًا للتصنيف** رغم وجود كلمة “regression” في اسمها، لأن Output الخاصة بها يمكن تفسيرها كـ Class probability.

### Unsupervised Learning

في **unsupervised learning**، لا توجد Target labels مقدمة مع Data. يبحث System عن Structure مفيدة.

تشمل Unsupervised tasks المهمة:

**Clustering**

تجميع Examples المتشابهة معًا من دون أن تُعطى أسماء Groups مسبقًا. قد تكتشف شركة Customer segments من Browsing وPurchasing behavior.

**Dimensionality reduction**

تمثيل Structure المهمة لعدد كبير من Features باستخدام Dimensions أقل. قد يقلل ذلك Storage وComputation ويزيل Redundancy ويحسن Learning أحيانًا.

إذا دُمجت عدة Original variables داخل Representation أكثر فائدة، فهذا شكل من **feature extraction**.

**Visualization**

تحويل High-dimensional data المعقدة إلى بعدين أوثلاثة حتى يستطيع Humans فحص Structure.

**Anomaly detection**

تعلم شكل Normal data واكتشاف Unusual cases مثل Suspicious transactions أوManufacturing defects.

**Novelty detection**

اكتشاف Examples تختلف عن Clean training distribution. وهي تشبه Anomaly detection، لكن Novelty detection تفترض عادةً أن Training set نفسها تحتوي Normal examples فقط.

**تعلّم قواعد الارتباط: Association rule learning**

اكتشاف Relationships مثل:

```text
العملاء الذين يشترون A وB كثيرًا يميلون أيضًا إلى شراء C
```

وهذا مفيد لاكتشاف Co-occurrence patterns داخل Transactional data.

### التعلم شبه الخاضع للإشراف: Semi-Supervised Learning

غالبًا تكون Real datasets معظمها Unlabeled لأن Labeling مكلفة.

تجمع **semi-supervised learning** بين:

```text
كمية صغيرة من البيانات المصنّفة (labeled)
+
كمية أكبر بكثير من البيانات غير المصنّفة (unlabeled)
```

افترض أن Photo system تنفذ Clustering للوجوه وتكتشف أن Images كثيرة تحتوي Person نفسها. قد يحتاج Human إلى تسمية هذا الشخص مرة واحدة فقط، ثم يمكن لـ System نشر هذه Information إلى Similar images.

Pattern شائعة هي:

1. اكتشاف Structure باستخدام Unlabeled data،
2. استخدام عدد قليل من Labels لتحديد Groups،
3. Training أوRefinement لـ Supervised model باستخدام Expanded labeled set.

### التعلم ذاتي الإشراف: Self-Supervised Learning

تبدأ **self-supervised learning** بـ Unlabeled data لكنها تنشئ Prediction task من Data نفسها.

في Image، قد تخفي جزءًا من Image وتطلب من Model إعادة بناء Missing region.

مفاهيميًا:

```text
المثال الأصلي
      |
إنشاء مهمة تعلم اصطناعية
      |
المدخل: مثال مشوَّه أو محجوب جزئيًا (masked)
الهدف: معلومات مشتقة من المثال الأصلي
```

الفكرة الحاسمة أن Human لم يضع Target يدويًا. Data أنشأت Supervision الخاصة بها.

يمكن إعادة استخدام Representation المتعلمة في Task أخرى. وهذا قريب جدًا من **transfer learning**: Knowledge تعلمتها Model في Task تُعاد للاستفادة منها في Task أخرى.

مثلًا:

```text
مجموعة صور كبيرة غير مصنّفة
        |
تدريب مسبق ذاتي الإشراف (self-supervised pretraining)
        |
تمثيل بصري عام
        |
Dataset صغيرة مصنّفة لصور الحيوانات الأليفة
        |
الضبط الدقيق (fine-tuning)
        |
مصنِّف للحيوانات الأليفة
```

غالبًا تتبع Large pretrained models هذه Pattern العامة: تعلم Useful representations من كميات هائلة من Raw data، ثم Adapt لهذه Representations نحو Downstream tasks.

### Reinforcement Learning

تستخدم **reinforcement learning (RL)** نوعًا مختلفًا من Learning signal.

يتفاعل **agent** مع **environment**:

```text
رصد الحالة (state)
    |
اختيار إجراء (action)
    |
تتغير البيئة
    |
تلقي مكافأة أو عقوبة
    |
تحسين السياسة (policy)
```

تصف **policy** أي Action ينبغي أن تختارها Agent في Situation معينة.

Goal ليست Predict لـ Fixed label فقط. Goal هي اختيار Sequence من Actions تحقق Reward مرتفعة مع مرور Time.

Robotic control وGame-playing agents أمثلة كلاسيكية.

### يمكن دمج Categories مع تصنيفات أخرى

لا يكون System مجرد "supervised" أو"online". هذه Properties تصف Dimensions مختلفة.

يمكن أن تكون Spam filter:

```text
خاضع للإشراف (supervised)
+
متصل (online)
+
قائم على نموذج (model-based)
```

هذه Labels ليست متنافسة، بل تجيب عن أسئلة مختلفة حول System نفسها.

يشير Chapter سريعًا إلى Categories إضافية:

- **Ensemble learning:** دمج Predictions من Models متعددة.
- **Federated learning:** Training عبر Devices أوLocations متعددة من دون تجميع كل Raw data مركزيًا.
- **Meta-learning:** تعلم كيفية Adapt بسرعة إلى Tasks جديدة.

لا تحتاج إلى إتقان هذه الآن. المهم أن Machine Learning تحتوي عدة طرق متداخلة لتصنيف Systems.

## 3. Batch Learning مقابل Online Learning

تصنيف ثانٍ يسأل:

**هل تستطيع Model أن تتعلم Incrementally مع وصول Data جديدة؟**

### Batch Learning

في **batch learning**، تُدرّب Model على Training data المتاحة بوصفها Process منفصلة. وبعد Deployment، تنفذ Predictions عادةً من دون الاستمرار في Learning.

Cycle مبسطة هي:

```text
جمع البيانات
    |
تدريب نموذج من الـ Dataset
    |
التقييم
    |
النشر (deploy)
    |
الاستخدام في الاستدلال (inference)
    |
جمع بيانات أحدث
    |
تدريب نسخة جديدة من النموذج
```

يُنفذ هذا Training عادةً Offline، ولهذا ترتبط Batch learning غالبًا بمصطلح **offline learning**.

Batch learning بسيطة وموثوقة عندما يتغير العالم ببطء. لكن Retraining من الصفر على Dataset كبيرة قد يتطلب قدرًا كبيرًا من:

- CPU أوGPU compute،
- Memory،
- Disk capacity،
- Disk I/O،
- Network I/O،
- Time،
- Money.

### Data Drift

تعيش Deployed model داخل عالم متغير.

إذا تغيرت العلاقة بين Data وTask، فقد تتدهور Performance تدريجيًا. يصف Chapter هذا باسم **data drift** أو**model rot**.

قد تواجه Spam filter طرق Spam جديدة. وقد تواجه Finance model تغيرًا في Market behavior. وحتى Image classifier قد تتأثر بتغير Cameras أوImage formats أوLighting أوResolution أوUser behavior.

الحل ليس "درّب مرة واحدة وانسَ". يحتاج Production system إلى Monitoring واستراتيجية Update.

### Online Learning

في **online learning**، تتعلم System بصورة Incremental.

تُعالج New examples واحدة في كل مرة أوضمن Groups صغيرة تسمى **mini-batches**.

```text
بيانات جديدة -> خطوة تعلم -> نموذج محدَّث
بيانات جديدة -> خطوة تعلم -> نموذج محدَّث
بيانات جديدة -> خطوة تعلم -> نموذج محدَّث
```

قد تكون كل Update أرخص بكثير من Retraining كامل من الصفر.

تكون Online learning جذابة عندما:

- تتغير Data بسرعة،
- يجب أن يستجيب System بسرعة،
- تكون Resources محدودة،
- أوتكون Dataset أكبر من أن تدخل في Memory.

### التعلم خارج الذاكرة: Out-of-Core Learning

قد تكون Dataset ضخمة جدًا ولا تدخل في RAM.

يمكن لـ Online-capable algorithm معالجتها Piece by Piece:

```text
تحميل الجزء 1 -> تحديث النموذج
تحميل الجزء 2 -> تحديث النموذج
تحميل الجزء 3 -> تحديث النموذج
...
```

وهذا يسمى **out-of-core learning**.

هناك تحذير مهم في المصطلحات: قد تُنفذ Out-of-core learning Offline بالكامل. كلمة "online" هنا تشير إلى **incremental updating**، وليس بالضرورة إلى Live internet-connected production system.

### Learning Rate

يحتاج Online system إلى تحديد مقدار قوة استجابته لـ New observations.

تتحكم **learning rate** في حجم أوSpeed الخاصة بـ Adaptation.

Learning rate مرتفعة:

- تتكيف بسرعة،
- تستجيب بقوة لـ New data،
- لكنها قد تنسى Patterns قديمة مفيدة أوتستجيب لـ Noise.

Learning rate منخفضة:

- تتكيف ببطء،
- تكون أكثر Stability،
- لكنها قد تتأخر عن Genuine changes.

إذا تغير System بعنف أكثر من اللازم وفقد Knowledge مفيدة سبق تعلمها، يصف Chapter ذلك باسم **catastrophic forgetting** أو**catastrophic interference**.

### لماذا تحتاج Online Learning إلى Monitoring؟

تُدخل Incremental learning خطرًا مهمًا: يمكن لـ Bad incoming data أن تفسد Model بسرعة.

قد تأتي Bad data من:

- Broken sensors،
- Software bugs،
- Corrupted records،
- Unusual outliers،
- Deliberate manipulation لنظام Live.

لذلك تحتاج Online learning في Production إلى Safeguards:

```text
مراقبة بيانات الإدخال
مراقبة أداء النموذج
اكتشاف السلوك غير الطبيعي
إيقاف التعلم مؤقتًا عند الضرورة
الرجوع إلى نموذج معروف الجودة عند الحاجة (rollback)
```

Online learning ليست "أفضل تلقائيًا" من Batch learning. إنها تستبدل جزءًا من Retraining cost وزمن الاستجابة بمخاطر تشغيلية إضافية.

## 4. Generalization: Instance-Based مقابل Model-Based Learning

الهدف المركزي من Machine Learning ليس تحقيق Performance مثالية على Examples التي رأت Model مسبقًا.

الهدف هو **generalization**:

> تحقيق Performance جيدة على Cases جديدة لم تُرَ من قبل.

Approachان رئيسيان في Chapter هما **instance-based learning** و**model-based learning**.

### التعلم القائم على الأمثلة: Instance-Based Learning

تحتفظ Instance-based learning بـ Training examples، أوبتمثيل مفيد لها، وتتنبأ عبر مقارنة New case بحالات معروفة.

أبسط فكرة هي:

```text
مثال جديد
    |
إيجاد أمثلة تدريب مشابهة
    |
استخدام نتائجها للتنبؤ
```

تحدد Similarity measure معنى "قريب".

في Spam system بسيط، قد تعتمد Similarity على الكلمات المشتركة. وفي Numerical dataset، قد تكون Distance هندسية بين Feature vectors.

Example معروف هو **k-nearest neighbors (k-NN)**.

إذا كان `k = 3`، تجد Algorithm أقرب ثلاث Known examples وتدمج Labels أوNumeric targets الخاصة بها.

قد تشمل المزايا Simplicity وPerformance جيدة في بعض Datasets الصغيرة أوالمتغيرة.

وتشمل القيود:

- تخزين أوالوصول إلى Training instances كثيرة أثناء Prediction،
- Searches قد تكون بطيئة،
- صعوبة مع Very high-dimensional data،
- اعتماد قوي على Similarity measure المختارة.

### التعلم القائم على النموذج: Model-Based Learning

تأخذ Model-based learning مسارًا مختلفًا:

```text
أمثلة التدريب
      |
اختيار عائلة نماذج
      |
تعلّم معاملات النموذج
      |
النموذج المدرَّب
      |
التنبؤ بالحالات الجديدة
```

بدل البحث في Training set مع كل Prediction، تضبط Algorithm Model تلخص Pattern في Data.

### Model Selection وParameters وTraining

افترض أننا نعتقد أن Life satisfaction لها علاقة تقريبًا Linear مع GDP per capita.

يمكن كتابة Linear model بسيطة كالتالي:

```text
predicted_life_satisfaction = theta_0 + theta_1 * GDP_per_capita
```

`theta_0` و`theta_1` هما **model parameters**.

اختيار Linear relationship هو جزء من **model selection**.

أما العثور على Parameter values تناسب Training data فهو **training**.

تحتاج Learning algorithm إلى Objective. تقيس **cost function** أو**loss function** مقدار سوء Predictions. يبحث Training عن Parameter values تقلل هذه Cost.

وتعبر **utility function** أو**fitness function** عن الفكرة العكسية: مقدار جودة Model.

### Example مختصر باستخدام Scikit-Learn

يعرض Source chapter Workflow باستخدام Linear regression model. Pattern البرمجية المهمة هي:

```text

   ->
فصل الـ features X عن الهدف y
   ->

   ->
```

`model.predict(X_new)` هي **inference**: استخدام Trained model على New input.

### Parameters مقابل Hyperparameters

هذا التمييز أساسي.

**Model parameter** هي Value تُتعلم أثناء Training.

أمثلة:

```text
ميل الانحدار الخطي (slope)
الجزء المقطوع في الانحدار الخطي (intercept)
أوزان الشبكة العصبية
```

أما **hyperparameter** فتتحكم في Learning process أوModel configuration وتُختار خارج عملية Parameter fitting العادية.

تشمل الأمثلة:

```text
قوة الـ Regularization
عدد الجيران k
عمق الشجرة
معدل التعلم (learning rate)
```

أنت تختار أوTuning للـ Hyperparameters؛ أما Training algorithm فتتعلم Model parameters.

### سير عمل Machine Learning المعتاد

على مستوى High-level:

1. افهم Problem وحدد Task.
2. اجمع Data وافحصها.
3. اختر Features مفيدة وTarget إذا كانت Task supervised.
4. اختر Model family.
5. حدد Evaluation أوOptimization objective.
6. درّب Model.
7. قيّمها على Data لم تُستخدم في Fitting.
8. حسّن Data أوFeatures أوModel أوHyperparameters.
9. انشر Final model.
10. استخدمها في Inference وراقبها.

هذه Loop أهم من أي Algorithm واحدة. أغلب ML work الحقيقية تتكون من تحسين أجزاء مختلفة من هذا System بصورة متكررة.

## 5. قد تنجح Data في النظام أوتفشله

يلخص Chapter أسباب فشل ML بصورة مفيدة:

```text
بيانات سيئة
أو
نموذج سيئ
```

عمليًا، تكون مشكلات Data غالبًا أول مكان ينبغي فحصه.

### Training Data غير كافية

تحتاج معظم Machine-learning algorithms إلى Examples كثيرة لتتعلم Pattern مستقرة.

قد تجعل Dataset صغيرة جدًا Model حساسة للصدفة. وقد تتطلب Tasks معقدة في Perception مثل Speech أوImage recognition Datasets ضخمة جدًا ما لم يستطع Project إعادة استخدام Pretrained model عبر Transfer learning.

الدرس الأعمق ليس "اجمع Data أكثر دائمًا"، بل:

**يجب أن تكون كمية Data كافية لتعقيد Task وتنوع العالم الحقيقي ومرونة Model.**

### Data مقابل تطور Algorithm

يناقش Chapter Research توضح أنه في بعض Tasks الصعبة قد تصل Algorithms مختلفة جدًا إلى Performance متقاربة عندما تتوفر Data كافية.

هذا **لا** يعني أن Algorithm choice غير مهمة.

بل يعني أن تحسين Dataset قد يمنح أحيانًا Gains أكبر من الاستمرار بلا نهاية في Tuning للـ Algorithm.

Mindset هندسية عملية هي:

```text
لا تحسّن النموذج وحده.
اسأل هل البيانات الأفضل أو الأوسع أو الأنظف أو الأكثر تمثيلًا هي التحسين الأعلى قيمة.
```

### Training Data غير ممثلة

تتعلم Model مما تراه.

إذا اختلفت Training sample عن Cases التي ستقابلها لاحقًا، فقد لا تعني Good training performance الكثير.

قد يحدث ذلك بسبب:

- أجزاء مفقودة من Population،
- جمع Data من Biased source،
- اختيار Popular أوEasy examples فقط،
- Geographic أوDemographic imbalance،
- Changes بين وقت Training ووقت Deployment.

قد تكون Sample صغيرة غير ممثلة بسبب **sampling noise**.

وقد تكون Sample كبيرة أيضًا غير ممثلة بسبب Flawed collection process. وهذا هو **sampling bias**.

**Nonresponse bias** حالة خاصة: الأشخاص أوEntities التي تستجيب تختلف بصورة منهجية عن التي لا تستجيب.

الدرس الأساسي:

> حجم Dataset لا يصلح Sampling process متحيزة من الأساس.

### البيانات رديئة الجودة: Poor-Quality Data

قد تحتوي Training data على:

- Incorrect measurements،
- Duplicate records،
- Corrupted inputs،
- Mislabeled examples،
- Extreme outliers،
- Missing values،
- Inconsistent formats.

قرارات Cleaning جزء من Modeling.

بالنسبة إلى Missing values، قد تشمل الخيارات:

- حذف Rows المتأثرة،
- حذف Feature،
- Fill للقيم المفقودة باستراتيجية محددة،
- بناء Handling مختلف للحالات التي لا تتوفر فيها تلك Feature.

لا توجد إجابة عامة واحدة. يعتمد القرار على سبب Missing value وكيف ستُستخدم Model.

### Irrelevant Features

المزيد من Features ليس أفضل تلقائيًا.

قد تضيف Irrelevant inputs Noise، وتزيد Computational cost، وتمنح Flexible models فرصًا أكبر لاكتشاف Accidental patterns.

تشمل **feature engineering**:

- **feature selection:** الاحتفاظ بأكثر Existing features فائدة،
- **feature extraction:** دمج Existing features أوTransform لها،
- **creating new features:** جمع أوDerive معلومات إضافية.

قاعدة مفيدة:

```text
مدخلات رديئة -> مخرجات رديئة
```

لكن "garbage" لا تعني Errors فقط. قد تعني أيضًا Data صحيحة تقنيًا لكنها غير ذات صلة بـ Prediction task.

## 6. Overfitting وUnderfitting وRegularization

يجب أن تتعلم Model Structure كافية لحل Task من دون أن تتعلم Accidental details لا تعمم.

هذا هو التوتر بين **underfitting** و**overfitting**.

### Overfitting

تحدث **overfitting** عندما تحقق Model Performance قوية جدًا على Training data لكنها ضعيفة على New data.

تكون Model قد تعلمت عمليًا Patterns خاصة بـ Training sample بدل Stable properties للمشكلة.

يزداد احتمال ذلك عندما:

- تكون Model مرنة جدًا،
- تكون Training set صغيرة،
- تكون Data Noisy،
- توجد Irrelevant features.

قد تكتشف Complex model قواعد عرضية تصادف أنها صحيحة داخل Training set لكن بلا Predictive meaning حقيقي.

### كيف نقلل Overfitting؟

يقدم Chapter ثلاث Strategies رئيسية:

1. **بسّط Model.**
2. **اجمع Training data أكثر.**
3. **قلل Noise أوصحح Data problems.**

قد يعني Simplifying:

- استخدام Parameters أقل،
- استخدام Features أقل،
- فرض Constraints على Model.

### Regularization

**Regularization** تقيد Model عمدًا لتقليل Risk الخاصة بـ Overfitting.

الفكرة Trade-off:

```text
مرونة زائدة
-> قد يلائم الضوضاء

مرونة قليلة جدًا
-> قد يفوّت البنية الحقيقية

Regularization مناسبة
-> مرونة كافية للتعلم، وقيد كافٍ للتعميم
```

بالنسبة إلى Linear model، قد تمنع Regularization parameters من أن تصبح Extreme. وقد تحقق Model Fit أسوأ قليلًا على Training data لكنها تتنبأ بصورة أفضل على Unseen examples.

[[IMAGE_NEEDED: Regularization and generalization (Figure 1-24; key: regularization-reduces-overfitting) | Recreate the source comparison of linear models where the regularized model fits the original training examples less aggressively but generalizes better to examples that were not used during fitting | Learner should notice that the best training fit is not necessarily the best model for unseen data]]

**Regularization strength** هي Hyperparameter. إذا كانت ضعيفة جدًا، قد Overfit Model. وإذا كانت قوية جدًا، قد تصبح Model أبسط من اللازم.

### Underfitting

تحدث **underfitting** عندما تكون Model بسيطة جدًا بحيث لا تستطيع التقاط Structure المهمة في Data.

من Signs الشائعة Poor performance حتى على Training set.

تشمل Fixes الممكنة:

1. اختيار Model أقوى،
2. إنشاء أوتحديد Features أفضل،
3. تقليل Constraints أوRegularization المفرطة.

### شخّص قبل أن "تحسن"

خطأ Beginner شائع هو الاستجابة لكل Poor result باختيار Model أعقد.

بدلًا من ذلك، قارن Evidence.

```text
أداء التدريب ضعيف
-> اشتبه في underfitting أو features رديئة أو بيانات صعبة/مليئة بالضوضاء

أداء التدريب قوي
لكن أداء validation/test ضعيف
-> اشتبه في overfitting
```

ينبغي أن يكون Model complexity استجابة للتشخيص، لا Goal افتراضيًا.

### Deployment مصدر آخر للفشل

حتى Model دقيقة قد تكون غير مناسبة لـ Production.

تشمل Deployment problems المحتملة:

- Model بطيئة جدًا،
- Model كبيرة جدًا،
- Memory requirements مرتفعة جدًا،
- System لا تتوسع،
- Security vulnerabilities،
- Maintenance صعبة،
- Model تصبح Stale،
- Retraining مكلفة.

لهذا تحتاج Real ML systems إلى Operational engineering إضافةً إلى Statistical modeling. يشير Chapter إلى **MLOps** بوصفها Discipline تعالج كثيرًا من هذه Production concerns.

## 7. Testing وValidation وModel Selection وData Mismatch

لا تكون Model مفيدة إلا إذا عملت على Cases لم تحفظها مسبقًا.

لذلك يجب أن تحمينا Evaluation من خداع أنفسنا.

### Training Set وTest Set

Strategy أساسية هي تقسيم Data إلى:

```text
مجموعة التدريب (training set)
+
مجموعة الاختبار (test set)
```

تتعلم Model من Training set.

وتقدّر Test set Performance على Unseen data.

يسمى Error على Unseen examples **generalization error** أو**out-of-sample error**.

إذا كان Training error منخفضًا لكن Test error مرتفعًا، فمن المرجح أن Model Overfit.

Split بنسبة `80/20` شائع، لكنه ليس Law. مع ملايين Examples، قد تكون Percentage أصغر بكثير كافية لبناء Test set ضخمة وموثوقة.

### لماذا يجب أن تبقى Test Set غير مستخدمة؟

افترض أنك تقارن Models وأنواع Hyperparameters كثيرة باستخدام Test set.

كل مرة تتخذ قرارًا بسبب Test performance، تدخل Information من Test set في Design.

في النهاية قد تختار Model جيدة بصورة غير عادية على Test set المحددة بدل Model جيدة فعلًا على Future data.

تصبح Test set عمليًا جزءًا من Training.

لهذا تحتاج Model selection إلى Dataset أخرى.

### Validation Set

تستخدم **validation set**، وتسمى أيضًا **development set** أو**dev set**، لاختيار Models وHyperparameters.

Workflow سليمة هي:

```text
training set -> ملاءمة النماذج المرشحة
validation set -> مقارنة المرشحين وضبط الـ hyperparameters
test set -> تقييم النظام النهائي المختار مرة واحدة
```

بعد Model selection، يمكن Retraining لأفضل Configuration باستخدام كل Training data المتاحة للـ Fitting، بما فيها Data التي كانت محتجزة مؤقتًا للـ Validation، ثم تقييمها على Test set التي بقيت غير مستخدمة.

[[IMAGE_NEEDED: Holdout validation workflow (Figure 1-25; key: holdout-validation-workflow) | Recreate the source flow in which multiple models are trained on a reduced training set, compared on a validation/dev set, the best configuration is retrained on the full training data, and the final model is evaluated on the untouched test set | Learner should notice the separate roles of validation data for decisions and test data for final generalization estimation]]

### Cross-Validation

قد تكون Validation set واحدة غير مستقرة عندما تكون Data محدودة.

إذا كانت صغيرة جدًا، تصبح Performance estimate Noisy.

وإذا كانت كبيرة جدًا، يبقى Data أقل من اللازم لـ Fitting للـ Candidate models.

تغير **cross-validation** الجزء الذي يعمل كـ Validation data عدة مرات.

مفاهيميًا:

```text
التقسيم 1: التدريب على معظم الطيات، والتحقق على الطية A
التقسيم 2: التدريب على معظم الطيات، والتحقق على الطية B
التقسيم 3: التدريب على معظم الطيات، والتحقق على الطية C
...
حساب متوسط نتائج التحقق
```

يعطي ذلك Estimate أكثر Stability مقابل تكلفة Training لـ Model عدة مرات.

### Data Mismatch

أحيانًا تكون Training data الوفيرة سهلة الحصول، لكن Production data الحقيقية نادرة.

مثال:

```text
بيانات التدريب: صور زهور منزَّلة من الويب
بيانات الإنتاج: صور زهور التقطها المستخدمون بتطبيق جوال
```

قد تختلف Distributions في:

- Camera quality،
- Framing،
- Lighting،
- Backgrounds،
- Resolution،
- User behavior.

ينبغي أن تشبه Validation وTest sets **Production data التي تهمك فعلًا**، لا مجرد Abundant training source.

لكن هذا ينشئ Diagnostic problem.

إذا كانت Model ضعيفة على Production-like dev set، فهل السبب:

```text
هل يحدث overfitting لمصدر التدريب؟
أو
هل يعاني من عدم تطابق بين مصدر التدريب وبيانات الإنتاج؟
```

### مجموعة Train-Dev Set

تساعد **train-dev set** في الفصل بين التفسيرين.

استخدم Data من Source نفسها الخاصة بـ Training set، لكن لا تستخدمها في Training.

ثم قارن:

```text
training set:
تُستخدم لملاءمة النموذج

train-dev set:
التوزيع نفسه لبيانات التدريب
لا تُستخدم للملاءمة
تساعد على تشخيص overfitting

dev set:
توزيع شبيه ببيانات الإنتاج
تُستخدم لتطوير النموذج
تساعد على كشف عدم تطابق البيانات

test set:
توزيع شبيه ببيانات الإنتاج
تُستخدم للتقييم النهائي
```

التفسير:

```text
أداء train-dev ضعيف
-> النموذج لا يعمّم حتى على توزيع التدريب
-> اشتبه في overfitting أو مشكلات أخرى في النموذج/البيانات

أداء train-dev جيد
لكن أداء dev ضعيف
-> اشتبه في عدم تطابق البيانات (data mismatch)
```

### فكرة No Free Lunch

اختيار Model يعني وضع Assumptions.

Linear model تفترض أن Structure خطية تقريبًا مفيدة كـ Approximation.

أما Model أكثر Flexibility فتضع Assumptions مختلفة وتستطيع تمثيل Patterns مختلفة.

يقول **No Free Lunch theorem** إنه إذا لم تضع أي Assumptions حول Data-generating problem، فلا توجد Learning algorithm مضمونة أن تكون أفضل من كل Algorithms الأخرى على كل Problem ممكنة.

النتيجة العملية:

> لا تبحث عن Model "الأفضل عالميًا".

بدلًا من ذلك:

1. استخدم Knowledge الخاصة بالمشكلة لاختيار مجموعة صغيرة من Approaches معقولة،
2. قارنها باستخدام Validation سليمة،
3. اترك Test set للتقدير النهائي.

```text
        |

        |

        |
```

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> إذا كانت Model تمتلك Training error قريبًا من الصفر، فلا بد أنها ممتازة.

### لماذا هذا خطأ

Training performance توضح فقط مدى جودة تعامل Model مع Examples التي استُخدمت أثناء Learning. تستطيع Model شديدة Flexibility أن تحفظ أوتستغل Accidental patterns. الهدف الحقيقي هو Generalization إلى Unseen data.

### المفهوم الخاطئ 2

> المزيد من Data يصلح المشكلة دائمًا.

### لماذا هذا خطأ

تفيد Data الإضافية فقط عندما تكون ذات صلة وتمثل Population بدرجة كافية. ملايين Examples المتحيزة أوالخاطئة في Labeling قد تنتج System سيئة.

### المفهوم الخاطئ 3

> Online learning تعني أن Model يجب أن تتعلم Live عبر Internet.

### لماذا هذا خطأ

تشير كلمة "Online" إلى Incremental learning. قد تعالج Incremental algorithm Data Offline، بما في ذلك Datasets ضخمة لا تدخل في Memory.

### المفهوم الخاطئ 4

> Hyperparameter مجرد Model parameter أخرى.

### لماذا هذا خطأ

Model parameters تُتعلم من Data أثناء Training. أما Hyperparameters فتضبط Learning process أوModel structure وتُختار خارج Ordinary fitting step.

### المفهوم الخاطئ 5

> Test set هي أفضل مكان لاختيار Models وتنفيذ Tuning للـ Hyperparameters.

### لماذا هذا خطأ

الاستخدام المتكرر لـ Test performance في توجيه Decisions يسرّب Information من Test set إلى Development. استخدم Validation data للقرارات واحتفظ بـ Test set للتقييم النهائي.

| Reinforcement Learning | Learning لـ Policy عبر Actions وRewards داخل Environment |
| Batch Learning | Training على Dataset المتاحة ضمن Full training process منفصلة |
| Online Learning | تحديث Model بصورة Incremental من New examples أوMini-batches |
| التعلم خارج الذاكرة: Out-of-Core Learning | معالجة Incremental لـ Dataset أكبر من Memory |
| Data Drift | تغير في Data أوReal-world relationship قد يقلل Performance الخاصة بـ Deployed model |
| التعلم القائم على الأمثلة: Instance-Based Learning | Predict عبر مقارنة New cases بـ Stored examples |
| التعلم القائم على النموذج: Model-Based Learning | Fitting لـ Predictive model على Training examples واستخدامها في New cases |
| Generalization | تحقيق Performance جيدة على Examples لم تُرَ أثناء Training |
| Model Parameter | Value تتعلم أثناء Model training |
| Hyperparameter | Configuration تُختار خارج Ordinary model-parameter fitting |
| دالة Loss / Cost Function | Function تقيس مقدار سوء Predictions الخاصة بـ Model |
| Inference | استخدام Trained model لإنتاج Predictions |
| Sampling Bias | عدم تمثيل منهجي ناتج عن طريقة Sampling للـ Data |
| Feature Engineering | Selecting أوExtracting أوTransforming أوCreating لـ Useful features |
| Overfitting | Fitting مفرط لـ Training data مع Poor generalization |
| Underfitting | استخدام Model أبسط من أن تلتقط Structure المهمة |
| Regularization | تقييد Model لتقليل Overfitting |
| مجموعة Validation / Dev Set | Data تُستخدم لـ Model selection وHyperparameter tuning |
| Test Set | Held-out data تُستخدم لتقدير Final generalization performance |
| مجموعة Train-Dev Set | Held-out training-distribution data تُستخدم للفصل بين Overfitting وData mismatch |
| Generalization Error | Error مقاسة على Unseen cases |
| MLOps | Engineering practices لنشر وتشغيل ومراقبة وتحديث ML systems |
