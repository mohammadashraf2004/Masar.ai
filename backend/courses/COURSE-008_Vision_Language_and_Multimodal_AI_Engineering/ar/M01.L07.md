## 1. مسار VLM Inference (The VLM inference pipeline)

يعالج text-only LLM text tokens.

أما VLM فيضيف front end إضافية:

```text
صورة (image)
  ↓
معالج الرؤية (vision processor)
  ↓
مشفر الرؤية (vision encoder)
  ↓
visual tokens — tokens مرئية
  ↓

text prompt — prompt نصية
  ↓
text embeddings — embeddings نصية
  ↓

سياق visual + text
  ↓
LLM — نموذج اللغة
  ↓
generated tokens — tokens مولدة
```

قد يعالج vision encoder الصورة مرة واحدة فقط.

لكن visual tokens الناتجة تظل جزءًا
من model context أثناء توليد النص.

وهذا مهم لأن كل visual token تسهم في:

- طول context؛
- عمل attention؛
- ذاكرة KV cache.

ولهذا غالبًا ما تستهلك المحادثة multimodal الطويلة
memory أكبر من text-only chat مماثلة.

## 2. المقارنة بين Prefill و Decode (Prefill versus decode)

يتكون Transformer inference من مرحلتين.

### 2.1 مرحلة Prefill

يعالج Model كامل input context.

وقد يتضمن هذا context:

- عناصر visual tokens؛
- محتوى system prompt؛
- conversation history — سجل المحادثة؛
- prompt المستخدم الحالية.

أثناء prefill، يمكن معالجة العديد من tokens بالتوازي.

كما ينشئ Model الـ KV cache الأولية.

مفاهيميًا:

```text
جميع input tokens
      ↓
معالجة Transformer بالتوازي (parallel transformer processing)
      ↓
KV cache + أول next-token logits
```

يصف المصدر prefill بأنها **compute-bound** لأن عمليات
matrix الكبيرة يمكن أن تشغل GPU بكثافة.

### 2.2 مرحلة Decode

بعد أول output token، تصبح generation من نوع autoregressive:

```text
ولّد token واحدة
      ↓
أضفها
      ↓
ولّد next token
      ↓
كرر
```

يُعاد استخدام K/V tensors السابقة من cache.

ولا يلزم حساب سوى state الخاصة بالـ token الجديدة.

ومع ذلك، يجب قراءة model weights و KV cache
التي تكبر تدريجيًا بصورة متكررة.

لذلك يصف المصدر decode بأنها **memory-bound**.

### 2.3 أي مرحلة تهيمن؟

input كبير:

```text
صورة كبيرة (large image)
عدة صور (multiple images)
فيديو (video)
محادثة طويلة جدًا (very long conversation)
```

يمكن أن يجعل prefill مكلفة.

output طويل:

```text
input صغير
+
استجابة بطول 500-token
```

يمكن أن يجعل decode هي المهيمنة.

### قاعدة تقريبية مذكورة في المصدر (Source-reported heuristic)

يذكر الفصل قاعدة crossover تقريبية تفيد بأن input length عندما يتجاوز
تقريبًا 10× output length يميل إلى جعل prefill هي المهيمنة.

تعامل مع ذلك باعتباره heuristic من المصدر، وليس ثابتًا عالميًا.

يمكن أن تغيّر hardware و model architecture و kernel
implementation و batching نقطة crossover.

## 3. Metrics المهمة (Metrics that matter)

يحتاج Deployment optimization إلى أهداف قابلة للقياس.

يركز الفصل على اثنين منها.

### الزمن حتى أول Token (Time to first token — TTFT)

```text
وصول request
      ↓
ظهور أول output token
```

يؤثر TTFT بقوة في الإحساس بسرعة الاستجابة.

يقترح المصدر:

```text
< 500 ms
```

كهدف جيد للتطبيقات التفاعلية، ويشير إلى
أن التأخير لعدة ثوانٍ يبدو بطيئًا.

هذه إرشادات من المصدر وليست SLA عالمية.

### Tokens في الثانية (Tokens per second)

يقيس هذا سرعة generation.

مثال:

```text
50 tokens / second — سرعة توليد
```

### أعلى GPU Memory (Peak GPU memory)

يحدد ذلك ما إذا كان:

- request يمكن أن تعمل ضمن memory؛
- عدة requests يمكن أن تعمل بالتزامن؛
- batch أكبر ممكنًا.

### Throughput المطبّع حسب Memory (Memory-normalized throughput)

يقترح المصدر:

```text
tokens / second / GB — throughput لكل GB
```

لماذا؟

النموذج A (Model A):

```text
50 tok/s — معدل throughput
10 GB — حجم memory
= 5 TPS/GB — الكفاءة
```

النموذج B (Model B):

```text
40 tok/s — معدل throughput
4 GB — حجم memory
= 10 TPS/GB — الكفاءة
```

رغم أن B أبطأ في request واحدة، فقد يكون إعدادًا أفضل للخادم
لأن عددًا أكبر من requests قد يتسع على GPU نفسه.

وهذا يبرز درسًا مهمًا في deployment:

> أقل latency لطلب واحد وأعلى fleet
> throughput ليسا الهدف نفسه.

## 5. KV Cache: وفّر Compute مقابل استهلاك Memory

من دون caching، ستتطلب كل token جديدة مولدة إعادة
حساب keys و values لكل tokens السابقة.

يتجنب KV caching ذلك.

### أثناء Prefill

احسب:

```text
K and V — مفاتيح وقيم Attention
```

لجميع context tokens.

ثم خزّنها.

### أثناء Decode

لكل token جديدة:

```text
احسب K/V للـ token الجديدة
أضفها إلى cache
نفّذ attention على history المخزنة
```

لذلك تكبر cache مع sequence length.

وهذا يستبدل:

```text
memory ↑ — استهلاك memory أعلى
مقابل
repeated computation ↓ — حسابات مكررة أقل
```

## 6. حساب KV-cache Memory

يعطي المصدر:

```text
KV cache per token — حجم KV cache لكل token
=
2
× layers — عدد الطبقات
× number of KV heads — عدد رؤوس KV
× head dimension — بُعد الرأس
× bytes per element — عدد bytes لكل عنصر
```

يمثل العامل الأول `2`:

```text
K + V
```

إذا استُخدم FP16:

```text
bytes per element = 2 — عدد bytes لكل عنصر
```

### مثال المصدر: SmolVLM2 2.2B

يستخدم المصدر:

```text
layers      = 24 — عدد layers
KV heads    = 32 — عدد KV heads
head dim    = 64 — بُعد head
FP16 bytes  = 2 — bytes لكل عنصر
```

إذًا:

```text
2 × 24 × 32 × 64 × 2 — الحساب
= 196,608 bytes — الحجم بالـ bytes
≈ 192 KiB per token — الحجم التقريبي لكل token
```

لـ 1,000 tokens:

```text
≈ 187.5 MiB
```

قبل الضرب في batch size.

### لماذا تكون VLMs حساسة؟

يذكر المصدر أن صورة واحدة قد تضيف
مئات إلى آلاف visual tokens.

وتشغل هذه tokens أيضًا KV cache.

في multi-turn conversations، قد يظل visual context
موجودًا بينما تستمر text history في النمو.

لذلك:

```text
visual tokens — tokens مرئية
+
conversation history — سجل المحادثة
+
generated output — output مولدة
```

تتنافس جميعها على memory.

## 7. أساليب MHA و GQA و MQA

إحدى طرق تقليل KV cache هي مشاركة K/V heads.

### الانتباه متعدد الرؤوس (Multi-Head Attention — MHA)

لكل query head مجموعة K/V heads المقابلة الخاصة بها.

مفاهيميًا:

```text
Q1 → K1,V1
Q2 → K2,V2
Q3 → K3,V3
...
```

وهذا يسبب أكبر تكلفة KV-cache بين الأنماط الثلاثة.

### الانتباه المجمع للاستعلامات (Grouped-Query Attention — GQA)

تشارك عدة query heads في رأس K و V واحدة.

مثال:

```text
4 query heads — أربع query heads
share — تشارك
1 K/V head — رأس K و V واحدة
```

وهذا يقلل حجم KV-cache.

### الانتباه متعدد الاستعلامات (Multi-Query Attention — MQA)

تشارك جميع query heads في زوج K/V واحد لكل layer.

وهذا يقلل KV memory أكثر.

يقدم المصدر GQA باعتبارها توازنًا بين:

- الكفاءة (efficiency)؛
- جودة Model.

## 8. لماذا يكون Inference غالبًا Memory-bound؟

يشدد الفصل على GPU memory hierarchy.

مفاهيميًا:

```text
HBM — ذاكرة GPU الخارجية
كبيرة
عرض نطاق أبطأ (slower bandwidth)
تخزن model weights + KV cache

SRAM — ذاكرة سريعة على chip
صغيرة جدًا
سريعة جدًا
قريبة من compute units
```

يعطي المصدر أرقامًا توضيحية تُظهر فرقًا كبيرًا
في bandwidth بين on-chip SRAM و off-chip HBM.

### لماذا يهم ذلك؟

افترض أن model weights موجودة في HBM.

أثناء generation، يجب نقل هذه weights إلى compute units.

حتى إذا استطاعت tensor cores تنفيذ matrix multiplications
بسرعة شديدة، فقد تقضي وقتًا في انتظار البيانات.

وهذا ينشئ **memory wall**.

### تجربة فكرية من المصدر (Source thought experiment)

ينظر الفصل إلى Model ضخم جدًا باستخدام FP16 ويقسم:

```text
weight size — حجم weights
/
HBM bandwidth — عرض نطاق HBM
```

لتقدير حد أدنى لزمن streaming الخاص بالـ weights لكل token.

النقطة ليست الرقم الدقيق.

بل الفكرة هي:

> الحساب الأسرع لا يفيد إذا لم تستطع memory
> توفير weights بالسرعة الكافية.

وهذا يفسر لماذا تقلل كثير من inference optimizations من **data movement**.

```text

→ بيانات HBM أقل لنقلها
```


### التجميع في دفعات (Batching)

```text

عبر عدة requests
```

تحسن هذه التقنيات أجزاء مختلفة من النظام نفسه.

## 10. لماذا تنقل Standard Attention بيانات كثيرة جدًا؟

معادلة standard attention:

```text
softmax(QKᵀ / √d)V — معادلة Attention
```

في implementation ساذج، قد يحدث:

```text
1. احسب QKᵀ
2. اكتب attention scores إلى HBM — ذاكرة GPU الخارجية
3. اقرأ scores
4. نفّذ softmax
5. اكتب ناتج softmax إلى HBM — ذاكرة GPU الخارجية
6. اقرأ مرة أخرى
7. اضرب في V
```

الجزء المكلف ليس arithmetic فقط.

بل memory traffic المتكرر.

لـ sequences طويلة:

```text
N × N
```

تصبح attention matrices ضخمة.

sequence بطول 4K تحتوي على:

```text
4096 × 4096 — عدد الأزواج
≈ 16.8 million — نحو 16.8 مليون قيمة
```

score entries لكل head.

وقد يتجاوز ذلك on-chip scratch memory المتاحة.

## 11. FlashAttention: Exact Attention باستخدام Tiling

تتجنب FlashAttention materialization لمصفوفة attention كاملة داخل HBM.

بدلًا من ذلك:

```text
قسّم Q/K/V إلى tiles
      ↓
انقل tile بحجم مناسب إلى SRAM — ذاكرة سريعة على chip
      ↓
احسب مساهمة attention
      ↓
حدّث running softmax/output
      ↓
انتقل إلى tile التالية
```

يشدد الفصل على نقطة رئيسية:

> تحسب FlashAttention exact attention؛ فهي ليست approximation.

تأتي فائدتها من IO-aware algorithm design.

### سلوك Memory (Memory behavior)

يصف المصدر FlashAttention بأنها تقلل attention memory من مصفوفة
materialized بأسلوب O(N²) إلى working memory بمقياس O(N).

### لماذا يمكن أن تكون أسرع؟

عدد أقل من الرحلات بين:

```text
HBM ↔ SRAM
```

يعني effective throughput أعلى.

### التنفيذ الأساسي (`eager`)

هو standard baseline implementation.

ويفيد في:

- التوافق (compatibility)؛
- عمليات debugging؛
- مقارنة baseline.

### تنفيذ Scaled Dot-Product Attention (`sdpa`)

### تنفيذ FlashAttention المحسن (`flash_attention_2`)

- بنية GPU architecture؛
- إصدار CUDA version؛
- دعم package؛

## 13. Quantization من أجل Inference

تخزن Quantization قيم Model بعدد bits أقل.

مثال:

```text
FP16
→ INT8
→ INT4
```

الفائدة:

```text
memory أقل
data movement أقل
```

التكلفة:

```text
دقة عددية أقل (reduced numerical precision)
احتمال فقدان بعض الجودة
احتمال overhead من conversion/dequantization — تقليل precision
```

وهذه نقطة حاسمة:

> weights الأصغر لا تعني تلقائيًا latency أقل.

إذا كان runtime يجب أن:

```text
يحمّل INT4
يفك quantization بصورة منفصلة
ثم ينفّذ الضرب باستخدام FP16 — دقة 16-bit floating point
```

فقد تمحو تكلفة conversion الإضافية مكاسب السرعة.

تصبح Quantization مكسبًا في latency فقط عندما
يكون runtime و kernels محسنين لها.

## 14. W4A16: التكميم للـ Weights فقط (Weight-only Quantization)

يصف المصدر النمط الشائع:

```text
weights     → 4-bit — weights بدقة 4-bit
activations → 16-bit — activations بدقة 16-bit
```

وغالبًا يسمى:

```text
W4A16
```

لماذا نحافظ على activations بدقة أعلى؟

weights ثابتة.

ويمكن quantize لها offline بعناية.

أما activations فتتغير مع كل input.

وقد تؤدي quantization لها ديناميكيًا إلى:

- تكلفة overhead؛
- error إضافي.

لذلك توفر weight-only quantization قدرًا كبيرًا
من memory من دون quantize لكل قيمة وسيطة.

## 15. الحدس وراء Scale و Zero Point

تحوّل linear/affine quantization قيم floating-point إلى مجموعة أصغر من integers.

مفاهيميًا:

```text
float weight — weight من نوع floating point
   ↓
scale + zero point — معاملات quantization
   ↓
integer q — القيمة الصحيحة quantized
```

أثناء inference:

```text
integer q — القيمة الصحيحة quantized
   ↓
إعادة بناء float تقريبي
```

العلاقة المبسطة هي:

```text
w_hat ≈ scale × (q - zero_point) — إعادة البناء التقريبية
```

{{image:linear-quantization-scaling}}

يمكن أن تحصل blocks مختلفة من weights على scales مختلفة.

ويصبح ذلك مهمًا لأن توزيعات weights ليست موحدة.

## 16. مشكلة Outliers

قد تحتوي neural-network weights على قيم كبيرة بصورة غير معتادة.

افترض أن معظم القيم تقع قرب:

```text
-2 to +2
```

لكن توجد قيم قليلة قرب:

```text
-60 to +60
```

إذا كان على quantization scale واحدة أن تمثل النطاق بالكامل،
فإن القيم العادية تحصل على bins خشنة جدًا.

وهذا يضر precision.

### التكميم حسب الكتل (Block-wise Quantization)

بدل scale واحدة لكامل tensor:

```text
قسّم tensor إلى blocks
      ↓
احسب scale واحدة لكل block
```

حينها تؤثر outlier واحدة فقط في block المحلية الخاصة بها.

يربط المصدر هذا المبدأ بأساليب quantization حديثة مثل:

- أسلوب GPTQ؛
- أسلوب AWQ؛
- أساليب GGUF k-quants.

## 32. تقسيم Prefill إلى أجزاء (Chunked Prefill)

## 33. إدارة Attention بالصفحات (PagedAttention)

قد يحجز server ساذج maximum KV-cache block لكل request.

وهذا يهدر memory.

تعامل PagedAttention تخزين cache بصورة أقرب إلى virtual memory.

بدل reservation واحدة كبيرة ومتصلة:

```text
request A → cache blocks — request A تستخدم blocks من cache
request B → cache blocks — request B تستخدم blocks من cache
request C → cache blocks — request C تستخدم blocks من cache
```

تُخصص blocks حسب الحاجة.

الفوائد:

- fragmentation أقل؛
- over-allocation أقل؛
- effective batch sizes أكبر.

## 34. التجميع المستمر في دفعات (Continuous Batching)


```text
ومرة أخرى
```

تعيد Prefix caching استخدام KV states المحسوبة سابقًا.

وقد يقلل ذلك TTFT للـ prefixes المتكررة.

## 38. Cache لمعالجة الصورة المتكررة

قد يطرح المستخدم عدة أسئلة حول صورة واحدة.

من دون caching:

```text
question 1 → vision encoder(image) — السؤال الأول يعيد معالجة الصورة
question 2 → vision encoder(image) — السؤال الثاني يعيد معالجة الصورة
question 3 → vision encoder(image) — السؤال الثالث يعيد معالجة الصورة
```

يصف المصدر إسناد identifier ثابت للصورة حتى يستطيع server
إعادة استخدام visual representation المعالجة.

مفاهيميًا:

```text
image UUID — معرّف ثابت للصورة
      ↓
vision embedding مخزنة في cache
      ↓
إعادة الاستخدام عبر follow-up questions
```

### تصميم Cache Miss

يمكن أن تكون cache:

- قد تعرضت للإخلاء (evicted)؛
- قد مُسحت عند restart.

لذلك يجب أن يتعامل clients مع فقدان cached media object بإعادة إرسال الصورة.

وهذا مبدأ عام جيد في caching:

> ينبغي أن يحسن cache hit الأداء، لا أن يكون شرطًا لصحة النظام.

## 39. افصل Vision Encoder عند Scale كبير

تنفذ معظم VLM requests:

```text
vision encode مرة واحدة
ثم عدة خطوات LLM decode
```

يختلف resource profile بين هاتين المرحلتين.

عند scale كبير، يمكنك فصل:

```text
vision workers — workers لمعالجة الرؤية
و
decoder workers — workers لمرحلة decode
```

وقد تشمل الفوائد:

- توسيع image preprocessing بصورة مستقلة؛
- cache لخصائص الصور المشتركة؛
- إبقاء GPUs المكلفة الخاصة بـ LLM مركزة على decode.

يضع المصدر هذا النمط كخيار مفيد في large multi-GPU
deployments أكثر من الخدمات الصغيرة.

## 44. قراءة `Q4_K_M`

يشرح المصدر اسمًا من أسماء GGUF quantization.

```text
Q4_K_M
```

التفصيل:

### الرمز `Q`

يعني Quantized.

### الرقم `4`

يعني تقريبًا 4-bit weight quantization.

### اللاحقة `_K`

تشير إلى عائلة K-quant block/group quantization.

### اللاحقة `_M`

تشير إلى balanced quality preset وفق شرح المصدر.

يعطي المصدر spectrum:

```text
S → أصغر/أسرع، مع فقد جودة أكبر
M → متوازن
L → أكبر/جودة أعلى
```

قد يتجاوز عدد storage bits الفعلي لكل weight الرقم `4` الظاهر في الاسم لأن:

- قيم scales؛
- بيانات block metadata؛

تستهلك مساحة أيضًا.

## 45. النشر على الأجهزة المحمولة (Mobile Deployment)

على phones، تقليل model size ليس اختياريًا.

يعطي المصدر هذا التصور:

```text
500M parameters — عدد parameters
× 4 bits — دقة كل weight
≈ 250 MB raw weight storage — حجم تخزين weights التقريبي
```

وذلك قبل:

- قيم activations؛
- ذاكرة KV cache؛
- ذاكرة runtime.

وهذا حجم كبير بالفعل بالنسبة إلى mobile application.

لذلك يجمع mobile optimization بين:

- أسلوب quantization؛
- model architecture أصغر؛
- visual tokens أقل؛
- تنفيذ hardware-native.

## 47. حسّن Architecture، وليس Precision فقط

يستخدم الفصل FastVLM/FastViT مثالًا على architecture
مصممة لتقليل تكلفة visual-token.

```text

      ↓
visual tokens أقل
      ↓

      ↓
```

يذكر المصدر تحسينات كبيرة في token count والسرعة لذلك المثال.

> قد يتطلب on-device optimization إعادة تصميم Model،
> لا مجرد quantize لنفس server architecture.

## 49. أنماط Hybrid Edge/Cloud

لا يلزم أن يكون deployment:

```text
100% local — محلي بالكامل
أو
100% cloud — سحابي بالكامل
```

يقدم المصدر عدة hybrid strategies.

### Local-first مع Cloud Fallback

```text
query سهلة
→ VLM محلية صغيرة

query صعبة/غير مؤكدة
→ VLM سحابية
```

الفوائد:

- average latency أقل؛
- cloud cost أقل؛
- قدرة offline للحالات البسيطة.

التحدي:

- escalation logic موثوقة.

### Vision على الجهاز و Language في Cloud

```text
raw image — الصورة الخام
→ vision encoder محلي
→ embedding — تحويلها إلى embedding
→ cloud language system — إرسالها إلى نظام language سحابي
```

الفائدة المحتملة:

- نقل raw media أقل.

يؤطر المصدر هذا باعتباره تحسينًا للخصوصية/bandwidth، لكن
تذكر أن embeddings قد تظل application data حساسة.

### Cache محلية للاستجابة (Local Response Cache)

أعد استخدام النتائج لـ inputs/questions المتكررة.

ويفيد ذلك عندما تتكرر request patterns.

## 50. اختر Deployment من Workload Requirements

لا تبدأ بـ:

```text
"We should use vLLM." — "ينبغي أن نستخدم vLLM."
```

ابدأ بالمتطلبات.

### عبء العمل (Workload)

- مستخدم واحد أم آلاف المستخدمين؟
- interactive chat أم batch jobs؟
- صورة واحدة أم صور كثيرة؟
- إجابات قصيرة أم generation طويلة؟
- هل تتكرر الصور؟
- هل تتكرر system prompts؟

### العتاد (Hardware)

- هل hardware هي NVIDIA GPU؟
- هل hardware هي Apple Silicon؟
- CPU فقط؟
- هل hardware هي mobile NPU؟
- هل البيئة browser WebGPU؟

### متطلبات Product

- هل يجب أن تعمل offline؟
- هل البيانات حساسة للخصوصية؟
- هل نحتاج TTFT منخفضة؟
- هل الهدف maximum throughput؟
- هل الهدف lowest cost؟
- هل نحتاج runtime قابلة للنقل؟

### متطلبات Model

- ما الحجم؟
- ما عدد visual tokens؟
- ما مدى تحمل quantization؟
- ما export path المدعوم؟

ثم اختر:

```text
Transformers — مكتبة Transformers
vLLM — نموذج اللغة
TensorRT-LLM — نموذج اللغة
ONNX Runtime — بيئة تشغيل ONNX
transformers.js — مكتبة Transformers للـ JavaScript
```

يحافظ هذا الدرس على conceptual workflow الموجودة في المصدر
بدل الادعاء بأن كل command ستظل حديثة دائمًا.

مع الحفاظ على workflow المقصودة.

## 52. النموذج الذهني الكامل لـ Deployment

يمكن اختزال الفصل كاملًا في هذا pipeline:

```text

حجم KV cache؟
عرض memory bandwidth؟
    ↓
نفّذ Optimization (OPTIMIZE)

quantization — تقليل precision
compile — ترجمة وتحسين Model
token reduction — تقليل عدد tokens
    ↓
نفّذ Packaging (PACKAGE)
PyTorch — إطار التنفيذ
ONNX — صيغة graph محمولة
TensorRT — Runtime محسنة لـ NVIDIA
```

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: "إذا كانت Model دقيقة، فقد حُل Deployment."

لا.

تضيف production تحديات latency و concurrency و memory و scheduling و security و cost.

### المفهوم الخاطئ 2: "Vision encoding هي تكلفة VLM الإضافية الوحيدة."

تبقى visual tokens أيضًا داخل LLM context و KV cache.

### المفهوم الخاطئ 3: "Decode متوازية عبر Output Tokens."

autoregressive output generation متتابعة عبر generated tokens.

### المفهوم الخاطئ 4: "Model ذات Bits أقل يجب أن تكون أسرع."

ليس بالضرورة.

قد تجعل dequantization kernels البطيئة Model
quantized أبطأ رغم استخدامها memory أقل.

### المفهوم الخاطئ 5: "FlashAttention تقرّب Attention."

يقدمها المصدر باعتبارها exact attention باستخدام algorithm أكثر كفاءة من ناحية IO.

### المفهوم الخاطئ 6: "KV Cache تقلل Memory."

هي تقلل الحسابات المتكررة عن طريق **استخدام memory أكبر**.

### المفهوم الخاطئ 7: "إذا اتسعت Model مرة واحدة، فيمكنها خدمة مستخدمين كثيرين."

تضاعف concurrency ضغط KV-cache و activations.

### المفهوم الخاطئ 8: "Naive Fixed Batching كافية."

تدخل autoregressive requests وتخرج وتنفذ prefill و decode في أوقات مختلفة.

### المفهوم الخاطئ 9: "ONNX Export يتضمن كل Preprocessing تلقائيًا."

غالبًا لا يفعل.

قد تبقى image preprocessing و tokenization ضمن application code.

### المفهوم الخاطئ 10: "TensorRT قابلة للنقل تلقائيًا."

غالبًا ما تكون TensorRT engines خاصة بـ hardware.

### المفهوم الخاطئ 11: "نفّذ Quantization لكل مكونات VLM بالطريقة نفسها."

يجادل المصدر بأن LLM backbone الكبيرة ومكونات vision
الأصغر قد تملك precision trade-offs مختلفة.

### المفهوم الخاطئ 12: "Browser Deployment مجرد Cloud Deployment أصغر."

تهم browser memory و download size ودعم WebGPU و client preprocessing.

### المفهوم الخاطئ 13: "يمكن أن يكون Caching مطلوبًا لصحة النظام."

ينبغي أن تكون cache القوية اختيارية.

إذا حدث cache miss، يجب أن يستطيع النظام إعادة الحساب.

### المفهوم الخاطئ 14: "Public Image URLs Inputs غير ضارة."

يجلب fetching لـ user-controlled URLs مخاطر SSRF و availability.

### المفهوم الخاطئ 15: "Mobile Deployment لا يتطلب سوى Quantization."

تهم أيضًا architecture وعدد visual tokens واختيار
runtime والحدود الحرارية و memory.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| Inference | تشغيل Model مدرّبة لإنتاج outputs |
| مرحلة الإدخال الأولي (Prefill) | معالجة جميع input/context tokens وبناء KV cache الأولية |
| مرحلة التوليد المتتابع (Decode) | توليد output tokens الجديدة بالتتابع |
| الزمن حتى أول token (TTFT) | الزمن حتى ظهور أول generated token |
| معدل الإنتاج (Throughput) | عدد generated tokens لكل وحدة زمن |
| الكفاءة حسب memory (TPS/GB) | throughput مطبّع حسب استخدام memory |
| الإحماء (Warmup) | تشغيلات أولية غير محسوبة زمنيًا لإزالة startup effects |
| ذاكرة KV (KV cache) | attention keys/values المخزنة من tokens السابقة |
| الانتباه متعدد الرؤوس (MHA) | Multi-head attention باستخدام K/V heads منفصلة |
| الانتباه المجمع للاستعلامات (GQA) | Grouped-query attention يشارك K/V heads عبر query groups |
| الانتباه متعدد الاستعلامات (MQA) | Multi-query attention باستخدام مجموعة K/V مشتركة واحدة |
| ذاكرة GPU الخارجية (HBM) | GPU memory كبيرة خارج chip |
| الذاكرة السريعة على chip (SRAM) | memory صغيرة وسريعة على chip |
| مقيد بالذاكرة (Memory-bound) | أداء تحده حركة البيانات أكثر من arithmetic |
| الانتباه السريع (FlashAttention) | exact attention implementation واعية بـ IO وتستخدم tiling |
| Quantization للـ weights فقط (Weight-only quantization) | weights منخفضة bits مع activations أعلى precision |
| صيغة W4A16 | weights بـ 4-bit و activations بـ 16-bit |
| المعايرة (Calibration) | استخدام examples ممثلة لتوجيه quantization |
| أسلوب GPTQ | عائلة quantization تستخدم error-aware post-training methods |
| أسلوب AWQ | تكميم الأوزان الواعي بالتنشيط (Activation-aware weight quantization) |
| صيغة GGUF | ecosystem للملفات/quantization تُستخدم عادة مع llama.cpp |
| صيغة ONNX | interchange format محمولة لـ neural-network graphs |

| تسمية Q4_K_M | اسم balanced preset من GGUF-style 4-bit K-quant |

**يُعد VLM deployment مشكلة systems. Model ليست سوى مكون واحد. يعتمد الأداء

bandwidth و attention kernels و quantization kernels و scheduling و caching
