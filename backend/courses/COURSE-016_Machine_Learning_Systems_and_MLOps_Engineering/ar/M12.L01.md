## 1. Logging و Monitoring ليستا إضافات اختيارية للـ Production

يبدأ الفصل من مشكلة بسيطة: يفضل Engineers غالبًا كتابة Main application code ويؤجلون أعمالًا مثل Testing و Documentation و Logging و Monitoring.

هذا خطير في Production ML لأن Model قد تفشل بطرق يصعب إعادة بنائها بعد وقوع المشكلة.

توفر Logging و Monitoring أدلة عمّا كانت System تفعله قبل المشكلة وأثناءها.

ينبغي لاستراتيجية Observability مفيدة أن تساعد في الإجابة عن أسئلة مثل:

- ماذا حدث؟
- متى حدث؟
- أي Component كانت مشاركة؟
- هل كانت المشكلة في Infrastructure أم Software أم Data أم Model behavior؟
- هل تتحسن الحالة أم تسوء؟

الهدف الأساسي ليس إنتاج أكبر قدر ممكن من Output. بل إنتاج Information تساعد الأشخاص على فهم State الخاصة بالنظام.

## 2. ينبغي لسطر Log أن يحكي قصة، لا أن يصنع لغزًا آخر

يعطي المصدر Example على Low-level log entry غامضة لم يتمكن حتى User خبير من تفسيرها.

كان معناها الحقيقي بسيطًا: Machine واحدة لم تستطع الاتصال بـ Service أخرى على Address معينة.

يوضح ذلك قاعدة Design مهمة:

> **ينبغي أن تساعد Observability output المستهلك على فهم ما حدث دون إجباره على فك Implementation trivia.**

قد تتضمن Operational message جيدة:

- اسم Component،
- Severity،
- Operation التي فشلت،
- Resource أو Endpoint المعنية،
- Context كافية لبدء Debugging.

Logging السيئة ليست بلا ضرر. فالـ Output عديمة الفائدة تستهلك Storage و Attention، ومع ذلك تفشل في دعم Diagnosis.

## 3. Metrics الخاصة بـ CPU و Disk لا تستطيع إخبارك ما إذا كان Product ما يزال يعمل

يصف الفصل Content-management system كان Operations team فيها يراقب بالفعل Server health مثل Disk و Memory.

لكن تخيل أن زر **subscribe** الأكثر أهمية في Website تعطل بعد JavaScript deployment.

قد يظل Disk usage طبيعيًا.

وقد يظل Memory usage طبيعيًا.

ومع ذلك، قد تكون Business-critical action معطلة تمامًا.

قد تكون Metric أكثر فائدة هي تتبع Click-through أو Conversion behavior للزر بمرور الوقت.

ينشئ ذلك Hierarchy مهمة للمراقبة:

```text
صحة البنية التحتية (Infrastructure health)
CPU, memory, disk, network

صحة التطبيق (Application health)
errors, latency, successful requests

صحة ML (ML health)
accuracy / quality, drift, feature validity

صحة المنتج/الأعمال
conversion, engagement, revenue-related actions
```

Server صحية لا تثبت أن Product صحي.

## 4. يضيف MLOps إشارات Data و Model إلى Observability العادية للبرمجيات

تحتاج Traditional cloud software بالفعل إلى Logs و Metrics و Dashboards و Alerts.

ويضيف MLOps أهداف Observability جديدة مثل:

- Training metadata،
- Endpoint predictions،
- Model performance بمرور الوقت،
- Captured serving data،
- Drift indicators،
- Dataset constraints و Violations.

يؤكد الفصل أن Model التي ينخفض Accuracy الخاص بها بدرجة كبيرة لا ينبغي أن تصل إلى Production أو تبقى فيها بصمت.

كلما اكتُشفت هذه المشكلات مبكرًا، أصبحت أقل تكلفة في الإصلاح.

## 6. تفصل Logging بين الأحداث الطبيعية والأخطاء عبر Levels و Structure

يستخدم المصدر Nginx access logs و Error logs لتقديم Logging.

يمكن لـ Access log تسجيل Requests عادية مثل:

- Client address،
- Timestamp،
- HTTP method/path،
- معلومات User-agent.

ويمكن لـ Error log تسجيل Failure مثل Permission error أثناء فتح File.

الفكرة المهمة هي **Severity**: ينبغي لمستهلكي Logs التمييز بين Routine activity و Warning/Error conditions.

## 7. `print()` ليست Strategy للـ Logging في Production

يقوم Developers غالبًا بـ Debugging عبر إدخال `print()` statements.

قد يكون ذلك مفيدًا مؤقتًا، لكنه يصبح صعب الصيانة لأن:

- Statements يجب إضافتها وإزالتها يدويًا،
- Verbosity صعبة التحكم،
- Output تفتقر إلى Standardized severity،
- Routing للـ Output إلى Destinations متعددة يصبح مربكًا،
- التعامل المفيد مع Traceback/Context يجب إعادة اختراعه.

تحل Logging framework هذه المشكلات بصورة Systematic.

تستخدم أمثلة Python في الفصل Standard module باسم `logging`.

## 10. تتحكم Log levels في مقدار Operational detail التي تراها

يعرض المصدر خمسة Python logging levels شائعة.

من **الأكثر Verbose** إلى **الأقل Verbose / الأكثر Severity**:

```text
DEBUG
INFO
WARNING
ERROR
CRITICAL
```

تتضمن Configuration عند DEBUG تفاصيل تشغيلية منخفضة Severity إلى جانب Warnings/Errors.

أما Threshold أعلى مثل ERROR فتخفي Routine debug و Informational messages.

يسمح ذلك ببقاء Logging statements نفسها داخل Program بينما يغيّر Operators ما يتم Emit له فعليًا.

## 11. تتغير Verbosity المفيدة مع نضج Software

يوصي المصدر بتوقع مفاجآت أكثر في Software التي تم Deployment لها حديثًا.

لذلك قد تكون High verbosity مثل DEBUG مفيدة في بداية Deployment lifecycle.

بعد أن تصبح System مستقرة، قد يتحول الحجم نفسه إلى Noise.

عندها يمكن لـ Team تضييق Logging الطبيعية نحو INFO أو ERROR، مع الحفاظ على القدرة على زيادة Verbosity أثناء Investigation.

المبدأ هو:

> **ينبغي أن تتكيف Logging configuration مع Operational needs بدلًا من البقاء دائمًا عند الحد الأقصى أو الأدنى.**

## 14. إذا استطعت القياس، استطعت المقارنة؛ وإذا استطعت المقارنة، استطعت التحسين

يستخدم الفصل Athletic training journal كتَشبيه للـ Monitoring.

كانت Journal تسجل:

- Planned workout،
- Actual results،
- كيف شعر Athlete،
- Information أخرى مهمة مثل Pain أو Illness.

قد لا تبدو Entry واحدة ذات قيمة كبيرة.

ومع مرور الوقت، يصبح History أساسًا للمقارنة و Planning.

Production ML مشابهة: عندما تُطلق Model version جديدة، تحتاج إلى Historical signals لتحديد ما إذا كانت أفضل أو أسوأ أو مختلفة فقط.

لذلك Monitoring ليست Alerting فقط. بل هي أيضًا حفظ Operational history قابلة للمقارنة.

## 15. تقلل Metrics و Automation الاعتماد على شخص واحد

ينتقد المصدر Workflows التي يتلقى فيها Employee واحد Data يدويًا، ثم "runs some numbers"، ثم يعيد Report.

هذه Process لا تتوسع وتفشل **Bus test**: إذا أصبح هذا الشخص غير متاح فجأة، ينبغي أن تظل Workflow مفهومة وقابلة للتشغيل.

تساعد Automated metrics و Reports على تحويل Personal knowledge إلى Shared system behavior.

وهذا سبب آخر لأهمية Observability: ينبغي أن تكون Information متاحة باستمرار دون الاعتماد على Engineer واحدة تتذكر كيفية إنتاجها.

## 16. تغطي Model monitoring المسار الكامل إلى Production

يعرّف الفصل ML monitoring بصورة واسعة.

وتشمل Signals من:

- جمع Data وتنظيفها،
- Training jobs،
- Deployment services،
- Hosted inference،
- Model performance،
- بيانات Production.

لا توجد مجموعة Metrics واحدة Universal لأن Signal المهمة تعتمد على Step.

بالنسبة إلى Data-cleaning job، قد تشمل Metrics مفيدة:

- عدد Empty values لكل Column،
- مدة Processing.

وبالنسبة إلى Hosted model، قد تشمل Metrics مفيدة:

- Request latency،
- Prediction error rate،
- مؤشرات Drift.

## 17. ثلاثة أنواع أساسية من Metrics: Counter و Timer و Value

يحدد المصدر ثلاثة Metric patterns شائعة.

### العداد (Counter)

يعدّ Occurrences.

أمثلة:

- Empty cells،
- Failed requests،
- Records تمت معالجتها (Processed records).

### المؤقت (Timer)

يقيس Elapsed time.

أمثلة:

- Preprocessing time،
- Model inference latency،
- مدة Pipeline stage.

### القيمة (Value)

تخزن Measurement مرصودة ليست بطبيعتها Count أو Duration.

أمثلة:

- Resulting database size،
- Current accuracy،
- مقدار Drift.

## 18. تحتاج Drift monitoring إلى Reference وشيء جديد للمقارنة

يقدم الفصل Conceptين مهمين.

### المرجع (Baseline)

Reference تصف خصائص Data المقبولة أو المتوقعة.

### البيانات المستهدفة (Target data)

Data الأحدث التي تتم مراقبتها ومقارنتها مع Baseline.

قد تكون Terminology مربكة لأن Dataset المستخدمة لإنشاء Baseline قد تسمى أيضًا Baseline dataset، وقد تعمل Training dataset نفسها أحيانًا كـ Initial reference dataset.

نموذج ذهني بسيط هو:

```text
مجموعة البيانات المرجعية (Reference dataset)
      ↓
إنشاء Statistics + Constraints
      ↓
المرجع (Baseline)

بيانات Production الجديدة (New production data)
      ↓
المقارنة مع Baseline
      ↓
تقرير Violation / Drift
```

## 23. Violation إشارة للتحقيق، وليست تلقائيًا دليلًا على فشل Model

يعرض المصدر Constraint-violation reports.

توقعت Feature واحدة Values شبيهة بـ Integer بنسبة 100%، لكنها رصدت تقريبًا 99.7%.

وأظهرت Feature أخرى 0% في مكان كان المتوقع فيه 100% — وهي حالة أكثر خطورة بكثير.

يوضح ذلك فكرتين:

1. قد تحتاج Monitoring thresholds إلى Tuning حتى لا تنشئ Deviations صغيرة وغير ضارة Noise مستمرة.
2. قد تكشف Violations شديدة عن Data contracts مكسورة بسرعة.

تحتاج Monitoring output إلى Interpretation.

Threshold ليست مفيدة لمجرد وجودها؛ بل ينبغي أن تميز بين Abnormal behavior القابلة للتصرف و Variation المقبولة.

## 25. ليس كل تغير في Distribution عيبًا

إذا هبطت Sales فجأة نحو الصفر، فقد يشير ذلك إلى Bad data.

- تغيرات في Value type/unit،
- Null أو Empty values،
- Seasonal shifts مشروعة.

## 26. تجعل Time-aware datasets مقارنات Drift أكثر فائدة

يصف المصدر إعداد Azure target dataset كـ Time series.

يمكن أن تأتي Timestamp من:

- Explicit timestamp column،
- أو Virtual column مستنتجة من Storage path باستخدام Partition convention.

على سبيل المثال، يمكن لـ Path convention مثل:

```text
/2021/10/14/dataset.csv
```

أن ترمز إلى Dataset date دون الحاجة إلى Physical column إضافية.

يسمي الفصل هذا **Configuration by convention**: عندما يمكن استنتاج Structure موثوقة، قلل Manual configuration.

كلما قل Repeated configuration، قل Operational overhead.

## 28. تربط Automation الـ Logging و Monitoring و MLOps معًا

الخلاصة النهائية للفصل أوسع من أي Cloud service واحدة.

لا تكون Logging و Monitoring مفيدتين على Scale إلا إذا تم Capture للـ Information بصورة موثوقة وإتاحتها دون Effort يدوي متكرر.

ينبغي أن تجعل Automation ما يلي Routine:

- Emit لـ Logs مفيدة،
- Capture لـ Key metrics،
- جمع Serving data،
- المقارنة مع Baselines،
- إنشاء Reports،
- عرض Alerts،
- دعم Decisions قابلة لإعادة الإنتاج.

قد لا تكون Strong foundation أكثر جزء مثير في ML engineering، لكنها ما يجعل Exceptional results قابلة للتكرار.

---

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: المزيد من Logs يعني تلقائيًا Observability أفضل

قد تجعل Output غير الواضحة أو شديدة الضوضاء Diagnosis أصعب بدلًا من أسهل.

### المفهوم الخاطئ 2: Infrastructure metrics تكفي لـ ML systems

قد تبدو CPU و Memory و Disk صحية بينما يفشل Product behavior أو Data quality أو Model quality.

### المفهوم الخاطئ 3: `print()` مكافئة للـ Structured logging

توفر Logging مستويات Severity و Hierarchy و Traceback support و Routing و Verbosity قابلة للضبط.

### المفهوم الخاطئ 4: الإمساك بكل Exception مع Generic message يحسن Reliability

قد يخفي ذلك Real failure context ويجعل Remote debugging أصعب بكثير.

### المفهوم الخاطئ 5: ينبغي إبقاء DEBUG مفعلة إلى الأبد

تكون High verbosity مفيدة أثناء Early operation و Investigation، لكنها قد تتحول إلى Noise مع نضج Systems.

### المفهوم الخاطئ 6: Drift تعني أن Model معطلة بالتأكيد

قد يكون Distribution change مشروعًا، بما في ذلك Seasonality. وتحتاج Signal إلى Domain interpretation.

### المفهوم الخاطئ 7: Baseline هي نفسها كل Future target data

Baseline هي Reference؛ و Target data هي ما تتم مقارنته بها بمرور الوقت.

### المفهوم الخاطئ 8: Violation صغيرة في Constraint و Schema failure كاملة تستحقان الاستجابة نفسها

تحتاج Thresholds و Severity إلى Tuning حتى تبقى Monitoring قابلة للتصرف.

### المفهوم الخاطئ 9: Monitoring تتعلق فقط بـ Dashboards للبشر

يمكن لـ Observability signals أيضًا تغذية Automated alerts و Infrastructure reactions مثل Scaling.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التسجيل (Logging) | Emit لـ Structured event information تساعد في شرح Application behavior. |
| المراقبة (Monitoring) | قياس System/Model behavior بصورة متكررة حتى يمكن اكتشاف Changes و Problems. |
| قابلية المراقبة (Observability) | القدرة الأوسع على فهم System state باستخدام Logs و Metrics و Traces/Signals و Dashboards وأدلة مرتبطة. |
| مستوى Log (Log level) | Category للـ Severity/Verbosity تُستخدم للتحكم في Log messages التي يتم Emit لها. |
| DEBUG | أكثر Common logging level من حيث Verbosity في ترتيب الفصل. |
| مستوى INFO | Routine informational events — أحداث معلوماتية عادية. |
| WARNING | Potential problem أو Unusual condition. |
| ERROR | Failed operation أو Significant error condition. |
| CRITICAL | أكثر Common logging level Severity في ترتيب الفصل. |
| Root logger | Parent logger يمكن أن تؤثر Configuration الخاصة بها في Loggers عبر Application و Libraries التابعة لها. |
| Counter | Metric تمثل Count من Events/Items. |
| Timer | Metric تمثل Duration. |
| Value | Metric تمثل Numeric/State measurement مرصودة. |
| Baseline | Reference statistics/constraints تصف Expected data behavior. |
| Target data | Data أحدث تتم مراقبتها ومقارنتها مع Baseline. |
| Data capture | تسجيل Production endpoint inputs/outputs أو Serving information مرتبطة لتحليلها لاحقًا. |
| Data drift | تغير في Data distribution أو Characteristics بمرور الوقت. |
| Constraint violation | خروج Property تتم مراقبتها عن Baseline expectation/Threshold. |
| Configuration by convention | تقليل Explicit configuration عبر استنتاج Information موثوقة من Structure متفق عليها مثل Paths. |
| Bus test | اختبار ما إذا كانت Process تستطيع الاستمرار إذا أصبح الشخص الذي ينفذها عادة غير متاح فجأة. |
