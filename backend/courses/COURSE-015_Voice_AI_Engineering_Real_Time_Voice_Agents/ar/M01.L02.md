## 1. لماذا بدت Voice assistants المبكرة جامدة؟

بالنسبة إلى كثير من المستخدمين، بدت Voice assistants من الجيل الأول حوارية على السطح.

كان بإمكانك قول شيء بصوت مرتفع وسماع Response منطوقة.

لكن Architecture الكامنة تحت ذلك كانت عادةً أكثر جمودًا بكثير من المحادثة البشرية العادية.

قد يبدو Interaction مبسطًا هكذا:

```text
المستخدم: ابحث لي عن مطاعم إيطالية.
المساعد: في أي جزء من المدينة؟
المستخدم: بالقرب من مكتبي.
المساعد: وجدت نتائج ويب عن "بالقرب من مكتبي".
```

لماذا يمكن أن يفشل الطلب الثاني؟

لأن System قد لا تحتفظ بنفس Context الحواري المرن الذي يستطيع Language model حديث استخدامه.

يفترض المستخدم أن:

```text
"بالقرب من مكتبي"
```

تعني:

```text
"ابحث عن مطاعم إيطالية بالقرب من مكتبي."
```

لكن Architecture جامدة قائمة على الأوامر قد تتعامل مع أحدث Utterance على أنها أمر جديد مستقل.

### أنظمة Intent-and-slot

كان أحد أنماط التصميم الشائعة في Assistants الأقدم هو:

```text
عبارة المستخدم (User utterance)
     ↓
تصنيف Intent (Intent classification)
     ↓
استخراج Slots (Slot extraction)
     ↓
إجراء Backend محدد مسبقًا (Predefined backend action)
```

على سبيل المثال:

```text
"شغّل Bohemian Rhapsody لفرقة Queen"
```

يمكن Mapping هذه العبارة إلى:

```text
Intent: — نوع Intent
    PlayMusic — قيمة Intent

Slots: — القيم المستخرجة
    song_title = "Bohemian Rhapsody" — عنوان الأغنية
    artist_name = "Queen" — اسم الفنان
```

يعمل هذا جيدًا عندما يتوافق طلب المستخدم مع Form معروفة.

يمكنك التفكير فيه بوصفه Intelligent form-filling system.

```text
نموذج Intent (Intent form): PlayMusic
--------------------------------
عنوان الأغنية (song_title): [Bohemian Rhapsody]
الفنان (artist):     [Queen]
```

ينجح System إذا:

1. تعرّف على Intent،
2. عرف Slots المطلوبة لهذه Intent،
3. استخرج Values الخاصة بهذه Slots،
4. وكانت لديه Backend logic لهذا Form.

### لماذا يفشل هذا التصميم؟

لنفترض أن المستخدم يقول:

```text
"أرغب في بعض موسيقى الروك من السبعينيات (70s)."
```

هذه ليست بالضرورة Command مباشرة تطابق Form محددة مسبقًا.

يمكن للإنسان أن يستنتج أن:

- المستخدم يريد Music،
- النوع هو Rock،
- العقد هو 1970s،
- والمستخدم يريد على الأرجح Recommendations أو Playback.

قد يفشل Rigid intent system إذا لم توجد Intent محددة مسبقًا تغطي هذه الصياغة.

المشكلة الأعمق هي:

> يجب على المستخدم أن يتعلم كيف يتوقع Software أن تُصاغ الطلبات.

وهذا عكس المحادثة الطبيعية.

[[IMAGE_NEEDED: Intent-and-slot voice assistant | A diagram showing several example utterances flowing into one Intent block, with extracted slots such as song_title and artist_name feeding a predefined backend action | Learner should notice that the system behaves like a structured form-filling pipeline rather than open-ended contextual reasoning]]

### ما الذي تتطلبه محادثة طبيعية؟

يحتاج Conversational system مفيد إلى التعامل مع:

- Follow-up questions،
- Pronouns و References،
- Utterances غير المكتملة،
- إصلاح المحادثة (Conversational repair)،
- تغيير الاتجاه،
- Interruptions،
- و Context يمتد عبر عدة Turns.

يتطلب ذلك أكثر من Speech recognition.

فهو يتطلب Reasoning system يستطيع تفسير اللغة **داخل Context**.

## 2. Context: الركيزة الأولى للمحادثة في الوقت الحقيقي

يربط المصدر صعود Conversational AI الحديث بـ Language models المعتمدة على Transformer.

إحدى الأفكار المحورية هي **Self-attention**.

### Self-attention والعلاقات بين العناصر

تأمل الجملة:

```text
أسقط الكأس على الأرض فتحطّم.
```

إلى ماذا تشير **it**؟

يفهم الإنسان أن Glass هي التي Shattered.

كلمة "floor" أقرب إلى "it" داخل الجملة، لكن Semantic context يجعل "glass" هي Reference المنطقية.

لا يحتاج Transformer إلى التعامل مع كل كلمة بصورة مستقلة.

يمكن لآلية Attention فيه Modeling العلاقات عبر Sequence.

والنتيجة العملية هي أن Language models الحديثة أصبحت أفضل بكثير في مهام مثل:

- حل References،
- الحفاظ على استمرارية Topic،
- تفسير Ambiguous phrases،
- واستخدام Context السابق.

### Models و Conversation history

يصف الفصل Model بأنها Stateless بين Calls المنفصلة.

لذلك يكون نمط Application شائع هو:

```text
سجل Turn 1 (Turn 1 history):
User: What is the capital of France?
Assistant: Paris.

طلب Turn 2 المرسل إلى Model (Turn 2 request sent to model):
User: What is the capital of France?
Assistant: Paris.
User: What is its population?
```

يعيد Application إرسال Conversation history ذات الصلة.

وبذلك تستطيع Model استنتاج:

```text
"its" -> Paris — تشير "its" إلى Paris
```

هذه إحدى الطرق التي ينشئ بها Chat application تجربة Memory.

### Context ليست مجانية

كلما طالت Conversation، أصبح History أكبر.

وهذا يعني أن كمية أكبر من Data قد تحتاج إلى أن تكون:

- محفوظة،
- منقولة،
- معالجة،
- ومدارة ضمن Context limit.

بالنسبة إلى Text chat عادية، قد يظل هذا Overhead قابلًا للإدارة.

أما Live voice فيتطلب من System بالإضافة إلى ذلك التعامل مع Audio مستمر و Turn-taking منخفض Latency.

وهذا يقود إلى الركيزة الثانية: **Real-time transport**.

## 3. REST مقابل WebSockets: الرسائل البريدية مقابل خط هاتف

تستخدم Web APIs التقليدية غالبًا Model من نوع Request-response.

### النموذج الذهني لـ REST

Interaction مبسط هو:

```text
Client ينشئ Request كاملة (Client creates complete request)
            ↓
        إرسال Request (Send request)
            ↓
       Server يعمل (Server works)
            ↓
      إرسال Response (Send response)
            ↓
Client يستقبل Response كاملة (Client receives complete response)
```

يشبه ذلك إرسال Letter.

ترسل Message واحدة ثم تنتظر Reply.

بالنسبة إلى كثير من المهام، هذا ممتاز.

REST مفيدة على نطاق واسع في:

- عمليات CRUD،
- Web APIs العادية،
- Services المدعومة بـ Database،
- Request-response inference،
- والعمليات التي لا تتطلب Channel مفتوحة بصورة مستمرة.

### لماذا يختلف Real-time voice؟

المحادثة Live ليست ببساطة:

```text
Request -> Response -> Request -> Response — تبادل Transactional متتابع
```

أثناء المحادثة الطبيعية:

- قد يبدأ المستخدم الكلام قبل انتهاء Playback،
- قد تبث Assistant جزءًا من Output قبل اكتماله،
- يصل Audio بصورة مستمرة،
- قد تصل Session events في أي وقت،
- تكون Turn boundaries ديناميكية،
- ويحتاج الطرفان إلى إرسال Data بصورة مستقلة.

وهذا يجعل مشكلة Transport مختلفة.

### النموذج الذهني لـ WebSocket

ينشئ WebSocket اتصالًا Persistent وثنائي الاتجاه.

```text
Client  <====================>  Server
          الاتصال يبقى مفتوحًا (connection stays open)
```

يستطيع كلا الطرفين إرسال Messages ما دام Connection حيًا.

يستخدم المصدر تشبيهًا مفيدًا:

```text
REST      = خدمة بريدية (postal service)
WebSocket = خط هاتف مفتوح (open phone line)
```

لا يعني ذلك أن WebSockets تستبدل REST في كل مكان.

بل يعني أن WebSockets أنسب عندما يحتاج Application إلى **Continuous two-way streaming**.

[[IMAGE_NEEDED: REST versus WebSocket communication | Side-by-side diagram: REST shows separate Request -> Response cycles that repeatedly open logical exchanges, while WebSocket shows one persistent bidirectional connection with audio/events flowing in both directions | Learner should notice that live conversation benefits from a continuously open two-way channel]]

## 4. مكونات Voice assistant حديثة

Model قوية وحدها لا تكفي.

واتصال WebSocket وحده لا يكفي أيضًا.

يحتاج Live conversational system إلى عدة أجزاء تعمل معًا.

### 4.1 Model لغوية قوية

يجب أن تفهم Model اللغة الطبيعية غير المرتبة و Conversation context.

وهي توفر طبقة Reasoning.

### 4.2 Streaming في الوقت الحقيقي

يحتاج Application إلى Communication path مستمرة للـ Media والـ Events المتدفقة.

وهنا يأتي دور WebSockets.

### 4.3 اكتشاف نشاط الصوت باستخدام VAD

يجب أن يتعرف System على الحالات التي:

- يبدأ فيها المستخدم الكلام،
- يتوقف فيها المستخدم عن الكلام،
- ينبغي فيها تجاهل Background sound،
- وقد تقاطع فيها User turn جديدة Model playback.

تُعد VAD جزءًا من Natural turn-taking.

### 4.4 إدارة Session

يحتاج Application إلى تتبع:

- Live session الحالية،
- Conversation context ذي الصلة،
- Connection state،
- واستخدام Context window.

### 4.5 تعدد الوسائط (Multimodality)

قد يتضمن Interaction:

- إدخال Audio،
- إخراج Audio،
- Text،
- ولاحقًا Visual streams.

يركز المصدر في هذا الفصل على Conversational voice assistant بدل Complete tool-using agent architecture من الدرس السابق.

تمييز مفيد هو:

```text
Voice assistant:
    محادثة + Streaming + Turn-taking

Agent:
    محادثة + Reasoning + Memory/State + Tools/Actions + Goals
```

يمكن أن تتداخل الحدود في Systems الحقيقية، لكن هذا التمييز يساعد على فصل الاهتمامات أثناء التعلم.

### المخطط العام (Blueprint)

```text
المستخدم (User)
 ↓
Microphone
 ↓
Browser audio pipeline
 ↓
Persistent WebSocket
 ↓
Secure backend proxy
 ↓
Live model session
 ↓
Streaming response
 ↓
Browser playback
```

حول هذه Pipeline، يحتاج System أيضًا إلى:

```text
VAD — اكتشاف نشاط الصوت
Session state — حالة Session
Interruption handling — التعامل مع المقاطعة
Authentication — المصادقة
Error handling — التعامل مع الأخطاء
```

## 5. لماذا نبني Client داخل Web browser؟

يختار الفصل Architecture معتمدة على Browser عمدًا.

أحد الأسباب الرئيسية هو **Acoustic echo**.

### مشكلة Echo

افترض ما يلي:

1. تتحدث Assistant عبر Speakers الخاصة بـ Laptop،
2. يظل Microphone الخاص بـ Laptop يستمع،
3. يلتقط Microphone صوت Assistant نفسها،
4. ترى VAD وجود Speech،
5. وقد يعتقد System أن المستخدم قاطع Assistant.

يمكن أن يؤدي ذلك إلى Feedback loop.

```text
Output صوت AI من Speakers (AI speaker output)
      ↓
الصوتيات داخل الغرفة (room acoustics)
      ↓
Microphone
      ↓
VAD تعتقد أن المستخدم يتحدث (VAD thinks user is speaking)
      ↓
يتوقف AI playback (AI playback stops)
```

قد تكون النتيجة تجربة متقطعة وغير قابلة للاستخدام.

### إلغاء الصدى الصوتي باستخدام AEC

تحاول AEC إزالة Output الخاص بـ Speakers في System من Microphone signal.

وهذه Signal-processing problem.

قد يكون تنفيذها جيدًا أمرًا صعبًا.

يدافع المصدر عن Browser-based capture لأن Browsers الحديثة تحتوي بالفعل على خصائص Real-time communication متقدمة بُنيت لتطبيقات مثل Video calls.

الـ Architectural trade-off هو:

```text
بنية Web application أكبر (More web-application structure)
        مقابل (in exchange for)
استخدام قدرات Browser media ناضجة (using mature browser media capabilities)
```

### لماذا يُعد ذلك ذا قيمة؟

يمكن لـ Browser توفير:

- إدارة Microphone permission،
- Web Audio APIs،
- Media-stream processing،
- معالجة مدمجة مرتبطة بـ Echo حسب Environment،
- وطبقة UI محمولة.

الفكرة التي ينبغي الاحتفاظ بها أوسع من API واحدة:

> Architecture الجيدة تعيد استخدام قدرات Platform الناضجة بدلًا من إعادة بناء Low-level infrastructure صعبة بلا ضرورة.

## 6. Architecture آمنة من Serverين

يفصل Implementation في الفصل بين Frontend و Backend proxy.

### تطبيق Client

يتولى Browser:

- عرض UI،
- طلب Microphone permission،
- التقاط Audio،
- معالجة Audio،
- إرسال Audio chunks،
- استقبال Model events،
- وتشغيل Audio العائد.

### Backend WebSocket proxy

يتولى Backend:

- Server-side authentication،
- إنشاء Upstream live-model session،
- Forwarding لـ Audio من Browser إلى Model،
- Forwarding لـ Model responses إلى Browser،
- ودعم Server-side logic إضافية لاحقًا.

### لماذا لا يتصل Browser مباشرة؟

أحد الاهتمامات الأساسية هو Credential security.

لا ينبغي تضمين Sensitive server credentials داخل Browser JavaScript.

كل ما يُرسل إلى Browser يمكن للمستخدم Inspect له محتملًا.

ينشئ Proxy Trust boundary:

```text
Browser
 |
 | لا يوجد Server secret (no server secret)
 v
Backend proxy
 |
 | اتصال Server-side موثق (authenticated server-side connection)
 v
Model provider
```

### اتصالا WebSocket

تحتوي Architecture المصدر على:

```text
المتصفح
   ⇅ WebSocket 1
Backend Proxy
   ⇅ WebSocket 2
API النموذج المباشر
```

لذلك لا يكون Proxy مجرد HTTP endpoint عادي.

بل يحتفظ بـ Live connection على الجانبين.

[[IMAGE_NEEDED: Two-WebSocket real-time voice architecture | Browser on the left with UI, microphone, and speaker; Python proxy in the middle; Live model service on the right; show one bidirectional WebSocket between browser and proxy and another between proxy and model | Learner should notice that the proxy protects credentials while relaying a continuous two-way stream]]

### ملف البيئة `.env`

### خيارات Authentication الخاصة بالمصدر

- استخدام Application Default Credentials مع Vertex AI.

هذه Implementation choices متوافقة مع المصدر.

نظرًا لأن Provider APIs و Model names و Authentication methods و SDK signatures و Environment-variable conventions قد تتغير، فينبغي إعادة التحقق منها مقابل Current provider documentation قبل Production deployment.

## 8. التقاط Audio من Microphone داخل Browser

ندخل الآن مسار Real-time media.

### 8.1 طلب الوصول إلى Microphone

يطلب Browser Audio stream:

⟦CODE_0⟧

يعيد ذلك `MediaStream`.

### 8.2 إنشاء AudioContext

يضبط المصدر Audio context لمسار Input.

من حيث الفكرة:

⟦CODE_1⟧

يتوقع Implementation path في الفصل Input من PCM بتردد 16 kHz.

تعامل مع ذلك على أنه Requirement خاصة بمسار Live API المختار في المصدر.

### 8.3 لماذا لا نعالج كل شيء داخل `app.js`؟

يصل Audio بمعدل متكرر.

إذا نُفذت Audio work مكلفة على Main browser thread، فإنها تتنافس مع:

- تحديثات UI،
- Click events،
- Layout،
- Rendering،
- وJavaScript أخرى.

قد يجعل ذلك Page بطيئة أو متقطعة.

لذلك يستخدم المصدر **AudioWorklet**.

### النموذج الذهني لـ AudioWorklet

```text
Main browser/UI thread
        |
        | رسائل تحكم (control messages)
        v
Audio worklet thread عالية الأولوية (High-priority audio worklet thread)
        |
        | Chunks معالجة (processed chunks)
        v
Main application logic
```

يحافظ هذا الفصل على استجابة Audio processing من دون تجميد User interface.

### 8.4 التحويل من Float32 إلى Int16

غالبًا ما تعرض Browser audio processing عينات Floating-point حول:

```text
-1.0 to +1.0
```

⟦CODE_2⟧

من حيث الفكرة:

```text

عينة Int16 PCM (Int16 PCM sample)
```

## 14. نموذج التفاعل "Hot mic"

يتطلب Push-to-talk system تقليدي تحكمًا صريحًا في Turns.

على سبيل المثال:

```text

تحدث (Speak)

انتظر (Wait)
```

يهدف المصدر إلى Model أكثر طبيعية.

### الضغطة الأولى

### الضغطة الثانية

تكتم Microphone من دون تدمير Live session.

### الضغطة الثالثة

تلغي Mute وتستأنف Audio streaming.

يظل Connection حيًا.

يفصل هذا بين مفهومين:

```text
هل Session نشطة؟ (session active?)
هل Microphone يرسل حاليًا؟ (microphone currently sending?)
```

وهما ليسا الشيء نفسه.

### تحدد VAD حدود Turn

من دون زر "Stop speaking"، يجب أن يكتشف شيء ما أن المستخدم توقف.

```text

    ↓

    ↓

    ↓
اكتشاف Pause (pause detected)
    ↓
اعتبار User turn مكتملة (user turn considered complete)
    ↓
Model تستجيب (model responds)
```

### Interruption سلسة

المحادثة الطبيعية ليست دائمًا Turn-taking مهذبًا.

يقاطع المستخدمون.

ينبغي لـ Live assistant التعامل مع:

```text
AI تتحدث (AI speaking)
    ↓
المستخدم يبدأ الكلام (user starts talking)
    ↓
System يكتشف User speech جديدة (system detects new user speech)
    ↓
يتوقف AI playback (AI playback stops)
    ↓
الاستماع إلى المستخدم (listen to user)
```

يستمع المصدر إلى Interruption event ويستدعي Method باسم `stop()` في Audio streamer.

### لماذا يجب مسح Queue بالكامل؟

1. إيقاف Active source،
2. مسح Queued chunks،

## 15. تتبع Pipeline الكاملة من البداية إلى النهاية

ينبغي للمهندس الجيد أن يكون قادرًا على شرح المكان الذي تنتقل إليه Sample صوتية واحدة بالضبط.

دعنا نتتبعها.

### مسار Input

```text
1. يتحدث المستخدم (User speaks)
2. يلتقط Microphone في Browser الصوت (Browser microphone captures audio)
3. تغذي MediaStream الـ AudioContext (MediaStream feeds AudioContext)
4. يستقبل AudioWorklet عينات Float32 (AudioWorklet receives Float32 samples)
5. يحوّل Worklet العينات إلى Int16 PCM (Worklet converts to Int16 PCM)
6. تُجمع Samples في Chunks (Samples are grouped into chunks)
7. تُرسل Chunk إلى Main thread (Chunk is sent to main thread)
8. يرمّز Browser الـ Bytes كـ Base64 (Browser encodes bytes as Base64)
9. يغلّف Browser البيانات داخل JSON (Browser wraps data in JSON)
10. يرسل Browser الـ JSON عبر WebSocket (Browser sends JSON over WebSocket)
11. يستقبل Proxy الـ JSON (Proxy receives JSON)
12. يفك Proxy الـ Base64 إلى PCM bytes (Proxy decodes Base64 into PCM bytes)
13. يغلّف Proxy الـ Bytes لـ Provider SDK (Proxy wraps bytes for provider SDK)
14. يرسل Proxy الـ Audio إلى Live session (Proxy sends audio into live session)
```

### مسار Model/Session

```text
15. تستقبل الجلسة المباشرة الصوت المتدفق (streaming)
16. يحدد منطق VAD/الجلسة توقيت المحادثة
17. ينتج النموذج أحداث/صوت الاستجابة
```

### مسار Output

```text
18. يستقبل Proxy حدث Model response (Proxy receives model response event)
19. يحوله Proxy إلى صيغة Browser transport (Proxy serializes it for browser transport)
20. يستقبل Browser رسالة WebSocket (Browser receives WebSocket message)
21. يستخرج Browser الـ Audio payload (Browser extracts audio payload)
22. يفك AudioStreamer ترميز Base64 (AudioStreamer decodes Base64)
23. تصبح Int16 PCM عينات Float32 (Int16 PCM becomes Float32 samples)
24. يُضاف AudioBuffer إلى Queue (AudioBuffer is queued)
25. يشغّل Browser الصوت عبر Speaker (Browser plays audio through speaker)
```

### مسار Interruption

```text
26. يبدأ المستخدم الكلام أثناء حديث AI (User begins speaking while AI is talking)
27. تكتشف Live session الـ Interruption (Live session detects interruption)
28. يستقبل Browser حدث Interruption (Browser receives interruption event)
29. يوقف AudioStreamer الـ Active playback (AudioStreamer stops active playback)
30. تُمسح Pending queue (Pending queue is cleared)
31. يعود System إلى Listening (System returns to listening)
```

هذه هي Real-time loop الكاملة.

إذا كانت أي خطوة غير واضحة، يصبح Debugging صعبًا.

أما إذا كانت لكل خطوة مسؤولية واضحة و Checkpoint، تصبح Architecture قابلة للإدارة.

## 17. مبادئ Engineering المختبئة داخل Project

يعلّم الفصل أكثر بكثير من Voice app واحدة.

### المبدأ 1 — اختر Transport وفق Interaction pattern

استخدم Request-response عندما تكون Task من النوع Transactional.

واستخدم Persistent streaming عندما يحتاج الطرفان إلى Communication مستمرة وغير متزامنة.

### المبدأ 2 — افصل Trust boundaries

لا تعرض Server-side credentials داخل Browser code.

احتفظ بـ Sensitive authentication خلف Server تتحكم فيه.

### المبدأ 3 — انقل High-frequency processing بعيدًا عن UI thread

يجب ألا تجمد Real-time media الـ Interface.

استخدم Browser/Media execution paths المتخصصة عندما يكون ذلك مناسبًا.

### المبدأ 4 — تحقّق من Pipeline تدريجيًا

اختبر:

```text
Connection
ثم Capture (then capture)
ثم Transport (then transport)
ثم Upstream (then upstream)
ثم Downstream (then downstream)
ثم Playback (then playback)
ثم Interruption (then interruption)
```

لا تحاول Debug سبعة Unknowns في وقت واحد.

### المبدأ 5 — افصل Session state عن Media state

يمكن أن تظل Live session نشطة حتى أثناء Mute للـ Microphone.

وبالمثل، Model playback و Input capture نظامان فرعيان منفصلان.

### المبدأ 6 — صمم Interruption صراحةً

إيقاف Output ليس الشيء نفسه كإنشاء Output.

تحتاج إلى Logic واضحة لـ:

- Current playback،
- Queued playback،
- User speech الجديدة،
- و State transitions.

### المبدأ 7 — أعد استخدام قدرات Platform

تحل Browsers بالفعل العديد من مشكلات Media الصعبة.

جزء من Architecture هو تحديد ما **لا** ينبغي أن تبنيه بنفسك.

### المبدأ 8 — Code الخاصة بـ Provider ليست هي Architecture

يمكن أن تتغير Model identifiers و SDK functions و Authentication environment variables و Sample rates و Response shapes.

تبقى Architecture هي:

```text
التقاط (capture)
-> Streaming
-> Relay آمن (secure relay)
-> Live model session
-> Streaming عائد (stream back)
-> Playback
-> Interruption
```

وهذه هي المعرفة الدائمة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| النية (Intent) | Category محددة مسبقًا لأمر المستخدم في Architectures التقليدية للمساعدات |
| الحقل (Slot) | Structured value تُستخرج من Utterance لملء Parameters الخاصة بـ Intent |
| الانتباه الذاتي (Self-attention) | آلية Transformer لـ Modeling العلاقات بين العناصر داخل Sequence |
| السياق (Context) | Information المتاحة لـ Model عند تفسير Current input |
| استدعاء Model بلا حالة (Stateless model call) | Call لا تحتفظ بطبيعتها بـ Application turns السابقة ما لم تُمرر State/History |
| نمط REST | أسلوب شائع للاتصال عبر Web من نوع Request-response |
| اتصال WebSocket | Persistent bidirectional connection يدعم Asynchronous messaging |
| Streaming | Processing أو نقل Data تدريجيًا بدل انتظار Payload مكتملة |
| اكتشاف نشاط الصوت (VAD) | يحدد متى يبدأ Speech ومتى يتوقف |
| الجلسة (Session) | Persistent interaction context يمتد عبر عدة Live exchanges |
| إلغاء الصدى الصوتي (AEC) | يقلل Playback audio التي يلتقطها Microphone مرة أخرى |
| تدفق الوسائط (MediaStream) | Browser object يمثل Live media tracks مثل Microphone audio |
| سياق الصوت (AudioContext) | بيئة Web Audio API لمعالجة Audio وتشغيله |
| معالج الصوت (AudioWorklet) | Browser mechanism لمعالجة Audio مخصصة منخفضة Latency بعيدًا عن Main UI thread |
| تمثيل PCM | تمثيل عيّنات صوت رقمي خام |
| صيغة Int16 | تنسيق عيّنة عدد صحيح موقَّع بطول 16-bit |
| صوت Float32 | Floating-point audio representation شائعة في Web Audio APIs |
| ترميز Base64 | Text encoding يُستخدم عادةً لتمثيل Binary bytes داخل JSON/Text protocols |
| وسيط Backend (Backend proxy) | Trusted server يمرر Data ويحمي Provider credentials |
| اتصال كامل الازدواج (Full-duplex) | يستطيع الطرفان إرسال Data بصورة مستقلة عبر Connection |
| طابور التشغيل (Playback queue) | Ordered buffer من Received audio chunks المنتظرة للتشغيل |
| نموذج Hot mic | Interaction model يظل فيه Microphone streaming نشطًا حتى Mute/Disable صريح |
| المقاطعة (Interruption) | User speech تؤدي إلى إيقاف أو إعادة توجيه Current assistant playback/Generation flow |

## التحقق الذاتي

قبل المتابعة، تأكد من قدرتك على الإجابة عن الآتي:

1. لماذا عانت Intent-and-slot assistants مع Follow-up questions المرنة؟
2. ما دور Conversation history عندما تكون Model calls بلا State بطبيعتها؟
3. لماذا تكون Persistent bidirectional channel مفيدة لـ Live voice؟
4. ماذا تضيف VAD إلى Interaction؟
5. لماذا لا تكفي LLM قوية وحدها لتطبيق Real-time voice؟
6. لماذا يضع المصدر Backend proxy بين Browser و Model provider؟
7. ما المشكلة التي يمكن أن ينشئها Acoustic echo داخل Hot-mic system؟
8. لماذا يُستخدم AudioWorklet بدل تنفيذ كل Sample processing على Main thread؟
9. لماذا تتحول Float32 browser samples إلى Int16 PCM في Implementation المصدر؟
10. لماذا تُجمع Audio samples في Chunks؟
11. ما مسارا Forwarding المتزامنان داخل Proxy؟
12. لماذا يجب Serialization لـ Model response bytes بعناية قبل إرسالها إلى Browser؟
13. لماذا تكون Playback queue ضرورية لـ Streamed audio؟
14. لماذا يجب أن يمسح Interruption handling الـ Queued audio إضافة إلى إيقاف Current source؟
15. ما الفرق بين Microphone state و Session state؟
16. أي أجزاء من هذه Architecture تُعد Durable concepts، وأيها خاصة بـ Provider/Version؟
17. ما الذي ستقيسه لتشخيص Conversational latency ضعيفة؟
18. ما Failure cases التي ينبغي التعامل معها قبل اعتبار Application جاهزًا لـ Production؟
