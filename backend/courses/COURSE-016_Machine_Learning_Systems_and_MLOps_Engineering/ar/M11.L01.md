## 1. يبدأ Continuous delivery بالتقييم المستمر

يستخدم الفصل المصدر الأول تشبيه التعافي من الإصابة لشرح الفكرة المركزية في CI/CD: قيّم باستمرار، واستجب (React) للـ Feedback، وغيّر Strategy عند الحاجة، واستمر في تحسين Process.

تكون Manual release process المعتمدة على Emails والذاكرة وHuman confirmation بطيئة وغير متسقة.

تستبدل CI/CD قوية ذلك بـ Checks صريحة وقابلة للتكرار:

```text
تغيير (Change)
  ↓
بناء (Build)
  ↓
تحقق (Verify)
  ↓
تغليف (Package)
  ↓
إصدار / نشر
  ↓
مراقبة النتيجة (Observe result)
  ↓
تحسين العملية (Improve the process)
```

الكلمة المهمة هي **مستمر (continuous)**: لا تعني "انشر كل دقيقة"، بل حافظ على Feedback process متكررة تقلل المخاطر والعمل اليدوي تدريجيًا.

## 5. Infrastructure as code تجعل Model delivery قابلة لإعادة الإنتاج

يقدم الفصل Failure mode: توجد Container image داخل Registry، لكن لا أحد يملك Source files اللازمة لإعادة إنشائها.

الاستجابة الصحيحة ليست Reverse engineering للـ Image في كل مرة. الحل الأفضل هو تعريف Build process داخل Version-controlled automation.

يمكن لـ Reproducible delivery process تحديد:

- من أين تأتي Source code،
- من أين تأتي Registered model،
- كيف تعمل Authentication،
- كيف تُبنى Image،
- ما Tests التي تعمل،
- وأي Registry تستقبل Result.

هذه هي عقلية Infrastructure-as-code: **يجب أن تكون Process التي تنشئ Deployable artifact قابلة لإعادة الإنتاج هي الأخرى.**

## 8. Steps الصغيرة في CI/CD تنشئ Failure domains أصغر

يحذر الفصل من **Greedy steps**، أي Pipeline steps التي تحاول تنفيذ أشياء كثيرة جدًا.

قارن:

```text
Step عملاقة واحدة (One giant step):
Download + Validate + Train + Package + Publish
```

مع:

```text
الخطوة 1: تنزيل
الخطوة 2: تحقق
الخطوة 3: تدريب
الخطوة 4: تحزيم
الخطوة 5: نشر
```

عندما تفشل Pipeline، تجعل المسؤوليات الصغيرة تحديد Failure وDebugging أسهل.

هذه Theme متكررة عبر الفصلين: ينبغي أن تبسّط Automation الـ System، لا أن تخفي Script يدويًا ضخمًا داخل CI runner فقط.

## 9. تكمل Secrets وRegistries مسار Delivery

تحتاج Automated workflows إلى Credentials للوصول إلى Model registries وCloud workspaces وContainer registries.

ينبغي تخزين هذه Credentials بوصفها CI/CD secrets بدل Hard-coding داخل Workflow file.

يعرض الفصل ذلك باستخدام Cloud credentials وRegistry tokens.

بعد ذلك تصبح **Container registry** نقطة Distribution للـ Built image.

```text
CI runner
  ↓ مصادقة (authenticate)
Container registry
  ↓ سحب (pull)
بيئة Staging / Production
```

الفائدة التشغيلية الرئيسية هي أن Versioned packaged artifact نفسها يمكن استهلاكها بصورة متكررة بواسطة Downstream systems.

## 12. Blue-green deployment: جهّز الاستبدال الكامل قبل تحويل Traffic

تحافظ Blue-green strategy على Old production version وNew version منفصلتين.

تُنشر New version داخل Environment يُفترض أن تطابق Production بدرجة كبيرة، ثم تُختبر قبل تحويل Traffic.

```text
Traffic الحالية → Green v1

يُنشر Blue v2 بصورة منفصلة (Blue v2 deployed separately)
      ↓
تحقق (verify)
      ↓
حوّل Traffic إلى Blue (switch traffic to Blue)
```

الميزة الرئيسية هي Isolation قبل Cutover.

أما التحدي العملي فهو الحفاظ على نسختين/بيئتين شبيهتين بـ Production بدرجة عالية.

## 13. Canary deployment: زد Traffic فقط ما دامت Candidate سليمة

ترسل Canary نسبة صغيرة من Production traffic إلى New model بينما تستمر Previous version في خدمة الباقي.

مثال:

```text
90% → Model الحالية (current model)
10% → Model المرشحة (candidate model)
```

إذا ظلت Candidate سليمة، يمكن زيادة النسبة نحو 100%.

إذا ارتفعت Errors، يمكن إعادة Traffic إلى Old version. يسمى هذا العكس **Rollback**.

Example المصدر الخاص بـ Dependency error مهم: قد تمتلك Candidate دقة Model أفضل ومع ذلك تفشل كـ Software service.

لذلك يجب أن تتضمن Canary health gates الـ Operational metrics إضافةً إلى Model metrics.

## 15. Automated checks مكانها داخل Pipeline

يرى المصدر أن Verification ينبغي أن تكون Automated بدل الاعتماد على Last-minute manual inspection.

تشمل Checks المفيدة:

- نجاح Container build،
- بدء Service،
- وجود Endpoint،
- إرجاع Inputs الصحيحة للـ Expected schema،
- إرجاع Inputs غير الصحيحة Controlled errors،
- توافق Dependency versions،
- اكتشاف Linters لأخطاء Code،
- عمل Model/Runtime integration.

الهدف ليس Automation من أجل السرعة فقط، بل Repeatable confidence.

## 16. Shift left: اكتشف Problems عندما تكون أرخص في الإصلاح

يستخدم المصدر Linting كمثال بسيط.

يستغرق إصلاح Undefined import اكتشفها Linter أثناء Development ثوانٍ.

```text
Developer → CI → Staging → Canary → Production
   ↑ اكتشاف أرخص (cheaper detection)                ↑ اكتشاف مكلف (expensive detection)
```

## 17. يقود Continuous delivery طبيعيًا إلى Continuous improvement

يروي المصدر Release story كسر فيها Change صغير من سطر واحد الـ Released software.

الدرس المهم ليس "لا تنفذ تغييرات صغيرة أبدًا". بل هو:

> **إذا حدث Failure، فحسّن Process بحيث تصبح هذه الفئة من Failures أرخص أو مستحيلة في المرة التالية.**

تشكّل هذه الفكرة جسرًا إلى الفصل الثاني.

يحسن Continuous delivery طريقة Shipping للـ Artifacts. وتوسع KaizenML مفهوم Continuous improvement ليشمل ML system بالكامل.

## 18. تنفذ AutoML أتمتة لإنشاء Model من Prepared data

يعرّف المصدر الثاني **AutoML** تعريفًا ضيقًا: Automation للمهام الداخلة في Training model من Clean data.

قد يشمل ذلك مجموعات من:

- Algorithm/Model selection،
- Hyperparameter search،
- Preprocessing choices،
- Training،
- Evaluation،
- Model export.

الحجة المركزية للمؤلف هي أن Teams ينبغي أن تستخدم Automation حيث تقلل Manual complexity.

لذلك يُفهم AutoML بصورة أفضل بوصفها Technique لأتمتة Modeling portion داخل ML workflow.

## 19. تنفذ KaizenML أتمتة وتحسينًا لنظام ML كامل

تعني **Kaizen** التحسين المستمر ضمن Framing المستخدم في المصدر.

ويعرّف الفصل **KaizenML** بصورة أوسع من AutoML.

فهي تتضمن Continuous improvement لـ:

- Data quality،
- Feature quality،
- Software quality،
- Model quality،
- Deployment automation،
- Production feedback.

علاقة مفيدة من المصدر هي:

```text
AutoML = أتمتة إنشاء Model (automation of model creation)

KaizenML = التحسين المستمر لنظام ML من البداية إلى النهاية (continuous improvement of the end-to-end ML system)
```

## 20. ينبغي أن تنقل Automation الجهد من Mechanics المتكررة إلى Execution

يقارن المصدر مرارًا بين Research أوManual tuning وبين Goal المتمثل في تحويل Useful ideas إلى Working systems.

الخلاصة العملية في Engineering هي:

- لا تكتب Custom code لمجرد إثبات قدرتك على ذلك،
- استخدم High-level tools عندما تحل المشكلة بصورة صحيحة،
- احفظ Human attention للقرارات التي تحتاج Judgment فعلًا.

هذا لا يعني اختفاء Humans من ML.

يعرض الفصل AutoML بوضوح بوصفها Technique داخل Human-directed MLOps process أكبر.

ما يزال Engineer يختار Problem وData وQuality requirements وDeployment target وما إذا كانت Automated result مفيدة.

## 21. تتعامل KaizenML مع Data وSoftware وModels بوصفها أهداف Improvement متساوية

```text
جودة Data (Data quality)
```

## 22. Feature stores إحدى Mechanisms الخاصة بـ KaizenML

- غالبًا ما تدعم Warehouse أعمال Analytics/Business intelligence،
- بينما تنظم Feature store المدخلات التي تستخدمها ML systems.

## 24. أحيانًا تكون أفضل Automation هي عدم Training من الأساس

يقدم مثال Core ML نقطة مهمة: إذا كانت Strong pretrained model موجودة بالفعل، فقد يكون Reuse أوConversion لها أرخص وأسرع من Training نموذج جديد من الصفر.

```text

      ↓

      ↓

```

## 29. ما تزال AutoML تحتاج Human constraints وJudgment

لا تقرر Automation كل شيء نيابةً عنك.

ما يزال Humans يحددون أو يتحققون من:

- Problem المطلوب حلها،
- Target label،
- مدى ملاءمة Data،
- Evaluation metric،
- Compute/Time budgets،
- Deployment constraints،
- وهل Final behavior تنشئ قيمة مفيدة.

يمكن لـ Automated system Optimization لـ Wrong metric بكفاءة شديدة إذا كان Human framing خاطئًا.

ولهذا تُعد AutoML Component داخل MLOps، لا بديلًا عن ML systems engineering.

## 34. ما الذي ينبغي Automation له أولًا؟

أقوى قاعدة عملية عبر المصادر هي Automation لمصادر Friction وFailure المتكررة.

تشمل المرشحات المبكرة الجيدة:

- بناء Environment/Package،
- Container builds،
- Service-contract tests،
- Linting،
- Model retrieval وPackaging،
- Image publishing،
- Model registration،
- Repeated feature preparation،
- Repetitive model search،
- توليد الشرح/التقرير.

تكون Automation أكثر قيمة عندما تجعل Failure التالية أسهل في الفهم وRelease التالية أسهل في الثقة.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: CI/CD تعني Deployment مستمرًا بلا Controls

يركز الفصل على Continuous feedback وVerification وSafer delivery، لا إزالة Quality gates.

### المفهوم الخاطئ 2: تغليف Model يعني نسخ Model file فقط

Serving code وRuntime وDependencies وPreprocessing وAPI contract كلها أجزاء من Deployable unit.

### المفهوم الخاطئ 3: ارتفاع Model accuracy يثبت أن Deployed service تعمل

يمكن أن تفشل API وDependency versions وInput/Output types وRoutes وRuntime بصورة مستقلة عن Model quality.

### المفهوم الخاطئ 4: Pipeline step واحدة ضخمة أبسط

قد تكون أقصر في الكتابة، لكنها تنشئ Failure domain أكبر بكثير ويصعب Debugging لها.

### المفهوم الخاطئ 5: Canary rollout تحتاج Model metrics فقط

يمكن لـ Operational errors مثل HTTP failures أوDependency breakage أن تجعل Model عالية الدقة غير قابلة للاستخدام.

### المفهوم الخاطئ 6: AutoML تنفذ Automation لدورة حياة ML كاملة

يعرّف المصدر AutoML أساسًا حول Model creation من Clean data. أما KaizenML فهي مفهوم تحسين System أوسع.

### المفهوم الخاطئ 7: AutoML تلغي الحاجة إلى ML engineers

ما يزال Humans يختارون Objectives وData وConstraints وMetrics وIntegration وDeployment وProduct decisions.

### المفهوم الخاطئ 8: Training نموذج بنفسك دائمًا أكثر "حقيقية" من استخدام Pretrained model

يعامل المصدر Model reuse وConversion بوصفهما Workflows صحيحة وغالبًا أكثر كفاءة.

### المفهوم الخاطئ 9: Feature stores وAutoML تحلان Problem نفسها

تحسن Feature stores مدخلات ML القابلة لإعادة الاستخدام، بينما تنفذ AutoML أتمتة لأجزاء من Model creation.

### المفهوم الخاطئ 10: Explainability مخصصة فقط لـ Research reports

يتعامل المصدر مع Explanation information بوصفها Operational signal يمكن أن تكون جزءًا من MLOps workflows.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| التكامل المستمر (Continuous Integration — CI) | دمج Changes والتحقق منها تلقائيًا بصورة متكررة. |
| التسليم المستمر (Continuous Delivery — CD) | Process تلقائية وقابلة للتكرار لإعداد Artifacts لـ Safe release/deployment. |
| تغليف Model (Model Packaging) | تجميع Model مع Runtime والـ Software اللازمة لتشغيلها. |
| سجل Containers (Container Registry) | Repository لتخزين Container images وتوزيعها. |
| Infrastructure as Code | تعريف Infrastructure/Build/Deployment processes داخل Configuration أوCode قابلة للـ Versioning وإعادة الإنتاج. |
| Pipeline | مجموعة Steps مرتبة أو واعية بالـ Dependencies لتحقيق Automation goal. |
| نطاق الفشل (Failure Domain) | النطاق الذي يمكن أن يحدث داخله Failure أو يجب تشخيصه. |
| أسلوب Blue-green deployment | نشر New version بصورة منفصلة والتحقق منها ثم تحويل Traffic من Old إلى New. |
| Canary deployment | إرسال نسبة متزايدة من Live traffic إلى Candidate مع Monitoring للصحة. |
| Rollback | إعادة Traffic أوDeployment state إلى Version سابقة كانت تعمل. |
| Shift left | نقل Error detection إلى مراحل أبكر في Software/Model delivery lifecycle. |
| AutoML | Automation لمهام Model training وModel selection انطلاقًا من Prepared data. |
| KaizenML | Continuous improvement وAutomation عبر Data وSoftware وFeatures وModels وDeployment وFeedback. |
| ML المرتكزة على Data (Data-centric ML) | التركيز على تحسين Data quality وData processes، لا Model architecture فقط. |
| Feature Store | System مشتركة لـ Reusable features المستخدمة في Model training و/أو Prediction. |
| Pretrained Model | Model جرى Training لها مسبقًا ويعاد استخدامها أوAdaptation لها بدل Training من الصفر. |
| Explainability | Methods لفحص أسباب Producing model predictions. |
| SHAP | Explanation framework يناقشه المصدر لـ Local وGlobal feature contributions. |
| Permutation Importance | Estimate للأهمية يعتمد على تدهور Model performance عند إفساد Information الخاصة بـ Feature. |
