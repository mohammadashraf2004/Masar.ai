## 1. الفكرة الكبيرة الأولى: يكتب LLM token واحدة في كل مرة

من الخارج، يبدو نظام text-generation بسيطًا:

```text
الموجه (Prompt)
   ↓
نموذج اللغة (Language model)
   ↓
الاستجابة المولدة (Generated response)
```

هذه الصورة مفيدة، لكنها تخفي أهم حقيقة عن generation:

> **لا ينتج generative Transformer استجابة كاملة عادةً في خطوة واحدة. بل يتنبأ مرارًا بـ next token واحدة.**

افترض أن prompt هو:

```text
The capital of France is — نص المصدر المستخدم في المثال
```

يعالج Model الـ prompt ويتنبأ بتوزيع احتمالي عبر next tokens الممكنة.

قد تكون next token مرجحة تُفك إلى:

```text
Paris — token مرجحة تالية
```

والآن تصبح sequence الفعلية:

```text
The capital of France is Paris — النص بعد إضافة token الجديدة
```

يشغّل Model نفسه مرة أخرى للتنبؤ بما يأتي بعد ذلك.

ثم مرة أخرى.

ثم مرة أخرى.

وهذا ينشئ generation loop:

```text
1. اقرأ token sequence الحالية.
2. تنبأ بدرجات next token.
3. اختر token واحدة.
4. أضف تلك token إلى sequence.
5. كرر العملية.
```

[[IMAGE_NEEDED: Autoregressive token generation loop | Show an initial prompt entering the model, one output token being selected, that token appended to the prompt, and the enlarged sequence entering the model again for the next step | Learner should notice that generation is an iterative loop rather than one operation that writes the whole answer at once]]

### مثال مفاهيمي بسيط

تخيل أن النص الحالي هو:

```text
I like machine — النص الحالي في المثال
```

قد يسند Model افتراضي القيم الآتية:

```text
"learning"     0.63
"tools"        0.12
"systems"      0.08
"models"       0.06
other tokens   0.11 — tokens أخرى
```

بعد أن تختار decoding strategy:

```text
learning — token المختارة
```

يصبح input التالي لـ Model من الناحية المفاهيمية:

```text
I like machine learning — النص بعد اختيار token الجديدة
```

ويتنبأ Model الآن بـ next token أخرى.

### ماذا يعني “autoregressive”؟

يكون Model من نوع **autoregressive** عندما تصبح المخرجات التي ولدها سابقًا جزءًا من input المستخدم لتوليد المخرجات اللاحقة.

في text generation:

```text
generated token 1
        ↓
تساعد في توليد token 2
        ↓
tokens 1 and 2
        ↓
تساعدان في توليد token 3
        ↓
...
```

ولهذا توصف generative LLMs من نوع decoder عادةً بأنها autoregressive.

لا يتم التخطيط للمخرجات كفقرة مكتملة ثم إصدارها دفعة واحدة. بل تظهر بالتتابع.

## 3. ماذا يحدث في Forward pass واحدة؟

تعني **forward pass** أن قيم input تتدفق عبر حسابات neural network حتى يتم إنتاج قيم output.

بالنسبة إلى خطوة next-token واحدة، يقدم الفصل ثلاثة مكونات رئيسية للنظام:

```text
أداة Tokenizer
    ↓
مجموعة Transformer blocks
    ↓
رأس نمذجة اللغة (Language Modeling Head — LM head)
```

هذا أحد أكثر الرسوم الذهنية فائدة للتذكر.

### المكون 1 — Tokenizer

يحوّل tokenizer النص المرئي إلى token IDs.

على سبيل المثال:

```text
"The capital of France is" — النص المرئي

→ [token_id_1, token_id_2, ..., token_id_6] — قيم token IDs الناتجة
```

تحدد هذه IDs صفوفًا داخل token-embedding table الخاصة بـ Model.

### المكون 2 — Transformer stack

تمر token representations عبر stack من Transformer blocks.

يحتوي مثال Phi-3 في الفصل على:

```text
32 طبقة Transformer decoder
```

يحتوي كل block على مكونات رئيسية تشمل:

```text
آلية self-attention
معالجة feedforward/MLP
عملية normalization
مسارات residual
```

وعلى مستوى عالٍ، تعمل stack تدريجيًا على تحويل representation لكل token position.

### المكون 3 — LM head

بعد Transformer stack، لا يزال Model يمتلك vectors.

يقوم **language modeling head** بتحويل هذه vectors إلى score واحدة لكل vocabulary token.

في مثال Phi-3 داخل الفصل، تحتوي model vocabulary على:

```text
32,064 tokens — حجم Vocabulary
```

ولذلك ينتج LM head:

```text
32,064 output scores — درجة لكل Vocabulary token
```

لكل sequence position.

### بنية Model تروي القصة نفسها

يطبع الفصل Model ويبرز بنية تشبه مفاهيميًا:

```text

│   ├── decoder layers × 32
│   └── final normalization
└── lm_head
```

```text

```

التفسير:

```text

×
3,072 قيمة لكل token vector
```

ويظهر LM head تقريبًا كالتالي:

```text

    in_features=3072,
    out_features=32064
)
```

يكشف هذا تناظرًا جميلًا:

```text
internal model vector
      3072 قيمة
          ↓
        LM head
          ↓
درجة واحدة لكل token

```

## 5. عملية Model scoring ليست نفسها Token selection

تنتج neural network scores لـ next tokens المحتملة.

ثم توجد خطوة أخرى تختار أي token ستصبح output فعليًا.

تُسمى عملية اتخاذ القرار هذه **decoding strategy**.

### أسلوب Greedy decoding

أبسط strategy هي:

```text
اختر دائمًا token صاحبة أعلى score
```

مثال:

```text
Dear       40% — candidate token واحتمالها
Hello      24%
Hi         16%
Greetings   9%
...
```

يختار greedy decoding:

```text
Dear — أعلى token من حيث Score
```

لأنها صاحبة أعلى score.

### أسلوب Sampling

هناك احتمال آخر وهو إجراء sampling وفقًا للتوزيع.

حينها قد تكون `Dear` صاحبة أكبر فرصة للاختيار، لكنها ليست مضمونة تمامًا.

يسمح ذلك بوجود تنوع بين candidates المعقولة.

يقدم الفصل هذا التمييز الآن ويترك الاستكشاف الأعمق لعناصر تحكم generation مثل temperature لفصل لاحق.

### لماذا يهم هذا التمييز؟

Model و decoding algorithm ليسا الشيء نفسه تمامًا.

من الناحية المفاهيمية:

```text
MODEL
"ما tokens التي تبدو معقولة؟"
        ↓
DECODER
"أي token معقولة ينبغي أن نصدرها فعليًا؟"
```

يساعد ذلك في تفسير لماذا يمكن لـ Model نفسه أن يتصرف بصورة مختلفة مع generation settings مختلفة.

## 6. تدفقات Token والمعالجة المتوازية و Context length

أحد أسباب أهمية Transformers هو أن بنيتها تدعم قدرًا كبيرًا من المعالجة المتوازية لمواضع sequence مقارنةً بالأساليب recurrent الأقدم.

أحد النماذج الذهنية الأولية المفيدة هو تخيل processing stream واحدة لكل token position:

```text
token 1 → processing stream 1 — مسار معالجة
token 2 → processing stream 2
token 3 → processing stream 3
...
token N → processing stream N
```

هذه streams **ليست مستقلة** لأن attention تسمح للمواضع بتبادل المعلومات.

لكن صورة parallel-stream مفيدة لفهم tensor shapes وحدود context.

[[IMAGE_NEEDED: Parallel token processing streams | Show several input token embeddings entering parallel vertical streams through the same stack of Transformer blocks, with attention links connecting token positions | Learner should notice both parallel per-position processing and the cross-position interaction introduced by attention]]

### طول Context

لا يستطيع Model معالجة أكثر من عدد معين من token positions في الوقت نفسه.

وهذا الحد الأقصى هو **context length**.

إذا كان Model يمتلك context limit قدره 4K، فلا يستطيع معالجة token sequence طويلة بلا حدود تتجاوز هذا الحد في الوقت نفسه.

لذلك يحدد context length مقدار المعلومات بعد tokenization التي يمكن أن توجد داخل model context واحدة.

تذكر من Chapter 2:

```text
characters ≠ words ≠ tokens — وحدات مختلفة
```

ولذلك يعتمد مقدار النص القابل للقراءة الذي يمكن إدخاله جزئيًا على tokenization.

### شكل Hidden-state

في مثال الفصل المكون من ست tokens، يكون output الخاص بـ Transformer stack بالشكل:

```text
[1, 6, 3072]
```

التفسير:

```text
1      عنصر واحد في Batch
6      token positions
3072   hidden values لكل token position
```

بعد LM head:

```text
[1, 6, 32064]
```

التفسير:

```text
1      عنصر واحد في Batch
6      token positions
32064  vocabulary scores لكل position
```

من المفيد حفظ هذا التحويل مفاهيميًا:

```text
[batch, sequence, hidden_size] — شكل Hidden states
              ↓ LM head
[batch, sequence, vocabulary_size] — الشكل بعد LM head
```

### لماذا يختار الموضع الأخير فقط Next generated token؟

في next-token generation، يحتاج Model إلى prediction المقابلة لنهاية sequence الحالية.

لذلك يصبح hidden vector الخاص بالموضع الأخير هو LM-head input المرتبط باختيار next token.

ومع ذلك، لم تكن token positions السابقة بلا فائدة.

تسهم representations الخاصة بها بمعلومات سياقية من خلال attention.

ولهذا يستطيع representation الخاص بآخر token أن يشفّر معلومات من tokens السابقة.

## 7. لماذا تهدر Generation العمل دون Caching؟

ارجع إلى autoregressive generation.

افترض أن prompt token sequence هي:

```text
A B C D
```

يحسب Model representations ويتنبأ بـ:

```text
E
```

ثم تصبح sequence التالية:

```text
A B C D E
```

قد يعيد implementation ساذج حساب كل شيء لـ:

```text
A B C D
```

مرة أخرى، رغم أن هذه tokens تمت معالجتها بالفعل.

ثم بعد توليد `F`، قد يعيد حساب:

```text
A B C D E
```

مرة أخرى.

وهذا يكرر قدرًا كبيرًا من العمل.

### ذاكرة Key/Value المؤقتة (KV cache)

تستخدم حسابات Attention كائنات تسمى:

```text
queries — الاستعلامات
keys — المفاتيح
values — القيم
```

وسنشرحها لاحقًا.

أثناء generation، يستطيع Model تخزين **keys و values** المحسوبة سابقًا مؤقتًا، بحيث لا يلزم إعادة إنشاء حسابات attention السابقة من الصفر عند كل خطوة.

يسمى هذا optimization:

```text
KV cache — ذاكرة المفاتيح والقيم المؤقتة
```

الفكرة العامة هي:

```text
بدون Cache (WITHOUT CACHE)

الخطوة 1:
A B C D → احسب

الخطوة 2:
A B C D E → أعد حساب جزء كبير من A B C D

الخطوة 3:
A B C D E F → أعد حساب جزء كبير من A B C D E — sequence الحالية
```

مقابل:

```text
باستخدام KV Cache (WITH KV CACHE)

الخطوة 1:
احسب A B C D
خزّن نتائج K/V المفيدة

الخطوة 2:
أعد استخدام A B C D المخزنة
احسب الموضع الجديد E

الخطوة 3:
أعد استخدام history المخزنة
احسب الموضع الجديد F
```

> يمكن لإعادة استخدام نتائج attention السابقة أن تقلل بصورة كبيرة العمل المتكرر أثناء autoregressive generation.

### لماذا تقوم APIs غالبًا بـ Streaming لـ Tokens؟

حتى generation المحسنة تظل sequential.

وقد لا يرغب المستخدمون في الانتظار حتى تكتمل الاستجابة بالكامل.

لذلك تعرض الأنظمة tokens غالبًا أثناء توليدها.

يحسن ذلك الاستجابة المدركة، رغم أن Model لا يزال ينتج الاستجابة token واحدة في كل مرة.

```text
block 2
  ↓
block 3
  ↓

block 32
```

```text
"Redemption" — تكملة مرتبطة بقوة
```

تسهم مكونات feedforward عبر model layers في المعلومات والسلوكيات المتعلمة التي تجعل مثل هذه predictions ممكنة.

لكن الفصل يحذر أيضًا من التفكير في LLM على أنه مجرد database ضخمة.

يجب على Model المفيد أن يفعل أكثر من حفظ training fragments الدقيقة.

كما يجب أن يعمم على inputs وتركيبات لم يرها بالصورة نفسها تمامًا.

لذلك فالفكرة الحدسية الأفضل هي:

```text
معلومات متعلمة (learned information)
+
أنماط متعلمة (learned patterns)
+
تحويلات تدعم التعميم (transformations that support generalization)
```

بدلًا من:

```text
قاعدة بيانات Lookup للجمل المخزنة
```

## 9. آلية Attention: إدخال Context ذي الصلة في Token representation

تعتمد اللغة اعتمادًا كبيرًا على context.

انظر إلى:

```text
The dog chased the squirrel because it ... — جملة المثال
```

إلى ماذا تشير:

```text
it
```

؟

يعتمد التفسير الصحيح على context.

لا يستطيع Model فهم مثل هذه العلاقات إذا تعامل مع كل token بمعزل عن غيرها.

تمنح Self-attention كل token position آلية لدمج معلومات من مواضع أخرى ذات صلة داخل sequence.

### أبسط تصور لـ Attention

عند معالجة token position الحالي:

```text
1. قيّم مدى صلة المواضع الأخرى المسموح بها.
2. ادمج المعلومات من تلك المواضع وفقًا لهذه الدرجات.
```

هذا هو جوهر attention.

[[IMAGE_NEEDED: Attention intuition with pronoun reference | Show “The dog chased the squirrel because it” with the current token “it” highlighted and attention links of different strengths to earlier words, especially dog and squirrel | Learner should notice that attention lets the current representation incorporate information from relevant earlier positions]]

يلخص الفصل attention في خطوتين مفاهيميتين بالضبط:

```text
الخطوة 1:
حساب الصلة (relevance scoring)

الخطوة 2:
دمج المعلومات (information combination)
```

كل ما يتعلق بـ queries و keys و values هو الآلية التي تمكّن هاتين العمليتين.

## 10. مفاهيم Query و Key و Value: أبسط تفسير ممكن

قد تبدو مصطلحات **query** و **key** و **value** أكثر تعقيدًا من الفكرة الأساسية.

دعنا نستخدم تشبيهًا من retrieval.

تخيل أن token position الحالي يسأل:

```text
"ما المعلومات السابقة المرتبطة بي؟"
```

تمثل **query** ما يبحث عنه الموضع الحالي.

يمتلك كل موضع سابق **key** تشارك في تحديد ما إذا كان هذا الموضع ذا صلة.

ويمتلك كل موضع سابق أيضًا **value** تمثل المعلومات التي يمكن إدخالها إلى representation الجديد.

من الناحية المفاهيمية:

```text
QUERY
ما الذي أبحث عنه؟

KEY
ما مدى صلة هذا الموضع بتلك Query؟

VALUE
ما المعلومات التي ينبغي أخذها من هذا الموضع؟
```

هذا التشبيه ليس مثاليًا، لكنه يمنحك نموذجًا ذهنيًا قابلًا للاستخدام.

### من أين تأتي Q و K و V؟

تستقبل attention layer input vectors.

أثناء training، يتعلم Model ثلاث projection matrices:

```text
W_Q  إسقاط Query
W_K  إسقاط Key
W_V  إسقاط Value
```

تتحول input vectors كما يلي:

```text
input × W_Q → queries — إسقاطات Query
input × W_K → keys — إسقاطات Key
input × W_V → values — إسقاطات Value
```

النقطة المهمة هي أن Q و K و V ليست قطعًا منفصلة من النص.

بل هي learned projections مختلفة لـ token representations.

[[IMAGE_NEEDED: Query-key-value projection | Show the same set of token input vectors branching through three learned projection matrices W_Q, W_K, and W_V to create query, key, and value representations | Learner should notice that Q, K, and V are different learned views of the same underlying token representations]]

## 11. الخطوة 1 في Attention: حساب Relevance

افترض أننا نعالج final token position الحالي.

تُقارن query vector الخاصة به مع key vectors للمواضع المسموح له بالانتباه إليها.

من الناحية المفاهيمية:

```text
Query الحالية
      ×
Keys المرشحة
      ↓
درجات الصلة (relevance scores)
```

إذا بسطنا الفكرة:

```text
current token: "it"

المواضع السابقة (previous positions):
"The"       → صلة منخفضة
"dog"       → بعض الصلة
"chased"    → بعض الصلة
"the"       → صلة منخفضة
"squirrel"  → صلة مرتفعة
"because"   → صلة منخفضة
```

يتم normalized للـ raw scores باستخدام خطوة softmax حتى تشكل attention weights توزيعًا قابلًا للاستخدام.

من الناحية المفاهيمية:

```text
raw relevance scores — درجات الصلة الخام
        ↓
       softmax
        ↓
normalized attention weights
```

تشير weights إلى مدى القوة التي ينبغي أن يسحب بها الموضع الحالي معلومات من context positions المسموح بها.

### لماذا كلمة “Allowed” مهمة؟

يكون generative Transformer من نوع decoder نموذجًا autoregressive.

عند التنبؤ بالنص اللاحق، يجب ألا يسرب معلومات من future positions.

لذلك يتم masking لـ decoder attention حتى لا يستطيع الموضع الحالي الانتباه إلا إلى المواضع السابقة المسموح بها وإلى نفسه، وليس إلى future positions التي لم تُولد بعد.

وهذا أحد أسباب ظهور attention pattern في generative decoders بشكل اتجاهي.

## 12. الخطوة 2 في Attention: دمج المعلومات

بعد حساب relevance weights، يستخدمها Model لدمج value vectors.

بصورة مبسطة:

```text
attention weight لـ token 1 × value 1
attention weight لـ token 2 × value 2
attention weight لـ token 3 × value 3
...
                     ↓
                    المجموع (sum)
                     ↓
context-aware output vector جديدة
```

إذا حصلت token `squirrel` على relevance weight أكبر بالنسبة إلى token الحالية `it`، فإن value الخاصة بـ `squirrel` تسهم بقوة أكبر في النتيجة.

ينتج عن ذلك representation جديد يحتوي على معلومات سياقية تم اختيارها من sequence.

لذلك تكون القصة المبسطة الكاملة لـ attention هي:

```text
QUERY + KEYS — حساب الصلة
    ↓
relevance scores
    ↓
normalized weights
    ↓
weights × VALUES
    ↓
weighted combination
    ↓
context-aware representation
```

[[IMAGE_NEEDED: Two-step attention calculation | First panel shows current query compared with keys to create relevance weights; second panel multiplies those weights by value vectors and sums them into one output vector | Learner should connect query/key interaction with scoring and values with information transfer]]

هذه هي الآلية الأساسية التي ينبغي فهمها قبل القلق بشأن matrix equations الدقيقة.

## 13. لماذا تستخدم Attention عدة Heads؟

قد تتعلم عملية attention واحدة pattern مفيدًا واحدًا.

لكن اللغة يمكن أن تحتوي على علاقات كثيرة في الوقت نفسه.

على سبيل المثال، قد يحتاج Model إلى تتبع:

```text
مرجع الضمير (pronoun reference)
البنية النحوية (syntactic structure)
علاقات العبارات القريبة (nearby phrase relationships)
العلاقات بعيدة المدى (longer-range dependencies)
أنماط متعلمة أخرى (other learned patterns)
```

لذلك ينفذ Transformer عدة عمليات attention بالتوازي.

تسمى كل عملية attention متوازية **attention head**.

من الناحية المفاهيمية:

```text
input representations
       ↓
 ┌─────┼─────┐
 ↓     ↓     ↓
head 1 head 2 head 3 ...
 ↓     ↓     ↓
 └─────┼─────┘
       ↓
ادمج مخرجات Heads
       ↓
مخرجات Attention layer
```

يمتلك كل head learned projections تسمح له بتطوير attention behavior مختلفة.

الفكرة الأساسية في الفصل ليست أن لكل head دورًا واحدًا يمكن للبشر تفسيره بوضوح.

بل النقطة المهمة هي:

> تزيد Multiple heads قدرة Model على التقاط علاقات مختلفة بالتوازي.

[[IMAGE_NEEDED: Multi-head attention | Show one input sequence branching into several parallel attention heads, each with different attention patterns, then recombining into a single output | Learner should notice that multi-head attention repeats the same core mechanism in parallel with different learned projections]]

## 14. جعل Attention أكثر كفاءة

Attention قوية، لكنها مكلفة حسابيًا.

ومع نمو Models و context lengths، يبحث الباحثون عن طرق لتقليل تكلفة attention دون التضحية بقدر كبير من الجودة.

يعرض الفصل عدة approaches.

### 14.1 أسلوب Full attention

في decoder-style full-attention pattern، تستطيع token الانتباه إلى جميع المواضع السابقة المسموح بها.

من الناحية المفاهيمية:

```text
current token
    ↓
كل tokens السابقة مرشحة (all earlier tokens are candidates)
```

يوفر هذا context واسعًا، لكنه قد يكون مكلفًا.

### 14.2 أسلوب Local أو Sparse attention

تقلل Sparse/local attention عدد المواضع السابقة المرئية لعملية attention معينة.

من الناحية المفاهيمية:

```text
current token
    ↓
مجموعة أصغر من tokens السابقة القريبة
```

يمكن أن يحسن ذلك الكفاءة.

لكن إذا كانت كل layer مقيدة بصورة شديدة، فقد يفقد Model معلومات مهمة بعيدة المدى.

يصف الفصل architectures تمزج بين attention patterns الأوسع والمقيدة.

[[IMAGE_NEEDED: Full versus local attention | Show two triangular decoder-attention grids: one where each position can see all previous positions, and one where each position sees only a recent local window | Learner should notice the efficiency-versus-context tradeoff]]

### 14.3 أسلوب Multi-head attention

في standard multi-head attention، يمتلك كل head query و key و value projections خاصة به.

من الناحية المفاهيمية:

```text
head 1 → Q1 K1 V1 — إسقاطات Head الأولى
head 2 → Q2 K2 V2
head 3 → Q3 K3 V3
...
```

### 14.4 أسلوب Multi-query attention

تحافظ Multi-query attention على query projections منفصلة لكل head مع مشاركة keys و values.

من الناحية المفاهيمية:

```text
head 1 → Q1
head 2 → Q2
head 3 → Q3
             \
K و V مشتركتان (shared K and V)
```

يعرض الفصل هذا باعتباره طريقة لتحسين inference scalability عبر تقليل متطلبات key/value matrices.

### 14.5 أسلوب Grouped-query attention

توفر Grouped-query attention حلًا وسطًا.

بدلًا من:

```text
زوج K/V واحد لكل Head
```

أو:

```text
زوج K/V مشترك واحد لكل Heads
```

تستخدم:

```text
عدة مجموعات من Heads
تشارك كل مجموعة K/V
```

من الناحية المفاهيمية:

```text
Heads 1–4   → تشترك في K/V group A
Heads 5–8   → تشترك في K/V group B
Heads 9–12  → تشترك في K/V group C
```

يصف الفصل ذلك بأنه يضحي بجزء صغير من كفاءة multi-query attention مقابل جودة أفضل.

[[IMAGE_NEEDED: MHA vs MQA vs GQA | Three side-by-side diagrams showing multi-head attention with unique Q/K/V per head, multi-query attention with unique Q but one shared K/V set, and grouped-query attention with unique queries and several shared K/V groups | Learner should understand exactly what is being shared in each design]]

## 15. تقنية Flash Attention: تحسين حركة البيانات لا معنى Attention

Flash Attention هي implementation approach لجعل attention أسرع وأكثر كفاءة في استخدام الذاكرة على GPUs.

الفكرة المهمة في الفصل هي:

> يتم الحفاظ على الهدف الرياضي لـ attention، لكن تُنظم الحسابات للاستفادة من أنظمة GPU memory بصورة أكثر كفاءة.

تحتوي GPUs الحديثة على مستويات مختلفة من memory.

ويركز الفصل تحديدًا على الحركة بين:

```text
SRAM — ذاكرة أسرع وأصغر
and
HBM — ذاكرة أكبر وأبطأ نسبيًا
```

يمكن أن تصبح حركة البيانات تكلفة أداء كبيرة.

تحسن Flash Attention التنفيذ عبر تحسين طريقة تحميل البيانات المتعلقة بـ attention ونقلها ومعالجتها.

هذا التمييز مهم:

```text
Flash Attention
≠ معنى دلالي جديد لـ Attention

Flash Attention
= طريقة أكثر كفاءة لتنفيذ حسابات Attention
```

[[IMAGE_NEEDED: Flash Attention memory intuition | Show a GPU diagram with slower/larger HBM and faster/smaller SRAM, comparing inefficient repeated data movement with a tiled/reuse-oriented attention computation | Learner should notice that Flash Attention targets memory movement and execution efficiency rather than changing what attention conceptually means]]

## 16. تضيف Transformer blocks الحديثة تحسينات هندسية

أنشأ Transformer block الأصلي البنية الأساسية.

تحتفظ Models الأحدث بالأفكار الرئيسية نفسها لكنها تحسن التفاصيل.

يسلط الفصل الضوء على عدة أمثلة.

### موضع Normalization

تطبق بعض تصاميم Transformer الأحدث normalization على inputs **قبل** معالجة attention و feedforward.

ويُوصف هذا عادةً بأنه pre-normalization.

ويشير الفصل إلى ارتباط ذلك بتقليل training time المطلوب.

### أسلوب RMSNorm

يسلط الفصل الضوء على RMSNorm باعتباره بديلًا أبسط وأكثر كفاءة لـ LayerNorm المستخدم في Transformer الأصلي.

لا تحتاج إلى معادلته بعد.

في هذه المرحلة، الفكرة الأساسية هي أن normalization تظل جزءًا من block، لكن implementation choices تطورت.

### دوال Activation

يقارن الفصل ReLU في Transformer الأصلي مع variants أحدث مثل SwiGLU.

ومرة أخرى، هدف الدرس هنا هو الوعي المعماري:

```text
تظل فكرة Transformer الأساسية كما هي
+
وتستمر التفاصيل في التحسن
```

### وصلات Residual

تتضمن صورة Transformer-block الأكثر اكتمالًا أيضًا residual paths.

تسمح هذه المسارات للمعلومات بالتحرك حول sublayers الرئيسية بدلًا من إجبار كل transformation على استبدال incoming representation بالكامل.

## 17. لماذا يحتاج Transformer إلى معلومات موضعية؟

تقارن Attention بين token representations عبر sequence.

لكن اللغة تعتمد على الترتيب.

انظر إلى:

```text
dog bites man — ترتيب أول للكلمات
```

مقابل:

```text
man bites dog — ترتيب مختلف للكلمات نفسها
```

تظهر الكلمات نفسها، لكن المعنى يتغير لأن مواقعها تتغير.

لذلك يحتاج Model إلى معلومات عن ترتيب tokens.

### الأساليب الموضعية الأقدم

يصف الفصل أساليب Transformer الأصلية التي تستخدم absolute positional information.

من الناحية المفاهيمية:

```text
first token  → position 1 — الموضع الأول
second token → position 2
third token  → position 3
...
```

قد تكون هذه positional signal ثابتة أو متعلمة اعتمادًا على design.

### لماذا تجعل كفاءة Training التعامل مع Position أكثر تعقيدًا؟

يمكن أن تكون training examples بأطوال مختلفة جدًا.

لذلك تتمثل إحدى الأفكار الشائعة في packing لعدة documents أقصر داخل training context واحدة.

من الناحية المفاهيمية:

```text
| doc A | doc B | doc C | padding | — مثال على Sequence packing
```

يخلق ذلك تحديات عملية للـ positional schemes لأن كل document منفصل دلاليًا رغم مشاركته training context المعبأة نفسها.

## 18. التمثيلات الموضعية الدوّارة (Rotary positional embeddings — RoPE)

يسلط الفصل الضوء على **RoPE** باعتباره positional method حديثة مهمة.

الفكرة الأساسية على مستوى هذا الدرس هي:

> تمزج RoPE المعلومات الموضعية داخل عملية attention عبر تحويل query و key representations وفقًا لموضع token.

بدلًا من التفكير في position على أنها مجرد vector أخرى تُضاف مرة واحدة في البداية، يؤكد الفصل أن rotary positional information تدخل أثناء attention.

من الناحية المفاهيمية:

```text
token representations
        ↓
إسقاطات Q و K
        ↓
طبّق positional rotation
        ↓
Q و K مدركتان للموضع
        ↓
relevance scoring
```

[[IMAGE_NEEDED: RoPE placement in attention | Show query and key projections followed by a rotary positional transformation before Q×K relevance scoring; values remain on the information-combination path | Learner should notice that RoPE injects position into Q and K immediately before attention relevance scoring]]

### لماذا تسمى “Rotary”؟

تعتمد الطريقة على تدوير vector components داخل embedding space وفقًا للموضع.

لا تحتاج إلى تنفيذ mathematical rotation في هذا الدرس.

يكفي فهم architecture الأساسي:

```text
تساعد RoPE آلية Attention على معرفة مواضع Tokens
وكيف ترتبط المواضع بعضها ببعض
```

الموضع ضروري لأن ترتيب sequence نفسه يحمل معلومات.

### المفهوم الخاطئ 1

> يكتب LLM الاستجابة بالكامل في neural-network pass واحدة.

### لماذا هذا خطأ؟

تولد Generative LLMs عادةً token واحدة في كل مرة. وتصبح كل token مولدة حديثًا جزءًا من sequence المستخدمة في generation اللاحقة.

---

### المفهوم الخاطئ 2

> ينتج Transformer stack الكلمة النهائية مباشرةً.

### لماذا هذا خطأ؟

ينتج Transformer stack hidden representations. ويحوّل LM head هذه representations إلى scores تغطي vocabulary بالكامل، ثم تختار decoding strategy الـ output token.

---

### المفهوم الخاطئ 3

> لا يهم سوى final input token لأن output الخاصة بها وحدها تُستخدم لاختيار next token.

### لماذا هذا خطأ؟

تسهم المواضع السابقة بمعلومات سياقية من خلال attention. وقد لا تختار outputs النهائية لها next generated token مباشرةً، لكن intermediate representations من المواضع السابقة ضرورية لحساب الموضع الحالي.

---

### المفهوم الخاطئ 4

> تخزن KV cache النص الإنجليزي الذي تم توليده.

### لماذا هذا خطأ؟

يظل النص المرئي أو tokens جزءًا من sequence، لكن KV cache تعيد تحديدًا استخدام key/value representations المحسوبة سابقًا داخل attention حتى يتجنب Model تكرار عمل مكلف.

---

### المفهوم الخاطئ 5

> Attention مجرد database lookup.

### لماذا هذا خطأ؟

تحسب Attention learned relevance scores بين projected representations، ثم تكوّن weighted combination من value vectors. وتظهر العلاقات نتيجة model parameters المتعلمة.

---

### المفهوم الخاطئ 6

> تمثل Query و Key و Value ثلاث جمل مختلفة.

### لماذا هذا خطأ؟

هي learned projections لـ input representations تُستخدم لأدوار مختلفة داخل attention.

---

### المفهوم الخاطئ 7

> تعني Multi-head attention أن Model يولد عدة إجابات ثم يصوت بينها.

### لماذا هذا خطأ؟

تنفذ عدة attention heads حسابات attention بالتوازي داخل layer. ثم تُدمج نتائجها لتكوين representation الخاصة بالـ layer.

---

### المفهوم الخاطئ 8

> Flash Attention آلية attention دلالية مختلفة تغير ما يركز عليه Model.

### لماذا هذا خطأ؟

يقدم الفصل Flash Attention باعتبارها implementation optimization تجعل attention computation أكثر كفاءة على أنظمة GPU memory.

---

### المفهوم الخاطئ 9

> المعلومات الموضعية اختيارية لأن tokens تحتوي بالفعل على ترتيبها.

### لماذا هذا خطأ؟

لا تشفّر Token embeddings تلقائيًا موضع token داخل sequence. تحتاج Transformer architectures إلى positional information حتى يؤثر الترتيب في المعالجة.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مصطلح Autoregressive model | Model تصبح مخرجاته التي ولدها سابقًا جزءًا من input المستخدم في predictions اللاحقة |
| مصطلح Forward pass | تدفق واحد لـ input عبر حسابات neural network لإنتاج outputs |
| مصطلح Transformer block | وحدة neural-network متكررة تحتوي على attention و feedforward processing بالإضافة إلى عمليات داعمة |
| مصطلح LM head | Output layer تحوّل hidden representation إلى next-token scores تغطي vocabulary بالكامل |
| مصطلح Hidden state | Internal vector representation ينتجها Model لـ token position |
| مصطلح Decoding strategy | قاعدة أو عملية تُستخدم لاختيار output token فعلية من model scores |
| مصطلح Greedy decoding | اختيار next token صاحبة أعلى score دائمًا |
| مصطلح Sampling | الاختيار بين candidate tokens وفقًا لـ probability distribution بدلًا من أخذ الأعلى دائمًا |
| مصطلح Context length | الحد الأقصى لعدد token positions التي يستطيع Model معالجتها داخل context واحدة |
| مصطلح KV cache | Attention key/value representations مخزنة مؤقتًا من tokens السابقة لتجنب generation computation المتكرر |
| مصطلح Self-attention | آلية تسمح لـ token position بدمج معلومات من المواضع الأخرى المسموح بها داخل sequence نفسها |
| مصطلح Query | Learned projection تمثل ما يستخدمه token position لمطابقة relevance |
| مصطلح Key | Learned projection تُستخدم لتحديد مدى صلة موضع معين بـ query |
| مصطلح Value | Learned projection تحمل المعلومات التي يمكن دمجها في attention output |
| مصطلح Attention weight | قيمة relevance بعد normalization تحدد مدى قوة مساهمة موضع معين |
| مصطلح Attention head | نسخة متوازية واحدة من attention calculation ولها learned projections خاصة بها |
| مصطلح Multi-head attention | عدة attention heads تُحسب بالتوازي ثم تُدمج |
| مصطلح Sparse/local attention | Attention pattern تقيد كل position بمجموعة فرعية من context positions |
| مصطلح Multi-query attention | Attention variant تحتفظ فيها heads بـ queries مختلفة مع مشاركة keys و values |
| مصطلح Grouped-query attention | Attention variant تشترك فيها مجموعات من heads في key/value representations |
| مصطلح Flash Attention | GPU-efficient implementation approach تقلل حركة memory المكلفة أثناء attention |
| مصطلح Feedforward network / MLP | Neural-network transformation لكل position داخل Transformer block |
| مصطلح Residual connection | مسار يحمل المعلومات حول sublayer ويجمعها مع النتيجة المحولة |
| مصطلح RMSNorm | Normalization variant يبرزها الفصل باعتبارها تحسينًا حديثًا في Transformer |
| مصطلح RoPE | Positional method دوّارة تُطبق على query/key representations قبل relevance scoring |
| مصطلح Sequence packing | وضع عدة training documents قصيرة بكفاءة داخل context ثابتة الحجم وأكبر |

## احتفظ بهذه الفكرة

**أفضل طريقة لفهم generative Transformer LLM هي باعتباره آلة متكررة للتنبؤ بـ next token. ينشئ tokenizer قيم token IDs، وتحولها embeddings إلى vectors، ثم تمزج Transformer blocks المتراكبة المعلومات السياقية مرارًا عبر attention وتحول representations عبر feedforward networks، وبعد ذلك يحول LM head الموضع الأخير إلى scores تغطي vocabulary بالكامل، وتختار decoding strategy token واحدة. تُضاف هذه token إلى context، ويعاد استخدام attention state المخزنة مؤقتًا عندما يكون ذلك ممكنًا، وتستمر generation cycle بالكامل.**
