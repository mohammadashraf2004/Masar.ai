## 1. ما الذي يقدّمه خادم MCP فعليًا؟ (What does an MCP server actually provide?)

من جهة Client، بدا MCP كوسيلة لربط Application بقدرات جديدة. أما من جهة Server فالمهمة معاكسة: **تجميع القدرات المفيدة بحيث تستطيع تطبيقات متعددة متوافقة مع MCP اكتشافها واستخدامها**.

تظل Primitives الأساسية الثلاثة كما هي:

| العنصر (Primitive) | الجهة المقصودة بالتحكم | الغرض الرئيسي |
|---|---|---|
| نوع **Tool** | يتحكم فيه Model | تنفيذ إجراء |
| نوع **Resource** | يتحكم فيه Application | توفير بيانات سياقية |
| نوع **Prompt** | يتحكم فيه مستخدم Application | توفير تعليمات تفاعلية قابلة لإعادة الاستخدام |

نموذج التحكم هذا هو نمط تفاعل مقصود، وليس آلية فرض. يمكن لـ Client application أن يختار عرض Primitives أو استخدامها بطريقة مختلفة. لذلك، بصفتك مطور Server، فأنت تصمم للمسار الطبيعي المقصود، لكن لا يمكنك التحكم بالكامل في UX الخاصة بـ Host application.

### الفائدة الأعمق هي قابلية التوزيع (Distribution)

قبل وجود Protocol مشترك، كان تكامل Tool أو البيانات غالبًا مضمّنًا مباشرة داخل تطبيق AI واحد. وإذا أراد تطبيق ثانٍ التكامل نفسه، كان على مطوره تكرار العمل: دراسة API، وكتابة منطق Authentication، وإنشاء Wrappers، وتعريف Schemas الموجهة إلى Model، وصيانة التكامل.

ينقل خادم MCP هذا التكامل إلى مكوّن قابل لإعادة الاستخدام:

```text
قبل MCP (Before MCP)
التطبيق A ── تكامل مخصص (custom integration) ── الخدمة (Service)
التطبيق B ── تكامل آخر (another integration) ── الخدمة (Service)
التطبيق C ── تكامل آخر (another integration) ── الخدمة (Service)

مع MCP (With MCP)
التطبيق A ─┐
التطبيق B ─┼── خادم MCP (MCP Server) ── الخدمة (Service)/البيانات (Data)/المنطق (Logic)
التطبيق C ─┘
```

يمكن لمؤلف Server أن يفهم Service الأساسية بعمق ويوزّع تلك المعرفة مرة واحدة، بينما يركّز مطورو Client على سلوك تطبيقاتهم الخاصة.

{{image:mcp-server-distribution-layer}}

### لماذا تهم جودة تصميم Server؟ (Why server design quality matters)

لا يؤدي سهولة تطوير Server تلقائيًا إلى خوادم جيدة. ويحذر المصدر من أنماط فشل حقيقية مثل:

- خوادم غير موثوقة،
- صلاحيات محلية مفرطة،
- اتصالات غير مستقرة،
- كتالوجات Tools ضخمة تستهلك context window،
- ارتباك Model عند اختيار Tool.

الدرس هنا هو أن **جودة Server هي جزئيًا تصميم لواجهة AI**، وليست مجرد تصميم تقليدي لـ backend API.

## 2. ربط Servers بالتطبيقات باستخدام Transports (Connecting servers to applications with transports)

تستخدم رسائل MCP بروتوكول JSON-RPC، لكن Transport هو ما يحدد كيفية انتقال هذه الرسائل بين Client و Server.

يركز الفصل المقدَّم على نوعين من Transport:

| نوع Transport | النشر المعتاد | كيفية عمله |
|---|---|---|
| نقل محلي عبر `stdio` | Server محلي | يشغّل Client الخادم كـ subprocess طويل التشغيل ويتبادل الرسائل عبر stdin/stdout |
| نقل بعيد عبر Streamable HTTP | Server بعيد | يرسل Client طلبات HTTP POST منفردة إلى MCP endpoint، مع إمكانية SSE streaming للاستجابات الطويلة |

### النقل المحلي عبر `stdio` (stdio)

يُعد stdio مناسبًا بطبيعته للخوادم الموزعة على هيئة Code يشغّله المستخدمون محليًا. يمكن لملف README أن يخبر Host application بالأمر والـ arguments التي تشغّل Server. يبدأ Client الـ process ويستمر في التواصل معها طوال مدة تلك الجلسة المحلية.

### النقل البعيد عبر Streamable HTTP (Streamable HTTP)

صُمم Streamable HTTP للخوادم المستضافة عن بُعد. يصف الفصل MCP endpoint مثل `/mcp` يتعامل مع طلبات POST. قد يعيد الطلب القصير JSON عاديًا فورًا؛ بينما قد تستخدم العملية طويلة التشغيل SSE response stream مؤقتًا لإرسال التقدم أو الإشعارات.

لذلك من الأفضل تصور التفاعل البعيد الحديث كسلسلة من الطلبات، لا كاتصال Socket دائم واحد.

[[IMAGE_NEEDED: MCP server transport comparison | Two panels: stdio with a client launching a local server subprocess and reading/writing streams; Streamable HTTP with a client sending POST requests to a remote /mcp endpoint and optionally receiving an SSE response stream | Learner should notice the local process lifecycle versus remote request/response lifecycle]]

### النشر البعيد يوسّع سطح الأمان (Remote deployment expands the security surface)

يشدد المصدر على أن الخوادم المستضافة عن بُعد تحتاج إلى التفكير في Authorization والأمان منذ البداية. وتشمل التهديدات المذكورة interception، وإساءة استخدام session/token، و tool poisoning، وهجمات أخرى على البيانات و credentials.

طريقة التفكير التصميمية المهمة بسيطة: **خادم MCP البعيد هو Network service لها مسارات هجوم خاصة بـ AI، وليس مساعدًا موثوقًا لمجرد أنه يتحدث MCP.**

## 3. طريقتان لبناء خوادم MCP باستخدام Python (Two ways to build Python MCP servers)

يعرض المصدر مستويين لتطوير Server في Python SDK.

### الواجهة عالية المستوى (`MCPServer`)

يُعد `MCPServer` النهج المفضل في معظم حالات الاستخدام. فهو يوفّر decorators و type inference بحيث يمكن لدوال Python العادية أن تصبح MCP tools و prompts و resources مع قدر قليل من protocol boilerplate.

يمكن أن يكون Server بسيط بالحد الأدنى بهذا الحجم من الناحية المفاهيمية:

⟦CODE_0⟧

تدعم API عالية المستوى أيضًا lifecycle management و advanced configuration.

### الواجهة منخفضة المستوى (Low-level API)

تُظهر Low-level API قدرًا أكبر من Protocol مباشرة. يستطيع المطور تنفيذ handlers لعمليات مثل listing tools و calling tools، وبناء protocol response objects يدويًا، والتحكم في سلوك capabilities بدرجة أدق.

تأتي هذه المرونة مع قدر كبير من Code الإضافي. وقد تحتاج إلى تعريف:

- metadata لمرحلة initialization،
- handlers للقوائم،
- handlers للاستدعاءات،
- مخططات JSON (JSON Schemas)،
- كائنات النتائج (result objects)،
- routing بين عدة Tools،
- حالة lifespan وعمليات cleanup.

### النموذج الذهني (Mental model)

```text
واجهة MCPServer (MCPServer API)
دالة Python + مُزيّن (decorator) + تلميحات الأنواع (type hints)
        ↓
تستنتج SDK تمثيل البروتوكول (protocol representation)

واجهة منخفضة المستوى (Low-level API)
يكتب المطور protocol handlers و result objects مباشرة
```

يشرح الفصل Low-level API لإظهار الآليات الداخلية، لكنه يعود بعد ذلك إلى `MCPServer` لأن بساطته عادةً هي المقايضة الأفضل.

### ملاحظة حول التسمية (A note on naming)

يحذر المصدر المقدَّم من الخلط بين API عالية المستوى `MCPServer` وبين Frameworks أخرى غير مرتبطة تحمل أسماء متشابهة أو بينه وبين FastAPI. وقد تغيرت تسميته تاريخيًا عبر إصدارات SDK، لذا اقرأ Code في سياق إصدار SDK المستخدم.

## 4. لماذا يُعد تغليف REST API وفق Endpoint واحد مقابل Tool واحدة نمطًا مضادًا؟ (Why wrapping a REST API endpoint-by-endpoint is often an antipattern)

تحسّن REST APIs التقليدية و MCP tools الموجهة إلى Model تجربة أنواع مختلفة من المستهلكين.

غالبًا ما تعرض REST APIs endpoints صغيرة قابلة للتركيب لأن Code الحتمي في Application يستطيع ربطها بشكل موثوق. أما LLM فعليه أن **يختار** كل Tool بناءً على الأسماء والأوصاف و schemas و context الحالي.

تخيل أن Agent يريد إرسال رسالة مباشرة إلى Bob. قد يعرض API wrapper دقيق التفاصيل:

```text
1. find_user_id(name) — البحث عن معرّف المستخدم بالاسم
2. open_direct_message_channel(user_id) — فتح قناة رسالة مباشرة لمعرّف المستخدم
3. send_message(channel_id, text) — إرسال رسالة إلى معرّف القناة
```

بالنسبة إلى Agent، قد تكون Tool الأفضل:

```text
send_direct_message(user_name, text) — إرسال رسالة مباشرة باستخدام اسم المستخدم والنص
```

ما يزال Server قادرًا على استدعاء عدة helper functions خاصة داخليًا. والمهم هو أن **الواجهة الموجّهة إلى Agent تعكس الإجراء المتكامل الذي يريد Agent إنجازه بالفعل**.

### لماذا تضر الدقة الزائدة في تقسيم Tools؟ (Why granularity hurts)

إذا كان لكل قرار لاختيار Tool احتمال ما للخطأ، فإن الحاجة إلى عدة اختيارات تراكم احتمال فشل Workflow كامل. كما أنها تنشئ عددًا أكبر من model turns، وتتضمن الـ turns اللاحقة input/output tokens من الـ turns السابقة، ما قد يزيد التكلفة بصورة كبيرة.

يقدم المصدر مثالًا بسيطًا: معدل نجاح قدره 95% في اختيار Tool عند تكراره عبر خمسة اختيارات مطلوبة ينتج معدل نجاح إجماليًا يقارب 77% للسلسلة كاملة.

### مفهوم Agent stories

يوصي المصدر بالتفكير من خلال **Agent stories**، بصورة مماثلة لـ product user stories.

بدلًا من أن تسأل:

> ما Endpoints التي تتضمنها API؟

اسأل:

> ما الإجراء المفيد الذي يحاول Agent إكماله؟

ينقل هذا تصميم Server من محاكاة API إلى قابلية الاستخدام من قِبل Agent.

## 5. تصميم Tools يستطيع LLM استخدامها بموثوقية (Designing tools that an LLM can use reliably)

باستخدام High-level API، تصبح دالة Python عبارة عن Tool عند تزيينها بـ `@mcp.tool()`.

يمكن لـ SDK استنتاج protocol metadata مهمة من بنية Python العادية:

- اسم function → اسم Tool،
- docstring → الوصف،
- أسماء/أنواع parameters → input schema،
- return annotation → output schema عندما يكون ذلك مدعومًا.

تعني هذه السهولة أن التسمية و typing في Python يصبحان جزءًا من الواجهة الموجهة إلى Model.

### قائمة فحص تصميم Tool (Tool design checklist)

ينبغي أن تمتلك Tool القوية:

- اسمًا مميزًا موجّهًا نحو الإجراء،
- وصفًا واضحًا بما يكفي لكي يختارها Model،
- inputs محددة بوضوح،
- outputs محددة بوضوح،
- type annotations مفيدة،
- namespace مناسبة عند وجود عدة Tools مترابطة،
- مسؤولية واحدة متماسكة من البداية إلى النهاية.

### تنظيم الأسماء باستخدام Namespace (Namespacing)

يمكن لـ prefix مفصول بـ underscore أن يوفر سياقًا إضافيًا ويقلل الغموض:

```text
grader_generate_report_card
grader_calculate_gpa
```

تصبح Namespacing مفيدة بصورة خاصة عندما تجمع تطبيقات Client بين Tools من عدة Servers.

### أوصاف Tool جزء من مساحة Reasoning لدى Model (Tool descriptions are part of the model's reasoning surface)

ينبغي أن تكون الأوصاف مفصلة بما يكفي ليفهم Model متى تنطبق Tool، ولكن من دون إسهاب يهدر context window. يقارن المصدر كتابة وصف Tool بشرح Code لمهندس جديد: اجعل الافتراضات الضمنية صريحة عندما تؤثر في الاستخدام الصحيح.

### اجعل الكتالوج صغيرًا عن قصد (Keep the catalog intentionally small)

يحذر المصدر من أن أداء اختيار Tool قد يتدهور عندما تكون Tools كثيرة نشطة في الوقت نفسه. وهذا يعني أن مطور Server لا ينبغي أن ينقل المسؤولية كلها إلى Client. يكون الكتالوج الأصغر من الإجراءات المصممة جيدًا أسهل عمومًا على Agents والمستخدمين.

### تلميحات Cache والقوائم الحتمية (Cache hints and deterministic lists)

بالنسبة إلى القوائم المستقرة نسبيًا، يصف المصدر cache hints مثل TTL. كما يساعد deterministic ordering عملية caching اللاحقة لأن القائمة المنطقية نفسها تصبح أكثر احتمالًا لإنتاج prompt content مستقرة.

## 6. مخرجات Tool المنظمة ومتعددة الوسائط والمزوّدة بـ Annotations (Structured, multimodal, and annotated tool outputs)

إحدى المزايا الرئيسية لـ High-level API هي أن return types يمكن أن تتحول تلقائيًا إلى structured output schemas.

يسرد المصدر أنماط structured-return المدعومة مثل:

- نماذج Pydantic،
- أنواع TypedDicts،
- أنواع dataclasses،
- classes ذات typing،
- dictionaries قابلة لـ JSON serialization،
- أنواع primitive/generic مغلفة داخل structured result.

على سبيل المثال:

⟦CODE_1⟧

تمنح return annotation الـ SDK معلومات كافية لوصف شكل output والتحقق منه.

### الصور والصوت (Images and audio)

توفر High-level server API أيضًا أنواع output مريحة للصور والصوت. يستطيع Server إعادة binary data مغلفة بالشكل المناسب لكي يستقبل Client content blocks أصلية، من دون أن ينشئ مطور Application يدويًا كل wire-level response object.

### ملاحظات سلوك Tool (Tool annotations)

يمكن لـ Tool تضمين hints عن سلوكها، مثل كونها read-only. تمنح هذه التلميحات Clients معلومات أكثر عن Tool، لكن لا ينبغي الخلط بينها وبين Security enforcement.

### الإجراءات الكاملة يمكنها استدعاء Helper functions داخليًا (Complete actions can call helper functions internally)

يمكن لـ Tool المعروضة إلى Model استدعاء دوال Python عادية أخرى، بما في ذلك دوال مزينة بنفسها كـ Tools. لا يحتاج Agent إلى رؤية التقسيم الداخلي. يحافظ هذا على testability مع إبقاء الواجهة الموجهة إلى Model بسيطة.

## 7. كيف تتحرك Tools عبر دورة حياة MCP؟ (How tools move through the MCP lifecycle)

يساعدك فهم تدفق الرسائل على تصميم سلوك أفضل لـ Server.

يكون تدفق Tool المعتاد كالتالي:

```text
Client → Server: tools/list — يطلب Client قائمة Tools
Server → Client: تعريفات Tools (tool definitions)
Client → Model: طلب المستخدم (user request) + Tools المتاحة (available tools)
Model → Client: Tool المختارة (selected tool) + arguments
Client → Server: tools/call — يطلب Client استدعاء Tool
Server: تنفيذ Tool (execute tool) + التحقق من output (validate output)
Server → Client: نتيجة Tool (tool result)
Client → Model: نتيجة Tool (tool result)
Model: متابعة reasoning أو الإجابة عن المستخدم (continue reasoning or answer user)
```

لا يقرر Server عادةً متى ينبغي لـ Model استدعاء Tool. مسؤوليته الأساسية هي نشر تعريف Tool قابلة للاستخدام وتنفيذ العملية المطلوبة بصورة صحيحة.

### قوائم Tool الديناميكية (Dynamic tool lists)

إذا تغيّر كتالوج Tools المتاحة، يمكن لـ Server الإعلان عن تغيّر القائمة عبر request context. ويمكن لـ Clients الحديثة التي تستمع للتغييرات عندئذ تحديث عرضها.

يصف المصدر context notification helpers لتغيّرات قوائم Tool و Prompt و Resource، إلى جانب التحديثات على Resources بعينها.

## 8. التعامل مع أخطاء Tool: هل يستطيع Model التعافي؟ (Handling tool errors: can the model recover?)

يقدم الفصل قاعدة قرار مفيدة لاختيار نوع الخطأ:

> **هل يستطيع Model أفضل اطلاعًا إصلاح المشكلة؟**

### خطأ قابل للتعافي ومرئي لـ Model (Recoverable/model-visible error)

إذا كان Model قادرًا على تصحيح طلبه، فارفع Python exception عاديًا مع رسالة مفيدة.

مثال:

```text
الطالب المطلوب (Requested student): 'Alan Turning'
لا يعرف Server طالبًا بهذا الاسم (Server knows no such student).
```

يمكن لخطأ مفيد أن يخبر Model بأن الاسم غير موجود، ما يسمح له بسؤال المستخدم أو إعادة المحاولة بقيمة مصححة.

### خطأ Protocol غير قابل للتعافي (Protocol/unrecoverable error)

إذا كان الطلب غير صالح بصورة جوهرية، أو لا يستطيع Model إصلاح الحالة الأساسية باستخدام arguments أفضل، يوصي المصدر بـ MCP protocol error منظّم.

مثال:

```text
لم تُنشر الدرجات بعد (Grades have not been published yet).
```

لا يمكن لأي تصحيح إملائي أو argument بديل أن يجعل تلك الحالة غير المتاحة صالحة.

### رسائل الخطأ لها جمهوران (Error messages have two audiences)

تساعد الرسالة الجيدة كلاً من:

- مطور بشري في تشخيص Server،
- Model في تحديد ما إذا كان يمكنه التعافي وكيف يفعل ذلك.

## 9. تقديم Prompts قابلة لإعادة الاستخدام (Serving reusable prompts)

تتيح Prompts لـ Server توزيع تعليمات تفاعل قابلة لإعادة الاستخدام على تطبيقات Client. وفي نموذج تفاعل MCP المقصود، تكون Prompts تحت تحكم المستخدم: يمكن لـ Application عرضها في menu أو command palette أو slash-command interface أو UI أخرى.

تُزيّن دالة Prompt باستخدام `@mcp.prompt()` ويمكنها إعادة representations مثل النص أو message objects.

### Prompts ذات Parameters (Parameterized prompts)

تتحول parameters الخاصة بالدالة إلى قيم يمكن لـ Client جمعها وإرسالها إلى Server. ثم يحقن Server هذه القيم في template الخاصة به.

⟦CODE_2⟧

لا يفرض MCP لغة templating بعينها. فـ Python f-strings مجرد احتمال واحد.

### مبادئ تصميم Prompt من المصدر (Prompt-design principles from the source)

يلخص الفصل خمس أفكار مفيدة في prompting:

1. أعطِ توجيهًا واضحًا.
2. حدّد format عندما يكون مفيدًا.
3. قدّم أمثلة عندما تحسن السلوك.
4. قيّم الجودة عبر Models وحالات مختلفة.
5. قسّم العمل عندما تصبح Prompt واحدة واسعة جدًا.

تقدم الأمثلة مقايضة: فهي تساعد Model على فهم المهمة، لكنها قد تثبت النبرة والطول والبنية بقوة أكبر مما هو مقصود.

### تصميم Prompt مستقل عن Model (Model-agnostic prompt design)

قد تستجيب عائلات Models المختلفة بصورة جيدة لبنى Prompt مختلفة. وبما أن خوادم MCP مصممة للعمل مع Models متعددة، فتجنب جعل Server يعتمد اعتمادًا كبيرًا على حيلة خاصة بـ Provider واحد، إلا إذا اختبرتها على نطاق واسع ووثقت ذلك الافتراض.

### الانتباه إلى تكلفة System-prompt (System-prompt cost awareness)

يُرسل محتوى Prompt الدائم مرارًا إلى Model، ولذلك له تكلفة Token مستمرة. ويظل من الضروري كتابة Prompts واضحة ومفيدة مع مراعاة كفاءة Context.

## 10. Prompts متعددة الأدوار و Prefilling و Tools و Resources (Multiturn prompts, prefilling, tools, and resources)

لا يلزم أن تكون Prompt عبارة عن سلسلة نصية واحدة. يمكنها إعادة sequence من رسائل user و assistant تمثل بداية Conversation.

### التهيئة المسبقة (Prefilling)

يمكن لـ Server توفير رسالة assistant جزئية تحدد شكل Response أو نقطة البداية.

من الناحية المفاهيمية:

```text
رسالة المستخدم (User message):
  Summarize this text into 3 ideas. — Prompt المصدر المطلوب تلخيصه إلى 3 أفكار

التهيئة المسبقة للمساعد (Assistant prefill):
  Here are 3 main ideas: — بداية رسالة assistant المحضّرة مسبقًا
  1. — بداية العنصر الأول
```

يواصل Model من محتوى assistant المحضّر مسبقًا. ويمكن لهذا تشجيع بنية معينة بقوة أكبر من instruction نصية عادية.

### يمكن لـ Prompts توجيه استخدام Tool (Prompts can guide tool usage)

يمكن لـ Prompt أن تخبر Model بالنظر في Tool معينة، أو يمكن لـ Server code استدعاء دالة Python عادية/دالة Tool واستخدام نتيجتها أثناء بناء رسائل Prompt. وينبغي لمؤلف Server أن يفهم أن Application ما يزال في النهاية يقرر كيفية إدراج رسائل Prompt المعادة داخل محادثة Model.

### يمكن لـ Prompts ربط Resources (Prompts can link resources)

يوضح المصدر تضمين `ResourceLink` داخل محتوى Prompt. ويسمح ذلك لـ Prompt قابلة لإعادة الاستخدام بتوجيه Client نحو contextual data يعرضها Server نفسه.

[[IMAGE_NEEDED: MCP prompt lifecycle and composition | A diagram showing prompts/list discovery, user selecting a prompt, prompts/get with arguments, server returning user/assistant messages, and optional links to tools/resources | Learner should notice that prompts are server-distributed but normally user-selected and client-integrated]]

### دورة اكتشاف Prompt واستخدامها (Prompt discovery and use lifecycle)

```text
Client → Server: prompts/list — يطلب Client قائمة Prompts
Server → Client: تعريفات Prompts المتاحة (available prompt definitions)
المستخدم يختار Prompt داخل Application (User selects prompt in application)
Client → Server: prompts/get(name, arguments) — يطلب Client Prompt بالاسم و arguments
Server → Client: رسائل Prompt (prompt messages)
Client → Model: دمج Prompt وفق UX الخاصة بـ Host (integrate prompt according to host UX)
```

إذا تغيّرت قائمة Prompts، يستطيع Server إخطار Clients الحديثة المشتركة لكي تحدّثها.

## 11. تقديم Resources كسياق للقراءة فقط (Serving resources as read-only context)

توفر Resources بيانات يمكن لتطبيقات Client استخدامها كـ Model context. وتشمل أمثلة المصدر:

- بيانات logs،
- مخططات database schemas،
- بيانات images،
- ملفات PDFs،
- إعدادات JSON/YAML،
- ملفات documentation و knowledge.

يُنشأ Resource أساسي باستخدام `@mcp.resource(uri)`.

⟦CODE_3⟧

تُعد URI المعرّف الثابت لـ Resource. كما أن الأوصاف مهمة لأن Client يمكنه استخدامها عند تحديد Resource ذات الصلة بمهمة المستخدم.

### ينبغي أن تكون Resources خفيفة (Resources should be lightweight)

يقدم الفصل تحذيرًا تصميميًا قويًا: ينبغي أن تعمل دوال Resource أساسًا على **استرجاع البيانات**. ويجب أن تتجنب computation الثقيلة و side effects. فإذا أدت قراءة Resource سرًا إلى تعديل state أو تشغيل إجراء، يكون Server قد طمس الحد الفاصل بين Resource و Tool.

هناك قاعدة مفيدة:

```text
الأداة (Tool)     → إجراء (action)
المورد (Resource) → بيانات (data)
```

### أنواع المحتوى (Content types)

يمكن لـ Text resources إعادة strings. ويمكن لـ Binary resources إعادة bytes. وقد تمثّل SDK هياكل أخرى قابلة لـ serialization على هيئة JSON text.

## 12. قوالب Resource والتحميل المؤجل (Resource templates and deferred loading)

يمتلك Resource الثابت URI محددة واحدة. أما **resource template** فيحتوي على variables داخل URI الخاصة به، ما يسمح لتعريف Server واحد بتمثيل Resources كثيرة مترابطة.

مثال مفاهيمي:

⟦CODE_4⟧

يتحول variable الموجود في URI إلى parameter في دالة Python. ويمكن لـ Client اختيار قيمة محددة عند قراءة Resource.

### التحميل المؤجل (Deferred loading)

لا يحتاج Server إلى تحميل البيانات الكاملة لكل Resource لمجرد إدراج Resources في قائمة. يمكن لـ SDK الاحتفاظ بـ representations الخاصة بـ metadata/functions داخل resource manager، ثم استدعاء الدالة فقط عندما يقرأ Client الـ Resource بالفعل.

هذا مهم لقابلية التوسع، لأن الاكتشاف ينبغي أن يكون أرخص بكثير من تحميل كل Resource ممكن.

### كائنات Resource (Resource objects)

يعرض الفصل أيضًا classes أكثر صراحة للـ Resource مثل `FileResource`. يمكن إعادتها من decorated functions أو إضافتها مباشرة إلى resource manager الخاصة بـ Server عندما يحتاج Server إلى تحكم أكبر مما توفره قيمة return بسيطة من نوع string/bytes.

### ملاحظات Resource (Resource annotations)

يمكن لـ annotations الاختيارية توصيل hints مثل audience و priority ومعلومات last-modified. وهذه Metadata مخصصة لـ Client، وليست بديلًا عن access control أو application policy.

## 13. تقديم Resources كبيرة بأمان وكفاءة (Serving large resources safely and efficiently)

لا ينبغي ببساطة دفع الملفات الكبيرة عبر MCP في استجابة هائلة واحدة. يصف المصدر المقدَّم استراتيجيتين عمليتين.

### الاستراتيجية 1: الإحالة عبر URL (Strategy 1: URL indirection)

يمكن لـ Resource تحديد أو إعادة URL يجلبه Client من خارج MCP payload.

يكون هذا مفيدًا بصورة خاصة عندما يكون الكائن الفعلي موجودًا في Storage مصممة لتوصيل البيانات الكبيرة.

بالنسبة إلى URLs منتهية الصلاحية أو المتغيرة، أبقِ URI الخاصة بـ MCP resource ثابتة وأعد fetch URL الحالية عندما يقرأ Client الـ Resource.

### الاستراتيجية 2: التقسيم عبر Resource templates (Strategy 2: chunking through resource templates)

يمكن لـ Template عرض parameters شبيهة بـ query مثل start/count، بحيث يقرأ Client جزءًا فقط من البيانات:

```text
logs://application.log?start=0&count=100 — الشريحة الأولى من log
logs://application.log?start=100&count=100 — الشريحة التالية من log
```

يستخدم المصدر logs الموجّهة بحسب الأسطر مثالًا طبيعيًا على Chunking.

### أخبر Clients بالحجم عندما يكون ذلك ممكنًا (Tell clients about size when possible)

يسمح توفير metadata عن حجم Resource لـ Client بتحديد ما إذا كان تحميل Resource كاملة مناسبًا لـ Context أو UX الخاصة به.

### لماذا يُعد هذا أيضًا Context engineering؟ (Why this is also context engineering)

حتى لو لم تكن قيود Transport مشكلة، فإن تحميل Resources ضخمة داخل Model context قد يهدر Tokens ويزاحم المعلومات التي يحتاج إليها Model فعلًا.

## 14. دورة حياة Resource وأنماط الاستخدام المتقدمة (Resource lifecycle and advanced usage patterns)

يفصل Protocol بين اكتشاف Resource وقراءة Resource:

```text
Client → Server: resources/list — يطلب Client قائمة Resources
Server → Client: Metadata + URIs

يختار Client الـ Resource (Client chooses resource)

Client → Server: resources/read(uri) — يطلب Client قراءة URI
Server → Client: المحتوى (content)
```

تُكتشف Resource templates من خلال عملية list خاصة بها، وتُنشأ Instances منها باستخدام قيم URI فعلية.

### إشعارات التغيير والاشتراكات (Change notifications and subscriptions)

يميّز المصدر بين تصميم Subscription أقدم خاص بالـ Resource ونموذج Listening الحديث. وفي التدفق الحديث الموصوف، يستطيع Client إرسال طلب واحد `subscriptions/listen` يصف أنواع التغييرات التي يهتم بها. يتعامل `MCPServer` مع آليات Subscription، بينما يعلن Server code التغييرات عبر context notification methods.

### حالات استخدام Resource تتجاوز فتح ملف (Resource use cases beyond 'open this file')

يصف الفصل أنماطًا أكثر ثراءً:

- Context لتحليل logs،
- documentation تقنية محدثة،
- اكتشاف Entities،
- Retrieval شبيه بـ RAG يعيد Resource URIs،
- Caching لمراجع Resource بحيث لا يلزم إبقاء Context القديمة موسعة بالكامل.

هناك مبدأ متكرر مفاده أن **Resources تحت تحكم Application**. يجعل Server البيانات قابلة للاكتشاف والقراءة؛ ويقرر Client application كيف ومتى تدخل تلك البيانات إلى Context الخاصة بـ Model.

## 15. الاختبار أثناء التطوير باستخدام MCP Inspector (Testing during development with MCP Inspector)

يقدم المصدر MCP Inspector باعتباره Client تفاعليًا للتطوير لخوادم MCP. فهو يسمح لك بفحص ما يعرضه Server وتشغيل السلوك يدويًا.

هذا مفيد بصورة خاصة لأن صحة MCP server لها عدة طبقات:

- هل يبدأ Server؟
- هل يعمل اكتشاف capabilities؟
- هل يمكن فهم schemas الخاصة بـ Tool؟
- هل تعيد استدعاءات Tool المحتوى و structured output المتوقعين؟
- هل يمكن إدراج Resources وتحميلها؟
- هل تظهر Prompts وتُعرض مع arguments بصورة صحيحة؟
- هل تظهر Notifications عند توقعها؟

يعرض المصدر نمط command للتطوير مثل:

```text
uv run mcp dev server.py — تشغيل Server في وضع تطوير MCP
```

كما يصف خيارات لإضافة development dependencies أو mounting لـ local code قابل للتعديل.

### لماذا يهم اختبار Protocol تفاعليًا؟ (Why interactive protocol testing matters)

يمكن لدالة Python أن تعمل بصورة صحيحة عند استدعائها مباشرة، ومع ذلك تعرض MCP interface سيئة أو غير صالحة. ويُظهر الاختبار من خلال MCP client فعلي التمثيل على مستوى Protocol الذي ستراه التطبيقات الحقيقية.

## مفاهيم خاطئة مهمة (Important misconceptions)

### الاعتقاد الخاطئ 1: «خادم MCP هو في الأساس REST API مع Endpoints أعيدت تسميتها.» (Misconception 1)

**لماذا هذا خطأ:** ينبغي لـ Tools الموجهة إلى Agent غالبًا أن تمثل النية من البداية إلى النهاية بدلًا من محاكاة عمليات API دقيقة التفاصيل.

### الاعتقاد الخاطئ 2: «كلما زاد عدد Tools التي يعرضها Server كان ذلك أفضل.» (Misconception 2)

**لماذا هذا خطأ:** تستهلك كتالوجات Tools الكبيرة Context وقد تقلل دقة اختيار Tool.

### الاعتقاد الخاطئ 3: «ينفذ Model دالة Python الخاصة بـ Tool مباشرة.» (Misconception 3)

**لماذا هذا خطأ:** يختار Model الـ Tool؛ ثم يرسل Client استدعاء MCP إلى Server؛ وينفذ Server الدالة ويعيد النتيجة.

### الاعتقاد الخاطئ 4: «Structured output مجرد Documentation.» (Misconception 4)

**لماذا هذا خطأ:** تسمح Schemas بالتحقق من Outputs واستهلاكها بصورة متوقعة من قِبل Clients.

### الاعتقاد الخاطئ 5: «ينبغي أن تكون كل أخطاء Tool من نوع MCP protocol errors.» (Misconception 5)

**لماذا هذا خطأ:** ينبغي عادةً عرض الأخطاء العادية التي يستطيع Model تصحيحها بطريقة تمكّنه من التعلم منها وإعادة المحاولة.

### الاعتقاد الخاطئ 6: «MCP prompts هي System prompts تلقائيًا.» (Misconception 6)

**لماذا هذا خطأ:** يوزع Server محتوى Prompt، لكن Client application هو من يقرر كيفية دمجه.

### الاعتقاد الخاطئ 7: «ينبغي لـ Resource تنفيذ إجراءات مفيدة عند قراءتها.» (Misconception 7)

**لماذا هذا خطأ:** ينبغي أن تظل Resources موفّرات بيانات خفيفة وموجهة للقراءة؛ أما side effects فمكانها في Tools.

### الاعتقاد الخاطئ 8: «إدراج Resources يعني تحميل محتواها كله.» (Misconception 8)

**لماذا هذا خطأ:** اكتشاف Metadata وقراءة المحتوى عمليتان منفصلتان؛ ويمكن لـ Resource templates و resource managers تأجيل التحميل.

### الاعتقاد الخاطئ 9: «ينبغي دائمًا إعادة الملفات الكبيرة مباشرة عبر MCP.» (Misconception 9)

**لماذا هذا خطأ:** يمكن أن تكون URL indirection أو Resource templates المقسمة إلى Chunks أكثر عملية وكفاءة في استخدام Context.

## المصطلحات الأساسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| خادم MCP (MCP server) | مكوّن يوزع Tools و Resources و Prompts والقدرات المرتبطة بها على MCP clients |
| عنصر أساسي من MCP (Primitive) | لبنة أساسية في MCP: إما Tool أو Resource أو Prompt |
| نوع الإجراء (`Tool`) | إجراء تنفيذي موجّه إلى Model يعرضه Server |
| نوع السياق (`Resource`) | بيانات سياقية للقراءة فقط، تحت تحكم Application، ويحددها URI |
| نوع التعليمات (`Prompt`) | Template قابلة لإعادة الاستخدام وموجّهة إلى المستخدم يوزعها Server |
| النقل المحلي (`stdio`) | Transport محلي يستخدم standard input/output لـ server subprocess |
| النقل البعيد (Streamable HTTP) | Transport بعيد يستخدم HTTP POSTs مع SSE response streaming اختياري |
| واجهة الخادم عالية المستوى (`MCPServer`) | Python server API عالية المستوى تستنتج protocol metadata من decorated functions |
| الواجهة منخفضة المستوى (Low-level API) | Python API تعرض protocol handlers وبناء Responses بصورة أكثر مباشرة |
| وصف نية Agent (Agent story) | وصف لإجراء متكامل من منظور Agent يُستخدم لتوجيه تصميم Tool |
| نطاق الاسم (Namespace) | Prefix يجمع Tools المترابطة ويميز بينها |
| مخطط الإدخال (Input schema) | وصف منظم للـ arguments التي تقبلها Tool |
| مخطط الإخراج (Output schema) | وصف منظم يُستخدم للتحقق من output المتوقعة لـ Tool |
| ملاحظة سلوك Tool (Tool annotation) | Hint لـ Clients حول سلوك Tool، مثل read-only intent |
| خطأ مرئي لـ Model (Model-visible error) | خطأ Tool قابل للتعافي يوصف بحيث يستطيع Model تصحيح الإجراء التالي |
| خطأ على مستوى Protocol (`MCPError`) | خطأ Protocol يُستخدم لحالات MCP المشوهة/غير القابلة للتعافي في أمثلة الفصل |
| Prompt متعددة الأدوار (Multiturn prompt) | Prompt ممثلة كسلسلة من رسائل user/assistant |
| التهيئة المسبقة (Prefill) | رسالة assistant جزئية تُقدَّم لتشكيل بداية output الخاصة بـ Model |
| معرّف Resource (Resource URI) | معرّف فريد يُستخدم لتوجيه الطلب إلى Resource |
| قالب Resource (Resource template) | نمط URI ذو Parameters يمكنه تحديد Resources كثيرة مترابطة |
| التحميل المؤجل (Deferred loading) | إبقاء Metadata الخاصة بـ Resource متاحة مع تحميل المحتوى الفعلي فقط عند طلبه |
| الإحالة عبر URL (URL indirection) | إعادة أو تحديد URL خارجي بدلًا من نقل كائن كبير مباشرة عبر MCP |
| التقسيم (Chunking) | تقديم شرائح قابلة للإدارة من بيانات كبيرة من خلال Template parameters |
| أداة الفحص (MCP Inspector) | MCP client/tool تفاعلية لفحص سلوك Server واختباره أثناء التطوير |
