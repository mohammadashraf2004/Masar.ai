## نواتج التعلم

بنهاية هذا الدرس، ينبغي أن تكون قادرًا على:

- استخدام نموذج Agent ذي الطبقات الخمس بوصفه Checklist لتصميم Production systems.
- التعامل مع Persona الخاصة بالـ Agent بوصفها API contract بدل Prose غامضة.
- تعريف Roles ضيقة وBoundaries صريحة ومسار `I don't know`.
- تفضيل Typed structured outputs عندما تتفاعل Agents مع Code أوAgents أخرى.
- استخدام Dynamic instructions دون إنشاء Context bloat.
- تصميم Tools ذات Single responsibility بأسماء وSchemas وسلوك Failure واضح.
- التحكم في Tool invocation وتجنب Tool bloat.
- تطبيق ReAct وPlan-then-execute وSelf-review وHard iteration limits بالشكل المناسب.
- فصل Short-term sessions عن Long-term memory.
- التعامل مع RAG بوصفها First-class capability وتحسين Retrieval بصورة مستقلة.
- استخدام ANN indexes وMetadata filtering وHybrid retrieval واختيار Embeddings عمدًا.
- Grounding للإجابات بصورة صارمة والحفاظ على خيار قول `I don't know`.
- تقسيم Knowledge حسب Role وTenant وDomain وVersion وDate.
- بناء Evaluation وFeedback layer تتضمن Traces وAutomated evals وHITL وGuardrails.
- تصميم Customer-support agentic system تتضمن Triage وRetrieval وGrounding وAction وEscalation.
- بناء Modular RAG agent system ومعرفة متى لا ينبغي إضافة Orchestration.
- بناء Two-tier deep-research system تتضمن Planner وStateless workers وCritic وWriter.
- تطبيق Streaming وCaching وBudgets وBounded loops على Long-running agent systems.

## 1. استخدم طبقات Agent الخمس بوصفها Checklist للتصميم

يعود الفصل إلى الطبقات الوظيفية الخمس المستخدمة في الكتاب:

1. **Persona**
2. **الأدوات والإجراءات**
3. **التفكير والتخطيط**
4. **المعرفة و memory**
5. **Evaluation و التغذية الراجعة**

الدرس العملي هو تحسين كل Layer بصورة مستقلة قبل دمج System كاملة.

غالبًا يمكن تتبع Production failure إلى Layer واحدة:

```text
Role خاطئة / Scope متشعبة       -> Persona
سلوك API سيئ / سوء استخدام      -> Tools
لا Decomposition / Loops منفلتة  -> Reasoning
إجابات غير مدعومة               -> Knowledge
Failures غير مكتشفة             -> Evaluation
```

## 2. تعامل مع Persona بوصفها API contract

أول Production rule في الفصل هي أن Persona لا ينبغي أن تكون مجرد Storytelling غامضة.

Persona مفيدة تعرّف:

- Role،
- Responsibility،
- Boundaries،
- Output contract،
- Uncertainty behavior.

مثال:

```text
أنت SupportMentor.
تجيب عن أسئلة Product support باستخدام Retrieved internal context.
لا تقدم Policy exceptions.
إذا كانت Evidence المطلوبة غير موجودة، فقل إنك لا تعرف.
أعد JSON يطابق Answer schema.
```

هذا أقرب إلى Interface specification من Character description.

## 3. اجعل Scope الخاصة بالـ Agent ضيقة

عادةً ما تكون Specialized agents أسهل في:

- الاختبار،
- المراقبة،
- التأمين،
- التحسين،
- فهم سلوكها.

Agent للدعم مسؤولة فقط عن Orders وReturns وDelivery status أسهل في Hardening من Agent تتعامل مع Support وSales وBilling وHR وEngineering.

تقلل Scope الضيقة الغموض في Prompt instructions وفي Tool selection.

كما تجعل Composition أسهل لأن عدة Agents مركزة يمكنها التعاون بدل Agent ضخمة تحاول تنفيذ كل شيء.

## 7. Tools هي يدا Agent وحواسها

حتى Model قوية مع Tools سيئة التصميم تنتج System ضعيفة.

يقدم الفصل خمس إرشادات لتصميم Tools.

### 1. Single responsibility

ينبغي لكل Tool تنفيذ Job واضحة واحدة.

### 2. Descriptions واضحة وTyped parameters

تتعلم Model كيفية استخدام Tool من اسمها وDocstring وSchema.

### 3. فضّل Function tools للـ APIs/Code الخاصة بك

تجعل Typed function definitions إنشاء Schemas واختبارها أسهل.

### 4. تحكم في توقيت تشغيل Tools

استخدم Tool-choice settings وParallel-call settings وPrompt policy عند الحاجة.

### 5. خطط للـ Failure

ينبغي تصميم Timeouts وRetries وStructured error payloads وFallbacks قبل حدوث Failure.

## 9. تجنب Tool bloat

كل Tool تزيد Context overhead لأن Model يجب أن تستقبل Description وSchema الخاصتين بها.

تنشئ Tool catalog ضخمة نوعين من التكلفة:

### Token cost

تستهلك Tool descriptions جزءًا من Context في كل Model call ذات صلة.

### Decision cost

يجب على Model الاختيار بين Options أكثر تشابهًا، مما يزيد احتمال اختيار Tool الخطأ.

لذلك يوصي الفصل بـ Tool sets صغيرة ومخصصة لكل Role.

وبالنسبة إلى MCP servers، افحص عدد Capabilities التي تعرضها Server بدل الاتصال Blindly بـ Server كبيرة.

---

## 10. تحكم في Tool invocation

لا ينبغي للـ Agent أن تقرر دائمًا Tool usage بلا Constraints.

تشمل Controls مفيدة:

- `tool_choice="auto"`،
- Force لـ Tool مطلوبة،
- منع Tools في Turn معينة،
- السماح بـ Parallel tool calls،
- التوقف بعد أول Tool result كافية.

يكون هذا مفيدًا بصورة خاصة عندما تجيب API response واحدة عن Request بالكامل، بينما تضيف Calls إضافية Latency وCost فقط.

التحكم في Tools جزء من Planning، وليس مجرد SDK configuration.

## 11. Reasoning وPlanning تحتاجان Boundaries

يقدم الفصل خمس قواعد عملية للـ Reasoning.

### استخدم ReAct للمهام غير البسيطة

بدّل بين Reasoning وAction وObservation عندما تكون External evidence مهمة.

### خطط قبل تنفيذ Goals كبيرة

أنشئ Checklist أوPlan قصيرة قبل تنفيذ Actions كثيرة.

### ضع حدًا للـ Iterations

ضع دائمًا Cap لعدد Tool calls أوTurns.

### نفذ Self-review قبل Final

استخدم Check سريعًا لاكتشاف أخطاء واضحة والتأكد من أن السؤال تمت الإجابة عنه فعلًا.

### تجنب Reasoning غير الضرورية في المهام البسيطة

Simple one-shot work لا تحتاج Deliberation loop طويلة.

## 13. Reasoning capability لا تعني Reasoning reliability

قد تحتوي Models الحديثة بالفعل على Built-in reasoning behavior.

هذا لا يعني أنه ينبغي تركها دون Constraints.

ما تزال Reasoning systems قادرة على:

- Overthinking لمهام بسيطة،
- استدعاء Tools غير ضرورية،
- تنفيذ Steps أكثر من اللازم،
- اتباع Plan ضعيفة،
- أن تصبح مكلفة.

Goal في Production هي **Guided reasoning**، لا Maximum reasoning.

## 15. افصل Session context عن Long-term memory

يميز الفصل عمليًا بين:

### Session memory

Short-term thread state الخاصة بالمحادثة الحالية.

### memory طويلة الأمد

Facts وPreferences محفوظة يتم استرجاعها انتقائيًا لاحقًا.

أمثلة:

```text
Session: المستخدم سأل عن Refund policy منذ خمس دقائق.
Long-term: المستخدم يفضل Email notifications.
```

ينبغي Pruning للـ Long-term stores بدل تجميع كل تفاصيل كل Conversation إلى الأبد.

## 16. حسّن Retrieval على نطاق واسع

يوصي الفصل بالتفكير فيما يتجاوز Basic flat vector index.

قد تحتاج Production retrieval إلى:

- Approximate nearest-neighbor indexes مثل HNSW أوIVF،
- Domain sharding،
- Metadata filtering،
- Reranking،
- Multilingual أوDomain-specific embeddings،
- مرشِّحات التاريخ/الإصدار.

قد تحتاج Support query إلى استرجاع ما يلي فقط:

```text
tenant = acme
role = عميل
product = API
version = 3.2
date <= التاريخ الحالي
```

تُعد Filtering ميزة Relevance وميزة Access control في الوقت نفسه.

## 17. استخدم Hybrid retrieval بدل Signal واحدة

يحذر الفصل صراحة من الاعتماد على Vector search فقط.

ادمج Retrieval families عندما يحتاج Domain ذلك:

- Semantic/vector،
- Keyword/lexical،
- Graph/hierarchical،
- Metadata filters،
- Reranking.

لماذا؟

لأن Query قد تحتاج Semantic similarity، بينما تعتمد أخرى على Version number أوCode أوName أوRelationship صريحة.

توفر Hybrid search للنظام كلًا من Recall وPrecision.

## 18. قسّم Content بصورة متماسكة وطبّق Grounding صارمة

يضر Poor chunking بالـ Retrieval قبل أن تبدأ Agent في Reasoning أصلًا.

يوصي الفصل بـ Semantically coherent chunks وتعليمات Grounding صارمة.

مثال:

```text
استخدم Retrieved context فقط.
اذكر Chunk IDs الداعمة.
إذا لم تكن Answer موجودة، فقل إنك لا تعرف.
```

ينبغي التعامل مع Grounding بوصفها Correctness requirement لا مجرد Style preference.

## 21. أتمت Evaluation مع كل تغيير مؤثر

يمكن لـ Prompt changes وModel changes وRetrieval changes وTool changes جميعًا أن تنشئ Regressions.

ينبغي لـ Evaluation pipeline عملية أن تحافظ على:

- Curated test cases،
- Known failure cases،
- LLM-as-judge checks عندما تكون Semantic evaluation مطلوبة،
- Accuracy وSafety metrics،
- مقاييس معدل الحل.

شغّل هذه Evaluations كلما تم تحديث Components تؤثر في Behavior.

يمكن لـ Observability systems مثل Phoenix المساعدة في ربط Traces وDatasets وExperiments وEvaluations.

---

## 22. HITL وGuardrails هي Features وليست Afterthoughts

تساعد Human feedback في الحالات التي لا تستطيع Automated checks حسمها بثقة.

تفرض Guardrails حدودًا عند:

- Input،
- Tool invocation،
- Output.

قد تستخدم Architecture ناضجة Critic أوGuardrail agent ثانوية لفحص Output قبل وصولها إلى User.

تكون HITL مفيدة بصورة خاصة في:

- High-value refunds،
- Customers غاضبين أوضعفاء،
- Policy غير واضحة،
- Irreversible actions،
- حالات الثقة المنخفضة.

## 24. إرشادات Production للـ Customer support

يوصي الفصل بسبعة Controls عملية.

### ضيّق نطاق المهمة

ابدأ بمجموعة Intents محددة مثل Orders وReturns وStatus.

### طبّق Grounding على كل Answer

استرجع من Manuals/Policies وتحقق من Grounding عند الحاجة.

### اجعل HITL سهلة

اعرض Explicit escalation tool.

### تحقق من Identity

نفّذ Authentication قبل عرض Account-specific data.

### طبّق Least privilege

ينبغي أن تعمل Tools داخل Scope المسموح بها للمستخدم.

### صمّم Resilience

Retries وFallbacks وTimeouts وFriendly error behavior كلها مهمة.

### استخدم Cache وRate limiting بصورة انتقائية

اعمل Cache للـ Stable popular answers؛ وطبّق Throttling على External APIs.

### حافظ على Transparent traces

تحتاج Support teams إلى Audit للـ Searches وSources وTool calls وEscalation decisions.

## 27. أنظمة RAG agent: Retrieval هي المحرك

يقدم الفصل تمييزًا معماريًا مهمًا:

> Retrieval هي الـ Capability الأساسية؛ ويضيف Agentic control الـ Routing وCritique وRefinement وAction حولها.

لا تضف Orchestrator لمجرد أنك تبني RAG.

إذا كان هذا يكفي:

```text
الاستعلام -> الاسترجاع -> الإجابة
```

فحافظ على البساطة.

أضف Agentic components فقط عندما تحتاج إلى:

- Routing عبر Corpora،
- Corrective retrieval،
- Diagnostics،
- Actions،
- Multistep refinement.

## 30. Corrective retrieval تحتاج Bounded loop

قد تقوم Advanced RAG systems بتقييم Retrieved context قبل الإجابة.

```text
الاستعلام
 |
 v
الاسترجاع
 |
 v
الترتيب / فحص Grounding
 |             |
 جيد          ضعيف
 |             |
 v             v
الإجابة     تحسين الاستعلام
               |
               +----> استرجاع مرة أخرى
```

يذكر الفصل صراحة أن Refinement loop هذه يجب أن تحتوي Counter أوStop condition أخرى.

Corrective retrieval بلا Bounded retries يمكن أن تتحول إلى Runaway agent loop أخرى.

## 31. قِس RAG عند طبقتي Retrieval وAnswer

لا تقيّم Final generated text وحدها.

تتبّع:

- Retrieval recall،
- Retrieval relevance،
- Answer accuracy،
- Grounding/Citation quality،
- الحالات التي كان ينبغي للـ Agent أن تقول فيها `I don't know`،
- استعلامات البحث الفاشلة/المحسَّنة.

هذا التمييز مهم لأن Bad answer قد تنتج من Bad retrieval لا Bad generation.

## 33. Two-tier orchestration: Brain وHands

يستخدم Blueprint الخاصة بالـ Deep-research في الفصل Planner بوصفها Brain وStateless workers بوصفهم Hands.

### Brain

Research planner:

- تقوم Decompose للـ Goal،
- تقرر ما الذي يجب Search عنه بعد ذلك،
- تتبع Coverage،
- تقوم Routing للعمل.

### Hands

Workers:

- Web searcher،
- Extractor،
- Analyst،
- Summarizer/Writer.

ينبغي أن تظل Workers Stateless وTool-like قدر الإمكان ما لم تكن تحتاج Decision-making loops خاصة بها.

يحافظ ذلك على Strategic state مركزية بينما تظل Specialized workers بسيطة.

## 34. افرض Evidence-backed research behavior

بالنسبة إلى Factual claims، ينبغي إلزام Deep-research planner باستخدام Retrieval أوWeb/Document tools.

Policy مفيدة هي:

```text
لا Factual claim دون Source محددة.
استخدم Search/Document tools للحقائق.
تتبّع Sources طوال Run.
لا تنهِ Unsupported claims.
```

يمنع ذلك Planner من تجاوز Research process والإجابة اعتمادًا على Model memory فقط.

---

## 35. Critic قبل Writer

بعد أن تجمع Research workers Evidence كافية، يضع الفصل Critic قبل Final synthesis.

تتحقق Critic من:

- Completeness،
- Missing perspectives،
- Bias،
- Contradictions،
- ما إذا كانت Evidence كافية للإجابة.

إذا كانت Evidence غير كافية:

```text
الناقد -> المخطِّط -> مزيد من البحث
```

إذا كانت Evidence كافية:

```text
الناقد -> الكاتب -> التقرير النهائي المُوثَّق بالمراجع
```

يفصل ذلك بوضوح بين Discovery وQuality control وCommunication.

---

## 36. اعرض Progress أثناء Long-running research

قد تستغرق Deep research وقتًا كافيًا ليبدو Silent interface وكأنه معطل.

يوصي الفصل بـ Streaming للـ Partial progress مثل:

- Current search stage،
- Evolving outline،
- Source collection progress،
- تحديثات الحالة رفيعة المستوى.

يحسن ذلك Perceived latency ويخلق فرصًا لـ Checkpoint approvals.

الفكرة المهمة في UX هي إظهار Progress دون إجبار النظام على كشف Private internal model reasoning.

---

## 37. Deep research تحتاج Cache وCall وToken budgets

يمكن للـ Long-running systems أن تصبح مكلفة بسرعة.

استخدم:

- Repeated-query caching،
- Per-run token budgets،
- API-call budgets،
- Throttling،
- Alerting.

لكن Cache freshness مهمة.

قد تكون Search result مكررة مفيدة اليوم وقد تصبح Stale لاحقًا.

لذلك تحتاج Caching إلى Expiration وInvalidation بدل Policy دائمة من نوع `store everything`.

## 38. قائمة تحقق إنتاجية متكاملة

عند مراجعة Agentic system، اطرح الأسئلة التالية.

### Persona

- هل Role ضيقة؟
- هل Boundaries صريحة؟
- هل يوجد مسار `I don't know`؟
- هل Output Typed عندما تستهلكها Code؟

### Tools

- هل لكل Tool مسؤولية واحدة؟
- هل Names/Docstrings/Parameters واضحة؟
- هل Failure modes Structured؟
- هل Tool set صغيرة بما يكفي؟

### Reasoning

- هل تستخدم Reasoning فقط عندما تضيف قيمة؟
- هل توجد Plan للـ Goals الكبيرة؟
- هل Turns/Iterations محدودة؟
- هل يوجد Self-review أوCritic path؟

### المعرفة و memory

- هل Retrieval First-class؟
- هل Session وLong-term memory منفصلتان؟
- هل Retrieval Hybrid عندما تحتاج؟
- هل Access مقسمة بصورة صحيحة؟
- هل تستطيع Agent أن تقول `I don't know` بأمان؟

### Evaluation و التغذية الراجعة

- هل Traces كاملة؟
- هل يتم تقييم Prompt/Model changes تلقائيًا؟
- هل يتم التقاط User feedback؟
- هل توجد Guardrails حول Risky actions؟

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: Persona قوية تتعلق أساسًا بالـ Tone

> Production persona design تعرّف Role وBoundaries وUncertainty وOutput contract.

### المفهوم الخاطئ 2: المزيد من Tools يجعل Agent دائمًا أكثر قدرة

> Excess tools تزيد Context cost وSelection ambiguity.

### المفهوم الخاطئ 3: Reasoning models لا تحتاج Explicit limits

> ما تزال Reasoning تحتاج Turn budgets وStop conditions وSafe fallback behavior.

### المفهوم الخاطئ 4: RAG تعني وضع كل Documents داخل Prompt

> Production RAG تستخدم Retrieval لاختيار Relevant context فقط.

### المفهوم الخاطئ 5: Vector index واحدة تكفي لكل Future RAG use case

> تحتاج Production systems غالبًا Partitions وHybrid search وFiltering وReranking وFreshness controls.

### المفهوم الخاطئ 6: Support agent هي Agent واحدة

> Mature support workflows غالبًا تحتوي Triage وRetrieval وGrounding وBusiness-action وGuardrail وAnswer وHITL roles.

### المفهوم الخاطئ 7: كل RAG application تحتاج Agentic orchestrator

> إذا كانت Retrieval call واحدة تليها Answer step واحدة تحل Task، فحافظ على البساطة.

### المفهوم الخاطئ 8: ينبغي أن تحتفظ Deep research بكل Worker في حالة Stateful

> يوصي الفصل بـ Centralized planning مع إبقاء Workers Stateless/Tool-like قدر الإمكان.

### المفهوم الخاطئ 9: Caching جيدة دائمًا

> Stale cache entries يمكن أن تضر Search quality وFactual freshness.
