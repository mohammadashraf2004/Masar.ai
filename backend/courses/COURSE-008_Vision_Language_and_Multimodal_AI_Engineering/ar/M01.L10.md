## من فهم Multimodal إلى توليد Multimodal (From multimodal understanding to multimodal generation)

كانت VLMs السابقة تجيب عن أسئلة مثل:

```text
صورة (image) + نص (text)
→ نص (text)
```

وسّعت Video-language models ذلك إلى:

```text
فيديو (video) + نص (text)
→ نص (text)
```

ويمكن لـ Models القادرة على معالجة audio إضافة:

```text
صوت (audio)
→ نص (text)
```

لكن Assistant أوسع بصورة حقيقية قد يحتاج إلى:

```text
يرى (see)
يسمع (hear)
يقرأ (read)
يفكر (reason)
يتحدث (speak)
يولد صورًا (generate images)
يولد فيديو (generate video)
```

داخل نظام واحد.

يسمي المصدر المرحلة التالية **any-to-any models**.

وفق تعريف الفصل، يجب أن يدعم نظام any-to-any حقيقي على الأقل:

```text
2 input modalities — نوعان من input modalities
and — و
2 output modalities — نوعان من output modalities
```

على سبيل المثال:

```text
INPUT: — الإدخال
text + image + audio — يجمع text و image و audio

OUTPUT: — الإخراج
text + speech — يجمع text و speech
```

أو:

```text
INPUT: — الإدخال
text + image — يجمع text و image

OUTPUT: — الإخراج
text + generated image — يجمع text مع generated image
```

السؤال الصعب ليس ببساطة:

```text
"Can one model accept many modalities?" — جملة المصدر محل التحليل
```

بل هو:

> **كيف نمثل الإشارات المستمرة مثل images و audio و video في
> صيغة يستطيع Transformer فهمها وتوليدها معًا؟**

- شرح عدم توازن task/data في any-to-any training.
- التمييز بين data-side balancing و loss-side balancing.
- شرح connector-first training.
- شرح sequential training القائم على understanding-before-generation.
- شرح gradual unmasking في discrete multimodal models.
- مطابقة architecture families مع training losses المناسبة لها.
- شرح لماذا يمكن أن تسبب objectives غير المتوافقة gradient conflicts.
- تصميم staged any-to-any training plan انطلاقًا من pretrained components.

## 1. مشكلة Any-to-Any (The any-to-any problem)

يبدأ المصدر بملاحظة مهمة.

يتواصل البشر عبر قنوات كثيرة:

```text
نص (text)
صور (images)
كلام (speech)
صوت (sound)
فيديو (video)
```

قد يجمع software system تقليدي بين:

```text
نموذج الرؤية (Vision model)
+
أداة تعرف الصوت (Audio recognizer)
+
نموذج اللغة (Language model)
+
توليد الكلام (Speech synthesis)
+
مولد الصور (Image generator)
+
Code للتنسيق (Orchestration code)
```

يسأل بحث any-to-any عما إذا كان يمكن توحيد قدر أكبر من ذلك.

ليس الهدف بالضرورة التخلص من كل أشكال التخصص.

بل يستكشف أماكن مختلفة لرسم الحد الفاصل بين:

```text
Shared multimodal reasoning — reasoning مشتركة متعددة الوسائط
and — و
modality-specific representation/generation — تمثيل أوتوليد خاص بكل modality
```

## 2. لماذا لا تتصرف Modalities بالطريقة نفسها طبيعيًا؟ (Why modalities do not naturally behave the same)

يشدد المصدر على أن modalities تمتلك هياكل مختلفة.

### النص (Text)

هو discrete بطبيعته:

```text
word/subword/token IDs — معرّفات الكلمات أو Subwords أو Tokens
```

ويعمل autoregressive next-token prediction معه بصورة طبيعية.

### الصور (Images)

عالية الأبعاد ومستمرة.

تتغير pixels بسلاسة من حيث:

- اللون؛
- الشدة؛
- الموضع.

يجادل المصدر بأن الأساليب iterative مثل diffusion تناسب غالبًا high-fidelity
visual generation بصورة أفضل من vocabulary صغيرة discrete.

### الصوت (Audio)

زمني ومستمر.

ويمكن تمثيله على صورة:

- أكواد codec منفصلة (discrete codec codes)؛
- خصائص continuous spectrogram و latent.

### الفيديو (Video)

يضيف:

```text
المكان (space)
+
الزمن (time)
+
متطلبات token/compute ضخمة
```

وهذا الاختلاف هو ما يجعل "one representation for everything" أمرًا صعبًا.

## 3. ثلاثة ضغوط تصميم متنافسة (Three competing design pressures)

يصف الفصل ثلاث مفاضلات.

### الكفاءة مقابل الدقة (Efficiency versus fidelity)

تتميز backbone واحدة قائمة على token بالكفاءة وتسمح لنا بإعادة استخدام:

- عملية tokenization؛
- توليد autoregressive؛
- تدريب باستخدام cross-entropy.

لكن continuous media قد تفقد بعض التفاصيل عند
إجبارها على vocabulary صغيرة discrete.

### البساطة مقابل Modular Design (Simplicity versus modularity)

Model واحدة ضخمة تبدو أنيقة مفاهيميًا.

لكن الربط المحكم بين:

- مكوّن language؛
- مكوّن perception؛
- مكوّن generation؛

يجعل تحسين المكونات بصورة مستقلة أكثر صعوبة.

### Shared Representation مقابل تفاصيل خاصة بكل Modality (Shared representation versus modality-specific detail)

تسهل shared representation تنفيذ cross-modal reasoning.

لكن كل modality تستفيد من بنيتها الخاصة:

```text
images → بنية مكانية (spatial)
audio → temporal/acoustic — بنية زمنية وصوتية
video → spatial + temporal — بنية مكانية وزمنية
```

وتنتج الحلول الوسط المختلفة عائلات architecture الثلاث في الفصل.

## 4. العائلات المعمارية الثلاث (The three architectural families)

يقدم المصدر:

```text
1. نماذج Unified vocabulary
2. نماذج Hybrid multiobjective
3. نماذج Modular / late-conditioning
```

### عائلة Unified Vocabulary

الفكرة:

```text
حوّل كل modality إلى discrete codes
→ توقّع tokens بصورة autoregressive
```

نقطة القوة:

- بساطة مفاهيمية؛
- generation منخفضة latency مقارنة بـ iterative diffusion؛
- تنسيق autoregressive محكم.

نقطة الضعف:

- قد تقلل quantization من media fidelity.

### عائلة Hybrid Multiobjective

الفكرة:

```text
text → discrete autoregressive tokens — يتحول text إلى tokens منفصلة autoregressive
media → continuous latents + diffusion/flow — تتحول media إلى latents مستمرة مع diffusion أو flow
shared transformer — Transformer مشتركة
```

نقطة القوة:

- visual/media fidelity قوية؛
- cross-modal integration محكم.

نقطة الضعف:

- توليد iterative؛
- objectives متعددة؛
- training أكثر تعقيدًا.

### عائلة Modular / Late-conditioning

الفكرة:

```text
يفهم MLLM ما ينبغي أن يحدث
→ connector — تمر عبر وحدة الربط
→ specialist generator ينفذ Rendering
```

نقطة القوة:

- تصميم modular؛
- يمكن تبديل المكونات أوترقيتها.

نقطة الضعف:

- قد تصبح conditioning interface عنق زجاجة.

## 5. نماذج Unified Vocabulary (Unified vocabulary models)

تستهلك Transformers الـ tokens بصورة طبيعية.

لذلك فإن فكرة unified-vocabulary هي:

> اجعل كل modality تتحدث بصيغة tokens.

بالنسبة إلى text:

```text
"cat" — كلمة المصدر
→ text token ID — معرّف token نصية
```

بالنسبة إلى image:

```text
image patch — patch من الصورة
→ continuous feature — feature مستمرة
→ nearest codebook entry — أقرب مدخل في codebook
→ visual token ID — معرّف visual token
```

بالنسبة إلى audio:

```text
audio chunk — جزء صوتي
→ code — كود
→ audio token ID — معرّف audio token
```

ثم يمكن لـ Transformer معالجة:

```text
[text][text][visual][visual][audio][text]... — sequence متعددة modalities
```

باستخدام autoregressive machinery واحدة.

## 6. Vector Quantization: تحويل Continuous Signals إلى Tokens

يستخدم الفصل تشبيه الألوان.

بدل تمثيل كل قيمة RGB ممكنة:

```text
(127, 45, 203)
```

تخيل إجبار الألوان على الانتماء إلى فئات:

```text
أحمر (red)
أخضر (green)
أزرق (blue)
... — فئات أخرى
```

تقوم **codebook** متعلمة بذلك داخل embedding space.

المسار:

```text
continuous vector — vector مستمرة
      ↓
قارنها بمدخلات codebook
      ↓
أقرب reference vector
      ↓
codebook index — فهرس codebook
      ↓
discrete token — token منفصلة
```

تتعلم codebook أثناء training.

---

## 7. Codebook باعتبارها Vocabulary خاصة بـ Modality

الـ codebook جدول ثابت الحجم من vectors.

افترض:

```text
image codebook size = 8,192 — حجم codebook الخاصة بالصور
```

حينها يمكن تمثيل كل visual code باستخدام ID مثل:

```text
<vis0> — visual token مرئية
<vis1> — visual token مرئية
... — بقية visual tokens
<vis8191> — visual token مرئية
```

يعطي المصدر مثالًا على توسيع vocabulary:

```text
text vocabulary = 152,064 — حجم text vocabulary
image codebook   =   8,192 — حجم image codebook
--------------------------------
unified total    = 160,256 — الحجم الموحد الكلي
```

والآن تتعلم autoregressive model متى تتنبأ بـ:

```text
a text token — token نصية
or — أو
a visual token — token مرئية
```

انطلاقًا من context.

## 8. عنق الزجاجة في Discrete Codebook (The discrete codebook bottleneck)

تتميز codebook الصغيرة بالكفاءة.

لكنها لا تستطيع التعبير عن تفاصيل بصرية غير محدودة.

Codebook أكبر:

```text
حالات بصرية ممكنة أكثر
→ fidelity أعلى محتملة
```

لكنها تعني أيضًا:

```text
prediction space أكبر
تعقيد أكبر
optimization أصعب
```

وهذا ينشئ أول مفاضلة متكررة في any-to-any:

```text
fidelity — الدقة
vs — مقابل
تعقيد discrete vocabulary
```

يذكر المصدر أن quantized visual encoders غالبًا ما تتأخر عن
continuous representations في جودة الفهم والتوليد معًا.

## 9. البنية المتجانسة (Monolithic Architecture)

في الفكرة monolithic النقية:

```text
Transformer واحدة
+
discrete vocabulary موسعة واحدة
```

تتعامل مع:

- عناصر text tokens؛
- عناصر image tokens؛
- عناصر audio tokens؛
- modalities discrete أخرى.

وتتنبأ next-token machinery نفسها بكل هذه العناصر.

مفاهيميًا:

```text
الموجه (prompt):
"Draw a lake at sunset" — جملة المصدر المستخدمة كموجه

نموذج Transformer:
<vis43> <vis1001> <vis805> ... — visual tokens مولدة

أداة الفك (decoder):
visual tokens → pixels — تحويل visual tokens إلى pixels
```

### لماذا هي أنيقة؟ (Why it is elegant)

Sequence واحدة.

autoregressive logic واحدة.

وقد يكون لها main loss واحدة:

```text
cross-entropy — دالة الخسارة
```

### لماذا هي صعبة؟ (Why it is difficult)

يجب على LLM أن تنمذج في الوقت نفسه:

```text
high-level meaning — المعنى عالي المستوى
and — و
low-level reconstruction details — تفاصيل reconstruction منخفضة المستوى
```

داخل discrete prediction space نفسها.

## 10. Janus-Pro بوصفه تصميمًا انتقاليًا (Janus-Pro as a transitional design)

يتعمد المصدر عدم تقديم Janus-Pro باعتباره
monolithic architecture نقية تمامًا.

ينتمي إلى هذا القسم لأنه يستخدم discrete visual tokens في generation.

لكنه **يفصل visual encoders وفق الدور**.

### جانب Perception / Understanding

يعالج continuous visual encoder عالي السعة
الصور من أجل semantic understanding.

### جانب Generation

يحول tokenizer بأسلوب VQ-VAE محتوى الصورة إلى discrete generation codes.

لذلك يكون النظام غير متماثل:

```text
UNDERSTANDING: — الفهم
continuous image representation — تمثيل صورة مستمر

GENERATION: — التوليد
discrete visual codes — أكواد بصرية discrete
```

ويقلل ذلك توتر "one encoder must do everything".

## 12. رؤوس Generation المفصولة (Factorized generation heads)

تزيل factorized heads مهمة التنبؤ بـ nontext tokens من LLM head الرئيسية.

وبدلًا من ذلك:

```text
نموذج LLM
→ تتنبأ بـ ordinary text tokens
→ تتنبأ بـ special trigger token عند الحاجة إلى modality أخرى
→ يتولى specialized head المهمة
```

مثال:

```text
تُخرج LLM:
<image_start> — trigger لبدء الصورة

رأس الصورة (image head):
تولد image codes

أداة الفك (decoder):
codes → pixels — تحويل codes إلى pixels
```

وبالمثل:

```text
<audio_start> — trigger لبدء audio
→ audio head — الانتقال إلى رأس audio
→ codec codes — توليد أكواد codec
→ waveform — إنتاج waveform
```

## 13. التسليم الدلالي (Semantic handoff)

لا تحتاج LLM إلى توليد pixels أو waveforms.

بل توفر:

```text
hidden states — الحالات الداخلية
=
semantic intent — القصد الدلالي
```

ثم يحول modality-specific head هذا القصد إلى:

- أكواد image؛
- أكواد speech؛
- أكواد audio.

الكود الدقيق هو pseudocode.

## 14. لماذا نفصل Output Heads؟ (Why factorize output heads?)

يذكر المصدر عدة فوائد.

### فصل المسؤوليات (Separation of concerns)

```text
نموذج LLM:
ما الذي ينبغي توليده؟

رأس متخصص (specialist head):
كيف ينبغي Rendering له؟
```

### LLM Vocabulary أنظف (Cleaner LLM vocabulary)

لا تحتاج text vocabulary إلى آلاف image/audio tokens.

### Representation أفضل خاصة بكل Modality (Better modality-specific representation)

يمكن لـ specialized heads استخدام codec structures أغنى.

### التداخل بين الأنماط (Interleaving) طبيعي (Natural interleaving)

نظرًا لأن LLM تتحكم في trigger tokens، يمكن للنظام مفاهيميًا أن ينتج:

```text
نص (text)
→ صورة (image)
→ نص إضافي (more text)
→ كلام (speech)
```

من دون الحاجة إلى global generation-mode switch.

## 15. النمط غير المتماثل: Continuous In, Discrete Out

يصف المصدر نمطًا factorized مهيمنًا.

### جانب Input

تستخدم vision/audio/video inputs continuous encoders:

```text
نموذج ViT — Vision Transformer للرؤية
SigLIP-style visual encoder — visual encoder بأسلوب SigLIP
streaming audio encoder — Audio encoder متدفقة
```

وتنتج هذه dense embeddings.

### مرحلة Reasoning

تستخدم LLM آلية attention فوق هذه embeddings.

### جانب Output

تُخرج LLM trigger.

ويتنبأ specialized head بـ discrete codec/codebook tokens.

ثم يقوم decoder بتحويل تلك codes إلى المخرج النهائي.

إذًا:

```text
continuous perception — Perception مستمرة
→ language reasoning — Reasoning لغوية
→ discrete specialist generation — Generation منفصلة متخصصة
```

ويحافظ ذلك على core token vocabulary الخاصة بـ LLM موجهة
إلى text مع الإبقاء على perception inputs غنية.

## 16. التكميم المتجهي المتبقي (Residual Vector Quantization — RVQ)

تواجه codebook واحدة سقفًا في fidelity.

يقدم المصدر RVQ كطريقة لدمج عدة codebooks أصغر.

Codebook واحدة:

```text
اختر 1 code
من 8,192 احتمالًا
```

مثال RVQ:

```text
8 codebooks — ثماني codebooks
×
1,024 اختيارًا لكل واحدة
```

عدد combinations مفاهيميًا:

```text
1,024^8
```

وهذا لا يعني توسيع LLM vocabulary إلى هذا الحجم الهائل.

تُعالَج كل codebook باعتبارها prediction
level منفصلة داخل specialist head.

### تشبيه (Analogy)

بدل اختيار وصف كامل واحد
لشخص، اختر سمات منفصلة:

```text
الطول (height)
الشعر (hair)
العينان (eyes)
الملابس (clothing)
... — سمات أخرى
```

تنتج combination قدرة تعبيرية أغنى بكثير.

## 24. VAE مقابل VQ-VAE

## 25. لماذا تحل Diffusion مشكلة Continuous Generation؟

تتنبأ LLM من finite vocabulary.

أما continuous image latent فيمكن أن تأخذ عددًا غير محدود عمليًا من القيم.

تغير Diffusion مشكلة prediction.

فبدل التنبؤ بالـ final latent مباشرة:

```text
ابدأ من noise
→ تنبأ بصورة متكررة بكيفية denoising
→ استعد structure تدريجيًا
```

هناك اتجاهان مهمان.

### Forward Process أثناء Training

```text
clean latent — latent نظيفة
→ أضف Gaussian noise
→ مزيد من noise
→ noise شبه خالصة
```

### Reverse Process أثناء Generation

```text
random noise — noise عشوائية
→ predict/remove noise — تنبأ بالـ noise ثم أزلها
→ latent أنظف
→ final media latent — latent النهائية للـ media
```

يذكر المصدر أن denoising model يمكن تدريبها
باستخدام mean squared error بين:

```text
actual added noise — noise التي أضيفت فعليًا
and — و
predicted noise — noise المتنبأ بها
```

## 30. التوجيه من دون Classifier (Classifier-Free Guidance)

يعطي المصدر:

```text
ε_hat — تقدير noise الموجه
=
ε_uncond — تقدير noise غير المشروط
+
s × (ε_cond - ε_uncond) — تعديل الفرق باستخدام guidance scale
```

حيث:

```text
ε_cond   = prediction with prompt — prediction مع prompt
ε_uncond = prediction without prompt — prediction دون prompt
s        = guidance scale — قيمة guidance scale
```

التفسير:

```text
ε_cond - ε_uncond — اتجاه التأثير الناتج عن conditioning
```

هو الاتجاه الذي يضيفه conditioning.

إذا كان:

```text
s = 1
```

فنحصل على ordinary conditional prediction.

وإذا كان:

```text
s > 1
```

يتضخم تأثير prompt.

المفاضلة:

```text
guidance أعلى
→ التزام أقوى بالـ prompt
لكن
diversity أقل / artifacts محتملة
```

يعطي المصدر guidance ranges نموذجية على سبيل المثال.

وتعامل معها باعتبارها settings تعتمد على Model.

مفاهيميًا:

```text
instruction + source image — يجمع التعليمة مع الصورة المصدر
→ semantic representation — representation دلالية

semantic representation — representation دلالية
→ diffusion renderer — الانتقال إلى renderer تعتمد على diffusion
```

وهذا يجعل architecture boundary ظاهرة في code.

## 42. Modularity قوية، لكن Interfaces قد تصبح Bottleneck

تجعل late conditioning المكونات قابلة للاستبدال.

الفوائد:

```text
قم بترقية image generator
قم بترقية speech engine
احتفظ بـ MLLM
أعد استخدام connector strategy
```

لكن interface ضيقة قد تفقد معلومات fine-grained.

لذلك تستبدل late conditioning:

```text
maximum integration — أقصى تكامل
for — مقابل
maximum flexibility — أقصى مرونة
```

ويقارن المصدر ذلك بـ hybrid models حيث تشترك text و continuous
media في attention layers نفسها بصورة متكررة.

## 43. لماذا يُعد Any-to-Any Training صعبًا؟

تتنافس عدة tasks الآن داخل training system واحد.

أمثلة:

### من Perception إلى Text

- مهام captioning؛
- مهام VQA؛
- مهام transcription.

### من Text إلى Media

- مهام text-to-image؛
- مهام text-to-video؛
- توليد text-to-speech.

### مهام Editing

- مهام image editing؛
- مهام style transfer؛
- مهام inpainting.

وتختلف هذه tasks في:

- أعداد token counts؛
- قيم losses؛
- حجم data scale؛
- مستوى difficulty؛
- الـ target modalities.

إذا هيمنت إحداها على mixture، فقد تصبح Model over-specialized.

---

## 44. يمكن لـ Token Count نفسها أن تخلق Imbalance خفيًا

افترض:

```text
عينة Caption (caption sample):
256 image tokens + 20 output text tokens — عينة تضم هذا العدد من tokens

عينة Conversation (conversation sample):
200+ text tokens — أكثر من 200 token نصية

عينة Video (video sample):
potentially very long multimodal sequence — sequence متعددة modalities وقد تكون طويلة جدًا
```

لا تساوي dataset percentage مباشرة gradient contribution.

قد يهيمن video على batches ببساطة بسبب sequence length.

وقد يهيمن text إذا كانت أغلب samples من text-only.

لذلك يحتاج any-to-any training إلى mixture design مقصودة.

## 45. الموازنة من جانب Data (Data-side Balancing)

تحكم فيما تراه Model.

يقترح المصدر استراتيجيات مثل:

- oversample للـ tasks ناقصة التمثيل؛
- وضع سقف للـ sequences الطويلة جدًا؛
- ضمان أن batches تعكس target capabilities؛
- الإبقاء على general-purpose data أثناء specialization.

الهدف هو تجنب:

```text
one modality swallowing the training signal — استحواذ modality واحدة على training signal
```

وتقليل catastrophic forgetting.

---

## 46. الموازنة من جانب Loss (Loss-side Balancing)

حتى مع أمثلة متوازنة، قد تختلف magnitudes الخاصة بالـ losses.

يمكنك إعطاء weights لـ:

```text
L_total
=
w_text × L_text
+
w_image × L_image
+
w_audio × L_audio
+ ...
```

يقترح المصدر البدء بصورة بسيطة، ثم التعديل بناءً على validation.

ويذكر أيضًا تقنيات آلية مثل:

- موازنة gradient magnitude؛
- weighting للـ tasks اعتمادًا على uncertainty.

الفكرة الأساسية:

```text
data mixture controls examples — data mixture تتحكم في examples
loss weights control gradient influence — loss weights تتحكم في تأثير gradients
```

## 47. التدريب المرحلي: قسّم ثم سيطر (Staged training: divide and conquer)

يجادل المصدر بأن تدريب كل شيء معًا من الصفر
يسبب interference في كثير من الأحيان.

وتُبرز ثلاثة أنماط:

```text
1. connector-first — ابدأ بالـ connector
2. understanding before generation — ثبّت understanding قبل generation
3. gradual unmasking for discrete models — نفّذ gradual unmasking في discrete models
```

## 48. محاذاة Connector أولًا (Connector-first alignment)

جمّد pretrained backbones قوية:

```text
LLM — Model اللغة
vision encoder — مشفر الرؤية
audio encoder — مشفر الصوت
```

ودرّب adapter/connector فقط.

مثال:

```text
vision encoder — مشفر الرؤية
→ small MLP — شبكة MLP صغيرة
→ LLM embedding space — فضاء embeddings الخاص بـ LLM
```

لماذا؟

تتعلم modality الجديدة كيف تتواصل مع LLM قبل السماح لـ multimodal
gradients الواسعة بتغيير pretrained capabilities المستقرة.

## 49. Understanding قبل Generation

يقدم المصدر sequential training باعتبارها استراتيجية قوية.

### المرحلة 1 (Phase 1)

درّب understanding tasks:

- مهام VQA؛
- مهام captioning؛
- مهام perception.

### المرحلة 2 (Phase 2)

جمّد MLLM.

ودرّب generator conditioned on outputs الخاصة بها.

السبب:

```text
text cross-entropy — خسارة cross-entropy للنص
and — و
diffusion MSE — خسارة MSE للـ diffusion
```

يمكن أن تسحب shared parameters في اتجاهات متعارضة.

ويقلل فصل المراحل من negative transfer.

ويذكر المصدر BLIP3-o مثالًا على هذه الفلسفة.

## 50. Gradual Unmasking في Discrete Multimodal Models

قد تكون predictions المبكرة لـ visual/audio codes مليئة بالـ noise فعليًا.

يقترح المصدر:

```text
ابدأ مع nontext token loss وهي masked/downweighted
→ زد weight الخاصة بها تدريجيًا
```

ويسمح ذلك لـ language structure بالاستقرار قبل أن تستقبل
Model الصعوبة الكاملة للـ multimodal codebooks الكبيرة.

وهذا يشبه curriculum learning:

```text
ابدأ objective سهلة/مستقرة
→ انتقل إلى objective أصعب ومترابطة لاحقًا
```

يصف المصدر مثالًا يبدأ فيه النظام
من pretrained components قوية.

```text
speech continuation — استكمال الكلام
→ stability tuning — ضبط الاستقرار

```

ويعكس ذلك القاعدة الأوسع:

> بصورة غير ضرورية.

## 52. Losses خاصة بكل Architecture

تحتاج العائلات المختلفة إلى supervision مختلفة.

### النمط Unified Discrete Autoregressive

الفكرة الرئيسية:

```text
cross-entropy over discrete tokens — cross-entropy فوق discrete tokens
```

وهي أنيقة لأن categorical prediction objective واحدة يمكن أن تغطي modalities.

لكن تصميم codebook يخلق ضغطًا بين fidelity و optimization.

### النموذج الهجين متعدد الأهداف (Hybrid Multiobjective)

هناك نوعان من objectives:

```text
النص (text):
cross-entropy — خسارة للنص

الوسائط المستمرة (continuous media):
diffusion/noise MSE — خسارة MSE الخاصة بالـ diffusion
```

يحذر المصدر من إجبارهما على المرور عبر shared output head واحدة.

استخدم outputs/heads مناسبة لكل modality حتى لا تتصادم
targets غير المتوافقة داخل final prediction layer.

### الربط المتأخر (Late Conditioning)

تكون parameter sets أكثر انفصالًا.

النمط المعتاد:

```text
MLLM understanding loss — خسارة فهم MLLM
separate from — منفصلة عن
generator diffusion/flow loss — خسارة خاصة بالـ generator
```

يجعل هذا العزل إدارة gradient conflicts أسهل.

## 53. ملاحظة من جدول المصدر حول Factorized Heads

يصف أحد جداول المقارنة في المصدر
جانب factorized-head بلغة مثل:

```text
"single objective: cross-entropy over unified vocabulary" — عبارة المصدر
```

وفي موضع آخر، يشرح الفصل نفسه بعناية أن factorized
heads تحافظ على LLM vocabulary قائمة على text وتفوض
media-code prediction إلى specialized heads.

والخلاصة المعمارية الأكثر اتساقًا من الفصل هي:

```text
generation تظل discrete/autoregressive في جانب factorized
but — لكن
تتعامل specialized heads مع modality codes بدل أن تكون جزءًا من
monolithic LLM vocabulary واحدة
```

يحافظ الدرس على الفكرتين الواردتين في المصدر ويتجنب دمج factorized
heads مرة أخرى في monolithic vocabulary design.

## 55. راقب عدة Capabilities في الوقت نفسه

يمكن لـ any-to-any training تحسين مهارة واحدة مع إضعاف أخرى بصمت.

يوصي المصدر بمتابعة عدة عائلات من metrics.

أمثلة:

### قدرات Understanding

```text
VQA accuracy — دقة VQA
```

### قدرات Generation

```text
FID — مقياس FID
CLIP-style alignment score — مقياس alignment بأسلوب CLIP
```

### الحفاظ على Language (Language preservation)

```text
language benchmark / perplexity — benchmark لغوية مع perplexity
```

إذا:

```text
image quality ↑ — جودة الصورة ترتفع
language ability ↓ — قدرة اللغة تنخفض
```

فقد تكون المشكلة في:

- تركيب mixture؛
- أوزان loss weighting؛
- قيمة learning rate؛
- استراتيجية staging.

## 56. Learning Rates تراعي Task

ينبغي عمومًا أن تتغير pretrained components المستقرة
بصورة أقل حدة من components المهيأة حديثًا.

يقترح المصدر النمط:

```text
lower LR: — Learning rate أقل
pretrained backbone — backbone مدربة مسبقًا

higher LR: — Learning rate أعلى
new connector / adapter — connector أو adapter جديدة
```

وهذا يطابق سرعة optimization مع نضج parameters.

ويجب التحقق من العامل الدقيق على Model الفعلية.

## 57. اختيار Any-to-Any Architecture

### اختر Unified Discrete/Autoregressive عندما

- تكون latency مهمة جدًا؛
- يستطيع output تحمل حدود quantization؛
- يكون generation framework واحدة من نوع autoregressive خيارًا جذابًا؛
- يمكن أن تعمل generated media كـ intermediate reasoning أو output أقل fidelity.

### اختر Factorized Heads عندما

- تريد autoregressive orchestration؛
- تريد text vocabulary نظيفة؛
- تريد modality-specific code generators؛
- يكون natural interleaving مهمًا.

### اختر Hybrid Multiobjective عندما

- تكون high media fidelity هي الأهم؛
- تكون iterative generation الأبطأ مقبولة؛
- تستطيع إدارة عدة objectives و training أكثر تعقيدًا.

### اختر Late Conditioning عندما

- تكون modularity مهمة؛
- تكون training budget محدودة؛
- توجد pretrained MLLM و generator قويتان بالفعل؛
- تريد تبديل generation components بصورة مستقلة.

لا تفوز عائلة واحدة بكل المفاضلات.

## 58. قيّم Any-to-Any Systems بوصفها Portfolio من Capabilities

لا تحكم باستخدام scalar metric واحدة.

قيّم:

### قدرات Understanding

- جودة text؛
- مهام visual QA؛
- فهم audio؛
- فهم video.

### قدرات Generation

- جودة image؛
- جودة speech؛
- جودة video؛
- الالتزام بالـ prompt.

### المحاذاة (Alignment)

هل تطابق generated media الـ semantic intent؟

### التداخل بين الأنماط (Interleaving)

هل يستطيع النظام الانتقال بصورة صحيحة بين text و media outputs؟

### الحفاظ على القدرات (Preservation)

هل أضرت إضافة modality واحدة بـ modality أخرى؟

### الكفاءة (Efficiency)

قِس:

- زمن latency؛
- استخدام memory؛
- عدد diffusion steps؛
- أعداد token counts؛
- معدل generation throughput.

### قابلية التركيب (Modularity)

بالنسبة إلى late-conditioning designs:

- هل يمكن استبدال generator من دون إعادة تدريب MLLM؟
- ما مقدار connector retraining المطلوب؟

### تصنيف Qwen-Image-Edit

يقول المصدر صراحة إنها ليست canonical

```text
decode — فك representation
```

وليس implementation لـ production scheduler.

### مصطلحات Family/Loss

discrete-token architectures و factorized-head architectures.

## 60. النموذج الذهني الكامل لـ Any-to-Any

يمكن تلخيص الفصل كله في سؤال واحد:

```text
HOW DO WE BRIDGE
DISCRETE LANGUAGE
AND
CONTINUOUS WORLD SIGNALS?
```

ثلاث إجابات:

```text
A. اجعل كل شيء Discrete (DISCRETIZE EVERYTHING)

image/audio/video — يشمل image و audio و video
→ codebooks — التحويل إلى codebooks
→ tokens — التحويل إلى tokens
→ autoregressive model — الإدخال إلى Model autoregressive

simple + fast — بسيط وسريع
لكن fidelity هي عنق الزجاجة
```

```text
B. LET ONE TRANSFORMER SPEAK TWO REPRESENTATION TYPES   — اجعل Transformer واحدًا يتعامل مع نوعين من التمثيلات

النص (text)
→ discrete tokens + cross-entropy — تمثيل text باستخدام tokens وخسارة cross-entropy

الوسائط (media)
→ continuous latents + diffusion MSE — تمثيل media باستخدام latents وخسارة diffusion MSE

تكامل محكم + fidelity مرتفعة
لكن أبطأ + أصعب في training
```

```text
C. KEEP REASONING AND RENDERING MODULAR   — أبقِ الاستدلال والعرض في وحدتين منفصلتين

نموذج MLLM
→ semantic queries — إنتاج queries دلالية
→ connector — تمر عبر وحدة الربط
→ specialist generator — الانتقال إلى generator متخصصة

مرن + قابل لتبديل المكونات
لكن interface قد تعوق alignment
```

وداخل عائلة discrete/autoregressive:

```text
MONOLITHIC — تصميم monolithic
تتنبأ LLM بـ media tokens بنفسها

FACTORIZED HEADS — رؤوس factorized
تقرر LLM ماذا/متى
وتولد specialist head أكواد modality
```

مبدأ training:

```text
ابدأ من pretrained components
→ قم بمحاذاة connectors
→ ثبّت understanding
→ أضف generation
→ وازن data
→ وازن losses
→ راقب كل modality
```

الفكرة المركزية هي:

> **Any-to-any architecture هي في جوهرها قرار بشأن موضع الحد الفاصل بين
> shared semantic reasoning و modality-specific
> representation/rendering.**

## مفاهيم خاطئة مهمة (Important misconceptions)

### المفهوم الخاطئ 1: "أي Multimodal Model هي Any-to-Any."

ليس وفق تعريف المصدر.

ينبغي أن تتعامل Model مع input modalities اثنتين على الأقل و output modalities اثنتين على الأقل.

### المفهوم الخاطئ 2: "يمكن تمثيل Text و Image و Audio و Video كلها بالطريقة المثلى نفسها."

خصائصها الحسابية والبنيوية مختلفة.

### المفهوم الخاطئ 3: "Unified Vocabulary تعني أن Continuous Media تظل Continuous."

لا.

الفكرة المعرّفة هي discretizing للـ media إلى code tokens.

### المفهوم الخاطئ 4: "Codebook أكبر تحل Visual Fidelity بلا تكلفة."

تزيد prediction spaces الأكبر من عبء training و computation.

### المفهوم الخاطئ 5: "Janus-Pro هي Monolithic Model نقية تمامًا."

يسميها المصدر صراحة transitional لأنها تفصل perception
encoders عن generation encoders.

### المفهوم الخاطئ 6: "Factorized Heads تضع Image/Audio Tokens داخل LLM Vocabulary."

يحافظ تصميم factorized في المصدر على LLM vocabulary أنظف
ويفوض modality-code generation إلى specialized heads.

### المفهوم الخاطئ 7: "RVQ تعني Vocabulary واحدة هائلة."

لا.

تنشئ عدة codebooks أصغر combinatorial representation capacity.

### المفهوم الخاطئ 8: "Hybrid Multiobjective و Factorized Heads الشيء نفسه لأن كليهما يمكن أن يستخدم Specialized Generation."

لا.

تعالج Transformer الرئيسية في العائلة hybrid بنفسها continuous
noisy latents أثناء iterative denoising.

### المفهوم الخاطئ 9: "VAE و VQ-VAE لهما نوع Latent نفسه."

VAE latents مستمرة.

أما VQ-VAE فتستخدم discrete codebook entries.

### المفهوم الخاطئ 10: "Diffusion تتنبأ بالصورة النهائية في خطوة واحدة."

هي تحسن noise بصورة iterative حتى تصبح latent نظيفة.

### المفهوم الخاطئ 11: "يجب أن تستخدم Text و Image Latent Blocks قناع Attention نفسه."

يستخدم التصميم hybrid في المصدر causal text attention
و bidirectional within-image attention.

### المفهوم الخاطئ 12: "CFG Scale الأعلى أفضل دائمًا."

قد يقلل guidance الأقوى diversity وينشئ artifacts.

### المفهوم الخاطئ 13: "Factorized Heads و Late Conditioning تختلفان فقط لأن إحداهما Frozen."

الفرق الأعمق هو architectural coupling مقابل
generators مستقلة/قابلة للاستبدال.

### المفهوم الخاطئ 14: "Late Conditioning ليس لها أي جانب سلبي."

قد تحد connector/query interface الخاصة بها من fine-grained alignment.

### المفهوم الخاطئ 15: "Dataset Ratio واحدة تكفي لموازنة Any-to-Any Training."

يمكن لـ sequence length و loss magnitude خلق imbalance
خفي حتى عندما تبدو sample counts متوازنة.

### المفهوم الخاطئ 16: "درّب كل شيء بصورة Joint من الصفر لأقصى Integration."

يوصي المصدر مرارًا بـ staging لتقليل interference.

## المصطلحات الرئيسية (Key terminology)

| المصطلح | المعنى |
|---|---|
| نموذج Any-to-Any (Any-to-any model) | Model تتعامل مع عدة input modalities وعدة output modalities |
| Vocabulary موحدة (Unified vocabulary) | discrete token space واحدة موسعة لتضم أكواد modalities غير النصية |
| التكميم المتجهي (Vector quantization) | ربط continuous vector بأقرب learned codebook vector |
| جدول الأكواد (Codebook) | جدول متعلم من reference vectors تعمل فهارسه كـ discrete codes |
| نموذج Monolithic (Monolithic model) | autoregressive model رئيسية تتنبأ مباشرة بـ modality tokens |
| رأس Factorized (Factorized head) | specialized output head تشغلها LLM لتوليد nontext codes |
| Token تحفيز (Trigger token) | token خاصة مثل `<image>` أو `<audio>` تشير إلى handoff إلى modality أخرى |
| نمط Continuous in, discrete out | continuous perception embeddings مع discrete specialist generation codes |
| أسلوب RVQ | Residual vector quantization باستخدام عدة codebooks |
| نمط Thinker-Talker | فصل بين semantic reasoning و speech-code generation |

| نموذج VQ-VAE | Autoencoder تكون latent الخاصة بها quantized عبر codebook |

| نموذج DiT | Transformer من نوع diffusion |
| نموذج MMDiT | Transformer متعددة الوسائط من نوع diffusion |
| موازنة Data-side | التحكم في tasks/modalities التي تظهر داخل training batches |
| موازنة Loss-side | التحكم في المساهمة النسبية للـ gradients القادمة من objectives مختلفة |

## احتفظ بهذه الفكرة (Retain this idea)

**لا تُعرَّف any-to-any systems من خلال architecture عالمية واحدة.
قرار التصميم المركزي فيها هو: أين ينبغي أن تتحول continuous media
إلى discrete، وأين ينبغي أن يحدث continuous generation، وما مدى إحكام
ربط rendering بـ semantic reasoning. تعظم unified-vocabulary models
البساطة، وتعظم hybrid diffusion models التكامل و fidelity، بينما
تعظم late-conditioning systems modularity.**
