## 1. لماذا يحتاج Agents إلى Retrieval؟

لا تستطيع LLM أن تستخدم مباشرةً إلا ما هو متاح داخل Model parameters و Current context. وهذا يفرض حدودًا فورية على Agents الحقيقية.

قد يحتاج Agent إلى الإجابة عن أسئلة حول:

- Document تم رفعها مؤخرًا،
- Internal company policy،
- Private codebase،
- Current structured data،
- Conversation سابقة،
- Preference شاركها المستخدم الأسبوع الماضي.

لا ينبغي افتراض وجود أي من هذه المعلومات داخل Training data الخاصة بالـ Model.

يحل Retrieval هذه المشكلة عبر البحث في معلومات مخزنة **خارج** LLM وإحضار الأجزاء ذات الصلة فقط إلى Current model call.

وهذا يعطينا Architecture أساسية:

```text
مخزن خارجي كبير
      |
      | استرجع العناصر ذات الصلة
      v
نافذة Context الحالية
      |
      v
LLM / Agent
```

يمكن لـ External storage أن تنمو بصورة مستقلة، بينما تظل كل LLM call منفردة محدودة بـ Finite context window.

## 2. Knowledge و Memory شقيقتان وليستا الشيء نفسه

تستخدم Knowledge و Memory غالبًا Retrieval technologies نفسها، لكنهما تمثلان أشياء مختلفة.

### المعرفة (Knowledge)

Knowledge هي معلومات خارجية يرجع إليها Agent.

أمثلة:

- PDFs،
- Manuals،
- Policies،
- Database tables،
- Code repositories،
- كتالوجات المنتجات (Product catalogs).

### Memory

تأتي Memory من Experience أو Interaction سابق.

أمثلة:

- Previous conversation turns،
- Earlier agent actions،
- Recorded user preferences،
- Prior task outcomes،
- العلاقات الملحوظة (Observed relationships).

| الخاصية | المعرفة (Knowledge) | Memory |
|---|---|---|
| المصدر الرئيسي | معلومات خارجية | Interaction و Experience |
| التحديث المعتاد | عندما يتغير Source | أثناء الاستخدام المستمر |
| مثال | ملف سياسة الشركة (Company policy PDF) | المستخدم يفضّل Summaries موجزة |
| Retrieval | Vector و Keyword و SQL و Graph | عائلات Retrieval نفسها |

تتداخل Storage mechanisms، لكن معنى المعلومات المخزنة ودورة حياتها يختلفان.

## 3. Retrieval و Augmentation

تشكل عمليتان أساس RAG.

### Retrieval

ابحث في External source عن معلومات ذات صلة بالـ Current query أو Task.

### الإضافة إلى السياق (Augmentation)

أدخل المعلومات المسترجعة داخل Current context الخاصة بالـ Model حتى تستطيع Model استخدامها.

معًا:

```text
استعلام المستخدم
   |
   v
استرجاع المعلومات ذات الصلة
   |
   v
إضافة المعلومات إلى Prompt/Context
   |
   v
تولّد LLM إجابة Grounded
```

هذا هو **RAG**.

يمكن للآلية العامة نفسها استرجاع Document knowledge أو Memories سابقة.

## 4. المرحلتان في نظام RAG

يفصل الفصل RAG إلى **Ingestion** و**Retrieval**.

### المرحلة A — Ingestion

```text
Documents
  -> تحميل
  -> تقسيم/Chunking
  -> Embedding
  -> تخزين Vectors + Source data
```

### المرحلة B — Retrieval و Generation

```text
استعلام المستخدم
  -> Embedding للاستعلام
  -> البحث في Vector store
  -> استرجاع Chunks ذات الصلة
  -> إضافة Chunks إلى Prompt
  -> تجيب LLM
```

هناك تمييز بالغ الأهمية: تنفذ **Embedding model** و**Generative LLM** مهمتين مختلفتين.

- Embedder: يحوّل Text إلى Vectors من أجل Retrieval.
- LLM: تستدل على Retrieved context وتولّد الإجابة.

[[IMAGE_NEEDED: RAG ingestion and retrieval phases | Two-column diagram. Ingestion: Document -> Chunk -> Embedding Model -> Vector DB. Retrieval: Query -> Embedding -> Similarity Search -> Retrieved Chunks -> LLM -> Answer | Learner should clearly see that embedding and generation are separate operations]]

## 5. Semantic search: الاسترجاع حسب المعنى

تبحث Traditional keyword search عن Literal terms. أما Semantic search فتحاول مطابقة **معنى** Query مع معنى Stored content.

على سبيل المثال:

```text
الاستعلام: مركبات
    المستند: السيارات تحتاج إلى صيانة منتظمة
```

قد يفوّت Pure word-matching system الـ Document لأن `vehicles` و`cars` كلمتان مختلفتان. أما Semantic embedding system فقد يضعهما قريبًا من بعضهما في Vector space.

هذا قوي، لكن Similarity ليست Truth.

يسلط الفصل الضوء على ثلاثة قيود عملية:

1. قد تظل Result المتشابهة دلاليًا خاطئة Factually.
2. قد يؤدي Top-K retrieval إلى استبعاد معلومات ذات صلة خارج K Results المختارة.
3. توازن Approximate nearest-neighbor search بين قدر صغير من Exactness وبين Speed أعلى.

لذلك تظل Retrieval quality بحاجة إلى Evaluation.

## 6. ابدأ ببساطة: TF-IDF

قبل Neural embeddings، يقدم الفصل TF-IDF لأن آليتها سهلة الفهم.

يشير **TF-IDF** إلى **Term Frequency–Inverse Document Frequency**.

وهو يمنح Weight أعلى للمصطلحات المهمة في Document واحدة وغير الشائعة عبر جميع Documents.

### تكرار المصطلح (Term Frequency — TF)

بالنسبة إلى الجملة:

```text
The sky is blue and beautiful    # السماء زرقاء وجميلة
```

إذا ظهرت `blue` مرة واحدة ضمن ست كلمات:

```text
TF(blue) = 1 / 6 ≈ 0.167    # تكرار الكلمة blue
```

### معكوس تكرار المستند (Inverse Document Frequency — IDF)

إذا احتوى Corpus على ثماني Documents وظهرت `blue` في أربع منها:

```text
IDF(blue) = log10(8 / 4)    # معكوس تكرار المستندات
          ≈ 0.301
```

### قيمة TF-IDF

```text
TF-IDF = TF × IDF
       ≈ 0.167 × 0.301
       ≈ 0.050
```

تعني Value الأعلى أن المصطلح أكثر تميزًا لتلك Document داخل Corpus.

### ما الذي تجيده TF-IDF؟

تكون TF-IDF مفيدة عندما تكون Literal words مهمة:

- Product codes،
- Names،
- Error identifiers،
- Uncommon technical terms،
- المصطلحات الدقيقة (Exact terminology).

أما قيدها فهو Semantic generalization: تظل `cars` و`vehicles` Features مختلفة.

## 7. التشابه الجيبي (Cosine similarity)

بمجرد تمثيل Text كـ Vectors، نحتاج إلى طريقة لمقارنتها.

تقيس Cosine similarity **الزاوية** بين متجهين (Vectors) بدل Raw magnitude.

صيغة مبسطة هي:

```text
cosine_similarity(A, B) = (A · B) / (||A|| ||B||)
```

الفكرة المهمة هي:

- الاتجاه نفسه -> Similarity مرتفعة،
- اتجاه مختلف -> Similarity أقل.

بالنسبة إلى كثير من Text vectors، تكون Cosine similarity مفيدة لأن وثيقتين (Documents) يمكن اعتبارهما متشابهتين حتى إذا كانت إحداهما أطول من الأخرى.

يستخدم الفصل أيضًا Cosine distance:

```text
cosine_distance = 1 - cosine_similarity
```

لذلك:

- Similarity الأعلى تعني أقرب،
- Distance الأقل تعني أقرب.

لا ترتّب Cosine distance بالخطأ كما لو أن الأكبر أفضل.

## 10. Neural embeddings: من الكلمات إلى المعنى

تمثل TF-IDF أهمية المصطلح. أما Neural embeddings فتحاول تمثيل Semantic meaning.

تحول Embedding model الـ Text إلى Dense vector:

```text
"السيارات تحتاج إلى صيانة"
        |
        v
[0.12, -0.42, 0.08, ..., 0.31]
```

ينبغي أن تنتهي أجزاء Text المرتبطة دلاليًا في مواضع متقاربة نسبيًا داخل Learned vector space.

### Sparse vectors مقابل Dense vectors

تكون TF-IDF vectors عادةً Sparse: معظم Dimensions تساوي صفرًا.

أما Neural embeddings فهي Dense: تتوزع المعلومات عبر العديد من Learned dimensions.

### مفاضلة قابلية التفسير (Interpretability trade-off)

يمكن لـ TF-IDF dimension أن ترتبط بمصطلح معروف. أما Neural-embedding dimension منفردة فلا يكون لها عادةً معنى Human-readable بسيط.

لذلك نفسر Embeddings أساسًا من خلال علاقات مثل Similarity و Distance.

### قيّم Embeddings على Domain الخاصة بك

يستخدم الفصل OpenAI embedding API كمثال عملي، لكن الدرس الأوسع هو تقييم Embedding quality على Content و Queries الفعلية التي سيخدمها نظامك.

## 13. لماذا لا تكفي Vector search وحدها؟

تعد Semantic search أساسًا قويًا، لكن Production RAG تحتاج غالبًا إلى أكثر من Retrieval signal واحدة.

يحدد الفصل عدة Failure cases شائعة.

| المشكلة | المثال | Retrieval داعمة أفضل |
|---|---|---|
| فقد Exact identifier | رمز خطأ `P0420` (Error code) | Keyword أو Hybrid search |
| عدم تطابق Jargon | Technical terms مختلفة | بحث Lexical واعٍ بالمرادفات (Hybrid / Synonym-aware lexical search) |
| سيطرة Near duplicates | Product sheets مكررة | إزالة التكرار والترتيب الهجين (Deduplication / MMR / Hybrid ranking) |
| Chunk مرتبطة لكنها لا تجيب | استرجاع صفحة عامة بدل Exact fact | إعادة ترتيب و Filters (Reranking / Filters) |
| الحاجة إلى Relationships | سؤال "Who reports to Alice's manager?" — من يتبع لمدير Alice؟ | Graph أو Relational query |
| الحاجة إلى Fresh structured fact | السعر الحالي (Current price) | مصدر بيانات Relational/Live |
| كلمة ملتبسة | `mouse` كحيوان مقابل Device | Filters / Hybrid search — ترشيح وبحث هجين |
| Content مقيّدة | مستند HR غير مصرح به (Unauthorized HR document) | Retrieval واعٍ بالـ ACL |

وظيفة Retrieval system ليست مجرد العثور على Related text. بل يجب أن تجد **Evidence الصحيحة**.

## 14. اختيار Retrieval methods

تتطلب أنواع Data المختلفة Retrieval approaches مختلفة.

### البحث بالكلمات المفتاحية / Lexical search

الأفضل لـ:

- Exact terms،
- IDs،
- Legal wording،
- Error codes،
- مفردات Domain نادرة (Rare domain vocabulary).

الأفضل لـ:

### البحث في Relational database

الأفضل لـ:

- Structured facts،
- Filters،
- Joins،

- Multihop questions،
- Explainable paths بين Facts.

## 15. Hybrid retrieval و RRF

تنفذ Hybrid retrieval عادةً عمليتي Search على الأقل:

```text
استعلام المستخدم
   +--> Lexical search -> Ranked list A
   +--> Vector search  -> Ranked list B
                           |
                           v
                     Fusion / Reranking
                           |
                           v
                     Final context
```

المشكلة هي أن Raw scores من Search systems مختلفة قد لا تكون قابلة للمقارنة مباشرةً.

يقدم الفصل **RRF** بوصفها حلًا شائعًا.

قيمة RRF مبسطة هي:

```text
RRF(المستند) = Σ 1 / (k + rank_i)
```

حيث تمثل `rank_i` موضع Document داخل كل Ranked list وتمثل `k` Constant.

الفكرة الأساسية هي أن RRF تستخدم **Rank positions**، وليس Raw underlying similarity/BM25 scores.

تحصل Document ذات Rank مرتفع في عدة Retrieval systems على Fused ranking قوية.

## 17. Grounding: اجعل Retrieved evidence هي المرجع

Retrieval وحده لا يضمن Grounded answer.

قد تظل Model تعتمد على معلومات مشفرة داخل Parameters الخاصة بها ما لم يقيّد النظام صراحةً كيفية إنتاج Answers.

تعليمات Grounding قوية تشبه:

```text
أجب فقط باستخدام Retrieved context.
إذا لم تحتوِ Retrieved context على الإجابة، فاذكر ذلك بوضوح.
استشهد بمقطع Source الذي يدعم كل Claim factual.
```

### Grounding ضعيفة (Weak grounding)

تتبع Answer الـ Retrieved content عمومًا، لكنها قد تتضمن Outside knowledge.

### Grounding قوية (Strong grounding)

يمكن تتبع كل Claim إلى Retrieved evidence، وعادةً مع Citations.

تكون Strong grounding مهمة بصورة خاصة عندما يكون للـ Incorrect answers عواقب حقيقية.

### Grounding ليست Prompt problem فقط

تعتمد Grounding quality أيضًا على:

- Chunk quality،
- Retrieval relevance،
- Source quality،
- Citation handling،
- Evaluation.

لا تستطيع Grounding prompt مثالية إصلاح Retrieval سيئة باستمرار.

## 19. Agent memory كـ Architecture، لا كبيولوجيا

يستخدم الفصل تسميات مألوفة مثل Short-term و Long-term memory، لكنه يحذر من أخذ تشبيه Human memory حرفيًا أكثر من اللازم.

نموذج هندسي أوضح هو:

### Context window

المعلومات المتاحة داخل Current model call.

### التخزين الخارجي (External storage)

Databases و Vector stores و Files أو Graphs تستمر خارج Model.

### إدارة الحالة (State management)

Working notes و Scratchpads و Task state و Plan trackers المستخدمة أثناء Workflow.

### Retrieval

الآليات التي تعيد Stored information المناسبة إلى Current context.

هذه Architecture أكثر فائدة من تخيل أن Agent "يتذكر" بالطريقة نفسها التي يتذكر بها الإنسان.

افترض أننا نخزن:

```text
مايكل --lives_in--> كالغاري
    مايكل --works_at--> شركة A
    شركة A --located_in--> ألبرتا
```

يستطيع Graph الإجابة بكفاءة عن Relationship-based questions عبر Traversing للـ Edges.

### نقاط القوة

- Entities واضحة،
- Relations صريحة،
- Multihop traversal،
- Paths قابلة للفحص.

### القيود

- قد لا تتطابق Fuzzy language مع Exact entity names،
- قد ينتج LLM-based fact extraction أخطاء،
- قد تتحول Aliases مثل `Doc` و`Doc Brown` إلى Nodes منفصلة،
- تنشئ Dense graphs مشكلات Scale و Maintenance خاصة بها.

وهذا يحفز **Hybrid memory**.

## 24. أمثلة التعلم مقابل Production memory

يذكر الفصل صراحةً أن الأمثلة Local أو In-memory البسيطة تعليمية وليست Production systems كاملة.

تحتاج Production memory إضافةً إلى ذلك إلى:

- Persistent storage،
- Access control،
- Observability،
- Retrieval-quality evaluation،
- Policies للمعلومات القديمة،
- Correction و Update mechanisms،
- فصل واضح بين Users/Tenants،
- Privacy و Retention rules.

MCP server ليست سوى Interface. تأتي جودة Memory من Pipeline كاملة خلفها.

## 25. Semantic augmentation للـ Memories

قد يصعب Retrieval لـ Memory مخزنة إذا صاغ المستخدمون مستقبلًا أسئلتهم بصورة مختلفة.

يصف الفصل تعزيز Memories بإشارات Semantic إضافية أوأسئلة Retrieval متوقعة.

مثال Memory:

```text
أكمل المستخدم مسار الـ onboarding في 2 أكتوبر.
```

Retrieval cues محتملة:

```text
متى أنهى المستخدم الـ onboarding؟
    هل اكتمل الـ onboarding؟
    ماذا حدث خلال جلسة الـ onboarding في أكتوبر؟
```

يمكن لهذه Semantic representations الإضافية تحسين Retrieval مستقبلًا لأن Stored item تصبح مرتبطة بعدة طرق قد تُطلب بها المعلومات لاحقًا.

## 26. ضغط Memory و Knowledge

مع نمو Stores، قد تتراكم Duplicates و Repeated observations و Verbose histories.

تقلل Compression هذه الفوضى.

يصف الفصل Pattern مثل:

```text
عناصر memory كثيرة
      |
      v
تجميع العناصر المتشابهة في clusters
      |
      v
تلخيص كل cluster
      |
      v
تخزين تمثيلات مضغوطة
```

يمكن لطرق Clustering مثل k-means تجميع Items المرتبطة دلاليًا قبل Summarization.

قد تساعد Compression عندما:

- تكون Memories كثيرة متكررة،
- يكون Source material Verbose،
- تهيمن Duplicates على Retrieval results،
- تزداد Token cost بسبب Retrieved context.

لكن Compression لها تكلفة: قد تحذف Summarization تفاصيل. لذلك يجب أن تتطابق Compression policy مع حاجة Application إلى Fidelity.

## 27. Forgetting و Retention

أحيانًا لا تكفي Summarization. ينبغي لبعض المعلومات في النهاية أن تتوقف عن المشاركة في Retrieval.

قد يكون Forgetting مفيدًا عندما تكون Stored items:

- متكررة،
- قديمة،
- منخفضة القيمة،
- متعارضة مع معلومات أحدث،
- لم تعد مرتبطة بهدف Agent.

يقارن الفصل فكرتين:

- **Compression:** الحفاظ على المعلومات المهمة في Representation أصغر.
- **Forgetting:** إزالة المعلومات التي لم يعد ينبغي أن تشارك في Retrieval.

Retention أيضًا قضية Operational و Compliance. قد يكون Aggressive deletion غير مناسب عندما يجب على Application الاحتفاظ Records، بينما عدم إزالة أي شيء أبدًا قد ينتج Retrieval قديمة أو Noisy.

تعتمد Policy الصحيحة على Application.

## 28. دليل عملي لتصميم RAG و Memory

استخدم هذا التسلسل عند تصميم Agent knowledge أو Memory system.

### الخطوة 1 — حدّد نوع المعلومات

هل هي Free text أو Exact terminology أو Relational facts أو Live structured data أو Past interaction؟

### الخطوة 2 — اختر Storage وفق احتياجات Retrieval

لا تبدأ بـ Vector database لمجرد أن RAG شائعة.

### الخطوة 3 — صمّم Ingestion و Chunking

ينبغي أن تحافظ Chunks على Context كافية للإجابة عن Queries المتوقعة.

### الخطوة 4 — اختر Retrieval signals

استخدم Lexical أو Vector أو SQL أو Graph أو Hybrid retrieval وفق Data.

### الخطوة 5 — استرجع فقط Context كافية

Chunks أكثر ليست أفضل تلقائيًا.

### الخطوة 6 — اعمل Grounding للإجابة

اجعل Retrieved evidence هي المرجع واطلب Citations عندما يكون ذلك مناسبًا.

### الخطوة 7 — قيّم Retrieval بصورة منفصلة عن Generation

إذا لم يتم Retrieval للـ Evidence الصحيحة أصلًا، فلن يصلح Prompt tuning وحده الإجابة.

### الخطوة 8 — اجعل Memory انتقائية

ليست كل تفاصيل Conversation جديرة بـ Persistent storage.

### الخطوة 9 — حافظ على Store

حدّث أواضغط أوأزل Duplicates أوانسَ Stale information.

### الخطوة 10 — احمِ Access

يجب أن تحترم Retrieval صلاحيات User و Tenant قبل وصول Content إلى Model.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1: RAG تعني Vector search

> Vector search هي Retrieval technique واحدة، وليست RAG architecture كاملة.

قد تستخدم Production RAG أيضًا Lexical و Relational و Graph أو Hybrid retrieval.

### المفهوم الخاطئ 2: Similar يعني Correct

> تقيس Semantic similarity المعنى المرتبط، لا Truth أو Authority.

تظل Source quality و Grounding مهمتين.

### المفهوم الخاطئ 3: Top-K أكبر يحسن Answers دائمًا

> قد تضيف Retrieved chunks أكثر Noise وتزيد Tokens وتخفف Evidence ذات الصلة.

ينبغي تقييم K مقابل Queries فعلية.

### المفهوم الخاطئ 4: Embedding search تستبدل Exact keyword search

> غالبًا ما تستفيد IDs والأرقام والأسماء والعبارات الدقيقة من Lexical retrieval.

تجمع Hybrid systems بين القوتين.

### المفهوم الخاطئ 5: Grounded prompt تصلح Retrieval سيئة

> لا تستطيع Model الاستشهاد بـ Evidence لم تجدها Retrieval layer أصلًا.

يجب تقييم Retrieval و Generation بصورة منفصلة.

### المفهوم الخاطئ 6: Agent memory مثل Human memory

> يتم تنفيذ Agent memory عبر Context و Storage و State و Retrieval.

Human cognitive labels مفيدة كاستعارات، وليست Mechanisms حرفية.

### المفهوم الخاطئ 7: خزّن كل شيء إلى الأبد

> Memory غير المحدودة تنشئ Redundancy و Stale facts و Privacy risk و Retrieval noise.

تحتاج Memory إلى Maintenance و Retention policies.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| Retrieval | العثور على معلومات ذات صلة داخل External store |
| الإضافة للسياق (Augmentation) | إضافة Retrieved information إلى Current model context |
| RAG — الاسترجاع المعزز بالتوليد | Retrieval-Augmented Generation — التوليد المعزز بالاسترجاع |
| القطعة (Chunk) | Segment من Source material تتم فهرستها واسترجاعها كوحدة |
| التضمين (Embedding) | Dense numeric representation تستخدم للمقارنة Semantic |
| قاعدة البيانات المتجهية (Vector database) | Store محسّنة لـ Similarity search عبر Vectors |
| TF-IDF — وزن المصطلحات | Lexical weighting method تعتمد على Term frequency و Corpus rarity |
| التشابه الجيبي (Cosine similarity) | Angular similarity بين Vectors |
| المسافة الجيبية (Cosine distance) | `1 - cosine similarity` — واحد ناقص التشابه الجيبي |
| أعلى K نتائج (Top-K) | عدد أعلى Retrieval results في Ranking التي يتم إرجاعها |
| Semantic search | Retrieval حسب المعنى بدل Exact surface terms |
| البحث بالكلمات المفتاحية (Keyword search) | Retrieval باستخدام Exact words أو Tokens أو Lexical signals |
| Hybrid search | دمج Semantic و Lexical/Other retrieval signals |
| RRF — دمج الرتب التبادلي | Reciprocal Rank Fusion، طريقة لدمج Results اعتمادًا على Rank |
| الإسناد إلى الأدلة (Grounding) | تقييد Generated claims بـ Retrieved evidence |
| الذاكرة العاملة (Working memory) | Current task/Conversation state المتاحة أثناء Active work |
| الذاكرة طويلة المدى (Long-term memory) | معلومات Persistent مخزنة خارج Current context |
| ذاكرة Graph (Graph memory) | Memory ممثلة كـ Entities و Relations و Observations |
| الذاكرة الحدثية (Episodic memory) | Events أو Experiences مخزنة |
| الذاكرة الإجرائية (Procedural memory) | Processes أو Steps مخزنة |
| الضغط (Compression) | دمج Stored items مرتبطة في Representations أصغر |
| النسيان (Forgetting) | إزالة Information من Future retrieval وفق Policy |

**تحل RAG و Agent memory المشكلة المعمارية نفسها: لا تستطيع Model استخدام سوى مقدار محدود من Context في كل مرة، بينما تعيش Knowledge و Experience المفيدة داخل External stores أكبر بكثير. لذلك تسترجع Agents الموثوقة بصورة انتقائية، وتجمع Retrieval methods المناسبة، وتعمل Grounding للـ Outputs باستخدام Evidence، وتحافظ على Memory stores بحيث تظل المعلومات ذات الصلة قابلة للعثور عليها دون أن تسيطر Context قديمة أومتكررة.**
