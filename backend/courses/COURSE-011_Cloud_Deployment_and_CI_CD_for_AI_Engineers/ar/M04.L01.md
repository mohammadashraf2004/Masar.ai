## مخرجات التعلّم

بنهاية هذا الدرس يجب أن تكون قادرًا على:

- شرح لماذا تخلق إدارة البنية التحتية يدويًا مشكلات في السرعة والاتساق والتعاون.
- تعريف البنية التحتية بوصفها شيفرة (Infrastructure as Code أو IaC).
- التمييز بين نهجي البنية التحتية التصريحي (declarative) والأمري (imperative).
- شرح دور Terraform بوصفه أداة IaC تصريحية.
- وصف غرض providers وresources وstate في Terraform.
- شرح لماذا ملف حالة Terraform (state) مهم ولماذا لا ينبغي إيداعه في Git.
- شرح غرض الـ backend البعيد في سير العمل الذي يصفه المصدر.
- تثبيت Terraform والتحقق منه.
- كتابة إعداد Terraform أساسي لـ AWS.
- شرح سير العمل `terraform init → terraform plan → terraform apply`.
- تفسير مؤشرات الإنشاء والحذف والتعديل في خطة Terraform (plan).
- شرح انحراف الإعداد (configuration drift) وكيف يكتشفه Terraform.
- حذف البنية التحتية المُدارة باستخدام `terraform destroy`.
- استبدال القيم المثبّتة في الشيفرة بمتغيرات إدخال في Terraform.
- شرح كيف توفّر ملفات `.tfvars` قيم المتغيرات.
- إنشاء مخرجات Terraform (outputs) والإشارة إلى خصائص الموارد.
- ربط تخطيط Terraform بمراجعة pull request في سير عمل احترافي.

## 1. البنية التحتية بوصفها شيفرة: إدارة البنية التحتية كما تُدار البرمجيات

في الدرس السابق، منحنا Docker artifact تطبيق قابلًا للتكرار.

وقد حلّ ذلك سؤالًا رئيسيًا:

> "كيف نحزّم التطبيق ليعمل باتساق؟"

لكن التطبيق ما زال يحتاج إلى مكان يعمل فيه.

وقد يتطلب:

- خوادم،
- شبكات،
- تخزينًا،
- قواعد بيانات،
- جدران حماية،
- موازنات حمل.

وسؤال DevOps التالي هو:

> **كيف ننشئ البنية التحتية ونديرها بالانضباط نفسه الذي نستخدمه مع شيفرة التطبيق؟**

هذا هو دور **البنية التحتية بوصفها شيفرة (Infrastructure as Code أو IaC)**.

### النموذج القديم: click-ops

يصف المصدر سير عمل البنية التحتية التقليدي بأنه عملية يدوية.

قد يطلب مطوّر خادمًا.

ثم قد يقوم مهندس عمليات بما يلي:

1. فتح console سحابي،
2. النقر عبر عدة شاشات إعداد،
3. اختيار الأحجام والمناطق،
4. ضبط الشبكات،
5. تعيين الصلاحيات،
6. تكرار الخطوات نفسها لبيئة أخرى.

يسمى هذا الأسلوب اليدوي غالبًا **click-ops**.

المشكلة ليست أن النقر سيئ في ذاته.

المشكلة أن الإعداد اليدوي المتكرر يصعب جعله:

- سريعًا،
- متسقًا،
- قابلًا للتكرار،
- قابلًا للمراجعة،
- خاضعًا للإصدارات.

### ما الذي يغيّره IaC

مع IaC، تُوصف البنية التحتية في ملفات مقروءة آليًا.

وبدلًا من القول:

```text
"سجّل الدخول إلى AWS وأنشئ هذا المورد يدويًا."
```

تكتب إعدادًا يصف البنية التحتية.

من الناحية المفاهيمية:

```text
النموذج اليدوي

إنسان
  ↓
Cloud console
  ↓
نقر الإعدادات
  ↓
أُنشئ المورد


نموذج IaC

ملف الإعداد
  ↓
أداة IaC
  ↓
Cloud API
  ↓
أُنشئ المورد
```

ينقل IaC البنية التحتية من عملية يدوية غير موثّقة إلى شيء يمكن تخزينه ومراجعته وتكراره وأتمتته.

### أربع فوائد رئيسية من المصدر

#### 1. الأتمتة والسرعة

يستطيع تعريف بنية تحتية قابل لإعادة الاستخدام إنشاء موارد كثيرة دون تكرار كل خطوة يدوية.

وهذا يجعل إنشاء البيئات أسرع بكثير.

#### 2. الاتساق والموثوقية

يميل الإعداد اليدوي إلى الانحراف.

فقد تكون في بيئة واحدة:

```text
الخادم A
- الإعداد X مفعّل
- المنفذ Y مفتوح
- الحزمة Z الإصدار 1
```

بينما يختلف خادم آخر أُنشئ يدويًا اختلافًا طفيفًا.

يقلّل IaC هذا التباين باستخدام إعداد المصدر نفسه.

#### 3. التحكم بالإصدارات والتعاون

يمكن تخزين تعريفات البنية التحتية في Git.

وهذا يمنحك:

- التاريخ،
- تتبّع التغييرات،
- pull requests،
- مراجعة الشيفرة،
- رؤية الفريق.

تصبح تغييرات البنية التحتية عملًا قابلًا للمراجعة.

#### 4. ضبط التكلفة عبر سهولة الإزالة

إذا كان يمكن إنشاء البيئات من الشيفرة، فيمكن أيضًا تدميرها من الشيفرة.

ويبرز المصدر هذا بوصفه مفيدًا لبيئات التطوير أو الاختبار المؤقتة.

أنشئ ما تحتاجه، واستخدمه، ثم أزله عندما لا يعود مطلوبًا.

[[IMAGE_NEEDED: Click-ops versus Infrastructure as Code | A side-by-side diagram. Left side shows a human manually clicking through cloud-console screens to create resources. Right side shows version-controlled Terraform files flowing through Terraform into cloud APIs to create the same resources | Learner should notice that IaC turns manual infrastructure steps into repeatable, reviewable configuration]]

### الفكرة المحورية

تذكّر:

```text
شيفرة التطبيق تحدّد سلوك البرمجيات.
شيفرة البنية التحتية تحدّد البيئة التي تعمل عليها البرمجيات.
```

وكلتاهما يمكن أن تكون:

- خاضعة للتحكم بالإصدارات،
- قابلة للمراجعة،
- مؤتمتة،
- قابلة لإعادة الإنتاج.

## 2. البنية التحتية التصريحية مقابل الأمرية

يقدّم المصدر أسلوبين عامين في IaC.

### النهج الأمري (Imperative)

يصف النهج الأمري **الخطوات**.

فكّر:

```text
1. أنشئ جهازًا افتراضيًا.
2. أرفق قرصًا بسعة 10 GB.
3. ثبّت Apache.
4. اضبط الخدمة.
```

المنطق إجرائي.

أنت تحدّد كيف تصل إلى الحالة النهائية.

ويستخدم المصدر أدوات مثل Ansible وChef أمثلةً يمكن أن تستخدم الأسلوب الأمري.

### النهج التصريحي (Declarative)

يصف النهج التصريحي **الحالة النهائية المطلوبة**.

فكّر:

```text
"أريد جهازًا افتراضيًا واحدًا
بهذه المواصفات
وبإعداد التخزين هذا."
```

ثم تقرر الأداة الإجراءات اللازمة.

يُقدَّم Terraform في المصدر بوصفه أداة تصريحية.

### تشبيه المخطط

يستخدم المصدر مقارنة بديهية:

```text
الأمري = وصفة
التصريحي = مخطط هندسي
```

تقول الوصفة:

```text
نفّذ الخطوة A
ثم الخطوة B
ثم الخطوة C
```

ويقول المخطط الهندسي:

```text
هكذا ينبغي أن يبدو الشيء المكتمل.
```

### لماذا يهمّ التفكير التصريحي في Terraform

افترض أن شيفرتك تقول:

```text
الحالة المطلوبة (Desired state):
1 S3 bucket
```

إذا لم يوجد أي bucket، فقد يخطط Terraform لإنشاء واحد.

وإذا كان الـ bucket المُدار موجودًا أصلًا كما هو متوقع، فقد يخطط Terraform لعدم إجراء أي تغيير.

وإذا لم تعد البنية التحتية الحقيقية تطابق الإعداد، يستطيع Terraform اكتشاف الفرق والتخطيط لتصحيح.

مقارنة الحالة المطلوبة هذه من أهم النماذج الذهنية في الفصل كله.

```text
الحالة المطلوبة في الشيفرة
        ↓
مقارنة
        ↓
حالة البنية التحتية المعروفة/الحالية
        ↓
الفرق
        ↓
خطة التنفيذ
```

## 3. أساسيات Terraform: providers وresources وstate

Terraform أداة بنية تحتية بوصفها شيفرة مفتوحة المصدر أنشأتها HashiCorp.

ويقدّم المصدر Terraform على أنه محايد تجاه السحابات لأنه يستطيع العمل مع منصات خارجية كثيرة عبر **providers**.

وتُكتب إعدادات Terraform بلغة **HashiCorp Configuration Language (HCL)**.

تشكّل ثلاثة مفاهيم أساس هذا الدرس:

1. Providers
2. Resources
3. State

### 3.1 الـ Providers: إضافات لواجهات API الخارجية

يعرف **provider** في Terraform كيف يتواصل مع خدمة أو منصة معيّنة.

وتشمل الأمثلة المذكورة في المصدر:

- AWS،
- Azure،
- GCP،
- GitHub،
- Docker.

من الناحية المفاهيمية:

```text
إعداد Terraform
       ↓
Provider
       ↓
Platform API
       ↓
مورد حقيقي
```

يفهم provider الخاص بـ AWS واجهات API الخاصة بـ AWS.

ويفهم provider الخاص بـ Azure واجهات API الخاصة بـ Azure.

يوفّر Terraform نفسه سير العمل واللغة؛ أما الـ providers فتربط ذلك السير بالأنظمة الخارجية.

### 3.2 الـ Resources: لبنات البناء

يمثّل **resource** في Terraform كائنًا من البنية التحتية.

وتشمل الأمثلة:

- حاوية تخزين (storage bucket)،
- شبكة افتراضية،
- نسخة حوسبة،
- سجل DNS.


فكّر:

```text

```

### 3.3 الـ State: خريطة Terraform إلى العالم الحقيقي

يحتاج Terraform إلى أن يتذكر أي كائن سحابي حقيقي يقابل أي resource في الإعداد.

ويقدّم المصدر:

```text
terraform.tfstate
```

بوصفه ملف الـ state.

من الناحية المفاهيمية:

```text
شيفرة Terraform

aws_s3_bucket.my_bucket
          |
          | مرتبطة عبر الـ state
          v
الـ bucket الحقيقي في AWS S3
my-unique-devops-book-bucket-98765
```

يتيح هذا الربط لـ Terraform التفكير في البنية التحتية المُدارة القائمة.

### لماذا يهمّ الـ state

يبرز المصدر ثلاثة أغراض.

#### الربط (Mapping)

يحتاج Terraform إلى معرفة أي مورد حقيقي يقابل أي مورد مُعلَن.

#### الأداء

يساعد الـ state على ألا يعامل Terraform كل تشغيل كأنه لا يوجد شيء.

#### التخطيط

يستخدم Terraform الـ state أثناء مقارنة البنية التحتية الحالية بالمطلوبة لتحديد ما ينبغي أن يتغير.

## 4. أمان الـ state والـ backends البعيدة

ملف الـ state مهم، لكن المصدر يعامله أيضًا على أنه حساس.

فقد يحتوي تفاصيل البنية التحتية وقد يحتوي قيمًا حساسة.

لذلك يقول المصدر صراحةً:

> لا تودِع ملفات حالة Terraform في Git.

### `.gitignore`

يوصي الفصل بإضافة ما يلي على الأقل:


إلى `.gitignore`.

لماذا؟

#### `.terraform/`

يحتوي هذا المجلد بيانات الـ providers المنزَّلة.

ويمكن إعادة إنشائه بـ:

⟦CODE_3⟧

لذلك لا حاجة إلى تخزينه في التحكم بالمصدر.

#### `*.tfstate`

تحتوي هذه الملفات حالة Terraform.

ولا ينبغي إيداعها.

### الـ backend البعيد

بالنسبة إلى مشاريع الفرق الحقيقية، يوصي المصدر بتخزين الـ state عن بُعد بدلًا من الاكتفاء بملف محلي.

ويعطي مثالًا على S3 backend:

⟦CODE_4⟧

ويربط المصدر الـ state البعيد بما يلي:

- تخزين مركزي للـ state،
- تعاون أكثر أمانًا في الفريق،
- قفل الـ state (state locking) لتجنب عمليات Terraform المتزامنة المتعارضة.

والفكرة المهمة للمبتدئ:

```text

الـ state ينبغي أن يُدار بشكل منفصل وآمن.
```

لا تخلط بين هذين الـ artifact.

### الإعداد مقابل الـ state

| الـ Artifact | الغرض |
|---|---|
| ملفات `.tf` | تصف البنية التحتية المطلوبة |
| `terraform.tfstate` | يتتبّع ربط Terraform بالبنية التحتية الحقيقية المُدارة |
| `.terraform/` | بيانات المزوّدين/المشروع المنزَّلة محليًا |

## 6. سير عمل Terraform الأساسي: init وplan وapply

أهم سير عمل تشغيلي في الفصل هو:

```text
terraform init    # تهيئة
      ↓
terraform plan    # معاينة
      ↓
terraform apply    # تنفيذ
```

لكل أمر غرض مختلف.

### 6.1 `terraform init`

شغّل:

⟦CODE_15⟧

يهيّئ هذا المشروع.

ويشرح المصدر أن Terraform:

- يقرأ الإعداد،
- يحدّد الـ providers المطلوبة،
- ينزّل إضافات الـ providers المطلوبة،
- يخزّن بيانات الـ providers في `.terraform/`.

تشغّل `init` عادةً:

- عند بدء مشروع Terraform جديد،
- عند إضافة providers أو تغييرها.

### 6.2 `terraform plan`

شغّل:

⟦CODE_16⟧

هذه أهم خطوة أمان في الفصل.

يعاين الأمر ما **كان** Terraform سيفعله.

وهو لا يجري التغييرات بعدُ.

يقارن Terraform:

```text
الإعداد المطلوب
        +
الحالة المعروفة/الحالية
        ↓
خطة التنفيذ
```

### رموز الخطة (Plan)

يستخدم المصدر:

```text
+  إنشاء
-  حذف
~  تعديل في المكان
```

راجع الخطة دائمًا قبل التطبيق.

الخطة فرصتك لأن تسأل:

- هل ينشئ Terraform ما أتوقعه؟
- هل يحاول حذف شيء بشكل غير متوقع؟
- هل الاستبدال أو التعديل مقصود؟

ويوجّه المصدر المتعلّم إلى كتابة:

```text
yes    # اكتب هذه الكلمة
```

للمتابعة.

وفي هذا الدرس يعني ذلك إنشاء S3 bucket.

بعد اكتمال الـ apply، يوجد ملف محلي:

```text
terraform.tfstate
```

يربط مورد Terraform بالـ S3 bucket الحقيقي.

## 7. اكتشاف الانحراف وخطط pull-request والحذف

Terraform ليس لإنشاء الموارد فقط.

ويوضح المصدر أيضًا كيف يساعد Terraform في صيانة البنية التحتية وإزالتها.

### 7.1 انحراف الإعداد (Configuration drift)

افترض أن شيفرة Terraform تصف إعدادًا واحدًا، لكن شخصًا غيّر البنية التحتية الحقيقية يدويًا.

الآن:

```text
شيفرة Terraform
      ≠
البنية التحتية الحقيقية
```

هذا الفرق هو **انحراف الإعداد (configuration drift)**.

ويشرح المصدر أن:

⟦CODE_18⟧

يستطيع اكتشاف هذا عدم التطابق.

وقد يقترح Terraform:

```text
~ تعديل
```

أو:

```text
-/+ استبدال
```

بحسب التغيير.

والفكرة التصريحية:

> تمثّل الشيفرة الحالة المطلوبة، ويخطط Terraform لتغييرات تعيد الواقع نحو تلك الحالة.

### 7.2 خطة Terraform في pull requests

يمدّ المصدر الفكرة إلى سير عمل الفرق.

في الفرق الاحترافية، يستطيع نظام CI تشغيل:

⟦CODE_19⟧

عند فتح pull request للبنية التحتية.

عندها يستطيع المراجعون فحص تغيير البنية التحتية المقترح قبل تطبيقه.

من الناحية المفاهيمية:

```text
تغيير شيفرة البنية التحتية
        ↓
Pull Request
        ↓
terraform plan
        ↓
مراجعة الموارد المقترحة
        ↓
الموافقة أو التعديل
```

يربط هذا نموذج تعاون Git من الدروس السابقة مباشرةً بتغييرات البنية التحتية.

### 7.3 احذف البنية التحتية المُدارة

يستخدم المصدر:

⟦CODE_20⟧

لإزالة الموارد التي يديرها Terraform.

يعرض Terraform أولًا خطة الإزالة ويطلب التأكيد.

وفي بيئة التدريب هذا مهم لأن ترك موارد سحابية تعمل قد يولّد تكلفة غير ضرورية.

ويؤكد المصدر أن IaC تجعل الإزالة سهلة.

من الناحية المفاهيمية:

```text
terraform apply
    ↓
الموارد موجودة

terraform destroy
    ↓
أُزيلت الموارد المُدارة
```

### لماذا يهمّ الحذف مفاهيميًا

IaC ليست فقط:

> "إنشاء البنية التحتية بشكل أسرع."

بل هي أيضًا:

> "إدارة دورة حياة البنية التحتية بأكملها عبر الشيفرة."

وهذا يشمل:

- الإنشاء،
- التعديل،
- الاستبدال،
- الحذف.

## مفاهيم خاطئة شائعة

### المفهوم الخاطئ 1

> "البنية التحتية بوصفها شيفرة تعني فقط حفظ لقطات شاشة لإعدادات السحابة."

### لماذا هذا خاطئ

تستخدم IaC إعدادًا مقروءًا آليًا لتعريف البنية التحتية وإدارتها.

وتأتي القيمة من الأتمتة وقابلية التكرار والتحكم بالإصدارات والمراجعة.

---

### المفهوم الخاطئ 2

> "Terraform أمري لأنني أشغّل الأوامر بالترتيب."

### لماذا هذا خاطئ

يستخدم سير عمل CLI أوامر مثل `init` و`plan` و`apply`، لكن إعداد البنية التحتية نفسه تصريحي في طرح المصدر.

أنت تصف حالة البنية التحتية المطلوبة.

---

### المفهوم الخاطئ 3

> "`terraform plan` يغيّر حسابي في AWS."

### لماذا هذا خاطئ

يقدّم المصدر `plan` بوصفه معاينة.

أما `terraform apply` فهو الأمر الذي ينفّذ تغييرات البنية التحتية الحقيقية.

---

### المفهوم الخاطئ 4

> "ملف حالة Terraform مجرد ملف مصدري آخر ينتمي إلى Git."

### لماذا هذا خاطئ

يحذّر المصدر صراحةً من إيداع الـ state.

يتتبّع الـ state ارتباطات البنية التحتية الحقيقية وقد يحتوي تفاصيل حساسة.

---

### المفهوم الخاطئ 5

> "إذا غيّر شخص البنية التحتية يدويًا فلن يستطيع Terraform المساعدة بعد الآن."

### لماذا هذا خاطئ

يشرح المصدر أن `terraform plan` يستطيع اكتشاف انحراف الإعداد بين الحالة المطلوبة المعلنة والبنية التحتية الحقيقية.

---

### المفهوم الخاطئ 6

> "المتغيرات مخصصة فقط للقيم السرية."

### لماذا هذا خاطئ

يستخدم الفصل المتغيرات لإعدادات عادية قابلة لإعادة الاستخدام مثل:

- المنطقة،
- اسم الـ bucket.

والمتغيرات تتعلق أساسًا بالتحويل إلى معاملات وإعادة الاستخدام.

---

### المفهوم الخاطئ 7

> "المخرجات تنشئ موارد سحابية جديدة."

### لماذا هذا خاطئ

تعرض المخرجات قيمًا من موارد يديرها Terraform بعد الـ apply.

وهي لا تنشئ المورد بنفسها.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| البنية التحتية بوصفها شيفرة (IaC) | ممارسة إدارة البنية التحتية عبر ملفات إعداد مقروءة آليًا |
| Click-ops | إدارة البنية التحتية يدويًا عبر console تفاعلية وشاشات إعداد |
| انحراف الإعداد (Configuration drift) | الفرق بين البنية التحتية المعلنة أو المتوقعة وإعدادها الحالي الحقيقي |
| IaC تصريحي (Declarative) | وصف الحالة النهائية المطلوبة وترك الأداة تحدّد الإجراءات اللازمة |
| IaC أمري (Imperative) | وصف الخطوات الصريحة المطلوبة للوصول إلى حالة مستهدفة |
| Terraform | أداة بنية تحتية بوصفها شيفرة تصريحية قُدّمت في الفصل |
| HCL | لغة HashiCorp Configuration Language |
| Provider | إضافة Terraform تتواصل مع واجهة API لمنصة خارجية |
| Resource | كتلة Terraform تمثّل كائنًا من البنية التحتية |
| نوع المورد (Resource type) | نوع بنية تحتية يعرّفه الـ provider مثل `aws_s3_bucket` |
| الاسم المحلي (Local name) | اسم Terraform يُستخدم للإشارة إلى مورد داخل الإعداد |
| State | ربط Terraform المخزَّن بين الإعداد والموارد الحقيقية المُدارة |
| `terraform.tfstate` | ملف حالة Terraform المحلي الافتراضي |
| Backend | موقع/آلية تُستخدم لتخزين حالة Terraform |
| `.terraform/` | مجلد المشروع الذي يحتوي بيانات providers المنزَّلة |
| `terraform init` | يهيّئ مشروع Terraform وينزّل الـ providers المطلوبة |
| `terraform plan` | يعاين تغييرات البنية التحتية المقترحة |
| `terraform apply` | ينفّذ التغييرات المخطَّطة على الـ provider |
| `terraform destroy` | يخطط لإزالة البنية التحتية التي يديرها Terraform وينفّذها |
| متغير إدخال (Input variable) | معامل يُقدَّم إلى إعداد Terraform |
| `terraform.tfvars` | ملف يُستخدم في الفصل لتوفير قيم المتغيرات |
| قيمة مخرجات (Output value) | قيمة يعرضها Terraform بعد تقييم الموارد المُدارة |
| ARN | Amazon Resource Name؛ يُستخدم في الفصل مثالًا على خاصية مخرجات |

## اختبر نفسك

قبل أن تواصل، تأكد من قدرتك على الإجابة عن:

1. ما المشكلة التي تحلها البنية التحتية بوصفها شيفرة؟
2. لماذا قد يخلق click-ops انحراف الإعداد؟
3. ما الفرق بين IaC الأمري والتصريحي؟
4. لماذا يوصف Terraform بأنه تصريحي؟
5. ماذا يفعل provider في Terraform؟
6. ما الفرق بين نوع المورد والاسم المحلي للمورد؟
7. لماذا يحتاج Terraform إلى state؟
8. لماذا لا ينبغي إيداع `terraform.tfstate` في Git؟
9. لماذا يُستبعد `.terraform/` من التحكم بالإصدارات في سير عمل المصدر؟
10. ما الذي يحله الـ backend البعيد مفاهيميًا؟
11. ماذا يفعل `terraform init`؟
12. ماذا يفعل `terraform plan`؟
13. ماذا تعني الرموز `+` و`-` و`~` في الخطة التي يصفها الفصل؟
14. ماذا يفعل `terraform apply`؟
15. كيف يستطيع Terraform اكتشاف الانحراف؟
16. لماذا قد يشغّل فريق Terraform plan في pull request؟
17. ماذا يفعل `terraform destroy`؟
18. لماذا تُعدّ المتغيرات أفضل من تثبيت كل قيمة خاصة ببيئة في الشيفرة؟
19. ما الفرق بين متغير له قيمة افتراضية ومتغير بدونها؟
20. ما الدور الذي يؤديه `terraform.tfvars`؟
21. إلى ماذا يشير `aws_s3_bucket.my_bucket.arn`؟
22. ما الفرق بين متغير الإدخال وقيمة المخرجات؟
23. كيف يرتبط Terraform بدرسي Git وDocker السابقين؟
