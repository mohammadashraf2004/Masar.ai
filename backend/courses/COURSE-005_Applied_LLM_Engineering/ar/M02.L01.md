## 1. النموذج الذهني الأساسي: يجب أن يتحول النص إلى أرقام

ينفذ language model عمليات حسابية رقمية. أما اللغة البشرية فتصل في صورة نص.

وهذا يعني أن النظام يحتاج إلى جسر بين:

```text
لغة قابلة للقراءة البشرية (Human-readable language)
        ↓
أرقام قابلة للقراءة آليًا (Machine-readable numbers)
```

يركز Chapter 2 على جزأين من هذا الجسر:

1. تقسم **Tokens** النص إلى أجزاء يمكن التعامل معها.
2. تمثل **Embeddings** تلك الأجزاء — أو أجزاء أكبر من النص — في صورة vectors رقمية.

أسهل pipeline عالي المستوى يمكن تذكره هو:

```text
النص الخام (Raw text)
   ↓
أداة Tokenizer
   ↓
وحدات Tokens
   ↓
معرّفات Token IDs
   ↓
البحث عن Embedding (Embedding lookup)
   ↓
متجهات Token (Token vectors)
   ↓
نموذج اللغة (Language model)
   ↓
تمثيلات مكيّفة بالسياق / معرّفات Token مولدة
   ↓
يفك Tokenizer ترميز المعرّفات المولدة (Tokenizer decodes generated IDs)
   ↓
نص إخراج قابل للقراءة (Readable output text)
```

يوضح هذا pipeline بالفعل أحد أكثر أوجه سوء الفهم شيوعًا لدى المبتدئين:

> **Token ID ليس Embedding.**

Token ID هو عدد صحيح يشير إلى entry داخل tokenizer vocabulary. أما embedding فهو vector من القيم الرقمية مرتبط بذلك token ويستخدمه Model في العمليات الحسابية.

على سبيل المثال، تخيل vocabulary صغيرة:

```text
ID 10 → "cat" — المعرّف 10 يشير إلى token "cat"
ID 11 → "dog" — المعرّف 11 يشير إلى token "dog"
ID 12 → "runs" — المعرّف 12 يشير إلى token "runs"
```

لا يحتوي العدد الصحيح `10` على معنى “cat.” فهو مجرد identifier.

داخل Model، قد يتم ربط ID `10` بـ vector مثل:

```text
[0.17, -0.52, 0.04, 0.91, ...]
```

هذا vector — وليس integer ID — هو التمثيل الرقمي الذي تستخدمه neural network.

[[IMAGE_NEEDED: Tokens-to-embeddings overview | A left-to-right diagram showing raw text being split into tokens, tokens mapped to integer IDs, IDs mapped to embedding vectors, and vectors passed into a language model | Learner should notice that tokenization and embedding are separate stages and that token IDs are identifiers rather than semantic vectors]]

### لماذا تهم Tokens في الإدخال والإخراج معًا؟

Tokens ليست فقط الطريقة التي يستقبل بها Model الـ prompt.

يقوم generative language model أيضًا بإنتاج إجابته **token واحدة في كل مرة**. وتكون النتيجة المولدة في البداية sequence من token IDs. ثم يحول tokenizer هذه IDs مرة أخرى إلى نص قابل للقراءة البشرية.

لذلك يُستخدم tokenizer في اتجاهين:

```text
الإدخال (INPUT):
text → token IDs → model

الإخراج (OUTPUT):
model-generated token IDs → text
```

لهذا السبب لا تعد tokenization مجرد تفصيلة شكلية في preprocessing. بل هي جزء من interface بين اللغة و Model.

## 2. ما Token بالضبط؟

**Token** هي وحدة يستخدمها tokenizer لتمثيل جزء من text sequence.

قد تكون token:

- كلمة كاملة،
- جزءًا من كلمة،
- حرفًا،
- byte،
- علامة ترقيم،
- أو رمز تحكم خاص.

انظر إلى prompt مشابه لمثال الفصل:

```text
Write an email apologizing to Sarah for the gardening mishap. — نص مصدر يُحلَّل بواسطة Tokenizer
```

قد يقسم subword tokenizer الأجزاء بصورة تقريبية هكذا:

```text
Write — Token كاملة
an — Token كاملة
email — Token كاملة
apolog — جزء Subword
izing — جزء Subword
to — Token كاملة
Sarah — Token كاملة
for — Token كاملة
the — Token كاملة
garden — جزء Subword
ing — جزء Subword
m — جزء Subword
ish — جزء Subword
ap — جزء Subword
. — علامة ترقيم Token
```

يعتمد التقسيم الدقيق على tokenizer.

النقطة المهمة هي أن **حدود tokens لا يلزم أن تطابق حدود الكلمات**.

قد تتحول الكلمة:

```text
apologizing — الكلمة التي يجري تحليلها
```

إلى شيء مثل:

```text
apolog + izing — تقسيم تقريبي إلى Subwords
```

وقد تُقسم كلمة أقل شيوعًا إلى أجزاء أصغر من ذلك.

### لماذا تكون Subwords مفيدة؟

افترض أن vocabulary تحتوي على:

```text
apolog — جزء داخل Vocabulary
ize — جزء داخل Vocabulary
izing — جزء داخل Vocabulary
etic — جزء داخل Vocabulary
ist — جزء داخل Vocabulary
```

عندئذ يستطيع tokenizer إعادة استخدام الأجزاء عبر كلمات متعددة مترابطة بدلًا من تخزين token منفصلة تمامًا لكل صيغة ممكنة من الكلمات.

وهذا يمنح vocabulary قدرة تعبيرية أكبر.

كما يساعد tokenizer على تمثيل كلمات لم يرها كوحدات كاملة أثناء tokenizer training.

### يمكن أن تمتلك Tokens حدودًا غير متوقعة

قد يتوقع المبتدئ أن:

```text
Subject — كلمة ظاهرة قد تبدو Token واحدة
```

تكون دائمًا token واحدة.

لكن tokenizer قد يشفرها هكذا:

```text
Sub + ject — تقسيم محتمل إلى Subwords
```

لا يزال بإمكان Model توليد الكلمة الظاهرة الصحيحة، لأن decoding يعيد ضم أجزاء token.

وهذا يعلمنا قاعدة مهمة:

> **الكلمات التي تراها و model tokens يمثلان مستويين مختلفين من التجريد.**

يفكر الإنسان في الكلمات والجمل. أما Model فيستقبل sequence يحددها tokenizer.

[[IMAGE_NEEDED: Visible text versus token pieces | Show one sentence with colored token boundaries, including at least one full-word token, one split word such as apolog + izing, punctuation as its own token, and a special token | Learner should notice that tokens can be words, subwords, punctuation, or control symbols]]

### معرّفات Token IDs

بمجرد أن يقسم tokenizer النص إلى tokens، يستبدل كل token بـ vocabulary ID الخاص بها.

من الناحية المفاهيمية:

```text
الوحدة (Token)   معرّف Token ID
----------------------
<s>              1
Write        14350
an             385
email         4876
...
```

لا يستقبل Model الـ string الأصلي.

بل يستقبل tensor تحتوي على IDs، على سبيل المثال:

```text
tensor([[1, 14350, 385, 4876, ...]]) — Tensor تحتوي على Token IDs
```

تشير هذه IDs إلى جدول vocabulary الخاص بـ tokenizer.

## 4. لماذا تقسم Tokenizers المختلفة النص نفسه بطرق مختلفة؟

لا توجد tokenization عالمية موحدة لأي جملة.

يمكن لـ Models مختلفين استقبال النص نفسه تمامًا وتحويله إلى token sequences مختلفة.

يحدد الفصل ثلاثة أسباب رئيسية.

### 4.1 طريقة Tokenization

تتعلم tokenization algorithms المختلفة أو تطبق token vocabularies بطرق مختلفة.

تشمل الأساليب التي يناقشها الفصل:

- طريقة **Byte Pair Encoding (BPE)** — ترتبط على نطاق واسع بـ GPT-style tokenizers.
- طريقة **WordPiece** — يستخدمها BERT.
- أداة **SentencePiece** — implementation يمكن أن تدعم أساليب تشمل BPE و unigram language model.

تهدف هذه الأساليب جميعًا إلى تمثيل النص بكفاءة، لكنها لا تبني vocabularies بالطريقة نفسها تمامًا.

### 4.2 إعدادات Tokenizer واختيارات Vocabulary

حتى بعد اختيار algorithm، لا يزال المصمم يتخذ قرارات مثل:

- حجم vocabulary،
- اختيار special tokens،
- طريقة التعامل مع capitalization،
- واختيار domain-specific control tokens.

قد تحتوي vocabulary على عشرات الآلاف تقريبًا من tokens، بينما تستخدم بعض tokenizers الأحدث vocabularies أكبر.

يمكن أن تسمح vocabulary الأكبر بتمثيل strings الشائعة بعدد أقل من tokens، رغم أن تصميم vocabulary يتضمن trade-offs.

### 4.3 بيانات Training الخاصة بـ Tokenizer

تتأثر vocabulary بـ dataset المستخدمة في تدريب tokenizer.

سيتعلم tokenizer تم تدريبه أساسًا على:

```text
نثر باللغة الإنجليزية (English prose)
```

أجزاء مفيدة مختلفة عن tokenizer تم تدريبه بكثافة على:

```text
شيفرة مصدرية (source code)
```

أو:

```text
نص متعدد اللغات (multilingual text)
```

ويعطينا ذلك قاعدة مختصرة:

```text
سلوك Tokenizer (Tokenizer behavior)
    =
طريقة Tokenization (tokenization method)
    +
اختيارات الإعداد (configuration choices)
    +
مجال بيانات Training (training-data domain)
```

هذه واحدة من أهم الأفكار في الفصل.

## 5. أربع طرق مفيدة للتفكير في Tokenization

يسلط الفصل الضوء على أربعة مستويات عامة لـ tokenization.

### 5.1 استخدام Word tokens

يحاول word tokenizer تمثيل النص باستخدام كلمات كاملة.

مثال:

```text
machine learning works — نص الإدخال

→ ["machine", "learning", "works"] — تقسيم إلى Word tokens
```

يبدو ذلك طبيعيًا للبشر.

لكنه يخلق مشكلات.

ستحتاج vocabulary إلى احتواء صور عديدة:

```text
apology — صيغة كلمة
apologize — صيغة كلمة
apologetic — صيغة كلمة
apologist — صيغة كلمة
apologizing — صيغة كلمة
...
```

وعندما تظهر كلمة جديدة غير موجودة في vocabulary، فقد لا يمتلك tokenizer تمثيلًا جيدًا لها.

كانت word-level tokenization مهمة تاريخيًا، بما في ذلك في أساليب مثل word2vec، ويمكن أن تكون الفكرة نفسها مفيدة خارج اللغة عند التعامل مع عناصر مثل الأغاني بوصفها tokens.

### 5.2 استخدام Subword tokens

تمزج subword tokenization بين الكلمات الكاملة وأجزاء الكلمات.

مثال:

```text
apologizing — الكلمة الكاملة

→ apolog + izing — تقسيم إلى Subwords
```

يمنح ذلك tokenizer ميزتين:

1. يمكن أن تبقى الكلمات الشائعة ممثلة بصورة مدمجة.
2. يمكن غالبًا بناء الكلمات الجديدة أو النادرة من أجزاء أصغر معروفة.

هذا التوازن هو سبب شيوع subword tokenization في language models الحديثة.

### 5.3 استخدام Character tokens

قد يشفر نظام على مستوى character:

```text
play — الكلمة الكاملة

→ p + l + a + y — تقسيم إلى Characters
```

يمكن لذلك تمثيل كلمات جديدة لأن الحروف نفسها متاحة.

لكن sequences تصبح أطول.

قد يمثل subword model كلمة `play` باستخدام token واحدة، بينما يحتاج character model إلى أربع.

ومع سعة context ثابتة، تعني token sequences الأطول أن مقدارًا أقل من النص يمكن وضعه في Model دفعة واحدة.

### 5.4 استخدام Byte tokens

هناك أسلوب آخر يمثل النص على مستوى byte.

قد يكون ذلك مفيدًا بصورة خاصة لتغطية نطاق واسع من الحروف وفي البيئات متعددة اللغات.

ويشير الفصل أيضًا إلى نقطة دقيقة مهمة:

> قد يحتوي subword tokenizer على byte tokens كآلية fallback دون أن يكون Model يعمل بالكامل على مستوى byte أو يكون “tokenization-free”.

لذلك لا تصنف tokenizer على أنه byte-level لمجرد وجود bytes في جزء من vocabulary الخاصة به.

[[IMAGE_NEEDED: Word vs subword vs character vs byte tokenization | Use the same short input and show four parallel rows demonstrating how it would be segmented as whole words, subwords, individual characters, and bytes | Learner should compare sequence length, vocabulary flexibility, and the ability to handle unseen text]]

### مقارنة عملية

| الأسلوب | الفكرة الأساسية | نقطة القوة | التكلفة / القيد |
|---|---|---|---|
| أسلوب Word | token واحدة لكل كلمة معروفة | وحدات قابلة للقراءة البشرية | Vocabulary ضخمة/مفتوحة ومشكلات الكلمات غير المرئية |
| أسلوب Subword | إعادة استخدام أجزاء مفيدة | توازن جيد بين الاختصار والتغطية | قد تبدو الحدود غير بديهية |
| أسلوب Character | حرف واحد لكل token | يستطيع تمثيل الكلمات غير المرئية | Sequences طويلة |
| أسلوب Byte | العمل انطلاقًا من byte representations | تغطية واسعة للرموز/اللغات | قد ينتج sequences على مستوى أدنى |

لا يتمثل هدف الفصل في إخبارك بأن طريقة واحدة هي الأفضل دائمًا.

بل الهدف هو مساعدتك على رؤية tokenization بوصفها **اختيارًا هندسيًا يغير ما يراه Model**.

## 6. استخدام Special tokens: عناصر Vocabulary تتحكم في البنية

لا تمثل كل token نصًا عاديًا ظاهرًا.

غالبًا ما تحتوي tokenizers على **special tokens** تحمل معاني بنيوية أو خاصة بالمهمة.

تشمل أمثلة الفصل:

### رموز بداية النص (Beginning-of-text tokens)

```text
<s>
```

يمكن أن تشير هذه الرموز إلى بداية input sequence.

### رموز نهاية النص (End-of-text tokens)

يمكن لـ end token الإشارة إلى وجوب توقف generation.

### رموز Padding

```text
[PAD]
```

يستخدم Padding عندما تحتاج inputs إلى المحاذاة إلى طول مشترك.

### رموز Unknown

```text
[UNK]
```

تمثل هذه الرموز نصًا لا يستطيع tokenizer تمثيله باستخدام vocabulary العادية.

### رمز Classification

يستخدم BERT عادةً:

```text
[CLS]
```

يمكن لـ Model استخدام هذا الموضع الخاص بوصفه representation لمهام موجهة نحو classification.

### رمز Separator

يستخدم BERT أيضًا:

```text
[SEP]
```

يمكن لذلك الفصل بين أجزاء النص، مثل query و candidate document في مهمة paired-input.

### رمز Mask

```text
[MASK]
```

يستخدم هذا في BERT-style masked language modeling.

### رموز أدوار Chat

تتضمن مناقشة Phi-3 في الفصل tokens موجهة للأدوار مثل:

```text
<|user|> — رمز دور المستخدم
<|assistant|> — رمز دور المساعد
<|system|> — رمز دور النظام
```

تعكس هذه الرموز أهمية conversational interaction في chat models.

### رموز Domain-specific الخاصة

يمكن لـ Models المتخصصة الذهاب إلى أبعد من ذلك.

قد يستخدم code model tokens مرتبطة بـ:

```text
اسم الملف (filename)
اسم المستودع (repository name)
توليد Fill-in-the-middle
```

وقد يحتوي scientific model على بُنى مخصصة لـ:

```text
الاستشهادات (citations)
الرياضيات (mathematics)
علامات الاستدلال (reasoning markers)
التسلسلات الحيوية (biological sequences)
```

ويمنحنا ذلك فكرة مفيدة:

> **يمكن لـ vocabulary ترميز افتراضات حول المهام المتوقع من Model تنفيذها.**

لذلك ترتبط tokenization بتخصص Model.

## 7. ما الذي تعلمنا إياه مقارنات Tokenizer الحقيقية؟

يقارن الفصل عدة tokenizers مدربة باستخدام نص يحتوي على:

- اختلافات capitalization،
- نص غير إنجليزي،
- رموز emoji،
- syntax شبيه بـ code،
- indentation و whitespace،
- أرقام،
- ورموز خاصة.

ليس الهدف من المقارنة حفظ المخرجات الدقيقة لكل tokenizer.

بل الهدف الحقيقي هو تعلم **ما الذي ينبغي فحصه**.

### 7.1 نموذج BERT uncased: يمكن أن تختفي معلومات عن قصد

يزيل BERT tokenizer من نوع uncased فروق capitalization.

لذلك:

```text
English — نص بحالة أحرف عادية
CAPITALIZATION — نص بأحرف كبيرة
```

تتم عملية normalization له باتجاه سلوك lowercase.

كما يوضح الفصل أن بعض الرموز غير المدعومة قد تتحول إلى:

```text
[UNK]
```

وهذا يعني أن معلومات قد تُفقد قبل أن يبدأ Model أي عملية حسابية.

وهذا درس رئيسي:

> إذا لم يتمكن tokenizer من الحفاظ على المعلومات، فلن يستطيع Model استعادة تلك المعلومات لاحقًا من token sequence.

### 7.2 نموذج BERT cased: الحفاظ على Case قد يزيد تجزئة Tokens

يحافظ BERT tokenizer من نوع cased على uppercase text، لكن الكلمة المكتوبة كلها بأحرف كبيرة قد تُقسم إلى أجزاء أكثر.

على سبيل المثال، يوضح الفصل أن كلمة مكتوبة بحروف كبيرة قد تتطلب tokens أكثر بكثير مقارنة ببعض tokenizers الأحدث.

يوضح ذلك trade-off:

```text
الحفاظ على المعلومات (preserve information)
        versus
تمثيلها بصورة مدمجة (represent it compactly)
```

### 7.3 نموذج GPT-2: Newlines وآلية Byte fallback

توضح مقارنة GPT-2 في الفصل قدرة أفضل على الحفاظ على line breaks وإعادة بناء مجموعة واسعة من الحروف من خلال سلوك fallback موجه نحو byte.

وهذا مفيد لأن formatting نفسه قد يحمل معنى.

### 7.4 أدوات Tokenizer الموجهة لـ Code تهتم بـ Whitespace

تكون whitespace ذات معنى مهم بصورة خاصة في لغات مثل Python.

انظر إلى:

⟦CODE_8⟧

تخبر indentation لغة Python أي statement تنتمي إلى block الخاص بـ `if`.

يجعل tokenizer الذي يمثل أنماط indentation الشائعة بكفاءة sequence أسهل على code model في التعامل معها.

ويشير الفصل إلى أن tokenizers الأحدث أو الموجهة لـ code قد تتضمن تمثيلات مدمجة لتتابعات spaces.

### 7.5 أدوات Tokenizer المتخصصة ترمز بنية Domain

يحتوي StarCoder2 على tokens مرتبطة بـ code repositories و files.

وتحتوي Galactica على بُنى خاصة مرتبطة بالمحتوى العلمي.

وهذا يوضح المبدأ الأوسع:

```text
بيانات خاصة بمجال (Domain-specific data)
        ↓
اختيارات Tokenizer مدركة للمجال (Domain-aware tokenizer choices)
        ↓
إمكان تسهيل Modeling لذلك المجال (Potentially easier modeling of that domain)
```

### 7.6 يمكن أن تختلف Tokenization للأرقام

يوضح الفصل أيضًا أن بعض tokenizers تقسم الأرقام إلى digits، بينما قد تتعامل أخرى مع مجموعات أكبر من digits بوصفها tokens منفردة.

لذلك:

```text
600
```

قد يكون:

```text
["600"]
```

أو:

```text
["6", "0", "0"]
```

اعتمادًا على tokenizer.

لا تحتاج إلى افتراض أن إحدى الاستراتيجيتين أفضل دائمًا.

المهم هنا هو إدراك أن **tokenization تغير الوحدات الأساسية التي يجب أن يتعلم Model الاستدلال عليها**.

[[IMAGE_NEEDED: Comparison of real tokenizer behavior | A compact comparison graphic using one mixed input with English capitalization, emoji/non-English text, code indentation, and numbers, showing that BERT-like, GPT-like, and code-focused tokenizers preserve and split information differently | Learner should notice that tokenizer choices affect case, unknown symbols, whitespace, number segmentation, and sequence length]]

### أسئلة تشخيصية عملية

عند تقييم tokenizer لمهمة معينة، اسأل:

1. هل يحافظ على اللغات التي تهمني؟
2. هل يحافظ على capitalization عندما تكون مهمة؟
3. كيف يتعامل مع whitespace و newlines؟
4. كم token تحتاج إليها domain vocabulary؟
5. هل يمثل code بكفاءة؟
6. ما special tokens التي يوفرها؟
7. كيف يتعامل مع الرموز النادرة أو غير المرئية سابقًا؟
8. ما مقدار context window الذي ستستهلكه inputs المعتادة؟

هذه الأسئلة أكثر فائدة من مجرد السؤال: “أي tokenizer هو الأفضل؟”

## 8. من Token IDs إلى Token embeddings

تحل tokenization الجزء الأول فقط من مشكلة representation.

بعد tokenization، يمتلك Model شيئًا مثل:

```text
[1, 14350, 385, 4876, ...]
```

هذه integer identifiers.

تحتاج neural networks إلى representations رقمية أكثر ثراءً.

وهنا يأتي دور **embedding matrix**.

### 8.1 Vector واحد لكل Vocabulary token

يخزن pretrained language model embedding vector مرتبطًا بكل vocabulary token.

من الناحية المفاهيمية:

```text
Vocabulary الخاصة بـ Tokenizer
-------------------------------
ID 0   token A
ID 1   token B
ID 2   token C
...
ID N   token N

مصفوفة Embedding (Embedding matrix)
------------------------------------------
ID 0 → [ ... embedding values ... ]
ID 1 → [ ... embedding values ... ]
ID 2 → [ ... embedding values ... ]
...
ID N → [ ... embedding values ... ]
```

إذا كانت vocabulary تحتوي على `V` من tokens وكان لكل embedding عدد `D` من الأبعاد، فيمكن تصور embedding table على أنها matrix:

```text
V × D
```

عندما يستقبل Model token ID بقيمة `i`، فإنه يسترجع embedding vector الموجود في الصف `i`.

[[IMAGE_NEEDED: Vocabulary embedding matrix | Show a tokenizer vocabulary column with token IDs pointing to rows in a matrix where each row contains a dense vector | Learner should notice that every vocabulary token has a learned vector and that the token ID acts as the lookup key]]

### 8.2 يجب أن يتفق Tokenizer و Model

يؤكد الفصل أن pretrained language model مرتبط بـ tokenizer الخاص به.

لماذا؟

تخيل أن tokenizer A يقول:

```text
ID 420 = "cat" — Mapping في Tokenizer A
```

لكن tokenizer B يقول:

```text
ID 420 = "database" — Mapping في Tokenizer B
```

إذا تم تدريب Model على افتراض tokenizer A، فإن تمرير IDs أنشأها tokenizer B سيجعل تلك الأرقام تشير إلى learned vectors غير الصحيحة.

لذلك لا يكون tokenizer مجرد text splitter يمكن تبديله بحرية بعد Model training.

يحمل mapping معنى لأن Model تعلم parameters باستخدام هذا mapping.

### 8.3 تبدأ Embeddings عشوائية ثم يشكلها Training

قبل training، يمكن أن تبدأ embedding vectors في صورة قيم رقمية عشوائية.

أثناء training، يحدّث Model parameters الخاصة به — بما في ذلك embeddings — حتى تصبح مفيدة للمهمة التي يتم تعلمها.

التحول المهم هو:

```text
متجهات عشوائية (random vectors)
     ↓
Training على أمثلة كثيرة
     ↓
متجهات مفيدة لنمذجة أنماط اللغة (vectors useful for modeling language patterns)
```

تكون القيم النهائية متعلمة، ولا تُسند إليها semantic labels يدويًا.

## 9. مقارنة Static embeddings و Contextualized embeddings

يربط raw vocabulary embedding كل token بـ initial learned vector.

لكن اللغة تعتمد على context.

انظر إلى الكلمة:

```text
bank — كلمة متعددة المعاني
```

قارن بين:

```text
I deposited money at the bank.   — كلمة bank هنا بمعنى مصرف
```

و:

```text
We sat on the bank of the river.   — كلمة bank هنا بمعنى ضفة
```

الكلمة الظاهرة هي نفسها.

لكن دورها ومعناها مختلفان.

يعالج language model الـ token مع surrounding sequence وينتج **contextualized token representations**.

لذلك يكون النموذج الذهني المفيد:

```text
تمثيل Token خام (raw token embedding)
        +
السياق المحيط الذي عالجه Model (surrounding context processed by the model)
        ↓
تمثيل Token مكيّف بالسياق (contextualized token embedding)
```

يمكن أن يختلف representation الناتج لـ token نفسها اعتمادًا على الجملة التي توجد فيها.

وهذا تحسين رئيسي مقارنة بـ static word representations فقط.

[[IMAGE_NEEDED: Static versus contextual token embedding | Show the word “bank” appearing in a financial sentence and a river sentence; start from the same token-level lookup concept and end with two different contextual vectors | Learner should notice that the language model changes a token's representation according to surrounding context]]

### لماذا تهم Contextual token embeddings؟

يربط الفصل هذه representations بمهام مثل:

- مهمة named-entity recognition،
- مهمة extractive text summarization،
- مهمة text classification،
- وأنظمة أخرى تحتاج إلى token-level understanding.

كما تمثل contextual representations جسرًا مهمًا نحو فهم طريقة عمل Transformer models الحديثة داخليًا.

## 11. استخدام Text embeddings: Vector واحد لجملة أو مستند

تمثل token embeddings مواضع token الفردية.

تحتاج تطبيقات كثيرة إلى تمثيل **نص كامل** باستخدام vector واحد.

تشمل الأمثلة:

- جملة كاملة،
- فقرة،
- تذكرة دعم،
- مستندًا،
- و search query.

يمكن تصور text embedding model هكذا:

```text
النص (Text)
  ↓
نموذج Embedding
  ↓
متجه كثيف واحد يمثل النص (One dense vector representing the text)
```

على سبيل المثال:

```text
"Best movie ever!" — نص مصدر يتم تحويله إلى Embedding
```

قد يتحول إلى vector يحتوي على مئات الأبعاد الرقمية.

لا يُقصد قراءة القيم نفسها يدويًا.

بل تأتي فائدتها من العلاقات بين vectors.

### لماذا يكون Vector واحد مفيدًا؟

إذا حصلت أجزاء النص المتشابهة دلاليًا على vectors متقاربة، يمكننا بناء أنظمة تقارن المعنى بدلًا من الكلمات المتطابقة حرفيًا.

على سبيل المثال:

```text
الاستعلام (Query):
"How do I reset my password?"

المستند A (Document A):
"Steps for changing a forgotten password"

المستند B (Document B):
"How to choose a payment method"
```

ينبغي لـ embedding model جيد أن يضع query أقرب إلى document A داخل embedding space لأن المعنيين مرتبطان.

هذا هو أساس semantic retrieval.

يربط الفصل لاحقًا text embeddings بـ:

- مهام categorization،
- تطبيقات semantic search،
- تطبيقات موجهة نحو topics،
- وأنظمة RAG.

[[IMAGE_NEEDED: Sentence-to-vector embedding | Show a complete sentence entering a text embedding model and emerging as one vector, followed by three example application branches: semantic search, categorization, and RAG retrieval | Learner should notice the difference between many per-token vectors and one vector representing a whole text]]

يستخدم الفصل `sentence-transformers`:

⟦CODE_14⟧

افحص shape:

⟦CODE_15⟧


```text

→ متجه واحد (one vector)
→ 768 قيمة رقمية
```

لا تخلط بين ذلك وبين output السابق من DeBERTa:

```text

```

احتوى output السابق على vector واحد **لكل token position**.

```text

```

فهو vector واحد للنص الكامل.

### مقارنة Token embedding و Text embedding

| التمثيل | ما الذي يمثله | التصور المعتاد لـ Shape |

## 13. كيف يتعلم Word2vec متجهات مفيدة؟

يستخدم الفصل word2vec لتقديم learning pattern مهم سيظهر مرة أخرى لاحقًا.

السؤال الرئيسي هو:

> كيف يمكننا تدريب vectors بحيث تصبح الكلمات التي تظهر في contexts متشابهة مرتبطة بصورة مفيدة؟

### 13.1 بناء أمثلة من Sliding window

افترض أن لدينا sequence من الكلمات:

```text
Thou shalt not make a machine in the likeness of a human mind — نص مصدر يُستخدم لبناء أمثلة Word2vec
```

اختر center word وانظر إلى الكلمات القريبة منها داخل window.

إذا كانت window تشمل كلمتين مجاورتين في كل جانب، فيمكن إقران center word بعدة كلمات قريبة.

تصبح هذه **positive examples**.

من الناحية المفاهيمية:

```text
(center word, nearby word) → related / positive — زوج Training إيجابي
```

[[IMAGE_NEEDED: Word2vec sliding window | Show a short sentence with one center word highlighted and two neighboring words on each side inside a sliding window; draw positive training pairs from the center to each neighbor | Learner should notice how ordinary running text is converted into many word-pair training examples]]

### 13.2 لماذا لا تكفي Positive examples وحدها؟

تخيل أن كل training target كانت:

```text
1 = these two words are neighbors — Label لمثال إيجابي
```

يمكن لـ Model غير مفيد أن يتنبأ دائمًا بـ:

```text
1
```

ويبدو وكأنه صحيح.

لذلك يحتاج training أيضًا إلى أمثلة لا يُتوقع فيها أن يمثل pair علاقة تجاور طبيعية.

وهذه هي **negative examples**.

من الناحية المفاهيمية:

```text
(real neighbor pair)   → 1 — مثال إيجابي
(random/non-neighbor)  → 0 — مثال سلبي
```

يمنح ذلك Model شيئًا ذا معنى ليتعلم التمييز بينه.

### 13.3 أسلوب Skip-gram وتقنية Negative sampling

يؤكد الفصل فكرتين:

**أسلوب Skip-gram**

استخدم center word لتوقع العلاقات مع الكلمات المحيطة أو تعلمها.

**تقنية Negative sampling**

أضف sampled non-neighbor examples حتى يتعلم Model التمييز بين العلاقات السياقية الحقيقية و unrelated pairs.

قد تبدو training set مبسطة هكذا:

```text
(machine, make)     → 1 — زوج إيجابي (Positive pair)
(machine, in)       → 1 — زوج إيجابي (Positive pair)
(machine, likeness) → 1 — زوج إيجابي (Positive pair)

(machine, banana)   → 0 — زوج سلبي (Negative pair)
(machine, ocean)    → 0 — زوج سلبي (Negative pair)
(machine, violin)   → 0 — زوج سلبي (Negative pair)
```

تعتمد الأمثلة الدقيقة على dataset و sampling.

[[IMAGE_NEEDED: Positive and negative word2vec pairs | Two groups of word pairs: genuine context neighbors labeled 1 and sampled unrelated pairs labeled 0, feeding a small neural network | Learner should notice that embeddings improve because the model learns to separate observed contextual relationships from negative samples]]

### 13.4 تهيئة Embedding matrix

كما هي الحال مع language model vocabulary، تحصل كل كلمة على vector.

في البداية:

```text
word → random vector — التهيئة الأولية لـ Embedding
```

ثم يعدل training هذه vectors بصورة متكررة.

إذا شاركت كلمتان في contextual patterns متشابهة، يمكن لعملية learning تحريك representations الخاصة بهما إلى مواضع نسبية مفيدة.

### 13.5 الناتج الحقيقي هو Embedding space المتعلم

تمثل classification task آلية training.

لكن ما يهمنا في النهاية هو vector representation الذي تم تعلمه خلال هذه العملية.

بعد training:

```text
word → useful learned vector — Embedding متعلم ومفيد
```

يمكن استخدام هذه vectors في similarity calculations والتطبيقات اللاحقة.

### الفكرة الأوسع

يستخدم الفصل word2vec لإعدادك لمفهوم أكثر عمومية بكثير:

> تعلم representations من خلال تدريب Model على التمييز بين related pairs و unrelated pairs.

يظهر هذا pattern مرة أخرى في contrastive learning و cross-modal systems.

## 14. استخدام Embeddings خارج الكلمات: نظام Recommendation للأغاني

أحد أهم دروس الفصل هو أن embeddings **ليست مقتصرة على اللغة**.

إذا استطعت التعبير عن البيانات في صورة sequences أو relationships ذات معنى، يمكنك غالبًا تعلم embeddings لعناصر أخرى.

## 15. جمع Tokens و Embeddings معًا

أصبحت لديك الآن قطع كافية لتتبع input في language model حديث من البداية إلى النهاية.

انظر إلى:

```text
"Hello world" — نص الإدخال
```

### المرحلة 1 — تنفيذ Tokenization

قد ينتج tokenizer:

```text
[CLS] — Special token
Hello — Token من النص
world — Token من النص
[SEP] — Special token
```

### المرحلة 2 — تحويل Tokens إلى IDs

من الناحية المفاهيمية:

```text
[101, 7592, 2088, 102]
```

تعتمد IDs الدقيقة على tokenizer.

### المرحلة 3 — تنفيذ Embedding lookup

تحدد كل ID صفًا متعلمًا داخل embedding matrix:

```text
101  → vector A — Embedding للمعرّف 101
7592 → vector B — Embedding للمعرّف 7592
2088 → vector C — Embedding للمعرّف 2088
102  → vector D — Embedding للمعرّف 102
```

### المرحلة 4 — تنفيذ Contextual processing

تعالج Transformer layers هذه vectors معًا.

يحتوي output على contextualized representations:

```text
contextual([CLS]) — تمثيل مكيّف بالسياق
contextual(Hello) — تمثيل مكيّف بالسياق
contextual(world) — تمثيل مكيّف بالسياق
contextual([SEP]) — تمثيل مكيّف بالسياق
```

### المرحلة 5 — استخدام Output في مهمة

اعتمادًا على Model والتطبيق، يمكن لهذه representations دعم:

- مهمة classification،
- مهمة named-entity recognition،
- مهمة extraction،
- عملية retrieval،
- عملية semantic comparison،
- أو مهام لاحقة أخرى.

يستخدم generative model تمثيلاته للتنبؤ بـ next token ثم متابعة sequence مرارًا.

### مخطط نهائي مختصر

```text
النص (TEXT)
"Hello world"
    ↓
أداة TOKENIZER
["[CLS]", "Hello", "world", "[SEP]"]
    ↓
معرّفات TOKEN IDS
[101, 7592, 2088, 102]
    ↓
عملية EMBEDDING LOOKUP
4 متجهات خام (raw vectors)
    ↓
بنية TRANSFORMER / نموذج LANGUAGE MODEL
4 متجهات مكيّفة بالسياق (contextualized vectors)
    ↓
استخدام خاص بالمهمة (TASK-SPECIFIC USE)
classification / extraction / generation / etc. — أمثلة على المهام
```

بالنسبة إلى sentence embedding systems، تعطي عملية إضافية في النهاية:

```text
النص الكامل (whole text)
    ↓
متجه دلالي واحد (one semantic vector)
```

يمكن فهرسة هذا vector ومقارنته لاستخدامه في تطبيقات مثل semantic search.

## مفاهيم خاطئة مهمة

### المفهوم الخاطئ 1

> Token هي الشيء نفسه الذي يسمى كلمة.

### لماذا هذا خطأ؟

يمكن أن تكون token كلمة أو subword أو character أو byte أو علامة ترقيم أو special token.

افحص tokenizer دائمًا بدلًا من افتراض حدود الكلمات.

---

### المفهوم الخاطئ 2

> Token ID يحتوي على معنى دلالي.

### لماذا هذا خطأ؟

Token ID هو index داخل vocabulary.

أما learned embedding vector فهو التمثيل الرقمي الأكثر ثراءً الذي يستخدمه Model.

لن يؤدي تغيير arbitrary integer label الخاص بـ token في حد ذاته إلى إنشاء علاقة دلالية جديدة. ما يهم هو كيفية ربط Model لذلك index بـ learned parameters.

---

### المفهوم الخاطئ 3

> يمكن استخدام أي Tokenizer مع أي Pretrained model.

### لماذا هذا خطأ؟

تم تدريب Model باستخدام mapping محدد بين token IDs و vocabulary entries.

يمكن أن يؤدي استبدال tokenizer إلى تغيير معنى كل input ID بالنسبة إلى Model.

---

### المفهوم الخاطئ 4

> تمثل Embeddings الكلمة دائمًا بالطريقة نفسها.

### لماذا هذا خطأ؟

تربط static word embeddings vector واحدة بكلمة/token، لكن language models تستطيع إنشاء contextualized token embeddings تعتمد قيمها على surrounding sequence.

---

### المفهوم الخاطئ 5

> Text embedding هو مجرد Token ID لجملة.

### لماذا هذا خطأ؟

Text embedding هو dense learned vector يمثل جزءًا أكبر من النص.

وهو ليس identifier.

---

### المفهوم الخاطئ 6

> Tokenization مجرد تفصيلة في Implementation ولا تؤثر في سلوك Model.

### لماذا هذا خطأ؟

تؤثر tokenization في sequence length والحفاظ على capitalization و whitespace والتغطية متعددة اللغات وتمثيل code والأرقام و special control structures ومقدار المعلومات الذي يمكن وضعه داخل context محدود.

## المصطلحات الأساسية

| المصطلح | المعنى |
|---|---|
| مصطلح Token | وحدة يحددها tokenizer، مثل كلمة أو subword أو character أو byte أو علامة ترقيم أو رمز خاص |
| أداة Tokenizer | مكون يحول النص إلى token IDs ويفك token IDs مرة أخرى إلى نص |
| مصطلح Vocabulary | مجموعة tokens المعروفة لدى tokenizer و IDs الخاصة بها |
| مصطلح Token ID | integer identifier لـ token داخل vocabulary |
| أسلوب BPE | طريقة subword tokenization شائعة |
| أسلوب WordPiece | طريقة tokenization مرتبطة بـ BERT |
| أداة SentencePiece | tokenizer implementation تدعم أساليب تشمل BPE و unigram language modeling |
| مصطلح Special token | Token لها دور بنيوي/خاص بالمهمة بدلًا من معنى نصي عادي |
| الرمز `[UNK]` | Unknown token يُستخدم عندما لا يمكن تمثيل النص من خلال vocabulary العادية |
| الرمز `[CLS]` | Special token موجهة نحو classification في BERT-style models |
| الرمز `[SEP]` | Separator special token تُستخدم للفصل بين أجزاء input |
| الرمز `[MASK]` | Token تُستخدم في masked language modeling |
| مصطلح Embedding | Dense numerical vector يُستخدم لتمثيل عنصر |
| مصطلح Embedding matrix | جدول يحتوي على learned vectors لعناصر vocabulary |
| مصطلح Static embedding | Learned representation واحدة مرتبطة بـ token/word بصورة مستقلة عن الجملة الحالية |
| مصطلح Contextualized embedding | Representation لـ token بعد أن يعالج language model السياق المحيط بها |
| مصطلح Text embedding | Vector واحدة تمثل جملة أو فقرة أو مستندًا |
| مصطلح Embedding dimension | عدد القيم الرقمية في embedding vector |
| أسلوب Skip-gram | أسلوب Word2vec قائم على تعلم العلاقات بين center word والكلمات القريبة |
| تقنية Negative sampling | Training technique تضيف sampled non-neighbor examples |
| مصطلح Semantic similarity | تشابه قائم على المعنى أو أنماط الاستخدام بدلًا من exact string equality |
| مصطلح Recommendation embedding | Vector representation لعنصر تم تعلمها من علاقات سلوكية/سياقية |

## اختبار ذاتي

قبل المتابعة، تأكد من أنك تستطيع الإجابة عن الأسئلة الآتية دون الرجوع إلى ما سبق:

1. لماذا يحتاج LLM إلى tokenizer؟
2. ما الفرق بين token و token ID؟
3. لماذا لا يعد token ID هو embedding؟
4. ما الميزة التي تقدمها subword tokenization مقارنة بـ pure word tokenization؟
5. لماذا يمكن أن تستهلك character tokenization مساحة context window بسرعة أكبر؟
6. ما العوامل العامة الثلاثة التي تحدد سلوك tokenizer؟
7. لماذا يمكن أن تهم whitespace tokenization في code؟
8. ما special token؟ أعط ثلاثة أمثلة.
9. لماذا ينبغي لـ pretrained model عادةً استخدام tokenizer المرتبط به؟
10. ما shape الذي تتوقعه من Model ينتج vector واحدة لكل token؟
11. كيف يختلف text embedding عن contextual token embedding؟
12. ما الذي يضيفه skip-gram و negative sampling إلى word2vec؟
13. كيف يمكن التعامل مع playlists مثل الجمل لتعلم song embeddings؟
14. لماذا يمكن لـ nearest-neighbor search على embeddings دعم recommendations؟
15. تتبع المسار الكامل من raw text إلى contextualized token vectors.

## احتفظ بهذه الفكرة

**لا يعمل LLM مباشرةً على الجملة التي تراها على الشاشة. يحدد tokenizer أولًا الوحدات الخاصة بـ Model ويربطها بـ IDs؛ ثم يحول Model هذه IDs إلى learned vectors ويغيرها وفقًا لـ context. إن فهم هذا الفصل بين text و tokens و IDs و embeddings و contextual representations هو أساس لفهم كل ما يأتي بعد ذلك في language models الحديثة.**
